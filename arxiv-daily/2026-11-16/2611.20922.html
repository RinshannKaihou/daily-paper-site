Experience rot/ Agent memory/ Negative result

After a silent tool change, agents with stale experience do worse than novices: 23% vs 63% success.

Why it matters

An agent's memory of what worked becomes a liability once an API changes silently. Memory must detect that a remembered call no longer holds.

Applies to MCP servers, SDK upgrades, schema migrations.

Critical edge

The 23% vs 63% headline sits in the one block the authors did not preregister — and the novice arm there wins about half the time by luck on defaults.

Critical Assessment · rigor

01Protocol

Hold the memory fixed. Move the world.

An episode pairs one earlier task — run live, retried up to ten times and discarded unless the stored state matched — with a final task of the same kind, delivered as the next message in the same conversation. Only the version that produced the experience is flipped.

earlier task · vA ✓→ silent swap→ final task · vB→ reuse own call
noneno earlier task at all
validearlier and final task on the same version
staleearlier task on the other version

Three services (calendar, task list, mail) · six models · every change run in both directions · identical task instances across arms.

04Mechanism

They remember correctly. They stop checking.

95–100%of first writes get the task content right — the facts are not misremembered.
70–100% / ≤6%lookup before writing — novices / experienced agents.
24–25%of experienced runs cite the earlier task — as often when it is stale as when it is valid.
read-back after write94 / 97 recovered
no read-back183 / 184 failed

Only 6% of experienced runs plan a doc lookup, against 69% of novices. And 347 of 348 complete-doc failures still told the user the task was done; under incomplete docs, 405 / 438 (92%).

Qwen reads back after every write and never rots; MiniMax recovers in 5% of runs. Under incomplete docs, MiniMax, DeepSeek and Muse fall to 0.01–0.02 while Qwen holds 0.93 — the gap looks like a policy, not a capability limit.

08Strengths

What the design earns

  • Flips only the version behind the experience; identical task instances and both change directions make the comparison causal, not correlational.
  • The mechanism is triangulated three ways: lookup rates, reasoning-text references, and the read-back path analysis (183/184 vs 94/97).
  • Six models × six changes × four memory forms × four experience amounts × seven remedies, with the effect pointing the same way everywhere.
  • Preregistered with hashed code; all 20 directional contrasts held, and the two unpredicted ones are reported honestly.
  • The hand-written-history result prices benchmark inflation: 0.11 measured versus 0.54 real, roughly 5×.
09Limits

Where it stops

  • Synthetic, single-detail services; real migrations bundle renames, semantic flips and partial error behaviour.
  • The headline incomplete-docs block was not preregistered, and its novice arm is partly a lottery on defaults.
  • All six models run the same minimal ≤16-call loop; no planner, verifier or retrieval baseline is tested.
  • Rejecting unknown fields — the obvious engineering fix — is untested, and remedies only cover conversation memory.
  • Exclusions concentrate on the weekday change (124 of 127); completion and lookup are keyword regexes. No code or data released.
10Open questions

What to test next

  1. Would rejecting unknown fields turn silent rot into a visible error — and at what compatibility cost?
  2. Does the effect persist in frontier reasoning models, or is Qwen's read-back policy proof it can be trained away?
  3. What happens when one migration bundles several changes, some of them producing partial errors?
  4. Can memory carry version metadata that agents actually act on, when a tag in the memory file only moved cost 0.27 → 0.20?
  5. Are published memory-robustness numbers inflated ~5× by hand-written histories? The 0.11 vs 0.54 gap says test it.
