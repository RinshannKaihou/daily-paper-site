Key metric

15,726MOps/s

Float64x4 addition on an A100 (N=10M) — 1.5× CAMPARY (10,468 MOps/s), the number the abstract leads with.

Same table: Julia MultiFloats.jl does 16,581 MOps/s. The 1.5× is against the slowest baseline.

Why this matters

Extended precision normally means rewriting kernels per vendor. Here one source keeps cross-backend ULP error and throughput measurable in a single benchmark suite.

Relevance to precision/determinism work: the study pairs 0-ULP error-free transformations with division, square root and transcendental error bounds, and documents compiler codegen that silently corrupts low limbs.

Critical edge

On the one metric the abstract advertises, the library does not beat the state of the art — it beats the slowest competitor. The 4.2–6.6× CPU win stacks SIMD-vs-scalar on top of GCC-vs-Clang codegen.

Source: Critical Assessment, “headline comparison is not against the strongest baseline”.

01Methodology

N IEEE limbs→ two_sum (Knuth)→ FMA two_prod→ renormalize→ Newton–Raphson→ Kokkos backend
  • Representation. A value is an unevaluated sum of N IEEE doubles: Float64x2 ≈ 106 bits through Float64x4 ≈ 212 bits. Fixed-size aggregate, no allocation, no runtime polymorphism.
  • Error-free primitives. Knuth's two_sum plus a two_prod whose residual is fma(a,b,−prod) rather than Dekker splitting — so −ffp-contract=fast stays legal, which CAMPARY must disable.
  • Renormalization. A fixed sweep count after each operation; five at Float64x4, chosen to cap GPU register pressure “without affecting the observed ULP error”.
  • Division / sqrt. Newton–Raphson over the multi-limb primitives. Default Float64x4 sqrt refines 1→2→4 limbs, skipping the three-limb stage; sqrt_accurate adds it at ~2× cost.
  • Portability. Operators are KOKKOS_INLINE_FUNCTION, values live inside Kokkos::View, so the ordinary parallel_for form survives. Only CMake changes between Serial, OpenMP, CUDA and HIP.
  • Vec<T,W>. A struct-of-arrays SIMD type that sidesteps GCC's failure to vectorize the inlined AoS two-sum graph: 1.9–2.2× on x2 add/mul, up to 4.7× on three-/four-limb division.

Evaluation protocol

7 SHOC-style kernels (AXPY, DOT, Reduction, Triad, SpMV, GEMM, FFT) × 8 precision levels × CPU / A100 / GH200 / RX 780M. Accuracy oracle: 1024-bit MPFR on the host. CPU runs pinned with taskset, GPU runs fenced with a device-quiescence check; each number is the median of three runs, itself best-of-five.

03Strengths

  • Portability measured cleanly. One source, one lambda per kernel, configure-time backend, ≤1.7% overhead against handwritten CUDA on two NVIDIA parts.
  • The FMA argument is well made. fma(a,b,−prod) keeps FMA contraction legal and plausibly explains the 1.1–1.6× edge over CAMPARY instead of hand-waving it.
  • Right fix for a real compiler problem. Quantifies both the Vec<T,W> wins and the loss (x2 division 3.58 vs 2.39 ns from an anti-vectorization guard).
  • Breadth plus honesty. 7 kernels × 8 precisions × 2 compilers × 3 accelerators, and it reports the awkward results: CAMPARY tied at x2, Julia ahead, non-monotonic sqrt error, a Clang SLP miscompile.

04Limitations

  • No end-to-end science. The Teukolsky / EMRI solver that motivates the work is deferred; the practicality claim rests on microbenchmarks.
  • Benign accuracy regime. Random inputs in [0.1, 1000] only — no subnormals, near-overflow, cancellation or ill-conditioned cases, though all are named as failure modes (including Rump's polynomial where x2 gets the wrong sign).
  • Weak baselines. No vectorized QD, DoubleFloats.jl or intrinsics double-double, so “4.2–6.6×” conflates SIMD with algorithmic quality.
  • No performance-portability normalization. A discrete A100 vs an integrated RX 780M; no roofline, no second discrete AMD part, no H100 / MI300.
  • Correctness not systematized. A Clang 21 SLP corruption of Float64x2 FFT low limbs is patched per target, with no compiler/flag accuracy CI.

05Open questions

  1. Would the CPU advantage survive against hand-vectorized AVX2 qd_real, or is it entirely SIMD-vs-scalar plus GCC-vs-Clang?
  2. What does LLVM emit on A100 that NVCC does not, and can the 5% Julia gap be closed by changing the renormalization schedule?
  3. What is sqrt_accurate's real cost at Float64x4 on CPU and GPU — does 1.2 ULP still beat qd_real's 802 ns/op?
  4. How many renormalization sweeps are genuinely needed, and what does each buy in ULP versus registers?
  5. Does 17.9 ULP local sqrt error show up as waveform phase error in the EMRI solver, or is it washed out?
