> **一句话总结：** 提出 ELITE（Explore-then-Integrate）：每一代从同一父代并行实现 K=7 个针对具体实现缺陷的独立补丁，再由 LLM 检查这些可执行补丁的机制（互补/冗余/冲突/不完整/过度复杂），把兼容机制重新实现成一个后代，整个进化循环只用编译、接口、冒烟测试等确定性检查，不使用任何下游任务评分；在 SWE-bench Pro 60 题上把初始 agent 从 60.0% 提升到 85.6%（DGM 86.7%、HGM 88.3%，即目标集上略输），但候选任务评估从 810/800 次降为 0 次、墙钟时间 4.90h vs 43.15h/15.66h（8.8×/3.2×），且零样本迁移到 SWE-bench Verified 73.3%、Polyglot 69.3%（DGM 63.3%/62.7%，HGM 65.3%/64.7%）。

> **TL;DR:** ELITE replaces the "evaluate-and-select" loop of DGM/HGM with same-parent parallel exploration plus LLM-driven *mechanism integration*, using zero downstream candidate task rollouts (DGM/HGM use 810/800) and only deterministic compile/interface/smoke gates. On a fixed 60-task SWE-bench Pro subset with DeepSeek-V4-Flash it reaches 85.6%±1.0 vs 86.7% for DGM and 88.3% for HGM — i.e. it loses on the evolution benchmark by 1.1–2.7 pts — but transfers better without adaptation: 73.3% on SWE-bench Verified (+8.0 over HGM, +10.0 over DGM) and 69.3% on Polyglot (+4.6 over HGM, +6.6 over DGM), for a 3-benchmark average of 76.1% vs 72.8% (HGM) and 70.9% (DGM). Evolution costs 4.90 h / ~80 M tokens / ~$8 vs 43.15 h / 2,900 M / $45 for DGM and 15.66 h / 2,100 M / $30 for HGM. Ablations: removing the deterministic gates collapses the average to 52.0%; removing integration in favor of LLM- or SIFT-style child selection gives 71.8%/67.7%; cheap evaluation-based selection still wins on target Pro (91.7%) but loses on transfer.

## 核心贡献

- **问题重构（把主流自进化范式命名为 evaluate-and-select 并指出其双重代价）**：DGM 用基准分数做父代选择、HGM 用后代成绩估计谱系潜力、GEA 用任务新颖性、SIFT 用 LLM 排序降低评估量，但都保留下游任务反馈。反馈需要执行 M×N 次 rollout，探索越宽越贵；而对着固定评测分布反复优化又容易过拟合基准。作者由此提出一个更尖锐的问题：进化循环里能不能完全不用候选的下游任务评估？
- **方法（ELITE：同父代可执行探索 + 机制级集成）**：每代先从当前 agent 源码里找出具体缺陷，生成 K 个聚焦的改进假设；每个假设独立地在**同一个父代**上打补丁，得到 K 个可直接比较的可执行子代；确定性门 `G_exp` 只筛掉不可编译/不可导入/越界修改的候选；集成器读取假设、补丁摘要和门结果（必要时看完整 diff），按"互补/冗余/冲突/过度复杂/不完整"五个维度判断，再把兼容机制**重写**为一个连贯后代（不是机械拼接补丁）；更严格的 `G_acc`（含工具调用协议与主流程冒烟测试）通过才替换父代，否则保留原 agent。
- **实证（无候选评估也能大幅自进化）**：DeepSeek-V4-Flash 上 SWE-bench Pro 60 题 60.0%→85.6%（+25.6），十代里 5 次被接受更新；该次运行的后验轨迹为 60.0%→86.7%，中间有两次回退。Qwen-3.7-Plus 上 33.3%→45.6%（+12.3）。另在 mini-swe-agent v2.4.6 + Claude-opus-5.5 上十轮六次接受，Pro 71.7%→83.3%（+11.7）、Verified 70.0%→78.0%、Polyglot 72.0%→78.0%。
- **效率与成本（把"评估"从循环里彻底移除）**：候选任务评估 0 次（DGM 810、HGM 800），墙钟 4.90h vs 43.15h/15.66h，估计 token 80M vs 2,900M/2,100M，API 成本约 $8 vs $45/$30，自修改吞吐 16.35 次/小时 vs 0.58/3.77。
- **机制级分析（补丁本身作为证据）**：DeepSeek 运行的 41 个合格提案中有 25 个的主机制被并入后代；典型案例如 H3 的退出码反馈 + H4 的连续输出读取被合成为一个既能返回 100,000 行输出、又能报 `exit code: 7` 的工具；探索门 41/48 通过、接受门 5/7 通过。
- **消融（约束不可省、集成优于选择）**：去掉两个确定性门后平均分从 76.1% 崩到 52.0%；K=1 单路探索 69.9%；七提案联合直写 72.1%；LLM 选一个孩子 71.8%；SIFT 式 Bradley–Terry 选择 67.7%；用真实任务分数选孩子则在 Pro 上最高（91.7%）但迁移更差（平均 74.6%）。

## Key Contributions

- **Reframes the field's shared assumption.** The paper names the dominant pattern *evaluate-and-select* and shows that it is what makes broad exploration expensive and what invites benchmark-specific adaptation; it then poses the cleaner research question of whether evolution can run with no downstream candidate evaluation at all.
- **A concrete evaluation-free algorithm.** ELITE = limitation-driven hypothesis portfolio + K independent same-parent executable patches + deterministic admissibility gate + compatibility-aware mechanism integration + deterministic acceptance gate. The unit of evolutionary decision moves from *whole candidates* to *implemented mechanisms*.
- **Evidence that it works, with the trade-off stated honestly.** On SWE-bench Pro ELITE sits 1.1–2.7 pts below DGM/HGM, but it wins the 3-benchmark average (76.1% vs 72.8%/70.9%) and both transfer benchmarks, while using no task rollouts.
- **A cost accounting of self-improvement.** Task evaluations, self-modifications/hour, estimated tokens, wall-clock, and dollars are reported side by side for all three methods and both backbones (Table 2).
- **Mechanism-level forensics.** Manual incorporation analysis (25/41 proposals), gate-outcome accounting (85.4% / 71.4% pass rates), and six code-level case studies that trace an evolved patch to its runtime effect (exit codes, parser repair, test discovery without model calls).

## Methodology

**Formalization.** An agent is `A = (θ, Σ)`, LLM parameters fixed, scaffold `Σ` a source-code repository; updates are `A_{t+1} = IMPROVE(A_{0:t}; S_t)`. Evaluate-and-select puts task outcomes `R(A, τ_i)` into `S_t`. ELITE puts only implementation artifacts and deterministic gate results there.

**Explore (Section 4.1).** At generation `t`, a proposal operator `P(A_t, m_t; K)` sees the current implementation plus a compact evolution history `m_t` (past modification instructions and code-based rationales) and emits `K` hypotheses. Each hypothesis must name: the capability to improve, a concrete limitation in the current code, a focused mechanism, and completion conditions. An implementation operator `E(A_t, h_t^{(k)})` produces a patch `Δ_t^{(k)}`, applied to the *same* parent, so children differ only by mechanism and are directly comparable — no sequential accumulation. A deterministic gate `G_exp` checks non-empty patch, compilation of key/modified Python files, module imports and tool loading, permitted modification scope, and dependency deployment rules; it is explicitly an *admissibility* check, not a capability estimate.

**Integrate (Section 4.2).** The integrator receives each valid child's hypothesis, a patch summary, gate results, and can pull full diffs for a shortlist. It labels mechanisms as complementary / redundant / conflicting / overly complex / incomplete and then reimplements a compatible subset as one coherent patch against the original parent — reconciling shared interfaces, state and control flow rather than concatenating diffs. A stricter `G_acc` adds smoke tests of the call/return protocol, message ordering, and bounded execution; failure keeps the parent.

**Setup.** Backbones DeepSeek-V4-Flash and Qwen-3.7-Plus, thinking enabled, `MAX_OUTPUT_TOKENS=16384`; fixed 60-task SWE-bench Pro subset over 11 repositories for evolution, 50-task SWE-bench Verified (25 Django + 25 Sphinx) and 50-task Aider Polyglot for transfer only; each child runs in an isolated Docker working copy; `K=7`, `T=10` generations, 8 workers (so exploration concurrency ≤7); DGM/HGM are given ~800–820 task evaluations, ELITE a fixed 10-generation horizon. Additional scaffold: mini-swe-agent v2.4.6 + Claude-opus-5.5. All prompts, gate definitions and task IDs are in the appendix (A.2–A.6).

## Results & Highlights

- **Target benchmark, DeepSeek-V4-Flash (3-run means ± sample SD).** On the fixed 60-task SWE-bench Pro subset ELITE goes 60.0% → **85.6%±1.0** (+25.6 pts), versus **86.7%±1.7** for DGM and **88.3%±1.7** for HGM — a 1.1 and 2.7 pt deficit despite no task feedback; per-run ELITE values are 86.7/85.0/85.0.
- **Transfer without adaptation is where it wins.** SWE-bench Verified: **73.3%±1.2** vs initial 64.0%, DGM **63.3%±1.2** (+10.0), HGM **65.3%±3.1** (+8.0). Polyglot: **69.3%±2.3** vs initial 64.0%, DGM **62.7%** (+6.6), HGM **64.7%** (+4.6). Three-benchmark average **76.1%±0.8** vs HGM 72.8%±1.3 and DGM 70.9%±0.6.
- **Cost.** ELITE: **0** candidate task evaluations, **16.35** self-modifications/hour, **~80 M** estimated tokens, **4.90 h**, **~$8**. DGM: 810 evaluations, 0.58/h, 2,900 M, 43.15 h, $45. HGM: 800, 3.77/h, 2,100 M, 15.66 h, $30 — i.e. 8.81× and 3.20× wall-clock speedups under the reported settings.
- **Second backbone, Qwen-3.7-Plus.** Pro 33.3% → **45.6%** vs DGM **50.0%** and HGM **48.3%** (a 2.7–4.4 pt deficit), but Verified **56.7%** vs 54.0%/54.0% and Polyglot **61.3%** vs 50.0%/58.0%, average **54.5%** vs 53.4% (HGM) and 51.3% (DGM). Note Qwen baselines are single runs.
- **Ablations (DeepSeek, Table 4).** Full ELITE 85.6/73.3/69.3 → avg **76.1**. Removing both deterministic gates: **59.4/51.3/45.3 → 52.0** (below the 60.0% initial agent). LLM Select-one 83.3/68.0/64.0 → 71.8; SIFT-style Select-one 85.0/72.0/46.0 → 67.7; evaluation-based Select-one **91.7**/70.0/62.0 → 74.6; K=1 single exploration 81.7/64.0/64.0 → 69.9; direct joint implementation of seven proposals 78.3/72.0/66.0 → 72.1; w/o hypothesis generation 85.0/68.0/60.0 → 71.0.
- **Exploration width.** K∈{3,5,7,9} averages 70.5 / 74.8 / **76.1** / 75.6; K=9 gives the best Pro score (88.9%) but the best transfer at K=7 (Verified 73.3 vs 70.0 at K=9), i.e. diminishing returns past 7.
- **Post-hoc dynamics (not visible to ELITE).** First accepted step: seven exploratory children score 83.3/81.7/80.0/80.0/80.0/76.7/**3.3**%, and the integrated child reaches **81.7%** — better than five of seven children but below the best child (83.3%). Over ten generations five updates are accepted; the gate rejects two integrated descendants (one tool-order violation, one call-limit violation) and three generations fail at hypothesis composition.
- **Mechanism composition.** In the DeepSeek run integration carries primary mechanisms from **25 of 41** eligible proposals; gate pass rates are 41/48 (85.4%) for exploration and 5/7 (71.4%) for acceptance, with 6 of the 7 exploration rejections being *conservative type-check false positives*.
- **Repository spread.** DeepSeek scaffold improves on 8 of 11 repositories, ties 2, declines 1 (e.g. Tutanota 13/15→15/15, Qutebrowser 4/9→8/9, Navidrome 2/3→1/3); Qwen improves 7, ties 2, declines 2 — so gains are not from a single repo.
- **Cross-backbone portability.** The DeepSeek-evolved ELITE scaffold run on Qwen scores 51.7% Pro / 56.0% Verified / 54.0% Polyglot, best on all three (initial 33.3/48.0/50.0); the reverse direction gives best-or-second-best, a weak but real sign that the mechanisms are not backbone-specific.

## Authors & Credibility

Zhe Ren, Guowei Rong and Dandan Guo (corresponding) are at the School of Artificial Intelligence, Jilin University; Yimeng Chen, Nanbo Li, Piotr Piękos, Mateusz Ostaszewski and Jürgen Schmidhuber are at KAUST. The lineage is directly relevant: Schmidhuber formulated recursive self-improvement (1987) and the Gödel machine (2003), and both baselines — DGM (Zhang et al., 2026b) and HGM (Wang et al., 2026a) — come from the same research cluster, as do several closely related systems (MGM, Hyperagents, GEA, SIFT). That gives the authors deep context and access to baseline configurations, but it also means the comparison is largely intra-lab. The paper is a preprint with no venue listed, the code/agents are not released as an artifact in the PDF, and — critically — Table 2's DGM/HGM resource figures are taken from the original runs rather than re-measured on the authors' hardware. The appendix is unusually complete (prompt templates, gate checklists, exact task IDs, per-run tables, six code-level case studies), which raises confidence in the reporting even where the experimental design is thin.

## Critical Assessment

The framing is genuinely useful and the honesty is above average: the paper states in the abstract that ELITE is *below* DGM and HGM on the evolution benchmark, reports SDs, and admits that "integration does not necessarily recover the best-performing exploratory alternative" (81.7% integrated vs 83.3% best child at step one). But several claims are weaker than the presentation suggests.

**The efficiency headline is partly definitional and partly unmeasured.** ELITE does no task rollouts by construction, so "8.8× faster wall-clock" is close to a restatement of the method rather than an independent finding — the interesting quantity is performance per unit of *self-modification* budget, and there the comparison is not matched: 10 generations × 7 children = up to 70 patches for ELITE, versus roughly 0.58/h × 43.15 h ≈ 25 for DGM and 3.77/h × 15.66 h ≈ 59 for HGM. The authors concede these are "method-specific search budgets, not matched compute budgets." Worse, Table 2's baseline numbers are explicitly imported from the original papers, so 43.15 h vs 4.90 h mixes algorithmic savings with different machines, concurrency settings (DGM 1 self-mod worker + 8 eval workers; HGM 20 shared; ELITE 8), and implementation maturity. The $8 vs $45 and 80 M vs 2,900 M token figures are estimates, not measurements.

**Statistical resolution is thin where it matters.** The 85.6 vs 88.3 gap is 2.7 pts with per-run SDs of 1.0 and 1.7 over only three runs on a *fixed* 60-task subset; at p≈0.85 and n=60 the task-sampling binomial noise alone is ≈4.6 pts, which the reported SDs do not capture because the tasks never change. The same fixed-subset issue applies to the 50-task Verified and Polyglot results, where the headline transfer advantage (+8.0 and +4.6 over HGM) rests on three ELITE runs against three DGM/HGM runs — and on Qwen, one baseline run each against three ELITE runs, so the 45.6 vs 50.0 Pro deficit there is essentially unresolvable.

**The most informative ablation cuts against the thesis.** Evaluation-based Select-one — the paradigm ELITE is arguing against — gets **91.7%** on the evolution benchmark, 6.1 pts above ELITE, at the cost of 210 child-task evaluations per round. So on the target distribution, paying for evaluation still wins; ELITE's counter-argument is transfer (73.3 vs 70.0 on Verified, 69.3 vs 62.0 on Polyglot), and those comparisons are single-run. The paper's real claim should be narrower than "evaluation-free is competitive": it is "evaluation-free generalizes better," which is plausible (less benchmark fitting) but demonstrated on 50-task public subsets that the LLM has plausibly seen in pretraining, with no contamination check.

**The deterministic gates do almost all the work, and they are brittle.** Removing them drops the average from 76.1% to 52.0% — below the 60.0% initial agent — meaning unconstrained self-modification is actively harmful and the "evaluation-free" story is really "cheap-static-check-gated." Yet the gates are heuristic Python assertions whose precision is poor: 6 of 7 exploration rejections in the analyzed run were *type-check false positives*, and one timeout was excluded from the denominator. There is no precision/recall analysis of the gates, no ablation separating the exploration gate from the acceptance gate, and the "permitted modification scope" rule (don't touch tests, benchmark infrastructure, or evolution logic) is enforced at the prompt level, not by the checker — a real concern for a system that rewrites its own source.

**Integration is under-isolated.** The closest ablation, direct joint implementation, differs from ELITE in two ways at once (no independent executable children *and* no inspection step), so it cannot tell us whether the gain comes from the integrator's mechanism reasoning or merely from having seven concrete patches in context. The mechanism-incorporation number (25/41) comes from manual inspection of a single run by the authors, with no inter-annotator agreement. And the post-hoc comparison of integrated descendants against sampled exploratory means (68.0% vs 48.0%, 20 pp, on 10 tasks × 30 rollouts) uses a subset chosen independently of outcomes but still only one lineage, which the authors themselves flag as descriptive.

**Design scope limits the claim.** Single lineage, no archive: HGM's archive-based search is a genuinely different capability, so the comparison conflates "selection paradigm" with "search architecture" — ELITE's 85.6% may simply be a local optimum that an archive would escape, which the authors list as future work. Only coding tasks, only three benchmarks with hand-picked subsets, only T=10 generations, and no evaluation of what happens when the agent's edits accumulate enough to break interfaces the gates do not model.

## Strengths

- **A clean, falsifiable research question** that isolates one design choice (task-feedback in the loop) instead of stacking engineering tricks; the *evaluate-and-select* abstraction is a real conceptual contribution that makes DGM, HGM, GEA, SIFT and MGM comparable.
- **Unusually candid reporting**: losing numbers in the abstract, per-run tables with SDs, explicit acknowledgement that the integrated child can be worse than the best exploratory child, and an explicit statement that budgets are not compute-matched.
- **Transfer results are the substantive finding.** A scaffold evolved with zero task feedback gaining +8.0 (Verified) and +4.6 (Polyglot) over HGM, and improving 8/11 repositories, is evidence for the benchmark-overfitting hypothesis that a pure leaderboard comparison would miss.
- **Mechanism-level evidence, not just scores.** The H3+H4 composition (100,000 output lines *and* exit code 7), the single-quote parser repair, and the deterministic test-discovery case make "integration" concrete and auditable rather than a metaphor.
- **Cost transparency** unusual for this literature: evaluations, self-modifications/hour, tokens, hours and dollars for every method/backbone pair.
- **Breadth checks**: a second scaffold (mini-swe-agent + Claude-opus-5.5, 71.7→83.3 Pro), cross-backbone scaffold portability in both directions, width sensitivity, and a repository-level breakdown.

## Limitations

- **No compute-matched comparison.** Different self-modification counts, different worker pools, and baseline resource numbers imported from prior papers; the efficiency claim cannot be separated from implementation and hardware differences.
- **Small, fixed, public evaluation subsets** (60/50/50 tasks) with no task-sampling error bars and no contamination analysis; all three benchmarks are likely in pretraining data.
- **Few repetitions** for the most interesting comparisons: Qwen baselines and most ablations are single runs, including every selection-strategy variant that the paper's argument depends on.
- **Single lineage, no archive**, so the method cannot revisit stepping stones or maintain diversity — acknowledged, but it means the comparison with archive-based HGM is not apples-to-apples.
- **Gates are opaque heuristics** with documented false positives and no precision/recall characterization; the "permitted modification scope" constraint is prompt-level, and there is no safety analysis of an agent editing its own evaluation or tooling code.
- **Integration quality is judged by an LLM with no verification** of its compatibility claims, and the incorporation statistics are manual, single-run, and subjective.
- **Coding-only.** No evidence the mechanism-integration idea transfers to memory, web-search, or multimodal agents, which the authors list as future work.

## Relevance

直接契合"自进化 agent / 递归自我改进"这一主线：它把 DGM、HGM 这类系统共同依赖的"用下游分数选后代"抽象成 evaluate-and-select，并给出一个不依赖任何候选任务评估的替代方案，代价与收益都量化得很清楚（0 次评估、约 1/9 的训练墙钟、目标集略输但迁移更好）。对关心 coding agent scaffold 自动设计、以及"基准过拟合 vs 可迁移改进"这一评测方法论问题的读者，方法与消融部分（尤其是去掉确定性门后崩到 52.0%）比主结果更值得读。

## Questions for Further Exploration

1. Under a matched *self-modification* budget (equal number of implemented patches, equal tokens), does mechanism integration still beat evaluation-based child selection on Pro, or was the 91.7% vs 85.6% gap a budget artifact?
2. How much of the transfer advantage survives on a contamination-resistant benchmark (e.g., post-cutoff repositories or a private SWE-bench-Pro-style suite) rather than the public Verified/Polyglot subsets?
3. Which gate is doing the work — exploration admissibility or descendant acceptance? A 2×2 ablation is missing, and it would tell us whether the method is really "integration" or really "reject anything that doesn't compile and pass a smoke test."
4. Does the integrator's mechanism reasoning add anything beyond "seven patches in one context"? A variant that gives the integrator only patch summaries (no full-diff inspection) would separate the two.
5. Would an archive of historical agents (the authors' proposed extension) let ELITE escape the local optimum implied by 85.6% vs HGM's 88.3%, or does the absence of task feedback make archive scheduling itself uninformative?
6. What happens over 50+ generations, once the readily identifiable implementation defects (missing exit codes, blocking reads, brittle parsers) are exhausted and remaining gains require behavioral rather than structural changes?
7. Can the deterministic gates be replaced by stronger static analysis or property-based tests that keep the zero-task-evaluation property but reduce the 6/7 false-positive rate?
