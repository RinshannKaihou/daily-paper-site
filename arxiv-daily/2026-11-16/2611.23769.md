> **一句话总结：** 论文先诊断出一个具体故障：在 Qwen3-VL-Thinking 这类长推理 VLM 里，图像与推理文本共用同一个 KV 预算，第一轮推理结束时 DBTrimKV（B=256）已删掉 97.9% 的视觉条目，导致同一道 CharXiv 描述题"直接问"只掉 8.3 分、"推理一轮后再问"掉 24.3 分；据此提出免训练 ShelfKV——把全部视觉 KV 留在 CPU（"书架"），每步用 4-bit PCA sketch（r=32, b=4）选候选，再把高分视觉条目与最低分文本条目成对交换（最多 Rmax=B/4），图像永不被逐出但只在被读时占注意力槽。8B 模型上 CharXiv follow-up 用 386 条/头 GPU 缓存达 84.0%（DBTrimKV B=384 为 71.3%，同显存固定视觉预留为 79.0%，全缓存 85.7%），代价是 batch 64 时每步解码从 41.8 ms 涨到 103.2 ms 且总内存并未减少。

> **TL;DR:** Under DBTrimKV at B=256, a CharXiv descriptive follow-up loses 8.3 points to the full cache when asked first but 24.3 points when it follows a long reasoning turn — because the host has deleted 97.9% of the visual entries by then. A protected 128-entry visual reserve recovers 17.7 of those 24.3 points, versus 10.0 for the same extra slots in the shared budget and 7.3 for the same entries left evictable: the image lacks protection, not capacity. ShelfKV turns that reserve into on-demand reading: every visual KV entry stays in CPU memory, a 32-dim 4-bit PCA sketch proposes c=4·Rmax candidates every N=4 steps, and the current query swaps the highest-scoring visual entries into the slots of the lowest-scoring parkable text entries. On CharXiv follow-ups with Qwen3-VL-8B-Thinking it reaches 84.0% at 386 GPU entries/head vs 79.0% for a matched-memory fixed reserve (+5.0), 71.3% for DBTrimKV at B=384 (+12.7) and 85.7% for the full cache; at 259 entries it beats DBTrimKV's 61.3% by 20.4 points and still leads DBTrimKV at B=512 (73.0%) by 8.7. The trade is explicit: decoding is 2.5× slower at batch 64 (103.2 vs 41.8 ms) and total memory is unchanged, since the whole visual KV now lives in CPU RAM.

## 核心贡献

- **把"多轮推理下图像被逐出"量化成一个可复现的故障，并做了归因实验**：CharXiv follow-up 上，DBTrimKV（B=256）直接问掉 8.3 分、推理一轮后再问掉 24.3 分；缓存内每头保留的视觉条目从 prefill 后的 184.5 条跌到首轮输出结束时的 12.5 条，follow-up 到达时 97.9% 的视觉条目已被删除。
- **证明缺的是"保护"而不是"容量"**：同一总容量 384 条/头下，扩大共享预算只把 follow-up 从 61.3% 抬到 71.3%，同样初始视觉条目但不加保护是 68.7%，受保护的 128 条预留达到 79.0%——即 17.7 分 vs 10.0 分 vs 7.3 分（全缓存为 85.7%，缺口 24.3）。
- **提出 ShelfKV：把"保留"与"读取"解耦的免训练方法**。宿主策略（DBTrimKV / R-KV）只管文本；全部视觉 KV 留在 CPU 的 shelf 上，GPU 上的 desk 每步用成对交换把高分视觉条目借入，被顶掉的文本条目只是"停车"（parked）而非删除，因此 `|D_t| = |H_t|`，注意力集合大小不变。
- **一个廉价的相似度代理**：对每样本/层/KV 头的视觉 key 拟合 PCA 基底（r=32）并按维度量化到 4 bit，每 N=4 步用上一查询刷新 top-c 候选，候选 key 以 4-bit 传到 GPU；消融显示用精确分数替代 sketch 在 CharXiv 上完全无增益（81.3% vs 81.3%），MMMU-Pro 反而略低（51.3% vs 52.7%）。
- **在 4 个 benchmark、2 个宿主策略、2 个模型（8B/4B）上给出对照**，并额外做了"最优固定文本/图像切分"这一更强基线（128/256/384 条预算下 ShelfKV 分别领先 12.7 / 5.0 / 3.0 分）。
- **诚实地报告成本**：GPU 峰值显存与 R-KV 基本相同（20.8 vs 21.1 GB @ batch 64），但每步解码变慢，且 prefill 峰值与 CPU 侧内存都没减少。

## Key Contributions

- **Diagnosis with a mechanism, not just a benchmark drop.** The paper isolates the failure: visual entries and generated reasoning share one budget under DBTrimKV, so retained visual entries per KV head fall from 184.5 after prefill to 12.5 at the end of turn 1, and 97.9% of the image is already gone when the follow-up arrives. The first-turn output is fed identically across methods, so the measured gap is attributable to cache retention alone.
- **A clean capacity-vs-protection control.** Holding total size at 384 entries/head, a 128-entry protected reserve (79.0%) beats both a larger shared budget (71.3%) and the same entries left evictable (68.7%), recovering 17.7 of the 24.3 lost points. This is the paper's most transferable result and applies to any modality-shared eviction policy.
- **ShelfKV, a host-agnostic, training-free read-on-demand scheme.** Shelf = all visual KV in CPU; desk = the host's entry set; pairwise swap using log-sum-exp-aggregated query-key scores across grouped-query heads (Eq. 2); parking instead of eviction for displaced text; the most recent W=32 tokens and the prompt always stay resident (Eq. 3); per-step swap count `n_t = Σ 1[u_sj > u_pj + δ]` with δ=0 and `R_max = B/4`.
- **A two-level retrieval cost design.** A PCA sketch (r=32, 4 bits/dim) scores every visual entry in sketched space without transferring full-precision keys, refreshing candidates every 4 steps in a background thread; only selected entries are gathered from pinned CPU memory at full precision.
- **Ablations that separate the three ingredients**: host-managed text (removing it costs 5.3 points on MMMU-Pro and doubles generation-limit hits, 7.7%→19.0%), sketch vs exact scoring (free), and candidate-key storage (4-bit on GPU > 16-bit on GPU > CPU with previous query at 259 entries: 81.7 / 75.7 / 79.7).
- **Implementation-level diligence**: a mask-based evaluation framework is cross-checked against a physical kernel implementation (median first differing token 179 on CharXiv, 90.5 on MMMU-Pro; 41/3,943 and 31/2,044 forced steps differ, 48 of 72 at bf16 logit ties), and A100 vs A800 reruns reproduce every generated token.

## Methodology

**Problem setting.** A reasoning VLM emits a long chain of thought before answering; every generated token appends a KV entry, so the cache must be bounded by a retention policy (the "host"). The paper studies what happens when the same policy ranks visual entries V, prompt text A, and generated text R under one budget B (average entries per head, pooled over layers/heads by DBTrimKV). The evaluation protocol feeds the first-turn reasoning and answer from the full-cache model token by token through each method's cache, so all methods see identical reasoning but retain it differently — this isolates retention from generation drift, at the cost of measuring a single fixed first turn.

**ShelfKV.** (1) *Shelf*: every visual KV entry stays in CPU memory and is never deleted. (2) *Desk*: `D_t = (H_t \ P_t) ∪ E_t` with `E_t ⊆ S`, `P_t ⊆ H_t`, `|E_t| = |P_t| ≤ R_max`; the desk has exactly the host's cardinality, so attention cost is unchanged. (3) *Pairwise swap*: visual candidates ranked by score `u_i = log Σ_g exp(q^(g)·k_i / √d)` (log-sum-exp over the G query heads sharing a KV head), text parkable set `H̄_t = H_t \ (A ∪ R_{t−W:t})` ranked ascending, compared in pairs, swapped while `u_s > u_p + δ` (δ=0), stopping at the first failure or `R_max = B/4`. (4) *Sketch*: per sample/layer/KV head PCA to r=32 dims, per-dimension 4-bit quantization, `û_i(q) = log Σ_g exp((U q^(g))ᵀ ẑ_i + (q^(g))ᵀ μ)/√d`, refreshed every N=4 steps with the previous query's top c=4·R_max candidates; their 4-bit codes go to the GPU and are reused until refresh. (5) *Memory*: `M_GPU = B + c/8 + ⌈N_v/128⌉` entries per head, the last term being the 16-bit min/max ranges of each 128-token visual group.

**Setup.** Qwen3-VL-8B-Thinking (main) and Qwen3-VL-4B-Thinking (second), with DBTrimKV's released pretrained gates as main host and R-KV as second host (the 4B model uses R-KV only, since DBTrimKV needs a gate trained per model). Benchmarks: CharXiv follow-ups (300 charts, two-turn reasoning→descriptive), CharXiv conversations (the same charts chained into five-turn dialogues where every turn is generated by the method itself, scoring turns 2–4), MMMU-Pro Vision (300 single-turn questions with the question printed in the image), MMDU (110 multi-image conversations, 1,645 questions, judge score 1–10). Baselines: full cache, host alone at B = 128…1024, host + fixed visual reserve (V=128, selected by the host's own score after the prompt), host + ShelfKV at matched GPU memory (B lowered to 338/320/296 so the measured GPU cache matches 384 entries), DSTP+R-KV, and a "best fixed split" sweep over text/visual allocations. Hyperparameters (R_max=B/4, W=32, r=32, b=4, N=4, c=4·R_max) were chosen on 64-question development splits disjoint from evaluation.

## Results & Highlights

- **CharXiv follow-ups, 8B, DBTrimKV host, matched GPU memory**: ShelfKV reaches **84.0%** at 386 entries/head vs **79.0%** for the fixed 128-entry reserve at 384 (+5.0), **71.3%** for DBTrimKV alone at B=384 (+12.7), and **85.7%** for the full cache — within 1.7 points of uncompressed while using less GPU cache than DBTrimKV's 1024-entry configuration (78.0%).
- **The headline +20.3 is against a much smaller budget**: at 259 entries/head ShelfKV scores **81.7%** while DBTrimKV at B=256 scores **61.3%** (+20.4), and it still beats DBTrimKV at B=512 (**73.0%**) by **8.7 points** with roughly half the cache. Note the fair matched-capacity comparison is the +12.7 above, not this one.
- **Protection beats capacity at fixed size (the paper's key control)**: with total 384 entries/head, follow-up accuracy is **61.3%** (host alone, 256), **71.3%** (shared budget 384), **68.7%** (same 128 visual entries, unprotected) and **79.0%** (protected 128-entry reserve) — 17.7 vs 10.0 vs 7.3 of the 24.3-point gap, so a reserve recovers 77% more than the equivalent shared capacity.
- **Conversations and multi-image dialogues**: on five-turn CharXiv conversations ShelfKV gets **85.0%** vs **81.9%** for the reserve, **79.4%** for DBTrimKV at B=1024, **87.3%** full cache; on MMDU the judge score is **4.9** vs **4.5** (DBTrimKV 512) and **5.2** (full cache). Per-turn numbers (Table S6) show the largest gain on turn 4 (87.0% vs 72.0% for DBTrimKV at 512) and none on turn 1 (46.3% vs 45.0%), as expected since turn 1 has no prior reasoning.
- **Against the strongest simple baseline, the best fixed split**: ShelfKV leads by **12.7 / 5.0 / 3.0** points at 128 / 256 / 384 GPU entries per head on CharXiv (66.7 vs 54.0; 81.7 vs 76.7; 84.0 vs 81.0), and by 1.4 points on MMMU-Pro and 0.3 on MMDU at 384.
- **MMMU-Pro, single-turn**: ShelfKV **56.7%** at 383 entries vs reserve **55.3%**, DBTrimKV B=384 **54.0%**, and full cache **54.0%** — a compressed cache nominally beating the full cache, which is best read as ~±3 points of noise on 300 questions rather than a real gain.
- **Ordering of the ablation components (Table 2, DBTrimKV B=256)**: reserve size 32 → **74.3%** CharXiv / 47.3 MMMU-Pro; 64 → **81.0 / 53.0**; 128 → 79.0 / **55.3**; 256 → 80.3 / 53.0 (53.0). Entry *selection* matters as much: random selection at matched counts gives 78.2 CharXiv but only **35.7** MMMU-Pro (vs 55.3 host-selected), and keeping the lowest-scoring entries collapses to **53.3 / 11.3**.
- **Host removal and candidate storage (Table 3)**: letting the reasoning live on the shelf too drops MMMU-Pro from 52.7 to **47.3** (−5.3) and raises generation-limit hits from 7.7% to **19.0%**; 16-bit candidate keys cost **6.0** points at 259 entries (75.7 vs 81.7) because they cut the host budget from 225 to 171; CPU-side candidates with the previous query cost 2.0 (79.7 vs 81.7).
- **Weak hosts are not rescued**: with R-KV as host, ShelfKV lifts CharXiv follow-ups from the reserve's **17.3%** to **42.7%** (8B) and **9.8%** to **24.1%** (4B), yet the full cache is **85.7% / 82.4%** — so absolute accuracy remains far below uncompressed when the text eviction policy itself is bad (R-KV alone at B=256 is 4.7%).
- **Cost (Table 4, 80 GB A100)**: decoding peak at batch 64 is **20.8 GB** on CharXiv (vs **21.1 GB** for R-KV at B=384 and **22.8 GB** at B=512) and **21.4 GB** on MMMU-Pro (vs 21.1 / 22.8); step time at batch 1 is **48.3 ms** vs **41.0 ms**, and at batch 64 **103.2 ms** vs **41.8 ms** (2.5×), rising to 126.8 ms when the sketch is scored at step start instead of in the background.
- **What is actually being read (Table S2)**: **91.4%** of borrow steps land on entries the host has already deleted, and on 56 recorded questions the host alone answers 39 correctly while ShelfKV answers **49** — direct evidence that the gain comes from re-reading information the host discarded, not from a different eviction heuristic.

## Critical Assessment

**Novelty.** Modest and clearly positioned as such. Read-on-demand KV with CPU offload is ShadowKV/ArkVale/InfiniGen territory, and modality-aware KV budgeting is VL-Cache/MadaKV/AsymVLM territory; concurrent work ViMoD trains a router to recall visual KV, and RCR re-selects visual KV on attention drift. The genuinely new pieces are (a) the specific diagnosis that a *single shared* budget under a learned gate (DBTrimKV) crowds out vision in multi-turn reasoning, with the 97.9%-deleted number, and (b) the swap formulation that keeps the desk cardinality exactly equal to the host's, so protection costs no extra attention slots. That is a real contribution, but it is a mechanism recombination rather than a new capability.

**Rigor — where the paper is strong.** The capacity-vs-protection control (61.3 / 71.3 / 68.7 / 79.0) is the right experiment and is run correctly, including the "same entries, unprotected" arm that most papers would omit. The first-turn-feeding protocol removes generation variance from the follow-up measurement. The best-fixed-split baseline (Table S1, sweeping 96+32, 64+64, 192+64, 224+32, 128+128, 256+128, 320+64, 352+32) is a stronger baseline than most KV papers bother with, and reporting it honestly shrinks the headline from +12.7 to +3.0 at 384 entries. The implementation-agreement appendix (Table S5) and the borrow-overlap analysis (Table S2) are the kind of evidence that usually goes missing.

**Rigor — where it is weak.** (1) *The headline number is against the wrong baseline.* "+20.3 points" is ShelfKV at 259 entries vs DBTrimKV at B=256, i.e. a host that already scores 61.3% on a task where the full cache is 85.7%. Against the trivially cheap fixed reserve at matched memory the gain is +5.0 (CharXiv follow-ups), +3.1 (conversations), +1.4 (MMMU-Pro) and +0.3 (MMDU), and no confidence intervals are reported for any of these. The MMDU comparison (4.9 vs 4.6 for the reserve) is inside the judge's own 0.51 mean absolute difference between two LLM judges. (2) *ShelfKV nominally beats the full cache on MMMU-Pro (56.7 vs 54.0)* while the reserve is at 55.3 — three compressed variants all at or above uncompressed on a 300-question set is a noise signature, and the paper does not flag it. (3) *Accuracy is measured in a mask simulator*, not the physical system; Table S5 shows divergence at 41/3,943 CharXiv steps, so per-question outcomes can flip even if aggregate accuracy is close. (4) *Hyperparameters were tuned on 64-question development splits*, and Table S3 shows the sketch configuration swinging CharXiv accuracy from 71.9 to 82.8 across five settings — an 11-point spread chosen on 64 questions is thinner than several claimed margins. (5) *Missing ablations*: no test of ShelfKV with a *trained* host other than DBTrimKV, no test where the reserve is also allowed R_max-limited borrowing of reasoning entries (asymmetric treatment), no breakdown of whether the +5.0 over the reserve comes from which turns, and no measurement of the CPU-side memory pressure under realistic concurrency (the appendix quotes 0.14–0.27 GB of pinned memory per question, which at batch 64 implies ~9–17 GB of host RAM — never stated in the main text). (6) *DQ on 4B*: with R-KV as host all methods are catastrophic (24.1% vs 82.4% full cache), so the 4B row primarily demonstrates that a weak host cannot be fixed, which the authors do say, but it also weakens the "consistently outperforms" framing since absolute utility at that scale is nil.

**Significance.** The diagnostic result — protect the image, because extra shared capacity is worth less than protection — is more valuable than the method, and it generalizes to any modality-shared eviction policy, including ones not evaluated here. The method itself buys a modest, memory-neutral accuracy recovery at 2.5× decoding cost, which is a hard sell for serving; it is best read as "what a visual reserve should look like when you cannot afford to keep the image resident," not as a general efficiency win.

**Red flags (none fatal).** Headline framing vs the matched-baseline reality (+20.3 vs +5.0); a compressed cache exceeding the full cache with no noise discussion; dev splits of 64 questions; training-free claim is accurate but the host DBTrimKV is itself gate-trained, so "training-free" is only true relative to the host; a 6-author, 4-institution preprint with no code link yet.

## Strengths

- The diagnosis is crisp and mechanistically grounded: 184.5 → 12.5 retained visual entries per head, 97.9% deleted, 8.3 → 24.3 point degradation for the identical image and question. A reader can check and reuse this.
- The capacity-vs-protection experiment is a model of how to argue "the problem is X, not Y": three configurations of identical total size, with the unprotected control that isolates selection from survival.
- Design choices are individually ablated rather than bundled: host-managed text (+5.3 MMMU-Pro), sketch vs exact (0.0 CharXiv, −1.4 MMMU-Pro), 4-bit vs 16-bit vs CPU candidates (+6.0 / +2.0 at 259 entries).
- The swap rule is elegant: desk cardinality equals the host's, so protecting vision costs no extra attention work and does not lengthen the context — a genuinely different point in the design space from "keep everything and read on demand."
- Baseline coverage is unusually honest for this literature: full cache, four host budgets, fixed reserve at four sizes, random/lowest-scoring selection controls, best fixed split per budget, DSTP, and a second host and second model.
- Reproducibility signals are concrete: released DBTrimKV gates, physical-vs-masked implementation agreement, A100/A800 token-exact reruns, pinned-CPU gather kernels adapted from open source, code promised.

## Limitations

- **No total-memory win.** All visual KV moves to CPU; prefill peak is unchanged; only the GPU-resident cache shrinks. Under memory pressure this is a GPU-budget trick, not a memory reduction, and the paper says so.
- **Decoding is slower and the penalty grows with batch**: 48.3 vs 41.0 ms at batch 1, 103.2 vs 41.8 ms at batch 64 on CharXiv (2.5×), 152.2 ms on MMMU-Pro; the CPU-side pinned memory (~0.14–0.27 GB per question) is not counted in any headline number.
- **Only the image is protected.** Text eviction remains whatever the host does, so ShelfKV with R-KV as host tops out at 42.7% against an 85.7% full cache — the method cannot compensate for a bad text policy.
- **Only images present at prefill are shelved**, so on MMDU all images must enter in turn 1; later-turn images fall back to host behavior.
- **Requires regions the reasoning did not use.** On single-turn MathVerse and short-answer VisDial the 16-bit variant only matches the host; on HR-Bench 4K fine details every compressed cache, including this one, stays 3.5–6.0 points below full cache; when the reasoning question comes last, a 128-entry reserve gives no benefit on it.
- **Evaluation is simulator-first** for accuracy, with a single fixed first turn for the follow-ups; the conversations are constructed from CharXiv rather than collected, and only 110 MMDU conversations are used.

## Relevance

直接命中 "Reliability under Extreme Performance Optimization"：这是一篇把 **KV-cache 压缩/逐出在长推理多轮场景下的失效模式**（视觉条目被推理文本挤掉、同一问题"推理前问"与"推理后问"差 16 分）定量刻画出来的论文，并给出"保护优先于扩容"这一可迁移结论。对关注推理模型在激进推理加速下能力退化的读者，诊断部分（97.9% 视觉条目被删、17.7 vs 10.0 vs 7.3 的对照）比方法本身更值得读。

## Questions for Further Exploration

1. The 97.9%-deleted figure is for DBTrimKV at B=256 on CharXiv charts (~671 visual tokens). How does it move with image size — 2.9K tokens on MMMU-Pro, 6.4K on MMDU — and does the reserve need to scale with `N_v` rather than a fixed 128 entries? Table 2 hints yes (V=64 is best on CharXiv, V=128 best on MMMU-Pro) but no rule is given.
2. What happens with a trained host other than DBTrimKV (e.g., ForesightKV or TrimKV) — does a gate trained to keep vision make ShelfKV redundant, or is the crowding-out effect structural to any single global budget?
3. How much of the +5.0 over the fixed reserve survives at the 95% level? A bootstrap over the 300 CharXiv questions, as done in Table S2, would settle whether the MMMU-Pro (+1.4) and MMDU (+0.3) gaps are real.
4. Does the swap interact badly with prefix caching / continuous batching in a real server, where different requests have different desks and the gather kernels must be scheduled per sequence?
5. Could the parking mechanism be inverted — protect the reasoning's *early* tokens and let late reasoning be evicted — given the paper's own finding that the reasoning (unlike the fixed-size image) is poorly served by on-demand reading (MMMU-Pro −5.3, generation-limit hits 7.7%→19.0%)?
6. Why does a compressed cache exceed the full cache on MMMU-Pro (56.7 vs 54.0)? Is that noise, or does evicting low-score text actually help by removing distractors — and would a direct test of that hypothesis be worth running?
