> **一句话总结：** 在单张 RTX 4090 上以 bfloat16 运行 Qwen3-0.6B，作者把「一次验证 4 个草稿 token」「左填充到 64 的倍数」「batch=4」等数学等价的贪心解码路径与逐 token 的 width-1 参考路径对比，发现 128 个新 token 下分别有 60.0%、68.0%、69.3% 的 prompt 输出不同，而所有首次分叉处参考 margin 均 ≤0.375；进一步用 teacher-forcing 把噪声拆成「query 形状」与「宽 pass 写入的 KV cache」两部分，证明后者与前者同样嘈杂，因此「margin gate + 直接读那份 cache 的 width-1 回退」几乎无效（58/100 仍不同），只有用 width-1 pass 重建 cache 才能把差异降到 0/100，代价是每 token 7.24 次前向（参考为 1.0）。

> **TL;DR:** On Qwen3-0.6B (bfloat16, 128 new tokens, GSM8K + ARC-Easy/Challenge prompts), 4-token prompt-lookup speculative verification changes the greedy text of 90/150 prompts (60.0%) relative to a width-1 cached reference, padding to a multiple of 64 changes 102/150 (68.0%) and batch-of-4 changes 104/150 (69.3%), while a rerun of the reference itself changes 0/60. A teacher-forced split on 5,253 positions shows the mean noise statistic S is 0.117 for cache entries written by wide passes versus 0.078 for the wide query shape alone (+0.039, bootstrap [0.036, 0.042]), so a width-1 fallback over a wide-written cache flips the argmax as often as the wide pass it is meant to repair. Consequently a calibrated margin gate (eps = q99 = 0.375) with a stale cache leaves 58/100 prompts different vs 61/100 for plain verification (McNemar p = 0.664), and even an *oracle* trigger only reaches 49/100; rebuilding the generated cache with width-1 passes reaches 0/100 (p = 8.7e-19) at 7.24 target passes per token vs 1.00 for the reference. Fixed-width-5 decoding instead makes drafted and plain decoding bit-identical (0/100) at 0.75 passes per token, but neither agrees with the width-1 path (66/100 each). A float32 check shows the bf16 reference is *not* closer to float32 than the verify pass (34 vs 24 argmax disagreements per 5,380 positions).

## 核心贡献

- **首次系统测量「同一贪心函数、不同执行路径」的输出差异率**：在 batch size 1、簿记完全正确的前提下，单独隔离出 4-token 验证、padding、batching 三条路径相对 width-1 参考的差异（60.0% / 68.0% / 69.3%），并给出 Wilson 区间与 McNemar 检验，把「speculative decoding 输出与目标模型完全一致」的承诺在有限精度下量化了。
- **把舍入噪声按来源拆分**：沿参考 token 做 teacher-forcing，用「宽 query + 参考 cache」（只含形状噪声 q）与「width-1 query + 宽 cache」（只含 cache 噪声 c）两个探针分离两种来源，发现 c 的平均 S（0.117）反而大于 q（0.078），二者几乎不叠加。
- **证明「margin gate + 就地 width-1 回退」这一直觉上最省钱的修复方案失效**：包括 oracle 触发器（精确知道哪里该回退）在内的 stale-cache 变体仍有 49%–58% 的 prompt 不同，从而把失败归因于 cache 内容而非触发器。
- **给出 cache 重计算的剂量-反应曲线**：stale → 当前 chunk → 最后 16 条 → 全部生成部分，差异率单调下降到 0，为「噪声来自宽 pass 写入的 cache」提供因果性证据；并给出成本-精确度帕累托前沿（eps = 0.125 时 3.55 passes/token 仍达 0 差异）。
- **提出 fixed-shape decoding 作为替代方案**：所有 pass 固定宽度 W=5，使 drafted 与 plain 解码完全一致（0/100），成本与变宽验证相同（0.75 passes/token），但代价是放弃了与 width-1 参考的等价性。
- **width scan 给出机理解释**：在 2,459 个位置上逐位比较整行 logit，width-1 与任何更宽 pass 的逐位相同比例为 0.0%，而 width 2/3 共享一组 kernel、width 4/5/6 共享另一组——不同宽度分组走不同 reduction，这正是所有差异的数值根源。

## Key Contributions

- **Quantifies path-dependence of greedy decoding at batch size 1**, where no batching bookkeeping bug can be blamed: 4-token prompt-lookup verification diverges from a width-1 reference on 90/150 prompts (60.0%), padding on 102/150 (68.0%), batch-of-4 on 104/150 (69.3%), against 0/60 for a reference rerun.
- **A teacher-forced decomposition of rounding noise into query-shape and cache-content components**, with an exactness control (a width-1 replay of the reference cache reproduces reference logits with max |diff| = 0.0), showing cache noise is *larger* than query-shape noise and largely non-additive.
- **A negative result with a clean mechanism**: a calibrated margin gate whose fallback reads the wide-written cache does not restore exactness (58/100 vs 61/100, p = 0.664), and neither does a perfect oracle trigger (49/100) — isolating cache contents, not gate quality, as the blocker.
- **A dose-response experiment plus a cost frontier** for cache rebuilding: 0/100 divergences at 7.24 target passes/token (q99), or 3.55 passes/token at eps = 0.125, versus 1.00 for the reference.
- **Fixed-shape (width-5) decoding as a lossless-in-practice alternative for speculation**: 0/100 prompts differ between drafted and plain decoding, at 0.75 passes/token — self-consistency bought without extra passes, at the cost of abandoning agreement with a variable-width reference.
- **A bit-level width scan** establishing that widths fall into kernel-sharing equivalence classes (2–3, 4–6), with width-1 sharing nothing with any wider width — the numerical explanation for every divergence measured.
- **Transfer checks**: the bound calibrated on 42 GSM8K prompts holds on 78 further calibration prompts (0.55% of positions above q99, 0/162 flips missed) and on 60 shifted MMLU/HellaSwag prompts (0.61%, 0/147 missed); the rebuild gate reaches 0/60 there while plain verification reaches 48/60.
- **A float32 sanity check that undercuts the natural "reference = ground truth" reading**: the bf16 reference disagrees with float32 at 34/5,380 positions, more than the verify pass (24), the cache-noise pass (25) or the padded pass (29).

## Methodology

**Model and stack.** Qwen3-0.6B (Apache-2.0) in bfloat16 via transformers 5.20 / PyTorch 2.11 on one RTX 4090 (shared with ~8 other jobs), default SDPA attention, TF32 disabled. A second size, Qwen3-1.7B, is used for one replication. Chat template with thinking off; greedy decoding, at most 128 new tokens.

**Prompt sets.** A fixed shuffled evaluation pool of 500: 250 GSM8K test (step-by-step arithmetic), 125 ARC-Easy test, 125 ARC-Challenge test (lettered multiple choice answered with an explanation). Every run uses the first *n* prompts of that order, so smaller runs are strict subsets of larger ones. A 120-prompt calibration list (60 GSM8K train, then 60 ARC-Challenge test) supplies the noise bound; because the run was stopped early, only the first 42 (all GSM8K train) set it, and the remaining 78 serve as a held-out check. A shifted set of 200 MMLU-test and HellaSwag-validation prompts provides an out-of-distribution test.

**Reference path.** Batch size 1, `DynamicCache`, one whole prefill pass, then width-1 decode steps. Explicitly treated as *a convention*, not as ground truth — Section 10 measures distance to float32 for every path.

**Compared paths.** Padded (left-pad prompt to a multiple of 64 with mask and explicit positions); batch-of-4; k-token verification (k = 4) with prompt-lookup drafting (propose the continuation of the longest matching suffix n-gram, n ≤ 3), scoring k+1 positions in one pass, committing the longest agreeing prefix plus the verifier token, and cropping the cache — so **cache entries for committed tokens are written by the wide pass and kept**, which is the crux of the paper.

**Noise statistic S.** Teacher-forced along the reference tokens, let D = reference logit − path logit. For the path's argmax *a* and each rival *j* in the path's top 16, the noise can move *j* above *a* by D_j − D_a; S is the maximum of these, clamped at 0. If the path margin ≥ S no rival can overtake. A bound eps on S yields the gate: fall back whenever the path margin ≤ eps. eps is set to q99 / q999 / max of S over 5,253 calibration positions: 0.375 / 0.625 / 1.375.

**Five noise probes** at each calibration position: *spec* (wide query over wide cache), *q* (wide query over reference cache — query shape only), *c* (width-1 query over wide cache — cache only, i.e. what a gate fallback sees), plus whole-sequence and padded whole-sequence passes.

**Gate variants.** *plain* (commit everything), *stale* (width-1 fallback over the wide-written cache), *chunk* (recompute only the current chunk token-by-token), *rebuild-16* (recompute the last 16 cache entries), *rebuild* (recompute the whole generated cache), and *oracle* variants that fall back exactly where the verify argmax differs from the reference — an unattainable upper bound on any real trigger.

**Fixed-shape decoding and width scan.** Every post-prefill pass has a fixed width W = 5, unused rows filled with a filler token, so drafted and plain steps run identical kernels on identical shapes. The width scan compares full logit rows bit-for-bit across widths W ∈ {2,…,32} against width-1 and width-2 rows on 20 prompts (2,459 positions).

**Statistics.** A prompt "diverges" if its 128-token sequence differs from the reference. Rates carry 95% Wilson intervals over prompts; means carry bootstrap intervals; same-prompt comparisons use exact McNemar tests. Greedy decoding has no seeds, so the only sampling is prompt selection. All numbers are recomputed at build time from cached per-path JSON results.

## Results & Highlights

- **Divergence is the norm, not an edge case.** Against the width-1 reference, 4-token verification changes 90/150 prompts = 60.0% [52.0, 67.5], padding to 64 changes 102/150 = 68.0% [60.2, 74.9], and batch-of-4 changes 104/150 = 69.3% [61.5, 76.2], while a rerun of the reference changes 0/60 = 0.0% [0.0, 6.0]. Padding vs 4-token verification differs on a near-tie set of prompts (27 only-padding / 15 only-4-token, McNemar p = 0.088), whereas batch-of-4 is statistically distinguishable (27 / 13, p = 0.038).
- **The rate is duration-dependent, so no single number describes a path.** At position 64 only 32.0% of prompts had diverged, versus 60.0% at position 128; the median first divergence sits at position 62 for 4-token verification but at 34 for padding and 44 for batching, and the "still identical" curves fall steadily with no knee.
- **Prompt source matters as much as path**: 4-token verification diverges on 30/73 GSM8K prompts (41.1% [30.5, 52.6]) but 35/43 ARC-Easy (81.4% [67.4, 90.3]) and 25/34 ARC-Challenge (73.5% [56.9, 85.4]), tracking the density of fragile positions (margin ≤ 0.25 at 5.6% of GSM8K vs 10.2% and 10.8% of the ARC sets) rather than any property of the algorithm.
- **Every one of 296 pooled first divergences (127 distinct prompts, 3 paths) sits at a reference margin ≤ 0.375**, with median 0.125 and 99.7% at ≤ 0.25 — in the same units, the median margin over all 18,689 reference positions is 3.12 and only 8.1% lie at ≤ 0.25. 39.2% of divergences occur at an *exact* bf16 logit tie versus 1.5% of all positions, and the smallest non-zero margins observed (0.1250, 0.1875, 0.2500, 0.3750) coincide with the bfloat16 grid spacing for logits in [16, 32).
- **Reference margin is a near-perfect ranking signal** for fragile positions: AUROC 0.993 [0.989, 0.996] for low reference margin, 0.992 for low wide-pass margin, 0.922 for reference entropy, and only 0.446 [0.388, 0.522] for position, on 71 flipped positions out of 5,253.
- **Cache noise is not smaller than query-shape noise.** Mean S is 0.078 [0.076, 0.080] for the wide query over reference cache, 0.117 [0.113, 0.120] for the width-1 query over wide cache, and 0.120 [0.116, 0.124] for both together; the paired per-prompt difference c − q is +0.039 [0.036, 0.042]. Argmax flips are close across sources (40 for q, 42 for c, 37 for both, 43 whole-sequence, 46 padded whole-sequence) and *do not add up* — of the 37 verify-pass flips, 29 also flip under q, 33 under c, 27 under both, and 19 positions flip under q or c but not under the verify pass.
- **The margin gate with a stale cache buys essentially nothing**: 58/100 = 58.0% [48.2, 67.2] prompts still differ versus 61/100 for plain verification on the same prompts (McNemar p = 0.664), at 0.86 target passes/token and 13.55 fallbacks per prompt. Recomputing only the current chunk is also insufficient (32/60 = 53.3% vs 35/60, p = 0.581), and rebuild-16 halves it but does not close it (19/60 = 31.7% vs 35/60, p = 0.004, 2.37 passes/token). The interaction is a clean dose-response across the 60 prompts every variant finished.
- **A perfect trigger cannot save a stale cache**: the oracle stale variant still leaves 49/100 = 49.0% [39.4, 58.7] prompts different (versus 61/100 plain), at 1.02 passes/token with 26.7 fallbacks per prompt — the strongest single piece of evidence that cache *contents*, not gate quality, is the binding constraint.
- **Full cache rebuild is exact but 7× slower than the thing it fixes**: 0/100 = 0.0% [0.0, 3.7] differ (McNemar p = 8.7e-19 vs 61/100) at 7.24 target passes/token, 13.32 fallbacks per prompt and 809 width-1 fallback passes per prompt; q99 flags 10.7% of generated tokens. A looser bound is worse (eps = q999 = 0.625: 9.29 passes/token) and a tighter one is better (eps = 0.125: still 0/100 exact but only 3.55 passes/token, 5.75 fallbacks/prompt) — the calibrated q99 bound is thus ~2.0× more conservative than necessary. At eps = 0 (exact ties only) the gate collapses to 15/45 = 33.3% [21.4, 47.9] still different, versus 27/45 plain.
- **Fixed-shape decoding makes speculation self-consistent for free**: fixed-width-5 drafted vs fixed-width-5 plain differ on 0/100 = 0.0% [0.0, 3.7] prompts at 0.75 target passes/token (same as variable-width verification), but both differ from the width-1 reference on 66/100 = 66.0% [56.3, 74.5], essentially the same as variable-width verification (61/100 on the same prompts). Fixed shape buys agreement with itself, not with an unfixed reference.
- **The width scan explains why**: across 2,459 teacher-forced positions, the share of positions where a width-W logit row is bit-identical to the width-1 row is 0.0% for every W from 2 to 32; widths 2 and 3 are 100% identical to each other, as are 4, 5 and 6; width-2 vs width-5 rows agree at 76.5%, width-8 vs width-5 at 65.4%, and widths 12/16/32 at 0.0%. Variable-width verification therefore mixes two kernel groups (2–3 and 4–6) while the reference lives alone in the single-row group.
- **The bound transfers, and the gate's failure transfers too**: on 60 shifted MMLU/HellaSwag prompts plain verification differs on 48/60 = 80.0% [68.2, 88.2] (margin ≤ 0.25 at 10.5% of positions vs 8.1% on evaluation prompts), the stale gate on 41/60 = 68.3% [55.8, 78.7] at 0.90 passes/token, and the rebuild gate on 0/60 = 0.0% [0.0, 6.0] at 10.71 passes/token. In teacher-forced terms, S exceeds q99 = 0.375 at only 0.70% (37/5,253), 0.55% (53/9,626) and 0.61% (46/7,552) of positions on the calibration, further and shifted sets, and a q99 gate misses 0 of 37, 0 of 162 and 0 of 147 argmax flips respectively.
- **Agreement with the width-1 reference is not agreement with exact arithmetic**: on 5,380 teacher-forced positions from 43 calibration prompts, the bf16 reference disagrees with the float32 argmax at 34 positions (6.3 per 1,000), the verify pass at 24 (4.5), the cache-noise pass at 25 and the padded whole-sequence pass at 29 — the reference is the *worst* of the four.
- **The mechanism replicates at 1.7B**: 4-token verification changes 27/45 = 60.0% for 0.6B and 31/45 = 68.9% for 1.7B (padding 71.1% and 73.3%; intervals overlap, so the sizes are not ranked); the noise split gives mean S of 0.157 (cache) vs 0.102 (query) at 1.7B vs 0.117 / 0.078 at 0.6B, and q99 rises to 0.500; the 0.6B-calibrated eps = 0.375 rebuild gate still reaches 0/45 at 3.28 passes/token while the stale gate leaves 30/45.
- **Text divergence rarely changes the ARC answer**: of the 60 ARC prompts where 4-token verification changed the text, 52 state an option letter in both outputs and the letter changed in 0; for padding, 64 differ, 53 state letters, 2 letters change; pooled, 2 of 192 differing prompt-path pairs (1.0% [0.3, 3.7]) change the named option.
- **Wall-clock (context only, shared GPU)**: 26.9 ms/token for the reference, 18.7 for 4-token verification (0.71×), 18.0 for fixed-width-5 with drafts (0.68×), 21.5 for the stale gate (0.81×), 85.6 for the eps = 0.125 rebuild gate (3.44×) and 127.5 for the q99 rebuild gate (6.13×).
- **Margin gating also rescues deliberately inexact cheap paths**: logit-lens exit at layer 26 of 28 goes from 82.3% argmax agreement to 93.5% while keeping 71.7% of positions; 8-bit round-to-nearest weights from 98.4% to 100.0% keeping 63.6%; 4-bit from 80.9% to 95.7% keeping 60.2%; 3-bit from 21.6% to 54.6% keeping only 15.8%. The full-depth whole-sequence pass is the rounding floor at 99.1%.

## Authors & Credibility

Both authors — Mohammed Nayeem Khan and Navin Kumar R — are at Intel Corporation with Intel e-mail addresses, and this looks like an internal local-inference characterization study rather than a benchmark-driven academic paper. Credibility signals in the writing are unusually strong for a 27-page arXiv v1: every number is recomputed from cached per-path JSON at build time; the paper states it was drafted and edited with LLM assistance but that the authors checked all numbers; intervals are Wilson for rates, bootstrap over prompts for means, exact McNemar for paired comparisons; the plan-vs-execution gap (42 of 120 calibration prompts) is disclosed rather than hidden; the paper explicitly refuses to make speed claims from a shared GPU; and it upfront concedes that its "reference" is one arbitrary convention and then *tests* that concession against float32 instead of asserting the reference is correct. The related-work section is honest about searches being incomplete ("a margin gate with cache rebuild may exist in engines or in papers that our searches did not reach"). Weak spots: no public artifact or repository is referenced (Appendix A lists Windows PowerShell driver scripts such as `a15b_shard.ps1` under `tasks\locallm`, i.e. an internal path), the paper carries an unexplained codename ("Vega-Fafnir") in its title, and the PDF metadata shows it was produced by a headless browser from an HTML source, consistent with the acknowledged LLM-assisted drafting pipeline. Nothing here looks fabricated — the tables are internally consistent and the reported failures are the kind an author would prefer not to report — but independent reproduction would currently require re-implementing the harness from Appendix A.

## Critical Assessment

Novelty is real but narrow in framing and sharp in content. The premise (finite-precision non-determinism across serving paths) is well established — the authors cite batch-size/GPU/engine effects including a 16.6-percentage-point backend swing (arXiv:2605.19537) and 9% reasoning-accuracy drift (arXiv:2506.09501) — and much of the headline divergence rate would be unsurprising to anyone who has run bf16 inference twice. What is genuinely new is the *decomposition*: the `c` probe (width-1 query over a wide-written cache) is a clean, cheap instrument, and the oracle-stale result (49/100 still different even with a perfect trigger) is a decisive, falsifiable argument that a widely held intuition — "just fall back to width 1 when the margin is small" — is wrong. The dose-response across stale → chunk → rebuild-16 → rebuild is the right experimental design for a causal claim, and the paper deserves credit for running it rather than stopping at the negative result.

Rigor is above average, with specific soft spots. The mechanism claim rests on a single GPU, single driver, single PyTorch/SDPA build: the width-grouping result (2–3 and 4–6 sharing kernels, width-1 sharing nothing) is a property of *that* reduction schedule, and every divergence rate inherits it. The authors say this in Limitations, but it means the paper's central quantitative claims are not portable numbers — they are one stack's numbers. The zero-divergence claims are also weakly bounded: 0/100 gives a Wilson upper bound of 3.7%, and 0/60 gives 6.0%, so "rebuild is exact" really means "≤ ~4% of prompts still differ", which the authors state but the abstract's rhetoric ("0 of 100 different") does not. The calibration is thinner than planned (42 prompts, 5,253 positions) so q999 and max rest on "a handful" of positions — and note that q999 produced a *looser* and strictly more expensive gate (9.29 vs 7.24 passes/token) with no accuracy benefit, which quietly shows the quantile is not well estimated. Statistical practice is otherwise careful (McNemar across 11 non-independent variants without multiplicity correction is flagged by the authors themselves).

The most interesting finding is also the least exploited. 39.2% of pooled first divergences sit at an *exact* bf16 logit tie (versus 1.5% of all positions), and the observed non-zero margins are literally the bf16 grid spacing at these logit magnitudes. That says a large fraction of the problem is tie-breaking on quantized logits, not accumulated error — which suggests a far cheaper fix than cache rebuilding (e.g., break ties on higher-precision or stable-ordered accumulators, or nudge exact ties deterministically). The paper notes it "did not examine how ties between equal bfloat16 logits are broken" but never tests the obvious cheap intervention, so the 7.24-passes/token conclusion may be an artifact of treating tie collapses as generic rounding noise. Similarly, the eps = 0.125 result is presented as a cost win, but 0.125 is one bf16 grid step — i.e. the "tighter calibrated bound" is essentially "flag every near-tie", which loops back to the tie-break question.

The cost accounting is honest but incomplete in a way that matters for the conclusion. Passes per token assume the memory-bound regime, and the authors concede a width-5 pass does 5× the arithmetic of a width-1 pass, so 0.75 vs 1.00 passes/token is not a 25% win in FLOPs. The wall-clock numbers (0.68× for fixed-width, 6.13× for the rebuild gate) come from one timing run of 12 prompts through a Python decode loop on a GPU shared with eight other jobs, which the authors correctly refuse to call a benchmark — but that leaves the practical recommendation resting on pass counts that are themselves a lower bound on cost. And the fix "costs 7.2× the thing being fixed" is a strange deliverable unless the goal is auditability rather than throughput, a framing the paper only reaches in the final sentence.

There is also an unresolved definitional tension. If the width-1 path is not closer to float32 (Section 10: 34 vs 24 argmax disagreements), then "exactness" is agreement with an arbitrary convention, and the rebuild gate is a very expensive way to reproduce one particular kernel's rounding. The paper says this out loud and then still frames the rebuild gate as the "exact" solution throughout the abstract and conclusion. The honest synthesis — that the right move is to *fix the pass shape and declare it the reference* (Section 8), which costs nothing extra — is present but underweighted relative to the expensive result, presumably because the expensive result is the paper's contribution. One more gap: the answer-level check covers only ARC option letters (2 of 192 changes), while GSM8K outputs are truncated at 128 tokens before the final number, so the task where numerical divergence should matter most is exactly the one not graded.

## Strengths

- A genuine mechanistic contribution — separating query-shape noise from cache-content noise — that changes what practitioners should believe about "verify then fall back" fixes, delivered with an exactness control (width-1 cache replay reproduces reference logits with max |diff| = 0.0).
- The oracle-trigger experiment is exemplary experimental design: it converts a negative result about a specific gate into a statement about *all possible triggers*, which is far more durable than "our heuristic didn't work".
- The dose-response over how much of the cache is recomputed (stale → chunk → last 16 → all) is a causal argument, not a correlation, and it comes with a cost curve rather than a single point.
- Unusual intellectual honesty on the reference itself: Section 10 is included even though it weakens the paper's own framing, and the conclusion still tells readers that the width-1 path is only a convention.
- Held-out testing is built in rather than bolted on: 78 unseen calibration prompts and 60 shifted MMLU/HellaSwag prompts test both the calibrated bound (0.55% / 0.61% exceedance, 0/162 and 0/147 flips missed) and the gates' behavior, and both tests include the *failure* of the stale gate, not just the success of the rebuild gate.
- The width scan is a small gem: a 2,459-position bit-level census showing exactly which widths share kernels, which turns a mysterious 60% divergence rate into an expected consequence of reduction-group membership.
- Reproducibility discipline unusual for this genre: all figures and tables regenerated from cached JSON at build time, Wilson/bootstrap/McNemar stated per claim, and the plan shortfall (42 of 120 calibration prompts) disclosed rather than papered over.

## Limitations

- **One stack, one GPU.** RTX 4090, one driver, PyTorch 2.11 / transformers 5.20, default SDPA. The width-grouping in Section 8 is a property of that reduction schedule, so both the kernel classes and every divergence rate may differ on other hardware, and the paper's numbers should be read as existence proofs, not constants.
- **Small samples with wide intervals on the key zero results.** 0/100 → Wilson upper bound 3.7%, 0/60 → 6.0%, 0/45 → 7.9%, 0/30 → 11.4%. The exactness claims are therefore "consistent with up to a few percent still diverging", and several gate variants ran on only 30–45 prompts.
- **The calibration quantiles are thin.** 42 prompts / 5,253 positions for q99; q999 and max rest on a handful of tail points, and the q999 gate turned out both looser and more expensive (9.29 vs 7.24 passes/token) with no accuracy gain — evidence the tail estimate is not stable.
- **Cost is measured in passes, not arithmetic.** A width-5 pass does 5× the work of a width-1 pass, so 0.75 passes/token is not 25% cheaper in FLOPs; the only wall-clock data is one run of 12 prompts on a shared GPU, explicitly not a benchmark.
- **The rebuild implementation is the naive one.** Recomputing the entire generated cache at every fallback is the simplest exact scheme, not the cheapest; the authors concede an implementation that rewrote each entry once would be cheaper and that they did not build it, so the 7.24-passes/token headline is an upper bound on the cost of exactness.
- **Exact ties are left unexamined** even though they account for 39.2% of pooled divergences versus 1.5% of positions. No tie-breaking policy is tested, which leaves the cheapest plausible fix (deterministic tie resolution on higher-precision logits) unexplored and may inflate the apparent cost of every exactness strategy.
- **Answer-level impact is barely measured.** Only ARC option letters are graded (2 of 192 changed); GSM8K generations are cut at 128 tokens before the final number, so the arithmetic task — where a changed digit matters — is not evaluated at all, and correctness effects on longer reasoning traces are outside the evidence.
- **Greedy only, 128 tokens, prompt-lookup drafter only.** Sampling, long chains of thought, and trained drafters (EAGLE/Medusa-style) are out of scope; the authors argue a trained drafter changes which widths occur but not the cache/kernel argument, which is plausible but untested.
- **No public artifact.** Scripts are named and their invocation order given, but no repository, hashes or environment lockfile are referenced, so independent replication means re-implementing the harness.
- **Framing instability.** The abstract and conclusion call the rebuild gate "exact" while Section 10 shows the width-1 reference is not closer to float32 than the paths it is used to judge; the practically free alternative (fix the pass shape, declare it the reference) is correctly identified but demoted to a secondary recommendation.

## Relevance

直击「Operator Precision, Determinism & Error Propagation」核心：用干净的 teacher-forcing 探针把浮点非结合性噪声拆成 query 形状与 KV cache 内容两部分，并证明「margin gate + 就地 width-1 回退」这一主流修复直觉在 cache 层面失效——对做投机解码、batch-invariant kernel、推理可复现性审计的工作高度可复用。其 width scan 的「哪些宽度共享同一 kernel 组」方法论，也可直接迁移到跨引擎/跨 kernel 数值等价性验证。

## Questions for Further Exploration

1. How much of the 60% divergence survives if exact bf16 logit ties are broken deterministically (e.g. on a float32 shadow accumulator or by a fixed index rule)? Given 39.2% of divergences sit at exact ties, this could be a near-free fix and would materially change the cost conclusion.
2. Does the width-grouping result (1 | 2–3 | 4–6) hold on Triton/FlashAttention-v3/vLLM kernels, on H100 versus RTX 4090, and with TF32 enabled? If the groups are stack-specific, so is every rate in the paper.
3. What does the q99 exceedance rate look like on a genuinely harder distribution shift — long-context code, multilingual, or tool-calling prompts where answer formats are rigid — rather than MMLU/HellaSwag multiple choice?
4. Would a trained drafter (EAGLE, Medusa) with longer accepted runs, and hence more wide-written cache entries per token, push the stale gate's failure from 58% toward 100%? The mechanism predicts it should, which is a sharp test.
5. On GSM8K with a longer token budget so the final numeric answer is reached, what fraction of 128-token divergences actually flip the arithmetic answer? The paper's own framing implies wording-only changes, but the task where that matters most was not graded.
6. Can the rebuild cost be reduced below 1.0 passes/token by a rewrite-each-entry-once scheme, or is one width-1 pass per committed token a hard floor as the authors suspect but do not prove?
7. Is there a cheaper certificate than a margin bound — e.g. tracking the accumulated S along the sequence and falling back only when the running sum approaches a grid step — that keeps 0/100 divergences at well under 3.55 passes/token?
