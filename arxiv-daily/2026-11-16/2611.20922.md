> **一句话总结：** 论文用三个自建服务（calendar / task / mail）的 A/B 双版本接口，在同一批任务上做三臂对照（无经验 / 经验有效 / 经验过时），发现当 MCP 工具接口被"静默"改动后，拥有此前成功经验的 agent 成功率跌到 23%（文档不完整时）和 26–49%（文档完整时），而无经验的 agent 分别为 63% 和 88–100%；过时经验比没有经验更糟（−0.40），且 347/348 次失败的 run 反而向用户报告"已完成"，作者把这一现象命名为 Experience Rot。

> **TL;DR:** With three small synthetic services (calendar, task list, mail) whose A/B versions differ in exactly one interface detail, six models are run over 12,624 episodes in three arms — no experience, valid experience, out-of-date experience. After a silent change, out-of-date experience yields 23% success vs 63% for novices under incomplete documentation (a drop 0.40 below no-experience) and 26–49% vs 88–100% under complete documentation, while agents with valid experience reach ~100%; failures are reported as successes in 347 of 348 complete-doc failures, lookup-before-write falls from up to 100% (novices) to ≤6% (experienced), the damage grows with experience (46% → 33% → 26% at 1/3/10 prior tasks), and the only remedy that works without reading docs (read-back of stored state) costs 6.5 vs 2.9 model calls.

## 核心贡献

- **命名并量化 "Experience Rot"**：agent 自己过去成功的工具调用在接口静默变更后变成错误，但 agent 仍然照抄，导致"有经验反而不如没经验"。关键在于实验设计把经验内容固定住，只翻转环境版本，从而把"经验本身的价值"和"经验过时后的代价"分离开。
- **提出一个干净的受控三臂设计**：同一 final task、同一批任务实例，唯一差别是 earlier task 跑在版本 A 还是版本 B（或没有 earlier task）。每个变更都双向跑（A→B、B→A），12,624 个 episode，其中大部分条件预注册并冻结了代码哈希。
- **定位失效机制是"停止检查"而非"记错"**：过时经验下首写内容正确率仍有 95–100%（participants 之类信息没记错），错的是接口字段/取值语义；写前查文档的比例从 novice 的 70–100% 掉到 ≤6%，而只要写后 read-back 就能恢复（184 次"旧用法且不 read-back"中 183 次失败；97 次"旧用法但 read-back"中 94 次成功）。
- **证明记忆形态与经验数量都会影响代价**：conversation 里代价 0.53，memory file 0.27，retrieved memory 0.20，skill 0.30；1/3/10 条 earlier task 使过时经验成功率 46%→33%→26%，查文档率 4%→0%。
- **给出对评测方法的警告**：研究者手写的 history 中只要包含一个 read-back 步骤，过时经验成功率就从 agent 自己跑出来的 46% 升到 88%，测得代价只有真实代价的约五分之一（0.11 vs 0.54）——这可能是该失效长期未被发现的原因之一。

## Key Contributions

- **Defines and measures "experience rot"**: an agent's own earlier tool call, correct when made, becomes wrong after a silent interface change, yet the agent reuses it and then reports success. The design holds experience content fixed and flips only the environment version, isolating the causal effect.
- **A controlled three-arm protocol** (no / valid / out-of-date experience) over three services that differ in exactly one interface detail per version pair, run in both directions, with 12,624 episodes, preregistered predictions and code hashes for the complete-documentation conditions.
- **Mechanistic localization**: the failure is not misremembered content (first-write content is right in 95–100% of runs) but the abandonment of verification — lookup before first write collapses from 70–100% to ≤6% — and read-back after the write is the discriminating behaviour (183/184 failures without it, 94/97 recoveries with it).
- **Systematic variation of memory form and amount**: memory file, retrieved memory and skill all show the cost (0.20–0.30) but less than conversation (0.53); cost grows monotonically with the number of prior tasks.
- **A methodological critique of memory evaluation**: hand-written histories that contain a check step measure ~1/5 of the real cost, which may explain why the phenomenon has been under-reported.

## Methodology

Three synthetic services — calendar, task list, mail — each with two versions A and B differing in one interface detail (Table 1). Three changes are visible in a typed tool definition (field name `attendees`→`guests`, structure `end_time`→`duration_minutes`, value enum `urgent/high/normal/low`→`p0..p3`); three are invisible because the number keeps its range (priority direction 1-highest vs 4-highest, weekday numbering 0=Monday vs 0=Sunday, plus month numbering and duration unit used only in the incomplete-documentation block). Tools are MCP/function-calling style: name, description, JSON schema. Each service also exposes read tools that report state in neutral terms ("Highest", "Tuesday") and a `docs_search` tool returning the running version's reference docs.

An **episode** = one earlier task (run live, on the running version) plus one final task of the same kind, as the next message in the same conversation. Three arms: *valid* (earlier task on same version as final), *out-of-date* (earlier task on the other version), *none*. Every change is run in both directions with identical task instances, so valid and out-of-date arms differ only in which version produced the experience. Earlier attempts are retried up to ten times and discarded unless the stored state matched, so experience is always genuinely successful. Success is checked programmatically against stored state; the paper also logs lookup before first write, "old usage" in the first write, read-back after the write, model calls, and whether the final reply claims completion.

Documentation is manipulated in two regimes. *Complete*: docs give fields, values and their meaning, so the agent has three routes to notice a change (untyped payload + docs, typed definition listing current fields, or docs describing what a number means). *Incomplete*: docs give only the type/range ("priority is an integer from 1 to 4") — mirroring real documentation — and the earlier request, not the final one, states what the values mean. Later sections vary where experience is stored (conversation, memory file, top-3 retrieved memory, reusable skill script + note), how much of it exists (1/3/10 earlier tasks), what is appended to the final task (version notice, docs in system prompt / tool description / task message, instruction to read docs, instruction to verify and correct, writes returning the stored object), and who wrote the earlier task (agent itself vs hand-written history with/without a read-back step).

Six models — GLM-5.3-Flash, Muse-Glimmer-30B, DeepSeek-V4-Flash (0731), MiniMax-M3, Qwen3.8-Flash, Inkling — with native tool calling, temperature 0.7, ≤16 model calls per task, ≤4,096 output tokens. Estimates are pooled over models, changes and directions with a cluster bootstrap (10,000 replicates) over task instances; 136 of 12,624 episodes excluded (9 failed requests, 127 earlier tasks that never succeeded in ten attempts).

## Results & Highlights

- **Out-of-date experience is worse than no experience.** Under incomplete documentation, success is 63% with no experience, 100% with valid experience, and 23% with out-of-date experience — 0.40 ± 0.01 *below* the novice arm, and every first write in the out-of-date arm uses the earlier version's semantics. Per-change out-of-date success ranges 15–31% (duration unit 15%, priority direction 19%, weekday 27%, month 31%).
- **The failure survives complete documentation.** With complete docs, novices succeed 88–100% and valid-experience agents 100%, but out-of-date agents reach only 26% when the field is documented only (untyped tool), 49% when the typed definition in front of them lists `guests` (cost 0.51), and 42% for a changed meaning of a number (cost 0.58). The clearest single number: the definition says `guests`, the agent writes `attendees` — in 69% of runs for definition-visible changes vs 99% for documentation-only changes.
- **Failures are reported as successes.** 347 of 348 failed runs with out-of-date experience and complete documentation end with a completion claim ("The event 'Security Review' has been scheduled … with Paul and Maya as attendees", MiniMax-M3, for an event stored with no participants); under incomplete documentation the share is 405/438 (92%).
- **Experienced agents stop checking, and cannot tell valid from stale memory.** Lookup before the first write: novices 100% (fields only in docs) and 70% (meaning of a number); experienced agents ≤6% in every condition. Before the first write, 24–25% of experienced runs refer to the earlier task (as often when it is stale as when it is valid) while only 6% plan a doc lookup, against 69% of novice runs planning a lookup. Path analysis: of 184 runs that wrote the old usage and did not read back, 183 failed; of 97 that wrote the old usage and did read back, 94 succeeded.
- **Every memory form is affected, and more experience is worse.** Cost (valid minus out-of-date success) is 0.53 in conversation, 0.27 in a memory file, 0.20 in top-3 retrieved memory, 0.30 in a skill — with 60–73% of memory files and 92% of skill notes recording the earlier version's field or value. With 1/3/10 earlier tasks in the conversation, out-of-date success falls 46% → 33% → 26% (cost 0.54 → 0.66 → 0.71) while valid experience holds at 97–100% and the lookup rate falls 4% → 0%.
- **Remedies mostly fail, and one backfires.** Version number + update notice: 50% (vs 46% baseline). Docs in the task message: 99%. Docs in the system prompt: 54%; in the tool description: 55%. An instruction to read the docs first *in the system prompt* drops success to 29% — agents comply in the earlier task (98%) but not the final one (4%). Under incomplete documentation the same instruction appended to the task message makes every agent search yet success stays at 25%, because the docs do not contain the answer. Verify-and-correct works (91% complete / 69% incomplete) but at 6.5 and 10.6 model calls vs 2.9/3.1 for valid experience; writes that return the stored object give 79% at 4.6 calls, and 59 of the 77 remaining failures see the wrong stored state and still do not write again.
- **Hand-written histories hide the effect.** With a hand-written earlier task that includes a read-back step, out-of-date success is 88% versus 46% after the agent's own earlier task (cost 0.11 vs 0.54); read-back rises to 84% vs 30% because agents copy the procedure. Removing the read-back step from the same history drops success to 58% (cost 0.36 vs 0.54 own).
- **Per-model spread is enormous.** With complete documentation, out-of-date success is Qwen3.8-Flash 1.00 (it reads back after every write), GLM 0.70, Inkling 0.38, DeepSeek 0.35, Muse 0.25, MiniMax 0.05; under incomplete documentation MiniMax, DeepSeek and Muse fall to 0.01–0.02 while Qwen stays at 0.93.
- **Preregistration held.** All 20 preregistered contrasts matched their directional predictions, including two the authors had no prediction for: docs in the tool description cost +0.09 ± 0.02 (positive, i.e. small but real benefit) and version notice +0.04 ± 0.02; the visible-change-minus-docs-only contrast came out −0.23 ± 0.02 (definition-visible changes are *cheaper* than documentation-only ones).

## Authors & Credibility

Zhen Xu (University of Chicago) with Hang Yin, Zitao Zhang and Kevin Zhao (eBay) and Xuefeng Liu (University of Florida). The work reads like an industry-plus-academia collaboration on agent reliability: the protocol is unusually careful for this genre — preregistration with code hashes, a pre-run calibration with four fixed exclusion rules, cluster bootstrap over task instances, both change directions, and a related-work section that positions the paper precisely against experience-following (Xiong et al., 2026), MCPEvol-Bench, ProEvolve and SKILL.nb. The honesty is notable: they report that the most dramatic figure (novices 63% vs experienced 23%) comes from the *non-preregistered* incomplete-documentation block, that most excluded episodes are on the weekday change, and that an obvious fix (rejecting unknown fields) was never tested. No released code or data is mentioned, which is the main reproducibility gap.

## Critical Assessment

*Novelty*: the behavioural core — agents copy their own past calls — is already documented as experience-following (Xiong et al., 2026) and in the Einstellung/set-shifting literature; the genuinely new move is the experimental inversion: hold the experience fixed and mutate the environment silently, then measure lookup behaviour. That framing plus the "worse than no experience" result is a real contribution, and the hand-written-history critique (0.11 vs 0.54 measured cost) is a sharp, actionable point about a whole literature's methodology.

*Rigor*: strong on the axis the authors chose — preregistration, bidirectional changes, identical task instances across arms, per-run programmatic state checks rather than LLM judges. But the headline comparison (23% vs 63%) is exactly the condition they did *not* preregister, and the novice arm there is partly a lottery on defaults: with incomplete docs, an agent that assumes January = 1 or priority 1 = highest wins only if the running version happens to agree, which is why the per-version numbers are 49%/71%, 43%/86%, 100%/40%, 100%/17%. Both directions are run, so the pooled 63% is fair, but it means "novices succeed" is really "novices succeed about half the time by luck", which weakens the rhetorical framing of *novices succeed where experts fail*.

*Baselines*: there is no comparison to a retrieval/verification agent framework (ReAct+reflection, MCPEvol-Bench-style reflection modules, or a "check the tool list every turn" policy). All six models run the same minimal 16-call loop, so the paper measures a lower bound on what deployed harnesses would do — the authors say so, but a single "always call `docs_search` when the schema differs from the cached call" policy baseline would have made the cost estimate concrete.

*Missing ablations*: (a) rejecting unknown fields / returning an error is the single most obvious engineering fix and is explicitly untested, so the paper's practical recommendation is weaker than it could be; (b) no test of partial/error-producing changes, which the authors concede ("real changes often come in groups, and some produce partial errors"); (c) no test of experience the agent had to discover by trial-and-error rather than being told in the earlier request — the incomplete-doc setting hands the agent an explicit rule sentence, which makes the stale knowledge unusually crisp; (d) remedies were tested only with experience in the conversation, not with memory files or skills, yet Section 9 recommends harness-level remedies as if they generalized.

*Red flags*: 127 of 12,624 episodes were dropped because the earlier task never succeeded, and 124 of those are on the weekday change (Inkling 76, DeepSeek 36, MiniMax 15) — so the weekday estimates condition on a selected subset, and weekday is also where novices do worst (78%). The completion-report and "plans a lookup" measures are keyword regexes (check/look up/consult within 40 characters of docs/reference/schema), which can both miss paraphrases and fire on negations. All six models are Flash/small-tier; whether a frontier reasoning model with an explicit verification habit also rots is untested, and Qwen3.8-Flash's 1.00 out-of-date success in complete docs suggests the effect is a policy artifact that some models simply do not have. Finally, the services are synthetic and single-detail; the paper's own Table 1 observation (Todoist priority 1 vs 4 across two real MCP servers) is the strongest external evidence offered, and it is anecdotal.

## Strengths

- The three-arm design is the right instrument: flips only the version that produced the experience, keeps task instances and experience content identical, runs every change in both directions.
- The mechanism claim is triangulated three ways — lookup rates, reasoning-text references, and the read-back path analysis (183/184 vs 94/97) — rather than inferred from success rates alone.
- Breadth of the manipulation grid (6 models × 6 changes × 4 memory forms × 4 experience amounts × 7 remedies) with consistent direction of effect everywhere.
- Preregistration with hashed analysis code and a pre-run calibration; every directional prediction held, and the two unpredicted contrasts are reported honestly.
- The hand-written-history result is immediately useful to anyone building memory benchmarks: it quantifies how much a single check step in a researcher-authored trajectory inflates measured robustness.
- Unusually candid limitations section that names the synthetic services, the single-detail changes, the short tasks, the non-preregistered conditions and the keyword-based measures.

## Limitations

- Services are synthetic and tiny; each version pair differs in exactly one interface detail, whereas real API migrations bundle renames, semantic changes and partial error behaviour.
- Tasks are one- or few-step, with 1–10 prior tasks of the same kind; long-horizon workflows where stale knowledge is one of dozens of decisions are not covered.
- Incomplete-documentation conditions were not preregistered, yet they carry the headline "experience is worse than none" claim.
- The earlier request states the value semantics explicitly, so the stored experience is a crisp rule rather than something learned by trial and error.
- All models run the same minimal agent loop with ≤16 calls; harnesses with planners or verifiers may behave differently, and no such harness is tested.
- Most remedies are tested only with experience in the conversation, not with memory files, retrieved memory or skills.
- Exclusions concentrate on the weekday change (124 of 127), so those estimates are conditional and possibly optimistic; bootstrap treats models and changes as fixed.
- No released artifact; "reports success" and "plans a lookup" are regex-based proxies.

## Relevance

直接对应"agent 记忆 / 工具使用 / MCP 接口演化"这条线：它给出一个可复用的三臂评测模板和一组可复现的数字，说明记忆系统不能只存"什么曾经有效"，还必须能发现"这个用法已经不再成立"。对做 agent memory、tool-use benchmark 或想把经验回灌进生产 agent 的工作，这篇是必读的负面结果。

## Questions for Further Exploration

- Would rejecting unknown fields (turning the silent change into an explicit error) restore novice-level success, and at what cost in compatibility with clients that send stale payloads?
- Does the effect persist in frontier reasoning models with explicit self-verification habits, or is Qwen3.8-Flash's read-back-every-write policy evidence that it is a trainable/steerable behaviour rather than a fundamental limit?
- How does experience rot interact with bundling — multiple simultaneous changes, some producing partial errors — where "old usage" might be partially correct?
- Can a memory system store provenance/version metadata in a form agents actually act on, given that a version tag in the memory file only moved cost from 0.27 to 0.20?
- What happens with experience acquired by trial and error (no explicit rule sentence in the earlier request), where the agent's stored belief is vaguer and possibly more fragile?
- Would the hand-written-history correction (0.11 vs 0.54) replicate on existing memory benchmarks such as STALE, MemTrapBench or MCPEvol-Bench — i.e., are published memory-robustness numbers inflated by roughly 5×?
