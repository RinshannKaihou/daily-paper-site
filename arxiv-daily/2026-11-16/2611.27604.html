Headline result

160/160

AIME + MATH500 · batch 8 · greedy · ≤16K tokens

Bitwise-identical greedy outputs across all-CPU, 20-slot, 41-slot and online placement (49,712 swap-ins). The same engine with replay switched off manages 1/160.

Why it matters

Free GPU memory silently rewrites your answers, contaminating every hybrid-inference comparison. IsoMoE removes that variable — and still decodes 1.26× faster than the best baseline.

Critical edge

“Bitwise identical” means identical to KTransformers’ approximate vrcp14ps arithmetic. Accuracy is never measured against ground truth — this is determinism, not correctness.

Read the invariance claim narrowly

The problem is not a corner case

Placement changes are decided by whatever else is running on the GPU at launch. Existing hybrid engines diverge badly — and quietly.

No random seed is involved. Rounding-level differences flip which expert a token routes to; Top-8 routing then magnifies “8th vs 9th expert are almost tied” into a discrete jump, and the answer changes.

One canonical arithmetic, replayed

The inversion: don’t make both devices “more correct”. Declare the bottleneck side canonical and let the idle side emulate it.

Step 01 · choose a reference

Keep the CPU kernel untouched

CPU expert compute is 82% of each decode step with all experts on CPU, and still 49% with 13.5 GiB resident on the GPU. Fixing the busy side costs throughput; emulating the idle side costs almost nothing.

Step 02 · replay the dot product

vdpbf16ps → two fma.rn.ftz

AVX-512 adds the odd product first, the even one second, rounding after each add. Two inline-PTX FMAs reproduce that order and denormal handling exactly, in code the compiler cannot reassociate.

Step 03 · tabulate the rest

65,536-entry activation table

vrcp14ps’s 14-bit reciprocal cannot be reproduced bit-for-bit on the GPU, so every BF16 activation input maps to the CPU-computed output instead.

Step 04 · lay out the weights

“CPU order” 12-bit codewords

Low byte kept, high byte squeezed to sign + 3-bit exponent offset against a per-matrix base (≈12.1 bits/weight). Rows are permuted into the dot-product’s fetch order, so decompressed w0/w1 are the operands — no 32×32 transpose per call.

Step 05 · pipeline without bits moving

Two micro-batches, whole-batch shapes

Micro-batches are offset by half a layer and computed at full-batch shape (zero-row padding, KV split by whole batch), so library kernel selection cannot perturb arithmetic. Swap-ins commit after each layer’s attention and router.

Step 06 · merge in routing order

k=1 dummy tokens for single experts

The CPU library only returns a pre-accumulated y. IsoMoE feeds each (token, expert) pair as its own weight-1.0 token to recover d_j, then the GPU re-applies the same FMAs in routing order.

Read it like a reviewer

Strongest controls in the paper, and the claims it does not actually test.

Strengths

  • A problem statement you cannot wave away. “5 of 56 unchanged”, “3 of 16 when another process holds 4 GiB” turn reproducibility into a concrete evaluation hazard.
  • The asymmetric-replay inversion. Letting the bottleneck side define the reference arithmetic is a reusable idea for any heterogeneous engine, not just MoE.
  • CPU order is mechanism, not marketing. The decompressor’s output is the dot-product operand — and the row-major sweep (0.68–0.70× vs 1.28–1.35×) shows why.
  • Honest controls. The fast-mode row flips 159/160 outputs; per-layer hashes are checked against an untouched engine; 49,712 swap-ins are stress-tested online.

Limits & open edges

  • One box. Single 8488C, single A6000, PCIe 4.0, batch ≤32, GPU budget ≤37.5% of BF16 experts. No multi-GPU, NVLink, H100/B200, AMX, or ARM — and the AVX-512 layout has no stated portability path.
  • No accuracy evaluation. The 8.8–10.0% answer churn in fast mode is never scored, so the cost of divergence is unknown.
  • The reference is an approximation. vrcp14ps activations are canonized by table; compare across engines or kernel versions and the guarantee evaporates.
  • Exception paths are unquantified. Overflow-segment frequency, side-table size, data-dependent access cost, offline 12-bit conversion — all unmeasured.
  • Decode only. No prefill/TTFT, tail latency, or staging-buffer footprint, even though the dual micro-batch design is decode-phase specific.
  • Baseline gaps. FreeToken on Qwen3 only, HybriMoE excluded, and the 1.54× headline is a self-ablation against IsoMoE’s own BF16 variant; the honest number is 1.26×.

Questions for further exploration

  1. How far is the frozen reference from a correctly rounded SiLU — and could a “correct-activation” canonical be shared by both sides at similar cost?
  2. What fraction of 64-weight row segments overflow the 3-bit exponent offset, how big is the side table, and does it show up in the per-step latency tail?
  3. What happens on H100/B200 with different Tensor-Core accumulation, or on SPR/AMX where vdpbf16ps becomes tile instructions?
  4. With CPU still at 82% of the step, what is the headroom from reducing CPU work — a cheaper exact activation, or 2:4 sparsity — and does invariance constrain it?
  5. Does the extra 12-bit slot budget interact with KV-cache pressure? Qwen3’s 24.1 GiB KV cache already caps its expert budget at 31.25%.
  6. Can placement invariance compose with batch invariance and cross-engine reproducibility without a 20–50% throughput tax?
