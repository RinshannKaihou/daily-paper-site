Distributed sparse attention · systems

A millisecond planner is enough to make mask-aware distributed sparse attention pay off.

DexAttention: Distributed Sparse Attention through Rapid Online Planning and Persistent GPU Execution

Sirui Chen (Purdue) · Xuehai Qian (Tsinghua) Preprint, 14 pp. Code released

把稀疏注意力在 context parallelism 下的“规划”当作一等公民：GPU 端聚类 assigner + CPU 贪心 scheduler（6–23 ms 一次），配上每卡只启动一次的常驻 kernel。

Key metric

1.39×

Geometric-mean end-to-end training speedup over the fastest applicable baseline — 11 configurations on 4 nodes × 4 RTX A5000.

dynamic video workload: 2.11–2.37× vs Ring, planning included

Why this matters

Long-context training chokes on attention communication. Cheap online scheduling, not faster hardware, reclaims it — and the pattern transfers to any mask-irregular distributed operator.

Critical edge

Every result comes from one 16-GPU A5000 cluster on 200 Gb/s IB with no NVLink — and the gain falls as per-GPU bandwidth rises, so these are a fabric-specific upper bound, not a forecast.

Three stages, one attention pass

01 · Assigner (GPU)

64-row Q chunks are clustered by shared-KV similarity S = AAT; four rounds yield ~19 clusters under a load cap Cε = (1+ε)W/|U|, with KV re-split (k ≤ 4) for communication-bound candidates.

4.9–6.3 ms · assignment only
02 · Scheduler (CPU)

One gateway GPU per node absorbs a shared remote chunk, transfers are ordered by compute work ÷ transfer time, and remote partial outputs return first.

12–19 ms static · 6–23 ms dynamic
03 · Executor (persistent)

One controller block + 63 worker blocks, launched once per pass. Block 0 polls NVSHMEM epoch signals; ready tiles dispatch with no host round-trip.

0.07 ms launch + setup per call
  • The cost model only ranks candidates, it never simulates a timeline: Tb = max(compute, communication) + tail, with calibration fixed across all six workloads.
  • Deliberate division of labor — the planner gives coarse order and refuses to predict interleaving; piece-level readiness is a runtime signal. A coarse plan drives fine-grained execution.
  • Runs behind FA2, InfLLM-v2, SpargeAttention2 and FlexPrefill; dense matmuls are captured in CUDA graphs and inter-node traffic uses NVSHMEM put-with-signal.

Where it does not pay

  • W4 top-k training: 1.00–1.12×. Non-attention work is 72–82% of the step, so there is almost nothing left to win; the assigner declines to move Q and keeps ownership.
  • W6 prefill gets slower with assignment: 0.98–1.07× vs Ring with the assigner, 1.11–1.16× without — FlexPrefill's mask selection alone is 24–31% of prefill time.
  • Memory: 0.8–2.4 GiB above Ring (W3 at 128K: 16.4 vs 14.2 GiB), though still under UltraAttn's 17.6 and ahead of DCP, which OOMs at 128K.
  • Balance is a means, not the objective: on W5 traffic drops 277 → 126 MiB per node while compute imbalance rises 1.05 → 1.31.

Strengths

  • Tables 5 and 6 are the control most systems papers skip: replaying each plan on the other's stack makes the 1.39× attributable, and yields an honest negative — a 12–19 ms heuristic matches planners that take seconds.
  • Planning latency is measured end to end, including table upload and W5's rank-0 broadcast, rather than quoted as solver time.
  • Real executor engineering: one kernel launch per GPU per pass, controller/worker split that dodges the register spilling seen in fused ring stages.
  • Publishes the failures and explains them — W4 keeps ownership, W6 slows down — plus FP64 checks on outputs and gradients, a memory table with DCP's OOM, and released code.

Limitations

  • One 4-node, 16-GPU A5000 cluster over 200 Gb/s IB, no NVLink, 1.75 GB/s per GPU — no faster fabric is tested, so the speedups are an upper bound.
  • 1.3B–8B models, ≤256K context, 2–4 warmed steps per configuration: no convergence evidence, which is what practitioners actually need.
  • Global planning stops at one node: at ≥16 nodes each rank plans only its own node and metadata exchange is excluded; the 128-GPU axis invites over-reading.
  • No per-layer mask dynamism test — “dynamic” replays masks rather than producing them live inside a step, sidestepping the pipeline stall that motivates online planning.
  • SparSP, FlashMask-3 and db-SP are discussed but never run, leaving the ceiling of placement + assignment + persistent execution untested.

Open questions

  1. How much of the 1.39× survives on NVLink or 400G/800G IB? The cost model already parameterizes link bandwidth, so a sweep would settle whether online planning is a slow-fabric fix or a general technique.
  2. What does planning cost when masks change per layer and are produced live in the training step, rather than replayed?
  3. Why does W6 lose with assignment while W5 gains 1.14–1.41× — planning residue, lost ownership locality, or Q redistribution? Can the assigner learn to decline before it plans?
  4. Can the assigner compose with SparSP-style initial placement or FlashMask-3 interval masks without breaking the millisecond budget?
  5. How sensitive is the 126 MiB / 1.31-imbalance operating point to ε, and does the buffer-credit protocol hold under recomputation plus HSDP with overlapping backward plans?
  6. How does the persistent kernel interact with CUDA-graph capture when mask shapes vary across calls — is W6's four-layer sampling cost-driven or a capture limitation?
