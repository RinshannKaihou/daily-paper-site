> **一句话总结：** 这是中国电信星辰 AGI 实验室的 Xing 4（TeleChat 第四代）技术报告，核心不是模型能力而是"如何在昇腾 910C + MindSpore 上把 285B MoE 训起来"：架构上选 MLA+DSA+跨层 IndexShare（仿真下 TTFT 降到 0.21×、prefill 吞吐 4.68×）、45 层偏宽偏浅拓扑（比 60 层基线 prefill 1.20×、训练吞吐 +10%）、DSpark 块式投机解码（六个代码/数学基准上输出吞吐 2.67×–3.77× 基线、1.48×–2.10× MTP3），系统上以 HyperParallel-FSDP 彻底删掉流水线并行（36.4s→31.8s，1.14×）、owner 化 Muon（−9.1%）、算子级选择性重算（−6.9%）、逐层 indexer 反传（−15.2%），最终在 8,192 张 910C 上完成 285B 预训练并开源 29B-A4B；但全文没有任何模型精度评测。

> **TL;DR:** A systems/engineering technical report for the Xing 4 (TeleChat-lineage) family from China Telecom's Xingchen AGI Lab, describing how a 285B-parameter MoE (17B activated, 1M context) was pretrained on 8,192 Ascend 910C NPUs with MindSpore HyperParallel, plus a 29B-A4B member that is actually open-sourced (256K context). Architectural ablations on the 285B: MLA+DSA+IndexShare vs MLA-only gives 0.21× TTFT / 4.68× prefill throughput and 1.27× decode throughput, but these are Zhanlu-*simulated* numbers, not measured; the 45-layer wider-FFN topology beats a 60-layer narrower one (prefill 1.20×, decode 1.11×, training throughput +10%); DSpark speculative decoding reaches 2.67×–3.77× base output throughput (115.8 vs 35.4 tok/s on GSM8K) and 1.48×–2.10× over MTP3. On systems, HSDP without pipeline parallelism cuts step time 36.4s→31.8s (1.14×) on a 1,024-NPU profiling cluster at 262K sequence length, and three further optimizations each save 6.9%–15.2% against that baseline. The report is unusually candid about its own scope, but reports **zero** downstream model-quality numbers — no MMLU, no GSM8K accuracy, no agent benchmark — so "frontier agentic models" in the title is an aspiration, not a measured claim.

## 核心贡献

- **给出一条在国产芯片上做大模型的可复现工程路线**：不是提出新算法，而是把架构选择（MLA/DSA/IndexShare、深度-宽度、投机解码）与系统实现（HSDP、Muon、重算、KV 压缩、CPU 绑核）放在同一套"算力-访存-串行开销"权衡框架里做完整实验，并在 8,192 张昇腾 910C 上真实跑通 285B MoE 预训练。
- **用 DP 维度的分片取代流水线并行**：HyperParallel-FSDP 在每个 SuperPoD 内做 FSDP 分片、跨 SuperPoD 只做粗粒度梯度规约，并对单个参数张量直接做 AllGather/ReduceScatter 实现零拷贝，配合三层通信重叠；在 1,024 NPU、262K 序列、285B 模型上把 step time 从 36.4s（PP=4, 1F1B）降到 31.8s，直接消掉约 27% 的理论气泡。
- **把"谁来算全矩阵"从"谁拥有分片"里解耦**：Muon 的 Newton–Schulz 需要完整权重矩阵，朴素实现让每个持有分片的 rank 都重算一遍；作者改为每个矩阵指定唯一 owner rank，非 owner 用 P2P 收发分片，权重与动量布局不变，step time 再降 9.1%。
- **算子级而非层级的选择性重算**：把"保留哪些算子输出"写成 0-1 背包（收益=前向耗时，成本=输出字节），并识别重算区→保存区边界的张量地址，用占位符替代常驻显存；在 HSDP+Muon 基础上再省 6.9%。
- **TeleGym：面向异构 agent harness 的统一执行与 RL 数据面**：把任务执行、评测、轨迹构造接到同一条策略优化流水线，用"生成/训练分离 + 有界过采样 + partial rollout + 采样时刻 log-prob 留存 + 执行级 reward 分组"处理 agent 任务时长极度不均与策略滞后问题。

## Key Contributions

- **An integrated architecture-and-systems recipe for Ascend**, rather than a new algorithm: attention (MLA + DSA + cross-layer IndexShare), depth-width (wider-and-shallower MoE), and decoding (DSpark block-wise speculative decoding with a 5-layer DFlash draft, a Markov head and an acceptance-confidence head) are each ablated on the 285B model, then the winning combination is actually pretrained at 8,192-NPU scale.
- **Pipeline-parallelism-free large-scale pretraining.** HyperParallel-FSDP shards parameters inside each Ascend SuperPoD and replicates across SuperPoDs, so weight AllGather and sharded-gradient ReduceScatter stay on the high-bandwidth intra-SuperPoD domain; only coarse gradient reduction crosses SuperPoD boundaries. Per-parameter (rather than flattened-buffer) collectives remove copy-in/copy-out, and a three-way overlap schedule (ReduceScatter of layer i+1, AllGather of layer i−1, inter-SuperPoD AllReduce) hides the rest. Result: 36.4s → 31.8s step time versus PP-1F1B, 1.14× end-to-end.
- **Owner-based execution for distributed Muon.** Each 2D matrix gets one owner rank inside its shard group; owners assemble the full input via batched P2P, run Newton–Schulz, and scatter scaled update shards back, with shape-grouped batching to amortize kernel launches. Sharded parameter/momentum layout is untouched: 31.8s → 28.9s (9.1%, 1.10×).
- **Object-based fine-grained selective recomputation.** Operators are named model objects whose member paths can be individually marked as recompute or exclude/save, avoiding a Python policy callback per dispatch (the cost of native operator-level checkpointing). Exclusion is chosen by solving a knapsack over measured forward time vs. measured output footprint; a boundary-activation trick replaces large inputs crossing into the save region with address-keyed placeholders. 28.9s → 26.9s (6.9%).
- **DSA long-sequence training optimizations.** Layer-wise indexer backward uses the fused KL operator's forward-computed gradient so the auxiliary graph retires per layer instead of waiting for the LM backward (28.9s → 24.5s, 15.2%, the largest single gain); Q-block head-tail pairing balances the causal workload; document-aware KV compaction shrinks the KV window from `[0, b)` to `[d(a), b)` for each query block.
- **TeleGym** unifies heterogeneous agent harnesses behind one episode interface and one trajectory representation, with disaggregated async generation/optimization, bounded oversampling (finite lookahead window plus separate pending/ready bounds), partial rollout across policy publications, and execution-level (not segment-level) reward grouping so multi-turn tasks don't get counted as extra attempts.

## Methodology

**Architecture.** The 285B member is a decoder-only MoE: 45 layers, hidden 4096, 128 heads, 256 routed experts of intermediate size 2048 with 8 selected per token plus 1 shared expert; the first 2 layers use dense FFNs, the rest MoE FFNs. Attention combines MLA (KV compression), DSA (lightning indexer picks Top-K historical KV) and IndexShare (reuse sparse indices across layers, so the indexer graph is traversed once per group). cmHC modifies residual connectivity for stability; MTP is retained as an auxiliary training objective; Muon optimizes matrix-valued parameters; DSpark handles inference-time speculative decoding. The released 29B member (Xing4.0-29B-A4B) is 40 layers, hidden 3584, 64 routed experts of size 1024, 4 activated per token + 1 shared, 4B activated, native 256K context, mHC + MLA + MTP.

Design is explicitly hardware-driven: the Ascend 910C has strong Cube matrix throughput but comparatively constrained Vector compute and HBM bandwidth, so the stated objective is "matrix-dominant computation, structural avoidance of Vector bottlenecks, sparse memory access to relieve HBM". Two bottlenecks are targeted: long-context decode latency (MLA shrinks the KV cache but main attention still touches many historical KV states) and non-matrix overhead (normalization, routing, indexing, scheduling grow with depth and depress Cube utilization).

**Systems.** All performance studies run on a 1,024-NPU Ascend profiling cluster with sequence length 262,144, global batch 16, TP=4/EP=64/CP=32, using the 285B configuration; production pretraining of the 285B then runs on 8,192 Ascend 910C cards. Table 9 profiles one forward Transformer layer on rank 0 (150 kernels, 115.1 ms) to show execution time and output footprint are poorly correlated — SparseLightningIndexerGradKLLoss costs 38.32 ms for 193 MiB, while AllGatherMatmul emits 656 MiB for 15.90 ms — which is why the recomputation decision is a two-dimensional knapsack rather than a size-sorted heuristic. Host-side, CPU affinity is applied at three granularities (job set T, device pool Tᵢ, role-specific subsets of Tᵢ) crossed with core isolation on/off, giving six configurations evaluated on 512- and 8,192-card clusters.

**Post-training.** Three cooperating layers: TeleGym (environment/session/sandbox execution, black-box and white-box harness adapters, common episode lifecycle), an intermediate server (turns model interactions into training groups, records sampled tokens, behavior-policy log-probs and policy versions, aligns context/response tokens and builds generated-token masks, routes scores back by request/execution identity), and Slime (rollout scheduling + policy optimization over SGLang generation). Task synthesis reuses the same execution interfaces: multiple harnesses propose tasks, then attempt each other's tasks independently from identical initial state, with executable tests or model-based graders filtering and deduplicating. Evaluation is task-typed — executable tests for code, transcript/artifact grading for general agents, direct rollout + answer grading for math.

## Results & Highlights

- **Attention ablation (simulated, 285B, 256K context, 32 cards, P/D disaggregation, all normalized to MLA-only):** MLA+DSA reaches KV HBM access 0.85×, TTFT 0.37×, TPOT 0.84×, prefill throughput 2.67×, decode 1.18×; adding cross-layer IndexShare reaches 0.80× / 0.21× / 0.79× / **4.68×** / 1.27×. The 4.68× headline is the paper's most-quoted number and is *not* a hardware measurement — it comes from Huawei's Zhanlu simulation framework, and the authors state the results "may be more optimistic than full end-to-end deployment measurements."
- **Depth-width ablation (also simulation plus real-system training runs):** against a 60-layer / expert-FFN-1536 / 6-activated baseline, the selected 45-layer / 2048 / 8-activated topology gives relative TTFT 0.83×, TPOT 0.90×, prefill throughput 1.20×, decode throughput 1.11×, and roughly **+10%** large-scale training throughput. Only two points are compared, and three variables move together (layers 60→45, expert intermediate 1536→2048, activated experts 6→8), so the +10% cannot be attributed to depth alone.
- **Speculative decoding (285B, output tok/s Base / MTP3 / DSpark):** GSM8K 35.4 / 63.7 / **115.8** (MTP3 1.80×, DSpark 3.28×, DSpark/MTP3 1.82×); MATH-500 36.8 / 70.0 / **128.1** (1.90× / 3.49× / 1.83×); HumanEval 35.7 / 64.1 / **134.7** (1.80× / **3.77×** / **2.10×**, the largest DSpark/MTP3 gap); MBPP 37.1 / 70.0 / 132.0 (1.89× / 3.56× / 1.89×); AIME25 37.0 / 71.5 / 109.2 (1.93× / 2.95× / 1.53×); LiveCodeBench 35.6 / 64.5 / 95.2 (1.81× / **2.67×** / 1.48×). DSpark's advantage over MTP3 shrinks from 2.10× on HumanEval to 1.48× on LiveCodeBench — i.e. the gain is smallest exactly on the hardest, longest-output reasoning workload.
- **Pipeline-parallelism removal (285B, 1,024 NPUs, 262K seq, global batch 16):** PP-1F1B (pp=4, vpp=1) 36.4s → PP-interleaved (vpp=2) 34.2s (6.0% step-time cut, 1.06×) → HSDP with pp=1, dp 4 replicate × 2 shard, mbs 2: **31.8s, 12.6% reduction, 1.14× speedup**. The paper also notes that at p=4 stages and m=8 micro-batches the 1F1B bubble is (p−1)/(m+p−1) = 3/11 ≈ 27%, which is a much larger structural loss than the 6.0% that interleaving actually recovers — the measurements and the idealised bubble model do not line up, and the report does not reconcile them.
- **Stacked single-feature ablations against the HSDP+Muon baseline of 28.9s:** fine-grained selective recomputation → **26.9s** (6.9%, 1.07×); layer-wise indexer backward → **24.5s** (15.2%, 1.18×, the largest single-feature gain). Each is measured *independently* against the same baseline; no run applies all three together, even though naive multiplication of the three factors would predict ≈22.8s.
- **Host-side (285B pretraining, MindSpore HyperParallel):** CPU pinning + core isolation together raise training throughput by **1–2% on the 512-card cluster** but **5–10% on the 8,192-card cluster** — a clean demonstration that host scheduling contention scales with cluster size rather than being a constant overhead.
- **Numerical-equivalence check for the DSA layout pipeline:** a weighted combined comparison on 8 devices / 8 layers / 16K sequence with TP2/CP4, 8 steps per configuration, gives maximum absolute differences of **0.000530** (main loss) and **0.000441** (MTP loss) — the only numerical-fidelity evidence in the entire report.

## Authors & Credibility

Xingchen AGI Lab (China Telecom) with Huawei and Harbin Institute of Technology (Shenzhen); ~150 authors listed alphabetically in Appendix A, a large-team industrial report rather than a small-group paper. Credibility positives: this is the sixth-plus entry in a documented TeleChat lineage (TeleChat 2024, TeleChat2/2.5/T1 2025, TeleChat3-MoE 2025), the 29B member is actually released on the Ascend/MindSpore stack, and the claims are tied to named hardware and named frameworks (MindSpore HyperParallel, HyperParallel-FSDP, MindFormers, SGLang, Slime). Credibility limits: the report is largely a description of an internal production system, so nothing here is independently reproducible — the profiling cluster, the Zhanlu simulator, the TeleGym sandbox layer and the 285B checkpoint are all unavailable, and there are no released logs, configs, or data-mixture details.

## Critical Assessment

**Novelty is integration, not invention, and the paper mostly says so.** Every named component is external: MLA (DeepSeek-V2), DSA (DeepSeek-V3.2), IndexShare (IndexCache / Z.ai), MTP (DeepSeek-V3), DSpark and DFlash, Muon, FSDP, mHC/cmHC. The genuine contributions are the owner-based Muon execution, the object-based exclusion knapsack with boundary-placeholder handling, the layer-wise indexer backward, and TeleGym's async/partial-rollout bookkeeping. That is a respectable systems contribution, but it sits uneasily with a title promising "advancing frontier agentic models."

**The single biggest red flag: there is not one model-quality number in 32 pages.** No MMLU/MMLU-Pro, no GPQA, no AIME accuracy, no SWE-bench, no τ-bench, no agent success rate — for either the 285B or the *open-sourced* 29B. GSM8K, MATH-500, HumanEval, MBPP, AIME25 and LiveCodeBench appear only as throughput workloads. This matters twice over: (a) a reader cannot judge whether the architecture choices preserved capability, and (b) **throughput on a reasoning benchmark is confounded with output length and answer quality** — a model that emits shorter or worse reasoning chains scores a higher tokens/s. Without paired accuracy, the 2.67×–3.77× DSpark speedups and the 1.48×–2.10× DSpark-over-MTP3 margins are not interpretable, especially since speculative decoding acceptance rates typically decay at long context and the benchmark context length is never stated.

**Arithmetic and reporting inconsistencies that a careful reader will trip on.** (1) The abstract claims "a 16.1% throughput improvement from eliminating pipeline parallelism," but Table 7 reports 36.4s → 31.8s, which is a 12.6% step-time reduction and 1.14× (≈14.5% throughput) — 16.1% matches neither and has no supporting table row. (2) §3's summary sentence says the three optimizations reduce step time "relative to the HSDP baseline of 31.8 s," while Tables 8, 10 and 11 all measure against **HSDP + Muon = 28.9s**; the percentages are only correct against the latter. (3) The prose says "the largest output in the layer occupies 516 MiB yet costs only 13.47 ms" (SparseFlashAttention), but Table 9 lists AllGatherMatmul at **656 MiB** for 15.90 ms — its own table contradicts the sentence, and a reader relying on the prose would mis-rank the operators. (4) The 27% idealised pipeline bubble versus the 6.0% recovery from interleaving is asserted without reconciliation.

**Missing ablations that would have made the systems claims much stronger.** The three post-training-side optimizations (Muon owner, selective recompute, indexer backward) are each reported in isolation against one baseline and never combined, so the reader learns nothing about whether they overlap — 9.1% + 6.9% + 15.2% obviously do not add to 31.2% (that would be 19.8s), and a single 4-row cumulative table would have settled it. The depth-width study is a two-point comparison with three simultaneous variable changes. The selective-recomputation knapsack is solved from **one rank-0 layer profile** (150 kernels, 115.1 ms) and the activation-memory budget M is never stated numerically, so the strategy's transferability across layers, ranks and sequence lengths is unverified. For a training report, the absence of the token budget, learning rate, data mixture, loss curves and any training-stability metric (loss spikes, router collapse, overflow events) is a conspicuous gap — the report's own framing is "training infrastructure," yet it reports no training outcome other than wall-clock step time.

**Attention numbers are simulation, and the paper is honest about it — but the honesty is buried.** The 4.68× prefill and 0.21× TTFT come from Zhanlu, not from real serving, and the caveat appears in §2.2 body text, not in the abstract where the number is headlined. There is also no hardware control group: nothing on the same model is run on H800/GB200-class GPUs, so it is impossible to tell how much of the design is "Ascend-specific adaptation" versus a reasonable choice everywhere. The claim that "MLA+DSA+IndexShare reduces KV HBM access to 0.80×" is a simulation output that a reader may easily mistake for a measured counter.

**TeleGym is described, not evaluated.** For the entire post-training half of the report there is no experiment: no RL curve, no comparison of synchronous vs. asynchronous training at matched compute, no measurement of how bounded oversampling or partial rollout affects sample efficiency or policy staleness, no numbers for the lookahead window or staleness threshold. The design reasoning is sound — retaining sampling-time log-probs and rejecting whole query groups on stale trajectories are the right choices — but "we built it and it works" is the level of evidence presented.

**Minor but real:** the KV-compaction equivalence check (8 devices / 8 layers / 16K / 8 steps, max |Δ| 5.3e-4) verifies that the layout pipeline does not break short runs, not that the 285B production run is numerically equivalent; the authors themselves note that reordering execution and batching kernels "can change floating-point results," which is exactly the kind of drift this check cannot rule out at scale. And there is no discussion of what happens when the release-mode 29B model is served with DSpark at 256K context, which is the configuration users will actually run.

## Strengths

- A genuinely useful and hard-to-find artifact: a full engineering account of training a 285B MoE on a non-NVIDIA stack, with named frameworks, named hardware, and the production cluster size (8,192 Ascend 910C) stated rather than hedged.
- Each systems optimization is isolated against a **fixed** baseline with the parallelism layout held constant (e.g. Table 8 keeps the HSDP layout of Table 7 and changes only the optimizer path), which is the right experimental discipline for attributing system-level wins.
- **Unusual candour.** The report repeatedly refuses to overclaim: the selective-recomputation memory budgets are called "heuristics rather than a global memory bound"; the indexer-backward section says "this must not be described as a zero-memory-cost design"; the Muon section says keeping per-matrix orthogonalization domains is "not a guarantee of bitwise equivalence or unchanged convergence"; communication overlap is "opportunistic"; the fixed head-tail pairing "cannot guarantee equal load or an optimal cost." This is rarer than it should be and makes the numbers easier to trust within their stated scope.
- The host-side result (1–2% at 512 cards vs. 5–10% at 8,192 cards from the same pinning+isolation change) is a small but clean and generalisable finding: host scheduling contention is a scale-dependent tax, not a constant.
- The recomputation knapsack framing — cost = measured time, weight = measured output bytes, solved per layer — plus the boundary-placeholder trick is a neat, reusable idea that is more principled than "checkpoint every k-th layer," and the profiling table that motivates it (38.32 ms/193 MiB vs 15.90 ms/656 MiB) makes the case concretely.
- TeleGym's separation of concerns (execution identity vs. token-level trajectory; execution-level rather than segment-level reward grouping; whole-group rejection on stale members) is a thoughtful answer to a problem many async-RL papers hand-wave.

## Limitations

- **No capability evaluation whatsoever** — the report cannot support any claim about model quality, and its title's "frontier agentic models" is unmeasured.
- No baseline against any GPU-trained model, so the Ascend design choices cannot be decomposed into platform-specific adaptation and generally-good practice.
- Attention and depth-width results are simulation-derived; the paper concedes they may be optimistic.
- No combined ablation of the three single-feature optimizations; no sensitivity to sequence length, cluster size (beyond 512 vs. 8,192 for the host experiment), or batch shape for the HSDP results, which are all reported at exactly one point (262K, 1,024 NPUs, gbs 16).
- No pretraining data composition, token count, learning-rate schedule, or loss/stability telemetry, so training efficiency cannot be normalised per token and the MoE stability story on a new stack is untold.
- Speculative-decoding numbers omit acceptance length, draft-model cost breakdown, context length, and any accuracy delta under speculative decoding.
- TeleGym and the entire RL post-training pipeline are described without a single measurement.
- Internal inconsistencies (16.1% vs. 12.6%; 28.9s vs. 31.8s baseline attribution; 516 MiB vs. 656 MiB "largest output") suggest the tables were assembled from separate runs and lightly edited, which lowers confidence in the less-checkable numbers.
- Reproducibility is effectively nil: proprietary cluster, proprietary simulator, unreleased 285B checkpoint and no configs.

## Relevance

高度贴合 **Compute Infrastructure for Large-Scale ML**（1,024/8,192 卡规模的并行策略、集合通信重叠、流水线气泡消除、主机侧 CPU 争用与 straggler）与 **Model System Cards & Technical Reports**（国产芯片上的前沿模型技术报告）；其可选相关性在于 **Reliability under Extreme Performance Optimization**——DSpark 投机解码只报了吞吐、没报任何精度变化，而这正是该方向关心的"优化换来的能力退化"缺口；另外文中明确承认"重排执行与算子批处理会改变浮点结果"、并只给出 5.3e-4 量级的短程等价性检查，对 **Operator Precision, Determinism & Error Propagation** 也是一个有价值的（反面）案例。

## Questions for Further Exploration

1. What are the actual capability numbers for Xing4.0-29B-A4B versus Qwen3-30B-A3B / Hunyuan-A13B at matched activated-parameter budget, and did the 45-layer wider-shallower choice cost anything in quality versus the 60-layer baseline?
2. Do the 2.67×–3.77× DSpark speedups survive at 256K context, and what is the acceptance length and per-token accuracy delta there? Is there a context length beyond which DSpark falls below MTP3?
3. What is the combined step time when owner-based Muon, selective recomputation and layer-wise indexer backward are all enabled — additive, sub-additive, or partially conflicting? A four-row cumulative table would resolve this.
4. Where does the abstract's 16.1% pipeline-parallelism throughput gain come from, given Table 7's 12.6% step-time reduction? Is there an unshown run at a different configuration?
5. How sensitive is the recomputation knapsack solution to the activation-memory budget M, and does a rank-0, single-layer profile generalise to other ranks and to 1M-token sequences where the indexer graphs dominate?
6. Does asynchronous training with partial rollout measurably beat synchronous GRPO at matched wall-clock and matched sample count on the same agent tasks — and how much does the stale-group rejection filter cost in throughput?
7. How much of the Ascend-specific design (wider-shallower, DSA+IndexShare, object-based exclusion) would still be selected if the same 285B model were trained on an H800-class cluster with abundant HBM bandwidth?
