01 Methodology · certify, don't pre-pay

GEMM is ABᵀ over decoded MXFP4 operands. Because E2M1 elements sit under a shared power-of-two E8M0 block scale, a row can be written x_k = λ_x·a_k with integer a_k, so the exact dot product is λ·Σa_k b_k. If Σ|a_k b_k| < 2²⁴, every partial sum fits in 24 significant bits and FP32 accumulation is exact for every summation tree — the Ozaki-style error-free condition, checked at runtime instead of reserved offline.

The condition is tested from row statistics (L=Σ|v|, M=max|v|, Q=Σv²) emitted for free during quantization: min(L_aM_b, M_aL_b, √(Q_aQ_b)) bounds the sum at a cost independent of reduction length K. Passing outputs keep the vendor kernel untouched. Failing ones escalate. Merging aligns units by exact power-of-two shifts and adds as integers under int32/FP64 capacity checks, so associativity and commutativity make the result independent of shard count, merge order and reduction tree.

Layout invariance: MX blocks are assigned by global element position, so TP shards and DP/micro-batch contributions are disjoint partial sums of one reduction. Attention merges numerator and denominator exactly, then rounds the quotient once (RN32(n_i/ℓ_i)) — an exact split-KV. Per-row pruning thresholds are fixed, so pruning is layout-invariant too.

  1. STEP 01 Quantize + emit stats 4-bit codes, E8M0 scales, and L/M/Q in one pass; weight stats cached between optimizer updates.
  2. STEP 02 Certify rows One inequality per output group, valid for all orders. Cost does not grow with K.
  3. STEP 03 Route or escalate Native kernel if certified; else block bound → tight bound → exact repair kernel, with GPU-resident flags.
  4. STEP 04 Merge exactly Shift-aligned integer sums under capacity checks; identical bits whatever the partition.

06 Strengths

  • Load-bearing insight: block-scaled low-bit formats are integers under a power-of-two scale, so exactness is a cheap runtime question, not an offline worst-case design.
  • Sound by construction: every tier’s rounding allowance is derived, not assumed, so the certificate cannot go unsound because its own evaluation rounds.
  • Covers the awkward cases most determinism papers skip: TP/micro-batch weight-gradient partials, attention numerator/denominator, pruning reference.
  • Right verification standard: parameter and optimizer hashes, not just loss curves — plus the 32/32 vs 0/32 inference table.
  • Format-generic (MXFP6, NVFP4, MXFP8), which outlives a single-format hack.

07 Limitations

  • The evidence gap: cross-vendor identity only where no reduction is split; all reduction-splitting runs are MI350X-only. Two vendor stacks, one CUDA/ROCm generation.
  • Narrow regime: 8B–14B dense models, 200 steps at 1×4096, 4K/16K sequences; no MoE, no long context, no production run.
  • No quality result: no convergence or downstream comparison between the exact and non-exact trajectories.
  • Large integration surface: GEMM, attention, gradient collectives, autograd and end-of-step commit must all be replaced; no code release.
  • Fragile assumptions: per-kernel guarantees (zeroed accumulators, exact FP32 products, no BF16 intermediate) plus identical quantizer codes across vendors — a pinned Tensile version hints a bump could break it.

08 Reading it with suspicion

  • Baseline commensurabilityThe 1.24× BF16 speedup compares implementations: torchtitan uses different data, random init and different TP communication volume. The E/T overhead ratio is more defensible — same structure, only exactness swapped.
  • Cost accounting is partialRepair work counts repair dot products, not all repair arithmetic; Table 6 sums nominal FLOPs rather than measuring time; the 83–88% slowdown attribution comes from instrumented traces that include profiling overhead.
  • The inference demo is a toy32 questions, one model, greedy decoding. The twin’s 0/32 under TP4 is striking, but deterministic BF16’s 25/32 is the more interesting failure and is left undiagnosed.
  • Unexplored design choiceThe fixed per-row pruning threshold is never ablated against a tighter reference that would prune more — and the 50× repair-rate gap between 14B TP4 and the 8B models is not explained.

09 Open questions

  1. Why never run the cross-vendor test with an actual split reduction — TP2 with K-splitting, or DP2? Memory constraint, or an expected certificate failure?
  2. What drives Qwen3-14B TP4’s 0.97% repair rate versus <0.02% for the 8B models — width or layout?
  3. At 20k steps, once the trajectories have genuinely diverged, what does exactness cost in loss?
  4. Could a vendor GEMM accumulate in something narrower than documented FP32? Would the sign-cleared tight-bound GEMM work as a runtime probe?
