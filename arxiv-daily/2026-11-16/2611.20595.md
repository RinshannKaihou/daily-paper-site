> **一句话总结：** 作者提出 SilentGuard——把"这个工具返回值能不能信"的判断从模型手里移到运行工具调用的 harness 里，用计数恒等式、记录成员检查、参数白名单等不变式对每个结果做在线校验并触发补查询，验证失败两次就扣留该值（只接受通过检查的计数），在自建 AgentOrchBench 上把 7 个开源模型的错误答案率从 74.0% 压到 1.7%、3 个前沿模型从 70.2% 压到 0.5%，且无故障任务准确率不掉（84.9% vs 84.9%），代价是大量弃答而非恢复。

> **TL;DR:** SilentGuard is a harness-level guard that tests every tool result against API invariants (a count identity `N(F) + N(F∧¬C_k) = N(F_<k)` issued as extra queries, record-membership checks, a published-parameter whitelist, and a value-swap probe), re-checks failures once, and withholds values that break an exact check. On the authors' AgentOrchBench (36 count tasks, 2 seeds), wrong answers under injected silent faults drop from 74.0% (no guard) to 1.7% across 7 open models (self-verification, the best baseline, leaves 56.2%) and from 70.2% to 0.5% on GPT-5.6 Sol/Terra/Luna, with clean accuracy unchanged at 84.9%; on 9 real public APIs given slightly wrong docs, wrong answers fall 89.8% → 21.3%, but a plain parameter whitelist alone already reaches 21.0%, so most of that gain is spec-checking rather than invariant reasoning.

## 核心贡献

- **对真实 API 的静默失败做了系统测量**：在 15 个公开研究型 API 上发现 11 个至少存在一种静默故障；10 个对"拼错名字的过滤参数"返回 HTTP 200 加未过滤计数，其中 ChEMBL 返回 2,921,148 而正确答案是 4,225（虚高 691 倍），UniProtKB 83 倍、arXiv 67 倍、NCBI gene 24 倍。
- **把"是否可信"的决策从模型移到 harness**：提出 SilentGuard，用精确不变式（计数恒等式、记录成员、参数白名单）与从干净响应中挖掘的学习式契约检查每个结果，失败后自动补查询复核一次，再按检查的误报率决定"扣留 / 警告 / 放行"。
- **用受控实验拆开三个要素**：证据（补查询得到的检查结果）、许可（允许回答"无法确定"）、执行（harness 是否真正扣留）。结论是三者缺一不可，且只有"执行"能让效果跨模型稳定：单给警告仍留 70.1% 错误，警告加弃答许可降到 18.2%（但模型间 0–59% 波动），harness 扣留则到 1.7%。
- **揭示"模型看见了却照样回答"的现象**：一个看到检查结果的 LLM judge 能标出 82.4% 的故障运行，但 agent 在被标出的运行中仍有 77.4% 直接报出被标记的计数；置信度从 1.00 掉到 0.43、40% 的错误答案还主动提到了警告，说明问题不在感知而在默认行为。
- **给出失败模式的反面证据**：自动修复（auto-repair）在它被设计的故障上能恢复 57.3% 的正确计数，但在方法冻结后新写的 6 类故障上，把 49 个错误计数当作"已验证"释放出去——这比不给答案更糟。
- **发布 AgentOrchBench 与全部代码/预测日志**：36 个计数任务、30 个列表任务、零售 schema、8 个本地 REST 服务与故障注入器，并在实验前把 39 条预测写进日志（26 条成立、13 条明确报告失败）。

## Key Contributions

- **Measurement of silent API failures at scale.** Probing 15 public research APIs with an unfiltered query, the documented filtered query, and 2–3 plausibly misnamed filter names, the authors find 11/15 exhibit at least one silent fault. Ten return HTTP 200 with the unfiltered count (ChEMBL 691× high, UniProtKB 83×, arXiv 67×, NCBI gene 24×, Europe PMC 19×); 6/14 silently cap page size; 3 silently drop a filter whose *value* has a typo. A value-swap probe catches 26 of 28 ignored filter names.
- **Harness-enforced invariants instead of model self-checking.** Exact checks (count identity, record membership, published parameter list) prove that a broken result did not answer the request; learned contracts mined from clean traces only warn, because they can themselves be wrong. `π(r)` = release / withhold / warn, with `α̂_j = 1/(n_j+2)` and cutoff `τ = 1%`; exact checks have `α̂ = 0`.
- **A controlled decomposition of evidence, permission, and enforcement**, showing that the same evidence changes nothing as advice (71.2% wrong) but almost everything when the harness blocks on it (6.1% wrong), and that permission to abstain only helps in the presence of evidence (73.3% → 18.2%).
- **A quantitative account of why agents fail here**: faults are never signalled, the response is internally consistent, and no check on the response alone can reveal the fault — extra queries to the same endpoint are required.
- **AgentOrchBench**, with exact answers computed from seed data (no judge needed), six design-time fault types plus six written after the method was frozen, a second retail schema, and all eight services reset per task.
- **Pre-registration practice**: code frozen by file hash, runs refuse to start if the code changed, and 39 predictions logged before the runs.

## Methodology

**Problem definition.** A tool call is a request `q` and a response `r`; a *silent failure* is a response with a success status whose content does not answer `q` (a filter ignored, a condition misread, a total capped). Nothing in `r` marks it, and because `r` is internally consistent, no response-only check can detect it.

**Exact checks.** For a filtered count query `F = C_1 ∧ … ∧ C_k` returning `N`, the harness issues the two complement queries itself and tests, at every position `i`:

```
N(F) + N(F_<k ∧ ¬C_k) = N(F_<k)
```

so an ignored filter at any position is caught (2k extra queries per filter call, at most 6 here). For list answers it additionally checks that every returned record meets the filter, that no record repeats, and that list size matches the reported total. When the API publishes its parameter list (*spec check*), a request with an out-of-spec parameter is rejected before it runs; for in-spec parameters a *value-swap check* re-issues the query with the filter's value changed — an unchanged count means the filter was ignored.

**Learned checks.** Mined from clean traces (field presence/type, echoed arguments, positive values, categorical values, linear relations, date order), following the Outcome Monitors contract miner, with 5-fold cross-fitting by task so a contract is never mined on the workflow it checks. False-alarm estimate `α̂_j = 1/(n_j+2)` by the rule of succession.

**Action rule.** Every result is checked; a failure is re-checked once (same call, released only if the second response passes). If it fails again: exact check (`α̂_j ≤ τ`, `τ = 1%`) → **withhold** the value and tell the agent which value could not be verified and which other tool could redo the step; learned check → **warn**, keeping the data visible with the failed property named. On count answers the withhold becomes an answer rule: only a count from a query that passed a check is accepted, a non-passing count is rejected twice, then the harness answers that the count cannot be determined. A count counts as verified only if it came from a checked query with at least as many conditions as any other query in the run. SilentGuard never repairs a value itself and makes no extra LLM call.

**Benchmarks.** AgentOrchBench: 36 count tasks (400 synthetic catalog records, 2–3 conditions each) and 30 list tasks over 8 local REST services, agent protocol restricted to one `curl` per turn or an `ANSWER:` line, faults injected server-side and repeated on every call, exact grading from seed data. Retail domain: a second schema (orders API, 30 count tasks, 4 fault types). Real APIs: 9 APIs × 5 count tasks, with either correct documentation or documentation containing one misnamed filter. ToolMaze: 180 never-used workflows with P0–P4 fault modes, scored by its own judge. τ-bench retail with two silent read faults. Baselines: no guard, caution prompt, LLM judge (gpt-oss-120b, sees the check results), self-verification, blind retry, re-query, plus checklist, reviewer, and Outcome Monitors, plus harness-action ablations (warning, warning + tip, answer gate, Enforce, auto-repair).

**Models and protocol.** 7 open-weight models (Phi-4, gpt-oss-120b, Gemma-3-27B, Llama-3.3-70B, Llama-4-Scout, Llama-4-Maverick, Nemotron-3-Ultra) at temperature 0; 3 frontier models (GPT-5.6 Sol/Terra/Luna) at provider default. 2,000 output tokens per turn, 16 turns (25 on ToolMaze). Mean over models with SE, task-cluster bootstrap for key differences, exact sign-flip tests over models.

## Results & Highlights

- **Real APIs, silent-failure prevalence and magnitude.** Of 15 public research APIs, 10 return HTTP 200 with the unfiltered count for a plausibly misnamed filter: ChEMBL 2,921,148 vs 4,225 correct (**691×**), UniProtKB 55,460 vs 666 (83×), arXiv 186,698 vs 2,799 (67×), NCBI gene 37,885 vs 1,567 (24×), Europe PMC 291,095 vs 15,436 (19×); 11 of 15 show at least one silent fault of any kind. The value-swap check flagged 26 of the 28 ignored filter names with no false alarm on the correctly spelled queries.
- **AgentOrchBench, 7 open models (36 count tasks × 2 seeds).** Wrong answers under silent faults fall from **74.0% ±7.1** (no guard) to **1.7% ±0.5** with SilentGuard, with unknown rising to 95.8% and correct collapsing from 16.4% to 2.4%; clean accuracy is identical at **84.9% vs 84.9%**. The strongest baseline is self-verification at 56.2% wrong (the model runs the same check itself); checklist 72.3%, reviewer 73.8%, Outcome Monitors 72.2%, LLM judge 71.2%, blind retry 74.4%, re-query 74.9%. SilentGuard wins on 7/7 models (exact sign-flip p = 0.016, the smallest attainable with 7 models).
- **Evidence vs. permission vs. enforcement (Table 2).** A warning from the same check leaves **70.1%** wrong; adding permission to abstain cuts it to **18.2%**, but with a 0–59% spread across models; the harness withholding the value reaches **1.7%** (max 4% on any model). A judge that *sees* the check results still leaves 71.2% wrong as advice, versus **6.1%** when the harness blocks on its verdict — and that blocking costs correct answers (3.5% vs 2.4%, unknown 90.4% vs 95.8%).
- **Frontier models.** No guard: 89.4% (Sol), 62.3% (Terra), 59.0% (Luna) wrong, mean **70.2%**; SilentGuard: **0.0 / 0.2 / 1.4%**, mean **0.5%**, with clean accuracy 100.0 / 98.6 / 95.8% (vs 100.0 / 98.6 / 95.8 no-guard — i.e. no clean loss). Told to run the check themselves, frontier models give few wrong answers (4.5%) but collapse on clean tasks (20.4% correct), i.e. they mostly refuse.
- **Real APIs with one misnamed filter.** Wrong answers fall from **89.8% ±5.3** to **21.3% ±3.8**, correct rises from 3.5% to 69.5%, and accuracy with correct documentation is preserved (92.4% vs 92.1%). But the **spec check alone reaches 21.0%** and typed/function-calling tool calls do worse (28.6%), so the gain here is parameter validation, not the count identity. Frontier models on these APIs: 57.8% → **8.9%**.
- **Unseen fault types (written after the method was frozen, harness alone, no model).** On 6 new count faults, wrong answers fall only from **61.1% to 24.5%** and correct from 38.9% to 19.0%; on 5 new list faults, wrong lists fall from 37.8% to **11.5%** while correct lists fall from 56.7% to 7.1%. Where the check fires, SilentGuard never released a wrong count (0/36 on each of partial-shard, cursor-ties and lossy-index).
- **ToolMaze (180 fresh workflows, its own judge).** Silent success 36.0% ±2.5 vs **32.7% ±2.2** for checklist + Outcome Monitors (+3.3 pts, 95% CI [1.8, 4.9]; ahead on 5/7 models), but clean success is **52.5% vs 57.1%** for OM — a 4.6-point clean loss from learned-check false alarms. Blind retry beats SilentGuard on one-call faults (**60.4% vs 47.6%**) and on two-call faults (56.0% vs 46.4%).
- **Auto-repair is dangerous out of distribution.** On the fault types it was built for, auto-repair recovers 57.3% correct counts (vs 2.4% for SilentGuard); on the 6 fault types written after freezing it returned more correct counts (79 vs 41) but **102 wrong ones, 49 of them marked as verified** — indistinguishable from correct answers to a user.
- **Perception without action.** The judge flags 82.4% of faulted runs (13.9% of clean ones); agents report the flagged count anyway in **77.4%** of flagged runs and in 64.4% of warned runs; stated confidence drops from 1.00 to 0.43 and 40% of wrong answers mention the warning.
- **Secondary domains.** Retail schema: wrong 78.6% → **11.0%**, clean 36.2% → 38.5%. iNaturalist wrong date-format documentation: 97.1% wrong unguarded, **100.0%** with the spec check (the parameter name is valid), 20.0% with SilentGuard but only 2.9% correct and 77.1% unknown. Risk–coverage at a 25% fault rate: SilentGuard 3.3% risk at 67% coverage vs 24.6% risk at 90% coverage for no guard.
- **Cost.** 18.9 s, 9,055 tokens, 3.8 tool calls per faulted run, vs 9.2 s / 3,183 / 2.0 for no guard and 47.2 s / 6,287 for the LLM judge; no extra model call. The all-conditions check costs 5.2 extra queries per clean filter call and catches 97.2% of faulted results; checking only the last condition catches 88.0%.

## Critical Assessment

*Novelty.* The core idea — use metamorphic relations / query partitioning as an *online* per-call oracle and let the harness, not the model, act on the verdict — is a genuine and well-motivated reframing. The components are borrowed (count identity from Rigger & Su's query partitioning, learned contracts from Outcome Monitors, abstention from selective prediction), and the paper says so. Its real claim is architectural: the decision locus matters more than the detector. That claim is supported, and the "evidence without enforcement is worthless" result (82.4% flagged, 77.4% answered anyway) is the most useful finding in the paper.

*Rigor — strong where it is cheap, thin where it matters.* The 74.0% → 1.7% headline is measured on the authors' own servers, where every fault repeats on every call and every answer is graded against seed data — the most favorable possible regime for a check that re-queries. The honest stress test is the frozen-then-new-fault experiment, and there the number is **61.1% → 24.5%**, not 1.7%. Similarly, the 89.8% → 21.3% real-API headline is almost entirely the spec check (21.0% alone), which is a parameter whitelist — useful engineering, but not the invariant machinery the abstract advertises; and the split is stark (38.6% wrong on the 4 APIs chosen before freezing, 7.4% on the 5 added later), which suggests the pre-freeze set was not representative. The abstract's "counts inflated up to 691 times" rests on a single ChEMBL outlier; the median overcount across the 10 misbehaving APIs is around 4×.

*The cutoff machinery is essentially untested.* `α̂_j = 1/(n_j+2)` with `τ = 1%` is presented as the principled heart of Eq. 2, but on ToolMaze the largest support among 2,448 withhold-or-warn decisions is 52 clean examples, so *no learned check ever reaches τ* and the policy collapses to "exact → withhold, learned → warn." The sensitivity table (every cutoff below 1.85% gives identical decisions) is presented as robustness but actually shows the parameter was never exercised. The paper concedes the 1% was chosen after seeing earlier results.

*Baselines.* The published methods were re-implemented with prompts the authors wrote (App. C), and the LLM-judge baseline had to be upgraded from GPT-4o-mini — which "called correct responses suspect even when given the passing check numbers" — to gpt-oss-120b. That is a defensible fairness move, but it also means the comparison depends on prompt authorship and judge choice, and only one judge model was tried. On ToolMaze the margin over checklist + OM is 3.3 points with p = 0.125 across 7 models, which the paper reports honestly but the abstract does not qualify. On τ-bench, SilentGuard merely ties the published methods (App. J) — absent from the abstract.

*Abstention, not repair, and the cost is real.* Correct answers fall from 16.4% to 2.4% on AgentOrchBench and from 56.7% to 7.1% on unseen list faults; on the iNaturalist date-format task SilentGuard is right only 2.9% of the time. The risk–coverage framing is the right way to present this, and the λ* analysis (Table 16) is a nice touch, but a practitioner reading "1.7% wrong" should also read "95.8% unknown." Auto-repair's 49 verified-but-wrong releases are a strong argument against repair, yet the comparison is somewhat rigged by construction: auto-repair is evaluated on faults it was never built for, which is exactly the point, but SilentGuard is never evaluated on a fault class where its own invariants are the wrong tool and a repair heuristic would win — apart from blind retry on one-call faults, where it loses (60.4% vs 47.6%).

*Reproducibility.* Good on the open side: code, injectors, benchmark, tasks, prediction log and hashes are released, and the 13 failed predictions are listed. Weak on the frontier side: those runs were added after the planned experiments, with no predictions, on an internal platform, with no logs and no hash records, so the 0.5% figure cannot be audited or recomputed. Three frontier models from one vendor is also a narrow sample for a claim about "frontier models" generally.

*Red flags to note.* (i) The headline 1.7% and the 0.5% frontier number both come from the same favorable regime (repeating, exactly-injectable faults on self-built servers), while the paper's own out-of-distribution experiment says 24.5%. (ii) The learned-check branch of the decision rule has no empirical support in the regime it was designed for. (iii) The consistent-lie fault defeats every check by construction (2.8% detection) — the paper is commendably explicit that no check built from the API's own answers can help, but this bounds the whole approach to faults that break a checkable identity. (iv) The count identity assumes two-valued filters; missing values need the three-way partition the authors decline to implement, and the identity held on only 25 live queries. (v) Larger fault budgets are cheap (5.2 extra queries per clean call, 3.8 vs 2.0 tool calls) but "cheap" is measured on a local mock service, not on rate-limited production APIs, where the real-API study ran at about one request per second.

## Strengths

- The central architectural claim is well isolated by ablation: same evidence as advice → 71.2% wrong; as blocking → 6.1%; harness withhold → 1.7%. Very few agent-reliability papers separate detector quality from decision authority this cleanly.
- Genuinely useful negative results, reported rather than buried: blind retry beats SilentGuard when faults clear within one or two calls; auto-repair emits wrong answers marked as verified; the learned-check cutoff is never reached; τ-bench shows no gain; 13 of 39 predictions failed.
- Real-API measurement with concrete, checkable numbers (ChEMBL 691×, page-size caps on 6/14 APIs, typo'd filter values on 3 APIs) turns "APIs fail silently" from an anecdote into a quantified phenomenon.
- Cost analysis is unusually complete for this literature: tool calls, tokens, wall time, extra LLM calls, and extra queries per clean call, plus a cheaper randomized-position variant that keeps 97.2% detection at 2.3 extra queries.
- Excellent reproducibility hygiene on the open-source side (hash-frozen code, pre-registered predictions, released fault injectors and benchmark).
- The 84 documented operations in 13 APIs (61 allow an exact check, all allow a spec check) gives practitioners a concrete map of where this technique applies.

## Limitations

- Faults are injected by the authors' own servers; only three fault kinds (ignored parameter, capped page, ignored filter value) are verified in real APIs, and the other nine types — including all the ones where SilentGuard looks best — are synthetic by construction.
- Abstention dominates: 95.8% unknown on AgentOrchBench and 77.1% unknown on the value-format study. Users get safety, not answers, and the paper does not measure downstream task utility (e.g. whether an agent can complete a multi-step workflow after a withhold).
- Blind spots are structural: prefix matching, a consistently lying API (2.8% detection), filters the agent never sends, and filters embedded inside query strings (NCBI, UniProt, Europe PMC, arXiv) are all invisible to the parameter and value-swap checks.
- The count identity assumes two-valued filters and stable totals; four wrong answers in the value-format study passed because the live total drifted between the request and the check. The three-way partition needed for missing values is not implemented.
- Frontier-model results (70.2% → 0.5%) come from one vendor, on an internal platform, without logs, hashes, or pre-registered predictions; they should be read as a demonstration rather than a measurement.
- Only 7 models for model-level tests (minimum attainable p = 0.016), and a single judge model for the LLM-judge baseline.
- The decision threshold τ was set after seeing earlier results, and no learned check ever reaches it, so Eq. 2's second branch is untested.
- Clean-accuracy cost appears on ToolMaze (−4.6 points vs Outcome Monitors) and is attributed to learned-check false alarms, but the paper does not quantify how often those false alarms fire per workflow.

## Relevance

与"LLM agent 工具调用可靠性 / agent harness 工程 / 工具失败评测"这条线高度相关：它把"模型自检不可靠"从直觉变成了可量化的实验（82.4% 被标出、77.4% 照样作答），并给出一个可直接落地的 harness 侧方案——对计数类查询加补查询恒等式校验、对文档化 API 加参数白名单、失败两次即扣留。对做 agent 评测或多工具流水线的人，AgentOrchBench 的故障分类表和"auto-repair 会把错答案标成已验证"这条结论，比 1.7% 这个数字更值得带走。

## Questions for Further Exploration

1. What happens to end-to-end task success (not just answer correctness) when the harness withholds? The paper reports 95.8% unknown but never measures whether the agent recovers the workflow through the suggested fallback tool.
2. How does the spec check alone compare on a benchmark where faults are *not* documentation-name typos — e.g. silently dropped date ranges inside a valid query string, where both the spec check and the value swap are blind (the iNaturalist result suggests 20% wrong, 2.9% correct)?
3. Would the 61.1% → 24.5% unseen-fault number improve if the withheld value included a machine-readable failure reason that the agent could act on, rather than just a text note?
4. Is the 691× ChEMBL overcount representative, or does the distribution of overcounts have a long tail that makes the "up to 691 times" framing misleading? What is the median across the 10 affected APIs?
5. How much of the frontier-model result survives if the three models are from different vendors and run with released logs?
6. Can the 2k extra queries be shared across an agent's turns (caching per filter) so the 5.2-queries-per-clean-call cost does not scale with conversation length?
7. Does a harness that withholds on exact checks and *also* allows a bounded number of blind retries dominate both SilentGuard and blind retry alone, given that retry wins on one-call faults (60.4% vs 47.6%) and withholding wins on lasting ones?
