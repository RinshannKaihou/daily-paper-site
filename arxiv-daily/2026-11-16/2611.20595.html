7 open-weight models, 36 count tasks × 2 seeds, faults injected server-side and repeated on every call.

The trade is abstention: correct answers drop 16.4% → 2.4% and 95.8% of runs end in “unknown”.

Why this matters

Your agent’s APIs can return HTTP 200 with the wrong number. Model self-checks still leave 56.2% wrong; blocking at the calling layer is what travels.

Critical edge

The headline 1.7% comes from the authors’ own servers where every fault repeats on every call; on fault types written after the method was frozen, wrong answers only fall from 61.1% to 24.5%.

01 · Method

Check the answer with the API, not with the model

Silent failure, defined. A response with a success status whose content does not answer the request — a filter ignored, a total capped, a parameter value typo’d. It is internally consistent, so no check on the response alone can reveal it.

  • Exact checks. A count identity across every filter position, issued as extra queries; record-membership and list-size checks; out-of-spec parameters rejected before the call runs; a value-swap probe for ignored filters.
  • Learned checks. Contracts mined from clean traces (field types, echoed arguments, linear relations, date order), 5-fold cross-fitted by task, false-alarm estimate α̂j = 1/(nj+2). These only warn — they can be wrong.
  • Action rule. Every result is checked; a failure is re-checked once. Still failing: exact check → withhold the value and name a tool that could redo the step; learned check → warn. A count counts only if it came from a checked query with at least as many conditions as any other in the run.
  • No repair. SilentGuard never rewrites a value and makes no extra LLM call.
N(F) + N(F_<k ∧ ¬Ck) = N(F_<k) 2k extra queries per filter call (≤6 here); an ignored filter at any position breaks the identity.
  1. Call. Agent issues a filtered count or list query; the harness materialises the complement queries itself.
  2. Test. Identity, membership, spec and value-swap checks run on the returned value — not on the model’s belief about it.
  3. Re-check once. A failed result gets a second response; only a pass releases it.
  4. Enforce. Second failure → withhold (exact) or warn (learned); the agent is told which value is unverified.

03 · Field evidence

HTTP 200, filtered by nothing

04 · Ablation

Same evidence, three delivery modes

One experiment isolates what actually changes behaviour: giving the agent the check result, letting it abstain, or having the harness act on the verdict.

Exact check result, delivered as…

A warning only70.1%
Warning + permission to abstain18.2%
Harness withholds the value1.7%

LLM judge sees the check results, but…

Its verdict is advice to the agent71.2%
The harness blocks on its verdict6.1%

Warning + permission still spreads 0–59% across models; withholding stays ≤4% on every model. Judge-blocking also costs correct answers vs SilentGuard (3.5% vs 2.4%).

06 · Where it loses

Reported, not buried

  • ToolMaze: beats checklist + Outcome Monitors by 3.3 pts on silent success (32.7% vs 36.0%), 95% CI [1.8, 4.9] — but p = 0.125 across 7 models, and clean success falls 57.1% → 52.5%.
  • One-call faults: blind retry beats it, 60.4% vs 47.6%.
  • τ-bench retail: it merely ties the published methods; absent from the abstract.
  • Auto-repair releases 102 wrong counts, 49 marked “verified” on fault types written after the method was frozen.
  • The learned-check cutoff (τ = 1%, max 52 support examples) is never exercised; the policy collapses to “exact → withhold, learned → warn”.

Real-API gain 89.8% → 21.3% is mostly the spec check alone (21.0%): a parameter whitelist, not the identity machinery.

07 · Strengths

What the paper earns

  • The architectural claim is isolated by ablation — same evidence: advice 71.2%, blocking 6.1%, withhold 1.7%. Detector quality and decision authority are rarely separated this cleanly.
  • Negative results are reported rather than buried: retry wins on transient faults, auto-repair lies, τ-bench shows no gain, 13 of 39 predictions failed.
  • Real-API measurement turns “APIs fail silently” into checkable numbers: 691× on ChEMBL, page caps on 6/14 APIs, value typos on 3.
  • Cost accounting is complete: wall time, tokens, tool calls, extra queries per clean call (5.2 for 97.2% detection; 2.3 randomized-position variant).
  • Reproducibility hygiene: hash-frozen code, 39 pre-registered predictions, released injectors and benchmark (Apache-2.0 / CC-BY-4.0).
  • 84 documented operations across 13 APIs map where the technique applies — 61 admit an exact check.
08 · Limitations

What it does not cover

  • Faults are injected by the authors’ servers; only 3 kinds are verified in real APIs, and the rest — including the best-looking results — are synthetic.
  • Abstention dominates: 95.8% unknown on AgentOrchBench, 77.1% on the value-format study. Downstream task utility after a withhold is never measured.
  • Structural blind spots: prefix matching, filters inside query strings (NCBI, UniProt, Europe PMC, arXiv), filters never sent, and a consistently lying API (2.8% detection).
  • The count identity assumes two-valued filters and stable totals; the three-way partition for missing values is not implemented, and 4 answers failed on live-total drift.
  • Frontier-model runs (70.2% → 0.5%) come from one vendor, on an internal platform, with no logs, hashes or predictions — a demonstration, not a measurement.
  • Only 7 models for model-level tests (p floor 0.016) and a single judge model for the LLM-judge baseline.
09 · Open questions

What the next paper should test

  1. Does end-to-end task success survive a withhold? The harness names a fallback tool, but recovery is never measured.
  2. Is the 691× ChEMBL outlier representative, or does the overcount distribution have a long tail that makes the framing misleading?
  3. How much of the 61.1% → 24.5% unseen-fault result improves if the withhold carries a machine-readable failure reason?
  4. Would “withhold on exact checks + a bounded blind retry” dominate both, given retry wins on one- or two-call faults?
  5. Does the frontier result survive three vendors, released logs, and pre-registered predictions?
