> **一句话总结：** 作者指出低比特量化的失败不在"短任务准确率"而在"长程 agent 任务"——Qwen3.8-27B 的 3-bit GSQ-RCO 文件在 AIME 上只差 BF16 0.8 分（96.9 vs 97.7），但在 DeepSWE 上只解出 BF16 的 63%；NariQ 因此在 QTIP 格码 + YAQA 双边舍入的骨架上只改四件事：把端到端 KL 的监督位置限制为"模型自己写出的 token"、用梯度反推每个模块自身损失并据此分配位宽、把 lm_head 按 token 预测概率分 16 个 band 且每 band 至少 2 bit、以及用 70:30 的 coding:general 数据微调 scales/norms；最终 3.0 bpw 在 DeepSWE 解 47/113、Terminal Bench 63.8 分，均与 BF16 的 44/113、62.6 分持平，2.5 bpw 也持平，2.0 bpw 掉到 33/113（−7.3 分）。

> **TL;DR:** Re-calibrating and re-allocating a trellis-coded 27B agent model around **model-written tokens from real agent sessions** closes the sub-3-bit agent gap: on DeepSWE v1.1 (113 tasks) NariQ at 3.0 bpw solves 47 tasks vs BF16's 44 and scores 84.9% vs 83.0% (paired +1.9 pts, s.e. 3.2), and at 2.5 bpw 46 tasks / 84.5% — whereas every published ≤3.0 bpw file of the same model solves at most 72% as many, with GSQ-RCO IQ3_XXS at 3.00 bpw managing 29 tasks (63%). On Terminal Bench 2.1 the 3.0 / 2.5 bpw files score 102% / 96% of BF16 (63.8 and 60.2 vs 62.6), and offline agent KL drops from 0.0276 (GSQ-RCO IQ3_XXS, 3.00 bpw) to 0.0063 (4.4×). The catch: 2.0 bpw fails the claim (33/113 DeepSWE, 86.0 AIME vs 97.7), the non-BF16 baselines are copied from Unsloth's *different* harness, and the DeepSWE evidence is 113 one-shot tasks where the paired s.e. alone is ±3.2 points.

## 核心贡献

- **把"低比特量化在 agent 上崩掉"变成一个具体的、可对照的现象**：同一份 Qwen3.8-27B，3.50 bpw 的 GSQ-RCO IQ3_S 在 AIME 上只差 1 分之内，但在 DeepSWE 上只解 40.4/113（88% BF16），3.00 bpw 的 IQ3_XXS 解 29/113（63%）；2.50 bpw 的 GSQ-RCO IQ2_XS 更是只有 19/113（42%）。作者由此论证：perplexity 和短基准筛不出 agent 能力。
- **提出 NariQ 这套"只改监督位置 / 位宽分配 / scale 数据"的后训练配方**：不发明新的权重量化格式（仍是 QTIP bitshift trellis + 计算式 codebook + Hadamard 旋转，如 EXL3），而是改**损失算在哪些 token 上**——校准轨迹里由 BF16 生成的 token 才计入 KL，工具输出与文件内容只作为上下文前缀保留。
- **一种对格码仍然有效的模块级损失估计**：发现 3-bit 误差与 2/4/5-bit 误差的曲率加权余弦仅 0.035 / 0.009 / 0.004，即 RCO 式一阶打分中"目的位宽误差与当前误差对齐"这一项几乎为零、因而失去信息；NariQ 反过来用该内积估计**当前**位宽的损失 ℓ_c，再按码的实测 MSE 比例（每加 1 bit 约降 4×）外推到目标位宽，并用多组位宽分配的逆方差加权合并、取"均值 + 2 个标准误"加正下限。
- **输出层按 token 概率分 band 的非均匀位宽**：利用 KL 对某 logit 的曲率 p(1−p)≈p，把 248,320 行按平均预测概率排序切成 16 个约 15,500 行的 band，每个 band 独立参与位宽分配；因为 1-bit band 在多语等稀有 token 轨迹上反而抬高 KL，硬性规定每 band ≥2 bit（3.0 bpw 下平均 per-trial KL 降 12.1%）。
- **一套自洽的评测与发布**：DeepSWE v1.1（113 题、91 个仓库、5 种语言，Claude Code 驱动、SGLang 服务、每题一次尝试、3 小时上限）与 Terminal Bench 2.1（Unsloth 报告的 82 题、每题 3 次）、外加 AIME 2025+2026 / RealWorldQA / MGSM 与四组 offline KL（含一个从未用于任何选择的 reserve 集）；权重以 GGUF 公开，推理走作者自维护的 llama.cpp fork。

## Key Contributions

- **Diagnoses the failure mode as calibration/objective mismatch, not format capacity.** The paper argues the remaining gap cannot be closed by a better weight format alone: after random rotation weights are near-Gaussian, and on Gaussians QTIP-style trellis codes are already within ~10% of the rate–distortion bound at 2 bits (MSE 0.069 vs 0.063). The lever it pulls instead is *which tokens the loss counts*: standard low-bit recipes calibrate on short web-text chunks and weight every token equally, while an agent's quality is carried by the tokens it writes.
- **Model-token-masked end-to-end KL.** The objective is `L = (1/|M|) Σ_{t∈M} KL(p_BF16(·|x_<t) ‖ p_θ̂(·|x_<t))`, where `M` indexes positions generated by BF16 in real agent traces; both models see the identical prefix including tool outputs, so the mask changes prediction targets only.
- **A gradient-based per-module loss estimator that survives uncorrelated trellis errors.** Because RCO's first-order score collapses to ≈ −2ℓ_c for every k ≠ c, the paper instead averages ½⟨G, W_c − W_k⟩ over k ≠ c to estimate ℓ_c, then predicts ℓ_k ≈ ℓ_c·r_k/r_c using the code's measured MSE, combining several width assignments by inverse variance with a mean + 2 s.e. margin.
- **Budget-constrained width allocation plus an empirically enforced 2-bit floor on every linear layer.** One width per module turns allocation into multiple-choice knapsack, solved by DP over a discretized budget with an exact-cost storage check; a measured failure of the loss model at 1 bit (moving the 12 modules the allocator had placed at 1 bit up to 2 bits cut KL by 7.2% for only 0.021 bpw) motivates banning 1-bit linears.
- **Probability-banded output layer and a 70:30 scale-tuning mix.** lm_head rows are ranked by mean predicted probability into 16 bands of ~15,500 rows, each ≥2 bits; at 2.0 bpw the input embedding is banded too, ranked by input frequency and allowed 1-bit rare-token bands. Scales and norms are then tuned on coding agent traces plus BF16 replies to general prompts (math, science, chat, code, long documents) at 70:30.
- **Public release of weights, plus an honest scope statement** — 3.0/2.5 bpw level with BF16 on all four benchmarks run, 2.0 bpw explicitly trailing, and an appendix that scores every public file of this model under the authors' own KL code.

## Methodology

**Base format.** Each matrix is rotated with randomized power-of-two Hadamard blocks and trellis-quantized with QTIP's bitshift trellis; the codebook is computed from trellis state as in EXL3 so kernels decode inside the matmul, which is why the format needs no Hadamard sizes tied to a particular model dimension. In attention and DeltaNet layers one side of most matrices is first shuffled by a seeded permutation. Rounding is YAQA-style: input-only rounding is kept unless two-sided rounding lowers held-out curvature-weighted error by ≥5%, which happens for almost every module.

**Four changes.** (1) *Model-token loss*: the end-to-end KL is restricted to BF16-generated positions in calibration traces, so long tool outputs cannot dominate. (2) *Per-module loss allocation*: with `ℓ_k = ½⟨E_k, H E_k⟩` and `G ≈ H E_c` measured on a file where every module sits at some width, the paper estimates ℓ_c from the width-direction inner products, extrapolates across widths via the code's MSE ratio (≈4× per bit, so a module's 2-bit loss is predicted at ≈3.9× its 3-bit loss), and solves `min Σ ℓ̂_{m,k_m} s.t. C_fixed + Σ n_m k_m ≤ B·N`. (3) *Banded output layer*: 16 probability bands, each a separate module in the allocation, all ≥2 bits; the 2.0 bpw file also bands the embedding by input frequency with 1-bit allowed for rare tokens. (4) *Scale tuning*: coded-matrix scales and all norm weights optimized on a 70:30 mix of coding agent traces and general-prompt replies.

**Calibration data.** Agent sessions of the BF16 model on open-source software tasks, split by **repository** into calibration / development / reserve sets, with every repository shared with DeepSWE removed — a leakage control that matters because DeepSWE is the headline benchmark. The reserve set is never used for any selection decision, and offline KL is reported on it separately.

**Evaluation.** DeepSWE v1.1 at task-repo commit `0b9fabb`: 113 tasks from 91 repositories in five languages, Claude Code as the scaffold, SGLang serving, thinking on at maximum effort, ≤65,536 output tokens per request, 3-hour cap, one attempt per task, failures scored zero, no reruns; reported as solved count, mean fraction of new tests passed, and paired differences with standard errors. Terminal Bench 2.1: the same 82 tasks Unsloth reports, 3 attempts each, mean test reward with ungraded trials as zero. Outside coding: AIME 2025+2026 (avg@8), RealWorldQA (3 samples), MGSM (1 sample) via simple-evals. Shared settings for every file including BF16: 262,144-token context, temperature 1.0 / top-p 0.95 / top-k 20, no retries.

**Baselines.** BF16 and NariQ files are run in the authors' own harness; every other quantized file (Unsloth Dynamic V3.1, GSQ-RCO, EXL3) is taken from Unsloth's published DeepSWE / Terminal Bench 2.1 numbers, which use mini-swe-agent and ≥3 passes per DeepSWE task. Results are reported as a percentage of each harness's own BF16 — the paper states plainly that this normalization does not remove harness differences. The offline-KL appendix re-scores every published file with the authors' own code, which sidesteps that confound.

## Results & Highlights

- **DeepSWE v1.1, the headline benchmark**: NariQ 3.0 bpw solves **47/113** tasks and scores **84.9%** of new tests passing vs BF16's **44/113** and **83.0%** (paired +1.9 pts, s.e. 3.2); 2.5 bpw gives **46/113 / 84.5%** (+1.5 pts, s.e. 3.6). For reference, the best published ≤3.0 bpw file in Unsloth's table, GSQ-RCO IQ3_S at 3.50 bpw, solves 40.4/113 (88% of its BF16) and GSQ-RCO IQ3_XXS at 3.00 bpw only 29.0/113 (63%) — so NariQ is not merely level with BF16 but ~8 tasks above the strongest 3.5-bit scalar baseline.
- **Terminal Bench 2.1**: BF16 scores 62.6; NariQ 3.0 bpw **63.8 (102% of BF16**, paired +1.2 pts, s.e. 3.5), 2.5 bpw **60.2 (96%**, −2.4 pts, s.e. 3.2). Published ≤3.0 bpw files land at 64–90% of Unsloth's BF16 (GSQ-RCO IQ2_XS 37.8 = 64%, Unsloth UD-IQ2_S 44.6 = 75%, GSQ-RCO IQ3_XXS 51.2 = 87%).
- **2.0 bpw is a real failure, reported as one**: 33/113 DeepSWE (75% of BF16), score 75.7% (−7.3 pts, s.e. 3.3), Terminal Bench 52.4 (84%, −10.2 pts, s.e. 3.5), AIME **86.0 vs 97.7** (−11.7), RealWorldQA 80.9 vs 82.4, MGSM 90.6 vs 94.0. The paper attributes the AIME collapse partly to calibration data: a 2.0 bpw file tuned on coding traces alone scored **77.3** on AIME, and adding the 30% general data raised it to **86.0**.
- **Offline KL at model-written tokens** cleanly separates the files. At 3.0 bpw NariQ's agent KL is **0.0063** vs 0.0276 for GSQ-RCO IQ3_XXS and 0.0239 for Unsloth UD-IQ3_XXS (3.8–4.4× worse despite the latter's 3.14 bpw), and 0.0060 on the untouched reserve set vs 0.0333. At 2.5 bpw NariQ is 0.0117 vs 0.0275 for the best published file in that budget band (Unsloth UD-Q2_K_XL at 2.85 bpw) and 0.0435–0.0623 for the true 2.5-bit group. At 2.0 bpw NariQ is 0.0284 (agent) and 0.0841 (general); Unsloth UD-IQ2_XS at 2.27 bpw is slightly better on the math set (0.0819 vs 0.0829) but 2.1× worse on agent KL (0.0593).
- **Ablation-by-development-sequence (Figure 1, 3.0 bpw, agent KL)**: GPTQ+GSQ with RCO widths and probabilities re-rounded under trellis costs 0.0592 → trellis with re-rounded widths 0.0186 (3.2× better) → feed-weighted sensitivity allocation 0.0193 → model-token loss + 2-s.e. margin 0.0110 → second allocation round 0.0095 → two-sided rounding 0.0077 → lm_head bands with 2-bit floor **0.0070** → scale and norm tuning 0.0068. The paper flags that the model-token step entangles masking with the s.e. margin, so it does not isolate masking alone.
- **Sizing and speed**: text-only GGUFs (embeddings and output layers included) are **10.1 / 8.4 / 6.8 GB** at 3.0 / 2.5 / 2.0 bpw, against a 55.6 GB BF16 checkpoint (which also carries vision and MTP); vision adds a shared 0.9 GB BF16 projector. The llama.cpp fork on one RTX PRO 6000 generates **89 / 99 / 112 tok/s** at 4K context and **71 / 77 / 85 tok/s** at 64K.

## Authors & Credibility

Single author: Doyeob (Toby) Kim, Nari Labs (`toby@narilabs.com`) — an industry lab rather than an academic group, and this is a preprint with no venue. The engineering credibility is nonetheless high in the dimensions that are checkable: the weights and a working inference fork are both public, every published competitor file is re-scored under one code, the DeepSWE repositories are excluded from calibration at the repository level, a reserve KL set is held out from all decisions, and the paper reports its own clearest negative result (2.0 bpw trails by 7.3 points on the headline benchmark) instead of burying it.

Credibility is limited in the other dimensions. There is no second model, so the method is demonstrated on exactly one architecture (Qwen3.8-27B, which includes DeltaNet layers) at exactly three budgets. The comparison against other quantization methods is not run by the authors at all for the agent benchmarks — Table 1's non-BF16 rows are transcribed from Unsloth's charts, with solved counts reconstructed as "reported rate × 113, read to ±0.5 tasks". And the acknowledgments state that "AI tools assisted with writing, literature search, implementation, and research analysis", which for a single-author paper with a custom quantizer and a forked inference engine is a real, if increasingly common, caveat about how much of the implementation was independently verified.

## Critical Assessment

The scientific core — that no trellis-code improvement is needed, only a change in *which tokens the KL is computed on* — is a genuinely useful reframing, and the supporting measurement is the paper's best single argument: the curvature-weighted cosine between the 3-bit error and the 2-, 4-, 5-bit errors is **0.035 / 0.009 / 0.004**, which is a clean, falsifiable reason why RCO-style first-order width scoring (used by the strongest published baseline, GSQ-RCO) carries almost no information for trellis codes. That is a specific mechanistic claim about a named competing method, not a generic "our method is better".

The evaluation, however, is much thinner than the framing suggests. The headline table rests on **113 DeepSWE tasks with one attempt each**, and the paper's own paired standard errors are 3.2–3.6 points; the 3.0 bpw "+1.9 points over BF16" is therefore roughly half a standard error, and "level with BF16" is the correct reading — but then so is "indistinguishable from a 1.5-point regression", and the paper's 47 vs 44 solved count is a 3-task difference on a benchmark where single tasks are stochastic. No seed replication is reported for DeepSWE or Terminal Bench, no confidence interval is given for the solved-count comparison itself, and AIME is a single avg@8 number with no spread across the eight samples, so the paper cannot distinguish "NariQ 3.0 matches BF16" from "NariQ 3.0 and BF16 are both at the harness ceiling near 98%".

The baseline comparison is the weakest link. All non-BF16 agent numbers come from a *different* harness (mini-swe-agent, ≥3 attempts per DeepSWE task) and are normalized by that harness's own BF16 — a normalization the authors correctly say does not remove harness differences, which means the "at most 72% of BF16" framing for competitors and the "107% of BF16" for NariQ are not measured on the same instrument. Notably the discrepancy is not uniform across benchmarks: Unsloth's BF16 Terminal Bench (59.15) is 3.5 points *below* the authors' (62.6) while its DeepSWE BF16 (45.7) is *above* (44), so harness offsets push in opposite directions on the two benchmarks, and no attempt is made to estimate that offset (e.g. by running one Unsloth GGUF in the authors' harness — a single missing experiment that would have made the comparison sound).

The ablation is a cumulative development sequence rather than a factorial one, and the paper says so: the model-token step is bundled with the two-standard-error margin (0.0186 → 0.0110), so the paper's central claim — that masking to model-written tokens is what matters — is never isolated. The allocation contribution is likewise only shown cumulatively (0.0095 → 0.0077 for two-sided rounding, 0.0070 for bands, 0.0068 for scale tuning) and on an earlier checkpoint, with no per-component KL ablation at 2.5 or 2.0 bpw, where the margin is much tighter and where a component could plausibly hurt. The 2.0 bpw result also quietly undercuts the "sub-3-bit" branding: the claim holds at 2.5 and 3.0, fails at 2.0, and the paper's explanation for the 1-bit allocation failure (12 modules moved from 1 to 2 bits cut KL 7.2% for 0.021 bpw, "far more than predicted") shows the loss model is known to break down precisely in the regime the title advertises.

Smaller issues: the bpw accounting is not apples-to-apples across the table (EXL3 "3.00 bpw" is actually 3.77 bpw, GSQ-RCO IQ3_S is 3.50) but the text sometimes compares against the nominal label; the 2.0 bpw embedding bands are allowed 1 bit while output bands are not, which is justified only by a qualitative observation about rare tokens; the MTP module is left unquantized, so the released files are not a full-fidelity port of the original checkpoint; and the fork is tuned to SM120 only, so the throughput numbers are single-GPU-generation claims. None of these are fatal, but together they mean "first quantizations ≤3 bits shown to match full precision on long-horizon agentic tasks" is supported by one model, one scaffold, two benchmarks, one attempt per task, and a competitor column measured elsewhere.

## Strengths

- Identifies a real and under-measured failure mode (short-benchmark parity masking long-horizon agent collapse) and quantifies it on the same model across four published baseline families before proposing anything.
- The intervention is unusually cheap and well-targeted: no new format, no fine-tuning of weights, four changes to the loss mask, the allocator's objective, the output-layer layout, and the scale-tuning data.
- A genuinely mechanistic contribution to the bit-allocation literature — the measured near-zero curvature cosine between width errors explains *why* RCO's score degenerates for trellis codes, and the "estimate ℓ_c, extrapolate by code MSE" alternative follows directly from it.
- Strong leakage hygiene for the headline benchmark (repository-level exclusion of DeepSWE repos; a reserve KL set never touched by any decision).
- Complete artifacts: GGUF weights, a working llama.cpp fork, and an appendix that re-scores every competitor file with the authors' own KL code, which is the one comparison free of harness confounds.
- Honest reporting of the 2.0 bpw regression, including the specific mechanism (AIME 77.3 → 86.0 from adding general data) rather than a vague "future work".

## Limitations

- One model (Qwen3.8-27B), one agent scaffold (Claude Code), two agentic benchmarks, one attempt per task; no replication across seeds, no second architecture, no non-DeltaNet transformer.
- Non-BF16 baselines are not run by the authors; they are Unsloth chart readings normalized per harness, with an unquantified harness offset that the paper acknowledges but does not measure.
- The four contributions are validated only as a cumulative sequence on an earlier 3.0 bpw checkpoint; there is no factorial ablation, and the central masking claim is entangled with the 2-s.e. margin.
- Statistical power is low: paired s.e. of 3.2–3.6 points on 113 tasks means the headline "level with BF16" cannot exclude a several-point regression, and solved-count differences of 3 tasks carry no interval at all.
- The sub-3-bit claim holds at 2.5/3.0 bpw only; the 2.0 bpw file trails BF16 by 7.3 points on DeepSWE and 11.7 on AIME, and the loss model is documented to fail at 1 bit.
- Calibration requires running the full-precision model through real agent sessions on open-source software repositories — a nontrivial data-collection cost that the paper does not quantify (trace count, token volume, or sensitivity to the trace mix).
- Released artifacts are partial for reproduction of the *method*: weights and a fork are public, but the quantizer, allocation code, and calibration traces are not described as released.
- Throughput claims are tied to a single GPU generation (SM120), and the MTP module remains unquantized; KV-cache and activation quantization are explicitly future work.

## Relevance

直接命中"低比特量化 + 长程 agent"这条正在变热的交叉线：它给出的证据是"短基准（AIME 96.9 vs 97.7）几乎看不出问题，但 DeepSWE 只解出 63%"，这个反例对任何用 perplexity 或 MMLU 类指标给量化文件背书的工作都是提醒；而"损失只算模型自己写出的 token"这一条对做 agent 训练/蒸馏/量化的读者都可直接借用。

## Questions for Further Exploration

1. Does model-token masking alone account for the gain? Running a factorial ablation at 2.5 bpw (mask on/off × margin on/off × bands on/off × 70:30 scale data on/off) would settle whether the other three changes are load-bearing or merely additive polish.
2. How sensitive is the result to the calibration trace distribution — number of sessions, repository diversity, and the fraction of tokens that are tool output? The paper masks tool output from the loss but still uses it as context; a trace-mix sweep would tell whether the recipe needs thousands of sessions or dozens.
3. Would scoring one Unsloth GGUF (e.g. UD-Q3_K_XL) inside the authors' Claude Code harness recover the claimed 28-point DeepSWE gap, or does most of it come from mini-swe-agent's ≥3-attempt protocol?
4. Does the near-zero curvature cosine between width errors (0.035 / 0.009 / 0.004) also hold for scalar/vector codes and for larger models, i.e. is RCO's score degenerate only for trellises or more broadly for any code whose error directions decorrelate with width?
5. With paired s.e. ≈ 3.3 points, how many DeepSWE tasks would be needed to certify "within 2 points of BF16" at 95% confidence — and would a multi-attempt protocol (which the baselines used) be a cheaper way to get there than more tasks?
6. Does the banded-lm_head trick interact with tokenizer fertility in non-English use? The 1-bit floor for rare output tokens was motivated by multilingual traces, but MGSM at 2.0 bpw still drops 3.4 points, suggesting the floor is necessary rather than sufficient.
