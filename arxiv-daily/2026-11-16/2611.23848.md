> **一句话总结：** AMD 提出 KIWI——一个把 GPU 端发起的通信请求以"一次 wave 级 16 字节 PCIe store"投递到 CPU 回调的最小化 reverse-offload 框架（SPSC 队列、无原子操作/无内存栅栏，单程延迟 1.92 µs、空闲轮询 0.87 ns），在其上构建的 KIWI-P2P 小消息单程 put 5.64 µs（比 MORI 低 1.8×、比 rocSHMEM 低 3.4×），KIWI-EP 用三个工作负载自定义算子（multicast put、count all-to-all、barrier）把 DeepSeek-V3 尺寸的 MoE dispatch+combine 延迟最多降低 2.3×，在 vLLM 上服务 GLM-5.3（FP8、PD 分离）把 TPOT 最多降低 29%。

> **TL;DR:** The paper argues that reverse offload (GPU kernel hands each communication request to a CPU proxy thread that drives the NIC) is not a slow fallback but can beat GPUDirect Async (GDA), and makes it programmable: kernels invoke arbitrary host callbacks through an SPSC device-to-host queue published by one wave-wide store. On an 8×MI300X / ConnectX-7 RoCE cluster, KIWI-P2P's small-message one-way put is 5.64 µs vs 10.2 µs for MORI and 19.2 µs for rocSHMEM (1.8× and 3.4× lower), and KIWI-EP cuts MoE dispatch+combine latency by up to 2.3× versus ROCm DeepEP / MORI-EP / UCCL-EP (up to 1.77× at 1 token/GPU) and vLLM TPOT for GLM-5.3 by up to 29% on 8 nodes — but the EP win shrinks to 1.08× at 64 tokens/GPU.

## 核心贡献

- **翻转既有假设**：主流设备发起通信库（NVSHMEM、rocSHMEM、NCCL GIN、MORI）把传输控制放在 GPU 线程上（GDA），把 reverse offload 降级为慢速 fallback。作者论证 GDA 的根本瓶颈是 GPU 线程的弱顺序执行能力与 NIC 端点数量远少于 GPU 线程，并用实测证明优化良好的 reverse offload 在延迟和带宽上都能胜过 SOTA GDA。
- **提出"可编程 reverse offload"编程模型**：不再调用库固定的 put/get/quiet，而是由 kernel 开发者把任意 host 函数注册为 callback，从 GPU kernel 内异步 `invoke`。新算子变成应用自己代码里的一个自包含 host 回调，无需改动厂商库内部传输层。
- **实现 KIWI 核心**：每个 wave 独占一个 SPSC GPU→CPU 队列，每个 8 字节槽把 4 字节描述符与 4 字节信号放在同一次 16 字节 store 中（64 lane 的 wave 一次可发布最多 512 字节描述符），因此无需原子操作、无需 fence；生产者索引/消费者索引缓存全在寄存器中，仅在可能满时通过 PCIe 重读消费者索引。
- **KIWI-P2P**：用不到 1,000 行 C++ 把 KIWI 与主机 HPC 通信库 LCI 组合成 SHMEM 风格库，证明 reverse offload 在通用点对点原语上就能打赢 GDA。
- **KIWI-EP**：把 MoE dispatch/combine 重构为三个 EP 专用算子（multicast put、非阻塞 count all-to-all、非阻塞 barrier），并额外解决两个工程问题——连续批处理导致的动态活跃端点范围（由 kernel 内回调发布端点计数，兼容 HIP graph 重放），以及 proxy 线程间的负载不均（提出 skewed round-robin：端点 q 的归属为 q 的 P 进制各位数字之和 mod P）。
- **端到端验证**：把 KIWI-EP 接入 vLLM 服务 GLM-5.3，并做五级消融阶梯（GDA → Proxy-MPSC → Proxy-SPSC → Proxy-Callback → +skewed round-robin）拆解每一处收益。
- 开源：https://github.com/AMDResearch/kiwi

## Key Contributions

- Reframes reverse offload as a first-class programming model for device-initiated communication rather than a compatibility fallback, with an explicit argument for why GDA's GPU-side control path (branches, global-memory access, system-scope fences, endpoint sharing) is structurally limited.
- KIWI: a minimal interface (`register_callback` / `invoke` / `progress`) plus an SPSC device-to-host queue whose handoff costs one wave-wide store over PCIe with no atomics and no fences; each wave owns its queue, each proxy thread owns a disjoint set of endpoints.
- KIWI-P2P: a <1,000-line SHMEM-like library combining KIWI with LCI, used both as an existence proof for reverse offload and as a head-to-head comparison against GDA transports (MORI, rocSHMEM).
- KIWI-EP: workload-defined EP operations (multicast put, count all-to-all, barrier) plus dynamic endpoint polling and skewed round-robin endpoint→proxy assignment, delivering kernel-level and vLLM-level gains.
- A careful decomposition (ablation ladder) that reports where reverse offload loses to GDA (large batches, round-robin assignment) rather than only where it wins.

## Methodology

**Design goals and interface.** A KIWI context owns a callback registry and a set of endpoints; registering a callback assigns a small integer id. Inside a kernel a wave obtains a handle and calls `invoke(cb_id, args)`; KIWI serializes the arguments into a descriptor and publishes it to the endpoint. `invoke` is asynchronous (returns after publication) and non-blocking (returns `false` if the endpoint is full, which kernels handle by retrying in a `while` loop). KIWI creates no hidden threads: the application calls `progress(ep)` from its own proxy threads, which pop descriptors and run callbacks. Because endpoints are SPSC, each endpoint needs exactly one producer wave and one polling thread at a time — which is what removes locks and atomics from the critical path. Device-side support is not tied to HIP C++: FlyDSL and Triton libraries publish the same descriptors, so kernels in those languages call the same C++ host callbacks unchanged.

**The handoff queue (Section III-B).** The ring lives in GPU-accessible host memory as 8-byte slots, each pairing 4 bytes of descriptor with a 4-byte signal. Each lane writes two adjacent slots in a single 16-byte store over PCIe; because the slot itself becomes visible atomically in host memory, a valid signal implies the adjacent descriptor bytes arrived, so no separate flag write and no fence are needed. Producer index, a cached copy of the consumer index, and ring metadata stay in the wave's registers, so the fullness check and index update are register arithmetic; the producer re-reads the consumer index over PCIe only when its cached copy suggests the ring may be full. A 64-lane wave thus publishes up to 512 bytes per push. The pop path mirrors it: the consumer polls the signal of the first slot at its consumer index, copies out the full descriptor once all its slots' signals are valid, and advances. An idle consumer always polls the same address, so idle polls hit in the CPU L1. An MPSC variant also exists, but endpoints default to SPSC.

**KIWI-P2P (Section IV).** Combines KIWI with LCI (a multi-threaded host HPC library over libibverbs/libfabric) using only LCI's public interface. Each proxy thread is paired with its own LCI device so threads do not contend; a new device-initiated operation needs only a descriptor struct, a device wrapper that invokes a callback with it, and a host callback that translates it into LCI operations (Listing 2 shows `post_put_signal`: look up the symmetric-heap rkey, post the payload, then post a 1-byte readiness flag on the same LCI device so ordering is guaranteed).

**KIWI-EP (Section V).** Dispatch packs tokens into network-registered staging buffers, issues one multicast put per token (descriptor built cooperatively in LDS, up to eight destination ranks with offsets and readiness slots), then unpacks received rows; a workgroup-0 prescan computes per-destination send counts and posts a non-blocking all-to-all (hierarchical: RDMA across nodes, IPC loads within a node; each count travels as one 64-bit word with a 32-bit epoch so arrival is detectable without a separate signal). Combine packs expert output rows, posts puts back to source ranks, accumulates, and posts a non-blocking barrier to protect staging buffers. Each operation is a single KIWI invocation with post/wait split so progress overlaps payload work. For dynamic batching, wave 0 of workgroup 0 invokes an active-endpoint-count callback (HIP-graph-safe) and proxies sweep their endpoints up to that boundary, growing immediately and draining on shrink. Endpoint→proxy assignment uses skewed round-robin (digit-sum of the endpoint index in base P, mod P) so that both an active prefix and the strided wave-0-only request pattern spread across all proxies.

**Experimental setup.** Two to eight nodes, each with 2× Intel Xeon Platinum 8480+ (56 cores), 8× AMD MI300X (192 GB HBM3), 8× ConnectX-7 400 Gb/s RoCE, PCIe Gen5 x16 switch (one NIC per GPU, GPUDirect RDMA bypassing the root complex). Processes and proxy threads pinned to the NUMA node of their GPU. Median of ≥3 runs. Baselines: for handoff, six existing GPU→CPU queues in a common harness (NVSHMEM and rocSHMEM re-implemented from upstream source since they cannot run unmodified on AMD); for P2P, MORI and rocSHMEM GDA paths with matched kernels; for EP, ROCm DeepEP, MORI-EP, UCCL-EP on identical inputs with DeepSeek-V3 MoE dimensions (hidden 7168, 256 experts, top-8, BF16); end-to-end, vLLM serving GLM-5.3 in FP8 with prefill-decode disaggregation, 8K input / 1K output tokens, 8 GPUs per node, prefill always MORI-EP and decode either MORI-EP or KIWI-EP.

## Results & Highlights

- **Handoff latency matches a bare store (Table III, one MI300X).** KIWI's queue round trip is 1.92 µs median (p99 1.98 µs), identical to the raw wave-wide-store floor of 1.92 µs, while the fastest existing queues are 2.68 µs (NVSHMEM†), 2.72 µs (MSCCL++), 2.80 µs (UCCL-EP) and 3.86 µs (RCCL GIN); rocSHMEM† is 9.28 µs and LLVM libc RPC 7.92 µs.
- **Push cost and throughput stay flat as producers grow.** Per-wave push is 0.12 µs at W=1 and still 0.12 µs at W=1,024, whereas every existing queue's push grows 4.6–16× (e.g., NVSHMEM† 0.92 → 14.92 µs, rocSHMEM† 3.84 → 55.64 µs, RCCL GIN 1.32 → 6.04 µs). At 256 waves KIWI sustains 392.0 Mops/s versus 119.4 Mops/s for the best existing queue (MSCCL++), a 3.3× gap. Idle polling costs 0.87 ns versus 20.9 ns (RCCL GIN), 2.44 ns (MSCCL++) and 1,356 ns (rocSHMEM†), which is what lets a few proxies watch hundreds of endpoints.
- **Programmability is nearly free.** With real callbacks the median round trip and single-wave push are unchanged (1.92 µs / 0.12 µs), push at 1,024 waves rises only to 0.16 µs; at 256 waves throughput drops to 62% of the bare queue because the proxy must execute a callback per message. Kernels in FlyDSL and Triton match HIP C++ round trip within 2% and reach 78–96% of its single-endpoint throughput.
- **Reverse-offload overhead over a hand-written host path is small (Table I, 8-byte puts, two nodes).** KIWI-P2P is 5.23 µs latency vs 5.25 µs for flag+LCI and 2.88 vs 2.97 Mops/s throughput (−3%), while flag+ibverbs reaches 3.40 Mops/s — i.e., the residual gap is LCI's per-put cost, not reverse offload.
- **KIWI-P2P beats GDA on point-to-point (Fig. 5).** A small put takes 5.64 µs one-way, 1.8× lower than MORI and 3.4× lower than rocSHMEM; with eight workgroups KIWI-P2P nearly saturates the 400 Gb/s link at 8 KiB messages where MORI and rocSHMEM need 64 KiB, and MORI with 128 workgroups still delivers less 4 KiB bandwidth than KIWI-P2P with eight workgroups. Scaling is set by proxy-thread count: eight proxy threads per GPU approach the NIC payload limit from 8 KiB.
- **KIWI-EP beats existing EP backends at low-to-medium batch (Fig. 7, DeepSeek-V3 MoE dims, dispatch+combine on slowest rank).** Lowest latency up to 16 tokens/GPU on 2 nodes, up to 32 on 4 nodes, and at every token count on 8 nodes, with up to 2.3× lower latency than the best of ROCm DeepEP / MORI-EP / UCCL-EP. At higher token counts RDMA bandwidth dominates because KIWI-EP sends each token once per destination GPU while MORI sends once per node and forwards intra-node.
- **End-to-end serving gain (Fig. 8, vLLM, GLM-5.3 FP8, PD-disaggregated).** KIWI-EP lowers TPOT versus MORI-EP at every measured scale and concurrency, by up to 29% on eight nodes; GSM8K and needle-in-a-haystack runs confirm no accuracy change.
- **Ablation ladder (Fig. 9, eight nodes, normalized to GDA).** KIWI-EP is 1.77× faster than GDA at 1 token/GPU, 1.29× at 8, and only 1.08× at 64. Proxy-MPSC alone is 27% lower latency than GDA at one token; per-wave SPSC queues add another 14%; programmable callbacks (fusing payload+signal, coalescing multicasts/collectives) cut a further 21%; skewed round-robin adds 19% at 8 tokens and 9% at 64. Critically, round-robin proxy variants are 28% and 29% *worse* than GDA at 64 tokens — the assignment scheme, not reverse offload per se, is what fixes large batches.

## Authors & Credibility

Six authors, all at AMD (Advanced Micro Devices), including Bradford Beckmann (AMD Fellow, well known for HPC/accelerator architecture and communication work, e.g., earlier work on fused computation-collective operations at SC24) and Brandon Potter (AMD Research, GPU architecture/simulation). The paper is an arXiv preprint (cs.DC, submitted 18 Nov 2026), formatted as an IEEE-style conference submission; no venue is stated, so it has not passed peer review as posted. Credibility signals are strong on the empirical side: code is public at github.com/AMDResearch/kiwi, measurements are on real MI300X + ConnectX-7 hardware rather than simulation, each data point is a median of ≥3 runs, baselines are named and configured explicitly (queue-pair counts, GDRCopy path, per-workgroup resources), and the authors are the vendor whose hardware is being measured — an obvious incentive to show AMD-optimized stacks favorably, though the comparison targets are also AMD-side or AMD-supported stacks (MORI, rocSHMEM, ROCm DeepEP), which cuts both ways. The most notable credibility plus is that the ablation publishes the regime where their own design loses.

## Critical Assessment

*Novelty.* Programmable reverse offload is a real conceptual contribution: prior GPU→CPU callback/RPC work (Punniyamurthy et al.-style system-call offload, LLVM libc RPC) targeted infrequent operations, and prior reverse-offload transports (NVSHMEM IBRC, fabric-lib, UCCL-EP's CPU proxy) hide the proxy behind a fixed operation set. The claim that reverse offload can beat GDA is not new — the paper itself cites UCCL-EP and fabric-lib as concurrent results showing a well-tuned CPU proxy matches or beats GDA in EP kernels — so the incremental novelty is (a) doing it for *general* point-to-point primitives on AMD, and (b) opening the operations themselves to the application. The SPSC-with-signal-in-same-store trick is closely related to the "LL protocol" of GPU communication libraries the paper cites ([13], NCCL/RCCL's low-latency protocol); the novel part is applying it per-wave with wave-owned queues and register-resident indices, not inventing the store-pairing idea.

*Rigor and baseline fairness.* The handoff comparison (Table III) is the weakest link: NVSHMEM cannot run on AMD and rocSHMEM's reverse-offload queue is internal, so both are *re-implementations* "following the upstream source". rocSHMEM's 9.28 µs round trip and 55.64 µs push at 1,024 waves are ~5× worse than NVSHMEM's re-implementation, which readers should treat skeptically — a faithful copy of a slow code path and a missed micro-optimization look identical from the outside, and this is exactly the kind of number that flatters the proposed design. Similarly, in the P2P comparison KIWI-P2P gets eight proxy threads (eight CPU cores) while MORI and rocSHMEM get one queue pair or context per workgroup with no dedicated CPU cores; the paper reports CPU cores as "acceptable" overhead but never prices them, and the ablation shows the proxy design is 28–29% *slower* than GDA at 64 tokens until the endpoint-mapping fix, so the headline P2P win is at small messages where control-path cost dominates by construction. The EP comparison is fairer (common harness, identical inputs, matched MoE dimensions) but KIWI-EP is benchmarked against backends that, unlike KIWI-EP, were not co-designed with this paper's multicast put and count all-to-all — the comparison is of complete stacks, which is the right question for practitioners but not a like-for-like isolation of reverse offload.

*Missing ablations and regimes.* (i) There is no breakdown of what fraction of the 29% TPOT gain comes from the three EP operations versus simply having four extra CPU cores of proxy per GPU; the ablation ladder is kernel-level only. (ii) No high-concurrency throughput result (tokens/s per GPU or per node) is reported for vLLM — only TPOT — so a reader cannot tell whether the 29% TPOT win costs decode throughput, which is the metric that actually decides serving cost; with 8 GPUs per node and four proxy cores per GPU, KIWI-EP consumes 32 of 112 CPU cores, and no experiment reduces cores per GPU to show the sensitivity. (iii) No multi-NIC/multi-rail, congestion, or failure results, despite 8 NICs per node; all experiments use one NIC per GPU with a 1:1 PCIe switch mapping, the most favorable possible topology. (iv) No InfiniBand numbers at all, even though most NVSHMEM/GDA deployments in the field are IB-based and the paper's argument is about the control path, which should be transport-agnostic — the absence weakens the generality claim. (v) The barrier is admitted to be a reuse of the count all-to-all's hierarchical exchange, with a dissemination barrier left as future work, so the "three workload-defined operations" framing slightly oversells the third.

*Data/topology quirks worth flagging.* The one-way 5.64 µs small-put latency in Fig. 5 is higher than the 1.92 µs queue round trip in Table III plus the 5.23 µs KIWI-P2P latency in Table I — these tables measure different things (queue RTT on one GPU vs 8-byte two-node put), and the paper does not reconcile them in one place, so a careless reader can conflate "sub-microsecond" from the abstract with the actual two-node put latency. The abstract's "sub-microsecond one-way device-to-host latency" refers only to the GPU→CPU handoff, not to any network operation; the two-node put is 5.64 µs. That framing is defensible but easy to misread.

*Significance.* If the numbers hold, this is a meaningful result for AMD's LLM-serving stack: it decouples GPU producer count from NIC endpoint count, which is the actual scaling wall for GDA on MI300X, and it turns "write a new collective" into "write a host function", which is a genuine productivity argument for fused MoE kernels. The main threat to significance is that the win is regime-specific: 1.08× at 64 tokens/GPU means the paper's own data says GDA is roughly fine for high-batch decode, and continuous batching in production often runs at higher concurrency than the low-concurrency agentic regime the paper motivates.

## Strengths

- Clean, minimal abstraction: three verbs (`register_callback`, `invoke`, `progress`) that compose with any host transport (LCI, ibverbs, libfabric) instead of forking a vendor library's internals.
- The queue design is genuinely well engineered — signal and descriptor in one atomically visible 8-byte slot, indices in registers, PCIe consumer-index re-read only on suspected fullness — and the paper demonstrates it reaches the raw-store floor (1.92 µs vs 1.92 µs), which is the cleanest possible evidence that the mechanism adds no overhead.
- Honest, informative ablation ladder: it reports 1.77× → 1.29× → 1.08× as batch grows and explicitly states that round-robin proxy assignment is 28–29% *worse* than GDA at 64 tokens, which is the kind of negative result that makes the positive ones trustworthy.
- Practical engineering details that papers usually omit: HIP-graph-safe dynamic endpoint counts under continuous batching, epoch-tagged 64-bit counts to avoid separate signal writes, skewed round-robin derived from digit sums so both active prefixes and strided wave-0 requests balance.
- Real-hardware end-to-end validation (vLLM + GLM-5.3, FP8, PD disaggregation) with accuracy checks, plus public source code.
- Language-agnostic device side verified in FlyDSL and Triton within 2% of HIP C++, which matters for a compiler-driven ecosystem.

## Limitations

- Single-vendor, single-topology evaluation: MI300X + ConnectX-7 RoCE with one NIC per GPU and a 1:1 PCIe switch; no InfiniBand, no multi-rail, no oversubscribed PCIe, no cross-NUMA or congested-network regimes.
- CPU cores are treated as free. KIWI-EP uses four proxy cores per GPU (32 of 112 cores per node at 8 GPUs); no experiment varies core count, and no analysis shows whether a dense deployment could instead spend those cores on more GPUs or on host-side work.
- High-batch regime is only 1.08× better than GDA, and the paper leaves hierarchical token routing (MORI's send-per-node-then-forward) as future work, so at large token counts KIWI-EP is bandwidth-limited by a design choice it has not yet fixed.
- Only TPOT is reported end to end; no throughput, no cost-per-token, no tail-latency distribution under load.
- Two of six handoff baselines (NVSHMEM, rocSHMEM) are re-implementations rather than upstream code, and rocSHMEM's re-implementation is anomalously slow; the queue comparison therefore cannot be taken as a definitive ranking.
- The barrier is borrowed from the all-to-all exchange rather than a scalable algorithm; the paper acknowledges this.
- No failure, preemption, or interference study, even though proxies are ordinary preemptible OS threads and the paper concedes scheduling support is absent.
- Peer review status unknown (arXiv preprint); no artifact-evaluation or independent reproduction yet.

## Relevance

与"GPU 集群通信/LLM 推理系统"这条线高度相关：它挑战了 GDA 一定更快的默认假设，并给出一个可直接复用的抽象（GPU 内 invoke 任意 host 回调），对 MoE 专家并行、低延迟 agentic serving 的 kernel 设计有直接参考价值；同时提供了 MI300X 上 EP 后端（MORI/ROCm DeepEP/UCCL-EP）的可比数字。

## Questions for Further Exploration

1. How much of the 29% TPOT gain survives if the proxy thread count is cut from four per GPU to one or two — i.e., is the win from reverse offload or from spending otherwise-idle CPU cores?
2. What does decode throughput (tokens/s/GPU) and p99 TPOT look like at high concurrency, where the paper's own ablation says the advantage over GDA falls to 1.08×?
3. Would the queue comparison change on InfiniBand (ConnectX-7 IB instead of RoCE), and does the "no atomics, register-resident indices" design still reach the raw-store floor there?
4. If KIWI-EP adopted MORI-style hierarchical token routing (send once per node, forward intra-node), where would the crossover between the two designs move on 8 nodes at 64–256 tokens/GPU?
5. Can the callback model absorb operations beyond RDMA — GPU copy engines, storage I/O, CPU-side sparse work — without violating the SPSC single-producer assumption when multiple engines need to post?
6. How sensitive is skewed round-robin to non-power-of-two configurations (waves per workgroup or proxy counts not powers of two), and is there a general assignment rule with a bound rather than an alignment argument?
