> **一句话总结：** IsoMoE 把 KTransformers 的 CPU 专家核当作"规范算术"，让 GPU 用 `fma.rn.ftz` inline PTX 逐位重放同一累加顺序（含 65,536 项激活查表），再配一套按 `vdpbf16ps` 操作数布局排布的 12 位无损专家格式（"CPU order"）和精确双 micro-batch 流水线，从而做到专家放在 CPU 还是 GPU 上输出逐位相同；在 Qwen3-30B-A3B / AIME+MATH500 的 160 题上，20 槽、41 槽、全 CPU 三种放置均 160/160 逐位一致（fast 模式仅 1/160），解码吞吐相对各设定最快基线平均 1.26×、最大 1.54×，且 exact 模式几乎不损失速度（117.9 vs 118.5 tok/s）。

> **TL;DR:** IsoMoE is a hybrid CPU-GPU MoE inference engine built on KTransformers 0.3.2 that makes greedy decoding output *bitwise invariant to expert placement*: the GPU expert kernel replays the CPU kernel's arithmetic exactly (AVX-512 `vdpbf16ps` emulated with paired `fma.rn.ftz`, approximate `vrcp14ps` activations replaced by a 65,536-entry table of CPU results), lossless 12-bit Glyd-style codewords are stored in a "CPU order" layout so AVX-512 dot products consume them without transposes, and a dual micro-batch pipeline computes each micro-batch at whole-batch shape. On Qwen3-30B-A3B with 160 AIME+MATH500 problems (batch 8, ≤16K tokens, greedy) it gives 160/160 identical outputs across all-CPU, 20-slot, 41-slot and online placement (49,712 swap-ins), versus 1/160 and 0/160 for the same engine's fast mode; it also matches the original KTransformers CPU reference on 32,264-token outputs. Decoding throughput beats the fastest baseline in every one of the 3 models × 4 GPU budgets × 2 batch sizes settings: 1.26× average, 1.54× max (Qwen3, 13.5 GiB, batch 16, vs IsoMoE-BF16), and 1.39–2.76× versus the fastest baseline that is *forced* to keep all experts on CPU to preserve its outputs.

## 核心贡献

- **问题提出与量化：专家放置会改变输出，这不是实现细节而是评测污染源。** llama.cpp 把 12 层专家移到 GPU 后，Qwen3-30B-A3B 在 56 道数学题上只有 **5 题**输出不变；FreeToken 把专家 cache 减半后 **56/56 全部改变**；若启动时有别的进程占了 4 GiB 显存，llama.cpp 会把多 4.1 GiB 的专家留在 CPU 上，前 2048 token 内只有 **3/16** 题输出不变。分歧输出的相同前缀中位数只有 **125–320 token**。
- **机制解释：不是随机数，而是"哪个专家被选中"被舍入差异翻转。** 只在层内 87 个不在显存中的专家上引入舍入级差异，BF16 router 下 **15.8%** 的路由决策改选其它专家，即便换成 FP32 router 仍有 **13.5%**；Top-8 路由把"第 8 名 vs 第 9 名概率几乎相等"放大成离散跳变。
- **非对称重放（关键设计取舍）：不改 CPU，而让 GPU 去模仿 CPU。** 因为 CPU 专家计算占每步 82%、GPU 大量空闲，所以保留 KTransformers 的 CPU 算术作为规范，GPU 逐位重放：`vdpbf16ps` 的"先奇后偶、每次加法后舍入"用两条 `fma.rn.ftz` inline PTX 复现（禁止编译器重排）；`vrcp14ps` 近似倒数无法在 GPU 上逐位复现，于是把 BF16 输入的 65,536 种取值对应的 CPU 激活结果做成查表。
- **CPU order 内存布局：让 12 位定长码在寄存器里一次解压。** 低 8 位保留，高 8 位压成 4 位码（符号 + 相对每矩阵基值的 3 位指数偏移），平均 12.1 bit/权重；把 32 行 × 一对 BF16 列的 "unit" 按 `vdpbf16ps` 的取数顺序排列，解压后 `w0/w1` 直接就是两条点积指令的操作数，免去行主序下每次调用都要做的 32×32 转置。
- **精确双 micro-batch 流水线：并行但不改位。** 每个 micro-batch 用 whole-batch 形状计算（矩阵乘零行填充、attention 按整批 KV 划分调度），并在每层注意力与 router 之后统一 commit 已预取的 swap-in，使 swap-in 的早晚只影响"何时算"而不影响"算出什么"。
- **合并顺序的正确性细节：** KTransformers 的 CPU 调用只返回按路由顺序累加后的 `y`，因此 IsoMoE 把每个 (token, expert) 当作 `k=1`、权重 1.0 的独立 token 送入，取回单专家 `d_j`，再由 GPU 用与 CPU 相同的 FMA 与舍入按路由顺序合并。

## Key Contributions

- **Formalizes placement invariance as a system property** distinct from batch invariance, and shows empirically that existing hybrid engines (llama.cpp, FreeToken) violate it badly under placement changes that a user does not control (free GPU memory at startup).
- **Asymmetric CPU-GPU replay**: rather than making both devices numerically "better", it declares the CPU kernel canonical and rebuilds the GPU kernel as a bit-exact emulator of `vdpbf16ps` semantics, including a precomputed activation table to sidestep the non-reproducible `vrcp14ps` reciprocal.
- **CPU order**, a byte layout for fixed-length lossless 12-bit codewords that matches the AVX-512 dot-product operand pattern, turning decompression into register-resident permutes and reaching the byte-ratio speedup that entropy-coded formats cannot.
- **An exact dual micro-batch pipeline** that overlaps CPU and GPU without perturbing bits, by computing non-expert work at whole-batch shape and by making swap-in commit points deterministic per layer.
- **An implementation and artifact** on KTransformers 0.3.2 (C++ AVX-512 CPU library, CUDA + inline PTX GPU kernel, separate streams and a background swap-in thread), with an anonymous code release.

## Methodology

**Setup / problem setting.** Experts of a layer are split by a *residency table* into a CPU work list (computed on the CPU in 12-bit CPU-order format) and a GPU work list (in GPU slots, same bytes copied verbatim). The router's selected experts are split by residency; a *merge map* records routing order. Outputs from both sides are merged in routing order.

**Bitwise replay (Algorithm 1).** For a token `t`, one output row is accumulated by one FP32 lane on the CPU and by one thread on the GPU, reading the same 12-bit bytes in the same order. CPU: `vdpbf16ps` adds the odd product first then the even one, rounding after each. GPU: two `fma.rn.ftz` instructions with identical rounding and denormal handling, in inline PTX so the compiler cannot reassociate. Both round `z_t`/`u_t` to BF16 identically; `h_t = bf16(mul.rn.ftz(ACT[z_t], u_t))` uses the CPU's activation values from the lookup table. A warp handles one row (`s = blockIdx.x mod (N/32)`, `q = threadIdx.x mod 32`), with 3-stage `cp.async` shared-memory staging.

**12-bit format.** Adopts Glyd's fixed-length codewords: low byte of the BF16 weight kept, high byte replaced by 4 bits (sign + 3-bit offset of the upper 7 exponent bits against a per-matrix base). Row segments (64 weights) whose offset overflows 3 bits store the original high bytes in a side table. Average ≈12.1 bits/weight. `vpmultishiftqb` extracts codes, `vpermb` maps codes to high bytes, `vpunpcklbw`/`vpunpckhbw` interleave into the two `vdpbf16ps` operands, and two `vpermt2ps` restore row order per 32-row group.

**Pipeline.** Whole-batch pipeline (GPU waits for CPU experts, then merges and does attention, CPU idles) vs IsoMoE's two micro-batches offset by half a layer. Padding to whole-batch shape and per-row computation keep each row bit-identical to its whole-batch counterpart even though cuBLAS/cuDNN still select kernels by shape.

**Implementation & evaluation.** KTransformers 0.3.2 base, C++ AVX-512 CPU expert library, CUDA+PTX GPU kernel, offline BF16→12-bit conversion, a Triton "fast mode" (Tensor Cores, no replay) for comparison. Platform: 48-core Xeon Platinum 8488C + 48 GB RTX A6000 over PCIe 4.0×16, 32 CPU threads for expert compute. Models: Qwen3-30B-A3B-Thinking-2507, DeepSeek-V2-Lite-Chat, Mixtral-8x7B-Instruct; four GPU expert budgets per model (0 to ≤37.5% of BF16 expert size); batch 8/16 (Qwen3, Mixtral) and 16/32 (DeepSeek). Workloads: 82 hard problems from AIME+MATH500 (Qwen3), 279 MATH500 (DeepSeek), 336 math/code/chat prompts (Mixtral). Baselines: KTransformers 0.3.2 (given IsoMoE's slots and pipeline but its own CPU kernel), FreeToken, llama.cpp, IsoMoE (BF16). HybriMoE omitted (released code is batch-1 with 4-bit experts).

## Results & Highlights

- **Placement invariance, Qwen3-30B-A3B, 160 AIME+MATH500 problems, batch 8, greedy, ≤16K tokens (Table I).** Exact mode gives **160/160 bitwise-identical outputs** for all-CPU vs 20-slot vs 41-slot placements and **56/56** under online placement with **49,712 swap-ins**; the same engine's fast mode gives **1/160** (moving 20→41 slots) and **0/160** (all-CPU vs 41 slots), with final answers changing on **8.8%–10.0%** of problems. This is the paper's strongest single result: determinism is exact, not statistical.
- **Agreement with the untouched reference engine.** Against original KTransformers 0.3.2 (all experts on CPU), IsoMoE with 41 slots matches all outputs on 16 Qwen3 problems with the cap raised to 32K tokens, the longest being **32,264 tokens**; on DeepSeek at batch 16 and 32 with 4,096-token outputs it matches logits and per-layer output hashes at **every step** for 10/21/31 slots; on Mixtral (256 tokens, 1/2/4 slots) likewise at every step.
- **End-to-end throughput (Fig. 6; 3 models × 4 budgets × 2 batch sizes).** IsoMoE has the highest decoding throughput in **every** setting, **1.26× on average and 1.54× at maximum** over the fastest baseline in that setting. The 1.54× point is Qwen3 at 13.5 GiB, batch 16, where the fastest baseline is IsoMoE's own BF16 variant (87.7 tok/s at the batch-8 13.5 GiB ablation point, Table II). Against baselines that must keep all experts on CPU to preserve outputs, IsoMoE reaches **1.39×–2.76×** at each model's maximum budget.
- **Ablation, Qwen3, batch 8, 13.5 GiB (Table II).** BF16 baseline 87.7 tok/s → +12-bit format **105.1 tok/s (1.20×)** while the slot memory drops 13.5 → 10.3 GiB → reuse of freed memory for 41 slots raises hit rate 67% → 75% → **118.5 tok/s (1.35×, +13% over the format-only step)** → exact mode **117.9 tok/s (1.34×)**, i.e. the determinism guarantee costs **0.5%**, within run-to-run variation (exact/fast = 1.02× on Qwen3 with 41 slots, 0.97× on DeepSeek with 21 slots).
- **CPU kernel speedup from the 12-bit format (Fig. 1b, 32 threads).** CPU expert computation with CPU order runs at **1.35× BF16**, matching the ~1.33 byte ratio (12.1 vs 16 bits), whereas zstd (ZipMoE), Huffman (DFloat11) and rANS reach only **0.59×–1.07×** despite a ~1.5 byte ratio — the decompression overhead eats the bandwidth saving.
- **CPU order vs row-major, 1–40 threads (Section VI-D).** BF16 expert compute spans ~3.3–15 GB/s per thread; CPU order stays **1.28–1.35×** BF16 across the sweep, while row-major is **1.02–1.05×** at ~8 GB/s and collapses to **0.68–0.70×** at ~15 GB/s — the layout, not the compression, is what preserves the win as bandwidth per core grows.
- **Motivational measurement (Fig. 1a).** With all BF16 experts on CPU, CPU expert compute is **82%** of each decode step at a memory read rate of **~127 GB/s** (at the measured ceiling); even with 13.5 GiB of experts resident on the GPU it is still **49%**, which is what justifies attacking the CPU path rather than the GPU path.

## Critical Assessment

**The core inversion is the paper's real intellectual contribution, and it is correct.** Almost all determinism work tries to make hardware agree on a "good" arithmetic (batch-invariant reductions, cross-hardware bit-exact kernels). IsoMoE instead notes that only *one* side is the bottleneck — CPU expert compute is 82% of the step and the GPU idles — so the GPU can afford to be the emulator. That framing also explains why the cost is near zero (117.9 vs 118.5 tok/s): the expensive side is untouched. The corollary, which the authors state plainly, is that "bitwise identical" here means identical to *KTransformers' approximate arithmetic*, `vrcp14ps` (14-bit-accurate reciprocal) included. So the paper canonizes a slightly wrong activation function as the reference; if KTransformers changes its kernel, or a user compares across engines, the guarantee evaporates. That is a legitimate design choice for reproducibility, but it means this is a *within-engine* determinism result, not a correctness result — and the paper never measures accuracy against ground truth, so we cannot tell whether the frozen reference answers are good, only that they are stable.

**The activation lookup table is a bigger constraint than the paper admits.** A 65,536-entry table of CPU BF16 activation outputs works for SiLU/GELU-style elementwise activations whose input happens to be BF16. It is presented in one sentence (line 12 of Algorithm 1). But it hard-codes the activation to a table size of 2^16, which makes the technique awkward for architectures with different activation granularity, for FP8/BF16 mixtures, or for any activation not elementwise. There is no cost analysis of the table lookup (cache footprint, gather latency relative to the two FMAs it replaces), and no ablation that removes the table to show it is not the throughput limiter.

**Baseline construction is generous in one direction and unflattering in another, and both need scrutiny.** KTransformers 0.3.2 — a system that cannot keep individual experts in GPU memory — is handed IsoMoE's slot machinery and pipeline while keeping only its CPU kernel. That is a *stronger* baseline than the released KTransformers, so the reported speedup is conservative; good. But llama.cpp keeps whole *layers* in GPU memory, so at small budgets it wastes slots on entire layers and its hit rate is structurally poor — exactly the regime where the 12-bit format's extra slots pay off. FreeToken supports only Qwen3, so two of three models have no adaptive-caching baseline at all, and HybriMoE is dropped because its released code is batch-1 with 4-bit experts — a defensible exclusion, yet it removes the one prior system that also changes placement during inference. The headline 1.54× is against IsoMoE's own BF16 variant, which is a self-ablation being counted as a baseline; the honest number is the 1.26× average, and even that averages over a benchmark set the authors chose.

**Two systems claims are asserted rather than measured.** First, the 12-bit exception side table: row segments of 64 weights whose 3-bit exponent offset overflows dump their original high bytes into a side table. The paper gives the average of 12.1 bits/weight but never says how many segments overflow, how large the side table is, or what the worst-case (data-dependent) access pattern costs. This is precisely the kind of tail behaviour that decides whether a format is deployable. Second, only decoding throughput is reported: no prefill/TTFT, no latency percentiles, no memory-footprint accounting for staging buffers and the residency table, and no cost for the offline BF16→12-bit conversion, which for a 235B model is a nontrivial one-time job.

**Scope.** All experiments are one CPU (8488C), one GPU (A6000 48 GB), PCIe 4.0×16, batch ≤32, and GPU budgets ≤37.5% of BF16 expert size. The motivating example is Qwen3-235B-A22B's 454 GB of experts, but the largest model actually run is Qwen3-30B-A3B. Nothing is said about multi-GPU, NVLink, H100-class GPUs whose Tensor-Core arithmetic differs again, AMX-capable CPUs (CoX-MoE's target), or non-x86 hosts — and the whole CPU-order trick is welded to AVX-512 `vdpbf16ps`, which has no ARM SVE equivalent as written. Generality is therefore unestablished, and the paper does not claim it, but the abstract's framing invites the broader reading.

**Rigor is otherwise high.** The correctness argument is decomposed properly (arithmetic replay, memory layout, pipeline shape, swap-in timing) and each is separately ablated or argued. Table I's fast-mode row is the right control: same engine, same format, only the replay removed, and it changes 159/160 outputs. The 49,712-swap-in online test and the 32,264-token longest-output test are exactly the stress cases a skeptical reviewer would ask for.

## Strengths

- **A sharp, well-measured problem statement.** "5 out of 56 problems unchanged after moving 12 layers' experts" and "3 out of 16 when another process holds 4 GiB" are the kind of numbers that make a systems problem undeniable, and they turn an abstract reproducibility concern into a concrete evaluation hazard.
- **The asymmetric-replay insight.** Recognizing that the bottleneck side should define the reference arithmetic, and that the idle side can afford bit-exact emulation, is a genuinely reusable idea for any heterogeneous engine.
- **CPU order is a real, non-obvious optimization.** It is not "we compressed the weights"; it is "we laid out the compressed words so that the decompressor's output *is* the dot-product operand", and the row-major-vs-CPU-order sweep (0.68–0.70× vs 1.28–1.35× at high bandwidth) shows the mechanism, not just the outcome.
- **Determinism at near-zero cost.** 117.9 vs 118.5 tok/s in the ablation and 0.97–1.02× exact-vs-fast across two models — the paper can claim the guarantee is free, and it has the numbers to back it.
- **Honest controls.** The fast-mode row in Table I, the untouched-KTransformers bitwise comparison with per-layer hashes at every step, and the 49,712-swap-in online test are all stronger evidence than the typical "we are deterministic" claim.
- **Concrete, reusable engineering detail.** `fma.rn.ftz` chosen for matching rounding *and* denormal handling, the `k=1` dummy-token trick to extract single-expert outputs without reimplementing the reduction, whole-batch-shape padding so library kernel selection cannot perturb bits.

## Limitations

- **One hardware configuration.** Single Xeon 8488C + single A6000, PCIe only, batch ≤32, GPU budgets ≤37.5%. No multi-GPU, no NVLink, no H100/B200, no AMX, no ARM. The AVX-512-specific layout has no stated portability path.
- **No accuracy evaluation.** Determinism is measured only against KTransformers' own outputs; the paper never reports task accuracy for exact vs fast mode at a *fixed* placement, so the reader cannot see what the 8.8%–10.0% answer churn in fast mode actually costs in correctness.
- **The reference arithmetic is an approximation.** `vrcp14ps`-based activations are canonicalized via a lookup table; the guarantee is relative to one engine's kernel, not to a mathematically defined function.
- **12-bit exception handling is unquantified.** Frequency of overflow segments, side-table size, and access-pattern cost are all unmeasured, as is the offline conversion cost.
- **Partial baseline coverage.** FreeToken only on Qwen3; HybriMoE excluded; CoX-MoE and Fiddler cited but never compared; llama.cpp handicapped by layer-granular placement at small budgets.
- **Decode-only.** Prefill/TTFT, tail latency, and end-to-end serving behaviour are absent, which matters because the dual micro-batch pipeline is a decode-phase design.
- **Narrow determinism scope.** Same hardware, same software, same request batch — explicitly not cross-device or cross-version reproducibility.

## Relevance

正中"Operator Precision, Determinism & Error Propagation"这一核心方向：它把跨设备浮点非结合性（AVX-512 `vdpbf16ps` 与 GPU FMA 的舍入次序差异）如何经 Top-8 路由放大成 15.8% 的路由翻转、进而改变推理输出，做了完整的因果链测量，并给出"以 CPU 算术为规范、GPU 逐位重放"的可复现推理方案；同时其 12 位无损格式与 1.26× 加速也提供了"精度保证几乎不损失性能"的实证，对评估量化/压缩方案的可复现性权衡很有参考价值。

## Questions for Further Exploration

1. The guarantee is relative to KTransformers' `vrcp14ps` activation. How much does the frozen reference differ numerically from a correctly-rounded SiLU, and would a "correct-activation" reference (with a shared exact activation on both sides) be achievable at similar cost?
2. What fraction of row segments overflow the 3-bit exponent offset on each of the three models, how large is the side table in bytes, and does the resulting access pattern show up in the tail of the per-step latency distribution?
3. How does the approach degrade on H100/B200, where Tensor-Core FP32 accumulate and denormal handling differ again, and on an SPR/AMX CPU where `vdpbf16ps` is replaced by AMX tile instructions?
4. Since the CPU is 82% of the step, what is the headroom from *also* reducing CPU work — e.g. a faster exact activation path than the 65,536-entry table, or 2:4 sparsity on the CPU — and does the placement-invariance framework constrain those choices?
5. Does the 12-bit format's extra GPU slots interact with KV-cache pressure in a way that changes the optimal budget? Qwen3's 24.1 GiB KV cache already caps its expert budget at 31.25%, so the achievable slot count is partly a KV-cache story.
6. Can placement invariance be composed with batch invariance and with cross-engine reproducibility, i.e. is there a single canonical arithmetic that a CPU kernel, a CUDA kernel, and a Triton kernel could all replay without a 20–50% throughput tax?
