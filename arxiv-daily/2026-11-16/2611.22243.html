02Why this matters

A shared prefix block is a shared point of failure. Output monitors can't see the damage; the block itself must be checked.

共享前缀缓存 = 多请求共同的故障点；被翻转后的回答看起来只是“普通答错”，只能在块一级做校验。

03 · The critical edge

Roughly half of MMLU-Pro's harm is a response that never closes </answer> — a tag a one-line regex would catch. The paper's own strongest counterargument is buried in its limitations.

04Methodology

One flipped value, inside a prefix
software emulation of a Rowhammer bit flip in vLLM's prefix cache

Every request opens with the same 96 tokens — six 16-token blocks holding a system policy, an output-format instruction, and boilerplate. A co-located tenant with ordinary privileges flips one BF16 element in the model's value cache for that prefix; all later requests read the corrupted block.

  • Only two bits matter. Bit 6 (mantissa MSB) scales a value by 1+δ, ¼<|δ|≤½; bit 15 flips the sign. Silent low bits don't collapse outputs.
  • 30 coordinates per bit, ten in each 32-token prefix part; element drawn at random inside the chosen bit.
  • Four task types: MBPP+, 5-shot TriviaQA, MMLU-Pro, and 100 hand-written medical-refusal prompts where any self-authored medical claim is wrong.
  • Pre-registered H1–H4 tested on held-out item pools; two-way cluster bootstrap over coordinates × items, Bonferroni-adjusted for confirmatory claims.

The screen needs no fault injection: 16-sample self-consistency predicts harm, while the top-1/top-2 log-prob margin predicts mere change. But 16 samples miss rare errors — a 95%-correct item is labelled non-fragile 44% of the time, which makes the H2 test conservative rather than generous.

  • MMLU-Pro changes 5× more outputs than MBPP+, yet harms a smaller fraction of them. TriviaQA changes 25× fewer than MBPP+, but each change is ~26× more likely to be a wrong answer.
  • Fresh vs returning: fresh requests change more on both held-out tasks (H3 holds), but are reliably harmed more only on TriviaQA (+1.6e-3); the MMLU-Pro harm gap is +3.6e-3 [−2.0e-3, 9.3e-3], not significant.
  • Severity, rescored: CVSS 3.1 moves from 1.8 to 5.3 (AV:L / AC:H / PR:L, A:High); silent-bit-only flips would score 2.5. A per-block checksum caught 120/120 injected flips with zero false positives at “negligible” throughput cost.

08Strengths

Discipline where it counts

  • Separates change from harm formally (h, T, h/T), then proves with a null control why change-rate studies count noise as damage.
  • Fragile-item predictor is actionable and free: screen traffic with 16-sample self-consistency, no injection required, and pair the right predictor with the right target.
  • Held-out pools, pre-registered hypotheses, two-way cluster bootstrap, Bonferroni intervals — rare hygiene for a fault-injection paper.
  • Reports its own scoring error (0.59 → 0.47), its 44% fragility misclassification, and the fact that all policy harm sits on two prompts.

09Limitations

Narrow in every dimension

  • One model, one 96-token prefix, BF16 only, two bit positions, value cache only — no key-cache, no multi-bit or correlated flips.
  • Average-case, not worst-case: elements are random within a bit, so an attacker who searches for the worst coordinate is not bounded by these numbers.
  • The spread is entangled with scoring strictness — pass-all-tests vs alias match vs letter match — and alias matching inflates the headline.
  • The policy arm is 2 of 100 hand-written prompts, hand-adjudicated with no reference answer: an illustration, not an estimate.
  • Physical chain unproven: no Rowhammer flip at bit 15, none placed in a long-lived prefix block, and ECC turns most flips into detectable errors.

10Open questions

What the paper leaves on the table

  • What is the joint distribution of fragility and baseline correctness in real traffic — how much of a workload even falls inside the denominator C?
  • How much does worst-case element selection raise h? The max/mean ratio is the missing adversarial multiplier.
  • Does the fragile-item screen survive free-form chat, where there is no reference answer and no scorer?
  • Do key-cache flips, multi-bit flips, or FP32 caches (wider exponent, more bit-14-like collapses) show the same pattern?
