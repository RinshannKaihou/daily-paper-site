# Portable Extended-Precision Floating-Point Arithmetic for Scientific Computing Kernels

> **一句话总结：** 作者用 Kokkos 写了一个 header-only C++17 多浮点库 MultiFloats.cpp（Float64x2–x4，即 106–212 bit），同一份源码经 CMake 切换即可编译到 Serial/OpenMP/CUDA/HIP；在 A100 上 Float64x4 加法达 15,726 MOps/s（为 CAMPARY 的 1.5 倍）、Kokkos 抽象开销 <1.7%，CPU 上 Vec4 SIMD 版 Float64x4 比 QD 的 qd_real 快 4.2–6.6 倍，加乘对 1024-bit MPFR 在 10,000 个随机输入上为 0 ULP，但 Float64x4 除法/开方最大误差仍有 1.71/17.9 ULP。

> **TL;DR:** MultiFloats.cpp is a header-only C++17 multi-float (double-double through quad-double, 106–212 bits) library built on Kokkos so one source tree compiles for Serial, OpenMP, CUDA and HIP. On an A100, Float64x4 addition reaches 15,726 MOps/s (1.5× CAMPARY's 10,468) with under 1.7% Kokkos overhead versus raw CUDA; on a single EPYC 7313 core, GCC-compiled Vec4<Float64x4> add/mul/div cost 6.09/5.37/42.20 ns versus QD's 38.85/35.51/218.17 ns (4.2–6.6× faster); addition and multiplication are exact (0.0 ULP vs 1024-bit MPFR over 10,000 inputs in [0.1, 1000]) while Float64x4 division and square root peak at 1.71 and 17.9 ULP. The portability claim is real and cheap; the speedup claim is partly a SIMD-vs-scalar and GCC-vs-Clang codegen artifact, and Julia's MultiFloats.jl is actually slightly faster than this library on A100 add/multiply.

## 核心贡献

- **一套源码覆盖四种后端**：基于 Kokkos 的 `KOKKOS_LAMBDA` 内核，只改 CMake backend 就能在 Serial / OpenMP / CUDA / HIP 上编译，A100 与 GH200 上相对原生 CUDA 的开销实测 ≤1.7%，彻底避免了为 NVIDIA 和 AMD 各写一份扩展精度实现。
- **显式 SIMD 类型 `Vec<T,W>`**：把 W 个多浮点展开按 struct-of-arrays 布局存放，绕开 GCC 对 array-of-structures 两和（two-sum）依赖图无法自动向量化的问题，Float64x2 的加法/乘法因此提速 1.9–2.2×，Float64x3/x4 的三、四 limb 除法提升最高 4.7×。
- **FMA 残差式 `two_prod`**：用 `fma(a,b,-prod)` 求乘法的精确残差，而不是 Dekker 拆分，因此可以在 `-ffp-contract=fast` 下正常工作；CAMPARY 的拆分序列必须 `--fmad=false`，作者把这个差异直接归因于两者在 A100 上 1.1–1.6× 的性能差距。
- **一套可验证的 SHOC 风格基准**：7 个 kernel（AXPY/DOT/Reduction/Triad/SpMV/GEMM/FFT）× 8 个精度级别（Float64x1–x4、Float32x2–x4）× GPU/CPU，并且用 1024-bit MPFR 做 ULP 精度参照，同时给出 add/mul/div/sqrt 与超越函数的误差。

## Key Contributions

- **One source path for CUDA and HIP.** Every kernel is a Kokkos `KOKKOS_LAMBDA`, and `MultiFloat<T,N>` operators are `KOKKOS_INLINE_FUNCTION`, so extended-precision values live directly in a `Kokkos::View` and the native `parallel_for` form is preserved. Backend selection happens at configure time; the arithmetic types and kernel source are untouched. Measured abstraction cost is below 1.7% on both A100 and GH200 against a same-session raw-CUDA baseline.
- **`Vec<T,W>` struct-of-arrays SIMD types for CPUs.** GCC does not recover packed AVX instructions from the inlined two-sum graph of an AoS representation, while Julia's LLVM pipeline apparently does. Exposing W independent expansions in SoA order lets `Vec4<Float64x2>` advance four values without a runtime transpose, yielding 1.9–2.2× on Float64x2 add/multiply and up to 4.7× on three- and four-limb division versus GCC scalar code.
- **FMA-residual `two_prod`, enabling `-ffp-contract=fast`.** `two_sum` uses Knuth's sequence (insensitive to FMA contraction) and `two_prod` computes its residual as `fma(a, b, -prod)` rather than Dekker splitting. This is the stated reason the library keeps fused operations where CAMPARY must disable FMA contraction.
- **A cross-precision, cross-vendor benchmark suite.** Seven SHOC-style workloads across Float64x1–x4 and Float32x2–x4, ULP measurements against a 1024-bit MPFR reference, and performance comparisons against QD, CAMPARY, MPFR and Julia MultiFloats.jl on A100, GH200 and an AMD RX 780M.

## Methodology

**Representation and primitives.** A value is an unevaluated sum of N IEEE limbs: `MultiFloat<T,N>` is a fixed-size aggregate with no allocation or runtime polymorphism (`Float64x2` aliases `MultiFloat<double,2>`), targeting ≈53N bits of significand. Arithmetic follows Hida et al.'s QD algorithms: `two_sum` (Knuth) + `two_prod` (FMA residual), then a fixed number of renormalization sweeps (five for Float64x4, chosen to control GPU register pressure "without affecting the observed ULP error"). Division and square root use Newton–Raphson iterations over the multi-limb primitives. The default Float64x4 `sqrt` uses a 1→2→4 refinement that skips the three-limb stage; `sqrt_accurate` extends to four limbs at roughly twice the cost.

**Kokkos integration.** Because operators are device-callable, an extended-precision AXPY keeps the ordinary `parallel_for` form; only the CMake backend changes between Serial, OpenMP, CUDA and HIP. `Vec<T,W>` (AoS→SoA) provides the explicit SIMD path for CPU targets.

**Benchmark design.** Seven SHOC-style workloads spanning the complexity ladder: micro-operations (N=10K on CPU, 10M on GPU), Level-1 kernels (N=1M), SpMV (100K rows, CSR, 5 nnz/row), GEMM (N=64–4096, LayoutLeft), FFT (256–1M, complex), and a 10K-input accuracy suite reporting ULP statistics on the host (Table I).

**Protocol.** CPU micro-operations are pinned with `taskset -c 0`, warmed for three seconds, and timed over five trials with N=10,000; OpenMP runs use N=1M with close thread binding and 1–16 cores. GPU runs use N=10M, one warmup, 50 invocations per trial, explicit fences and a device-quiescence check via `nvidia-smi`. Every reported number is the median of three independent runs, each run being the best of five measurements.

**Systems and software.** AMD EPYC 7313 (16-core, AVX2+FMA, 3.0 GHz ceiling), NVIDIA A100 80 GB PCIe, GH200, and an AMD RX 780M (RDNA 3) for HIP; GCC 13.3.0 and Clang 21.1.8 with `-O3 -march=native -ffp-contract=fast`; CUDA 12.9 / NVHPC 25.7, Kokkos 4.7.02, ROCm 6.3.1, Julia 1.12.5 with MultiFloats.jl v3.2.6 and CUDA.jl 6.2.0, QD v2.3.22 with `QD_IEEE_ADD`, MPFR as the accuracy oracle.

## Results & Highlights

- **A100 micro-operations (Table VII, N=10M).** Float64x4 addition sustains 15,726 MOps/s versus 10,468 MOps/s for CAMPARY (+50%, the headline 1.5×); multiplication 16,605 vs 10,520; division 7,099 vs 6,601; square root 7,275 vs 6,468. But Julia MultiFloats.jl is *faster* than MultiFloats.cpp on addition (16,581 vs 15,726) and multiplication (17,189 vs 16,605) at Float64x4, and at Float64x2 CAMPARY is essentially tied (34,238 vs 34,786) — the "1.5×" is against the weakest of the three extended-precision baselines.
- **CPU micro-operations (Table II, EPYC 7313 single core, GCC 13.3).** `Vec4<Float64x4>` costs 6.09 / 5.37 / 42.20 / 190.63 ns per op for add / mul / div / sqrt versus QD's `qd_real` at 38.85 / 35.51 / 218.17 / 802.0 ns, i.e. 6.4× / 6.6× / 5.2× / 4.2× (the reported 4.2–6.6×). At Float64x2 the same comparison is 0.73 vs 1.53 (add) and 0.47 vs 2.36 (mul) against `dd_real`, but division is *slower* than scalar GCC (3.58 vs 2.39 ns/op) because a "correctness-preserving GCC anti-vectorization guard" fires.
- **Accuracy against 1024-bit MPFR (10,000 random inputs in [0.1, 1000]).** Addition and multiplication give 0.0 ULP at every tested precision. Float64x2 division peaks at 2.15 ULP (median 0.11) and square root at 0.45 ULP (median 0.06); at Float64x4 the maxima are 1.71 and 17.9 ULP (medians 0.02 and 0.14) — so square-root accuracy is 40× *worse* at four limbs than at two, because the default refinement skips the three-limb stage. `sqrt_accurate` restores 1.2 ULP at about 2× the cost. Float32-based division/square root peak at 2.40/0.46 ULP (two limbs) and 1.72/19.85 ULP (four limbs).
- **Kokkos abstraction cost.** A same-session direct comparison against handwritten raw CUDA puts the overhead below 1.7% on both A100 and GH200 — the single strongest portability result in the paper, and the one claim the benchmark design supports cleanly.
- **GPU kernels on A100 (Table VIII, N=10M).** AXPY falls from 102,469 MOps/s (Float64x1) to 15,334 (Float64x4), a 6.7× slowdown; DOT 41,384 → 8,334 (5.0×); SpMV 73,001 → 15,508 (4.7×); FFT 5,684 → 1,330 (4.3×). Float32x2 AXPY reaches 101,998 MOps/s, 99% of native Float64x1 while carrying a ~48-bit significand.
- **GEMM (A100, N=4096).** The naive kernel drops from 283 GFLOPS at Float64x1 to 38.8 GFLOPS at Float64x4; a 16×16 shared-memory tile lifts Float64x1 to 2,049 GFLOPS and Float64x2 to 333 GFLOPS but "provides little benefit at three and four limbs, where the O(k²) arithmetic dominates data reuse". On GH200 the tiled rates are 3,423 and 127 GFLOPS for Float64x1 and Float64x4, against a stated 33.5 T FP32/FP64-class peak. GEMM stays below 10 ULP at Float64x2 and hits 0.0 ULP at Float64x3–x4 for N ≤ 32.
- **OpenMP scaling (16 threads, EPYC 7313).** At ≥2 limbs, AXPY/DOT/Reduction/Triad/SpMV keep 88–97% parallel efficiency; Float32x4 AXPY goes 17.2 → 259 MOps/s (15.1×, 94% efficiency), and FFT efficiency rises from 20% to 74% (Float64) and 44% to 82% (Float32) as limbs increase — consistent with a shift from bandwidth-bound to compute-bound.
- **Transcendentals.** On A100, Float64x2 `exp` reaches 10,952 MOps/s but Float64x4 only 757 (14.5× slowdown, versus 4.3× for addition); on CPU, Float64x4 `exp`/`log`/`sinpi`/`cbrt` cost 2202/1425/1786/477.1 ns/op versus Float64x2's 186.6/141.9/227.6/79.04. Against 1024-bit MPFR, `exp`/`log`/`sinpi` have 8–38 ULP maxima and sub-1-ULP medians.
- **FFT error amplification.** Against an O(N²) MPFR DFT at N=256, mean errors are 5.4 / 3.2 / 1.5 / 1.0 ULP with maxima of 810 / 365 / 157 / 100 ULP for x2–x4 — the maximum only drops 8× while cost rises 4.3×.
- **Cross-vendor run (Table IX).** The identical Float64x2 source gives 34,717 MOps/s on A100 CUDA versus 1,589 on RX 780M HIP for addition (21.8×) and 43,950 vs 1,119 for AXPY (39.3×); the authors state plainly that these ratios "stem from the hardware gap, not the quality of the code".

## Authors & Credibility

Single-author paper by Manas Vishal (Department of Mathematics, University of Massachusetts Dartmouth), published at IEEE HPEC 2026 as a short conference paper. The author's prior line of work is exactly the motivating application: time-domain solvers for the scalar Teukolsky equation with singular source terms (Phys. Rev. D 110, 104009, 2024), superconvergent DG methods for waveform/self-force computation on hyperboloidal domains (GRG 57, 104, 2025), and a 2026 PhD dissertation on precision and perturbation in black hole dynamics. That history makes the "we needed more than Float64 in our EMRI/self-force solvers" framing credible rather than rhetorical. Code, data and artifact are released at github.com/manasvishal/MultiFloats.cpp. Acknowledged readers include Sigal Gottlieb, Gaurav Khanna, Aaron Jarmusch and Connor Kenyon; A100/GH200 access came from UMass Dartmouth via MGHPCC Unity. Weaknesses of provenance: one author, one institution, no independent replication, and GPU coverage limited to a single A100 PCIe, a single GH200 and an iGPU.

## Critical Assessment

**Novelty.** The arithmetic is not new — it is Hida's QD algorithm family with an FMA-residual `two_prod`, and the paper says so. The genuine novelty is engineering: (a) a single Kokkos-based C++17 source compiling to CUDA and HIP, which the related-work section correctly identifies as missing relative to QD (CPU), CAMPARY (CUDA), GQD (CUDA) and MultiFloats.jl (Julia); and (b) the `Vec<T,W>` SoA layout as an explicit workaround for GCC's failure to vectorize the inlined two-sum graph. Both are modest but real contributions for a 4-page HPEC paper.

**The headline comparison is not against the strongest baseline.** The abstract advertises 15,700 MOps/s "or 1.5× CAMPARY". Table VII shows Julia MultiFloats.jl at 16,581 MOps/s for Float64x4 addition and 17,189 for multiplication — both *above* MultiFloats.cpp's 15,726 and 16,605 — and CAMPARY is only 1.5× behind because it is restricted to double limbs and to k≤4. So on the one metric the abstract leads with, the library does not beat the state of the art; it beats the slowest competitor. The paper's own text concedes "within 6%" and "within 1.2×", which is honest, but the abstract's framing is not.

**The 4.2–6.6× CPU result is largely a compiler artifact and a SIMD-vs-scalar comparison.** Table II shows GCC scalar Float64x4 add/mul at 23.12/24.14 ns against Clang's 6.30/6.30 ns — a 3.7× gap from code generation alone. The Clang scalar path is within 3% of `Vec4` on addition (6.30 vs 6.09), 17% on multiplication, 1% on division and 3% on square root, which means the explicit SoA layout buys almost nothing once the compiler does its job. The 6.4× "vs QD" therefore stacks a SIMD-vs-scalar comparison on top of a GCC-vs-Clang comparison. A fair test would be `qd_real` hand-vectorized with AVX2 intrinsics, DoubleFloats.jl, or an xsimd port; none is included. The codegen picture is also non-monotonic and unexplained: Clang nearly matches GCC at Float64x4 (6.30 vs 23.12) yet is 3× *worse* than GCC at Float32x2 addition (2.18 vs 0.70) and does not recover at Float64x3 (10.98 vs 11.73 GCC, versus 2.65 for `Vec4`). That cliff-shaped behaviour is presented as motivation, not investigated.

**Square-root accuracy degrades with precision and this is under-sold.** Float64x2 `sqrt` peaks at 0.45 ULP, but Float64x4 peaks at 17.9 ULP — a user adding limbs specifically to gain accuracy gets 40× worse square root. The abstract's "division and square root remain within 1.71 and 17.9 ULP" reads as reassurance; no baseline is given for `sqrt_accurate` (1.2 ULP at ~2× cost) against QD's 802 ns/op or CAMPARY's 6,468 MOps/s, so the reader cannot tell whether the accurate variant is still competitive. Since Newton–Raphson square root appears inside normalization and FFT butterflies, 17.9 ULP local error is exactly the kind of thing this audience would want bounded, not just reported.

**Accuracy testing avoids the regimes the paper admits are broken.** The ULP study uses 10,000 random inputs in [0.1, 1000]. The limitations section concedes that subnormal inputs underflow intermediate products and that values near the Float64 overflow threshold degrade the refinement — yet neither regime is measured, and neither is a cancellation-heavy or ill-conditioned input, even though the introduction motivates the entire work with Rump's polynomial at (77617, 33096), where Float64 returns −1.18×10²¹ against a true value of ≈−0.8274 and Float64x2 gets the *wrong sign*. Reporting 0.0 ULP on benign random inputs validates plumbing (error-free transformations plus renormalization are exact by construction); it does not validate the division, square-root or transcendental paths under stress.

**The "cross-vendor portability" experiment measures the hardware, not the code.** Table IX compares an A100 80 GB PCIe against an RX 780M integrated GPU sharing system memory, producing 17–39× gaps that say nothing about code quality; the authors acknowledge this in the caption, which is to their credit, but then the table still functions as the portability evidence. There is no roofline normalization per device, no efficiency percentage, and no second discrete AMD GPU — so "runs on HIP" is demonstrated while "performs portably on HIP" is not.

**GEMM is a straw man.** The GEMM evaluation is a naive kernel plus one 16×16 shared-memory tile, compared to no extended-precision GEMM baseline other than an MPFR accuracy check. The 38.8 GFLOPS Float64x4 figure against a 9.7 T FP64 peak says almost nothing about achievable efficiency, and the claim that tiling "provides little benefit at three and four limbs" is asserted without isolating register pressure — especially since the five renormalization sweeps are justified by register control, yet no sweep-count ablation is shown.

**A silent-wrong-answer compiler bug is disclosed but not systematized.** Clang 21's SLP vectorizer "corrupts the low limbs of the Float64x2 FFT under the reported optimization flags"; the fix is to disable SLP for Clang FFT targets only. That means the library produced numerically wrong results under a mainstream compiler with the paper's own recommended flags, and the mitigation is a per-target workaround rather than a compiler/flag test matrix or CI. For a library whose entire value proposition is bit-level accuracy, the absence of a multi-compiler accuracy regression suite is the most consequential gap.

**Protocol caveats.** Every number is the "median of three independent runs of best-of-five measurements" — the per-run best-of-five biases optimistically, and with only three runs the spread is unreported. Coverage is a single EPYC 7313 socket, one A100 PCIe, one GH200 and one iGPU: no H100, no MI300, no multi-node, no NUMA study. MPFR is unavailable on device, so the GPU comparison set reduces to Julia plus (double-limb-only) CAMPARY. And there is no end-to-end scientific result at all: the motivating EMRI/self-force application is explicitly deferred to future work, so "extended precision can remain practical" rests entirely on microbenchmarks and SHOC kernels.

## Strengths

- The portability result is genuinely useful and cleanly measured: one C++17 source, one `KOKKOS_LAMBDA` per kernel, backend chosen at configure time, and ≤1.7% overhead against raw CUDA on two different NVIDIA parts.
- The FMA-residual `two_prod` argument is well made: using `fma(a,b,-prod)` instead of Dekker splitting keeps `-ffp-contract=fast` legal, and the paper grounds the 1.1–1.6× advantage over CAMPARY in exactly that difference rather than hand-waving.
- `Vec<T,W>` is the right shape of fix for a real problem (AoS two-sum graphs defeat GCC's vectorizer), and the paper quantifies both the wins (1.9–2.2× at Float64x2, up to 4.7× on multi-limb division) and the loss (Float64x2 division at 3.58 vs 2.39 ns due to the anti-vectorization guard).
- Breadth of evaluation: 7 SHOC-style workloads × 8 precision levels × 2 compilers × 3 accelerators, plus 1024-bit MPFR as an accuracy oracle — far more than a typical 4-page library paper.
- Unusually honest reporting of negative or awkward results: CAMPARY tied at Float64x2, Julia ahead on A100 add/multiply, non-monotonic square-root error, the Clang SLP bug, and the admission that subnormals and near-overflow inputs break the refinement.
- Header-only delivery, artifact on GitHub, and `KOKKOS_INLINE_FUNCTION` throughout, so adoption in an existing Kokkos code is essentially a `#include` plus a type alias.

## Limitations

- No end-to-end scientific application result; the EMRI/self-force solver that motivates the work is deferred to future work.
- No performance-portability normalization: cross-vendor numbers compare a discrete A100 against an integrated RX 780M, giving ratios that reflect hardware class rather than code.
- Float64x4 square root at 17.9 ULP (vs 0.45 ULP at Float64x2) with no cost-vs-accuracy comparison of `sqrt_accurate` against QD or CAMPARY.
- Accuracy suite restricted to benign random inputs in [0.1, 1000]; no subnormal, near-overflow, cancellation-heavy or ill-conditioned tests despite those being named as failure modes.
- No comparison against vectorized QD, DoubleFloats.jl, or an intrinsics-based double-double implementation, so the 4.2–6.6× claim conflates SIMD with algorithmic quality.
- GEMM evaluated only as naive plus one 16×16 tile, with no extended-precision GEMM baseline and no register-pressure or sweep-count ablation.
- Hardware coverage is thin for a portability paper: one A100 PCIe, one GH200, one iGPU; no H100/MI300, no multi-node, no NUMA effects.
- Compiler robustness is a single workaround (disable SLP for Clang FFT) rather than a tested matrix; no CI for numerical correctness across compilers and flags.
- No discussion of thread safety, error handling for unsupported `N`, memory footprint per value beyond "bytes per value", or interaction with Kokkos reductions/atomics at multi-limb granularity.

## Relevance

直接落在「Operator Precision, Determinism & Error Propagation」核心议题上：它把扩展精度运算的 ULP 误差（含 0 ULP 的 error-free transformation、除法/开方/超越函数的误差上界）与跨后端（CUDA/HIP/OpenMP）数值一致性放在同一套基准里量化，是研究 kernel 级舍入误差与可复现性的少见的系统化对照数据。同时它对「编译器代码生成差异导致数值/性能偏差」（GCC 不向量化、Clang SLP 破坏低位 limb）的记录，也与该方向关注的编译器数值 bug 直接相关。

## Questions for Further Exploration

1. If `qd_real` or `dd_real` were hand-vectorized with AVX2 intrinsics, or DoubleFloats.jl were used as the baseline, would the 4.2–6.6× CPU advantage survive — or is it entirely a SIMD-vs-scalar plus GCC-vs-Clang artifact?
2. On A100, Julia MultiFloats.jl edges out MultiFloats.cpp on Float64x4 add (16,581 vs 15,726) and multiply (17,189 vs 16,605). What specifically does LLVM emit that NVCC does not, and is the gap closeable by changing the renormalization schedule?
3. What is the actual cost of `sqrt_accurate` (1.2 ULP) at Float64x4 on CPU and GPU, and does it stay faster than qd_real's 802 ns/op and CAMPARY's 6,468 MOps/s?
4. How many renormalization sweeps are genuinely required at Float64x4 on GPU, and what does each sweep buy in ULP versus registers? The "five sweeps" choice is justified only qualitatively.
5. Does 17.9 ULP local square-root error propagate into a visible waveform phase error in the Teukolsky/EMRI solver, or is it washed out by the surrounding arithmetic?
6. Which compiler/flag/architecture combinations silently produce wrong results? The Clang 21 SLP corruption of Float64x2 FFT low limbs suggests the current mitigation is per-target patching rather than a tested correctness envelope.
7. Normalized to each device's achievable roofline, what efficiency does Float64x4 AXPY achieve on A100 (15,334 MOps/s at N=10M) versus the bandwidth-bound ceiling — and how far is the naive GEMM at 38.8 GFLOPS from what a proper tiled or tensor-core/Ozaki implementation could reach?
