> **一句话总结：** GNoF 把 NVMe-oF/RDMA 的完整数据路径（64 B 命令胶囊构造、mlx5 SEND WQE、BlueFlame 门铃、CQ 收割）搬进 GPU 设备代码，再用门铃合并器、批量 CQ 轮询（无锁快速窥视 + 单调完成计数器）和集合相联的 GPU 页缓存替代自旋等待，在 200 Gb/s InfiniBand 上以 0.37% 主机 CPU、约 1% SM 占用达到每客户端 1.77 M 4 KB IOPS，并在列扫描上比整镜像搬运快 10–22×。

> **TL;DR:** GNoF is a client-side, target-agnostic GPU-initiated NVMe-oF/RDMA data path that runs against an unmodified SPDK target and needs no SSD firmware change. Replacing BaM-style lock-step spin-polling with doorbell coalescing, batched lock-free CQ drainage, and an on-demand GPU page cache, it hits 1.77 M 4 KB IOPS at 0.37% host CPU and 0.03–1.07% SM throughput occupancy — versus 40.3% host CPU for kernel nvme-rdma and ~100% SM issue for BaM over a BlueField-3 DPU or a local SSD. On a NYC-taxi cold column scan (38.3 M rows, 2.85 GB image, 6 queries) it is 10–22× faster than a fixed ~5 s bulk-image load with bit-identical results; the paper is explicit that bulk staging still wins BFS on an 8.5 GB graph (9873 ms vs 11870 ms).

## 核心贡献

- **首个不用改目标端/固件的 GPU 原生 NVMe-oF/RDMA 发起端**：GPU 线程自己构造 64 B NVMe 命令胶囊（keyed SGL 指向 VRAM）、写 32 B mlx5 SEND WQE、敲 BlueFlame 门铃、解析 CQ，字节级兼容 libmlx5 的 provider 契约，因此未改动的生产级 SPDK `nvmf_tgt` 可直接接受流量；CPU 只保留连接建立、admin 队列和一个 keep-alive 线程。
- **两个面向长 RTT 的队列机制**：门铃合并器（doorbell mover）把一轮突发里每线程的门铃收敛成一次 MMIO（按连续 `wrote[]` 前缀扫描，保留 WQE 顺序）；批量 CQ 收割用无锁 `fast peek`（先读 owner bit，不碰锁字）+ 单把 poll 锁一次性排空整批 + 单调递增的 per-slot 完成计数器（从不回清标志，结构上消除丢失唤醒）。
- **按需远程分页的 GPU 页缓存**：8 路集合相联、引用计数钉住、`fetch`/`wait` 拆分以实现 miss 流水线，以及"孤儿填充接管"（owner 线程卡住约 100 ms 后其它线程可代为收割），让线程超额订阅时仍有进展。
- **槽位即 CID + 在飞守卫**：SQ 槽号直接当 NVMe CID 用，handle 用 `(target+1)<<32 | slot` 编码；只有 `head - resp_done < sq_slots` 时槽才可认领，从根上消除"胶囊在响应回来前被复用"的 send-CQE-lag 竞态。
- **一份诚实的四方案对比评测**：与 kernel nvme-rdma、BaM over BlueField-3 SNAP DPU、BaM on local SSD 在相同工作负载下对齐在飞请求数 C，同时测量 SM 占用、主机/DPU 资源成本、干扰免疫、三级 I/O 引起的 GPU 停顿，并明确指出 GNoF 输给批量搬移的场景。

## Key Contributions

- **A complete GPU-resident NVMe-oF/RDMA engine.** Device-side construction of 64 B NVMe command capsules with keyed SGLs targeting VRAM, mlx5 SEND WQE posting, BlueFlame doorbells, and CQ parsing — byte-compatible with the CPU libmlx5/provider contract, so an unmodified production SPDK target accepts the traffic without target- or SSD-firmware changes.
- **Two queue mechanisms that let thousands of GPU threads share 64 queues without serializing on the NIC.** (i) A doorbell mover that coalesces a burst's per-thread doorbells into one MMIO ring by scanning the contiguous prefix of set `wrote[]` flags under a single `db_lock`, updating the DBrec and ringing BlueFlame once per batch. (ii) A batched CQ poller with a lock-free fast peek on the head CQE's owner bit, one poll lock that drains the entire ready batch, and monotonic per-slot completion counters that never clear a flag — structurally eliminating lost-wakeup races.
- **A GPU page cache for on-demand remote paging.** Set-associative (8-way, Fibonacci-hashed set selection), reference-pinned against eviction, with `gnof_pc_fetch` split from `gnof_pc_wait` so a thread can pipeline many misses; duplicate requests for an in-flight LPN wait on the slot instead of re-issuing I/O; orphan-fill takeover after a ~100 ms grace lets any thread reap a wedged owner's handle because `gnof_wait` is valid from any thread.
- **A careful treatment of discrete-GPU non-coherence.** NIC-produced data is read with `__ldcg` to bypass stale L1 lines, MMIO doorbells use `st.mmio.relaxed.sys`, and `__threadfence_system()` precedes publishing WQEs/completions observed by the HCA or peer threads.
- **A four-scheme characterization** that positions the contribution as much in the controlled comparison as in the mechanism: where GPU-native fabrics access is decisive (selective analytic I/O, interference immunity) and where simple bulk staging remains pragmatic.

## Methodology

The design partitions the NVMe-oF stack by critical-path relevance rather than by the historical CPU/GPU boundary. The CPU control plane runs at session open only: open the HCA and protection domain, RDMA-CM connect an admin QP and perform fabrics CONNECT / Identify / Set-Features, create one RC QP per I/O channel with the correct private data (probing real mlx5 ring geometry via `mlx5dv_init_obj`, since mlx5 pads the ring beyond the requested depth), allocate and register a single GPU memory pool via `ibv_reg_mr` over `nvidia-peermem`, post the RQ of Recvs targeting GPU response slots, `cudaHostRegister` the SQ/CQ/DBrec buffers and the BlueFlame UAR page so the GPU can MMIO them, and then start one keep-alive thread. After setup the host blocks rather than spins.

The GPU data plane holds 64 channels (one RC QP = one NVMe-oF I/O queue pair) with 256 SQ slots and 1024 CQ entries each; threads pick `chans[tid % n]`. Submission claims a slot with a single CAS on `sq_head`, fills the 64 B capsule with `gnof_build_rw` (keyed SGL with the pool rkey, zero-based NLB), writes the 32 B SEND WQE at the true HCA ring position (`cnt & (sq_ring_cnt-1)`), then commits through the doorbell mover. Completion reaping extracts the CID from each recv CQE (handling both the inline-data segment and the RQ buffer indexed by the software recv tail, since non-SRQ RQ CQEs do not carry the WQE index), writes status into `cplstat[slot]`, `atomicAdd(comp[slot],1)`, re-posts the Recv, and updates the CQ consumer-index DBrec before publishing the consumer counter. Waiters spin on `comp[slot] > target` with a ~10 s time budget that returns `0xffffffff` on expiry instead of hanging; the same poll routine is invoked by in-flight-full and page-cache waiters as "helping," so a blocked thread still makes queue progress.

The page cache carves fixed 4 KB slots from the registered pool with per-set spinlocks, global LRU stamp ticks, per-slot reference counts, and `EMPTY/FILLING/VALID` slot states. On a miss a thread claims a victim (empty, else oldest unreferenced), marks FILLING, submits the fetch round-robin without waiting, and returns PENDING; with no free way, `fetch` returns RETRY rather than blocking while holding pins.

Evaluation runs on a GPU client (Ada-generation datacenter GPU, 46 GB VRAM, compute capability 8.9, plus a BlueField-3 DPU) and a remote target exporting high-endurance enterprise NVMe SSDs through an unmodified SPDK NVMe-oF target, connected by 200 Gb/s InfiniBand. The GPU and NIC sit across a NUMA boundary (SYS topology class), which the authors report rather than assume away. Four schemes are aligned by total in-flight requests C (not thread or core count): P1 kernel nvme-rdma + fio/io_uring into host memory; P2 GNoF; P3 BaM over BF3 SNAP (DPU Arm initiator, queue depth capped by SNAP `MQES=64`); P4 BaM on a local SSD. All use direct I/O, one scheme at a time, three repetitions. SM occupancy is measured with Nsight — `ncu` for GNoF, `nsys` GPU metrics for BaM because `ncu` cannot replay its BAR-side-effect kernels.

## Results & Highlights

- **Resource cost at peak concurrency (C=1024, Table 3):** GNoF spends 0.37% host CPU versus 40.3% for kernel nvme-rdma (P1), 0.90% for BaM over the DPU (P3, which additionally burns 24.8% of the DPU's Arm cores), and 1.20% for BaM local (P4) — a ~109× reduction in host CPU against the CPU-centric baseline at comparable fabric throughput.
- **SM occupancy (Table 2, Figure 2):** GNoF's `sm_throughput` rises only 0.03% → 0.13% → 0.53% → 1.07% across T = 128/512/2048/4096 threads with warps-active capped at 16.67%, while BaM (P3 and P4) sits at ≈100% SM-issue/GR-active at every thread count — the paper's central claim that GPU-native I/O need not cost the SM.
- **4 KB random-read throughput (Figure 3):** GNoF peaks at ~1.77 M read IOPS and ~1.0 M write IOPS per client; P1 saturates as early as C=64 while GNoF and P3 ramp to 1.2–1.8 M IOPS, and P4 plateaus at only ~55 K random / ~126 K sequential IOPS regardless of C — a same-drive fio test at 1.76 M IOPS proves that is BaM's lock-step read path, not the device (7% of capability), whereas its writes scale normally to 1.17 M.
- **Single-I/O latency (strict in-flight=1, ≥500 requests/point):** P1 and GNoF show comparable ~98 µs end-to-end RTT for a 4 KB read, but GNoF uses 0.2% host CPU versus 17.6% and has a lower p99 (135 µs vs 197 µs) — the low-SM design costs nothing in latency.
- **Interference immunity (Figure 5):** with 0→72 host cores burned by pinned `while(1)` loops, GNoF/P3/P4 hold normalized throughput ≈1.00 through 36 burned cores, and P1 only degrades to 0.84–0.94 past 56 cores; burning the DPU Arm (P3 only) leaves throughput flat through 4 cores but drops it to 0.59 at 8, exposing the SNAP initiator as P3's structural bottleneck.
- **Async overlap (CoPilotIO's intra-warp taxonomy):** GNoF achieves a 2.60× speedup from compute/I/O overlap across compute:IO ratios with 36/36 zero-failure runs, versus 2.25× for P1 which pays a ~139 µs per-round kernel-launch cost; BaM's device async primitives race (Xid43) and cannot run this test at all.
- **Selective column I/O (NYC taxi, 38.3 M rows, 2.85 GB image, 6 queries):** cold GNoF runs take 224–804 ms against a fixed ~5 s full-image bulk load, i.e. 10–22×, with results bit-identical to an independent NumPy reference.
- **Honest losses:** BFS on the 8.5 GB R-MAT graph is slower with GNoF (11870 ms) than bulk staging (9873 ms), and vector-add reaches 863 MiB/s / 3.56 s at T=512 versus 1.56 s for the best staged pipeline; inter-SM contention costs GNoF 5–8% through 32 copy SMs but collapses to 0.227 retention at 48 as the DRAM subsystem saturates and CQ polling is starved.

## Authors & Credibility

Lei Tian (corresponding author) and Wenhao Gu, both at the National University of Defense Technology (NUDT). The paper is a well-scoped systems contribution written in a single-anchor, single-testbed style: no industry co-authors, a modest prototype ("on the order of a few thousand lines of CUDA/C++"), and an explicitly enumerated reproducibility appendix. Credibility markers are unusually strong for a preprint of this length: the design is specified completely enough to re-implement (Algorithm 1 plus the state-block layout, owner-bit validity rule, monotonic counters, and page-cache state machine), failures are reported as failures (P3's `MQES=64` cap returns FAIL rather than a missing sample; BaM's Xid43 race is documented with an exclusion chain), and the related-work section names the closest concurrent system (GNStor, arXiv:2606.04908) and states plainly what it does differently. The main credibility caveats are that this is a client-only probe with no deployment story, and that the "reference implementation may be released separately" phrasing means no artifact exists yet.

## Critical Assessment

The core intellectual move — "keep polling, but make it cheap" — is deliberately less glamorous than CoPilotIO's "move polling back to the CPU with hardware-barrier wakeups," and the paper argues the trade-off well: GNoF avoids both a host-side co-pilot and a dependency on platform barrier/GDRCopy support, at the cost of inventing the batching machinery that makes device-side waiting affordable over a 10–100 µs fabric RTT. The monotonic completion counter is the cleanest idea in the paper: because `comp[]` never decrements and a waiter snapshots its target at claim time, the lost-wakeup race is eliminated by construction rather than by careful flag protocol, which is the kind of invariant that survives being re-implemented by someone else.

The evaluation is more honest than most, and that honesty is also where the paper is weakest. Three of the four quantitative claims rest on comparisons the authors themselves flag as mismatched: BaM's ~55 K random-read IOPS is a BaM-library limitation (P4 writes scale to 1.17 M on the same drive), so the dramatic "GNoF vs. BaM local" gap partly measures BaM's read path rather than a fundamental local-vs-fabric trade-off; the single-flight latency comparison is explicitly not same-caliber because the stock BaM tool reports batch-amortized elapsed/ops over 64 threads and emits no percentiles, leaving the ~98 µs / p99 135 µs numbers without a matched GPU-native fabrics counterpart. And the paper concedes in §6.8 that application-level BaM numbers are "the principal remaining gap" — BaM ships BFS/CC/vector benchmarks but they were not integrated into this campaign, so Table 4's application comparison is effectively GNoF vs. bulk staging only, with no BaM or CoPilotIO column. That is a significant hole given that BFS and columnar scans are exactly where the BaM line of work claims its wins.

Several specific weaknesses deserve naming. (1) **Single testbed, single topology.** Everything is measured on one Ada GPU across a SYS (NUMA-crossing) host bridge; the authors concede near-switch P2P numbers may differ, which matters because the entire 5–8%-loss-then-collapse-at-48-SMs inter-SM result is a DRAM-subsystem-saturation artifact that would move with topology. (2) **No ablation of the three mechanisms.** The doorbell mover, the batched poller with monotonic counters, and the page cache are presented as a bundle; there is no measurement of, say, GNoF with per-command doorbells or with naive flag-clearing completion, so the reader cannot attribute the 1.07% SM occupancy among them. The paper's own motivation section claims "thousands of unsynchronized doorbells serialize on the NIC MMIO region" — that claim is never quantified, which is precisely the ablation that would justify contribution #2. (3) **BFS results are counterintuitive and underexplained.** The 2.13 GB graph is won by GNoF (1975 ms vs 2567 staged) but the 8.5 GB graph loses (11870 vs 9873) — a 6× size increase flipping the winner by 67% is attributed to a "965 MB/s fabric" making the bulk-load tax fall, but no breakdown separates the tax from on-demand read amplification, and the cache-size sweep (61.3 s → 9.65 s for 1 → 16 GiB) suggests the 16 GiB configuration is not what the 8.5 GB experiment used. (4) **The 46 GB VRAM budget is quietly doing work.** Peak VRAM for GNoF is 8702 MiB at C=1024 versus 552 MiB for both BaM variants (Table 3) — a 16× memory footprint for the registered pool — and the paper never discusses what happens when the page cache plus pool must fit alongside a real training or inference working set, which is the actual deployment question for a GPU-resident storage layer. (5) **Throughput parity is asserted, not stress-tested.** P1/P2/P3 all "reach 1.2–1.8 M IOPS," but P3 is capped at C=1024 by SNAP's MQES=64, so the three-way comparison at high concurrency is really a two-way comparison; and the 1.77 M figure is a per-client peak that says nothing about multi-client fairness, which §6.8 explicitly disclaims.

None of this is fatal — the paper does not overclaim, and its headline claim (low-SM GPU-native fabrics I/O with no target change) is supported by a direct measurement with a clean 0.37%-vs-40.3% contrast. But the contribution is a well-engineered client library with a good measurement discipline around SM occupancy, not a demonstrated end-to-end system win: the application section shows it beating bulk staging on one selective workload, losing on another, and roughly tying on writes.

## Strengths

- The monotonic per-slot completion counter is a genuinely elegant fix — no flag is ever cleared, so the lost-wakeup race cannot exist rather than being patched around, and the same poll routine doubles as a "helping" primitive for in-flight-full and page-cache waiters.
- Deployability is treated as a first-class result: byte-compatibility with the libmlx5 provider contract, an unmodified SPDK target, no SSD firmware change, and 64 RC QPs is a story a datacenter operator can actually adopt, in contrast to target-side firmware designs like GNStor.
- The non-coherence section is the kind of detail most GPU-I/O papers omit: `__ldcg` for NIC-written pages, `st.mmio.relaxed.sys` for doorbells, `__threadfence_system()` before publishing, and an explicit discussion of why GPU L1 caches cannot be invalidated from device code.
- Evaluation discipline is above average: schemes aligned by total in-flight requests rather than thread count, three repetitions, direct I/O, one scheme at a time, and a "limitations and honest scope" subsection that lists the missing BaM application comparison before a reviewer can.
- Reporting failures as failures — P3's `MQES=64` cap, BaM's Xid43 async race, and the 8.5 GB BFS loss are all presented as findings rather than smoothed over.

## Limitations

- Client-side only: no multi-client coordination, access control, or replication, so the "all-flash array" framing outruns what is implemented.
- Peak VRAM of 8702 MiB at C=1024 (vs 552 MiB for either BaM variant) is a 16× footprint increase that is never analyzed against a realistic application working set.
- No mechanism ablation: the doorbell mover, batched poller, and page cache are never individually disabled, and the claimed per-command doorbell serialization is never measured.
- Application-level comparison omits BaM and CoPilotIO entirely, so Table 4 supports "beats bulk staging on selective scans" but not "beats existing GPU-native storage on applications."
- Single testbed, single 200 Gb/s fabric, single SYS-topology host bridge; the authors note near-switch P2P may differ, and both the inter-SM collapse at 48 copy SMs and the 8.5 GB BFS loss are plausibly topology- and bandwidth-specific.
- The 10–100 µs RTT design point means the batching machinery may be pure overhead on local PCIe or on lower-latency fabrics (CXL, near-memory), a regime the paper never tests.
- No artifact: "a reference implementation and the per-point measurement dataset may be released by the authors separately."

## Relevance

直接命中了"GPU 直连远端闪存、把 CPU 移出 I/O 关键路径"这条系统栈主线：门铃合并、单调完成计数器、按需 GPU 页缓存这三个机制对任何做 GPU-initiated storage / NVMe-oF 发起端的人都可直接借用。对关心"GPU 存储栈到底该谁轮询"这一设计争论的读者，它的四方案对比和 ~1% vs ~100% SM 占用的硬数据是目前最清楚的证据之一。

## Questions for Further Exploration

- What is the SM-occupancy and IOPS contribution of each mechanism in isolation — GNoF with per-thread doorbells, and GNoF with flag-clearing completion instead of monotonic counters? The motivation's serialization claim needs a number.
- Why exactly does the 8.5 GB BFS lose while the 2.13 GB BFS wins by 23%? Is it read amplification, cache thrashing above some working-set threshold, or the fabric's 965 MB/s ceiling? A miss-rate trace would settle it.
- How does the 8702 MiB pool interact with a real co-running workload (e.g. an LLM inference batch) that already occupies 30+ GB of the 46 GB VRAM?
- Does the doorbell mover still help when the burst is sparse — e.g. 64 threads each issuing one request every few microseconds — where the contiguous-prefix scan may degenerate toward one MMIO per request?
- How does GNoF behave with multiple clients contending for the same SPDK target namespace, given that per-client SQ/CQ isolation is assumed but target-side queue arbitration is not modeled?
- Would the same monotonic-counter completion design transfer to CXL-attached memory or to a local PCIe SSD, where the 10–100 µs RTT justification for batching disappears?
