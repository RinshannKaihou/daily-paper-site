> **一句话总结：** 把 Qwen3-4B-Instruct 放在 vLLM 0.33.0 上、用 9 种单特性配置和 5 个参考副本跑 3,380 道五基准题，发现 vLLM 文档里标称"精确"的 7 个特性（prefix caching、chunked prefill、限制并发、关 CUDA graph、n-gram/EAGLE-3/draft-model 投机解码）在准确率始终落在 ±1 点等价区间内的同时，会翻转 1.47%–1.78% 的判分结果——但这一数量并不高于"同样请求换个到达顺序"的 1.72% 调度底噪；FP8 KV cache 翻转 3.36%（比调度底噪高 1.65 点，与 FP8 权重的 3.38% 相当）才是真正有损的改动；换成 batch-invariant kernel 后七个精确特性在全部 3,380 题上逐 token 复现参考文本（底噪归零），FP8 KV 仍翻转 3.91%。

> **TL;DR:** On 3,380 graded items (GSM8K 1319, MATH500 500, MMLU 1140, HumanEval 164, MBPP 257) served by Qwen3-4B-Instruct in vLLM 0.33.0 on one RTX 5070 Ti, every one of eleven single-feature serving configurations keeps accuracy inside a ±1-point margin of the 85.94% reference (largest change: EAGLE-3 at +0.42 pts), yet the seven features vLLM documents as exact flip 1.47% (max-16-sequences) to 1.78% (n-gram speculation) of graded outcomes — statistically indistinguishable from the 1.72% scheduling floor obtained by merely reordering the same requests (largest excess estimate +0.06 pts, upper bound +0.33). The FP8 KV cache is the exception: 3.36% flips (95% CI 2.80–3.96), +1.65 pts over that floor with a one-sided lower bound of +1.19, matching FP8 weights at 3.38% and flipping 54% of generated texts while accuracy moves +0.13 pts. With `VLLM_BATCH_INVARIANT=1` the floor becomes exactly 0.00% and all seven exact features reproduce the reference text token-for-token on all 3,380 items, while FP8 still flips 3.91% — evidence that the "exact" features flip answers only through batch-dependent floating-point arithmetic, the same channel request order uses. A practical corollary: a flip gate whose floor comes from a single replica pair returns FAIL on an unchanged configuration (holding out restart R2 gives +0.96 pts, upper bound +1.34).

## 核心贡献

- **重新定义了"验证一个 serving 特性"的判据。** 现行做法是重跑 benchmark 看准确率是否不变；作者指出准确率是聚合量，特性完全可以在准确率不动的情况下改变"哪些请求被答对"。于是把决策单元下沉到单题判分结果，并给出配对翻转率 + 聚类 bootstrap 区间的度量。
- **分离了两类底噪。** 把"新进程重启"（restart floor，1.38%）和"同样请求换顺序"（scheduling floor，1.72%）分开估计，证明前者会系统性低估：在生产里请求顺序本来就在变，因此只有高于调度底噪的翻转才算特性带来的。
- **实证结论：7 个"精确"特性确实会翻转答案，但不比换顺序更多。** 默认 kernel 下翻转率 1.47%–1.78%，没有任何一个特性相对调度底噪有正的置信下界；准确率全部等价。作者据此把这解读为"它们翻转答案，生产流量也在翻转答案"。
- **FP8 KV cache 不是"近似精确"，是与 FP8 权重同级的量化改动。** 翻转 3.36%，高出调度底噪 1.65 点，翻掉一半以上的生成文本，但准确率只动 +0.13 点——正是"准确率检查会放过它"的典型反例，且方向平衡（63 对 61，McNemar p = 0.93），说明准确率之所以稳定是正负抵消而非无效应。
- **batch-invariant kernel 控制臂给出机制归因。** 换成 `VLLM_BATCH_INVARIANT=1` 后底噪精确为 0，七个精确特性在 3,380 题上逐 token 复现参考文本，FP8 仍然翻转 3.91%——把"精确特性的翻转来自 batch 相关的浮点运算"这一因果链钉死，而不是停留在相关性。
- **交付了一个可执行的验收门（gate）并诚实地报告它在默认 kernel 下被证伪。** 预注册的 C3 要求门在所有零假设对比上都不给 FAIL；实际把 R2 留出当候选时，未改动的配置被判 FAIL（+0.96 点，上界 +1.34），原因是三个重启对之间本就相差 25–62 题。结论是可操作的建议：要么在 batch-invariant 模式下认证（底噪为 0），要么用至少三个副本、所有配对来估底噪。

## Key Contributions

- **Reframes serving-feature validation from aggregate accuracy to per-item graded outcome.** The paper's central measurement object is the *graded flip*: for a candidate run C and reference replicas R₁…R_k, the per-item flip probability is the share of pairs (C, R_j) whose graded outcome differs, and the flip rate is its mean over items. This makes a feature that preserves accuracy but changes who is right visible.
- **Two separate noise floors instead of one.** A restart floor (fresh process, same request order) and a scheduling floor (same requests, shuffled order) are estimated with the same paired machinery, so a feature's excess is measured against traffic-like variation rather than against the easiest possible control. Empirically the restart floor (1.38%) understates the scheduling floor (1.72%) by about 0.34 points.
- **A nine-configuration, five-benchmark audit in one engine.** Seven features vLLM documents as exact (prefix caching, chunked prefill at 512 tokens, max 16 concurrent sequences, CUDA graphs off, n-gram / EAGLE-3 / draft-model speculative decoding), plus an FP8 KV cache and dynamic FP8 weights as positive controls, all served from Qwen3-4B-Instruct with everything else held at the reference configuration.
- **A clean control arm that localizes the mechanism.** With batch-invariant kernels the restart and scheduling floors are both exactly 0.00%, all seven exact features reproduce the reference text on every item, and both FP8 configurations keep flipping at roughly the default-arm rate. The paper therefore attributes exact-feature flips to batch-dependent arithmetic rather than to the features' algorithmic content.
- **A decision procedure with a preregistered failure.** The shipped gate combines a paired accuracy equivalence test (margin 1 point) with a flip-rate test against the floor from all reference replica pairs (tolerance 0.5 points), and the preregistered claim C3 that it never FAILs a null comparison is refuted in the default arm and confirmed in the batch-invariant arm — reported as refuted, not massaged.
- **An exploratory but honest analysis of which requests flip.** Token-margin triage reaches ROC AUC 0.89, but output length alone reaches 0.88 and the two predictors correlate at −0.76, so the paper declines to claim margin as a useful screen and flags that 38% of items have a margin of exactly zero at bf16 logprob resolution.

## Methodology

**Setup.** Qwen3 4B Instruct 2507 in bf16, served by vLLM 0.33.0 through the offline `LLM.generate` interface in the official container, on a single RTX 5070 Ti (16 GB). Greedy decoding (temperature 0, seed 0). All requests of a task are submitted together so the engine forms batches by continuous batching as it would under load, and each configuration runs in a fresh process.

**Reference configuration (REF).** Prefix caching off, prefill budget 8192 tokens, at most 128 concurrent sequences, CUDA graphs on, bf16 KV cache, no speculation. Each candidate changes exactly one factor: prefix caching on (PC); prefill budget 512 so GSM8K prompts and most MMLU prompts are chunked (CP); ≤16 concurrent sequences (BS); CUDA graphs off (EAGER); speculative decoding with an n-gram proposer at 4 tokens (NGRAM), an EAGLE-3 head at 3 tokens (EAGLE3), or Qwen3 0.6B as draft model at 4 tokens (DRAFT); FP8 KV cache (FP8KV); dynamic FP8 weights (FP8W). The first seven are called *exact features* because under exact arithmetic none changes the greedy output. REF runs five times: R1, R2, R3 in fresh processes with canonical request order, and S1, S2 with order shuffled by seeds 1 and 2, which changes batch composition and nothing else. The batch-invariant arm repeats the whole fourteen-run design with `VLLM_BATCH_INVARIANT=1`.

**Items and grading.** 3,380 items: all 1,319 GSM8K test items (4-shot), all 500 MATH500 (boxed answer, `math-verify`), 1,140 MMLU test items (20 per subject, 5-shot, free-form answer with a final answer line), all 164 HumanEval and all 257 sanitized MBPP items, the last two graded by executing the official tests in a network-isolated container. Generation caps are 768 / 4096 / 1024 / 1024 / 1024 tokens and a truncated output is graded as produced.

**Statistics.** Flip probability is per item, so candidate and floor are paired on the same items; the excess flip rate is the per-item flip probability minus the per-item floor, averaged. Accuracy change is the paired difference against the mean reference accuracy. All intervals are cluster bootstrap intervals (2,000 resamples, seed 0), with the MMLU subject as the cluster where applicable and the item otherwise — 2,297 clusters. Secondary metrics are answer flip rate (extracted answer differs) and text flip rate (any generated token differs).

**Preregistration and kill checks.** Claims C1 (at least three of seven exact features have a positive one-sided lower bound on excess over the restart floor *and* are accuracy-equivalent within one point), C2 (under batch-invariant kernels PC/CP/BS/EAGER give zero text flips, speculative features zero correctness flips, both FP8 configurations some), and C3 (the gate gives no FAIL on any null comparison and FAIL on FP8W) were committed at hash `c00e671c…` before any main run, with one dated amendment that touches exploratory analyses only. Four kill checks gate interpretation: K1 grading determinism (rescoring 3 runs gives 0 differing rows out of 10,140; re-executing R1's 421 generated programs gives 0 differing pass flags), K2 batch-invariant restarts bitwise identical, K3 default-arm floor under the 2% instability line, and K4 every feature actually engaged, verified from engine counters (1,424,672 prefix-cache hit tokens for PC; 1,982 prompts above the 512-token prefill budget for CP; draft acceptance 13.7% / 50.8% / 65.6% for NGRAM / EAGLE3 / DRAFT).

**The gate.** Given reference replicas and candidate runs on a fixed request set, it reports the paired accuracy change with a 90% interval (PASS inside a 1-point margin) and the excess flip rate over the floor of all reference replica pairs (PASS when the one-sided 95% upper bound is at most 0.5 points, FAIL when the lower bound is above it, otherwise INCONCLUSIVE). Overall verdict is FAIL if either test fails.

## Results & Highlights

- **Accuracy equivalence holds for all eleven candidates, including the positive control.** Reference accuracy is 85.94% (95% CI 84.26–87.53) on the 3,380-item pool; every configuration's 90% accuracy interval lies inside the ±1-point margin. The largest movement is EAGLE-3 at +0.42 pts (90% CI +0.12 to +0.73), and FP8 weights — *known* to be lossy — sits at −0.29 pts (−0.76 to +0.19). An accuracy-only check therefore passes all eleven candidates, which is exactly the failure mode the paper targets.
- **Exact features flip graded outcomes at 1.47%–1.78% on the five-benchmark pool, versus a 1.72% scheduling floor and 1.38% restart floor.** Best case is max-16-sequences at 1.47% (95% CI 1.13–1.85) and worst is n-gram speculation at 1.78% (1.39–2.20); text flips run 28.47%–31.02%. Three features (EAGER +0.12, NGRAM +0.14, DRAFT +0.05 one-sided lower bounds over the restart floor) satisfy preregistered C1 — exactly the 3-of-7 threshold — but against the scheduling floor no exact feature has a positive lower bound, with the largest estimates +0.06 (NGRAM) and +0.05 (EAGER) and upper bounds +0.33 and +0.32.
- **FP8 KV cache doubles the flip rate: 3.36% (95% CI 2.80–3.96) versus 1.72% for a reordered rerun, i.e. +1.65 pts with a one-sided 95% lower bound of +1.19.** FP8 weights gives 3.38% (2.80–4.01), +1.67 pts (lower bound +1.22). Both flip more than half of all generated texts (54.2% and 55.4%) yet stay accuracy-equivalent (+0.13 pts, 90% CI −0.37 to +0.63; −0.29, −0.76 to +0.19). Direction is balanced — against R1, FP8KV makes 63 items right and 61 wrong, exact McNemar p = 0.93 — so the stable accuracy is cancellation, not absence of effect.
- **Batch-invariant kernels zero the floor and exonerate every exact feature.** With `VLLM_BATCH_INVARIANT=1` the three restart pairs differ on 0 generated texts, the restart and scheduling floors are both 0.00% (one-sided 95% upper bound 0.09% of items), and all seven exact features — speculative decoding included — reproduce the reference text token-for-token on all 3,380 items. FP8KV still flips 3.91% (3.28–4.53, 132 items) and FP8W 3.43% (2.83–4.06, 116 items), close to their default-arm 3.36% / 3.38%.
- **A single-replica-pair floor fails an unchanged configuration.** Holding out restart R2 against a floor built from R1 and R3 gives excess +0.96 pts with a one-sided 95% upper bound of +1.34 — a FAIL — while R1 (−0.28) and R3 (−0.68) pass, because the three restart pairs differ on 25 to 62 items (0.74%–1.83%) and holding out R2 leaves the quietest pair as the floor. In the batch-invariant arm all five null comparisons pass at exactly +0.00 and both FP8 configurations FAIL on the flip test, so preregistered C3 is refuted in the default arm and confirmed in the control arm.
- **Flips concentrate on long derivations and on short-answer tasks respectively.** MATH500 has the highest flip rate for every configuration, 4.53%–6.53% for the exact features (500 items with 4,096-token derivations), while MMLU stays at ≤0.41% for all exact features; the FP8 configurations raise MMLU to 2.63% / 2.57% and HumanEval to 4.88% (FP8KV) versus 0.41–1.02% for exact features, which is where KV-cache precision shows most clearly.
- **Token margin is predictive but redundant.** The 10th percentile of R1's top-1-minus-top-2 logprob predicts whether an exact feature flips an item at ROC AUC 0.89 (95% CI 0.85–0.92), and its lowest decile holds 70% (60–79) of exact-feature flips; but output length alone gets AUC 0.88 (0.84–0.91), the two correlate at −0.76, and the margin is exactly zero for 38% of items at bf16 logprob resolution, so margin-based triage adds little to "long outputs flip".
- **Speed sits beside the flips (exploratory, indicative).** On the shared GPU at 128 concurrent sequences, FP8W and FP8KV generate 1.77× and 1.66× as fast as REF, PC 1.18× and EAGLE3 1.16×, while NGRAM (0.97×), BS (0.84×), EAGER (0.77×) and DRAFT (0.50×) are not faster — i.e. the two configurations with the largest speedup are precisely the two that double the flip rate.

## Authors & Credibility

Single author, Sharven Rane, Independent Researcher, no institutional affiliation; this is a self-published preprint dated November 2026. That provenance normally predicts a thin, anecdotal systems note, and this paper is the opposite: the hypotheses, metrics, thresholds, kill checks and the exploratory list were preregistered at a named commit hash before any main run, one dated amendment is disclosed and explicitly confined to exploratory analyses, four kill checks verify that grading is deterministic and that each feature was actually engaged (with engine counters quoted, not asserted), and the confirmatory claim that failed (C3 in the default arm) is reported as refuted rather than reinterpreted. The measurement design — separate restart and scheduling floors, paired per-item statistics, cluster bootstrap with the MMLU subject as cluster, a batch-invariant control arm — is more careful than most industrial serving-evaluation write-ups.

Credibility caveats are structural rather than sloppy. The evidence is one 4B model, one engine version, one consumer GPU, and the code, per-item outputs and figure scripts are promised "with the public code release" and otherwise "available from the author on request" — so as of the PDF, none of the 3,380 per-item outcomes can be independently re-graded, which is a real limitation for a paper whose entire contribution is a measurement. The AI-disclosure statement is unusually good practice: every number enters the text as a macro generated by a script from result files, and every reference was checked against its arXiv or publisher record. The related-work section engages closely with the closest prior measurements (Blagojevich & Sunderland 2026 on quantization noise floors, Chodavarapu & Xu 2026 on FP16 KV-cache divergence, Patodiya 2026 on cache-induced divergence, Zhang et al. 2025 on batch speculative decoding corruption, DriftBench 2026 on infrastructure drift), and the differentiation is stated precisely: those vary the stack broadly or toggle one feature, this one holds engine/model/GPU fixed and toggles one documented feature at a time with two floors.

## Critical Assessment

**Novelty.** The individual observations are not new — that batching changes logits is documented by Thinking Machines Lab (2025), that speculative decoding implementations can corrupt output is shown by Zhang et al. (2025), that FP16 KV caching diverges from no-cache is shown by Chodavarapu & Xu (2026), and Blagojevich & Sunderland (2026) already frame quantization effects as excess over an engine/restart/batch/kernel drift floor. The genuinely new pieces are (i) routing the question through *graded correctness* rather than text equality, (ii) separating a restart floor from a *scheduling* floor and showing the former understates the latter by 0.34 points in this setup, and (iii) the batch-invariant control arm, which converts "these features flip answers" into "these features flip answers through batch-dependent arithmetic and nothing else". That is a methodological contribution rather than a discovery, and the paper is honest about it.

**Rigor.** The statistical hygiene is the strongest part: preregistration with a hash, paired per-item statistics, cluster bootstrap that clusters MMLU by subject rather than pretending 1,140 items are independent, kill checks for grading determinism (0/10,140 rescoring discrepancies, 0/421 differing program pass flags) and feature engagement, and a positive control (FP8W) that the gate must catch. The mechanism claim is properly ablated: the batch-invariant arm is the right experiment, and the prediction it tests — exact features go to zero, FP8 does not — is stated in advance as C2 and confirmed in all nine features.

**The main weakness is statistical power, and the paper's own headline is constrained by it.** The confirmatory test C1 requires three of seven features to clear the restart floor; exactly three do, with lower bounds of +0.12, +0.14 and +0.05 — the DRAFT result at +0.05 pts against a floor estimated from three pairs is not a robust finding, and one different run could turn C1 into a refutation. More importantly, the *negative* claim ("no exact feature exceeds the scheduling floor") is an equivalence claim supported only by non-significance: the upper bounds reach +0.33 pts on a 1.72% base, so a real excess of roughly +0.2 points — about 7 flipped items out of 3,380 — would be invisible at this sample size. The paper never computes the power or the item count needed to certify a 0.2-point excess, which is precisely what a practitioner would need before trusting the gate.

**The gate is validated only where teams cannot easily use it.** In the default arm, seven of nine exact features come out INCONCLUSIVE at 3,380 items, and one null comparison (held-out R2) comes out FAIL. So the operational recommendation collapses to "run in batch-invariant mode", and the paper gives that mode a ~4% throughput cost (REF mean of three restarts per arm) without measuring its memory overhead, its interaction with the FP8 speedups, or whether it is available for every kernel a production deployment would hit — the paper itself concedes the result is tied to vLLM 0.33.0's kernels and would not transfer to a version that falls back to a batch-dependent kernel. A team that cannot switch kernels is left with a method that mostly returns INCONCLUSIVE.

**Missing ablations and scope holes.** (1) Only one candidate run per feature, so candidate-side restart variability is never averaged — the paper argues this widens rather than biases the interval, which is plausible, but it means the reported candidate flip rates are themselves single-sample estimates and the INCONCLUSIVE verdicts are partly a variance artifact that more candidate replicas would fix cheaply. (2) Batch size is varied only as a binary feature (≤16 vs 128); there is no dose–response sweep over concurrency, which would be the natural test of the batch-dependence mechanism and would tell a practitioner how much concurrency heterogeneity is tolerable. (3) Greedy decoding only. Production traffic overwhelmingly samples with temperature > 0, where the relevant question shifts from "does this request flip" to "does the output distribution shift", and none of the metrics here answer it. (4) Five benchmarks with exact grading; judge-graded or preference-graded tasks are excluded by construction, which the paper acknowledges but which excludes most of the current evaluation surface. (5) The accuracy-equivalence margin of one point is asserted, not justified — 1 point on an 85.94% base is ~34 items, far larger than any of the flip effects being discussed, so "accuracy equivalent" is a weak certificate in this design.

**Framing overreach, mild.** The normative claim in the impact statement — that flipped answers mean "individual users get different answers from a model whose reported accuracy did not move, and nobody chose that change on purpose" — is fair as an auditability argument, but the paper's own McNemar result (63 right / 61 wrong for FP8KV) shows the flips are directionally symmetric. A team could reasonably read 1.5% symmetric churn under an exact feature as acceptable, and the paper's framing of "serving shortcuts" implies harm that its own data does not establish. To its credit, the conclusion explicitly disclaims accuracy loss and states the claim is about *which* requests are correct; the tension is in the title and framing, not in the results.

**Red flags.** Code and per-item outputs are not yet public for a paper whose entire value is a reproducible measurement, and the preregistration is identified only by a commit hash with no repository URL, so neither can currently be checked. The remaining risks are scope, not integrity: single model, single version, single consumer GPU, shared GPU during timing runs (correctly flagged as making speed numbers indicative only).

## Strengths

- Reframes serving-feature validation around the right object — per-item graded outcome rather than aggregate accuracy — and shows concretely why the conventional check fails (all eleven candidates, including the known-lossy FP8 weights at −0.29 pts, pass a ±1-point accuracy test).
- Introduces a two-floor design (restart 1.38% vs scheduling 1.72%) and demonstrates that the cheaper floor understates the noise a production service actually experiences, which changes the verdict on every exact feature.
- The batch-invariant control arm is a genuinely decisive ablation: zero floor, seven features bit-exact on 3,380 items, FP8 unaffected — clean mechanism attribution rather than correlation.
- Statistical machinery is appropriate and preregistered: paired per-item differences, cluster bootstrap over 2,297 clusters with MMLU clustered by subject, explicit one-sided bounds for the direction of the claim.
- Kill checks and an engagement audit (prefix-cache hit tokens, prompts over the prefill budget, draft acceptance rates) preempt the obvious objection that a feature was silently inactive.
- The failed confirmatory claim (C3 in the default arm) and the null exploratory result (margin predictor adds nothing over output length) are both reported plainly; the amendment is dated and scoped.
- The per-task breakdown is informative and internally consistent: MATH500 at 4.53%–6.53% for exact features versus MMLU ≤0.41% (long derivations amplify a single switched token), and FP8 specifically inflating MMLU to 2.6% and HumanEval to 4.9%.
- Actionable output: a command-line gate plus the recommendation to certify under batch-invariant kernels or against a ≥3-replica floor — advice a serving team can implement this quarter.

## Limitations

- One 4B instruction model, one engine version (vLLM 0.33.0), one consumer GPU (RTX 5070 Ti, 16 GB). Larger models have larger margins on easy items and longer outputs on hard ones, and the paper does not test which dominates.
- One candidate run per feature, so candidate-side restart variability is not averaged out; three restart replicas make the floor estimate itself noisy (demonstrated by the R2 hold-out FAIL), and no power analysis is given for the effect sizes the paper wants to certify.
- Request order is the only scheduling perturbation; real traffic also varies arrival times, preemption patterns and concurrent request lengths, which the paper expects to raise the scheduling floor further — i.e. the measured excesses are, if anything, upper bounds on the true excess.
- Greedy decoding with fixed seed only: nothing here speaks to temperature > 0 sampling, beam search, or any setting where the relevant quantity is a distribution shift rather than a token flip.
- The batch-invariant result is tied to the kernels shipped in vLLM 0.33.0 on this GPU; a version or device that falls back to a batch-dependent kernel would not be exact, so "certify under batch-invariant kernels" is not a portable guarantee.
- The GPU was shared with other jobs, so the speed numbers (FP8W 1.77×, FP8KV 1.66×, DRAFT 0.50×) are indicative only, and the ~4% cost of batch-invariant kernels is a single-arm mean of three restarts.
- Five benchmarks with exact grading; judge-graded, preference-graded and long-horizon agentic tasks are out of scope, and those are where current deployment interest concentrates.
- Code, per-item outputs and figure scripts are not released at publication time (available on request), and the preregistration is a bare commit hash, so independent verification of the 3,380 per-item grades is currently impossible.

## Relevance

正中「Operator Precision, Determinism & Error Propagation」核心：它把 batch 相关的浮点非结合性、kernel 选择与请求顺序如何改变逐题判分结果做了配对量化，并用 batch-invariant kernel 做零底噪对照，正是该方向关心的"执行非确定性如何传播到任务正确性"。同时对「Reliability under Extreme Performance Optimization」有直接价值——FP8 KV cache 被证明是与 FP8 权重同级的量化改动而非"近似精确"，给 KV 压缩/低精度推理的可靠性评估提供了一个可复用的验收协议。

## Questions for Further Exploration

1. How does the flip rate scale with concurrency heterogeneity? A sweep over max-num-seqs (16, 32, 64, 128, 256) and over deliberately mixed request lengths would test the batch-dependence mechanism directly and yield a practical tolerance, which the current binary ≤16 vs 128 contrast cannot.
2. What item count is needed for the gate to certify a 0.2-point excess over the scheduling floor with 80% power? Given upper bounds of +0.33 pts at 3,380 items, the required n is probably an order of magnitude larger than any routine benchmark — worth stating explicitly, since it determines whether the recommended protocol is affordable.
3. Does the effect survive sampling? With temperature 0.7 and top-p 0.95, per-request noise probably swamps a 1.5% flip rate, but the distributional question (do exact features shift the answer distribution?) is the one production teams actually face and is untouched here.
4. Are the 1.5% flips costless or harmful? Pairing each flipped item with a human or stronger-model judgement (is the new answer better, worse, or equally defensible?) would turn a symmetric churn statistic into a quality statistic — the McNemar balance (63 right / 61 wrong) suggests many flips are coin tosses on items the model barely knows.
5. Why does the restart floor (1.38%) sit below the scheduling floor (1.72%) rather than at it? Preemption counts are similar (~1,947 per REF replica, 34 for BS), so isolating whether arrival order changes kernel selection or batch composition would sharpen the claim that the two floors measure different channels.
6. Would the same audit on a larger model (e.g. 30B+) show smaller flip rates because margins grow on easy items, or larger ones because derivations get longer? This is the single most important generalization the paper leaves open, and it is cheap to test with the same harness.
