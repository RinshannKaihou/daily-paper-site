Methodology

Split the stack by critical-path relevance, not by the CPU/GPU boundary.

  1. 01Host sets up, then blocks. RDMA-CM connect, fabrics CONNECT / Identify / Set-Features, one RC QP per I/O channel, one GPU pool registered via nvidia-peermem, and cudaHostRegister over SQ/CQ/DBrec plus the BlueFlame UAR page so the GPU may MMIO them.
  2. 02GPU submits. 64 channels × 256 SQ slots. A CAS on sq_head claims a slot, the thread writes a 64 B capsule with a keyed SGL into VRAM, then posts a 32 B SEND WQE at the true HCA ring position.
  3. 03Doorbells are batched. A mover scans the contiguous prefix of set wrote[] flags under one lock and rings BlueFlame once per burst, preserving WQE order. It is the answer to “thousands of doorbells serialize on the NIC”.
  4. 04Completions drain in bulk. A lock-free peek on the head CQE’s owner bit, one poll lock draining the ready batch, then atomicAdd(comp[slot]). Counters are monotonic, so the lost-wakeup race is gone by construction.
  5. 05Waiters help instead of hanging. Spins on comp[slot] > target with a ~10 s budget returning 0xffffffff; the same poll routine is called by in-flight-full and page-cache waiters, so a blocked thread still moves the queue.
  6. 06Remote pages on demand. 4 KB slots, 8-way set-associative with Fibonacci hashing, reference pins, EMPTY/FILLING/VALID states, fetch split from wait, and orphan-fill takeover after ~100 ms.
Two invariants do the quiet work: the SQ slot number is the NVMe CID (encoded (target+1)<<32 | slot), and a slot is claimable only while head − resp_done < sq_slots — which removes the send-CQE-lag reuse race at the root. Non-coherence is handled explicitly: __ldcg for NIC-written pages, st.mmio.relaxed.sys for doorbells, __threadfence_system() before publishing.

Three mechanisms

The bundle that replaces BaM-style lock-step polling.

Doorbell mover MMIO

Collapses a burst’s per-thread rings into one BlueFlame doorbell by scanning the contiguous set prefix — one MMIO per batch, WQE order intact.

Batched CQ poller CQ

Owner-bit fast peek touches no lock word; one lock drains the whole ready batch. Per-slot counters only ever increase, so no wakeup can be lost.

GPU page cache VRAM

8-way set-associative 4 KB slots, pinned against eviction, misses pipelined via fetch/wait split, and wedged owners reaped after a grace period.

Reading the table: P3’s queue depth is hardware-capped, so the three-way high-concurrency comparison is really a two-way one plus a ceiling. P4’s read gap is the sharpest number in the paper and the least clean: its writes scale normally on the same SSD.

Honest losses, stated by the authors: BFS on the 8.5 GB R-MAT graph is slower with GNoF (11 870 ms) than bulk staging (9 873 ms), though the 2.13 GB graph wins 1 975 vs 2 567 ms. Vector-add reaches 863 MiB/s / 3.56 s at T = 512 versus 1.56 s for the best staged pipeline. Inter-SM contention costs 5–8% through 32 copy SMs, then collapses to 0.227 retention at 48 as DRAM saturates and CQ polling starves.

Strengths

  • The counter is the idea. Because comp[] never clears, the lost-wakeup race cannot exist rather than being patched; the same poll routine doubles as a helping primitive.
  • Deployable by default. Byte-compatible with the libmlx5 provider contract, an unmodified SPDK target, no firmware change, 64 RC QPs — an operator could actually adopt this.
  • Non-coherence taken seriously. __ldcg, st.mmio.relaxed.sys, system fences, and an explanation of why GPU L1 cannot be invalidated from device code.
  • Measurement discipline. Schemes aligned by in-flight C, three repetitions, direct I/O, one at a time — and failures reported as failures: P3’s MQES cap, BaM’s Xid43 race, the BFS loss.

Limitations

  • Client-side only. No multi-client coordination, access control, or replication, so the “all-flash array” framing outruns the implementation.
  • A 16× VRAM footprint. 8 702 MiB peak at C = 1024 versus 552 MiB for either BaM variant, never analyzed against a real 30+ GB working set.
  • No mechanism ablation. Doorbell mover, batched poller, and page cache are never individually disabled; the serialization motivation is never quantified.
  • Application comparison is incomplete. Table 4 has no BaM or CoPilotIO column, so it supports “beats bulk staging on selective scans”, not “beats existing GPU-native storage”.
  • One testbed, one topology. A single SYS-class NUMA-crossing bridge and a 200 Gb/s fabric; the 48-SM collapse and the large-graph BFS loss are plausibly topology artifacts.
  • No artifact yet. A reference implementation “may be released separately”.

Questions for further exploration

  1. What is each mechanism’s isolated contribution — GNoF with per-thread doorbells, or with flag-clearing completions? The serialization claim needs a number.
  2. Why does 2.13 GB BFS win by 23% while 8.5 GB BFS loses? Read amplification, cache thrashing above a threshold, or the fabric’s 965 MB/s ceiling? A miss-rate trace would settle it.
  3. How does an 8.7 GB pool coexist with an LLM batch already holding 30+ GB of the 46 GB card?
  4. Does the mover still help on sparse bursts, where the contiguous-prefix scan degenerates toward one MMIO per request?
  5. What happens with multiple clients on one target namespace, given per-client SQ/CQ isolation but unmodeled target arbitration?
  6. Does the monotonic-counter design transfer to CXL memory or local PCIe, where the 10–100 µs RTT that justifies batching disappears?
