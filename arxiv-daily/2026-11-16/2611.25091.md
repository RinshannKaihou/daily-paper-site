> **一句话总结：** Berth 不去改内核、驱动或框架，而是用一个 LD_PRELOAD 的 shim 在驱动 launch 路径上拦住 best-effort（训练）进程的 kernel 提交，只在没有延迟敏感请求时"喂"给它 GPU，并把 best-effort context 的 time-slice 用无特权的 RM ioctl 改成 500 µs——在 31 个场景点上做到平均 95.8% SLO 达成（单独跑为 97.9%），best-effort 吞吐仍有 48%，是四个最强 baseline 的 2.7–3.5 倍。

> **TL;DR:** On a single A100, Berth exploits two facts about stock NVIDIA time-slicing — it already preempts a running kernel in ~0.2 ms, but it is fair and therefore hands every other slice to whatever best-effort work is queued — and manufactures priority from user space by (i) blocking best-effort launches while a latency-critical request is in flight or when more than 1 ms of best-effort work is queued, and (ii) rewriting the driver's own unprivileged time-slice ioctl to 500 µs for the best-effort context only. Across 31 MLPerf-SLO scenario points against 13 baselines (including released XSched, TGS, Orion, Tally, MIG, MPS variants and a LithOS-like TPC-quota reimplementation) it averages 95.8% SLO attainment vs 97.9% alone and 88.4% for the best baseline (MIG), while keeping 48% of best-effort throughput vs 9–18% for the four closest baselines (+2.7–3.5×); on 7 vLLM points it holds a 25-ms TPOT target at p99 15–22 ms while training keeps 17–38%.

## 核心贡献

- **一个反直觉的观察**：商用 GPU 自带的 time-slicer 本身就是一个抢占式调度器——约 0.2 ms 内可以抢占正在运行的 kernel，并且在 context 没活干时立刻切换；它缺的不是抢占能力，而是"优先级"。因此优先级可以在**系统外部**造出来（让 best-effort 进程在请求到达时"无活可跑"）。
- **Feed control（喂入控制）**：每个租户预加载一个 shim，通过 libsmctrl 在驱动的 launch 路径上看到每一次 kernel 提交（包括 cuBLAS/cuDNN 这类闭源库的私有路径），依据两个条件挂起 best-effort 的 launch：(a) 请求门——有延迟敏感请求在飞（含 0.5 ms 宽限期）；(b) 队列门——已排队的 best-effort 工作量（按 profile 预测的 GPU 时间）超过每 GPU 共享预算 f = 1 ms。
- **Deadline reference（截止期参照）**：把上述规则从"请求级"扩展到连续 batching 的 LLM 引擎——引擎声明按 step 计的截止期，shim 用观测到的 step 时间与 profile 剩余比例算出 `need_by = b + D − r − g`，只要 `t + f + c < need_by` 就继续喂，于是训练能在 step 的松弛里跑，而不是被整段饿死（对比：把引擎当请求级处理，训练只剩 0–5% 吞吐）。
- **无特权的短 time-slice**：只在 best-effort 进程里拦截驱动自己的 `NVA06C_CTRL_CMD_SET_TIMESLICE` 调用，把 slice 从默认 2048 µs 改成 500 µs，从而给"已在运行的 62.8 ms 大 kernel"的代价封顶（tiny kernel 的 p99 从 2.25 ms 降到 0.55 ms）。
- **分层喂入（tiered feed）**：延迟敏感租户之间也按 SLO 松紧排队（`e + t_solo + g_t < D`），避免 130-ms 的 BERT-large 请求拖慢 15-ms 的 ResNet-50 请求。
- **一个诚实的评估**：13 个 baseline、31 个场景点 + 7 个 LLM 点，含 XSched/TGS/Orion/Tally 的官方 release，并明确把"策略跑不起来的租户记 0%"。

## Key Contributions

- **Reframing, not a new mechanism**: shows the commodity time-slicer is already preemptive (0.2 ms switch cost, up to 2.26 ms worst case = one slice + switch) and that what it withholds is priority, which can be synthesized outside the stack by controlling what the best-effort context has to run.
- **Feed control** implemented as a preloaded shim that intercepts every kernel launch (via a libsmctrl hook the driver calls synchronously, so closed-library launches are visible) plus `berthd`, a daemon holding a 16-slot shared-memory table per GPU: a request gate, a per-GPU queue bound `f = 1 ms`, per-thread FIFO tracking with predicted durations, and a shared budget so p processes cannot each queue f ahead of a request.
- **Deadline references**: arrival deadlines (request servers, held for the whole request + 0.5 ms grace) vs per-step deadlines (LLM engines, slack rule with a 20%-of-D guard), which is what makes co-serving a decode loop possible at all.
- **A 500 µs best-effort-only slice** set through the driver's own unprivileged RM control, plus a *slice rule* that restores the default while an iteration-deadline engine is registered (a 500 µs slice there splits admitted work into more, costlier turns; 100 µs is worse still).
- **A user-space-only implementation** (1,355 lines of C++ shim, 571-line daemon, a patch to libsmctrl) that changes no application, framework, kernel, driver or privilege setting.
- **A 13-baseline, 38-point evaluation** including the released artifacts of XSched, TGS, Orion and Tally, an MPS-limits/static-partition/MIG sweep, a LithOS-like TPC-quota reimplementation, and a GH200 portability study.

## Methodology

**Setting.** One operator starts every tenant; tenants are unmodified processes. Latency-critical tenants serve open-loop, first-come-first-served requests whose latency runs from arrival; best-effort tenants (training, GEMM jobs) run closed loop. Goal: every request/step completes about as fast as alone while best-effort uses the rest.

**Mechanism stack (in the order a launch meets it).** ❶ in-flight flag + 0.5 ms grace (set at the first kernel after a device sync, cleared at the next device sync); ❷ `need_by` from the declared step deadline and observed step time; ❸ feed gate `q ≤ t + f`; ❹ one shared queue budget per GPU; ❺ 500 µs best-effort slice through the driver's control; ❻ the GPU's own time-slicer does all preemption. Launch hooking is done by extending libsmctrl's driver callback, so cuBLAS/cuDNN/PTX-private launches are all seen; graph launches (`cudaGraphLaunch`) are gated as one launch of their profiled duration.

**Calibration.** A new best-effort job is profiled once for ~12 s with CUPTI, recording the median duration of each kernel *position* in the iteration (counted per launching thread from the last device synchronization); a position missing from the profile predicts zero. Engines run without a profile. f = 1 ms trades throughput against backpressure and is flat from 0.3 to 1 ms.

**Delay bound (§3.6).** With W ≤ f + k_max on the GPU at request arrival and n turns of at most one slice s, a request finishes at most `min(f + k_max, n·s) + n·c_s` later than alone (c_s ≈ 0.2 ms), so beyond n·s the delay stops growing with kernel length — the formal reason the slice caps the 62.8 ms GEMM's cost.

**Testbed.** One A100 PCIe 40 GB (Chameleon Cloud, 2× EPYC 7763, driver 580.178.04, CUDA 12.8, PyTorch 2.8.0) plus a GH200 (H100, 132 SMs) for portability. Latency-critical tenants: ResNet-50 batch 8 (5.3 ms alone, 15-ms MLPerf SLO), RetinaNet (10.5 ms, 100 ms), BERT-large (20.9 ms, 130 ms), a 4-frame perception loop (11.8 ms, 33.3 ms at 30 fps). Best-effort: BERT-large training (1.62 steps/s alone), ResNet-50 training (13.29 steps/s), and back-to-back 8192² fp32 GEMMs (15.81/s, one 62.8-ms kernel each).

**Protocol.** 31 scenario points varying load (30–80%), tenant mix, SLO tightness (0.5–3×), best-effort job, rate steps, Azure Functions 2021 trace bursts, churn, 5/10 tenants and two best-effort jobs; plus 7 vLLM 0.11.0 points (Qwen2.5-1.5B/0.5B, Azure LLM trace 2023) with 250-ms TTFT and 25-ms TPOT targets. Metrics: per-tenant SLO attainment, worst tenant, and best-effort throughput relative to alone; each cell is the mean of three runs (two for MPS static partitions on driver 595.91.07, two for one MIG cell).

## Results & Highlights

- **Mean SLO attainment over the 31 scenario points: Berth 95.8% vs 97.9% alone, above all 13 baselines** — the closest are MIG 88.4%, MPS static partitions 87.1%, MPS limits 86.9% and TPC quotas (LithOS-like) 85.5%, while plain time-slicing collapses to 48.9%, MPS to 3.8% and MPS priority to 24.3% (Table 3). Berth also keeps 24 of 31 points within 5 percentage points of every tenant's attainment alone, against at most 18 for any baseline.
- **Best-effort throughput is the decisive gap: Berth 48% of alone vs 18% (TPC quotas), 17% (MPS static partitions), 16% (MPS limits) and 14% (MIG)** — i.e. 2.7–3.5× the throughput of the four baselines whose SLO attainment comes close, and essentially the same 51% that plain time-slicing keeps while missing more than half its requests (worst-tenant mean 38.4%).
- **The long-kernel ablation isolates why the slice matters.** Next to the GEMM job, feed control alone serves ResNet-50 at 66.4% — no better than time-slicing (67.0%) or TGS (66.9%), with p99 2.3× alone's as §3.6 predicts for k_max = 62.8 ms; adding the 500-µs slice lifts it to 95.1% with p99 1.1× alone's, 99.6% for BERT-large and 96.4% for the mix, while the GEMM job still keeps 71%/63%/55% of its throughput.
- **Mechanism ablation (cumulative, mean over 31 points):** Feed only (grouped) leaves the worst tenant at 82.9% with 52% best-effort; adding the tiered feed and the slice reaches 91.9%; adding the grace period reaches 94.2% at 49%; full Berth is 94.1% at 48%. Without the grace period at high load, BERT-large at 70% load falls from 94.9% to 67.8%.
- **LLM co-serving works where stock mechanisms fail.** On 7 vLLM points with a 25-ms per-token target, the worst service attains 99.8–100.0% of requests on every point without a request server (TPOT p99 15–22 ms, TTFT p99 ≤ 126 ms) while training keeps 17–38% and the GEMM job 46%; under time-slicing, MPS and MPS priority the worst service's TPOT p99 reaches 35–431 ms and at most 3.1% of requests meet the target.
- **Overhead is small but real:** the launch hook lengthens a ResNet-50 request by 5.9% (222 launches/request) and a ResNet-50 training step by 6.4%, under 1% for RetinaNet, BERT-large, the perception loop, BERT-large training and the GEMM job; CPU use is 57% of one core on the ResNet-50 pair versus 135% under plain time-slicing, with berthd at 0.9% and the slice watcher at 0.3%.
- **Portability and sensitivity:** on a GH200, Berth reaches 94.2% worst-tenant / 95.5% mean at 51% best-effort (A100 on the same 30 points: 94.6%/96.1%/49%) and still leads time-slicing, MPS limits and MIG by 3–16 points; f is flat from 0.3 to 1 ms, but f = 3 ms costs 10.1 points with halved SLOs and buys no throughput; at 0.5× SLOs Berth holds 77.5% against TGS's 65.9%.

## Authors & Credibility

Five authors from USC (Ming Hsieh ECE / Viterbi): Mohammadali Khodabandehlou, Mahdi Alizadeh, Lei Gao, Murali Annavaram (well-known computer-architecture/systems researcher, M-CASH lab) and Bhaskar Krishnamachari (networking/ML-systems). The work reads like a mature systems paper: a real implementation (shim + daemon + driver-control interception), 13 baselines including four released systems, three runs per cell with error bars, a second GPU, and an explicit delay bound with stated assumptions. Baseline honesty is above average — the paper reports where it *loses* (two best-effort jobs, bursts near saturation, MPS limits and TPC quotas beating it on attainment on the mixed LLM point at ~4× the best-effort cost) and explains why. The AI-use disclosure is unusually explicit: Claude, via Claude Code, "wrote much of the shim, daemon and evaluation-suite code, the scripts that run the experiments and generate the figures, and drafts of the text", with the authors claiming verification of every number. There is no artifact-availability statement or anonymized repo link in the text, which is the main reproducibility gap alongside the hardware's single-GPU scope.

## Critical Assessment

**Novelty.** The intellectual core is a genuine reframing rather than a new primitive: "the time-slicer already preempts, it just lacks priority, and priority can be built outside." That is a clean, useful, and testable claim, and the paper supports it with a mechanism-level probe table (Table 1: 61-ms hog → tiny kernel at 0.27 ms median, 2.26 ms worst case = one slice plus a 0.2-ms switch). But every individual component has a close ancestor: Orion already launches a best-effort kernel "only when the high-priority client is idle, bounding outstanding work by predicted duration" — which is precisely feed control plus the queue bound; Valve disables an offline job's channels while an online request is active; XSched's Level 3 zeroes a context's slice through *the same* `NVA06C_CTRL_CMD_SET_TIMESLICE` control Berth rewrites. What is new is (a) doing it as a preloaded shim that sees closed-library launches without framework instrumentation, (b) composing the gate with a *fixed, once-set* short slice, and (c) the arrival-vs-per-step deadline reference distinction that makes vLLM co-serving actually work. The paper is fair about this in §7, but a reviewer should press on how much of the 95.8% comes from the composition versus from careful tuning.

**Rigor.** The evaluation is broad (31 + 7 points, 13 baselines, 3 runs, error bars, a second GPU, ablation in a cumulative chain) and the bound in §3.6 is the right kind of theory: it predicts the 2.3× p99 penalty for k_max = 62.8 ms *before* the measurement, and it correctly predicts that a 100-µs slice is worse than the default under feed control alone. Two accounting choices deserve scrutiny. First, "a tenant that a policy cannot run counts as 0%", which is defensible but materially inflates Berth's average lead: XSched fails on 4 points (its Level-1 queue breaks on ResNet-50 training's launches) and still reaches 81.9% at 48% throughput on the 27 points it can run, versus Berth's 95.5% at 48% — a 13.6-point gap, not the 24-point gap the headline table implies. Second, Tally's baseline is partly a port artifact: its own PyTorch build lacks cuDNN, so "most tenants are overloaded even alone", which makes its 24.5% mean nearly uninformative about the idea. Similarly, GPreempt and MorphX are listed in Table 2 but only GPreempt is built, and it cannot serve open-loop arrivals because its release needs a 100-µs-ahead early-execution hint — a real limitation of that artifact, but it means the "no new preemption needed" claim is never tested against a *working* kernel-level preemptor on these workloads.

**Baseline tuning.** MPS limits, MPS static partitions, TPC quotas and MIG are not run at defaults: they are sized by an M/D/1 model so each latency-critical tenant's p99 stays "within 60% of its SLO", leaving the best-effort job the remainder (and at least four SMs for the partition cases). That is a reasonable and disclosed methodology, and the paper shows the resulting baselines reach 85–88% attainment, so they are not straw men. Still, the 60%-of-SLO and 95%-attainment sizing targets are knobs chosen by the authors, and they also happen to be the knobs that decide how much capacity is left for best-effort — the exact axis on which Berth wins by 2.7–3.5×. A sensitivity sweep on those sizing targets (does MIG/TPC do better at 50% or 70% of SLO?) is the missing control.

**Data quirks worth naming.** (i) The MPS static-partition cells were run on a *different driver* (595.91.07, which they require) and with only two runs, and that baseline could not run the BERT-large + GEMM point at all, so its mean covers 30 points. (ii) "Alone" is measured as the only client of an MPS server, which is not the same as a bare GPU — clock and context-mode differences could account for part of the 2.1-point gap to Alone (95.8% vs 97.9%), and the paper does not decompose that residual. (iii) The suite's tenants mostly declare arrival deadlines, so the slack rule — the mechanism that carries the entire LLM result — "changes nothing on the suite"; only §5.8 exercises it, on 7 points with two model sizes from one family. (iv) The 40%-load LLM result is at 38% of DRAM read bandwidth (47% at 7B), close enough to the memory ceiling that the conclusion may not survive a bandwidth-heavier mix, which the paper itself flags as ungoverned.

**Overclaiming check.** "Without new preemption" is accurate for the mechanism but conditional on an undocumented-stability assumption: the RM control is unprivileged on the three drivers probed (550 patched, 560 proprietary, 580 open) on Ampere and Hopper, and Tegra is unchecked; a future driver that privileges it costs Berth the slice and all the long-kernel results (§5.6), i.e. its advantage next to the GEMM job. The paper says this plainly, which is to its credit, but the abstract's framing does not carry the caveat. Likewise "meets SLOs within a few percentage points of running alone" holds on average and on 24 of 31 points, not on all: at 0.5× SLOs it is 77.5%, and under bursts and near saturation the authors concede Berth is weakest because its shim cannot see request queues.

**Deployment friction not priced in.** Every best-effort job must be profiled for ~12 s before it can run with a useful queue bound, and a new model/batch size/GPU needs a new profile; graphs launched from device code are invisible, and BERT-large training with per-step random sequence lengths runs up to 2.9× longer than profiled (the slice saves the SLO, but the queue bound degrades). Berth also does not govern memory capacity, copy-engine/PCIe traffic, or L2/DRAM bandwidth — for a 2026 GPU-sharing paper that omits the LLM KV-cache dimension entirely, a notable scope limit. Finally, the trust model is explicit and narrow: the slice control is unprivileged, so a tenant running its own code could raise its own slice; Berth isolates tenants from interference, not from a hostile tenant.

## Strengths

- A crisp, falsifiable thesis backed by a mechanism-level probe: it *measures* the stock time-slicer's 0.2-ms preemption and the 0.5-ms grace-period need rather than assuming them, and the delay bound in §3.6 predicts the ablations it later confirms.
- Genuinely user-space: no kernel module, no driver patch, no framework hooks, works with closed cuBLAS/cuDNN and with unmodified PyTorch and vLLM — this is the property an operator of a closed GPU stack actually needs.
- The best-effort/serving trade-off is measured on the axis that matters: near-Alone SLO attainment *at* 48% best-effort throughput, versus 14–18% for the baselines that match its attainment.
- Unusually honest baseline handling: four released systems run as shipped, unrunnable points reported as such, GPreempt's release limits stated, per-cell run counts disclosed, and a section (§5.6, §5.9) that shows where Berth loses.
- Two concrete, reusable mechanisms that others can lift: the arrival-vs-per-step deadline reference with a slack rule, and the rule that the short slice must be *disabled* beside an iteration-deadline engine.
- Full ablation chain, three runs per cell with error bars, a second GPU, and a portability result (GH200: 94.2% / 51%) that keeps the same settings.

## Limitations

- Single-GPU, single-node only; no multi-GPU, no NVLink/PCIe copy-engine contention, no memory-capacity or KV-cache governance, and no L2/DRAM-bandwidth control even though the LLM points already sit at 38–47% of read bandwidth.
- The queue bound is per launching thread within a process and shared across best-effort processes at f; under bursts and near saturation the shim's blindness to request queues leaves Berth weakest (its own §6), and a held tenant's requests back up.
- Requires a 12-s per-job profile plus a declared SLO/solo-time/deadline reference for every tenant; new shapes, device-side graph launches, or per-step variable sequence lengths degrade the bound (up to 2.9× mispredictions observed).
- The 500-µs slice depends on `NVA06C_CTRL_CMD_SET_TIMESLICE` staying unprivileged — verified on Ampere/Hopper with three drivers, unchecked on Tegra; a driver change removes the long-kernel advantage entirely.
- Grouped layout places all latency-critical tenants in one MPS fault domain (a crash takes them together), ordered by a tiered-feed guard that the authors call "a heuristic without a bound"; the separate layout avoids the fault domain but slices among the critical tenants themselves.
- No hostile-tenant isolation: a tenant can raise its own slice; containment is future work.
- The LLM evaluation covers only Qwen2.5-0.5B/1.5B (and 7B on GH200) on one trace; no tensor-parallel, no prefill/decode disaggregation, no prefix caching, and improvements that a modern engine's own chunked-prefill scheduling would give are not compared against.
- No artifact link or reproducibility package in the paper; the shim, daemon and most evaluation code were LLM-written, so independent re-implementation risk is higher than usual for a systems paper.

## Relevance

与"LLM 推理服务系统 / GPU 多租户与 SLO 保障"这条线高度相关：它给出了一个不改驱动、不要特权就能在闭源 GPU 栈上做延迟隔离的可行路径，对推理服务与训练混部（机会式训练、离线 batch）的调度设计有直接参考价值。方法层面（用 profile 预测 kernel 时长 + 外部制造的优先级 + 无特权 slice 改写）也可以迁移到国产/闭源加速卡上的 SLO 调度研究。

## Questions for Further Exploration

1. How much of the 95.8% survives if the MPS-limits / TPC-quota / MIG sizing targets are swept (50%, 70%, 90% of SLO) rather than fixed at "p99 within 60% of SLO" and "95% attainment"? Is 2.7–3.5× robust to that knob?
2. What decomposes the 2.1-point gap to "Alone" (95.8% vs 97.9%) — MPS server overhead, the 500-µs slice's cache-refill cost, the 5.9% launch-hook tax on ResNet-50, or the grace period's residual queue?
3. Can the shim see request-queue state (e.g., the server's accept backlog or a socket-level hint) to fix the burst/near-saturation weakness without touching the framework?
4. What happens with a genuinely preemptive kernel-level baseline (GPreempt or Hummingbird) given a workload with the early-execution hint it needs — does the 500-µs slice still earn its keep, or is hardware/software preemption strictly better once available?
5. Does the per-step deadline reference survive tensor-parallel serving, prefill/decode disaggregation, or a chunked-prefill engine where step time varies by an order of magnitude within a request?
6. How does Berth interact with KV-cache paging and memory-capacity limits it explicitly does not govern — is the 1-ms queue bound still safe when the best-effort job's footprint forces eviction?
