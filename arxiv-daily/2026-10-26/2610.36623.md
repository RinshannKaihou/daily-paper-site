> **一句话总结：** 发现已发布的 LLM 生成 GPU kernel 中 22.9%（83 个可批处理 artifact 中的 19 个）违反批不变性（batch invariance, BI）——同一请求的输出随 batch 大小/组合逐位变化；提出的 BIEvolve 以"DSL 合约静态依赖分析 + 跨 batch 上下文逐位动态校验"双闸门插件形式嵌入现有 kernel 优化 agent 循环，在 K-Search / Iterative / Evolve 三个 agent 上将 BI 通过率从 67.6% 提升到 91.9%，同时保留 91.8% 的基线几何平均加速比（28.91×→26.54×）。

> **TL;DR:** LLM kernel-generation agents optimize for correctness and speed but ignore batch invariance (BI): in dynamic-batching serving, an unchanged request gets bitwise-different outputs depending on its batch context. Auditing released artifacts, the authors confirm 19 BI violations among 83 batch-applicable kernels from KernelBench.com/FlashInfer-Bench (77.1% BI pass). BIEvolve is a plug-in that inserts two acceptance gates — a DSL-guided static dependency analysis (batch symbols must not flow into protected parameters like `NUM_SPLITS`/`RNG_SEED`) and a dynamic bitwise-consistency validator across batch contexts — ahead of benchmarking, feeding failures back to the agent. On a 39-task, 1,180-workload suite (KernelBench.com + FlashInfer) with three agents (K-Search, Iterative, Evolve; Gemini 3.7 Flash on an H100 NVL), overall BI pass rate rises from 67.6% to 91.9% (+24.3 pts) while retaining 91.8% of baseline geometric-mean speedup; the ablation on a 200-candidate independently-labeled pool shows the combined gates detect 92% of confirmed violations (vs 83% static-only, 55% dynamic-only) at 2% false rejection and 10.21 ms/candidate. A solid, well-executed reliability paper; the residual 8.1% violations, the hand-curated contract DSL, and the compact attention-heavy task suite are the main caveats.

## 核心贡献

- **提出并实证了一个被忽视的可靠性问题**：LLM 生成的 GPU kernel 普遍违反批不变性（BI）——由于浮点加法不满足结合律，batch 上下文变化会改变 kernel 的 tiling、并行划分和归约顺序，从而使同一输入的输出逐位漂移。对 131 个已发布 artifact 的审计发现 83 个有语义 batch 维度，其中 19 个（22.9%）存在已确认的 BI 违规（attention 家族违规率最高，达 "High" ≥50%）。
- **BIEvolve 插件：BI 合约 DSL 静态分析 + 动态逐位校验**。静态模块用可执行合约（如 `batch_identity.bid`）声明 batch 符号（`batch_size`, `num_seqs`, …）和受保护参数（`NUM_SPLITS` 及其 20+ 别名、`RNG_SEED`），做污点式依赖分析并输出可修复诊断；动态模块按 kernel 家族选择 batch 测试策略，把同一目标样本嵌入不同 batch 上下文做逐位比较。二者互补：静态覆盖已建模模式，动态暴露运行时行为。
- **即插即用接入现有 agent**：不改 agent 的提示、搜索策略和候选选择，仅在候选评估流水线中按"静态 BI → 参考正确性 → 动态 BI → 性能基准"的顺序插入验收闸门，失败诊断经框架原有反馈通道回传。据作者所知这是首个在 LLM kernel 优化过程中把 BI 作为验收标准的工作。
- **跨三个异构 agent 框架的受控评估**：K-Search（世界模型协同进化搜索）、Iterative Agent（单轨迹精修）、Evolve Agent（多实现进化池），统一使用 Gemini 3.7 Flash 与相同 turn 预算，证明结论不依赖特定搜索范式。

## Key Contributions

- **Identifies and evidences an overlooked reliability failure mode.** LLM-generated kernels can pass tolerance-based correctness tests yet still be batch-dependent: changing batch size/composition selects different kernel variants, tile shapes, or split-reduction schedules, and FP non-associativity makes outputs differ bitwise. A concrete code pattern is shown where `batch_size` propagates into `num_splits`, which changes the page ranges each split reduces.
- **Field evidence from released artifacts.** Of 131 released kernels, 83 are batch-applicable and 19 (22.9%) contain confirmed BI violations (KernelBench.com: 18/79; K-Search/FlashInfer-Bench: 1/4); attention is the highest-risk family (≥50% confirmed-violation rate among batch-applicable artifacts).
- **BIEvolve: a two-module plug-in.** (1) A BI-contract DSL (BNF-specified, executable) declares `invariant_axis batch symbols` and protected parameters with semantics (`split_structure`, `recurrence_structure`, `rng_stream`) and policies (`fixed_across_batch`, `may_depend_on_batch`, `free`) plus aliases; a dependency analyzer rejects direct/transitive data- and control-dependencies from batch symbols to protected sinks and emits mechanism/location/dependency-path diagnostics. (2) A dynamic validator that, per kernel-family test policy, embeds the same preserved sample into multiple batch contexts (baseline: batch size 1) and requires bitwise-identical structure, shape, dtype, and values.
- **Integration as successive acceptance gates without touching the agent.** A framework adapter orders evaluation as static BI → reference correctness → dynamic BI → benchmarking, and routes failures back through the framework's native feedback channel; prompts, search state, and selection policies stay unchanged.
- **First work (to the authors' knowledge) to make BI an acceptance criterion during LLM-driven kernel optimization**, versus prior system-specific fixes (Thinking Machines' batch-invariant ops replaced only four PyTorch operators; vLLM's BI mode covers supported implementations only).

## Methodology

The paper formalizes BI as: for kernel K, input domain X, and the set C(x) of admissible batch contexts preserving target sample x (batch size, composition, and position of x may vary), K is batch invariant iff K(B_c)_{i_c} ≡_bit K(B_c')_{i_c'} for all admissible context pairs under fixed hardware/software. This is deliberately distinct from run-to-run nondeterminism (unordered atomics) and environment-induced variation. The goal is a kernel that (i) meets the task's numerical correctness tolerance, (ii) is BI, and (iii) is fast.

**Static analysis module.** A DSL contract per task declares the batch-source vocabulary (e.g., `B, batch, batch_size, num_seqs, len_indptr, num_kv_indices, total_pages`) and protected parameters. Example: `NUM_SPLITS { semantic split_structure; policy fixed_across_batch; aliases [num_splits, split_k, SPLIT_K, num_partitions, ...] }` — the analyzer then rejects any dependence (including batch-derived control dependence through conditionals/loops) from a declared batch symbol to `NUM_SPLITS` or an alias. On rejection it reports the protected mechanism, source location, dependency path, and mechanism-specific repair guidance. Opaque runtime effects (autotuning, backend dispatch) are out of scope statically and delegated to dynamic validation.

**Dynamic validation module.** Task metadata selects a predefined batch-test policy by kernel family — higher-risk families like attention exercise more execution boundaries. The harness runs the preserved target sample at a baseline context (sample 0 at batch size 1), then re-embeds the identical sample in each larger batch context, extracting and comparing its output bitwise with the baseline; testing stops at the first mismatch.

**Agent integration.** A lightweight adapter wraps both modules into the candidate-evaluation pipeline of each framework, preserving the framework's original correctness test, benchmark, prompt, and search state. Candidates pass four sequential gates (static BI, correctness, dynamic BI, benchmark); BI failures skip later stages and inject diagnostics into the framework's existing feedback path so later rounds can condition on them.

**Evaluation protocol.** Controlled generation with three agents — K-Search (co-evolving world model, 20 turns), Iterative Agent (single-trajectory refinement, 25 turns), Evolve Agent (recent/elite candidate pools, 25 turns) — all using Gemini 3.7 Flash on an NVIDIA H100 NVL, with turn budgets held fixed between vanilla and BI-aware reruns. The task suite is a compact, risk-focused selection of 39 batch-applicable tasks (attention: GQA/MLA/DSA across paged/ragged prefill/decode; linear attention: KDA/Gated DeltaNet; plus MoE, normalization, sampling) covering 1,180 benchmark workloads/shapes. Metrics: final-solution BI pass rate (fraction of correctness-passing kernels with no confirmed violation, labeled by independent local tests), BI intervention rate, geometric-mean speedup vs the task reference, and speedup retention. Ablations run offline on a balanced 200-candidate pool (100 confirmed violations + 100 clean, independently labeled, near-duplicates limited).

## Results & Highlights

- **Released-artifact audit:** 19 confirmed BI violations out of 83 batch-applicable artifacts (131 total) — a 77.1% BI pass rate; on KernelBench.com artifacts specifically, 18/79 violations (77.2% pass), and 1/4 on K-Search/FlashInfer-Bench (75.0% pass). Attention kernels show a confirmed-violation rate ≥50% ("High" evidence tier).
- **Main controlled result:** across the three agent frameworks, the final-solution BI pass rate improves from 67.6% (baseline) to 91.9% (BI-aware) (+24.3 pts) on the 39-task KernelBench.com/FlashInfer suite, while geometric-mean speedup goes from 28.91× to 26.54× — 91.8% of the baseline speedup retained; ordinary (tolerance-based) correctness is essentially unchanged, 94.9% → 95.7%.
- **Per-framework:** K-Search BI pass 75.7% → 97.4% with GM speedup 40.94× → 35.39× (86.4% retained) and correctness 94.9% → 97.4%; Iterative Agent 48.6% → 89.2% with 25.84× → 22.66× (87.7% retained); Evolve Agent 78.4% → 89.2% with 22.85× → 23.31× (102.0% retained — BI-aware actually faster). The weakest-baseline framework (Iterative, 48.6%) needed the highest intervention rate (43.6% of tasks vs 23.1% K-Search, 25.6% Evolve).
- **Component ablation (N=200 balanced, independently labeled pool):** full BIEvolve detects 92% of confirmed BI violations vs 83% for static-only and 55% for dynamic-only (46% detection overlap between modules), at 2% false rejection and a median 10.21 ms evaluation cost per candidate (7.69 ms static, 2.24 ms dynamic) — quantifying the intended complementarity.
- **Where the speed is lost:** retention is 86.0% on tasks whose baseline kernel had a confirmed BI violation vs 95.7% on clean tasks (e.g., Iterative Agent: 74.2% vs 93.6%), consistent with BI gating pruning fast-but-batch-dependent tricks; notably, on those 9 violation tasks BI-aware generation keeps improving late — a 26.30% best-so-far GM-speedup gain over the final 5 turns vs 6.11% for baseline (Appendix D, 37 tasks) — though it does not close the gap within the fixed budget.

Simin Chen's prior work includes the S&P 2026 paper on compiler-inconsistency vulnerabilities in deep-learning compilers cited here ([9]), so the group has direct expertise in numerical-consistency/reproducibility issues in ML infrastructure. The paper is a preprint (v1, cs.AI, 27 Oct 2026) with a released artifact (github.com/STAR-Computing/BIEvolve), executable contract listings (Appendix B reproduces `batch_identity.bid` verbatim), and unusually careful evaluation hygiene: independent BI labeling separate from BIEvolve's own decisions, a balanced ablation pool, reported false-rejection rate, and per-subgroup speedup retention rather than a single aggregate.

## Critical Assessment

- **Novelty: moderate-to-good, and honestly positioned.** The claim of "first to make BI an acceptance criterion during LLM-driven kernel optimization" is credible given the related-work survey (KernelBench/FlashInfer-Bench are evaluation frameworks; Kevin/K-Search optimize correctness+speed; Thinking Machines' batch-invariant ops replaced only four PyTorch operators; vLLM's BI mode is system-specific). But the components themselves — taint-style dependency analysis and differential testing — are standard software-engineering techniques; the contribution is the contract-DSL design, the gate ordering, and the plug-in integration, not a new analysis algorithm.
- **Rigor: high.** Controlled reruns with fixed turn budgets and a single model (Gemini 3.7 Flash) per framework; correctness reported separately from BI; the ablation pool (100 confirmed violations + 100 clean) is labeled by independent local tests that observe actual bitwise differences, not by BIEvolve's own output; false rejections (2%) and per-candidate timing are disclosed.
- **Red flags / caveats that temper the headline numbers:** (1) The dynamic validator samples only a finite subset of the BI context space — one preserved sample at position 0, batch-size-1 baseline, first-mismatch stopping — so "BI pass" is not a proof of invariance; consistent with this, 8.1% of final kernels still fail. (2) The static rules are hand-curated contracts with enumerated aliases; anything undeclared (e.g., opaque algorithm selection, expert routing) is only caught if the finite dynamic sweep happens to trigger it — the paper acknowledges limited cross-file analysis. (3) The 39-task suite is deliberately compact and attention/linear-attention-heavy ("risk-focused" selection), so the 91.9% figure should not be read as coverage of the whole FlashInfer space. (4) All results use one LLM and one GPU (H100 NVL); sensitivity to other models/hardware is untested. (5) The real cost is visible for K-Search: GM speedup drops 40.94× → 35.39× (−13.6%), i.e., BI is not free even if the average retention (91.8%) sounds benign. (6) Evaluation is at kernel-output level; the paper itself concedes end-to-end effects on token generation, RL rollout-training mismatch, and serving are future work — so the practical severity of a BI violation is asserted (via prior work) rather than measured here.
- **Reproducibility: good.** Code and contracts are released; the DSL grammar, an executable contract, the exact gate order, turn budgets, model, GPU, dynamic-validation protocol (3 warmups, 10 synchronized reps, median reported) are all specified. The task suite being hand-selected is the main thing a replicator would have to match.

## Strengths

- Turns a real, previously unmeasured serving-reliability problem (batch-dependent outputs from agent-generated kernels) into a precise, testable definition (bitwise invariance over admissible batch contexts) and backs it with field evidence from released artifacts.
- The plug-in design is the right engineering call: it preserves each agent's optimization capability (prompts, search state untouched) and is demonstrated on three architecturally distinct frameworks, including one (Evolve Agent) that retains 102% of baseline speed.
- Static and dynamic modules are genuinely complementary and the paper quantifies this (92% combined detection vs 83%/55% individually; 46% overlap) instead of asserting it.
- Actionable diagnostics (mechanism, location, dependency path, repair hint) close the loop with the agent rather than just rejecting candidates — and the low per-candidate overhead (10.21 ms median) makes the gates practical.
- Honest subgroup reporting: retention split by baseline BI outcome (86.0% vs 95.7%) and a late-stage-gain analysis that resists overinterpreting the fixed-budget comparison.

## Limitations

- Static analysis has limited cross-file scope and only covers patterns declared in hand-written contracts (alias lists like the 20+ `NUM_SPLITS` variants must be enumerated); automated rule extraction is left as future work.
- Dynamic validation checks a deliberately lightweight, finite subset of contexts (single preserved sample at position 0, batch-size-1 baseline, stop-at-first-mismatch), so passing is evidence, not proof — 8.1% of final solutions still exhibit confirmed violations.
- Evaluation is kernel-level: no end-to-end measurement of how residual batch variance propagates to generated tokens, evaluation scores, serving behavior, or RL training-inference mismatch.
- The task suite is compact (39 tasks) and skewed toward the highest-risk attention/linear-attention families; a single LLM (Gemini 3.7 Flash) and single GPU (H100 NVL) are used, so generalization across models, hardware, and operator families is unverified.
- Enforcing BI costs real performance for some frameworks (K-Search retains 86.4% of speedup; Iterative Agent only 74.2% on violation-prone tasks), and the paper cannot yet say whether larger search budgets close that gap.

## 相关性（Relevance）

本文正处在「LLM agent 自动生成/优化 GPU kernel」与「LLM 推理服务可靠性与可复现性」的交叉点上：它指出仅以正确性+加速比为目标的 kernel agent（KernelBench、K-Search、FlashInfer 系）会系统性地产出批依赖的 kernel，并给出可插拔的验收闸门方案。对关注代码生成 agent 的可靠性评估维度、以及动态 batch serving 中数值一致性的研究与应用都是直接的补充。

## Questions for Further Exploration

- Can the BI-contract DSL rules (batch symbols, protected parameters, alias lists) be synthesized automatically by an agent from representative violation examples, and would learned rules generalize beyond the attention/linear-attention families that dominate the current suite?
- What is the end-to-end impact of the residual 8.1% violating kernels — do bitwise differences at the kernel level measurably alter generated tokens, benchmark scores, or RL rollout-training mismatch in a production serving stack?
- Since the Evolve Agent retains 102% of baseline speed while K-Search loses 13.6%, which search-strategy properties (candidate-pool breadth vs single-trajectory refinement) determine the performance cost of BI constraints, and can larger turn budgets close the gap given the 26.3% late-stage gains observed on violation-prone tasks?
- Would integrating BI into the training signal itself (e.g., Kevin-style RL with a BI reward) internalize invariance better than rejection gates, and at what sample-complexity cost?
- Does the approach transfer to other hardware/backends (AMD, tensor-parallel settings where Zhang et al.'s deterministic-inference work operates), and would dynamic validation with multiple preserved samples and positions (not just sample 0 at batch size 1) materially raise the 92% detection rate?
