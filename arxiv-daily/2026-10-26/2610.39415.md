> **一句话总结：** Evo 2 DNA 语言模型的 1B/40B 检查点在 Blackwell GPU 上失效的根源不是精度降低而是精度提高——作者用自研的位精确 H100 FP8 GEMM 模拟器 mmaemu 把依赖定位到每个模型的第一个 FP8 投影，并证明仅用一张查表替换该投影（权重不变）就能把 40B 在 RTX 5070 Ti 上的 BRCA1 变异分类 AUROC 从 0.434（低于随机）恢复到 0.869（H100 参考为 0.868）。

> **TL;DR:** The Evo 2 DNA language models (1B, 40B) fail their official forward tests on Blackwell sm_120 GPUs not because FP8 there is sloppier but because it is *more* accurate: the RTX 5070 Ti's native GEMM rounds 99.996% of block-0 projection outputs correctly (H100: ~30%), and even plain fp32 accumulation of the same E4M3 operands reproduces the failure (loss 1.2480 vs expected 0.5020 for the 1B). Using mmaemu, a bit-exact H100 FP8 GEMM emulator validated on all 168 captured 1B projection outputs, the authors bisect the dependence to the first FP8 projection (1 of 21 in the 1B, 1 of 42 in the 40B); substituting just that projection via a 512-entry lookup table restores 40B BRCA1 variant-classification AUROC from 0.434 to 0.869 on the RTX 5070 Ti (H100 baseline 0.868, paired delta +0.435, 95% CI 0.360–0.507) and from 0.481 to 0.867 on an RTX PRO 6000, at only ~16% latency overhead — though the 40B forward test still narrowly misses tolerance (0.2170 vs 0.2159 ± 0.001), showing application agreement and test compatibility are distinct.

## 核心贡献

- **证明"更高精度反而破坏检查点"**：Evo 2 的 1B/40B 检查点在 Blackwell (sm_120) GPU 上失效，而失效的 native FP8 GEMM 恰恰是更精确的那个（99.996% 输出正确舍入 vs H100 的约 30%）；对相同 E4M3 操作数做 IEEE fp32 或 float64 累加同样复现失效——排除了 FP8 核本身的嫌疑，把问题锁定在累加算术上。
- **构建并验证了位精确的 FP8 GEMM 模拟器 mmaemu**：能整体模拟库级 GEMM 调用（张量核心累加链、split-K 行为、输出 epilogue），对捕获的全部 168 个 H100 1B 投影输出逐位一致，split-K 合并规则在后续 2,416 次调用上全部命中；由此实现"按算术对模型做二分"。
- **把依赖定位到单个投影**：1B 的 21 个 FP8 投影中只有第 0 块的第一个是关键——仅模拟它其余 native 则通过测试（0.5027），仅它 native 其余模拟则失效（1.2500）；40B（42 个投影）同样如此。该投影输入只含单个 token id，其参考输出可装进 512 项查表。
- **刻画了被依赖的具体算术性质**：1B 第 0 块上，H100 式 13 位截断链通过，精确累加失败；精确和乘以 H100 实测的 1.4% 收缩增益（a=0.985869）通过，除以 a 则失败；提高截断链精度（13→25 位）逐步恶化至失效，13 位改最近舍入也失败——说明"更不准更安全"不成立，检查点依赖的是参考算术的特定性质（朝零方向的轻微收缩）。
- **区分三层一致性并给出工程建议**：算子一致、模型功能一致、应用一致可以互相脱钩（两个参考 GPU 每个投影的位都不同却都通过；查表恢复 AUROC 却仍差 0.0011 未过前向测试）；建议发布方注明参考算术、提供应用级参考输出，并提出廉价筛查：用 fp32 累加相同操作数重跑测试。

## Key Contributions

- **Demonstrates that greater accuracy, not lower accuracy, breaks the checkpoints.** On Blackwell sm_120 GPUs the Evo 2 1B and 40B fail the developers' forward tests while the 7B passes; the failing native GEMM is the *more* accurate one (99.996% correctly rounded outputs on one measured 1B projection vs ~30% on H100/RTX 4060, whose errors lean toward zero). Accumulating the identical E4M3 operands in IEEE fp32 (or float64) reproduces the failure with no FP8 kernel involved — matching BioNeMo's earlier observation on Hopper.
- **Builds and validates mmaemu, a bit-exact FP8 GEMM emulator of whole library calls** (Transformer Engine on H100 PCIe and RTX 4060), modelling the tensor-core accumulation chain, split-K decomposition, and output epilogue. It reproduces bit-for-bit all 168 captured H100 outputs of the 1B's 21 projections, and a split-K combination rule fitted on one probe matched all 2,416 split calls of a later sweep. This enables "bisecting a model by arithmetic" while GPU, weights, and FP8 operands stay fixed.
- **Localises the dependence to a single early projection.** For the 1B (21 FP8 projections), emulating only block 0's projection and leaving the other 20 native passes the forward test (loss 0.5027 vs native 1.2480), while block 0 native with the rest emulated fails (1.2500); the 40B (42 projections) behaves the same (0.2170-with-table vs 1.4277 block-0-native). Because block 0's projection sees the normalised embedding of a single token, its reference outputs for all 512 token ids fit a lookup table that matches live emulation on every call.
- **Characterises *which* arithmetic property the 1B depends on.** At block 0, the H100-like 13-fraction-bit truncating chain passes; exact accumulation fails (1.2480); the exact sum multiplied by the H100's measured least-squares gain (a = 0.985869, a 1.4% shrinkage toward zero) passes (0.5027) while dividing the reference chain by a fails (1.3730). Of nine sampled gains only two mild shrinkages (~0.986, 0.993) pass; raising the truncating chain from 13 to 25 fraction bits monotonically breaks it (0.5027 → 1.2480), and round-to-nearest at 13 bits fails (1.1924). So the checkpoint depends on a *specific* bias of its reference arithmetic, not on inaccuracy per se.
- **Separates three levels of agreement and proposes cheap screens.** Operator agreement, model function, and application agreement demonstrably dissociate: the two reference GPUs differ in every projection's bits yet both pass; full emulation passes with non-H100 logits; the 40B table restores BRCA1 AUROC while still missing the forward tolerance by 0.0011. The authors recommend releases specify reference arithmetic (GPU, stack, effective accumulation mode) and suggest screening FP8 checkpoints by re-running tests with the same operands accumulated in fp32 (noting a pass does not rule dependence out).

## Methodology

The study is a controlled numerical-intervention experiment on fixed weights, organised as arithmetic bisection:

1. **Baseline matrix.** Official Evo 2 checkpoints (evo2_1b_base, evo2_40b, evo2_7b) are run on reference GPUs (H100 PCIe and RTX 4060 via the official Transformer Engine FP8 path) and on Blackwell sm_120 GPUs (RTX 5070 Ti, cu128; later RTX PRO 6000, cu13), varying only the FP8 input projections (21 GEMMs in the 1B, 42 in the 40B; other computation native). Pass criterion is the upstream forward test: mean bf16 next-base cross-entropy over four prompts within 0.001 of expected (1B 0.5020, 40B 0.2159); a greedy generation test (500 bases, within 3 points of expected identity) and BRCA1 variant scoring complete the picture.
2. **Emulation (mmaemu).** The FP8 GEMM is modelled as chains of block FMAs (blocks of 16 products on Ada, 32 on Hopper), each aligning products and incoming accumulator to a common exponent, truncating toward zero to 13 fraction bits, summing exactly, truncating again; split-K partial sums are combined per-platform; the epilogue computes bf16(RN32(acc · RN32(sa·sb))). Validation: bit-exact on all 168 captured H100 outputs (two output types × two accumulation modes × two APIs across the 1B's 21 projections) and on the 2,416 split calls of a later sweep. Longer windows and all 40B projections rely on the validated model rather than direct captures.
3. **Single-projection bisection.** Individual projections are swapped between native, emulated (hopper-te / ada-te profiles), fp32/float64 accumulation, bf16 GEMM, and a block-0 lookup table, under a locally SHA-256-hashed analysis plan (PLAN_C) frozen before the GPU runs, with a ten-entry deviation log.
4. **Mechanism probes at block 0 (1B).** Accumulator treatments (truncating chains of 13–25 bits, round-to-nearest, exact sums scaled by sampled gains, noise on the reference accumulator) isolate shrinkage-vs-pattern effects; matched-size Gaussian perturbations of the residual stream after block 0's residual addition test whether the native-minus-emulated difference's *size* or its *structure* causes the collapse.
5. **Application recovery.** 500 BRCA1 variants (111 loss-of-function) from the Findlay et al. saturation-genome-editing assay, scored zero-shot by change in mean sequence log-probability over 8,192-bp windows; AUROC with 2,000-resample variant bootstrap, paired differences on shared resamples, Pearson correlation and sign agreement against the H100 reference.

## Results & Highlights

- **Forward-test failure magnitudes (upstream four-prompt test, RTX 5070 Ti native FP8):** the 1B's mean loss is 1.2480 vs expected 0.5020 (2.5x) and the 40B's is 1.4023 vs expected 0.2159 (6.5x); the 40B's next-base accuracy drops to 25.7%, essentially the 25% guessing floor over four bases, against 91.6% on the same GPU under hopper-te emulation and 91.7% on the H100. The 1B's next-base accuracy roughly halves (79.5% → 38.5%) and it fails the generation test at 32.65% identity vs the expected 68.0 ± 3.
- **The accuracy paradox, quantified:** on the 1B's block-0 projection (one 2,048-bp window, 11,796,480 outputs), the RTX 5070 Ti natively returns the correctly rounded bf16 value for 99.996% of outputs vs ~30% on both reference GPUs (H100 29.9%, RTX 4060 29.7%); accumulating the same E4M3 operands in IEEE fp32 or float64 reproduces the native failure exactly (1B loss 1.2480, 40B loss 1.4023), and a truncating chain with 25 fraction bits matches the RTX 5070 Ti's native outputs bit for bit.
- **Localisation:** with only block 0's projection emulated (rest native) the 1B passes at 0.5027 and the 40B reaches 0.2170 (0.0011 from expected, just outside the 0.001 tolerance; 0.2168 with the other projections in bf16); with only block 0 native (rest emulated) the 1B fails at 1.2500 and the 40B at 1.4277.
- **Mechanism (1B block 0):** exact accumulation fails (1.2480) but the exact sum shrunk by the H100's in-sample gain a = 0.985869 passes (0.5027), while the reference chain divided by a fails (1.3730); truncating-chain precision sweeps give 0.5027 / 0.5037 / 0.7163 / 1.1406 / 1.2480 at 13/14/15/16/25 fraction bits, and 13-bit round-to-nearest fails (1.1924). Only 2 of 9 sampled gains pass, both mild shrinkages (~0.986, 0.993); an enlargement at 1.007 equidistant from exact fails.
- **Structured, not sized:** injecting the full native-minus-F13 residual difference after block 0 collapses the model (fp32 loss 1.2488), but five Gaussian perturbations whose per-token L2 norms match it within 1% all keep the model healthy (0.5023–0.5027) — direction/structure matters, not magnitude.
- **Application recovery (500 BRCA1 variants, 111 LoF):** 40B AUROC on the RTX 5070 Ti rises from 0.434 native (below 0.5; 95% CI 0.373–0.497, per-variant Pearson r = −0.032 vs H100) to 0.869 with the block-0 table (paired delta +0.435, 95% CI 0.360–0.507; r = 0.997, 97.4% sign agreement), matching the H100 reference's 0.868; on the RTX PRO 6000 (cu13) it rises from 0.481 to 0.867 (paired +0.385, CI 0.306–0.463) and the 1B from 0.556 to 0.721 (H100 1B reference: 0.733). The 1B table also restores the generation test (70.95% vs expected 68.0 ± 3).
- **Cost of the fix:** an 8,192-bp 1B forward pass with the block-0 table runs 16% slower than native (medians), vs 2.2x for full emulation; per-call, emulated GEMMs are 21.8–28.5x slower than native torch._scaled_mm.

## Critical Assessment

- **Novelty:** The failure phenomenon itself is known (community GitHub issues #132/#157, BioNeMo's documentation, an evo2_ft fine-tuning project that localised something to block 23) — the paper says so explicitly. The genuine novelty is the controlled chain: a bit-exact emulator validated on captures, single-projection arithmetic bisection, mechanism probes that separate shrinkage from pattern, and recovery of a scientific application with weights untouched. This is a solid incremental-methods contribution, not a new capability.
- **Rigor:** High on the intervention side and refreshingly honest, but with real soft spots. The shrinkage gain a = 0.985869 is fitted in-sample (on one of six windows) and no rescaling correction was tested, so the "checkpoint depends on a 1.4% shrinkage" claim is a diagnostic, not an established mechanism; the authors label it as such. The training-origin hypothesis (training compensated for truncated accumulation) is a back-of-envelope construction modelled neither on FP8 arithmetic nor Evo 2's training and is untested. mmaemu's bit-exactness is validated only on 1B captures — all 40B conclusions ride on an extrapolated model, and there are no direct H100 captures of 40B projections.
- **Reproducibility:** Excellent — hashed plans with deviation logs, public code, archived recordings, CI replaying committed subsets, and a number-to-file ledger. Caveats they disclose themselves: the exploratory RTX 4060 runs' fp32 code is "not preserved", the torch._scaled_mm script version "is not established", and the PRO 6000 follow-up changes software (cu13) along with hardware, so its H100 comparisons confound two variables.
- **Significance:** A crisp, well-documented case study with a transferable lesson (accuracy ≠ compatibility; releases should specify reference arithmetic) and a practical patch (token-id lookup table at 16% overhead). But generality is unproven: one model family, one assay, one 500-variant cohort, and the proposed fp32 screen and per-projection bisection are explicitly "untested beyond Evo 2". Even within Evo 2 the 7B passes and BioNeMo's B300 result for the 1B is an unexplained boundary case.
- **Red flags (minor, mostly self-flagged):** the 40B block-0 table still misses the forward-test tolerance (0.2170 vs 0.2159 ± 0.001) and the PRO table's forward loss was never recorded, so the headline "restores variant scoring" is application-level recovery, not full compatibility — a distinction the abstract conveys only via "despite a narrow forward-test miss". The rounding-accuracy measurement (99.996% vs 30%) comes from a single window whose GEMM rows embed only four distinct tokens (23,040 distinct dot products), an unusual quirk of the first projection; mechanism controls use just the four upstream prompts; and the AUROC bootstrap is conditional on single recorded runs, with no run-to-run or cross-region uncertainty. None of these undermine the main claims, which are stated with appropriate hedging.

## Strengths

- Turns a confusing community bug report into a fully controlled causal chain: arithmetic change → localised single-projection dependence → candidate property (mild shrinkage, not inaccuracy) → application-level recovery with weights fixed.
- mmaemu is a genuinely useful tool beyond this paper: bit-exact emulation of whole library GEMM calls (not just instructions), cross-validated on split-K behaviour, Apache-2.0 with archived validation logs and CI.
- The matched-perturbation control (Gaussian noise at the native difference's norm passes while the structured difference collapses the model) is exactly the right experiment to rule out "big perturbation = broken model".
- Conceptually clarifying distinctions: operator agreement vs model function vs application agreement, and determinism ≠ compatibility (two reference GPUs disagree on every projection's bits yet both pass; the two sm_120 GPUs match bit for bit yet fail).
- Exceptional transparency: hashed analysis plans, deviation logs, per-number provenance ledger, unfunded-status and AI-assistance disclosure, and restraint in not interpreting the below-0.5 AUROC as anti-correlation.

## Limitations

- One model family (Evo 2); the 20B checkpoint, B200, and B300 were never run, and the 7B has no reference-GPU comparison; prevalence of such arithmetic dependence across low-precision checkpoints is not estimated.
- Reference evidence rests on exactly two configurations (one H100 PCIe, one RTX 4060); 40B findings extrapolate a 1B-validated emulation model, with no direct H100 captures of 40B projections and tests limited to ≤8,192 projection rows.
- The 1.4% shrinkage gain is in-sample; no rescaling correction was validated as a fix, and the training-origin explanation is untested conjecture.
- The 40B lookup table misses the forward tolerance on the RTX 5070 Ti (0.2170, off by 0.0011), the PRO table's forward loss was not recorded, and 40B generation was never tested under emulation or the table — so full 40B compatibility is not restored, only BRCA1 scoring.
- Biology evidence is one assay (BRCA1 saturation genome editing) on a seeded 500-of-3,893 variant subset (111 LoF); bootstrap intervals are conditional on the recorded runs and ignore window-overlap dependence and run-to-run variation.
- Mechanism controls (gain sampling, precision sweep, matched perturbations) cover sparse grids and only the four upstream prompts; the block-23 localisation reported by the evo2_ft project under other criteria and GPUs is not reconciled.
- mmaemu does not support bias, row-wise scales, autograd, or CUDA graphs, limiting reuse for training-side studies.

## Relevance

这篇论文是"极限性能优化下的可靠性"与"推理可靠性"方向的典型案例：它精确刻画了低精度（FP8）张量核心累加算术的代际差异如何在权重完全不变的情况下静默破坏模型输出（下游 AUROC 跌破 0.5），并提供了定位、筛查与低成本修复的完整方法论——对任何依赖低精度推理栈的模型部署与检查点可移植性评估都有直接参考价值。

## Questions for Further Exploration

- How common is accumulation-arithmetic dependence across other released FP8/FP4 checkpoints (LLMs as well as genomic models)? Would the proposed fp32-accumulation screen, run across a broad checkpoint corpus, find many false negatives (dependence despite passing)?
- Did the dependence actually arise during training — i.e., can controlled fine-tuning under truncated vs exact accumulation create (or remove) it? BioNeMo's fine-tuned 40B that flips which arithmetic it tolerates is the natural starting point.
- Why does block 0 dominate when its residual addition largely cancels the branch output (12.5–13.4x relative amplification across the addition)? Is the amplification mechanism (fitting r = x + αwx to a near-cancelling target) quantitatively consistent with the observed 1.4% gain sensitivity?
- Can the shrinkage diagnosis be turned into a validated correction — e.g., a per-projection learned rescale fitted on reference outputs — that passes the 40B forward test everywhere, not just the application benchmark?
- Does the "application agreement without forward-test compatibility" gap generalise: should model releases ship application-level reference outputs and tolerances (BRCA1-style scoring vectors) alongside operator-level tests, and what tolerance bands separate platform noise (84.2% cross-reference sign agreement) from genuine failure?
