Why this matters

Pairs 100% validity with a 1.0–1.4× speedup for structured outputs — tool calls, plans, itineraries — instead of trading one for the other.

hits both speculative-decoding and constrained-generation lines; deployable in SGLang / vLLM today

Critical edge

The 13.9× counts valid records against baselines that mostly emit invalid ones — the pure speed lead is 1.01–1.43×, shrinking to 1.01–1.12× exactly where the model, not the relations, chooses most tokens.

Methodology 方法

1 · DeclareJSON Schema + relations over JSON Pointer paths (12 relation kinds); compiles in 0.05–0.55 ms median
→
2 · Factor grapheach relation = Boolean table; exact support via memoized bucket elimination (min-fill order)
→
3 · Certain draftspositions with exactly one token form determined runs, proposed as speculative drafts
→
4 · Verifytarget model provably accepts them; per-request width from a concave return model

The invariant: every admitted token extends to a complete, valid record — no arc-consistency-style dead ends (which the paper shows strand 12–64% of planning records in prior semantic constrained decoders). Query cost is tamed by memoization (consecutive decoder queries share almost all work) and smarter encodings: a naive all-different table over 7 cities would join 22.2M entries; a visited-set chain encoding needs 8,575 (529,200 at 10 cities).

The systems half: mask computation lives in 8 worker processes per rank, writing double-buffered shared-memory mask rows and precomputing the next reply while the GPU runs — so exactness costs ~8 host CPU cores per GPU, not GPU time. Registers as a grammar backend + five speculative algorithms in SGLang, and a reply-block grammar object in vLLM; non-relational requests fall through to XGrammar.

  • Empirical hygiene unusually strong for a systems preprint: per-cell tuned baselines across 11 drafter shapes, 95% Wilson intervals, closed- and open-loop protocols.

Strengths 优势

  • Turns an inherent cost (exact joint-relation checking) into a speed source via lossless drafting — a clean, transferable insight.
  • The problem is real and well-quantified: 10–14% valid itineraries for Qwen3-8B even with retries; ~1/3 at best for meetings under all syntax-only baselines.
  • Exactness at essentially grammar-mask throughput — memoized elimination, chain encodings, shared-memory worker service, ablated piece by piece.
  • Evaluation breadth: 2 engines, 4 models, 7 syntax-only baselines plus solver / enumerated-schema / retry / thinking alternatives, per-cell tuned.
  • Intellectual honesty: reports where it ties, where it loses (solver gold-match), and where gains fade.

Limitations 局限

  • Relations must be hand-declared per task over finite domains; 12 fixed relation kinds; a wrong spec silently constrains to the wrong relation.
  • Gains proportional to the determined token share — inherently small on generation-heavy structured tasks (1.77× → 1.13× with free-text notes).
  • Where gold follows a fixed objective, model freedom tracks gold far worse than a solver (14–16% vs 46–56%).
  • One GPU type (RTX A6000), models ≤ 14B, ≤ 128 in flight; faster devices may need more workers — the ~8-cores/GPU host budget could grow.
  • Verify-width rounding can flip 1–4 of 64 greedy records between runs (still valid); some figure settings ran at a later commit.

Questions for further exploration 待探索

  1. Can relation specs be inferred automatically (an LLM reading tool docs or few-shots) and verified against the constraint engine, removing the hand-declaration bottleneck?
  2. How do the width allocator and worker overlap behave on H100/B200-class GPUs and 30B–70B models, where the step shrinks and the host must hide a larger share of the check's tail?
  3. Does drafting determined tokens change the conditional distribution of model-chosen fields — is the record the model "would have" written?
  4. Could the factor-graph feasibility check replace enumerated schemas (anyOf of up to 1,024 records) when the feasible set is exponential but the factor structure compact?
  5. How does it interact with continuous serving concerns absent from the paper — preemption, chunked prefill mixing, multi-tenant spec pools beyond 128 in flight?
