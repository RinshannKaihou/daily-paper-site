方法论 · METHODOLOGY

Three moving parts, one shared cluster

Trainer
Async GRPO (Qwen3.5-35B-A3B) · Ray workers live outside the sandboxes
─▶
Pod provider
Paced creates (shared token bucket) · nonce-tagged for idempotent delete · owner-ref GC fallback
─▶
Sandbox pod + execd
Daemon read-only-mounted into unmodified task images (needs only bash + Python 3) · persistent bash keeps cwd / env / background processes · per-sandbox token · bidirectional network guards
＋
Warm pool (optional)
Ray actor, pods keyed by (image, base commit) · caps + idle eviction · worker fallback to direct create (4.3% of gradings)
  • Burst survival: token-bucket pacing across on-demand / warm / replacement creates, soft topology spreading (max skew 2), up to 30 retries with backoff+jitter on 429 / webhook timeout.
  • Handoff gate: readiness probe + execd health check (incl. image pull) must pass before a sandbox is delivered.
  • Cleanup ownership: caller timeout ≠ abandonment — the provider finishes accepted creates, deletes on nonce match, retries unconfirmed deletes; owner references let Kubernetes GC orphans.
  • Checked reuse (grading pods): baseline of grader-touched state recorded at create; restore-or-delete after each grading; max 8 reuses; retire on contradicting verdicts.
  • Determinism guard: pre-grading in-pod probe verifies declared execution conditions (egress, CPU quota, timezone, hash seed) — because 15/500 SWE-bench Verified reference patches flip verdicts across conditions.
  • Hard lessons baked in: direct pod addresses replaced Service-per-slot (0.05 s vs 2.3 s to first command; Service links injected ~23,400 env vars into new containers).

Provisioning is a rounding error next to data wait — faster sandboxes alone will not speed up training. This decomposition is the paper's most transferable finding.

The prewarming trade, in full
Warm pool served 93–96% of gradings; median grading acquisition 6.2 s → 0.12 s; step 24 arrived 9.4% sooner — but reserved vCPU-hours ×2.46, and the steady-state step-interval difference (−8.7 s, 95% CI −38.4…+21.0) never left zero. Checked reuse: −29% pod creations per grading (95% CI 22–36%).
长处 · STRENGTHS

What it gets right

  • Trace-driven design: every mechanism (pacing, nonce cleanup, address-aware spreading, condition probes) answers an observed failure; 41 operational cases with causes, fixes and bounded costs are documented.
  • Exceptional measurement honesty: negative results, confounded experiments flagged as confounded, incident losses labeled upper bounds, and a version-provenance table separating what each study actually ran.
  • First training-time anatomy for agentic RL infrastructure — corrects the intuition that faster provisioning would directly speed training.
  • Full-cost accounting others omit: ×2.46 vCPU for prewarming, 10.5% / 1.9% actual CPU / memory utilization vs requests, 1.7–4.0% of GPU spend.
  • Cleanup proven by fault injection (25 trials, zero leaks), not just happy-path benchmarks.
局限 · LIMITATIONS

Where it stops short

  • Novelty is engineering, not invention: daemon injection is shared with agent-sandbox; serial create loses to CubeSandbox snapshots (2.18 s vs 0.08 s).
  • Comparison fairness: baselines acknowledged as under-tuned; most burst configurations ran once (headline 116/308 s vs 198/547 s has no repeats).
  • Scope: one EKS cluster, SWE-style Python tasks, one agent harness, one async trainer — browsing / computer-use agents untested.
  • Peak numbers with asterisks: the 11,858-concurrency run used tiny 0.1 vCPU / 128 MiB pods; campaigns A–D ran earlier Sandman versions (Table 3).
  • No isolation upgrade over runc: no seccomp, shared kernel, model code as root — "we do not claim protection against a malicious co-tenant."
  • Not reproducible yet: open-sourcing of daemon / provider / pool still pending at paper time.
追问 · QUESTIONS FOR FURTHER EXPLORATION
  1. Would microVM isolation (Firecracker / Kata) shift the latency–cost frontier at this scale, given gVisor only partly supports the packet filter behind the outbound guard?
  2. What model links sandbox-acquisition delay to rollout throughput — and would more prewarming pairs show a steady-state gain?
  3. How much of the −2.33 pp pass-rate drop comes from preflight task removal vs authentication changes? A factorial ablation is needed before adoption.
  1. Can hermetic execution eliminate the residual 15/500 SWE-bench Verified verdict flips — and what does that noise do to GRPO group-relative advantages at small group sizes?
  2. Does the design port to bursty non-SWE agents (browsing, computer-use) whose sandboxes are long-lived and stateful?
  3. Once open-sourced, how does checked reuse compare against DeltaBox-style millisecond checkpoint-rollback on correctness and pod-hours?
