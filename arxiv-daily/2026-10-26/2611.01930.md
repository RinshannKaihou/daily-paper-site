> **一句话总结：** 本文首次定义并测量 LLM Agent 的"返回假设"（工具调用会在有限时间内返回且动作已完成）：关闭输入时 11.5% 的交互式命令会跳过动作却返回 status 0 造成假成功，开放输入则令 token 消耗放大 2.9 倍并扭曲 LLM 排名（Llama-3.3-70B 从第 7 名升至第 3 名）；作者提出 Receipt，从系统调用读取进程真正等待的对象并报告给 Agent，在自建 Tripwire 基准上把 5 个 LLM 的假成功声明从 34 降到 9（-73.5%），检出率 85.0% 且零误报，每次 shell 调用检测开销中位数仅 0.54 毫秒。

> **TL;DR:** The first paper to measure and repair the "return assumption" of LLM agents — that a tool call returns in bounded time with its action done. On their Litmus catalog, closed stdin makes 11.5% of prompting invocations (18/156, e.g. `docker system prune`, `rm -i`) return status 0 without doing the work, and 7 of 8 harnesses (Claude Code, Codex CLI, Gemini CLI, …) close input headless. On their 25-pair Tripwire benchmark, an unanswered question at a plain terminal multiplies token use by 2.9 and moves Llama-3.3-70B from 7th to 3rd of 8 LLMs. Their fix, Receipt (reads what each process waits for from syscalls, model-checked TLA+ protocol), cuts false success claims 73.5% vs closed input (34 → 9 across 5 LLMs incl. Qwen2.5-Coder-32B), beats DeepSeek's stdin-only inspector (85.0% vs 66.7% report rate on Litmus, zero false positives on 119 controls), uses 24.4% fewer tokens than a plain terminal, and completes all 25 trap tasks on Terminus 2 — at ≤0.54 ms median overhead per shell call, already deployed in a commercial agent runtime.

## 核心贡献

- **定义并首次测量"返回假设"**：Agent 依赖"每个工具调用都在有限时间内返回且请求动作已完成"的隐含假设。论文证明该假设在两种输入连接方式下都会失效——关闭输入时程序读到 EOF 走默认路径（可能返回 status 0 却没做动作，如 `docker system prune` 什么都没删、`rm -i` 保留文件），开放输入时程序挂起等到超时，浪费时间和 token。
- **大规模实证测量**：收集 91,469 次生产环境工具调用（6 名开发者、19 个仓库）和 89,047 条公开轨迹（23 种 harness、19 个 LLM），发现公开轨迹中有 1,345 次调用在等待输入（616 次在 Web 运维工具中），并实测 8 种主流 harness（Claude Code、Codex CLI、Gemini CLI、Goose、Aider、OpenCode、mini-SWE-agent、Terminus 2）在无终端时全部关闭输入（Terminus 2 除外）。
- **构建三个可复用数据资产**：Litmus（158 条带验证的交互式命令调用目录，77 个程序、7 类问题）；WaitAtlas（668 个包族 4,855 条命令，证明发射前预测不可行——最佳预测器 AP 仅 0.477）；Tripwire（首个"问题守护请求动作"的 25 对任务基准，每对仅 trap 变体会提问，验证器只查最终状态）。
- **提出 Receipt 修复方案**：保持输入开放但不回答，每 0.1 秒从内核采样系统调用/描述符/CPU 节拍来识别进程真正等待的对象（区分受控输入与外来 socket），报告程序名、提示语、读类型（口令/整行/按键/全屏）；用 TLA+ 模型检查器验证输入投递、中断与报告的顺序协议（7 条性质，去掉规则违反 5 条），无需修改 Agent 或程序。
- **揭示排行榜的系统性偏差**：输入连接方式会改变 LLM 排名（Kendall's τb 仅 0.47），呼吁基准维护者固定并报告输入连接方式。

## Key Contributions

- **Problem definition and finding.** Defines the *return assumption* (every tool call returns in bounded time with its requested action finished) and shows it fails under both input connections: an agent's reliability depends on what its harness lets it observe, not just on its LLM. A "false return" (status 0 without the action) is like a 200 OK with an error body.
- **First real-world measurement of input waits.** 91,469 production tool calls (107 Claude Code sessions, 3 months, 52,953 shell calls) + 89,047 public trajectories from Terminal-Bench 2.0, SWE-rebench, and SWE-bench Verified submissions: 1,345 calls wait for input, 616 inside Web-operations tools; production agents issued 2,910 commands that only check liveness, and a third of shell timeouts are agent-written polling loops.
- **Artifacts.** Litmus: 158 checked prompting invocations of 77 programs in 7 categories, run under closed/pipe/terminal input with post-checks of the requested action. WaitAtlas: 4,855 commands (1,151 programs, 668 package families) showing pre-launch wait prediction caps at AP 0.477 (pipe) / 0.395 (terminal) even for zero-shot Qwen2.5-32B — so waits must be detected at run time. Tripwire: 25 minimal-pair tasks (database migration, deploy, key rotation, cleanup…) where only the trap variant guards the action behind a question; a hidden final-state verifier scores every run.
- **Receipt.** A harness wrapper that (1) samples syscall + waited-on descriptors + CPU ticks every 0.1 s per thread and confirms a wait after 1 s of silence with ≤5 CPU ticks, excluding foreign descriptors; (2) classifies terminal reads (canonical line, secret no-echo, key-by-key, alternate-screen) and holds agent keystrokes that don't fit the reader's class; (3) orders input/interruption/report via a knowledge-condition automaton (`K(σ) ⇔ c = |E| ∧ (r = blocked ⇒ seen)`) verified by TLA+/TLC (499 states) plus a second finite-state explorer and 30 Docker test cases with real tmux — reproducing 4 of 7 forbidden orders without the rules.
- **Deployment.** The detector was ported to Rust and shipped as an opt-in feature of a commercial document-review agent runtime (Linux + Windows, released 2026-10-09); median check cost 0.11 ms (Windows) / 0.54 ms (Linux) per shell call.

## Methodology

The paper proceeds in three stages. **Measurement (Sec. 2):** witness programs (a heartbeat logger and input witnesses) independently record process behavior under closed, pipe, and terminal input; 8 harnesses are tested for how they launch commands and what they do at the time limit; production timeouts are double-annotated (Cohen's κ = 0.89); 3 public corpora are scanned for non-returning calls, and 123 Terminal-Bench waits are replayed in their own containers. **Repair (Sec. 3):** Receipt keeps stdin open and supplies no reply. Layer 1 identifies a *candidate wait* when a thread's syscall is a read/multiplex call (read, poll, epoll_wait), its descriptors intersect the controlled inputs C (the command's pipe/terminal, which can grow when sudo/script relay it) and no foreign descriptor F is waited on; a candidate becomes *confirmed* after 1 s of no tree output and ≤5 CPU ticks. The returned receipt names the program, the last output line as the prompt, the read class κ, whether Receipt killed the tree, and marks earlier effects unverified. Layer 2 is the terminal protocol: a sender types agent keystrokes, an observer may interrupt; every send must satisfy the knowledge condition (agent has read all receipts, and has seen a blocked reader's question before any answer reaches it) — this is exactly the race where native Terminus 2 feeds a queued `cd` as the migration script's confirmation. Layer 3 verifies Proposition 3.1 (no unseen-question input delivery, no interrupted scheduled input, no stale input after interruption, no stale receipts) with two model checkers (TLA+/TLC over 499 states and a finite-state explorer) and Docker tests with real tmux. **Evaluation (Sec. 4):** Receipt is plugged into two *unmodified* harnesses (mini-SWE-agent 2.4.6 and Terminus 2), compared against closed input, plain terminal, a "Receipt w/o report" ablation (same detector/interruption, single-line notice instead of the full receipt), a text-hint baseline, a verification-instruction prompt, a post-hoc TF-IDF trajectory classifier (Advani et al.), Panthi et al.'s outcome monitor with contracts mined from 3,464 SWE-rebench trajectories, and DeepSeek's process inspector. Tripwire runs use Qwen2.5-Coder-32B at temperature 0 (plus Coder-7B/14B, Qwen2.5-72B, Llama-3.1-70B, and Llama-3.3-70B / Mistral-Small-24B / Gemma-2-27B for rankings), 3 repetitions per variant, with task-paired resampling (20,000 resamples) for significance.

## Results & Highlights

- **Closed input is not safe (Litmus):** 11.5% of prompting invocations (18/156) return status 0 *without* performing the requested action under closed input — `docker system prune` removes nothing, `rm -i`/`rm -I` keep the files, `find -ok` and `tar -w` skip every entry; 12 more act without their confirmation (e.g. ssh-keygen writes a key with an empty passphrase). Under a plain terminal, 123/125 invocations hang instead. 7 of 8 harnesses close input when no terminal is attached (only Terminus 2 does not), and Claude Code's `GIT_EDITOR=true` makes `git rebase -i` squash with status 0.
- **Real-world wait frequency (RQ-2):** across the 3 public corpora (456,085 observed calls), 1,345 calls wait for input, 616 of them inside Web-operations tools (corepack 339, git 127); in Terminal-Bench 2.0, 6.0% of the 205,500 multiplexer calls (56.1% of trials) never return vs only 0.7% under pipes (8.5% of trials). In production, agents issued 2,910 pure liveness-check commands and 27/81 timeouts were agent-written polling loops.
- **Cost of an unanswered question (Tripwire, mini-SWE-agent, 5 LLMs):** trap runs under a plain terminal take 2.6× the run time and **2.9× the tokens** of control runs (10.4M vs a 3.6M-scale control delta); closed input yields the most false successes (34 across 5 LLMs), and a post-hoc trajectory classifier catches only 6 of those 34 at a 10% flag rate.
- **Receipt recovers tasks at lower cost (Table 4, 15 trap pairs × 5 LLMs × 3 reps):** successes rise 153 → 176 vs stock closed input, false successes drop 34 → 9 (**−73.5%**; task-paired 95% CI −11.1 pp [−20.9, −3.1]), median run time 62 s vs 105 s for terminal, and total tokens 7.9M vs 10.4M (**−24.4% vs a plain terminal**). The matched-streams ablation (Table 6) shows the receipt text itself — not just the detector — drives the gain: 161 → 174 trap successes and 20 → 8 false successes vs Receipt w/o report.
- **Detection quality (Litmus, 120 Linux invocations + 119 controls):** Receipt reports 85.0% of tested waits with **0 false positives** on terminal controls (1 on pipe) at 1.1 s median delay, vs 66.7%/68.3% for text baselines; the 1-second inactivity watchdog is as fast but kills 82/119 controls while Receipt kills none. Against DeepSeek's stdin-only inspector at 7 s, Receipt alone confirms 37 invocations, the inspector alone 1 (it misses /dev/tty reads).
- **Baselines (Table 5, Qwen2.5-Coder-32B):** Receipt 45/40 control/trap successes with 1 false success vs text hint 44/41 with 2 (and 51 s vs 109 s median trap run), outcome monitor 41/30 with 6, DeepSeek inspector 40/35 with 3.
- **Leaderboard distortion:** Kendall's τb between the closed-input and terminal rankings of 8 LLMs is only 0.47; Llama-3.3-70B moves 7th → 3rd, Gemma-2-27B's trap successes jump 9 → 31 from closed input to Receipt w/o report.
- **Persistent terminal fixed (Terminus 2, all 25 pairs):** native Terminus completes 17 trap tasks (3 false successes) because it types the agent's queued keystroke as the answer; with Receipt it completes **25/25 with 0 false successes** (control 25/25).
- **Deployment overhead:** in the commercial runtime, detector checks took a median of 0.11 ms (Windows, 1,436 calls) and 0.54 ms (Linux, 149 calls) per shell call.

## Authors & Credibility

A mixed academic–industry team: Boyang Yang, Ziyao Yang, and Yu Zhang (Yanshan University), Duo Chai (Tencent), Xiaoming Chen (Shenzhen Intelligent Strong Technology), and Haoye Tian (Aalto University, correspondence). The first author has directly relevant prior work — a survey of LLM-based program repair, repository-aware repair, and "Do tool calls execute as intended?" (arXiv:2610.04375) on intent-execution correspondence — so the return-assumption framing is a natural, credible continuation rather than a one-off. Methodological credibility is high: two independent model checkers agree on the protocol, Docker tests with real tmux reproduce forbidden orders without the rules, production timeouts are double-annotated (κ = 0.89), the detector was frozen before the last 10 of 25 Tripwire pairs were written (to mitigate benchmark–detector co-design), temperature 0 with 3 repetitions and task-paired bootstrap CIs are used, and the system is actually deployed (Rust port in a commercial runtime since 2026-10-09, plus a rule-only hook over 11,694 shell calls in the author's own Claude Code). All dangerous programs ran in containers without network access.

## Critical Assessment

- **Novelty: genuinely strong.** No prior work measures how often agent commands wait on input in the wild, and the observation that the harness's input connection (not just the LLM) determines leaderboard order — moving Llama-3.3-70B from 7th to 3rd — is a real, quantified contribution. The distinction from DeepSeek's stdin-only inspector and output-text detectors (misses questions on /dev/tty, e.g. passphrases) is concrete and empirically demonstrated (37 vs 1 confirmations at 7 s).
- **Rigor: above average, with two soft spots.** (1) The Terminus-2 headline ("completes all 25 trap tasks, 0 false successes") rests on single runs (each variant once, 600 s limit) — no repetitions, no variance, unlike the 3-rep mini-SWE-agent protocol. (2) The production corpus is 6 developers at the authors' own company and is not released (privacy), so the 91,469-call measurement — the paper's real-world anchor — cannot be independently verified.
- **Benchmark–detector co-design risk.** The first 15 Tripwire pairs were written with knowledge of the detector; freezing the detector before the last 10 pairs (all completed on Terminus 2) mitigates but does not eliminate this — the benchmark's tasks (confirmation prompts, passphrases, pagers) are exactly the waits Receipt detects by construction.
- **The token-saving headline needs careful reading.** The 24.4% saving is relative to a *plain terminal* (10.4M → 7.9M tokens); relative to closed input, Receipt uses ~80% *more* tokens (4.4M → 7.9M). That trade is legitimate — closed input is cheap precisely because it skips actions and produces false successes (34) — but a skimmer of the abstract could read "24.4% fewer tokens" as a pure win over the default condition.
- **Detection blind spots are paper-specific and acknowledged:** of 18 unreported Litmus waits, 3 are npm commands that draw a spinner while waiting (the 1-s no-output + ≤5-CPU-tick confirmation fails on any progress output), and 15 of the 18 exit or act under Receipt's own launch — so the 85.0% report rate is conditioned on Receipt's launch environment. The 0.1 s sampling and 1 s confirmation also mean sub-second or chatty waits are structurally missed. The Windows backend is validated on only 26 native cases.
- **Reproducibility:** Litmus/WaitAtlas/Tripwire and the TLA+ specs are described in enough detail to rebuild; harness versions and commits are pinned (e.g. DeepSeek inspector at commit d743267, Claude Code 2.1.292); no code link is visible in the text I read, which tempers the release claim ("release its detector in a commercial agent runtime" is a product feature, not an artifact drop).

## Strengths

- First to define, measure at scale (production + 89k public trajectories + 8 harnesses), and repair a failure mode that every shell-driven agent has but no benchmark scores.
- Minimal-pair benchmark design (trap vs control differing in exactly one change) makes the causal cost of a question cleanly measurable — a methodological template other agent-evaluation papers should copy.
- The Receipt w/o report ablation isolates the value of *what the agent reads* (161→174 successes, 20→8 false successes), and the matched-streams variant rules out the pipe-vs-terminal confound.
- Model-checked intervention protocol (TLA+/TLC, 7 invariants, counterexamples when rules are removed) instead of ad-hoc synchronization — rare rigor for an agents paper.
- Real deployment with per-call latency (≤0.54 ms median) rather than a prototype-only evaluation; honest threats-to-validity section including the benchmark-co-design concern.

## Limitations

- Tripwire is small (25 pairs) and self-authored; gains are measured mostly with Qwen-family and Llama-3.x models (8 LLMs total, no frontier closed models), all at temperature 0 with a 30-step budget.
- Terminus 2 results are single-run; the production measurement (6 developers, one company, unreleased logs) limits external validity of RQ-2.
- The wait detector assumes quiet waits: spinner/progress output (npm) and sub-second waits defeat it; 15% of Litmus waits go unreported.
- Linux-centric implementation (syscall sampling); Windows support validated on only 26 cases; macOS not addressed.
- Receipt costs more tokens than closed input (~4.4M → 7.9M across 5 LLMs) — the right trade when actions matter, but not free; and its interruption kills the local process tree, so long-running interactive sessions lose state unless deployed in report-only mode.

## Relevance

对研究 LLM Agent 工具调用可靠性与评测的读者高度相关：它量化了"假成功"这一 Agent 落地 Web 运维时的真实故障模式，并证明 harness 的输入连接方式会系统性扭曲 LLM 排行榜——这对任何构建或评测 shell 驱动 Agent（含 coding agent benchmark）的工作都是必须知道的偏差来源。

## Questions for Further Exploration

- How does Receipt interact with agents that already use structured tool-output parsing or retry heuristics — does the receipt format generalize to non-shell tools (HTTP APIs that block on confirmation tokens)?
- Would frontier closed models (GPT-5-class, Claude-class) show the same 73.5% false-success reduction, or do they already infer waits from silence in the tool output?
- Can the 1-s-quiet + ≤5-tick confirmation rule be replaced by a spinner-aware heuristic (e.g. detecting cursor-escape output) to recover the remaining 15% of Litmus waits, including the 3 npm cases?
- Since Kendall's τb between launch conditions is only 0.47, what would a "harness-normalized" Terminal-Bench 2.0 leaderboard look like — and should benchmarks report the input connection as a first-class experimental variable?
- Does returning process state (rather than fixing the harness) transfer to the async/function-calling setting, where the analogous assumption is that a returned call id implies a started job?
