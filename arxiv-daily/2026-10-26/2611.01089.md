> **一句话总结：** 本文提出 Scute——在 vLLM 之上通过一个六"槽位"(slots) 的 LoRA 规范形 (normal form) 加三条计算"路由"(routes)，使 DoRA、(IA)³、VeRA、OFT 等非 LoRA 的 PEFT 适配器能与 LoRA 在同一批次内被**精确**服务：相比 PEFT 参考库任务精度偏差 ≤0.4 分，混合五方法仅比纯 LoRA 多花 5–17% 的解码时间，而把 (IA)³ 转换为 rank-64 LoRA 在 MNLI 上会损失 23.2 个百分点；单张 RTX A6000 可服务 1024 个 (IA)³/VeRA 租户，可持续请求速率是其 LoRA 转换版的 1.5–2.5 倍以上。

> **TL;DR:** Production multi-tenant LLM engines (vLLM, SGLang, Punica, S-LoRA) batch many LoRA adapters but reject DoRA, (IA)³, VeRA and OFT at load; converting them to LoRA is lossy — on MNLI, an (IA)³ adapter converted to rank-64 LoRA by SVD drops from 90.2% to 66.6% (−23.2 points), and a rank-256-exact VeRA conversion costs 21.47 GB/step vs 1.19 GB for Scute's exact route. Scute expresses all five methods in one six-slot normal form around the shared GEMM, proves a fold rule for which slots can merge into adapter weights at load (DoRA's scale never folds — W·diag(s−1) is full numerical rank on 60/60 projections of Llama-3.1-8B), and pays the remaining live slots via three routes whose cost a zero-parameter byte model predicts to within 0.7–14%. Built as a runtime patch on vLLM 0.19.1 (no fork), it matches the Hugging Face PEFT library within 1.5% of each adapter's effect and 0.4 accuracy points; a burst mix of 4–5 methods costs only 5–17% more decode time than the same number of rank-16 LoRA adapters, and 64–1024 (IA)³/VeRA tenants sustain 1.5×–≥2.5× the request rate of their LoRA conversions (2.01× throughput at 1024 tenants, 932 vs 464 tokens/s).

## 核心贡献

- **规范形 (normal form) 与折叠规则 (fold rule)**：用一个带六个"槽位"的公式覆盖 LoRA、DoRA、(IA)³、SSF、VeRA、OFT——基座路径上的输入变换 R、输出缩放 s、输出平移 b，以及每个低秩项上的内向量 d、外向量 e、标量 c。折叠规则 (Proposition 1) 严格刻画了哪些槽位可在加载时并入适配器自身权重 (折叠、零服务成本)，哪些必须保持"活跃"逐 token 计算；并证明 DoRA 的缩放 s 无法精确折叠 (W·diag(s−1) 在 Llama-3.1-8B 全部 60/60 个被适配投影上均为满秩，最优 rank-16 近似仍残留 ≥59.7% 的 Frobenius 范数)。
- **三条路由 + 零参数字节模型**：活跃槽位有三种支付方式——(1) 在 expand 核内顺带施加 s (每次迭代只多读 ≤k·d_out 个元素)；(2) 用两个按行分块的 GEMM 计算 VeRA 共享因子项，使共享因子每步只读一次、与租户数无关；(3) 在共享 GEMM 之前用独立 pass 施加 OFT 的块对角旋转 R。基于带宽的字节模型 (t = t₀ + ΔQ/β + ΔL·λ，无拟合参数) 预测每条路由的耗时，实测中位误差 0.7%–14%。
- **编译器 + 运行时补丁，不 fork vLLM**：准入编译器把 PEFT 库 checkpoint 编译为规范形，运行时补丁把三条路由接入 vLLM 的 LoRA 路径；支持 CUDA graphs、torch.compile 与张量并行，调度器/分页/注意力完全不动。代码开源 (github.com/ThomasWalker1/Scute-deploy)。
- **精确且便宜的混合服务**：五方法同批服务，与 PEFT 库的平均误差 ≤1.5% (以"适配器效应"计)、任务精度差 ≤0.4 分；突发负载下混合方法池只比纯 LoRA 多 5–17% 解码时间；1024 个 (IA)³/VeRA 租户在单张 RTX A6000 上的可持续请求速率是其 LoRA 转换的 1.5–≥2.5 倍，吞吐 2.01×。
- **栈式适配器**：证明两个规范形成员的复合 (如 LoRA 叠加在 (IA)³ 之上) 仍是规范形成员，可作为同一段 (segment) 运行而不增加 kernel 启动；并指出复合顺序在 s≠1 时会影响语义。

## Key Contributions

- **A normal form with six slots and a fold rule**: one formula (base path: input transform R, output scale s, output shift b; each low-rank term: inner vector d, outer vector e, scalar c) expresses LoRA, DoRA, (IA)³, SSF, VeRA and OFT. Proposition 1 gives exact conditions for a slot to fold (merge into adapter-owned weights at load) — and proves s, b, R never fold because only the shared W sits next to them. Corollary 1 + App. B show an exact fold of DoRA's scale would need rank ≥ rank(W·diag(s−1)): measured full numerical rank on 60/60 adapted projections of Llama-3.1-8B, with the best rank-16 approximation leaving ≥59.7% of the squared Frobenius norm — so a batched engine must keep s live.
- **Three routes for live slots, priced by a zero-parameter byte model**: (i) carry s inside vLLM's expand (one extra read of ≤ k·d_out elements per step); (ii) compute VeRA's shared-factor term with two row-tiled GEMMs so the shared A, B are read once per step regardless of tenant count (Proposition 2(iv)); (iii) apply OFT's block-diagonal R in a dedicated pass before the shared GEMM. The byte model t = t₀ + ΔQ/β + ΔL·λ (β = 680 GB/s DRAM, β_L2 = 3205 GB/s, λ = 0.96 µs/launch on RTX A6000) predicts route time with 0.7%–14.0% median error where bytes dominate, and explains the 2.38×–2.95× cost of the alternative DoRA patch in an open vLLM PR (Proposition 2(ii) predicts ~3×).
- **A compiler + runtime patch instead of a fork**: an admission compiler turns PEFT-library checkpoints into the normal form under vLLM's tensor names; a runtime patch hooks vLLM 0.19.1's loader, packer and layer-apply. Scheduler, paging, attention and batch composition are untouched; CUDA graphs, torch.compile (Triton kernels registered as custom ops) and tensor parallelism all work. Released with tests and examples.
- **Exact, cheap mixed-method serving**: matches the PEFT library with mean error ≤1.5% of each adapter's effect (validated with amplified adapters in a 9-adapter batch) and within 0.4 accuracy points for 15 trained adapters served in one batch; a burst mix of 4–5 methods costs 5–17% more decode time than the same number of rank-16 LoRA tenants; 64–1024 (IA)³/VeRA tenants sustain 1.5×–≥2.5× the request rate of their LoRA conversions on one RTX A6000.
- **Stacking composition**: applying two members at one hook (e.g., a tenant's LoRA on top of (IA)³) is again a member — one segment, no extra launch — with an explicit caveat that order matters when one member has s ≠ 1.

## Methodology

The paper proceeds in three layers — theory, cost model, system — each validated separately.

1. **Normal form (§3)**. Every considered PEFT method rewrites each adapted projection ("hook") as F_a(x) = (xR)W ⊙ s + b + Σ_k c_k((xA_k) ⊙ d_k)B_k ⊙ e_k. Each of the six slots defaults to the identity; a method is a member iff (1) can express it (Table 1 maps all five: e.g., (IA)³'s learned vector on the FFN up-projection is the slot s, using (σ(xW_g) ⊙ xW_u) ⊙ l = σ(xW_g) ⊙ (xW_u ⊙ l); OFT's Cayley rotation is R). The fold rule (Proposition 1, App. A) states a slot folds iff the adapter owns an adjacent matrix/vector; the identities (xA) ⊙ d = x(A diag d), etc., prove sufficiency, and a rank argument proves necessity. Corollary 1 quantifies what exact folding of s would require, and App. B measures it on four public DoRA fine-tunes: g deviates from 1 by only ~0.2% RMS yet W·diag(g−1) is full rank, so folding would force one copy of W per tenant.

2. **Routes and the byte model (§4)**. Because adapter passes move far more bytes than they compute, cost is counted in bytes (a roofline argument). Three routes cover the live slots: route 1 piggybacks s on the expand pass the schedule already runs; route 2 replaces the segmented per-adapter traversal of VeRA's shared factors with two GEMMs over row tiles (factors read once per step); route 3 gives OFT's R its own pre-GEMM pass (2N·d_in extra elements + blocks). Table 2 compares these against LoRA conversion bytes for Llama-3.1-8B, 16 tenants: e.g., VeRA route 2 = 1.19 GB vs 21.47 GB for its exact rank-256 conversion. The byte model t = t₀ + ΔQ/β + ΔL·λ is tested on OFT's transform and four DoRA-scale routes (Fig. 2), with median error 0.7%–14%.

3. **Scute (§5) and evaluation (§6)**. The admission compiler maps each checkpoint to the normal form (DoRA's s = m ⊘ ‖W + cAB‖_c computed at admission in the engine's own fused/sharded layout; methods without a low-rank term get a zero rank-one term so vLLM's loader accepts them). The runtime patch adds the routes as Triton custom ops. Evaluation: vLLM 0.19.1 + Llama-3.1-8B fp16, CUDA graphs and torch.compile on; fifteen adapters trained with PEFT library v0.20 (LoRA/DoRA rank 16 α=32; VeRA rank 256; OFT blocks of 32; (IA)³ default hooks) on GSM8K, MNLI, BoolQ. Four engines are compared under identical device memory (Scute gets 0.83 vs 0.90 of GPU memory, since its slot buffers sit outside vLLM's budget): Ours (exact normal form), Stock (vLLM with rank-64/256 LoRA conversions), LoRA-only (same number of rank-16 LoRA tenants), and the base model. Loads: 256-token prompts/8 outputs (prefill-heavy) and 8-token prompts/128 outputs (decode-heavy), Poisson arrivals or all-at-once bursts, round-robin or Zipf tenant popularity; median of per-repetition ratios over six repetitions (three for many-tenant pools); repeated on an A100-SXM4-80GB. Serving cost uses synthetic tenants with trained-adapter shapes; accuracy uses the 15 trained adapters plus SVD/ASVD/distillation conversions.

## Results & Highlights

- **Exactness (vs Hugging Face PEFT library)**: with 9 amplified adapters of all five methods in one batch, mean error is 0.3%–1.5% of each adapter's effect on log-probabilities (float32 reference); across all fifteen trained adapters served together, every task metric stays within 0.4 points of the PEFT library (Tables 3/A4), e.g., (IA)³ GSM8K 59.8% +0.4, OFT GSM8K 63.0% +0.2, VeRA MNLI 90.9% +0.1.
- **Conversion to LoRA is lossy**: truncated SVD of the exact update falls >3 points below the PEFT library in 9 of 12 (IA)³/OFT cases at ranks 16 and 64; the worst case is (IA)³ on MNLI at rank 64: 90.2% − 23.2 = 66.6% (SVD), and activation-aware SVD fitted on generic text (ASVDg) loses up to 19.6 points ((IA)³ GSM8K 59.8 → 40.2); a rank-16 VeRA conversion loses up to 18.5 points (MNLI 90.9 → 72.4), while Scute's error is +0.1. DoRA converts within noise (scale deviates from 1 by median 0.22% over columns, 144/149 public DoRA adapters on HF Hub within 1% median deviation).
- **Byte-level cost (Llama-3.1-8B, 16 tenants, fp16, per decode step, Table 2)**: VeRA route 2 reads 1.19 GB (1.75 ms) vs 21.47 GB (31.58 ms) for its exact rank-256 LoRA conversion — an 18× byte reduction; (IA)³ route 1 reads 0.01 GB (0.01 ms) vs 1.88 GB (2.76 ms) for a rank-64 conversion that is still inexact.
- **Per-tenant cost (Fig. 3)**: growing VeRA tenants 1→16 with all adapters resident, Scute stays nearly flat at 35.4→36.1 ms/token while the rank-256 conversion grows 36.7→65.1 ms (1.80× Scute); at 16 tenants the rank-64 conversions of (IA)³ and OFT each take 1.23× Scute's time (OFT 1.34× on vLLM as shipped). Each Scute tenant adds 0.05–0.16 ms/token vs the byte model's prediction-matched growth for conversions.
- **Mixed pools under burst (Table 4, RTX A6000)**: the five-method 20-tenant pool takes 1.17× the decode time and 1.18× the TTFT of LoRA-only (four-method no-VeRA pool: 1.05×/1.04×) — the 5–17% headline; conversions take 1.65× (VeRA@256) / 1.12× (VeRA@64) Scute's decode time, and vLLM as shipped takes 1.21×–1.98× Scute at every arrival rate (2–16 req/s). Padding to the pool's largest rank explains much of this: conversion bytes at their own ranks would be 13.0 ms/step but padding raises this to 31.6 ms vs 34.7 ms measured.
- **Many tenants (Fig. 4)**: with 64/256/1024 (IA)³+VeRA tenants on one RTX A6000 under an SLO (TTFT ≤1 s, ≤100 ms/token), Scute sustains 10/8/6 req/s vs 4/4/4 for rank-64 conversions (1.5×–≥2.5×, a lower bound since the 64-tenant case maxes out the tested rates); at 1024 tenants and 8 req/s, 82% of Scute's requests meet the target vs 9% for stock, throughput is 932 vs 464 tokens/s (2.01×), and stock's mean TTFT is 65× Scute's. Scute holds all 1024 adapters resident (a few MB each) with a 98k-token KV cache; stock holds only 64 conversions with 28k.
- **A100-SXM4-80GB (§6.6)**: results replicate — stock takes 1.12×–1.69× Scute's TPOT in mixed pools (1.83× with 16 VeRA tenants), OFT/(IA)³ conversions 1.31×/1.34× at 16 tenants; at 64 tenants Scute sustains 20 req/s vs 8. The one cell where stock wins: prefill-heavy mean TTFT can be 0.76× Scute's on the A100.

## Authors & Credibility

Thomas Walker and Richard Baraniuk are at Rice University (Baraniuk is a highly cited figure in signal processing and compressed sensing; the group has prior systems+ML work). The paper is a preprint (31 Oct 2026, cs.LG) with code, tests and examples released at github.com/ThomasWalker1/Scute-deploy, and it builds on a real production engine (vLLM) rather than a toy. The methodology shows unusual care for a systems paper: amplified adapters to make exactness measurable, per-method learning-rate selection on held-out loss, per-repetition ratio medians with engine order balanced across repetitions, a controlled "same GEMM path" comparison isolating the adapter cost from an unrelated fused-GEMM speedup they discovered (split GEMM 26.8 vs 30.6 ms/token), and explicit device-memory equalization (0.83 vs 0.90) to keep the comparison fair. The AI-usage disclosure (Claude Code for code, benchmarking, plotting, and drafting under author direction) is transparent and increasingly standard. Funding: ONR, DOE, DOI, and a Google Cloud award.

## Critical Assessment

- **Novelty**: genuine and well-scoped. PetS (USENIX ATC '22) already served multiple PEFT methods over one shared model, but with per-task custom operators; Scute's contribution is running every method inside the *same batched LoRA kernels*, with a formal fold rule and a predictive cost model — that combination is new, and the proof that DoRA's scale cannot be folded without per-tenant W copies (Corollary 1 + the 60/60 full-rank measurement) is a nice negative result that justifies the whole live-slot machinery.
- **Rigor**: strong on measurement hygiene (medians of per-repetition ratios, order-balanced engines, memory equalization, six repetitions, two GPUs, burst + Poisson + Zipf). The exactness check via amplified adapters is a thoughtful solution to "trained vectors are close to identity so errors are invisible." The byte model has zero fitted parameters and its 0.7–14% error is honestly reported rather than oversold.
- **Reproducibility**: good — public code with tests, exact versions pinned (vLLM 0.19.1, PEFT 0.20, fp16, CUDA 12.2), full training hyperparameters in App. D, and every conversion variant (SVD/ASVD/ASVDx/ASVDg/distillation at ranks 16/64) tabulated in App. C. One friction point: vLLM 0.19.1 is an old release chosen because of the authors' CUDA 12.2 driver, so numbers may shift on current vLLM, whose LoRA kernels have evolved since.
- **Significance**: the multi-tenant PEFT-serving problem is real (platforms reject non-LoRA checkpoints today), and the 1024-tenant result (1.5–≥2.5× sustainable rate, 2.01× throughput) is a large practical win for vector-style methods. However, the headline "5–17% more decode time than LoRA" applies to a *burst* of 20 mixed tenants; the per-tenant increments (0.05–0.16 ms/token) matter most in exactly the many-tenant regime the paper studies, so scope and claims line up reasonably.
- **Red flags / weak spots**: (1) **single base model** — everything is Llama-3.1-8B in fp16; no Qwen/Mistral/MoE, no bf16/fp8, no non-Llama architectures where hook layouts differ. (2) **Synthetic serving tenants**: serving-cost experiments use synthetic tenants with trained-adapter shapes, not real trace-driven tenant mixes; the many-tenant pools are only (IA)³+VeRA (the two cheapest methods), so OFT/DoRA scaling to 1024 tenants is untested. (3) **Accuracy evidence is thin**: 15 adapters across 3 tasks (GSM8K/MNLI/BoolQ), tasks where several methods sit within ~1 point of the base model on 2 of 3 datasets (BoolQ base 74.0% vs adapted ~88–90%), so "within 0.4 points" is a weak stress test of exactness at the metric level — the amplified-adapter log-prob check carries the real weight. (4) **Missing ablations**: no breakdown of the 1.17× five-method overhead per route on the A100 (only aggregate numbers), no measurement of admission-compiler load time (DoRA's s needs the full W at admission), and stacking is proven but never benchmarked end-to-end. (5) **Fairness caveats acknowledged but worth flagging**: Scute gets 0.83 of device memory vs 0.90 for baselines (equalizing total usage), and on A100 prefill-heavy load stock's mean TTFT is 0.76× Scute's — the exact-engine win is not universal across load types. (6) SSF is excluded (absent from PEFT 0.20), BOFT's multi-factor extension is unimplemented, and HiRA/full fine-tuning are out of the normal form — coverage is five methods, not "all PEFT".

## Strengths

- Turns an ad-hoc engineering question ("which PEFT methods can we serve?") into a clean formalism (normal form + fold rule) with proofs, and derives the serving design from it rather than from benchmark tuning.
- The zero-parameter byte model is genuinely predictive (0.7–14% median error) and retrodicts third-party choices — it correctly predicts that an open vLLM DoRA PR's after-expand scale pass costs ~3× LoRA's expand (measured 2.38×–2.95×), while carrying s in the expand is ~free (0.985×–1.022×).
- Practical, deployable artifact: a runtime patch (no fork) on a production engine, keeping CUDA graphs, torch.compile and tensor parallelism intact, with released code, tests and examples.
- Honest, well-controlled evaluation: same-GEMM-path isolates confounds, memory budgets equalized, results replicated on a second GPU, and negative cells reported (stock's better A100 TTFT).
- The many-tenant result is substantial: 1024 exact adapters resident with a 98k-token KV cache on one 48 GB GPU, 2.01× the throughput of rank-64 conversions at 8 req/s.

## Limitations

- Single base model (Llama-3.1-8B) and precision (fp16); no evidence yet for other architectures, MoE models, or quantized serving.
- Serving costs use synthetic tenants with real adapter shapes rather than production traces; the 1024-tenant pools include only (IA)³ and VeRA, the two most slot-friendly methods.
- Accuracy deltas rest on 15 adapters over 3 tasks, two of which have high baselines that compress differences; exactness at the metric level is therefore a weak signal compared to the log-probability check.
- Coverage gaps: SSF unimplemented (missing from PEFT 0.20), BOFT needs an unimplemented multi-transform extension, HiRA and full fine-tuning fall outside the normal form (they need per-adapter dense matrices).
- Admission cost is not reported: DoRA's scale is computed from the full base weight at admission (in-engine layout), which could matter for platforms churning many adapters; stacking is formalized but not benchmarked.
- Built on vLLM 0.19.1 due to the authors' CUDA 12.2 driver constraint; kernel-relative numbers may not transfer to newer vLLM/SGLang LoRA stacks, and the SGLang path is untested.

## Questions for Further Exploration

- How do the route costs and the byte model transfer to newer vLLM/SGLang kernels (e.g., FlashInfer's latest SGMV), to quantized bases (fp8/int4 AWQ), and to MoE models where hooks sit inside experts?
- Can the normal form be extended to HiRA or full fine-tuning deltas approximated by BitDelta-style compression, i.e., does a "compressed slot" preserve exactness under a byte budget?
- What is the admission-compiler cost at scale — how long does computing DoRA's s from the full base weight take, and does it bottleneck platforms that hot-swap thousands of adapters per hour?
- Does stacking (e.g., tenant LoRA over shared (IA)³) change the 5–17% mixed-pool overhead, and can the scheduler exploit stack sharing across tenants?
- Would trace-driven tenant mixes (real popularity distributions beyond Zipf, heterogeneous prompt lengths) shift the 1.5–2.5× sustainable-rate advantage, especially for OFT-heavy pools that were not tested at 1024 tenants?
