> **一句话总结：** 在 B200 GPU 上用 verl（Megatron/Transformer Engine 训练 + vLLM/SGLang 采样）实现端到端 MXFP8 强化学习（Qwen3-8B 与 Qwen3-30B-A3B），实测表明：让采样器使用学习器自己的量化网格（shared-grid 权重同步）比 BF16 采样器的 train–rollout KL 低 16%（固定权重、逐 prompt 配对），MoE 上整步提速 10.7%、生成提速 23.8%；但 MXFP8 每个 micro-batch 附加约 47–51 ms 的主机侧固定开销，每 micro-batch 约 4.5k token 以下反而比 BF16 慢，且作者在真机上遇到的 7 个权重同步失效中 5 个是静默失败（exit code 0、指标看起来正常）。

> **TL;DR:** A single-author measurement study of end-to-end MXFP8 RL on B200 GPUs (verl + Megatron/Transformer Engine learner, vLLM/SGLang samplers, Qwen3-8B dense and Qwen3-30B-A3B MoE, GRPO on gsm8k and DAPO-Math-17k). Three results: (1) Consistency — for an MXFP8 learner, a sampler quantized with the learner's own quantizer ("shared grid") beats a higher-precision BF16 sampler: at fixed weights on gsm8k, train–rollout KL is 0.00682 vs 0.00812 (−16.1%, 95% CI 14.1–18.1), and the synchronized weights match the learner's FP8 forward weights byte for byte (0 of ~600 MB differ); late in training it beats a per-tensor FP8-TW/BF16 baseline by 43–70% KL, but that baseline drifts. (2) Speed — MXFP8 adds ~51 ms host-side cost per micro-batch and saves ~11 µs/token, so it breaks even only above m* ≈ 4.5k tokens/micro-batch (95% CI 4.3–4.8k): on MoE DAPO-Math-17k (12.3k tokens/micro-batch) step time drops 10.7% and generation 23.8% vs BF16, while a short-sequence dense gsm8k workload is 5.1% slower. (3) Correctness — seven conditions a weight sync must preserve; all seven real failures on B200 broke one condition, five silently, and complementary run-time guards (kernel self-check, engine-state audit, step sentinel) caught the silent ones. All runs are single-seed and ≤60 steps; no claims about final model quality.

## 核心贡献

- **首个对端到端 MXFP8 RL 的系统化测量**（在 Blackwell B200 上，verl + Megatron/Transformer Engine 训练、vLLM/SGLang 采样，稠密与 MoE 模型），把"匹配买什么、什么时候回本、怎么失效"三个工程问题变成可量化的结论，而非仅可行性报告。
- **Shared-grid 权重同步**：每个 optimizer step 后用学习器自己的 TE MXFP8 量化器（E4M3、1×32 块、E8M0 scale）量化权重发给采样器；字节级比对确认采样器收到的权重与学习器前向 GEMM 的 FP8 权重完全一致（0/~600 MB 差异；TE 与 vLLM 量化器在全部 252 个线性矩阵、69.5 亿元素上逐字节一致）。
- **一致性的受控实验**：单引擎、固定权重（lr=0）、相同 prompt 下，KL 随采样器落在学习器网格上的线性层比例单调下降（BF16 采样器 0.00812 → 半匹配 0.00726 → 全匹配 0.00682，降幅 10.6% / 16.1%，配对 bootstrap 95% 置信区间不含零）。
- **低精度 RL 训练的 break-even 模型**：每个阶段时间拟合为 t = F + cT，证明附加固定成本是"每 micro-batch"而非"每 step"（m* = Δδ/Δc ≈ 4.5k token/micro-batch），并在固定数据的 micro-batch 扫描 + 留出工作负载上验证；Nsight 追踪显示附加时间 86% 是 GPU 空等主机（912 次额外 kernel launch）。
- **训练–推理边界的正确性规范**：7 条权重同步必须保持的条件（C1 层集合 … C7 可观测性），3 个运行时守卫 + 108 个 CPU 故障注入测试（已合入 verl，PR #7986/#7987/#8062）；真机上 7 个失效每个恰好破坏 1 条条件，其中 5 个静默，守卫互补捕获。
- **学习动力学观察**：MXFP8 下策略熵持平或上升（DAPO 上 +4%/MoE +6%），而 FP8-TW 熵暴跌 74% 且训练奖励虚高（0.240 vs BF16 0.150）——量化配方会改变探索/收敛轨迹，步数对齐的 checkpoint 不可跨配方比较。

## Key Contributions

- First systematic measurement (not just a feasibility report) of end-to-end MXFP8 RL on Blackwell B200: verl + Megatron/Transformer Engine learner, vLLM and SGLang samplers, dense (Qwen3-8B) and MoE (Qwen3-30B-A3B) models, GRPO with verifiable rewards.
- **Shared-grid weight synchronization**: at every optimizer step, weights are quantized with the learner's own TE MXFP8Quantizer (E4M3, rowwise, 1×32 blocks along K, E8M0 power-of-two scales) and streamed to the sampler, so the sampler receives exactly the learner's forward weight grid. A byte-level comparison confirms the engine's weights, kernel layouts, and the learner's cached forward weights are identical: 0 of ~600 MB differ; TE's and vLLM's quantizers agree byte for byte on all 252 linear matrices (6.95B elements).
- **A controlled matching experiment**: one engine (vLLM), learning rate 0 (identical weights every step), same 576 prompts across arms — KL falls monotonically as more of the sampler's linear layers join the learner's grid: 0.00812 (BF16 sampler) → 0.00726 (gate_up_proj off-grid) → 0.00682 (all on grid), i.e. −10.6% and −16.1% vs the BF16 sampler (paired bootstrap 95% CIs 8.6–12.7% and 14.1–18.1%).
- **An empirical break-even model for low-precision RL**: each stage's time is fit as t = F + cT; the added fixed cost is shown to be per micro-batch (~51.5 ms for update, ~12 ms forward-only), giving a threshold m* = Δδ/Δc ≈ 4.5k tokens per micro-batch (95% CI 4.3–4.8k). Confirmed four ways: a micro-batch sweep on replayed identical data, within one run (update stage below m* is slower, old-log-prob above m* is faster, same run), a held-out workload (per-micro-batch model predicts B's savings within 0.1–4.0 pts vs missing by 4.1–9.0 pts for a per-step model), and a host-speed dependence (net loss on a slower CPU).
- **Profiling where the cost goes**: Nsight Systems shows MXFP8 launches 912 extra kernels per micro-batch (325 quantization + 576 block-scale rearrangements); of the +43.4 ms added wall time, GPU busy time grows only +5.9 ms (14%) while 37.4 ms has no GPU operation running at all — 30.6 ms waiting for the host to issue the next operation. The GPU is busy only 37% of the stage under MXFP8 (44% under BF16).
- **A correctness specification for the train–inference boundary**: seven conditions (C1 layer set, C2 weight grid, C3 derived kernel state, C4 CUDA-graph storage identity, C5 streamed-update completeness, C6 output sanity, C7 observability) with three run-time guards (per-sync kernel self-check, quantized-layer audit against the engine's live parameters, step sentinel) and 108 CPU fault-injection tests upstreamed to verl. Each of seven real failures on B200 broke exactly one condition; five were silent (exit code 0, normal-looking metrics); the guards are complementary — the audit alone caught F2, the self-check alone caught F4.
- **Learning-dynamics finding**: under MXFP8 the policy entropy stays flat or rises while under FP8-TW it collapses (−74% in 32 steps on DAPO-Math-17k) alongside an inflated training reward — recipe changes move the exploration trajectory, so step-matched checkpoints from different recipes are not comparable.

## Methodology

The author implements the full pipeline in verl: a Megatron-Core + Transformer Engine learner with BF16 master weights/FP32 optimizer states whose decoder linear GEMMs (fprop, dgrad, wgrad) run MXFP8 (E4M3 elements, 1×32 blocks, E8M0 scales applied inside Blackwell's block-scaled MMA instructions); embedding, lm_head, MoE router, norms, and attention stay in high precision. Sequence padding changes from lcm(16,·) to lcm(32,·) because MXFP8 wgrad scale blocks run along the token dimension.

At every synchronization, (Wq, s) = Q(W) with Q the learner's TE quantizer; for vLLM the quantization runs inside the worker process, for SGLang on the trainer side. Serving engines rewrite weights/scales into kernel-specific layouts at load (FlashInfer scale swizzling, TRT-LLM MoE expert shuffling); a "refit cycle" (record → stage → load → reprocess → fold) rebuilds these derived layouts in place after each sync so CUDA-graph-captured addresses stay valid. Two MoE-specific repairs were upstreamed to verl (#7986 same-shape repack detection, #7987 in-place staging).

Four experimental settings on B200 (CUDA 13.0, PyTorch 2.11, TE 2.16.1, vLLM 0.24.0, SGLang 0.5.12): A = Qwen3-8B on gsm8k (vLLM, 60 steps), B = Qwen3-8B on DAPO-Math-17k with 8192-token responses and FP8 KV cache, C = gsm8k with SGLang, D = Qwen3-30B-A3B MoE on DAPO-Math-17k (4 GPUs, CPU optimizer). All use GRPO (64 prompts × 8 samples, lr 1e-6, KL 0.001), same seed/data order per setting. Arms span BF16/BF16, FP8-tensorwise/BF16, MXFP8/BF16, MXFP8/MXFP8 (shared grid), and FP8-blockwise/FP8-blockwise (mismatched grids on SM100).

Consistency is measured with verl's rollout_corr diagnostics (KL, χ², log-perplexity gap, Pearson correlation) anchored at step 1 (all arms hold identical weights); a controlled matching experiment (lr 0, paired prompts, bootstrap CIs) isolates the sampler's effect; a byte-level comparison verifies C2 offline. Speed is measured by regressing stage time on tokens per step (t = F + cT, exploiting RL's natural token-count variation), a controlled micro-batch sweep on replayed identical data (1/2/4/8 sequences), and Nsight Systems traces. Correctness is grounded in seven conditions, three run-time guards, evidence from seven real failures, and CPU fault-injection tests with a specified hardware injection protocol.

## Results & Highlights

- **Matching beats a higher-precision sampler (controlled, fixed weights, Qwen3-8B/gsm8k, 576 paired prompts)**: train–rollout KL (rollout_corr/kl) is 0.00682 with every decoder linear on the learner's grid vs 0.00812 with a BF16 sampler (**−16.1%**, 95% CI 14.1–18.1) and 0.00726 half-matched (**−10.6%**, CI 8.6–12.7); fully matched is 6.1% below half-matched (CI 3.9–8.3). Late in training the shared-grid pipeline lowers last-10-step KL vs the FP8-TW/BF16 baseline by **43% (A/gsm8k), 70% (B/DAPO), 46% (C/SGLang), 23% (D/MoE)** — but most of that margin is the per-tensor baseline's own drift (its KL rises 3.1× in B, 0.0100 → 0.0313, while MXFP8 stays flat, 0.0095 → 0.0087).
- **Mismatched grids are worse from step 1**: on the MoE model the FP8-blockwise pipeline (sampler uses FP32 scales the learner cannot use on SM100) has **2× the KL of the shared-grid pipeline at step 1 (0.00921 vs 0.00446)** and over the last 10 steps (0.00899 vs 0.00449); without a quantized KV cache, BF16 end-to-end remains 2.5–10× more consistent than any quantized pipeline.
- **Speed is conditional on tokens per micro-batch**: on the MoE DAPO-Math-17k workload (Qwen3-30B-A3B, 4 B200, ~12.3k tokens/micro-batch), MXFP8 cuts **step time by 10.7%** (506.0 → 451.8 s), **generation by 23.8%** (133.6 → 101.7 s), update_actor by 9.4%, and raises throughput **+12.2%** (1,678 → 1,883 tokens/s/GPU) at identical response lengths — fastest at every one of the 10 steps. On short-sequence dense gsm8k (~3.4k tokens/micro-batch, below m*), MXFP8 **raises step time by 5.1%** and is slower than BF16 at 57 of 60 steps.
- **The break-even is m* ≈ 4.5k tokens/micro-batch** (95% CI 4.3–4.8k): in the controlled micro-batch sweep on identical replayed data, the MXFP8−BF16 update-stage difference is **+15.37 s/step at 1.3k tokens/micro-batch but −7.61 s/step at 10.3k** (through +0.64 at 5.2k), following the per-micro-batch prediction while a per-step cost predicts a constant −0.9 s; the sweep's own fit gives Δδ = 47.0 ± 4.5 ms/micro-batch vs 51.5 ms inferred from the main run. Both FP8 recipes cut update_actor's per-token cost by 43–45% but add +5.8/+6.6 s per step of fixed cost.
- **The added cost is host-side**: of +43.4 ms added per micro-batch (profiled), summed GPU kernel time grows only +3.5 ms (GEMMs actually save 7.1 ms) and merged GPU-busy time +5.9 ms (14%); **37.4 ms (86%) pass with no GPU operation running**, 30.6 ms of it because the host had not yet issued the next operation; MXFP8 launches 912 extra kernels per micro-batch. On the slower-CPU host the same recipe is a net loss (update_actor +23–31% vs BF16).
- **Correctness**: seven failures met on B200, each breaking one of the seven conditions, **five silent** (exit code 0 with normal-looking metrics) — e.g. F1 (lm_head quantized → NaN logits, reward 0.000 for all 20 steps vs a healthy 0.316 on the untrained model), F2 (vLLM 0.24 substring matching silently left gate_up_proj — 52% of each layer's linear weights — in BF16, 56/311 parameters), F4 (stale MoE expert layout, expert-probe relative error 1.74 vs healthy 0.05, KL only 0.047 — below any plausible divergence alarm). Guards are complementary: the engine-state audit alone caught F2, the kernel self-check alone caught F4; five failures are reproduced by CPU fault-injection tests (108 tests in verl).
- **Quality/entropy signals**: held-out gsm8k accuracy after 60 steps is 0.9393 (MXFP8/MXFP8) vs 0.9363 (BF16) vs 0.9249 (FP8-TW) on the full 1,319-problem test set — within noise the author identifies (samplers differ by 1.9 points on the untrained model; host changes accuracy by up to 2.0 points). Policy entropy falls 74% under FP8-TW on DAPO-Math-17k (with the highest training reward, 0.240 vs BF16's 0.150) but stays flat/rises under MXFP8 (+4%); FP8 training also costs memory: actor peak +25% on MoE (60.0 → 75.0 GiB).

## Authors & Credibility

Single author, Wengee Zhang (independent affiliation, gmail contact). The work is concurrent with industrial end-to-end MXFP8/NVFP4 RL efforts from Miles (LMSYS/Ant Group) and SkyRL (Anyscale), and the paper honestly positions itself relative to them: the design principle (shared quantizer/byte-exact weights) is the same; the contribution is measurement — consistency ordering at identical weights, a fitted break-even threshold tested on held-out data and a controlled sweep, and a correctness specification with run-time checks. Implementation artifacts are real and partially upstreamed (verl PRs #7986, #7987, #8062; 108 CPU fault-injection tests). The paper acknowledges that implementation, experiment design, analysis, and drafting were done with the assistance of an AI coding assistant, with the author reviewing every line and taking responsibility. The self-declared scope limits (single seed, 10–60 steps, no final-quality claims) are stated in the abstract itself, which is a credibility plus.

## Critical Assessment

- **Novelty**: moderate on design (shared-grid sync was already used by Miles/SkyRL; the paper says so), genuinely novel on measurement: the controlled fixed-weight matching experiment, the per-micro-batch break-even model with a controlled sweep + held-out validation, the byte-for-byte quantizer comparison, and the C1–C7 correctness conditions with guard-coverage analysis are all new contributions to this specific literature.
- **Rigor**: unusually high for a systems-measurement paper — paired-prompt bootstrap CIs, a BF16 reference-stage control that validates the timing fit (per-token costs agree within 1.4%), explicit warnings that the rollout diagnostics are not independent confirmations, and discarded measurement rounds with negative intercepts. But every arm is one run of one seed; "confidence intervals" resample prompts or steps within a run, not runs, and consecutive-step autocorrelation of the KL series is 0.68–0.99, which the paper flags. The headline 43–70% late-training KL improvements are measured against an FP8-TW baseline the paper itself shows is pathological (drifting 3.1× in setting B) — the step-1 margins against it are 0–23%, and the paper is open about this decomposition.
- **Reproducibility**: good — exact software versions, two host types documented, fixes upstreamed, CPU tests shippable without GPUs; but the hardware fault-injection campaign (detection rates, false alarms, delay, per-check cost) is specified and not run, and the byte comparison covers only 3 of 36 dense layers at two synchronizations, offline, with no MoE byte comparison at all.
- **Significance**: strong for practitioners on Blackwell (the m* ≈ 4.5k tokens/micro-batch rule, "prefer MXFP8 over emulated FP8-blockwise on SM100", and the guard design are immediately actionable); the correctness section generalizes beyond verl. The consistency findings partially formalize what SkyRL/Miles reported anecdotally.
- **Red flags / paper-specific caveats**: (1) the dense vLLM arms of settings A and B were affected by the F2 bug — gate_up_proj (52% of each decoder layer's linear weights) stayed in BF16 — so the main dense MXFP8/MXFP8 results are for a *half-matched* sampler, reported "as run" and rationalized as a natural experiment; (2) setting B ran an FP8 KV cache in *all* arms, so its "BF16" arm is not BF16 end-to-end (step-1 KL 0.00610 vs 0.00066 in A) and B's absolute KL numbers are not comparable to other settings; (3) the fixed-weight matching comparison exists only at the initial checkpoint, so "matching helps" is untested on trained weights; (4) the matching experiment cannot split the 16% gain between weight grid, activation quantization, and kernel terms (the paper proposes but did not run the three extra dequantized-sampler ablations); (5) in setting D the CPU fused-AdamW computed the weight-decay factor in FP32 where 1 − 1e-8 rounds to 1, so weight decay was silently inactive in all arms — an ironic data quirk for a paper about silent numeric failures, honestly disclosed in Appendix D; (6) gsm8k accuracy differences (0.9393 vs 0.9363) are within noise the author himself quantifies and should not be read as an MXFP8 win.

## Strengths

- Measures exactly the questions practitioners ask — what matching buys, when FP8 pays off, how it fails — with controlled experiments (fixed weights, paired prompts, replayed identical data) rather than only end-to-end anecdotes.
- The break-even model is validated four independent ways (sweep, within-run crossing, held-out workload, host dependence) and its mechanism is traced to host-side dispatch gaps, with concrete remedies (CUDA graphs, TE ≥ 2.18 weight-scale preswizzling) — the latter already implemented upstream.
- The correctness section turns seven painful silent failures into a reusable specification (C1–C7), guards whose blind spots are stated by construction, and CPU-injectable tests; the observation that divergence alarms cannot catch moderate faults (F4's KL of 0.047 vs healthy max 0.037) is important and general.
- Exceptional honesty: scope limits in the abstract, discarded rounds disclosed, baseline pathology (FP8-TW drift) separated from the matching effect, and no final-quality overclaim from 10–60-step single-seed runs.

## Limitations

- Single seed per arm; runs of 10–60 steps at lr 1e-6; the controlled runs 3–12 steps — no statement about final model quality is possible, and the entropy differences' effect on learning is left open.
- The matching gain is measured only at the initial checkpoint, in one engine, and conflates weight grid, activation quantization, and kernel changes; the proposed dequantized-weight/input-rounding sampler ablations were not run.
- Setting B's FP8 KV cache is a confound shared by all its arms; the dense MXFP8 rollout speed claim rests on short controlled runs where the 5.3% gain is within the 3.1% spread between two identical BF16 samplers; SGLang's default Triton path was 1.9× slower than BF16 generation, so dense rollout speed is effectively unmeasured in the main settings.
- The break-even model is fitted on one model (Qwen3-8B) and one host type; the sweep ran each configuration once, BF16 before MXFP8; BF16's 8-sequence point falls off its linear model; predicted scaling with width/tensor-parallelism is untested.
- Byte-for-byte verification sampled 3/36 layers offline; MoE weights never compared; the hardware fault-injection campaign (detection/false-alarm/delay/cost) is specified but not executed; unprobed-layer faults are a sized-unknown blind spot.
- MoE coverage is one family (Qwen3-30B-A3B), vLLM only, 10 steps, with parameter offloading and a CPU optimizer that accidentally disabled weight decay in every arm.

## Relevance

直接命中"极端性能优化下的可靠性"方向：这是低精度（MXFP8/FP8）训练与推理数值行为及其静默失效的系统性测量研究——train–rollout 一致性、量化网格失配、每 micro-batch 主机侧开销和 5 个静默失效案例都属该领域核心问题。同时对"RL 后训练动态与失效"方向有价值：量化配方改变策略熵轨迹（MXFP8 持平 vs FP8-TW 暴跌 74%）并与训练–推理失配、重要性采样校正等 RLVR 失效模式直接相关。

## Questions for Further Exploration

- Does the 16% consistency gain from matching grow, shrink, or reverse at trained checkpoints (with drifted, outlier-heavy weights), and how does it interact with an FP8 KV cache on the sampler side?
- What share of the 16% is weight grid vs activation quantization vs kernel/accumulation differences — the proposed dequantized-MXFP8-weight, rounded-input, and both-combined sampler arms would split it cleanly.
- Is MXFP8's flat/rising policy entropy useful exploration or slower sharpening, and is FP8-TW's −74% entropy collapse with the highest training reward early over-exploitation? Needs multi-seed, long-horizon runs with held-out evaluation.
- Does m* shrink as predicted with wider models, lower tensor parallelism, CUDA-graph capture of the micro-batch, and TE ≥ 2.18's preswizzled weight scales — and does the host-side dispatch cost persist on next-generation hosts?
- Can the remaining ~84% of the BF16-sampler mismatch be attributed quantitatively (per-function host profile; activation-quantization sharing via bitwise-identical upstream kernels), matching the error-decomposition framework the paper sketches in Section 10?
- Would the C1–C7 conditions and guards transfer unchanged to NVFP4 RL pipelines (QUADS reports activation error dominates there), and what are the actual measured detection rates/false alarms of the hardware fault-injection protocol?
