Exponent spread ≤ 3 makes an MXFP4 row exactly INT8 × power-of-two — every linear layer collapses to one exact INT8 GEMM.

一句话总结（摘录）：当 MXFP4 权重行的块指数跨度不超过 3 时，该行可精确表示为 “一个 INT8 向量 × 单个 2 的幂缩放因子”，从而把整个线性层折叠成单次 INT8 GEMM； 真实权重 97.9–99.97% 的行天然满足该条件。

Why this matters

4-bit LLMs on Apple Silicon can finally ride the M5’s fastest datapath — INT8×INT8 at 1.79–1.98× FP16 rate — while files stay standard MXFP4.

解决 W4A16 预填充用不上 M5 最快 INT8 数据通路的痛点，同时保持标准 MXFP4 文件兼容。

Critical edge

Folding buys exactness and format compatibility, not speed — expert GEMMs run at 0.76–0.94× oMLX’s rate and batch-1 decode is never improved (0.90–1.01× MLX), so practical deployments must mix kernel families.

Non-compliant rows (≤2.1% even on the worst model): exponents raised to max−3 — added error ≤ 1/16 of the row’s worst-case rounding (Prop. 2); the file remains a standard MXFP4 any decoder reads.

  • Measured motivation: on M5 Neural Accelerators, INT8×INT8 hits 109–127 TOPS (1.79–1.98× FP16) while every float×integer mix runs below FP16 — both operands must be integer.
  • Exact folding (Prop. 1): a folded layer needs no per-32-block E8M0 scaling inside the reduction; INT32 accumulation cannot overflow for K ≤ ~176k.
  • 16-block format (§3.5): generalizes to integer block multipliers m ∈ {1…10} × E2M1 codebook × 16-wide blocks = 4.26 bit/weight — still a single exact INT8 GEMM (max C · max M ≤ 127).
  • Deployed in MLX: dense prefill, grouped MoE prefill (counting-sort of token–expert assignments → one grouped INT8 GEMM), packed-weight decode GEMV. Exponents fixed before rounding, so GPTQ composes unchanged.

Results beyond the headline

Strengths

  • A provable iff-condition turns a heuristic (block exponents cluster) into an exact single-GEMM guarantee, with a quantizer whose damage is bounded at 1/16 of the row’s worst-case rounding error.
  • Drop-in compatibility: SC-MXFP4 files remain standard MXFP4 (4.07 bit/weight at K=4096) — existing decoders read the same bytes, a property most format papers sacrifice.
  • The 16-block integer-multiplier format gets NVFP4-class accuracy at 4.26–4.28 bits with exact INT8 execution, demonstrated up to a 125B MoE with the strongest measured GSM8K (94.84%).
  • Measurement hygiene: bit-exactness checks end-to-end, fake-quant/kernel cross-checks, paired McNemar tests, clock-regime-aware timing — and honest positioning against concurrent oMLX/scratchy work.

Limitations

  • Decode gains are absent: batch-1 is memory-bound (0.90–1.01× MLX); the 16-block GEMV runs at 0.65× on the 125B, so deployments must mix kernel families (ours for prefill, MLX’s for decode).
  • One device, one OS version: all numbers from a single M5 Max on macOS 26.6; native FP8/FP4 matmul in macOS 27 is unmeasured; NVIDIA/AMD/SME portability argued, not shown.
  • Missing ablation: rotations + GPTQ (MR-GPTQ) under the spread constraint — round-to-nearest rotations actively hurt E2M1 here (10.99 → 13.18 ppl).
  • Compatible format pays: SC-MXFP4 trails NVFP4 / MLX affine INT4 by 0.2–0.3 ppl on 3 of 6 models; llama.cpp’s ~5-bit Q4_K_M beats every format here above 4.5 bits. The 125B was quantized from FP8, not BF16.

Questions for further exploration

  • Does spread ≤ 3 hold for vision transformers, other linear-attention / SSM families, or quantization-aware-trained models?
  • Can the unoptimized 16-block decode GEMV reach parity (register-fragment decoding, fused multiplier LUTs), ending mixed-kernel deployments?
  • Does the INT8-exact advantage survive macOS 27’s native FP8/FP4 matmul types, or does native FP4 hardware make folding obsolete?
  • How do rotations + GPTQ (MR-GPTQ) interact with the spread constraint, given RTN rotations cost 2+ perplexity points here?
  • Can the 1/16 error bound tighten into an output-aware (Hessian-weighted) guarantee, composed with outlier-channel smoothing?
  • Is per-token INT8 activation still “free” under long contexts with large activation outliers — and for KV-cache quantization?
