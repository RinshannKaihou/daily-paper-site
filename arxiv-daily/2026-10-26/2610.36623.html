Key Finding · 关键发现

LLM-generated GPU kernels silently violate batch invariance — the same request returns bitwise-different outputs as its batch context changes.

God Does Not Play Dice: Enforcing Batch Invariance in Agentic Kernel Generation ↗

Youwei Bao · Chengpeng Wang · Simin Chen — GMU STAR Lab · NUS  ·  2026-10-26

已发布的 LLM 生成 kernel 中 22.9%（83 个可批处理 artifact 中的 19 个）违反批不变性；BIEvolve 以“DSL 合约静态分析 + 跨 batch 逐位动态校验”双闸门，将三个 agent 的 BI 通过率从 67.6% 提升到 91.9%，同时保留 91.8% 的基线几何平均加速比。

Key Metric · 核心指标

+24.3pts

Final-solution BI pass rate: 67.6% → 91.9% across three agent frameworks — while retaining 91.8% of baseline geometric-mean speedup (28.91× → 26.54×).

Why This Matters · 为何重要

Kernel agents that chase correctness and speedup systematically ship batch-dependent kernels — a silent reliability bug for anyone serving LLMs with dynamic batching.

仅以正确性+加速比为目标的 kernel agent 会系统性地产出批依赖 kernel，直接威胁动态 batch serving 的数值一致性与可复现性。

Critical Edge · 批判视角

A “BI pass” is evidence, not proof — the dynamic gate samples only a finite subset of batch contexts, and 8.1% of final kernels still violate BI.

01Methodology核心方法

  • Definition. A kernel is batch-invariant iff a preserved sample's output is bitwise-identical across every admissible batch context (size, composition, position may vary; fixed hardware/software) — deliberately distinct from run-to-run nondeterminism.
  • Static gate. An executable DSL contract declares batch symbols (batch_size, num_seqs, …) and protected parameters (NUM_SPLITS + 20 aliases, RNG_SEED); taint-style dependency analysis rejects any batch→protected flow and emits mechanism / location / dependency-path / repair diagnostics.
  • Dynamic gate. Per kernel-family test policy: the identical preserved sample (position 0, batch-size-1 baseline) is re-embedded in larger batch contexts; structure, shape, dtype and values must match bitwise. Stops at first mismatch.
  • Integration. A lightweight adapter inserts the gates into each framework's candidate evaluation — prompts, search state, and selection policies stay untouched.
  • Evaluation. Three agents (K-Search, Iterative, Evolve), one model (Gemini 3.7 Flash), one GPU (H100 NVL); 39 batch-applicable tasks, 1,180 workloads; ablations on a 200-candidate independently-labeled pool.

Acceptance-gate order

①Static BI · DSL deps → ②Reference correctness → ③Dynamic BI · bitwise → ④Benchmark

BI failure ↩ diagnostics (mechanism · location · dependency path · repair hint) re-enter the agent's native feedback channel; later rounds condition on them.

03Strengths优势

  • Turns a real, previously unmeasured serving-reliability problem into a precise, testable definition — backed by a field audit of 131 released artifacts.
  • Plug-in design preserves each agent's optimization ability; demonstrated across three architecturally distinct frameworks (Evolve even keeps 102% of baseline speed).
  • Static/dynamic complementarity is quantified (92% combined vs 83% / 55% individually; 46% overlap), not asserted.
  • Actionable diagnostics (mechanism · location · dependency path · repair hint) close the loop with the agent, at just 10.21 ms per candidate.
  • Honest subgroup reporting — retention split by baseline BI outcome, plus a late-stage-gain analysis that resists overinterpreting the fixed-budget comparison.

04Limitations局限

  • Static rules are hand-curated contracts — 20+ NUM_SPLITS aliases enumerated by hand, limited cross-file scope; automated rule extraction is future work.
  • Dynamic validation checks a finite, lightweight subset (sample 0, batch-size-1 baseline, stop at first mismatch) — passing is evidence, not proof; 8.1% of final solutions still violate.
  • Kernel-level only: no end-to-end measurement of generated tokens, benchmark scores, serving behavior, or RL rollout-training mismatch.
  • Compact 39-task suite skewed toward attention / linear-attention families; one LLM and one GPU — generalization unverified.
  • BI is not free: K-Search retains 86.4% of speedup (−13.6% GM); Iterative Agent only 74.2% on violation-prone tasks.

05Questions for Further Exploration待探索问题

  1. Can the BI-contract DSL rules (batch symbols, protected parameters, aliases) be synthesized automatically from violation examples — and would learned rules generalize beyond attention / linear-attention?
  2. What is the end-to-end impact of the residual 8.1% violating kernels on generated tokens, benchmark scores, and RL rollout-training mismatch in production serving?
  3. Why does Evolve retain 102% of speed while K-Search loses 13.6% — which search-strategy properties set the cost of BI constraints, and can larger turn budgets close the gap?
  4. Would baking BI into the training signal (Kevin-style RL with a BI reward) internalize invariance better than rejection gates — at what sample-complexity cost?
  5. Does the approach transfer to other hardware/backends (AMD, tensor-parallel) — and would multi-sample, multi-position dynamic validation push detection past 92%?
