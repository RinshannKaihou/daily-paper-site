> **一句话总结：** FactorSpec 把 JSON Schema 及其跨字段关系编译成带精确可行性检查的因子图，将约束"确定"的 token 作为零损耗投机草稿直接写入验证步，在 SGLang/vLLM 中既把接受长度提升到每步 10.5 个 token（最快 n-gram 草稿器的 1.9 倍）、比逐负载调优的投机器最多快 1.43 倍，又保证 100% 记录满足关系约束（Qwen3-8B 直接生成的行程仅 10% 有效），以语法掩码的成本换取高达 13.9 倍的每 GPU 秒有效记录数。

> **TL;DR:** Grammar masks in serving engines enforce only syntax, so Qwen3-8B produces a valid itinerary for just 10% of NATURAL PLAN trip problems (14% even with error-feedback retries). FactorSpec compiles a JSON Schema plus declared relations into a factor graph with an exact feasibility check, drafts every constraint-determined token as a "certain" speculative draft (up to 10.5 accepted tokens per verify step on trip planning vs 5.9 for the best n-gram shape, a 1.9x acceptance gain), verifies each request at an individually chosen width, and computes masks in worker processes off the scheduler thread. Result: up to 1.43x faster than speculators tuned per load in SGLang (1.03-2.24x over the best of six baselines in vLLM), 100% valid records, and up to 13.9x more valid planning records per GPU-second than the strongest syntax-only baseline; the lead shrinks to 1.01-1.12x where the model (not the relations) chooses most of the record, and a solver still beats it on matching gold meeting plans (46-56% vs 14-16%).

## 核心贡献

- **约束即草稿器（核心洞见）**：精确的关系约束本身就知道哪些位置的 token 是被唯一确定的，因此可以直接把这些 token 作为"必然被接受"的投机草稿提交给目标模型验证——约束的开销被转化为加速的来源。
- **逐请求自适应验证宽度**：服务引擎的传统做法是对整个 batch 用同一验证宽度，导致高负载下投机收益消失；FactorSpec 用凹收益模型（least concave majorant）为每个请求单独分配验证槽位，使投机在高负载和自由文本中依然有利可图。
- **token 级的精确联合关系约束**：区别于语义约束解码器只做局部一致性检查（arc consistency 会把 12–64% 的规划记录引入不可行前缀），FactorSpec 用因子图上的 memoized bucket elimination 精确计算每个变量的 support，保证每个被采样的 token 都能扩展为完整合法记录。
- **调度器外的约束服务**：掩码计算放在每 rank 8 个 worker 进程中，通过共享内存写掩码行并在 GPU 前向计算期间预计算下一步，使精确约束的成本仅为语法掩码级别的吞吐（0.95–1.07 倍 XGrammar）加约 8 个 host CPU 核心。
- **大规模实证**：在 SGLang 和 vLLM 两个引擎、四个模型（Qwen3-1.7B/8B/14B、Llama 3.1 8B）、六个工作负载（ledger、τ-bench retail、BFCL、NATURAL PLAN 的 trip/meeting/calendar）、332 组配置各跑三次，与逐 cell 调优的 11 种草稿形态及 enum schema、重试、思维链、求解器、枚举 schema 全面对比。

## Key Contributions

- **The constraint as a lossless drafter**: an exact constraint knows which positions it determines, so it proposes those tokens as certain drafts (the target provably accepts them all), and it knows how many of its drafts the target will accept, so it sizes each request's verify width accordingly (Sections 3.1-3.3).
- **Exact per-token enforcement of joint relations**: a memoized bucket-elimination feasibility check over factor graphs (Boolean semiring, min-fill order), a structure engine that keeps every admitted token completable to a valid record, and a JSON Schema + relations frontend with twelve relation kinds (allowed rows, all-different, running sums, visit schedules, ...) compiled in 0.05-0.55 ms at the median.
- **A constraint service outside the scheduler process**: worker processes (8 per rank) write shared-memory mask rows and compute ahead while the GPU runs, so a step of 64 requests costs only 8-16 messages each way — the exact check's millisecond tail overlaps the device.
- **Dual benefit, measured end-to-end**: both faster (up to 1.43x over per-load-tuned speculators in SGLang; 1.03-2.24x over the best of six baselines in vLLM) and always valid (100% of records satisfy the relations), which compounds to up to 13.9x valid planning records per GPU-second over syntax-only baselines.
- **Honest systems evaluation**: 332 configurations x 3 runs, closed-loop (1-128 requests in flight) and open-loop (Poisson arrivals), tensor parallelism, temperature-1 sampling, ablations of workers/widths/jump-forward, and validators written independently of the constraint engine.

## Methodology

**Spec declaration and compilation.** A client declares a record as a JSON Schema plus a list of relations over JSON Pointer paths (Figure 4). The server compiles this into (1) a template whose choice fields are factor-graph variables and (2) a factor graph where each relation is a Boolean table over the variables in its scope. Specs come in three levels compared in the evaluation: syntax (grammar-enforceable), membership (each reference must be one of the declared identifiers), and relational (all factors).

**Exact feasibility.** Every mask rests on one query: the *support* of the next field given committed values — the set of values that extend to a full assignment satisfying every factor. FactorSpec answers it exactly via bucket elimination in the Boolean semiring (tables joined by AND, eliminated by OR). Because a decoder's queries form a walk that clamps one variable at a time, consecutive queries share almost all work; the engine memoizes reduced tables by factor-plus-restriction and bucket messages by variable-plus-input keys, so a query only touches what the newest value changes. Encoding matters: a naive all-different table over cities joins up to 22.2M entries at seven cities (exceeding the budget at eight), while a chain encoding over visited-set states needs only 8,575 entries at seven cities and 529,200 at ten, covering every NATURAL PLAN trip problem. Relations that stay large under any table encoding (e.g., meeting schedules with waiting) enter as *global factors* with dedicated dynamic programs (2^P · P states: parties met × last party) that yield each field's exact support by lookup.

**From values to tokens.** The structure engine maintains the invariant that every admitted token extends to a complete, valid record. States hold candidate continuations tokenized *in context*; the allowed set is the next token of every candidate matching the tokens emitted so far. Positions admitting exactly one token form *determined runs*, which the drafters propose. A per-request session exposes fill / accept / rollback / fork / expand, so rollbacks are list truncations and forked trees share states.

**Drafters and per-request widths.** Three drafters are provided: the factor drafter (determined runs alone), grafted onto the engine's n-gram corpus or EAGLE-3 head. Because determined tokens are provably accepted, drafting is lossless — the sampled record equals the unconstrained-model record restricted to valid ones. Each request's verify width is chosen by a return model: expected accepted tokens of certain nodes (1 each, taken first) plus an EMA of measured returns for guessed nodes, read through its least concave majorant so a sorted pass allocates the step's slots to the highest-return requests (knee K = 128 tokens, measured on the A6000).

**Constraint service.** Worker processes hold each request's session, write mask rows into double-buffered shared-memory blocks, and precompute the next reply for determined positions while the device verifies — so even opening a field of several hundred values does not stall the next step.

**Engine integration.** In SGLang 0.5.16, FactorSpec registers a grammar backend plus five speculative algorithms via plugin registries and hands non-relational requests to XGrammar; in vLLM 0.21.0, the grammar object answers from its last reply block and the proposer posts all requests' steps before waiting for any reply. Implementation: 16,700 lines of Python (9,100 constraint engine, 7,600 serving layer).

## Results & Highlights

- **Acceptance length**: on NATURAL PLAN trip planning with Qwen3-8B, FactorSpec's combined drafter accepts **10.5 tokens per verify step at 8 requests in flight (9.9 at 64)**, vs **5.9 (5.3)** for the fastest n-gram shape and 3.9 (2.6) for EAGLE-3 — up to **1.9x** the best n-gram, because a determined run is accepted whole. Meeting planning: 8.4 vs 5.7; calendar: 6.9 vs 6.8 (Table 2).
- **Throughput vs tuned speculators**: leading the per-cell-tuned speculator (best of 11 drafter shapes) by up to **1.43x at 8 in flight, 1.26x at 64, 1.39x at 128**; on workloads where the model chooses most of the record (BFCL, calendar) the lead shrinks to **1.01-1.12x**. In vLLM the factor drafter leads the best of six baselines by **1.03-2.24x**; across four models the combined drafter leads by **1.02-1.50x**.
- **Validity**: Qwen3-8B under XGrammar writes a valid itinerary for **10%** of NATURAL PLAN trip problems; error-feedback retries raise this only to **14%**; thinking mode yields **19%** valid trip plans / 31% meeting schedules. FactorSpec's records are **100% valid** by construction, giving **2.6-13.9x** the valid planning records per GPU-second of the strongest of seven syntax-only baselines (at least 9.3x on trip, where baselines make fewer than 1 in 10 valid), and 79-631x the thinking-mode baselines' valid records per GPU-second.
- **Cost of exactness**: the masks alone run at **0.95-1.07x** XGrammar's throughput up to 64 in flight in SGLang (up to **1.19x** in vLLM on trip planning), because workers overlap the GPU — exactness costs host CPU (~8 cores per GPU), not GPU time. A single feasibility query takes 2-131 µs at the median (at most 3.2 ms).
- **Against equally-valid baselines**: vs solve-then-emit, FactorSpec serves **1.28-1.46x** the solver's valid itineraries/meeting schedules (solver computes each answer in 0.3-1.7 ms but still emits one token per step); vs the enumerated schema (anyOf of up to 1,024 records) it leads **1.06-1.31x** on calendar/retail/BFCL. The solver chooses better where gold follows a fixed objective: its earliest meeting plans match gold in **46-56%** of problems vs FactorSpec's **14-16%**, so it serves 2.6-2.8x FactorSpec's *correct* meeting schedules.
- **Open-loop stress**: at 32 requests/s on trip planning, FactorSpec completes **32 valid itineraries per second within 10 s vs 1.2 for the n-gram drafter**, with 99th-percentile latency **3.8 s vs 26 s**. On full sets, it matches gold on 98-99% of itineraries and 67.4% of calendar slots vs at most 13.6% and 36.3% for baselines.
- **Ablations**: 8 workers per rank add **19-31%** over one worker; per-request widths add **2-22%** to the factor drafter at 64 in flight (costing up to 2.3% at 1 request); jump-forward-style verify of determined runs alone reaches 0.89-0.97 of the factor drafter. With 128-token free-text notes the trip-planning lead falls from 1.77x to **1.13x**, while tuned n-gram and EAGLE-3 drop below XGrammar to 0.72/0.73.

## Authors & Credibility

Jianchang Su, Dawei Xiang, and Wei Zhang (corresponding author) are at the University of Connecticut, Storrs. This is a preprint (arXiv 2611.02297v1, 1 Nov 2026), not yet peer-reviewed. The group has a visible research line on factor-graph constraints — the related-work section cites their prior set-automata constrained decoding (Su et al., 2026) and FactorDLM for diffusion models (Su & Zhang, 2026) — so the core machinery is a continuation of established work rather than a first attempt. The paper's empirical hygiene is unusually strong for a systems preprint: 332 configurations x 3 runs, per-cell tuned baselines, 95% Wilson intervals, closed- and open-loop protocols, and validators written independently of the constraint engine. Versions are pinned (SGLang 0.5.16, vLLM 0.21.0) and a repository with the declaration examples is referenced.

## Critical Assessment

- **Novelty: genuinely strong.** Reframing an exact constraint as a speculative drafter — exploiting that it knows which tokens are determined and how many drafts the target will accept — is a real conceptual contribution beyond jump-forward decoding (grammar-determined tokens only) and semantic constrained decoders (local checks only, which the paper shows strand 12-64% of planning records at infeasible prefixes under arc consistency). The per-request width allocator and off-scheduler worker service are solid systems contributions.
- **Rigor: high, with disclosed quirks.** Baselines are tuned per cell over eleven drafter shapes (a stronger baseline protocol than most speculative-decoding papers), and the solver/enumerated-schema comparisons are fair and honestly reported — including the case where the solver wins. One protocol wrinkle: settings (b), (d), (e), (f) of Figure 10 ran at a later commit, disclosed but still a mild apples-to-oranges risk. Table 1's "computed" share is admitted to be an upper bound (any computed value in a run counts the whole run), which inflates the stated opportunity.
- **The 13.9x headline needs unpacking.** It counts *valid records per GPU-second* against baselines that mostly emit invalid records; the pure speed lead over tuned speculators is 1.01-1.43x, and collapses toward 1.01-1.12x exactly on workloads (BFCL, calendar) where the model, not the relations, chooses most tokens. The paper says this plainly, but a skim of the abstract alone would overestimate the speed contribution.
- **Spec authoring is the real deployment cost.** Relations must be hand-declared per task with finite domains and a table budget; twelve fixed relation kinds are covered, and new kinds need a server-side extension. Correctness of the declaration is the application's responsibility — a wrong spec silently constrains to the wrong relation, and nothing here infers relations from tool docs automatically. The ledger workload is synthetic; generality rests on five public benchmarks.
- **Hardware and model scope.** All timing runs are on RTX A6000 GPUs (48 GB) with models up to 14B; the overlap analysis is measured down to Qwen3-1.7B's step time on one GPU type at up to 128 in flight. Faster GPUs (H100/B200) shorten the step, and the paper itself concedes more workers per rank may be needed — the host-core budget (~8/GPU) could grow. No 30B+ or MoF models are tested.
- **Reproducibility: good.** Pinned engine versions, LOC counts, an independent conformance test replaying traces through both engines' grammar objects, and independently written validators. No public code link is given in the body I could verify beyond "our repository".

## Strengths

- Turns an inherent cost (exact joint-relation checking) into a speed source via lossless drafting of determined tokens — a clean, transferable insight.
- The validity problem it targets is real and well-quantified: 10-14% valid trip itineraries for Qwen3-8B even with retries, ~1/3 at best for meeting planning under all syntax-only baselines.
- Exactness is achieved at essentially a grammar mask's throughput by moving the check to worker processes and computing ahead — the systems engineering (double-buffered shared-memory rows, batched 8-16 messages/step, memoized elimination, chain encodings, global-factor DPs) is careful and ablated piece by piece.
- Evaluation breadth: two engines, four models, tensor parallelism, temperature-1 sampling, closed/open loop, seven syntax-only baselines plus solver/enumerated-schema/retry/thinking alternatives, with per-cell tuned speculators.
- Intellectual honesty: reports where the method ties (1.01-1.12x), where it loses (solver matches gold meeting plans 46-56% vs 14-16%), and where gains fade (free-text notes).

## Limitations

- Relations must be declared correctly by the application over finite domains within a table budget; the twelve built-in relation kinds do not cover arbitrary relational semantics, and extending them requires server-side code.
- Speed gains are proportional to the determined share of tokens: with 128-token free-text notes the trip-planning lead falls from 1.77x to 1.13x over XGrammar, and the advantage is inherently small on generation-heavy structured tasks.
- Where gold follows a fixed objective (meeting planning), letting the model choose among valid plans tracks gold far worse than a solver (14-16% vs 46-56% match), so the "model freedom" design choice trades correctness-for-speed in objective-driven tasks.
- Measured on one GPU type (RTX A6000), models up to 14B, up to 128 requests in flight; the overlap argument may need re-tuning (more workers) on faster devices or bigger models, and exactness costs ~8 host cores per GPU.
- Verify-width rounding can change 1-4 of 64 greedy meeting records between runs (all still valid); a few figure settings were run at a later commit than the main campaign.

## Relevance

对关注 LLM 推理加速与服务系统的研究者，本文同时命中投机解码（speculative decoding）与结构化输出（constrained/structured generation）两条主线，并给出"约束即草稿器"这一可迁移的设计原则；对需要部署可靠工具调用/规划类结构化生成的场景（τ-bench、BFCL、NATURAL PLAN 类任务），其 100% 有效性保证加 1.0–1.4 倍加速的组合具有直接工程价值。

## Questions for Further Exploration

- Can relation specs be inferred automatically (e.g., by an LLM reading tool documentation or few-shot examples) and *verified* against the constraint engine, removing the hand-declaration bottleneck the paper identifies as the application's task?
- How does the per-request width allocator and worker-service overlap behave on H100/B200-class GPUs and 30B-70B models, where the step time shrinks and the host must hide a relatively larger share of the check's tail?
- Does drafting the determined tokens change the conditional distribution of the model-chosen fields (the record is valid, but is it the record the model "would have" written), and does that affect downstream utility beyond gold-match rates?
- Could the factor-graph feasibility check replace the enumerated-schema baseline it compares against (anyOf of up to 1,024 records) in agentic pipelines where the feasible set is exponentially large but the factor structure is compact?
- How does the approach interact with continuous serving concerns absent from the paper — preemption, chunked prefill mixing with speculative batches, and multi-tenant spec pools beyond 128 requests in flight?
