Key finding arXiv 2611.02207 BOBA-Bench

Coding agents solve 95% of requests alone, but only 51% as chains — verification, not skill, is the bottleneck.

Built on Broken Assumptions (BOBA): Why Coding Agents Cannot Be Left Alone

Key metric · chain collapse

95%→51%

Requests completed one-at-a-time vs. as 20-request chains — averaged over ten coding agents on 280 chains (5,600 requests), 8 attempts each.

+18 ppnext-request failure after one unverified miss (nearly triples)

Why this matters

Quantifies the compounding cost of failed self-verification in continuous delegation — even one bit of external verification is the reliability bottleneck for unattended coding agents.

它量化了连续委托场景下自检失效的复合代价，并证明外部验证通道（哪怕只有一个比特）是当前智能体系统的可靠性瓶颈。

Critical edge

Headline 51% is an upper bound: strict pass@1 — no silent miss, no regression — is just 39%, and the 95%-vs-51% juxtaposition conflates two different evaluation regimes.

Methodology · distilled

How BOBA-Bench isolates verification from authorship

  1. MINE — consecutive commits touching tests + source from 140 real Python repos → 280 chains × 20 requests (5,600 total).
  2. SPECIFY — specs model-written from the test diffs; agents under test never see the tests.
  3. AUDIT — three model families rewrite each spec until all accept identical text.
  4. CERTIFY — released only if the developers' own patches pass every hidden test at every state, inside a sealed, dependency-frozen image.

Each request starts a fresh conversation on whatever state the previous one left; a silent grader runs hidden tests after every submission but never tells the agent — chains run all 20 requests regardless. pass@1 from 8 attempts, repo-clustered 95% CIs. Strengths

What holds up

  • Clean causal decomposition of the collapse into authorship vs. verification, with matched settings holding spec, budget, and grader identical.
  • Validity gate — developers' patches must pass every hidden test at every state — makes every miss attributable to the agent, not an unsolvable spec.
  • Self-critical reporting: strict pass@1 beside pass@1, regression rates, memorization analysis, full AI-use disclosure.
  • Actionable and costed: naming the failing test once beats multiple rounds of insisting; phantom "wrong" verdicts cost little (≈98% of phantom repairs leave work passing).
  • Full artifact release with pinned digests and per-table reproduction scripts.

Limitations

Where it bends

  • Fixed-test correctness only — not user intent, readability, or production readiness; Python-only, many repos small.
  • Twenty sequential requests ≠ a deep dependency chain; "chain completion" partly proxies accumulated silent-miss risk.
  • Specifications are model-written and model-audited, not human-reviewed; residual spec-quality noise remains.
  • Near-verbatim memorization (14–19% for three Claude models) is bounded but not excluded as a leaderboard effect.
  • Headline pass@1 credits chains repaired by request 20 despite mid-chain misses; the stricter measure is 10–15 points lower.
  • Review experiment bounds this protocol — richer reviewer contexts (diffs, run logs) might change the verdict.

Questions for further exploration

  • Would richer reviewer contexts (full diffs, execution logs, the hidden contract itself) lift cross-model review above the 53% coin-flip ceiling?
  • Can a verifier-trained self-certification head — predicting "my own tests would fail" — transfer to chain completion without seeing hidden tests?
  • Does the built-on-broken-assumptions effect scale past 20 requests, or to genuine cross-file dependency chains?
  • Does the ~18 pp penalty per unverified mistake persist for non-Python languages and frameworks with persistent memory across requests?
  • What is the minimal informative feedback signal (failing test name + stack trace) that closes most of the 51%→100% gap per call budget?
  • Could the flat 3–6% per-request silent-miss rate serve as a training-time reward for certification-aware fine-tuning?
