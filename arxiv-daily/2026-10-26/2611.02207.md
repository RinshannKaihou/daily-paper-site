> **一句话总结：** 本文构建了 BOBA-BENCH（从 140 个真实 Python 仓库的提交历史中抽取 280 条、每条 20 个连续请求的链，共 5,600 个请求），发现十个主流编码智能体单独完成请求的成功率高达 95%，但连续成链后平均只能完成 51%；根因不是智能体写的代码差（经验证的智能体代码与人类代码几乎同样可扩展，平均仅差 1 个百分点），而是未被发现的自检遗漏——单个未验证错误使下一请求失败率平均上升 18 个百分点，而一次外部"验证失败"提示加一轮修复即可将链完成率从 51% 提升至 59%。

> **TL;DR:** Amazon builds BOBA-BENCH, 280 chains of 20 back-to-back requests mined from 140 real Python repos (5,600 requests), and runs ten coding agents (Claude Opus 5.5 down to GLM-5.3-Flash) with 8 attempts per chain: agents complete 95% of requests one at a time but only 51% of chains (best model Claude Opus 5.5: 66.7% pass@1; worst Claude Opus 4.8: 39.2%). The cause is not authorship — on verified states agent code is within ~1 pp of human code as a base — but unchecked mistakes: one unverified miss raises next-request failure by ~18 pp (nearly tripling), and cross-model review barely beats chance (53% accuracy; lenient reviewers accept 77–95% of wrong implementations). A single external "verification failed" bit plus one repair round lifts chain completion 51%→59% (+1.1 to +22.1 pp by model), making verification access, not raw coding skill, the binding constraint on unattended agents.

## 核心贡献

- **提出"无人值守开发"的评测维度**：指出现有基准（SWE-bench 系列、FeatureBench、SWE-EVO 等）都是单请求、人类代码起点、一次性判定，无法测量智能体在连续委托、无验证反馈场景下的可靠性；此前链式基准要么将已验证与未验证工作混在一起推进，要么在首次失败即终止。
- **构建 BOBA-BENCH**：从 140 个真实 Python 仓库的提交历史中挖掘出 280 条链、每链 20 个连续请求（共 5,600 个请求）；规格说明由模型从开发者新增的测试（而非代码）撰写，经三个模型家族审核一致，且仅当开发者自己的补丁在链上每个状态都通过全部隐藏测试时才发布该链，保证"漏做"可归因于智能体。
- **自主评测协议**：每个请求在全新会话中下发，智能体在上一请求留下的代码状态上工作；隐藏测试在每次提交后静默判定（silent miss / regression），但绝不反馈给智能体，链始终跑满 20 个请求——这正是无人值守开发的形态。
- **分解"代码作者"与"是否验证"两种因素**：证明性能崩塌主因是后者（Built on Broken Assumptions 现象）：经验证状态下智能体代码与人类代码几乎同样可扩展，而未验证错误会让后续请求失败率成倍增长。
- **跨模型互审实验**：让十个模型互相审查 2,180 个实现（错误实现配对正确孪生），证明没有任何模型能充当可靠的审查者。
- **量化最小外部验证的价值**：仅一个比特的"验证失败"信号加一轮修复即可部分恢复性能，并给出对系统构建者、模型构建者、基准构建者和用户的四类建议；全部工件（规格、隐藏契约、金补丁、轨迹、评分器）开源。

## Key Contributions

- **Defines the "unattended development" evaluation gap**: existing benchmarks (SWE-bench Verified/Pro, FeatureBench, SWE-EVO, Commit0, etc.) test one request on human-written code with a single verdict; prior chain-style benchmarks either carry verified and unverified work forward as one, or stop at the first failure — neither isolates what unattended agents lack: verification.
- **BOBA-BENCH construction**: mines runs of consecutive commits that change tests and source together from 140 real Python repositories into 280 chains of 20 requests (5,600 total); specifications are model-written from the developers' test diffs, audited until three model families accept identical text, and a chain is released only if the developers' own patches pass every hidden test at every state inside a sealed, dependency-frozen offline image.
- **Autonomous evaluation protocol**: each request arrives in a fresh conversation on whatever state the previous one left; a separate grader runs hidden tests of requests 1..k after every submission (classifying silent misses and regressions) but tells the agent nothing; the chain runs through all 20 requests regardless.
- **Authorship-vs-verification decomposition** via five controlled settings (AUTONOMOUS, AGENT CODE, HUMAN CODE, SILENT CONTINUATION, VERIFIED, REVIEW), establishing the "built on broken assumptions" phenomenon: degradation is driven by unverified mistakes, not by agent authorship.
- **Cross-model review experiment**: ten models each review 2,180 implementations (every wrong implementation paired with the same author's correct twin), showing no model can serve as the check — lenient reviewers accept most wrong code, strict ones reject much correct code.
- **Quantifies the value of one bit of external verification** ("verification failed" + one repair round), with practical guidance for system, model, benchmark builders and users; full artifacts (specs, hidden contracts, gold patches, sealed images, all trajectories, graders) released at github.com/amazon-agi/BOBA-bench, pinned by digest and hash.

## Methodology

**Benchmark construction (semi-automatic, four stages).** (1) *Mine history*: stretches of consecutive commits that change tests and source together become candidate requests, kept only if the new tests fail before the developers' change and pass after it (fail-to-pass / pass-to-pass contract). (2) *Specify*: Claude Opus 4.8 writes each specification from the test diff, aided by commit messages and issue text — the agent under test never sees the tests. Solvability is probed blind: two models solve 78% of released specifications between them; the rest were probed for behavior the tests demand but the text omits, then rewritten or kept as hard-but-fair. (3) *Audit*: three model families (GLM-5.2, Fable 5, GPT-5.6) read every specification against its hidden tests, rewriting until all three accept identical text. (4) *Certify*: 20 consecutive requests form a chain sealed into one offline container image with frozen dependencies, released only if the developers' patches pass every hidden test at every state.

**Evaluation protocol.** The agent works through the 20 specifications in one offline container (mini-swe-agent 2.4.6 harness; unlimited model calls, 2 h tool execution per chain, no wall-clock limit), each request in a fresh conversation, submitting via a submit tool; the grader runs in a separate container seeing only the agent's git history. A submission whose own hidden tests fail is a *silent miss*; a previously passing test that fails is a *regression*. The agent is told neither the verdict nor that it is on a chain. A chain counts as complete if the repository after request 20 passes every hidden test; pass@1 is estimated from eight independent attempts per chain, with repository-clustered 95% bootstrap intervals.

**Five settings.** AUTONOMOUS (the benchmark run); AGENT CODE vs HUMAN CODE (request k+1 solved on k certified requests written by the agent itself, with retries, or by the developers — isolates authorship); SILENT CONTINUATION (request k+1 issued on a silent miss, counting only that request's own test failures — isolates verification); VERIFIED (after the miss, an external "verification failed" message plus one repair round); REVIEW (a different model accepts or rejects a finished implementation without knowing its author).

**Models.** Ten agents on all 280 chains in AUTONOMOUS: Claude Opus 5.5 / Opus 5 / Opus 4.8 / Fable 5, GPT-6 Astra / GPT-6.1-sol / GPT-5.6-sol, GLM-5.3 / GLM-5.3-Flash, Kimi K3 (median 182–739 model calls per chain). The other settings use five of these plus GLM-5.2. A judge model assigned one of 17 failure tags to all 4,787 failed requests of the first attempts; three alternative harnesses were checked (no model completes more chains under them).

## Results & Highlights

- **Chain vs single-request completion (BOBA-BENCH, 280 chains, pass@1 from 8 attempts):** the ten agents complete 95% of requests when taken one at a time, but only 51% of chains on average (abstract headline). Within the chain runs themselves, per-request completion is 66.2–84.0%, versus chain pass@1 from 39.2% (Claude Opus 4.8) to 66.7% (Claude Opus 5.5, 95% CI [61.3, 71.9]) — a 25+ point collapse for the same models on the same requests.
- **Strict pass@1 and regressions:** requiring every request to pass on its own step with no test ever broken drops completion to an average of 39% (27.5% for Opus 4.8 to 55.8% for Opus 5.5); in 23–43% of attempts a later request breaks a test that previously passed, and only 14–33% of failing tests are ever repaired. 16% of chains are completed by none of the ten models on the first attempt and 16% by all ten (fewer than one expected under independence) — the same chains fail everyone.
- **Authorship is not the problem (AGENT CODE vs HUMAN CODE):** building on *verified* agent code costs at most a few points relative to human code — the gap across eleven models runs −3.6 to +0.8 pp (average −1 pp), excluding zero for only three models (Claude Opus 5, Opus 4.8, GLM-5.2, at 3–4 pp).
- **Verification is the problem (SILENT CONTINUATION):** after a single unverified mistake, failure of the next request's own tests rises by an average of 18 pp (nearly tripling); the same requests attempted from the developers' own state still fail 9–19 pp less often, and the odds of failing roughly double with each additional unverified mistake beneath a request.
- **Cross-model review (2,180 items, wrong implementation paired with correct twin):** overall accuracy is 53%, barely better than a coin flip. Lenient reviewers (the four Claude models, GLM-5.3, GLM-5.3-Flash, Kimi K3) accept 77–95% of wrong implementations; strict reviewers (GPT-6 Astra, GPT-6.1, GPT-5.6) reject 41–58% of correct ones; only 4–19% of matched pairs are discriminated (Youden J ≤ 0.15).
- **One bit of external verification (VERIFIED setting):** told only "verification failed" with one repair round, chain completion rises from 51% to 59% on average — per-model gains from +1.1 pp (GPT-5.6) to +22.1 pp (GLM-5.3), seven of ten paired intervals above zero — and a repaired state no longer hurts subsequent requests (equivalent to a certified state), whereas restarting without the message does not help. Agents repair a third to a half of misses in one round, a quarter to a half when the failing test is named; applied after every failed submission, completion rises 8–16 pp per model, at the cost of a 3–9 pp higher regression rate and 47–294 extra calls per chain.
- **Robustness checks:** repeating the bare rejection helps with diminishing returns (30% → 54–59% over eight rounds for GPT-5.6 and Kimi K3, >40% of misses remaining); naming the failing test once achieves what ~three rounds of insisting achieve. Contamination: three Claude models reproduce 14–19% of sampled change blocks near-verbatim, yet do not measurably complete more chains of memorized repositories (±12–18 pp intervals).

## Authors & Credibility

Two authors — Alejandro Cuadron and Arpit Gupta — at Amazon, which provides the compute and engineering resources a 280-chain × 10-model × 8-attempt evaluation demands (tens of thousands of agent runs; hundreds of model calls per chain). Credibility signals are unusually strong: repository-clustered bootstrap confidence intervals throughout, an explicit AI-use statement disclosing every LLM role in the pipeline (spec writing, auditing, judging), a contamination analysis for memorization, harness-robustness checks across three alternative harnesses, and a full public release (github.com/amazon-agi/BOBA-bench) including specifications, hidden contracts, gold patches, sealed images pinned by digest, all trajectories, and the grader/analysis scripts behind every table and figure. The benchmark's validity gate — the developers' own patches must pass every hidden test at every state — is a well-chosen ground-truth anchor. The 56-page preprint with extensive appendices reads as careful, pre-release-of-models empirical SE work rather than a marketing document.

## Critical Assessment

- **Novelty:** the core observation (agents report wrong work as done; failures compound) is documented in prior trajectory studies, and the related-work table itself lists a dozen chain/repository-evolution benchmarks (CodeThread, SWE-EVO, SlopCodeBench, Jin et al. 2026, Deng et al. 2026). The genuine novelty is the *controlled decomposition* — separating code authorship from verification status via the AGENT CODE / HUMAN CODE / SILENT CONTINUATION / VERIFIED settings — which no prior chain benchmark does, plus the withhold-all-feedback protocol that makes self-certification itself the measured quantity.
- **Rigor:** high. Eight attempts per chain, clustered CIs, paired comparisons against the first AUTONOMOUS attempt, oracle checks with human patches at every state, cross-harness replication, and a quantified contamination bound. One caveat the authors themselves flag: headline pass@1 "judges only the final repository, crediting chains that missed or broke something on the way" — the 51% is thus an *upper* bound on unattended reliability, and strict pass@1 (39% average) is the harsher, more honest number.
- **Reproducibility:** excellent on the artifact side (pinned digests, hashes, trajectories, released grader). But the *specifications are model-written and model-audited, not human-reviewed* (their own Appendix D.5 admission) — a validity threat they mitigate with the blind-solvability probe (78% solved by two models) and the three-family audit, yet a nontrivial fraction of "hard but fair" specs rests on model judgment about what the hidden tests demand.
- **Significance:** the decomposition result — agent code is fine once verified; unverified mistakes are what compounds — is actionable for both agent-pipeline design (route verifier feedback to subagents directly) and model training (certification as a first-class objective). The finding that no model can review another's work (Youden J ≤ 0.15) directly undercuts "just add a reviewer agent" architectures.
- **Red flags / weaknesses:** (1) Python-only, many repositories small, and, as the authors concede, twenty requests do not imply a twenty-link dependency chain — the "chain" structure partly measures accumulation of silent misses rather than deep sequential dependency; (2) the abstract's "95% one at a time" is a different (independent-request) setting than the 66–84% per-request completion inside chains — the headline juxtaposition is fair in direction but the two numbers come from different regimes, and a casual reader may conflate them; (3) three of the ten VERIFIED-setting gains have CIs overlapping zero, so "1 to 22 points" spans statistically solid to noise; (4) the review experiment gives the reviewer limited information ("with the information given here"), so it bounds this protocol rather than review-in-principle; (5) Claude models reproduce 14–19% of change blocks near-verbatim — the ±12–18 pp intervals bound but do not exclude a memorization effect on the leaderboard.

## Strengths

- Clean causal decomposition of the chain-completion collapse into authorship vs verification, with matched settings that hold specification, budget, and grader identical.
- The benchmark's validity gate (developers' patches must pass every hidden test at every state) makes every miss attributable to the agent rather than to an unsolvable spec.
- Honest, self-critical reporting: strict pass@1 alongside pass@1, regression rates, memorization analysis, AI-use disclosure, and limitations stated without hedging.
- Directly actionable findings with quantified costs: one bit of feedback recovers a meaningful share of the loss; naming the failing test beats multiple rounds of insisting; phantom "wrong" verdicts on correct work cost little (≈98% of phantom repair rounds leave work passing).
- Full artifact release with pinned digests and per-table reproduction scripts — rare even for benchmark papers.

## Limitations

- Measures fixed-test correctness only — not user intent, readability, or production readiness; Python-only; many source repositories are small.
- Twenty sequential requests do not guarantee a deep dependency chain, so "chain completion" partly proxies for accumulated silent-miss risk rather than long-horizon planning.
- Specifications are model-written and model-audited, not yet human-reviewed; residual spec-quality noise cannot be fully excluded.
- Repositories come from public agent-task pools and changes largely predate model cutoffs; near-verbatim memorization (14–19% for three Claude models) is bounded but not ruled out as a leaderboard effect.
- Headline pass@1 credits chains repaired by request 20 despite mid-chain misses or broken tests; the stricter measure is 10–15 points lower.
- External-validity of the review experiment depends on the information given to the reviewer; richer contexts (diffs, run logs) might change the verdict.

## Relevance

本文直接回应"多智能体/编码智能体可靠性与自我验证"这一核心关切：它量化了连续委托场景下自检失效的复合代价，并证明外部验证通道（哪怕只有一个比特）是当前智能体系统的可靠性瓶颈。对于设计 coding agent 流水线、评估 LLM 长程可靠性、或研究 self-verification / 过程监督的工作，BOBA-BENCH 的协议与结论都具有直接的参考和基准价值。

## Questions for Further Exploration

- Would richer reviewer contexts (full diffs, execution logs, or the hidden contract itself) move cross-model review above the coin-flip regime, or is the 53% ceiling a property of the models rather than the information?
- Can a verifier-trained self-certification head (predicting "my own tests would fail") be optimized directly, and would it transfer to BOBA-BENCH chain completion without seeing the hidden tests?
- How does the built-on-broken-assumptions effect scale with chain length beyond 20, and with genuine cross-file dependency chains rather than sequential commits in small repos?
- Does the ~18 pp penalty per unverified mistake persist for non-Python languages and for agentic frameworks with persistent memory across requests (the fresh-conversation protocol here deliberately forbids it)?
- Since naming the failing test once beats several rounds of bare rejection, what is the minimal *informative* feedback signal (e.g., failing test name + stack trace) that closes most of the 51%→100% gap per call budget?
- Could the silent-miss rate (3–6% per request, flat across the chain) serve as a training-time reward signal for certification-aware fine-tuning?
