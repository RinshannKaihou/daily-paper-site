> **一句话总结：** 该文把 Agent 的上下文建模为五段流水线并实测每一段的信息流失：在一个读取 Linux 内核追踪、诊断注入故障的真实 Agent 中，34% 的工具结果（11,189 中的 3,827 个）在送达模型前就被 harness 的定长前缀截断切成坏 JSON（证据字段仅 4.7% 送达），而上下文窗口只用了 5.75%；注册对照实验证明这种数据销毁首先以"多干活"而非"答错题"的形式付出代价——工具调用 +43%、计算量翻倍、yield 从 0.61 跌到 0.31，且对 7 个主流框架的调研发现 langchain-core 与 smolagents 仍在用同样不安全的按位置截断。

> **TL;DR:** Instead of asking how big an LLM agent's context window is, this paper measures what survives the trip from tool output to model input. In a real Linux-kernel-trace fault-diagnosis agent (720-run field eval), 3,827 of 11,189 tool results (34%) were destroyed by a fixed-length prefix-slice cut — every one became broken JSON and one evidence field reached the model in only 4.7% of 742 calls — while the 400k-token window sat 94% empty (largest prompt 23k tokens). A registered controlled experiment (145 runs, 5 recordings × 3 repeats per fault class, temperature 0) shows the cut costs work, not answers: versus the repaired row-aware-cut baseline, the shipped prefix slice keeps accuracy (15/15 vs 14/15 on spawned culprits) but raises tool calls 53 → 76 (+43%), roughly doubles computations (18 → 36), and collapses yield from 0.61 to 0.31. Only on a "quiet" production-scale culprit (21-container trace, 0/128 late-list records delivered) does the cut also kill accuracy (0/5 correct vs 3/6 repaired). A survey of seven agent frameworks finds two (langchain-core's 500-char front-keep, smolagents' middle-delete over 20k chars) cutting positionally the same unsafe way.

## 核心贡献

- **提出"上下文即五段流水线"模型**：produce→deliver→act→retain→transfer（+persist），并为每个边界给出实测失败率与统一度量——yield（记录到的发现 ÷ 运行的计算数），主张 harness 应把"每段的丢失数"与准确率并列上报。
- **实测量化了 S1 边界的破坏性交付**：720 次运行、11,189 个工具结果中 3,827 个（34%）被按固定长度前缀切片截断、全部变成坏 JSON；按位置截断对固定键序的 JSON 是"整段删除"——同一结果里一个字段送达率 4.7%、另一个 99.3%，且与故障类别（新进程 vs 常驻容器）的准确率分裂（40–55/60 vs 0–24/60）完全对齐。
- **确定性重放证据**：重放 31 次运行的 864 个真实工具结果——所有超预算结果在前缀切片下必坏、在行感知切割下零坏；一条 33,370 字符的真实生产追踪（21 容器、预算的 5.6 倍）中，出厂切割只送出早期列表 118 条中的 30 条、晚期列表 128 条全灭。
- **注册对照实验得到"补偿税"结论**：单变量重引入缺陷后，Agent 在有"第二条路"时仍能答对（15/15），但代价是 +28%/+43% 工具调用、计算翻倍、yield 0.61→0.34→0.31；只有对无第二路线的"安静元凶"，切割才同时摧毁准确率（生产规模重放 0/5 vs 修复版 3/6）。
- **七框架普查**：langchain-core（截到 500 字符留前段）与 smolagents（>20k 删中段）按位置切割且不看结构；三个框架完全不切（把同样的丢失推给上下文窗口）；安全范式（按整行切割并声明）存在但不是默认。

## Key Contributions

- A **five-boundary pipeline model of agent context** (produce→deliver, deliver→act, act→retain, retain→transfer, transfer→persist), each with a measured failure rate from the harness's own field data, plus a proposed instrumentation standard: per-boundary loss counts and one yield number (findings recorded ÷ computations run) reported alongside accuracy.
- **Quantification of destructive delivery (S1)**: in a 720-run evaluation of a kernel-trace fault-diagnosis agent, 3,827 of 11,189 tool results (34%) were cut by fixed-length prefix slicing; every cut result became broken JSON, and because JSON keys have fixed order, a prefix slice deletes whole late fields — one field was delivered in only 4.7% of 742 calls while a neighboring field reached 99.3%, exactly matching the accuracy split between fault classes (spawned faults 40–55/60 vs resident faults 0–24/60).
- **Deterministic replay evidence** with no model in the loop: replaying 864 recorded results from 31 runs broke every over-budget result under the shipped prefix slice and none under a repaired row-aware cut; a production-scale 21-container trace (33,370 chars, 5.6× the 6,000-char budget) had its entire late-list evidence class (128 records) deleted by the shipped cut.
- **A registered, controlled experiment** isolating one boundary at a time (145 runs; 5 recordings × 3 repeats per fault class; temperature 0; predictions written before each wave): the cut's causal cost first appears as extra work, not wrong answers — a "compensation tax" of +28%/+43% tool calls, doubled computations, and yield 0.61→0.31 — with the authors honestly reporting that their own accuracy-drop prediction was refuted (the agent recovered via sorted tables when the culprit was the loudest process at 14.0% of kernel events).
- **A survey of seven agent frameworks** (langchain-core 1.6.12, langchain 1.4.6, smolagents 1.26.0, openai-agents 0.24.0, autogen-agentchat 0.7.5, pyautogen 0.10.0, crewai 0.11.2): two use position-based cutting identical in kind to the defect (langchain-core keeps the first 500 characters; smolagents deletes the middle of observations over 20k chars); no consistent, structure-aware alternative exists in the rest.

## Methodology

The paper combines four methods. (1) **Pipeline instrumentation**: the agent's context path is modeled as five boundaries (S1 produce→deliver, S2 deliver→act, S3 act→retain, S4 retain→transfer, S5 transfer→persist), each instrumented with a concrete unit (e.g., top-level fields of a tool result at S1; recorded findings transferred at S4) and a summary yield metric. (2) **Field measurement**: the deployed harness's own 720-run evaluation (11,189 tool results) provides failure rates per boundary — S1 prefix slicing cut 34% of results; S2's step budget stopped 51% of 554 workers at exactly the limit; S3's retention cap raise from 80k to 150k chars grew a run from 303k to 545k tokens; S4's voluntary hand-off meant 98 workers passed on nothing. (3) **Deterministic replay**: transcripts storing both the full result and the text actually sent allow replaying 864 real results (and one 33,370-character production trace) through the shipped prefix-slice cut and a repaired row-aware cut, no model involved, producing the "delivery cliff" curve. (4) **Registered controlled experiment**: with agent, model (temperature 0), tools, and task fixed, six configurations (repaired; S1 defect; S1 reversed — same cut with keys serialized in reverse so only position changes; order-only control — reversed keys, no cut; single-defect arms for S2–S4; all defects) are run on spawned vs resident fault classes with exact ground truth and a strict commitment-based scorer (the agent must name the culprit in its answer field; an earlier lenient mention-counting scorer that inflated one arm from 2/15 to 14/15 was caught in a 46-run audit and replaced). Predictions were written down before each wave, and deviations are logged in the artifact.

## Results & Highlights

- **Field data (720-run kernel-trace diagnosis eval)**: 3,827 of 11,189 tool results (34%) were cut before reaching the model and every cut result became broken JSON, while the largest prompt of any run was only 23k tokens — 5.75% of the 400k-token context window (93%+ empty at the median).
- **Positional delivery asymmetry (same 720-run eval, 742 relevant calls)**: the late-list field reached the model in only 4.7% of calls vs 99.3% for the early-list field in the very same payloads; diagnosis scores split along the same line — spawned faults (evidence in the surviving early list) scored 40–55/60, resident faults (evidence in the deleted late list) scored 0–24/60.
- **Replay of 864 recorded results from 31 runs**: 100% of over-budget results broke under the shipped 6,000-char prefix slice vs 0% under the row-aware cut; 50% of process-listing calls and 43% of the agent's own analysis outputs broke, but only 2.5% of all calls were affected at all — which is exactly why the defect survives inspection.
- **Production-scale replay (real 21-container deployment, one service CPU-throttled)**: the listing result is 33,370 chars (5.6× the shipped budget); the shipped slice delivers 30 of 118 early-list records and 0 of 128 late-list records, in an already-broken payload — the culprit's entire evidence class disappears. A repeated paired test on this trace: repaired condition named the throttled service correctly in 3/6 runs with 0/6 broken payloads; S1-defect condition 0/5 correct with 10–14 broken payloads per run.
- **Controlled experiment, spawned culprits (Table II; medians over 15 runs/config, 5 recordings × 3 repeats)**: repaired = 14/15 correct, 53 tool calls, 18 computations, yield 0.61, 567k median input tokens; S1 defect = 15/15 correct but 68 calls (+28%), 27 results lost per run, 32 computations (~1.8×), yield 0.34, +5% tokens; S1 reversed = 15/15, 76 calls (+43% vs repaired), 36 computations (2×), yield 0.31, +14% tokens. Recorded findings stayed constant at 11 across all three — the agent finds the same answers by working much harder. The order-only control (reversed keys, no cut) returns yield to 0.61, confirming the effect is the cut, not reordering.
- **Framework survey**: 2 of 7 surveyed agent frameworks cut positionally — langchain-core 1.6.12 truncates serialized tool output to 500 characters (front-keep) and smolagents 1.26.0 deletes the middle of any observation over 20k characters; neither inspects structure. A structure-aware pattern (whole-line shell-output cutting with an explicit notice) exists in one framework but is not the default.
- **Why the defect goes unnoticed (10 uncapped production coding-agent runs)**: waiting on the model consumed a median 84% of wall-clock time (range 80–91%), so a data-destruction defect that costs tokens and correctness barely moves the latency metric teams watch; and handing the agent a written procedure reached the same verdict as free exploration at just 35% of the tokens — the "usual remedy" masks the symptom rather than fixing delivery.

## Authors & Credibility

The authors are Yuvraj Sehgal and Naser Ezzati-Jivan (Department of Computer Science, Brock University, Canada) and Mahsa Panahandeh (School of Electrical Engineering and Computer Science, University of Ottawa, Canada). The work is a software-engineering empirical study (cs.SE, cross-listed cs.AI) rather than a frontier-lab system paper, and its credibility rests on unusually transparent methodology: registered predictions written before each experimental wave with a dated deviation log shipped in the artifact; a self-caught scoring bug (a lenient mention-counting scorer inflated one arm from 2/15 to 14/15, discovered in a 46-run audit and replaced with a commitment-based scorer before the controlled experiment); explicit separation of what the experiments settled (the compensation tax, deterministic data destruction) from what they did not (causal proof that the cut drives the field-wide accuracy split); and a public replication package (drivers, scorer, results, replay corpus, registered plan) at https://doi.org/10.5281/zenodo.23614755. The honest reporting of a refuted prediction (reversing key order did not reduce accuracy) is a notable credibility signal.

## Critical Assessment

- **Novelty**: The reframing — measuring what the harness destroys between tool and model, rather than window size or in-window attention — is genuinely fresh, and the five-boundary pipeline plus yield metric is a reusable instrument. The nearest prior work ([10] LLMs processing tool outputs, [12] harness design policies, [13] file-retrieval vs context) measures outcomes, not delivery losses; the delta is real but incremental in method (instrumentation + registered experiment, standard SE tooling).
- **Rigor**: High for a 5-page paper: paired controlled design, order-only and reversed-key controls that cleanly isolate position from content, deterministic replays with no model in the loop, and a caught-and-fixed scorer. But no statistical significance tests are reported anywhere — 15/15 vs 14/15 is correctly called noise, yet the production-scale accuracy claim rests on 3/6 vs 0/5, six runs versus five, which the authors themselves label noisy; that cell cannot support a strong causal claim and the paper wisely hedges.
- **Threats the authors own**: one harness, one domain (kernel-trace fault diagnosis), one model; the defect was injected by the authors themselves (reintroduced under registered predictions, not discovered in the wild); only 5 distinct fault recordings per class with paired repeats rather than independent instances; the field accuracy split remains correlation — and they note a confound that fixing delivery also shipped two new analysis tools, so field gains cannot be attributed to the fix alone.
- **Missing evidence**: the survey of seven frameworks is code-reading at specific versions with no end-to-end measurement in those frameworks; the page-on-request safety net they built never fired, so its value is untested; no conventional build-test-fix coding agent (compiler/CI-log truncation) is measured despite being the most obvious generalization; yield is a count-based proxy with no relevance weighting (acknowledged as needing ground truth).
- **Red flags / overclaim check**: The abstract and conclusion are careful ("Whether the data cut truly causes the accuracy drop is still an open question"), and the headline numbers (34% cut, 4.7% vs 99.3%) are delivery metrics, not accuracy metrics — a reader skimming only the intro could mistake the 0–24/60 field scores as proven caused by the cut, which the controlled experiment did not establish for spawned faults. The paper is commendably explicit about this boundary.

## Strengths

- Identifies and names an invisible, general failure class — destructive delivery by position-based truncation — that both window-size research and failure-taxonomy work structurally miss, because run logs record what a tool delivered, not what it produced.
- The measurement is deterministic and cheap: replays and delivery cliffs require no model, making the instrument CI-friendly (their future-work item 4 makes each boundary failure mechanically testable).
- Exemplary experimental hygiene: registered predictions, a logged refutation, controls that separate position from content, and a strict scorer that replaced a caught lenient one.
- Practical, actionable findings: two production frameworks (langchain-core's 500-char cut, smolagents' 20k middle-delete) are shown to carry the same defect; the safe whole-line/structure-aware pattern is demonstrated; and "yield" gives teams a number to watch besides latency and accuracy.
- Public replication package with replay corpus and registered plan.

## Limitations

- Generalization is asserted more than measured: one harness, one domain (Linux kernel-trace diagnosis), one model, and a defect the authors wrote themselves; no end-to-end measurement in any of the surveyed third-party frameworks.
- The central causal question — does the cut cause the field-wide accuracy drop for quiet culprits — is unsettled: the controlled spawned-fault experiment refuted the accuracy prediction, and the production-scale quiet-culprit replication (3/6 vs 0/5) is too small to be decisive.
- Sample sizes are small throughout (5 recordings × 3 repeats; 145 total controlled runs; 6 vs 5 production runs), with no significance testing.
- Yield is a narrow proxy (work that reached the decision), not evidence relevance or quality; the S3 retention analysis rests on a single before/after run.
- The page-on-request safety mechanism never fired in any run, so the proposed remedy for oversized results is unvalidated.

## Relevance

对研究 LLM Agent 系统与上下文工程的工作直接相关：它把"上下文窗口够不够大"的问题换成"harness 在工具输出到模型之间丢了多少证据"，提出的五边界流水线模型、yield 指标与按行/按结构切割的安全范式，可迁移到任何工具增强型 Agent（包括编码 Agent 的编译器日志、CI 输出截断）的 harness 设计与评测中。

## Questions for Further Exploration

- Does the compensation tax (yield 0.61→0.31 at equal accuracy) generalize to conventional build-test-fix coding agents, where compiler errors and CI logs are routinely truncated (one cited harness caps every tool result at 24k chars)?
- How many runs would the production-scale quiet-culprit comparison (3/6 vs 0/5) need to statistically settle whether destructive delivery causally kills accuracy, not just data?
- Would paging-on-request delivery (which never fired here) recover quiet-culprit accuracy without incurring the extra tool calls of compensation, and can it be made to fire reliably on 33k+ character results?
- How does position-based field deletion interact with models' known positional attention biases ("lost in the middle") — do the two losses compound when a field survives the cut but lands in an weakly attended region?
- Can per-boundary loss counts (S1 field-delivery rates, S4 hand-off completion) be packaged as standard CI assertions for agent harnesses, and would langchain-core's 500-character default be fixed by such a test?
- Does the S2 step-budget wall (51% of workers stopping exactly at the limit) interact with S1 loss — i.e., does compensation work fail partly because workers exhaust their budget re-fetching cut results?
