> **一句话总结：** 提出 GSE 框架，通过 Skill Relation Graph 联合演化技能间的依赖/共用/冲突关系，并用聚类合并 + 回放验证将单条 trace 的局部更新抽象为可复用技能，在 bug-revealing 测试生成和误报 bug 报告过滤两个 SE 任务上，相比 Live-SWE-agent 和 Trace2Skill 等强基线在 precision/recall/F1 上均有显著提升，并在字节内部工业 Agent 上将 F1 提升 61.4%。

> **TL;DR:** GSE reframes agent skill evolution as a *global* optimization over an interconnected skill bank: a Skill Relation Graph co-evolves inter-skill dependency/co-usage/conflict edges and cluster-based consolidation plus replay-driven validation converts trace-local updates into reusable skills. On bug-revealing test generation (Java Multi-SWE-Bench, 108 bugs) it lifts OpenHands F1 from 0.22 (Live-SWE-agent) to 0.31 (+40.9%) and on false-positive filtering (ByteDance's IndustrialBugs, 500 reports) it lifts OpenHands precision 0.29→0.55 (+89.7%) and F1 0.43→0.70 (+62.8%); deployed on a proprietary industrial agent it improves F1 by 61.4% over human-written skills while actually using fewer per-case execution tokens than every baseline.

## 核心贡献

- **将技能演化重新表述为全局优化问题。** 指出现有方法（Live-SWE-agent、Trace2Skill）把技能演化当成一系列相互独立的局部更新，忽视了技能之间的耦合关系，导致技能库逐渐积累冲突与过拟合条目。GSE 把整个技能库当作相互连接、可复用的系统来联合优化。
- **Skill Relation Graph (SRG)。** 用有向图显式建模技能间的三类关系（dependency / co-usage / conflict），并把关系当作一等公民与技能内容一起演化；当一个 proposal 影响邻居技能时，自动派生辅助演化 proposal 以保持全局一致性。
- **全局技能泛化机制。** 通过 cluster-based consolidation（按受影响技能集或语义相似度聚类）和 replay-driven validation（在相关历史案例上回放，只有维持或提升性能才入库）把 trace 级别的局部改进抽象成高阶可复用技能，同时防止回归。
- **DSL 化的演化 proposal + 双数据集验证。** 用结构化 DSL（target skill / operation / content / rationale / expected behavior / relationship updates）约束 proposal；在 Java 测试生成（Multi-SWE-Bench 派生，9 个开源项目 108 个真实 bug）和 Go 误报过滤（与字节合作构建的 IndustrialBugs，8 个生产仓库 500 份报告）两个跨语言、跨场景任务上系统评估，并进一步部署到工业级内部 Agent。

## Key Contributions

- Reframes skill evolution as global optimization over an interconnected skill bank rather than a sequence of independent local updates, identifying two concrete failure modes (incompatible assumptions across skills; fragmented, over-specialized skills that don't transfer).
- Introduces the Skill Relation Graph (SRG), a directed graph over skills with three edge types (dependency, co-usage, conflict), and treats relations as first-class objects of evolution; a relationship-aware propagation step generates auxiliary proposals so a local change doesn't silently break neighbor skills.
- Adds a two-stage skill generalization mechanism — cluster-based consolidation (cluster by affected-skill set for updates, by semantic similarity for new skills; a merge agent strips case-specific details) and replay-driven validation (replay on historical cases that previously activated the affected skills; accept only if performance is preserved or improved).
- Provides a DSL that constrains every evolution proposal (operation, target skill, content, rationale, expected behavior, relationship updates), reducing ambiguity for downstream processing.
- Evaluates across two diverse SE tasks (Java bug-revealing test generation from Multi-SWE-Bench; Go false-positive filtering on a newly built industrial dataset IndustrialBugs), two open-source SOTA coding agents (OpenHands, mini-SWE-agent), and one proprietary industrial agent — all under a one-project-held-out protocol with temperature 0.

## Methodology

GSE is a three-stage loop running on top of any skill-augmented coding agent.

1. **Trace Collection.** The base agent (OpenHands or mini-SWE-agent) is instrumented to record reasoning blocks, tool calls, parameters, environment feedback, and the final outcome. A *trace simplification* step strips token-heavy but causally low-value output (full `find`/`grep` results, raw file contents, info-level build/test logs) while preserving command metadata, targeted paths, key errors, and reasoning blocks — yielding a "semantic-rich" simplified trace.

2. **Evolution Proposal Generation.** An update agent (powered by DeepSeek-V4-Flash) performs a *hierarchical failure diagnosis* classifying each failure as navigation / reasoning / execution, then formulates a root-cause hypothesis. It distinguishes two evolution types: general capability enhancement (workflow-level) and reusable problem patterns (e.g., bug-triggering or framework-contract patterns). The SRG is then consulted: GSE identifies affected neighbor skills in the graph plus semantically related skills retrieved via metadata, decides whether each update changes assumptions/outputs/applicability of those neighbors, and emits *auxiliary* proposals when needed. Each proposal is serialized in the DSL (Figure 2 in the paper gives a concrete ContextExplorer example that adds a dependency edge to TestRunnerConfig). Before generalization, every proposal is replayed against its originating failure case; failures are discarded immediately (local validation gate).

3. **Skill Generalization (Algorithm 1).** Locally validated proposals are clustered — by affected-skill set for updates, by semantic similarity of rationale/expected-behavior for new skills. A merge agent extracts the common capability pattern, removes case-specific detail, and instantiates a candidate skill bank on the SRG. The candidate is then validated by replaying on a *replay set*: for skill updates, the historical cases in which the affected skills were previously activated (most likely to surface regressions); for new skills, all cases that produced the clustered proposals. The candidate is merged into the skill bank only if it preserves or improves performance across the replay set.

All agents run on the same LLM (DeepSeek-V4-Flash), same tools, same per-task budget. The skill bank is versioned with Git worktree and traces/replay outcomes are persisted in SQLite, so concurrent evolution runs don't interfere and every accepted skill version is reproducible.

## Results & Highlights

- **Bug-revealing test generation (Table 1).** On OpenHands, GSE reaches P=0.35 / R=0.28 / F1=0.31 vs the strongest baseline Live-SWE-agent at P=0.31 / R=0.17 / F1=0.22 — i.e. **+6.1% precision, +64.7% recall, +40.9% F1**. On mini-SWE-agent, GSE reaches P=0.55 / R=0.29 / F1=0.38 vs the strongest baseline P=0.43 / R=0.22 / F1=0.29 — **+27.9% precision, +31.8% recall, +31.0% F1**. Across agents this corresponds to the abstract's headline range of +6.1%~34.1% precision and +31.8%~180.0% recall for test generation.
- **False-positive bug report filtering (Table 2).** On OpenHands, GSE reaches P=0.55 / R=0.95 / F1=0.70 vs the strongest baseline Trace2Skill at P=0.29 / R=0.84 / F1=0.43 — **precision +89.7%, recall +13.1%, F1 +62.8%**. On mini-SWE-agent, GSE reaches P=0.30 / R=0.97 / F1=0.46 vs P=0.26 / R=0.84 / F1=0.39 — **precision +15.4%, recall +15.5%, F1 +17.9%**. The dominant effect is a large precision jump, meaning GSE simultaneously surfaces more real bugs and flags far fewer false alarms.
- **Industrial deployment (Table 5).** On the proprietary ByteDance bug-triage agent (whose base F1=0.43 already exceeds both open-source agents), GSE reaches P=0.56 / R=0.97 / F1=0.71, a **+61.4% F1 improvement over human-written skills (0.44)** and +65.1% over the base agent — showing the gains transfer to a strong domain-specialized agent, not only lightweight open-source harnesses.
- **Ablation (Table 3).** Removing the SRG (`GSE_w/o graph`) drops F1 from 0.31→0.27 on test generation and from 0.70→0.59 on filtering; removing generalization (`GSE_w/o gen`) drops F1 to 0.27 and 0.54 respectively. Both components are individually necessary — neither the graph nor the consolidation/replay gate alone recovers full performance.
- **Cost (Table 4).** GSE's evolution cost is 401.55K tokens/case vs Trace2Skill's 357.64K (+12.28%). Strikingly, at task-execution time GSE consumes *fewer* tokens than every other skill method: 593.21K/case vs 620.58K (Human Skills), 613.61K (Live-SWE-agent), 619.65K (Trace2Skill) — a 3.3%~4.4% reduction — because the generalized skills induce more efficient reasoning/exploration. Human-written skills (authored by 6 senior engineers) give only marginal gains and on mini-SWE-agent actually *reduce* F1 from 0.28 to 0.26.

## Authors & Credibility

- Authored by a Tianjin University group (Yang, Tian, Wang, Liu, Chen) with one Tsinghua co-author (Ye); the senior author Junjie Chen works on automated debugging and test generation. The work is co-developed with an industrial partner explicitly named in the text as ByteDance ("a leading international IT company"), which lent both the proprietary code-review tool and the production repositories for IndustrialBugs.
- Methodology is unusually careful for an agent-evolution paper: one-project-held-out evaluation protocol on both tasks, temperature 0 for determinism, identical base LLM / tools / budget across all techniques, official OpenHands and mini-SWE-agent harnesses, released artifacts for Live-SWE-agent and Trace2Skill, a data-leakage check confirming none of GSE's generated tests match Multi-SWE-Bench reference tests, and the industrial partner's confirmation that the Go codebases are not in public LLM training corpora.
- Skill bank versioning via Git worktree + SQLite persistence of traces/replays is a reproducibility-friendly design choice that is explicitly called out.

## Critical Assessment

- **Novelty:** Genuine. The framing of skill evolution as global optimization, the explicit three-type SRG (dependency/co-usage/conflict) co-evolved with skill contents, and the replay-on-historical-activations validation gate are a clear conceptual step beyond Trace2Skill's "merge multiple analyst sub-agents at once" and Live-SWE-agent's online scaffold evolution. The DSL example (Figure 2) is small but concrete.
- **Rigor:** Strong on confound control (same LLM, same harnesses, held-out project, temp 0, leakage check). The ablation cleanly isolates both new components. The two case studies (Fig 3 cache-state bug; the nullability-conflict example for filtering) are illustrative but somewhat cherry-picked — they showcase exactly the conflict patterns GSE is designed to fix.
- **Reproducibility:** Mixed. IndustrialBugs is proprietary and will not be released (unavoidable, but it limits external verification of the RQ2 headline numbers and the industrial deployment). The Java benchmark (108 focal methods from Multi-SWE-Bench) and the GSE/agent code are described as implementable, but no public repo link is given in the body; the SRG construction and the "merge agent" prompt are described only at the algorithmic level, leaving the most subjective LLM steps under-specified.
- **Significance:** High for the coding-agent skill-evolution subfield; the finding that human-written skills can *hurt* (mini-SWE-agent F1 0.28→0.26) and that all local-update baselines barely move mini-SWE-agent (F1 0.28→0.29) while GSE reaches 0.38 is a meaningful data point. The execution-token *reduction* is a counterintuitive and useful result.
- **Red flags / overclaiming:**
  - The recall ranges in the abstract (+31.8%~180.0% for test generation) are dominated by the very low OpenHands base recall (0.06); the 180% figure is a small-absolute-number artifact and is presented without that caveat.
  - Baselines are hampered by a fairness issue the paper itself notes: Live-SWE-agent "originally designed to evolve tools" is *adapted* to skills, and Trace2Skill merges proposals "at once" — neither is run in its native strongest setting, which inflates GSE's relative gap.
  - Only one LLM (DeepSeek-V4-Flash) is used throughout; no test of whether GSE's gains hold with a different backbone, so the "generalizable" claim is under-tested along the model axis.
  - No statistical significance / multiple-seed analysis is reported despite LLM-agent evaluations being high-variance; temp 0 reduces but does not eliminate this (network, tool, and retrieval nondeterminism remain).
  - The SRG edges are themselves LLM-generated; there is no human audit of edge quality or of how often the "auxiliary proposal" propagation actually fires, so it is hard to tell how much of the SRG's benefit is structural vs. simply forcing the update agent to re-read neighbor skills.

## Strengths

- Conceptually clean motivation: the two challenges (cross-skill compatibility; generalization beyond originating traces) map directly onto the two mechanisms (SRG; consolidation + replay), and the ablation confirms both pull their weight.
- Strong and consistent empirical wins across two tasks, two open-source agents, one industrial agent, two languages (Java, Go), and three metric axes (P/R/F1).
- The execution-token result — GSE is the *cheapest* skill method at inference time — is a pleasant and important finding for practitioners worried about prompt-budget bloat from evolved skills.
- Honest about human-skill limitations: the paper does not hide that 6 senior engineers' hand-written skills gave near-zero or negative gains on the stronger agent.
- One-project-held-out protocol genuinely tests cross-project generalization rather than in-distribution memorization.

## Limitations

- IndustrialBugs is closed, so the strongest RQ2 numbers and the industrial-deployment result (the headline +61.4% F1) cannot be independently reproduced.
- Single LLM backbone (DeepSeek-V4-Flash); no GPT/Claude/Qwen comparison, so model-axis generalization is unverified.
- No statistical significance testing or multi-seed runs; given agent-execution variance, some of the smaller gaps (e.g., mini-SWE-agent filtering F1 0.39→0.46) warrant error bars.
- The SRG construction, edge typing, and the merge-agent prompts are under-specified; the most consequential and subjective steps rely on LLM judgment whose quality is not audited.
- Scope is limited to two SE tasks (test generation, FP filtering). Although the authors argue these exercise the "core capabilities" of SE agents, the claim that GSE generalizes to e.g. bug *fixing* or code *review* is asserted, not demonstrated.
- Evolution cost (+12.28% over Trace2Skill) is modest per case, but the paper does not report total wall-clock or $ cost of the full evolution pipeline, nor how the SRG scales as the skill bank grows (graph density, retrieval cost, replay-set size).

## Relevance

与用户对「LLM agent 自演化 / 技能系统 / 软件工程智能体」的研究兴趣高度相关：GSE 提供了一个把技能库当作带关系图的系统进行全局优化的新范式，并给出了在真实工业 Agent 上显著增益的证据，可作为自演化 agent 与 skill library 方向的重要参考工作。

## Questions for Further Exploration

- How much of GSE's gain comes from the SRG's *structure* (edge types, propagation) vs. simply forcing the update agent to re-read semantically related skills? An ablation that replaces the SRG with flat top-k neighbor retrieval would isolate this.
- Do the SRG edges survive human audit? What fraction of dependency/co-usage/conflict edges are correct, and how often does the auxiliary-proposal propagation actually fire and change the outcome?
- Does GSE transfer to a different LLM backbone (e.g., GPT, Claude, Qwen), or are the evolved skills tightly coupled to DeepSeek-V4-Flash's reasoning style?
- How does GSE behave on SE tasks where the "right answer" is open-ended (bug fixing, code review, refactoring) rather than the binary TP/FP classification studied here?
- As the skill bank grows, does replay-set size scale linearly, and does the SRG become noisy enough to hurt retrieval — i.e., is there a steady-state skill-bank size, and does GSE ever *prune* or retire skills?
- The execution-token reduction is intriguing: is it driven by shorter trajectories, fewer tool calls, or smaller retrieved-skill prompts? A trajectory-length / action-count breakdown would clarify the mechanism.
- Could the cluster-based consolidation step be gamed by adversarial or low-quality proposals, and does replay-driven validation catch semantic regressions that preserve surface metrics?
