> **一句话总结：** 提出 TRAJDEBUG，一个三阶段的"错误生命周期追踪"框架——通过多粒度历史压缩定位长轨迹中的本地错误、用证据约束的触发器检测并按错误状态（已修复/活跃/有终端影响）分类、再做候选集引导的因果归因，从而找出导致最终失败的最早关键错误步；配套构建了 486 条人工标注的 TRAJERRBENCH 基准，平均关键步检测准确率 34.11%（较同骨干直接提示 +8.42），并把诊断作为反馈使下游 agent 成功率提升约 10.80 个百分点。

> **TL;DR:** TRAJDEBUG reframes critical error detection in failed LLM-agent trajectories as an error-lifecycle tracing problem: multi-granularity history compression + verbatim-evidence error triggers + four-state error classification (resolved/active × footprint/no-footprint) + candidate-set-guided causal attribution. On a suite spanning AgentDebugBench, WhoAndWhen, and the new 486-trajectory TRAJERRBENCH (τ²-Bench + SWE-Bench Pro), it reaches 34.11% average critical-step accuracy versus 25.69% for direct prompting with the same Qwen3-235B-A22B-Thinking backbone (+8.42), and beats frontier-model and multi-agent baselines; when its diagnoses are fed back to a GLM-5.1 actor it lifts task success from 78.07 to 88.87 (+10.80 avg) on τ²-Bench/SWE-Bench Verified.

## 核心贡献

- **提出 TRAJDEBUG 框架**：将"关键错误检测"分解为三阶段流水线——错误触发器检测、错误状态分类、候选集引导的因果归因；把以往"对整条轨迹做一次性判断"转化为"找证据支撑的本地错误 → 判定状态 → 从剩余候选中选因果责任步"的可审计流程。
- **多粒度历史压缩**：对每个步保留高/中/低三种细节视图，本地验证用高细节、远距离上下文用压缩视图，在不牺牲可验证证据的前提下缓解长上下文负担。
- **证据约束的触发器与四态分类**：每个错误触发器必须满足"逐字证据"条件（错误承诺 qw 与被违反参照 qr 都必须可引用），按参照类别（任务冲突/历史冲突/步内冲突/环境异常）与执行阶段组织，并聚合成"已修复/活跃 × 有/无终端足迹"四种状态，从而把被修复或休眠的错误与真正导致失败的错误区分开。
- **构建 TRAJERRBENCH 基准**：486 条人工标注的失败轨迹，400 条来自 τ²-Bench（平均 29.3 步，客服工具使用），86 条来自 SWE-Bench Pro（平均 119.7 步，长程代码工程），关键步标注在 τ²-Bench 上 Fleiss' κ=0.91，在 SWE-Bench Pro 上 κ=0.67。
- **应用价值验证**：把诊断作为反馈注入下游 actor，逐轨迹修复场景成功率从 78.07 提升到 88.87（+10.80 平均），失败记忆迁移到未见任务上仍有 +5.70 平均提升。

## Key Contributions

- **TRAJDEBUG, an error-lifecycle tracing framework** that decomposes critical error detection into three controlled stages instead of a single end-to-end judgment over the full trajectory: (1) evidence-grounded error trigger detection, (2) object-anchored error instance clustering with four-state classification, and (3) candidate-set-guided causal attribution.
- **Multi-granularity history compression** that builds high-/medium-/low-detail views per step, preserving verifiable local evidence while keeping distant context compact — this single component accounts for a 21.02-point AVG swing in ablation.
- **A verbatim-evidence trigger schema and four error states** (Clean Resolution, Costly Resolution, Manifest Active, Latent Active) that turn subjective "is this step wrong?" judgments into an auditable verification problem and filter out repaired/dormant errors before final attribution.
- **TRAJERRBENCH**, 486 manually annotated failed trajectories from τ²-Bench (tool-use/customer-service) and SWE-Bench Pro (long-horizon coding, ~120 steps), with near-perfect annotator agreement on τ²-Bench (Fleiss' κ=0.91) — explicitly complementing existing single-domain, shorter benchmarks.
- **Two inference-time application studies** showing critical-error diagnoses convert failed rollouts into actionable feedback: +10.80 avg success gain in per-trajectory repair and +5.70 avg in failure-memory transfer to held-out tasks.

## Methodology

TRAJDEBUG takes a failed trajectory τ = (x₁, …, x_N) and locates the **critical error step** — the earliest *decisive* step (Zhang et al., 2025c) whose replacement by a correct action would have flipped failure to success.

**Stage 0 — Multi-granularity compression (§3.1).** For every step the LLM constructs three views: (1) high-detail = original instruction/action/observation plus locally relevant reasoning; (2) medium-detail = summarized intent, action, state update; (3) low-detail = coarse progress, salient entities, unresolved commitments. Each downstream stage pulls the finest view it needs (high for local verification, compressed for distant context).

**Stage 1 — Error trigger detection (§3.2).** For each step, given the trajectory prefix, the detector extracts atomic triggers e = (t, c, p, q_w, q_r), where q_w is an erroneous commitment in the current step, q_r the violated reference, c the reference category, and p the execution phase (planning/reasoning/action/observation/verification). Reference categories are: **Task Conflict** (q_r from task instruction), **History Conflict** (from prior trajectory/tool output), **Intra-Step Conflict** (from the same step), and **Environment Anomaly** (exogenous). A strict verbatim-evidence condition discards any trigger whose q_w or q_r cannot be explicitly cited, which the authors argue suppresses hallucinated diagnoses (Gao et al., 2023).

**Stage 2 — Error state classification (§3.3).** Triggers violating the same reference object O are clustered into an instance E = (E, O) to avoid overcounting repeated manifestations. Each instance gets two judgments: (a) *resolved vs. active* — resolved only if later steps explicitly revisit O with citable superseding evidence; (b) *terminal footprint* — present if there is an irreversible state change, a semantic footprint reflected in the terminal state, or budget debt (resolved only after consuming >50% of the trajectory). This yields four states: **Clean Resolution**, **Costly Resolution**, **Manifest Active**, **Latent Active**. Only terminal-relevant instances (Costly Resolution, Manifest Active) survive into the candidate set F(τ).

**Stage 3 — Candidate-set-guided causal attribution (§3.4).** A final LLM head selects, from F(τ), the instance whose origin step best explains the terminal failure. Crucially this is *not* "earliest candidate wins": temporal order alone is insufficient because an earlier budget-debt instance should not outrank a later semantic one unless the wasted budget plausibly caused the later failure. An out-of-set prediction is allowed only under strict evidence requirements (the model must explain why no retained candidate accounts for the failure and supply the missing trigger/reference/origin/footprint).

**Pilot study motivation (§2).** On 50 sampled failed trajectories, the authors find 381 local errors (avg 7.62 per trajectory) yet only one critical error each; of the 331 non-critical errors, 61.9% are later repaired, 31.4% persist, and only 6.6% are unrepaired-but-dormant — empirically justifying the need to model error *state*, not just error *occurrence*.

## Results & Highlights

- **Best overall critical-step accuracy (Table 1):** TRAJDEBUG reaches **34.11% macro-average** across all seven benchmark splits, beating the strongest direct-prompting model Gemini-3.1-Pro (31.29%) and all three multi-agent systems (AgentDebugger 23.72%, AgentRX 23.10%, CHIEF 18.77%). It ranks first on five of seven datasets.
- **Same-backbone gain:** Implemented with Qwen3-235B-A22B-Thinking, TRAJDEBUG lifts average accuracy from **25.69% (Qwen3 direct prompting) to 34.11% (+8.42)**, demonstrating the gain comes from the framework, not a stronger judge.
- **Long-horizon robustness:** On the two longest benchmarks — ALFWorld (60.0 steps avg) and SWE-Bench Pro (119.7 steps avg) — TRAJDEBUG attains the best accuracy with gains of **+13.00% (ALFWorld) and +6.97% (SWE-Bench Pro, 24.41 vs Gemini's 17.44)** over the corresponding best direct baseline. Length-bucket analysis (Figure 5) shows it retains **>20% accuracy on the longest (141+ step) bucket where the best baseline drops to ~14%**.
- **Ablation (Table 2):** Removing multi-granularity compression collapses AVG from 38.58 to 17.56 (**−21.02 points**, the largest drop); removing trigger detection costs −4.99 and removing state classification costs −7.31. On SWE-Bench Pro, dropping state classification falls to 16.28, *below* the 17.44 direct-prompting baseline — confirming the paper's thesis that long trajectories need state-based filtering.
- **Application — per-trajectory repair (Table 3, oracle failure):** Feeding TRAJDEBUG's diagnosis into GLM-5.1 raises task success from 78.07 to **88.87 (+10.80 avg)**, beating Vanilla Debug (88.07) and Self-Reflection (85.20). Per-domain: Airline 78.00→90.00 (+12.00), Retail 84.21→95.61 (+11.40), SWE-Bench 72.00→81.00 (+9.00).
- **Application — failure-memory transfer (Table 3, realistic, held-out tasks):** Aggregating diagnoses from a 1/3 memory split and injecting into unseen tasks yields **+6.06 (Airline), +6.57 (Retail), +4.48 (SWE-Bench)** — avg +5.70, whereas Vanilla Debug and Self-Reflection are unstable and can *hurt* (e.g., Vanilla −3.03 on Airline).

## Critical Assessment

- **Novelty — genuine, well-scoped.** The error-lifecycle framing (trigger → state → attribution) and the four-state taxonomy (Clean/Costly Resolution, Manifest/Latent Active) are a real conceptual advance over CHIEF's connectedness proxy and AgentRX's constraint-only flagging. The verbatim-evidence condition on triggers is a clean, falsifiable mechanism for suppressing hallucinated diagnoses.
- **Rigor — strong on the central claim, weaker on the application claim.** The main-detection table compares against 7 frontier direct-prompting models *and* 3 multi-agent systems under a uniform "failed trajectory + failure signal only" protocol — this is the right realistic setting. However, the application study (Table 3) is thin: only 3 task settings (Airline, Retail, SWE-Bench Verified-100), **no confidence intervals or significance tests** are reported, and the per-trajectory repair scenario assumes an *oracle failure signal*, which is a strong, arguably unrealistic assumption for production. The failure-memory transfer uses a single 1/3–2/3 split with no variance reported.
- **Reproducibility — mixed.** Backbone (Qwen3-235B-A22B-Thinking), temperature 0, and benchmark provenance are specified, and MIT release is promised; but the LLM-based compression/attribution stages are prompt-dependent and the multi-granularity view-construction prompts are deferred to appendices not shown in the main text. The k=50 budget-debt threshold and the four-state definitions are concrete enough to reimplement.
- **Significance — high if it holds up.** The pilot-study statistic (7.62 local errors per failed trajectory, only 1 critical, 61.9% repaired) is a valuable empirical contribution by itself and directly motivates the design. The TRAJERRBench annotation effort (κ=0.91 on τ²-Bench) is a durable artifact.
- **Red flags / things to probe.** (a) **Absolute accuracies remain low** — 34.11% average means the framework still mislocalizes the critical step in ~2/3 of cases; the paper is honest about this but it tempers the application claims. (b) **Backbone confound in application study:** the detector uses Qwen3 while the actor is GLM-5.1 — it is unclear whether gains come from diagnosis quality or from cross-model prompt diversity. (c) **CHIEF's collapse to 2.32% on SWE-Bench Pro** is suspicious and suggests SWE-Bench Pro may be systematically hard for *all* graph/counterfactual methods in ways that flatter TRAJDEBUG's design — a head-to-head error analysis would strengthen the claim. (d) **No ablation of the budget-debt threshold k=50** or the reference-category taxonomy, despite both being load-bearing. (e) The benchmark mixes two very different domains; macro-average over 7 splits of wildly different sizes (e.g., 50 vs 400 trajectories) gives undue weight to small subsets.

## Strengths

- Clean problem decomposition: three stages each address one of the two stated challenges (long context → compression; error ambiguity → state classification).
- The verbatim-evidence condition on triggers is a principled anti-hallucination lever that prior prompt-based detectors (WhoAndWhen, AgentDebugger) lack.
- TRAJERRBench fills a real gap: existing critical-error benchmarks (WhoAndWhen, AgentDebug, TRAIL, CodeTracer) are single-domain and short; the ~120-step SWE-Bench Pro split is the longest annotated to date.
- Honest, fine-grained reporting: per-dataset tables, length-bucket analysis, ablation isolating each component, and explicit acknowledgment that absolute accuracy is low.
- The failure-memory transfer experiment is a genuinely novel framing — turning a *diagnostic* tool into a *data-augmentation* source for agent improvement.

## Limitations

- **Pipeline fragility:** as a staged system, false negatives in trigger detection or state classification propagate — the out-of-set escape hatch mitigates but does not eliminate this. The authors acknowledge this explicitly in §9.
- **LLM dependence:** despite evidence constraints, final interpretation and attribution still rely on the backbone's reasoning/calibration; gains could shrink or vanish with weaker open-source models (only Qwen3-235B-A22B-Thinking is tested for the framework itself).
- **Low absolute accuracy (~34%)** means the tool is currently a *triage aid*, not a reliable locator — the application-study gains may not transfer to settings where the actor cannot compensate for a mislocalized hint.
- **Narrow application evaluation:** 3 tasks, no significance testing, oracle failure signal in the main repair setting.
- **No tuning study** for the k=50 budget-debt threshold or the reference-category definitions, leaving their sensitivity unknown.

## Relevance

这篇文章直接命中「LLM agent 调试 / 失败归因 / 长程轨迹分析」这一核心方向：它把「找到导致最终失败的关键错误步」形式化、给出可审计的多阶段方法与配套的长轨迹基准 TRAJERRBENCH，与我对 agent 可靠性、过程监督和可解释失败分析的研究兴趣高度一致，其「错误状态分类」与「把诊断转为可迁移失败记忆」的思路对构建自进化 agent 也很有借鉴价值。

## Questions for Further Exploration

- How does TRAJDEBUG's accuracy scale with the detector backbone — does the +8.42 gain hold for smaller open models (e.g., 7B–32B), or does the evidence-verification stage itself require frontier-grade reasoning?
- The four-state taxonomy assumes errors are *either* resolved *or* active; could partially-resolved errors (fixed in some branches but not others) be modeled, especially in multi-agent / multi-attempt settings?
- Can the verbatim-evidence trigger condition be made self-verifying (e.g., a second model re-cites the span) to further suppress the residual hallucinated diagnoses implied by the ~66% error rate?
- The failure-memory transfer uses a 1/3 memory split — how does transfer quality scale with memory-pool size, and is there a saturation point or does noise eventually dominate?
- On SWE-Bench Pro, where CHIEF collapses to 2.32% — is the failure method-specific (graph/counterfactual methods fail on code) or benchmark-specific (annotation artifacts)? An error-category-stratified analysis would clarify.
- Could the budget-debt footprint (k=50) be made adaptive to task length, since "half the trajectory" means very different recovery budgets for a 30-step vs 120-step rollout?
