> **一句话总结：** AMD 提出 Primus 系统，用"单节点微基准实测 + 解析式升级（PP→EP→TP 缩放-测量-还原）"的混合投影引擎把多节点 LLM 训练配置的吞吐/显存预测误差压到 ~10% 以内（DeepSeek V3 671B 在 1,024 GPU 上仅 4.7% 误差，Qwen3-235B 在 256 GPU 上 1.9%），再以投影为快速打分器驱动"确定性种子规划器 + LLM 调查循环"的自动调参 Agent，30 分钟单节点探索即为 Mixtral 8×22B 找到比 AMD 官方 4 节点 BF16 基准高 27% 吞吐的配置。

> **TL;DR:** Primus Projection replaces expensive multi-node trial-and-error for LLM training configs with a hybrid engine that benchmarks kernels on as few as 1 GPU and analytically restores pipeline schedules, FSDP overlap, and out-of-scope collectives at the target scale (plus a CPU-only pre-silicon simulation mode). Validated on Llama 3.1 and Mixtral 8×22B across MI325X/MI355X, all projections stay within ~10% of measured throughput — e.g., Mixtral 8×22B at 4 nodes/32 GPUs: projected 3,688 tok/s/GPU vs. 3,475 measured (+6.1%) from a 1-GPU benchmark, tightening to +1.6% at 8 GPUs; at production scale it hits 4.7% error on DeepSeek V3 671B (1,024 GPUs: 2,808 projected vs. 2,946 measured) and 1.9% on Qwen3-235B-A22B (256 GPUs). The Primus Tuning Agent (deterministic seed planner + Claude-based DSPy LLM loop with an analytic memory pre-filter) uses the oracle to search the joint config space, beating a Galvatron-style exhaustive 530-config FP8 sweep (4,698 vs. 3,656 tok/s/GPU projected) and delivering +27% measured throughput over AMD's published 4-node BF16 Mixtral reference (4,402 vs. 3,475 tok/s/GPU) in under 30 minutes of single-node exploration.

## 核心贡献

- **混合投影引擎（Primus Projection）**：把"能实测的实测、不能实测的解析建模"系统化——GPU 微基准（最少单卡即可）捕获计算内核与基准范围内的通信；PP→EP→TP 优先级的"降规模-测量-升规模"工作流在目标多节点规模上解析还原流水线调度（1F1B/Interleaved/Zero-Bubble/ZBV/ILP 共 6 种）、FSDP 重叠与跨节点集合通信，无需启动任何多节点作业。
- **纯 CPU 仿真模式**：内核时间来自 Origami GEMM 解析模型 + tile 级 FlashAttention-3 仿真器，可在笔记本上做预硅芯（pre-silicon）硬件探索，硬件规格以 YAML 描述即可扩展新 GPU。
- **Primus 调参 Agent**：以投影引擎为秒级打分器，两阶段搜索——确定性种子规划器扫单轴（12 个候选），LLM 调查循环（DSPy 实现，Planner=Claude Sonnet 4.6 + RLM=Claude Opus 4.6，ReAct 风格）提出种子规划器无法触及的跨轴组合；解析显存预过滤器在任何 GPU 时间消耗前拒绝 OOM 配置。
- **高保真 + 排序保持的实证**：稠密（Llama 3.1）与 MoE（Mixtral 8×22B）模型、两代 GPU（MI325X/MI355X）上投影误差全部 ~10% 以内；生产规模 DeepSeek V3 671B（1,024 GPU）误差 4.7%、Qwen3-235B-A22B（256 GPU）1.9%；三个 MoE 模型上 Spearman ρ ≥ 0.93 且选择遗憾（selection regret）为 0%。
- **MoE 负载均衡鲁棒性分析**：区分"强制均衡基准 / 真实训练 I≈1.1–1.3 / 故意压力测试 I≤4"三种情形，提出 busiest-rank 修正，把失衡情形的最坏误差从 53–71% 压到 10% 以内，并证明训练好的 DeepSeek V3 检查点上步级合并失衡仅 1.05–1.12。

## Key Contributions

- **Hybrid projection engine (Primus Projection):** measures what it can and simulates what it cannot — GPU microbenchmarks on as few as a single device capture compute kernels and in-scope collectives, while a downscale–measure–upscale workflow (reduction priority PP → EP → TP, CP never reduced) analytically restores the full pipeline schedule, FSDP overlap, and inter-node communication at the multi-node target. Per-iteration time composes as `iter_time = T_pipe({t_l}, N_µB, schedule) + FSDP_exp + grad_AR_exp + opt_step`.
- **CPU-only simulation mode:** layer kernel times come from the Origami GEMM analytical model and a tile-level FlashAttention-3 simulator, enabling pre-silicon planning for hypothetical future GPUs described only by a hardware-profile YAML (bundled: MI300X, MI325X, MI355X).
- **Primus Tuning Agent:** a two-phase search over the joint config space (TP/PP/VPP/EP/CP/DP, micro-batch, recompute, precision, MoE backend, overlap flags) using the projection oracle as a seconds-per-candidate surrogate: a deterministic seed planner emits 12 single-axis candidates into a shared trial ledger; an LLM investigation loop (DSPy, Planner = Claude Sonnet 4.6 with ChainOfThought, Recursive LM = Claude Opus 4.6 in a ReAct-style tool loop, ≤25 candidates/round × ≤4 rounds) proposes cross-axis combinations; an analytic memory pre-filter rejects OOM-bound candidates before any GPU time (~25 min saved per rejection), with legality = axes tile the cluster ∧ projected memory ≤ 0.9×(HBM − overhead) ∧ parseable throughput.
- **Validation of fidelity AND ranking:** absolute errors within ~10% across two model families, two precisions, two GPU generations; rank-preservation tested with fully-measured paired sweeps — Spearman ρ = 1.000 on Mixtral-8×22B (n=7) and Qwen3-235B-A22B (n=7), ρ = 0.933 on GPT-OSS-120B (n=9, all 3 discordant pairs within a ~9% near-tie band), selection regret 0% everywhere — establishing that the ~10% workload-level calibration offset (k = 0.90–1.24) does not reorder candidates.
- **MoE load-balancing robustness theory + correction:** separates forced-balanced benchmarking (I = 1 by construction), real training (steady-state I ≈ 1.1–1.3), and deliberate stress tests (I up to 4×); a busiest-rank correction (grouped-GEMM time gated by I at experts-per-rank E/EP, plus an A2A regime term) cuts worst-case error from 53–71% to under 10%, and on a trained DeepSeek V3 checkpoint per-layer median imbalance (1.38 at EP=8) collapses to step-level pooled imbalance 1.05–1.12 because the busiest device rotates layer-to-layer.

## Methodology

Primus Projection is a modular pipeline of five components: (1) analytical memory projection via a hierarchical profiler tree mirroring the model's module structure — returns sharded per-GPU parameter/gradient/optimizer-state counts plus per-microbatch activation memory, treating precision as two independent axes (parameter/optimizer regime vs. saved-activation regime with byte costs, e.g., BF16+Adam = (2,2,10) bytes, FP8 weight = 1 B) and composing recompute, interleaving, and gradient accumulation; (2) layer profiling — benchmarks a minimal set of layer types (one dense, one MoE), timing forward/backward separately, with MoE compute and All-to-All measured independently so A2A can be swapped analytically at upscale; (3) topology-aware communication modeling across intra-node (xGMI ~1,024 GB/s, 0.45 µs) / inter-node (~50 GB/s per NIC, 2.0 µs) / inter-pod (~25 GB/s, 10 µs) domains, enumerating algorithm candidates per collective (ring/hypercube/Bruck/single-shot AllReduce; direct/hierarchical/PXN-DeepEP A2A) and picking the minimum-time one; (4) exact pipeline-schedule simulation over six algorithms from per-stage time matrices; (5) multi-node scaling. The sub-node workflow (Algorithm 1) downscales along PP first (schedule exactly replayable, so no compute information is lost), then EP (num_experts scaled so experts/rank — hence grouped-GEMM time — is preserved, leaving only the A2A delta), then TP (compute rescaled by bench_tp/target_tp plus an AllReduce delta, improved by a ratio form AR* = AR_meas × analytical*/analytical_bench); CP is never reduced. This ranking (PP exact → EP preserves compute → TP relies on a scaling assumption) matches restoration fidelity. The engine defaults to benchmark mode (real kernels, ~8 min on 8 GPUs) but supports simulate (no GPU) and both (side-by-side cross-validation). The Primus Tuning Agent layers search on top: the seed planner sweeps memory frontier (full→selective→no recompute), MoE backend (A2A vs. DeepEP), pipeline schedule/VPP depth, and second-order axes (MBS, distributed optimizer), all anchored on the user baseline; the LLM loop then reads the shared ledger and proposes JSON candidates the single-axis planner cannot reach (the paper's example: MBS=1 × no-recompute × DeepEP). MoE benchmarking forces uniform load via a random straight-through router (never used in real training), and the memory pre-filter's predictions matched hardware perfectly: every config projecting ≤ cap ran, every config > cap OOMed.

## Results & Highlights

- **Sub-node projection accuracy (MI325X dense targets, 8 nodes/64 GPUs):** Llama-3.1-8B FP8 measured 16,186 tok/s/GPU vs. 1-GPU projection 17,619 (+8.9%, Max Δ across benchmark counts only 0.1%); Llama-70B FP8 FSDP measured 1,726 vs. 1,825 at 8 GPUs (+5.7%); Llama-70B BF16 measured 1,174 vs. 1,086 (−7.5%) — all 12 dense cells within ±9%.
- **MoE full-pipeline projection (Mixtral 8×22B, MI355X, 4 nodes/32 GPUs, BF16 reference 3,475 tok/s/GPU):** errors shrink from +6.1% (1-GPU benchmark, all communication modeled analytically) to +1.6% (8 GPUs) as analytical components are replaced by measurement, exercising PP=1→4 restoration, EP A2A modeling, VPP=2 interleaved simulation, and MoE gradient-AllReduce decomposition; Max Δ 4.9%.
- **Production-scale fidelity:** DeepSeek V3 671B FP8 at 1,024 GPUs/128 nodes — agent-selected recipe (PP=8/VPP=2/EP=8/ZBV, GBS=32,768) projected 2,808 vs. 2,946 measured tok/s/GPU (4.7% error); Qwen3-235B-A22B FP8 at 256 GPUs — 4,860 vs. 4,952 (1.9%). On DeepSeek the agent's "batch to the memory ceiling" insight alone lifted projected throughput 1,869 → 2,808 tok/s/GPU (+50%).
- **Tuning case study (Mixtral 8×22B, FP8, 4-node MI355X):** seed planner reaches 4,036 tok/s/GPU projected (+16.1% over the 3,475 BF16 reference); the LLM's first cross-axis proposal (MBS=1 + no recompute + DeepEP) jumps to 4,908 projected (+41.2%); on the real cluster the best config measures 4,402 tok/s/GPU (+27% over AMD's published 4-node BF16 reference; projection bias −10.3%), all in ~30 minutes of single-node exploration, with the memory pre-filter rejecting 7 of 30 trials at zero GPU cost (~175 GPU-min saved).
- **Rank preservation:** Spearman ρ / Kendall τ = 1.000/1.000 on Mixtral-8×22B FP8 (n=7) and Qwen3-235B-A22B FP8 (n=7), 0.933/0.833 on GPT-OSS-120B BF16 (n=9); selection regret 0% on all three — the agent always picks the measured-optimal config, and every pair separated by >~9% measured throughput is ordered correctly.
- **Head-to-head vs. Calculon (Llama-3.1-70B, MI325X, 8 nodes/64 GPUs):** Primus mean absolute error 6.6% vs. Calculon's 28.9%; Calculon's opposite-sign errors (+16.2% FP8, −41.6% BF16) inflate the true 1.5× FP8–BF16 throughput gap to 2.9×, and Calculon cannot express MoE/All-to-All/ROCm at all.
- **Head-to-head + ablation vs. Galvatron-style search (Mixtral, 4-node, FP8, baseline 3,368 projected tok/s/GPU):** exhaustive 530-config FP8 sweep with Primus's own simulate oracle reaches only 3,656 vs. 4,698 for Tuning Agent + Benchmark (+28%); ablation attributes +36% to the benchmark oracle (vs. simulate) and +10% to the agent framework (vs. a bare Claude Code agent with the same oracle); a Galvatron-style search with the agent's 30-trial budget stays BF16 and lands at 2,155 (−36%, below the untuned baseline) because it lacks a precision knob.
- **Communication model and pipeline schedules:** 4.2% average error across 11 collective/topology combinations at training-relevant message sizes ≥64 MB on MI325X (small latency-dominated messages err 20–30%); on Llama2-7B/MI300X/PP=8, Zero-Bubble beats 1F1B by 13% (11,411 vs. 10,057 tok/s) at only 2% memory overhead, with ZBV within 1% of Zero-Bubble.
- **Memory projection insight:** for Mixtral 8×22B at 4 nodes (PP=4, EP=8, VPP=2, no recompute), per-rank activation memory is 197.83 GB — 2.5× the 79.26 GB parameter+optimizer budget (total 277.09 GB) — quantifying why recompute/MBS/activation-precision are first-class tuning axes.
- **MoE load-balancing stress test:** with balancing disabled and imbalance swept 1×–4× on MI355X, the uncorrected uniform-load model errs up to 53.1–70.8% (DeepSeek V3 / Mixtral), while the busiest-rank correction keeps worst-case error under 10% (Qwen3: 3.3%); on the trained DeepSeek V3 checkpoint the corrected error at EP=8 is ≈2%.

## Authors & Credibility

All ten authors (Anshu Raina, Peyman Razaghi, Yuankai Chen, Cheng Yao, Yao Fu, Vidushi Goyal, Devang Patel, Wen Xie, Zhenyu Gu, Emad Barsoum) are employees of Advanced Micro Devices, Inc., with funding and conflicts disclosed as AMD-only — the work is accepted at NeurIPS 2026. Credibility is bolstered by unusually careful methodology: ground truth comes from AMD's published ROCm performance results page plus their own measured runs; the Calculon baseline was first reproduced against Calculon's own published A100 numbers (3.65% avg error) before the head-to-head; the Galvatron-style baseline was deliberately handed Primus's more expressive simulate oracle ("an advantage to the baseline"); rank-preservation sweeps are fully measured per config; and the MoE load-balancing analysis cleanly separates benchmark, training, and stress regimes with a mechanism-level explanation of why pooled imbalance (1.05) dominates per-layer imbalance (1.38). The claims are framed honestly — the paper explicitly reports its own ~10.5% optimistic projection bias and the 3 discordant GPT-OSS pairs rather than hiding them. The framework is stated to be open-sourced (auditable oracle, planner, and agent loop).

## Critical Assessment

- **Novelty: solid but compositional.** The core ideas — microbenchmark-anchored cost modeling, analytical restoration of reduced parallelism axes, and LLM-driven config search — each have precedents (Calculon, Galvatron, ASTRA-sim, AgentHPO/LLAMBO); the contribution is the coupling: a single-node benchmark oracle accurate enough that an LLM loop can exploit it, plus the downscale priority ordering (PP→EP→TP) justified by restoration-fidelity analysis. The claim of being "the first" to couple a benchmark-anchored projection oracle with an LLM cross-axis loop is plausible but narrow.
- **Rigor: high, with a few soft spots.** The rank-preservation analysis is the strongest part (fully measured paired sweeps, discordant-pair forensics identifying mbs16's k=1.235 offset as the sole reversal driver). But the sweeps are small (n = 7/7/9 configs), and "0% selection regret" on 7–9 candidates is weak evidence for regret over the O(10^4)-point space the agent nominally searches. The Galvatron comparison is a reimplementation "in the spirit of" the original (forced to uniform per-layer parallelism for Megatron compatibility), not the actual Galvatron system, and the "Claude Code agent" ablation baseline is a bare LLM without the DSPy framework — both comparisons somewhat favor the authors' design choices.
- **The +27% headline mixes precision with tuning.** The winning Mixtral config is FP8 hybrid compared against AMD's published BF16 reference (3,475 tok/s/GPU), so part of the +27% is simply the BF16→FP8 switch, which is one of the agent's search axes but not a tuning insight. The paper partially defuses this in the ablation (a Galvatron-style FP8 sweep reaches 3,656, still 22% below the agent's 4,698), yet the headline number as stated would be smaller against an FP8-tuned reference. The agent's measured 4,402 also sits −10.3% below its own projection, consistent with the acknowledged systematic optimistic bias.
- **Vendor lock-in of the evidence.** Everything is validated on AMD Instinct (MI300X/MI325X/MI355X) + ROCm, against AMD's own performance page, by AMD employees with a clear incentive to portray the ROCm stack favorably. The vendor-neutrality argument (YAML hardware profiles, benchmark runs "on any supported GPU") is architecturally convincing but empirically unverified on NVIDIA or TPU — explicitly admitted in Appendix I. Related-work competitors with comparable numbers (Lumos: 3.3% average error up to 512 H100s) are mentioned but not compared head-to-head.
- **Reproducibility: good on paper, contingent in practice.** Verbatim LLM prompts, search traces, and per-config appendices are provided and the framework is claimed open-source, but the agent depends on proprietary Claude Sonnet/Opus 4.6 models via LiteLLM (cost and availability unstated — no token/cost accounting for the agent loop is given), requires an idle benchmark node (co-located load is shown to corrupt the oracle), and assumes homogeneous nodes and clocks. Unmodeled network contention is acknowledged as a possible error source at extreme scale, and ZeRO-2 is excluded with only a one-line justification.
- **Red flags: minor.** The "MoE priority order" hint (~35% DeepEP win) is baked verbatim into the Planner prompt (Appendix H), meaning part of the agent's apparent intelligence may be hand-encoded domain priors rather than discovered reasoning — the seed-planner-vs-LLM ablation (+21.6%) doesn't isolate how much the prompt hints contribute. FP8 recipes are throughput-only predictions with convergence explicitly out of scope.

## Strengths

- Turns the "measure what you can, model what you cannot" principle into a principled, fidelity-ranked downscale order (PP exact → EP compute-preserving → TP approximate) with auditable per-dimension deltas.
- Exceptional scale of validation for a systems paper: from 1-GPU benchmarks up to a 1,024-GPU/128-node DeepSeek V3 run at 4.7% error, on architectures (MLA, 3-dense+58-MoE mix) never seen during development.
- The rank-preservation study directly tests the property search actually needs (ordering, not absolute accuracy), including why opposite-sign offsets (Mixtral k=1.13, Qwen3 k=0.90) both preserve ordering exactly.
- Honest error accounting: reports optimistic bias, discordant pairs, idle-node requirement, and the FP8-vs-BF16 reference caveat in the ablation.
- The MoE load-balancing appendix is a genuinely useful standalone contribution — the pooled-vs-per-layer imbalance decomposition (max_r Σ_l n_{l,r} ≤ Σ_l max_r n_{l,r}) explains why real training stays near-uniform at the step level.
- Strong practical economics: ~30 min of single-node exploration replacing days of multi-node sweeps; memory pre-filter with perfect OOM agreement on hardware.

## Limitations

- Validated only on AMD Instinct/ROCm; NVIDIA/TPU porting is argued but untested.
- Network contention, node heterogeneity, and GPU-to-GPU clock variation are unmodeled.
- Absolute throughput carries a systematic ~10% multiplicative calibration offset (k up to 1.235 on large-MBS full-recompute configs); fine for ranking, misleading if read as a prediction.
- Rank-preservation evidence covers only 3 MoE models with 7–9 configs each; no large-scale study of regret over the full O(10^4) space.
- The agent searches only axes exposed as oracle flags; new optimizations (e.g., a new MoE A2A backend) require extending both oracle and planner; ZeRO-2 is excluded.
- Precision is a throughput knob only — FP8 recipes need separate convergence validation.
- LLM-loop operating cost, token usage, and sensitivity to the backbone model are not reported; prompts embed hand-written MoE priority hints that blur the line between learned search and encoded expertise.

## Relevance

对关注"大规模 LLM 训练系统与效率"的方向高度相关：论文把并行策略（TP/PP/EP/CP/DP）、MoE 通信后端、显存-吞吐联合调参这一实际训练中最耗 GPU 时间的问题形式化为"投影预言机 + LLM Agent 搜索"，其单节点预测多节点、保序不保绝对值的思路对任何需要在大集群上跑 MoE/稠密模型训练的人都有直接工程参考价值。

## Questions for Further Exploration

- How much of the LLM loop's +21.6% advantage over the seed planner survives if the hand-written MoE priority hints (e.g., "~35% DeepEP win") are stripped from the Planner prompt — is the agent discovering structure or replaying encoded expertise?
- Does the ~10% multiplicative calibration offset stay stable across ROCm releases, and can a single measured anchor config per workload calibrate it away without breaking rank preservation?
- How does the projection degrade under realistic network contention (multiple jobs sharing inter-node fabric) and heterogeneous clusters — the two explicitly unmodeled regimes?
- Can the busiest-rank load-balancing correction be extended to predict throughput during early training when router balance is still converging (I potentially ≫ 1.3)?
- What is the token cost and latency budget of the Claude-based agent loop, and could a small open-source model with the same DSPy scaffold match it given the oracle does the heavy lifting?
- Would the downscale–measure–upscale methodology transfer to inference/serving workloads (continuous batching, KV-cache pressure) where activation-memory and communication patterns differ fundamentally from training?
