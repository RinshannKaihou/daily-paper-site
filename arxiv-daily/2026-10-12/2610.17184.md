> **一句话总结：** Google/UC Berkeley/Stanford 提出的 DuoDiscover 让一队编码智能体同时"共同发现"优化目标（target）和廉价的代理评估器（yardstick），在内环以秒级代理评分爬山、外环用昂贵真评估确认增益，并用 Kendall-τ 保真度测试持续作废漂移的代理评估器，从而突破"评估太贵"这一自主发现瓶颈：在 SWE-fficiency 上取得 15.02× 几何平均加速（人类专家 6.90×），在 SOL-Exec 235 个 GPU kernel 上以 79.74% 平均 SOL 分排名第一（121 个第一），并在 DPC4 CPU 预取器设计上以 +6.31% 首次超越最佳人类设计（+3.52%）。

> **TL;DR:** When one true evaluation costs minutes-to-hours (85 min for a vLLM serving benchmark, up to 28 h for a CPU microarchitecture simulation), LLM search can only afford a handful of real evaluations. DuoDiscover fixes this by having each agent in a fleet co-discover an optimization target AND a cheap "yardstick" proxy evaluator (40 s vs 15 min true eval on SWE-fficiency, 22× faster), hill-climbing the yardstick in a fast inner loop while true evaluations confirm gains and a Kendall-τ fidelity test (τ ≥ 0.5, re-checked after every true eval) invalidates drifting proxies — so proxy reward hacking never produces a false gain. Results: 15.02× geometric-mean speedup on SWE-fficiency vs 12.81× for Claude Code and 6.90× for human experts; 79.74% mean SOL on the 235-kernel SOL-Exec leaderboard (1st on 121) vs 70.22% for KDA; 1.92× vs Claude Code's 1.07× geometric mean on vLLM multi-objective serving; and +6.31% on DPC4 prefetcher design, beating both the AlphaEvolve-based ArchAgent v2 (+3.82%, in 16.7 days vs 40+) and the best human design (+3.52%) — the first autonomous system to beat the human best on DPC4 multi-core workloads. Caveats: main results are single-run, FormulaCode uses a 25-task subset, and full runs are expensive (~$375 API per kernel).

## 核心贡献

- **共同发现（co-discovery）机制**：每个编码智能体不再只是改代码，而是同时选择要优化的代码区域（target，并按 Amdahl 定律给出其可贡献上限的估计 w_T）并亲手编写一个针对该 target 的廉价代理评估器（yardstick），在内环以秒级评分快速爬山，外环用昂贵的真评估确认每一次增益——只有真评估确认的增益才被接受。
- **保真度测试（fidelity test）对抗代理评估器的漂移与奖励作弊**：用 Kendall τ 秩相关（阈值 τ ≥ 0.5，仅在真分数差异超过评估噪声的状态对上计算）持续检验 yardstick 与真目标排序的一致性，并在每次真评估后复查；漂移即作废，智能体须重建 yardstick 或换目标。消融显示没有保真度测试的 yardstick 反而会拖累搜索（SWE-fficiency 从 12.85× 掉到 10.33×），说明该机制是必需品而非装饰。
- **自底向上的多智能体舰队与轻量编排器**：不做中心化问题分解；编排器只负责三类动作——终止停滞智能体、以"全新/迁移（transfer）/合并（combine）"三种方式派生新智能体、给在跑的智能体发简报，把昂贵的真评估预算导向有进展的方向。
- **跨全计算栈的实证**：在 2 个仓库级基准（FormulaCode、SWE-fficiency）、4 个 GPU/TPU kernel 套件（SOL-Exec、FA4、JAXBench、TPU-Inference）和 5 个真实系统案例（vLLM、FreeToken、SQLite、zstd、DPC4 CPU 预取器设计）上全面超越基线，并首次在 DPC4 多核负载上让自主系统超过最佳人类设计。
- **诚实且可审计的评估纪律**：报告的分数是最终候选多次重评估的中位数（按下置信界选候选、Student-t 区间），绝不报告搜索过程中的最好分；正确性检查失败记为无结果；vLLM/FreeToken 的维护者参与了正确性与奖励作弊的初审查，部分 FreeToken 解已合入上游（PR #619）。

## Key Contributions

- **Co-discovery of targets and yardsticks.** Each worker agent (an off-the-shelf LLM coding agent) jointly picks a target region of code T — annotated with a guess w_T of its share of the true score, bounding achievable gain by Amdahl's law at 1/(1−w_T) — and writes a cheap yardstick g_T, a scorer script (e.g., a shrunken input, a profiled hot loop, or a decode-cost model) that only needs to rank edits like the true objective, not match its values. The orchestrator feeds back the cost ratio r = c_f/c_g and the agent decides whether to keep it.
- **A fidelity test that tames proxy drift and reward hacking.** Because search exploits gaps between yardstick and true objective, the orchestrator re-tests every yardstick after every true evaluation using Kendall's τ (validated at τ ≥ 0.5, computed only on pairs whose true scores differ by more than evaluation noise); drifting yardsticks are invalidated and rebuilt. In the vLLM run, a load-sweep yardstick passed, was invalidated when higher load reversed its ranking, and was re-validated after rebuilding on two arrival rates.
- **Bottom-up fleet with a lightweight orchestrator.** No central decomposition. The orchestrator (itself an LLM) terminates stalled agents, spawns fresh/transfer/combine agents, and briefs runners on the fleet's confirmed findings. Its actions are interdependent: removing any single one costs 0.63–1.01× on SWE-fficiency or 2.3–4.4 SOL points, and removal losses sum to more than its net gain.
- **The first discovery agent that discovers and validates its own evaluators.** Unlike AlphaEvolve (user marks the code to evolve) or SIFT (spends expensive evaluations on promising solutions only), DuoDiscover synthesizes cheap, target-specific evaluators and validates/invalidates them during search — extending LLM-generated-test ideas from correctness to progress measurement.
- **Evidence across the computing stack** — from Python repositories to CUDA/Pallas kernels to a real CPU microarchitecture competition — with an unusually complete ablation suite (additive components, per-mechanism removal, task-wide-evaluator alternative, fleet scaling 1→16, backbone swap to Gemini 3.8 Flash, and 3-seed variance).

## Methodology

DuoDiscover frames optimization-under-expensive-evaluation as search over program states X with a true objective f: X → ℝ ∪ {⊥} (⊥ = correctness failure) whose single call costs c_f from minutes to hours (Table 8: vLLM 85 min, DPC4 up to 28 h), so a 20-hour budget affords only ~a dozen true evaluations for a frontier agent.

**Worker agent (fast inner loop, seconds per edit).** Each of N agents works on its own copy of the codebase and (1) profiles the workload, (2) picks a target T with an Amdahl-bound guess w_T, (3) writes a yardstick g_T: X_T → ℝ ∪ {⊥} as a script returning score + correctness flag (c_g ≪ c_f; e.g., a decode-time model scoring vLLM's prefill cap in seconds vs an 85-minute true eval), and (4) edits T, keeping edits that improve g_T and reverting others.

**Slow outer loop (hours per evaluation).** True evaluations confirm yardstick-reported gains; only confirmed gains are accepted, and every confirmed state feeds the fidelity test, which reuses the same true evaluation (no extra cost). Fidelity = Kendall τ ≥ 0.5 over state pairs whose true-score gap exceeds estimated evaluation noise.

**Orchestrator (coordination, not planning).** Periodically reads short progress summaries and acts: terminate (stalled agents), spawn (fresh, transfer = seeded with the best agent's confirmed state, or combine = re-implements several agents' confirmed changes, each kept only if a true evaluation confirms it), and brief (tell running agents what the fleet found). A run ends when budget is exhausted, a target score is reached, or the fleet empties.

**Reporting discipline.** The run's score is the median of several re-evaluations of the final candidate, selected by lower confidence bound with a Student-t interval; best-score-seen is never reported; correctness failures count as no result. Default setup: 8-hour wall clock, N = 4 agents, Claude Code v2.1 on claude-opus-5 with claude-sonnet-5 as the fast helper, identical hardware for all methods.

## Results & Highlights

- **SWE-fficiency-Lite (100 tasks, geometric-mean speedup):** DuoDiscover reaches **15.02× vs 12.81× for Claude Code, 12.27× for PerfAgent, 3.76× for OpenEvolve, and 6.90× for human expert patches** — more than double the human experts. On the 20-task sample it tests 358 candidates on yardsticks (median 40 s each, 22× faster than the 15-min true eval) while sending only 59 to true evaluation, vs Claude Code's ~72 true evaluations; it doubles confirmed gains (~12 vs 6 per task) and passes Claude Code's 8-hour score after a median of 2.5 hours.
- **SOL-Exec (235 GPU kernels, mean % speed-of-light):** **79.74% vs 70.22% for KDA (top MLSys 2026 Competition entry), 67.31% for Claude Code, 64.10% for PerfAgent, 52.36% for OpenEvolve** (+9.5 points over the best baseline, a 14% relative gain); ranks 1st on 121/235 kernels, 2nd on 61, 3rd on 30 (top-3 on 212) on the Sept 10, 2026 leaderboard snapshot. Equaling Claude Code's final 69.12% takes 2.8 h, 0.93M tokens (74% fewer), and 13 true evaluations (83% fewer) — $79.60 vs $309 for Claude Code's full run.
- **FormulaCode (25-task subset of FormulaCode-V, speedup):** **2.156× vs 1.778× (Claude Code), 1.774× (PerfAgent), 1.161× (OpenEvolve), and 1.048× for the human PRs** — a 21% gain over the strongest agentic baseline, with broader edits (avg 22 files, 51 functions, ~1,800 lines vs PerfAgent's 14 files/800 lines and OpenEvolve's 2 files/250 lines).
- **Kernel suites beyond SOL-Exec:** FA4 on 24 B200 configs: **11.97% geometric-mean gain over the Flash Attention 4 reference vs 8.93% (KDA), 4.11% (NVIDIA AVO), 1.30% (cuDNN attention)**; JAXBench (17 JAX/TPU kernels): **4.62× over XLA vs 4.08× (PerfAgent), 3.82× (Claude Code), 2.66× (OpenEvolve)**; TPU-Inference (production Pallas kernels from GLM-5.2/Kimi K3): **2.68× vs 2.38× (Claude Code), 2.14× (PerfAgent), 1.14× (OpenEvolve)**.
- **vLLM case study (serving GLM-5.2-NVFP4 on 8×B200 under 4 SLOs, 85-min true eval, 20-h budget):** **1.92× geometric mean vs 1.07× for Claude Code** (which improved neither p99 decode latency nor power), with **2.94× lower p99 decode latency (141–337 ms → 22–26 ms), 3.61× lower first-token latency, 21% lower GPU power (4594–4968 W → 3038–3237 W), and unchanged peak throughput (within 1%)**, using 7 true evaluations (9.9 h) vs Claude Code's 12 (16.8 h) — a ~500-line pure-system-level patch touching no kernel. FreeToken (753B-param MoE on a 48 GB L40S): 1.44× geomean vs 1.05× (1.76× at batch 8), partly merged upstream; SQLite: 1.38× vs 1.12×; zstd: 1.16× instruction-ratio vs 1.05×.
- **DPC4 CPU prefetcher design (true eval = up to 28 h over 1,700 simulations):** **+6.31% overall geometric-mean gain over the reference core vs +3.82% for the AlphaEvolve-based ArchAgent v2 and +3.52% for BertiGO, the best human design**, using ~8,000 candidates over 16.7 days vs ArchAgent v2's 12,000+ candidates over 40+ days; on Multi-Core workloads **+3.93% vs +2.85% (human) and +1.33% (ArchAgent v2)** — reportedly the first autonomous system to beat the human best on those cases, against a background of ≈3.5%/year single-processor performance improvement.
- **Ablations and analysis:** untested yardsticks without the fidelity test *hurt* (10.33× vs 12.85× Claude Code on SWE-fficiency); adding the fidelity test recovers 13.25×, co-discovery 13.76×, and the orchestrator brings the largest single kernel step (+6.37 SOL to 80.80%). A single task-wide evaluator instead of per-target yardsticks passes the fidelity test on only 21% of repository tasks and drops kernels from 80.80% to 71.36% SOL. Fleet scaling: DuoDiscover climbs from 70.26% (N=1) to 84.41% (N=8) and 85.96% (N=16) while Claude Code plateaus at 72.20%. Yardstick fidelity: median Kendall τ of 0.66 (repositories) and 0.76 (kernels); 41–45% of validated yardsticks are later invalidated for drift — wasted budget, but no false gains. Run-to-run variance (3 seeds): ±1.12% (kernels) / ±1.8% (repositories) vs ±3.27% / ±5.21% for Claude Code. Backbone swap to Antigravity/Gemini 3.8 Flash lifts 9.72×→12.66× and 58.79%→73.26% SOL (bigger relative gains than with Opus 5), with the whole run 5.1× cheaper.

## Authors & Credibility

A 25-author team spanning Google (Cloud AI Research / Systems Research), UC Berkeley (Aditya Parameswaran, Ion Stoica), and Stanford, with senior stewardship from Vahab Mirrokni, Burak Gokturk, Parthasarathy Ranganathan (Google), Tomas Pfister, and co-last authors Nanyun Peng and Chun-Liang Li. The team sits at the intersection of LLM agents and systems optimization, and the paper's credibility is strengthened by external anchors: rankings on the public SOL-ExecBench leaderboard, the official DPC4 competition's simulator/traces/scoring, maintainer review of the vLLM and FreeToken results for correctness and reward hacking, and one solution actually merged into FreeToken upstream (GitHub PR #619). The evaluation protocol itself is unusually disciplined (median of re-evaluations, lower-confidence-bound candidate selection, correctness failure = no result, never reporting the best score seen during search).

## Critical Assessment

- **Novelty: high but incremental-combinatorial.** The ingredients (proxy evaluation, LLM-written tests, multi-fidelity optimization, agentic code search) each exist; the contribution is the tight loop of co-discovering per-target proxies and validating them online with Kendall-τ fidelity tests, plus the terminate/spawn/brief orchestrator. The claim of being "the first discovery agent that finds both the solution and cheap evaluators which are validated or invalidated during the discovery process" is carefully scoped and, per the related-work survey (AlphaEvolve allows user-specified cheaper checks; SIFT prioritizes expensive evaluations), defensible.
- **Rigor: above average, with honest ablations.** The paper publishes the ablation where its own central mechanism without the fidelity test *underperforms* the plain baseline (10.33× vs 12.85×), reports high yardstick invalidation rates (41–45%), and reports variance only where it has it. However, **all main table results are single-run**; the 3-seed variance study covers only 20 SWE-fficiency tasks and 50 SOL-Exec kernels, not the headline 100-task/235-kernel tables.
- **Baseline gaps and asymmetries.** KDA is absent from repository benchmarks, AVO appears only on FA4, and PerfAgent is a re-implementation "modeled on" the original rather than the authors' code. The DPC4 comparison takes ArchAgent v2 and BertiGO numbers "as reported in the ArchAgent v2 paper" rather than re-running them, so hardware/config comparability rests on that paper. The Claude Code baseline keeps all four agents on throughput for 10 of 20 hours in the vLLM case — arguably a weak agentic strategy the orchestrator explicitly fixes.
- **Subset and snapshot caveats.** FormulaCode is evaluated on a 25-task subset of the 108-task human-checked FormulaCode-V (selected tasks span 7-min to 6.8-h evaluations; selection criteria beyond evaluation time are not detailed in the main text). SOL-Exec rankings are pinned to the Sept 10, 2026 leaderboard state, and some competitors there are proprietary with unknown budgets.
- **Reproducibility: limited for academic groups.** Runs depend on proprietary backbones (claude-opus-5 / Gemini 3.8 Flash at Sept 2026 list prices: ~$375 API per 8-h 4-agent kernel run, plus GPU time for true evaluations; the DPC4 run consumed 16.7 days with up-to-28-h evaluations). No code release is mentioned in the main text.
- **Red flags largely pre-empted.** The obvious failure mode — proxy reward hacking — is explicitly engineered against (every accepted gain requires a true evaluation; the fidelity test rechecks rankings), and maintainers reviewed the vLLM/FreeToken wins. The reported gains are therefore unlikely to be proxy artifacts. Remaining overclaim risk is modest: "doubling human experts" on SWE-fficiency-Lite compares geometric means over 100 tasks against expert PRs optimized for other constraints (reviewability, maintainability), not pure speed.
- **Acknowledged limitations:** if no faithful yardstick can be built, the system falls back to expensive-objective search; and yardstick construction plus initial fidelity testing is a warmup cost that makes DuoDiscover less attractive under very short evaluation budgets.

## Strengths

- Directly attacks the real bottleneck of autonomous discovery on production systems — evaluation cost — rather than yet another search-harness tweak; the vLLM numbers (12 vs 7 true evaluations for a 1.07× vs 1.92× outcome) make the point concretely.
- The fidelity test converts proxy-guided search from "trust me" to "verify continually," and the negative ablation (yardsticks without fidelity testing hurt) is a genuinely useful negative result for practitioners.
- Evaluation breadth is exceptional: 6 benchmarks + 5 real-world case studies spanning Python repos, CUDA/Pallas kernels, serving systems, C codebases (SQLite, zstd), and chip microarchitecture — the full computing stack.
- Honest measurement hygiene (median-of-re-evals, LCB candidate selection, correctness-failure = no result) and third-party validation hooks (public leaderboards, upstream merge, maintainer review).
- Strong orchestration economics: 74% fewer tokens and 83% fewer true evaluations to match the baseline's final score, and the fleet-scaling gap widening from +3.8 to +13.8 SOL points from N=1 to N=16 shows coordination, not just parallelism.

## Limitations

- Main results are single-run; seed variance is only measured on subsamples (20 repository tasks, 50 kernels), leaving run-to-run spread on the full benchmarks unquantified.
- High yardstick churn: 41% (repositories) to 45% (kernels) of validated yardsticks are invalidated for drift after ~15–19 candidates, and 8 of 15 pursued kernel targets (53%) never confirm a gain — meaningful budget burn, only partially mitigated by early dropping (19–20% of true evaluations).
- Expensive and proprietary: depends on frontier closed-weight agents; ~$375 of API per kernel run at list prices (before GPU evaluation time) and multi-day runs for the architecture task put it beyond most academic budgets; no stated code release.
- The τ ≥ 0.5 validation bar and the evaluation-noise filter are heuristic thresholds; sensitivity to these choices is not deeply explored, and noise estimation itself is nontrivial for workloads like serving sweeps.
- Target selection relies on the agent's Amdahl guess w_T and profiling intuition; the paper does not quantify how often agents pick fundamentally wrong targets beyond the 53%-never-confirm statistic, nor how performance degrades as true-evaluation cost drops toward yardstick cost (short-budget regime is acknowledged but not benchmarked).
- Baseline coverage is uneven across benchmarks (dashes in Table 1), and the DPC4 human/ArchAgent v2 comparisons are transplanted numbers rather than same-hardware re-runs.

## Relevance

该论文是"用 LLM 智能体自动优化 LLM 系统本身"的代表作：vLLM/FreeToken 案例直接展示了多目标推理服务优化（p99 延迟、首 token 延迟、功耗、吞吐），GPU/TPU kernel 套件覆盖 SOL/注意力/推理 kernel 优化，与高效推理与系统级加速的研究兴趣高度契合。其"代理评估器 + 保真度校验"思路对任何评估昂贵的自动化实验流程（如基准测试、训练配置搜索）都有直接借鉴意义。

## Questions for Further Exploration

- How sensitive are the results to the fidelity-test threshold (τ ≥ 0.5) and the evaluation-noise filter — does a stricter bar reduce the 41–45% yardstick invalidation rate, and at what cost in discarded useful yardsticks?
- Can yardstick construction be amortized across tasks (a library of validated proxy evaluators), or does drift make every yardstick fundamentally single-run?
- The orchestrator is itself an LLM — what is its failure mode profile, and would a deterministic orchestrator (bandit allocation over agents) match the +1.17× / +6.37 SOL contribution?
- How does the co-discovery advantage shrink as true-evaluation cost falls (the paper's own short-budget limitation) — is there a crossover point below which plain agentic search is optimal, and can warmup cost be cut by warm-starting yardsticks from prior runs?
- For DPC4, DuoDiscover's prefetcher reportedly includes a temporal-correlator LLC prefetcher written unprompted — could the discovered designs transfer across trace sets, or are they overfit to the 610-trace benchmark the way yardsticks drift?
- Since DuoDiscover improves any backbone (1.16–1.30× on repositories), does it also raise weaker open-weight agents to competitive levels, enabling reproducible open-source replications of the whole pipeline?
