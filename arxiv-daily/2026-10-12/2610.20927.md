> **一句话总结：** 指出压缩摘要会混入"环境确立的事实"与"压缩器自己写的推理"（AppWorld 上 67.7% 的 Open TODOs 无环境来源、29/35 个失败 run 可追溯到执行某条摘要条目），并提出 SJC——一个免训练、即插即用的后处理步骤：用非生成式概率判定模型 Jev 给每条摘要条目打"是否有环境输出或上一版摘要作为来源"的分、删掉无来源条目；在 AppWorld 与 OfficeBench、GPT-5.6 Luna 与 MiniMax-M3 两个 agent 上，Pass3 相对底层压缩器提升 2.1%–8.9%，且 token 开支不升反降。

> **TL;DR:** Long-horizon agents periodically replace history with a natural-language summary, but compaction prompts ask for decisions and next steps, so summaries mix environment-established facts with compressor-invented reasoning that the agent cannot distinguish afterwards — in the authors' analysis of OpenClaw on AppWorld, 67.7% of Open TODO entries have no source in environment outputs and 29 of 35 failed runs trace to an action carrying out a specific summary entry. SJC (Source-Judged Compaction) post-processes each candidate summary: it splits it into entries, retrieves BM25 evidence from environment outputs, and asks Jev (a non-generative decision model returning a calibrated probability) whether each entry has a source; unsupported entries are deleted whole, retained ones stay byte-identical, and neither agent nor compressor changes. On AppWorld (168 tasks) with GPT-5.6 Luna, Pass3 rises from 64.3% (Prompting/OpenClaw compressor) to 73.2% (+8.9 pts), with hard tasks going 39.7%→52.4% (+12.7 pts); on OfficeBench (95 tasks) gains are +5.3 pts (GPT-5.6 Luna) and +2.1 pts (MiniMax-M3), while cumulative LLM tokens drop by 1.3%–8.0% and the judge costs under $0.002 per task. Caveats: provenance is not correctness (both entry types are ~90% correct), only one host compressor and single-instruction tasks are evaluated, and one setting (OfficeBench/M3 average accuracy) regresses.

## 核心贡献

- **对压缩摘要的系统剖析**：收集了 29 个主流 agent 系统（OpenClaw、Codex CLI、Gemini CLI、Hermes、LangChain 等）的压缩 prompt，发现 21 个要求压缩器输出"决策"或"下一步计划"——每个压缩边界都是一次推理步，摘要因此混入了环境从未报告的内容。
- **量化了"无来源推理"问题**：在 AppWorld 训练拆分上分析 OpenClaw 压缩器的 667 份摘要（26,881 条条目）：Exact identifiers 仅 3.4% 无来源，但 Open TODOs 达 67.7%、Pending user asks 达 86.1%；且这些无来源推理会在每个压缩边界被重新生成（每份摘要稳定含约 4 条），而非简单沿用。
- **失败归因**：35 个可分析失败 run 中有 29 个（83%）的失败动作是在执行某条具体摘要条目，其中 22 条无任何环境输出支持、3 条与环境输出矛盾；失败模式归纳为改写约束（15）、虚构交付物（5）、矛盾状态（3）等。
- **SJC 方法本身**：免训练、只删不写的后处理算子——条目级来源判定（Jev 概率判分，阈值 τ=0.5）+ 无来源条目整条删除 + 保留条目与压缩器原文逐字一致；不改 agent、不改压缩器、每次压缩只加一个廉价 judge 请求。
- **与同类方法的清晰区隔**：相比 ReSum/SUPO/ACM（需训练或改 agent）和 Fast-Jev（用同一 judge 选原始历史而非摘要），SJC 是唯一"摘要式 + 免训练 + 即插即用"三者兼得的方法；实验证明收益来自"问 judge 什么、用在哪"，而非 judge 模型本身。

## Key Contributions

- **A systematic anatomy of compaction summaries**: a survey of 29 compaction prompts from widely used agent systems (OpenClaw, Codex CLI, Gemini CLI, Hermes Agent, LangChain, etc.) shows 21 ask for decisions or next steps (18 request decisions, 17 remaining work) — every compression boundary is also a reasoning step whose output the environment never reported.
- **Quantification of unsupported reasoning**: analyzing 667 OpenClaw summaries (26,881 entries) on the AppWorld training split, only 3.4% of Exact identifiers are unsupported, versus 67.7% of Open TODOs and 86.1% of Pending user asks; only 20.5% of unsupported reasoning entries survive into the next summary, yet each summary stably contains ~4 of them (4.3/3.9/3.8 at first/second/later boundaries) — the compressor regenerates them at every boundary.
- **Failure attribution**: 29 of 35 analyzable failed runs (83%) trace to an action that carries out a specific summary entry; 22 of those entries are supported by no environment output and 3 contradict one (two independent annotation rounds, κ = 0.86). Failure patterns: rewritten constraints (15 runs), invented deliverables (5), contradicted state (3), carried-over choices / partial-as-complete (6).
- **The SJC operator**: a training-free, deletion-only post-processor G with the constraint B(Mt) ⊆ B(M̃t) — it judges each entry's provenance with Jev (a non-generative decision model emitting a calibrated probability, τ = 0.5, not tuned), removes unsupported entries as complete units, keeps retained entries byte-identical, and leaves the agent and host compressor untouched.
- **Clean ablation of where the gain comes from**: Fast-Jev uses the same Jev model to select raw history but falls below Prompting in 3 of 4 settings, and a generative self-judge (the compressor itself) helps in only 1 of 4 settings despite pruning similar fractions — the gain comes from the question asked and where the judge is applied.

## Methodology

**Setup.** At compression boundary t the context is the fixed prompt P, the previous summary M(t−1), the history span Ht, and the most recent interaction Rt (kept verbatim). A host compressor produces a structured candidate summary M̃t = C(P, M(t−1), Ht, Rt); SJC seeks a post-processing operator G committing Mt = G(M̃t) to maximize task success subject to B(Mt) ⊆ B(M̃t) — G may only delete entries, never rewrite or add.

**Three stages.** (1) *Generate*: the host compressor (OpenClaw safeguard-mode structured prompt, unchanged) produces M̃t with sections Decisions / Open TODOs / Constraints/Rules / Pending user asks / Exact identifiers. (2) *Judge sources*: SJC parses M̃t into bullet entries, retrieves evidence by BM25 over environment outputs of the compressed span (300-character passages, top-3 per entry expanded to enclosing ≤2,000-character chunks, pooled across entries — so the judge never reads the full history), and issues ONE judge request covering all entries: "Does the entry contain information that came from an environment output in the span or from the previous checkpoint... rather than only plans, decisions, or readings of the task?" The judge is Jev-1.13, a non-generative decision model that returns a calibrated probability of "yes" instead of text. (3) *Prune and commit*: entries scoring ≥ τ = 0.5 are kept verbatim and re-rendered preserving section structure; unsupported entries are removed whole. The same Mt becomes the "previous summary" at the next boundary, and because unsupported reasoning is regenerated each boundary, the gate is applied at every boundary, not once. The fixed prompt P does not count as a source (it stays visible to the agent), which is also what makes it safe to drop entries that merely restate the task.

**Evaluation protocol.** Frozen-agent setup: only the context representation changes. Three independent runs per configuration; metrics are mean success (Acc.), cross-run reliability Pass3 (fraction of tasks solved in all three runs), mean steps, and peak input length. Benchmarks: AppWorld test-normal (168 stateful API-use tasks, split Easy 57 / Medium 48 / Hard 63) and the ACON test set of OfficeBench (95 multi-application office tasks, 42 1-APP / 22 2-APP / 31 3-APP). Agent and compressor use the same model (GPT-5.6 Luna with medium reasoning effort, or MiniMax-M3); compaction windows deliberately small (4,096 tokens AppWorld, 2,048 OfficeBench) so compaction occurs within each task. Baselines: No compression, FIFO, LLMLingua, LLMLingua-2, Fast-Jev, and Prompting (the OpenClaw compressor alone, which SJC post-processes).

## Results & Highlights

- **Headline reliability gains (Tables 3–4)**: SJC raises Pass3 over Prompting in all four benchmark×model settings by 2.1%–8.9% absolute. AppWorld/GPT-5.6 Luna: 64.3%→73.2% Pass3 (+8.9) and Acc. 76.8%→82.1% (no-compression reference: 78.6% Pass3, so SJC closes most of the compaction reliability gap); AppWorld/MiniMax-M3: 55.4%→62.5% (+7.1); OfficeBench/GPT-5.6 Luna: 68.4%→73.7% (+5.3); OfficeBench/MiniMax-M3: 74.7%→76.8% (+2.1, though Acc. falls 84.2%→83.2%, the only accuracy regression). Across the 12 benchmark–model–subset groups, Pass3 improves in 10, is unchanged in 1, and decreases in 1 (OfficeBench 1-APP/M3, 90.5%→88.1%, where Prompting nears saturation).
- **Gains concentrate where compaction hurts most**: on AppWorld hard tasks Pass3 improves +12.7 pts with GPT-5.6 Luna (39.7%→52.4%) and +6.3 pts with MiniMax-M3 (41.3%→47.6%), and +10.4 pts on medium for both models (66.7%→77.1%; 47.9%→58.3%); on OfficeBench 3-APP tasks with GPT-5.6 Luna, Acc. rises 59.1%→64.5% and Pass3 41.9%→54.8% (+12.9).
- **SJC is free or cheaper than the summaries it prunes (Table 5)**: cumulative agent+compressor tokens change by −8.0% (AppWorld/GPT), −2.9% (AppWorld/M3), −1.3% (OfficeBench/GPT), −7.0% (OfficeBench/M3) relative to Prompting, because pruning removes 13%–21% of entries and shortens summaries 14%–27%; steps change by at most +0.1 and peak input by ≤0.47K tokens. The Jev judge adds one request per compaction, max 29.0K input tokens (within its 32K window), costing $1.2–$1.5 per 1,000 tasks (<$0.002/task). Peak input stays 27%–54% below uncompressed execution.
- **The analysis motivating the method (Tables 2, 9–11)**: 17.9% of all summary entries (and 67.7% of Open TODOs, 86.1% of Pending user asks) have no source in environment outputs; 54.9% of reasoning entries are unsupported at the first boundary; 29 of 35 failed runs trace to executing a specific summary entry (22 unsupported, 3 contradicted, only 4 supported).
- **Judge quality and the self-judge ablation (Tables 6, 12)**: against human annotation, Jev separates supported from unsupported entries at AUROC 0.905 (GPT-5.6 Luna generative self-judge: 0.792); at τ=0.5, 96.9% of entries Jev marks supported are truly supported, and it recovers 64.2% of all supported ones (conservative). Replacing Jev with the compressor itself gives the best AppWorld/GPT Pass3 (75.6) but drops below Prompting in the other three settings (e.g., 50.0 vs 55.4 on AppWorld/M3) despite pruning similar fractions (14.6–18.6% vs 13.0–21.3%) — the difference is repeatability: re-issuing the same 40 requests five times, the self-judge flips its answer on 8.6% of entries vs 2.1% for Jev (23.4% on entries Jev scores <0.2).
- **Sensitivity and selectivity (Figure 3, Section 5.4)**: Jev scores are bimodal (73.9% of entries ≥0.8, 10.6% <0.2, only 8.1% in 0.3–0.7), so moving τ from 0.3 to 0.7 changes the pruned fraction by at most 10.2%. Pruning is section-selective, not wholesale: SJC keeps 92.8%–97.4% of Exact identifiers and 84.2%–92.5% of Decisions but only 28.5%–64.9% of Open TODOs and 2.0%–12.8% of Pending user asks (these two sections hold 15.2% of entries but 59.5% of prunes), concentrated at the first boundary (29.9%–39.6% pruned there vs 8.8%–17.7% later).
- **Case study (Figure 4)**: asked to copy yesterday's habit log "except I did not meditate", Prompting's summary converts this into an instruction to omit the line (score 0.15); the agent deletes `practiced_meditation: yes` and fails the checker in 2 of 3 runs. SJC prunes that entry, keeps the note-grounded entry (score 0.94), and the agent correctly sets `practiced_meditation: no`, succeeding 3 of 3.

## Authors & Credibility

Guanghui Min and Chen Chen (corresponding author), Department of Computer Science, University of Virginia. The paper continues a visible research line by the first author on context compression for long-horizon agents (the authors self-cite their prior empirical study of execution instability, arXiv:2608.06503, and counterfactual-continuation compression, arXiv:2609.36526 — the latter also defines the Pass3 metric reused here), suggesting sustained, non-opportunistic engagement with the problem. Credibility signals: code released at https://github.com/GuanghuiMin/sjc; every quantitative claim about failure attribution was verified by two independent annotation rounds with reported Cohen's κ (0.86 support judgment, 0.80 failure pattern, 0.95 support labels in the judge-validation appendix) plus script verification of quoted entries; the limitations section is unusually candid (they themselves quantify when SJC hurts). The 29-prompt survey pins every prompt to a repository commit (Table 8). Risks to validity they acknowledge: LLM annotators for the failure analysis, an external API judge that is not fully deterministic, and the nine failed runs excluded because the scenario's reference solution contradicts its own environment data.

## Critical Assessment

- **Novelty**: The core observation — compaction summaries mix facts with compressor reasoning, and provenance can be checked at compaction time — is genuinely sharp and well-evidenced; framing the fix as a deletion-only post-processor over an existing compressor is a distinct design point versus training-based methods (ReSum, SUPO, ACM). However, the ingredients are familiar: Jev, BM25 retrieval, and structured summaries all pre-exist; the contribution is the composition and the analysis, not any new algorithm or model. The provenance idea also echoes hallucination/attribution detection, which the related work only partially connects to.
- **Rigor**: The main claims are well supported (3 runs, four settings, absolute deltas reported, thresholds not tuned, κ-reported annotation), but the evaluation breadth is thin for a "drop-in" claim: exactly ONE host compressor (OpenClaw safeguard mode), two agent models, two benchmarks, and deliberately tiny context budgets (2K–4K tokens) that force many compactions per task — it is unclear the 2.1%–8.9% Pass3 deltas transfer to realistic 128K–1M-token windows where summaries are longer and retrieval hits are sparser. The one setting that regresses (OfficeBench/M3 accuracy −1.0) is disclosed but under-analyzed.
- **Reproducibility**: Strong on paper — code is public, prompts and commit hashes are pinned, official implementations are used for LLMLingua/LLMLingua-2/Fast-Jev — but the method depends on a proprietary Jev-1.13 decision model accessed via OpenRouter whose scores are "not fully deterministic", and on GPT-5.6 Luna/MiniMax-M3 APIs that will drift; exact reproduction will decay even though the protocol can be re-run.
- **Provenance ≠ correctness — the conceptual soft spot the authors own**: supported and unsupported entries are correct at nearly identical rates (92.2% vs 90.6%; source score ranks correctness no better than chance, AUROC 0.444), so SJC is not filtering errors per se; at τ=0.5 it also recovers only 64.2% of supported entries, i.e., it throws away ~1/3 of well-grounded content, and the paper gives a concrete case where pruning a correct-and-helpful restriction makes MiniMax-M3 fail 2 of 3 runs. The mechanism story ("unsupported reasoning derails execution") explains 29 of 35 failures, but among the ten tasks SJC fixes deterministically, only four failures actually trace to an unsupported entry — the authors admit the unsupported entry raises rather than determines the error.
- **Significance and red flags**: The problem is real and deployed systems ship workarounds (Hermes' "treat as background reference, NOT as active instructions" banner is nice independent evidence). Main red flags for practice: single-instruction benchmarks where the task stays visible after compaction are precisely the regime where deleting task-restating entries is safe — the authors concede multi-turn settings, where earlier user messages ARE a source, are unevaluated; and the headline "83% of failed runs" from the abstract comes from a training-split failure analysis of the very compressor SJC post-processes, with one scenario (9 runs) excluded and one scenario contributing 9 of the remaining 35 failures, so per-run percentages overstate statistical independence (the per-scenario count is 15 of 19).

## Strengths

- Diagnoses a real, previously under-formalized failure mode of deployed agent systems (summary entries acting as self-generated instructions) with unusually careful, commit-pinned prompt archaeology across 29 real systems.
- The fix is minimal and compositional: no training, no agent/compressor modification, deletion-only, one cheap judge call per compaction (<$0.002/task), and it actually SAVES 1.3%–8.0% of tokens while improving reliability.
- Honest, quantitative self-scrutiny: provenance-vs-correctness AUROC (0.444), self-judge ablation, threshold sensitivity, a worked case where pruning hurts, and per-scenario recounting of the failure analysis.
- Reliability framing (Pass3 across three runs) targets the property practitioners actually care about for long-horizon agents, rather than single-run accuracy.

## Limitations

- Filters by provenance, not correctness — both kinds of entries are ~90% correct, and 4 of the 29 summary-executed failures were supported entries, which no source-based filter can remove; meanwhile SJC deletes correct and sometimes load-bearing content (recovers only 64.2% of supported entries at τ=0.5).
- Narrow evaluation: one host compressor (OpenClaw), two benchmarks, two models, unnaturally small context windows, and single-instruction tasks where the task remains visible post-compaction; multi-turn conversations, where earlier user turns are legitimate sources, are explicitly untested.
- Dependence on an external, non-deterministic proprietary judge (Jev via OpenRouter); the generative self-judge substitute is unreliable in 3 of 4 settings, so the plug-in is currently coupled to one vendor's model.
- Failure analysis rests on LLM annotators (mitigated by double annotation and κ statistics) and excludes a broken scenario (b0a8eae, 9 runs) that no method solves.
- Gains are moderate in absolute terms (2.1–8.9 Pass3 points) and one setting regresses in accuracy; SJC never beats the no-compression reference, so it mitigates rather than eliminates the cost of compaction.

## Relevance

论文直接针对长时程 LLM agent 的上下文压缩这一核心工程问题，提出免训练、即插即用的摘要来源审查机制，与当前 agent 系统（Claude Code、Codex、OpenClaw 等采用 compaction 的框架）的设计痛点高度契合。对关注 agent 记忆管理、上下文工程与可靠性（cross-run Pass3）方向的研究非常有参考价值。

## Questions for Further Exploration

- Does SJC transfer to realistic large context windows (128K–1M tokens) where compaction is rare but each summary is much longer, and where BM25 evidence retrieval over a huge history span may miss the grounding passage?
- How should multi-turn settings be handled, where earlier user messages are themselves legitimate sources — can the judge's source set be extended to "any content that will no longer be visible after compaction" without degenerating into keep-everything?
- Since provenance and correctness are statistically independent (AUROC 0.444), would a two-channel filter — source judgment plus a separate correctness/consistency check against retrieved evidence — stack the gains?
- Can the deletion-only constraint be safely relaxed to allow rewriting an unsupported-but-correct entry into a supported form (e.g., attaching the grounding environment quote) instead of dropping information the agent may need?
- How does SJC interact with compressors whose prompts are redesigned to request facts only (the 8 of 29 surveyed prompts that do not ask for plans) — does the unsupported fraction collapse, and does SJC then become unnecessary or still help reliability?
- Could the bimodal Jev score distribution be exploited for an abstain band (entries in 0.3–0.7 flagged for a cheaper second check) instead of a hard threshold, to recover part of the 35.8% of supported entries currently pruned?
