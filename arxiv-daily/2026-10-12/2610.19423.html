Key metric · projection error

4.7%

DeepSeek V3 671B FP8 at 1,024 GPUs / 128 nodes — 2,808 projected vs 2,946 measured tok/s/GPU.

Qwen3-235B-A22B @ 256 GPUs: 1.9% · all projections across 2 model families, 2 precisions, 2 GPU generations stay within ~10%.

Why this matters

Parallelism, MoE backend, and memory–throughput tuning eat the most GPU time in real training — this turns days of cluster sweeps into ~30 single-node minutes.

Critical edge

The +27% headline mixes precision with tuning — the winning FP8 config is measured against AMD's published BF16 reference, so part of the gain is just the BF16→FP8 switch.

Also: validated only on AMD Instinct/ROCm, by AMD employees; NVIDIA/TPU porting argued but untested.

Methodology — distilled

  • Measure what you can, model what you cannot. GPU microbenchmarks capture compute kernels and benchmark-scope communication; everything outside that scope is restored analytically at the target multi-node scale.
  • Fidelity-ranked downscale order. PP first (schedule exactly replayable — zero compute information lost), then EP (experts/rank preserved, only the A2A delta remains), then TP (relies on a scaling ratio, improved by AR* = ARmeas × analytical*/analyticalbench).
  • Per-iteration time composes as:
  • iter_time = T_pipe({t_l}, N_µB, schedule) + FSDP_exp + grad_AR_exp + opt_step
  • Five components: hierarchical memory profiler (precision as two axes, e.g. BF16+Adam = 2/2/10 bytes) · layer profiling · topology-aware comm model (rings/hypercube/Bruck/single-shot AR, direct/hierarchical/PXN-DeepEP A2A — min-time pick) · exact schedule simulation · multi-node scaling.
  • Search on top of the oracle: legality = axes tile the cluster ∧ projected memory ≤ 0.9×(HBM − overhead) ∧ parseable throughput. The pre-filter's OOM predictions matched hardware perfectly; it rejected 7 of 30 tuning trials at zero GPU cost (~175 GPU-min saved).

Strengths · what holds up

  • Turns "measure what you can, model what you cannot" into a principled, fidelity-ranked downscale order (PP exact → EP compute-preserving → TP approximate) with auditable per-dimension deltas.
  • Exceptional validation scale for a systems paper: 1-GPU benchmarks up to a 1,024-GPU DeepSeek V3 run at 4.7% error, on architecture features (MLA, 3-dense+58-MoE mix) never seen during development.
  • The rank-preservation study tests the property search actually needs — ordering, not absolute accuracy — including why opposite-sign offsets (k = 1.13, k = 0.90) both preserve order exactly.
  • Honest error accounting: reports its own ~10.5% optimistic bias, the 3 discordant GPT-OSS pairs, the idle-node requirement, and the FP8-vs-BF16 reference caveat in the ablation.
  • Strong practical economics: ~30 min of single-node exploration replacing days of multi-node sweeps; memory pre-filter with perfect OOM agreement on hardware.
  • MoE load-balancing appendix stands alone: pooled-vs-per-layer imbalance decomposition (step-level 1.05–1.12 vs per-layer 1.38) explains why real training stays near-uniform.

Limitations · where it strains

  • Validated only on AMD Instinct/ROCm; the vendor-neutrality argument (YAML hardware profiles) is architecturally convincing but empirically unverified on NVIDIA or TPU.
  • Absolute throughput carries a systematic ~10% multiplicative calibration offset (k up to 1.235) — fine for ranking, misleading if read as a prediction.
  • Rank-preservation evidence covers only 3 MoE models with 7–9 configs each; no large-scale study of regret over the O(10⁴)-point space the agent nominally searches.
  • Network contention, node heterogeneity, and GPU-to-GPU clock variation are unmodeled; requires an idle benchmark node.
  • Precision is a throughput knob only — FP8 recipes need separate convergence validation.
  • Planner prompt embeds hand-written MoE priority hints (e.g. "~35% DeepEP win"), blurring learned search vs encoded expertise; LLM-loop token cost and backbone sensitivity unreported.

Questions for further exploration

  1. How much of the LLM loop's +21.6% edge over the seed planner survives if the hand-written MoE priority hints are stripped from the Planner prompt?
  2. Does the ~10% calibration offset stay stable across ROCm releases — can one measured anchor config per workload calibrate it away without breaking rank preservation?
  3. How does the projection degrade under realistic network contention (shared fabric) and heterogeneous clusters — the two explicitly unmodeled regimes?
  4. Can the busiest-rank load-balancing correction predict throughput during early training, while router balance is still converging?
  5. What is the token cost / latency budget of the Claude-based loop — could a small open-source model on the same DSPy scaffold match it, given the oracle does the heavy lifting?
  6. Would downscale–measure–upscale transfer to inference/serving (continuous batching, KV-cache pressure), where activation-memory and communication patterns differ fundamentally?
