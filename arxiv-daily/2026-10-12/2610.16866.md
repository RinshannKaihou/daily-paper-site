> **一句话总结：** PivotRL 针对 GenRM 强化学习后训练中 rollout / 奖励评估 / 训练三个阶段静态分配 GPU 导致的利用率不足，提出"资源可转移部署"范式：通过集群级 CPU 内存参数池（GPS）、统一的角色上下文转移机制、支持序列迁移的 shift-aware 调度器和基于收益-代价规划的 planner，在 128 卡 H20 集群上把端到端吞吐相对 colocated 提升 1.81–2.05 倍、相对 disaggregated 提升 1.50–1.95 倍，且资源转移仅需数秒、不损害 RL 收敛性。

> **TL;DR:** PivotRL is a systems paper (built on veRL) that attacks the static-GPU-allocation bottleneck of RL post-training with generative reward models (GenRM), where rollout, GenRM-based reward evaluation, and training all contend for GPUs. It lets GPUs dynamically shift between the three roles at runtime via a Global Parameter Storage (cluster CPU-memory parameter pool), a unified role-context shifting mechanism (discard/offload/preserve), a shift-aware scheduler with sequence migration, and a DP-based planner that trades off aggregate throughput gain (weighted harmonic mean of rollout/reward throughput over a 60 s window) against shift penalty. On a 128-GPU H20 cluster with four policy+GenRM model groups (up to Qwen2.5-72B policy with Qwen3.5-122B-A10B GenRM) training on DAPO-Math-17k (validated on AIME24), it reaches 22,822 tok/s vs 11,545 for colocated and 11,711 for disaggregated in the Qwen2.5-7B & Qwen3-30B-A3B group (1.98x / 1.95x), with shifts completing within seconds and equal convergence in ~30 h wall-clock vs >50 h for baselines.

## 核心贡献

- **首次系统性地指出**：在带生成式奖励模型（GenRM）的 LLM RL 后训练中，奖励评估本身已变成一个完整的 LLM 推理负载，rollout、奖励、训练三阶段同时竞争 GPU；而现有 colocated / disaggregated 部署均为**静态资源分配**，无法适配步内持续变化的各阶段负载，是关键系统瓶颈。
- **提出"资源可转移部署"（resource-shiftable deployment）新范式**并在 PivotRL 中实现：GPU 可在运行时按瞬时负载在不同角色间动态转移（如 rollout 尾部空闲 GPU 转给 reward，训练结束后的 GPU 立即归还推理）。
- **资源可转移运行时**：全局参数存储 GPS 把整个集群的 CPU 内存池化为分布式参数库（策略模型 + GenRM），任何 GPU 可按任意并行策略 Read 参数；Write 仅在每个 RL 步训练后更新策略模型（GenRM 冻结），并与下一步训练重叠隐藏开销。
- **统一角色转移机制**：将角色上下文分类为无状态（临时数据、参数 → 丢弃，参数可随时从 GPS 重读）与有状态（优化器状态 / CUDA Graphs → offload 到 DRAM；CUDA context、NCCL 通信组等 <3.37 GB/GPU → 保留在 GPU），把任意角色间转移分解为 shift down + shift up。
- **shift-aware 调度器**：共享等待队列 + 离线拟合的副本吞吐模型，把 shift 引发的重调度归约为原生的 Abort + Dispatch 序列迁移，复杂度上界 O(I·N^Seq + I·log I)。
- **五步 planner**：确定 shift-up 角色（训练批次就绪优先，否则选生成时延更大者）→ 构造带惩罚 φ 的转移对 → 动态规划（O(I²)）构造候选集 → 用序列迁移模拟器评估加权调和平均吞吐 → 选最大正收益方案（B = H·(T_cand − T_current) − φ，H 默认 60 s）。

## Key Contributions

- First systematic study of LLM RL post-training with generative rewards (GenRM) that identifies **static resource allocation** as the key system bottleneck: reward evaluation becomes a full LLM inference workload, so rollout, reward, and training all need substantial GPUs, yet existing colocated and disaggregated systems pin each stage to a fixed GPU set.
- Propose and realize **resource-shiftable deployment** in PivotRL: GPUs migrate among the three roles at runtime, matching instantaneous demand (e.g., rollout's long-tail headroom shifts to reward; training GPUs return to inference immediately after a step).
- A **resource-shiftable runtime** built on a Global Parameter Storage (GPS) that pools cluster CPU memory to hold both models' parameters, exposing just Read/Write (realized as CPU-GPU all-to-all collectives over PCIe + RDMA); Write fires only after each training step and is overlapped with the next step's training.
- A **unified role-shifting mechanism** that classifies role context by data type — stateless (temporary buffers, parameters: discard; parameters re-Read from GPS) vs stateful (optimizer states/gradients/CUDA Graphs: offload to DRAM; CUDA context and NCCL groups, <3.37 GB/GPU: preserve) — so any role-to-role shift avoids both cold starts and memory bloat.
- A **shift-aware scheduler** that reduces post-shift rescheduling to native scheduling: a shared waiting queue plus a profiled per-replica throughput model T = N^Seq / (A·N^Token + max(B, C·N^Seq) + D) drives throughput-maximizing dispatch; migration is just Abort + Dispatch.
- A **five-step planner** (pick shift-up role → prepare penalty-sorted shift pairs φ = Σ τ_shift·T_i → DP candidate construction in O(I²) → benefit simulation with rollout/reward weighted-harmonic-mean throughput → select max positive B = H·(T_cand − T_current) − φ), which provably avoids thrashing by refusing negative-benefit shifts.

## Methodology

PivotRL is implemented on top of veRL and addresses three design challenges. (C1) Supporting shifts: a GPU holds parameters and role-bound context (CUDA Graphs for rollout, optimizer states and NCCL groups for training), so a shift must move both. GPS mediates parameter movement through pooled CPU memory — available even when a role has zero replicas, unlike GPU-to-GPU transfer, and far cheaper than disk reload. Read fetches parameters under any parallelism layout via an all-to-all CPU-GPU collective; the training stage Writes updated policy weights back after each RL step (overlapped with subsequent training), while the frozen GenRM never Writes. Role context is handled per category (discard / offload-to-DRAM / preserve-on-GPU), and a shift decomposes into shift down (old role) then shift up (new role). Granularity is deliberately restricted: rollout and reward shift per replica (equivalent to DP scaling, no repartitioning), training shifts as a monolith. (C2) Rescheduling: the scheduler keeps a shared waiting queue and dispatches each sequence to the replica with the highest modeled throughput gain ΔT; a shift simply aborts affected sequences back to the queue and re-dispatches, with shift-up additionally migrating the shortest sequences from the highest-throughput replicas to exploit diminishing marginal returns. (C3) Shift decisions: the planner picks the shift-up role (training if the next batch is ready, otherwise the role with larger generation latency N^Seq/T), builds shift pairs penalized by tokens forgone during the shift, constructs candidates with a DP that keeps the minimum-penalty plan for each shift-up count k, evaluates each candidate by replaying sequence migration in a simulator, and selects the plan maximizing B = H·(T_cand − T_current) − φ over a default 60 s benefit window; if no plan is positive, nothing shifts. Evaluation runs on 16 nodes × 8 NVIDIA H20 (96 GB) GPUs (NVLink 900 GB/s intra-node, InfiniBand 50 GB/s inter-node), with DAPO-Math-17k as the training set, AIME24 as validation, hybrid reward R = R_DAPO + R_GenRM, and token caps of 2K (prompt) / 15K (response) / 20K (GenRM response). Four model groups span dense and MoE architectures; three baselines (colocated, disaggregated, rollout-reward colocated) are each tuned to their optimal allocation; every experiment is repeated three times.

## Results & Highlights

- On the Qwen2.5-7B & Qwen3-30B-A3B group, PivotRL reaches 22,822 ± 51.07 tok/s end-to-end throughput vs 11,545 for colocated deployment (1.98×) and 11,711 ± 36.37 for disaggregated (1.95×); on rollout-reward colocated it is 1.61× (14,189 tok/s baseline).
- Across all four model groups (up to Qwen2.5-72B policy + Qwen3.5-122B-A10B GenRM at 12,503 ± 15.05 tok/s vs 6,915 colocated / 7,530 disaggregated), PivotRL improves end-to-end throughput by 1.81–2.05× over colocated, 1.50–1.95× over disaggregated, and 1.66–1.97× over rollout-reward colocated.
- Shift overheads stay in the seconds range: inference shift up grows from ~1 s (Qwen2.5-1.5B) to ~9 s (Qwen3.5-122B-A10B) while shift down stays <2 s; training shift up reaches ~8.5 s with shift down <6 s; scaling 16→128 GPUs keeps shift up within ~3–4 s for the 30B-A3B GenRM, and total sequence-migration time stays below 1.18 s (dispatch dominates at 0.22–1.03 s; abort and re-prefill each <0.19 s). The planner itself costs 0.31–2.95 s and runs concurrently with RL execution.
- Ablations (relative to disaggregated) show the planner is the differentiator: a static even-split strategy yields only 1.55× / 1.27× and a KV-utilization rule-based strategy only 1.31× / 1.05× on the two ablation groups, vs 1.95× / 1.61× for full PivotRL; component-wise, the runtime+planner alone gives 1.79× / 1.43×, adding the throughput model raises it to 1.87× / 1.53×, and adding sequence migration reaches 1.95× / 1.61×.
- RL convergence is preserved: reward and AIME@1 curves nearly overlap with both baselines when plotted against RL steps, and PivotRL reaches the same reward/AIME@1 level in ~30 h of wall-clock time vs more than 50 h for colocated and disaggregated deployments.
- Sensitivity: the only hyperparameter H is stable in 60–120 s; too small an H makes the planner overly conservative (fewer shifts, lower throughput) while too large an H triggers excessive shifting whose overhead erodes gains.

## Authors & Credibility

The team spans Shanghai Jiao Tong University (Yanfeng Zhao, Fangcheng Fu), Peking University (Haoyang Li, Sheng Lin, Yuming Zhou, Bin Cui), and Central China Normal University (Jiawei Jiang), with two equal-contribution first authors. The group has a strong track record in LLM systems: they are the authors of related systems work cited in the paper (Hydraulis, Hetu v2 at OSDI '26, Malleus, and the concurrent StaleFlow disaggregated RL system), and PivotRL is built on veRL, the de-facto standard open-source RL post-training framework. The evaluation is unusually solid for a systems paper: a real 128-GPU H20 cluster, four policy+GenRM combinations including 30B–122B MoE GenRMs, three baselines each tuned to optimal configurations, three repetitions with standard deviations, full ablations of both shift strategy and system components, micro-benchmarked shift/migration overheads, a hyperparameter sensitivity study, and a convergence check — not just throughput numbers.

## Critical Assessment

- **Novelty:** The core insight — static allocation is the bottleneck once GenRM makes reward evaluation a full inference workload — is well-motivated and the three-role/two-model shifting problem is genuinely harder than the two-role (rollout/training) elasticity tackled by concurrent RLVR systems the authors cite. That said, the ingredients (CPU-memory parameter pools, context offload, migration via abort/re-dispatch, benefit-vs-penalty planning) are each individually familiar from elastic inference/training work (Llumnix, SpotServe, Pollux, Malleus); the contribution is the synthesis into one RL runtime rather than any single new mechanism.
- **Rigor:** Strong on the systems side (tuned baselines, std over 3 runs, ablations, overhead breakdowns). Weaker on workload generality: all results use a single training dataset (DAPO-Math-17k) and a single math validation (AIME24), and the reward is the hybrid R = R_DAPO + R_GenRM. This is somewhat self-undermining: the introduction motivates GenRMs by open-ended tasks (creative writing, long-form QA) where verifiable rewards are unavailable, yet the evaluation only covers math — a domain where the verifiable component alone already works — so the claimed GenRM-centric setting is tested in its least GenRM-dependent form. Whether gains hold with a GenRM-only reward or non-math workloads (different rollout/reward token-length mixes) is untested.
- **Metric caveats:** The planner's objective (Equation 1) is the weighted harmonic mean of rollout and reward throughput only — training tokens are excluded, so the "overall throughput" visibly dips while training runs (visible in their own Figure 10 trace), and the reported end-to-end throughput definition (tokens processed / total time) is not fully spelled out with respect to which token populations are counted; the headline speedups depend on this choice.
- **Reproducibility:** Built on open-source veRL with named models, parallelism settings, token caps, and dataset; hyperparameters are few (only H, default 60 s). No code release is mentioned in the paper body, and the throughput-model constants A–D require offline profiling per deployment, so exact reproduction would need re-fitting.
- **Red flags / missing ablations:** Convergence (Figure 15) appears to be shown for only one model group rather than all four; the granularity restriction (training as a monolith, inference at replica granularity) is a pragmatic but untested-against-alternatives choice — no experiment quantifies what finer-grained shifting would buy; the 60 s benefit window is empirically tuned on this specific H20/InfiniBand hardware and workload, and cluster-scale conclusions beyond 128 GPUs rest on an argument rather than measurement; shift penalties assume τ_shift is a constant, which their own Figure 12 shows is not true across model sizes.

## Strengths

- Identifies and cleanly articulates a real, timely systems problem: GenRM-based RL post-training (as in DeepSeek-R1, GLM-5, Kimi-K3) triples the GPU-hungry stages, and both existing paradigms leave large throughput headroom.
- The design is principled end-to-end: GPS makes parameter availability role-independent, the context taxonomy (discard/offload/preserve) generalizes across all six role-pair shift cases, and reducing rescheduling to Abort+Dispatch on a shared queue is elegant.
- The planner's benefit-minus-penalty formulation with DP candidate construction is a principled answer to shift thrashing, and the ablation confirms it decisively beats both a static split (1.55× vs 1.95×) and a local-utilization heuristic (1.31× vs 1.95×).
- Evaluation depth: 128 real GPUs, dense and MoE models up to a 122B-A10B GenRM, tuned baselines on the same veRL substrate, per-component ablations, second-scale overhead measurements at multiple cluster sizes, sensitivity analysis, and a convergence study showing equal RL quality with ~40% less wall-clock time.

## Limitations

- Single-domain workload (math reasoning on DAPO-Math-17k / AIME24) with a hybrid verifiable+generative reward; the open-ended tasks that supposedly justify GenRMs are never evaluated, so generalization of the throughput gains to GenRM-only or non-math regimes is unverified.
- The overall-throughput objective counts only rollout and reward tokens, and convergence is demonstrated for only one setting; effect of shifting on RL stability under partial rollout or high staleness is not studied (they cite footnote-level staleness handling but defer it).
- Shifting granularity is deliberately coarse (replica-level for inference, whole-training), and the paper's own scalability argument beyond 128 GPUs is analytical, not measured; benefits on higher-bandwidth interconnects (where disaggregation is cheaper) or on smaller clusters are unknown.
- The throughput model constants (A, B, C, D) and the 60 s window H are profiled/tuned per setup; practitioners on different hardware must redo this fitting, and the planner treats shift duration as constant although it varies 1–9 s across model sizes.
- No public code artifact is referenced in the paper, limiting immediate adoption.

## Questions for Further Exploration

- Do the 1.5–2.05× throughput gains persist when the reward is purely generative (no verifiable component) and on open-ended tasks like creative writing or long-form QA, where GenRM response lengths and rollout/reward balance differ substantially from DAPO-Math?
- How does PivotRL interact with orthogonal techniques the authors cite as compatible — partial rollout (AReaL, MiMo), length-aware scheduling (SortedRL, RollPacker, Seer), and per-replica asynchrony (Laminar, StaleFlow)? Is there a combined system where the asynchrony reduces the headroom that shifting exploits?
- What would finer-grained shifting buy: per-GPU (sub-replica) inference shifts or elastic training parallelism, given the paper's argument that the current granularity is purely an overhead/pruning trade-off?
- How sensitive is the planner to its throughput model's offline-fitted constants A–D — could online model adaptation (e.g., updating profiles as batch composition drifts across RL steps) improve shift decisions, especially under distribution shift during training?
- On clusters with faster interconnects (400 Gb/s+ RDMA, NVLink domain spanning more GPUs) or with multi-tenant GenRM serving (Reward-as-a-Service), does the colocated/disaggregated gap — and hence PivotRL's advantage — shrink?
- Does frequent role shifting introduce subtle effects on RL dynamics beyond step-count convergence, e.g., stale-policy rollout mixtures or correlated batching, when combined with aggressive on-policy algorithms?
