Why this matters

A training-free, plug-in provenance audit for context compaction — aimed at the memory-management pain of Claude Code-, Codex-, and OpenClaw-style agents.

免训练、即插即用的摘要来源审查机制，直击长时程 agent 记忆管理与可靠性（cross-run Pass3）的工程痛点。

⚠ Critical edge

Provenance ≠ correctness: supported and unsupported entries are ~90% correct alike (AUROC 0.444). SJC filters grounding, not errors — and deletes ~1/3 of well-grounded entries.

τ=0.5 recovers only 64.2% of supported entries

01

Methodology — a deletion-only post-processor

G may only delete

At every compaction boundary, SJC post-processes the host compressor's candidate summary: judge each entry's provenance, delete what has no source, keep the rest byte-identical. Neither agent nor compressor changes.

constraint  B(Mₜ) ⊆ B(M̃ₜ) — never rewrite, never add · applied at every boundary (unsupported reasoning regenerates each time, ~4 entries/summary)

STEP 1

Generate

Host compressor (OpenClaw, unchanged) emits a structured summary: Decisions / Open TODOs / Constraints / Pending user asks / Exact identifiers.

STEP 2

Judge sources

BM25 over environment outputs (300-char passages → ≤2,000-char chunks, top-3/entry). One request to Jev-1.13, a non-generative decision model returning a calibrated probability the entry has an environment / previous-summary source.

STEP 3

Prune & commit

Entries scoring ≥ τ = 0.5 (untuned) are kept verbatim; unsupported entries removed whole. Judge cost <$0.002/task (≤29K input tokens).

Frozen-agent eval — only the context representation changes; 3 independent runs per config.
Metric — Pass3: solved in all 3 runs; plus Acc., steps, peak input length.
Benchmarks — AppWorld test-normal (168 tasks: 57 E / 48 M / 63 H); OfficeBench ACON (95 tasks: 42 1-APP / 22 2-APP / 31 3-APP).
Models — GPT-5.6 Luna & MiniMax-M3 (agent = compressor); tiny 2K–4K compaction windows force frequent compaction.

03

Strengths

What holds up
  • Names a real, under-formalized failure mode — summary entries acting as self-generated instructions — pinned to commits across 29 deployed systems (21 of 29 prompts ask for decisions or next steps).
  • Minimal, compositional fix: no training, no agent/compressor edits, deletion-only, <$0.002/task — and it actually saves 1.3–8.0% of tokens.
  • Unusually honest self-scrutiny: provenance-vs-correctness AUROC, self-judge ablation, threshold sensitivity, a worked case where pruning hurts.
  • Pass3 reliability framing targets the property practitioners care about for long-horizon agents, not single-run accuracy.
04

Limitations

Where it breaks
  • Filters provenance, not correctness — both kinds ~90% correct; recovers only 64.2% of supported entries, sometimes deleting load-bearing content (4 of 29 traced failures were supported entries).
  • Narrow evaluation: one host compressor (OpenClaw), two benchmarks, 2K–4K windows, single-instruction tasks; multi-turn conversations — where earlier user turns are legitimate sources — untested.
  • Coupled to a proprietary, non-deterministic judge (Jev via OpenRouter); the generative self-judge substitute fails 3 of 4 settings.
  • Moderate absolute gains (2.1–8.9 pts); never beats no-compression — it mitigates, not eliminates, the cost of compaction.
05

Questions for further exploration

from the source note
Does SJC transfer to realistic 128K–1M-token windows, where compaction is rare but each summary is longer and BM25 evidence sparser?
Multi-turn settings: earlier user messages are legitimate sources — can the judge's source set extend to "anything that vanishes after compaction" without degenerating into keep-everything?
Provenance and correctness are statistically independent (AUROC 0.444) — would a two-channel filter (source judgment + separate correctness check) stack the gains?
Can deletion-only be safely relaxed into rewriting — attaching the grounding environment quote instead of dropping information the agent may need?
How does SJC interact with fact-only compressor prompts (8 of 29 surveyed) — does the unsupported fraction collapse, making SJC unnecessary?
Could the bimodal Jev scores support an abstain band (0.3–0.7 flagged for a cheaper second check) to recover part of the 35.8% of supported entries currently pruned?
