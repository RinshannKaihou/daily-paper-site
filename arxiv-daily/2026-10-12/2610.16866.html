Efficient Resource-Shiftable RL Post-training with Generative Rewards (PivotRL)

Yanfeng Zhao, Haoyang Li, Sheng Lin, Yuming Zhou, et al. ·SJTU / PKU / CCNU ·128× NVIDIA H20 cluster ·built on veRL
resource-shiftable deployment RL post-training GenRM GPU scheduling systems efficiency
Key metric · end-to-end throughput
1.98×

22,822 tok/s vs 11,545 for tuned colocated deployment (Qwen2.5-7B policy + Qwen3-30B-A3B GenRM, 128 GPUs). Across all four model groups: 1.81–2.05× vs colocated, 1.50–1.95× vs disaggregated — up to a 72B policy with a 122B-A10B GenRM.

Why this matters

GenRM-era RL post-training triples GPU-hungry stages; PivotRL recasts three-role GPU scheduling as benefit-minus-penalty planning, directly reusable for large-scale RL infrastructure.

⚠ Critical edge

All results come from one math dataset with a hybrid verifiable+generative reward — the GenRM-centric setting is tested in its least GenRM-dependent form; GenRM-only and non-math regimes are untested.

Methodology — the shift loop

PivotRL replaces static GPU splits with runtime role migration. A Global Parameter Storage (GPS) pools cluster CPU memory as a parameter bank for the policy and the frozen GenRM: any GPU can Read parameters under any parallel layout (PCIe + RDMA all-to-all); only the policy Writes, once per RL step, overlapped with training. Every shift decomposes into a shift-down + shift-up, with role context handled by type. A shared-queue scheduler turns rescheduling into native Abort + Dispatch sequence migration, and a five-step planner shifts only when the predicted benefit is positive.

01 · GPS Parameter pool Cluster CPU memory holds policy + frozen GenRM; role-independent availability.
02 · DOWN Shift down Discard stateless buffers · offload optimizer state & CUDA graphs to DRAM · preserve <3.37 GB CUDA/NCCL context.
03 · UP Shift up Read parameters from GPS under any parallelism; training-batch-ready roles get priority.
04 · RESCHED Shift-aware scheduler Shared waiting queue + profiled throughput model; migration = Abort + Dispatch, O(I·NSeq + I·log I).
05 · PLAN DP planner Shift only if B = H·(Tcand − Tcurrent) − φ > 0; H = 60 s window; never thrashes.

Strengths

  • Timely, real problem: GenRM-based RL (DeepSeek-R1, GLM-5, Kimi-K3 class) triples GPU-hungry stages; both colocated and disaggregated paradigms leave large throughput headroom.
  • Principled end-to-end design: GPS makes parameters role-independent; the discard/offload/preserve taxonomy covers all six role-pair shifts; Abort+Dispatch rescheduling is elegant.
  • Planner decisively validated: 1.95× vs 1.55× (static split) and 1.31× (utilization heuristic) in ablations.
  • Evaluation depth: 128 real H20 GPUs, dense + MoE models to a 122B-A10B GenRM, tuned baselines, overhead breakdowns, convergence study (~40% less wall-clock).

Limitations

  • Single-domain workload: math only (DAPO-Math-17k / AIME24) with a hybrid reward; the open-ended tasks that justify GenRMs are never evaluated.
  • Metric caveat: the planner objective counts only rollout + reward tokens — visible throughput dips during training; convergence shown for one model group only.
  • Coarse granularity & unmeasured scale: replica-level inference shifts, training as a monolith; beyond-128-GPU claims are analytical; faster interconnects untested.
  • Per-setup fitting: throughput constants A–D and H = 60 s are profiled per deployment; shift duration is treated as constant though it varies 1–9 s.
一句话总结 · source one-liner (原文)

PivotRL 提出「资源可转移部署」范式：通过集群级 CPU 内存参数池（GPS）、统一的角色上下文转移机制、支持序列迁移的 shift-aware 调度器和基于收益-代价规划的 planner，在 128 卡 H20 集群上把端到端吞吐相对 colocated 提升 1.81–2.05 倍、相对 disaggregated 提升 1.50–1.95 倍，且资源转移仅需数秒、不损害 RL 收敛性。

Questions for further exploration

  • Do the 1.5–2.05× gains persist with purely generative rewards and open-ended tasks (creative writing, long-form QA), where rollout/reward token mixes differ substantially?
  • How does it compose with partial rollout, length-aware scheduling, and per-replica asynchrony — could asynchrony shrink the very headroom shifting exploits?
  • What would finer-grained shifting buy: per-GPU inference shifts or elastic training parallelism?
  • Can the offline-fitted throughput constants A–D adapt online as batch composition drifts across RL steps?
  • Does the advantage shrink on 400 Gb/s+ interconnects or multi-tenant Reward-as-a-Service serving?
  • Do frequent role shifts perturb RL dynamics (stale-policy mixtures, correlated batching) beyond step-count convergence?
