> **一句话总结：** 亚马逊推出 ATTUNE——单个无人值守的 coding agent（Claude Opus 4.8）在用户设定的 GPU 时预算内，通过"逐杠杆诊断式搜索 + 独立于 agent 的确定性正确性门（配置检查 + 20 步损失曲线收敛检查）"自动调优多节点 LLM 训练配方：在 GLM-4.5（128×B200）上较最强公开配方平均提速 33.9%（最佳 54.7%），Llama-3.1-405B 上 +6.7%，并在相同预算下以约一半 GPU 时全面胜过 OptiCo、贝叶斯优化与随机搜索。

> **TL;DR:** ATTUNE (Amazon) turns LLM training-recipe tuning over to a single unattended coding agent that diagnoses each 14-step run, changes one lever at a time over the framework's full argument space (not a fixed knob schema), and ships only recipes passing an agent-independent correctness gate (config check + 20-step loss-curve comparison vs. baseline). On four held-out models at 64–128 GPUs it beats the strongest public recipe by +33.9% mean throughput on GLM-4.5/128×B200 (723.6→969.0 tokens/s/GPU, best campaign +54.7%), +6.7% on Llama-3.1-405B, and honestly ships Mixtral-8x22B unchanged (+0.0%, best candidate only +2.2%, inside the 3% noise band). Under equal GPU-hour budgets it dominates OptiCo (+0.0% on GLM-4.5), Bayesian optimization (TPE, +1.8%) and random search (+7.8%) on GLM-4.5 with +33.9% at 669 GPU-h vs 1,407–1,695 GPU-h for the alternatives, and +164.1% vs the best alternative's +55.5% on MiniMax-M2. Code plus TrainingThroughputBench (correctness-gated leaderboard of fastest known recipes for MoE models up to 744B params) are released.

## 核心贡献

- **单个 agent 的诊断式调优器（ATTUNE）**：一个 coding agent（Claude Opus 4.8，禁用 web 工具）在无人值守的 harness 中完成整个调优循环——诊断每次运行的瓶颈、必要时 profile、在启用任何 flag 前先读其在训练镜像中的源码实现、每次只改一个杠杆（或一组耦合的并行度）、在预算内或判定收敛后停止。
- **独立于 agent 的正确性门（correctness gate）**：两层确定性检查保证"提速不改变训练目标"——(1) 启动前配置检查，拒绝任何改变数值/目标的参数或命中已知栈缺陷的配置（在完全解析后的参数与环境上复查，防止 flag 静默改写，如 `--grad-reduce-in-bf16` 会顺带关闭 FP32 梯度累加）；(2) 基于 Megatron-Bridge 的 20 步损失曲线收敛检查（逐步容差 2–10%、最终损失差 ≤5%、相关系数 ≥0.95）。在 133 个合法运行上零误拒，24 个故障运行中拦下 16 个。
- **可自进化的 tuning skill**：杠杆目录（lever catalog）沉淀历史 campaign 的经验（机制、适用场景、方向、量级），campaign 结束后 agent 把可泛化的教训写回 skill 供后续 campaign 使用；append-only ledger 保证崩溃后可恢复。
- **统一协议下的系统评测**：四个留出模型（Llama-3.1-405B、Mixtral-8x22B、GLM-4.5、MiniMax-M2）上，从最强公开配方出发，与 OptiCo、贝叶斯优化（TPE）、随机搜索在相同 GPU 时预算、相同正确性门、相同裁决规则（mean rule + 置换检验）下对比。
- **TrainingThroughputBench (TTB)**：开放的训练吞吐排行榜——每个模型×加速器组合的最快已知配方，附 tokens/s/GPU、每百万 token 成本、通过的 correctness check，覆盖至多 744B 参数 MoE 模型、至多 256 GPU；代码与排行榜开源（github.com/amazon-science/attune）。

## Key Contributions

- **ATTUNE, a single-agent throughput tuner**: one coding agent (Claude Opus 4.8, web tools disabled) runs the entire tuning loop unattended — diagnosing each run's bottleneck from metrics/logs, profiling when needed (one traced rank per pipeline stage, split into compute/communication/host/idle), reading a flag's implementation in the training image before using it, and changing one lever (or one coupled parallelism set) per candidate within a user-set GPU-hour budget.
- **An agent-independent correctness gate** — the key safety mechanism no prior LLM-training tuner has: a pre-launch configuration check refuses any objective-changing or unlisted numeric argument and known stack defects (re-checked on fully resolved args, catching silent overrides like `--grad-reduce-in-bf16` disabling FP32 gradient accumulation), and a 20-step convergence check compares the candidate's loss curve against the baseline's (per-step tolerance 2–10%, final loss within 5%, correlation ≥0.95). It rejected 0 of 133 legitimate runs and caught 16 of 24 faulty runs.
- **A self-evolving tuning skill**: a lever catalog distilled from past campaigns (mechanism, when it helps, direction, rough size) plus a ledger and campaign summaries the agent writes back for later campaigns; an autonomous harness (stop hook, pre-tool hook, deny-by-default shell policy, crash-resume from the ledger) keeps it running for hours.
- **A rigorous common-protocol evaluation** on four models held out from development (dense Llama-3.1-405B plus MoE Mixtral-8x22B, GLM-4.5, MiniMax-M2 at 64–128 GPUs), starting from the strongest public recipe, against OptiCo, Bayesian optimization (TPE), and random search under identical budgets, gates, and a single mean-rule decision procedure with permutation p-values.
- **TrainingThroughputBench (TTB)**: an open leaderboard of the fastest known correctness-gated training recipes per model/accelerator (MoE up to 744B parameters, up to 256 GPUs), each with tokens/s/GPU and cost per million tokens; ATTUNE's code and TTB are open-sourced at github.com/amazon-science/attune.

## Methodology

ATTUNE separates tuning into an agent-driven search and deterministic checks outside the agent. A *campaign* tunes one model on one cluster at a fixed GPU count, starting from a working baseline recipe under a GPU-hour budget.

**Measurement (fixed-shape workload).** The workload (model, real-text dataset packed to exactly the sequence length, global batch, precision, GPU count) is held identical across candidates so throughput differences reflect the recipe. Each run lasts 14 optimizer steps; steps 0–3 (startup/compilation) are discarded and steps 4–13 form the measured window, scored as aggregate tokens/s/GPU (sum-then-divide so short steps don't dominate). The baseline is run ≥5 times on different node allocations; its mean is the gain denominator and its relative std sets the noise band max(3%, 3σ). A candidate replaces the leader only when it beats the leader by more than the band.

**Search loop.** The agent runs a reason–act loop (file search/read including framework source, shell, cluster API) guided by a tuning skill with six discipline rules: (1) state a hypothesis (bottleneck, mechanism, expected gain) before each launch; (2) change one lever or one coupled parallelism set (world = TP·PP·CP·DP; MoE experts further split ETP·EP·EDP = TP·CP·DP) per candidate; (3) read a flag's implementation before using it and record the code location; (4) rule out a lever only after two values measured or its feasible limit, and call topology exhausted only after probing TP/PP/EP/CP/DP; (5) when trying a new layout, start without the leader's memory savings and, if it OOMs, retry with them before ruling it out; (6) re-test winning flags after the layout changes. The control plane refuses to relaunch an identical recipe (infrastructure failures excepted), charges every job its GPU-hours including failures and checks, and admits launches only within budget.

**Correctness gate (two layers).** Levers are classed as structural (placement/scheduling only), same-math (e.g., fusion, optimizer offload), or numeric (dtype/precision/loss/routing/batch/LR); only the first two may run or ship. Layer 1 checks every argument against per-model lists no tuner can edit, both pre-launch and on resolved args of final candidates. Layer 2 runs each final candidate 20 steps on the baseline's data/seed and applies Megatron-Bridge's convergence check. The control plane checks up to three final candidates fastest-first and ships the first that passes, or the baseline if none does.

**Harness.** A stop hook blocks the agent from ending its turn until the budget is spent or an evidence-backed stop is recorded; a pre-tool hook auto-takes defaults instead of asking the user and enforces a deny-by-default shell policy; an append-only ledger lets a fresh session rebuild and continue the campaign after crashes or context compaction.

**Evaluation setup.** Four held-out models at their public recipe's workload on H100/B200; every tuner (ATTUNE, OptiCo with its 11-knob schema, TPE Bayesian optimization ± analytical memory pre-filter, random search) gets the same budget (30× one baseline benchmark run), sandbox, and gate; 3 campaigns per tuner per model; final numbers come from two re-measurements of baseline and shipped recipes in randomized interleaved order, judged by the mean rule with permutation tests.

## Results & Highlights

- **GLM-4.5 / 128×B200**: mean throughput rises from the public recipe's 723.6 to 969.0 tokens/s/GPU — a **+33.9% mean gain (best campaign +54.7%), MFU 7.2% → 9.7%** — by moving expert all-to-all inside a node (EP=8), some campaigns swapping in the DeepEP dispatcher, and the best campaign dropping tensor parallelism to 1 (TP1 at 16 pipeline stages) after retrying the OOM layout with full recomputation.
- **Llama-3.1-405B / 128×B200**: **+6.7% mean (397.3 → 423.9 tokens/s/GPU; best campaign +11.9%; MFU 22.3 → 23.8)** by cutting pipeline send/recv traffic across nodes (e.g., 8 stages × 8 virtual stages → 16 stages × 2, dropping DP to 1). **Mixtral-8x22B / 128×H100: +0.0%** — the best candidate measured only +2.2% during search, inside the 3% noise band, so all three campaigns shipped the public recipe unchanged (an honest no-op).
- **Tuner comparison, GLM-4.5 (budget 1,880 GPU-h)**: ATTUNE **+33.9%** using 669 GPU-h and 6.4 h wall-clock, vs random search +7.8% (1,688 GPU-h), BO+pre-filter +3.9% (1,695), BO/TPE +1.8% (1,675), and **OptiCo +0.0% (1,407 GPU-h, 15.7 h wall-clock, ~3× the launches)** — ATTUNE's mean gain is >4× the best alternative at less than half the GPU-hours, every ATTUNE campaign gained ≥22%, while 8 of the other tuners' 12 campaigns shipped the public recipe unchanged.
- **Tuner comparison, MiniMax-M2 / 64×B200**: ATTUNE **+164.1%** with 203 GPU-h, 13.3 launches, 3.1 h wall-clock, vs BO+pre-filter +55.5% (489 GPU-h), BO +46.1% (492), random +32.7% (487), OptiCo +22.4% (386); on both models the tuning pays for itself within a day of training, at least 4× sooner than any other tuner.
- **Correctness gate**: on runs with known answers it **passed all 133 legitimate runs (0 false rejects) and caught 16 of 24 faulty runs** — layer 1 refused all 6 objective-changing arguments and 4 configuration defects pre-launch, and the convergence check caught all 6 code faults that break the loss; the 8 misses were 4 subtle faults (e.g., one gradient bucket's reduction skipped, load-balancing loss zeroed, loss mask shifted by one token, QK-norm gradients summed over TP ranks) that move the 20-step loss less than tolerance at early-step learning rates; a 1,000-step run of the shipped MiniMax-M2 recipe confirmed losses agree within run-to-run noise and the 14-step gain holds.
- **Ablations (GLM-4.5)**: removing the lever catalog ties full ATTUNE (+30.1% vs +33.9%, inside the 3% band), a multi-agent committee arm gets +28.3%, a public-guide-only catalog +29.1% — but full ATTUNE's **best campaign is 17% faster than the minimal skill's best**, and the largest gains trace to one search rule (rule 5: retry the OOM TP1 layout with recomputation), which only 1 of 3 full-ATTUNE campaigns applied (that campaign gained 54.7%); diagnosis let ATTUNE reach a winning recipe in ≤8 launches while black-box search with the same levers available mostly OOMed or got pruned.

## Authors & Credibility

Eleven authors (Leo Fan, Hongyang Wang, Wenbo Chen, Jingguo Liu, Xian Li, Xuan Wang, Ruochen Wen, Yiming Yan, Hao Wu, Zheshen Wang, Benoit Dumoulin) all affiliated with Amazon, corresponding author Leo Fan (jianhfan@amazon.com). This is a systems-paper team with access to real 64–128 GPU H100/B200 clusters, which the results (multi-hundred-GPU-hour campaigns, 669–1,695 GPU-h per arm) plainly required — the work cannot be faked on a workstation. Credibility is strengthened by unusual honesty: shipping Mixtral-8x22B's recipe unchanged when nothing cleared the noise band, an explicit Limitations section admitting lower absolute throughput than published vendor figures on their stack, and releasing code plus the TrainingThroughputBench leaderboard at github.com/amazon-science/attune. Statistics are taken seriously (mean rule + exact permutation and block-stratified p-values, 3 campaigns per arm, randomized interleaved final re-measurement), though n=3 makes several verdicts admittedly "weak." Agent model is named (Claude Opus 4.8, web tools disabled, frozen skill) rather than hidden.

## Critical Assessment

- **Novelty: solid, incremental.** The run-and-measure agent loop exists (OptiCo, PROMPTS, ASAP); the genuinely new parts are (a) searching the framework's full argument space instead of a fixed 11-knob schema, and (b) the agent-independent correctness gate — a real contribution since a microbatch change can alter MoE load-balancing loss and a "communication" flag can disable FP32 gradient accumulation while the job still runs to completion. TTB is a useful community artifact.
- **Rigor: strong protocol, weak n.** Equal budgets, shared gate, interleaved re-measurement, and permutation tests are better than most systems papers. But 3 campaigns per arm yields p = 0.05–0.10 unrestricted and 0.125 block-stratified — the lowest that test allows — and the authors themselves call ablation verdicts weak. Campaign-to-campaign variance (+22.4% to +54.7% on GLM-4.5) swamps most arm differences.
- **Red flags / paper-specific caveats**: (1) The headline +33.9% on GLM-4.5 measures improvement over a public recipe *written for H100 and ported to their B200 stack* — some gain is porting friction, not tuning genius; their stack also only reaches 397.3 vs the published 661 tokens/s/GPU on Llama-3.1-405B (259.7 vs 445 TFLOP/s on Mixtral), which they attribute ~30% to slime's inter-step work. (2) GLM-4.5 is in the same family as development model GLM-5.2, so catalog priors could leak — though the no-catalog ablation tying full ATTUNE (+30.1% vs +33.9%) suggests the effect is small. (3) Only the models are held out; the stack, accelerators, and agent model are exactly those used in development. (4) The search rules are advisory — the agent skipped rule 5's OOM-retry in 2 of 3 GLM campaigns, so the best result hinges on LLM rule-following luck, which the paper candidly flags as the top next fix. (5) The OptiCo baseline runs outside its native environment with its schema frozen at baseline values for levers outside its 11 knobs — fair to OptiCo's design, but the comparison is on ATTUNE's home stack. (6) The gate's 20-step check misses 8/24 injected faults by design (favoring false accepts), and long-run convergence was verified for only one shipped recipe (1,000 steps).
- **Reproducibility: good.** Open-source code and leaderboard, fixed measurement protocol (14-step runs, steps 4–13, packed real text, fixed row order), frozen skill for evaluation arms, append-only ledger. The main barrier is hardware: reproducing campaigns needs hundreds of GPU-hours on B200/H200-class clusters.
- **Significance: practical and real.** A +33.9% throughput gain that pays for itself within a day of training is directly monetizable for anyone training at scale; the correctness-gate design pattern (deterministic checks outside the LLM agent) generalizes beyond throughput tuning.

## Strengths

- Diagnoses each run like an expert (bottleneck → lever, with profiling) instead of black-box sampling; this is shown to matter — black-box search had every winning lever in its space on GLM-4.5 yet mostly OOMed or got pruned, while ATTUNE reached a winner in ≤8 launches.
- Correctness gate enforced by the control plane, not the agent, with measured false-accept/false-reject rates (0/133 legitimate rejected, 16/24 faults caught); the config check even re-runs on fully resolved arguments to catch silent flag overrides.
- Honest negative results: ships Mixtral-8x22B unchanged (+0.0%) when nothing clears the noise band, and reports the noise band itself (max(3%, 3σ)) rather than claiming noise-level wins.
- Strong engineering for autonomy: stop hooks preventing premature exit, pre-tool hooks replacing user questions with recorded defaults, deny-by-default shell policy, crash-resume from an append-only ledger.
- Ablations ask the right question (does the catalog matter? single agent vs. committee?) and find the uncomfortable but useful answer: the biggest gains come from one retry rule, not the accumulated knowledge.
- Releases both the tool and TrainingThroughputBench — a correctness-gated, cost-annotated leaderboard that fills a real gap left by vendor tables and MLPerf.

## Limitations

- Baselines are public recipes run on the authors' stack (slime + Megatron-LM), each tuned by its authors for different hardware/GPU counts; gains measure improvement over these recipes *in their setting*, and their stack reaches materially lower absolute throughput than published figures (e.g., 397.3 vs 661 tokens/s/GPU on Llama-3.1-405B).
- Generalization is narrow: only the models were held out — every campaign ran on the authors' stack, their accelerators (H100/B200), their network (whether DeepEP works across nodes is stack-specific), and one agent model (Claude Opus 4.8); no other stacks or agent models were evaluated.
- The lever catalog may leak family-specific priors (development model GLM-5.2 vs evaluation model GLM-4.5).
- Skill rules are unenforced: rule-following is at the agent's discretion, and skipping the rule-5 retry cost 2 of 3 GLM campaigns roughly half the achievable gain — the paper names enforcing rules in the harness as the top next step.
- Scope is configuration-only: no framework code modification, no kernel writing, no custom image; RL rollout/generation phases are not covered; no optimality guarantee on the returned recipe.
- Statistical power is limited (3 campaigns/arm; several comparisons at p = 0.05–0.125), and the gate's 20-step window, while validated to 1,000 steps for one recipe, remains a short-horizon proxy for training-quality preservation.

## Relevance

对于关注大规模 LLM 训练系统效率的用户，这篇论文直接命中"并行策略/训练配方自动化调优"这一核心痛点：它展示了 coding agent 在真实 64–128 GPU 集群上无人值守完成专家级吞吐调优（GLM-4.5 +33.9%、MiniMax-M2 +164.1%），其"LLM agent 搜索 + 确定性外部门控"的设计范式对任何涉及 LLM 自动化系统运维（auto-tuning、性能诊断）的研究都有借鉴价值。

## Questions for Further Exploration

- Would enforcing the six search rules in the harness (rather than leaving them to agent discretion) close the campaign-variance gap and make the +54.7% outcome the norm instead of the lucky 1-of-3?
- How does ATTUNE behave on held-out *stacks*, clusters, and agent models — e.g., open-source models like Qwen3 or DeepSeek-V3, AMD accelerators, or cheaper/faster agent models where rule-following may degrade?
- Can the 20-step convergence check be replaced or augmented by a cheap long-horizon guarantee (e.g., gradient-statistics fingerprints) to catch the four subtle fault types that currently pass?
- Could the approach extend to the RL training loop's rollout/generation phases, or to tuning ZeRO/FSDP stacks outside Megatron — where the flag-interaction graph (silent overrides) is different?
- What happens when multiple teams' campaigns feed a shared skill: does the self-evolving catalog compound (better initial levers, fewer launches), or does stale, stack-specific advice start to mislead?
- On Mixtral-8x22B the search found nothing above the 3% band — is there a diagnosable reason (already near-optimal H100 recipe?), and would a larger budget or a data-shape change open headroom?
