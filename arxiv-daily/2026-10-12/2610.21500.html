When the KV Cache Is Slower Than the GPU: Scaling Remote KV Tiers for Context-Parallel Prefill

Muhammad Ibrahim · Multiverse Computing 2026-10-12 llm-serving kv-cache context-parallelism distributed-systems

Key metric — tail latency

124×

Hit-heavy p99 TTFT 83.32 s → 0.67 s; p50 9.70 s → 0.40 s on the 450-request replay (98.5% of tokens served from L2).

Single-instance synchronous tier → 8 sharded Valkey instances + async loading + 3 client-bug fixes.

Why this matters

Judge a KV cache tier against your GPUs' prefill rate, not network latency — break-even bandwidth B\* = sR rises with every GPU generation.

Critical edge

The 124× is measured against the paper's own pathological baseline — versus plain recompute, the best config's median hit (0.40 s) is still 0.09 s slower.

Methodology

A production regression disciplined into a falsifiable cost model, then fixed and re-validated end to end.

  1. 01
    ObserveEnabling LMCache's remote L2 (Valkey) regresses production 16k p99 TTFT 3.96 → 17.3 s (32k: 6.06 → 25.0 s); rolled back.
  2. 02
    ReplayThe exact 683-request router-log stream on an isolated 8×B300 node, identical container (vLLM 0.31.0, LMCache 0.5.5, FlashInfer 0.7.0, NCCL 2.30, CUDA 13.0); hit-heavy subset = 98.5% L2 tokens.
  3. 03
    ModelFit T₀ on one point only; validated out-of-sample (0.79 s predicted vs 0.83–0.88 s measured on runs not used for the fit).
  4. 04
    FixSharded MLA store (chunk c → rank c mod W, Prop. 1 keeps lookup correct), one Valkey per rank via {rank} URL, async loading, three hang-forever client bugs fixed.
  5. 05
    ValidateNeedle-in-a-haystack 24/24, 3,000-pattern property test, 30-min 1,549-request soak with zero errors; 5-node SLA benchmark passes.

T_load = T₀ + ns/B  vs  T_recompute = n/R
⇒ break-even B\* = sR ≈ 2.53 GB/s (s = 48.4 KB/tok, R = 52.2k tok/s on one B300 node)
⇒ fixed floor R·T₀ ≈ 17k tokens — shorter prompts lose at any bandwidth

Results & Highlights

The regression that started it: with the remote tier ON in production, 16k p99 3.96 → 17.3 s, 32k p99 6.06 → 25.0 s — median unchanged, tail destroyed.

  • The problem, isolated: a 16k hit took 0.88 s vs 0.31 s to recompute; one Valkey tops out at 1.71 GB/s < B\* = 2.53 GB/s, and the sync path becomes an unstable queue (ρ ≈ 1.13, 59 requests queued, GPUs 7% busy).
  • Correctness: 24/24 needles across cold/L1/L2/control (up to 166.7k tokens), 36/36 in a concurrent burst, zero errors in the 1,549-request soak.
  • Honest ceiling: best config's median hit (0.40 s) remains 0.09 s slower than recompute — the tier's value is tail stability and freed GPU capacity, not median speed.

Strengths

  • Crisp, falsifiable two-parameter cost model (B\* = sR, T₀), validated on configurations not used for the fit.
  • Coordination-free scale-out as a corollary of static chunk ownership: one Valkey per rank, no hashing, no cluster protocol, cross-engine reuse preserved.
  • Correctness treated as first-class: a proof that existing lookup stays correct under sharding, property tests with injected failures, non-determinism-aware needle tests.
  • Every fix upstreamed with a regression test — six LMCache PRs plus the FlashInfer kernel PR.
  • Exceptional measurement honesty: production / replay / model numbers kept separate; the residual 0.09 s gap is decomposed, not hidden.

Limitations

  • Every condition run exactly once; no error bars; differences under ~10% (e.g. sync vs async on 8 instances) not statistically established.
  • One prompt-length bucket (14.7k–17.9k) for all latency results; T₀ fitted on a single point; the ~17k-token break-even is an untested prediction.
  • The 98.5% hit-heavy subset was engineered to fit the cache (flush + prime + restart); production hit rates were 1–35%, and eviction would add EXISTS-to-GET races.
  • Prefill-only replay: KV handoff to decode omitted; multi-engine contention estimated (~2 GB/s for six engines), not measured.
  • Constants specific to GLM-5.3 FP8 MLA on B300; no RDMA-transport or compression alternatives evaluated yet.

Questions for Further Exploration

  1. Where does the ~17k-token break-even move for GQA/MHA models with 5–20× larger per-token KV — a clear median-latency win at much shorter prompts?
  2. Would an RDMA-backed store (Mooncake-style) meet B\* = 2.53 GB/s, and does rank-partitioning compose with RDMA transports?
  3. Can T₀ be shrunk by batching per-owner chunks into one collective — and would a load-or-recompute admission policy recover the 0.09 s median gap?
  4. Do results hold under real multi-engine contention and production eviction, where hit rates drop from 98.5% to 10–35%?
  5. How many rank-mismatched kernel inefficiencies (like the SwiGLU that wasted 17% of prefill GPU time under EP8) lurk in other fused kernels?

Relevance 相关性

面向大规模 LLM 推理集群中集合通信（AllGather / PCP 锁步）、远端 KV 分层与多引擎共享基础设施的性能与正确性工程："缓存层必须对标硬件预填充速率而非网络延迟"的 B\*=sR 判据、按 rank 无协调扩展远端层的设计，以及三个令引擎静默停摆的客户端 bug，对构建可靠推理服务栈有直接参考价值。
