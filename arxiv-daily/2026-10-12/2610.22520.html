⚠ Critical edge

How corrupted outputs were assigned to the four failure categories is never specified — manual or automated, by whom, with what agreement — leaving every distribution result hard to reproduce.

Methodology

Fault model & the LLMEI injector

Soft errors are simulated as random bit flips injected into LLM parameters at a target bit-error rate, mirroring transient SRAM upsets on DNN accelerators (ARES / Goldeneye practice). The BER sweep is grounded in measured hardware regimes, from ECC-protected DRAM to radiation-exposed systems. Robustness = pass@1 under rising BER, each configuration averaged over 10 trials.

  1. 01Allocate zero-initialized binary error maps shaped per tensor, plus a bit-width dim (fp32 → 32).
  2. 02Match user JSON config → target parameters (or activations), per component.
  3. 03Generate flips probabilistically by BER or fixed count via torch.rand / torch.randperm.
  4. 04Inject: re-interpret tensors as torch.int32 via torch.view, apply with torch.bitwise — no Python-level bit-casting.

→ injection phase >1,000× faster than bitstring/struct frameworks — which cannot finish at LLM scale at all.

Strengths

What this paper gets right

  • First causal, distributional characterization of hardware-provenance hallucination — an underexplored axis, posed as a clean falsifiable question.
  • The four-category taxonomy is concrete, illustrated with real examples, and directly usable for failure-mode-specific runtime detectors.
  • LLMEI is the missing tool: config-driven (component / BER-or-count / params-or-activations), open-sourced, >1,000× faster injection.
  • Operationally meaningful: component ranking and the 10⁻⁹ code cliff give concrete priorities for selective ECC budgets on accelerators.
  • Real-world grounding: BER tied to measured hardware conditions, 10 trials per config, 3,200 GPU-hours.
Limitations

Where to read carefully

  • Taxonomy-labeling procedure unspecified (manual vs. automated? annotator agreement?) — the single biggest reproducibility gap.
  • Uniform random flips only: no clustered multi-bit-upset patterns, no bit-position (sign / exponent / mantissa) analysis, no real-hardware validation.
  • Evidence lives in stacked-bar figures: no numeric tables, no confidence intervals — despite 10-trial averaging being available.
  • Narrow scope: AIME 2024 is ~30 problems; models top out at 8B; activation injection supported but never exercised; code-model roster counts slightly inconsistent.
  • Deliberately diagnostic-only: no detection or mitigation is proposed or evaluated.
Questions for further exploration

Open threads

  1. Q1Would protecting only exponent bits (or early NaN/Inf detection) postpone the III → I transition by orders of magnitude?
  2. Q2Do spatially clustered multi-bit upsets — real SRAM MBU patterns — shift the thresholds, especially the 10⁻⁹ code cliff?
  3. Q3Can the four categories be auto-labeled reliably at scale (perplexity spikes, language-ID) for continuous serving telemetry?
  4. Q4Does activation-only injection — already supported by LLMEI — show the same component and BER sensitivity as parameter injection?
  5. Q5Do INT8 / INT4 quantized models mask mantissa errors — or make every bit more lethal?
  6. Q6Can runtime detectors separate soft-error Logical Corruption from ordinary hallucination, cost-effectively, in the fragile BER regimes?
