Why this matters

Evaluation cost is the real bottleneck when agents optimize LLM systems; the yardstick + fidelity-test recipe transfers to any expensive-to-evaluate automated experiment.

「代理评估器 + 保真度校验」的思路对任何评估昂贵的自动化实验流程（基准测试、训练配置搜索）都有直接借鉴意义。

Critical edge

All main-table results are single-run — the 3-seed variance study covers only subsamples, not the headline tables — and each kernel run costs ~$375 of proprietary API with no code release.

01 Methodology — two loops, one guardrail

One true evaluation costs minutes-to-hours (85 min for a vLLM serving benchmark, up to 28 h for a CPU microarchitecture simulation), so a 20-hour budget affords only ~a dozen real evaluations. DuoDiscover spends them only where they count.

STEP 1

Fast inner loop seconds / edit

Each of N agents profiles its own codebase copy, picks a target T (bounded by an Amdahl-share guess w_T), writes a cheap yardstick g_T — a shrunken input, a profiled hot loop, a decode-cost model that only has to rank edits like the true objective — then hill-climbs on it (40 s vs 15 min true eval; 22× faster).

STEP 2

Slow outer loop hours / eval

True evaluations confirm yardstick-reported gains; only confirmed gains are accepted. After every true eval, a Kendall-τ fidelity test (τ ≥ 0.5, on pairs above evaluation noise) rechecks each yardstick — drifting proxies are invalidated and rebuilt, so reward hacking can never fake a gain.

STEP 3

Orchestrator coordination, not planning

No central decomposition. An LLM orchestrator periodically terminates stalled agents, spawns fresh / transfer / combine agents, and briefs runners on the fleet's confirmed findings — aiming the expensive true-eval budget at what works.

Reporting discipline: score = median of repeated re-evaluations of the final candidate, selected by lower confidence bound; correctness failure = no result; best-score-seen during search is never reported.

Strengths
  • Attacks the real bottleneck — evaluation cost, not another search-harness tweak: vLLM used 7 true evals for 1.92× vs Claude Code's 12 for 1.07×.
  • Fidelity test turns proxy search from "trust me" to "verify continually"; publishing the ablation where untested yardsticks hurt is a genuinely useful negative result.
  • Breadth across the full stack: 6 benchmarks + 5 production cases — Python repos, CUDA/Pallas kernels, serving systems, SQLite/zstd, chip microarchitecture.
  • Honest measurement hygiene (median-of-re-evals, LCB selection, correctness failure = no result) plus external anchors: public leaderboards, maintainer review, an upstream merge.
Limitations
  • Single-run headline results; seed variance measured only on subsamples (20 repo tasks, 50 kernels).
  • Yardstick churn: 41–45% of validated yardsticks invalidated after ~15–19 candidates; 53% of pursued kernel targets never confirm a gain.
  • Expensive and proprietary: frontier closed-weight agents, ~$375 API per kernel run before GPU time, multi-day DPC4 runs, no stated code release.
  • Heuristic thresholds (τ ≥ 0.5, noise filter) unexplored for sensitivity; short-budget regime acknowledged but not benchmarked; DPC4 human/ArchAgent comparisons are transplanted numbers, not re-runs.

04 Questions for further exploration

Q1Would a stricter τ bar cut the 41–45% yardstick-invalidation churn — and at what cost in discarded, still-useful yardsticks?
Q2Can validated yardsticks be amortized into a reusable library across tasks, or does drift make every yardstick fundamentally single-run?
Q3The orchestrator is itself an LLM — would a deterministic orchestrator (bandit allocation over agents) match its +6.37 SOL contribution?
Q4Is there a crossover point — as true-eval cost falls — below which plain agentic search wins, and can warmup cost be cut by warm-starting yardsticks?
Q5Do DPC4's discovered prefetcher designs transfer across trace sets, or are they overfit the way yardsticks drift?
Q6Does the recipe raise weaker open-weight agents to competitive levels, enabling reproducible open-source replications?
