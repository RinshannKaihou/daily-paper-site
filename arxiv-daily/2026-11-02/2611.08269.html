Why it matters

A green CI run can hide a repair that silently changes behavior. One cheap, release-note-derived input catches most of them before shipping.

Release gating · agent pipelines
Critical edge

The 0.410 headline is a property of these author-built menus, not of release gates in general: changing the menu alone moves the rate by ~0.14.

Critical assessment · point 3
01

How they measured a gate's blind spot

No sampling: every candidate repair runs against contracts the repairer never sees.

  1. 1

    Build a finite repair space

    73 tasks across CPython 3.9→3.12, Node.js 20→24 and SQLite 3.51→3.54. Each repair is a choice of documented fragments: 405 → 1,491 → 1,689 fragments, up to 2,310 procedures.

  2. 2

    Withhold the oracle

    Contracts and hidden inputs are never shown to the repairer. Expected outputs come only from the old runtime; every candidate executes offline on the real runtime.

  3. 3

    Swap only the gate's inputs

    T typical inputs; E T plus one release-note edge input that must make the stale procedure fail; W blind-writer inputs; G only inputs the writer calls legacy-binding; S self-tests.

  4. 4

    Score the complete space

    Report false acceptance and false rejection over every program, average within change clusters, and test with sign-flip permutations under two SHA-256 preregistration freezes.

Blind writer An isolated GPT-5.6-luna sees no program, template, fragments or hidden inputs: one call per task, at most three inputs.

03

Where it holds, where it strains

The paper's own failures are part of the evidence.

Strengths

  • A new, falsifiable question: how often a given release check would ship a wrong repair, measured over the whole repair space rather than one failing test.
  • Real substrate: real runtimes, verbatim release notes, withheld contracts, offline execution. No simulated APIs, no LLM-as-judge for correctness.
  • The blind-writer arm answers the obvious confound and reports its overlap: 3 inputs equal a hidden one; mean similarity 0.70.
  • Failures reported as failures: the guard misses its ceiling, LM3 reverses, the strong-evidence criterion is declared unmet.
  • A cheap, specific recipe: one call per task, expected outputs from the old runtime, and never let the writer adjudicate bindingness.

Limitations

  • No free-form repair: every repair is a choice among author-written fragments. The authors explicitly do not claim transfer.
  • Menu dependence: the headline rate moves by ~0.14 with menu construction, and 0.168 of the hard-origin wrong programs still pass the edge gate.
  • Everything is author-built and no human signed the contracts. The AI audit flags 34/73; the R2 class-label dispute stays open.
  • Only four model families. The confirmatory base is two 8B-class models; the frontier model sits near ceiling (p = 0.499), and gemma was excluded for a serving artifact.
  • Artifacts on request only, so the hidden evaluation key cannot be independently audited.
  • Difficulty may be unrepresentative: GPT-5.6-luna solved 37/45 CPython tasks with no release notes at all.
04

Open questions

What would decide whether the recipe is deployable.

Q1

Does the edge-input effect survive free-form repair, where the model writes code instead of picking fragments?

Q2

Why does the false-acceptance rate fall as the menu grows while the absolute count of indistinguishable wrong programs rises?

Q3

Can bindingness be decided mechanically, instead of asking the writer which legacy outputs still constrain?

Q4

If 0.168 of legacy-matching wrong programs pass every visible check, is the right policy abstention, human review, or differential testing on production traffic?
