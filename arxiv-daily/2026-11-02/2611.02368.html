Counter-example
10×

Qwen-32B already produces ten times the compile errors of Qwen-7B at BF16 (13.3% vs 1.3%), climbing to 17.7% / 20.7% after quantization — large, but not significant (pHolm = 0.97 / 0.75).

Failure profiles diverge by model; they do not converge on one “quantized” pattern.

How it was measured →
02

The setup

One benchmark · four models · three precisions

An execution-feedback agent is not a single generation: it writes code, runs it, reads the failure, and tries again. The study asks what 4-bit weights do to that loop — and measures the loop, not just the final score.

01

Benchmark

OJBench Easy+Medium: 115 NOI/ICPC problems, Python only. The Hard split is excluded — every configuration scored 0%.

02

Quantize

W4A16 AWQ and GPTQ via llmcompressor; 256 calibration samples, 1,024-token sequences; weights only, ≈3.4× smaller.

03

Run the loop

vLLM, one tool python_executor(code, stdin), 30 s timeout, at most 5 calls, temperature 0.6, 32k context.

04

Three axes

Accuracy; solve path (one-shot vs loop, valid tool use, mean calls); terminal failure class — IR / WA / TLE / CE / MLE.

05

Inference

Exact McNemar on 345 pairs, Holm across eight comparisons, plus cluster bootstrap (20,000 resamples) and within-problem permutation.

03

Strengths & limitations

Workshop-length scope, main-track question

What holds up

05
  • Measures what pass rate hides. Solve path, tool validity and failure class are exactly what a deployment engineer needs.
  • A clean within-problem control. The 8/8 one-shot→loop flip removes the difficulty confound that plagues before/after comparisons.
  • Statistics beyond the workshop norm. Holm correction, exact McNemar, cluster bootstrap and permutation tests that respect seed correlation.
  • Honest about the borderline case. 32B/AWQ is reported with raw p, adjusted p, CI and problem-level p — and labelled not significant.
  • A usable negative result. For a 7B–14B coder served at W4A16, the accuracy cost is plausibly within noise.

What doesn't

05
  • Underpowered by design. 5–16 solves per configuration; with no equivalence test, “no significant loss” cannot separate no effect from a 3-point drop.
  • The promised ablation is missing. No single-pass control, so “the loop absorbs the error” is never tested against “the benchmark is too easy to show damage.”
  • One of everything. One benchmark, Python only, one scaffold, W4A16 only — no FP8, 3-bit or KV-cache quantization.
  • Cost is never measured. No latency, throughput, memory or cost per solve; 3.4× storage is the only efficiency number, and loop solves may add turns.
  • Recipe not reproducible. Calibration corpus unnamed, group size / act-order / damping unreported, seeds unspecified, no code release.
04

Open questions

What the next run should test
Q1 · EQUIVALENCE

Would a TOST with a ±2-point margin reject “no accuracy loss” for Qwen-32B? Its problem-level CI is [0.58, 6.09] — probably yes.

Q2 · CONTROL

Does a no-tool run on the same problems show the loop absorbing error, or the benchmark being too blunt to see it?

Q3 · MECHANISM

Is Qwen-7B's vanished one-shot ability a capability loss or a shifted “test first” policy? A tool-forbidding prompt would separate them.

Q4 · COST

Does the one-shot→loop shift burn more tokens than 4-bit weights save? Measure per solved problem, not per attempt.
