01

Two controls, one serving path

PACE keeps “which tokens” and “where they sit” separate — then fixes both. Built as an H2O subclass in SparseEngine; one 24 GB L4, Qwen3-8B, greedy decode, persistent sessions, 2,048 resident tokens (4 sink + 128 recent).

  1. STEP 01

    Blueprint → span table

    The planner already emits a step-dependency DAG. It is sent to the server as a blueprint, which maps each message to its token span and records which future step will read it.

  2. STEP 02

    Foresight bonus

    Referenced tokens get β_t = σ(½ + ½e−λ(s⋆−t)), λ = 0.35, added to H2O's cumulative attention score. σ = 10⁵ puts a 50K floor above every observed score (max 25K at 2M tokens), so planned tokens outrank unplanned ones.

  3. STEP 03

    Bounded positions

    As positions approach L = 8,192, resident rows are renumbered to {0…R−1} in logical order and each key is re-rotated from the engine's own cos/sin tables — exact, because R_a R_b = R_(a+b).

  4. STEP 04

    fp32 anchor

    Each key is copied to an fp32 reference store at its first renumber; later positions derive from that copy, so bf16 rounding never compounds (max key error 0.003 vs 0.031).

Capacity rule: L > Bmax + H, and smaller is better. L = 8,192 — the smallest admissible power of two for 2,048 tokens plus 4,096-token chunks — beat the model's native 40,960 at a matched ~24K gap (56 / 64 / 93%).

03

What holds, what doesn't

The reframing is well defended; the generality and the baseline set are where the paper is thin.

+ Strengths

  • Measures the blind spot at fixed residency — 0.995–0.996 across 225 probes, not asserted.
  • The failure taxonomy shows the two halves repair different errors: lost facts vs misapplied facts.
  • Exact re-rotation with a proof, plus a capacity rule (L > Bmax + H) that says smaller is better.
  • Finds, quantifies and fixes a bf16 rounding bug that only appears past ~1M tokens (100% → 84%, restored to 75/75).
  • Pre-registration, template fingerprints, merge refusal, a no-eviction control, disclosed post-hoc changes.
  • 2M tokens on one 24 GB L4: 0.7 GB of KV where full caching needs 295 GB.

− Limitations

  • One synthetic coding task with stdlib filler; tool traces and multi-document work are untested.
  • Two 7–8B models on one GPU; larger models may use distant context better, shrinking the effect.
  • Mostly an oracle planner; behaviour under a worse planner (recall < 0.9) is uncharacterized.
  • The agent-aware baselines it argues against — KVFlow, ActKV, MemDecay — are cited, never run.
  • 5–10 sessions per cell; the 300K arm has n = 3, and SnapKV is a weak stand-in.
  • Rehydration is scripted-test only, and the 2M per-turn slowdown is unexplained.
04

Still open

Q1

Does the split hold on non-coding long-horizon work — tool traces, multi-document QA — where the needed span is a paraphrase, not a verbatim definition?

Q2

Is the mechanism rotary distance or effective-context density? Renumbering to a random permutation within the same range would separate “close” from “compact”.

Q3

What is full-context Qwen3-8B accuracy at 100K? Without it, 42% → 97% may be recovering a real ceiling — or a shrinking one.
