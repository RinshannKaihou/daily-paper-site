> **一句话总结：** Firepool 是 LinkedIn 生产环境中的 GPU 沙箱/执行代理（broker），它用"晚绑定"（每个硬件 SKU 共用基础镜像，作业的代码包、增量依赖和多机拓扑在作业启动时才绑定）让同一个热池可以服务各种不同实验，再用"仅限上次调用者复用 + 零显存 standby 容器 + 队列驱动的 GPU 预算"来安全且省卡地保温；在生产 H200 节点上，agent 与 RL 循环比"每作业新建 pod"分别快 13.0×（119.3 s vs 1,554.2 s）和 10.8×（163.0 s vs 1,761.9 s），采样高峰期内 94.7% 的 3,206 次 pod 申请由热池或 standby 满足，而 60 s keep-alive 只占常开池约一半的容量。

> **TL;DR:** A production systems paper from LinkedIn describing Firepool, a per-Kubernetes-cluster broker that keeps GPU pods warm for short, bursty agent and RL jobs. The core mechanism is *late binding*: one curated base image per GPU SKU plus a content-addressed code zip, incremental pip/uv installs, and torchrun/Ray topology injected at job start (~0.4–0.54 s median binding cost), so many distinct environments share one warm pool instead of fragmenting into per-image pools. Safety and cost are handled by owner-only reuse with a verified process-tree reset (9.3 ms clean, 1.67 s worst case), zero-VRAM standby pods staged on fractional HAMi/Volcano shares of a busy GPU (promoted behind a per-GPU gate), and queue-driven scaling with a physical-GPU budget ledger. On a pinned 8×H200 production node with 1-GPU pods and a 2-GPU cap, agent and RL loops finish **13.0× and 10.8× faster** than with a fresh pod per job (makespan 119.3 s vs 1,554.2 s; 163.0 s vs 1,761.9 s), and against a fresh reuse tag per job warm reuse cuts p90 start latency from **59.1 s to 3.5 s**; standby promotion cuts the handover wait from **51.0 s to 0.94 s**. Read it if you run agent sandboxes or rollout fan-out on GPUs and care about tail latency per loop iteration; skip it if you want an apples-to-apples comparison against Ray static pools or Kubernetes agent-sandbox — those are only characterized from public docs, never benchmarked head-to-head.

## 核心贡献

- **晚绑定让 pod 可互换（§4）**：每个 SKU 只维护一份精选基础镜像（重、慢变的层），用户代码以内容寻址 zip 包在作业启动时下发并解包（中位 ~0.4 s，包上限 512 MiB 压缩 / 2 GB 解压），增量 Python 依赖按 requirements 文件的 SHA-256 打标记后原地安装，多机拓扑（torchrun rendezvous / Ray head-worker）也由 executor 在启动时注入。这样 N 个不同实验共享少数热池，而不是每个镜像/形状一个池。
- **安全复用边界（§5）**：四条规则——① 已用 pod 只复用给上次使用它的调用者（owner-only reuse），并带可配置的 owner hold；② 会话边界（reuse tag / queue 变化）后该 pod 最多再跑一个作业即退休；③ 作业之间 kill 整个进程树并用 `/proc` 验证其确实消失，清空包目录、`/dev/shm` 和按作业的 GPU 记账文件；无法确认干净就删 pod；④ 调用者身份用集群签发/federated token 校验（缓存校验 6.6 µs）并过滤可影响 loader 的环境变量。
- **零显存 standby（§6）**：在 HAMi + Volcano 的分数份额调度下，一张卡上放 1 个 active pod 和最多 3 个 standby pod（按 GPU UUID 钉在同一张卡），standby 只跑 pod agent，不建 CUDA context、不占显存；作业在 active pod 上运行时，agent 在**作业进程环境**里把 CUDA 显存上限提到整卡 141 GB（改 pod spec 会让 standby 也拿到整卡）。每卡一个 gate 保证同时只有一个 pod 真正跑作业，promotion 在进程退出后立即发生。
- **按队列而非利用率伸缩（§7）**：热池按设计就是空闲的，利用率驱动的伸缩器会在最该吸收突发时缩容；Firepool 用 `add = min(need, ceiling − physical, step, headroom)` 从排队需求出发扩容，并把 active–standby 组只算作**一张物理 GPU** 计入所有预算，避免 hold 住的 pod 把 standby 挤到额外的卡上。另有 floor / idle cap / ceiling / keep-alive τ 四个旋钮，可退化为 serverless TTL 或静态集群。
- **生产与受控评测（§8–§9）**：14 小时采样高峰（含 3 小时约 2,500 个单卡 H200 作业的突发）内 94.7% 的 3,206 次申请走热路径；受控基准给出 13.0×/10.8× 循环加速、p90 59.1→3.5 s、handover 51.0→0.94 s；并用本地集群 + 校准模拟器给出"容量 vs 延迟"前沿与"作业变长后保温失效"的边界。

## Key Contributions

- **Interchangeable pods via late binding.** Firepool splits a job into (a) a curated per-SKU base image holding native builds and framework pins, and (b) a content-addressed code package plus incremental dependency installs plus injected topology. Measured binding cost is 0.40–0.54 s at the median (p99 ≤ 1.45 s on H200), so a warm pool stays usable across dozens of distinct experiment environments. In simulation with 64 environments, one late-bound pool holds 1.06× an always-on pool while per-environment pools hold 2.15× and their RL-rollout warm hit rate falls from 0.85 to 0.68.
- **A concrete, four-rule isolation policy for GPU pod reuse**, decided at claim time so the release path stays fast: owner-only reuse, retire at the session (reuse-tag) boundary, verified process-tree and scratch-space reset, and verified caller identity with env-var filtering. The paper is explicit that a caller's state can reach at most one job of that caller's *next* session, and that kernel-level isolation is out of scope (it composes with microVMs).
- **Zero-VRAM standby pods.** Rather than co-running jobs on a shared GPU (Salus/AntMan/HAMi style), Firepool uses fractional scheduler shares only to *stage* the next pod: standby runs no CUDA context and holds no memory, is pinned to the active pod's card by GPU UUID, and is promoted atomically behind a per-GPU gate once the previous job's processes are gone. This converts GPU-sharing into a sub-second handover mechanism (51.0 s → 0.94 s) without co-tenancy interference.
- **Queue-driven warm-pool economics with a physical-GPU budget.** Explicit floor / idle-cap / ceiling / keep-alive knobs, an in-memory per-accelerator ledger reserved before the Kubernetes create call, active–standby groups counted once, and optional borrowing of unused reserved capacity with preemption (borrow 11.8 s, return 30.0 s, 80/80 owner pods honored).
- **An unusually careful evaluation for a production systems paper**: Williams crossover arm interleaving, paired per-repeat differences with 95% bootstrap CIs, a simulator fitted on train campaigns and validated on pre-registered hold-outs (46/55 = 84% of held-out metrics in band; ×0.69–1.44 prediction intervals for queue medians), plus fault injection (30 SIGKILLs under load, 0 lost and 0 duplicated jobs) and control-plane microbenchmarks (110k–220k claims/s at 100k pods, 1.5–2.6 µs lock hold, ~1 KB/pod).

## Methodology

**System.** One broker per Kubernetes cluster. Callers submit a job naming an SKU (which fixes GPU model, CPU, memory, base image, scaling policy) and optionally a code package; jobs land in a durable SQL store (MySQL in production). A dispatch loop takes queued jobs in priority order and claims warm pods from an in-memory tracker under a single read/write lock held 1.5–2.6 µs at the median (≤8 µs p99, 100k tracked pods, 110k–220k claims/s), then commits the QUEUED→RUNNING transition with a version check before any user code runs. Submission, pod release and pod readiness wake the loop; a 3 s tick remains as fallback. A pool controller creates and retires pods from queue depth and budgets every 30 s.

**Claim order (the placement policy that matters).** For a job the broker searches the SKU bucket in order: an idle pod last used by the same caller (preserving page cache and installed deps) → a never-used idle pod → a zero-VRAM standby on an active GPU → a new pod. Multi-pod jobs claim all N pods in one step under the tracker lock (all-or-nothing over idle pods and promotable standbys on distinct cards), so no job holds a partial set that could deadlock against another; measured warm multi-pod claims take 0.27–0.45 s for N = 2–8 with 0 partial claims in 50 jobs.

**Standby mechanics.** HAMi + Volcano allocate fractional shares of a card; Firepool places one active and up to `standbys_per_active` standbys on the same card pinned by GPU UUID, capping each pod's memory at its share through a CUDA interception library. On job start the agent sets `CUDA_DEVICE_MEMORY_LIMIT_<i>` to the full framebuffer in the job process environment (never the pod spec) and points the shared-memory cache at a fresh per-attempt file. A periodic sweep verifies that every share on a card belongs to Firepool's active–standby group; after a restart, promotions fail closed until the sweep re-verifies exclusivity.

**Scaler.** `add = min(max(floorDeficit, demandDeficit), ceiling − physical, step, headroom)` with `need = max(floor − physical, demand − eligible, 0)`; scale-down removes only idle pods whose keep-alive has expired and never drops below the floor. Two accounting choices prevent oscillation: starting pods count as supply (GPU pods take 22–200 s to become ready), and owner-held pods count toward floor and ceiling but are not supply for other callers.

**Evaluation design.** Headline numbers come from dedicated benchmark pools on production nodes: one pinned 8×H200 node, 1-GPU pods, cached 12.2 GB base image, two-GPU pool cap; and a production CPU pool of 4 vCPU/8 GiB pods with a cached 4.4 GiB image and a 16-pod cap. Two synthetic loops: W-RL runs 4 barrier-synchronized iterations of 8 rollouts + 2 evaluations + 1 policy update (1.5–4 s fixed-duration bodies); W-Agent runs 2 or 4 concurrent agents for 3 iterations of 2–4 calls (0.5–1.6 s bodies, last call a verify step) with 0.5–2 s think pauses between calls and 2–5 s between iterations. Three arms: Reuse On (stable reuse tag per caller), Reuse Off (fresh tag per job, so a pod runs at most one job past its tag — ablates owner reuse), and Fresh pod per job (single-use pod created and deleted per job, the closest analogue of a Kubernetes Job). Mechanism costs come from a local k3d cluster and a trace-calibrated simulator; simulator rankings are preserved in every hold-out set and all effect signs are correct, and the authors state they use it for shapes and orderings, "never for headline numbers."

## Results & Highlights

- **Production warm-hit rate:** over a sampled 14-hour peak period Firepool served **94.7% of 3,206 pod acquisitions** without creating a pod (98.6% on the primary single-GPU H200 pool, 97.7% on the second); when a 3-hour burst of ~2,500 single-GPU H200 jobs exhausted the unheld idle pods, standby promotion served **187 of 222** such jobs (84.2%), with the remaining 35 getting new pods. Note this is a share of *requests*, not of GPU-hours saved.
- **Loop-level speedup vs a fresh pod per job (production H200, 2-GPU cap, fixed-duration bodies):** agent loop makespan **119.3 s vs 1,554.2 s (13.0×)** and RL loop **163.0 s vs 1,761.9 s (10.8×)**; per-repeat paired median differences are **+95.4 s [82.4, 107.8]** (W-Agent, 720 jobs) and **+119.1 s [105.5, 134.4]** (W-RL, 880 jobs). Start latency p50 goes from 89.5 s to 0.61 s (agent) and 115.8 s to 3.92 s (RL), p90 from 354.6 s to 3.51 s and 315.2 s to 80.8 s.
- **vs Reuse Off (fresh reuse tag per job — the owner-reuse ablation):** H200 agent p90 start latency **3.52 s vs 59.1 s**, loop 3.6× (51.8 s vs 186.4 s); CPU RL 4.5× (116 s vs 516 s) and CPU agent 2.2× (186 s vs 403 s). The H200 *median* barely moves (1.91 s vs 2.29 s, paired CI +0.43 [−0.03, 0.84] spans zero) because Reuse Off jobs often land on standby or recycled pods — the win is entirely in the tail, which is exactly the authors' own operating rule ("judge warm pools by tails, loops and held capacity").
- **Standby handover (2-GPU pool, 10 paired repeats of 30 sequential jobs with a fresh reuse tag each):** **86% of handovers (101/117) were served by promotion**; median queue wait at a handover **0.94 s vs 51.0 s** (0.81 s for promotions alone), submit→first-instruction p50 **1.66 s vs 28.2 s**, loop makespan **337 s vs 1,023 s (3.0×)**; all 10 paired repeats favored standby (paired makespan +685 s [591, 766]).
- **Late binding is cheap and prevents fragmentation:** package delivery + unpack + job start takes **0.40–0.54 s at the median (p99 ≤ 1.45 s)** on production GPUs; first install of 23 pins 2.5 s, repeated pins 0 s (marker hit), one changed pin 0.03–0.06 s. In the simulator with 64 distinct environments, a pool-per-environment that may grow to the budget holds **2.15×** an always-on pool with RL-rollout warm hit rate falling **0.85 → 0.68**, against **1.06×** for one shared late-bound pool; splitting the budget instead pushes p90 start latency to **400 s**. The shared pool only loses if binding is slow: at a 30 s hand-off it holds as much as per-environment pools (2.08× vs 2.15×).
- **What warmth costs:** on the local cluster a floor-1/idle-cap-2/60 s-keep-alive configuration held **0.52× [0.52, 0.53]** the always-on peak pool for **+28 ms** at the median; a bare 60 s keep-alive held 0.24× for +46 ms; a 900 s keep-alive with no idle cap held **1.15× [1.09, 1.18]** for +57 ms — i.e. a long keep-alive is *worse than an always-on pool*. On production H200, warm reuse held **12.3 GPU-seconds per job vs 10.7** for Reuse Off (**15% more** GPU time for a 3.6× faster loop), 87% of it idle and almost all owner-held between agent steps.
- **The benefit has a hard boundary:** the per-job saving stays at 10–35 s on CPU, but loop speedup falls **below 1.1× beyond ~196 s (RL) or ~104 s (agent) job bodies** with no think time, and vanishes once think time exceeds the keep-alive. At 1–2 s bodies the simulator gives 4.1–4.3× for RL (4.5× measured) and 1.6–2.0× for agents (2.2× measured).
- **Control plane holds up:** 30 SIGKILLs under load produced **0 lost and 0 duplicated jobs**, all **90/90 owner holds restored**, dispatching in 0.045 s and first claim 3.0 s after restart, API reachable 20 s after the kill; durable dispatch tops out at **483 jobs/s on MySQL** (2,365 on PostgreSQL) versus observed peak cluster arrival rates; a saturated-load template rollout converged in 324 s with 0 failed jobs and Δp50 +0.03 s; borrowing took 11.8 s to acquire and 30.0 s to return with owners getting 80/80 pods.

## Authors & Credibility

All seven authors are at LinkedIn (correspondence: Ankit Goyal, angoyal@linkedin.com), and the paper is a preprint, not a peer-reviewed publication — no venue is listed. That is the central credibility fact: this is an industry engineering report on a system the authors built and operate, which buys unusual access to production telemetry (fleet pod-creation times, a 14-hour peak window with a 2,500-job burst, per-minute pool gauges) but means no external review of the mechanism claims. The evaluation craft is well above the norm for such reports: Williams crossover arm interleaving to balance carry-over, paired per-repeat differences with 95% bootstrap CIs (seed 2027, 2,000 resamples), a simulator fitted on train campaigns and validated on *pre-registered* hold-outs, and explicit statements about what the simulator may and may not be used for. They also document the alternatives they rejected (one lock per SKU, exact shapes, per-image pools, a hard per-tag boundary) and report the cost side (15% more GPU-seconds per job, 87% of held time idle) rather than only the speedups. The AI-usage disclosure is specific: GitHub Copilot wrote parts of Firepool, the harnesses and analysis scripts (author-reviewed); Copilot converted the draft to LaTeX; AI reviewers (DeepReview, GPT-6 Astra, Claude Opus 5.5) critiqued drafts; every reference was hand-verified against its publisher or arXiv record. No data was generated by AI.

## Critical Assessment

*Novelty.* Late binding is the genuinely new idea and it is a good one: the observation that a warm pool only helps if *arriving jobs can use its pods*, and that the fix is to bind as little as possible at creation and as much as possible at claim, reframes warm pooling as a **matching** problem rather than a **pre-warming** problem. Zero-VRAM standby is the second real contribution and is the more surprising mechanism — using HAMi/Volcano fractional shares not to co-run work but to *park* a pod on a busy card, pinned by GPU UUID, and promoting it behind a per-GPU gate the instant the previous process tree dies. The subtle detail that an active–standby group must count as one physical GPU in every budget (otherwise held pods spill standbys onto extra cards) is the kind of correctness point that separates a deployed system from a prototype. By contrast, owner-only reuse with a verified reset is competent engineering rather than novelty.

*Weak baselines — the biggest problem.* Table 2 compares Firepool against Ray/static pools, serverless keep-alive, warm-pool controllers (Kubernetes agent-sandbox, SageMaker Managed Warm Pools, OpenKruise Agents) and node image caching, but the table's caption concedes that "characterizations of other systems reflect their public documentation" — **none of these is actually run**. The only real baselines are three arms of Firepool itself (Reuse On / Reuse Off / fresh pod per job). "Fresh pod per job" is a Kubernetes Job, i.e. the strawman the whole paper exists to beat; the interesting comparison, a persistent Ray rollout pool or a Kubernetes agent-sandbox `SandboxWarmPool` on the same node, is never measured. This matters most for the late-binding claim: per-environment pools are evaluated *inside Firepool's own simulator*, so the 2.15× vs 1.06× fragmentation result tests the authors' model of a competitor, not a competitor.

*Confounded ablation.* Table 5 notes in its caption that "the fresh-pod columns ran the event-driven dispatcher of §3; the Reuse Off columns ran an earlier, tick-driven one with the reuse tag as a retiring boundary." The 3.6×/4.5×/2.2× Reuse Off speedups therefore mix a reuse-policy change with a dispatcher change. The paper reports the confound honestly and separately measures the dispatcher effect elsewhere (a warm start took 1.85 s under the 3 s tick and 0.59 s event-driven), but the headline ablation number is not clean, and no re-run with the dispatcher held fixed is reported.

*The speedup is mostly a function of the chosen body length.* The benchmark jobs are 0.5–1.6 s (agent) and 1.5–4 s (RL) fixed-duration bodies — deliberately near-worst-case for provisioning overhead, which is defensible as a characterization of agent loops, but it means 13.0× and 10.8× are upper bounds conditioned on that choice. The authors are commendably explicit that the gain drops below 1.1× past ~196 s (RL) / ~104 s (agent) bodies and disappears when think time exceeds the keep-alive, so the honest headline is "10–35 s saved per job, which is 10× only if your jobs are seconds long."

*Scale and single-node framing.* Headline benchmarks use **one** pinned 8×H200 node with a two-GPU cap. The 94.7% production figure is a share of 3,206 acquisitions over 14 hours (~230/hour) — real, but modest for a fleet-scale claim, and it measures *how a request was satisfied*, not cluster utilization, queue time, or dollars saved. There is no fleet-level cost accounting: the paper says idle pods are "a small share of the GPU time Firepool holds" but never gives the fleet-wide fraction, and the "about half the capacity of an always-on pool" claim comes from a 2,300-job local cluster plus the simulator, not production. A skeptical reader also notices that the one production capacity number that *is* measured — 12.3 vs 10.7 GPU-s/job, 87% idle — implies Firepool is trading real capacity for latency, and the break-even think-time is left to the operator.

*Data quirks worth flagging.* Table 4's quiet standby p90 of 50.4 s "reflects retry polling from before dispatch became event-driven" — a stale measurement left in a results table, which the caption admits but which still makes the standby row non-comparable to the warm-reuse row. The 5,025 jobs/s SQLite number is explicitly called an engine bound rather than a production figure (good), yet it sits in the same paragraph as the MySQL 483 jobs/s result. And the burst rows in Table 4 are hard to read causally: warm-reuse jobs waited 53 s at the median during the burst because callers had saturated their own GPU quota, so burst latency there measures quota contention, not pod acquisition — the authors say so, but it muddies the table.

*Isolation and failure scope.* Reuse relies on killing a process tree and verifying via `/proc`, plus clearing the package dir and `/dev/shm`. That is weaker than a microVM or kernel boundary, and the paper says so: state from one session can reach the first job of the same caller's next session, incremental dependencies are never uninstalled until the pod retires (so a dropped pin leaves residue), and callers needing a clean environment must request a single-use pod. Network partitions are outside the tested scope, and the recovery design admits that a re-queued attempt can overlap its predecessor during a partition. For an internal-trust deployment this is a reasonable posture; presented as a general multi-tenant sandbox it would need the microVM composition the authors mention only in passing.

*Verdict.* A strong, honest engineering paper with one genuinely transferable idea (late binding) and one clever mechanism (zero-VRAM standby), weakened by baselines that are argued rather than measured and by headline multipliers that depend on very short job bodies. The negative results — long keep-alives cost more than always-on pools; warmth stops paying past ~100–200 s bodies — are as valuable as the positive ones and are the parts most likely to change a reader's design.

## Strengths

- **The core insight is stated crisply and defended:** a warm pod is worthless unless the next job can use it, so the design problem is matching, not pre-warming. Late binding follows directly, and the fragmentation experiment (0.85 → 0.68 hit rate, 2.15× vs 1.06× held capacity at 64 environments) is a clean demonstration of the failure mode it avoids.
- **Zero-VRAM standby is a real mechanism, not a slogan.** Pinning standbys to the active pod's card by GPU UUID, raising the memory limit in the job *process environment* rather than the pod spec, gating promotion on verified process death rather than polling device memory, and counting the active–standby group as one physical GPU — each of these is a non-obvious detail that a naive implementation gets wrong.
- **The cost side is measured and reported.** 15% more GPU-seconds per job, 87% of held time idle, 0.52× / 0.24× / 1.15× capacity ratios for three keep-alive settings, and an explicit statement that a 900 s keep-alive is worse than an always-on pool. Papers in this genre usually publish only the speedup.
- **Negative results are given equal billing:** warmth stops paying past ~196 s (RL) / ~104 s (agent) bodies and vanishes when think time exceeds the keep-alive; custom-image jobs (which dominate their 8-GPU pools) get no benefit at all and are named as future work rather than quietly excluded.
- **Statistical hygiene unusual for a systems paper:** Williams crossover interleaving, paired per-repeat differences, bootstrap CIs, pre-registered simulator hold-outs with reported coverage (46/55 = 84%, ×0.69–1.44 prediction intervals), and an explicit rule that the simulator is never used for headline numbers.
- **Operational realism throughout:** rejecting unknown request fields and returning typed errors because the caller is a *program* that retries blindly; recording each pod's acquisition path so cold-start regressions can be told apart from quota exhaustion; breaking expired owner holds only above a 60 s minimum tenure and sparing owners with queued jobs; failing standby promotions closed after a restart until a sweep re-verifies card exclusivity.
- **Fault and scale testing is concrete:** 30 SIGKILLs under load with 0 lost and 0 duplicated jobs, 90/90 holds restored, template rollout under saturated load with 0 failed jobs, gang claims with 0 partial claims in 50 jobs, borrowing with 80/80 owner pods and exactly one borrowed GPU released per owner GPU.

## Limitations

- **Competing warm-pool systems are never benchmarked.** Table 2's characterizations of Ray, agent-sandbox, SageMaker warm pools and OpenKruise Agents come from public documentation; the only measured baselines are Firepool's own arms. The central claim — late binding beats per-environment pools — is tested only in the authors' simulator.
- **Single-node headline benchmarks.** All controlled H200 results use one pinned 8×H200 node with 1-GPU pods and a two-GPU cap; the CPU venue is a 16-pod pool. Multi-node, multi-tenant effects (network, shared storage, scheduler contention across SKUs) are not exercised at benchmark scale.
- **Speedups are conditioned on very short job bodies** (0.5–1.6 s agent, 1.5–4 s RL). The paper reports the crossover but the abstract and conclusion lead with 13×/10.8× without that caveat in the same sentence.
- **The Reuse Off ablation is confounded with a dispatcher change** (tick-driven vs event-driven), acknowledged in Table 5's caption but not re-run.
- **No fleet-level economics.** The 94.7% figure counts requests, not GPU-hours; there is no utilization, queue-time or cost-per-loop number at fleet scale, and the "half the capacity" claim rests on a local cluster plus simulation.
- **Weak isolation for untrusted tenants.** Process-tree kill + `/proc` verification is not a kernel boundary; dependency residue persists until pod retirement; one session's state can reach the next session's first job; network partitions are untested and can let a re-queued attempt overlap its predecessor.
- **Custom-image jobs get no benefit**, and these dominate the authors' 8-GPU pools — so the mechanism as deployed covers the 1-GPU short-job regime, not the multi-GPU training regime. Multi-GPU standby would need gang-wide promotion plus reservations to avoid starvation, both listed as future work.
- **One production trace, one operator.** All production numbers come from LinkedIn's internal workload over a single sampled 14-hour window; the burst is ~2,500 jobs. Generalization to other traffic shapes (heavier multi-tenancy, longer think times, many small callers) is untested.
- **Preprint, no peer review.** Mechanism and measurement claims have not been externally vetted, and several key numbers (simulator calibration, hold-out coverage) would benefit from an artifact or independent replication.

## Relevance

直接命中「Compute Infrastructure for Large-Scale ML」——集群调度与 GPU 资源管理方向：它把"短作业的供给延迟"当成一等公民，用晚绑定、零显存 standby 和按队列伸缩把 pod 启动从关键路径上拿掉，并给出 p50/p90、容量占用和故障注入的完整账本。对做 agent 沙箱、rollout fan-out 或任何"秒级作业、分钟级启动"基础设施的人，这是目前少见的、把成本与尾部延迟同时量化的生产级参考。

## Questions for Further Exploration

1. How would Firepool compare head-to-head against a persistent Ray rollout pool and a Kubernetes agent-sandbox `SandboxWarmPool` on the same 8×H200 node with the same fixed-duration bodies? Without that, the 13× is only a statement about Kubernetes Jobs.
2. The 15% extra GPU-seconds per job (12.3 vs 10.7) is measured at a 2-GPU cap; what does the latency–capacity frontier look like at realistic production concurrency, where owner-held idle pods are partitioned across many callers and the idle cap must be sized per active caller?
3. Is the 0.94 s handover robust when the active job is a long-running CUDA kernel that ignores SIGTERM, or when the driver takes seconds to free a large context? The paper gates on process death rather than device memory, which is the right call — but the worst-case promotion latency is not reported.
4. What breaks first at 10× the caller count? The tracker scales to 100k pods at 110k–220k claims/s, but per-caller GPU limits and owner holds partition the idle pool, so the effective warm hit rate may degrade with caller cardinality in a way the 14-hour trace does not expose.
5. Could late binding be extended to multi-GPU images (the stated next step) without losing the "one base image per SKU" property, given that 8-GPU jobs are exactly where custom images dominate?
6. How much of the 13× survives if the agent's think time is 30–120 s rather than 0.5–2 s? The paper's own Figure 7 says the gain vanishes once think time exceeds the keep-alive — is the production agent traffic actually in the short-pause regime, and is that measured anywhere?
7. What is the security argument for owner-only reuse under a compromised caller? A malicious job could leave a payload in a read-only cache that survives the reset and is then trusted by the same caller's next session — is the same-caller threat model considered acceptable by policy, or only by convenience?
