> **一句话总结：** 作者把"改 harness"从离线预处理变成任务执行中的一个工具调用——智能体自己喊 `boxbox()` 叫暂停，内核挂起任务、保留轨迹/终端/工作区，让智能体在独立 review session 里重写整套可执行 harness（工具、控制流、prompt、状态管理），验证通过后热重载并接着跑；在新基准 PerfRace 的 50 个测试任务上，Speedup@4h 达 1.702×，高于 Harness Scaling 的 1.539× 和 Frozen Harness 的 1.442×，同时把单次模型成本从 $23.22 降到 $16.43。

> **TL;DR:** On PerfRace — a new 100-task benchmark of real GitHub projects (Rust/Python/TypeScript/C++, 7 workload domains) where an agent must find correctness-preserving speedups under a 4-hour budget with no reference patch — BOXBOX beats both test-time baselines: harmonic-mean Speedup@4h of 1.702× vs 1.539× for Harness Scaling (HS, +0.163×, +10.6% relative) and 1.442× for Frozen Harness, at a mean model cost of $16.43/run vs $23.22 for Frozen (−29.3%) and $12.98 for HS (BOXBOX wins on speedup-per-dollar, 0.4886 vs 0.2872). The paper's second contribution is a clean negative result: offline Harness Evolution (HE) *loses* to doing nothing, 1.281× vs 1.442×, and costs ≥$33.73/run once offline training+validation is amortized. Read this if you care about self-modifying agent runtimes, harness engineering, or how to build a performance-optimization benchmark that resists reward hacking; the mechanism delta over Continual Harness is agent-controlled (not scheduled) revision with full-harness editability plus context-preserving hot reload.

## 核心贡献

- **PerfRace 基准（本文更可能被长期引用的部分）**：100 个来自真实 GitHub 仓库的性能优化任务，覆盖 7 个负载域（开发工具 30、数据系统 25、科学计算 15、媒体处理 9、几何 8、机器学习 7、安全 6），16 种主语言（Rust 25、Python 18、TypeScript 15、C++ 11…）。任务**不给参考补丁、不给目标热点**——只给一个固定 workload 和一个 Judge，智能体必须自己 profile 出瓶颈。评分是 best-so-far 正确加速比 $S(t)=\max_{i:t_i\le t}s_i$，错误提交记 0，未改动项目记 1×。
- **把 harness 优化变成智能体自己的一个动作**：注册 `boxbox()` 为工具，调用即"进站"（名字来自 F1 无线电 "box, box"）。与 Continual Harness 的定时 refiner、Harness Scaling 的 session 间外部控制器不同，**由任务智能体自己决定何时把剩余预算投给 harness 修订**，因此可以针对"刚刚才暴露出来的"困难做适配。
- **全 harness 可编辑 + 内核管理热重载**：以往方法把可编辑面限制在 $H_{bounded}\subset H$（预定义组件），BOXBOX 允许 $H_k'\in H$——工具实现、控制流、prompt 规则、状态管理都能改。代价是错误更新会直接打断任务，所以引入**独立于可编辑 harness 的内核**：暂停→保留执行上下文（对话、review 历史、终端 session、工作区）→验证候选 commit→热重载→失败则回滚到上一个 confirmed runtime。
- **递归性**：修订后的 harness 同时治理后续任务执行**和**后续 review 过程本身，因此第二次 review 是在第一次改完的 harness 下进行的——这是标题里 "recursive" 的实际含义。
- **一个诚实的负结果**：在 PerfRace 上，离线 Harness Evolution 不仅没赢，还输给 Frozen Harness（1.281× vs 1.442×），且训练/验证损失并不随迭代下降（epoch 聚合 1.086×→1.062×→1.069×）。作者给了逐条失败归因（见 Critical Assessment），不是一句"效果不好"了事。

## Key Contributions

- **A benchmark, not just a method.** PerfRace is built workload-first rather than patch-first: tasks start from an end-to-end real workload and the agent must *discover* the bottleneck, unlike GSO / SWE-Perf / SWE-fficiency which hand over a targeted performance test or a human reference optimization. Construction is a live pipeline (GitHub coding-agent activity → deterministic precheck → LLM source assessment → agent–human "Pair Verification"), so new tasks can be sourced continuously.
- **Agent-triggered harness revision as an in-task action.** `boxbox()` is a tool in the action space $A(H_k)$; the kernel suspends the task loop, runs a separate review session (project code read-only, harness writable), then resumes. Budget $B$ is shared and explicitly allocated by the agent between project-code optimization and harness revision, which no prior harness-evolution method does.
- **Kernel-managed hot reloading with context transfer.** Execution context is split into runtime-owned state (task conversation, review history, reviewed-entry bookkeeping, exported as a snapshot) and the live environment (terminal session, running processes, workspace files, kept in place). The kernel copies the snapshot before import so a failed candidate runtime can be rolled back; a newly activated runtime stays *provisional* until it survives one agent-requested review without a fault.
- **Fault-triggered review as a second entry point.** Beyond voluntary `boxbox()`, runtime faults also invoke recovery + review using the recorded fault evidence, so harness repair is not purely discretionary.
- **A matched-budget empirical comparison** against Frozen / offline HE / externally-controlled HS, including full cost accounting (token rates, offline amortization) rather than speedup alone.

## Methodology

**Problem formulation.** Fixed model $M$, harness $H_k$ that may change mid-task. At step $k$: $a_k \sim p_{M,H_k}(\cdot\mid\tau_k)$ with $a_k\in A(H_k)$; $(e_{k+1},o_{k+1}) \leftarrow \mathrm{Execute}_{H_k}(e_k,a_k)$; $\tau_{k+1}=\tau_k\oplus(a_k,o_{k+1})$; and $H_{k+1}=H_k'$ if a revision activates, else $H_k$. Two distinct levers follow: changing how the harness builds model inputs shifts $p_{M,H_k}$; changing $\mathrm{Execute}_{H_k}$ shifts how actions are carried out and how observations are rendered. Because the active harness also governs the review loop, revisions compound.

**The pit stop.** Agent calls `boxbox()` → kernel traps, suspends the task interaction loop (**pauses the agent's decisions, not the container/processes**) → prepares an independent review environment $(e_r,\tau_r)$ with read access to $\tau$ → agent iterates until `commit(H')` → kernel validates the commit, loads the runtime, verifies it supports execution and context transfer, transfers the same terminal session, resumes from the preserved conversation. Failure ⇒ retain/restore previous runtime. Initial harness enforces a 30-minute cooldown and requires intervening task activity between reviews; the reviewer may instead leave concise guidance that the resumed agent is prompted to read.

**Default self-review skill.** Two steps: *Diagnosis* (scan trajectory for execution failures, repeated work, and successful patterns that could be automated; infer missing capabilities or costly tool interactions) and *Revision* (pick changes by expected benefit within remaining budget — add guidance, improve tools, change execution logic; e.g. collapse repeated tool calls into a reusable tool). Revisions are tracked as Git commits so later reviews can inspect prior changes against execution records.

**PerfRace construction.** Discovery: query ClickHouse `github_events` for PRs/branch pushes by a configured list of coding-agent accounts, May–Aug 2026 → 118,517 repos → 104,428 with metadata → **103,475 candidates** (112,127 from branch pushes, 6,390 from PRs). Filter: deterministic checks (accessible revision, redistributable license, 10–4,999 stars, ≤500 MiB / ≤25,000-entry git tree) → **7,257**; then GPT-5.6-Luna structured assessment of setup path / evaluable process / runtime fit / optimization potential → **239**. Pair Verification: agent-led construction with human gates at Realism, Reliability, Integrity → **100 accepted** (132 rejected at Explore & Design, 6 at Build & Calibrate, **0 at Validate Integrity**, 1 at Finalize). Cost per accepted task: mean 9.1 h, 12 agent–human interactions, $11.35 (medians 4.5 h / 8 / $8.83).

**Evaluation hygiene.** Shadow verification: on each submission the Judge `docker compose commit`s the agent container, spins a separate shadow container that alone holds verifier code, workload copy, held-out cases and expected outputs, then destroys it; verification time counts against $B$. Tasks declare warmups, repetition count, aggregation rule and required correctness pass rate in `task.toml`; measurement protocols were calibrated to CV < 10%. Baseline Judge evaluation: median 4.9 min, mean 6.1 min, 20-min cap. Red-teaming with invalid / partial / hard-coded / work-skipping solutions before acceptance.

**Experimental setup.** 100 tasks split 40 train / 10 validation (HE only) / 50 held-out test. All methods start from the same harness $H_0$ = Terminus-KIRA (shell-command terminal harness), per Meta-Harness convention. GPT-5.6-Luna, high reasoning effort, for both task execution and harness optimization. 3 runs × 50 tasks × 4 methods = 600 test runs, each with a 4-hour budget $B$ shared across execution, harness optimization and evaluation. Single Azure Standard_D96ads_v5 (96 vCPU EPYC 7763, 384 GiB, Ubuntu 24.04 + Docker). Aggregation: geometric mean over the 3 runs per task, then **harmonic mean** over the 50 tasks; Speedup/\$ is the arithmetic mean of task-level $\bar S_i/\mathrm{Cost}_i$.

## Results & Highlights

- **Main table (Table 1, 50 test tasks × 3 four-hour runs, harmonic-mean Speedup@4h):** BOXBOX **1.702×** vs Harness Scaling **1.539×** (+0.163×, +10.6% relative) vs Frozen Harness **1.442×** (+0.260×, +18.0%) vs Harness Evolution **1.281×** (−0.161× *below* doing nothing). Cost per run: BOXBOX **$16.43**, HS **$12.98**, Frozen **$23.22**, HE **$24.56**; Speedup/\$ 0.4886 / 0.2872 / 0.2142 / 0.1243 — BOXBOX is **1.70× more cost-efficient than HS** and 2.28× than Frozen, despite HS being $3.45/run cheaper in absolute terms.
- **The gap is a *late-run* gap, which is the paper's real claim.** Over hours 2→4 Frozen moves 1.410×→1.442× (+0.032), HS 1.431×→1.539× (+0.108), BOXBOX 1.530×→1.702× (+0.172). Frozen has effectively plateaued while BOXBOX is still climbing — consistent with "harness revision unlocks progress that a fixed harness cannot reach," not merely "BOXBOX is faster early."
- **Offline HE loses and is expensive.** Test 1.281× at $24.56/run; amortizing the offline pipeline (training $200.34 over 40 tasks, validation $1,176.12 for 3 harnesses × 3 runs × 10 tasks, test $3,683.34) raises the effective cost to **≥$33.73 per test run** — 45% above Frozen's $23.22 with worse speedup. Training aggregate actually *decreased* epoch-over-epoch (1.086× → 1.062× → 1.069×), and validation picked $h_{24}$ (1.289×) over $h_{16}$ (1.273×) and $h_8$ (1.244×) on a 10-task set — a spread small enough that checkpoint selection looks like noise.
- **Ablation (14 randomly sampled test tasks, Table 2):** full BOXBOX 1.584× at $15.07 (0.3452/\$) > w/o agent triggering 1.508× at $21.58 (0.1338/\$) > w/o full editing 1.349× at $16.07 (0.1132/\$). The scheduled-review variant (every 30 min, following Continual Harness) is thus **2.6× worse per dollar** than agent-triggered, mostly through wasted review calls.
- **Budget behaviour is sane.** Median **5 reviews per run**, with 92% of the 150 test runs in the 3–6 range. Reviews consume a median **2.1% of the 4-hour time budget** and **13.8% of model cost** — the agent spends the overwhelming majority of its budget on actual optimization, which is the mechanism the cost win rests on.
- **What gets edited (620 applied non-empty updates, multi-label):** review feedback 40.8%, prompt rules 42.9%, tool functionality 16.9%, skills 16.6%, fault fixes 12.7%, execution logic 4.7%. So the bulk is guidance and tooling, not exotic control-flow surgery.
- **Longer budgets keep paying (Appendix B.5, 88 tasks × 3 runs):** Terminus-KIRA with no harness revision goes 1.314× (1 h) → 1.377× (2 h) → 1.396× (3 h) → 1.435× (4 h); 2 h→4 h adds +4.2%, the fourth hour alone +2.8%; 24 tasks gain ≥5% from 2 h→4 h and 12 from 3 h→4 h; among the 228 improving runs the best result is first reached at a median of **88.1%** of the budget, and 51/264 runs post a new ≥5% gain in the final hour. This validates the 4-hour horizon as non-saturated — and also means the benchmark is measuring "who keeps finding things late," which is exactly the regime harness revision should help.
- **Case-study numbers that make the mechanism concrete.** On `ccc-compile-speed` the agent's own harness work reduced official runtime 6.321 s → 6.095 s → 5.792 s (final 1.748×); critically, an apparent 9.4% win vanished under alternating A/B runs, which is what motivated baking paired-comparison into the helper at review #3. On `fluidsynth-bagatelles`, harness work (adaptive waiting → `benchmark_matrix` batching) plus disabling OpenMP reached 1.183×.
- **HS failure case, quantified:** on `kitops-minilm-pack`, HS's controller added a "warn after 3 consecutive matching command batches" check, but the agent then ran **113 consecutive checks** in different command forms without a new measurement; the run peaked at 1.649× at checkpoint 5 and never improved, because HS can only revise *between* sessions. **HE failure case:** a training-derived submission gate hard-coded a repo-location assumption, producing **473 blocked submissions over ~3 h 46 min** on `mirage-kubernetes-triage`.

## Critical Assessment

**Novelty is real but incremental, and the paper is honest about the seam.** Every ingredient has a precedent: Continual Harness already preserves task state across an outer-loop refiner; TTHE already evolves harnesses at test time without reference answers; Meta-Harness/AHE already edit executable harness code. The delta is (a) *agent*-chosen timing instead of scheduled or controller-chosen, and (b) full-harness editability with (c) kernel-level hot reload and rollback. That is a meaningful systems contribution — the 30-minute cooldown and provisional-runtime protocol are the kind of detail that only comes from having actually run this — but it is a control-placement contribution, not a new learning signal. The genuinely new artifact is PerfRace.

**The single most important missing ablation is context preservation.** The paper's mechanistic story for beating HS is that HS's session resets throw away accumulated reasoning, so later attempts re-derive earlier decisions (they even show the cost side: HS is $12.98 vs BOXBOX $16.43 because resets truncate history). But they never run the obvious control — HS-style external control *with* context preservation, or BOXBOX with context deliberately dropped at each reload. Without it, "preserving execution context" is supported by a cost argument and one anecdote (`kitops-minilm-pack`), not by a measured contribution. This is the ablation I would have demanded in review.

**The HE baseline is a scaled-down reimplementation, and the negative result inherits that.** The reference HE setup trains full-batch on Terminal-Bench 2.1 where trajectories average ~50 steps and 12.2 min; PerfRace Frozen runs average **965 steps** under 4 h. The authors respond by capping training runs at 45 min and using mini-batches of 5 over 24 iterations — a ~5× shorter horizon than the test condition, with a 10-task validation set choosing among three checkpoints whose scores span 1.244–1.289. So "offline harness optimization does not reliably improve performance" is really "offline HE at 45-minute training granularity, validated on 10 tasks, does not transfer to 4-hour open-ended optimization." That is a defensible and probably correct claim, but the paper's framing occasionally slips toward the general one. The failure analysis (the promotion gate that hard-codes repo location and blocks 473 submissions) is excellent and specific; the aggregate claim deserves the same hedging.

**Statistical reporting is uneven.** Figure 1 has 95% fixed-task resampling bands, but Table 1 and Table 2 report point estimates with **no intervals and no paired test** for the headline 1.702 vs 1.539. Given 3 runs × 50 tasks and heavy right tails in speedup, a +0.163× gap on a harmonic mean is plausible but unverified; the ablation table is worse — 14 tasks, no intervals, and the full-BOXBOX number there (1.584×) differs from the 50-task headline (1.702×) by more than the entire effect of removing agent triggering (1.584−1.508 = 0.076×). Readers should treat the ablation ordering as directional.

**Metric design has a soft spot: best-so-far is a ratchet with no consolidation requirement.** $S(t)$ credits any submission that ever passed correctness, even if the workspace later regresses or the "win" was a single lucky measurement. The CCC case study is precisely a story about a 9.4% phantom gain from between-batch variation — which the agent caught — but nothing in the scoring *forces* that discipline, and the harness revisions that encode A/B methodology are exactly what BOXBOX is being credited for. A "final-state speedup" or "median-of-last-k-submissions" metric would test whether the gains are real and durable. The 5-minute final-delivery prompt partially addresses this, but the reported number is still best-so-far.

**Two smaller flags.** (1) Table 3 lists GPT-5.6-Terra token rates ($2.50/$0.25/$15.00) but every experiment uses Luna; either Terra appears in some appendix run not visible in the main text, or the table is vestigial — minor, but it makes the cost accounting slightly harder to audit. (2) **Zero candidates were rejected at the Validate Integrity gate** (0 of 239), while 132 died at Explore & Design. The text explains this as red-team fixes being applied in place before the gate, which is coherent, but a 0% rejection rate at the one gate specifically designed to catch reward hacking is the kind of number that deserves a sentence of justification rather than a bar of height zero. Related: Discovery keys on repos that *coding agents already push to*, which selects for projects agents find tractable — a self-selection that likely flatters absolute speedups (though not the between-method comparison).

**Scope limits worth naming.** One model (GPT-5.6-Luna), one initial harness (Terminus-KIRA), one hardware profile, CPU-only workloads. The abstract's claim that these results "support harness optimization as part of an agent's own capabilities" is a claim about a capability *existing*, and it is demonstrated for one (model, harness) pair on 50 tasks. Nothing here shows the revised harnesses transfer, or that a weaker model can perform competent self-surgery (a real risk: the review session is itself a hard agentic task, and a model that writes a subtly broken harness now has kernel rollback as its only safety net). The security section is refreshingly blunt that this is a research prototype, not a security boundary.

## Strengths

- **A benchmark that fixes a real methodological gap.** Workload-first task construction with no reference patch is the right formulation for performance engineering, and the pipeline (103k → 239 → 100 with published per-stage rejection counts) is auditable in a way most agent benchmarks are not.
- **Benchmark hygiene is unusually serious.** Shadow containers, held-out correctness cases, CV < 10% calibration, declared warmup/repetition/aggregation in `task.toml`, red-teaming with hard-coded and work-skipping solutions, verification time charged to the agent's budget. The 20-minute Judge cap with a measured 4.9-min median shows they checked the thing that would silently invalidate every run.
- **The negative result is delivered properly.** HE's failure is not asserted, it is traced to a specific revision (iteration 5's promotion gate), a specific wrong assumption (repo location), and a specific cost (473 blocked submissions, 3 h 46 min). Same for HS (`113` repeated checks, 1.649× frozen at checkpoint 5). These case studies are the most convincing pages in the paper.
- **Cost accounting is complete enough to be re-derived.** Token rates, per-stage offline costs, cached-vs-uncached input, and the amortization arithmetic ($24.56 → ≥$33.73) are all on the page. Most harness papers report speedup and stay quiet about spend.
- **The ablation isolates the two design choices separately** (triggering, editability), and the "scheduled reviews waste calls even when no revision is needed" explanation is a mechanism, not a hand-wave.
- **Genuinely useful systems detail**: the provisional-runtime protocol, snapshot-copy-before-import, fault-triggered review, and the note that `boxbox()` pauses agent decisions rather than the container are the parts another team would need to rebuild this.

## Limitations

- **No context-preservation ablation** — the mechanism most responsible for beating HS is argued, not isolated (see Critical Assessment).
- **One model, one seed harness, one machine.** GPT-5.6-Luna + Terminus-KIRA on a single 96-vCPU Azure VM; no cross-model or cross-harness generalization, no GPU workloads (so no kernel-optimization tasks, which is where much real performance work lives).
- **HE is re-scaled to fit**, so the offline-vs-online conclusion is conditional on 45-min training runs, mini-batches of 5, and a 10-task validation set.
- **Best-so-far metric rewards lucky submissions** and does not require the final workspace to retain the gain; no durability or re-verification analysis of credited speedups.
- **No intervals or significance tests on Tables 1–2**, and the ablation uses 14 tasks with a full-BOXBOX number (1.584×) that sits 0.118× below the 50-task headline.
- **Benchmark construction does not scale cheaply**: 9.1 h and $11.35 of agent cost per accepted task, plus human review at three gates, for 100 tasks. "Continually source new tasks" is a design aspiration, not a demonstrated throughput.
- **Discovery is biased** toward repositories that coding agents already touch, which likely selects easier-than-average optimization targets.
- **Self-modification risk is acknowledged but unquantified**: no measurement of how often a revised harness introduces a correctness or security regression that rollback catches, and no red-team of the *review session* itself (e.g. an agent editing the harness to weaken its own submission discipline).
- **Fault-recovery reviews are folded into the same "median 5 reviews" statistic** as voluntary ones, so the paper cannot say how much of the 1.702× comes from discretionary self-improvement versus crash repair.

## Relevance

正中"Self-Evolving Agents & Automated Research"：这是一篇把**自我修改**做成运行时机制（agent 触发 + 内核热重载 + 上下文保留 + 回滚）并给出受控评测的工作，而不是又一篇 prompt 自反思。对关注长时自主智能体可靠性的读者尤其有价值——它同时提供了"自改 harness 确实能在长跑后段继续涨分（1.530×→1.702×）"的正结果，和"离线演化会输给什么都不做（1.281× vs 1.442×）并因一次错误 gate 浪费 3 小时 46 分"的失败解剖。

## Questions for Further Exploration

1. What happens with context preservation turned off but everything else identical? Is the 1.702 vs 1.539 gap mostly context, mostly editability, or mostly trigger timing?
2. Does a weaker/cheaper model (e.g. a mid-tier model with the same kernel) still produce net-positive harness revisions, or does self-surgery require frontier-level review competence? The 13.8%-of-cost figure suggests the review sessions are not cheap in capability terms.
3. Under a final-state or median-of-last-k metric instead of best-so-far, how much of BOXBOX's advantage survives? The CCC phantom-9.4% story suggests measurement discipline is doing real work that the metric does not reward.
4. Do revised harnesses transfer? If you take a harness BOXBOX evolved on `ccc-compile-speed` and drop it into a fresh run of the same task (or a sibling task in developer tools), does it help, or is it as task-specific as the offline HE revisions that failed to generalize?
5. Can the review session itself be attacked — an agent that edits submission gating, timing boundaries, or its own review skill to make numbers look better? The 0% Integrity rejection rate makes this the obvious next red-team.
6. How sensitive is the result to the 30-minute cooldown and the "intervening task activity" requirement? Those are unablated constants that directly set the review/execution budget split.
7. Is PerfRace's difficulty calibrated? The 88-task no-revision baseline reaching 1.435× at 4 h means substantial speedups are available without any harness work — what fraction of tasks have a large, easily-found first win, and does that compress between-method differences?
