> **一句话总结：** StrataFlux 把"精度"和"存放位置"解耦——GPU 里只留 2–3 bit 权重与 KV 作常驻基座，主机 RAM/SSD 只存"精化位"（refinement bits），用激活幅度/注意力权重挑选极少量通道与 token、跨 Transformer block 的 fetch lead/lag 调度、以及跨解码步缓存复用，把 Llama-3.1-8B-Instruct 2-bit 权重的 WikiText-2 PPL 从 9.46 降到 8.40（RTX 5090 上保留 95.4% 吞吐），并把 Qwen3-8B 在 2-bit 权重+2-bit KV 下的 AIME 2024/2025 从 11.0% 提到 47.1%，GPU 显存不变。

> **TL;DR:** Quantization and offloading are usually posed as a tradeoff (lose accuracy vs. stall on transfers); StrataFlux argues the tradeoff comes from bundling representation with placement, and splits them: the resident base stays 2–3-bit, while 4 extra bits per *selected* channel/token live in host RAM or SSD and are fetched asynchronously. Three pieces do the work — nested refinement (fetched bits pick a finer value inside the resident code's interval, inherited from Any-Precision LLM), activation/attention-ranked selection (top-k channels per 1,024, 1/128 of KV token groups), and cross-block scheduling (fetch lead: select channels from a residual-stream activation 0.5–1 blocks early; fetch lag: add the correction to the residual stream 0.5–1 blocks late) so a 200 µs SSD read hides behind intervening projections instead of behind one GEMV. On Llama-3.1-8B-Instruct / YAQA 2-bit at a 5% slowdown budget, WikiText-2 PPL goes 9.46 → **8.40** (KL 0.257 → 0.139) versus **DecDEC's 9.03**, at 234.4 vs 245.8 tok/s (95.4%) on an RTX 5090; on Qwen3-8B the same setting lifts MATH500 77.2 → 92.4 and AIME 19.2 → 46.7 (DecDEC: 86.2 / 30.8; BF16: 97.2 / 71.0). The full system at 128K reaches PPL 10.80 at 7.3 GB / 102 tok/s, against vLLM's AWQ-4bit + FP8-KV at 11.03 / 14.3 GB / 106.8 tok/s. Honest caveat buried in the appendix: after YAQA recovery fine-tuning the 2-bit base is already at 8.45, so the gain shrinks to 0.26 PPL — and on Qwen3-8B the fine-tuned base actually beats refined inference on PPL.

## 核心贡献

- **把"表示"与"放置"拆开（核心论点）。** 量化单独看是丢掉了另一层本可以留住的精度，offloading 单独看是选完表示之后才去搬数据。StrataFlux 让两层同时存在：常驻低bit 基座 + 后台层里的"补充精度位"，于是"精度上限由 GPU 常驻位宽决定"和"解码速度由 offload 层延迟决定"这两个约束同时被打破。
- **选择性精度流（selective precision streaming）。** 权重按每 1,024 个输入通道取 |x_i| 最大的 k 个（四组投影各有独立预算 k_qkv / k_o / k_gu / k_d）；KV 按"共享该 KV head 的所有 query head 上的最大注意力权重"给 token 打分（Eq. 7），以 2 或 4 token 为一组、只取 1/128 的组做精化。因为重要性高度不均（Fig. 3：精化 top-ranked 的一小部分就去掉了不成比例的 MSE），选择性才成立。
- **嵌套精化编码（nested refinement）。** 不搬完整的 FP16 值，而是搬"在常驻低bit 码已经确定的区间内部再细分"的索引位（权重 4 bit、KV +4/+4 bit）。在相同 K+V 预算下，嵌套精化比 sparse attention 和"整条换 FP16"的 KL 都更低（Fig. 2b）——这是与 SpeCache 那类"取回完整 16-bit 条目"路线的关键区别。
- **精化值拟合（fitting）。** 不直接存残差 R = W − Ŵ，而是解一个带 ridge 的加权最小二乘（Eq. 3–4），让被选中的列去补偿没被选中的列的遗漏贡献，再把拟合矩阵量化到 4 bit。消融显示单独这一项带来 0.09 PPL（Llama 2-bit：8.68 → 8.59）。
- **跨 block 的 fetch lead / lag 调度。** 权重的 QKV/gate-up 投影从残差流读入，所以可以用**更早**一个 block 的激活提前选通道并发起取数（lead）；attention-output 与 down 投影写回残差流，所以精化可以**推迟**到后面一次残差更新再加（lag）。这把可隐藏延迟的窗口从"单个投影的执行时间"扩展到"中间隔着的若干算子"，Nsight 上 block 执行时间缩短 30.7%（Fig. 7）。CUDA stream/event 的 fork-and-continue 实现见附录 G。
- **跨解码步复用 + 跳过缺失（skip-on-miss）。** 选择在相邻步高度重合（Fig. 5：缓存 1/64 的条目就能拿到很高的命中率），所以取回的精化位进 RAM 缓存（LRU），未命中的步**直接跳过**精化、用常驻低bit 值算，同时后台线程把位读进缓存供后续步使用——把"等待"换成"延迟受益"。
- **统一内存平台上的完整落地。** DGX Spark / MacBook Air M3 上 GPU 与 CPU 共享同一块 RAM，精化位放 SSD、经 RAM 缓存供 GPU 直接读；专用 GPU 上则直接从 pinned host RAM 取。两套路径共用同一套缓存策略与调度。
- **自动调参器。** 在给定"相对量化基座的减速上限"下，逐模型/逐量化器/逐平台搜索每组的 k、各投影组的位移 s、MLP 用 channel-wise 还是 neuron-bundle、以及 refinement kernel 的 thread-block 数，用 held-out KL 选点。

## Key Contributions

- **A reframing, not just a kernel.** The paper's actual thesis is that the accuracy/latency dichotomy is an artifact of deciding representation before placement. Concretely: keep the resident quantizer's format and kernels untouched, and store only the *additional* bits needed to subdivide its existing bins. This is what makes refinement cheap enough to be selective (4 bits per selected element, not a 16-bit replacement).
- **Selection grounded in measured structure.** Weight-channel importance is proxied by input activation magnitude |x_i| (justified by the error decomposition (W−Ŵ)x = Σ x_i R_{:,i}); KV importance by max attention weight across the query heads sharing a KV head. Both are cheap to compute from data already on the GPU, and Fig. 3 shows ranked selection dominates random selection by a wide margin on both axes.
- **Refinement fitting as error compensation.** Eq. 3 minimizes E‖Rx − Cz_k(x)‖² + λ‖C − R‖²_F, whose solution is a ridge-regularized normal equation (Eq. 4) with λ set to the mean diagonal of the second-moment matrix. The point is subtle but real: the selected columns are optimized to stand in for the *unselected* ones, not merely to be accurate themselves.
- **Cross-block latency hiding for weight refinement.** DecDEC can only overlap a fetch with the projection it refines; at 2-bit the projection is fast (21 µs average for Llama-3.1-8B's YAQA 2-bit output projection on DGX Spark) while a 2 KB random SSD read is 200 µs median / 709 µs p99, so projection-local overlap cannot work on unified memory. Fetch lead/lag widens the window by ±0.5–2 blocks, and the ablation shows it is worth 0.17 PPL at matched budget (8.57 → 8.40 on Llama 2-bit).
- **A second, independent axis: reuse.** Caching turns a bandwidth problem into a hit-rate problem. Measured: at 1/128 selection fraction, caching the union of the last 32–64 steps' KV selections yields very high hit rates, so most decoding steps never touch SSD.
- **An end-to-end system, not a simulation.** Implemented in llama.cpp with CUDA 13.4.2 and Metal backends; evaluated on RTX 5090 / 5070 Ti / PRO 6000 Max-Q, DGX Spark, and MacBook Air M3, across Llama-3.1-8B/3.3-70B, Qwen3-8B/32B/30B-A3B, Qwen3.5-9B, DeepSeek-V2-Lite, with baselines ported into the same framework using author-provided kernels.

## Methodology

**Resident representation.** The base stays exactly as the quantizer produced it: YAQA/QTIP trellis weights, AWQ, LNQ+GuidedQuant, SqueezeLLM, and for KV the KVarN format (with KVQuant and TurboQuant adaptations in Appendix E). StrataFlux adds a parallel array of refinement bits per projection (weights) or per KV head (cache), plus metadata. Because the resident code is kept as the *identifier of the coarse bin*, reconstruction is a two-level lookup rather than a replacement — this is what keeps the low-bit attention and GEMV kernels usable.

**Weight path.** For input x, y′ = Ŵx + Σ_{i∈S(x)} x_i C_{:,i}, where S(x) is the top-k channels per 1,024-channel chunk and C is the fitted refinement matrix. Refinement values are encoded as integers with their own per-column scale, so the refinement kernel has a format independent of the resident quantizer (this is what allows one kernel to serve YAQA, AWQ, LNQ, SqLLM). For MLP layers there are two schemes: channel-wise (refine x for gate/up, h for down) and neuron-wise (select the k_n neurons with largest post-gating activation |h_j| and refine gate/up rows, down column, plus a 4-bit copy of the BF16 down column, then recompute h′_j = φ(g_j + c_gj x)(u_j + c_uj x)). Neither dominates across models/quantizers/platforms, so both are kept and chosen by the tuner.

**KV path.** StrataFlux-KV subdivides each KVarN code's quantization interval into equal sub-intervals and stores the sub-index in the backing tier. Token groups are scored by s_j(i) = max_{h∈H(j)} α_{h,i} using attention weights computed from the *resident low-bit keys* (so scoring costs nothing extra), and the top groups per KV head are refined. Refinement is fused into the attention update analytically: o′ = (Z·o + Σ_{i∈S}(e^{ℓ′_i}v′_i − e^{ℓ_i}v_i)) / (Z + Σ_{i∈S}(e^{ℓ′_i} − e^{ℓ_i})), which corrects both the numerator and the softmax normalizer. Groups are packed contiguously for larger reads. During prefill, attention runs on uncompressed K/V first, then resident codes are written and refinement bits offloaded; during decoding, completed blocks of new KV are encoded the same way.

**Scheduling.** Fetch lead computes the projection's normalization on a residual-stream activation s blocks earlier, selects channels, and issues the fetch; the refinement kernel then consumes the fetched columns once the real input is available. Fetch lag adds attention-output and down refinements to the residual stream s blocks after their original addition point. Because separate CUDA streams do not by themselves guarantee concurrency (a large base-projection grid can occupy all SMs), Appendix G describes a fork-and-continue scheme with per-operation events and continuation streams, plus atomic accumulation into initialized outputs. The tuner sweeps s per projection set; the paper notes the required shift is quantizer-dependent (YAQA 2-bit is slower and gains most at s = 0.5; AWQ 3-bit needs s = 1).

**Caching.** Weight and KV refinement have separate cache budgets; the weight cache is LRU over all four projection sets, the KV cache is shared across heads and blocks. On a miss, the current step can either skip refinement (background CPU loader fills the cache for later) or wait. The paper measures both: on DGX Spark with a 128 MiB cache, waiting gives 8.52 PPL at 17.9 tok/s while skipping gives 8.94 at 69.2 tok/s — a 3.9× throughput cost for 0.4 PPL, hence skip is the default at small slowdown budgets.

**Tuning.** The tuner profiles base projections against refinement, then for each (s, MLP scheme) finds the largest common channel budget k meeting the slowdown limit, ranks candidates by KL on held-out text, and finally grows individual per-projection budgets while re-measuring latency. Fitting is done at a ladder of power-of-two budgets during search and re-fit exactly at the chosen budgets.

**Evaluation.** WikiText-2 2K-token windows for PPL/KL; 17 PG-19 test books × 16 windows of 128K tokens (prefill to C−256, score the last 256 with teacher forcing) for long context; RULER at 4K–128K; MATH500; AIME 2024/2025 with avg@8. Throughput: PG-19 prompt, prefill to C−641, 512 untimed + 128 timed steps; weight-only comparisons at empty context. KL is approximated over the top-1,024 vocabulary tokens plus a grouped tail.

## Results & Highlights

- **Weight refinement on Llama-3.1-8B-Instruct / YAQA 2-bit, RTX 5090, 5% slowdown budget.** WikiText-2 PPL **9.46 → 8.40**, KL **0.257 → 0.139**; DecDEC at the same budget reaches 9.03 / 0.211, and BF16 is 7.22 / 0.000. Throughput is 234.4 vs the quantized base's 245.8 tok/s — the headline "95.4% of base throughput" is exactly this ratio. On DGX Spark, where DecDEC cannot fetch from SSD at all, StrataFlux-W gets 9.46 → 8.94 at 69.2 tok/s.
- **The same setting on reasoning tasks (Qwen3-8B, YAQA 2-bit, 5%).** MATH500 **77.2 → 92.4** and AIME 2024/2025 **19.2 → 46.7** on RTX 5090; DecDEC gets 86.2 / 30.8 and BF16 is 97.2 / 71.0. On DGX Spark the same method yields 89.4 / 40.0 — a 6.7-point AIME spread across platforms for a nominally identical configuration, which is a useful reminder that "the" number is platform-tuned.
- **KV-only refinement at 128K (Llama-3.1-8B-Instruct, 2/2 KV, BF16 weights, RTX 5090).** PG-19 PPL **10.98 → 10.40** and KL **0.067 → 0.003**; RULER@128K **68.6% → 78.1%**, against BF16's 10.32 / 77.9%. On Qwen3-8B: PPL 14.40 → 12.98, RULER 66.0 → 74.2 (BF16 12.89 / 74.1). The refinement recovers essentially all of the 2/2-KV accuracy loss on RULER.
- **Full system (weights + KV) on Qwen3-8B, YAQA 2-bit + 2/2 KV, 128K.** PG-19 PPL **19.48 → 14.91**, KL 0.434 → 0.165, RULER@128K 58.8 → 68.3, MATH500 **68.0 → 91.2**, AIME **11.0 → 47.1**, at 7.1 GB and 97.6 tok/s (base: 7.1 GB, 76.6 tok/s). BF16 is 12.89 / 74.1 / 97.2 / 71.0 at 35.7 GB. So on AIME the method closes 36 of the 60 points between the 2-bit base and BF16 — a little over half the gap.
- **System-level frontier at 128K (Llama-3.1-8B-Instruct, RTX 5090).** StrataFlux with YAQA 3-bit + 2/2 KV: PPL **10.80**, **7.3 GB**, **102.0 tok/s**. vLLM AWQ-4bit + FP8-KV: 11.03, 14.3 GB, 106.8 tok/s. EXL3 4.0 bpw + 4/4 KV: 10.78, 9.8 GB, 101.7 tok/s. llama.cpp Q4_K_M + q8_0: 10.59, 14.0 GB, 63.1 tok/s. QServe W4A8KV4: 11.34, 10.3 GB, 42.6 tok/s. BF16: 10.32, 33.2 GB, 47.6 tok/s. The "half the memory at comparable PPL and speed" claim checks out against vLLM (7.3 vs 14.3 GB, 102.0 vs 106.8 tok/s, 10.80 vs 11.03 PPL).
- **Ablation decomposition (Llama-3.1-8B-Instruct, YAQA 2-bit, RTX 5090, all re-tuned to 5%).** Unfitted + s=0: 8.76; + fitting: 8.67; + tuned lead/lag: 8.59; + neuron bundles: **8.40** — i.e. fitting is worth 0.09 PPL, lead/lag 0.17, and the MLP scheme 0.19. For AWQ 3-bit the same ordering gives 8.70 → 8.61 → 8.50 → 8.38, except neuron bundles *hurt* AWQ (8.56), which the paper acknowledges by forcing the outlined bar in Fig. 12(a).
- **Throughput overhead scales with batch.** At 128K on RTX PRO 6000 Max-Q, KV refinement costs **11.2%** at batch 1 and **18.8%** at batch 16; on DGX Spark **7.0%** and **25.4%**. This is the honest cost side of the accounting and it grows exactly where serving systems live.
- **Storage, not free.** At 128K with YAQA 2-bit weights + 2/2 KV: VRAM 3.86 GB, host RAM 4.43 GB, SSD 2.58 GB (≈10.9 GB total) against BF16's 33.24 GB. The "unchanged GPU memory" claim is literally true, but the precision is paid for in backing-tier capacity.
- **Where it does not recover: LongBench.** Llama-3.1-8B-Instruct at 128K: 2-bit weights + 2/2 KV gives LongBench 46.2 → **46.5** (BF16 49.6); Qwen3-8B 43.3 → **44.5** (BF16 49.4). Compare RULER's 50.4 → 63.8 on the same configuration. The recovery is large on synthetic retrieval and nearly absent on realistic long-context tasks.

## Authors & Credibility

Jake Hyun, Jae-sun Seo, and Mohamed S. Abdelfattah are at Cornell (Seo: efficient ML hardware/accelerators; Abdelfattah: AI-generated hardware and kernel generation); Ziyu Zhao is at CMU. The provenance matters here: Hyun is a co-author of **DecDEC** (OSDI'25) and **Any-Precision LLM** (ICML'24), i.e. the strongest baseline and the nested-quantization representation both come from the same group. That is a double-edged signal — the comparison against DecDEC is deep and fair (they port its correction kernel into llama.cpp and use its tuner), but it is also a self-comparison, and the paper does not discuss that.

The engineering credibility is high: two backends (CUDA 13.4.2, Metal), six platforms including two unified-memory ones, baselines ported with author kernels where they exist and honestly flagged where they do not (AWQ 3-bit kernel written by the authors because none is released; SpeCache implemented from the paper because no code exists; TurboQuant adapted from a community vLLM backend; AQUA-KV reimplemented in CUDA). The AI-usage disclosure (Claude Code and Codex for implementation, evaluation scripts, figures, and manuscript revision) is present and specific. There is **no code or artifact link anywhere in the PDF**, which is the single biggest reproducibility gap for a systems paper whose value is largely in the kernels.

## Critical Assessment

**Novelty: an integration paper, and it says so.** Nested refinement is Any-Precision LLM's idea, activation-ranked channel selection is DecDEC's, KV token selection is Quest/SpeCache's, and cross-block overlap is the Deja Vu / KTransformers pattern. What is genuinely new is (a) refinement *fitting* so selected columns compensate for unselected ones (Eq. 3–4), (b) extending weight-refinement overlap outside the projection's own execution window via residual-stream fetch lead/lag, (c) fusing nested refinement into a low-bit KV attention kernel including the softmax normalizer correction, and (d) the skip-on-miss cache policy. That is a solid systems contribution; it is not a new quantization algorithm, and readers looking for one will be disappointed.

**The headline gain partly overlaps with recovery fine-tuning.** Table A10 is the most important table in the paper and it is in the appendix. After YAQA's own recovery fine-tuning, the Llama-3.1-8B 2-bit base moves from 9.46 to **8.45**, and StrataFlux-W at 5% only reaches **8.19** — the "1.06 PPL" headline becomes 0.26. Worse for the narrative: on Qwen3-8B the fine-tuned base is **10.24**, while StrataFlux-W lands at 10.50 / 10.40 / 10.37 / 10.36 across budgets 2.5–20% — i.e. *worse on PPL at every budget*, even though KL improves (0.162 → 0.137/0.125). PPL and KL disagree, the paper reports both without reconciling them, and the abstract's 9.46 baseline is the un-fine-tuned one. This is not fraud — recovery fine-tuning is expensive and not always available — but it means the method's real niche is "you cannot afford QAT," which the paper never states.

**Accuracy recovery is benchmark-selective.** RULER@128K goes 50.4 → 63.8 on Llama 2-bit+2/2, but LongBench on the same configuration goes 46.2 → 46.5 against BF16's 49.6. RULER is synthetic needle/retrieval, which rewards exactly the property refinement provides (recovering a few high-attention tokens' precision); LongBench is realistic multi-task long-context, where the residual error is distributed rather than concentrated. The abstract's "recovers long-context accuracy" is supported by the weaker of the two benchmarks, and the LongBench numbers sit in Table A38 with no discussion.

**A baseline that is better than the method, in their own table.** Table A33 shows llama.cpp Q4_K_M + q8_0 KV at 128K achieving PPL **10.59** vs StrataFlux's 10.80 (YAQA 3-bit + 2/2), at 14.0 GB and 63.1 tok/s. StrataFlux wins decisively on memory (7.3 GB) and throughput (102 vs 63 tok/s), and the paper frames the comparison on the memory/speed axes — but "pushes beyond the accuracy frontier" is only true below ~10 GB. At equal memory there is no accuracy win over plain 4-bit GGUF; the win is that you get 4-bit-ish accuracy at 3-bit memory.

**Refinement slightly beating BF16 is not interrogated.** StrataFlux-KV on Llama 2/2 reaches RULER 78.1 vs BF16's 77.9, and on Qwen3-8B MATH500 97.0 vs BF16 97.2 / AIME 71.5 vs 71.0. A low-bit method "exceeding" BF16 is almost certainly RULER/AIME noise (avg@8 on AIME has several points of standard error), but the paper presents these as plain wins without error bars anywhere. No confidence intervals appear in any table — for a paper whose central claim is sub-point accuracy recovery, that is a real gap.

**Baselines are partly home-made, in the authors' favour.** AWQ 3-bit uses an authors-written kernel (no official 3-bit kernel exists), SpeCache is reimplemented from the paper, TurboQuant from a community vLLM backend, AQUA-KV reimplemented in CUDA. Each is documented honestly, and the system-level comparison against vLLM/EXL3/QServe/KVSwap in their own runtimes mitigates the concern — but the per-method tables (Table 1, Table 3) still compare against reimplementations, and a reimplementation is usually a few percent worse than the original.

**The 5% slowdown budget is a tuner constraint, not a result.** "Maintains 95.4% of throughput" is true by construction: the tuner maximizes k subject to a ≤5% slowdown. The interesting question — how much accuracy is available per percent of throughput — is answered by the budget sweeps (Table A8: at 20% budget, 8.37 vs 8.40 at 5%), and the answer is that accuracy saturates almost immediately. That is good news for the method but it also means the reported PPL gain comes from the representation, not from spending more time.

**Small-batch regime only.** Throughput is measured at batch 1 (empty context for weights, 128K single sequence for KV). The one batch sweep (Fig. 11) shows KV overhead rising from 7–11% at batch 1 to 19–25% at batch 16, and there is no tensor-parallel or multi-GPU evaluation at all. Serving is a batched, often multi-GPU business; the paper's frontier plots are single-stream.

**Unquantified costs.** Prefill must compute attention on uncompressed K/V, then encode resident codes and offload refinement bits — the prefill overhead is never measured, even though long-context prefill is where 128K users actually spend time. The tuner's search cost (per model × quantizer × platform) is also unmeasured, and the configurations in Table A13 are hand-listed per platform.

## Strengths

- **The reframing is genuinely useful.** "Representation and placement should be co-designed" is the kind of sentence that is easy to write and hard to build; they built it, on six platforms, in two backends, and the design falls out of measured hardware facts (200 µs SSD latency vs 21 µs projection) rather than assertion.
- **The ablation is honest and decomposed.** Table A12 re-tunes each variant separately at the same 5% budget rather than stacking changes on one configuration, and it reports the one case where a component *hurts* (neuron bundles on AWQ: 8.38 → 8.56). Fig. 12(a) even marks the forced bar.
- **Skip-on-miss is the right engineering call, and they show the alternative.** Reporting 8.52 PPL at 17.9 tok/s (wait) vs 8.94 at 69.2 tok/s (skip) makes the tradeoff legible instead of hiding it.
- **Breadth of the baseline set.** Nine KV-quantization/offloading systems and five runtimes, including systems evaluated in their own runtimes, is more than most quantization papers attempt.
- **Uncomfortable numbers are in the paper.** Table A10 (fine-tuned base beats refinement on Qwen3-8B), Table A38 (LongBench barely moves), and the batch-16 overhead are all present. The framing underweights them, but the data is there to be found — which is more than can be said for most.
- **The system-level result is real.** 10.80 PPL / 7.3 GB / 102 tok/s at 128K versus BF16's 10.32 / 33.2 GB / 47.6 tok/s is a 2.1× speedup at 22% of the memory for +0.48 PPL, and that comparison is against a real runtime, not a simulated one.

## Limitations

- **Single-stream, single-GPU.** No tensor parallelism, no continuous batching evaluation, no multi-tenant serving; overhead grows with batch (19–25% at batch 16) exactly where deployment matters.
- **Backing-tier footprint is excluded from the headline.** 4.43 GB host RAM + 2.58 GB SSD at 128K for an 8B model; at matched *total* footprint the advantage over a static 4-bit + 8-bit-KV setup is much narrower than the GPU-memory framing implies.
- **Prefill cost unmeasured**, despite prefill being the dominant cost at 128K and despite prefill having to encode and offload all refinement bits.
- **Accuracy remains far from BF16 at 2 bits.** AIME 47.1 vs 71.0; MATH500 91.2 vs 97.2. "Recovers accuracy" means "recovers a majority of the gap," not "closes it."
- **No error bars anywhere.** No confidence intervals, no seeds, on metrics where 1–3 points is plausibly noise (AIME avg@8, RULER).
- **Per-platform, per-quantizer tuning is required**, and the tuning procedure needs a held-out calibration set (RedPajama) plus end-to-end latency profiling per candidate; the search cost is not reported.
- **No code release.** For a kernels-and-scheduling paper, this makes independent reproduction of the central numbers essentially impossible.
- **Refinement bit-width is fixed at 4** for weights and +4/+4 for KV; only Appendix C.6 varies it. A learned or layer-adaptive bit allocation is an obvious and unexplored degree of freedom.

## Relevance

直击 "Reliability under Extreme Performance Optimization" 这条主线：它把低比特量化带来的精度损失当作一个**可回收的数值误差**来处理，而不是只能接受的 tradeoff，并给出了误差在通道/token 维度上高度集中（因此可选择性补偿）的实测证据——这对关心"激进优化下模型输出何时失真、失真能否被局部修复"的研究很直接。同时对 "Compute Infrastructure for Large-Scale ML" 有价值：fetch lead/lag 的跨 block 调度、CUDA stream/event 的 fork-and-continue、以及"200 µs SSD 读 vs 21 µs GEMV"的延迟账，是把内存层次真正纳入推理系统设计的少见完整案例。

## Questions for Further Exploration

1. Why does the fine-tuned Qwen3-8B base beat refined inference on PPL while losing on KL (Table A10: 10.24 vs 10.40 PPL, 0.162 vs 0.137 KL)? Is the fitted 4-bit refinement introducing a systematic bias that flattens the distribution — and would fitting against a likelihood objective rather than a squared error fix it?
2. What is the prefill overhead at 128K? Encoding and offloading refinement bits for every KV entry during prefill is O(context) extra work and extra SSD writes; if it costs 20% of prefill time, the end-to-end case for 128K serving changes substantially.
3. Can the selection budget be allocated *across layers* rather than per projection set? The paper tunes k per projection group but never asks whether layer 3 deserves the same budget as layer 28 — the sensitivity literature suggests it does not.
4. How does this interact with speculative decoding and chunked prefill? Both change the compute/memory overlap structure that fetch lead/lag is tuned against, and both are standard in serving stacks.
5. What happens at batch 32–64 with paged attention? Fig. 11 shows overhead growing to 19–25% at batch 16; if it keeps growing, the method may be a single-user/long-context technique rather than a serving technique — which would still be valuable, but is a different paper.
6. Would a 2-bit base with *6* refinement bits beat a 3-bit base with 4 at the same backing-tier budget? The nested encoding makes this a clean experiment and it is not run.
