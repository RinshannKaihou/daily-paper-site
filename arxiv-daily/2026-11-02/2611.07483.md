> **一句话总结：** 论文在 48 个可精确判分的合成任务上做了一项预注册对照实验（Qwen3-8B，1440 条轨迹，6 种 handoff 形态 × 5 种威胁），把"需求在 agent 交接中被静默丢失"与"需求被篡改"分开测量：带 HMAC-SHA256 签名的需求清单（signed requirement manifest）把受攻击下的不安全提交从结构化 JSON 的 69.4% 压到 9.0%（60.4 pp），但增益几乎全部来自"检出后弃权"而非"决策更正确"（T0 下符合要求的提交两者都是 43.8%，MS 弃权 39.6%）；签名只保住传输途中的完整性——一次预注册的"签名前注入"把签名清单的违规率从 14.6% 抬到 37.5%，且 18/18 次违规的清单都是在签名前就被污染的，因此**抽取环节才是信任边界**。

> **TL;DR:** On a purpose-built 48-task synthetic bank (6 structural lineages × 8 variants, 3 integer settings, 2 mandatory requirements, one cross-branch target; IT-access / finance-approval / vendor-onboarding domains), a signed requirement manifest cuts unsafe commits under attack (T2a–T4) from 69.4% for a structured JSON handoff to 9.0% (paired Δ = 60.4 pp, 95% CI [51.4, 69.4], n = 144, McNemar p < 0.001) — but 91.7 pp of that comes from the in-transit-mutation cell where rejection is guaranteed by construction, and excluding it the rates are 58.4% vs 13.5%. The benign-condition gain (56.2% → 14.6% unsafe) is bought by abstaining (39.6% abstention) with zero improvement in conformant commits (43.8% for both J and MS), and the whole effect collapses on gpt-oss-20b, where structured handoffs were already at 2.8% unsafe and manifests were *worse* (11.1%) because the verifier faithfully enforced extraction errors. The genuinely novel result is the residual: an oracle manifest drives unsafe commits to 0% under all five threats, so the remaining 11.2 pp is entirely pre-signature extraction error, and a one-line pre-signing injection raises signed-manifest violations to 37.5% / 63.9% / 75.0% on Qwen3-8B / gpt-oss-20b / GPT-5.6-luna with the signature happily authenticating the attacker's text.

## 核心贡献

- **需求级威胁分解（五个威胁 + 两个端点）。** 把"最终决策违背用户要求"这一症状拆成两类机制：*loss*（T0 无对手、T1 摘要压缩损失）与 *tampering*（T2a 中间人脚本改写、T3 工具输出注入"修订后的需求"、T4 merger 被指示把需求降级为建议）。同时定义主安全端点 *unsafe commit*（已提交且违反任一原始需求）与效用护栏 *conformant commit*（已提交且满足全部需求），使得"靠弃权刷安全"无法伪装成改进。
- **用匹配的 arm 阶梯把三种机制分开归因。** S（自由文本）/ J（结构化 JSON）/ JL（结构化 + 决策型 LLM checker）/ M（未签名清单 + 确定性验证）/ MS（HMAC 签名清单 + 确定性验证）/ MSO（oracle 清单，探索性）共享同一条 pipeline、逐字节相同的格式参考与最终输出指令，只有 handoff schema 与校验方式不同——因此差异可以分别归给"显式化"、"代码校验"、"签名"。
- **同一轨迹上的确定性 vs LLM 校验（H2）。** MS 每条轨迹上挂一个*不参与决策*的影子 LLM checker，它看到的信息与 verifier 完全一致；于是"代码校验器 vs LLM 校验器"变成 requirement 级的配对比较，而非前人（MIRROR 的整消息级、A-VIP 的交易级）的粗粒度对比。
- **签名救不了的那部分：抽取残差。** oracle 清单控制（MSO）量化了签名之前就已产生的风险；预注册的 T5"签名前注入"进一步证明攻击者可以主动利用它——三个模型家族里，每一次签名清单的违规都来自签名前已被污染的清单，签名只是把攻击者的版本认证了一遍。
- **可审计的预注册协议。** 假设、Holm 家族、cut 顺序、parser 规则、启动规则在任何模型调用之前用 SHA-256 manifest 冻结（v1 → v1.3，5 次披露的修订，含第一次 pilot 失败后的 parser 修正）；"任务生成器对每个任务断言三条性质"（目标丢失/被改写时，偏好最优解必然违规；目标必然跨两个分支）保证了任务不是随手造的。

## Key Contributions

- **A requirement-level threat decomposition** for the orchestrator–subagent–merger topology: benign (T0), summarization loss by an LLM relay capped at 120 words (T1), scripted agent-in-the-middle rewriting (T2a), tool-output injection asserting a "revised requirement" (T3), and merger override declaring the requirement advisory (T4). Two endpoints — unsafe commit and conformant commit — are defined so that abstention cannot masquerade as safety.
- **An arm ladder that isolates three mechanisms.** Structure alone (J vs S), explicit quote-grounded predicates checked in code (M vs J), and cryptographic integrity (MS vs M). Every arm shares a byte-identical format reference and final-format suffix, so output-format failure cannot be mistaken for requirement loss — a confound the authors say bit them in earlier work.
- **Same-trajectory, per-requirement comparison of deterministic and LLM checking.** A non-deciding shadow checker receives exactly the verifier's inputs on every MS trajectory, turning H2 into a within-trajectory paired test rather than a cross-run comparison against a differently-prompted baseline.
- **The residual that signing cannot fix.** An oracle-manifest arm (MSO) establishes the ceiling, and a preregistered pre-signing injection (T5) demonstrates that the ceiling is reachable by an attacker: extraction, not transit, is the trust boundary. The authors frame this as the multi-agent analogue of the AP2 observation that inputs before a mandate is signed remain unprotected.
- **A frozen, auditable protocol** with SHA-256 freeze manifests over preregistration text, code tree, task banks and configs, plus verbatim disclosure of every amendment — including the first pilot's 67% orchestrator-failure rate and the one-key-unwrap parser fix that followed.

## Methodology

**Pipeline.** A user request `q` specifies a finite set of settings `V` (three integer-valued settings, partitioned across branches A and B), a set of mandatory requirements `R` expressed as hard constraints, preferences `P`, one withdrawn-draft decoy that *looks* like a rule, and six neutral background sentences. The orchestrator is the only agent that reads `q`; it emits a handoff `h` that travels through a relay to worker A, worker B and the merger. Workers propose values for their own settings; the merger emits `a: V → Z`, which is committed unless a check flags it. Every target requirement spans both branches, so no single worker can satisfy it alone.

**Trusted computing base.** Harness code — not a model — performs canonicalization, provenance filtering, HMAC signing/verification, the repair policy and the commit. It holds key `k`, which never appears in any prompt (a test scans every request byte for it). Models are untrusted; a compromised harness, a compromised orchestrator and key theft are explicitly out of scope.

**Manifest construction (four harness steps after the orchestrator's call).** (1) *Provenance filter*: keep an item only if its `source_quote`, after whitespace normalization, is a literal substring of the original request — this blocks requirements hallucinated by the model or injected at extraction time. (2) *Predicate validation*: keep an item only if its predicate parses in the grammar `true | eq | le | sum_le | not | and | or | implies` over public setting names with integer values. (3) *Normalization*: assign ids M1..Mk, record `settings_mentioned` from the predicate. (4) *Binding*: add task id plus a per-task nonce derived from the key; then canonicalize (sorted keys, compact separators, UTF-8 — the RFC 8785 subset needed when there are no floats) and compute `τ = HMAC-SHA256_k(canon(m))`.

**Verification.** Two pure functions running in microseconds: *receipt* (envelope fields, tag, schema, task binding, predicate validity, consistency between `settings_mentioned` and the predicate) and *decision* (evaluate every item's predicate on the complete final assignment). The verifier never sees gold; the scorer uses a second, independent implementation of predicate semantics, and tests assert the two agree on every assignment of every task.

**LLM checker baseline.** The checker returns a `checker_verdict` schema and receives the same delivered handoff and the same decision as the verifier. An unparseable verdict counts as *no flag* (fail-open, as a monitor with no verdict would behave) and is tracked by the instrument check. In JL the checker decides; in MS it shadows the verifier on identical inputs.

**Repair and fail-closed.** Every checking arm gets exactly one repair round (the merger sees its own previous answer plus the violated items), after which a still-flagged decision is not committed. An unparseable final decision is a workflow failure in every arm, with no repair — so the safety/utility endpoints stay comparable.

**Design and statistics.** Tasks come from six structural lineages (chain, budget, exception, cover, match, scoped) × 8 variants = 48 confirmatory tasks, plus a disjoint 6-task facilities development bank used only for the gate, smoke test and pilot. Arms × threats are fully crossed with every task in every cell; a preregistered exact-request cache (temperature 0, seed 0) reuses responses for byte-identical prompts. Inference uses two-sided exact McNemar tests with Holm correction and task-clustered bootstrap CIs (B = 10,000). Preregistered hypotheses: **H1** MS < J on unsafe commits under T2a–T4; **H2** verifier flags more than the shadow checker on the same violating first decisions (entering the Holm family only if ≥60 evaluable pairs); **H3a** MS < M under T2a; **H3b** M ≈ MS on conformant commits under T0 (TOST, ±5 pp, 90% CI). Secondary contrasts S1–S6 (CIs only) cover utility, JL vs MS, the oracle residual, brittleness under T1, and false alarms.

**Models.** Confirmatory: Qwen3-8B (MLX 4-bit, pinned snapshot, thinking disabled) as the primary family, plus gpt-oss-20b (LM Studio, reasoning effort low, only the final message parsed) as a second family from a different vendor at preregistered cut 5 (arms J/JL/M/MS × T0/T2a/T3 × 36 tasks = 432 roots). Exploratory, never in hypothesis tests: GPT-5.6-luna through a hardened stateless Codex CLI transport (12 tasks, arms J/M/MS, threats T0/T2a/T3), and a preregistered pre-signing injection stage T5 on all three families.

## Results & Highlights

- **H1 (Qwen3-8B, 48-task bank): unsafe commits under T2a–T4 fall from 69.4% (structured JSON, J) to 9.0% (signed manifest, MS)** — paired Δ = 60.4 pp, 95% CI [51.4, 69.4], n = 144 pairs, exact McNemar p < 0.001, Holm p < 0.001. Per threat: T2a 91.7% → 0.0%, T3 64.6% → 14.6%, T4 52.1% → 12.5%. The T2a cell is receipt rejection by construction; excluding it, the paper's own numbers are **58.4% vs 13.5%**.
- **The benign-condition gain is real but is bought with abstention, not better decisions.** Under T0, unsafe commits are 62.5% (S), 56.2% (J) and 14.6% (MS) — yet conformant commits are **43.8% for both J and MS**, because MS abstains in 39.6% of T0 runs, and 64.6% of M's *first* decisions under T0 already violated a gold requirement. The verifier catches errors after the fact; it does not make the merger more compliant.
- **H3a: signing is what defeats in-transit mutation.** Unsigned manifest M commits a target violation in **79.2%** of T2a runs versus **0.0%** for MS (Δ = 79.2 pp, 95% CI [66.7, 89.6], n = 48, p < 0.001) — M is essentially no better than J (87.5%) or S (75.0%), because the verifier faithfully enforces the forged predicate. Under T1, MS rejected only 2.1% of relayed manifests and held its T0 conformant rate at 43.8%, while unsigned M lost 16.7% of manifests to schema receipt failures.
- **H2: on 61 identical-trajectory violating first decisions (T3/T4), the deterministic verifier flags 78.7% versus 59.0% for the shadow LLM checker** (Δ = 19.7 pp, 95% CI [6.7, 34.4], Holm p < 0.001). False alarms on 28 conforming first decisions (T0/T1): **7.1% (2/28) for the verifier versus 50.0% (14/28) for the checker** (Δ = −42.9 pp, [−71.4, −14.3]). As the *deciding* check (JL), the LLM still commits 20.1 pp more violations than MS under T2a–T4 ([11.1, 29.9]).
- **S4: the pre-signing residual is 11.2 pp and it is the entire remaining risk.** Oracle manifest MSO reaches **0.0% unsafe commits under all five threats** (T0–T4) and lifts T0 conformant commits from 43.8% to **60.4%**; MS − MSO = 11.2 pp ([4.6, 19.6], p < 0.001). Extraction fidelity explains it: manifest recall **85.1%**, precision **70.4%**, target requirement recovered in **80.9%** of manifests; the provenance filter dropped 10 of 149 items (7 invalid predicates, 3 non-verbatim quotes), and **54 of the 139 kept items were preferences mis-encoded as mandatory**.
- **T5 pre-signing injection (preregistered): one adversarial line appended to the request context raises signed-manifest violations from 14.6% to 37.5% on Qwen3-8B** (+22.9 pp, [12.5, 35.4], Holm p = 0.002), **11.1% → 63.9% on gpt-oss-20b** (+52.8 pp) and **8.3% → 75.0% on GPT-5.6-luna**. Every MS unsafe commit under T5 (18/18 for Qwen3, 23/23 for gpt-oss) had a corrupted manifest, and the target was missing or altered in 62.5% / 100% of extracted manifests respectively — the signature authenticated the attacker's version.
- **Cost: 1.25× J's attributed tokens for MS (11,215 vs 8,961 per root) and 1.51× for JL (13,489).** Under T0 alone, MS costs 12.9k tokens/root (1.51×, including the shadow checker a deployment would drop) versus 8.5k for J. The verifier itself is microseconds of CPU.
- **The second family reverses the benign-condition story.** For gpt-oss-20b (432 roots, 36 tasks), H1 is supported at 36.1 pp ([27.8, 43.1]) *only* through T2a (83.3% → 0.0%); J was already at **2.8% unsafe under T0 and 0.0% under T3**, while the manifest arms were *worse* at **11.1%** because the verifier enforced mis-extracted items. Utility fell by 28.7 pp ([−39.8, −17.6]), driven by **8 of 36 tasks (22.2%)** producing no usable manifest. Pooled over shared cells: H1 = 52.8 pp ([45.8, 59.7]), H3a = 63.9 pp, H2 descriptive at 26 pairs.
- **GPT-5.6-luna (exploratory, 12 tasks) inverts the argument for strong models.** J commits **0.0%** violations under T0 and under T3, but **58.3%** under T2a; M reaches 75.0% under T2a; MS abstains in 100% of T2a runs. The manifest arms' 8.3% residual under T0/T3 is a single extraction error that the verifier then enforced.

## Authors & Credibility

Xiaobo Chen (University of Massachusetts Amherst), Genliang Zhu (Accentrust & Georgia Institute of Technology), Ziyuan Wang (Duke University), Chu Wang (Accentrust & University of Illinois Urbana-Champaign) — a four-author, three-university plus industry mix with no senior PI, and no visible prior publication record in agent security that I can verify from the paper alone. The work is cs.CR / cs.AI / cs.MA and reads like a carefully instrumented first paper from a group that has clearly run LLM experiments before: the appendices disclose a *failed* first pilot (67% orchestrator failures, 100% unparseable checker verdicts), the parser fix that followed, a launcher watchdog that killed the first scoring attempt, and a second family swapped in mid-stream — details that are normally buried.

Credibility signals that matter: preregistration frozen with SHA-256 manifests over 46 → 63 files across five versions; a gold-free instrument check that gates the study; an exact-request cache that is explicitly justified as not being able to change what any root saw; an independent second implementation of predicate semantics used only by the scorer; and a stated refusal to add samples after seeing results. Against that: code and data are "available from the authors on request", so the freeze manifests — the central evidentiary artifact of a preregistered study — are not deposited, and nothing here has been independently replicated. The results are internally consistent (Table 2 sums to 100 per cell; cost inconsistencies reported as 0; 1,440 scored roots), and the paper is unusual in reporting the numbers that weaken its own thesis (58.4% vs 13.5% excluding the by-construction cell; the gpt-oss reversal; the 22% manifest-failure rate).

## Critical Assessment

**Novelty.** The cryptography is deliberately unoriginal and the paper says so. The real contribution is the *measurement design*: matching six handoff forms against five threats with shared prompts, then using an oracle-manifest arm to bound the residual. That decomposition — loss vs tampering vs extraction error, each with its own contrast — is genuinely new at requirement granularity, and the positioning table (Table 1) is honest about what Jamshidi et al., A-VIP, MIRROR, Paul & Nandy, Facts-Without-Rules, CaMeL/FIDES and MasDrift each do and do not cover. The T5 finding (the signature authenticates a pre-corrupted manifest, so extraction is the trust boundary) is the most transferable idea in the paper and is not, to my knowledge, demonstrated this cleanly elsewhere for multi-agent handoffs.

**The headline number is inflated by a cell that cannot fail.** 91.7 of the 60.4 pp headline comes from T2a, where any byte change to an HMAC-signed manifest is detected with probability 1 − 2⁻²⁵⁶ — the paper calls this "by construction" and "a sanity check" in §8, then leads the abstract with 69.4% → 9.0% anyway. The honest figure (58.4% vs 13.5%, excluding T2a) appears only in the abstract's second sentence and never in the conclusion's bullet list. This is a framing problem, not a data problem, but it is the kind of framing that gets quoted.

**"No net loss of conformant commits" is a null result, not an equivalence result.** H3b was preregistered as TOST at ±5 pp and **failed**: the difference is 4.2 pp with a 90% CI of [−4.2, 12.5] (bootstrap 95% CI [−6.2, 14.6]), and S2 over all threats is −0.4 pp with [−14.2, 13.3] on n = 240. The body is scrupulous ("compatible with no utility cost but do not establish equivalence"), the abstract is not. With 48 tasks per cell the design simply cannot resolve a 5-pp utility difference, and the paper's own power analysis admits H3b is "weakly powered".

**The safety gain is mostly a refusal to act, and the paper's framing soft-pedals it.** MS abstains in 39.6% of benign runs; conformant commits under T0 are 43.8% for *both* J and MS; and 64.6% of M's first decisions already violate gold. So on a benign request the signed system does not decide better — it decides wrong, notices, and gives up. For IT access or payments that may be the right trade (the paper argues exactly this, and I find the argument reasonable), but it means the deployed system completes fewer than half of ordinary tasks, which is a far bigger operational fact than "60.4 pp safer". The paper never reports end-to-end task completion including abstentions as a single number, which would make this vivid.

**Circularity is acknowledged but under-tested.** The verifier's predicate grammar *is* the grammar in which gold requirements are written, so MSO's 0.0% unsafe / 60.4% conformant is close to a tautology — the authors say so. What they do not do is test a single requirement that is not a clean predicate over three integer settings: no "reasonable discount", no "comply with the vendor policy document", no requirement whose satisfaction needs retrieval or judgement. §8 announces "a secondary analysis restricts the verifier to provenance and coverage checks, without predicates, to show how much depends on executability" — **and no such analysis appears anywhere in the paper**. An announced analysis with no reported numbers is the most concrete gap here, and it is precisely the one that would tell a practitioner whether the method transfers to real enterprise requirements.

**The LLM-checker baseline is weak and unreplicated.** A Qwen3-8B with thinking *disabled*, one frozen prompt, 28 conforming decisions to estimate false alarms — 50% false-alarm and 59% detection is a strawman-shaped baseline, and the paper concedes "a stronger checker prompt or model may narrow H2". More damaging: H2 gets no second family (gpt-oss-20b produced only 4 violating first decisions, Δ = 0.0 pp, descriptive) and the pooled estimate is 26 pairs at p = 0.125. So "deterministic verification beats LLM checking" rests on a single 8B model against a deliberately unenhanced checker. The claim is probably directionally right — MIRROR found the same at message level — but the 19.7 pp is not a stable quantity.

**The second family does not replicate the thesis, and the paper deserves credit for saying so — but the conclusion should be rewritten accordingly.** For gpt-oss-20b, structured handoffs were already at 2.8% (T0) and 0.0% (T3) unsafe, manifests were *worse* at 11.1%, and utility dropped 28.7 pp. That is not "H1 supported, benefit confined to tampering"; it is "for a competent model on a benign or injection-only workload, this machinery is net negative". The paper reaches this in §6.5 and the conclusion, but the abstract still says "no net loss ... relative to structured handoffs" without the gpt-oss caveat, and the exploratory frontier subset (J at 0% under T0 and T3) points the same way. The mechanism's value proposition is narrower than the title suggests.

**A parser artifact contaminates the utility comparison.** 22.2% of gpt-oss-20b manifest failures are partly a transport quirk: gpt-oss emitted a `<|constrain|>` variant of the harmony final-channel header that the preregistered rule does not cover, and the authors declined to amend post hoc (principled, and I respect it). But the reported −28.7 pp utility loss is then a mixture of a real mechanism cost and an artifact, and the paper itself notes these arms "would have failed" the Qwen pilot's I2 criterion. The clean number is the among-usable-manifests fidelity (recall 87.5%, precision 93.4%), which is much less alarming.

**HMAC means signer = verifier = one trust domain.** The key never enters a prompt, which is the right hygiene, but it also means this is not the cross-organizational A2A/AP2 setting the paper invokes: a subagent runtime at another vendor cannot hold the same symmetric key, so real deployments need Ed25519 plus key distribution, revocation and identity binding — at which point "the harness is trusted" becomes a PKI problem the paper does not model. The claim being tested is "signing prevents in-transit mutation inside one administrative domain", which is narrower than the protocol discussion implies.

**Task scale and threat realism.** Three settings, two requirements, one cross-branch target, 48 tasks, fictional domains, and a single two-branch topology. Precision errors of the kind observed (54/139 preferences encoded as mandatory) will get worse, not better, with 15 requirements and four hops, and the paper's per-threat cells are n = 48, so the T4 contrast (52.1% vs 12.5%) carries wide uncertainty. T5's three injection templates are fixed, unoptimized and appended at the end of the request — the authors correctly label the resulting rates as lower bounds — and T5's T0 baselines come from earlier, non-interleaved runs, a design weakness they disclose.

**Reproducibility.** "Available from the authors on request" for a preregistered study whose entire epistemic value rests on frozen artifacts is a real deficiency. The task generator, the 48-task bank, the freeze manifests and the scorer should be deposited; without them, a reader cannot check the one thing that makes the paper credible — that the hypotheses really were frozen before the calls.

## Strengths

- **The arm ladder is the right experimental design, and it is executed cleanly.** S / J / JL / M / MS / MSO with byte-identical prompts and format references isolates structure, checking, signing and extraction error separately — the thing almost every "we added X to the handoff" paper fails to do.
- **The oracle-manifest control is a genuinely good instrument.** It converts a vague worry ("extraction might be lossy") into a bounded quantity (11.2 pp, all of the residual), and it makes the paper's central claim falsifiable rather than rhetorical.
- **T5 is the rare case of a paper preregistering an attack on its own defense and reporting the loss.** "Every unsafe commit of MS under T5 (18 of 18) had a corrupted manifest" is a crisp, memorable, actionable result, and it directly changes what a practitioner should build (confirm or re-extract the manifest before signing).
- **Same-trajectory shadow checking** is methodologically better than the message-level precedent it cites (MIRROR), because the checker and verifier see identical inputs and the comparison is paired at requirement granularity.
- **Transparency about failure.** The failed first pilot, the parser fix, the deferred Llama family, the gpt-oss parser quirk, the reduced cut, the non-equivalent H3b, and the reversal on stronger models are all disclosed rather than smoothed over. The deviations section is better than most camera-ready appendices.
- **Useful negative results for the field**: structure alone does little (J ≈ S: 56.2% vs 62.5% under T0), and a deciding LLM checker is both more expensive than the signed manifest and less safe under attack (20.1 pp more violations, 1.51× tokens).

## Limitations

- **Synthetic, finite-domain requirements only.** Every requirement is expressible as `eq / le / sum_le / implies` over three integer settings; the announced provenance-and-coverage-only secondary analysis that would probe this dependence is never reported. Real enterprise requirements ("reasonable", "policy-compliant", "as agreed with legal") are out of reach of the grammar.
- **One topology, small tasks.** Two branches, one merger, three settings, two requirements, 48 tasks. Deeper delegation trees, longer contexts and 10–20 requirements are untested, and extraction precision (70.4%) is likely to degrade first.
- **The confirmatory base is one 8B model family.** The second family ran at a reduced cut without its own pilot, and its 22% manifest-failure rate would have failed the primary family's instrument check. Frontier models appear only in a 12-task exploratory subset with wide uncertainty.
- **Abstention is counted as safety, not as cost.** Fail-closed is defensible, but 39.6% benign abstention means the system declines ~40% of ordinary requests, and no end-to-end completion metric captures that.
- **HMAC in a single trust domain.** No asymmetric signatures, no key distribution, no cross-vendor verification, no revocation — so the security claim does not yet reach the A2A/AP2 deployment story it motivates.
- **Threat scripts are minimal and non-adaptive.** Fixed T2a mutations, fixed T3/T4 tool notes, three fixed T5 templates appended at the end of the request; an optimizer attacking the extraction prompt is not modelled, so all attack rates are lower bounds.
- **The LLM-checker baseline is a single prompt on a thinking-disabled 8B model**, and H2 is not replicated in the second family (4 pairs) or the pooled analysis (26 pairs, p = 0.125).
- **No public artifact.** Code, task banks, freeze manifests and run logs are "available on request"; no dollar costs, no latency, no human-in-the-loop study of manifest confirmation.

## Relevance

这篇正好落在 **Agent & Pipeline Silent Failures** 的核心：它研究的不是模型本身会不会犯错，而是 orchestrator→subagent→merger 这条软件链路上，用户需求如何被摘要压缩、被中间层改写、被 merger 忽略——并且把"静默丢失"与"恶意篡改"分开量化，还给出了"抽取环节才是信任边界"这一条对任何 agent harness 设计都成立的结论。方法论上（预注册 + 冻结 manifest + 同一轨迹上的配对对照 + oracle 上界控制）也值得借鉴到"检测器 vs 基线"的可靠性评测里。

## Questions for Further Exploration

- Does extraction precision survive scale? With 12–15 requirements over four hops, does the 70.4% precision collapse, and does the 11.2 pp residual grow superlinearly?
- Would a second, independent extraction compared item-by-item (or a one-click user confirmation of the manifest) recover most of the residual, and at what human-time cost per request? The paper recommends both but measures neither.
- How much of H2's 19.7 pp survives a fairer checker — Qwen3-8B with thinking enabled, a 70B checker, or self-consistency over three checker samples? The frontier subset hints the gap narrows.
- What is the right fail-closed policy when the manifest is unparseable (22% of gpt-oss tasks)? Abstain is safe but costs 100% utility; a fallback to the structured handoff plus a warning might dominate.
- Can the "preference encoded as mandatory" error (54 of 139 kept items) be fixed by a typed `kind: mandatory | preference` field with a separate provenance rule, or is it a fundamental instruction-following limit of 8B orchestrators?
- How does this compose with CaMeL-style capability control — is the signed manifest the policy layer that CaMeL's interpreter should consume, and does the combination close both the injection and the extraction gap?
- With Ed25519 and cross-vendor key distribution, does receipt rejection still work when the verifier is a different organization, and what does revocation look like when a manifest outlives its signer's key?
- Does the brittleness cost (2.1% receipt rejection under a schema-preserving relay) explode under a realistic context-compaction middleware that re-encodes rather than preserves structure? The paper flags this as untested.
