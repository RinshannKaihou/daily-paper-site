> **一句话总结：** 这篇 7 页的 ACM letter 不是新方法而是一次系统性"证据盘点"：作者逐一核对截至 2026-10-05 所有 9B–20B 开源模型在 vLLM/SGLang 上的量化部署公开数据，发现全表只有两个 checkpoint（都是 Gemma 3 12B 的 INT4 构建）同时具备 vLLM 计时和准确率分数，而这个分数只覆盖一个 MMLU 子科目、且恰好是 AWQ 校准所用的科目；现存计时都服从同一条 roofline 规律——batch=1 时 decode 受内存带宽限制，4-bit 权重约提速 2 倍（Qwen2.5-14B 在 A100 上 GPTQ-Int4 达 2.12×），batch=256 时转为 compute-bound、增益消失（Gemma 3 12B 只剩 1.02×），长 prompt 同理；而大量已发表的准确率差值（包括全部 HumanEval 差值）落在单次运行的采样噪声之内。

> **TL;DR:** A 7-page measurement-survey letter, not a new method: it audits every public quantized-serving number for 9B–20B open models on vLLM/SGLang up to 5 Oct 2026 and finds the record answers "how much faster, how much worse" only in fragments. The one robust timing pattern is a roofline rule — W4A16 roughly doubles batch-1 decode (vLLM 0.6.3, one A100 80GB, Qwen2.5-14B-Instruct: BF16 46.30 → GPTQ-Int4 98.02 tok/s, **2.12×**, memory 28.08 → 9.94 GB) but collapses to **1.02×** at batch 256 (vLLM benchmark_latency, H100, Gemma 3 12B IT: 14.07 s → 13.81 s with TorchAO INT4), where FP8 is the recipe the roofline favors but nobody has timed above batch size 1. On accuracy, once you compute the single-run standard error (3.9 pts on HumanEval n=164, 0.8–1.3 on GSM8K n=1,319, 0.34–0.39 on full MMLU n=14,042), **every HumanEval delta in their table (−3.05 to +6.10) is inside noise**; only two GSM8K losses clear 3 SE (AWQ on Qwen3-14B −4.17, GPTQ on Mistral NeMo −4.02). Read it if you are picking a quantization recipe for self-hosted 9B–20B serving or writing a quant model card; skip it if you want new measurements — it runs no experiments, and its own Table 1 rows come from four mutually incomparable setups.

## 核心贡献

- **一次带准入门槛的公开证据盘点，而不是又一次 benchmark**。计时只在该来源同时给出引擎、GPU、checkpoint 和工作负载时被收录；准确率只在该来源同时给出同一 harness 下的 BF16 分数时被收录。检索范围覆盖 vLLM / SGLang / AMD ROCm / Intel Gaudi 官方文档、模型方与量化方的 Hugging Face 模型卡（Red Hat AI、PyTorch、Tencent AngelSlim）、benchmark 报告和 arXiv，把 7 个模型（Qwen2.5-14B、Qwen3-14B、Gemma 3 12B、Phi-4、Mistral NeMo、Ministral 3 14B、gpt-oss-20b）与 7 种 recipe（FP8、INT8、AWQ、GPTQ、INT4、NVFP4、MXFP4）逐一配对，截止 2026-10-05，每个数字回原文核对。
- **核心负面结论：证据链是断的**。整个参数带里只有两个 checkpoint——都是 Gemma 3 12B 的 INT4 构建——同时有 vLLM 计时和准确率分数，而那个分数只测了单个 MMLU 子科目（philosophy，311 题），并且 AWQ 构建正是在该子科目的 30 个样本上校准的。也就是说，"同一个 checkpoint、同一次实验里同时给出速度和精度"这件事，在 9B–20B 这一段基本没人做过。
- **用一条 roofline 规则统一解释所有计时**：batch=1 时每生成一个 token 要把全部权重读一遍，decode 时间由搬运的字节数决定，4-bit 权重只搬 BF16 的四分之一字节——这就是为什么所有 INT4 recipe 在 batch=1 都快 1.35–2.12×，而到不了 4×（dequant、attention、KV-cache 读取都不缩）。batch=256 时一次权重读取服务 256 条序列，matmul 转为 compute-bound，而 W4A16 仍在 16-bit 里算，于是 Gemma 3 12B 只剩 1.02×。长 prompt 因为同样理由退化：A100 上 INT4 的 2.12× 在 30,720 token 输入时掉到 1.64×。
- **给出可复用的"噪声标尺"**：没有任何来源报告标准误，作者用单次运行的 $p(1-p)/n$ 自己算——HumanEval（n=164）约 3.9 分、GSM8K（n=1,319）0.8–1.3 分、完整 MMLU（n=14,042）0.34–0.39 分、MMLU philosophy（n=311）2.3 分。用这把尺子量 Table 2，HumanEval 上从 −3.05 到 +6.10 的全部差值都不可区分。
- **指出 harness 的影响大于 recipe**：同一个 Qwen3-14B、同一个 W4A16 思路，两组来源在 GSM8K 上给出 −1.06 和 +3.94；而两者的 BF16 基线本身相差 20.77 分（67.63 vs 88.70）。这个基线差距比表里任何一个量化 delta 都大一个量级。
- **Table 3 逐条给结论打置信度**（按独立来源数 × 模型数 × GPU 数），并明确标注"AMD 与 Intel Gaudi 在该参数带没有任何计时"、"FP4 没有任何对 BF16 的加速测量"、"大 batch 下 FP8 未被测试"。
- **七条报告清单**：同一 checkpoint ID 与 revision 同时用于计时和精度、引擎版本与全部非默认 flag、GPU 型号与数量、输入输出长度与 batch/请求率及吞吐是否计入 prompt token、同栈 BF16 基线、harness 版本与 few-shot 数与 chat template 与 reasoning mode 及 n 与标准误、校准数据与评测集不相交。作者自己承认：没有任何一个来源满足全部七条。

## Key Contributions

- **A gated evidence audit rather than another benchmark.** A timing was admitted only if its source named the engine, GPU, checkpoint and workload; an accuracy score only if the same source reported a BF16 score from the same harness. The search spans vLLM, SGLang, AMD ROCm and Intel Gaudi documentation, Hugging Face model cards from both model developers and quantization publishers (Red Hat AI, PyTorch, Tencent AngelSlim), benchmark reports and arXiv, pairing seven models against seven recipes and both engines through 5 October 2026, with every number re-checked against its cited source.
- **The central negative finding: the evidence chain is broken.** In the entire 9B–20B band only two checkpoints — both INT4 builds of Gemma 3 12B — have both a vLLM timing and an accuracy score, and that score covers a single MMLU subject (philosophy, 311 questions) on which the AWQ build was calibrated on 30 samples. "Same checkpoint, speed and accuracy measured in the same experiment" is essentially unpublished for this class of model.
- **One roofline rule explains every timing in the table.** At batch size 1 each generated token reads every weight once, so decode is bandwidth-bound and 4-bit weights move a quarter of BF16's bytes — hence the uniform 1.35–2.12× INT4 gain, short of 4× because dequantization, attention and KV-cache traffic do not shrink. At batch 256 one weight read serves 256 sequences, the matmuls become compute-bound, and W4A16 still computes in 16 bits, so Gemma 3 12B gains only 1.02×. Long prompts degrade for the same reason: the A100 INT4 gain falls from 2.12× to 1.64× at a 30,720-token prompt.
- **A reusable noise yardstick.** No source reports a standard error, so the authors supply $p(1-p)/n$ for a single run: ≈3.9 points on HumanEval (n=164), 0.8–1.3 on GSM8K (n=1,319), 0.34–0.39 on full MMLU (n=14,042), 2.3 on MMLU philosophy (n=311). Measured against it, the whole HumanEval column (−3.05 to +6.10) fails to separate recipes.
- **Harness settings dominate recipes.** The same Qwen3-14B checkpoint under the same W4A16 idea moves GSM8K by −1.06 in one source and +3.94 in another, and the two BF16 baselines differ by 20.77 points (67.63 vs 88.70) — larger than any quantization delta in the paper.
- **Per-claim confidence grading (Table 3)** by number of independent sources, models and GPUs, with explicit "None" entries for AMD/Gaudi timings in this band, FP4 speedup versus BF16, and FP8 above batch size 1.
- **A seven-item reporting checklist** (checkpoint ID and revision shared by timing and accuracy; engine, version and non-default flags; GPU model and count; sequence lengths, batch/request rate and whether prompt tokens count; same-stack BF16 baseline; harness, version, few-shot count, chat template, reasoning mode, n and standard errors; calibration data disjoint from evaluation sets). The authors note that no source satisfies all seven.

## Methodology

This is a structured literature and documentation review, not an experimental paper. The design has five parts.

**Scope and inclusion rule.** Seven open-weight models in the 9B–20B band are in scope: Qwen2.5-14B, Qwen3-14B, Gemma 3 12B, Phi-4, Mistral NeMo, Ministral 3 14B and gpt-oss-20b. A *timing* was admitted only if the source named the engine, the GPU, the checkpoint and the workload; an *accuracy score* only if the same source also reported a BF16 score from the same harness. This rule is deliberately strict and is the reason the admitted evidence set is so small — it is a design choice, not an accident, and the paper's headline finding follows directly from it.

**Search protocol.** Documentation for vLLM, SGLang, AMD ROCm and Intel Gaudi; Hugging Face model cards from model developers (Qwen, Google, Microsoft, Mistral, OpenAI) and from quantization publishers (Red Hat AI, PyTorch, Tencent AngelSlim); benchmark reports (SemiAnalysis InferenceX, GPUStack's performance lab); and arXiv. Each model name was paired with each recipe (FP8, INT8, AWQ, GPTQ, INT4, NVFP4, MXFP4) and each engine, with a cutoff of 5 October 2026. An AI coding assistant assisted in collecting sources and extracting numbers; every number was then checked against its cited source on 5 October 2026. There is no reported inter-rater check, no rejected-source log, and no published extraction table.

**Roofline analysis.** The explanatory core. Decode at small batch is modeled as bandwidth-limited (bytes moved per token ∝ weight precision), prefill and large-batch decode as compute-limited (FLOPs per token ∝ activation precision and batch size). W4A16 sits in an awkward middle: it quarters weight traffic but keeps the matmul in 16 bits, so it wins exactly where traffic dominates and loses where arithmetic dominates. W8A8 and FP8 quarter *both*, which is why the paper predicts FP8 survives at large batch — a prediction it explicitly cannot test because no in-band source reports FP8 above batch size 1.

**Noise yardstick.** For a score $p$ on $n$ questions, one standard error of a single run is $\sqrt{p(1-p)/n}$, evaluated at the BF16 score reported in Table 2. This is used as a threshold for judging whether a reported delta is interpretable. The authors acknowledge (citing Dutta et al. on answer flips) that the standard error of a *delta* also depends on how many answers flip between runs, which no source reports.

**Grading.** Each claim in Table 3 is assigned a confidence level justified by the count of independent sources, models and GPUs behind it, producing a mix of Moderate, Low and None that is unusually candid for this genre.

## Results & Highlights

- **Batch-1 decode speedup is real and roughly 2×, not 4×.** vLLM 0.6.3, one A100 80GB, Qwen2.5-14B-Instruct, batch size 1, 2048 output tokens: BF16 46.30 tok/s → GPTQ-Int4 98.02 tok/s (**2.12×**), AWQ 92.66 tok/s (2.00×), GPTQ-Int8 70.40 tok/s (1.52×). GPU memory falls from 28.08 GB to 9.94 GB (GPTQ-Int4) and 9.79 GB (AWQ). The gap to the theoretical 4× is attributed to dequantization, attention and KV-cache reads, none of which shrink with weight precision.
- **The speedup vanishes at large batch, and this is the paper's title.** vLLM `benchmark_latency`, H100, Gemma 3 12B IT, 256 input / 256 output tokens: BF16 latency 14.07 s at batch 256 versus 13.81 s for TorchAO INT4 (**1.02×**) and 13.93 s for AWQ-INT4 (1.01×). The same two builds at batch 1 give 3.73 s → 2.73 s (1.37×) and 2.76 s (1.35×). A 37% latency win at batch 1 becomes a 2% win at batch 256 — the same checkpoint, the same engine, a 25× larger batch.
- **Long prompts reproduce the collapse, and FP8 overtakes INT4 there.** On the A100, Qwen2.5-14B's GPTQ-Int4 gain drops from 2.12× at 1-token input to **1.64×** at a 30,720-token input (60.91 vs 37.18 tok/s). On an H20 with SGLang 0.4.6.post1 and Qwen3-14B, FP8 W8A8 goes 97.11 → 880.72 (prompt+output) tok/s, i.e. 2.06× at short input and **1.68×** at 30,720 tokens, while AWQ-INT4 goes 96.49 → 744.74, i.e. 2.05× and **1.42×**. At batch 1 the two recipes tie (2.06× vs 2.05×); at long prompt FP8 wins by 18% in absolute throughput — the crossover the roofline predicts.
- **Every HumanEval delta is inside sampling noise.** With n=164 the single-run standard error is ≈3.9 points. The reported HumanEval deltas span −3.05 (FP8-dynamic, Qwen3-14B) to +6.10 (AWQ-INT4, Qwen3-14B), which is −5 to +10 problems out of 164. The nominally largest accuracy *gain* in the entire table — AWQ's +6.10 on Qwen3-14B (55.49 → 61.59) — is 1.6 standard errors and cannot be distinguished from zero.
- **Two GSM8K losses do clear the bar.** AWQ-INT4 on Qwen3-14B: 88.40 → 84.23 (**−4.17**), and GPTQ W4A16 on Mistral NeMo Instruct 2407: 74.45 → 70.43 (**−4.02**). At n=1,319 the standard error is 0.8–1.3, so both exceed three single-run standard errors and are the clearest genuine degradations in the paper.
- **8-bit is essentially free; INT4 is cheap on MMLU but not on GSM8K.** On full MMLU (n=14,042, SE 0.34–0.39) every 8-bit delta is at most 0.77 points (INT8-dynamic on Qwen3-14B, 78.90 → 78.13), about two standard errors; INT4 costs 0.43–1.43 points; NVFP4 costs 1.63 (Qwen3-14B, 78.86 → 77.23). Across five models from two publishers, the 8-bit MMLU claim is the best-supported accuracy statement in the letter.
- **The Gemma INT4 accuracy rows are both small-sample and contaminated.** They are scored on MMLU philosophy (311 questions, SE ≈2.3) and the AWQ checkpoint was calibrated on 30 of those 311 samples. TorchAO INT4 shows −3.54 and AWQ −2.25, but neither number can be read as a clean quantization cost.
- **Engine choice, not recipe choice, produced the biggest single number in the table.** gpt-oss-20b (MXFP4, 20.9B total / 3.6B active MoE) on one H100 SXM over 1000 ShareGPT prompts: vLLM 0.11.0 at **16,493.75** total tok/s versus SGLang 0.5.4.post2 at **5,626.99** tok/s, a **2.93×** gap at default settings; asynchronous scheduling raises vLLM to 19,128.79 tok/s. There is no BF16 timing for this model at all, so no speedup-versus-BF16 exists.

## Authors & Credibility

Smit Kadvani, Kriti Faujdar and Spurthi Tallam, all listed as "Independent researcher, United States" — no institutional affiliation, no lab, no prior serving-systems footprint that this letter leans on. The venue is *ACM AI Letters* in letter format: 7 pages, 50 references, a single table-driven argument, no appendix.

The sourcing is the credible part. Every row in Tables 1 and 2 carries a numbered citation to a specific document — vLLM and SGLang docs, ROCm blog posts, Intel Gaudi performance pages, and named Hugging Face model cards (`RedHatAI/gemma-3-12b-it-FP8-dynamic`, `pytorch/gemma-3-12b-it-AWQ-INT4`, `AngelSlim/Qwen3-14B_fp8_static`, `Qwen/Qwen3-14B-FP8`) — rather than to "reported results" in the abstract. Footnotes distinguish what was measured from what was inferred: the memory column carries a † because vLLM and SGLang pre-allocate GPU memory, so the figures come from a Transformers run in the same source; the ★ marks a checkpoint size taken from the model card rather than measured.

The paper is candid about its own process in a way that is rare and worth crediting: it states that an AI coding assistant helped collect sources and extract numbers, and that every number was manually re-checked on 5 October 2026. It also states plainly that no source in the letter meets all seven of its own checklist items, and that its Table 1 rows "come from different experiments and are not one benchmark."

Positioning against prior work is accurate. Kurtic et al. (ACL 2025) measure accuracy and vLLM speed together but only for Llama 3.1 at 8B/70B/405B — outside this band. Shi and Ding (2025) characterize eleven recipes on TensorRT-LLM for Llama-2 and CodeLlama — different engine, different models. Zhao et al. (2025) benchmark post-training quantization on quality alone. InferenceX benchmarks vLLM and SGLang continuously but lists no model in 9B–20B. The gap the letter claims is therefore real, and narrow in a defensible way.

The credibility gap is the absence of an artifact. For a paper whose entire contribution is a curated table, there is no CSV, no extraction script, no list of sources screened and rejected, and no query strings. The tables are the dataset, and the dataset is only available as typeset PDF.

## Critical Assessment

**Novelty is in the synthesis, and the synthesis is thinner than the framing suggests.** The roofline explanation — bandwidth-bound decode at small batch, compute-bound at large batch, W4A16 stuck in between because its matmul stays 16-bit — is standard systems reasoning and the paper does not claim otherwise. What is genuinely new is the *negative* result (nobody measures speed and accuracy on the same checkpoint) and the *yardstick* (compute the standard error yourself). Those two ideas would fill three pages; the letter is seven.

**The strongest observation in the paper is stated and then abandoned.** The two Qwen3-14B groups using "the same W4A16 idea" report GSM8K deltas of −1.06 and +3.94, and their BF16 baselines are 67.63 and 88.70 — a **20.77-point** spread on the same model family. That gap is roughly five times larger than any quantization delta in Table 2. The paper mentions it in one sentence as evidence that "harness settings matter as much as recipes," but the conclusion it actually implies is stronger: at that spread, the entire accuracy column of Table 2 is measuring harness configuration, not quantization, and the reported deltas should be read as upper bounds on recipe effects rather than estimates of them. A paper willing to follow its own evidence would have reorganized Section 4 around this.

**The noise argument is directionally right but systematically biased toward "everything is noise."** The yardstick uses the standard error of a *single run*, $\sqrt{p(1-p)/n}$, as the threshold for judging a *delta*. Quantized and BF16 evaluations run on the same question set, so the two scores are paired; the standard error of the paired difference is smaller than the standard error of either marginal whenever per-question outcomes correlate, and much smaller when they correlate strongly (which they do — most questions are answered correctly by both). The paper cites Dutta et al. on answer flips, so it knows this, yet it still applies the unpaired threshold. The effect is to inflate the noise band: some deltas dismissed as noise here (AWQ's +6.10 on HumanEval, GPTQ's +2.44) might survive a McNemar test on per-question correctness. The paper never runs one, and never reports per-question data — because no source publishes it. That is a fair excuse for not running the test, but not for presenting the unpaired SE as a decisive threshold.

**The 2.93× vLLM-versus-SGLang figure is the least defensible number in the letter and gets the most prominent treatment.** It comes from a single GPUStack blog post, at "default settings," on one GPU, with no tuning, no parallelism configuration reported, and no BF16 reference. A 3× engine gap on the same hardware and the same prompts is far more plausibly a configuration artifact — tensor-parallel degree, CUDA graph capture, scheduler chunking, or whether continuous batching was engaged — than an engine-quality difference. The paper grades it "Low: 1 source, untuned" in Table 3, which is correct, but it still appears in the narrative next to the roofline findings as though it were a comparable result. It isn't; it's a different kind of claim.

**The MXFP4-is-exactly-BF16 argument is an assertion used to dissolve a missing baseline.** The paper argues that "MXFP4 values are exactly representable in BF16 at realistic block scales, so a BF16 copy would have the same accuracy," which lets it treat gpt-oss-20b's absent BF16 timing as a non-problem for accuracy. The representation claim is arithmetically true (E2M1 values with a shared E8M0 scale fit inside BF16's 8-bit mantissa), but it only establishes that the *stored weights* are identical after dequantization. It says nothing about whether a BF16 execution path accumulates in the same precision, uses the same kernel, or produces the same logits — and the paper's own thesis is that kernels and numerics matter. Using a representation argument to close an empirical gap is exactly the move the letter criticizes elsewhere.

**The one experiment that would have settled the thesis was not run.** Section 3 ends with: "The rule predicts that FP8 keeps a speedup at large batch where INT4 loses it, but no in-band source tests FP8 above batch size 1." That is one afternoon on a single H100 — load a public FP8 checkpoint, run vLLM's `benchmark_latency` at batch 256, compare to BF16. The authors had the roofline prediction, the checkpoints are public, and the harness is a one-line command. Declining to run it leaves the letter's central open question self-inflicted, and it is the difference between a survey that diagnoses a gap and one that also closes it.

**Scope exclusions that matter in practice.** No energy or cost-per-token (the actual purchasing decision for self-hosted serving), no KV-cache quantization (which changes the memory-traffic balance the roofline depends on), no tensor parallelism (mandatory above one GPU for 14B at long context), no speculative decoding (which shifts decode from bandwidth-bound toward compute-bound and would therefore *shrink* the INT4 advantage), and no structured-output or tool-calling workloads (where token distributions differ sharply from MMLU). Each of these would move the crossover point the paper identifies.

**Table 1's internal comparability is weaker than the "1.35–2.12×" summary implies.** The four groups use three different metrics — output tok/s, wall-clock latency in seconds, and (prompt+output) tok/s — on three different GPUs (A100, H100, H20), two engines, and engine versions spanning 2024 to 2026. The paper is explicit that "speedups compare within a group only," but Table 3 then pools them into a single "W4A16 is 1.35–2.12× faster" claim graded Moderate on the strength of "3 sources, 3 GPUs." Those two statements are in tension: a range assembled from incomparable groups is not a confidence interval, and the confidence grade should reflect that the sources disagree on metric definition as much as they agree on the direction.

**Red flag on the headline claim's own footing.** "Only two checkpoints have both a vLLM timing and an accuracy score" is the sentence the abstract leads with, and it is checkable only against the authors' search. But the Gemma timing comes from vLLM's `benchmark_latency` on H100 and the Gemma accuracy from PyTorch's `lm-eval` on Transformers — the paper's own Table 2 footnote says "None of these scores comes from a timing run in Table 1." So even the two privileged checkpoints do not have speed and accuracy measured in one experiment; they have a timing from one source and a score from another, on different software stacks. The claim is technically true as stated ("have both") and materially weaker than a reader will take it to be.

**What is genuinely good.** The grading in Table 3 is the most useful artifact in the paper, and the honesty is unusual: writing "None" in a confidence column for AMD, Gaudi and FP4, and "Low: 1 model, 1 source" for the large-batch claim, is the kind of self-limitation most benchmarking papers avoid. The seven-item checklist is concrete enough to be adopted by a model-card author tomorrow, and item 7 (calibration data disjoint from evaluation sets) catches a real and common sin — one this paper documents in the Gemma AWQ row.

## Strengths

- **It answers a question practitioners actually ask** — "if I quantize this 14B model, how much faster and how much worse" — and answers it honestly, including when the answer is "nobody has measured that."
- **The roofline framing is correct and predictive, not just descriptive.** It explains the 2.12× and the 1.02× with one mechanism, predicts the FP8 crossover on long prompts, and correctly predicts that FP8 on Ampere should behave like weight-only INT8 (≈1.52×) rather than like INT4.
- **The standard-error yardstick is a transferable tool.** Anyone reading a quantization model card can apply $\sqrt{p(1-p)/n}$ in thirty seconds and discover that the ±2-point claim they were about to trust is inside noise. This alone justifies the letter's existence.
- **Per-claim confidence grading with explicit "None" entries.** Table 3 refuses to launder absence of evidence into a weak claim, which is rarer than it should be.
- **The seven-item checklist is immediately actionable** and each item is motivated by a specific failure documented in the tables, not invented in the abstract.
- **Sourcing discipline.** Fifty references, every number tied to a named document with a retrieval date, footnotes separating measured from inferred quantities, and an explicit statement of when verification happened.
- **Intellectual honesty about the authors' own method**, including the disclosure of AI-assisted extraction and the admission that no source — including the ones they rely on most — meets their own reporting standard.

## Limitations

- **No new measurements.** The letter is entirely secondary analysis; the one experiment that would test its central prediction (FP8 at large batch) is left to future work despite being cheap.
- **The evidence base is very small.** Four timing groups, five of seven models with any accuracy table, and one model with both. Conclusions about "the record" rest on a handful of vendor documents, several of which are marketing pages.
- **Metrics are not comparable across Table 1's groups** (output tok/s vs latency-seconds vs prompt+output tok/s), so the pooled "1.35–2.12×" range is a summary of direction, not a measured distribution.
- **The noise analysis uses unpaired standard errors** for what are paired evaluations, biasing the paper toward classifying real deltas as noise; no McNemar, bootstrap or per-question analysis is possible because no source publishes per-question outcomes.
- **Accuracy coverage is narrow**: MMLU, GSM8K, HumanEval and C-Eval only. No long-context retrieval, no multilingual beyond C-Eval, no instruction-following, no tool use, no calibration or refusal behavior — all plausible places for 4-bit damage to appear first.
- **No systems-level cost analysis**: no energy per token, no dollars per million tokens, no amortized hardware cost, which is what actually determines whether a 2× decode speedup is worth a 4-point GSM8K loss.
- **No treatment of KV-cache quantization, tensor parallelism, speculative decoding, or chunked prefill**, each of which changes the memory/compute balance the roofline argument depends on.
- **Web sources are ephemeral.** Every vendor page can change or disappear; the paper pins a retrieval date but ships no archive or snapshot, so the tables are not independently reconstructible.
- **No artifact.** For a paper that is essentially a curated dataset, the absence of a CSV of extracted rows with source URLs and retrieval timestamps is a significant missed opportunity.
- **The Gemma AWQ row is contaminated** (calibrated on 30 of the 311 evaluation questions) and the authors report the number anyway, with a footnote, rather than dropping the row.

## Relevance

直接命中 **Reliability under Extreme Performance Optimization**：它讨论的正是激进推理优化（4-bit/8-bit 权重量化、FP8/FP4 格式）在真实服务栈上付出的精度代价，并且给出了一把判断"这个精度损失是真的还是采样噪声"的定量尺子（单次运行标准误 $\sqrt{p(1-p)/n}$），做低精度数值可靠性的人可以直接复用。更重要的是它揭示了一个系统性证据缺口——速度和精度几乎从不在同一个 checkpoint、同一次实验里被同时报告——这本身就是量化可靠性证据链上的结构性问题。

## Questions for Further Exploration

1. If you ran the missing experiment — a public FP8 W8A8 checkpoint at batch 256 on H100 against a same-stack BF16 baseline — does it actually deliver the roofline-predicted speedup, or does attention and KV-cache traffic eat it the way it eats INT4's 1.02×?
2. What is the *paired* standard error of these deltas? Running McNemar on per-question correctness for the Qwen3-14B AWQ HumanEval comparison (+6.10 on n=164) would show whether the paper's noise verdict survives a test that respects the pairing — and would tell us how many of the dismissed deltas are actually real.
3. Why does the same W4A16 recipe on the same Qwen3-14B checkpoint move GSM8K by −1.06 in one harness and +3.94 in another, with BF16 baselines 20.77 points apart? Chat template, few-shot count, answer-extraction regex, or reasoning-mode default? A controlled ablation on this single discrepancy would be worth more than any new recipe comparison.
4. Does the 2.93× vLLM/SGLang gap on gpt-oss-20b survive matched tensor-parallel degree, CUDA-graph settings and scheduler configuration — and if it shrinks to, say, 1.2×, what does that imply about how the community reads single-source engine benchmarks?
5. For the silent-data-corruption angle: do FP8-static and FP8-dynamic differ in tail behavior — rare catastrophic outputs, per-token variance, long-context degradation — rather than in mean benchmark accuracy, which is all Table 2 can see?
6. Would publishing the extraction table (CSV with source URL, retrieval date, checkpoint revision, engine version per row) turn this kind of letter from a snapshot into citable infrastructure that others could extend quarterly?
7. At what batch size does the INT4 advantage actually cross zero for a 14B model with realistic 8K contexts — and does that crossover move enough between A100, H100 and H20 to make "quantize for throughput" a GPU-specific rather than a model-specific decision?
