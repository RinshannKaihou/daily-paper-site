> **一句话总结：** 论文把"提取器给模型看的文本 ≠ Office 渲染给人类看的内容"形式化为 extraction divergence（提取分歧），用静态源码分析（建模 descriptor 框架，把 python-pptx 的可达 selector 从通用调用图分析的 2 个恢复到 179 个元素 + 67 个属性，约 90 倍）+ 动态 canary 注入，在 10 个主流提取器上测出 31 条分歧通道（19 条注入人类看不见的内容、12 条丢弃人类看得见的内容）；据此构造 5 个**不含任何指令**的攻击（隐藏注入、静默省略、数字格式篡改、空间顺序反转、子词重组），在 400 次端到端试验中让 ChatGPT/Claude/Gemini/M365 Copilot 与 Codex/Claude Code/Antigravity/Copilot CLI 八个系统整体上当率 64%（聊天助手 75%，Gemini 100%）；防御方案 Prism 直接按 ECMA-376 规范从文件重建"人类视图"，静态解释器 0.5 ms/文档（markitdown 的 63 ms 的约 1/126），把预算表里的 1,000,000 还原成 $1,000、补回被丢掉的 80 psi 页脚，在 28 个未见载荷上 84/84 全部正确，误报率 2.6%。

> **TL;DR:** Office files are ZIP archives of OOXML parts, and the text an LLM sees comes from an extractor, not from Excel's renderer. This paper measures that gap and weaponizes it. On a 2,229-file corpus (govdocs1 + national open-data portals: 917 XLSX, 1,000 DOCX, 312 PPTX), 10 extractors (markitdown, python-docx/pptx, openpyxl, pandas, unstructured, Docling, Tika/POI, calamine, docx2python) diverge on 31 channels — markitdown alone exposes 9 invisible PPTX channels, python-docx drops 6 visible DOCX channels — and *all six* Python XLSX extractors emit the stored `1,000,000` instead of Excel's displayed `$1,000` (only Tika/POI applies the number format). Five instruction-free attacks then reach 64% success over 400 end-to-end trials against 8 products (Gemini 100%, Copilot CLI 86%, Codex 82%, ChatGPT 40%, Claude Code 24%, Antigravity 22%); formatting divergence is the strongest single vector at 88%. A controlled swap of only the extracted text (markitdown output vs clean control) flips GPT-5.6, Claude Opus 5.5 and Gemini 4 from the attacker's answer to the human's answer in 10/10 trials each, proving extraction — not reasoning — is the cause. Prism, the defense, resolves everything the spec fixes (visibility, number formats, part inclusion, paragraph order) statically in 0.5 ms/doc and only renders the genuinely layout-dependent residue, cutting the 64% ASR to 0 and recovering all 28 unseen payloads.

## 核心贡献

- **首次系统研究 Office 文档的提取分歧。** 把"人类视图 `H_R(f)`（Office 默认视图渲染出的内容 + 视觉阅读顺序）"与"模型视图 `E(f)`（提取器输出）"的差定义为 extraction divergence，并明确它**不是** prompt injection：文件语法合法、无恶意代码、无指令，因此恶意软件扫描器、CDR、prompt-injection 检测器全部失效。与并发工作 Liu & Ming 2026（Split-View PDF）相比，OOXML 额外提供了"存储值 vs 显示值分离"和"自由定位形状"两类 PDF 没有的分歧来源。
- **混合程序分析（本文方法论上最扎实的部分）。** 静态分析不读代码而读**声明**：python-pptx 的 `xmlchemy` 用 `ZeroOrOne("a:rPr")` 描述符声明 XML 访问，真正的 tag 只出现在类定义里，使用点 `run.rPr` 既无 tag 也无 `find()`，所以调用图/字符串分析只找到 2 个元素 selector；建模 descriptor 框架后恢复 179 元素 + 67 属性（python-docx 122+58，openpyxl 682+93）。动态分析用 canary 标记文档 + 对 `zipfile` 插桩记录打开的 part，补上静态分析看不见的直读 XML。
- **31 条分歧通道的定量刻画。** 19 条 injection（人类看不见但被提取：PPTX 10、DOCX 4、XLSX 5，含 off-slide 文本、隐藏幻灯片、演讲者备注、alt text、形状名、幻灯片母版、隐藏行列与隐藏工作表、单元格批注、定义名称），12 条 omission（人类看得见但被丢弃：DOCX 8、XLSX 3、PPTX 1，含页眉、页脚、脚注、文本框、内容控件）。格式特征鲜明：**PPTX 提取器主要"注入"，DOCX 提取器主要"遗漏"**。
- **表现层（presentation）分歧，与内容无关却同样致命。** 五个 PPTX 提取器在一个四形状幻灯片上给出**三种不同顺序**（python-pptx/Tika 跟 XML 兄弟序 `CADB`，markitdown/unstructured 跟严格 `(y,x)` 几何序 `BADC`，只有 Docling 得到视觉序 `ABCD`）；六个 XLSX 提取器全部输出存储值而非显示值；六个 DOCX 提取器全部把跨 run 的 `un`+`authorized` 直接拼成 `unauthorized`。
- **五个无指令攻击 + 八系统实测。** Content-1 隐藏注入（`w:vanish` 里的假 SOC 2 Type II 认证）、Content-2 静默省略（把 80 psi 压力上限放在页脚）、Presentation-1 格式篡改（预算 $1,000 vs 1,000,000）、Presentation-2 空间顺序反转（`Contractor indemnifies Client` → `Client indemnifies Contractor`，靠形状树逆序 + 每框抬高 1 个坐标单位，亚像素级）、Combination 子词重组（隐藏 `un` 前缀）。每个攻击配一个"干净对照"文档，只改一处使提取器能正确读出。
- **Prism：按规范重建人类视图。** `C(f) = serialize(order(display(visible(atoms(f)))))` —— atoms/visible 管注入与遗漏，display 管数字格式（从零实现 ECMA-376 数字格式求值器，不依赖任何渲染器），order/serialize 管顺序与 run 拼接；规范未定的部分（换行、分页、浮动对象遮挡）交给 render oracle（LibreOffice + Apple Quick Look 双引擎渲染 + VLM 读序，一致则输出、分歧则标 ambiguous）。支持 mediation 模式（替换提取器）与 checking 模式（只比对告警）。

## Key Contributions

- **A new threat class, cleanly separated from prompt injection.** Extraction divergence is a parser differential (Sassaman et al. 2013) at the document→LLM boundary where the second reader is a language model. Because no instruction is embedded, the whole defense stack built for prompt injection (StruQ, spotlighting, instruction/data separation) is inapplicable, and content-disarm-and-reconstruction passes the files untouched — they are valid OOXML.
- **Descriptor-framework-aware static analysis.** Recovering XML selectors from metaclass-installed descriptors rather than from code is the paper's genuine technical novelty: ~90× more selectors than a call-graph/string-literal baseline on python-pptx, and the only way to enumerate channels across Python, Java and Rust extractors with one method.
- **A three-way decomposition of extraction into selection / interpretation / serialization**, each mapping to one attack family (injection-omission / formatting / reading order). This is the conceptual spine that makes the 31 measured channels actionable rather than a bug list.
- **Empirical demonstration that susceptibility is an ingestion-path property, not a model property.** Same vendor, wildly different outcomes: Gemini chat 100% vs Antigravity 22%; Claude chat 80% vs Claude Code 24%. Coding agents that unpack the ZIP and read `sheet1.xml` directly resist; agents that shell out to pandoc + openpyxl do not.
- **A specification-grounded defense with a measured cost curve.** 0.5 ms/doc static pass vs 63 ms for markitdown vs ~12 s for the render oracle — the paper is explicit that the cheap path covers most documents (96% of spreadsheets and 79% of Word files never need the oracle; 99% of presentations do).

## Methodology

**Measurement (§4).** Ten extractors selected by download counts, stars, default-loader status and vendor backing, each run through its default text-extraction interface with versions recorded. Static analysis recovers selectors per library; dynamic analysis places unique canary strings at every text-capable location (including invisible ones) and greps the output, with `zipfile` instrumented to log which package parts were opened. Visibility labelling follows OOXML default-view rules (Word print layout, Excel sheet view, PowerPoint slideshow), which makes "invisible" relative to a named application `R` rather than an intrinsic XML property — an important and correctly stated scoping choice. A raw-XML dump of every part serves as the reference for "dropped" vs "never there."

**Presentation probes (§4.2).** Reading order is tested on a purpose-built four-shape slide (two rows, right shape of each row raised slightly, shape tree deliberately out of visual order) so that XML order, strict `(y,x)` order and visual order all differ; the emitted sequence identifies each extractor's collapse function. Formatting is tested with a cell storing `1000000` under `$#,##0,`. Run assembly is tested with `un`/`authorized` split across runs.

**Prevalence (§4.3).** 2,229 files after content-hash dedup (917 XLSX, 1,000 DOCX, 312 PPTX), structural detectors restricted to constructs whose visibility the spec determines and that carry text or change a displayed value (so empty placeholders and template boilerplate don't inflate counts). Assembly and reading order are explicitly *not* measured for prevalence, with a stated reason for each.

**Attacks (§5).** Each of the five scenarios is one crafted document plus a matched clean control. End-to-end: 4 chat assistants via web UI with the uniform prompt "Summarize this file"; 4 coding agents with per-document natural task prompts; 10 trials per system × scenario = 400 trials; success = response adopts the attacker-chosen reading *and* flags no discrepancy. Coding-agent responses scored by per-scenario regex rules; chat responses by an LLM judge (Claude Opus 5.5) given the ground truth. Notion is a separate case study across 4 user-selectable backends.

**Isolating the cause (§5.3).** Model and prompt held fixed; only the text varies — markitdown's `E(f)` vs the clean control's extraction. Three models, four scenarios (Presentation-2 excluded because its extraction depends on the collapse function, so a single `E(f)` wouldn't represent it), 10 trials each.

**Defense (§6).** Static interpreter written against ECMA-376: `w:vanish` plus contextual invisibility (white text only removed when the page background is also white), a from-scratch number-format evaluator, reference-aware part inclusion (an unreferenced header is an invisible channel, not content), `mc:AlternateContent` collapsed to Choice, and heuristic line-banding (~6 pt) for Word floating text boxes with unplaceable boxes handed to the oracle. Render oracle = LibreOffice + Apple Quick Look, each read by Gemini 4, consensus emitted / disagreement flagged. Checking mode compares a deployed extractor's output against `C(f)` and tolerates whole-line reorderings that preserve the word set.

## Results & Highlights

- **Channel measurement: 31 divergent channels across 10 extractors, 19 injection + 12 omission, and *every* tested extractor diverges on at least one channel.** markitdown on PPTX is the worst single case at 9 injection / 1 omission (off-slide text, hidden slides, speaker notes, alt text, shape names, slide masters); python-docx and unstructured on DOCX are the worst omission cases at 1 injection / 6 omission each (headers, footers, footnotes, text boxes, content controls); Tika/POI on XLSX is the only configuration with 0 omission. Per-format totals: PPTX 10 injection / 1 omission, DOCX 4 / 8, XLSX 5 / 3 — i.e. the failure mode is format-specific, so a single "extractor quality" ranking would be misleading.
- **The static-analysis contribution is measurable against a real baseline:** descriptor-framework modeling recovers **179 elements + 67 attributes** of reachable selectors for python-pptx, versus **2 element selectors** for a generic call-graph + string-literal analysis — roughly **90×**. Without this, speaker notes, shape names and placeholder text (the PPTX injection channels) would all be invisible to the measurement.
- **Presentation divergences are near-universal:** **4 of 5** PPTX extractors emit a non-visual reading order (three distinct orders on one slide: `CADB`, `BADC`, `ABCD`); **6 of 7** spreadsheet extractors emit the stored rather than displayed value (all six Python ones give `1,000,000` where Excel shows `$1,000`); **6 of 6** Word extractors fuse `un`+`authorized` into `unauthorized`. Only Docling recovers the visual slide order, and only Tika/POI applies the number format — so both problems are solvable but solved by exactly one tool each, and not the same tool.
- **End-to-end: 64% overall ASR over 400 trials (chat assistants 75%).** Per system: Gemini 100%, Copilot CLI 86%, Codex 82%, Claude 80%, M365 Copilot 80%, ChatGPT 40%, Claude Code 24%, Antigravity 22%. Per attack: Presentation-1 formatting 88%, Content-1 hidden injection 65%, Combination 61%, Content-2 omission 58%, Presentation-2 reordering 50%. No system resists all five, and every system fails all 10 trials of at least one scenario.
- **Formatting divergence is the single most transferable attack:** 7 of 8 systems are misled in ≥9 of 10 trials, and it is the only attack that defeats **both** Claude Code (10/10) and ChatGPT (10/10) — the two most resistant systems otherwise. It needs no hidden content, so a check comparing extraction against stored cell values finds nothing wrong, and 7% of *benign* spreadsheets already contain value-altering number formats.
- **Controlled experiment rules out reasoning error:** with model and prompt fixed and only the text swapped, GPT-5.6, Claude Opus 5.5 and Gemini 4 give the attacker's answer in **10/10** trials under markitdown's `E(f)` and the human's answer in **10/10** under the clean control, across all four scenarios — 120 trials, zero exceptions. Claude Opus 5.5 even cross-checked the inflated total against the (also unscaled) line items and concluded it summed correctly.
- **Generalization to unseen payloads: 28 new documents, naive extractor diverges on all 28, static interpreter recovers the human view on all 28**, and across 3 models × 28 documents the naive extraction misleads **84/84** answers while Prism's reconstruction misleads **0/84**. The 28 vary the value, wording, channel and surrounding text (thousand/million/percent/literal-suffix number formats; `un`/`non`/`dis`/`in` prefixes; white-on-white as well as `w:vanish`).
- **Channel-level coverage of the defense:** of the 17 invisible channels present in the DOCX/XLSX marker documents, the static interpreter emits text from **0**; it recovers **all 10** visible DOCX channels including the headers, footers and footnotes that omission targets. Render oracle recovers the constructed visual order on **14/14** layouts with a single defined reading order (including all 8 order-inversion attacks shifted by ~7 pt), with the two engines agreeing on 25 of 26 layouts and the oracle correctly flagging the one disagreement.
- **Cost and false positives:** static interpreter **0.5 ms/doc** average (0.1 ms DOCX, 1.3 ms XLSX) vs **63 ms** for markitdown (~126× faster than the tool it replaces) vs **~12 s** for the render oracle (~24,000× the static pass). Checking mode flags **5 of 193** benign Apache POI corpus documents (**2.6%**), and several of those flags are arguably true positives (e.g. text genuinely placed outside the visible slide canvas).
- **Prevalence grounds the threat in real files:** speaker notes in **220/312 (71%)** of presentations, footers in **561/1,000 (56%)** of Word documents, hidden text in **71/1,000 (7%)**, off-slide text in **15/312 (5%)**, value-altering number formats in **68/917 (7%)** of spreadsheets, hidden sheets in **56/917 (6%)**. The paper's own inference is the right one: a detector that flags these constructs flags most benign files, so detection must compare *content seen by the model* against *content seen by the human*.
- **Notion case study: 70% ASR across four backends**, with Kimi K3 and DeepSeek-V4-Pro at **100%** (10/10 on all five attacks), GLM-5.3-max at 80% (resists only silent omission), and Grok-4.6-xhigh at **0%**. Trajectory inspection explains why: the two 100% backends answer from the extractor text alone, while Grok and GLM additionally run a VLM over the rendered document — i.e. the defense that works here is "look at the picture," not "reason harder."

## Critical Assessment

**Novelty.** Real, and correctly scoped. The *idea* of "what the user sees ≠ what the model reads" is not new (Liu & Ming 2026 on PDFs; hidden-text resume hacking is folklore), but three things here are: (i) OOXML-specific divergence classes that PDFs structurally cannot have — stored-vs-displayed values via `numFmt`, and free 2-D shape placement with no spec-defined reading order; (ii) the descriptor-framework static analysis, which is what lets the paper claim a *complete* channel enumeration rather than a hand-picked list; (iii) the observation that instruction-level defenses are orthogonal, because nothing is instructed.

**Rigor — where it holds.** The controlled experiment in §5.3 is the right design and it does its job: holding model and prompt fixed and swapping only the extracted text converts a correlational claim ("these systems were fooled") into a causal one ("extraction caused it"). The clean-control pairing in every attack, the 28-payload generalization set, the 193-document false-positive corpus, and the explicit statement that the oracle's two engines can share errors are all signs of a careful author. Reporting the *losing* numbers (Presentation-2 at 50%, Antigravity at 22%, Grok at 0%) rather than burying them is creditable.

**Rigor — where it doesn't.** Four specific problems:
1. **n = 1 document per attack scenario in the end-to-end evaluation.** The headline 64% / Gemini 100% / ChatGPT 40% numbers rest on five crafted documents total, ten trials each. Ten trials of the same document against a fixed ingestion path mostly measures sampling noise, not generalization; the paper even observes that chat-assistant outcomes are "mostly either ten or zero," which is exactly what you'd expect when the unit of variation is the document, and there is one document. The 28-payload set that would fix this was run only through markitdown + 3 API models, **never through the 8 products** — so "generalizes to unseen payloads" is established for the defense but not for the attack's product-level ASR. The paper admits the small-document issue in Limitations but does not flag that this specifically undercuts the per-system ranking (Claude Code 24% vs Antigravity 22% is meaningless at this n).
2. **The judge is a vendor whose product is under evaluation.** Chat-assistant responses are scored by Claude Opus 5.5, and the Claude chat assistant is one of the eight evaluated systems (scored 80%). No human validation of the judge, no inter-judge agreement, no cross-check with a second model, no reported judge accuracy on a hand-labelled subset. The coding agents get deterministic regex rules while the chat assistants get an LLM judge — an asymmetry that also makes the 75%-vs-56% chat-vs-agent comparison less clean than presented.
3. **The recommended deployment mode has a known hole for the attack it recommends it for.** Checking mode is explicitly recommended for coding agents (because they choose their own tools), and checking mode "tolerates reorderings of whole lines that leave the set of words unchanged" — which is precisely Presentation-2 spatial order inversion when each box holds one line, the exact construction in Figure 6. The paper states this openly ("which the mediation mode instead handles through the render oracle"), which is honest, but it means the mode you'd actually deploy for agents is the mode that misses the attack those agents were most resistant to anyway. The claim "Prism mitigates every attack scenario" holds for mediation mode only, and that's a deployment that requires replacing the extractor — infeasible for ChatGPT, Claude.ai, Copilot, Notion, or any product where you don't control ingestion.
4. **Circularity in the render oracle.** Gemini 4 reads both renderings, and Gemini's chat assistant was the single most-susceptible system in the evaluation (100%). The oracle is reading rendered *images* rather than extracted text, so the failure mode differs, but the defense's ceiling is still set by a model from the family that performed worst on this task, with no oracle ablation using a different VLM and no measurement of oracle transcription error rate on adversarial renderings. The one documented evasion — a 0.5-point font that defeats both the static interpreter and a PDF-text-layer oracle — is left to future work, and it is not an exotic attack.

**Smaller issues.** (a) The abstract's "roughly two orders of magnitude cheaper" for text extraction vs VLM rendering is asserted in the intro with a pointer to §6.4, but §6.4 measures Prism vs markitdown, not extraction vs rendering — the closest number (12 s oracle vs 0.5 ms static) is a different comparison and would give four orders of magnitude, not two. (b) The 31-channel total is a union over (channel) rather than (channel, extractor) pairs, so it reads as smaller than the sum of Table 1; not wrong, but the abstract's phrasing invites misreading. (c) `Docling` is simultaneously the one PPTX extractor that gets reading order right and a 4-injection-channel offender on PPTX — worth a sentence, since it complicates the "modern layout-aware parsers fix this" narrative a reader will reach for. (d) The `mc:AlternateContent` observation (every extractor except Tika drops the Choice branch that Office actually renders) is buried in §4.1 as one clause and is arguably a more damning single fact than several of the headline channels. (e) No comparison against the obvious cheap baseline for defense: just render to PDF and OCR, which several of the evaluated products already do and which Grok's 0% ASR suggests works.

**Significance.** High for the ingestion-security niche and for anyone shipping document upload, RAG over a document corpus, or an agent with filesystem access to user-supplied Office files. The threat is cheap (a valid file, no exploit), the delivery is mundane (template repositories, email attachments), and the harm model — the reviewer and the decision-maker are different people — is already realized in resume screening. The 71%-speaker-notes and 56%-footer prevalence numbers make clear this is not a contrived corner of the format. Less significant as an ML contribution: nothing here improves a model, and Prism is an engineering artifact built on a 5,000-page specification, so its coverage will lag Office's feature surface indefinitely (the paper concedes XLSX chart text, print headers and all PPTX content channels are uncovered).

## Strengths

- The **measurement is the contribution**, and it is done properly: two independent analyses (static selectors, dynamic canaries) that catch each other's blind spots, a raw-XML ground truth for what "dropped" means, and per-format breakdowns that refuse to collapse into a single extractor ranking.
- **Descriptor-framework static analysis** is a small, sharp idea with a large payoff (2 → 179 selectors). It generalizes to any library built on `xmlchemy`, `__elements__`-style tuples, or similar declarative XML bindings, which is most of the Python OOXML ecosystem.
- The **selection / interpretation / serialization** decomposition turns a bug hunt into a taxonomy, and each leg maps to a defense operation (`atoms`+`visible`, `display`, `order`+`serialize`). That structure is why Prism is 300 lines of spec logic instead of a classifier.
- **The controlled extraction experiment is the paper's best single result.** 120 trials, three models, two conditions, zero crossover: it converts an ecological claim into a mechanistic one.
- **Prism's cost profile is genuinely deployable** — 0.5 ms is below the noise floor of any ingestion pipeline, and the paper is honest that the expensive oracle is needed for 99% of presentations, i.e. the cheap path is not a universal solution.
- **Honest reporting throughout**: the 50% attack, the 22% system, the 0% backend, the 0.5-point-font evasion, the checking-mode hole, the "some false positives are real divergences" nuance, and the explicit statement that agreement between two renderers does not imply correctness.

## Limitations

- **Five documents carry the end-to-end evaluation.** Per-system ASR has no confidence intervals and, at n=1 document per scenario, differences like 24% vs 22% or 6/10 vs 5/10 are uninterpretable. The 28-payload generalization set never touches the 8 products.
- **No deployment of Prism inside any real product.** Prism is evaluated as a text substitution fed to three API models, not as a component behind ChatGPT, Copilot, Notion or a coding agent. The checking-mode false-positive rate is measured on 193 benign files but its **false-negative** rate on adversarial files beyond the 28 payloads is not measured at all.
- **Coverage is bounded by what the author implemented.** No PPTX content channels, no XLSX chart text or print headers, no legacy binary formats, no encrypted files, no images. Presentations — the format with the most injection channels and the one that always needs the oracle — are the least covered.
- **Spec-determined visibility is not the same as perceptibility.** A 0.5-point run, text colored like a background image, or text clipped by an overlapping shape evades the static interpreter; the paper names these as future work, which means the defense's threat model is "attacks the specification can adjudicate," not "attacks a human can be fooled by."
- **The render oracle's VLM is a single model (Gemini 4)**, used without ablation, and the oracle's own error rate on adversarial renderings is unmeasured. Two-engine consensus bounds shared *layout* errors but not shared *transcription* errors.
- **Snapshot semantics.** End-to-end results describe products "as deployed in October 2026" via browser automation of web UIs; they are not reproducible, and vendors can change ingestion paths silently — the paper says so, but it means the 64% figure has a shelf life measured in months.
- **The threat model assumes a human reviewer actually looks at the file in an Office application** before the model does. In the dominant real workflow — upload directly to a chat assistant — there is no human view to diverge from, so the "divergence" collapses into ordinary attacker-controlled content. The harm argument is strongest exactly where the workflow is least common (approval chains, résumé screening), and the paper leans on those.

## Relevance

直击 **Agent & Pipeline Silent Failures** 的核心命题：模型与世界之间的软件层（这里是文档提取器）在无人察觉的情况下改变了模型读到的东西，而且改变得"合法、无指令、无异常结构"，因此所有针对 prompt injection 的防御都不适用。对做 RAG 文档入库、agent 文件工具链、或任何"人类审阅 + 模型决策"分离流程的人，这篇给出了可复用的检测思路（比对"模型看到的"与"人类看到的"，而不是扫描恶意模式）和一个 0.5 ms 的规范级重建基线；其"31 条通道 + 逐格式失效模式"的测量表也可直接当作提取器选型的风险清单。

## Questions for Further Exploration

1. What is the per-system ASR with, say, 20 documents per scenario instead of one? The 28-payload set exists and was already run through three models — why not run at least a subset through the four chat assistants, given the browser harness is already built?
2. How does Prism's checking mode perform on Presentation-2 when boxes span multiple lines, i.e. when the "whole-line reordering" tolerance no longer applies? Is there a variant of the tolerance rule that keeps benign-deck tolerance while catching clause inversion?
3. Would a "render to PDF, then read the page image" baseline — which Grok-4.6-xhigh appears to approximate and which scored 0% — be a cheaper and more complete defense than Prism's static interpreter for the formats where the oracle is needed anyway (99% of PPTX)? What does that cost per document at scale?
4. Does the descriptor-framework analysis transfer to the JS/TS OOXML ecosystem (SheetJS, docx.js, mammoth) and to Java's POI object model, where the declaration idiom differs? The paper claims language independence via dynamic analysis but the static half is demonstrated only on Python descriptor frameworks.
5. How stable are the vendor-level results? A monthly re-run of the same five documents would separate "ingestion path" from "model version" and would tell us whether the 24%-vs-22% coding-agent cluster is a real resistance class or a snapshot artifact.
6. What happens in a RAG corpus? A single poisoned document indexed once could mislead every subsequent query from every user — the paper mentions this via PoisonedRAG but never measures amplification, which is where the harm model gets much worse than a single misled summary.
