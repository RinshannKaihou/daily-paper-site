> **一句话总结：** BlockLock 不去掉批处理，而是把"被保护请求所看到的张量几何"钉死——BlockLock-Rows 用定宽行 `[B, W]` 保留全批 prefill 与全批 decode，BlockLock-Pack 用末端锚定打包 `[1, BW]` 加隔离 dummy 段后只抽取目标请求的 KV 做单请求 decode；在 5 个 dense 模型、3 种 GPU、1,336 个条件上把目标序列与 Top-20 logit 的一致率从 padded batching 的 52.59%/35.93% 提升到 100%，代价相对 vLLM 标准路径是 3.6–9.9% 时延，但比 vLLM Batch-Invariant 快 53.5–55.0%。

> **TL;DR:** Batch composition silently changes a request's output because padding and reduction order follow the companions' lengths. BlockLock freezes only the protected request's execution geometry instead of constraining every kernel: BlockLock-Rows keeps a fixed-width row inside a shared `[B, W]` prefill and still decodes all B requests together; BlockLock-Pack packs everything into one `[1, BW]` block with the target anchored at the terminal interval and a dummy filler segment, then decodes the target alone from its extracted KV cache. Across 1,316 single-GPU conditions (Qwen3-8B/14B, Llama-3.1-8B-Instruct, Gemma-3-4B/12B-IT on A6000/A100/H100; 8 datasets from tinyBenchmarks + BFCL v3; B ∈ {1,2,4,8,16}; 10 repetitions) padded batching agrees on only 52.59% of generated-sequence pairs and 35.93% of Top-20 logit traces, while both BlockLock modes reach 100.0% — bitwise, with no custom kernels. At B = 4 on A6000, BlockLock-Rows runs 1312.71 ms vs 4305.75 ms for a CoRun-style serialized-prefill baseline (3.28×, 195.02 vs 59.46 tok/s) and is only 2.5–2.7% slower than unconstrained padded batching; against vLLM Batch-Invariant it cuts total time by 53.5–55.0% and raises throughput by 115.2–122.2%. The catch is that the guarantee is per-deployment: change B, the GPU, or the length-class map and it must be re-validated, and at class width W = 4096 the row scheme actually loses to CoRun.

## 核心贡献

- **把"批导致的不可复现"重新定义为几何问题，而不只是 kernel 问题。** 论文指出 padding、行宽、位置偏移、归约树都随同批请求的长度变化；在 188 条 BFCL 查询的动机性审计里有 2 条查询因为批几何改变而给出了不同的函数调用，在 B = 1 且固定种子的情况下默认 cuDNN SDPA 后端也能产出 2/4、3/3、2/3 条不同的序列。
- **BlockLock-Rows：定宽行锁定。** 按对齐粒度 L（默认 64 token）把请求分入确定性的长度类，类宽 W 为 L 的倍数；整批是一个 `[B, W]` 张量，目标占固定行、固定逻辑位置，因此同伴的内容和长度怎么变，kernel 看到的形状都不变。不需要段间 mask，注意力代价是 O(BW²)，且**保留全批 decode**。
- **BlockLock-Pack：末端锚定打包。** 把同伴 + 隔离 dummy 段 + 目标拼成 `[1, P]`，目标永远落在固定物理区间 `Ix = [P − Lx, P)`；用 segment-causal mask 做逻辑隔离，prefill 后逐层抽取目标的 KV（全注意力层取末 Lx 个 K/V，Gemma-3 的滑窗层保留可见后缀并恢复逻辑累积长度），随后目标独占 decode。代价是 O(P²) = O(B²W²) 的 mask 与打分开销，收益是 decode 完全不付同伴的账。
- **给出可验证的三条件充分性契约并证明。** C1 规范几何与逻辑隔离、C2 算子/集合通信的重复稳定性、C3 忠实的 cache 交接；附录 A.4 用对生成步 t 的归纳法证明在固定部署元组 d 下目标原始 logit 逐位相同。这不是"我们跑了几次都一样"的经验声明。
- **把后端本身也列为不可复现源。** 论文要求关闭 cuDNN SDPA 与 TF32（保留 FlashAttention-2、Memory-Efficient SDPA、Math SDPA），并给出具体证据：第 280 步一个 logit 从 24.625 变成 24.5，两个候选 token 的排序翻转，之后整条生成路径分叉。
- **在 stock PyTorch 与 vLLM 上实现，不用自定义 kernel、不用 CUDA graph。** 这是相对 batch-invariant kernels（每个算子、每种硬件都要重写）最实质的工程差异。

## Key Contributions

- **Reframes batch-induced nondeterminism as a geometry problem.** Padding width, row offset, position IDs and reduction trees all track the companions' lengths, so a near-tie logit can flip and the rest of the generation diverges. The paper quantifies the effect rather than asserting it: 52.59% pair-weighted sequence agreement for standard padded batching over 1,316 conditions.
- **BlockLock-Rows.** Deterministic length classes of width `W = mL`; one `[B, W]` prefill where the target keeps a fixed row, fixed logical positions and independent row-wise reductions. Batched decode of all B requests is retained and no inter-segment mask is needed, so attention cost stays O(BW²) — linear in B.
- **BlockLock-Pack.** Terminal-anchored packing into `[1, BW]` with an isolated dummy segment absorbing companion-length variation, a segment-causal mask for logical isolation, layer-wise extraction of the target's KV state (including Gemma-3's interleaved sliding-window layers and their `seen_tokens` metadata), and target-only decode at shape `[1, 1]`.
- **A formal per-deployment contract with a proof.** Three sufficient conditions (canonical geometry, repeat-stable arithmetic, faithful cache handoff) and an induction over generation steps showing bitwise-identical raw logits for any compatible companion schedule π.
- **A backend-eligibility finding that stands on its own.** At B = 1, fixed seed, greedy decoding, 320 steps on H100, the default cuDNN SDPA dispatch produced 2/4, 3/3 and 2/3 unique sequences for CoRun, Padded and Rows respectively; after disabling cuDNN SDPA and TF32 all repeated runs collapsed to a single sequence with 100% bitwise raw-logit identity.
- **A measured efficiency point.** Determinism costs 0.5–0.8% over standard PyTorch padded batching and 3.6–9.9% over vLLM STD, versus the >2× penalty of batch-invariant kernels — i.e. the paper argues reproducibility is cheap if you pin geometry instead of arithmetic.

## Methodology

**Problem setup.** One protected target request `x` whose output must be reproducible, plus B − 1 ordinary companions that share the GPU. Standard dynamic batching ties `x`'s padding offset and reduction order to the longest co-scheduled request, so changing the companions changes the numbers.

**Length classes.** Tokenized lengths are bucketed at granularity `L = 64`; adjacent buckets may be merged into deterministic classes with fixed width `W = mL ≥ L`. The class map is frozen for all compared executions. A group of B requests of one class reserves `P = BW` prompt positions.

**BlockLock-Rows.** The group is a single `[B, W]` tensor. Each request occupies a fixed-width row with left padding and a 2-D padding mask; `x` keeps the same row index, row width and logical positions regardless of companion lengths. One prefill invocation processes all rows, and decode proceeds through the ordinary B-request batched KV cache. Because requests are separated along the batch dimension, no dense inter-segment mask is required. The paper notes the contract holds symmetrically for *any* row held fixed, not just a designated one.

**BlockLock-Pack.** Companions, a `D = BW − Lx − Σ Lf` token dummy segment, and `x` are concatenated into `[1, P]`. Each real segment gets reset local position IDs `0..Li−1`; a segment-causal additive mask (`0` if same segment and `v ≤ u`, else `dtype_min`) enforces segment-local visibility. A single forward pass yields the packed KV cache and the target's logits at position `P − 1`. Then `ExtractTargetKV` slices the terminal `Lx` K/V entries per layer for full-attention layers, and for sliding-window layers keeps the visible target suffix while restoring `seen_tokens = Lx`. Decode then runs at `[1, 1]` with positions `Lx + t` on the isolated cache. The paper is explicit that batch-decoding companions after unpadded KV extraction would re-expose the decode kernel to variable `Lf` and break C1 — padding all KV back to W just reduces to Rows.

**Contract and proof.** Deployment tuple `d = (Hardware, Software, Precision, BackendPolicy, ClassMap, B, L, Primitive, TPConfig)`; each GPU architecture is a distinct `d`. Conditions C1–C3 plus deterministic argmax give bitwise-identical `Lt(x; Θ, d, π)` for all `t ≥ 0`, proved by induction (base case prefill, inductive step decode). Backend policy: `allow_tf32 = False` for matmul and cuDNN, `enable_cudnn_sdp(False)`.

**Tensor parallelism.** Rank 0 constructs and broadcasts the canonical plan (token IDs, padding/segment masks, position IDs); all ranks hash-verify the received plan and sharding topology before the forward pass, so column- and row-parallel layers issue an identical collective sequence. C2 is extended to require repeat-stable NCCL collective algorithms under fixed shapes.

**vLLM integration detail.** For Rows, the adapter builds a flattened `BW`-token input with `W − Li` left-pad tokens per request, sets all padding positions to `SlotMapping = −1` so they never allocate or write PagedAttention KV blocks, keeps `seq_lens[i] = Li` and local RoPE positions, pins attention bounds, disables Split-KV, and replays captured CUDA graphs. This decoupling of prefill query padding from decode KV storage is the non-obvious engineering step.

**Evaluation protocol.** Companion-perturbation: for each target, B, dataset and platform, 10 repetitions each with a distinct randomly sampled companion tuple from the same length class → `C(10,2) = 45` pairwise comparisons per condition, 60,120 pairwise comparisons per scheme over 1,336 conditions. Metrics: generated-sequence agreement `Aseq` (pair-weighted over multiplicities, Eq. 7), Top-20 logit-trace agreement requiring identical candidate IDs *and* identical 16-bit BF16 raw-logit bit patterns at every step, plus SHA-256 over the full-vocabulary logit tensor for the 80-condition vLLM/PyTorch benchmarks. Hardware: A6000 (single + TP=2), A100 80GB, H100 NVL (including MIG 3g.47gb slices). Stack: Python 3.11, PyTorch 2.11.0+cu128, Transformers 5.13.0, vLLM with native BI support, CUDA 12.8, cuDNN 9.19, BF16, greedy, `B ∈ {1,2,4,8,16}`.

## Results & Highlights

- **Determinism, at scale.** Over all 1,316 single-GPU conditions (5 models × 3 GPUs × 8 datasets × B ∈ {1,2,4,8,16}, T = 500 generated tokens), standard padded batching reaches **52.59% pair-weighted generated-sequence agreement and 35.93% Top-20 raw-logit agreement**, while CoRun, BlockLock-Rows and BlockLock-Pack all reach **100.0% on both**. Per-configuration spread is wide: padded batching is worst on A6000/Gemma-3-4B-IT (40.4%) and best on A6000/Qwen3-8B (62.9%), so the damage is model- and hardware-dependent rather than a constant.
- **Tensor parallelism.** On 2×A6000 with Gemma-3-4B (TP=2), padded batching degrades from 100% at B = 1 to **72.4%, 43.6% and 21.8%** at B = 2, 4, 8, while both BlockLock modes hold 100% across all 20 TP conditions. This is the sharpest single number in the paper: at B = 8 fewer than one in four companion-perturbed run pairs reproduces.
- **Versus serialized prefill (CoRun-style), B = 4, A6000.** Qwen3-8B: **1312.71 ms vs 4305.75 ms (3.28×)**, 195.02 vs 59.46 tok/s. Qwen3-14B: **1913.56 ms vs 5983.14 ms (3.13×)**, 133.78 vs 42.79 tok/s. The price against *unconstrained* padded batching is **2.5–2.7%** (1280.58 ms → 1312.71 ms; 1863.16 → 1913.56). Phase split shows where the win comes from: prefill 76.58 vs 66.99 ms (shared `[B, W]` invocation) and decode 1236.13 vs 1213.59 ms (no 256-slot envelope).
- **Versus vLLM Batch-Invariant, B = 4, 8 datasets.** BI pays **+117.5% to +149.5%** over vLLM STD (e.g. MMLU/Qwen3-8B 2032.84 vs 871.32 ms, +133.3%; BFCL v3/Qwen3-14B 3258.17 vs 1497.90 ms, +117.5%), whereas vLLM Rows pays only **+3.6% to +9.9%** (Qwen3-8B) and **+4.0% to +7.2%** (Qwen3-14B). That yields the headline **53.5–55.0% lower total execution time and +115.2–122.2% throughput** relative to BI.
- **Native PyTorch overhead.** Torch Rows adds **0.5–0.8% geometric-mean latency over Torch Padded** across the eight-dataset benchmark at B = 4 and 64 output tokens per request; Torch Pack reaches 1.11 s vs Torch Padded 1.22 s on Qwen3-8B when only the target's 64 tokens are needed (vLLM: Pack 0.89 s vs Rows 0.91 s).
- **Where it loses.** Table 3 shows the crossover honestly: at class width **W = 4096 with T = 2048 output tokens, Rows takes 141.141 s versus CoRun's 135.103 s (+9.0% over Padded's 129.529 s)** and at W = 4096/T = 128, 9.176 s vs CoRun 9.016 s (+12.1%). Rows wins big only at narrow classes (W = 1024/T = 128: 3.761 s vs CoRun 8.472 s, +6.2% over Padded) and on BurstGPT's 4-request group (1.198 s vs 4.175 s, +2.1%). On the Blazedit group Rows is +43.5% over Padded (3.061 vs 2.133 s) — the one place where the protection is genuinely expensive.
- **Backend audit, B = 1, H100, Qwen3-8B, 117-token prompt, 320 greedy steps.** Default policy gives **2/4 (CoRun), 3/3 (Padded) and 2/3 (Rows) unique sequences**; the restricted policy gives **1/4, 1/3, 1/3 with 100% raw-logit bit match** across all 320 steps. Nsight Systems confirms cuDNN SDPA sits on the divergent path.

## Authors & Credibility

Xiuyuan Qi and Shanshan Liu are at the University of Electronic Science and Technology of China (UESTC, Chengdu); Liu is the corresponding author. Pedro Reviriego and Javier Conde are at Universidad Politécnica de Madrid. Qi and Reviriego share equal contribution.

The UPM group (Reviriego, Conde) has a sustained track record in exactly this niche — fault tolerance, error detection in arithmetic circuits, and more recently LLM numerical reliability — and one of the cited works, "Beyond reproducibility: token probabilities expose large language model nondeterminism" (Fu, Martínez, Conde, Arriaga, Qi, Liu, Reviriego, IEEE Transactions on Computers, 2026), is from the same collaboration and supplies the conceptual framing here. The measurement discipline in this paper reflects that background: bit-level comparison rather than string matching, SHA-256 over full-vocabulary logits, and a phase-instrumented timing methodology using `torch.cuda.Event(enable_timing=True)`.

That said, this is a systems paper from a group whose primary identity is numerical reliability rather than serving-systems engineering, and it shows in places: the baselines are reimplementations (a "CoRun-style" baseline rather than CoRun itself, a vLLM adapter written for this paper), the workload is a controlled fixed-target audit rather than a serving trace, and the artifact is withheld ("Omitted for double-blind review"), so neither the vLLM adapter nor the `SlotMapping = −1` trick can be inspected. The paper reads as a submission under review (34 pages with appendices, double-blind). Citation hygiene is good — He & Lab (Thinking Machines), LLM-42, CoRun, Vosti, Prepacking, BucketServe are all engaged with substantively rather than name-dropped.

## Critical Assessment

**Novelty.** The core insight — freeze the shape the kernels see, not the arithmetic — is a real and useful reframing, and it is different in kind from batch-invariant kernels rather than a weaker version of them. But the intellectual distance from prior work is shorter than the framing suggests. Prepacking (Zhao et al., AISTATS 2025) already packs variable-length prompts into fixed blocks; BucketServe already buckets by length to control padding; CoRun already argues that padding-based isolation is the practical route to determinism. BlockLock's contribution is the specific combination "fixed-width row / terminal anchor + frozen class map + backend eligibility gate", which is a genuine engineering contribution but not a conceptual leap. The terminal-anchoring trick in Pack is the most original piece, and it is also the piece with the worst asymptotic behavior.

**Rigor — the good.** The determinism measurement is unusually strong for this literature. 1,336 conditions, 10 repetitions, 45 pairs per condition, 60,120 pairwise comparisons per scheme, and agreement defined at three levels of strictness (token IDs, Top-20 raw-logit *bits*, full-vocabulary SHA-256). Reporting per-configuration padded-batching agreement that ranges from 40.4% to 62.9% rather than a single pooled number is the right call, and it exposes that the phenomenon is hardware- and model-dependent. The C1/C2/C3 decomposition is correct, the induction proof is valid, and — importantly — the paper states the contract as *conditional* rather than claiming unconditional determinism.

**Rigor — the problems.** Several are serious enough to change how the headline numbers should be read.

1. **The 53.5–55.0% headline is inherited, not earned.** Table 2 shows vLLM BI at +117.5% to +149.5% over vLLM STD. Any method that avoids BI's per-operator constraints will look ~2× faster than BI. Against the honest baseline — vLLM STD, i.e. the thing people actually deploy — BlockLock-Rows is **3.6–9.9% slower**, not faster. The abstract leads with the flattering comparison and buries the 3.6–9.9% in a subordinate clause. That is a framing choice, not a misstatement, but it is the kind of framing that gets quoted without the caveat.

2. **The 3.28× versus CoRun is measured against a badly tuned CoRun.** The baseline's decode uses a fixed 256-slot envelope while B = 4, so 252 of 256 slots are masked padding that is still computed (the paper's own Figure 2 makes this point). The paper concedes that "CoRun's graph capacity is configurable: 256 matches its evaluated maximum concurrency", but never re-runs CoRun with a 4-slot envelope. Since CoRun's whole thesis is padding-based isolation, giving it a 64× over-provisioned envelope and then reporting a 3.28× win conflates BlockLock's real advantage (shared prefill) with a baseline configuration error. The prefill numbers alone — 76.58 vs 91.55 ms — suggest the true shared-prefill advantage is ~16%, and the rest of the 3.28× comes from decode slot waste. The paper half-admits this ("this comparison does not isolate the cost of serialized prefill") but still headlines 3.12–3.28× in the introduction.

3. **The "0.5–0.8% overhead" claim lives on a backend nobody serves on.** Torch Padded is 1.22 s versus vLLM STD's 0.85 s on Qwen3-8B — the PyTorch baseline is ~43% slower than the vLLM one. So "near-zero overhead over standard batching" means "near-zero overhead over a slow standard path". The production-relevant number is the 3.6–9.9% against vLLM STD, and that is the one that should be in the abstract.

4. **The cost of the backend policy is never measured.** C2 requires disabling cuDNN SDPA and TF32. On Hopper, cuDNN's fused attention is frequently the fastest available path, and TF32 off costs matmul throughput on Ampere. This policy applies to *every* request in the deployment, reproducible or not — structurally the same complaint the paper makes about batch-invariant kernels constraining all requests. Yet no table reports throughput with the default backend versus the restricted policy. It is entirely possible that the restricted-policy tax exceeds the 3.6–9.9% BlockLock tax, in which case the paper's central efficiency claim is understated in the wrong direction — or, worse, that a large part of the "BI is 2× slower" gap is itself attributable to backend restrictions both methods share. Either way, the omission is the single biggest hole in the evaluation.

5. **No memory numbers at all.** The native PyTorch Pack path materializes a dense `[1, 1, P, P]` mask. At W = 4096, B = 4, P = 16,384, that is 16,384² entries — roughly 0.5 GB in BF16 for a single prefill, before activations (my arithmetic, not the paper's). The paper says the vLLM path replaces this with PagedAttention block tables "substantially reducing prefill overhead" but reports no peak-memory comparison for either implementation. For a method whose selling point is deployability on stock frameworks, that is a conspicuous gap.

6. **Seeded sampling is asserted, not evaluated.** The contract is stated for greedy decoding, and the paper says seeded sampling "fits the same design with request-local random-number state, the technique that CoRun uses". Every experiment is greedy. But RL rollout generation — one of the two motivating use cases in the introduction — samples by default, and request-bound RNG interacts with the geometry contract in ways that deserve measurement (e.g. whether the RNG stream stays aligned when a target's decode is isolated in Pack but batched in Rows).

7. **Thin evidence where it matters most.** TP is the regime where reduction trees and NCCL algorithm selection are most fragile, and the paper tests exactly one TP configuration (Gemma-3-4B, TP=2, 20 conditions). No TP=4/8, no NVLink-versus-PCIe contrast beyond a passing mention, no MoE. The 100% TP result is encouraging but is one model on two GPUs.

8. **The workload is a controlled audit, not serving.** The paper is candid — "our fixed-group timings do not measure queueing or tail latency" — but the consequence deserves more weight: BlockLock reserves `P = BW` positions per group, so under low occupancy the padding waste is exactly the problem the paper criticizes CoRun for. The Blazedit and BurstGPT entries are one hand-picked four-request group each, not arrival-trace replays, and Blazedit is precisely where Rows costs +43.5% over Padded. A reviewer should ask what the padding waste looks like at realistic occupancy distributions.

9. **The title overclaims relative to the contract.** "Reproducible LLM Inference" implies the property users want; the delivered property is reproducibility *conditional on a frozen deployment tuple*, and outputs still differ across batch sizes. Table 4 states this clearly, and the paper never hides it, but the title and abstract do not carry the qualifier. For an evaluation harness comparing two models, "reproducible at B = 4 on this A100 with this class map" is usually enough — but it is a weaker guarantee than batch invariance and should be named as such up front.

10. **Minor.** Section 4.2 says Figure 4(a,b) covers "three hardware platforms, five models" but the per-configuration condition counts are uneven (105–160 per row, with A6000/Qwen3-14B at 105 and no A100/Gemma entries), so the pooled 52.59% is not a balanced design — the paper reports it as pair-weighted but does not discuss the imbalance. Also, the abstract's "five dense models and three single-GPU deployments" omits that the strongest evidence (100% across all conditions) is partly a consequence of the contract being *defined* to hold only within a deployment, which makes the 100% less surprising than it reads.

## Strengths

- **The reframing is genuinely useful.** "Pin the geometry, not the arithmetic" is a one-sentence idea that a serving engineer can act on, and it dissolves the apparent trade-off between reproducibility and batching rather than just quantifying it.
- **No custom kernels.** This is the practical barrier that has kept batch-invariant kernels out of production, and BlockLock sidesteps it entirely — stock PyTorch, stock vLLM, no CUDA graphs required. The `SlotMapping = −1` decoupling of prefill query padding from decode KV storage is a neat, reusable trick.
- **Measurement quality.** Three levels of agreement strictness, 60,120 pairwise comparisons, SHA-256 full-vocabulary verification, and per-configuration reporting instead of a pooled average. This is well above the norm for determinism claims.
- **The B = 1 backend finding is independently valuable.** That cuDNN SDPA breaks repeatability at batch size 1 with a fixed seed, pinned to a specific logit flip (24.625 → 24.5 at step 280), is a concrete datum for anyone debugging "why did my eval change between runs" — and it holds regardless of whether anyone adopts BlockLock.
- **Honest reporting of the failure regime.** Table 3's W = 4096 rows, where Rows loses to CoRun, are in the paper. So is the admission that the CoRun comparison does not isolate serialized prefill. Many papers would have dropped both.
- **A clean formal contract.** C1/C2/C3 are stated precisely enough to be falsifiable, the proof is short and correct, and the deployment-validation checklist in Appendix D turns the contract into an operational procedure — including the honest warning that "passing the canary alone does not establish Condition C2 for other dispatches".
- **Good positioning.** Table 4 is a fair qualitative comparison against BI, LLM-42 and CoRun, and the paper correctly identifies itself as complementary to Vosti's formal verification rather than competing with it.

## Limitations

- **Per-deployment, not universal.** Changing GPU architecture, TP degree, framework version or the length-class map invalidates the guarantee and requires re-validation. Outputs are not comparable across batch sizes.
- **Dense models only.** No MoE; the authors flag that capacity-factor token dropping in MoE routing would induce cross-request interference that the current contract does not cover.
- **Padding waste under variance.** When companion lengths vary widely inside a coarse class, reserved capacity is wasted — visible as the +9.0% to +12.1% regressions at W = 4096 in Table 3. Long prompts push requests into wider classes, increasing waste for the whole class.
- **Pack scales quadratically.** The dense segment mask costs O(B²W²) in native PyTorch; the vLLM path avoids materializing it but no memory figures are given for either.
- **Pack protects only the terminal request.** Protecting several prompts needs one pack per prompt, i.e. multiple prefill passes — so Pack is a low-concurrency / single-audit tool, not a general serving mode.
- **Greedy only in practice.** Seeded sampling is argued to fit but is not measured.
- **No queueing, no tail latency, no occupancy sweep.** The evaluation is a fixed-group audit protocol; real serving behaviour under dynamic arrival is out of scope.
- **Not integrated with chunked prefill or prefix caching**, both of which would perturb the frozen geometry and are listed as future work.
- **Backend-policy cost unquantified** and **no memory measurements** — the two largest measurement gaps.
- **Artifact withheld**, so the vLLM adapter and the KV-extraction code cannot be checked.

## Relevance

这篇直接落在"Inference Reliability & SDC Detection"的核心议题上：它证明**输出不可复现的根源不只在模型，而在服务栈的张量几何与 kernel 调度**，并且给出了一个可操作的量化基线（padded batching 只有 52.59% 的序列一致率）。对关注"同一次评测/同一条 rollout 换一批请求就变答案"这类静默失效的读者，它提供了从病因（cuDNN SDPA、TF32、padding 偏移）到处置（几何锁定 + 后端资格门禁 + 部署校验清单）的完整链条，其中 B = 1 下固定种子仍不可复现的发现尤其值得单独引用。

## Questions for Further Exploration

1. What is the throughput cost of the restricted backend policy (no cuDNN SDPA, no TF32) relative to the default backend, holding everything else fixed? If it exceeds 10%, the paper's efficiency argument needs restating.
2. How does CoRun perform with a decode envelope matched to B = 4 instead of 256 slots? The 3.28× claim is only meaningful once that baseline is re-tuned.
3. Does the contract survive seeded sampling in practice, particularly for Pack where the target's decode runs at `[1, 1]` while companions were prefilled in a shared block? Does the RNG stream stay request-bound across that transition?
4. What happens at realistic occupancy — say a Poisson arrival process with mean concurrency 2–3 — where `P = BW` reservation is mostly waste? Does BlockLock still beat CoRun, or does the crossover in Table 3 migrate to smaller W?
5. Peak memory for the native PyTorch Pack path at W = 4096, B = 8: the dense mask alone would be ~2 GB in BF16. Is Pack usable at all outside the vLLM integration?
