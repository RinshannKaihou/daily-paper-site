> **一句话总结：** 在 OJBench 的 115 道 Easy/Medium 竞赛题上，对 Qwen2.5-Coder（7B/14B/32B）与 Devstral-Small-2507 做 W4A16 AWQ/GPTQ 量化后，三个随机种子下没有任何配置出现统计显著的准确率下降（最大名义跌幅为 Qwen-32B 的 AWQ 13.91%→10.72%，Holm 校正后 pHolm=0.21）；但量化彻底改变了智能体的解题轨迹——Qwen-7B 的一次性解出从 17 题塌陷到 0 题（AWQ），而带执行反馈的循环解出从 10 题升到 25 题（Fisher pHolm<0.001）。

> **TL;DR:** On OJBench (115 Easy+Medium NOI/ICPC problems, 3 seeds, Python-only, 5-call execution-feedback agent), 4-bit W4A16 AWQ and GPTQ applied to Qwen2.5-Coder-7B/14B/32B and Devstral-Small-2507 produce **no statistically significant accuracy loss versus BF16** after Holm correction across eight comparisons — the largest nominal drop is Qwen-32B under AWQ (13.91% → 10.72%, Δ=3.19 pts, raw McNemar p=0.027, pHolm=0.21, problem-level p=0.051). The interesting result is behavioral: Qwen-7B's one-shot solves collapse from 17 to 0 under AWQ and 3 under GPTQ while loop-based solves rise from 10 to 25/20 (Fisher pHolm<0.001/0.003, problem-level p=0.005/0.022, and 8/8 previously one-shot-solved problems flip to loop solves, p=0.008), and Devstral's failure profile shifts significantly from Invalid Return toward Wrong Answer/TLE (chi-square pHolm=0.011/0.009). Read this if you deploy quantized coding agents and currently judge them by pass rate alone; skip it if you want efficiency numbers, because the paper measures none.

## 核心贡献

- **首个针对"执行反馈式编码智能体"的 4-bit 权重量化实证研究**：以往量化-推理研究只看单轮输出，本文把评估对象换成"写代码 → 调 `python_executor` 测试 → 读反馈 → 改代码"的多轮闭环智能体，覆盖 Qwen2.5-Coder-Instruct 7B/14B/32B 与 Devstral-Small-2507（24B）三个规模档加一个跨家族对照。
- **提出"准确率之外"的三维评估框架**：最终准确率（RQ1）、解题轨迹（one-shot vs. loop-based、工具调用率、平均执行调用次数，RQ2）、终止失败类型分布（IR/WA/TLE/CE/MLE，RQ3）。
- **发现"准确率不变但行为大变"的解耦现象**：Qwen-7B 在 AWQ 下准确率仅从 7.83% 降到 7.25%（不显著），但一次性解出从 17 题归零、循环解出从 10 题涨到 25 题；也就是说同一个分数背后是完全不同的解题机制。
- **揭示不同模型有各自的"工具使用体制"且量化对其扰动不均匀**：Qwen-32B 在 BF16 下就 100% 依赖工具（0 次 one-shot），量化后仍如此；Qwen-14B 大致对半；Qwen-7B 被推向循环式；Devstral 在 GPTQ 下几乎退化为纯 one-shot（19 次成功全部无工具调用）。
- **给出量化会重塑失败谱系的证据**：Qwen-32B 的编译错误率远高于小模型（BF16 13.3% vs. Qwen-7B 1.3%），量化后进一步升到 17.7%/20.7%；Devstral 的失败则从运行时异常（IR 53.3%）显著转向错误答案与超时（WA 44.7%→51.0%/51.7%，TLE 7.0%→10.0%/14.3%）。
- **统计方法上的克制**：八个 BF16-vs-量化比较全部做 Holm 校正，并把"三个种子同属一题"的相关性显式处理——用 115 道题为单位的 cluster bootstrap（20,000 次重采样）与题内标签置换检验复核。

## Key Contributions

- **First empirical study of 4-bit weight-only quantization inside execution-feedback coding agents.** Prior quantization-and-reasoning work evaluates single-pass generations; this paper evaluates a multi-turn agent with a real Python executor, five tool calls per problem, and official OJBench judging.
- **A three-axis evaluation protocol beyond final accuracy**: accuracy (RQ1), solution trajectory — one-shot vs. loop-based solves, valid tool-use rate, mean executor calls (RQ2) — and terminal failure taxonomy over IR/WA/TLE/CE/MLE (RQ3).
- **Demonstrates accuracy/behavior decoupling.** Qwen-7B's overall accuracy moves 7.83% → 7.25% (not significant) while its solve mechanism inverts: 17 one-shot solves become 0, and 10 loop solves become 25.
- **Shows quantizers perturb each model's tool-use regime differently**, so there is no single "quantization effect" to report: Qwen-32B stays fully loop-dependent, Qwen-14B stays balanced, Qwen-7B is pushed toward looping, Devstral collapses toward one-shot.
- **Quantifies failure-mode reshaping**: Devstral's failure distribution shift is significant under both quantizers (chi-square pHolm = 0.011 AWQ, 0.009 GPTQ), while Qwen models' shifts are not.
- **Statistical hygiene unusual for a workshop paper**: Holm correction across eight comparisons, exact McNemar on 345 paired observations, plus problem-level cluster bootstrap and within-problem permutation tests to handle seed correlation.

## Methodology

**Benchmark.** OJBench, 232 competition problems from China's National Olympiad in Informatics (NOI) and ICPC. Only the 115 Easy+Medium problems are used because every model–precision configuration scored 0% on the Hard split. Python is the only solution language (OJBench also supports C++). Three seeds ⇒ 345 problem–seed observations per configuration. Accuracy = fraction of final programs passing all official test cases.

**Models and quantization.** Qwen2.5-Coder-Instruct at 7B, 14B, 32B (in-family scaling axis) plus Devstral-Small-2507 at 24B (out-of-family, agent-oriented comparison). Each is run at BF16 and as W4A16 AWQ and GPTQ produced with `llmcompressor` (256 calibration samples, max sequence length 1,024). Weight-only, so activations stay high precision. Reported storage saving: ≈3.4×.

**Agent scaffold.** vLLM serving, OpenAI-compatible tool schema, a single tool `python_executor(code, stdin)`, 30 s execution timeout, at most five tool calls per problem (K=5), nucleus sampling at temperature 0.6 / top-p 0.9, 32,768-token context. The system prompt walks the model through read → write → build test input from the examples → call the executor → compare → fix → emit final code block. Tool calls are parsed from generated text; outputs are truncated to 2,000 characters; when the call budget is hit the model gets one extra user turn asking for the final solution. Algorithm 1 (Appendix A.4) gives the full loop. Two disclosed harness quirks: the budget is checked once per *turn* rather than per call, so ~10% of attempts exceed K; and when context overflows, the oldest assistant/tool messages are dropped.

**Metrics.** Beyond accuracy: one-shot solves (zero tool calls) vs. loop solves (≥1 execution round); "used tool" = share of problems with at least one *valid* executor call; "tried tool" additionally counts schema-violating calls (broken JSON, tool invoked as a plain Python function); "malformed" = share of all tool calls violating the schema; mean calls per problem.

**Statistics.** Outcomes are paired (same problem, same seed), so accuracy is tested with an exact two-sided McNemar test on the 345 pairs, reporting discordant counts b (BF16-only solves) and c (quantized-only solves), with Holm correction across the eight comparisons. Behavioral measures use Fisher's exact test (solve path, tool use) and chi-square (failure distribution, MLE excluded for low counts), also Holm-corrected. Because seeds are correlated, the paper repeats everything at the problem level: 95% CIs from a cluster bootstrap over 115 problems (20,000 resamples, all three seeds of a problem kept together) and p-values from a permutation test that swaps precision labels within each problem.

## Results & Highlights

- **No accuracy loss survives correction, but the headline number is the 32B drop.** On OJBench Easy+Medium (115 problems, 3 seeds), Qwen-2.5-Coder-32B falls from **13.91%±2.3 (BF16) to 10.72%±1.8 (AWQ) and 11.01%±0.5 (GPTQ)** — Δ=3.19 and 2.90 pts. The raw paired McNemar is p=0.027 (b=16, c=5) for AWQ, but **pHolm=0.21**; at problem level Δ=3.19 with 95% CI [0.58, 6.09] and permutation p=0.051. This is the paper's strongest signal and it lands just on the wrong side of the threshold.
- **Smaller models barely move.** Qwen-7B: 7.83%±0.9 (BF16) → 7.25%±0.5 (AWQ) → 6.67%±1.0 (GPTQ), i.e. Δ=0.58/1.16 pts, McNemar p=0.79/0.39. Qwen-14B: 11.30%±0.0 → 9.28%±0.5 (AWQ) → 9.86%±2.7 (GPTQ), Δ=2.03/1.45 pts, p=0.065/0.27. Eight BF16-vs-quantized comparisons, zero significant after Holm.
- **Devstral nominally *improves* under quantization.** 4.64%±1.3 (BF16) → **6.09%±2.6 (AWQ)** → 5.51%±1.3 (GPTQ); the paired test gives Δ=−1.45 pts (i.e. AWQ solves more) with p=0.36 and b=7/c=12. A 1.45-pt "gain" from 4-bit weights is not a capability finding — the ±2.6 std swallows it — but it is a useful reminder of how noisy 5–7-solve regimes are.
- **Qwen-7B's solve mechanism inverts under AWQ.** One-shot solves: **17 (BF16) → 0 (AWQ) → 3 (GPTQ)**; loop solves: **10 → 25 → 20** (345 attempts each). Fisher's exact test p<0.001, pHolm<0.001 (AWQ) and pHolm=0.003 (GPTQ). Problem-level permutation test confirms it (p=0.005 AWQ, p=0.022 GPTQ). On the subset of problems solved by *both* precisions, **8 of 8 BF16 one-shot solves become loop solves under AWQ (p=0.008)**, and 7 of 8 under GPTQ (p=0.070). This within-problem control is the cleanest evidence in the paper.
- **Tool-use regimes are model-specific and are not preserved.** Qwen-32B uses the tool on 71.3% of problems at BF16 (63.8% AWQ, 67.0% GPTQ) and produces **zero one-shot solves at any precision** (48/37/38 loop solves); Qwen-14B sits at 31.6% tool use with a near-even 21 one-shot / 18 loop split; Qwen-7B moves 66.7% → 73.9% → 69.0% while its *solve path* changes drastically — tool-use rate and solve path are clearly different quantities.
- **Devstral's tool calling is largely broken at the schema level, and quantization makes it worse.** "Tried tool" drops 42.0% (BF16) → 27.0% (AWQ) → 21.4% (GPTQ), both significant after Holm (pHolm<0.001); valid "used tool" drops 8.7% → 8.4% → 1.2%; **malformed calls rise from 76.9% to 96.5%** under GPTQ, and mean executor calls fall from 0.11 to 0.01. All 19 GPTQ successes are one-shot.
- **Failure profiles diverge by model rather than converging on one pattern.** Qwen-32B produces far more Compilation Errors than the 7B model at BF16 (**13.3% vs. 1.3%**), rising to 17.7% (AWQ) and 20.7% (GPTQ) — not significant (pHolm=0.97/0.75) but large in absolute terms. Qwen-7B's AWQ shift from WA toward IR (WA 65.0→59.7, IR 21.7→29.0) is *not* significant (pHolm=0.84). Devstral's shift is: IR 53.3→37.3/39.3, WA 44.7→51.0/51.7, TLE 7.0→10.0/14.3, chi-square p=0.002/0.001, **pHolm=0.011/0.009**.

## Authors & Credibility

Four authors: Areej Mehboob, Muhammad Usman Qadeer, and Hamza Farooq at **Traversaal AI** (an applied AI startup), and **Muhammad Ali Shafique at Kansas State University**. Shafique also appears on the DSBC data-science benchmark paper cited in related work, so there is prior benchmark-construction experience in the group; Farooq is a co-author on the same line of work. The venue is the **NeurIPS 2026 workshop "SLMs for Agentic Systems"** (Paris), and the paper is written to workshop length (~10 pages including appendices) — the scope, the single-benchmark design, and the modest absolute numbers are all consistent with that format rather than with a main-track claim. The acknowledgments disclose LLM assistance for language and formatting only, with authors retaining responsibility — a reasonable and increasingly standard statement. The reference list is small but on-point (AWQ, GPTQ, llmcompressor, Qwen2.5-Coder, Devstral, OJBench, the "Quantization hurts reasoning?" study), and the paper positions itself correctly as extending that last line of work from single-pass to agentic settings.

## Critical Assessment

**Novelty.** The framing gap is real and was worth filling: the quantization literature evaluates single generations, while agentic coding is now the dominant deployment mode, and nobody had asked whether the execution loop absorbs quantization error. The specific contribution — measuring solve *path* and *failure type* rather than only pass rate — is a genuine methodological addition, not a rebranding. The finding that Qwen-7B goes 17 → 0 one-shot solves is memorable and, as far as I can tell, new.

**The central inferential problem is power, not correctness.** The "no significant loss" claim rests on eight null results obtained where BF16 accuracy is 4.6%–13.9%, i.e. **5 to 16 solved problems out of 115**. With ~15 successes, McNemar's discordant counts are b=8/c=6 or b=9/c=2 — the test simply cannot distinguish "no effect" from "a 3-point drop", and a 3-point drop is exactly the size the authors themselves flag as the largest observed. This is absence of evidence presented in the grammar of evidence of absence. The right instrument is an equivalence test (TOST) with a pre-declared margin — say ±2 pts — which would either license the "practical for deployment" conclusion or refuse it. As written, the conclusion "4-bit quantization appears practical for execution-feedback coding agents" outruns the design.

**Internal tension around the 32B result.** The paper correctly reports pHolm=0.21 and p=0.051, but also reports a cluster-bootstrap CI of [0.58, 6.09] that *excludes zero*, then describes the result as borderline in a footnote. A CI excluding zero and a p of 0.051 are not contradictory (different procedures), but the paper never reconciles them or says which it believes. Meanwhile the same 32B/AWQ cell shows Easy accuracy 32.41% → 25.93% — a 6.5-pt drop that is much larger than the 3.19-pt overall figure, and is buried in Table 1 rather than discussed. If a practitioner is choosing a quantizer for a 32B coder, that row matters more than the aggregate.

**The missing ablation is the one the paper promises.** The introduction explicitly asks "whether the execution loop absorbs quantization-induced errors." Answering that requires a **single-pass control**: the same models, same problems, same quantizers, no tool access. Without it, the paper cannot separate "the loop absorbs the damage" from "OJBench Easy+Medium is too easy to show damage and Hard is at 0% for everyone, so the benchmark has almost no dynamic range." The authors concede the second possibility only in the limitations ("absolute solve counts are modest"), but it is the more likely explanation and it undercuts RQ1's interpretation. A mid-difficulty benchmark (LiveCodeBench, or a HumanEval+/MBPP+ style set where models sit at 60–80%) would have delivered far more statistical power for the same compute.

**The Devstral comparison is confounded and the paper half-admits it.** At BF16, 76.9% of Devstral's tool calls already violate the schema, rising to 96.5% under GPTQ. So "Devstral rarely makes a valid executor call" is substantially a **prompt/tool-format compatibility artifact**, not a statement about the model's agency. The authors do note this ("most of Devstral's tool calls do not follow the tool schema, which keeps its recorded tool use low"), which is honest — but they then still use Devstral as the out-of-family comparison and call its failure-mode shift "the clearest change" in the paper. The shift is statistically the cleanest, yes; whether it reflects quantization or reflects a model whose tool interface was never working is unresolved. A per-model prompt adaptation, or reporting Devstral's results only under a no-tool condition, would have fixed this.

**The efficiency motivation is never measured.** The paper opens on inference cost limiting where agents can run, and closes with a 3.4× checkpoint-storage reduction as the sole efficiency number. There is no latency, no throughput, no tokens/sec, no memory footprint at serving time, no cost per solved problem. For an agent that makes 2–3 executor rounds, the relevant cost is total generated tokens across turns — and the Qwen-7B result (one-shot solves converting to loop solves) means the quantized model does *more* inference work per solved problem. Mean calls stay flat (2.26 → 2.29), so the effect is probably small, but the paper never checks whether the storage win survives contact with the agent loop. For a paper whose premise is cost, that is a conspicuous hole.

**Reproducibility is partial.** Strengths: the full system prompt, the tool description, the five-call budget, the 30 s timeout, the context-trimming policy, and Algorithm 1 are all in the appendix, and two harness quirks (per-turn budget check, ~10% overshoot; oldest-message dropping) are disclosed rather than hidden. Gaps: the **calibration corpus for AWQ/GPTQ is never named** (only "256 calibration samples, max sequence length 1,024"), group size / act-order / damping are unreported, the three seeds' values are unspecified, and no code or artifact link is given. Since quantization quality is highly sensitive to calibration data, this is the single biggest barrier to replication — and it also means a reader cannot tell whether AWQ's odd Qwen-7B behavior is intrinsic or an artifact of a poorly matched calibration set.

**Other specifics worth flagging.** (i) The GPTQ runs use `llmcompressor`'s implementation, which is not bit-identical to the original GPTQ codebase; results are labeled GPTQ but should be read as "GPTQ-as-implemented-in-llmcompressor." (ii) The Hard split contributes literally nothing — 0% for all twelve configurations — yet is described in the setup as part of the benchmark, which slightly inflates the apparent scope. (iii) Table 1's standard deviations are frequently larger than the effects (Qwen-32B AWQ Easy ±5.8 on a 25.93 mean), so several of the "darker shading marks best" cells are noise ordering. (iv) The claim that "quantization can change the type of terminal failure" is supported only for Devstral after correction; the Qwen-7B WA→IR narrative in the text (65.0 → 59.7) reads more confidently than pHolm=0.84 warrants.

## Strengths

- **Asks the right question and answers it with the right instrument.** Solve path, tool-use rate, and terminal failure class are exactly the quantities a deployment engineer needs and exactly the ones pass-rate reporting hides. The 17 → 0 one-shot collapse is a concrete, checkable, and genuinely surprising finding.
- **The within-problem control is well designed.** Restricting to problems solved by both precisions and finding 8/8 one-shot → loop flips (p=0.008) removes the "different problems, different difficulty" confound that plagues most before/after comparisons. This is the paper's best single piece of evidence.
- **Statistical care beyond the norm for a workshop submission.** Holm correction across eight comparisons, exact McNemar on paired observations, plus a cluster bootstrap and within-problem permutation test that explicitly handle the fact that three seeds of a problem are not independent. Most papers at this length would have run a t-test on the means and stopped.
- **Honest reporting of the borderline case.** The 32B/AWQ result is reported with its raw p, its Holm-adjusted p, its CI, and its problem-level p, and labeled not significant. It would have been easy to lead with p=0.027.
- **Disclosure of harness quirks.** The per-turn budget check that lets ~10% of attempts exceed five calls, and the oldest-message-dropping policy on context overflow, are both stated in A.4. Undisclosed harness details are a common source of irreproducible agent results; here they are on the record.
- **Useful negative result for practitioners.** If you are serving a 7B–14B coder agent at W4A16, the accuracy cost is plausibly within noise — that is a real, actionable takeaway even granting the power caveat.

## Limitations

- **Severe statistical underpowering.** With 4.6%–13.9% accuracy on 115 problems, the study has 5–16 successes per configuration; detecting a 3-pt effect is beyond the design, so "no significant loss" is weakly informative. Equivalence testing was not performed.
- **No single-pass control**, so the paper's own motivating hypothesis — that the execution loop absorbs quantization error — is never tested against the alternative that the benchmark is simply too hard to show damage.
- **One benchmark, one language (Python), one scaffold, one bit-width (W4A16).** No FP8, no 3-bit, no activation/KV-cache quantization, no C++ (which OJBench supports), no second harness. Generalization claims are correspondingly narrow.
- **Zero efficiency measurement.** No latency, throughput, memory, or cost-per-solve. The 3.4× storage figure is the only number bearing on the paper's stated motivation, and it ignores that quantized agents may take more turns.
- **Devstral's tool interface never functioned properly** (77–97% malformed calls), making the cross-family comparison largely uninterpretable as a statement about agentic capability.
- **Quantization recipe underspecified**: calibration corpus unnamed, group size / act-order / damping unreported, seed values unspecified, no code release.
- **The Hard split is dead weight** (0% everywhere), shrinking effective benchmark difficulty range and thus effective sample size.

## Relevance

直接命中"极端性能优化下的可靠性"这一关切：论文证明 4-bit 权重量化在编码智能体上可以不掉准确率，却悄悄把解题机制（17 题一次性解出 → 0 题）和失败类型分布改掉——这正是"指标没变但行为已变"的典型精度风险。同时对"Agent & Pipeline 静默失效"也有参考价值：Devstral 的 77%–97% 工具调用不符合 schema，属于 harness 层面被准确率掩盖的静默故障。

## Questions for Further Exploration

1. Would a TOST equivalence test with a ±2-pt margin accept or reject the "no accuracy loss" claim for Qwen-32B? Given a CI of [0.58, 6.09], the answer is probably "reject equivalence," which would flip the paper's conclusion.
2. What happens with a single-pass (no-tool) control on the same problems and quantizers? If quantized single-pass accuracy drops sharply while the agent's does not, the loop really is absorbing error; if both are flat, OJBench Easy+Medium is simply insensitive.
3. Why does Qwen-7B under AWQ lose *every* one-shot solve? Is it a degraded ability to emit a complete correct program in one shot (a capability loss), or a shifted prior toward "test first" (a policy change)? A prompt that forbids tool use would separate these cleanly.
4. Why does Qwen-32B produce 10× the compilation errors of Qwen-7B (13.3% vs. 1.3%)? More complex code, different Python idioms, or longer outputs hitting the 2,000-char truncation? This deserves its own analysis.
5. Does the one-shot → loop shift cost more than quantization saves? Measure total generated tokens and wall-clock per *solved* problem, not per attempt.
6. How sensitive are these behavioral findings to the calibration set? Rerun AWQ with coding-domain calibration data and see whether the 17 → 0 collapse persists.
7. Would per-model prompt/tool-schema adaptation rescue Devstral's tool use, and does its failure-mode shift survive once the tool actually works?
8. Do the same behavioral shifts appear under FP8 or KV-cache quantization, where the perturbation is smaller but applied to activations rather than weights?
