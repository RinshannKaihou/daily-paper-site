Why this matters

When a loop runs for seconds and its pod takes minutes to start, provisioning — not compute — sets your iteration time.

Judge warm pools by tails: p90 start latency drops 59.1 s → 3.5 s.

! Critical edge

02

Four moves that keep the pool usable

One broker per K8s cluster

The reframing is the contribution: warm pooling is a matching problem, not a pre-warming problem. A pod is only warm if the next job can actually use it.

01

Submit an SKU, not an image

A job names a GPU SKU — model, CPU, memory, curated base image, scaling policy — plus an optional content-addressed code package. Durable queue in MySQL; the dispatcher claims in priority order under one lock.

02

Claim in strict preference order

Idle pod last used by this caller → never-used idle pod → zero-VRAM standby on a busy card → brand-new pod. Multi-pod jobs claim all N at once, so no job holds a partial set.

03

Bind late, in sub-second time

Unpack the code zip, install only SHA-pinned dependency deltas, inject torchrun or Ray topology at start. Median 0.40–0.54 s, p99 ≤ 1.45 s — so dozens of environments share one pool.

04

Run, reset, retire at the session edge

Kill the whole process tree and verify via /proc, clear the package dir and /dev/shm, then hand the pod back — owner-only, and only until the reuse tag changes.

Zero-VRAM standby

HAMi + Volcano fractional shares park up to three standby pods on an already-busy card, pinned by GPU UUID. Standbys hold no CUDA context and no memory; the job's memory limit is raised to the full 141 GB in its process environment, never the pod spec.

A per-GPU gate promotes exactly one pod, only after the previous process tree is verified dead.

Queue-driven scaling

Utilization-driven autoscalers shrink exactly when a burst arrives. Firepool scales from queued demand — add = min(need, ceiling − physical, step, headroom) — and counts an active–standby group as one physical GPU in every budget.

Control plane, measured

110k–220k claims/s at 100k tracked pods; 1.5–2.6 µs median lock hold; 483 durable dispatches/s on MySQL. After a kill: 0 lost, 0 duplicated, first claim in 3.0 s.

03

What holds up, what doesn't

Preprint · no external review

Strengths +

  • The reframing is real. “A warm pod is worthless unless the next job can use it” turns pre-warming into matching — and the 64-environment simulation shows the failure it avoids (2.15× vs 1.06× held capacity).
  • Standby is mechanism, not slogan. GPU-UUID pinning, memory raised in the process environment rather than the pod spec, promotion gated on verified process death, group counted as one GPU.
  • The cost side is published. 15% more GPU-seconds, 87% idle hold time, and three keep-alive settings where the long one is worse than always-on.
  • Negative results get equal billing. The ~104 s / ~196 s crossover and the custom-image gap are named, not buried.
  • Unusual statistical hygiene. Williams crossover interleaving, paired bootstrap CIs, pre-registered simulator hold-outs (46/55 in band).

Fault injection is concrete: 30 SIGKILLs, 90/90 holds restored, 0 partial gang claims in 50 jobs.

Limitations −

  • Competitors are argued, not measured. The only real baselines are three arms of Firepool; the fragmentation result tests the authors' model of a rival pool, not a rival.
  • One node carries the headline. All controlled H200 results use a single pinned 8×H200 box with a 2-GPU cap; multi-node and cross-SKU contention are untested at benchmark scale.
  • The ablation is confounded. Reuse Off also swapped the event-driven dispatcher for a tick-driven one; no clean re-run is reported.
  • No fleet economics. 94.7% counts requests, not GPU-hours; there is no fleet utilization, queue-time or cost-per-loop figure.
  • Isolation is process-level. A process-tree kill is not a kernel boundary; dependency residue persists and one session's state can reach the next session's first job.
  • Custom images get nothing. They dominate the 8-GPU pools, so the deployed win is the 1-GPU short-job regime, not multi-GPU training.

Verdict from the source: a strong, honest engineering paper weakened by unmeasured baselines and multipliers that depend on very short bodies.
