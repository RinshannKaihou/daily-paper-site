Evidence, method, and the caveats ↓

How it decides

4 steps

LEAP owns one stage of the routing chain: rank candidate accelerators, then let the scheduler resolve that ranking against live capacity.

  1. 01
    Inputs at launch

    73 columns from launch config, 12 hardware specs and the job family's own past throughput. No profiling run, no computation graph.

  2. 02
    13-bin cascade

    Split ln q into 13 equal-frequency bins, fit a pinball-loss GBDT per bin, reassign rows and refit for ≤3 rounds. A bin classifier picks the expert, so serving needs no label.

  3. 03
    Serving

    The artifact embeds history for 250k job families. Any failure returns an empty preference list, which the scheduler reads as “no opinion”.

  4. 04
    Nightly retrain

    Trailing 30 days (~750k attempts), newest day held out, immutable versioned artifact behind a stable pointer.

Cold start is load-bearing: a new accelerator cannot be ranked until it has run real jobs, and one held-out model family costs the cascade 49.7 points (the graph model, 37.0).

What holds up Strengths

  • Scale that cannot be faked: 25k attempts/day, 660 model types, 20+ hardware types, 30 consecutive nightly retrains, six months of telemetry.
  • Uncommon candor: a >20-point overstatement from in-window scoring, a null GNN result, 18 dead features — all reported against interest.
  • A quotable cold-start measurement: −37.0 for a held-out accelerator versus −1.7 for an equal number of random rows.
  • Systems detail that transfers: embedded history snapshots, empty-list degradation, per-model-type rollout switches.

What doesn't Limitations

  • w20 is attempt-weighted. No GPU-hour- or cost-weighted accuracy is reported, so the metric that would match the 3% saving is absent.
  • The 3% is an estimate without a counterfactual, confidence interval, or described method — and coverage itself moved over the same period.
  • Cold start is unsolved. New accelerators are unrankable before they run real jobs; the proposed GNN fallback is a proposal, not a result.
  • Single fleet, no artifacts. No code, data, or benchmark; serving/offline feature skew is disclosed but unresolved.

Open questions

The tests the paper leaves for someone else.

01What is the GPU-hour-weighted w20 — and does the 3% saving survive if the model is optimized for cost instead of attempts?

02How much of the +4.1 architecture gain is memorization? Re-run the ablation with those features removed under model-family holdout.

03What does a trivial baseline get — per-model-type median log throughput, or ridge regression on log features?

04Why does LightGBM trail scikit-learn's GBDT on identical features? A tuning-budget parity check would settle it.

05Would an LLM classifying over the same 13 log bins close the gap, or is the failure about tabular numerics rather than output format?

06Does throughput/cost ranking beat raw throughput ranking — and what are the p50/p99 latencies of a routing call?
