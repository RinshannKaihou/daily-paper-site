> **一句话总结：** 作者手工标注了 FlashInfer、FlashAttention、Triton、CUTLASS、DeepGEMM、xFormers、bitsandbytes 七个 GPU kernel 库的 300 条 GitHub issue（从 9,099 条原始报告中筛出 3,181 条候选，kappa=0.87），得到 6 类症状与 3 个维度下 15 类根因；核心结论是 **60.33%（181/300）的问题根本不发生在 kernel 代码里，而在编译/构建（27.00%）与运行时环境（33.33%）**——部署失败（27.33%）+ 构建失败（24.33%）合计 51.67%，比真正在设备上崩掉/挂住的（Crash 21.00% + Hang 2.00% = 23.00%）多一倍以上，而数值类根因（Incorrect Numerical Computation 2.67%）在人工报告中几乎不可见。

> **TL;DR:** A manual, two-coder (Cohen's κ = 0.87) taxonomy of 300 GitHub issues from seven LLM GPU-kernel libraries (FlashInfer, FlashAttention, Triton, CUTLASS, DeepGEMM, xFormers, bitsandbytes), sampled proportionally from a 3,181-issue filtered pool out of 9,099 raw reports (Dec 2015 – Jul 2026). The headline distribution: Deployment Failure 82/300 (27.33%), Build Failure 73/300 (24.33%), Crash 63 (21.00%), Incorrect Functionality 53 (17.67%), Performance Degradation 23 (7.67%), Hang 6 (2.00%); root causes split Kernel Library 119 (39.67%), Runtime Environment 100 (33.33%), Compiler & Build System 81 (27.00%), with Software Incompatibility (76, 25.33%) the single largest of 15 categories. The most useful artifacts are the worked micro-cases rather than the percentages: a FlashAttention head-dim change of 128→132 costing 40.8% of H100 training throughput (~370 → ~219 TFLOPS), a Triton kernel spending 0.7 ms in JIT recompilation per call against ~12 µs of actual execution (≈58×), an xFormers `int16_t` valid-column bound silently turning long-context attention into NaN past 32,768 keys, and a bitsandbytes `state.idx` leak that degraded Llama2-13B eval numbers without any exception. Read it for the failure taxonomy and the case catalog; do not read it for causal claims about *why* the distribution looks this way — no cross-tab of symptom × root cause, no temporal trend, and the aggregate is dominated by bitsandbytes (26.33%) and Triton (25.67%).

## 核心贡献

- **第一个针对 LLM GPU kernel 库层的系统性 issue 实证研究。** 此前的工作分别覆盖了深度学习编译器缺陷（Shen et al. FSE'21）、DL 应用故障分类（Humbatova et al. ICSE'20）、DL 平台质量问题（Gao et al. ICSE-SEIP'23）和 LLM 训练系统问题（Gao et al. FSE'25），但"夹在模型算子与硬件之间"的 kernel 库层（attention / GEMM / 量化 / 低精度 / codegen / dispatch）此前是空白。作者主张这一层的诊断需要同时推理 tensor shape 与 layout、向量化访存、同步、低精度语义、代码生成和架构相关 dispatch，与上层的故障模式不可互相归约。
- **一个 6 症状 × 15 根因 × 3 维度的分类体系（Table II / Table III）。** 症状沿用并适配已有实证文献的术语：Deployment Failure、Build Failure、Crash、Incorrect Functionality、Performance Degradation、Hang，每条 issue 只给一个主标签，另记录硬件、数据类型、触发条件、下游上下文与诊断证据作为辅助信息。根因在已有分类（Concurrency Error、API Misuse、Incorrect Numerical Computation、Software Incompatibility）之外**新增了两类**：`Improper Kernel Dispatch`（算子本身被支持，但没有合法的实现被选中，10 例）和 `Incorrect Compiler Transformation`（DSL/JIT/IR 层的变换破坏了合法语义，46 例），这两类正是 kernel 库特有的。
- **把"执行前失败"抬成第一类公民（Finding 1）。** 51.67% 的样本在设备执行之前就已经失败，因此验证必须覆盖从安装到 kernel 生成的整条路径，而不仅是 kernel 代码。这一条对工程实践的冲击最大：绝大多数 kernel 库的 CI 只跑算子正确性，不跑"装得上、编得过、选得对"。
- **提出 kernel specialization 的隐式契约问题（Finding 2）。** 特化（按 dtype/head_dim/causal/arch 生成专用实现）在带来性能的同时，对 tensor shape、metadata layout、内存 alias、硬件资源施加了**未写进 API 的隐式约束**；违反这些约束时，即使算子"被支持"也会输出错误结果或启动失败。作者据此论证库应当把这些契约做成 wrapper/dispatch 层的可执行检查，并在报错时同时打印期望值与实际值。
- **对现有测试/调试实践的分类与批评（Sec. VI）。** 归纳出五类互补实践：兼容性与集成测试、差分测试（differential testing）、边界值分析、动态分析（Compute Sanitizer / Nsight）、性能回归测试；并指出这些实践对**低精度数值问题**和**硬件特定执行失败**系统性失效——差分测试会因为参考实现自身用 FP16 而误报（FlashAttention issue #385 里梯度与 FP16 参考不符、但与 FP32 一致），边界值分析则很少扫到"head dim = 8/16 才炸、32 不炸"这种非单调故障面。
- **给出工具与库设计的五个方向（Sec. VII-C）。** 兼容性检查器（区分"安装版本"与"编译时版本"）、数值调试工具（在中间阶段比对 shape/dtype/accumulation mode/mask/tolerance）、编译器调试工具（保留 IR 快照做差分与回归）、契约感知的校验（contract-aware validation）、以及 record-and-replay（记录算子、tensor metadata、dispatch 决策、版本、架构与生成的 IR，并把确认的 case 固化成回归测试）。

## Key Contributions

- **First empirical study of the GPU-kernel-library layer as its own subject.** Prior empirical SE work covers DL compilers, DL applications, DL platforms, and LLM training systems; this paper targets the layer that sits between model operators and hardware and that is invoked *indirectly* — the user writes high-level Python, but which kernel actually runs depends on shape, layout, dtype, CUDA version, and GPU architecture. The authors argue (correctly, I think) that diagnosis at this layer is not reducible to any of the adjacent layers.
- **A two-level taxonomy with an explicit novelty claim at the root-cause level.** 6 symptom categories (adapted from Tan et al., Shen et al., Humbatova et al., Islam et al., Chen et al., Liu et al.) and 15 root causes across 3 dimensions. Two root-cause categories are genuinely new to this layer: `Improper Kernel Dispatch` (10 cases, 3.33%) — a supported operation for which no valid implementation gets selected because a variant is missing or a dispatch predicate is over-restrictive — and `Incorrect Compiler Transformation` (46 cases, 15.33%) — a DSL/JIT/IR pass that fails to preserve kernel semantics.
- **An evidence-linked case catalog, not just counts.** Every category is illustrated with a named, URL-referenced issue and, in six cases, an annotated code diff (Figures 2–4 show the block-sparse forward/backward state loss, the `int16_t` → `int` widening, and the DeepGEMM peer-CTA liveness predicate). This makes the taxonomy falsifiable and reusable by other researchers in a way that a bare distribution table would not be.
- **The "pre-execution dominates" finding.** 155/300 (51.67%) of sampled issues are Deployment Failure or Build Failure. The actionable restatement: a kernel library's reliability is a property of its packaging, dependency graph, compiler toolchain, and generated artifacts at least as much as of its CUDA code.
- **A critique of the prevailing test oracle.** The paper's sharpest observation is that differential testing — the default oracle for kernel work — has a *reference-side* failure mode: in FlashAttention #385 the "bug" was rounding error in the FP16 reference, and in CUTLASS #1270 the "bug" was that the sparse tensor-core path silently used TF32 while the reference used true FP32. Both directions (kernel wrong, reference wrong) produce the same signal, and the paper's remedy — make effective precision and accumulation mode explicit — is a concrete, checkable design requirement.
- **Five research directions tied to specific counts** (compatibility checker ← 100 Runtime Environment cases + 82 Deployment Failures; numerical debugging ← 53 Incorrect Functionality; compiler debugging ← 46 Incorrect Compiler Transformations; contract validation ← dispatch/layout/aliasing/resource cases; record-and-replay ← value-dependent failures that metadata alone cannot reproduce).

## Methodology

**Study subjects (Sec. III-A).** Seven open-source repositories chosen to span complementary parts of the ecosystem: attention/operator kernels (FlashAttention, FlashInfer, xFormers), GEMM and low-precision matrix kernels (CUTLASS, DeepGEMM), GPU compilation and code generation (Triton), and quantization kernels plus CUDA packaging (bitsandbytes). Complete serving engines (vLLM, SGLang) and training frameworks (Megatron-LM) are deliberately excluded because their trackers mix in model loading, scheduling, distributed runtime, and service-level problems.

**Collection (Sec. III-B).** GitHub REST API, all open and closed issues, 2015-12-26 → 2026-07-10. Per issue: title, body, labels, state, timestamps, comments, linked references.

**Filtering funnel.** 9,099 raw → drop all open issues (only *closed* reports of concrete, complete failures of existing functionality are in scope) → title-keyword screen (`bug`, `error`, `fail`, `wrong`, `crash`, `hang`, `regression`, `performance`, `numerical issue`) plus exclusion of placeholder/support/feature-request/doc/maintenance/tracking/duplicate reports, guided by negative labels (`question`, `feature request`, `enhancement`, `documentation/docs`, `roadmap`, `tracking`, `help wanted`, `good first issue`, `chore`, `style`) → **3,181 candidates** → repository-stratified sample of **300**, with each repository's quota proportional to its candidate count. Reports containing only symptoms, speculative explanations, or competing explanations were excluded and **replaced by the same-repository issue whose creation time was closest** to the excluded one, iterating until 300 high-quality issues remained.

**Final sample (Table I).** FlashInfer 1,051 raw / 390 candidate / 37 final; FlashAttention 1,786 / 302 / 28; Triton 2,205 / 815 / 77; CUTLASS 1,931 / 597 / 56; DeepGEMM 180 / 38 / 4; xFormers 722 / 206 / 19; bitsandbytes 1,224 / 833 / 79. Total 9,099 / 3,181 / 300.

**Labeling (Sec. III-C).** Two authors independently labeled all 300 issues on (a) one primary symptom, (b) one primary root cause, (c) the associated fix. Auxiliary fields: hardware, data type, trigger condition, downstream context, diagnostic evidence. Agreement was measured **at the issue level with a disagreement defined as a mismatch in *either* the symptom or the root-cause label**, yielding Cohen's κ = 0.87. Disagreements were reconciled by discussion; out-of-scope issues were removed. Symptom terms were adapted from prior empirical SE/DL studies; root-cause terms were adapted where possible and extended with two new categories where the observed mechanism had no home (`Improper Kernel Dispatch`, `Incorrect Compiler Transformation`).

**Analysis structure.** Three RQs — RQ1 symptoms (Sec. IV), RQ2 root causes and typical fixes (Sec. V), RQ3 testing and debugging practices (Sec. VI) — each closed by an explicit *Finding* + *Implication* pair. Sec. VII covers threats to validity, generality, and future directions.

**Note on what "quantitative" means here.** This is a corpus study, so its numbers are distributional (counts, ratios, per-repository breakdowns) plus measured symptoms quoted from the issue threads (TFLOPS, milliseconds). There is no model, no benchmark suite, and no head-to-head baseline in the ML sense; the implicit comparison is against prior taxonomies of DL framework/compiler/platform bugs.

## Results & Highlights

- **Pre-execution failures outnumber execution-time failures 2.25×.** Of 300 issues, Deployment Failure (82, 27.33%) + Build Failure (73, 24.33%) = 155 (51.67%) never reach device execution, versus Crash (63, 21.00%) + Hang (6, 2.00%) = 69 (23.00%) that fail at launch or during execution. The remaining 76 are Incorrect Functionality (53, 17.67%) and Performance Degradation (23, 7.67%). In other words the most common way an LLM GPU kernel library fails is that it never installs or never compiles — not that it computes the wrong thing.
- **Software Incompatibility is the single largest root cause of 15, at 3.5× the runner-up.** Software Incompatibility 76/300 (25.33%) vs Code Logic Error 22/300 (7.33%) vs API Misuse 26/300 (8.67%) vs Incorrect Compiler Transformation 46/300 (15.33%) vs Incorrect Numerical Computation 8/300 (2.67%). Dimension totals: Kernel Library 119 (39.67%), Runtime Environment 100 (33.33%), Compiler and Build System 81 (27.00%) — i.e. the two *non-code* dimensions together hold 181/300 (60.33%), 1.52× the kernel-code dimension.
- **The symptom profile is almost entirely a per-library signature, with a 6× spread on the same category.** Derived from Table II counts: Deployment Failure is 47/79 (59.5%) of bitsandbytes' issues but only 13/77 (16.9%) of Triton's and 6/56 (10.7%) of CUTLASS's. Inverted, Build Failure is 22/56 (39.3%) of CUTLASS's and 29/77 (37.7%) of Triton's but just 5/79 (6.3%) of bitsandbytes'. So the aggregate "27.33% deployment failure" is not a property of GPU kernels in general — 47 of the 82 deployment failures (57.3%) come from one library's wheel/CUDA-packaging problems.
- **A 3.1% change in head dimension costs 40.8% of training throughput.** On H100, a FlashAttention report (issue #1141) documents training throughput dropping from ~370 to ~219 TFLOPS when head dim moved 128 → 132. The maintainer's explanation: implementations favor tensor-core-aligned dimensions and pad unconventional ones to multiples of 32/64/128, so the extra padded compute is real work. This is a clean example of specialization creating a performance cliff that is invisible in the API.
- **JIT specialization can dominate execution by ~58×.** A Triton attention-mask kernel (issue #6480) passed values that varied between invocations as `constexpr` parameters, so every change triggered a fresh specialization: ~0.7 ms of compilation and code generation per call against ~12 µs of actual kernel execution (0.7 ms / 12 µs ≈ 58×). The repeated compilation blocked the CPU and produced execution gaps in an SGLang serving workload; stabilizing the compile-time arguments removed the slowdown. This is the paper's best illustration that "performance regression" in this layer often has nothing to do with the GPU.
- **Silent correctness failures are 17.67% of the corpus and mostly invisible to launch-success checks.** 53/300 issues complete normally but violate semantics: 12 (4.00%) tensor layout mismatch, 7 (2.33%) improper memory access, 8 (2.67%) incorrect numerical computation, 4 (1.33%) incorrect indexing, 22 (7.33%) code logic error. The block-sparse FlashAttention case (#2623) is the canonical one: the forward pass matched the sparse reference exactly, but the backward pass returned *finite but severely inaccurate* gradients because the mask rule and backward block list were never saved for the gradient kernel — dense-attention gradients computed for a sparse forward. A correct forward result does not imply correct training.
- **Two hard, checkable bug mechanisms worth memorizing.** (i) xFormers #719: the number of valid key columns in the current tile was narrowed into a signed `int16_t` bound, so once the remaining span exceeded 32,767 keys the predicates operated on a corrupted bound and attention returned NaN — the fix was widening the parameter to `int` *plus adding oversized query/key regression shapes*. (ii) CUTLASS #2494: a Blackwell 2-SM GEMM example computed its launch grid from the MMA tile size rather than the smaller per-CTA tile, giving a 4×4 grid instead of the required 8×4 for a 1024×1024 output — too few CTAs, so part of the GEMM result was simply never computed, with no error raised.
- **Hangs are rare but structural.** Only 6/300 (2.00%), and the worked example is a barrier-accounting bug: a CUTLASS Stream-K GEMM (#1801) hung for specific shapes because the separate-reduction path mis-coordinated participating work. The DeepGEMM SM90 case (#147/#149) is the more instructive one — a stage barrier needed 2 CTAs × 4 warps = 8 arrivals, a faulty peer-liveness predicate treated the idle peer B9 as active, B8 routed 4 arrivals to itself and 4 to B9 (which did no consumer work and returned none), the barrier sat at 4/8, and the TMA producer could never pass its serialization wait.
- **Silent quality degradation can be a state bug, not a numerics bug.** bitsandbytes #767: `Linear8bitLt` / `MatMul8bitLt` retained `state.idx` across batches, so a later batch reused index state from an earlier one and matmul could select the wrong data. The reporter's evidence was indirect and exactly the kind that is hard to attribute: Llama2-13B evaluated *worse after training* than in an independent inference run of the same weights. 2/300 (0.67%) — the smallest category — but arguably the highest severity per case.

## Critical Assessment

**Novelty.** The framing claim — "first comprehensive empirical study of GPU kernel libraries for LLM systems" — is defensible for this exact layer, and the paper is careful to position itself against the four nearest neighbors rather than pretending they don't exist. The genuinely new taxonomic content is narrow but real: `Improper Kernel Dispatch` (10 cases) and `Incorrect Compiler Transformation` (46 cases) are mechanisms that the DL-framework and DL-compiler taxonomies genuinely lack, and the dispatch category in particular names something practitioners recognize but the literature doesn't ("the op is supported, the implementation just isn't there for your group size"). Beyond that, the contribution is consolidation and case curation rather than new method.

**Rigor — the sampling is the weak point.** Three specific problems. (1) **The title-keyword screen is not symptom-neutral.** Candidate issues had to contain `bug|error|fail|wrong|crash|hang|regression|performance|numerical issue` in the *title*. Build and deployment failures almost always say "error" or "fail" in the title ("Error: Install pip install flash-attn", "The installation process always freezes"). Silent wrongness often does not — real titles in this space look like "outputs all zeros", "loss goes to NaN", "results differ from reference". The 27.33% / 24.33% pre-execution figures are therefore plausibly inflated relative to Incorrect Functionality, which the paper then cites as evidence that pre-execution failures dominate. The direction of the finding may well be right, but this design cannot establish the magnitude, and the paper never flags it as a threat.
(2) **The replacement rule induces temporal clustering.** Excluded reports were replaced by the same-repository issue with the *closest creation time*. If a single CUTLASS DSL bump generated twenty near-duplicate failures in one week (and §IV describes exactly such a case — the CUTLASS DSL 4.2.1 SSA-dominance regression), the nearest-timestamp rule pulls in more issues from that same burst, inflating within-category clustering and making one root cause look like many independent observations. A random replacement within repository, or a reported dedup check on the final 300, would have cost nothing.
(3) **The aggregate is two libraries wearing a trench coat.** bitsandbytes (79) + Triton (77) = 156/300, 52% of the corpus, while DeepGEMM contributes 4 issues — and the paper still prints DeepGEMM ratios to two decimals (0.67%, 0.33%), which is 2 issues and 1 issue. Percentages of n=4 are noise, and the paper draws per-library narrative conclusions from them ("DeepGEMM provides GEMM and low-precision matrix kernels…") without ever saying "n=4, ignore these columns." Meanwhile 47 of the 82 deployment failures come from bitsandbytes alone, so Finding 1 is substantially a finding about one project's wheel-packaging strategy.

**Missing analyses that the paper's own framing demands.** (1) **No symptom × root-cause cross-tabulation.** The paper produces a 6-category symptom table and a 15-category root-cause table and then never crosses them. That 6×15 matrix is the single most useful thing this dataset could yield — "I see NaN, where do I look?" — and its absence is a real gap, not a formatting choice. The prose substitutes one anecdote per cell. (2) **No temporal analysis** despite a 10.5-year window (Dec 2015 – Jul 2026) that spans Volta → Hopper → Blackwell and CUDA 8 → 13. Are issues getting worse? Is Incorrect Numerical Computation growing as FP8/FP4 adoption grows? The 2.67% figure is an average over a decade in which low-precision arithmetic went from exotic to default, which makes the average nearly meaningless for current practice. (3) **No fix-level data.** "Typical fixes" are one example per category; there is no distribution of fix size (LOC), time-to-fix, fixer identity (maintainer vs. reporter vs. drive-by), or whether a fix regressed later — all of which are trivially extractable from the same API pull and would have made the fix section quantitative. (4) **No control corpus.** The interesting claim is comparative — that kernel libraries fail *differently* from DL frameworks. But the paper never labels a sample of, say, PyTorch or TensorFlow issues with the same taxonomy. Gao et al. 2023 already reported deployment-heavy distributions for a DL *platform*; without a side-by-side, "60.33% pre-execution is a kernel-library property" is unfalsifiable.

**Overclaiming, mild.** The abstract's third finding — "current testing and debugging practices are often insufficient for identifying low-precision numerical problems and hardware-specific execution failures" — is supported only by what reporters *happened to write in the thread*. Successful debugging produces no issue at all, and a resolved issue is by construction a case where the practice eventually *worked*. The paper does acknowledge this ("our evidence is limited to what appears in the reports"), but the abstract states the conclusion without that qualifier. Similarly, "silently corrupt outputs" is the motivating threat in the introduction, yet only 53/300 (17.67%) issues are correctness issues and only 8 are numerical — the motivating scenario is real but rare in the reported record, which is itself the paper's most interesting unstated result: **silent corruption is under-reported, and the paper's data cannot distinguish "rare" from "rarely filed."**

**Reproducibility.** The 300-issue labeled dataset with symptom/root-cause/fix labels and the issue URLs is the natural artifact and there is no statement about whether it is released. Every individual case is traceable (issue/PR numbers are given), and the labeling protocol is described well enough to re-run, but the κ = 0.87 is a *combined* figure — "a difference in either the symptom label or the root-cause label counted as a disagreement" — so we cannot tell whether the 6-way symptom task (likely high agreement) or the 15-way root-cause task (with cells of size 2, likely much lower) is carrying the number. Separate κ per labeling task, plus a confusion matrix, would cost one paragraph.

**Significance.** Moderate and durable. The taxonomy will be cited; the percentages should be cited with the sampling caveats above. The case catalog is the part with the longest shelf life, because the failure mechanisms (int16 index overflow, missing forward→backward state, peer-CTA liveness, grid-vs-tile mismatch, `state.idx` leakage, constexpr-triggered recompilation) are architectural and will recur on the next GPU generation under different names. The five proposed tools are sensible but generic — "compatibility checker", "record and replay" — and don't engage with the cited prior art (CUDAsmith, NNSmith, GPUVerify) enough to say what specifically fails when those techniques are pointed at kernel libraries.

**Red flags.** (i) Per-library percentages computed on n = 4 with no suppression. (ii) A title-keyword screen that is correlated with the outcome variable, undisclosed as a threat. (iii) Nearest-timestamp replacement of excluded issues, which manufactures clusters. (iv) "First comprehensive" in the abstract and "to the best of our knowledge" in the body — inconsistent hedging strength for the same claim. (v) A 10.5-year window averaged into single percentages with no era breakdown.

## Strengths

- **The Finding/Implication pairing is executed consistently and well.** Every one of the five findings ends with a concrete, actionable implication ("distinguish compilation errors and genuine non-progress from slow build progress; preserve compiler artifacts and build logs, and verify build dependencies before concluding that compilation has stopped making progress"). This is rarer than it should be in empirical SE papers and makes the paper immediately usable by a kernel-library maintainer.
- **The case studies are genuinely instructive and correctly chosen.** The six annotated diffs are the paper's best asset: Figure 2 (forward/backward block-sparse state loss), Figure 3 (`int16_t` → `int` bound widening), Figure 4 (peer-CTA liveness predicate and barrier arrival routing). Each is a complete, self-contained lesson in a failure mode that is hard to invent and easy to miss in review.
- **Honest about what issue-tracker data can and cannot show.** Sec. VI opens by conceding that the evidence "does not establish whether developers also used practices that went unrecorded," and Sec. VII-A separates internal validity, construct validity (replacing reports without identifiable causes "may favor well-documented cases"), and external validity rather than lumping them together. The acknowledgement that the seven libraries' integration into Megatron-LM/PyTorch/Transformers/DeepSpeed/vLLM/SGLang "supports relevance but does not establish" generalizability is the right register.
- **The reference-side failure mode of differential testing is a real and underappreciated insight.** Two independent cases (FlashAttention #385: FP16 reference was the wrong one; CUTLASS #1270: sparse tensor-core path silently used TF32) establish that the oracle itself needs a numerical contract. This is the kind of observation that changes how people write kernel tests.
- **Genuinely useful negative result on low-precision numerics.** Only 8/300 (2.67%) issues are Incorrect Numerical Computation, and the paper is clear-eyed that this is a *reporting* fact, not a *prevalence* fact — the tooling gap (no way to compare intermediate stages with explicit accumulation modes and tolerances) is exactly why these cases are hard to file. Naming the gap and the count together is more useful than either alone.
- **The bitsandbytes `state.idx` case is a small masterpiece of diagnosis.** A user noticed Llama2-13B evaluated worse after training than in independent inference; the cause was cross-batch index-state reuse in an 8-bit matmul kernel. That chain — quality regression → training/inference discrepancy → stale kernel state — is the exact shape of the silent-corruption failures that matter most and that benchmarks never catch.

## Limitations

- **Sampling validity.** The title-keyword prefilter correlates with the symptom being measured, and the nearest-timestamp replacement rule clusters the sample around regression bursts. Neither is disclosed as a threat to validity, and together they plausibly inflate the pre-execution share.
- **Aggregate composition.** 52% of the corpus is two libraries (bitsandbytes 79, Triton 77), 26% is one (bitsandbytes), and one subject contributes 4 issues. Aggregate percentages are effectively weighted by candidate-pool size, which reflects each project's issue-filing culture (bitsandbytes: 1,224 raw issues for a quantization library) at least as much as its defect density. There is no normalization by code size, user base, or release count — so no statement about which library is *more* reliable is possible, and the paper correctly doesn't make one, but it also doesn't warn against making one.
- **No temporal dimension.** Ten and a half years collapsed into one distribution. Hardware Incompatibility at 8.00% is uninterpretable without knowing whether it is front-loaded in the Volta era or growing with Blackwell/FP4.
- **No cross-tabulation of symptom × root cause**, which is the analysis a debugger would actually want.
- **Fix analysis is anecdotal.** No time-to-fix, no fix size, no fix-author distribution, no regression rate — all extractable from the same data pull.
- **Sec. VI's practices are inferred from what reporters wrote**, not from repository CI configuration or maintainer interviews. A study of what these projects' CI actually runs (and what it skips) would have been far stronger evidence for "practices are insufficient" than issue-thread archaeology.
- **Single primary label per issue** forces multi-cause failures into one bucket. The DeepGEMM peer-CTA hang is simultaneously a concurrency error and a resource/launch-configuration problem; the block-sparse backward bug is both state mismanagement and code logic. With 15 categories and 300 issues, the single-label choice materially changes the distribution, and no multi-label sensitivity check is reported.
- **No artifact release stated.** The labeled dataset is the paper's most reusable output and its availability is unaddressed.
- **Generality to closed-source and vendor kernels is untested.** CUTLASS and FlashAttention are open, heavily scrutinized, and community-triaged; proprietary cuBLAS/cuDNN-class kernels have no public issue tracker, so the entire study is silent on the layer that most production LLM traffic actually runs through.

## Relevance

这篇直接命中「Inference Reliability & SDC Detection」的核心命题：论文开篇就指出"产生错误结果的 GPU kernel 会在不抛任何异常的情况下静默污染生成的 token"，而 53/300 的 Incorrect Functionality 案例（前向正确但反向梯度全错、`int16` 溢出导致长上下文 NaN、`state.idx` 跨 batch 泄漏导致 Llama2-13B 训练后评测反而变差）正是"模型之下的数值/kernel/服务栈造成输出损坏"的具体机制清单。对「Reliability under Extreme Performance Optimization」同样高度相关——head dim 128→132 掉 40.8% 吞吐、constexpr 触发 JIT 导致 0.7 ms 编译对 12 µs 执行，说明特化优化引入的隐式契约本身就是可靠性风险的来源。

## Questions for Further Exploration

1. **How much of the 51.67% pre-execution share survives a symptom-neutral sampling frame?** Re-run the candidate selection using body-text and label signals only (no title keywords), or sample uniformly at random from the 3,181 pool, and report the symptom distribution. My prediction: deployment/build falls to ~35–40% and Incorrect Functionality rises above 25%. This is the single experiment that would most change how the paper is cited.
2. **What does the symptom × root-cause matrix look like, and is it stable across libraries?** Specifically: conditional on observing NaN/Inf output, what fraction traces to Incorrect Numerical Computation vs. Improper Memory Access vs. Incorrect Indexing? And does the answer differ between Triton (JIT, DSL-level) and CUTLASS (template, C++-level)?
3. **Is `Incorrect Numerical Computation` at 2.67% a prevalence fact or a reporting fact?** A natural probe: take the 300 issues and check how many *closed-as-fixed* issues have a comment thread where the reporter compared against a reference at a single tolerance and stopped. If the answer is "most", then silent numerical wrongness is systematically under-filed, and the 2.67% is a lower bound of unknown looseness.
4. **Does the taxonomy transfer to a control corpus?** Label 100 PyTorch and 100 vLLM issues with the same 6×15 scheme. If Software Incompatibility is also ~25% there, the finding is about the DL software stack, not about kernel libraries, and the paper's central framing needs revision.
5. **What is the fix half-life, and do fixes regress?** For each of the 300, extract the fix commit, its diff size, the time from report to merge, and then check whether the same issue file/line is touched again within 12 months. A high regression rate would argue for the record-and-replay direction far more forcefully than any of the paper's current evidence.
6. **How would a contract-aware validation layer actually be specified?** The paper calls for executable contracts on shape/dtype/layout/alignment/aliasing/shared-memory. A concrete follow-up: instrument one library (FlashInfer is the natural candidate, being dispatch-heavy and small) with such checks and measure the runtime overhead and the number of the 37 sampled FlashInfer issues it would have caught pre-launch.
7. **Where do these failures go when there is no issue tracker?** Vendor kernels (cuBLAS, cuDNN, TensorRT plugins) have no public equivalent, yet they dominate production inference. Any estimate of the failure distribution in *that* layer, even from a single large operator's internal bug database, would be more decision-relevant for serving teams than the open-source distribution.
