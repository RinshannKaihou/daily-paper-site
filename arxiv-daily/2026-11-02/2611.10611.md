> **一句话总结：** 论文指出批量不变性（batch invariance）的真正缺口不在 kernel 内部而在 **kernel 选择**：引擎按 batch 的 token 数、KV 长度、消息字节数去挑 kernel 和参数，两个算出同一和的 kernel 舍入不同。作者把选择逻辑写成可执行 DSL（SelIR），用最大流最小割求出"必须钉死的最少几个值"（pin），再按 workload 调优成 commitment tuple；在 vLLM/SGLang 的 Llama-3.1-70B 与 Qwen3-30B-A3B 四卡部署上，p50 每输出 token 延迟只有 Stock 的 1.10×/1.11×（确定性模式是 2.4–5.7×），而 512/512 条 seeded rollout 逐 bit 复现，trainer 与 rollout 的 logprob 完全一致（KL=0），BF16 GRPO 不再崩（reward 0.843 vs Stock 0.436）。

> **TL;DR:** Instead of forcing one conservative kernel per operator, Detent pins the handful of batch-dependent values that kernel *selection* reads — 3 attention pins + 3 all-reduce pins (+3 MoE pins on Qwen3-30B-A3B), found as a weighted minimum vertex cut over a partially-evaluated SelIR program (FA3's graph: 8,076 values, 26 selection points, 3 batch-dependent). On 4×H100 with Llama-3.1-70B and Qwen3-30B-A3B in both vLLM 0.26.0 and SGLang, tuned Detent serves at 1.08–1.11× Stock's p50 latency per output token vs 2.4–5.7× for SGLang-Det/vLLM-Det (1.67–10.3× vs Stock at worst load), passes all 26 cells of a batch-invariance battery where Stock fails 5–19 cells, and holds GSM8K at 94.16% vs SGLang-Det's 93.63% on Qwen3 (+0.53 pts, p=0.14). Seeded rollouts replay 512/512 bit-for-bit, the trainer matches 100% of rollout tokens every step where Stock matches only 1.0–47.7%, and BF16 GRPO keeps KL=0 to step 600 while Stock's reward collapses 0.733→0.436 and AIME 2024 Pass@1 drops 29.2%→8.5%. The price is per-workload tuning (10–19 min) and a tuple that can cost 4.17× if traffic drifts.

## 核心贡献

- **一个充分条件，把问题从 kernel 搬到选择层。** `BI(kernel) ∧ BI(selection) ⟹ BI(end-to-end)`：只要用户提供批量不变的 kernel，端到端不变性就等价于"选择函数的输出不依赖 batch"。这把 SGLang-Det / vLLM-Det 那种"每个算子只留一个保守 kernel"的粗粒度做法，换成"保留快 kernel、只钉死选择读到的少数值"。
- **SelIR：把 kernel 选择写成可执行程序。** Python 子集 DSL，纯函数，输入分 `Runtime` / `Unpinnable` / deployment facts，`knob` 声明部署期设置，`require`/`assume` 声明合法性条件；每个返回值是一个 selection point。同一个程序既被 solver 分析、也被引擎在服务时执行，因此"在 SelIR 里钉死"就等于"在运行引擎里钉死"。JIT cache 命中约 20 ms，冷启动求解约 5 s。
- **用最小割自动找 pin，而不是靠人读源码。** 优化后的选择是依赖图，pin 一个值就切断所有经过它的路径，因此 pin 集合是一个 vertex cut；用最大流求加权最小割（权重偏向"pin 少"和"靠近 selection point"）。FA3 上割落在 batch 相关的 selection point，MoE 上割落在程序内部的 row key，一个 pin 就锁死 MoE 16 个 batch 相关 selection point 中的 14 个。
- **Pin Value Range Analysis（VRA）+ 加法分解的 tuner。** VRA 用"代入候选值跑程序、检查每条 require/assume"的方式判定合法取值；tuner 证明并利用 `T(a)=C+Σ_f T_f(a_f)` 的可加性，把联合搜索 `Π|L_f|` 降为 `Σ|L_f|`（Qwen3-30B-A3B 上 1,607,040 → 3,020），再只测其中 8.0% 就平均离最优 0.04%（最差 0.75%）。
- **两个引擎的落地实现 + RL 训练器。** vLLM 与 SGLang 各打一个补丁把 FA3 / fused MoE / all-reduce / GEMM 的选择路由到 selector；自建 CUDA all-reduce（固定 rank 序求和）与改造版 FA3（固定 split 边界）。训练侧复用同一套 kernel 与 tuple，另加一个 SelIR 之外的 seeded sampling 补丁，使 rollout 与训练逐 bit 一致。
- **覆盖面证据：** 2 个引擎、2 代 GPU（H100、B200）、TP=1/2/4/8、head dim 64–256、dense 与 MoE、8 个额外部署全部由 spec 直接求解成功。

## Key Contributions

- **Reframes the determinism problem.** Prior work makes each kernel's reduction order batch-independent; Detent observes that engines still choose kernels and their parameters from batch-derived quantities (FA3's split count and tile width, the fused MoE's nearest tuned row, the all-reduce algorithm by message bytes, cuBLAS by shape), so two kernels computing the same sum can still round it differently. Equation (1) makes the division of labour explicit: the user supplies batch-invariant kernels, Detent makes selection batch-invariant.
- **SelIR, an executable selection DSL with a JIT cache.** Selection programs are pure Python-subset functions over records and scalars with `Runtime` / `Unpinnable` inputs, `knob` declarations, and `require`/`assume` validity conditions. Because the solver and the serving engine consume the same program, a pin is not a documentation claim but a runtime constant.
- **A solver that derives pins instead of asking for them.** Partial evaluation for deployment facts, lowering to a single dependence graph with control dependences included, then a weighted minimum vertex cut via max-flow. The paper reports the ablation: with constant folding alone FA3 needs 12 pins instead of 3; without the cut, pinning everything the MoE's batch-dependent selection points read takes 10 pins instead of 3; without any analysis FA3's selection has 227 candidate assignments.
- **Pin VRA for legal values, and an additivity proof for the tuner.** VRA runs the program with candidate substitutions and checks every `require`/`assume`; the tuner's per-family decomposition is proved exact under three stated assumptions, with a bound `T(a*)/T(a) ≤ (1+δ)/(1−δ)` when additivity holds only to relative error δ (measured δ = 1.04% on Qwen3-30B-A3B, giving within 2.1% of the best tuple).
- **Two engine integrations plus an RL trainer, evaluated on the axes that matter for deployment.** The paper does not stop at a single-GPU microbenchmark: it covers both vLLM and SGLang, dense and MoE, TP 1–8, H100 and B200, and reports serving latency, accuracy, an LLM-42 comparison, seeded rollout replay, trainer bit-agreement and a GRPO stability sanity test.

## Methodology

**Problem statement.** A request's output is `y = F(x, s; M, D, T, B)` with prompt `x`, seed `s`, model `M`, deployment `D` (engine build, GPU, parallelism), commitment tuple `T` and batch state `B`. Batch invariance means `F(·;B) = F(·;B′)` for all `B, B′`. The paper separates *kernel* batch invariance (the user's job) from *selection* batch invariance (Detent's job), and assumes each request's output is mathematically a function of its own input.

**SelIR.** A Python-subset DSL with Python semantics; programs are pure functions over records and scalars with conditionals and reductions over static collections. Inputs are tagged `Runtime` (changes per batch, e.g. `num_tokens`, KV lengths) or `Unpinnable` (cannot be pinned). Each returned value is a selection point. `knob` declares a deployment setting no input determines (all-reduce workspace push/pull, GEMM padding). `require`/`assume` state when a selection is valid; the user never names pins or candidate values. Detent's shipped programs transcribe each engine's existing selection and then adapt its heuristics to Detent's kernels — e.g. the FA3 program adds a split stride the engine's heuristic never chooses.

**Compile.** Each program is partially evaluated for its deployment (head dim, head counts, dtype, SM architecture, TP degree, page size, max context), then lowered by compiler optimizations to a single dependence graph whose edges capture every batch dependence including control dependences. Values are simplified as far as deployment facts allow. The result is cached on disk under a hash of everything that can change the answer.

**Solve.** For each kernel family the solver computes a weighted minimum vertex cut (Edmonds–Karp max-flow) separating batch-dependent inputs from selection points, with weights favouring few pins and, among equal-size cuts, pins near the selection points. On FA3 the cut lands on the batch-dependent selection points; on the MoE it lands inside the program on the row key, which fixes 14 of the 16 batch-dependent selection points.

**Legal values.** Pin VRA substitutes candidate assignments and runs the program, judging an assignment legal if every `require` and `assume` holds at every input point tried (all points when domains are small, a fixed sample otherwise). At serving time the compiled selector checks these conditions once per new input combination and exits rather than silently running another kernel — unlike a failed `torch.compile` shape guard, a new batch never triggers a recompile.

**Tune.** Tuning uses a profiling workload with similar arrivals. The tuner starts from the unpinned program's most frequent legal value per pin and default knobs, records each family's distinct calls with their batch-dependent quantities and counts, then searches each family's legal grid, measuring only part of it. Each candidate is a "repin" that swaps constants and regenerates the selector without re-lowering or re-solving (~4 ms). The additivity argument (three assumptions: families run back to back without overlap; the recorded workload fixes batching so a tuple only changes which kernels are selected; a call's time depends only on the call and its family's assignment) licenses the per-family search; users must declare overlapping kernels (e.g. fusions) as one family.

**Serving.** During serving the commitment tuple is fixed, so the batch's composition cannot reach selection. An RL trainer that runs the same kernels under the same tuple differs from the server only in the batch, hence matches its logprobs; admitting only seeded sampling fixes the sampled tokens too.

**Implementation.** Solver, VRA, selector runtime, tuner and engine integrations in Python; all-reduce kernels and FA3 modifications in CUDA. Kernels: DeepGEMM (with tuned padding), Triton fused-MoE, custom fixed-rank-order all-reduce, rebuilt FA3 that keeps split-KV but follows a fixed split-size principle. Engines: SGLang (a 2026 development version) and vLLM 0.26.0, both with FA3, CUDA graphs, prefix caching, chunked prefill and greedy decoding; 16-token pages in vLLM.

**Evaluation setup.** Llama-3.1-70B-Instruct and Qwen3-30B-A3B (both head dim 128, bf16, TP=4 on H100). Workloads: W-A replays 600 requests from ~160 ShareGPT conversations turn by turn (short prompts, ~64% of tokens repeat the previous turn, exercises prefix caching); W-B sends 200 arXiv documents of ~8k tokens with Poisson arrivals (long prefill mixed with decode); W-B-c sends the first 64 in a closed loop. Nine loads (A1–A4, B1–B3, C1–C2), up to Stock's peak throughput λmax. Arms: Stock, SGLang-Det, vLLM-Det, Detent (Table 1). Batch invariance is tested with a 26-cell battery: temperature 0, reference batch vs same/changed batch, comparing the bits of the first 16 output logprobs (two reproducibility cells, fourteen co-batch changes, four row moves, six prefix-cache-split changes, plus nine "strong" cells placing the request next to 1–32 short/long/mixed requests). Latency is p50/p90/p99 per output token, median of three runs.

## Results & Highlights

- **Serving latency: 1.08–1.11× Stock at p50, where the deterministic modes are 2.4–5.7× slower.** Tuned Detent's p50 is 1.10× Stock on Llama-3.1-70B and 1.11× on Qwen3-30B-A3B in SGLang, 1.08× and 1.11× in vLLM; across the nine loads p50 ranges 1.01–1.22× and geometric-mean p99 1.12–1.22×. At the geometric mean SGLang-Det is 2.4–2.6× slower than Detent at p50 (2.8–3.0× at p99) and vLLM-Det 3.4–5.7× (3.7–9.1× at p99); measured against Stock directly, the deterministic modes cost 1.59–6.34× and 2.83–10.3× per load. On one queue-growing workload the deterministic modes reach 6.1× and 9.2× Detent's p50, and even when each arm is capped at 0.67–1.0 of its own max throughput, vLLM-Det on Llama-70B W-A and SGLang-Det on Qwen3 W-B still take 2.0–2.3× Detent's p50.
- **Invariance: Detent, SGLang-Det and vLLM-Det pass every cell; Stock fails 5–19 of them.** On the 26-cell battery Stock fails 9 cells on Llama-3.1-70B and 5 on Qwen3-30B-A3B in SGLang, and 19 of 24 and 2 of 23 applicable cells in vLLM; all three batch-invariant arms pass all nine "strong" cells, where Stock fails 4–7. The consequence is visible on GSM8K: changing only the load changes Stock's generated text on 790 of 1,319 problems (Qwen3-30B-A3B) and 484 (Llama-3.1-70B), and changes the final answer on 33 and 16 respectively — matching the abstract's "33 of 1,319".
- **Accuracy: GSM8K 94.16% vs 93.63% for SGLang-Det on Qwen3 (+0.53 pts), statistically indistinguishable.** Five-shot greedy on all 1,319 test problems at three load points: Qwen3-30B-A3B G1 93.48 vs 93.63 (−0.15, 95% CI [−0.92, +0.66], p=0.85) and G2/G3 94.16 vs 93.63 (+0.53, [−0.15, +1.02], p=0.14); Llama-3.1-70B 94.77 vs 94.69 (+0.08, [−0.39, +0.50]) and 94.84 vs 94.69 (+0.15, [−0.36, +0.57]). On GSM8K-Platinum's 1,209 corrected problems accuracy is 96.11–96.77% (Qwen3) and 96.86–97.11% (Llama), within [−0.93, +0.96] points of SGLang-Det (McNemar p 0.18–1). Wilson intervals are about ±1.3 points.
- **RL rollouts replay bit for bit, at 0.84–0.92× Stock throughput.** 512/512 seeded GSM8K rollouts at temperature 1 replay bit-identically under other batches and cache splits and match their rescoring, on Llama-3.1-8B (1×H100), Qwen3-30B-A3B (4×H100) and Llama-3.1-70B (4×H100); throughput at 1,024 output tokens is 0.917×, 0.837× and 0.872× Stock's and 1.15×, 1.27×, 1.35× SGLang-Det's. SGLang-Det's seeded rollouts change in all 20 cells where one co-batched request is greedy or uses top-p.
- **Trainer agreement: 100% of tokens every step, KL exactly 0.** On TBIK's on-policy protocol (Llama-3.1-8B, GSM8K, full fine-tuning, 100 steps, LR lowered 1e-5→1e-6) Detent's trainer matches the rollout's bits on every token of every step; Stock matches only 1.0–47.7% and SGLang-Det with batch-invariant operators 9.9–63.9%. Per generated token the rollout costs 1.03× Stock's time and the whole step stays within 4% of Stock's, versus 1.47× for SGLang-Det+BIO (whose median step is 1.09× because it generates 11% more tokens).
- **BF16 GRPO stability: Detent's run holds, Stock's collapses.** On the Qi et al. (2025) sanity recipe with DeepSeek-R1-Distill-Qwen-1.5B (one GPU serving, one training), Stock's reward falls from 0.733 at step 299 to 0.436 at step 500 and AIME 2024 Pass@1 from 29.2% to 8.5%, while Detent keeps KL at 0 through step 600 and reaches reward 0.843, at 1.18× Stock's time per token (most of it in training).
- **Solver and tuner cost.** Pins: 3 attention + 3 all-reduce + 0 MoE on Llama-70B, +3 MoE on Qwen3-30B-A3B, identical across the two engines. Judging FA3's 7,168 candidate assignments takes 130–180 s on 32 cores; repinning ~4 ms; tuning one workload 605–1,148 s (Qwen3) and 690–1,006 s (Llama) under a five-minute budget per family. Untuned default tuples are up to 103% (Llama) and 1–233% (Qwen3) slower at p50 in SGLang — tuning alone accounts for 1.34×/1.67× of SGLang-Det's gap and 1.13×/1.31× of vLLM-Det's.
- **LLM-42 comparison.** Ported LLM-42 on Llama-3.1-8B: even at a 2% deterministic share its median end-to-end latency is 1.15–1.20× Detent's, which makes 100% of requests deterministic; Detent's own median is 3.5–5.1% above Stock while SGLang-Det's is 39–49% above. Offline, Detent reaches 0.964× (ShareGPT) and 0.952× (arXiv) Stock throughput and 1.16×/1.11× SGLang-Det's; on arXiv, LLM-42 at ≤20% deterministic is 0.4–2.6% faster. Token-level stability: 0 of 45,184 comparisons changed for Detent, 0 of 87,916 for LLM-42.
- **Portability.** Eight additional deployments solved from specs alone (Llama-70B TP=8, Phi-3.5-mini, gemma-7b-it, Llama-3.1-8B in both engines, Llama-3.2-1B, Qwen3-14B/8B, plus a B200) all come out batch-invariant while Stock changes outputs in 8–16 of 26 cells; tuned tuples land at 0.97–1.09× Stock (W-A) and 1.01–1.13× (W-B-c), 1.14–3.01× faster than the deterministic modes.

Kan Wu at RadixArk is a direct signal: RadixArk builds Miles, the RL framework layered on SGLang that this paper's rollout/training story targets, so the authors are working on the exact stack they evaluate. ## Critical Assessment

**Novelty.** The reframing is genuinely new and, in hindsight, obvious in the good way: the field spent a year making kernels batch-invariant and then let the *selector* leak the batch back in. Casting pin discovery as a minimum vertex cut over a partially-evaluated selection program is a clean formalization, and the additivity argument that collapses the tuner's search from 1,607,040 to 3,020 assignments is a real (if assumption-laden) contribution. The weaker claim is "keeps the fast kernels": the FA3 used here is a *rebuilt* FA3 with a fixed split-size principle, and the all-reduce kernels are custom CUDA with a fixed rank order — so the user still does kernel work, just less of it. The paper is upfront about this ("Kernel batch invariance is the user's responsibility"), but the headline framing understates the engineering a new operator family demands.

**Rigor.** Mixed, in interesting ways. On the strong side: the kernel ablation in Appendix C is exactly the control a skeptical reader wants — swapped into Stock, Detent's GEMM and all-reduce *add* 0.6% (Qwen3) and 2.8% (Llama) GPU time per output token, and even with the tuple's padding 0.6%/2.1%, so Detent is not buying latency by giving itself faster kernels. They also check the FlashInfer all-reduce-fusion confound (0.996–1.103× Stock's decode step with the fusion on in Stock). On the weak side, three things stand out. First, **the accuracy evidence rests entirely on GSM8K** (plus GSM8K-Platinum), a benchmark both models already saturate at 93–95%: a ±1.3-point Wilson interval on 1,319 problems cannot detect a 1-point degradation, so "no accuracy loss" is really "no loss larger than ~1.3 points on grade-school math". No code, long-context, multilingual or agentic task is measured, even though the paper's own motivation (agent RL with long contexts, §10) is precisely where split-KV and prefix-cache effects bite hardest. Second, **the GRPO stability result is a single-seed sanity test**, and the training protocol lowers the learning rate from TBIK's 1e-5 to 1e-6; the text does not say whether that lowered LR also applies to the collapse experiment, which matters because a 10× lower LR is itself a well-known stabilizer and would confound the "bit-exactness prevents collapse" attribution. Third, **two latency numbers in §8.6 do not reconcile**: Table 5 reports 0.837–0.917× Stock *throughput* (i.e. 1.09–1.19× time per token) while the text reports the rollout at 1.03× Stock's time per token; the gap is plausibly prefill/sampling overhead or a different measurement point, but it is never explained.

**The LLM-42 comparison deserves a caveat.** It is the most persuasive baseline in the paper — LLM-42 is slower even when only 2% of its requests are deterministic while Detent makes 100% deterministic — but it is run on a *single* H100 with Llama-3.1-8B, a setting far from Detent's 4×H100 70B headline, and LLM-42's design point is verified speculation with rollback, not full determinism, so the two systems are being scored on a metric that favours Detent's guarantee. The port's fidelity is disclosed honestly (within 1.1% on the official online grid, 0.987× official throughput), but the pre-registered offline check failing by 44% and being corrected post hoc is the kind of degrees-of-freedom that should make a reader discount the arXiv offline numbers (where LLM-42 at ≤20% is 0.4–2.6% *faster*) more than the ShareGPT ones.

**Operational red flag: the tuple is a per-workload artifact.** Detent's own Figure 8 is the strongest argument against naive deployment: the W-A tuple on Qwen3-30B-A3B at load B2 takes 4.17× as long as the tuned tuple and raises median TTFT from 238 ms to 4.75 s, while on Llama-70B the same cell costs only 1.15×. Tuning takes 10–19 minutes per workload, and a stale tuple silently degrades rather than failing loudly. The paper acknowledges traffic drift in §10 but offers no detector, no re-tune trigger, and no online fallback — for a system whose selling point is reliability, that is a conspicuous gap.

**Reproducibility.** No artifact, code release or repository link is stated anywhere in the paper, and the deliverable is not a single binary but a solver, a VRA, a tuner, a DSL front end, CUDA all-reduce kernels, a modified FA3, and patches against a *2026 development version* of SGLang. Nothing here is reproducible from the text alone; even the pins (3+3+0 / 3+3+3) are only meaningful for those exact engine builds. Combined with the ~10-minute-per-workload tuning cost, independent verification would be a serious undertaking.

**Significance.** If the numbers hold, this is the paper that makes batch-invariant serving deployable rather than a research curiosity: 1.10× instead of 2.4–5.7× is the difference between "turn determinism on for the eval run" and "leave it on". The bit-exact trainer agreement (KL=0) is the cleanest evidence in the paper that the rollout-training mismatch is a numerics problem, not a modelling one, and the 26-cell battery with nine strong cells is a template other systems papers should copy.

## Strengths

- The problem decomposition in Equation (1) is crisp and immediately reusable: separate kernel invariance (user) from selection invariance (system), then attack only the second.
- The min-cut formulation is not decoration — the ablations quantify it (FA3: 3 pins vs 12 with constant folding alone; MoE: 3 vs 10 without the cut; FA3: 227 candidate assignments without any analysis).
- Unusually honest kernel ablation: the authors show their own GEMM and all-reduce kernels are *slower* than Stock's (adding 0.6%/2.8% GPU time per output token) rather than quietly benefiting from a faster stack.
- A real invariance battery (26 cells, nine "strong") instead of a single "same output twice" check, and it is applied to eight extra deployments, not just the two headline ones.
- The tuner's additivity proof with an explicit error bound (`(1+δ)/(1−δ)`, δ measured at 1.04%) is the kind of analysis that turns a heuristic search into an engineering choice.
- End-to-end RL evidence: 512/512 bit-identical replays, 100% trainer-token agreement at 1.03× Stock's per-token time, and a GRPO run that does not collapse where Stock's does.
- Cost transparency: every stage's wall-clock (130–180 s solve, ~4 ms repin, 605–1,148 s tune, 20 ms cache hit) is reported.

## Limitations

- **One deployment, one tuple.** Outputs match only within a fixed model, engine build and commitment tuple; cross-TP invariance needs TP-invariant kernels like TBIK's, which Detent does not provide.
- **Writing SelIR is manual.** Every operator family needs a hand-written selection program; the authors list LLM-assisted transcription and native-code selectors as future work. Only four families (FA3, fused MoE, all-reduce, GEMM) are demonstrated.
- **Accuracy is measured only on GSM8K / GSM8K-Platinum**, both saturated at 93–97%, so the "no accuracy loss" claim has roughly ±1.3 points of resolution and says nothing about code, long-context or agentic workloads.
- **Traffic drift is unhandled.** A tuple tuned for one workload can cost 4.17× on another's load (Qwen3) with TTFT going 238 ms → 4.75 s, and there is no detector or re-tune trigger.
- **Quantization is out of scope.** Dynamic per-tensor FP8 activation scales span the batch; batch-invariant FP8 would need per-token or static scales, so the fastest current serving configuration is not covered.
- **Sampling is restricted** to seeded temperature sampling; greedy/top-p mixes break the guarantee (SGLang-Det's seeded rollouts change in all 20 such cells), and the seeded sampler is a patch outside SelIR rather than part of the formal contract.
- **Single-seed GRPO evidence** on a 1.5B distilled model, with an LR change (1e-5→1e-6) that may confound the stability attribution.
- **No released artifact**, and the engine targets are development snapshots, making independent reproduction expensive.

## Relevance

直接命中 **Inference Reliability & SDC Detection** 的核心命题：模型输出被其下方的数值/kernel/服务栈静默改变——论文量化了"只换 batch 就改掉 1,319 道 GSM8K 中 790 道的生成文本、33 道题的最终答案"，并给出可部署的修法。同时也落在 **Compute Infrastructure for Large-Scale ML**（kernel 选择、all-reduce、TP）与 **RL Post-Training Dynamics & Failures**（rollout–trainer 失配导致 GRPO 崩溃）两块的交叉处。

## Questions for Further Exploration

1. How much of the 1.10× residual over Stock is the rebuilt FA3's 3 µs-per-call overhead versus the commitment tuple's loss of per-batch adaptation? The paper attributes "part of" the gap to each but never separates them cleanly.
2. Does the GRPO collapse experiment still collapse with the lowered 1e-6 learning rate under Stock? Without that control, "bit-exactness prevents collapse" is confounded with "a 10× smaller step size prevents collapse".
3. Why does the W-A tuple cost 4.17× on Qwen3-30B-A3B's B2 load but only 1.15× on Llama-70B? Is the MoE's 3-pin row-key choice the culprit, and could a per-family tuple (rather than a per-workload one) close that gap?
4. How would Detent interact with speculative decoding, chunked-prefill scheduling policies, or disaggregated prefill/decode — all of which introduce new batch-dependent selection points the current SelIR programs do not model?
