> **一句话总结：** GC-MoE 用 CUDA Green Contexts 在驱动层把设备 SM 静态切成一个小的通信分区和一个大的计算分区（B300 上 20/128，共 148 SM），把专家并行（EP）的 token dispatch 与 FP8×FP4 grouped GEMM 写成同一张 CUDA Graph 里两个**没有依赖边**的并发根节点，再用 generation 标记的 token ring 让 GEMM 在第一个 ring block 填满时就开始算、用按 parity 双缓冲的 receive counter 删掉每次 replay 末尾的跨 rank barrier；在 8×H20 上 DeepSeek-V4.1-Flash decode 平均 1.188×（峰值 1.296×@16 token/rank），8×B300 上 GLM-5.2 与 DeepSeek-V4.1-Flash 平均 1.106×（融合 shared expert 后 1.123×，峰值 1.209×），54 个测点全胜 DeepGEMM Mega MoE，但 256 token/rank 处增益收窄到 1.01–1.13×。

> **TL;DR:** A kernel-systems paper, not a modeling paper. Instead of DeepGEMM's Mega MoE — one persistent fused kernel that overlaps dispatch with GEMM by carving dispatch warps and their staging buffers out of *every* one of B300's 148 SMs, and that pays a cross-rank tag-2 barrier at the end of every replay — GC-MoE splits the device with CUDA Green Contexts into a 20-SM communication context and a 128-SM compute context, launches dispatch and grouped-GEMM as independent CUDA-Graph roots on disjoint SM sets, and removes the trailing barrier with parity-double-buffered receive counters. On 8×H20 (DeepSeek-V4.1-Flash, routed experts) it cuts slowest-rank per-layer decode latency from 442.7 µs to 341.7 µs at 16 tokens/rank — **1.296×** — with a 9-point mean of **1.188×**, but only **1.029×** at 256 tokens/rank; on 8×B300 the 18-point routed mean is **1.106×** (GLM-5.2 1.102×, DSV4.1-Flash 1.109×, best 1.189× at 1 token/rank) and **1.123×** with fused shared experts. Accuracy is matched at the BF16 output envelope (min cosine vs. Mega MoE 0.9999998 on the H20 routed suite). Read it if you build MoE decode kernels or care about green-context SM partitioning as a primitive; discount it for the fact that the H20 baseline is the authors' *own* SM90 port of DeepGEMM (the public release is SM100-only), and that the paper contains **no partition-size sweep and no overlap-on/off ablation**, so the 20-SM choice and the 1.19× attribution to partitioning specifically are both unverified.

## 核心贡献

- **把"算子内 SM 切分"做成第一类设计手段。** 以往 green context 的用法是进程间隔离、模型共置、prefill/decode 槽位隔离；本文第一次把 `cuDevSmResourceSplitByCount` + `cuGreenCtxCreate` 用在**单个 MoE 算子内部**，让 dispatch kernel 和 GEMM kernel 成为两个各自拥有独立 grid、寄存器预算、shared memory 预算和同步域的普通 kernel，而不是一个 CTA 里靠 warp specialization 硬塞进去的角色。作者明确说这是"to our knowledge"的首创，措辞克制。
- **指出融合式算子（Mega MoE）的三项结构性代价，并逐条消解。** (i) 每个 SM 上 4 个 dispatch warp 及其 staging buffer 要从寄存器文件和 SMEM 里抠出来，计算 warp 永远不拥有完整 SM；(ii) 同步域是整个 148-SM 阵列，prologue/tail grid sync 都要等最慢的 CTA；(iii) 所有角色共享一个 CTA 的 64 512 个寄存器和 227 KB SMEM，改一处就要保住其他角色的全部 barrier 和 buffer。GC-MoE 对应给出：专用通信分区、缩小到 20 SM（role1）/64 SM（role3）的 grid sync 域、每个 role 独立预算。
- **跨分区细粒度握手。** token ring 的四个持久信号（`l1_full_count`、`l1_empty_count`、64 位 `l2_full_mask`、`l2_empty_count`）带 generation tag，把基线的 block 粒度 handshake 搬到分区边界上，于是计算 kernel 在**第一个 ring block 填满**时就开始，而不是等 dispatch 全部结束；W2 的每个 K128 tile 只等它那两个 W1 N128 tile 的 bit，因此不需要 L1→L2 的额外 barrier。
- **删掉跨 rank 尾 barrier。** receive counter 按 parity 双缓冲：第 N 次 replay 消费 `N mod 2` 那一代，role3 在消费完计数并完成 grid sync 后翻转 parity，下一次 publish 就落到另一代；顺序由 tag-1 barrier 加 combine readiness 上的 release/acquire 链保证。这是把一次完整 NVLink 往返从**每次 replay 的**关键路径上拿掉，而不是拿掉一次性的启动开销。
- **双架构 FP8×FP4 grouped GEMM。** Blackwell 走 2-CTA `tcgen05.mma.cta_group::2.kind::mxf8f6f4.block_scale`，操作数交换（A=权重、B=激活），指令 N 取"有效 token 数向上取到 16"而非 padded block size，所以半满 block 只付按比例的成本；因为 CuTe DSL 公开的 block-scaled MMA 要求 A/B dtype 一致，作者用 inline PTX 绕过。Hopper 没有硬件 blockscale，走 register-A WGMMA + 寄存器内 FP4→E4M3 解码（两条 LDS.128 加 PRMT/LOP3），配合"窗口式"尺度重打包（按每个 expert 的 scale 极值取窗口基，最多 11 个指数步，越界幅值用 4-bit code space 查表精确右移 2 的幂，再记一个 per-expert 补偿因子）。
- **K128 tile 预打包权重。** 把每个 expert 的量化 FP4 矩阵从行主序 `[E, rows, K/2]` 重排成 K128-tile 连续的 `[E, kb, rows, 64]`，TMA 描述符编码 4-D box (128,128,1,1)，一次 TMA 就突发 8 KB 连续全局地址，而不是 128 段各隔一整行的碎片。作者诚实地说这是相对基线唯一的 GEMM 侧新增（gate/up 的 8 行交错、scale 行置换都沿用基线）。
- **shared expert 零成本融合。** shared W1 直接 alias 原激活 buffer（零拷贝，因为 shared expert 看得到所有本地 token，不需要 dispatch）；shared 激活 scale 通过一条显式行置换公式（Eq. 3）摆成与 routed 路径完全相同的 MN-major 布局，于是两条路径共用一个 TMA scale map 和一条 UTCCP 通路；shared 输出占 combine buffer 的第 k 条 lane，finalize 无需特例。
- **系统性评测 + 开源。** 8×H20 与 8×B300、两个生产级 MoE 配置（GLM-5.2、DeepSeek-V4.1-Flash）、每 rank 1–256 token 共 9 个 batch 点、routed 与 fused shared-expert 两套，合计 54 个测点全部更快；代码在 github.com/Bruce-Lee-LY/gc-moe 开源，版本与 commit 都钉死。

## Key Contributions

- **Intra-operator SM partitioning as a first-class design lever.** Prior green-context work uses the primitive for inter-process isolation, model co-location, or prefill/decode slot separation. GC-MoE is, to the authors' knowledge, the first MoE operator to use `cuDevSmResourceSplitByCount` / `cuGreenCtxCreate` *inside* one layer so that dispatch and grouped GEMM are two ordinary kernels with independent grids, register and shared-memory footprints, and synchronization domains, rather than warp-specialized roles crammed into one CTA budget.
- **A concrete diagnosis of monolithic fusion, with three named costs.** In Mega MoE the dispatch warps and their staging buffers are carved out of every SM's register file and shared memory, so compute warps never own a whole SM; the prologue and tail grid syncs span all 148 SMs on B300, so every phase waits on the slowest CTA; and all roles share one CTA's 64 512 registers and 227 KB of shared memory, so any local optimization must preserve every other role's barriers and buffers. GC-MoE answers each with a dedicated partition, a shrunken sync domain (20 SMs for role1, 64 for role3), and per-role budgets.
- **A cross-partition handshake at ring-block granularity.** Four persistent, generation-tagged signals per ring block (`l1_full_count`, `l1_empty_count`, a 64-bit `l2_full_mask`, `l2_empty_count`) carry the baseline's block-granular producer–consumer protocol across the partition boundary, so the compute kernel starts on the first filled block; each W2 K128 tile waits on exactly the two bits its two W1 N128 tiles set, which removes a separate L1→L2 barrier.
- **Removal of the inter-replay cross-rank barrier.** Receive counters are double-buffered by parity; role3 flips parity after consuming the counts and completing its grid sync, and ordering is carried by the tag-1 barrier plus a release/acquire chain on combine readiness. A full NVLink round trip leaves the critical path of *every* replay rather than of startup only.
- **Dual-architecture FP8×FP4 grouped GEMM.** Blackwell: 2-CTA `tcgen05` block-scaled MMA with swapped operands (weight as A, activation as B), N sized to the valid token count rounded to 16, scale factors moved by the dedicated UTCCP path (`tcgen05.cp.cta_group::2.32x128b.warpx4`, 512 B per K128 stage), emitted as an inline-PTX user op because CuTe's public block-scaled MMA demands matching A/B dtypes. Hopper: register-A WGMMA m64nNk32 on E4M3 with in-register FP4 decode (two LDS.128 plus PRMT/LOP3), per-K32 FMA scale application outside the MMA, a global ×64 headroom convention, and window-based scale repacking (window base from each expert's scale extremes, at most 11 exponent steps, exact power-of-two shifts via a 4-bit lookup table, plus a per-expert compensating factor).
- **K128 tile-prepacked FP4 weights.** Row-major `[E, rows, K/2]` is rewritten to `[E, kb, rows, 64]` so one TMA operation bursts a single 8 KB contiguous range instead of 128 segments spaced a full weight row apart. The authors are explicit that gate/up row interleaving and scale-row permutation follow the baseline, and that this packing is the only GEMM-side addition.
- **Fused shared experts at near-zero marginal cost.** The shared W1 GEMM aliases the original activation buffer (zero copy, no dispatch needed); shared activation scales are staged into the exact MN-major permuted layout the routed UTCCP path consumes, via an explicit row-index formula, so both paths share one TMA scale map; shared tasks enter the unified scheduler as `SharedLinear1/2` phases; and the shared output occupies lane k of the combine buffer so finalize needs no special case.
- **A systematic evaluation plus open source.** Two hardware generations, two production MoE configurations, nine batch points per sweep, routed and fused-shared-expert settings: 54 measured points, all faster than DeepGEMM 2.8.2 Mega MoE, with accuracy gated on cosine thresholds. Code, version (0.3.1, commit 9bdb81f) and baseline commit are pinned.

## Methodology

**The problem framing.** Under expert parallelism a MoE layer decomposes into (i) dispatch — an all-to-all that moves each token, its activation scales and routing metadata to the ranks owning its top-k experts; (ii) grouped GEMM 1 with SwiGLU in the epilogue; (iii) grouped GEMM 2; (iv) combine, the weighted reduction of the k partials back to source ranks. At decode each rank holds 1–256 tokens, so for GLM-5.2's 256-expert / 8-rank / top-8 configuration balanced routing gives T·k·P/E = T/4 tokens per expert — at one token per rank an expert receives 0.25 tokens on average and the padded M tile is almost entirely padding. The grouped GEMM is therefore bandwidth-bound (dominated by streaming FP4 weights and scales from HBM), while dispatch is latency-bound and needs very few SMs to saturate NVLink. The premise follows: a decode layer does not need the whole device for arithmetic, yet a single fused kernel spans all SMs and pays a device-wide sync.

**Green-context partitioning.** The runtime builds the context pair once per CUDA context and caches it thread-locally. It queries the device SM resource (SM count, minimum partition size, co-scheduling alignment), computes the compute target as ⌊(total − requested)/alignment⌋·alignment with `requested` = `GC_MOE_DISPATCH_SMS` (default 16), calls `cuDevSmResourceSplitByCount`, and receives the compute resource plus the complementary communication resource — so the split is **driver-aligned, not application-chosen**; on B300 (148 SMs) the default request yields 20/128. Balanced workqueues (`CU_WORKQUEUE_SCOPE_GREEN_CTX_BALANCED`, `wqConcurrencyLimit=1`) give each context its own hardware workqueue, which the authors flag as practically essential: without it two contexts can land on one workqueue and silently serialize the very kernels the design intends to overlap. The split is validated at runtime (≥32 compute SMs, even compute count, ≥2 dispatch SMs, sum equal to device SM count). Being static for the graph's lifetime makes replay deterministic — no kernel migration, dispatch SM count is a compile-time property.

**Graph structure.** One MoE layer = one replay of a child CUDA Graph with three kernel nodes ("roles"). role1 (dispatch) on the communication context performs routing accounting and the all-to-all pull into a local token ring. role2 (compute) on the compute context runs the routed and shared grouped GEMMs with fused SwiGLU and requantization and scatters BF16 partials directly to source ranks. role3 (finalize) on the compute context combines the k (+1 shared) partials. role1 and role2 are **concurrent roots with no dependency edge**, which is precisely what makes the driver schedule them simultaneously on disjoint SM sets; role3 depends on both and thereby absorbs the global completion condition. On SM90, fused shared experts add a fourth node (role4) that role2 may wait on.

**Token ring and scheduler.** All pulled tokens land in one globally reused ring of BM-token blocks rather than per-expert buffers. Ring capacity comes from a maximum-in-flight model: with per-rank capacity Tmax the maximum routed assignments are Tmax·P·min(k, e), the logical block pool is ⌈assignments/BM⌉ + e, and the live-block count is recomputed from the actual compute-partition SM count and L1/L2 cluster waves — so a graph never starts with an undersized ring. Each cluster's leader CTA runs a scheduler warp over phases (Linear1, Linear2, SharedLinear1, SharedLinear2) with a one-in-one-out discipline: every successful L2 claim publishes one more L1 task, and an L2 task is published only after all L1 tasks of its pool block. Task records are 32-byte descriptors broadcast to both CTAs of a cluster through distributed shared memory with transaction-count mbarriers and double buffering.

**Dispatch data path.** Six steps: warp-level token counting (32/k tokens per iteration) into shared-memory per-expert counters; a packed atomic add of `(1 ≪ 32) | count` where the high word counts (rank, dispatch-SM) contributors for arrival validation; a peer write of each token's routing entry into the target rank's source-index region; a grid sync after which block 0 publishes per-expert counts and prefix sums to every peer's receive counters; a two-phase NVLink tag-1 barrier (persistent, phase-encoded, with a configurable 3600 s timeout that traps rather than hangs); and a warp-walk over the expert-concatenated unpadded token sequence with lane-held per-rank count registers, warp reduction to locate each token's (src_rank, src_slot), and warp-private double-buffered SMEM staging for chunked bulk copies of FP8 activations and packed-scale rows, permuted into the MN-major row order the MMA path expects.

**Direct partial scatter and the three-node combine.** The W2 epilogue issues 16-byte BF16 stores straight into the source rank's combine buffer at (topk_slot, src_token); buffer recycling is governed by the `l1_empty`/`l2_empty` handshake, so the combine kernel only reduces, never gathers. role3 is one kernel with two concurrent halves: the first four warps publish combine readiness with a release system atomic (required even for ranks with no routed tokens), consume this generation's per-expert receive counts with an arrival check against `dispatch_sms · P`, flip `recv_parity`, and reset ring signals/counters/W1 bitmap for the next replay while the combine warps wait and reduce — so the bookkeeping adds no separate serial phase.

**Blackwell GEMM path.** Fixed BN = BK = 128; each CTA of a 2-CTA cluster owns half the BM rows; the TMEM allocation is 2BM accumulator columns plus scale columns, capped at 512. Each K128 stage is issued as four K32 MMAs whose scale-factor byte selector picks the corresponding K32 group; for the (1,128,128) shared recipe weight scales are staged once per four K128 blocks. The BM heuristic on the host picks from {16, 32, 64, 96, 128, 192, 240} using the expected tokens per expert m̂ = T·P·k/E and its standard deviation, covering m̂ + √m̂ at the largest candidate; small batches pin BM = 16–32.

**Implementation.** Python against NVIDIA's CuTe DSL (CUTLASS DSL 4.8.1), JIT-compiled per configuration to PTX and assembled by ptxas 13.2, with `--opt-level 3`, register-usage level 10, FMA on, and relocatable device code rejected. Two caches sit above the assembler (binary cache keyed on compiler identity plus kernel attributes/resources/tensor metadata but never CUDA addresses; capture-key cache additionally keyed on context, green partition, and all pointer/shape/timeout arguments). Because CUDA Graph nodes hold kernel parameters by value, a post-generation PTX rewrite converts the peer descriptor into a 592-byte `.b8` formal (base, 72 int64 offsets, rank index) and each of 18 tensor maps into a 128-byte-aligned by-value formal, rewriting every param-space address through `cvta.param.u64` and failing closed if the PTX shape changes. Device code is 1935 lines for SM103 and 1305 for SM90.

**Evaluation protocol.** 8×H20 (Hopper, sm_90a) and 8×B300 (Blackwell, CC 10.3, 148 SMs, sm_103f); CUDA 13.2 / ptxas 13.2.78, PyTorch 2.11.0, DeepGEMM 2.8.2+fcad603, GC-MoE 0.3.1. Baseline on B300 is the public `fp8_fp4_mega_moe`, invoked in fused shared-expert mode when shared experts are on, so that comparison is feature-matched; because the public release ships only the SM100 kernel, the H20 baseline is the authors' own `sm90_fp8_fp4_mega_moe` reference port, which has no fused shared-expert path. Both operators run under CUDA Graph replay with identical inputs, capacities and weight transformations. Each window replays the graph 100 times and reports CUDA-event elapsed / 100; 10 warmup windows, 30 measured windows, L2 flushed and synchronized between windows; each rank reports its window median and a point's latency is the **maximum across the eight ranks** (slowest rank). Reported means are arithmetic means of per-point ratios, not ratios of means. Runs are gated on idle GPUs (0% utilization, ≥51 200 MiB free over three samples spanning ten seconds).

## Results & Highlights

- **H20 routed decode (DeepSeek-V4.1-Flash, 9 points): mean 1.188×, peak 1.2957× at 16 tokens/rank.** Slowest-rank per-layer latency goes from 442.722 µs (Mega MoE) to 341.689 µs; the 8-token point is nearly identical at 368.254 → 284.310 µs (1.2953×). The curve rises from **1.0425×** at 1 token/rank (120.061 → 115.161 µs) to a 1.26–1.30× plateau at 4–32 tokens/rank, then decays to **1.0291×** at 256 (695.010 → 675.370 µs) — the paper's own framing is that at 256 weight streaming dominates and only the roughly fixed shared-SM and tail savings remain.
- **B300 routed decode (18 points): overall mean 1.1059×, GLM-5.2 1.1024×, DeepSeek-V4.1-Flash 1.1094×, per-point range 1.0846–1.1893×.** Best point is DSV4.1-Flash at 1 token/rank: 70.630 → 59.387 µs (**1.1893×**, an 11.2 µs saving on a ~70 µs layer). GLM-5.2 improves *with* batch instead: 64.184 → 58.601 µs at 1 token (1.0953×) growing to 164.383 → 145.683 µs at 256 (1.1284×), consistent with a dedicated-SM GEMM advantage that scales with grouped-GEMM work rather than with the fixed tail. Crucially the compute partition has 128 SMs versus the baseline's 148, so **none of the B300 win comes from more arithmetic capacity**.
- **Fused shared experts, B300 (feature-matched, 18 points): overall 1.1230×, GLM-5.2 1.1306×, DSV4.1-Flash 1.1154×, peak 1.2092×.** The peak is DSV4.1-Flash at 1 token/rank (73.541 → 60.816 µs). Note how close this is to the routed number (1.106 → 1.123): against a baseline that *also* fuses shared experts, fusion buys about 1.5 points of mean speedup.
- **Fused shared experts, H20 (9 points): 1.1880× mean versus the unfused Mega baseline, peak 1.3533× at 8 tokens/rank** (409.599 → 302.667 µs). But this comparison is *not* feature-matched — the H20 reference port has no fused shared-expert path, so the baseline is routed Mega plus a separate shared-expert kernel. The within-operator ablation is the honest number: gc-se is **1.0307×** faster than gc-unfused on average (6 of 9 points), and it is actually **slower** at 32 (0.9854×), 64 (0.9852×) and 128 tokens/rank (0.9728×) — the regime where the scheduler places shared tasks after routed work.
- **Effective throughput moves with the overlap at every point.** On H20 at 8 tokens/rank, effective TFLOPS rises 73.805 → 95.597 (**+29.5%**, near the 1.296× peak); at 256 tokens it is 1 251.393 → 1 287.785. The analytic HBM working-set bandwidth model peaks at 14 973.9 → 18 931.9 GB/s at 32 tokens/rank (**+26.4%**). On B300, GLM-5.2 reaches 7 524.828 → 8 490.679 TFLOPS at 256 tokens (**+12.8%**) and even at 1 token improves 75.280 → 82.453.
- **The NVLink payload is identical by construction, and its modeled bandwidth still rises.** At the largest H20 batch the one-way payload bandwidth goes 239.719 → 246.690 GB/s (+2.9%) — the same bytes move in less wall time because dispatch no longer competes with the GEMM for SMs and each replay skips the trailing cross-rank barrier. This is the paper's cleanest evidence that the partition does not cost cross-rank bandwidth.
- **Accuracy is matched at the BF16 envelope, and the match is almost suspiciously exact.** On the H20 routed suite, 47 cases × 8 ranks = 376 rank-checks all pass (cosine ≥ 0.97 vs. BF16 for both operators, ≥ 0.97 GC-vs-Mega). Minimum cosine GC/BF16 is 0.977039 (default), 0.977672 (boundary), 0.977837 (asymmetric) — **identical to Mega's own numbers to six digits**; minimum GC-vs-Mega cosine is 0.99999976. Maximum absolute error is 0.109375 for both operators and maximum relative L2 is 0.00600836286321 for both. The H20 shared suite passes all 47 cases with cosine ≥ 0.99 and minimum GC-vs-Mega 0.9999997; on B300 all 94 cases and 752 rank checks pass (≥ 0.97 routed, ≥ 0.99 shared).
- **Per-rank spread is tight, so the speedup is not a straggler artifact.** At 1 token/rank for DSV4.1-Flash on B300, GC-MoE's eight rank medians span 59.21–59.39 µs and the baseline's span 70.22–70.63 µs — the reported speedup uses the slowest rank, which is the conservative choice.

## Authors & Credibility

Three authors — Yong Li, Kan Liu, Tao Lan — all at Alibaba (`@alibaba-inc.com`), with an open-source artifact at github.com/Bruce-Lee-LY/gc-moe. No university affiliation and no prior-publication track record is visible from the PDF alone, so credibility here has to be earned from the artifact and the experimental hygiene rather than from institutional reputation. It largely is: the paper pins CUDA 13.2 / ptxas 13.2.78 / PyTorch 2.11.0 / CuTe 4.8.1 / DeepGEMM 2.8.2+fcad603 / GC-MoE 0.3.1 (commit 9bdb81f), states the exact baseline entry points (`fp8_fp4_mega_moe`, `num_shared_experts=1`), defines the measurement protocol down to warmup and measured window counts, and — unusually — pre-commits to the slowest-rank statistic and to "mean of per-point ratios, not ratio of means," both of which are conservative. The paper also volunteers its own weaknesses in the Limitations section (no partition-size ablation, no overlap-on/off comparison, single-instance workspace) rather than hiding them, and repeatedly marks which mechanisms are inherited from DeepGEMM versus added here ("The Blackwell-specific contribution is therefore not the instruction pattern … but the scheduling around it"). That kind of attribution discipline is rarer than it should be in kernel papers. Against this: the strongest numbers in the paper (1.296×, 1.353×) come from H20, where the baseline is the authors' own reimplementation of a design that has no public SM90 release, so the artifact cannot independently settle whether that port is a faithful stand-in for what DeepSeek would ship. The commercial context (Alibaba serving its own MoE models; GLM-5.2 and DeepSeek-V4.1-Flash are both third-party models being used as workloads, which is a point in favor of neutrality) does not obviously bias the numbers, but the H20 baseline asymmetry is a real confound that only external reproduction can resolve.

## Critical Assessment

**Novelty.** The genuine contribution is narrow but real: using green contexts *inside* an operator to give communication and compute disjoint SM sets, and then rebuilding the producer–consumer protocol so it works across that boundary. The authors do not oversell this — they state plainly that operand swapping, valid-M N sizing and the UTCCP scale path follow the baseline, that gate/up interleaving and scale-row permutation follow the baseline's weight transform, and that the only GEMM-side addition is K128 tile prepacking. That honesty makes the remaining claim (the partition plus the barrier removal) easier to trust, and the barrier removal in particular is a clean idea: parity-double-buffering the receive counters so the tag-2 barrier leaves *every* replay's critical path, not just startup, is the kind of change that looks obvious only after someone writes it down.

**The missing ablation is the paper's central weakness.** GC-MoE bundles four independent changes: (a) green-context SM partitioning, (b) the tag-2 barrier removal, (c) K128 weight prepacking, and (d) a shrunken grid-sync domain. The paper reports **no overlap-on/off comparison and no partition-size sweep** — the authors admit this in Limitations, and the only within-operator ablation is fused-versus-unfused shared experts. So the headline "1.188× from partitioning" cannot be decomposed. Worse, the 20-SM dispatch partition is the design's single most consequential parameter and it is never varied: no 8-, 12-, 24- or 32-SM comparison, no plot of speedup versus dispatch SM count, no measurement of where the curve turns over. The justification offered is analytical ("the grouped GEMM is bandwidth-bound, so 128 SMs suffice") plus one indirect data point (128 dedicated SMs beat 148 shared SMs). That is an argument, not a measurement, and it is exactly the experiment a reader would want before adopting the design. A cheap version — sweep `GC_MOE_DISPATCH_SMS` over four values on one model at three batch sizes — would have cost a page and settled the question.

**The H20 baseline is a self-built reference port, and it carries the paper's biggest numbers.** "The public release ships only the SM100 kernel; for H20 we built an SM90 reference port of the same design." Every H20 result — including the 1.296× peak and the 1.353× shared-expert peak that the abstract leads with — is measured against code the authors wrote themselves. A port that misses one optimization in the baseline inflates every ratio on that platform, and there is no cross-check against any independently produced Hopper MoE kernel (no DeepEP-based pipeline, no published SM90 fused MoE from another group). The B300 numbers, where the baseline is the official `fp8_fp4_mega_moe`, are the trustworthy ones — and they are noticeably smaller: 1.106× routed, 1.123× fused, best point 1.209×. The gap between the H20 headline (1.19× mean, 1.30× peak) and the B300 headline (1.11× mean, 1.19× peak) is large enough that a skeptical reader should treat the B300 numbers as the real effect size and the H20 numbers as an upper bound.

**The H20 shared-expert comparison is not feature-matched, and the arithmetic shows it.** On H20 the baseline has no fused shared-expert path, so 1.353× compares a fused GC-MoE against an unfused baseline. Decomposing: the within-operator fusion gain is 1.0307×, so the operator-only gain on that suite is roughly 1.188/1.031 ≈ **1.15×**, not 1.19× — and the 1.353× peak is substantially a fusion win, not a partitioning win. The tell is cross-platform: on B300, where both sides fuse, the shared-expert mean (1.123×) sits only ~1.5 points above the routed mean (1.106×); on H20 the same transition jumps from 1.188× to 1.353×. The paper does disclose this in the abstract parenthetical and in §6.3, which is to its credit, but the headline number still travels without the caveat.

**The accuracy claim is weaker than it looks.** "Matched numerical accuracy" is established by showing that GC-MoE and Mega MoE both hit cosine 0.977039 against BF16 — but that identity is nearly tautological: both consume the caller's identically quantized activations and the baseline's identically quantized weights and perform the same low-precision arithmetic, so the dominant error term is shared quantization, not kernel scheduling. The fact that max absolute error is **exactly** 0.109375 and max relative L2 is **exactly** 0.00600836286321 for both operators confirms this reading: the metric is saturated by the common quantization and cannot resolve kernel-level numerical differences. The more informative check is the processed-difference against an FP32 dequantized reference (1 − 2⟨y,ŷ⟩/(‖y‖²+‖ŷ‖²)), but it is reported only as a pass/fail against a 0.002 threshold, not as a distribution. And the accuracy evidence is thin on Blackwell: Table 11 covers only H20 routed, with the H20 shared suite and the entire B300 accuracy campaign compressed into one sentence ("all 94 cases and 752 rank checks pass") and no table — odd, since B300 is where the novel `mxf8f6f4` inline-PTX path and the UTCCP scale staging actually live.

**Scale and deployment gaps.** Every experiment is a single 8-GPU node with all peers on NVLink. The operator supports up to P = 72 ranks (a 72-entry by-value peer table), but nothing tests what happens when dispatch crosses InfiniBand: the whole premise — dispatch needs few SMs to saturate the link, and its latency is a short critical path — is calibrated to NVLink, and the 20-SM partition size would almost certainly need retuning for a multi-node fabric where per-message latency is several times higher. Relatedly, green contexts take SMs away from the rest of the process; the paper does not discuss co-existence with other tenants, what happens if another process already holds SMs, or interaction with MPS/MIG — all of which matter for the "integrate into a serving stack" future work it proposes.

**Minor issues worth flagging.** (i) The minimum-cosine-against-baseline figure drifts across the paper — Table 11 and §6.5 give 0.99999976 / 0.9999998 for the routed suite, the Conclusion says 0.9999997 "on both measured H20 suites", and the abstract writes "≥ 0.9999997" for both — trivial, but a reminder that these seven-digit figures sit at the float32 resolution limit and should not be over-interpreted. (ii) "Beats Mega MoE at all 54 measured points" is true but the 54 points are 9 token counts × 2 models × 2 shared settings × 2 platforms, i.e. four sweeps of a one-dimensional parameter — not 54 independent wins, and the sweep includes points where the margin is 1.01×. (iii) The effective-TFLOPS and HBM/NVLink bandwidth figures are analytic models, not hardware counters (the authors say so explicitly), so they corroborate rather than independently verify the latency measurements. (iv) The 256-token/rank regime — arguably the most common decode batch in production serving — shows only 1.029× on H20 and 1.089× on B300, which is a modest return for a design that requires driver-level SM partitioning, CUDA 12.4+, and a bespoke three-node graph.

## Strengths

- **A real, well-motivated systems insight.** The observation that a bandwidth-bound decode GEMM does not need all SMs, while dispatch needs SMs but no tensor cores, is the kind of reframing that unlocks a design space rather than optimizing within one. Partitioning at the driver level instead of by warp specialization follows naturally once stated.
- **The barrier removal is the best single idea in the paper.** Parity-double-buffered receive counters turn a per-replay cross-rank round trip into a generation flip. It is cheap, general, and would be useful even without green contexts.
- **Unusually honest attribution.** The paper repeatedly marks what is inherited from DeepGEMM (operand swap, valid-M N sizing, UTCCP path, gate/up interleaving, EVICT_FIRST hints) versus what is new (partitioning, ring protocol across partitions, K128 prepacking, the Hopper register-decode path). This makes the contribution legible and the claims checkable.
- **Strong experimental hygiene.** Pinned versions and commit hashes, slowest-rank latency (conservative), mean-of-ratios rather than ratio-of-means (conservative), idle-GPU gating, L2 flush between windows, 10 warmup + 30 measured windows of 100 replays each, and a per-rank spread reported to show no straggler artifact. The protocol section is better than most kernel papers'.
- **Dual-architecture engineering depth.** The Hopper path is not a port of the Blackwell path — no hardware blockscale exists there, so the authors built register-A WGMMA with in-register FP4→E4M3 decode, window-based scale repacking with exact power-of-two shifts and per-expert compensation, and a ×64 headroom convention. That is real work, and the paper explains *why* each piece is needed rather than just listing it.
- **Fusion that genuinely costs nothing at small batch.** Aliasing the activation buffer, staging shared scales into the routed path's own permuted layout, and parking the shared output in lane k of the combine buffer are three small decisions that together make one shared expert nearly free at small batch (1.031× mean, and the dips at 32–128 tokens are disclosed rather than hidden).
- **Open source with reproducible build identity.** Compiler-identity hashing, binary and capture-key caches, PTX by-value parameter rewriting that fails closed on shape change — this is production-grade infrastructure, and it is published.

## Limitations

- **Decode-only.** Prefill-sized token counts are supported but the compute partition, not the overlap, becomes the binding resource. At the largest measured batch (256 tokens/rank) the gain narrows to 1.01–1.13×, so the operator's value proposition evaporates exactly where MoE serving spends most of its FLOPs.
- **No partition-size sweep and no overlap-on/off ablation.** Stated by the authors. The 20-SM choice, and the causal attribution of the speedup to partitioning, are therefore both argued rather than measured. The fused-versus-unfused shared-expert comparison is the only within-operator ablation.
- **Single-node evaluation only.** 8 GPUs, all NVLink peers. The 72-rank peer table is supported but never exercised; multi-node InfiniBand behavior — where dispatch latency dominates differently and partition sizing would need retuning — is untested.
- **Asymmetric baselines.** The H20 baseline is the authors' own SM90 reference port (public release is SM100-only), and the H20 shared-expert baseline is unfused while GC-MoE is fused. Both are disclosed, but they mean the largest speedups in the paper rest on the least independently verifiable comparison.
- **Hard shape constraints.** I ≤ 4096 with I mod 128 = 0 (64-bit W1 completion bitmap and K128 tiles); H mod 256 = 0 (2-CTA N128 pairing); k + 1[shared] ≤ 32 (one warp lane per combine slot); E ≤ 2048 global and ≤ 512 per rank with E mod P = 0 (static signal sizing); P ≤ 72; BM restricted to {16, 32, 64, 96, 128, 192, 240}; routed recipe fixed to (1,1,32). Many production MoE shapes will not fit without rework.
- **Single-instance workspace.** Calls that share it must be serialized — a real constraint for a serving stack that wants concurrent requests, and the paper does not quantify what serialization costs.
- **Platform coupling.** Requires CUDA 12.4+ green contexts, a Hopper (sm_90a) or Blackwell (sm_103f) target, CUDA 13.2 toolchain, CuTe DSL 4.8.1, and one process per GPU with peer-accessible devices. Reproducing on a different driver or GPU generation is not a small lift.
- **Accuracy evidence concentrated on H20.** B300 accuracy is a single sentence with no table, despite B300 being where the inline-PTX `mxf8f6f4` path and UTCCP staging live. The reported cosine identities against BF16 are saturated by shared quantization and cannot resolve kernel-level differences.

## Relevance

命中 **Compute Infrastructure for Large-Scale ML**（算子是本文的正题：MoE decode 的 dispatch/GEMM overlap、CUDA Graph、green context SM 切分、NVLink 跨 rank 握手），同时与 **Reliability under Extreme Performance Optimization** 有实质交集——FP8×FP4 混合精度 grouped GEMM 的双架构实现、Hopper 上用窗口式尺度重打包 + 寄存器内解码替代缺失的硬件 blockscale，以及"精度是否被调度改动破坏"的验证方式，都是低精度算子正确性问题。对做推理可靠性的人，这篇最值得记的两点：一是它把"数值一致性"证成了 cosine 与 BF16 相同（但这恰恰说明该指标被共享量化饱和、分辨不出 kernel 差异），二是它用 parity 双缓冲消除了每次 replay 的跨 rank barrier——这类"把同步从热路径上拿掉"的手法，和 SDC/静默错误检测里"如何在不引入额外同步的前提下观测状态"是同一类工程问题。

## Questions for Further Exploration

1. **How sensitive is the speedup to the dispatch partition size?** The paper fixes 20 of 148 SMs and never sweeps it. Is there a knee, or does 8 SMs perform equally well (which would make the design much cheaper to adopt)? Does the optimum shift with model shape, top-k, or token count?
2. **What is the attribution among the four bundled changes?** A 2×2 of {green-context partition on/off} × {tag-2 barrier on/off} at one batch size would separate the partition's contribution from the barrier removal's — currently both are credited to "the partition."
3. **Is the SM90 reference port a faithful baseline?** The 1.296× and 1.353× headlines rest on it. An independent Hopper fused-MoE implementation (or DeepSeek publishing an official SM90 kernel) would settle whether the port leaves performance on the table.
4. **What happens on multi-node InfiniBand?** Dispatch latency across a fat-tree is several times the NVLink round trip; does the 20-SM partition still suffice, and does the tag-1 barrier plus the release/acquire combine-readiness chain remain the critical path or does it get swamped?
5. **Why is the accuracy evidence thin on B300?** The inline-PTX `mxf8f6f4` path with UTCCP scale staging is the most novel numerical machinery in the paper, yet B300 accuracy is one sentence. A per-category table for B300 (as in Table 11) would be far more informative than the H20 table, whose cosines are identical to the baseline's because both share quantization.
6. **Does green-context partitioning compose with other tenants?** What happens when another process already occupies SMs, or when the operator runs under MPS/MIG? Does the driver refuse the split, silently degrade the partition, or fall back?
7. **Is the design orthogonal to DeepEP-style communication kernels?** The paper claims composability with framework-level overlap (Lina, FasterMoE, DeepEP) but never tests a GC-MoE layer inside a real serving engine under concurrent request load, where the single-instance workspace serialization would actually bite.
8. **How does the K128 weight prepacking interact with weight-loading cost at model scale?** The transform is done once per weight set on the caller's stream, but for a 256-expert model the prepacked footprint and transform time are not reported.
