> **一句话总结：** 论文指出长程 Agent 的 KV 驱逐目标（"后续要用的 token 还在缓存里"）即使 99.6% 达成也不够——真正决定成败的是这些 token 与 query 之间的**旋转位置距离**；PACE 用"计划感知保留"（把 planner 的依赖 DAG 变成压过一切注意力分数的前瞻加分）+ "有界位置"（按序重编号保留 token 并精确重旋转 key，使旋转距离恒 ≤ 8K）两件套，在 Qwen3-8B 的 100K token 编码会话、2,048 token 预算下把隐藏单测通过率从 H2O 的 42% 提到 97%（SnapKV 仅 3%），单用任一半只有 63%；在单张 24 GB L4 上 1M/2M token 会话（定义写在 0.9M/1.8M token 之前）仍达 99%/100%，KV 状态 < 0.7 GB 而全缓存需 147–295 GB。

> **TL;DR:** The paper separates two things KV-eviction work conflates — *residency* (is the needed token still in the cache?) and *retrievability* (can the model actually use it where it sits in rotary-position space?). A planner-guided policy keeps 99.6% of needed tokens resident in 100K-token coding sessions on Qwen3-8B (budget 2,048) yet its hidden-unit-test pass rate decays from 93% to 64% as the definition-to-use gap grows 2K→90K tokens, because the RoPE distance grows with it; pooling all 225 probes of the three PACE-family arms, residency is flat at 0.995–0.996 while accuracy falls from 96–100% (<8K) to 69–77% (>16K). PACE fixes this by renumbering kept tokens whenever positions approach L=8,192 and re-rotating their keys exactly (RoPE's `R_a R_b = R_{a+b}` makes this algebraically lossless), so the query-to-definition gap stays 2.7–6.5K regardless of session length. In the pre-registered 100K run it passes 145/150 checks (97%, 28/30 probes fully passed, 100% fact recall) vs 42% for H2O, 63% for either component alone, and 3% for SnapKV; at 1M tokens 74/75 (99%) vs 33% for bounded positions without foresight, at 2M tokens 75/75 vs 13%. Cost: +9% wall time (1,047 s vs 963 s over ten sessions) and no measurable perplexity change (ΔNLL −0.003 nats).

## 核心贡献

- **一个可测量的负面结论：residency 不等于 retrievability。** 在 100K token 编码会话、2,048 token 预算（会话的 2%）下，一个由 agent 自身计划引导的保留策略在每个 gap 上都保持 99.6% 的所需 token 常驻，但准确率随"定义被写下"到"被使用"的距离从 2K 增到 90K 而从 93% 掉到 64%。把三个 PACE 家族 arm 的 225 个 probe 按重建出的旋转距离分箱后，residency 在每一箱都平在 0.995–0.996，通过率却从 8K 以内的 96–100% 降到 16K 以上的 69–77%——**跟着通过率走的是位置距离，不是保留策略**。
- **PACE 系统：把"留谁"和"留在哪"一起控制。** (1) *计划感知保留*：agent planner 本来就会产出步骤依赖 DAG，把它作为 blueprint 送进 serving 层，转成 span 级前瞻加分 β_t，加在 token 的累积注意力分数上；(2) *有界位置*：每层保留槽维护物理位置 p，当下一位置逼近上限 L 时把常驻行按逻辑序重编号到 {0,…,R−1}，并用引擎自己的 cos/sin 表把每个 key 精确重旋转（Proposition 1，由 Eq. 1 直接得证），位置永不越界；(3) *持久会话*：每步只发新增 token，驱逐决策跨步存活；(4) *分层再水化*：被驱逐行下沉到 host RAM → 本地盘 → 远端 Valkey，planner 前瞻发现缺口时从最近层恢复。
- **一个只在极长会话才暴露的数值 bug 及其修复。** key 以 bf16 存储，每次重编号重旋转就多一次舍入，而 planner 保护的 key 恰恰是活得最久的那些。模拟 1M 会话的累积舍入后，同一批任务从 100% 掉到 84%（63/75，未过预注册的 90% 门槛）。修法：每个 key 首次重编号时复制进 fp32 参考存储并记下有效位置，之后所有位置都由该副本导出——60 次位置变更后最大相对 key 误差 0.003，而直接重旋转存储 key 是 0.031；同一压力下恢复 75/75。
- **一个执行打分、预注册的长程 benchmark 协议。** 会话由 3 个定义步（随机化的类名/字段名/费用常数/异常码/取整模式/quantum）+ 大量 ~2,000 token 的 Python 标准库源码填充步 + 3 个 probe 组成；probe 代码在子进程里跑隐藏单测（p1 7 项、p2 3 项、p3 5 项），另有独立的 recall 指标，从而把"忘了"和"写错了"分开。30 个种子给 30 份不同规格，自动检查 probe 文本不泄露任何采样值；8K 无驱逐对照在 Qwen3-8B 上 100% 通过，说明长会话的失败可归因于缓存。
- **规模证据到 2M token。** 单张 24 GB L4：1M token（定义在 ~894K token 之前）74/75 checks、14/15 probe 全通、125/125 事实召回，0.3 GB 常驻 KV + 至多 0.3 GB 参考存储；2M token（定义在 1.8M 之前）75/75、15/15、125/125，全缓存则需约 295 GB。
- **诚实的负结果。** Mistral-7B-Instruct-v0.3 的编码能力天花板只有 40%（无驱逐对照），PACE 贴在天花板上（45/49/37% vs 40%）但**无法在 test-pass 上显著超过 retention-only**（D=90K：46% vs 36%，6 胜 4 负，p=0.75）；作者明确写"bounded positions 对 retention-only 的统计优势只在 Qwen3-8B 上成立"。

## Key Contributions

- **A reframing of the eviction objective.** Prior work (H2O, SnapKV, StreamingLLM, and the agent-aware line KVFlow/ActKV/MemDecay/CacheScout) all maximize residency ρ_t = |N_t ∩ C_t|/|N_t|. The paper shows ρ_t ≥ 0.99 is insufficient and adds a second controlled quantity, the rotary gap Δ_t = m̂_t − p(N_t) — the distance *as the model sees it* — and demonstrates accuracy tracks Δ_t at fixed ρ.
- **Two mechanisms that are individually necessary and jointly sufficient**, with the interaction analyzed rather than asserted: at L=40K foresight adds 5.9 pts with positions as written and 33.5 pts with bounded positions (interaction +27.6 pts, 95% CI [+12.0, +42.1], p=0.0014); at the recommended L=8K the interaction is +8.3 pts (CI [−8.0, +23.8], p=0.32) and the authors explicitly decline to claim super-additivity there.
- **Exact, cheap re-rotation** with a proof that re-rotating a cached key by the position delta yields bit-equivalent semantics to caching it at the new position, implemented against the engine's own frequency table so it composes with linear/YaRN/Llama-3 scaling and partial/interleaved layouts.
- **A capacity rule for the position limit:** L > B_max + H, and *smaller is better* — L=8,192 (the smallest admissible power of two for B=2,048 + 4,096-token chunks) keeps the gap at 2–7K, while L=40,960 (the model's native range) still leaves ~24K gaps and measures worse (56%/64%/93% at matched ~24K gap).
- **A serving design that makes eviction matter at all:** without persistent sessions an agent re-sends its transcript each step, silently re-inserting evicted tokens, so "eviction quality never matters across steps" and prefill cost grows quadratically. Persistence cuts prefilled tokens 5.5× and wall time 4.3× on a 16K session.
- **A pre-registration and integrity protocol** that is unusually explicit for a systems paper: fingerprints of every instruction template stored in each result file, a merge tool that refuses to pool runs with different wording/engine settings, separately reported trials after a probe rewording, and a documented filler-regime change discovered by checksumming paired prompts.

## Methodology

**Setup.** PACE is implemented as a subclass of the H2O cache manager in SparseEngine (Apache-2.0), toggled by a config switch, so PACE and H2O share prefill, eviction schedule and decode path; with all three features disabled it reproduces H2O token for token. An OpenAI-compatible server accepts the blueprint as an extra request field and exposes persistent sessions. All arms share B = 2,048 tokens (4 sink + 128 recent), greedy decoding, persistent sessions, and the eager decode path. Primary model Qwen3-8B (native range 40,960); second model Mistral-7B-Instruct-v0.3 (32,768). One NVIDIA L4 (24 GB) + 128 GiB host RAM.

**Plan-aware retention.** The planner sends a blueprint: segments naming earlier messages plus the future steps that will read them. The serving layer renders the chat template, locates each message's token span, and builds a forward-reference table (a, b, F). A token whose next planned reader is s⋆ = min{s ∈ F : s ≥ t} receives β_t = σ(1/2 + ½e^{−λ(s⋆−t)}) with λ = 0.35, added to its cumulative attention score; unreferenced tokens get 0. σ = 10⁵ gives a floor of σ/2 = 50K, which exceeds every cumulative attention score observed (max 25K at 2M tokens), so every referenced token outranks every unreferenced one; among referenced tokens the soonest-needed ranks highest — Belady's rule when protected spans exceed the budget. A span's bonus drops to zero once its last planned reader has run.

**Bounded positions.** Per resident slot a physical position p; per sequence a shift c with m̂ = m − c for new tokens. When the next physical position would come within headroom H of L (checked after each eviction), the resident row of each layer is renumbered to p′ ∈ {0,…,R−1} in logical order, each kept key re-rotated from p to p′, and c advanced so the next token continues at m̂ = R. Renumbering is order-preserving and gap-collapsing: kept tokens keep relative order, gaps left by evicted tokens vanish, and between renumbers ordinary relative distances apply. R_{p′−p} is computed from the engine's cos/sin tables as cos((p′−p)θ_i) = cos(p′θ_i)cos(pθ_i) + sin(p′θ_i)sin(pθ_i) (and the sine analogue), normalized to unit length, so it matches the engine's rotation convention and any frequency scaling it applies.

**Non-compounding re-rotation.** Keys are bf16; naive re-rotation of the stored key accumulates one rounding per position change, and planner-protected keys are exactly the long-lived ones. PACE copies each resident key into a reference store at its first renumber, along with the position it is valid at, and derives all later positions from that copy in fp32 (4,096 tokens/layer, 0.3 GB for Qwen3-8B; entries invalidated on slot reuse, moved on row compaction, and checked against the stored key before use).

**Benchmark.** Three definition steps (dataclass with randomized class/field names, two fee constants, exception with constructor code; a status class with three randomized members; a fee rule with randomized rounding mode and quantum) then filler steps each pasting ~2,000 tokens of Python 3.12 stdlib source and asking for its first function name, then three probes: fee_for(entry) (p1), settle(entries) (p2), and the complete module (p3). Scoring executes the answer against hidden tests in a subprocess; p1/p2 inject the reference classes before and after the answer so only recall of names/values/rules is tested; p3 is standalone with a fixed import prelude. An independent recall metric checks each session fact, letting every probe be classified as pass / failed-with-facts-recalled (coding error) / failed-with-facts-missing (forgetting). Two layouts: *single* (definitions 20% into a 100K session, probes at ~52K/74K/98K) and *distance* (session fixed at 100K, only the gap D varies).

**Statistics.** Unit of analysis is a (session, probe) pair scored as fraction of checks passed; paired comparisons on identical sessions use a two-sided sign test, full-pass rates Fisher's exact, two-factor interaction a sign-flip permutation test with bootstrap CIs. Pre-registered: headline comparison, second-model analysis, drift verification, and the 1M/2M evaluations.

## Results & Highlights

- **Headline (pre-registered, 100K tokens, Qwen3-8B, B=2,048, ten fresh sessions × 3 probes):** PACE passes 145/150 hidden-test checks (97%) and fully passes 28/30 probes with 100% fact recall, against H2O's 63/150 (42%, 7/30 full, 83% recall); paired on identical sessions PACE is better on 22 probes, worse on none (p < 10⁻⁶). SnapKV, on five further fresh sessions with the same budget, passes 2/75 checks (3%) versus H2O's 30/75 (40%; 11 worse, 1 better, p = 0.006) with 5% fact recall.
- **Ablation shows both halves are required, and they fix different failures:** retention only and positions only each reach exactly 94/150 (63%, p = 0.002 and p = 0.004 vs H2O) and tie each other (8 better, 6 worse, p = 0.79), while PACE beats retention only 17/0/13 (p = 1.5×10⁻⁵) and positions only 19/1/10 (p = 4.0×10⁻⁵); on the hardest probe p3, full-pass is 9/10 for PACE vs 1/10 for either single component. Failure taxonomy explains why: with positions only the details are simply gone (the quantum missing in 20 of 30 answers, the rounding mode in 14); with retention only residency is 1.000 but tokens sit 30–80K positions away, and 8 of its 18 failed probes contain *every* session fact and still apply them wrongly.
- **The distance sweep isolates the mechanism (100K tokens, five sessions per D, same seeds):** retention only decays 93% → 76% → 76% → 77% → 64% as D goes 2K → 90K at residency 0.992–0.996, while PACE at L=8K holds 97%/97%/100%/100%/100% with a reconstructed rotary gap of only 2.7–6.5K; H2O fails at every gap including 2K (44–55%, recall 76–83%) because a 2,048-token budget cannot survive one filler file. The L=40K arm is the control that proves the *limit* matters: it leaves 10.7–24.7K gaps and scores 100%/97%/56%/64%/93%.
- **Length scaling on one 24 GB L4:** 300K tokens — PACE 45/45 checks with every fact recalled vs 58%/79% recall for positions only and 0%/11% for a StreamingLLM-style arm; 1M tokens (definitions ~894K back) — 74/75 (99%), 14/15 probes fully passed, 125/125 facts, vs 33%/74% for positions only and 0%/8% for StreamingLLM (all 15 probes better, p = 6×10⁻⁵, ~13.6 min per session); 2M tokens (definitions 1.8M back) — 75/75, 15/15, 125/125 vs positions only collapsing to 13% (10/75) and 50% recall. KV state stays ~0.3 GB (+ ≤0.3 GB reference store) where the full cache would need 147 GB at 1M and 295 GB at 2M.
- **A real LLM planner instead of the oracle still works:** with blueprints from Qwen3-8B prompted to emit a dependency graph (edge precision 1.0, recall 0.9 in every session, the one miss always module→fee-rule), PACE at L=40K passes 69/75 (92%) vs H2O's 41% (11 better, 0 worse, p = 0.001), while retention only reaches 60% and is not significant against H2O.
- **Cost is small and measured:** 1,047 s vs 963 s over ten 100K sessions (+9%) on the same eager decode path; renumbering is token-identical to the baseline when inactive; teacher-forced ΔNLL after a 12K prefix with 16 forced renumbers is −0.003 nats (95% CI [−0.019, +0.015]) on Qwen3-8B and +0.007 ([−0.002, +0.016]) on Mistral; a 48K prompt beyond Qwen3-8B's 40,960 range recalls a needle at token 0 with continuation likelihood 0.515 vs H2O's 0.516 nats.
- **Second model reaches its own ceiling but not a significant win:** Mistral-7B has a 40% no-eviction test ceiling (99% fact recall, failures are coding errors), so the pre-declared primary measure is p1+p2 plus recall. PACE scores 45%/49%/37% at D=2K/25K/90K against the 40% ceiling with 100%/96%/99% recall, retention only falls 53%→32%→30% (recall 98%→94%→88%), H2O collapses 9%→1%→1%; but PACE vs retention only at D=90K is not significant (46% vs 36%, 6 better 4 worse, p = 0.75).

## Authors & Credibility

Single author, Suman Chatterjee, at Amazon Web Services — no academic co-authors, no prior-art cluster to lean on, and no external replication. The credibility signals here are procedural rather than institutional: (i) genuine pre-registration of the headline comparison, the Mistral analysis (including a *single* pre-declared extension at D=90K), the drift decision rule and the 1M/2M runs, with decision rules committed before the runs and reported regardless of outcome; (ii) a fingerprinting/merge-refusal protocol that caught a filler-regime change by checksumming paired prompts, and separately reported (never merged) trials from before a probe rewording; (iii) an explicit "design changes made after seeing data" disclosure (L=8K was chosen after the distance sweep, then tested on fresh seeds); (iv) a no-eviction control that validates the hidden tests accept a model that remembers; (v) negative and non-significant results reported in the abstract-level narrative, not buried (Mistral, the L=8K interaction, the L=40K arm's unexplained spread). Implementation is claimed open-source as a SparseEngine subclass. Against that: one author, one GPU type, one benchmark family he wrote himself, and a reference URL (`github.com/CURRENTF/SparseEngine`) that reads like an anonymized placeholder, so the open-source claim is not verifiable from the paper.

## Critical Assessment

**Novelty.** The reframing is the real contribution and it is genuinely new in this literature: the agent-aware KV line (KVFlow, PBKV, CacheScout, ActKV, MemDecay, TokenCake, Continuum) is entirely about *which requests/spans survive*, and "lost in the middle" / RULER document that distant context is used worse — but nobody had measured the residency-vs-retrievability split *inside* an evicting server at fixed ρ ≥ 0.99, which is the exact regime where serving systems claim victory. Bounded positions itself is not new (StreamingLLM assigns in-cache positions, InfLLM re-bases retrieved blocks); what is new is exact re-rotation of non-contiguous, planner-selected spans with a proven equivalence, plus the empirical rule that the limit should be as small as the budget allows.

**Rigor — what holds up.** The 2×2 with matched engine, budget, decoding and sessions; the sign tests on paired probes; the interaction computed rather than hand-waved, and the honest refusal to claim super-additivity at L=8K when p=0.32; the failure taxonomy that shows the two components repair *different* error modes (missing facts vs misapplied facts); the no-eviction control at 8K; the token-identity check when features are off; the drift bug found, quantified, fixed and re-verified under the same pre-registered criterion. This is more methodological care than most KV-eviction papers show.

**Rigor — where I would push back.**
- **The biggest missing baseline is the entire agent-aware family the paper positions against.** KVFlow, ActKV, MemDecay, CacheScout, PBKV and TokenCake are cited in Related Work and then never run. The only eviction baselines are H2O and SnapKV, and SnapKV is close to a strawman here: it is run "as the engine implements it" with decode-time eviction in a multi-turn setting, its 3% pass rate and 5% recall are a floor no reviewer would consider a serious competitor, and the authors say so themselves. The claim "bounded positions are what the family lacks" is therefore supported by argument and by one oracle-planner retention policy, not by a head-to-head with the family.
- **A YaRN confound sits inside the headline comparison.** Table 1 states that arms without bounded positions use YaRN ×4 so 100K sessions fit the positional range, while PACE arms run at native frequencies with positions < 8K. So "positions as written" vs "bounded positions" changes *two* things: the position assignment and the frequency scaling — and YaRN is known to degrade short-range fidelity. The pooled Figure 3 is the paper's best defense (the L=40K arm, which needs no YaRN, lands in the same 16–32K bins as the YaRN-scaled retention-only arm with similar pass rates), but that pooling is itself confounded with session position, as the authors concede. A clean control — retention only at native frequencies with sessions short enough to fit 40,960 — is absent.
- **No full-context reference at 100K.** The control is an 8K session, so "97% vs 42%" is not "PACE recovers what full context would give at 100K". If Qwen3-8B itself degrades at 100K even with the whole cache, part of the remaining 3% is not PACE's to close; if it does not, 97% is a genuine ceiling match. The hardware makes this hard (147 GB of KV on a 24 GB card), so the omission is forgivable — but then the claim should be stated as "beats every eviction baseline by a wide margin," not as recovery of full-context quality.
- **The 40% Mistral ceiling makes the second-model result weaker than the abstract implies.** The abstract says "PACE stays at that ceiling while retention alone falls below it," which is true in recall but the pre-declared paired test on p1+p2 at D=90K is p=0.75, and the five added sessions actually favored retention only. That is honest in §5.6 and dishonest nowhere, but the abstract sentence reads stronger than the evidence.
- **The L=40K arm's spread is an unexplained internal inconsistency:** at a matched ~24K rotary gap it scores 56% (D=25K), 64% (D=50K) and 93% (D=90K). If gap is the mechanism, these should be similar. The authors report it "as observed" with n=5 and correlated probes — the right thing to do, but it means the gap→accuracy relationship is noisier than Figure 3's clean binning suggests.
- **Filler-content quirk.** Filler is Python stdlib source, and a 300K session was derailed into reproducing the stdlib's own `decimal` implementation when a probe asked for decimal-based fee code. The fix — excluding chunks mentioning `Decimal`, `decimal`, `quantize` or `ROUND_*` for the 100K re-check, 300K, 1M and 2M runs — removes a legitimate hard case (topical distractors) and, by the authors' own admission, "real agent sessions offer no such filter." Earlier results were not re-scored under the filter. The 100K experiments also span two filler regimes (recurring vs non-repeating files); comparisons are always within one run, which is correct, but it means the headline and the replication are not on identical filler.
- **Samples are small:** 5–10 sessions per cell, 3 probes each, so the per-cell n for full-pass Fisher tests is 5–10. Pre-registration protects the headline; it does not protect the secondary patterns (the L=40K spread, the 300K arm at n=3).
- **Latency claims are thin for a serving paper.** All arms use the eager decode path, no concurrency, no throughput, only relative overhead. Worse, at 2M tokens the median filler turn grows 0.9 s → 1.7–3.2 s from start to end *equally in both arms*, and §5.7 says the source "is outside the bounded attention path" and "we have not yet isolated it." For a paper whose selling point is "one 24 GB GPU serves 2M-token sessions," an unexplained 2–3.7× per-turn slowdown that is not attributable to the method under study is the largest unaddressed engineering question.
- **The fixed foresight floor caps the method's validity at ~5M tokens** (50K floor vs max unprotected attention 14.6K at 1M, 25.1K at 2M). The authors flag this and propose a relative bonus but do not evaluate it — so "scales to any session length" is true for positions and false for retention.
- **Rehydration is barely evaluated.** It is disabled in the 300K/1M/2M runs and rarely fires at 100K; its only evidence is a scripted late-flag test (5/5 vs 1/5, p ≈ 0.05, n=5) plus a remote-tier variant. That is a design element, not a validated one.

**Reproducibility.** Benchmark templates are fully listed in Appendix A with sampled ranges; the integrity protocol is unusually complete; pre-registration and result fingerprints are described. Against: code is claimed but not verifiable from the paper, the engine is a niche open-source project, the planner experiment uses the same model family as the model under test, and the exact prompt for the LLM planner is not given.

**Significance.** If the residency/retrievability distinction replicates, it changes what agent-serving systems should optimize and explains a class of "the cache was right and the agent still failed" incidents that current eviction benchmarks cannot see. The finding is cheap to test (a distance sweep on any evicting server) and the fix is 9% wall time — that combination is what makes it matter.

## Strengths

- Identifies a failure mode that is invisible to the metric the entire subfield optimizes, and proves it at fixed residency (0.995–0.996) rather than by assertion.
- The two-mechanism decomposition is empirically justified by a failure taxonomy, not just by ablation numbers: positions-only loses the facts, retention-only keeps them and misapplies them.
- Exact re-rotation with a proof, and the "smaller L is better" rule with a concrete capacity derivation (L > B_max + H).
- Finds, quantifies and fixes a bf16 compounding-rounding bug that only appears past ~1M tokens — a genuinely useful negative result for anyone doing key surgery in a cache.
- Pre-registration, template fingerprinting, merge refusal, a no-eviction control, and disclosed post-hoc design changes: a level of integrity rare in systems papers.
- Honest reporting of the Mistral null result and of the non-significant L=8K interaction; the abstract's "both components are required" is scoped to what the paired tests actually establish.
- Real length scaling on commodity hardware (2M tokens on one L4, 0.7 GB vs 295 GB) with recall as a coding-independent metric.

## Limitations

- One synthetic task family (definition recall in a coding session) with stdlib filler; tool traces, multi-document research and multi-agent hand-offs are untested and may weight retention vs distance differently.
- Two 7–8B models, one GPU type; larger models may use distant context better, which would shrink the effect that motivates the whole design.
- Mostly an oracle planner (true dependency graph); the single LLM-planner run has recall 0.9 and the degradation curve under worse planners is uncharacterized — yet real planners are the deployment case.
- Requires the workload to be plannable at all: without a plan PACE degrades to attention-based eviction with bounded positions (63% at 100K vs 97% with foresight).
- The fixed bonus floor (50K) is outgrown by accumulated heavy-hitter scores at ~5M tokens; the relative-bonus fix is proposed but unevaluated.
- Gap collapse changes what the model observes: order is preserved, elapsed distance is not, so tasks that depend on "how long ago" could be affected (perplexity shows no cost, but that is a weak probe).
- Rehydration validated only in scripted tests; disabled in all the long runs.
- Latency measured only as relative overhead on an eager path, no concurrency, and the 2M per-turn slowdown is unexplained.
- No full-context reference at 100K; the 8K control cannot establish how much of the remaining 3% is the model rather than the cache.
- Small per-cell samples (5–10 sessions), and SnapKV is a weak stand-in for the agent-aware eviction family the paper argues against.

## Relevance

这篇正好落在"推理栈静默改变模型所见"这条线上：KV 驱逐是一个纯粹的性能优化，却会在 residency 看似完美（0.996）时静默地把模型准确率从 93% 打到 64%——属于 Agent & Pipeline / serving 层的 silent failure，且给出了可复现的检测方法（固定 residency、扫旋转距离）。对 **Reliability under Extreme Performance Optimization** 更直接：bf16 存储的 key 在反复重旋转下累积舍入，1M 会话等效压力就把 100% 打到 84%，这是一个典型的"低精度 + 长时累积"数值可靠性案例，其 fp32 参考存储的修法（误差 0.031 → 0.003）值得借鉴到其他原地修改缓存张量的优化里。

## Questions for Further Exploration

1. Does the residency/retrievability split replicate on a *non-coding* long-horizon workload (tool traces, multi-document QA) where the needed span is not a verbatim definition but a paraphrase? If the effect is RoPE attenuation, it should; if it is "the model needs exact strings nearby," it might not.
2. What happens with a clean control at native frequencies — retention only with sessions short enough to fit 40,960 positions — to separate the YaRN confound from the gap effect?
3. How does accuracy degrade as planner recall falls from 0.9 to 0.7 or 0.5, and does tiered rehydration actually recover it (the one experiment that could answer this is a scripted n=5 test)?
4. Is the mechanism really rotary distance, or is it effective-context density? A control that renumbers to a *random* permutation within the same range (same gap distribution, broken order) would separate "close" from "compact."
5. Why does the median filler turn grow 1.9–3.7× across a 2M-token session when attention, eviction and renumbering all act on a fixed 2K resident set? If it is the serving path's per-turn bookkeeping (message spans, blueprint parsing, host-side row management), that cost may dominate at 10M tokens regardless of KV budget.
6. Does the foresight bonus compose with a *learned* eviction scorer rather than H2O's cumulative attention, and does the 50K floor still dominate when the base scores are normalized differently?
7. What is the actual full-context accuracy of Qwen3-8B at 100K on this benchmark (needs a bigger GPU or offload), i.e. how much of the 42%→97% is recovering a real ceiling?
