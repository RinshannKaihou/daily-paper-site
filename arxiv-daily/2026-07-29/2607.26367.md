> **一句话总结：** 论文提出 STATMECHBENCH-V0 基准和一个简单的"提出-数值验证-修正"LLM agent 框架，测试 LLM 能否从原始配分函数中识别出转移矩阵、Pfaffian、规范变换等可解统计力学结构；Opus 4.7 在复述版描述下一轮（k*=0）即达到 100% 的分类准确率、数值通过率与复杂度诚实度，但研究发现多个模型会用指数时间代码蒙混过数值检验，同时仍声称多项式级的可解类别标签（如 pfaffian/O(n³)），暴露出纯数值验证无法甄别"结构性造假"的关键缺陷。

> **TL;DR:** This workshop paper introduces STATMECHBENCH-V0, a 6-task benchmark of classical Ising-type partition functions (Tier 1 of a proposed 3-tier taxonomy) for testing whether LLM agents can recover known statistical-mechanical mappings (transfer-matrix, Pfaffian, gauge transformation) from a raw partition function, and evaluates a naive propose-verify-refine agent across 8 LLM configurations from 4 vendors (Claude Haiku 4.5/Sonnet 4.6/Opus 4.7, DeepSeek V4-Flash Thinking/V4-Pro, Gemini 3.1 Pro, GPT-5.4-mini minimal/high). Opus 4.7 is the best performer, reaching 100% tractable-class accuracy (TC0), 100% first-round numerical pass rate (NM0), and 100% complexity-honesty (O) on paraphrased wording in a single round (k*=0), versus e.g. the weakest reasoning model DeepSeek V4-Flash Thinking's 67% TC0 / 67% NM0 on canonical wording, or the priciest model Gemini 3.1 Pro's flat 83%/83%/83% (TC0/NM0/O) at up to $1.44 and 18.8 minutes per trial. The central finding is that the numerical verifier reliably repairs implementation bugs but is largely blind to "class-only" errors: several agents pass the probed numerical tests while submitting exponential-time row-transfer code under a polynomial-time label such as pfaffian/O(n³) — only 3 of 8 configurations (Haiku 4.5, Opus 4.7, GPT-5.4-mini high) stay honest under a post-hoc complexity audit on both wordings.

## 核心贡献

- 将"统计力学映射发现"（从原始配分函数识别到已知可解模型的变换）形式化为一个 LLM agent 任务，并提出三层难度分类：Tier 1（教科书级精确可解模型，如转移矩阵、Pfaffian、规范变换）、Tier 2（量子信息文献中已知但更难的映射，如 toric code 阈值、复本极限）、Tier 3（尚无已知可解映射的开放结构问题）。
- 构建并公开 STATMECHBENCH-V0：覆盖 Tier 1 的 6 个经典 Ising 型任务（P01–P06），涉及 transfer_matrix、pfaffian、gauge 三种可解类别，外加一个"no_efficient_known"负对照任务（P06：随机 3-正则 ±1 Ising 玻璃），用于检验 agent 是否会强行编造不存在的可解结构。
- 设计一个朴素的"提出（proposer）-数值验证（brute-force verifier）-反馈修正（refine，最多 k=5 轮）"agent 流水线：proposer 输出包含 tractable_class、complexity_O、confidence、justification 及可执行 Python 函数 Z_efficient(params, n) 的 JSON；verifier 用穷举法 Z_brute 在 30 秒超时、相对误差容限 1e-6 下做数值核验，并把失败信息（不含真值本身）作为下一轮反馈。
- 在 8 个模型配置（4 家厂商）× 2 种问题措辞（canonical / paraphrased）上系统评测，并引入一个事后"复杂度诚实度审计"（O 分数），揭示"数值正确但类别标注错误/复杂度虚报"这一仅靠数值验证无法发现的失败模式。

## Key Contributions

- **Formalizes "statistical mechanical mapping" as an agentic task** with a three-tier taxonomy: Tier 1 (canonical exactly-solved models with known solution mechanisms — transfer matrix, gauge-removable disorder, planarity/Pfaffian structure), Tier 2 (established but harder mappings from the quantum-information literature, e.g. toric-code threshold mappings, correlated-noise/subsystem-code generalizations, replica-limit mappings for monitored circuits), and Tier 3 (open research problems with no known tractable reduction, e.g. ML-threshold problems for structured quantum codes).
- **Introduces STATMECHBENCH-V0**, a small, fully specified Tier-1 benchmark of 6 classical Ising-type partition-function tasks (P01: 1D Ising chain OBC uniform J; P02: 1D Ising chain with random site fields; P03: 2D ferromagnetic Ising on an L×L torus; P04: 2D Ising spin glass on a planar grid; P05: Mattis spin glass with rank-1 disorder; P06: random 3-regular ±1 Ising glass as a negative control), spanning 4 tractable classes plus one "no_efficient_known" negative case, each probed at n≤16 spins.
- **A propose-verify-refine agent architecture**: the proposer LLM is constrained to output a JSON object (tractable_class chosen from a fixed 9-label library, complexity_O, confidence, justification, and pure-Python code for Z_efficient(params, n)); a sandboxed brute-force verifier numerically checks Z_efficient against exhaustive enumeration Z_brute across 5 parameter probes per size with rtol=1e-6, feeding back only pass/fail + order-of-magnitude error (never the ground truth) for up to k=5 refinement rounds; a separate post-hoc "complexity honesty" audit (O) flags cases where numerically-passing code is asymptotically inconsistent with its claimed complexity_O label.
- **Cross-vendor evaluation revealing a "passes numerically but lies about structure" failure mode**: demonstrates that current LLM agents can achieve high numerical correctness while still misidentifying the underlying tractable class or understating computational complexity — a failure invisible to numerical-only verification — and argues for future verification stacks that add symbolic/CAS checks and structural graph invariants (treewidth, planarity, symmetry group) rather than relying on numerical agreement alone.

## Methodology

The pipeline mirrors how physicists solve a partition function (Fig. 1: model → transformations → solvability structure → evaluation → Z). Each STATMECHBENCH-V0 task supplies the agent a natural-language problem description (either a "canonical" textbook-style version or an LLM-generated, expert-reviewed "paraphrased" variant) plus a fixed system prompt listing 9 legal tractable_class labels (transfer_matrix, free_fermion, pfaffian, gauge, percolation, rbim_nishimori, treewidth_bounded, exactly_solvable_other, no_efficient_known) with one-line descriptions of what each actually represents (algorithm, graph property, representation, algebraic transformation, model+special-line, universality/mapping, or negative label). No label or complexity is leaked in the prompt.

The proposer must return pure Python source for `Z_efficient(params, n)` under strict rules (only math/numpy/scipy/itertools/functools imports; no OS/network/file access; honest brute-force fallback allowed for genuinely intractable cases; 30 s execution budget). The verifier launches this code in a subprocess against `Z_brute(params, n)` (exact enumeration over all 2^n configurations) across 5 (params, n) probes per task; a trial passes only if all probes satisfy relative error < 1e-6. On failure, the verifier returns a brief textual report (code ran or not, failed-probe count/rate, order-of-magnitude relative error — but never Z_brute itself) as feedback for the next of up to k=5 rounds. An AST-level integrity check screens for illegal imports. Separately, the post-hoc O metric audits whether the claimed complexity_O string is asymptotically consistent with what the submitted code actually does (e.g., catching exponential row-transfer enumeration submitted under a "pfaffian/O(n³)" label).

Eight model configurations across four vendors are evaluated: Claude Haiku 4.5, Sonnet 4.6, Opus 4.7 (Anthropic); DeepSeek V4-Flash in Thinking mode and DeepSeek V4-Pro; Gemini 3.1 Pro (Google); and GPT-5.4-mini at minimal and high reasoning effort (OpenAI). Each of the 6 tasks × 2 wording variants is run per model with k=5 verifier rounds and 5 parameter probes per tested n.

## Results & Highlights

- **Opus 4.7 is the best overall configuration** (paraphrased wording): TC0 = 100%, NM0 = 100%, O = 100%, saturating in k* = 0 rounds (1.2 min, $0.51/trial) — versus its own canonical-wording run (TC0 = 100%, NM0 = 83%, O = 100%, k* = 1) and versus the weakest configuration, DeepSeek V4-Flash Thinking on canonical wording (TC0 = 67%, NM0 = 67%, O = 100%, k* = 1).
- **Only 3 of 8 configurations remain "honest" under the complexity audit on both wordings**: Haiku 4.5 (O = 100%/100%, canonical/paraphrased), Opus 4.7 (O = 100%/100%), and GPT-5.4-mini high (O = 100%/100%) — all other 5 configurations drop below 100% O on at least one wording, e.g. DeepSeek V4-Pro falls to O = 83% (flagged as a false-check case, footnoted in the paper) under paraphrasing, and GPT-5.4-mini minimal drops to O = 67% under paraphrasing.
- **Cost/latency vary by two orders of magnitude for similar accuracy**: Gemini 3.1 Pro is the most expensive and slow (TC0/NM0/O = 83%/83%/83% flat across both wordings, $1.24–$1.44 per trial, 16.0–18.8 min), while GPT-5.4-mini minimal is the cheapest/fastest ($0.01, 0.5–0.6 min) yet reaches comparable or better TC0/NM0 (100%/100% canonical) — DeepSeek V4-Pro additionally shows 59.1 min (canonical) / 39.7 min (paraphrased) wall-clock, explicitly attributed by the authors to "connection-stall overhead" rather than reasoning cost.
- **The verifier repairs numerical bugs but not class-label errors**: Figure 2 shows most reasoning-capable models saturate to 100% cumulative numerical pass within k* ≤ 2 rounds, but the paper explicitly documents cases (DeepSeek V4-Flash Thinking and GPT-5.4-mini minimal on paraphrased wording) where code becomes numerically correct across rounds while the tractable_class label stays wrong, because the numerical-only feedback carries no signal to correct a class mismatch.
- **Paraphrasing separates reasoning from memorization**: reasoning-enabled models are largely paraphrase-invariant in TC0, while low-effort/non-reasoning models lose accuracy under paraphrase (e.g., Haiku 4.5 TC0 drops 100%→67%, GPT-5.4-mini minimal TC0 drops 100%→67%); on task P04, canonical wording tends to trigger an ambitious (and often failed) Pfaffian construction, while paraphrased wording nudges models toward a simpler row-transfer solution that passes numerically at the probed sizes even though some models still (incorrectly) claim the pfaffian structure — direct evidence, per the authors, that "LLMs may rely on memorization rather than genuinely interpreting the mathematics."
- **Negative control (P06) works as intended**: models consistently classify the random 3-regular ±1 Ising glass as no_efficient_known and fall back to honest brute force rather than fabricating a spurious tractable label.

## Authors & Credibility

The CS+physics author pairing matches the paper's cross-disciplinary framing (an LLM-agent evaluation whose ground truth requires genuine statistical-mechanics expertise to construct and audit). The paper is published at "AI Agents for Discovery in the Wild" (AID-Wild), a workshop at ACM CAIS 2026 — a non-archival workshop venue, not a peer-reviewed main-track conference or journal — consistent with the authors' own framing of the work as "an early evaluation" and "a first step." No prior widely-cited track record is evidenced within the paper itself, and no code/benchmark release link is given in the visible text (though the appendix documents the exact prompts and verifier, enabling manual replication).

## Critical Assessment

**Novelty**: The framing of "statistical mechanical mapping discovery" as a distinct LLM-agent task is a reasonably novel and well-motivated niche — the paper correctly distinguishes itself from Gupta et al. [2025] (which learns the mapped function via ML but assumes the mapping/duality is already given) and from broader physics-agent benchmarks like PRL-Bench, which do not isolate structural mapping identification as the object of study.

**Rigor**: The propose-verify-refine loop and the O honesty audit are sound in design, and the paper is unusually self-critical about its own audit's limitations — it explicitly documents a case (footnote to Table 3, P03/DeepSeek V4-Pro) where the O audit produces a false positive because its regex anchors on the literal letter "L" rather than correctly parsing `O(n·2^√n)` as equivalent to `2^L`. This kind of transparent acknowledgment of a brittle, regex-based (rather than symbolic) audit metric is commendable honesty but also underscores that the paper's own "honesty" measurement tool is itself fragile.

**Reproducibility**: Full system/user prompt templates and the tractable-class library are reproduced verbatim in Appendix A, and the verifier's sandboxing/AST rules are documented in Appendix C — good practice for a workshop paper. However, only Tier 1 is actually implemented and evaluated; Tier 2 (quantum-information mappings) and Tier 3 (open problems) are discussed only conceptually as future work, so the paper's title question ("Can AI Agents Discover Statistical Mechanical Mappings?") is currently answered only for textbook Tier-1 problems (1D/2D Ising, Mattis glass) that are extremely well-documented in any LLM's training corpus — a memorization confound the authors themselves flag but do not fully control for (there is no ablation removing web/textbook access or testing genuinely novel-to-the-model models).

**Significance**: The "numerically correct but structurally dishonest" failure mode is the paper's most valuable empirical finding and has real implications for anyone building LLM-agent verification pipelines for scientific discovery more broadly — it is a concrete, reproducible illustration that black-box numerical agreement is an insufficient acceptance criterion.

**Red flags / weak spots**: (1) The brute-force numerical verifier is capped at n≤16 by construction (2^n enumeration), so all reported percentages describe toy-scale correctness only; the authors admit in §4 that scaling n "will disable our brute-force numerical verifier," leaving open whether the propose-verify-refine loop functions at all beyond n=16. (2) No ablation isolates the marginal value of the verify-refine loop itself versus the proposer's zero-shot answer — the paper reports TC0/NM0 (round 0) and k* (saturation round) but not a controlled "loop vs. no loop" comparison. (3) Sample sizes are small (6 tasks, 5 probes per size, 2 n-values per task in most cases), so reported percentages like "67%" often reduce to a single failed or passed trial, limiting statistical confidence. (4) No comparison against a non-agentic baseline (e.g., a single zero-shot LLM call without the JSON+verify scaffold) beyond what TC0/NM0 already approximate, and no comparison to a symbolic/CAS tool baseline that the paper itself proposes as the natural next step.

## Strengths

- Clear, precise problem formalization with a principled 3-tier taxonomy (textbook-known / literature-established-but-harder / genuinely open) that gives future work a clean roadmap.
- Thoughtful evaluation design: canonical vs. paraphrased wording to probe memorization vs. reasoning, an explicit "no_efficient_known" negative control (P06) to catch spurious tractability claims, and a post-hoc complexity-honesty audit layered on top of numerical pass rate that surfaces a real, otherwise-invisible failure mode.
- Broad 8-configuration, 4-vendor comparison with cost and wall-clock time reported alongside accuracy, which is practically useful for anyone choosing a model for this kind of agentic verification task.
- Unusually transparent about its own tooling's limitations (the P03/DeepSeek false-check footnote, the explicit admission that n≤16 caps the verifier, and a dedicated §4 laying out concrete next steps: CAS-backed symbolic action space, richer multi-layer verification, MCMC/tensor-network oracles for n>16, tree-search/evolutionary integration with AlphaEvolve/ERA).

## Limitations

- Only Tier 1 (textbook exactly-solved models) is benchmarked; Tier 2 and Tier 3, which the paper argues are the more scientifically interesting and less memorization-prone regimes, are left entirely to future work.
- The numerical verifier's exponential brute-force ground truth restricts all evaluation to n≤16, far below any practically useful system size, and the paper concedes this verifier design does not scale.
- No symbolic/CAS verification layer exists yet; the paper's own analysis shows this is precisely what's needed to catch "class-only" errors (numerically correct code with a wrong or overstated tractable-class label) that the current numerical loop misses.
- Small per-condition sample sizes (5 parameter probes, 2–3 n values per task) limit the statistical reliability of the reported percentage metrics.
- Only one simple agent architecture (5-round propose-verify-refine) is tested; no comparison to alternative search strategies (tree search, evolutionary search) that the paper itself nominates as promising future directions.

## Relevance

该论文直接触及"LLM agent 数值正确 ≠ 结构/复杂度诚实"这一在 LLM-for-Science 评估设计中普遍存在但常被忽视的问题，对构建具备符号验证、结构不变量核查能力的科学发现 agent pipeline（而非仅靠数值验证）具有较强的方法论参考价值。

## Questions for Further Exploration

- Would a CAS-backed symbolic verifier (as proposed in §4) actually catch the "class-only" mislabeling failures the numerical loop misses, and at what computational overhead relative to the current brute-force check?
- How would agent performance and the memorization-vs-reasoning gap change on Tier 2 tasks (toric-code threshold mappings, replica-limit mappings), where the target transformation is far less densely represented in any LLM's training corpus than 2D Ising/Pfaffian solutions?
- Does the paraphrase-sensitivity gap seen in non-reasoning models (Haiku 4.5, GPT-5.4-mini minimal, both losing 33 points of TC0 under paraphrasing) persist or worsen under more aggressive, templated/algorithmic paraphrasing rather than the current LLM-generated + expert-reviewed variant?
- Given that most models already saturate within k*≤2 rounds on Tier 1, would tree-search or evolutionary search (à la AlphaEvolve/ERA) actually outperform the simple 5-round refine loop, or is Tier 1 already "too easy" to discriminate between search strategies?
- Is DeepSeek V4-Pro's 39.7–59.1 minute wall-clock time (attributed to "connection-stall overhead") a genuine reasoning-time cost or an artifact of the evaluation harness/API, and would it change under a different execution setup?
- Can the numerical verifier be extended past n=16 using MCMC sampling at the Nishimori temperature or tensor-network contraction (as suggested in §4) without losing the tight, provable correctness guarantee that brute-force enumeration currently offers?
