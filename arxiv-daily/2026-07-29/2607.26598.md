> **一句话总结：** Living-Harness 把每一轮任务的执行轨迹和评估反馈，通过一套人工编写的领域级"Evolution-SOP"，转化为对冻结工具/上下文之外的情景记忆和状态图的有界更新，在 τ²-Bench 和 MultiWOZ-2.4 上分别比最强交互式基线高出 10.07 和 9.91 个百分点（Pass@1），且演化出的状态可免训练迁移到其他模型骨干上。

> **TL;DR:** Living-Harness keeps an agent's tools and base context frozen but lets episodic memory and a workflow state graph evolve after every episode, guided by a fixed, domain-authored Evolution-SOP that gates what gets committed. On τ²-Bench, Living-Harness (GPT-5.2 backbone) reaches 83.09 average Pass@1 vs. 73.02 for the strongest interactive baseline (Reflexion) — a +10.07 point gain — and on MultiWOZ-2.4 it reaches 65.50 vs. 55.59 for ReasoningBank (+9.91 points). The evolved harness state also transfers retrieval-only to other backbones, e.g. lifting GLM-5's Taxi-domain Pass@1 from 0.00 to 43.08.

## 核心贡献

- **提出"持久化过程修复"（persistent procedural repair）问题**：区分"任务内纠错"（单次重试内的自我修正，随任务结束而丢失）与"跨回合适应"（把评估者确认过的失败证据固化进未来会用到的过程知识），并指出现有方法（静态 harness 设计 / 纯文本反思记忆）都只解决了其中一半。
- **提出 Living-Harness 框架**：将 harness 状态拆分为冻结部分（工具、基础上下文、领域规则、固定的 Evolution-SOP）和演化部分（情景记忆 R + 状态图 G）。每回合走"rollout → evaluate → update"闭环：领域级 Evolution-SOP 把完成的轨迹和评估信号转成结构化证据，经过 schema/scope/evidence/constraint/merge 五道门控后才写入持久状态。
- **给出 POMDP 视角的理论支撑**：把 harness 状态建模为"程序状态"（program state），证明（Proposition 1，附录含完整证明）在信息嵌套条件下，引入信息量为正的程序状态只会缩小贝叶斯误差下界，为"检索到的过程上下文能降低预测误差"提供了信息论论证。
- **在 8 个交互式环境上系统评测**：τ²-Bench（Retail/Airline/Telecom）与 MultiWOZ-2.4（Restaurant/Hotel/Train/Attraction/Taxi），相较最强交互式基线分别提升 10.07 和 9.91 个百分点 Pass@1；并展示跨演化周期的持续改进（consistent self-evolution）以及跨模型骨干的"只检索、不再更新"复用能力。
- **提供细致的消融与案例分析**：拆解 Evolution-SOP、情景记忆、状态图三个组件各自的贡献，并用一个具体案例说明 Reflexion 式的文本反思会"每次都得出正确结论但仍然漏调用工具"，而 Living-Harness 把该失败写成可执行修复（缺失的工具调用 + 状态图触发边），一次通过。

## Key Contributions

- **Formalizes persistent procedural repair**: distinguishes task-local correction (self-correction within a retry, discarded when the episode ends) from cross-episode adaptation (evaluator-grounded fixes that persist into future interactions), arguing that harness-design methods and reflection/memory methods each address only half of this gap.
- **Living-Harness framework**: splits harness state into frozen resources (tools, base context, domain rules, and a fixed domain-level Evolution-SOP) and an evolving state `S = (R, G)` — episodic memory and a state graph. A rollout–evaluate–update loop converts each trajectory and its evaluator signal into schema-normalized candidate repairs, which must pass five commit gates (schema, scope, evidence, constraint, merge) before being written into memory/graph.
- **Program-state POMDP formulation** with a formal proposition (proved in the appendix) showing that adding an informative program-state variable `z` to the belief cannot increase — and strictly decreases when `z` carries nonzero conditional information — the Bayes mean-squared estimation error, giving a principled reason why retrieved procedural context should help.
- **Broad empirical evaluation** across 8 interactive domains from τ²-Bench and MultiWOZ-2.4, with gains of +10.07 and +9.91 average Pass@1 points over the strongest interactive baselines, plus evidence of consistent recovery accumulation across evolution cycles and retrieval-only reuse of the frozen harness state across model backbones (GPT-5.2, Gemini 3 Pro, GLM-5, Qwen3-max, Kimi-k2).
- **Component ablations and a qualitative case study** isolating the contribution of the Evolution-SOP vs. memory vs. state graph, and showing concretely how a recurring tool-omission failure (missing `transfer_to_human_agents()` call) that Reflexion repeatedly "diagnoses correctly but still fails to execute" gets converted by Living-Harness into a retrievable episodic-memory entry plus a state-graph repair edge that fixes the behavior in one attempt.

## Methodology

Living-Harness models an agent operating in a domain `d` over a sequence of episodes. At episode `n`, the harness state is `H_d^(n) = (C_d^act, ψ_d, S_d^(n))` where `C_d^act` (tools, base context, domain rules) and `ψ_d` (the Evolution-SOP) are **frozen for the entire run**, and only `S_d^(n) = (R_d^(n), G_d^(n))` — episodic memory and a state graph — evolves. Episodic memory stores scoped trigger conditions, failure patterns, and recovery actions ("why a failure occurred and how it was fixed"); the state graph stores state nodes, transition rules, and repair edges ("where in the procedure the repair changes control flow").

The loop per episode:
1. **Retrieve**: build a task-conditioned query from the current task and its scope, and retrieve top-k=3 entries each from episodic memory and the state graph (same-family-first ranking), rendered as procedural context `κ_n`.
2. **Rollout**: the agent interacts with the environment using frozen tools/context plus `κ_n`, producing trajectory `τ_n`.
3. **Evaluate**: an evaluator produces signals `y_n` (reward/success, termination/warnings) — critically, this happens *before* any harness update, so an episode's own trajectory never contaminates its own score (the "score-before-update" protocol).
4. **Post-episode abstraction and extraction**: the Evolution-SOP `ψ_d` converts `(x_n, τ_n, y_n, C_d^act)` into an episode abstraction `e_n` (task objective, verified facts, execution outcome, critical failure/recovery point), then extracts candidate evidence `u_n = (u_n^R, u_n^G)` for memory and graph updates.
5. **Gated commit**: candidates must pass schema gate (valid JSON schema), scope gate (committed to the right task family unless cross-family transfer is explicitly supported), evidence gate (grounded in evaluator feedback/trajectory evidence/repeated failure patterns), constraint gate (must not override frozen domain policies or tool preconditions), and merge gate (semantically similar updates are merged via semantic hashing rather than duplicated). Only accepted evidence updates `S^(n+1)`.

The Evolution-SOP itself is **manually authored per domain** (one per τ²-Bench domain — Airline, Retail, Telecom — and one per MultiWOZ domain), specifying core procedural/domain laws (e.g., "identity resolution is a gate, not a side note," "lock the active intent first"), when to apply the SOP, and how to weight/rank candidate memory and workflow updates (e.g., "prefer failure memory over failure-informed success memory"). It is not learned or discovered by the system — it is a fixed, hand-written meta-procedure that governs how post-episode evidence is interpreted.

For τ²-Bench, the global state updates after every scored episode; for MultiWOZ-2.4, updates are synchronized every 4 scored episodes (a batch window). Task-local reflection (used within Reflexion-style retries) is kept strictly separate and is discarded at the end of the task instance — it is never written to the persistent `R` or `G`.

## Results & Highlights

- **Main results (Table 1, GPT-5.2 backbone)**: On τ²-Bench, Living-Harness reaches **83.09** average Pass@1 (Retail 85.96, Airline 88.00, Telecom 78.07), edging out the strongest flagship model Gemini 3 Pro (82.92 average) despite using GPT-5.2-medium as its base, and beating the strongest interactive baseline **Reflexion (73.02 average) by +10.07 points**. On MultiWOZ-2.4, Living-Harness reaches **65.50** average Pass@1 vs. the strongest interactive baseline **ReasoningBank (55.59 average), a +9.91 point gain**, and outperforms Reflexion (53.10 average) by 12.40 points.
- **A named weakness the authors report themselves**: on MultiWOZ-2.4's 1-domain subset, Living-Harness scores 76.55, which is *below* Reflexion's 77.88 — the authors note that Living-Harness's advantage shows up mainly in the 2-domain (70.52 vs. ReasoningBank's 58.33) and 3-domain (25.87 vs. Reflexion's 21.68) groups, i.e., "procedural repairs must transfer across domain boundaries" for the method's benefit to materialize.
- **Consistent self-evolution across cycles (Table 2)**: on τ²-Bench, Retail Pass@1 rises from 57.02 (cycle 0, no evolution) to 85.96 (cycle 3, a +28.94 point cumulative gain); Telecom rises from 57.39 to 78.07; Airline peaks at 88.00 in cycle 2 before a small −2.00 point dip to 86.00 in cycle 3 — illustrating that gains are front-loaded (early cycles fix missing workflow steps) with smaller/occasionally noisy refinements later.
- **Component ablation (Figure 3, τ²-Bench)**: removing the Evolution-SOP (replacing domain-specific extraction/commit rules with a generic extractor) drops the average score from 83.09 to **73.38** — the single largest degradation, showing the gain is not just from "having memory" but from structured posterior interpretation and bounded update rules. Removing memory alone drops it to 77.34; removing the state graph alone drops it to 79.50 — both matter but memory removal hurts more.
- **Cross-model retrieval-only transfer (Table 3)**: freezing the harness state evolved with a GPT-5.2 actor and giving other backbones retrieval-only access (no further global updates) improves every reported domain score. The largest gains appear where the base model struggles most — e.g., Taxi domain Pass@1 jumps from 0.00 to **43.08 for GLM-5**, 0.00 to **45.13 for Qwen3-max**, and 0.00 to **45.13 for Kimi-k2** — indicating the harness state encodes reusable, backbone-agnostic procedural knowledge rather than model-specific prompting tricks.
- **Harness-state scaling (Tables 4–5, appendix)**: episodic memory and state-graph size grow steadily but with diminishing per-cycle increments (e.g., τ²-Bench Retail episodic memory grows 0→67→131→198 entries across cycles 1–3), consistent with the "early cycles fix bigger gaps, later cycles refine" narrative.

## Critical Assessment

**Novelty**: The core idea — freezing tools/base context while letting only episodic memory and a workflow/state graph evolve, under a fixed governing "Evolution-SOP" with explicit commit gates — is a genuinely distinct combination relative to prior work that evolves a single artifact type (memory-only: Reflexion, ExpeL; workflow-only: AWM; strategy-only: ReasoningBank; whole-config: EvoTest). Table 6's comparison table makes this positioning explicit and is honest about it: e.g., it correctly marks AWM as only "Partial" on "procedure revised" and notes that Living-Harness is the only method with jointly gated memory-and-graph updates. The POMDP program-state framing (Proposition 1) is a nice touch that gives an information-theoretic reason to expect gains from retrieved procedural context, though the authors are careful to note it does not guarantee any *particular* implementation improves performance — it is a proof about optimal Bayes estimators, not about their specific system.

**A significant, underplayed caveat**: the "self-evolving" framing is qualified by the fact that the Evolution-SOP — the component whose ablation causes the single largest performance drop (83.09 → 73.38) — is **manually hand-authored per domain**, not learned or discovered by the system. This means a substantial fraction of the method's benefit comes from human domain engineers writing down procedural laws ("lock the active intent first," "identity resolution is a gate, not a side note") ahead of time, which is disclosed candidly in the Limitations section ("These domain rules are currently specified manually... do not establish zero-shot transfer of an Evolution-SOP to unseen domains"). This is a fair and important caveat: the system automates converting evaluated failures into structured repairs *within* a domain whose meta-rules a human already wrote, which is a narrower claim than "the harness discovers its own operating procedure."

**Rigor**: The score-before-update protocol (episode `n`'s score is locked before its own trajectory can influence the harness) is a sensible design that prevents trivial same-instance leakage. However, the paper does not report variance across seeds/runs (a single temperature=0.2 run per configuration), which matters given LLM stochasticity, especially for the smaller deltas (e.g., the Airline cycle-3 −2.00 point dip, or the τ²-Bench edge over Gemini 3 Pro of only +0.17 points). The paper also does not test robustness to shuffled task streams, unseen policy changes, or held-out task families within a domain — explicitly flagged in the Limitations section as future work, and a real open question since the current gates provide no rollback or regression testing against previously-solved tasks, so a bad evaluator signal or an overly narrow repair could persist and degrade future retrieval.

**Baselines**: The interactive baselines (ReAct, Reflexion, AWM, ReasoningBank, EvoTest) are reasonably representative and current, all matched to the same GPT-5.2-medium backbone and tool/evaluator interfaces per the appendix's cost-profile section, which is good experimental hygiene. Reflexion is allowed up to 3 trials per task as its task-local retry budget, matching Living-Harness's own task-local reflection budget — a fair comparison point.

**Significance**: The cross-model transfer result (Table 3) is arguably the most practically interesting finding — it suggests the evolved harness state is a genuinely reusable artifact rather than a backbone-specific crutch, which has real deployment value (evolve once with a capable/expensive model, deploy cheaply elsewhere). The magnitude of the Taxi-domain transfer gains (0.00 → ~43-45 points for three different backbones) is striking, though it also reflects that the base models scored essentially 0 on that domain without any harness — a low bar that makes the relative improvement look larger than it might in a domain where baselines are already competent.

## Strengths

- Clear conceptual separation between fixed execution resources and evolving procedural state, with concrete commit gates (schema/scope/evidence/constraint/merge) that make the update mechanism auditable rather than an opaque "append everything to memory" approach.
- Strong, consistent empirical gains across two different benchmark families (task-oriented dialogue and tool-mediated agent tasks) and against multiple well-known self-evolving baselines.
- Component ablation isolates the contribution of the Evolution-SOP itself from memory and graph mechanics, honestly showing the SOP matters most.
- Cross-model transfer experiment provides real evidence the evolved state is backbone-agnostic, not just prompt-engineering for one model.
- Appendix includes a formal proof (Proposition 1 with full derivation), detailed reproducibility protocol (retrieval top-k, gate definitions, synchronization windows), and the actual Evolution-SOP prompt text for multiple domains — unusually transparent for this class of paper.
- The Limitations section is candid rather than perfunctory, explicitly naming the manual-SOP-authoring caveat, the lack of rollback/regression testing, and privacy considerations for persisted interaction histories.

## Limitations

- Evolution-SOPs are hand-written per domain by the authors; no evidence is given that a generic or automatically-derived SOP would work, and zero-shot transfer of an SOP to an unseen domain is explicitly untested.
- No rollback, stale-entry removal, or regression testing over previously-solved tasks — incorrect evaluator feedback or an overly narrow repair can persist in the harness state indefinitely and is not guaranteed to be self-correcting (explicitly acknowledged).
- Evaluated only on two simulator-based benchmarks (τ²-Bench, MultiWOZ-2.4) with finite tool sets and evaluator-defined success criteria; robustness to shuffled task streams, reduced task recurrence, or real-world unseen policy changes is untested.
- No variance/seed analysis reported; single-run numbers make it hard to judge whether small deltas (e.g., the narrow win over Gemini 3 Pro flagship, or cycle-to-cycle dips like Airline's −2.00) are statistically meaningful.
- Post-episode computation (posterior generation, extraction, schema normalization, gated commit) adds a non-trivial cost overhead beyond the scored rollout itself, and persisted interaction histories may carry privacy-sensitive content requiring additional safeguards not implemented in the current system.
- No code repository was evident in the reviewed material, so reproduction currently depends on re-implementing the pipeline from the provided prompt specifications.

## Relevance

对研究"LLM agent 如何跨回合积累可复用过程知识"、"harness/workflow 层面的自演化系统"、以及"记忆-工作流联合更新与门控机制设计"感兴趣的读者会觉得本文的 rollout-evaluate-update 框架和五道门控设计很有参考价值；但要注意其"自演化"能力高度依赖人工编写的领域级 Evolution-SOP，这对希望做到"零人工先验、纯自动发现领域规则"的研究方向是一个需要正视的边界条件。

## Questions for Further Exploration

- Can the Evolution-SOP itself be learned or bootstrapped (e.g., meta-learned across domains) rather than hand-authored, and how much performance would be lost relative to the current manually-tuned version?
- How does Living-Harness behave under a shuffled or non-stationary task stream, or when the underlying domain policy changes mid-deployment — does the lack of rollback/regression testing cause measurable drift or regression on previously-solved task types?
- What is the actual latency/token-cost overhead of the post-episode posterior-generation, extraction, and gated-commit pipeline relative to a plain Reflexion-style retry loop, and how does this trade off against the accuracy gains in a production setting?
- Would combining Living-Harness's gated memory/graph evolution with a learned (rather than fixed) commit-gate policy further close the gap on the 1-domain MultiWOZ subset where it currently trails Reflexion?
- How sensitive are results to the top-k=3 retrieval budget and the 4-episode MultiWOZ synchronization window — would finer-grained or adaptive update scheduling change the cycle-3 fluctuations seen in the Airline domain?
