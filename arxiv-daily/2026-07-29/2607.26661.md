> **一句话总结：** 本文提出 AgenticCANN，一个针对华为 Ascend C（低语料 NPU 编程语言）的知识增强式智能体进化框架，通过六层知识分类体系的阶段差异化注入和探索/收敛模式的动态调度，把逐元素/归一化算子的可编译率从 0% 提升到 90–100%，并在 EoH 进化基线（GELU 上 83% 可行率、跨代 0% 优化增益）之上，用 Fix-Loop 模式以 350K token（比全工具代理省 12 倍）实现 100% 可行率与 +26.0% 的跨代性能增益，最终在 1B Pangu 模型推理中取得高达 6.65× 的单核加速与 8.3–10.1% 的端到端推理提速。

> **TL;DR:** AgenticCANN tackles the "feasibility barrier" of LLM-based kernel generation on Huawei's low-corpus Ascend C NPU language (where closed-world generation yields ~0% compilable output for non-trivial operators) by injecting a six-level, phase-differentiated knowledge taxonomy and dynamically switching between high-exploration (Tool-Agent) and high-convergence (Fix-Loop) LLM interaction modes across the evolutionary lifecycle. On a 54-operator stratified Ascend C benchmark and a GELU evolution study on Huawei Ascend 910B, it lifts elementwise-operator feasibility from 57% (no knowledge) to 86% (full knowledge) and beats the EoH evolutionary baseline (Liu et al. 2024) — which reaches only 83% feasibility and 0% evolutionary gain — with a Fix-Loop schedule that hits 100% feasibility and +26.0% evolutionary gain using 350K tokens versus Tool-Agent's 4.18M tokens for +0.04% gain. Deployed on a production 1B-parameter Pangu LLM, the resulting RMSNorm kernel achieves up to 6.65× speedup over PyTorch (0.118ms→0.018ms) and an 8.3–10.1% end-to-end inference latency reduction, though scaled-dot-product attention and broadcast operators fail at 0% feasibility across every configuration tested.

## 核心贡献

- **问题定位**：区别于 CUDA 在预训练语料中的丰富代表性，华为 Ascend C 是极度低语料的 NPU 编程范式（显式 TQue 向量流水线、UB 分块、L1/GM 多级内存），标准闭环式 LLM 代码进化（如 EoH）在非平凡算子上编译成功率约等于 0%，作者称之为"上游可行性瓶颈"（upstream feasibility bottleneck），并将其与下游"性能调优"问题明确区分。
- **六层知识分类体系**：提出 L0（硬件编程模型）→ L1（模式指南）→ L2（硬件约束，如 32 字节内存对齐、队列 ping-pong 平衡）→ L3（分块策略）→ L4（API 参考）→ L5（已验证算子范例）的结构化知识税onomy，并按算子计算模式（elementwise/reduction/normalization/fusion/broadcast 等）路由到对应知识资产，避免整份文档拼接造成的上下文稀释。
- **阶段差异化知识组装 + 阶段自适应智能体调度**：初始化阶段注入全部 L0–L5 知识以建立"心智模型"，变异/修复阶段仅保留紧凑的 L2–L4 护栏以防止结构漂移；同时在种群初始化阶段使用高探索的 Tool-Agent（全工具使用）模式发现可行初始解，在后续多代精炼阶段切换到高收敛的 Fix-Loop（单轮生成+反馈修复）模式，二者的组合在真实 NPU 硬件（Huawei Ascend 910B）上通过沙箱编译-验证-性能剖析闭环得到实证验证，覆盖 54 个跨 10 个拓扑类别的 Ascend C 算子。

## Key Contributions

- **Problem framing — the upstream feasibility bottleneck**: unlike CUDA, which benefits from abundant open-source representation in LLM pretraining corpora, Ascend C (Huawei's NPU kernel language, built on explicit TQue vector pipelines, unified-buffer/L1/GM tiling, and manual ping-pong synchronization) is a severe low-corpus domain. The paper shows standard closed-world LLM code evolution (e.g., EoH) collapses to near-zero compilable output for any operator beyond trivial elementwise patterns, reframing the challenge from "kernel performance tuning" to "code synthesis feasibility."
- **Six-level knowledge taxonomy (L0–L5)**: Programming Model (L0) → Pattern Guide (L1) → Hardware Constraint (L2, e.g., 32-byte alignment, queue ping-pong balance) → Tiling Strategy (L3) → API Reference (L4) → Verified Exemplars (L5), with pattern-based routing that maps a target operator's inferred compute category to the relevant knowledge assets rather than dumping full documentation into the prompt.
- **Phase-differentiated knowledge assembly**: initialization injects the full L0–L5 taxonomy to build the LLM's hardware mental model; mutation/compilation-fix/correctness-repair/performance-tuning phases each receive only the compact knowledge levels relevant to that step (e.g., mutation restricts context to L2–L4 guardrails), cutting prompt length from ~800 tokens at initialization to under 100 tokens at performance-tuning stages (an 8× per-generation cost reduction).
- **Stage-adaptive agentic evolution**: formalizes three interaction archetypes along an exploration/convergence spectrum — Single-Pass, Fix-Loop (closed-loop feedback with logs+context), and Tool-Agent (full read/edit/compile tool use) — and dynamically schedules high-exploration Tool-Agent/Fix-Loop modes for initial seed discovery, then high-convergence Fix-Loop/Single-Pass modes for structure-preserving refinement, empirically showing this beats a monolithic (single-mode) strategy by +26.0% at 8.4% of the token cost.
- **Empirical validation across 54 Ascend C operators** (10 topological categories: elementwise, reduction, normalization, broadcast, pooling, index, attention, fusion/misc, math, loss) on physical Huawei Ascend 910B NPUs, plus a production deployment integrating optimized kernels into a live 1B-parameter Pangu LLM inference pipeline.

## Methodology

AgenticCANN is architected as three tightly coupled layers (Figure 2):
1. **Knowledge Layer** — maintains the six-level (L0–L5) taxonomy and a pattern-based routing system that classifies a target operator specification into a canonical compute category (elementwise, reduction, softmax, broadcast, normalization, matmul, convolution, attention, index, pooling, resize, fusion) and assembles a phase-appropriate knowledge context K_g.
2. **Generation and Evolution Layer** — hosts the spectrum of interaction modes (Single-Pass, Fix-Loop, Tool-Agent), dynamically scheduled per generation via a `SelectAgentMode` routine: Tool-Agent/Fix-Loop for generation g=1 (initial seed discovery), Fix-Loop/Single-Pass for g>1 (mutation/refinement).
3. **Evaluation Layer** — runs a sandboxed three-stage pipeline (compilation via the Bisheng compiler, numerical verification against PyTorch golden references at tolerance ε≤10⁻³, hardware profiling on physical NPUs with 10 warm-up + 100 benchmark iterations), streaming diagnostic traces back to the Knowledge Layer to trigger targeted correction routines (e.g., L2 alignment fixes, L3 tiling fixes) when a candidate fails.

The overall search is formalized as constrained optimization x* = argmin_x T(x) s.t. C(x)=1, where T is measured NPU runtime latency and C is a binary compile+correctness indicator. Algorithm 1 (Appendix B.1) formalizes the loop: infer compute pattern π → assemble knowledge K_g → select agent mode → initialize or mutate the population → evaluate on hardware → apply TargetedCorrection when invalid → environmental selection. Table 10 (Appendix B.2) specifies exactly which knowledge levels are injected per phase (e.g., Initialization gets all L0–L5 full; Mutation gets only compact L2–L4; Correctness Repair gets full L2+L5 but compact L1). All experiments use DeepSeek-V4-Flash (6-operator in-depth study) and DeepSeek-V4-Pro (54-operator large-scale validation) at temperature=0.8, top_p=0.95, max generation length 8192 tokens, on an 8-Ascend-910B1-NPU cluster (61GB HBM/card, CANN 8.1.RC1), with population size 5, 5 generations, 2 parallel sampling workers, 3 numerical verification passes, and a 3600s sandbox timeout per candidate.

## Results & Highlights

- **Overall feasibility across operator patterns (Table 4)**: without knowledge orchestration, closed-world generation yields 0% feasibility for all non-elementwise operators. With full knowledge injection, elementwise operators (e.g., GELU) reach 100% feasibility with up to 2.71× speedup; normalization operators (LayerNorm, RMSNorm) reach 90–100% feasibility (1.41–2.71× speedup); fusion operators (Fused-AddNorm) reach only 56% feasibility (1.10× speedup); broadcast operators (add_bias_broadcast) remain stuck at 0% feasibility across all modes.
- **Knowledge ablation on LayerNorm (Table 5)**: feasibility rises monotonically from 0% (closed-world, no domain knowledge) → 40% (+L0 programming model) → 60% (+L0+L2 hardware constraints) → 80% (+L0+L2+L5 curated example) → 90% (full phase-differentiated knowledge), with speedup climbing from — → 1.12× → 1.85× → 2.41× → 2.71×. L2 (hardware constraints, especially the 32-byte alignment rule) contributes the single largest marginal gain (+20pp, 40%→60%).
- **Large-scale 14-operator elementwise benchmark (Table 6)**: valid solutions rise from 8/14 (57%, "Free"/no-knowledge) → 10/14 (71%, "Insight"/L5-only) → 12/14 (86%, "Full"/phase-differentiated), with mean kernel latency dropping 741.3μs → 721.6μs → 711.0μs. Per-operator gains include hardtanh −18.4% (835.3μs→681.5μs), softplus −15.2% (809.8μs→686.9μs), swish −17.0% (817.4μs→678.3μs), and ReLU −9.7% (751.7μs→678.8μs) (Table 14/Figure 5).
- **Stage-adaptive evolution vs. EoH baseline on GELU across generations (Table 7)**: Fix-Loop achieves 100% feasibility, 36.12ms best latency, +26.0% evolutionary gain, at 350K total tokens; Tool-Agent achieves 100% feasibility, 30.37ms best latency (fastest single kernel), but only +0.04% evolutionary gain despite 4.18M tokens (12× Fix-Loop's cost); the EoH closed-world evolutionary baseline (Liu et al. 2024) achieves only 83% feasibility, 48.84ms best latency, and 0% evolutionary gain at 242K tokens — i.e., structured knowledge + stage-adaptive scheduling beats a standard LLM-driven evolutionary baseline on every axis except raw token count.
- **Error-driven repair (Table 8)**: LayerNorm improves from an unoptimized 0.39× baseline to 2.68× speedup in a single repair iteration after L2/L3 knowledge injection; RMSNorm reaches 1.41× after 4 iterations; Softmax plateaus at 0.98× (vendor compiler already near-optimal, limiting further headroom).
- **Production deployment on 1B Pangu LLM (Table 9, Figure 6)**: normalization kernels account for ~11% of total end-to-end inference latency (1102ms of 5083ms across 3392 layer invocations). The synthesized RMSNorm kernel achieves 6.65× speedup at tensor shape (1,1,1536) (PyTorch 0.118ms → AgenticCANN 0.018ms) and 6.19× at (1,26,1536) (0.108ms → 0.017ms), raising vector pipeline utilization from 14.2% to 81.6% and yielding an estimated 8.3–10.1% end-to-end inference speedup when all 53 normalization layers are replaced.
- **Systematic failure case — scaled dot-product attention (Appendix D.2)**: attention operators failed to synthesize a single valid compiling kernel across all 8 execution configurations (2 sampler engines × {Free, Insight, Full} knowledge × 2 replications). The paper attributes this to high-dimensional constraint coupling (QKᵀ scaling + row-wise softmax + weighted V aggregation), host-kernel tiling misalignment, and unified-buffer boundary spills from the O(seq_len²) attention score matrix exceeding the 200KB UB capacity.

## Critical Assessment

**Novelty**: The core idea — a structured, phase-differentiated knowledge taxonomy substituting for missing pretraining data, combined with stage-adaptive (rather than monolithic) agent interaction modes — is a sensible and reasonably novel combination for the specific, underexplored problem of low-corpus hardware DSL code generation. It's an incremental-but-solid extension of existing agentic-evolution and RAG-for-code-generation ideas (the paper is explicit about building on EoH, ReAct, Reflexion) rather than a fundamentally new algorithmic mechanism.

**Rigor**: The 8-container parallel Docker matrix (Table 11) crossing sampler engine × knowledge level with 2 replication runs is a genuine attempt at controlled ablation, and the replication analysis (Table 15, <2% variance on simple ops) is a good practice rarely seen in this literature. However, a significant caveat undercuts the headline "54-operator" framing: per Appendix C.2, the detailed feasibility/latency sweep (Table 6/13/14, the 57%→86% numbers) was only fully run on the 14 elementwise operators; the remaining ~40 operators across reduction, normalization, broadcast, pooling, etc. "uniformly exhausted the API budget and are not reported" in that table. The abstract is careful to scope its "57% to 86%" claim to elementwise operators specifically, so this isn't outright misrepresentation, but the paper's title and framing ("Large-Scale Stratified Benchmark," "54 Ascend C operators") create an impression of broader validated coverage than the core ablation study actually delivers.

**Reproducibility**: Full system prompts, the exact K1–K4 knowledge injection snippets for the LayerNorm case study, the Algorithm 1 pseudocode, and per-container hardware mapping are all provided in the appendix — an above-average level of methodological transparency for this genre. However, the paper never mentions releasing code, the 54-operator dataset, or the knowledge taxonomy assets themselves; without those artifacts, exact reproduction is not currently possible, and the taxonomy is explicitly stated to require "5–8 expert-hours per new operator pattern" (Appendix D.3) to construct manually.

**Significance**: The EoH baseline comparison (Table 7) is a fair and relatively strong baseline choice — it's a real published closed-world LLM evolutionary framework (Liu et al. 2024), not a strawman — and AgenticCANN beats it decisively on feasibility (100% vs 83%) and evolutionary gain (+26.0% vs 0%) at comparable-to-lower token cost. The production 1B Pangu deployment with measured 6.19–6.65× kernel-level and 8.3–10.1% end-to-end speedup is a genuinely compelling real-world validation point that many "LLM writes fast kernels" papers lack.

**Red flags**: (1) Two operator categories — attention (0% feasibility across all 8 configurations) and broadcast (0% feasibility across all modes) — represent complete, systematic failures of the method on classes that are architecturally central to modern transformer workloads; the paper is commendably transparent about this in Appendix D.2, but it means the "up to 6.65× speedup" and "90–100% feasibility" headline claims apply only to a curated subset (elementwise/normalization) of operator types, not the harder ones. (2) All LLM backbones tested are DeepSeek-V4 variants (Flash/Pro); model-family generalization (Qwen2.5-Coder, Llama-3, GPT-4o) is explicitly listed as untested future work, so it's unclear whether the knowledge-injection benefit is LLM-agnostic or partly an artifact of DeepSeek-V4's specific behavior. (3) The end-to-end 1B Pangu speedup (8.3–10.1%) is bottlenecked by the embedding layer (44.5% of latency, per Table 16) which the framework does not address — the headline production number is a real but modest slice of total achievable speedup, and normalization (the one thing optimized) is only 11% of total latency to begin with.

## Strengths

- Clear, well-motivated problem framing that distinguishes "upstream feasibility" (can the LLM produce compilable, correct code at all) from "downstream tuning" (is it fast), which is the right lens for genuinely low-corpus target languages.
- Real physical-hardware evaluation (8× Ascend 910B1 NPUs) rather than simulated or CPU-emulated results, including a production LLM inference deployment with measured end-to-end latency impact.
- Transparent reporting of complete failure modes (attention, broadcast) rather than only showcasing favorable operator categories, plus a genuine ablation isolating which knowledge level (L0–L5) contributes most.
- Direct, favorable comparison against a real prior evolutionary baseline (EoH) with matched token-budget accounting, not just an internal ablation.

## Limitations

- Complete failure (0% feasibility) on attention operators and broadcast operators — two operator classes essential to transformer and dynamic-indexing workloads — leaving the method's scope currently confined to simpler compute patterns.
- The detailed knowledge-ablation feasibility curve (57%→86%) is validated only on 14 elementwise operators, not the full claimed 54-operator suite; ~40 operators are stated to have exhausted the API budget without producing reportable results.
- LLM backbone generalization is untested beyond DeepSeek-V4 Flash/Pro; the paper explicitly flags Qwen2.5-Coder/Llama-3/GPT-4o validation as future work.
- Knowledge taxonomy construction is manual and costly (5–8 expert-hours per new operator pattern per the authors' own estimate), partially undermining the "automated" framing in the title for genuinely novel operator types.
- No code, dataset, or knowledge-asset release is mentioned, limiting independent verification despite detailed prompt/algorithm disclosure.
- The end-to-end production speedup (8.3–10.1%) is modest relative to the per-kernel speedup (6.65×) because normalization is only ~11% of total model latency and the dominant embedding-layer bottleneck (44.5%) is outside the framework's current scope.

## Relevance

该工作与"低语料/新硬件平台上的 LLM 代码生成与智能体进化"高度相关，其"结构化知识分类替代预训练数据缺口"和"探索/收敛模式动态调度"的设计思路，对研究 agentic code evolution、LLM4EO/hyper-heuristics 或国产 AI 芯片编译工具链的读者有直接参考价值；其在真实 Ascend 910B 集群与生产级 Pangu 模型上的端到端验证也为"LLM 自动生成算子能否真正落地"提供了少见的实证数据点。

## Questions for Further Exploration

- Would the knowledge taxonomy transfer to other emerging low-corpus accelerator DSLs (e.g., Cerebras, Groq, or other domestic NPU toolchains), or is it fundamentally Ascend-C-specific?
- What would it take to push attention and broadcast operators past 0% feasibility — is hierarchical decomposition into matmul/softmax/elementwise primitives (as the authors suggest in D.2) sufficient, or does it require a fundamentally different tiling-simulator-in-the-loop approach?
- How sensitive are the reported feasibility/speedup numbers to the specific DeepSeek-V4-Flash/Pro model versions, and would a much weaker or much stronger LLM backbone change the relative value of knowledge injection versus agentic tool use?
- Could the manual 5–8 expert-hour taxonomy construction cost be substantially reduced by mining L2/L3 rules automatically from historical compilation-failure logs, as the authors propose, and how much feasibility would that automated variant retain relative to the hand-curated taxonomy used here?
- Given that the embedding layer dominates production Pangu inference latency (44.5%) but is architecturally very different (memory-bound gather operations) from the normalization/elementwise kernels this framework targets, is AgenticCANN's knowledge-taxonomy approach even applicable there, or does closing that gap require an entirely different knowledge layer?
