> **一句话总结：** 提出 LLVMhammer——首个通过 Rowhammer 在 CPU DRAM 中翻转 Triton 编译器（libtriton.so）目标无关优化阶段的一个比特位，使 vLLM 服务生成"功能等价但次优"的 GPU kernel 并写入磁盘缓存的攻击；在 ShareGPT 负载下使 4 个 7B 级 LLM 在 NVIDIA RTX 4090 / AMD RX 7900 XTX 上的端到端推理时间增加 4–16%（Deepseek-llm-7B-chat 在 4090 上 +16.0%），且同一翻转位置还能跨厂商破坏输出正确性（BERTScore 低至 0.25）。

> **TL;DR:** A Rowhammer bit-flip in the CPU-DRAM-resident Triton compiler library makes vLLM (Triton 3.6) emit functionally identical but de-vectorized GPU kernels that are persisted in the on-disk Triton cache. On ShareGPT prompts driven by `vllm bench serve` (n=1000, 30 runs, Welch's t-test), total inference time versus the unmodified-Triton baseline rises 6.3–16.0% on NVIDIA RTX 4090 (Deepseek-llm-7B-chat +16.0%) and 4.0–7.8% on AMD RX 7900 XTX across Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct, Mistral-7B-Instruct-v0.3, and Deepseek-llm-7B-chat — but the signal is statistically insignificant at n=10 (Mistral on NVIDIA: 0/5 metrics). The authors' Karnage tool prunes the bit-flip search space from ~1.18M candidate locations (~9,858 GPU-hours) to 1,176 profiled candidates in ~10 hours, and the same vendor-agnostic flip locations also corrupt outputs (BERTScore down to 0.25) on both GPU vendors.

## 核心贡献

- **首次将 Triton 编译管线作为 Rowhammer 攻击目标**：攻击者以无特权同宿主进程身份，用 Rowhammer 翻转驻留在 CPU DRAM 中的 `libtriton.so`（Triton 编译器共享库）里的一个比特位，使性能关键优化 pass 走向不同分支，生成"计算结果完全一致但明显更慢"的 GPU kernel。
- **持久化污染**：Triton 将 JIT 编译产物缓存于磁盘（`~/.triton/cache`），因此一次成功翻转即可跨推理会话、跨进程重启持续造成减速，受害者输出无任何异常，无从察觉。
- **GPU 厂商无关（vendor-agnostic）**：攻击目标是 Triton IR / Triton-GPU IR 等目标无关编译阶段（位于 MLIR/LLVM 管线中 LLVM IR 分叉之前），一个翻转位置同时影响 NVPTX 与 AMDGPU 后端，无需为每个厂商重新搜索。
- **Karnage 自动搜索工具**：通过四阶段剪枝（命名空间过滤 + Intel PT 函数轨迹求交 → 单比特汉明距离的控制流指令对筛选 → 基于 Triton 离线编译输出的比对剪枝 → GPU 推理减速实测剪枝），把 ~12.2 万函数 / ~118 万候选翻转点压缩到可实测的规模，无需人工检查。
- **从"减速"扩展到"输出破坏"**：同一目标无关位置的正确性 pass 被翻转后，可在 NVIDIA 与 AMD 上同时产生完全失连贯的输出（BERTScore 降至 0.25），超越此前绑定 NVIDIA SASS 的 PRowhammer（ISCA 2026，同组前作）。

## Key Contributions

- **First attack on Triton's compilation pipeline**: an unprivileged co-tenant CPU process uses Rowhammer to flip one bit in `libtriton.so` (the Triton compiler shared library) while it resides in CPU DRAM, altering a performance-critical optimization pass so the JIT compiler emits a kernel that is functionally identical but measurably slower.
- **Persistent poisoning via the on-disk kernel cache**: because Triton caches compiled kernels in `~/.triton/cache` and reuses them across requests and process restarts, a single successful bit-flip yields a sustained slowdown with no output anomaly to trigger investigation.
- **GPU-vendor agnosticism by construction**: the flip targets target-independent stages (Triton IR / Triton-GPU IR passes, before the pipeline forks into NVPTX vs AMDGPU LLVM IR), so one identified location transfers to every vendor's `libtriton.so` binary without re-profiling — the key contrast with PRowhammer, which is tied to NVIDIA SASS and cuBLAS.
- **Karnage**, a four-stage automated search that isolates useful bit-flips satisfying three properties — P1 target independence, P2 slowdown without crash/output corruption, P3 consistency across prompts and models: namespace filtering (121,735 → 7,963 functions on NVIDIA) plus Intel Processor Trace intersection across five representative kernels (matmul, vector addition, fused attention, layer norm, softmax) on both vendors yields 254 target-independent functions; restricting to x86-64 control-flow instruction pairs at Hamming distance 1 (e.g., `je` 0x74 ↔ `jne` 0x75, `cmov*` pairs) yields 38,769 candidate flips (NVIDIA); offline-compilation output-diff pruning (monkey-patched kernel-launch interception, CPU-only) then GPU profiling cut this to 1,176 flips profiled in ~10 hours (AMD: 810 in ~7 hours), versus ~9,858 hours for the namespace-filtered space.
- **A second attack mode — output corruption**: repurposing Karnage with only property P1, the same target-independent flip locations produce incoherent outputs on both NVIDIA and AMD from a single location, dropping BERTScore to as low as 0.25.

## Methodology

The attack chains three system facts. (1) Rowhammer: repeatedly activating DRAM aggressor rows (no root privileges needed) flips bits in adjacent victim rows; memory massaging or memory deduplication can place the victim's shared `libtriton.so` page on a flippable physical frame. (2) Triton's pipeline: Python `@triton.jit` kernels lower through Triton IR (MLIR dialect) → Triton-GPU IR → LLVM IR → NVPTX/AMDGPU backends. Every pass at the first two levels is target-independent and feeds all vendor backends equally — this is the architectural divide the attack exploits. (3) vLLM compiles attention/matmul/layernorm/softmax kernels through this pipeline at startup and persists them in the on-disk cache.

LLVMhammer fires before inference begins: the attacker flips one bit in a performance-critical pass inside `libtriton.so`; the next compilation then emits a suboptimal-but-correct kernel that is cached and reused forever. Karnage finds the flip offline in four stages (see Key Contributions), relying on the observation that flipping an opcode bit of a conditional-jump/cmov instruction at Hamming distance 1 yields another *valid* instruction that changes the pass's branch decision — the only realistic route to "slower but correct" rather than crash or unchanged output.

The root cause is verified at three IR levels (Table IV): at LLVM IR a single vectorized inline-asm load (`ld.global.v4.b32`, 4×32-bit in one call) becomes four scalar `ld.global.b32` calls; at PTX 128-bit coalesced loads/stores become 4× as many 32-bit scalar transactions; at SASS the six `LDG/STG.E.128` vectorized transactions vanish and are replaced by 48 scalar 16-bit `LDG.E.U16` loads, each independently traversing the memory hierarchy.

Evaluation uses two platforms — Intel i7-4790 + DDR3-1600 + RTX 4090 (CUDA 13.2, vLLM 0.24.0, Triton 3.6) and Intel i7-8700 + DDR4-2400 + RX 7900 XTX (ROCm 7.14, vLLM 0.25.1+rocm, Triton 3.6) — four 7B-class models, ShareGPT prompts via `vllm bench serve` with n ∈ {10, 100, 1000}, five metrics (TTFT, TPOT, ITL, tokens/s, requests/s), 30 runs per configuration, and Welch's t-test (p<0.05) to separate the flip's effect from vLLM continuous-batching scheduler noise.

## Results & Highlights

- **End-to-end slowdown (n=1000, ShareGPT, `vllm bench serve`, 30 runs)**: total inference time vs the unmodified-Triton baseline increases 6.3–16.0% on RTX 4090 — Deepseek-llm-7B-chat +16.0%, Mistral-7B-v0.3 +7.3%, Llama-3.1-8B +7.2%, Qwen2.5-7B +6.3% — and 4.0–7.8% on RX 7900 XTX (DeepSeek +7.8%, Llama +7.1%, Qwen +4.5%, Mistral +4.0%).
- **Statistical significance (Table VI, Welch's t-test, p<0.05)**: at n=1000 all 8 model×vendor combinations reach significance on all five metrics (TTFT, TPOT, ITL, req/s, tok/s). At n=100 the signal is partial — on NVIDIA only Llama hits 5/5 while DeepSeek and Mistral reach 3/5 — and at n=10 it is unreliable: NVIDIA Mistral shows 0/5 significant metrics and no NVIDIA model exceeds 2/5 (the authors exclude n=10 from the figures for this reason).
- **Karnage pruning efficiency (Table I/III)**: from 121,735 functions in NVIDIA's `libtriton.so` (~1,183,008 candidate bit-flip locations at ~30 s per GPU trial ≈ 9,858 hours) to 254 target-independent functions via namespace + Intel PT filters, 38,769 control-flow candidate flips, and finally 1,176 GPU-profiled flips in ~10 hours (AMD: 122,148 functions → 1,326,122 locations ≈ 11,051 h → 42,996 → 810 in ~7 h); brute-force over all functions would take ~12 years.
- **Kernel-level evidence (Table IV)**: in the flipped kernel the 6 baseline `LDG/STG.E.128` 128-bit SASS transactions are replaced by 48 scalar 16-bit `LDG.E.U16` loads (0 vectorized 128-bit transactions remain), i.e., 8× more memory requests per 16-byte datum per thread — the direct cause of the TTFT/TPOT/ITL increase with identical arithmetic and outputs.
- **Output corruption (Table VII)**: the same medical prompt (thrombocytopenia after orthopedic surgery) yields coherent differential-diagnosis answers under the baseline kernel, but under the flipped kernel produces a stream of repeated zeros on AMD and looping meaningless fragments on NVIDIA; BERTScore falls to as low as 0.25 across all four models on both vendors.
- **Cost extrapolation**: a 10% latency increase at 1M requests/day ≈ 876 hours (37 days) of serving capacity lost per year; at H100 pricing of $4.50–$10.00/GPU-hour this is $3.9K–$8.76K per GPU-year, or $1M–$2.24M/year for a 256-GPU deployment — while outputs stay correct, so nothing prompts investigation.

## Authors & Credibility

The three authors (Mrityunjay Shukla, Biswabandan Panda, Shubham Roy) are from IIT Bombay's computer architecture/security group; the same group published PRowhammer at ISCA 2026 (Rowhammer propagating bit-flips from CPU to GPU via cuBLAS/SASS), and this paper is a natural, credible follow-up that generalizes the idea to the vendor-neutral Triton/MLIR stack. The work is systems-security grade in method: real dual-vendor hardware (RTX 4090, RX 7900 XTX), real DRAM generations (DDR3-1600 and DDR4-2400), production software versions (vLLM 0.24/0.25, Triton 3.6, CUDA 13.2/ROCm 7.14), 30-run repetitions with Welch's t-tests to handle vLLM's known batching non-determinism, and multi-level (LLVM IR/PTX/SASS) root-cause evidence rather than black-box timing claims. The related-work and countermeasure sections are thorough and current (DDR5/PRAC/TPRAC, ZebRAM, Siloz, Citadel, Memory Band-Aid, MOAT).

## Critical Assessment

- **Novelty: high and well-motivated.** Targeting the compiler *pipeline* (rather than model weights or GPU SASS code) is a genuinely new angle, and the vendor-agnostic framing via target-independent MLIR stages is the paper's sharpest insight; the framing "a flip in a shared IR is a flip against every vendor's backend" is architectural, not rhetorical.
- **Rigor: strong on measurement, weaker on end-to-end attack practicality.** The slowdown claims are statistically validated (30 runs, Welch's t-test) and honestly reported — including that at n=10 the effect is indistinguishable from noise (NVIDIA Mistral 0/5 significant metrics, no model >2/5), which materially narrows the attack to sustained high-load servers. However, the paper does not report Rowhammer success rates or time-to-flip for getting the victim's `libtriton.so` page onto a flippable frame (the memory-massaging/deduplication step is only cited from prior work), so the true end-to-end feasibility on modern DDR5 systems is asserted via citations (ZenHammer, Phoenix), not demonstrated.
- **Missing ablations/evaluations.** There is no sensitivity analysis on prompt-length mix beyond ShareGPT, no evaluation on larger models or multi-GPU serving (the $1M–$2.24M/year figure extrapolates single-GPU deltas to 256-GPU fleets assuming a year of undetected persistence — an upper bound, since containerized deployments often start with ephemeral caches), and the output-corruption section (Section V) rests on one qualitative prompt example plus BERTScore floors without per-model baseline scores or standard accuracy benchmarks.
- **Reproducibility: good.** All software is off-the-shelf with pinned versions; Karnage's stages (namespace filter, Intel PT traces, offline-compilation diffing) are described precisely enough to reimplement, and the pruning counts per stage are tabulated.
- **Defensibility: the attack is cheap to defeat.** Setting `TRITON_ALWAYS_COMPILE=1` or reloading `libtriton.so` per session breaks persistence at startup-compile cost, and hash-verifying cached kernels against a clean recompile would detect the poisoned artifact; the paper acknowledges both. This limits severity more than the cost-extrapolation rhetoric suggests.
- **Red flags: minor.** Old test CPUs/DRAM (Haswell DDR3, Coffee Lake DDR4) versus the modern GPUs; BERTScore baseline values not stated numerically ("substantially higher" than 0.25); Triton 3.6-specific function counts will drift with releases, though the methodology transfers.

## Strengths

- Identifies an unexplored, structurally vendor-agnostic attack surface (Triton's target-independent MLIR passes) with a clean architectural argument for why it generalizes across NVIDIA and AMD.
- Karnage is a real engineering contribution: a principled, fully automated, offline pruning pipeline that cuts ~1.18M candidates (~12 years brute force) to ~1,176 GPU-profiled flips in ~10 hours, with the clever Hamming-distance-1 control-flow-opcode restriction guaranteeing flips produce valid instructions.
- Exceptional measurement hygiene: 30 repetitions, Welch's t-test chosen because the flipped kernel changes variance, explicit acknowledgment that n=10 is noise-dominated, and per-stage search-space accounting in Tables I and III.
- Multi-level causal evidence (LLVM IR → PTX → SASS de-vectorization, 128-bit transactions → 48 scalar 16-bit loads) explains *why* the kernel is slower rather than just observing it.
- Honest, current countermeasure discussion spanning Triton-level fixes and the full Rowhammer-defense landscape, including why existing defenses (SoftTRR, CATT, ZebRAM, Siloz, PRAC) do or do not apply.

## Limitations

- The effect is modest in absolute terms (4–16% latency) and only statistically reliable under sustained load (n≥100–1000 requests); for latency-sensitive low-batch serving the attack is likely undetectable — in both senses.
- No end-to-end Rowhammer success-rate or flip-latency statistics on the actual victim mapping step; practicality on DDR5/PRAC-equipped server DIMMs is cited, not shown.
- Output-corruption mode is demonstrated qualitatively (single prompt, Table VII) with only BERTScore floors; no systematic per-task accuracy degradation numbers, and flips for this mode only need property P1, so crash/no-effect rates are not characterized.
- Single-GPU, 7B-model scope; multi-GPU tensor-parallel serving, larger models, and containerized deployments with ephemeral Triton caches are not evaluated.
- Simple mitigations exist (cache-bypass recompilation, library reload, kernel-cache hashing), so the attack's realistic window is deployments that neither rotate caches nor verify kernel artifacts.

## Relevance

直接命中"Inference Reliability & SDC Detection"核心方向：本文研究的是模型下层 serving 栈（Triton 编译器 + vLLM + DRAM 硬件故障）引发的静默性能退化与静默输出损坏——bit-flip 既不改变输出正确性又能持续拖慢推理，正是 SDC 检测最难覆盖的盲区。同时对"Compute Infrastructure for Large-Scale ML"方向也有参考价值：揭示了 GPU kernel 编译/缓存基础设施可作为跨厂商的单一故障与攻击注入点。

## Questions for Further Exploration

- What is the true end-to-end attack success probability and time-to-bit-flip on modern DDR5 servers with PRAC enabled, including the memory-massaging step to place `libtriton.so` on a flippable frame?
- Would hash-verifying Triton's on-disk kernel cache (e.g., signing compiled artifacts per deployment) be a practical low-overhead defense, and what startup cost does `TRITON_ALWAYS_COMPILE=1` actually impose in production serving?
- Does the slowdown scale with model size (70B, MoE) and tensor-parallel multi-GPU serving, where attention kernels are a smaller fraction of end-to-end time?
- Can the de-vectorization signature (scalar 16-bit loads replacing 128-bit transactions) be detected at runtime via GPU performance counters (e.g., L1/LSU transaction counts) as a cheap SDC/DoS tripwire?
- Could analogous compiler-pipeline bit-flips target other MLIR-based stacks (IREE, XLA/StableHLO, torch.compile/Inductor) or quantization passes to corrupt numerics rather than latency?
