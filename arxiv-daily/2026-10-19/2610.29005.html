Why this matters

Self-improving agents are bottlenecked by evaluation, not search. VeriEvolve turns reward and benchmark design into executable code — the prerequisite for trustworthy long-horizon autonomy.

Critical edge

The headline 3× gain has no budget-matched control — part of the gain may be repeated sampling (5 paths × up to 15 rounds) rather than evaluator guidance.

— Critical Assessment

01Methodology

A tool task is (instruction, initial state, read-only observation). VeriEvolve builds a deterministic evaluator — binary verdict plus partial fitness — from the instruction and synthesized challenge states, never from the benchmark's own verifier.

  1. Evaluator construction

    Synthesize positive / clean-negative / adversarial near-miss challenge states; a sandboxed verify(context) — read-only ops only, no imports, network, or writes — is frozen after gates: ≥0.90 positive acceptance, ≥0.80 adversarial rejection.

  2. Workflow evolution

    Five persistent nodes — understanding, planning, ReAct execution, artifact inspection, post-processing — each holding alternative behaviors. The frozen evaluator scores final states and emits failed checks as repair signals.

  3. Evaluator refinement

    Diff strong-executor vs false-positive weak-executor end states; instruction-grounded difference clusters become paired counterfactual tests; patches promote only after cumulative regression preserves all earlier verdicts.

Roles: Claude Sonnet drives all model-backed roles; GLM-5.2 is the weak executor. The external MCPMark verifier is consulted only after freezing — evaluator admission requires ≥0.85 agreement.

  • Refinement yield: Stage 3 repairs all 3/3 evaluator false positives for just 64K tokens (<1% of Stage 3's 8.10M) — but practical yield is 1 recovered task.
  • Ablations: GLM-4.5 reaches only 7/30 under identical evaluators; removing context truncation flips internal convergence 7/18 → 21/30; $2.60 + 2.76M tokens per gained task.
  • Cross-environment ceiling: on PostgreSQL both executors solve only the same 3 tasks — a usable fitness signal is necessary but not sufficient.

03Strengths

  • Attacks the correct bottleneck: for stateful tool use, the evaluation layer — not the search operator — is the scarce resource; deterministic checkers are a more defensible fitness signal than LLM-as-judge.
  • Deterministic gates wrap every LLM role — label-consistency and coverage gates on counterfactual pairs, cumulative regression before promotion — making safety properties checkable rather than vibes-based.
  • Exceptional hygiene: McNemar tests with Wilson CIs, infrastructure failures quarantined from semantic ones, an audited-scope table, and a fully worked E(0) → E(1) three-line patch example.
  • Honest negatives, with numbers: the 12/15 PostgreSQL ceiling, Stage-3 re-search cost, and the failed verifier-free trigger are all reported openly.

04Limitations

  • The loop is not closed: an external verifier still gates evaluator admission, false-positive selection, and F+ confirmation — verifier-free deployment is not demonstrated.
  • Finite calibration ≠ coverage: a 5-of-8 placeholder gap slipped through a 141/141-agreeing evaluator; challenge states and evaluators share one author model.
  • Single runs, no budget-matched baseline — gains conflate evaluator guidance with repeated sampling.
  • Uneven coverage: only Filesystem has complete Stage 1+2+3 evidence; Playwright / Notion / GitHub runs are thin, excluded, or observation-limited.
  • Fragile reference: F+ is one valid execution — an erroneous F+ would poison refinement, and that failure mode is untested. Cost stays high (≈46.9M tokens on PostgreSQL).

05Questions for further exploration

  1. Would a budget-matched random-restart or LLM-judge baseline close part of the 6/30 → 18/30 gap, isolating the evaluator's true contribution?
  2. Can instruction-grounding plus regression gating serve as a verifier-free Stage-3 trigger without over-tightening the evaluator?
  3. What happens when the reference F+ itself is wrong — would multiple strong states or a per-cluster vote keep refinement robust?
  4. Do evaluator check families transfer across observation interfaces, or does serialization drift (Notion's 0.75 → 0.50 collapse) break the loop?
  5. Could surrogate re-scoring of archived states replace 15 fresh search rounds, preserving regression guarantees at a fraction of the 8.1M tokens?
