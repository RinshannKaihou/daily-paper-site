DuoPD moves the entire LLM decode phase into the HBM4 logic die — sharing memory bandwidth with GPU prefill, not scaling it.

一句话总结：DuoPD 把 LLM 解码阶段整体卸载到嵌入 HBM4 逻辑裸片内的轻量 PNM 单元、让 GPU 专心做 prefill，二者通过 TSV 级带宽共享并发执行；在 8×GB300 级模拟平台上，端到端吞吐最高提升 2.23 倍、TPOT 最多降低 77.66%，且每栈仅增加 6.51 mm² / 6.45 W 的 PNM 开销。

A Hybrid GPU and Processing-Near-Memory Architecture with Shared DRAM for Efficient Prefill–Decode Disaggregation

Sanghyeok Han · Inseong Choi · Byungkuk Yoon · Gyeonghwan Park, et al. — Seoul National University (VLSI/DRAM group)

LLM Inference Processing-Near-Memory HBM4 PD-Disaggregation Computer Architecture

Key metric · peak throughput gain

2.23×

end-to-end throughput vs 3:1 PD-disaggregation, GPT3-175B (best case; 1.46–2.23× across all baselines)

On GQA LLaMA2-70B the average gain is 1.29–1.61×; full range across settings: 1.31–3.44×.

Why this matters

A credible route to cheaper long-context LLM serving: reclaim the memory bandwidth that prefill/decode disaggregation wastes, using near-memory compute instead of faster memory.

Critical edge

Every result is simulation-only — the TSV direct-forwarding path has no silicon, FPGA, or RTL validation. And the 2.23× headline is the MHA best case; GQA gains shrink to 1.29–1.61×.

Methodology 01

One Blackwell-class GPU + eight HBM4 stacks; each stack's logic die carries a compact PNM unit whose 16×1,024-wide SIMD lanes (2 TB/s at 1 GHz) exactly saturate the stack — decode never touches the GPU's SMs. HBM4's relocated memory controller enables centralized arbitration.

  • TSV direct forwarding — returning data is latched straight from the TSVs into the PNM buffer, bypassing the memory controller so TSV I/O is never occupied twice.
  • MMU arbitration — tensor-granularity bitmap queues for GPU vs PNM traffic; prefill-first wins (decode-first starves the GPU and inflates TTFT; p99 TBT 17.18 ms vs p50 15.71 ms).
  • Hierarchical mapping — GPU-level tensor parallelism; PNM-level sequence parallelism + FlashDecoding partial reductions (inter-PNM all-reduce ≈2% of per-layer decode time); read-only shared weights + exclusively-owned KV caches eliminate coherence traffic.

Evaluated in an open-sourced DRAMSim3-integrated cycle-level simulator: 8× GB300-class GPUs, 8×HBM4/GPU, against 1:1 & 3:1 PD-D, chunked prefill, bank-level PIM, Duplex, and SM partitioning.

  • Latency envelope: at the QPS where TTFT hits 3× its no-queuing value, DuoPD sustains 2.13× / 1.39× / 3.12× higher QPS than 1:1 PD-D, 3:1 PD-D, and chunked prefill.

Strengths 03

  • Clean problem decomposition — roofline and cache-sensitivity data directly justify a lightweight near-memory substrate for decode.
  • Rare hardware honesty — full area/power/thermal budgeting against a real 140.8 mm² HBM4 logic-die footprint, plus explicit cost accounting of rivals (Duplex's 100.48 W/stack, HBM-PIM's 50% capacity loss).
  • End-to-end design thinking — arbitration (TTFT sensitivity, p50/p99 TBT) and parallelism choices (why PP fails, why PNM-level TP over-partitions GQA heads) are argued, not asserted.
  • Simple, correct coherence answer — read-only shared weights, exclusively-owned KV caches, LSU-enforced protection.

Limitations 04

  • Simulation-only evaluation — TSV forwarding handshake and MMU arbitration unvalidated against RTL or silicon timing.
  • Model-dependent gains — 1.29× best-case average on LLaMA2-70B vs 2.23× on dated MHA GPT3-175B; no Llama-3-class dense models tested.
  • Long-context bias — all experiments use ≥8K inputs; the short-context regime, where prefill itself is bandwidth-hungry, is never isolated.
  • Narrow tuning — PNM optimized for batch 16; batch-32 degradation admitted but not quantified; speculative decoding, FP8/INT4 KV, prefix caching unexamined.
  • Deployment dependency — requires a custom HBM4 logic die (memory-vendor adoption); GPU-side software stack out of scope.

Questions for further exploration 05

  1. Does the advantage invert with short contexts (≤2K) or compute-light prefills, where prefill demands more bandwidth itself?
  2. With FP8/INT4 KV caches or prefix-cache dedup, does the 2 TB/s-per-stack PNM become over-provisioned?
  3. Can the PNM SIMD units run speculative-decoding verification or draft-model passes, or does the 16 Op/B ceiling rule that out?
  4. What GPU-side software changes (CUDA graphs, dispatch, allocator) are needed, and what is the real prefill→decode KV handoff latency?
  5. Does the design compose with rack-scale disaggregation, or does single-package bandwidth sharing break at multi-node scale?
