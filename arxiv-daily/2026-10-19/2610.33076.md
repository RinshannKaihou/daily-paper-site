> **一句话总结：** 在 Apple M5 Max（MLX、LFM2.5-8B MoE 模型）上系统评测五种 KV cache 路径：将 PolarQuant 式径向量化的编码/重建融合进单个 Metal kernel 后，8K 上下文解码达 46.8 tok/s（3,456 B/token，3.64× 压缩），比 Python 参考实现快 1.84×、比 block-FP4 快 13%；但 FP4→Polar 串联"双重优化"完全不可叠加（4,241 B/token、15.1 tok/s，双轴皆劣于 FP4 单独使用），且 32K 起所有压缩路径因整缓存重建的累计 O(N²) 解码开销坍缩到 1.5–14 tok/s，64K 时 Metal 路径因 33.5 GB 级临时分配超过 MLX 22.6 GB 单缓冲上限而 OOM——结论是把表示层压缩与 kernel/分配器效应分开评估，长上下文可行的前提是直接在压缩域上做 fused SDPA。

> **TL;DR:** A single-author systems study on an Apple M5 Max (36 GB unified memory, MLX 0.32.2, LFM2.5-8B-A1B-OptiQ-4bit) benchmarks five KV-cache paths at 8K/32K/64K contexts. At 8K, a fused Metal kernel for PolarQuant-style radial quantization hits 46.8 tok/s at 3,456 B/token — 3.64× compression vs the 12,562 B/token bf16 baseline, 1.84× faster than the Python Polar reference (25.4 tok/s) and 13% faster than block-FP4 (41.5 tok/s at 3.62×) — but still only 0.27× the bf16 baseline's 171.4 tok/s. The paper's two negative results are equally central: stacking FP4 then Polar is Pareto-dominated (4,241 B/token at 15.1 tok/s, worse than FP4 alone on both axes), and at 32K all compressed paths collapse to 1.5–14 tok/s vs 91.8 tok/s baseline because the whole cache is reconstructed each decode step (cumulative O(N²)); at 64K the Metal path OOMs on a 33.5 GB temporary allocation against MLX's 22.6 GB buffer limit. Worth reading as an honest decomposition of representation vs kernel vs allocator effects — not as evidence that compression speeds up inference, and it contains no model-quality (perplexity/accuracy) evaluation at all.

## 核心贡献

- **首个在 Apple Silicon（M5 Max + MLX）上对 5 种 KV cache 路径的对照评测**：原生 bf16 基线、block-scaled E2M1 FP4、Python 版 PolarQuant 径向量化（含 QJL 式残差符号草图）、FP4→Polar 顺序串联（"双重优化"）、以及把打包/旋转/重建放进单个设备程序的 fused Metal 径向 kernel；统一报告 bytes/token、解码吞吐、prefill 吞吐与分配失败四类指标。
- **正面 kernel 结果**：径向量化在 Python 编排下慢于 block-FP4，但融合进 Metal 后反超——8K 时 46.8 tok/s 对 41.5 tok/s（+13%）且布局更小（3,456 vs 3,473 B/token），证明 8K 处的排名是**实现效应**而非表示本身的缺陷。
- **两个有价值的负结果**：(1) 编解码器串联不可加——FP4→Polar 得到 4,241 B/token（压缩比反而低于 FP4 单独的 3,473）且解码仅 15.1 tok/s（FP4 单独为 41.5），被双轴 Pareto 支配，因为两种 codec 破坏彼此依赖的分布结构；(2) 32K 起全缓存重建使压缩路径坍缩至 1.5–14 tok/s——量化只削减线性存储项，不改变注意力扫描与累计 O(N²) 解码功。
- **分离表示压缩与 kernel/分配器效应的分析框架**：64K OOM 的根因是迭代拼接在更新路径上触发 33,556,992,000 字节（≈33.5 GB）临时分配、超过 MLX 单个 Metal 缓冲 22,613,000,192 字节（22.6 GB）上限，而非 3,456 B/token 的持久表示本身；明确指出总物理容量（36 GB）与最大连续设备缓冲是两个不同约束。
- **用 DeepSeek-V4.1-Flash 的 FP4-only 消融（≈3,460 B/token）交叉验证了模拟方法论**（本文 FP4 为 3,473 B/token），并把 3,473→890 B/token 的 4× 差距归因于 CED 跨层共享、CSA2 复用与 SWA 有界重放等**正交轴**上的架构技术——与其不可加性发现自洽。

## Key Contributions

- A controlled comparison of five KV-cache paths on Apple Silicon M5 Max via MLX: a native bf16 baseline, block-scaled E2M1 FP4 (16-channel groups, E4M3-like scales), a Python PolarQuant-style radial codec (seeded Walsh–Hadamard preconditioning, polar pairs, optional QJL-style residual sign sketch), sequential FP4→Polar composition, and a fused Metal radial kernel — with bytes/token, decode tok/s, prefill tok/s, and allocation failures reported as separate outcomes.
- A positive kernel result: fusing radial packing, rotation, and reconstruction into one Metal device program lifts decode from 25.4 tok/s (Python Polar) to 46.8 tok/s at 8K (1.84×), beating block-FP4 by 13% (46.8 vs 41.5 tok/s) at slightly better compression (3,456 vs 3,473 B/token) — showing the radial-vs-FP4 ranking at moderate context is an implementation artifact, not a property of the representation.
- Two well-isolated negative results: (1) sequential codec stacking is non-additive — the double path retains the *final* polar layout (4,241 B/token, worse than FP4's 3,473) while paying both transforms' runtime (15.1 tok/s, 2.7× slower than FP4), because FP4's discrete symbols destroy the angular structure PolarQuant relies on; (2) compression without a compressed-domain attention kernel collapses at long context — at 32K every compressed path drops to 1.5–14 tok/s vs the 91.8 tok/s bf16 baseline since each decode step reconstructs and scans the full cache.
- A precise allocator-level diagnosis: at 64K the Metal path dies on a single 33,556,992,000-byte (~33.5 GB) temporary allocation from iterative concatenation, exceeding MLX's 22,613,000,192-byte (22.6 GB) maximum Metal buffer despite 36 GB of physical unified memory — distinguishing total capacity from maximum contiguous buffer size and motivating chunked pre-allocation/paged storage.
- A methodology sanity check against DeepSeek-V4.1-Flash: the FP4-only footprint (3,473 B/token) matches DeepSeek's reported ~3,460 B/token FP4-only ablation, and the remaining ~4× gap to 890 B/token is attributed to orthogonal architectural axes (CED ~4× cross-layer sharing, CSA2 ~1.5× reuse, SWA ~2× persistent-state reduction) rather than another scalar codec — consistent with the paper's non-additivity thesis.

## Methodology

All experiments run on a MacBook Pro with an Apple M5 Max (32-core integrated GPU, 36 GB unified memory), macOS 27.0.1, Python 3.14.5, and MLX-LM 0.32.2, using the mlx-community/LFM2.5-8B-A1B-OptiQ-4bit checkpoint. Weight quantization is held fixed across all conditions; only the KV cache path varies, so differences are attributable to cache handling rather than the model.

Contexts are built from deterministic token IDs at nominal lengths 8,192 / 32,768 / 65,536. Decode throughput is a steady-state tokens-per-second rate measured over a fixed 64-token window after warmup. Cache bytes/token divides persistent cache-owned storage by the effective cached-token count; compression is baseline bytes/token divided by the condition's bytes/token at the same context. Conditions run in fresh processes to avoid carrying compiled graphs, allocator state, or cache objects across contexts. The paper is careful about measurement validity: cache-owned bytes are explicitly *not* equated with resident-set size or MLX active allocations (which include weights, temporaries, and allocator slack); ratios are derived from rounded reported values; and no throughput value is imputed from a failed run (the 64K Metal row reports OOM rather than substituting the 32K layout).

The decode path is intentionally end-to-end — it includes the cache operations each implementation actually requires (reconstruction, concatenation, updates), rather than microbenchmarking only the packing kernel. Conversely, the authors are explicit that no compressed-domain SDPA kernel exists yet in the implementation, so the results measure the cost of *returning* compressed KV to an attention-compatible form. The block-FP4 codec is described as a structural simulation (16-channel groups, one E4M3-like scale per group, signed E2M1 symbols packed two-per-byte), not a reproduction of any proprietary kernel.

## Results & Highlights

- **8K context (Table 1):** Fused Metal Polar reaches **46.8 tok/s at 3,456 B/token (3.64× compression)** vs the bf16 baseline's 171.4 tok/s at 12,562 B/token — 1.84× faster than the Python Polar reference (25.4 tok/s) and 13% faster than block-FP4 (41.5 tok/s at 3,473 B/token, 3.62×). Crucially, this is a win *among compressed paths only*: 46.8 tok/s is still 0.27× the bf16 baseline, and the double FP4→Polar path is Pareto-dominated at 15.1 tok/s and 4,241 B/token (only 2.96× compression — worse than FP4 alone).
- **32K context (Table 2):** All compressed variants collapse to **1.48–14.0 tok/s vs 91.8 tok/s for the bf16 baseline** (block-FP4 is the strongest compressed path at 14.0 tok/s and 3,460 B/token, 3.57×). Notably the ranking inverts: fused Metal Polar (1.48 tok/s) falls *behind* Python Polar (1.83 tok/s) despite its smaller layout, because the fused kernel's long-context update overhead (iterative concatenation) dominates — the 8K fusion win does not extrapolate.
- **64K context (Table 3):** The Metal variant **fails with OOM on a 33,556,992,000-byte (~33.5 GB) allocation exceeding MLX's 22,613,000,192-byte (22.6 GB) maximum Metal buffer**; Python Polar completes at 0.47 tok/s at 3,072 B/token (4.01× compression vs the baseline's 12,323 B/token) while bf16 completes at 1.37 tok/s — the compressed path remains *slower* than baseline despite 4× smaller persistent state.
- **Prefill regression (8K):** the fused Metal prototype reaches **4,685 prefill tok/s vs 5,979 tok/s for the baseline**, motivating a batched encode kernel; this does not affect the decode tables.
- **Non-additivity of composition:** a naive 3.62× (FP4) × 2.96× (Polar) multiplication would predict ~10.7×; the measured double path delivers **2.96× at 4,241 B/token with 2.7× slower decode than FP4 alone** (15.1 vs 41.5 tok/s), because the intermediate FP4 representation is discarded and its discrete symbols break polar angular coding.
- **Cross-check with DeepSeek-V4.1-Flash:** FP4-only at 3,473 B/token matches DeepSeek's ~3,460 B/token FP4-only ablation, isolating the ~4× residual gap to 890 B/token as coming from CED/CSA2/SWA architectural sharing, not from quantization.

## Authors & Credibility

The paper is authored by Ibrokhimsho Abduchaborov, an independent researcher in Tajikistan (ORCID 0009-0009-2287-5266), with a single-author affiliation and no institutional compute backing — the work is a solo systems-engineering study on consumer Apple hardware. Credibility strengths: unusually honest framing (headline numbers immediately qualified by the 0.27×-of-baseline caveat; "values below 1.0× are slowdowns despite the column label"; no throughput imputed from the failed 64K run); exact byte-level allocation figures for the OOM; fresh-process isolation; and a genuinely useful calibration against DeepSeek-V4.1-Flash's published FP4-only ablation. The related-work coverage (KIVI, KVQuant, GEAR, ZipCache, MiKV, QJL, PolarQuant, TurboQuant, H2O, SnapKV, PyramidKV, StreamingLLM, CacheGen, PagedAttention, FlashAttention) is broad and accurately characterized. Credibility caveats: no code or artifact release is mentioned; there is no peer review or institutional verification; and the benchmark universe is one model, one machine, one framework version. The prose is precise about scope boundaries throughout, which raises trust in what is reported rather than lowering it.

## Critical Assessment

- **Novelty:** The fused Metal radial kernel is a competent engineering contribution, and the explicit decomposition of representation vs kernel vs allocator effects is cleanly done — but each ingredient exists (PolarQuant, QJL, block-FP4), and the paper's own framing concedes the fused path "stops short of fused scaled dot-product attention," i.e., the hard part of compressed-domain inference is left as future work. The value is in the disciplined negative results more than the positive one.
- **Rigor (measurement):** Generally strong — deterministic token IDs, fresh processes per condition, warmup before a fixed 64-token decode window, cache-owned bytes carefully separated from RSS, and the 64K Metal row honestly left as OOM. Two quirks deserve note: the decode measurement window is only 64 tokens, which is thin for steady-state throughput claims at throughputs below 2 tok/s; and the Python Polar 64K run uses a *different, more compact layout* (3,072 B/token) than its own 8K/32K runs (4,241/4,228 B/token), so the 4.01× 64K compression figure is not comparable to the 2.96× figure at shorter contexts — the paper flags this but it still makes cross-context trend-reading misleading.
- **Rigor (the missing evaluation):** There is **no model-quality evaluation whatsoever** — no perplexity, no long-context retrieval, no downstream accuracy for any of the quantized cache layouts, despite comparing a 4-bit block codec, a radial codec with quantized radius/angle, and a residual sign sketch, which have very different error distributions. Every number in the paper is bytes or tok/s. For a KV-quantization paper, quality is half the claim; as published, the reader cannot tell whether 3,456 B/token radial coding preserves model outputs at all, and the paper's own limitations section admits this.
- **The headline asymmetry:** The abstract leads with the flattering 8K number (46.8 tok/s, 1.84×, +13% over FP4) while the equally important facts — no compressed path ever beats bf16 decode (best is 0.27×), the fusion advantage inverts at 32K (Metal 1.48 tok/s loses to Python 1.83 tok/s), and the 64K Metal path simply cannot run — arrive later. The paper does disclose all of this, but the framing optimistically front-loads the regime where the method works.
- **Reproducibility:** No code release is mentioned; the model (LFM2.5-8B-A1B-OptiQ-4bit), hardware (M5 Max), and software (MLX 0.32.2, Python 3.14.5, macOS 27.0.1) are fully specified, so in principle reproducible by anyone with the same laptop, but there is no artifact to verify the kernel or the byte accounting.
- **Significance:** As evidence for practitioners: a clear demonstration that on unified-memory Apple Silicon, KV-cache compression today buys capacity, not speed, unless attention consumes the compressed layout directly; and that codec stacking is a dead end. These are useful, transferable lessons. But single-checkpoint, single-device, single-framework scope (acknowledged in §6.6) limits how far the rankings generalize — the authors themselves warn against extrapolating to CUDA without a matched kernel.
- **Red flags:** The "double optimization" of the title is essentially a strawman hypothesis (compression ratios multiply) refuted by construction; the DeepSeek-V4.1-Flash comparison is calibration against a reported number, not a reimplementation; and prefill regresses below baseline (4,685 vs 5,979 tok/s) even in the winning configuration.

## Strengths

- Exceptionally honest reporting discipline: slowdowns are labeled as slowdowns, the failed 64K run is reported as OOM with exact allocation sizes rather than estimated, and the paper repeatedly separates what was measured from what was not (e.g., no compressed-domain SDPA exists in the implementation).
- The core experimental design — holding model, weights, hardware, and framework fixed while varying only the cache path — cleanly isolates the variable under study, and fresh-process execution removes cross-condition contamination.
- The non-additivity analysis of sequential codec composition is a genuinely useful design lesson, and it is correctly reconciled with DeepSeek-V4.1-Flash's much larger savings (composition works across *orthogonal* redundancy axes — precision vs cross-layer duplication vs retained state — not by stacking codecs on the same elements).
- The 8K-vs-32K-vs-64K regime analysis (launch overhead → reconstruction traffic → allocator failure) is more informative than a single averaged throughput number, and the paper explicitly says so and structures its tables accordingly.
- The allocator diagnosis (33.5 GB temporary vs 22.6 GB max Metal buffer vs 36 GB physical) is the kind of precise systems forensics that actually helps someone implementing a fix (chunked pre-allocation, paged storage).

## Limitations

- No model-quality results: perplexity, long-context retrieval, and downstream task accuracy are entirely unmeasured, so the accuracy cost of FP4, radial, or double layouts at these bit budgets is unknown.
- Single model checkpoint (LFM2.5-8B-A1B MoE, itself already 4-bit weight-quantized), single device generation (M5 Max), single framework version (MLX 0.32.2); rankings may shift with head dimensions, GQA ratio, or Metal compiler behavior, and nothing transfers directly to CUDA without a matched kernel.
- The fused Metal path stops before SDPA, so the study cannot say whether radial KV caching is viable inside a real compressed-domain attention kernel — the one result that would change the practical conclusion.
- Inconsistent Python Polar layouts across contexts (4,241 B/token at 8K/32K vs a compact 3,072 B/token at 64K) make cross-context compression comparisons non-uniform; the 64K "five-path" table actually contains only two completed paths.
- Small decode measurement window (64 tokens) and single-request throughput only — no batching, concurrent serving, or prefix-cache reuse, which are the deployment regimes PagedAttention-class systems target.
- No code or artifact availability is stated, and the prefill path regresses below baseline (4,685 vs 5,979 tok/s).

## Relevance

与"Compute Infrastructure for Large-Scale ML"方向（任意硬件平台上的算子与 kernel、推理服务栈）高度相关：这是在 Apple Silicon/MLX 上把 KV cache 量化的表示层与 Metal kernel 融合、分配器行为拆开对照评测的系统工作。同时它触及"极限性能优化下的可靠性"主题的边缘——FP4/径向量化等低精度表示的误差影响被明确列为未评估项，本文只提供了性能与存储侧的证据。

## Questions for Further Exploration

- How much accuracy (perplexity, long-context needle-in-haystack, downstream tasks) do the radial and FP4 layouts actually cost at 3.4–4.2 KB/token, and does the QJL-style residual sketch close the gap to bf16 KV?
- If a fused SDPA kernel consumed the packed polar layout directly (dequantizing radius/angle in registers inside the attention tile), would the 32K collapse disappear entirely, or only shrink the constant factor of the O(N²) term?
- Would replacing iterative concatenation with chunked pre-allocation let the Metal path complete at 64K, and what would its throughput curve between 32K and 64K look like?
- Does the 8K fusion result (Metal Polar 13% over block-FP4) survive on models with different head dimensions and GQA ratios (Llama-3.2, Qwen2.5, Gemma-3), or is it an artifact of LFM2.5-8B-A1B's MoE cache geometry?
- Can radial precision be composed with CED-style cross-layer sharing (attacking orthogonal redundancy axes) without retraining, closing part of the 3,456 → 890 B/token gap to DeepSeek-V4.1-Flash?
- How do the rankings change under batched serving and prefix-cache reuse, where bandwidth savings from a 3.6× smaller cache should matter more than in single-stream decode?
