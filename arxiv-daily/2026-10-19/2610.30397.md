> **一句话总结：** 提出一条纯软件、端到端的 DRAM 地址映射逆向流水线：在 ARM 嵌入式平台（Jetson Orin Nano / LPDDR5 与树莓派 4B / LPDDR4）上采集 1000 万条地址对延迟样本，对每个候选阈值用 Knock-Knock 风格 GF(2) 线性代数求解 bank 掩码并逐一记录验证指标；在 Jetson 上选定阈值 550 CPU 周期处，最优 7 掩码解的组验证通过率达 0.996907，去掉任一掩码后通过率如预期近似减半（≈0.498454）。

> **TL;DR:** A software-only, end-to-end pipeline recovers and verifies DRAM bank-address masks on ARM embedded platforms — Jetson Orin Nano (LPDDR5) and Raspberry Pi 4B (LPDDR4) — by sweeping latency thresholds over 10,000,000 measured address-pair latencies, running a Knock-Knock-style GF(2) nullspace solver per threshold, and recording verification metrics for every candidate instead of returning a single answer. On Jetson Orin Nano the best 7-mask set reaches a 0.996907 group-verification pass rate at threshold 550 CPU cycles (10-round average), versus "substantially lower" pass rates for the lower-dimensional candidate sets (on Raspberry Pi 4B the runner-up 3-mask set drops to a negligible pass rate while the 4-mask set stays near 1.0); single-function verification on Jetson shows removing any one mask drops the pass rate to ≈0.498454, matching the predicted halving. Caveat: no Rowhammer bit flips are actually demonstrated — the attack payoff is deferred.

## 核心贡献

- **首个面向嵌入式 LPDDR5 平台（以 Rowhammer 分析为目标）系统研究"DRAM 地址映射逆向 + 软件验证"的工作**：填补了此前研究集中在桌面/服务器级 Intel/AMD 平台、而嵌入式 ARM + LPDDR5 系统缺少覆盖的空白。
- **纯软件、端到端、无需先验知识的自动化流水线**：延迟测量 → 延迟直方图 → 阈值扫描 → Knock-Knock 风格 GF(2) 线性约束求解 + RREF 得到 bank 掩码 → 组验证（group verification）+ 单函数验证（single function verification）。全程不需要 DRAM 层级先验知识——尤其不需要 bank 数量作为输入（LPDDR5 支持 BG/8B/16B 多种 bank 模式，连芯片料号都不足以确定 bank 数，这使许多先前方法不适用）。
- **对每个候选阈值系统性地记录求解出的 bank 掩码与验证指标**，而非像先前方法只返回单一推断解，从而支持更稳健、有证据支撑的掩码选择。
- **跨两个不同内存代际的平台实例化**（LPDDR5 与 LPDDR4），证明方法不依赖单一设备或 DRAM 配置；两个平台上最终解的组验证通过率都接近 100%。

## Key Contributions

- **First systematic study of DRAM address-mapping reverse engineering plus software verification on an embedded LPDDR5 platform in the context of Rowhammer analysis**, addressing the bias of prior work toward desktop/server-class Intel/AMD systems.
- **A software-only, end-to-end automatic pipeline** (latency measurement, histogram generation, threshold sweep, Knock-Knock-style solving, two verification stages) that requires **no prior knowledge of the DRAM hierarchy** — critically, it does not need the number of banks as input, which matters because LPDDR5 supports multiple bank modes (BG, 8B, 16B) so a DRAM part number alone does not reveal the bank count.
- **A record-everything workflow**: for each candidate threshold in the sweep, the pipeline stores the solved bank masks and their group/single-function verification metrics, enabling robust, evidence-based selection rather than returning a single inferred mapping like DRAMA-style exhaustive search or Knock-Knock alone.
- **Cross-platform instantiation on two ARM boards with different memory generations** — Jetson Orin Nano (LPDDR5) and Raspberry Pi 4B (LPDDR4) — showing the approach is not tied to one DRAM configuration; final solutions achieve group-verification pass rates close to 100% on both.

## Methodology

The core physical signal is the DRAM row-buffer conflict timing side channel: two physical addresses that map to the same bank but different rows force a PRECHARGE + ACTIVATE cycle when accessed sequentially, incurring higher latency than accesses serviced by bank-level parallelism. The pipeline has two phases.

**Phase 1 — Latency measurement.** The tool allocates a fraction of system memory and repeatedly measures the latency of sequentially accessing two randomly selected addresses, collecting 10,000,000 latency samples (latency expressed in CPU clock cycles).

**Phase 2 — Threshold sweep.** For every candidate threshold derived from a histogram of all measured latencies:

1. **Same-bank pair extraction.** Address pairs whose measured latency exceeds the threshold are treated as same-bank candidates.
2. **Bank-mask computation (Knock-Knock-style).** The key algebraic fact: if addresses *a* and *b* map to the same bank, then for every bank mask *m* (an XOR/parity function over physical address bits, i.e., linear over GF(2)), m(a) = m(b) ⇔ m(a⊕b) = 0 ⇔ m·Δ = 0 (mod 2), where Δ = a⊕b. Stacking XOR vectors of sampled same-bank pairs into a difference matrix D, all valid bank masks must lie in the GF(2) nullspace of D. The pipeline subsamples 100 same-bank pairs per run, repeats the computation 200 times, computes the nullspace basis, and applies Gaussian elimination over GF(2) to obtain the reduced row echelon form (RREF) — the RREF basis vectors are the final bank masks. This turns exhaustive XOR-function enumeration into polynomial-time linear algebra.
3. **Group verification** (protocol from Heckel et al., ESORICS 2025): 20,000 addresses from the allocated region are pooled, bank IDs are computed from the candidate mask set, and addresses are partitioned into 2^(#masks) groups. In each group, an anchor A1, a same-bank partner A2, and a different-bank address B1 are chosen; latencies t1 = lat(A1,A2) and t2 = lat(A1,B1) are measured. An iteration passes if t1 > threshold and t2 < threshold. The pass rate (averaged over 10 rounds) measures whether the induced bank partition agrees with observed timing behavior.
4. **Single-function verification.** Each bank mask is removed in turn and the group pass rate is re-measured; if the removed mask is correct and independently contributes to the partition, the pass rate should drop to roughly half the group-verification rate, giving per-function evidence.

A threshold-sensitivity model complements the sweep: with psame(τ) = Pr[L_same > τ] and pdiff(τ) = Pr[L_diff < τ] estimated from the 10M-sample dataset, the expected pass rate is p_pass(τ) = psame(τ)·pdiff(τ) under an independence approximation — near zero at extreme thresholds and near 1.0 only in the separation region.

## Results & Highlights

- **Jetson Orin Nano (LPDDR5), group verification:** the sweep produced five distinct recovered bank-mask sets; the best set — 7 masks (0x214ccde00, 0x110ad4400, 0x950ccc00, 0x50eeac00, 0x21708c00, 0xd331200, 0x235d600) — achieves a pass rate of **0.996907 at threshold 550 CPU cycles** (10-round average, the highest in the swept range), whereas the lower-dimensional candidate sets achieve "substantially lower" pass rates and several sets surface at only a single threshold (single points in Fig. 1).
- **Jetson Orin Nano, single-function verification:** removing any one of the 7 masks yields a measured pass rate very close to the predicted **0.498454** (exactly half of 0.996907), evidence that each addressing function contributes independently to the partition and that all 7 masks are individually justified.
- **Raspberry Pi 4B (LPDDR4), head-to-head candidate comparison:** the sweep yields two candidate sets — set 1 = {0x80000000, 0x2000, 0x1000} (3 masks) and set 2 = {0x80000000, 0x4000, 0x2000, 0x1000} (4 masks). Set 2 dominates the high pass-rate region, remaining **close to 1.0 across most of the selected threshold range, while set 1 yields a negligible pass rate** — a clean discrimination between hypotheses that differ by a single mask bit (0x4000).
- **Threshold-sensitivity analysis (Jetson):** modeling the expected pass rate as p_pass(τ) = psame(τ)·pdiff(τ) over the 10,000,000 measured latencies predicts near-zero pass rates at very low/high thresholds and a high-pass-rate region of approximately **500–570 CPU cycles**, consistent with the empirically observed best threshold of 550. The latency histogram partitioned by the predicted bank relation (Fig. 2) shows clear separation: different-bank measurements concentrate at low latencies, same-bank measurements at high latencies.
- **Data/solver scale:** 10,000,000 latency samples per platform; bank-mask computation run 200 times with 100 subsampled same-bank pairs per difference matrix; group verification uses a 20,000-address pool across 10 rounds.

## Authors & Credibility

The authors are Hewen Zhang and Ian G. Harris (professor) of the University of California, Irvine — a group with prior work in hardware security and embedded systems. The paper is a short (workshop-style, cs.AR) contribution that honestly positions itself as a combination and systematization of established components: the timing side channel and address-pair methodology trace to DRAMA (USENIX Security '16), the GF(2) nullspace formulation to Knock-Knock (Plin et al., arXiv:2509.19568), and the two verification stages to Heckel et al., "Verifying DRAM Addressing in Software" (ESORICS 2025). References are appropriate and current (through 2025). The framing is modest — claims are about pass rates and mask recovery, not about attacks demonstrated. No artifact or code release is mentioned, and no external ground-truth comparison of the recovered masks is provided.

## Critical Assessment

- **Novelty: moderate and incremental.** The three ingredients (row-buffer-conflict timing, GF(2) nullspace solving, two-stage verification) are all prior work; the new elements are the threshold sweep wrapper and the record-every-candidate workflow. This is a reasonable engineering contribution, but the paper should not be read as a new reverse-engineering algorithm.
- **Verification is self-referential.** Both recovery and verification rely on the same latency side channel, so systematic measurement biases (e.g., cache or prefetcher aliasing that correlates with address bits) could in principle fool both stages. There is no ground-truth check — notable because the Raspberry Pi 4B's LPDDR4 mapping has been characterized in earlier embedded-Rowhammer literature, so an external comparison was at least feasible there and is absent.
- **Missing ablations and coverage gaps.** Single-function verification is run only on Jetson Orin Nano, not on Raspberry Pi 4B. Only bank masks are recovered — channel/rank/bank-group/row/column functions (needed for actual double-sided Rowhammer) are not addressed, and the 7 Jetson masks are reported as raw 34–36-bit values with no decomposition into DRAM-component roles. The threshold range itself appears hand-chosen (500–580 cycles swept), and no wall-clock cost for the 10M-sample measurement phase is reported.
- **The headline motivation is not demonstrated.** The abstract promises "subsequent Rowhammer analysis," but no bit flips, no hammering experiments, and no TRR interaction results appear in the paper — the security payoff is entirely deferred.
- **Statistical rigor is thin.** Pass rates are averaged over 10 rounds with no variance, confidence intervals, or pass/fail criteria for accepting a mask set; several Jetson candidate sets exist at only a single threshold point, making the ranking between non-champion sets weakly supported. The p_pass = psame·pdiff model leans on an unvalidated independence approximation.

## Strengths

- Clean, reproducible-in-principle pipeline on cheap commodity hardware, with no privileged access (no kernel module dependencies described beyond user-space allocation), no DRAM documentation, and no bank-count input — exactly the DRAM-agnostic property LPDDR5 needs.
- The record-per-threshold workflow is a genuine methodological improvement over single-point-inference prior work: it converts an implicit hyperparameter (the latency threshold) into an explicit, evidence-ranked search.
- The Raspberry Pi result is a crisp, near-textbook discrimination: two hypotheses differing by one mask (0x4000) separate into near-1.0 vs negligible pass rates, which is convincing evidence the verification statistic has real discriminative power.
- Honest, well-scoped writing: limitations of prior work (Intel/AMD bias, bank-count requirement) are accurately stated, and the paper does not overclaim attacks it did not perform.

## Limitations

- Bank functions only: no row, column, channel, or bank-group recovery, so the output is not yet sufficient to mount targeted double-sided Rowhammer attacks.
- No end-to-end Rowhammer validation — recovered masks are never used to trigger a single bit flip, leaving the practical value unquantified.
- Verification evidence is self-consistency based; no external ground truth on either platform.
- Thresholds are in platform-specific CPU cycles and the sweep range is manually set; no guidance for porting to a third platform is given beyond the general recipe.
- Single-function verification absent on Raspberry Pi 4B; no runtime/cost reporting; no code or artifact release mentioned.

## Questions for Further Exploration

- Do the recovered 7 bank masks on Jetson Orin Nano actually enable double-sided Rowhammer bit flips on LPDDR5, and what flip rates are achievable against its Target Row Refresh (TRR)?
- Can the GF(2) framework be extended to recover row, column, bank-group, and channel functions, producing a complete mapping usable for attack or for memory-side SDC fault injection studies?
- How stable are cycle-based thresholds under DVFS, thermal variation, and OS/cache interference — would a normalized or percentile-based threshold make the sweep portable across platforms?
- Can ground truth (vendor documentation or prior published mappings for Raspberry Pi 4B) be used to externally validate the verification statistic's false-positive rate?
- What is the wall-clock cost of the 10M-sample measurement phase, and could active sampling (adaptively choosing address pairs) reach the same confidence with an order of magnitude fewer measurements?
- Does LPDDR5's 16B bank mode or refresh scheduling ever smear the same-bank latency distribution enough to break the separation shown in Fig. 2?
