Methodology

bytes (routing) × bandwidth (kernel) — each measured by the tool suited to it

Splits each speculative step's time into two independently measurable inputs, proves when speculation pays, then validates the prediction end-to-end on real engines.

Cost model

τ_p(n) = t₀ + D(n)/β_D + E_p(n)/β_p(n) + φ_p(n) — fixed overhead, dense attention/KV reads, expert bytes at each kernel's own effective bandwidth, plus launch overhead. Prior work charged every expert read the same bandwidth; this is what breaks.

Calibration (< 1 h per model)

Expert bytes follow from routing alone, computed offline from WikiText-103 traces (60 test articles). Bandwidths come from a one-layer benchmark running each engine's own kernels — 22 min (CUDA) / 48 min (Metal) vs 3.8–8 h whole-model speculative sweeps.

Theory — proved in Lean 4 (Mathlib)

Speedup condition for arbitrary positive step times; best draft length k*(a) is a monotone non-decreasing “staircase” in acceptance rate; dedup wins iff ū(n) < r(n); five error bounds — 10% bandwidth error moves predicted speedup ≤ 25%, savings near crossovers amplified 3.2–340×.

Experiment matrix

12 engine×model×depth configs (llama.cpp Metal/CUDA, MLX-LM × OLMoE-1B-7B, Qwen3-30B-A3B, gpt-oss-20b, DeepSeek-V2-Lite; depths 512/4096). Verify at n = 1–9; speculation at k = 0–8 × 11 acceptance rates (oracle draft); 70 Nsight Compute profiles verify byte counts without timing.

Results — beyond the headline

12 configurations · 3 engines · 4 MoE models
  • 8/8 engine×model pairs: dedup is slower at n = 2 — byte share ū(2) = 0.72–0.83 exceeds bandwidth ratio r(2) = 0.37–0.75; dedup only wins from 5–8 tokens per pass, or never.
  • Hardware counters (70 CUDA profiles): dedup kernel reads its union bytes within 0.2–2.5%; per-slot reads 1–2.35× union — L2 cache serves the repeats, and its median bandwidth (933–1018 GB/s at n = 8) exceeds the RTX 4070 Ti SUPER's 672 GB/s DRAM peak from n = 4.
  • Crossover predicted within one pass size in 10/12 configs (11/12 with recorded routing; the measured-time version matches all 4 CUDA crossovers exactly).
  • Pre-registered DeepSeek-V2-Lite on CUDA: best draft length within one at 22/22 acceptance values, verify time within 10.1% — while a post-hoc fit invents a crossover at n = 7 where none is measured.
  • Real-draft reality check: plain decoding fastest on 33/37 held-out MT-Bench prompts; the oracle draft emits 2–5% fewer tokens/step than the geometric expectation, putting measured speedups 1–21% below prediction.

Strengths

  • Clean conceptual split — bytes (routing-determined) vs bandwidth (kernel-determined) — each measured by the right tool: traces, a sub-hour single-layer benchmark, hardware counters as an independent check.
  • Lean 4/Mathlib formalization of the full theory (speedup condition, staircase, dedup threshold, five error bounds) — rare rigor for an inference-systems paper.
  • Unusually honest evidence handling: pre-registered vs post-hoc predictions kept distinct; failed scoring rules and the one post-hoc correction named openly.
  • Actionable output: crossover point and best draft length follow from a < 1-hour calibration instead of multi-hour sweeps or hand-tuned switches.

Limitations

  • Oracle draft with enforced geometric acceptance; no real draft model beyond one small MT-Bench check — and acceptance is neither geometric nor stationary in deployment.
  • Predictions for 3 of 4 models were computed after the measurements, with one post-hoc correction — “10 of 12 crossovers” is post-hoc accuracy, not forecasting skill.
  • Batch size one, one machine per platform, models spanning only 7B–30B; DRAM-byte validation exists only on CUDA.
  • Bandwidths don't transfer across models — fitted on one, misses a held-out model by 9–206%, so calibration must be redone per model; the theory never derives r(n) from kernel structure.
  • No public code/data/Lean artifact (“available on request”); single author with disclosed AI-agent assistance.

Questions for further exploration

open threads from the summary
  1. Q1Can r(n) be predicted from kernel structure — tile shapes, gather patterns, quantization format — instead of measured per model, given the 9–206% cross-model transfer failure?
  2. Q2Does the staircase prediction survive a real draft model with non-geometric acceptance and a nonzero, n-dependent draft cost h(k)?
  3. Q3How do the ū(n) vs r(n) trade-offs shift at batch sizes > 1, where the routing union grows and both kernels amortize launches differently?
  4. Q4Would hardware with lower DRAM bandwidth or weaker compute (edge NPUs, mobile SoCs) push r(n) toward 1 and let deduplication win at all pass sizes?
  5. Q5Can the gpt-oss d=4096 failure — self-repeating greedy continuations violating stationary routing — be modeled explicitly, e.g. conditioning the byte estimate on the draft's n-gram repetition statistics?
