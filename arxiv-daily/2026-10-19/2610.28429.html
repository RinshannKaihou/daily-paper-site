01Methodology — how it decides

Racer answers “do these two kernels compute the same function?” over a checking instance: the kernel under test, a reference, and declared shared tensors (inputs = free variables, uninitialized memory = symbolic).

  1. Pose. Pair the kernel with an independent — or naive LLM-drafted — reference; name the output tensors to compare.
  2. Lower to PTX. CUDA C++, Triton, and PTX front ends all compile to PTX ISA 8.4, making analysis front-end agnostic and memory ops explicit.
  3. Symbolic execution. Every instruction becomes a SymPy expression over exact rationals; a lockstep CTA scheduler orders memory per epoch, models atomics and async copies, refuses divergence.
  4. Decide. Per-cell expressions are CAS-simplified, then resolved by exact numeric refutation, then Z3 (counterexamples confirmed numerically). Shape reduction reuses proofs across uniformity classes via validated renamings.

02Results — beyond the headline

92.7% of the 82 bugs (76) were exposed automatically — 35 via race/memory diagnostics, 41 via output refutation. CAS alone caught just 1; numeric refutation + Z3 resolved 40 of 46 leftovers (87%).

03Strengths

  • Real, high-value problem: every AI stack rewrites the same operators per GPU generation and format; correctness currently rests on tolerance-based testing with known blind spots.
  • Grounded taxonomy: each of the four differential-testing blind spots is illustrated by a named, confirmed bug — fla's 4,032 out-of-allocation writes, FlagGems' +2ε variance error — not hypotheticals.
  • Sound by construction: fail-closed refusals, Z3 counterexamples must survive exact numeric confirmation, proof reuse requires structural validation.
  • Immediate impact: 76 new bugs filed upstream across 23 libraries that production systems run on.
  • Honest evaluation: per-bug assessments labeled as such; refused/timeout outcomes disclosed; cross-check shows zero disagreements.

·Limitations

  • Not a drop-in CI gate: 20.7% of kernels are execution-refused and 0.6% time out with no decision.
  • Per-configuration, not shape-generic: "entire input space" means input values at checked launch configs — a subtle echo of the sampling critique the paper aims at testing.
  • NVIDIA/PTX only; AMDGCN portability described in principle, unproven elsewhere.
  • Oracle problem remains: bugs shared by kernel and reference stay invisible; LLM-drafted references add a non-deterministic component.
  • Unknown verdicts persist (6 bugs needed manual expression inspection); idiom templates must be hand-authored per compiled routine — a maintenance treadmill.
  • Minutes per kernel — CI-scale, not inner-loop development.

04Questions for further exploration

  • Can shape reduction be lifted to shape-generic proofs covering all tensor shapes and launch configs, not sampled ×1/×2/×4 points?
  • What dominates the 499 refused kernels — and are tensor-core MMA and FP8 paths tractable under exact reals?
  • What is the real false-positive rate and triage cost behind 197 candidates → 82 bugs?
  • What runtime budget makes per-merge equivalence checks practical in FlagGems / vLLM / torchao CI?
  • Does the approach port to AMDGCN, or to Triton IR directly — and what is lost by leaving PTX?
  • Could Racer quantify the downstream training-loss impact of sub-tolerance kernel bugs compounding over millions of steps?
