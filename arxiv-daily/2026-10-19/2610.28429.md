> **一句话总结：** 提出 Racer——一个在 PTX 层对 GPU kernel 做符号等价性检查的引擎：把 kernel 与参考实现跑在符号输入上、将每个输出单元变成精确代数表达式，从而一次性覆盖整个输入空间并区分浮点误差与逻辑 bug；在 41 个生产级代码库的 2,408 个 kernel 中发现 82 个真实 bug（76 个为新发现、41 个已确认），远超 compute-sanitizer（18 个）和 Volta（9 个）。

> **TL;DR:** Racer replaces tolerance-based differential testing of GPU kernels with symbolic equivalence checking at the PTX level: both the kernel under test and a reference are executed over free-variable inputs, each output cell becomes an exact algebraic expression (via SymPy), and equivalence is decided for ALL inputs at once — plus race/memory diagnostics. Across 2,408 production kernels from 41 GitHub targets it finds 82 real bugs in 23 libraries (76 previously unknown, 41 confirmed), versus at most 47 for an idealized oracle differential tester with exhaustive inputs, 18 for NVIDIA's compute-sanitizer, and 9 for Volta, the closest prior equivalence checker. Shape reduction, a lockstep CTA scheduler, and idiom templates/Z3 refutation make it practical: 70.5% of kernels get an equivalence proof, with up to 11.8x end-to-end speedup from proof reuse (chunk_ttt_linear_bwd_dv: 204.9s to 17.4s), though 20.7% of kernels are still refused for unsupported constructs.

## 核心贡献

- **符号等价性检查（symbolic equivalence checking）用于 GPU kernel 正确性**：让待测 kernel 与参考实现在符号输入上执行，每个输出单元成为关于自由变量的精确代数表达式，再逐单元判定两组表达式是否对所有输入取值相同。一次检查覆盖整个输入空间，且表达式是精确的——任何差异都对应被计算函数的真实差异，而非浮点舍入的伪影。
- **对 82 个逃过差分测试的真实 bug 的系统研究**，归纳出差分测试的四大盲区：(a) 随机采样无法覆盖输入空间；(b) 隐式输入（如未初始化内存）不出现在函数签名中；(c) 输出张量之外的区域（越界写）从不被检查；(d) 逻辑 bug 造成的偏差可能小于为容纳正确优化 kernel 浮点误差而设的容差。
- **Racer 引擎（PTX 层）**：返回 Equivalent / Inequivalent（附具体反例输入）/ Unknown 三种判定；支持 CUDA C++、Triton 与 PTX 三种前端（nvcc 12.4 与 Triton 3.2.0 均编译到 PTX ISA 8.4），忠实建模整网格、多次 launch、原子操作与异步拷贝，不能建模的构造一律拒绝执行（fail closed）。
- **三项使技术实用的关键技术**：Shape Reduction（按一致性类复用代表性单元的证明并用经过结构验证的重命名传播）、lockstep CTA 调度器（同步点间锁步推进线程、按 epoch 记录内存访问以暴露缺失屏障、仅在完成点暴露异步拷贝数据、按序无关性合并原子更新）、idiom 模板 + 精确数值反驳 + Z3 第二证明器（把编译后的位操作序列还原为 log 等数学函数，并在 CAS 不决时搜索边界反例）。
- **大规模实证**：2,408 个生产 kernel、82 个 bug（76 新、41 确认），92.7%（76/82）由 Racer 自动暴露；对 CAS 化简后仍不决的 46 个案例，精确数值反驳解决 36 个、Z3 再解决 4 个（合计 87.0%）。

## Key Contributions

- **Symbolic equivalence checking as a principled alternative to differential testing**: both kernels run on symbolic inputs, every output cell holds an exact expression over free variables, and equivalence is a statement about functions, not sampled numbers. All four differential-testing blind spots dissolve by design: one check covers the input space; uninitialized memory is symbolic; every store address is known; and no tolerance parameter exists to hide a wrong formula.
- **A bug study of 82 deployed-library bugs** that enumerates, bug by bug, why differential testing cannot close its four blind spots — including 6 "below-tolerance" bugs (e.g., FlagGems InstanceNorm reconstructs variance from rstd = sqrt(1/(var+eps)) as 1/rstd^2 + eps instead of 1/rstd^2 - eps, overestimating variance by 2*eps) and 6 out-of-bounds write bugs (e.g., fla's squared-ReLU backward writes all 4,096 block results when the output tensor has only 64 elements, so 4,032 writes exceed the allocation while the checked output matches the reference).
- **Racer, a PTX-level checking engine** with three verdicts and fail-closed semantics: it models full grids (not just CTA 0 like Volta), multi-launch programs, atomics, and async copies; unsupported constructs are refused rather than approximated.
- **Three scalability/concurrency/conclusion techniques**: shape reduction (prove one representative cell per uniformity class and transport the proof via a structurally validated renaming of input variables); a lockstep CTA scheduler that runs threads between synchronization points, orders memory accesses in epochs, exposes async-copy data only at its completion point, and combines order-independent atomic updates; idiom templates that recover mathematical meaning from compiled bit-manipulation sequences (e.g., an inlined libdevice __nv_logf becomes log(x)), backed by exact numeric refutation over rationals/intervals and a Z3-based second prover for boundary counterexamples.
- **Evidence at production scale**: 82 real bugs across 23 libraries from 41 collection targets, 76 previously unknown, 41 confirmed (29 fixed upstream, 4 acknowledged, 8 independently validated), with per-method detection comparisons against an exhaustive oracle differential tester, compute-sanitizer, and Volta.

## Methodology

Racer answers "do these two kernels compute the same function?" via a four-step pipeline over a *checking instance* — a Python class declaring shared tensors (`vk.input` free variables, `vk.empty` uninitialized, `vk.zeros`/`vk.full` initialized), two programs as launch sequences, and launch configurations.

1. **Pose the question**: the user pairs the kernel under test with a reference (an independent implementation, a naive LLM-agent-drafted reference under the authors' direction, or another launch configuration expected to preserve semantics). Output tensors to compare are named explicitly.
2. **Lower to PTX**: all front ends (CUDA C++, Triton, PTX) compile to PTX — the lowest publicly documented NVIDIA instruction set — making analysis front-end agnostic and exposing memory operations explicitly. The running example (vLLM #941) shows two rotary-embedding kernels whose PTX differs only in address arithmetic.
3. **Symbolic execution**: every PTX instruction is interpreted into SymPy expressions with floating-point ops modeled over the reals (unbounded-precision rationals). The lockstep scheduler executes each thread until exit or a synchronization point; barriers resolve only when all participants arrive (divergence is refused); reads/writes are recorded per epoch to catch missing barriers; atomic updates are combined at the next barrier/launch completion only when order-independent; cp.async/TMA data appears only at its modeled completion point.
4. **Decide equivalence**: paired output cells' expressions are subtracted and simplified by the CAS. Unresolved cells go to exact numeric refutation (concrete rational assignments; interval arithmetic with outward rounding for sqrt/exp/log) and then to Z3, whose counterexamples must be confirmed numerically before an Inequivalent verdict. Shape reduction groups output cells whose expression pairs match under a shared renaming of input variables (candidates derived from input footprints: translations for matmul-style slices, plus an exchange for row-softmax numerators), so one proved representative covers the whole class.

A verdict is Equivalent only when every cell is proved equal directly or by validated proof reuse; any refuted cell yields Inequivalent with a concrete witness input; anything left unresolved is Unknown. Experiments ran on a 128-core dual AMD EPYC 9575F server, Python 3.11.16, SymPy 1.13.1, Rocky Linux 9.6, CUDA 13.1, with an NVIDIA RTX PRO 6000 capturing real launches and replaying witnesses.

## Results & Highlights

- **Bug yield**: Across 2,408 production kernels from 41 collection targets, Racer found **82 real bugs in 23 libraries — 76 previously unknown (all filed upstream), 41 confirmed** (29 fixed, 4 acknowledged, 8 independently validated). Per library: FlagGems 25 found / 23 new / 5 confirmed; flash-linear-attention 11/11/11; attorch 6/6/6; CuPy 6/6/1; Triton-distributed 4/3/1; torchao 4/4/3; Liger-Kernel 3/2/2; vLLM 2/0/0 (both rediscoveries); 15 others 21/21/12.
- **Head-to-head detection on the 82-bug set**: an oracle differential tester with unlimited compute and exhaustive tensor inputs could find at most **47/82**; NVIDIA's compute-sanitizer detects **18/82** (4 implicit-input, 3 unchecked-output, 11 other; it misses all 4 race bugs at the evaluated configurations); Volta, the closest prior equivalence checker, detects only **9/82** and none of the sampled-input, below-tolerance, or race bugs. Volta is blocked by unsupported instructions in 41 cases (e.g., it stops at an atomic before exposing the Triton-distributed uninitialized-memory bug), cannot compare kernels that partition work differently across CTAs (FlagGems MSE-backward writes 4 cells in CTA 0 while the reference writes 1 cell per CTA across 4 CTAs), and does not support multi-launch programs.
- **Automatic exposure rate**: Racer automatically exposes **76 of 82 bugs (92.7%)** — 35 via race/memory diagnostics, 41 via output refutation; the remaining 6 required manual inspection of Unknown cases. Of the 46 comparisons left inconclusive by CAS cancellation, exact numeric refutation resolves 36 and Z3 resolves 4 more (**40/46 = 87.0%**); CAS cancellation alone catches just 1 (a constant bias in FlagGems' running-statistics update).
- **Coverage over 2,408 kernels**: **1,698 (70.5%) proved Equivalent** (at least one proof, no bug-candidate outcome), **197 (8.2%) bug candidates** (77 kernels with refutations, 23 with Unknown, 110 with race/memory diagnostics — overlapping counts), **14 (0.6%) timeout with no decision**, and **499 (20.7%) execution refused** (unsupported integer ops, symbolic-dependent addresses/control flow, unsupported synchronization patterns).
- **Shape-reduction speedups (50-kernel sample at ×1/×2/×4 captured shapes, 150 configs)**: verdicts agree with whole-grid checking on all 148 configurations both decide — zero contradictions. On the linear-attention backward kernel chunk_ttt_linear_bwd_dv, end-to-end time drops from **204.9s to 17.4s at ×1 (11.8x)** and **415.8s to 34.0s at ×2 (12.2x)**, using only **16 representative proofs for 2,048/4,096/8,192 output cells**; at ×4 whole-grid checking exceeds the 600s budget while shape reduction proves equivalence in 70.7s. Across the 40 equivalent kernels at ×1, mean end-to-end time falls from 14.5s to 6.0s (2.4x aggregate); on the fixed 38-kernel set (Table 3), means fall from 9.5/22.2/47.0s to 5.5/14.3/30.3s (1.72x/1.55x/1.55x), with deciding time at ×4 dropping 18.7s to 2.1s while symbolic execution (~28s) becomes the bottleneck.

Tuan Truong Vu and Cheng Tan, Northeastern University. The work is a systems-verification study in the PL/systems tradition (the paper will feel at home at OOPSLA/PLDI/SOSP venues; the Volta baseline they compare against is published in PACMPL OOPSLA2 2026). Credibility is high: all 76 new bugs were filed upstream as issues or PRs rather than merely claimed; 41 are confirmed with a breakdown (29 fixed, 4 acknowledged, 8 independently validated), and the evaluation discloses its machinery (SymPy 1.13.1, Z3, nvcc 12.4, Triton 3.2.0, CUDA 13.1, RTX PRO 6000 for launch capture and witness replay). ## Critical Assessment

- **Novelty**: The individual ingredients (symbolic execution over exact reals, CAS-based equivalence, proof reuse) are not new — Volta already symbolically executes PTX over exact reals. The genuine novelty is engineering scale and bug orientation: whole-grid rather than CTA-0 comparison, multi-launch support, atomics and async copies, and a bug-finding campaign that demonstrates an order-of-magnitude detection advantage over the shipped Volta (82 vs 9 on Racer's bug set).
- **Rigor caveats on the baseline comparison**: the tool comparison is evaluated *on the set of 82 bugs Racer itself found*, which biases the deck — bugs invisible to Racer's refusal semantics are never counted against it. The authors are careful to label the oracle differential tester a per-bug assessment ("not a measured testing campaign") and to note sanitizer/Volta results are configuration-specific ("do not establish that no concrete test can expose those bugs"), which is honest, but a differential-testing campaign with adversarially improved generators would strengthen the 47/82 ceiling claim. Volta is run "as shipped," leaving version/config sensitivity unexamined.
- **Triage burden is understated**: 197 bug-candidate kernels yielded 82 real bugs, so roughly 115 candidates were dismissed on manual review — a substantial human cost that the paper does not quantify (no precision/recall analysis of candidate triage, no false-positive taxonomy).
- **Coverage gap**: 20.7% of kernels (499/2,408) are refused outright — unsupported integer operations, addresses or control flow depending on symbolic data, and synchronization patterns beyond the model. The paper defers this to future work; for a production user, one in five kernels simply cannot be checked today.
- **Per-configuration, not shape-generic**: a proof "applies only to the outputs and index assignments checked at that configuration." Checking ×1/×2/×4 shapes is sampling launch configurations, not proving equivalence across all shapes — a subtle echo of the sampling critique the paper aims at differential testing, now at the configuration level.
- **Scalability ceiling**: symbolic execution dominates end-to-end cost (~28s of 30.3s at ×4), so proof-reuse speedups cap out; the 600s budget shapes several claims, and kernel complexity growth (tensor-core MMA paths, FP8) may strain the idiom-template approach, which must be extended per compiled routine.
- **Reproducibility**: strong on artifacts in principle (checking instances are Python, verdicts have concrete witnesses replayable on the RTX PRO 6000), but no artifact-release statement is given in the paper body, and the LLM-agent-drafted references introduce a non-deterministic component into the experimental setup.

## Strengths

- Attacks a real, high-value problem: every AI stack repeatedly rewrites the same operators (per GPU generation, numeric format, serving regime, kernel language), and correctness currently rests on tolerance-based differential testing with well-documented blind spots.
- The four-blind-spot taxonomy is empirically grounded — each category is illustrated with named, confirmed bugs (attorch hardshrink keeping x = ±λ; Triton-distributed's atomic-add into an uninitialized cell; fla's 4,032 out-of-allocation writes; FlagGems' InstanceNorm +2ε variance error), not hypotheticals.
- Sound-by-construction design: fail-closed refusals instead of approximations; Z3 counterexamples must survive exact numeric confirmation; proof reuse requires structural validation of the renaming — no verdict rests on an interleaving the engine happened to choose.
- The bug study alone is a contribution: 76 new bugs filed upstream across 23 libraries (FlagGems, flash-linear-attention, attorch, CuPy, torchao, Liger-Kernel, ...) is immediate practical impact on software millions of models run on.
- Careful, honest evaluation writing — per-bug assessments are labeled as such, timeout/refused outcomes are broken out rather than hidden, and contradictory-verdict analysis between whole-grid and shape-reduction checking shows zero disagreements.

## Limitations

- 20.7% of production kernels are execution-refused (unsupported constructs), and 0.6% time out with no decision — Racer is not yet a drop-in CI gate for arbitrary kernels.
- Equivalence is decided per checking instance and launch configuration; shape-generic proofs (all tensor shapes and grid configurations) are out of scope, so the "entire input space" guarantee is input *values* at checked configurations, not all shapes.
- NVIDIA/PTX only — no AMDGCN or other backends; the approach is described as portable in principle but unproven elsewhere.
- CAS/Z3 dependence means Unknown verdicts persist (6 bugs needed manual expression inspection), and idiom templates must be authored for each new compiled transcendental routine, a maintenance treadmill as compilers change.
- The reference-implementation burden remains: someone must supply an independent reference (or trust an LLM-drafted naive one), so semantic bugs shared by both sides — the classic oracle problem — remain invisible.
- Runtime is minutes per kernel (means of 5.5–30.3s at small shapes, up to ~70s at ×4 for a hard kernel), fine for library CI but not for inner-loop development of every kernel variant.

## Relevance

与「大规模 ML 的算力基础设施（算子与 kernel）」和「极端性能优化下的可靠性（浮点精度与数值正确性）」两个研究方向高度相关：它直接检测 serving/训练栈底层 kernel 引入的静默错误——包括藏在浮点容差之内、差分测试永远发现不了的数值 bug——并对 vLLM、FlagGems、Triton 生态等生产系统发现了 76 个新漏洞。

## Questions for Further Exploration

- Can shape reduction be lifted from cell-level proof reuse to *shape-generic* proofs, so one verification covers all tensor shapes and launch configurations rather than sampled ×1/×2/×4 points?
- What would it take to close the 499-kernel execution-refusal gap — which unsupported constructs dominate (integer ops vs. symbolic-dependent control flow vs. exotic synchronization), and are tensor-core MMA and FP8 paths tractable under the exact-reals model?
- What is the actual false-positive rate and triage cost of the 197 bug candidates, and could automated candidate classification (e.g., LLM-assisted triage against the kernel source) reduce the manual review burden?
- Can Racer's diagnostics and witnesses be integrated into kernel-library CI (FlagGems, Liger-Kernel, vLLM, torchao) so that every rewrite is equivalence-checked before merge, and what runtime budget makes that practical?
- Does the approach port to AMDGCN or to Triton's IR directly, and would checking at an intermediate level rather than PTX lose the front-end-agnostic uniformity that PTX provides?
- Could the idiom-template library be mined automatically from compiler output (matching many compiled transcendental implementations at once) instead of being hand-authored per routine?
- Since 6 "below-tolerance" bugs cause systematic errors that "can compound over millions of training steps," could Racer be extended to quantify the downstream training-loss impact of sub-tolerance kernel bugs it finds?
