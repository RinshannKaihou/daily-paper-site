Why this matters

Serving LLMs when GPU memory overflows? Idle CPU AMX cores can absorb decode work productively — more requests served, calmer tail latency, no extra GPUs.

Distilled from Relevance: LLM inference infrastructure, heterogeneous GPU–CPU scheduling, KV-cache management.

Critical edge

The headline gains rest on a NEO baseline the authors ported themselves (Qwen3 patches) and a vLLM run with host offloading and prefix caching disabled — no comparison against APEX, OmniServe, or FastDecode.

+ no public code · no error bars / repeated runs

Inside the paper

01Methodology — dual engines, one assist channel

  • Two engines, no shared iteration barrier. GPU owns prefill + GPU-resident decode; the AMX CPU engine owns host-resident decode with independent queues, scheduling clock, and KV manager.
  • Three-mode routing πP,F(b): Full-CPU / Split-Final / Fused-Assist, switched by two offline-profiled batch thresholds — (32, 16) on RTX 4090, within 0.070% of the exact optimum.
  • AMX economics. oneDNN BF16 + custom AVX512-BF16 PagedAttention: 20 TFLOPS on Sapphire Rapids (4.5× AVX512) — ~10× behind a 4090, but practical at serving batch sizes.
  • Host-memory envelope. Four obligations — used + planned + finish-growth + migration reserve — stop the two schedulers from overselling host KV.
  • Eval. 2,000-request Azure Conversation & Code traces, fixed-seed exponential arrivals; baselines vLLM 0.22.1 and author-patched NEO; three model/hardware configs.

  • Dense Assist is cheap: 2–5 µs polling per layer; of assist time, CUDA execution is 60.4–70.0% — mostly the dense compute it exists to accelerate.
  • Host KV is an admission knob, not a fuel tank: 120 GiB sustains +28.7% vs 30 GiB, but plateaus to 240 GiB — CPU compute and bandwidth are the ceiling; smaller pools even yield lower P99 ITL.
  • CPU tensor parallelism pays: TP=2 lifts rates +15.0% (normalized-latency target) and +29.7% at P99 ITL by spreading AMX work and KV reads across NUMA domains.
  • Regime boundary (stated honestly): on prefill-heavy Azure-Code (2,348-token prompts, 22-token outputs), GPU-only vLLM wins on the H20 configs; DualPace still beats NEO and keeps the lowest P99 ITL over most rates.
Balance sheet

03Strengths

  • Clean problem decomposition: the GPU-gating diagnosis (overlap constraints → bursty stalls → P99 ITL) is argued and measured in Figure 1 before any solution is proposed.
  • Two-threshold routing with offline profile fitting sidesteps online config search; fully specified (Algorithm 1, Appendix B) with a near-optimal tie-break minimizing assist calls.
  • Cross-engine KV envelope with finish-peak and migration reserves — a principled answer to the double-buffering and oscillation decoupled schedulers would otherwise cause.
  • Honest boundary characterization: states where the approach does not help rather than hiding it.
  • Comprehensive tail reporting — P99 TTFT, ITL, and TPOT on both traces.

04Limitations

  • Decode-oriented bias: gains concentrate on sustained-decode workloads; short-output, long-prompt serving sees little over GPU-only vLLM.
  • The intrinsic CPU–GPU speed gap remains: DualPace removes the scheduler-induced tail, not the execution-speed tail — vLLM still wins absolute P99 ITL.
  • CPU compute is the eventual ceiling: past ~120 GiB host KV, AMX throughput and memory bandwidth saturate; TP only tested up to 2.
  • Single-NUMA CPU allocations, 2,000-request trace prefixes, no error bars — limited statistical confidence.
  • No comparison against FastDecode / APEX / OmniServe / LIA, and no public code artifact at time of writing.
Open threads

05Questions for further exploration

  1. Do the profiled (P, F) crossovers shift with quantized KV caches (INT8/FP8) as CPU attention bandwidth demand drops?
  2. Could Dense Assist extend to prefill assistance, or does ownership transfer at prefill time conflict with the admission envelope?
  3. Tail behavior under preemption, cancellation bursts, or adversarial arrivals — beyond exponential inter-arrivals?
  4. Does the migration reserve B_migration become overly conservative at high eviction rates, stranding host capacity?
  5. How much of the NEO gap is the authors' own Qwen3 port — a head-to-head vs APEX/OmniServe would isolate the architectural contribution?
