Key metric · fixed-answer verifier measure

90/90

verifier verdicts flipped from false acceptance to correct rejection — identical planted answers, only the formatter wording changed (scope · completeness · uncertainty families).

Why this matters

The neglected software layer between model and world silently corrupts what agents see — and a $74.44 audit can find it in any codebase.

Critical edge — read before citing

The 90/90 flip rests on author-written, deliberately maximal false answers — a worst-case construction likely to overstate real-world flip rates.

And condition B bundles disclosure with handling instructions, so the −62…−92 pp effect cannot be attributed to disclosure alone.

01 Methodology — how they proved wording alone does it

Every defect comes from one deployed system: a RAG research assistant over a 17,807-document digitized archive, so the failure families are grounded in production incidents, not synthetics.

  1. Audit the formatter layerReproduce each omission against database facts — a term first occurring at character 1,000,072 of a 1,031,201-char transcript, past a 1M cap the output never mentions.
  2. Paired causal experimentIdentical tool results, two wordings: A = warped (production-verbatim), B = disclosing; hash-frozen before grading rules were fixed. One-shot answers, no tool loops; overclaim graded against pre-written forbidden-claim lists.
  3. Measure both sidesAgents: 1,200 runs across Claude Sonnet 5, GPT-5.6 Sol, Gemini 3.1 Pro. Verifiers: planted false answers judged under both wordings, plus real answers judged as deployed.
  4. Transfer the auditA short frozen prompt directs Codex / Claude Code to compare “what the output tells the model” vs. “what the code did” — on the authors’ own repo and two outside projects.

Deployed verifiers inherit the formatter’s blind spot almost completely.

  • Audit in the wild: on the authors’ own pre-fix snapshot, agents re-found both live defects plus 12 uncatalogued warped formatters (e.g. semantic_search silently dropping 2 of 5 results).
  • OpenClaw: attachments_fetch reports messages outside its bounded history as “not found” — fix merged (PR #131702).
  • Hermes: search_files truncates matched lines at 500 chars with no marker — PR #96632, still open.
  • Robustness & cost: strict document-level holdout keeps scope at 100% → 9%; grader–human blind regrade 35/36; total API spend $74.44.

03 Strengths

  • Names a previously invisible failure class and shows both agent-side and verifier-side damage with a genuinely causal paired design.
  • Venue-exceeding hygiene: hash-frozen stimuli, tuning/holdout split, cross-vendor consensus grading, human adjudication, deterministic construction checks.
  • Reports its own failure honestly — provenance stays at 94% overclaim; “estimate laundering” survives at 20%.
  • The four-disclosure checklist and frozen audit prompt are immediately usable, with a merged upstream fix as external proof.
  • At $74.44 total, this class of audit is cheap enough to be routine.

04 Limitations

  • All four families come from one system; a fifth (a truncated font warning) surfaced during typesetting.
  • Adversarially selected stress cases — no base rate for warped formatters in the wild; 8–20% residuals are not field rates.
  • The harness strips real capability: one tool output, one answer, no tool loops, no production system prompt.
  • Condition B mixes disclosure with handling instructions — disclosure’s own effect is unmeasured.
  • 90/90 flip built on author-written maximal false answers; the frequency measure is confounded (different wordings yield different answers).
  • Audit demo was authored with prior knowledge of the defects; Hermes PR unmerged at time of writing.

05 Questions for further exploration

  1. What is the base rate of warped formatters across popular agent frameworks — would a blind, author-unaware audit find the same defect density?
  2. Can the −62…−92 pp effect be decomposed into disclosure-only vs. instruction-only contributions with a third condition?
  3. Is provenance failure a formatting problem at all — or does it require typed tool schemas / cross-namespace 400s to fix?
  4. Does “estimate laundering” generalize to other uncertainty-disclosure styles (confidence intervals, derived-from fields)?
  5. Can multi-turn tool loops — re-query, paginate, read scans — recover omitted facts, and at what token and trust cost?
  6. Could verifier-side “fact injection + correctness framing” (the 0/92 cell) ship as a cheap post-hoc check until formatters are fixed?
