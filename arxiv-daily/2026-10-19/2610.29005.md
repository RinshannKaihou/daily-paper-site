> **一句话总结：** 该论文提出 VeriEvolve——一个"评估器优先"的自进化框架：先用 LLM 从任务指令与初始环境状态合成可执行的挑战状态和确定性评估器（作为适应度信号），再在其冻结信号下进化工具调用工作流，并在轮间用强/弱执行器的终态差异生成反事实测试对来修订评估器；在 MCPMark Filesystem 全部 30 个任务上构建出 30/30 个评估器（141 个挑战状态、自检 141/141 与外部验证器一致、留出状态 113/122 一致），评估器引导的进化把弱执行器 GLM-5.2 的外部验证成功率从 6/30 提升到 18/30（McNemar p<0.001），把 Claude 从 27/30 提到 30/30，且强弱状态差异修订修掉了全部 3 个评估器假阳性。

> **TL;DR:** VeriEvolve attacks the missing fitness function in self-improving tool agents: instead of evolving a workflow against an LLM judge, it first synthesizes deterministic, instruction-grounded executable evaluators (from generated challenge states), then evolves five-node MCP workflows under the frozen evaluator, and finally revises the evaluator from counterfactual strong-vs-weak end-state diffs. On the 30-task MCPMark Filesystem benchmark it builds 30/30 evaluators (141/141 agreement with the external verifier on their own suites, 113/122 on held-out agent-produced states), triples weak-executor GLM-5.2's externally verified success from 6/30 to 18/30 (p<0.001) versus its own round-0 seed, and lifts Claude Sonnet from 27/30 to 30/30; state-diff refinement repairs all 3 evaluator false positives. The honest caveat: the external MCPMark verifier still gates evaluator admission and false-positive selection, so this is feasibility under external calibration, not a verifier-free loop — and on PostgreSQL only 3/15 admitted tasks are solved by either executor.

## 核心贡献

- **指出并定义了自进化智能体的"评估瓶颈"**：现实有状态 CRUD 工具任务（文件系统、数据库、浏览器、笔记、GitHub）的正确性由最终环境状态决定（产物存在性、内容、层级、一致性、无副作用），LLM 语义裁判无法可靠验证这些状态不变量，而人工编写验证脚本每个任务需数小时专家时间（MCPMark 自述）——缺少可扩展的确定性可执行评估器是自进化的前置缺失层。
- **提出 VeriEvolve 三阶段框架**：Stage 1 由 Test-Suite Generator 从指令+初始状态合成正例/干净负例/对抗性近似错误挑战状态（由确定性适配器实例化），Verifier Evolver 构建沙箱化可执行评估器并通过内部门控后冻结；Stage 2 在冻结评估器作为平稳适应度信号下，进化五节点持久多备选工作流（任务理解/规划/ReAct 执行/产物检查/后处理，沿用 EvoLattice 表示）；Stage 3 比较强执行器接受态 F+ 与弱执行器假阳性态 F− 的可观察差异，转化为成对反事实测试用例，经累计回归验证后晋升修订版评估器。
- **严格的评估器隔离与晋升门控**：外部 MCPMark 验证器从不进入搜索回路、不参与工作流排序或评估器修复，只用于（事后）准入评估器（≥0.85 一致率）、挑选触发 Stage 3 的假阳性、以及测量结果；反事实对必须通过标签一致性门和覆盖门，评估器修订必须保留全部历史判定。
- **实证覆盖 MCPMark 五个环境**：Filesystem 为完全对照研究（Stage 1+2+3 全覆盖），PostgreSQL 21 任务全覆盖 Stage 1 + 15 对强弱匹配 Stage 2，Playwright/Notion/GitHub 作为跨环境压力测试暴露可观测性与状态表示的互补限制。

## Key Contributions

- **Identifies evaluator construction as the missing prerequisite for self-improving agents.** For stateful create-read-update-delete (CRUD) tool workflows, correctness lives in the final environment state (artifact existence, content, hierarchy, consistency, preservation, absence of side effects). LLM judges cannot establish that every state invariant holds; MCPMark reports several hours of expert effort per hand-written task verifier. The paper asks whether agents can synthesize this evaluation layer themselves.
- **VeriEvolve, an evaluator-first evolution framework with four model-backed roles** (Test-Suite Generator, Verifier Evolver, Workflow Evolver, Workflow Executor) wrapped in deterministic scaffolding. Stage 1 derives positive, clean-negative, and adversarial challenge states from the instruction and observable initial state; a category adapter materializes them and the Verifier Evolver writes a sandboxed `verify(context)` evaluator that is frozen after passing internal gates (positive acceptance ≥ 0.90, adversarial rejection ≥ 0.80).
- **Stationary-fitness workflow evolution.** During Stage 2 the evaluator is immutable; search mutates how the task is understood, planned, executed, inspected, and post-processed across five persistent multi-alternative nodes, so partial behaviors are retained and recombined rather than overwritten.
- **Execution-state refinement.** Stage 3 mines instruction-grounded differences between a high-confidence strong-executor state F+ and an internally accepted weak-executor state F−, converts each selected difference cluster into paired counterfactual cases (negative reproduces it, positive control removes only it), and promotes a revised evaluator only after cumulative regression: it must accept F+, reject every prior false-positive weak state, and preserve all earlier verdicts.
- **An unusually audited empirical protocol**: external-verifier information boundaries reported per phase (procedural for interactive Stage 1, technically packet-enforced for Stage 3), infrastructure failures separated from semantic failures, provenance classes for every Stage 3 trajectory, and paired exact McNemar tests with Wilson CIs on the seed-vs-evolved gains. Code, challenge states, frozen evaluators, and the 258 labeled agent-produced states are promised on publication.

## Methodology

A stateful tool-use task is a tuple (instruction x, initial state s0, read-only observation interface O); a workflow W executed with the task's tools yields a final state sW, and an evaluator E is a deterministic program mapping O(s) to a binary verdict plus partial fitness r(s) ∈ [0,1] and check-level evidence. VeriEvolve builds E from x, O(s0), and synthesized labeled challenge states — never from the benchmark's verifier.

**Stage 1 (evaluator construction).** The Test-Suite Generator (Claude, interactive Claude Code session) maps instruction + initial state to declarative challenge-case specifications; deterministic category adapters materialize each in an isolated copy of the task environment. The Verifier Evolver (same session) writes a sandboxed evaluator over the observation interface — for Filesystem, nine read-only operations (existence, globbing, listing, text/JSON/CSV reading, hashing, size), with imports, subprocesses, network, and writes prohibited. Candidates failing the construction gate get case-level failure feedback for repair.

**Stage 2 (workflow evolution under frozen evaluation).** The workflow has five nodes (task understanding, planning, ReAct execution, artifact inspection, post-processing), each holding a capped pool of prompt/behavior alternatives weighted by historical mean internal score; a candidate path picks one alternative per node. The frozen evaluator scores the final state and emits failed checks plus repair signals; artifact inspection summarizes behavior that may explain failures; the Workflow Evolver (stateless Claude Sonnet, one call per round) appends at most one new alternative per selected node. Internal convergence means the evaluator accepts the state.

**Stage 3 (outer evaluator refinement).** A deterministic adapter symmetrically removes environment artifacts from F+ and F−, the State-Diff module clusters observable differences (missing/extra artifacts, content mismatches, structural deviations), and only instruction-groundable clusters are eligible. Each becomes a paired counterfactual anchored on the immutable states, gated by label consistency and coverage. The Verifier Evolver proposes a localized patch; cumulative regression decides promotion; weak-executor search then reruns under the sharper criterion. Termination distinguishes reference match, convergence, evaluator stabilization on a repeated already-covered difference, or budget exhaustion.

**Roles and budgets.** All model-backed roles use Claude Sonnet (Stage 3 sessions resolve to claude-sonnet-5; the interactive Stage 1 model was not logged and is reported only as "Claude"); the weak executor is GLM-5.2 via the Z.ai full-precision API. Stage 2 defaults: five paths/round (three for the Filesystem Claude campaign), ≤15 workflow rounds, one-hour round timeouts in the GLM-5.2/PostgreSQL campaigns; Stage 3: ≤3 refinement rounds, 24-case budget, ≤3 repairs. The external MCPMark verifier is consulted only after internal artifacts are frozen — to admit evaluators (≥0.85 agreement), select Int✓/Ext× false-positive states for refinement, and confirm reference states F+.

## Results & Highlights

- **Evaluator construction (RQ1):** Across all 30 MCPMark Filesystem tasks, VeriEvolve constructs 30/30 evaluators with 141 challenge states (34 positive / 107 negative, 62 adversarial near-misses), achieving 141/141 agreement with the external MCPMark verifier on the generated suites. On 122 distinct held-out states later produced by the executor agents (states no evaluator saw during construction), agreement is 113/122 (92.6%; 95% CI 86.6–96.1), with precision 93.2%, recall 87.2%, and specificity 96.0% — errors in both directions (3 false positives, 6 false negatives on four tasks).
- **Workflow evolution (RQ2), weak executor:** Under GLM-5.2, evaluator-guided evolution triples externally verified success on Filesystem from 6/30 (round-0 seed) to 18/30 — 12 tasks gained, 0 lost, exact McNemar p < 0.001 — and raises internal convergence from 8/30 to 21/30; 13 tasks converge only after evolution. Internal precision of the evolved weak executor is 85.7% (18/21 internally accepted final states externally verified).
- **Workflow evolution, strong executor:** Claude improves from 27/30 to 30/30 external success (3 gained, p = 0.25 — not significant) and from 24/30 to 30/30 internal (p = 0.031), while recording roughly 58× fewer executor tokens than GLM-5.2 over the campaign (0.58M vs 33.18M; Claude counts exclude prompt-cache reads).
- **Evaluator refinement (RQ3):** The weak Filesystem campaign produces exactly 3 Int✓/Ext× false positives (uppercase, debugging, structure_mirror); strong–weak state differences yield regression-verified revisions that remove all 3/3. On structure_mirror, E(0) checked placeholders in only 5 of 8 empty leaf directories; the three-line E(1) patch adds the missing paths, and the weak executor then converges at round 3 on a state the external verifier also accepts (canonical tree hash 80aeae4e…, reproduced by an independent controlled run). The evaluator revision itself is cheap: Test-Suite Generator + Verifier Evolver calls used only 64K tokens (<1% of Stage 3's 8.10M), the rest being weak-executor re-search.
- **Cross-environment (PostgreSQL):** 18/21 evaluators constructed over 120 calibration states (115/120 external agreement); on the 15 admitted tasks both executors solve only the same 3 (Claude at round 0; GLM-5.2 after 11, 2, and 7 evolution rounds at 5.2×, 32.2×, and 12.8× the strong executor's tokens), and neither converges on the remaining 12/15 within budget (8 weak runs end at the one-hour round timeout) — a usable fitness signal is necessary but not sufficient. No PostgreSQL trajectory yields a false positive, so Stage 3 is never triggered there.
- **Ablations and diagnostics:** Removing context truncation flips weak-executor internal convergence from 7/18 completed tasks to 21/30; GLM-4.5 reaches only 7/30 external vs GLM-5.2's 18/30 under identical evaluators. A retrospective verifier-free refinement trigger (flag any strong–weak state difference) would catch all 3/3 false positives but flags 10/18 correct states, so only 3 of 13 flags are real. Cost: the weak Filesystem campaign spends 2.76M executor tokens and $2.60 of evolver cost per gained task; PostgreSQL matched pairs total ≈46.9M executor tokens.

## Authors & Credibility

The work is a collaboration between the University of Illinois Urbana-Champaign (Yueshen Li, Gokhan Tur, Dilek Hakkani-Tür — an established voice-recognition/dialogue group) and aiXplain (Kamer Ali Yuksel, João Pedro Maia); Yuksel is the author of EvoLattice, the persistent multi-alternative workflow representation that Stage 2 builds on. The paper's credibility rests less on venue (arXiv preprint, cs.SE cross-listed to cs.AI/cs.CL, Oct 2026) than on its audit discipline: a task-scope table separating primary, historical, and excluded runs; provenance classes for all 42 Stage 3 trajectories; per-phase verifier-isolation evidence (procedural boundary for interactive Stage 1 vs packet-scanned, tool-disabled, allowlisted calls for Stage 3 with zero boundary violations in primary runs); and independent reproduction evidence (the uppercase E(1) evaluator is byte-identical across three independent Verifier-Evolver searches; canonical weak-state tree hashes recur across runs). Exact Stage 1 prompts were not recorded and are reported as role contracts instead; the framework and artifacts are promised on publication, which at review time is still a promise.

## Critical Assessment

- **Novelty is real but incremental in framing.** Co-evolving evaluators with agents is an active line (Red Queen Gödel Machine, self-modifying Lean agents, Verification Horizon); VeriEvolve's distinctive move is evaluator-first for stateful tool-use with deterministic state-diff-driven counterfactual tests, rather than learned reward models or benchmark co-evolution. The state-diff-to-paired-counterfactual mechanism is genuinely elegant.
- **The loop is not closed, and the authors say so — but the title oversells slightly.** The external MCPMark verifier decides which evaluators enter Stage 2 (≥0.85 agreement), which states trigger Stage 3, and that every reference F+ is valid. The retrospective verifier-free trigger (executor disagreement) catches all 3 FPs while flagging 10 of 18 correct states (Table 22), and whether the instruction-grounding filter would dismiss those false alarms is explicitly untested. So "agents construct the fitness signals they require" remains a calibrated-feasibility result, exactly as the Limitations section concedes.
- **The headline 3× gain has a confound: no budget-matched search baseline.** Seed (round-0 best) vs evolved is the only comparison, run once per condition; part of the 6/30 → 18/30 gain may simply be repeated sampling (5 paths × up to 15 rounds) rather than evaluator guidance. The paper acknowledges this but does not run the control.
- **Self-testing bias in the RQ1 headline numbers.** The 141 challenge states and the evaluators they calibrate share one author (Claude, in one interactive session), so 141/141 agreement is partly by construction; the held-out 122 states are best-of-round states chosen by the evaluator's own ranking, hence "not independent samples." The 92.6% held-out agreement is the trustworthy number, and it is decent but not decisive.
- **Tiny denominators where it matters most.** RQ3 rests on exactly 3 false positives with one task-generic strategy, single runs, and two of three refined tasks (uppercase, debugging) still not solved by the weak executor after refinement — only structure_mirror flips to solved. The abstract's "refinement removes all three false positives" is accurate but the practical yield is 1 recovered task.
- **Cross-environment evidence is thin outside Filesystem/PostgreSQL.** Playwright contributes 2 valid pairs (one passing under a format-only oracle, 2 tasks excluded for missing ground truth); Notion's single historical pair sits below the admission threshold with agreement collapsing 0.75 → 0.50 after a serialization change; GitHub's historical zero scores turned out to be sandbox-timeout artifacts, excluded from claims. These read as honest diagnostics, not evidence the framework generalizes.
- **Reproducibility gaps**: the Stage 1 interactive model was never logged, exact Stage 1 prompts were not recorded, per-task Verifier-Evolver iteration counts are missing, and the Claude token counts exclude prompt-cache reads, making the 58× ratio "indicative rather than exact" — the paper flags all of this itself.

## Strengths

- Attacks the correct bottleneck: for stateful tool use, the evaluation layer — not the search operator — is the scarce resource, and synthesizing deterministic checkers from instructions is a more defensible fitness signal than LLM-as-judge.
- Deterministic gates around every LLM role (label-consistency and coverage gates on counterfactual pairs, cumulative regression before evaluator promotion, adversarial-rejection thresholds) make the pipeline's safety properties checkable rather than vibes-based.
- Exceptional experimental hygiene: McNemar tests and Wilson CIs on paired gains, infrastructure failures quarantined from semantic results, an explicit audited-scope table, per-phase information-boundary analysis, and a fully worked end-to-end example (structure_mirror, with the E(0) → E(1) patch shown as a three-line diff).
- Honest negative results: 12/15 PostgreSQL tasks unsolved by either executor, the Stage-3 cost profile (each revision re-triggers a full weak-executor search), and the failed verifier-free trigger are all reported with numbers.

## Limitations

- Dependence on an external verifier for evaluator admission, false-positive selection, and F+ confirmation; a verifier-free deployment is not demonstrated.
- Calibration on a finite generated suite does not guarantee coverage (the structure_mirror gap — 5 of 8 leaf placeholders checked — slipped through a 141/141-agreeing evaluator); challenge states and evaluators share the same author model.
- Each Filesystem condition was run once, with no budget-matched baseline, so gains conflate evaluator guidance with repeated sampling.
- Coverage is uneven: only Filesystem has complete Stage 1+2+3 evidence; PostgreSQL shows the search/execution ceiling (12/15 unsolved); Playwright/Notion/GitHub are small or incomplete; several tasks are blocked or caveated by observation-interface limits (unobservable success conditions, serialization changes, missing ground truth).
- F+ is a single valid execution, not a characterization of all acceptable solutions; an erroneous F+ (one Notion strong state was Int✓/Ext×) would have poisoned refinement — this failure mode is untested. Cost remains high (≈46.9M executor tokens for the PostgreSQL pairs; ~$2.60 and 2.76M tokens per gained Filesystem task).

## Relevance

高度契合"自进化智能体与自动化研究"方向：论文的核心问题正是自进化/自我改进智能体缺少可靠适应度信号这一前置瓶颈，其"先构造可执行评估器、再冻结评估器做工作流进化、再用执行状态差异修订评估器"的闭环，等价于自动化基准/奖励设计的可执行化路径，且给出了跨 MCP 环境的可靠性证据；对长周期自主智能体系统的可信评估亦有直接参考价值。

## Questions for Further Exploration

- Would a budget-matched random-restart or LLM-judge-guided baseline close part of the 6/30 → 18/30 gap, isolating how much the frozen evaluator actually contributes versus repeated sampling?
- Can the instruction-grounding filter plus regression gate be validated as a verifier-free Stage-3 trigger — do they dismiss the 10/18 harmless strong–weak differences the "any difference" rule flags, without over-tightening the evaluator?
- How does the framework behave when F+ itself is wrong (the untested erroneous-reference case), and could multiple strong-executor states or a per-cluster vote over candidate F+ states make refinement robust to it?
- Does evaluator synthesis transfer across observation interfaces — e.g., can a Filesystem evaluator's check families bootstrap construction for Notion or Playwright states whose serialization changes (the 0.75 → 0.50 agreement collapse) currently break the loop?
- Since Stage 3 cost is dominated by re-running weak-executor search under each revised evaluator, would cheaper surrogate re-scoring of archived states (rather than 15 fresh rounds) preserve regression guarantees at a fraction of the 8.1M tokens?
