C / Critical edge

No model-quality evaluation whatsoever — no perplexity, no long-context retrieval, no downstream accuracy; every number in the paper is bytes or tok/s.

The accuracy cost of FP4 / radial / double layouts is unknown. Solo author, no peer review, one model–machine–framework; prefill regresses below baseline (4,685 vs 5,979 tok/s).

01 / Methodology · distilled
  • One variable, everything fixed. LFM2.5-8B-A1B-OptiQ-4bit weights held constant on an M5 Max (32-core GPU, 36 GB unified memory); only the KV-cache path varies across five conditions.
  • Contexts 8,192 / 32,768 / 65,536 built from deterministic token IDs; decode throughput is a steady-state rate over a fixed 64-token window after warmup.
  • Fresh process per condition — no carried kernel graphs, allocator state, or cache objects. Cache-owned bytes are kept distinct from RSS; no throughput is imputed from failed runs.
  • End-to-end decode path includes each implementation's real cache ops (reconstruction, concatenation). No compressed-domain SDPA kernel exists yet, so results measure the cost of returning compressed KV to attention-compatible form.
  • Block-FP4 is a structural simulation (16-channel groups, E4M3-like scales, E2M1 symbols packed two-per-byte), not a reproduction of any proprietary kernel.

  • Ranking inverts at 32K: Fused Metal (1.48) falls behind Python Polar (1.83) — the 8K fusion win does not extrapolate once iterative-concatenation update overhead dominates.
  • Prefill regresses in the winning configuration: 4,685 vs 5,979 tok/s baseline, motivating a batched encode kernel.
  • DeepSeek-V4.1-Flash cross-check: FP4-only 3,473 B/token matches their ~3,460 ablation; the residual 4× gap to 890 B/token belongs to orthogonal axes (CED, CSA2, SWA), not another scalar codec.
03 / Strengths
  • Exceptional honesty discipline: slowdowns labeled as slowdowns, the failed 64K run reported as OOM with exact allocation sizes, measured vs unmeasured cleanly separated.
  • Clean isolation: model, weights, hardware, framework all fixed; only the cache path varies; fresh processes remove cross-condition contamination.
  • The non-additivity lesson is genuinely useful and correctly reconciled with DeepSeek: composition works across orthogonal redundancy axes, not by stacking codecs on the same elements.
  • Precise allocator forensics (33.5 GB temp vs 22.6 GB max buffer vs 36 GB physical) points straight to fixes: chunked pre-allocation, paged storage.
04 / Limitations
  • Zero quality results: perplexity, long-context retrieval, and downstream accuracy entirely unmeasured — the accuracy cost of every layout is unknown.
  • Single checkpoint, single device, single framework version; rankings may shift with head dims or GQA ratio; nothing transfers to CUDA without a matched kernel.
  • Stops before SDPA: cannot say whether radial KV is viable inside a real compressed-domain attention kernel — the one result that would change the conclusion.
  • Thin measurement & inconsistencies: 64-token decode window; Python Polar layouts differ across contexts (4,241 → 3,072 B/token); no code release; no batching or prefix-cache reuse.
05 / Questions for further exploration
  1. How much accuracy (perplexity, needle-in-haystack, downstream tasks) do radial and FP4 layouts cost at 3.4–4.2 KB/token — and does the QJL-style residual sketch close the gap?
  2. If a fused SDPA kernel consumed the packed polar layout directly, would the 32K collapse disappear, or only shrink the O(N²) constant?
  3. Would chunked pre-allocation let the Metal path complete at 64K — and what does throughput look like between 32K and 64K?
  4. Does the 8K fusion win survive other head dimensions and GQA ratios (Llama-3.2, Qwen2.5, Gemma-3), or is it an artifact of LFM2.5's MoE cache geometry?
  5. Can radial precision compose with CED-style cross-layer sharing without retraining, closing part of the 3,456 → 890 B/token gap?
  6. How do rankings change under batched serving and prefix-cache reuse, where a 3.6× smaller cache should matter more?
