> **一句话总结：** DualPace 将 AMX CPU 变成拥有独立调度权的 LLM 解码引擎：GPU 引擎负责 prefill 与 GPU 驻留解码，CPU 引擎独立推进宿主内存驻留的解码批次，并可通过 "GPU Dense Assist" 选择性借用 GPU 执行稠密算子；在 Azure Conversation 负载上，其可持续请求速率比 NEO 高 6.9–43.2%、比 vLLM 高 11.5–90.6%，同时在相同 P99 ITL 水平下比 NEO 多承载 7.3–50.5% 的请求。

> **TL;DR:** Existing CPU-offloading systems (e.g., NEO) are "GPU-gated": CPU-resident requests only advance when the GPU scheduler happens to expose an overlap window, causing bursty progress and inflated tail inter-token latency. DualPace decouples scheduling authority from execution placement — an independent AMX-enabled CPU engine batches and advances host-resident decodes on its own clock, optionally invoking the GPU for dense stages (post-attention FFN / LM head) via operator-level "Dense Assist" requests guided by offline-profiled batch-size thresholds. On the Azure LLM Inference Trace (Conversation workload) across Llama-3.1-8B/RTX 4090, Qwen3-14B/2×H20, and Qwen3-32B/4×H20, DualPace sustains 43.2%/6.9%/18.1% higher request rates than NEO at a 1 s/token normalized-latency target (and 90.6%/11.5%/23.8% higher than vLLM), while at a 1.5 s P99 ITL target it sustains 50.5%/15.2%/7.3% higher rates than NEO. Gains shrink on prefill-heavy Azure-Code, which the authors honestly characterize as the regime boundary.

## 核心贡献

- **识别并命名"GPU-gated CPU offloading"问题**：在 NEO 等现有异构流水线中，CPU 驻留请求只有当 GPU 调度器恰好产生足够长的可重叠窗口（满足 T_lin^0 ≥ T_ca^1 等约束）时才能推进，导致 CPU 侧进展呈突发-停滞交替，最终在 600 秒后完全平台化，抬高 P99 ITL。
- **双引擎解耦调度架构**：GPU 引擎独占 prefill 与 GPU 驻留解码，CPU 引擎（AMX 加速）拥有独立队列、调度时钟与 KV 管理器，自主对宿主内存 KV 组批推进；两引擎之间无全局迭代屏障。
- **调度解耦但执行协作（GPU Dense Assist）**：CPU 保留请求所有权，仅在算子级边界（post-attention / post-layer）把稠密阶段按两阈值策略 π_{P,F}(b) 委托给 GPU——Full-CPU、Split-Final（仅最后 post-layer 借 GPU）、Fused-Assist（每层都借 GPU）三档，兼顾 CPU 独立进展与 GPU 吞吐。
- **离线画像驱动的硬件适配**：通过代价模型 S_r(b) = T_r^CPU(b) + λ·D_r^GPU(b) 与 Algorithm 1 枚举拟合 (P, F) 阈值、GPU batched-token 上限与 CPU 解码批次上限，避免在线搜索进入服务关键路径。
- **跨调度器的宿主内存准入控制**：以 B_used + B_planned + B_growth + B_migration ≤ B_capacity 的四项 KV 义务（含 finish-peak 预留与迁移预留）协调两个调度器，防止宿主内存超卖与迁移震荡。

## Key Contributions

- Identifies and names **GPU-gated CPU offloading**: in NEO's asymmetric pipeline, CPU attention is admitted only when its predicted execution fits a GPU overlap window (the two inequality constraints in Eq. 1), so CPU-resident progress is bursty and eventually plateaus (Figure 1 shows NEO's CPU-resident token curve stalling after ~600 s while total throughput continues), inflating P99 ITL.
- **Dual-engine decoupled scheduling**: the GPU engine owns prefills and GPU-resident decodes; an AMX-enabled CPU engine owns CPU-resident decodes with its own queues, scheduling clock, and KV-cache manager — no shared iteration barrier, so host-resident requests decode independently of GPU admission opportunities.
- **Stage-boundary cooperative execution (GPU Dense Assist)**: the CPU engine keeps request ownership while selectively delegating KV-independent dense stages (post-attention projection/FFN, post-layer/LM head) to the GPU via operator-level assist requests that never enter GPU scheduler queues; a three-mode policy (Full-CPU / Split-Final / Fused-Assist) is selected by two batch-size thresholds.
- **Profile-guided hardware configuration**: an offline profiler measures CPU-visible route costs and GPU-main disturbance (Eq. 6–8), then fits (P, F) with a regret-tolerance tie-break minimizing assist calls; on RTX 4090 it selects (32, 16) within 0.070% of the exact optimum (32, 0).
- **Global KV safety across schedulers**: a four-term host-memory envelope (used + planned + finish-growth + migration reserve, Eq. 2) with finish-peak-footprint admission prevents overcommitment and residency oscillation while keeping backpressure local to each engine.

## Methodology

DualPace is a Python/PyTorch serving runtime (FastAPI/Uvicorn, DistServe-style async engine) whose LLMEngine coordinates two independently scheduled engines backed by Ray actors. All prefills execute on the GPU; the GPU scheduler decides each new request's post-prefill residency (Prefill-to-GPU vs. Prefill-to-CPU with layer-wise async KV copy to reserved host blocks). The CPU engine batches CPU-resident decodes over host PagedAttention (custom AVX512-BF16/OpenMP kernel) and oneDNN BF16 dense operators exploiting Intel AMX (LIA reports 20 TFLOPS BF16 on Sapphire Rapids, 4.5× AVX512 — enough that dense CPU decode is practical at serving batch sizes, though still ~1 order of magnitude behind an RTX 4090). For each CPU decode batch of size b, the routing policy π_{P,F}(b) picks Full-CPU (b ≤ F), Split-Final (F < b ≤ P, one final GPU assist for the post-layer), or Fused-Assist (b > P, GPU assist at every layer). Dense Assist follows a CPU-Ready → GPU-Running → GPU-Done handshake through shared-memory buffers; the GPU worker services ready assists at FIFO stage boundaries without preemption, adding only 2–5 µs of polling per layer. Offline profiling (W=5 warm-up, I=100 invocations, R=3 repeats) derives (P, F), a GPU batched-token limit (1,024 tokens), and a CPU decode batch limit (256 requests, the AMX throughput peak). Host admission uses the four-obligation envelope including finish-peak KV footprints and a migration reserve for GPU requests that may later be evicted.

Evaluation uses three configs: Llama-3.1-8B on 1× RTX 4090 + 12 Xeon Silver 4510 cores; Qwen3-14B on 2× H20 + 24 Xeon Platinum 8469C cores; Qwen3-32B on 4× H20 + 48 cores. Workloads are the first 2,000 requests of the Azure LLM Inference Trace Conversation (mean prompt 1,599 / output 114 tokens) and Code (mean prompt 2,348 / output 22) with fixed-seed exponential arrivals. Baselines are vLLM 0.22.1 (no host offloading, chunked prefill, prefix caching disabled to avoid synthetic cache hits) and NEO (with author-supplied protocol/Qwen3 patches preserving its original scheduler and policy). Sustainable request rate is interpolated at targets of 1 s/token normalized latency, 5 s P99 TTFT, 1.5 s P99 ITL.

## Results & Highlights

- **Sustainable request rate (Azure-Conv, 1 s/token normalized-latency target):** DualPace sustains **43.2% (Llama-3.1-8B/RTX 4090), 6.9% (Qwen3-14B/2×H20), and 18.1% (Qwen3-32B/4×H20) higher request rates than NEO**, and **90.6%, 11.5%, and 23.8% higher than vLLM**, respectively — the headline range of 6.9–43.2% vs NEO and 11.5–90.6% vs vLLM.
- **Tail ITL (Azure-Conv, 1.5 s P99 ITL target):** DualPace sustains **50.5% (Llama-3.1-8B), 15.2% (Qwen3-14B), and 7.3% (Qwen3-32B) higher request rates than NEO** while remaining close to NEO at the 5 s P99 TTFT target — i.e., it preserves CPU offloading's TTFT advantage over vLLM while eliminating NEO's scheduler-induced ITL stalls (vLLM itself keeps lower P99 ITL since its decodes stay GPU-resident).
- **P99 TPOT (Azure-Conv, 1.5 s target):** DualPace sustains **61%, 15%, and 3% higher request rates than NEO** across the three configs, corroborating the ITL result with a request-level cadence metric.
- **Sensitivity — CPU tensor parallelism:** on Llama-3.1-8B/RTX 4090, CPU TP=2 (two 12-core NUMA-pinned ranks) sustains **15.0% higher rate at the normalized-latency target, 14.3% at P99 TTFT, and 29.7% at P99 ITL** vs CPU TP=1 (31% higher at the 1 s P99 TPOT target), because the extra rank exposes more parallel AMX work and spreads KV reads across NUMA domains.
- **Sensitivity — host KV capacity:** 120 GiB sustains **28.7% and 18.5% higher request rates than 30 GiB and 60 GiB** at the normalized-latency target (28.3%/14.6% at the TTFT target), but results plateau from 120→240 GiB — CPU compute and memory bandwidth, not host KV capacity, become the bottleneck; smaller pools actually yield lower P99 ITL, framing host KV size as an admission-control knob.
- **Dense Assist overhead:** with no assist ready, boundary polling adds only **2–5 µs per layer (O(0.1 ms) per 32–64-layer batch)**; of the assist's measured component time, CUDA execution is 60.4% (Qwen3-32B) / 70.0% (Llama-3.1-8B), with the post-attention stage alone at 79.8%/79.2% of CUDA time — most device time is the dense compute assists exist to accelerate.
- **Workload boundary (Azure-Code):** with 2,348-token average prompts and 22-token outputs, the GPU-only vLLM is favored on the Qwen3/H20 configs; DualPace still beats NEO by converting more host compute into useful progress and achieves the lowest P99 ITL over most measured rates — independent CPU decoding pays off when GPU KV pressure coincides with sustained decode work or prefill contention, not on prefill-dominated traces.

## Critical Assessment

- **Novelty:** The core insight — separating *scheduling authority* from *execution placement* — is a genuinely sharp reframing of the CPU-offloading design space, and the operator-level (non-queue-jumping) Dense Assist is an elegant mechanism. That said, the building blocks (AMX dense kernels from LIA, host PagedAttention from FastDecode/NEO, chunked-prefill-style token budgeting) are largely assembled from prior art; the novelty is in the architecture, not the kernels.
- **Baseline fairness (main concern):** upstream NEO is Llama-only, so the authors **patched NEO themselves** with "protocol-compatibility and dense-Qwen support patches" for the Qwen3 experiments. They claim the original scheduler/pipeline/policy is preserved, but a self-ported baseline always risks under-optimization; comparisons against APEX, OmniServe, FastDecode, or LIA are absent entirely, so "state-of-the-art" rests on NEO alone.
- **vLLM configuration:** vLLM runs without host KV offloading and with prefix caching disabled (justified — the synthetic length-preserving prompts would create artificial hits — but it removes a real production advantage); the +90.6% headline is against this constrained configuration on a consumer RTX 4090 with maximal KV pressure, and shrinks to +11.5% on the better-provisioned 2×H20 setup — the abstract's range presentation is honest but the top number is the least representative case.
- **Rigor and scope:** evaluation covers three model/hardware configs and two production-derived traces with fixed-seed arrivals, plus clean ablations (CPU TP, KV capacity, assist-cost breakdown) and an explicit negative-result boundary on Azure-Code — better than typical systems papers. However, no repeated runs/error bars are reported, and the λ_GPU = 1 weighting in the routing score (Eq. 6) gets no sensitivity analysis. Only the first 2,000 requests per trace are replayed, and CPU allocations are confined to a single NUMA node "due to resource constraints."
- **Reproducibility:** the appendices specify profiling methodology precisely (W/I/R, calibration), but no code release is mentioned, and the system spans Ray actors, shared-memory control, custom AVX512/oneDNN kernels, and FlashInfer — an independent reimplementation would be a major undertaking.
- **Red flags:** minor — the phrase "maintaining the same level of latency" in the abstract means "at equal latency targets," not that DualPace matches vLLM's absolute P99 ITL (it does not; vLLM's decodes stay on the faster GPU, as the paper itself clarifies).

## Strengths

- Clean problem decomposition: the GPU-gated progress diagnosis (Eq. 1 overlap constraints → bursty stalls → P99 ITL) is well argued and directly measured in Figure 1 before any solution is proposed.
- The two-threshold routing policy with offline profile fitting sidesteps online configuration search and is fully specified (Algorithm 1, Appendix B), including a near-optimal tie-break that minimizes assist frequency.
- The cross-engine KV envelope (Eq. 2) with finish-peak and migration reserves is a principled answer to the double-buffering/oscillation problems that decoupled schedulers would otherwise create.
- Honest boundary characterization: the paper states where the approach does not help (prefill-heavy Azure-Code, well-provisioned GPUs) rather than hiding it.
- Comprehensive tail-latency reporting (P99 TTFT, ITL, and TPOT on both traces) beyond the usual normalized-latency curve.

## Limitations

- Decode-oriented bias: benefits concentrate on workloads with sustained decode (Azure-Conv, mean output 114 tokens); short-output, long-prompt serving sees little or no gain over GPU-only vLLM.
- Intrinsic CPU–GPU speed gap remains: P99 ITL of both CPU-offloading systems exceeds vLLM's at the same load; DualPace removes the *scheduler-induced* tail, not the execution-speed tail.
- CPU compute is the eventual ceiling — once host KV reaches ~120 GiB, AMX throughput and memory bandwidth saturate, and scaling requires more NUMA-local ranks (TP sensitivity only tested up to 2).
- Single-NUMA CPU allocations, 2,000-request trace prefixes, and no error bars / repetition statistics limit statistical confidence.
- No comparison against FastDecode/APEX/OmniServe/LIA, and no public code artifact at the time of writing.

## Questions for Further Exploration

- How would DualPace interact with quantized KV caches (e.g., INT8/FP8 offloaded state) — does the profiled (P, F) crossover shift when CPU attention bandwidth demand drops?
- Could the Dense Assist mechanism extend to *prefill* assistance for CPU-resident long-prompt batches, or does ownership transfer at prefill time fundamentally conflict with the admission-control envelope?
- What is the tail-latency behavior under request preemption, cancellation bursts, or adversarial arrival patterns not captured by exponential inter-arrivals?
- Does the migration-reserve accounting (B_migration) become overly conservative at high eviction rates, effectively stranding host capacity, and could a probabilistic estimate improve utilization?
- How much of the NEO gap is attributable to the authors' own Qwen3 port of NEO rather than to GPU gating per se — a head-to-head against a natively supported offloading system (e.g., APEX or OmniServe) would isolate the architectural contribution.
