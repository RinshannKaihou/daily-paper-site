> **一句话总结：** 作者在 192GB 内存的 Mac Studio（M2 Ultra, macOS 27.0）上系统性地扫描发现：当 torch.bmm 的输出或输入超过 2^32 个元素时，PyTorch 的 Apple MPS 后端会**无任何报错地返回错误结果**（相对误差可达 1.7–2.2，等于忽略转置操作数的 stride、或扁平索引在 2^32 处回绕的计算），该行为贯穿 PyTorch 2.4.1–2.14.0 全部 11 个版本；在 TweetEval 情感分类真实负载中，单个超大 batch 使 33.4% 的输出损坏、预测坍缩到单一类别、整体准确率从 0.713 跌至 0.639，作者并发布了一个阻止任何 ≥2^32 元素 MPS 张量操作的防护 Guard。

> **TL;DR:** A black-box differential sweep (1,584 runs on PyTorch 2.14.0, plus 10 earlier releases) shows that PyTorch's Apple MPS backend silently returns wrong results — relative errors of 1.4–2.2, no error, warning, NaN or Inf — for torch.bmm (hence torch.matmul and eager attention) whenever the output exceeds 2^32 elements with a transposed operand (entire output wrong, strides ignored) or a contiguous input exceeds 2^32 elements (batches beyond 2^32 wrong, index wraps at 2^32), on every release from 2.4.1 to 2.14.0 on macOS 27.0. In a real workload (cardiffnlp/twitter-roberta-base-sentiment-latest, eager attention, first 2,048 TweetEval sentiment tweets at L=512), one oversized batch (B=2048) corrupts 33.4% of texts, changes 18.9% of predictions, collapses corrupted outputs onto the neutral class, and drops accuracy from 0.713 (chunked reference, bit-for-bit verified against CPU) to 0.639, while negative-class recall falls 0.788→0.529 overall and to 0.010 on corrupted texts. The same 48 configurations are all correct on an A100 CUDA control (max rel. error 9.2e-7 fp32), and a released TorchDispatchMode guard that blocks any MPS tensor with ≥2^32 elements stops all 481 silent failures across 5,240 recorded runs at ~1.00x overhead on large attention forwards.

## 核心贡献

- **边界定向差分扫描**：在单台 Mac Studio（M2 Ultra、192GB 统一内存、macOS 27.0）上对 MPS 后端的 torch.bmm 做系统性扫描——2 种 dtype（fp32/fp16）、4 种内存布局（连续、b 转置、a 转置、带 storage offset 的切片）、6 种形状、4096–65538 之间的 42 个 batch size，共 1584 次运行（PyTorch 2.14.0），并对 2.4.1–2.13.0 十个旧版本做缩减扫描；所有结果与 CPU 上的 float64 参考计算对比。
- **三条规则完整解释全部结果**（2.14.0，按优先级应用）：① 输出 >2^32 元素且某操作数为转置视图 → 整个输出静默错误（等于忽略该操作数 stride 的计算）；② 视图操作数 ≥2^31 元素 → 抛出异常；③ 连续输入 >2^32 元素 → 仅 2^32 之后的部分 batch 错误（等于扁平索引在 2^32 处回绕）。规则的顺序至关重要——更大的问题反而可能把显式报错变成静默失败。
- **索引编码输入技术**：将操作数元素编码为 batch 索引或矩阵位置的码字，从错误的输出中逐元素反解出后端实际读取了哪个输入（观测到 δ=−65536 个 batch 的精确回绕偏移），从外部黑盒地证实了两种错误机制。
- **真实负载案例研究**：Hugging Face 的 RoBERTa 情感分类器（eager attention），单个超 2^32 边界的 batch 静默腐蚀三分之一的输出、预测坍缩到单一类别，而分块执行完全正确（蜕变关系参考）。
- **可落地的防护**：发布了一个 TorchDispatchMode Guard，禁止任何创建或读取 ≥2^32 元素 MPS 张量的操作，并给出开销评估；同时发布了扫描 harness 与全部原始结果（含 SHA-256 校验的 manifest）。
- **跨后端对照与回归发现**：CUDA（A100）上全部 48 个 bmm 配置正确，证明失败是 MPS 特有的；但 torch.arange 在 CUDA 上同样存在 >2^32 元素静默截断，且 PyTorch 2.14.0 在 MPS 上引入了 arange 从"报错"退化为"静默截断"的回归。

## Key Contributions

- A boundary-targeted differential sweep of `torch.bmm` on the MPS backend on one machine (Mac Studio, M2 Ultra, 192 GB unified memory, macOS 27.0): 2 dtypes (fp32/fp16), 4 memory layouts (contiguous, either operand transposed, sliced with a storage offset), 6 shapes, 42 batch sizes between 4096 and 65538 — 1,584 runs on PyTorch 2.14.0 plus a reduced sweep over ten earlier releases (2.4.1–2.13.0), every result judged against a float64 CPU reference.
- Three rules, applied in order, that reproduce all 1,088 random-input outcomes on 2.14.0: (1) output > 2^32 elements with a transposed operand → the entire output is silently wrong and equals a computation that ignores that operand's strides; (2) a view operand with ≥ 2^31 elements → raises an exception; (3) a contiguous input > 2^32 elements → only the batches beyond element 2^32 are wrong, matching a flat index that wraps around at 2^32. Rule order matters: a slightly larger problem can convert an explicit error into a silent failure.
- Index-encoded inputs (elements carrying codes of their batch index or matrix position) that let the authors decode, element by element and purely from outside the black box, which input data the backend actually read — confirming a shift of exactly δ = −65536 batches (−2^32 elements) under rule 3 and a stride-ignoring row/column transposition under rule 1.
- A real-workload case study: a public sentiment classifier (RoBERTa-base, eager attention) where a single oversized batch corrupts a third of the outputs with no error, the corrupted predictions collapse onto one class, and chunked execution of the same inputs is bit-for-bit correct (metamorphic reference).
- A drop-in guard (TorchDispatchMode) that raises on any MPS operation creating or reading a tensor with ≥ 2^32 elements, evaluated against all 5,240 recorded sweep runs and measured for overhead; sweep harness, raw results and guard are released at github.com/jniimi/mps-silent-failures.
- Cross-backend controls: all 48 bmm configurations are correct on an NVIDIA A100 (CUDA, TF32 off), isolating the fault to MPS — yet `torch.arange` is silently wrong above 2^32 elements on CUDA too, and PyTorch 2.14.0 introduces an MPS regression where arange stops raising and silently truncates.

## Methodology

The study is deliberately black-box: it reports what the MPS backend returns versus reference results, never claiming a root cause inside Metal/MPSGraph source code. The unit under test is `torch.bmm` because `torch.matmul` folds leading dimensions into batch form and calls bmm, and Hugging Face "eager" attention computes both QK^T and softmax(QK^T)V through matmul — so the boundary findings propagate to the most common attention code path (fused SDPA and `nn.Linear`/addmm follow different paths and are covered separately).

**Sweep design.** Each series crosses one candidate boundary — 2^31 elements (B0=32768), 2^32 elements (B0=65536), or 2^32 bytes (B0=16384 in fp32) — chosen as hypotheses about 32-bit signed/unsigned integer indexing. Each series runs five consecutive batch sizes around each candidate, a small baseline (B=4096), and an evenly spaced grid between (37 batch sizes per fp32 series), with bisection available if two neighboring grid points disagreed (it never did). The crossing tensor has 2^16 elements per batch; additional shapes redistribute the same element counts across (M, K, N) to show the trigger is element count, not a particular dimension. Logical input values are generated on CPU from fixed per-batch seeds independently of layout, so all four layouts compute the same product and are directly comparable.

**Reference and error metric.** The reference is regenerated in float64 on CPU (never read back from the device, so a transfer fault cannot cancel out); the device output is copied back in chunks, compared, and discarded. A batch is "wrong" when its max-norm relative error exceeds a tolerance τd = max(10·êd, floor), calibrated far below any boundary (τfp32 = 1.2e-5, τfp16 = 4.2e-3). Comparisons are either full (all batches, 3 seeds at switch points) or sampled (~270–290 batches including positions where flat indices cross multiples of candidates). Each run executes in a fresh process; outcomes are classified as ok / error / crash / timeout / wrong / truncated (zeros) / input-corrupt, and each run logs one JSON line plus a manifest with OS build, hardware, versions, tolerances, and script hashes.

**Mechanism identification.** For wrong runs, four misreading hypotheses (strides ignored, index wraps at 2^32, both, storage offset ignored) are recomputed on CPU and scored by the fraction of wrong elements each reproduces. Index-encoded inputs then confirm the mechanism without any hypothesis: one operand's elements hold codes c(f) = (f mod P) + 1 of the batch index or matrix position, the other operand is a selection matrix, so each correct output element equals exactly one code; a wrong element's decoded field directly reveals what was read (shift δ = f′ − f mod P).

**Case study design.** cardiffnlp/twitter-roberta-base-sentiment-latest (12 heads), fp32, `torch.inference_mode()`, attn_implementation="eager", first 2,048 tweets of the TweetEval sentiment test split, padded to L=512, PyTorch 2.14.0 / Transformers 5.17.0. The reference is chunked execution (chunks of 256, scores of 8.1e8 elements) under the metamorphic relation f(concat(X)) = concat(f(X)) for inference; the reference was itself validated against CPU fp32 on 1,000 texts (largest relative logit difference 6e-5, no prediction change).

## Results & Highlights

- **Sweep outcome (PyTorch 2.14.0, 1,584 runs):** 1,273 correct, 214 raise an error, 97 silently wrong; zero crashes, zero timeouts, zero non-finite values. The silent-failure switch is exactly between B=65,536 and B=65,537 — correct at exactly 2^32 elements, wrong one batch later — and fp16 switches at the same batch size as fp32, so the limit is element count, not bytes. Nothing changes at the 2^32-byte candidate.
- **Error magnitudes and mechanisms:** rule-1 failures (transposed operand, output > 2^32) corrupt all 65,537 batches including batch 0 with relative error 1.7–2.2, exactly matching a computation that ignores the transposed operand's strides; rule-3 failures (contiguous input > 2^32) corrupt only batches beyond element 2^32 with relative error 1.4–1.7, exactly matching a flat index wrapping at 2^32 (index-encoded inputs show δ = −65536 batches for every wrong element; in fp16, δ = −288 ≡ −65536 mod 2039).
- **Case study (TweetEval sentiment, eager attention, L=512):** at B=1365 (just below 2^32 score elements) the single forward pass matches the chunked reference bit-for-bit (accuracy 0.708); at B=1366 exactly one text (the last) is corrupted with max relative error 0.78; at B=2048 (1.5×2^32), 683 of 2,048 texts (33.4%) are corrupted, 386 predictions (18.9%) change, max relative error 5.16, and accuracy drops from 0.713 (reference) to 0.639 — overall accuracy falls only 7.4 points while recall on the 683 corrupted texts collapses to 0.010 (negative) and 0.054 (positive), with 661 of 683 corrupted texts predicted as neutral (McNemar p = 4.1e-15). Every text before position 1365 still matches bit-for-bit; cyclically shifting the batch by 1024 keeps corrupted positions at 1365–2047, proving corruption depends on position in the batch, not content. Corruption begins exactly at (text 1365, head 4) in the softmax(QK^T)V product, matching rule 3 at the layer level.
- **SDPA vs eager and version regressions:** fused SDPA on the same B=2048 batch is correct (1.9e-5) on 2.13.0/2.14.0 but silently wrong up to 2.12.1; eager attention is silently wrong from 2.5.1 onward (and crashes on 2.13.0). On 2.14.0, `torch.arange` with N = 2^32 + 2^20 elements writes only the first N mod 2^32 elements silently, where 2.12.1/2.13.0 raised.
- **CUDA control (A100 80GB, TF32 off, PyTorch 2.11.0):** all 48 bmm configurations (both shapes sides, B ∈ {65520, 65552, 68544}, fp32/fp16, 4 layouts) are correct with largest relative error 9.2e-7 (fp32) / 4.5e-4 (fp16) versus same-GPU float64 — the bmm failures are MPS-specific, not inherent to the shapes.
- **Guard evaluation:** the inclusive rule "no MPS tensor with ≥ 2^32 elements" stops all 481 silent runs (wrong values or zeros) across all 5,240 recorded runs over 11 versions, with no run below 2^32 ever silently wrong; the price is stopping 630 of 4,083 correct runs (~15%). Overhead is 1.73x on a small 2-layer training loop (2000 steps, 1024×120 inputs) and 1.00x on large attention forwards (batch 64, 32 heads, length 1024, fp16) — negligible exactly in the regime where the guard matters.

## Authors & Credibility

The report is single-authored by Junichiro Niimi of Meijo University (jniimi@meijo-u.ac.jp), who also opened the underlying PyTorch GitHub issue #197636 on 2026-09-19 (the same day as the arXiv submission) — so the finding is publicly filed against the framework, not just claimed in a report. The work is explicitly framed as a technical report on observable behavior rather than a methods paper, which matches its content. Credibility signals are strong: exact environment disclosure (Mac Studio Mac14,14, M2 Ultra 24-core CPU / 76-core GPU, 192 GB, macOS 27.0 build 26A428, firmware, Python 3.12.12, eleven PyTorch versions installed via uv in fresh per-version environments), per-run JSON logs plus SHA-256-hashed scripts and a manifest, regenerated float64 references never read back from the device, three-seed full comparisons at switch points, fresh-process isolation per run, and a clearly labeled limitations section. Code, raw results, and the guard are released (github.com/jniimi/mps-silent-failures). The main credibility caveat is that all MPS measurements come from one machine and one macOS version, and the CUDA control covers only the first-pass configurations on one PyTorch version.

## Critical Assessment

- **Novelty:** High within its niche. Framework-bug and differential-testing literature (CRADLE, FreeFuzz, NNSmith, TitanFuzz) aims at breadth over cheap API calls; as the author correctly notes, none targets element-count boundaries (a single 2^32-element fp32 tensor is 17 GB, too expensive for fuzzers) and none uses MPS as the system under test. The index-encoding trick that recovers the misread source element-by-element from outside a black box is a genuinely elegant piece of experimental design.
- **Rigor:** Strong for a measurement study — pre-registered candidate boundaries derived from integer-width reasoning, exact switch points (no bisection ever needed), mechanism hypotheses tested by exact CPU recomputation and then confirmed hypothesis-free by index encoding, a metamorphic reference cross-checked against CPU on 1,000 texts including boundary and low-margin cases, and a McNemar test for the prediction flips. The after-the-fact nature of the three rules is honestly flagged: they were fitted to a finite configuration set (1,088 random-input runs), and the author explicitly states no swept configuration has both output and input above 2^32 simultaneously (a memory constraint), leaving the rules' interaction at larger scales untested.
- **Reproducibility:** Very good on software axes (released harness, raw per-run JSON, hashed scripts, per-version uv environments, fixed seeds, 11 PyTorch releases) but weak on hardware axes: every MPS number comes from one M2 Ultra machine on macOS 27.0 only. macOS 14/15/26 were never run; the claim that the silent behavior "begins with macOS 15" rests on a pre-2.14 error message text, not on measurement — a notable evidentiary gap the author admits. Other Apple chips (M1/M3/M4, different memory sizes) are untested.
- **Significance:** Practically important for the growing population running large-batch or long-context inference on ≥192 GB Apple Silicon machines — the affected scale (attention scores at 32 heads / 4096 tokens / batch 9, or batch 1,366 at L=512 with 12 heads) is ordinary, and the failure is silent, deterministic, and position-dependent, the worst combination for debugging. The observation that aggregate accuracy hides the damage (−7.4 points overall versus recall ≈ 0.01–0.05 on corrupted texts) generalizes uncomfortably to any evaluation run on MPS.
- **Red flags / weaknesses:** (1) single-machine, single-OS external validity; (2) the guard is evaluated against the very sweep outcomes that motivated it — a circularity the author acknowledges — and its conservative threshold discards ~15% of correct runs (630/4,083); (3) coverage gaps: systematic sweep is bmm-only (other operators get one shape each in the first-pass suite), bf16 is absent, only forward passes are tested so no statement about gradients/training, and sweep batch sizes stop just above 2^32 (only the case study reaches 1.5×); (4) black-box by design — no root-cause in MPSGraph/Metal source, so the 32-bit-index explanation remains inference from behavior, however compelling the δ = −65536 wrap evidence is; (5) the case-study collapse onto the neutral class is a single-model, single-dataset observation and could look very different (or be invisible) on a dataset dominated by the collapse class, as the author notes.

## Strengths

- Converts a single GitHub issue into a systematic, fully reproducible measurement study with exact switch points and a complete rule-based account of 1,584 runs.
- The index-encoded input technique is a clever, assumption-free way to prove *what* the backend actually computed, not merely that it is wrong.
- The real-workload case study is carefully designed: metamorphic reference validated against CPU, boundary-adjacent batch sizes (1365/1366/2048), cyclic-shift control separating position from content, layer-level localization to (text 1365, head 4), and fused-SDPA comparison isolating the eager-attention path.
- Honest, specific limitations section (single machine, bmm-only sweep, post-hoc rules, no training claims) and a practical mitigation with measured overhead rather than vague advice.
- Cross-backend control on CUDA that both isolates the bmm fault to MPS and reveals a parallel arange silent truncation on CUDA — a genuinely useful warning that a second GPU backend is not a safe oracle at this scale.

## Limitations

- All MPS results come from one Mac Studio (M2 Ultra, 192 GB) on macOS 27.0; macOS 14/15/26 and other chips/memory sizes are untested, and the macOS-version dependency is inferred from an error message rather than measured.
- The systematic sweep covers bmm only; attention, convolution, elementwise, reduction and indexing operations appear only in the 26-case first-pass suite with one fixed shape each, so for those the failure threshold is unknown.
- Dtypes are limited to fp32 and fp16 (no bf16); batch sizes stop just above 2^32 in the sweep (only the case study reaches 1.5×2^32); memory constraints prevented any configuration with output and input both above 2^32.
- Only forward computation is tested for bmm — no claims about gradients or training; the earlier-version sweep uses a coarser grid, one seed, and base shapes only.
- The three outcome rules were fitted after the fact and may not generalize beyond the swept configurations; the guard was validated on the same operations that motivated it and stops ~15% of correct runs; chunking must happen before the device (slicing chunks out of an already-oversized device tensor creates large-offset views the sweep does not cover).
- The case study uses one model, one dataset and one input length; the single-class collapse may not generalize.

## Relevance

对在大内存 Apple Silicon 上做大 batch / 长上下文 LLM 推理与评测的工作是直接相关的工程警示：任何经 torch.matmul / eager attention 且张量超过 2^32 元素的 MPS 负载都会静默产出错误结果，且整体指标（accuracy）几乎不露痕迹、只有分类别指标才暴露。对关注数值正确性、可复现性与系统可信 ML 的研究而言，这也是一个罕见的"边界定向差分测试 + 索引编码归因"方法论范例。

## Questions for Further Exploration

- Does the same 2^32-element boundary break bmm/attention on other Apple chips (M1/M3/M4 Ultra, M4 Max) and on macOS 15/26, or is it specific to the M2 Ultra + macOS 27.0 combination measured here?
- What is the actual root cause inside MPSGraph / Metal shaders — a 32-bit unsigned flat index in the compute-kernel address math — and does the same code path explain the CUDA `torch.arange` truncation?
- Do gradients and training break at the same boundary (backward passes through bmm), and could training-time silent corruption explain otherwise unexplained loss anomalies on MPS?
- Where do the thresholds sit for operations outside bmm (convolution, reductions, indexing) and for bf16 — and is there a cheap static checker that could flag oversized tensors at model-trace time instead of at dispatch time?
- Would the single-class collapse generalize: does the corrupted-output distribution always concentrate (e.g., because wrapped garbage logits saturate the softmax toward a majority attractor), and can evaluation pipelines add a chunked-vs-whole consistency check to catch such failures generically?
