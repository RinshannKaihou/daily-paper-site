Why this matters

Any MPS workload using matmul / eager attention over >232-element tensors silently produces wrong results; aggregate accuracy barely moves — only per-class metrics reveal it.

Critical edge

Every MPS number comes from a single M2 Ultra machine on macOS 27.0 — other Apple chips and OS versions were never measured, and the macOS-version dependency is inferred from an error message, not measurement.

— Reproducibility · Limitations

§1 Methodology — how they caught it

Deliberately black-box. The study reports what MPS returns versus reference results — it never claims a root cause inside Metal/MPSGraph. The unit under test is torch.bmm, because torch.matmul folds into bmm and Hugging Face eager attention computes both QKT and softmax(QKT)V through matmul — so findings propagate to the most common attention path.

Boundary-targeted sweep. Candidate boundaries — 231 elements, 232 elements, 232 bytes — chosen from 32-bit index reasoning. Each series runs batch sizes hugging the candidate: 2 dtypes × 4 memory layouts (contiguous, either operand transposed, sliced with storage offset) × 6 shapes × 42 batch sizes = 1,584 runs on 2.14.0, plus a reduced sweep over 2.4.1–2.13.0. Inputs are seeded on CPU so all four layouts compute the same product.

Reference & metric. float64 reference regenerated on CPU (never read back from the device, so a transfer fault can't cancel out), tolerance calibrated far below any boundary (τfp32=1.2e-5). Fresh process per run; per-run JSON logs plus a SHA-256 manifest.

Index-encoded inputs. Operand elements carry codes of their batch index / matrix position, so each wrong output element decodes — purely from outside the black box — to what the backend actually read: an exact shift of δ = −65,536 batches under rule 3, a stride-ignoring transposition under rule 1.

Case study. cardiffnlp/twitter-roberta-base-sentiment-latest, eager attention, first 2,048 TweetEval tweets at L=512. Reference is chunked execution under the metamorphic relation f(concat(X)) = concat(f(X)), itself validated against CPU fp32 on 1,000 texts.

Three rules explain all 1,088 random-input outcomes (applied in order)
  1. Output > 232 elements with a transposed operand → the entire output is silently wrong; equals a computation ignoring that operand's strides. rel err 1.7–2.2
  2. A view operand ≥ 231 elements → raises an exception (the "honest" failure).
  3. Contiguous input > 232 elements → only batches beyond element 232 are wrong; flat index wraps at 232 (decoded δ = −65,536 batches). rel err 1.4–1.7
Rule order matters: a slightly larger problem can convert an explicit error into a silent failure.

Cross-backend & versions

All 48 bmm configurations correct on an A100 CUDA control (max rel err 9.2e-7 fp32) — the fault is MPS-specific. But fused SDPA is silently wrong up to 2.12.1, eager attention silently wrong from 2.5.1 onward, and 2.14.0 regresses torch.arange on MPS from raising to silently truncating — which is also silently wrong above 232 elements on CUDA.

§3 Strengths

  • Converts a single GitHub issue into a systematic, fully reproducible measurement study — exact switch points (no bisection ever needed) and a complete rule-based account of 1,584 runs.
  • Index-encoded inputs prove what the backend computed, not merely that it is wrong — an elegant, assumption-free attribution.
  • Carefully designed case study: metamorphic reference validated against CPU, boundary-adjacent batches (1365/1366/2048), cyclic-shift control separating position from content, layer-level localization to (text 1365, head 4).
  • Honest, specific limitations section, plus a practical mitigation with measured overhead rather than vague advice.
  • CUDA control both isolates the bmm fault to MPS and exposes a parallel arange truncation on CUDA — a second GPU backend is not a safe oracle at this scale.

§4 Limitations

  • Single machine (M2 Ultra, 192 GB) on macOS 27.0 only — macOS 14/15/26 and M1/M3/M4 never run; the macOS dependency is inferred from an error message, not measured.
  • Systematic sweep covers bmm only; attention, convolution, elementwise, reduction and indexing appear with one fixed shape each — thresholds there are unknown.
  • fp32/fp16 only (no bf16); sweep batch sizes stop just above 232; memory constraints prevented any config with output and input both above 232.
  • Forward computation only — no claims about gradients or training.
  • The three rules were fitted after the fact; the guard was validated on the same runs that motivated it (circularity) and stops ~15% of correct runs. Chunking must happen before the device.
  • Case study is one model, one dataset, one input length — the single-class collapse may not generalize.

§5 Questions for further exploration

  • Does the same 232-element boundary break bmm/attention on other Apple chips (M1/M3/M4 Ultra, M4 Max) and on macOS 15/26 — or is it specific to M2 Ultra + macOS 27.0?
  • What is the actual root cause inside MPSGraph / Metal shaders — a 32-bit unsigned flat index — and does the same path explain the CUDA arange truncation?
  • Do gradients and training break at the same boundary, and could training-time silent corruption explain unexplained loss anomalies on MPS?
  • Where are the thresholds for ops outside bmm and for bf16 — and is there a cheap static checker flagging oversized tensors at trace time?
  • Does the corrupted-output distribution always concentrate on one class, and can pipelines add a chunked-vs-whole consistency check to catch such failures generically?
