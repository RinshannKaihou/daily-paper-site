> **一句话总结：** 单作者技术报告，记录如何在 AMD MI250（gfx90a/CDNA2）上让 DeepSeek-V4-Flash（284B 总参 / ~13B 激活、FP4 专家 + FP8 稠密）通过 SGLang 正确运行：先修复 W2 输出排列等致命数值 bug，再经自定义 HIP/CK/Triton 内核优化，在 8-GCD TP8 实例上把原生自回归解码做到 C1 88.63 tok/s、C64 1327.10 tok/s，8K 输入预填充约 10.4K tok/s。

> **TL;DR:** A single-author systems report that enables DeepSeek-V4-Flash (284B total / ~13B active params, FP4 routed experts, FP8 dense weights) inference on AMD MI250 (gfx90a/CDNA2) via SGLang, first recovering correctness — the initially "fast" ~60 tok/s AIter FP4 route was numerically wrong due to a routed-expert W2 output permutation (stage-2 cosine similarity ~0.24 vs oracle), fixed by applying an inverse 16-row block permutation [0,4,1,5,2,6,3,7] at weight load time — then optimizing decode with packed FP4 weights, INT8 activation quantization, CDNA2 v_dot4 instructions, and peer-read all-reduce (25.54 → 60.20 tok/s in the historical TP4 series). The current single TP8/EP1 eight-GCD instance with a 1M-token KV pool reaches 88.63 resident output tok/s at C1 and 1327.10 at C64 on a 64-case public-source code-request corpus (512-token inputs), versus its own broken ~14–20 tok/s TP4 starting points; C16 prefill sustains 10413.87 / 10263.02 / 9966.84 input tok/s at ~8K/16K/32K input lengths. Evidence hygiene is unusually strict, but validation is bounded (a "capital of France" oracle), baselines are all the author's own earlier configurations, and million-token-context occupancy is untested.

## 核心贡献

- **gfx90a 使能（enablement）**：在最初只支持 gfx942/gfx950 的 ROCm 栈上启用 MI250（gfx90a/CDNA2）运行 DeepSeek-V4-Flash，包括添加 gfx90a 构建目标、选择 HIP_FP8_TYPE_FNUZ、修复 ROCm 7.14 的 include/library/rpath 发现、AOT HIP 内核、AIter FP4 CK MoE、无 RDMA 网卡节点上的 Mori 拓扑与 XGMI 初始化，以及 CUDA graph 捕获/重放验证。
- **正确性恢复（最重要的贡献）**：识别并修复了一组致命数值 bug——最有代表性的是 CKTile FP4 专家 **W2 输出排列错误**（128 宽 N tile 内 16 行块映射 fast→reference = [0,2,4,6,1,3,5,7]，stage-2 余弦相似度仅 ~0.24），通过加载时应用逆排列修复且零解码热路径开销；还包括 E8M0 尺度布局、TP 注意力 sink 映射、mHC FP32 系数保留、确定性索引选择、C4 生命周期回调等修复。建立固定 token / 哈希正确性检查（France oracle）后才继续优化。
- **解码优化组合**（历史 TP4 路线）：打包 FP4 权重（无离线展开）、在线 BF16→INT8 激活量化（每 32 元素）、E2M1 nibble 查表、CDNA2 `v_dot4_i32_i8` 混合点积、AIter peer-read 自定义 all-replace 取代高固定延迟的 RCCL、TP-only mHC 启动几何。
- **预填充优化组合**：CDNA2 MFMA 路由内核、打包 FP4 解包复用（group8→group32）、`v_perm_b32` 查表、稀疏分页注意力从 8 wave 降到 1 wave、chunk 从 512/1024 增至 2048、专家排序块从 32 行增至 64 行（M2048 gate/up 7.26→5.55 ms，-23.6%）。
- **当前 TP8 原生 AR 矩阵**：单实例 TP8/EP1、1,048,576 逻辑 KV 池，C1–C64 七档、每格三轮取中位数；预填充接受配置组合了空 tile 消除、mHC 复用、paired-GCD 注意力、固定顺序 Top-6 FP32 专家归约。
- **严格的证据方法论**：显式区分原生 AR / 历史 ABBA 消融 / DSpark 投机解码 / 居住（resident）吞吐与整请求 HTTP 延迟；A1→B1→B2→A2 对照顺序、独立启动的对照进程、保留全部离群值；278 个经校验文件的正式证据归档。

## Key Contributions

- **gfx90a enablement**: ports the DeepSeek-V4 execution path to AMD MI250 (gfx90a/CDNA2), which the original ROCm implementation (targeting gfx942/gfx950) did not support — adding the gfx90a build target, selecting `HIP_FP8_TYPE_FNUZ`, repairing ROCm 7.14 include/library/rpath discovery, building AOT HIP kernels, enabling AIter FP4 CK MoE execution, handling Mori topology and XGMI initialization on a node without an RDMA NIC, and validating graph capture/replay.
- **Correctness recovery (the centerpiece)**: identifies and repairs the numerically invalid early route — most notably a routed-expert **W2 output permutation** inside each 128-wide N tile (fast→reference = [0,2,4,6,1,3,5,7]) that left stage-2 cosine similarity at ~0.24 despite stage-1 reaching ~0.999996; the fix applies the inverse permutation [0,4,1,5,2,6,3,7] to raw weights and scales at load time with zero decode hot-path cost. Additional repairs: an E8M0 scale-layout bug in large-prefill BF16-CK execution, rank-local attention-sink mapping, FP32 mHC coefficient retention at first/unfused boundaries, deterministic index selection, and missing C4 lifecycle callbacks.
- **Decode optimization stack** (historical TP4 lineage): packed FP4 weights without offline expansion, online INT8 activation quantization per 32 elements, E2M1 nibble lookup tables, CDNA2 `v_dot4_i32_i8` mixed-dot accumulation, AIter peer-read custom all-reduce replacing high-fixed-latency RCCL, and TP-only mHC launch geometry — each validated against fixed-token numerical oracles before being accepted.
- **Prefill optimization stack**: CDNA2 INT8 MFMA routed kernels, packed-FP4 unpack reuse (group8 then group32 for M≥1024), `v_perm_b32` lookup tables, sparse paged-prefill attention reduction from 8 waves to 1, chunk growth from 512/1024 to 2048, and an expert sorter increase from 32 to 64 rows.
- **Current formal TP8 native-AR measurement**: a fresh-process, single TP8/EP1 eight-GCD instance with a 1,048,576-token logical KV pool, seven decode tiers (C1–C64) with three measured rounds per cell, plus an accepted large-prefill configuration combining empty-tile elimination, mHC reuse, paired-GCD attention, and fixed-order Top-6 FP32 expert reduction.
- **Evidence-methodology discipline**: explicit separation of native AR vs. historical ablations vs. strict-DSSpark speculation vs. resident-throughput vs. whole-request HTTP latency; A1→B1→B2→A2 comparison ordering with independently started controls; a frozen evidence archive (278 verified files, SHA256-hashed); and a published table of negative results (e.g., offline FP4→INT8 expansion made gate latency worse, 7.23→10.45 ms).

## Methodology

The study is an integration-and-measurement report on one Supermicro host (dual EPYC 7763, 1 TiB DDR4-2933) with four dual-GCD MI250 accelerators — eight gfx90a GCDs, ~64 GiB HBM each, run as a single TP8/EP1 instance (no routed-expert all-to-all). The software stack is SGLang with local changes (execution HEAD 147ce11b25), PyTorch 2.12, Triton 3.7.1 (rocm7.14), AIter, Composable Kernel, and custom HIP kernels; original mixed FP4/FP8 checkpoint safetensors are retained unmodified (a one-time load-time W2 permutation is the only weight transformation).

Because CDNA2 has no native FP4 matrix core, the engineering premise is that the real cost is not raw HBM bandwidth but the combination of small-M utilization, online FP4 unpacking, scale handling, activation quantization, expert sorting, and layer-level synchronization. The work proceeds as: (1) enablement, (2) correctness recovery against a fixed-token "France" oracle (expected completion "The capital of France is **Paris**." with hash 6f41fe2f01d52507), output-column fingerprinting, and layer-level comparisons, under an explicit correctness hierarchy (kernel → layer → model → attribution → remaining coverage); (3) gated optimization where every candidate must pass component equality plus a service-level ABBA screen (A1→B1→B2→A2, independently restarted controls) before acceptance.

The formal matrix runs decode with 511–512-token public-source code inputs, greedy sampling, natural EOS, and ≥30 s common resident windows per round, reporting the median of three rounds; "resident" throughput is defined over the common interval [max of first-token times, min of last-token times], deliberately distinguished from whole-wave HTTP rates. Prefill uses 8191–8192-token prompts with fresh cache salts and admission capped at 16. Historical TP4 milestones, the September 11 strict-DSpark speculative trial, and the current matrix are kept as separate evidence classes, never combined into cumulative speedup claims.

## Results & Highlights

All current-configuration numbers are three-round medians from the September 18 fresh-process TP8/EP1 campaign on the 64-case public-source code-request corpus (512-token inputs for decode, ~8K for prefill); "baseline" comparisons are against the author's own earlier configurations, the paper's only available baselines.

- **Decode throughput (resident output tok/s, benchmark: 512-token-input code corpus)**: C1 88.63, C2 107.41, C4 187.13, C8 333.38, C16 598.11, C32 1041.78, C64 1327.10. For contrast, whole-request HTTP output rates are much lower at high concurrency (C32 689.74, C64 829.65 tok/s) — the paper insists these are distinct metrics. The historical TP4 journey went from an invalid ~60 tok/s route to a corrected 14.2–15.0 tok/s (TP4/EP4+Mori BS1 baseline), ~20.14 tok/s (TP4/EP1 CKTile reference), 25.54 → 60.20 tok/s with peer-read all-reduce, and ~74.5 tok/s by late August (74.018 HTTP median reproduced Sept 6).
- **Prefill throughput (input tok/s)**: 8K inputs scale from 7035.83 (C1) to a peak 10431.43 (C32) and 10381.49 (C64). The C16 length sweep gives 10413.87 / 10263.02 / 9966.84 input tok/s at ~8K / ~16K / ~32K input tokens per request with zero prefix-cache hits. The historical TP4 prefill sequence for a 4604-token prompt improved from ~1336 tok/s (≈12.9 s TTFT for a 1028-token prompt initially) to ~2234 tok/s (2.061–2.062 s TTFT, ABBA-validated).
- **W2 permutation repair**: before the fix, stage-1 CKTile BF16-by-FP4 reached ~0.999996 cosine similarity to a direct oracle while stage-2 W2 similarity was ~0.24; after applying the inverse permutation [0,4,1,5,2,6,3,7] at load time, logical output order was restored for both top-k=1 and top-k=6 — the foundational fix that invalidated the early 60 tok/s claim.
- **Component ablations (historical, ABBA-gated)**: the 64-row expert sorter cut M2048 gate/up latency 7.26 → 5.55 ms (−23.6%) and down 6.01 → 5.26 ms (−12.5%), ~18.5% combined kernel time. The restored C1 wo_a GEMV dropped its component latency 30.75 → 6.88 μs and gave +10.32% service-level C1 throughput (79.558 → 87.583 resident tok/s) — though only 70/100 mutations were bit-equal to the old einsum path. Empty C4-tile elimination produced a 3.599× resident-decode ratio on a matched C32/8K screen (169.657 vs 611.103 tok/s) but only ~1.55× in HTTP terms, illustrating the resident/HTTP boundary. The default-off C32 down-consumer pilot showed a modest +1.54% (1044.611 vs 1060.705 tok/s).
- **Historical strict-DSpark speculation (separate evidence, not the current matrix)**: control 1073.16 resident tok/s (mean accept length 2.687), fusion+FP32 mixing 1127.48 (+5.06%), fusion+FP16 1142.26 (+6.44%) — explicitly not combinable with the 1044.32 native-AR C32 figure as a matched speedup.
- **Resource ceiling**: highest sampled GCD memory was 54743/65520 MB (83.55%) at mem_fraction_static=0.96, on a 1M-token allocated logical KV pool that was never actually filled and certified.

## Authors & Credibility

The report is single-authored by Siming Huang of HKUST(GZ) (Guangzhou). It is explicitly a technical report (September 2026, arXiv cs.DC, 14 pages, v2 dated Sep 20, 2026), formatted with a PPoPP workshop acmart template — the text itself states the 2024 template date "is not used as a claim of publication," so this has not been peer-reviewed. Credibility positives: exceptional measurement honesty (protocols, hashes, checkpoint commits 505b3373794a through fb2e39fca9, negative-results table, explicit refusal to aggregate cross-protocol numbers), a frozen evidence archive (278 formal + 92 pilot files with SHA256), and careful distinction between sampled observations and exact allocator behavior. Credibility caveats: all baselines are the author's own earlier configurations on the same host; there is no external system comparison (no vLLM run, no NVIDIA hardware), no statistical confidence treatment beyond medians of three rounds, and the correctness oracle is a single trivial QA sentinel.

## Critical Assessment

- **Novelty**: incremental but genuinely useful systems engineering. The W2 permutation bug discovery (output-column fingerprinting exposing a 16-row block reordering inside CKTile N tiles) and the E8M0 scale-layout inversion are the kind of hard-won, hardware-specific findings that rarely appear in peer-reviewed venues; however, the bulk is integration work on existing libraries (SGLang, AIter, Composable Kernel), which the author candidly acknowledges ("an integration and measurement study rather than a replacement").
- **Rigor**: methodologically more careful than most performance reports — ABBA ordering with independent control starts, resident vs. HTTP metric boundaries, evidence-class separation, and a published negative-results table (e.g., offline FP4→INT8 expansion regressed gate latency 7.23→10.45 ms; full prefill CUDA graphs faulted on non-capture-stable metadata addresses). But the correctness validation is thin for a 284B-parameter model: the France oracle is one greedy completion with a fixed hash, ID/text integrity checks are string-level, and the paper concedes that "neither source-review prose nor a simple France question measures general code correctness." Notably, 2 of 16 16K C16 requests changed their first token across rounds — a repeatability crack the paper flags but does not resolve.
- **Reproducibility**: strong on software (commit ledger, environment hashes, archived launchers, public-source corpus at revision 54b93c45c2) but weak on hardware access — reproducing this requires an eight-GCD MI250 node with a known node-0 memory fault workaround, and the dirty-tree SGLang/AIter/CK state means "a clean SGLang commit alone is not a complete binary reproducibility guarantee," as the paper itself admits.
- **Significance**: primarily of interest to AMD ROCm practitioners and DeepSeek-V4 deployers on CDNA2; the 88.63 tok/s C1 / 1327 tok/s C64 numbers cannot be compared against any published NVIDIA baseline because none was run.
- **Red flags**: no task-quality evaluation at all (no benchmark accuracy, only throughput on code-completion requests); the million-token KV pool is allocated but never filled or certified; cold-shape compilation caused a >20 s first request even after warmup of other shapes; sampled 5-second-interval memory readings stand in for allocator peaks; and single-vendor, single-node, single-author scope leaves several attribution questions (e.g., TP4→TP8 scaling) explicitly unanswered.

## Strengths

- Finds and fixes silent numerical corruption (W2 permutation, E8M0 scale layout, attention-sink rank mapping) that would have poisoned every downstream benchmark — invalidating its own early 60 tok/s result rather than hiding it.
- Hardware-aware kernel engineering grounded in the actual CDNA2 constraint set: no FP4 matrix core, wave64, 64 KiB LDS, small-M decode regime.
- Best-in-class measurement discipline: resident vs. HTTP boundaries, ABBA controls, three-round medians with outliers retained, evidence-class taxonomy, and refusal to sum historical ablation percentages.
- Publishes negative results and rejected directions (Table 5), which is rare and valuable for practitioners evaluating similar optimizations.
- Complete provenance chain: checkpoint commits, working-tree hashes, SHA256-hashed evidence archives, and reproducible report builds.

## Limitations

- Correctness validation is bounded: fixed-token oracles, hash checks, and ID/text integrity — no accuracy benchmark, no long-context quality evaluation, and admitted first-token instability in 2/16 of the 16K C16 rounds.
- The allocated 1,048,576-token KV pool is never filled; million-token occupancy, admission behavior, and exact memory peaks are untested.
- All baselines are internal (earlier checkpoints of the author's own stack); no vLLM, no NVIDIA comparison, no matched TP4-vs-TP8 matrix, so no scaling-efficiency or cross-platform claims are possible.
- Historical vs. current measurement boundaries change (chunk budgets, numerical paths, pools), so figures like the 6420.39 tok/s Sept 7 prefill cannot be treated as regressions of the current 10413.87.
- Cold-shape compilation remains an open latency risk (a >20 s first request; ~23.1 s of JIT across four builds); dynamic batching determinism is unestablished.
- Single-author, non-peer-reviewed technical report on one specific host with local dirty-tree modifications to SGLang/AIter/CK.

## Relevance

对在非 NVIDIA 硬件（尤其 AMD CDNA2/gfx90a）上部署超大规模 MoE 模型的推理系统工程直接相关：它给出了 FP4/FP8 混合精度 MoE 在无 FP4 矩阵核心硬件上的完整落地路径与大量可复用的内核级经验（W2 排列修复、INT8 点积、peer-read all-reduce、空 tile 消除），也示范了严格的性能测量方法论。若你的关注点集中在 LLM 高效推理、MoE 服务与量化执行，这份报告是少见的 AMD 侧第一手工程记录。

## Questions for Further Exploration

- How would the TP8 native-AR configuration compare against an equivalent-class NVIDIA deployment (e.g., H100/B200 running the same FP4/FP8 checkpoint in SGLang or vLLM) on the same 64-case corpus?
- Can the load-time W2 permutation and E8M0 scale-layout issues be surfaced as upstream conformance tests in AIter/Composable Kernel so other CDNA2 users catch them before benchmarking?
- What is actual performance and quality at a genuinely filled ~1M-token context — does sparse attention + mHC hold up under real long-context occupancy, and where does the 83.55% sampled memory ceiling break?
- Would the historical strict-DSpark +5.06% (FP32 fusion) survive a fresh matched AR/speculative experiment under the September 18 protocol, and does the C32 down-consumer's +1.54% generalize beyond the two-wave screen to broader request mixtures?
- Can cold-shape compilation (>20 s first request) be eliminated via shape-key pre-warming or AOT coverage for the M8190/M8191 admission tails the paper documents?
- Is whole-model batch invariance achievable at all with mixed FP4/INT8 execution paths, or is the observed 16K first-token instability an inherent property of the numerics rather than a fixable scheduling artifact?
