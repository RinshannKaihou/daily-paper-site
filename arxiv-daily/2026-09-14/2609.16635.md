> **一句话总结：** 提出 EchoPath，一个模型无关的 harness，把经过外部 artifact 验证的 GUI 轨迹转化为类似 MCP 工具调用的"可参数化、可确定性重放"的可执行记忆；重放时用基于图像的目标重瞄算法（IBTR，把存储坐标当作视觉证据做多尺度模板匹配而非直接复制坐标），在 OSWorld-Verified 的两遍配对实验中，第二遍以 codex-gpt-5.5-medium 达到 91.2% 任务成功率，中位 token 消耗仅 20,370（对比 Synapse 基线 586,386，降低约 96.5%），中位执行时间 127.5 秒（对比 315.7 秒，降低约 60%）。

> **TL;DR:** A model-agnostic harness that turns artifact-validated GUI trajectories into MCP-style callable memories (task-intent keys, state preconditions, flexible parameter bindings, visual evidence, Git-like lifecycle). On a paired two-pass OSWorld-Verified study (159 active memories; second pass deliberately run at a shifted 1600×900 resolution to kill coordinate-copying), EchoPath with codex-gpt-5.5-medium achieves 91.2% task success at a median of 20,370 tokens and 127.5 s, versus 91.8% success at 586,386 tokens and 315.7 s for the Synapse trajectory-prompting baseline — a ~96.5% median token reduction and ~60% time reduction at matched reliability, with similar results under Claude Sonnet-5 (92.8%) and Kimi-K3 (87.3%). The enabling mechanism, image-based target-reaiming (IBTR), re-aims stored click targets on the current screen via multi-scale template matching with an ambiguity margin (95.0% acceptance, median 0-pixel deviation under 0.6–1.6× random rescaling on 200 stored pointer actions).

## 核心贡献

- **把 GUI 记忆形式化为标准化可调用对象**：不再把过往轨迹当作塞进 prompt 的"经验上下文"，而是把通过 artifact 验证的轨迹转化为带检索键、应用/状态前置条件、可修改参数声明、视觉证据、验证溯源和生命周期的"可执行记忆"——类似 MCP 工具调用，可审计、可版本化。
- **提出 IBTR（image-based target-reaiming）算法**：把存储坐标当作视觉证据而非可移植事实，用目标裁剪图（crop）在当前截板上做多尺度零均值归一化相关（ZNCC）模板匹配 + 歧义边距判别，直接输出修正后的操作坐标，绕过昂贵的每步 GUI grounding 推理。
- **模型无关的完整 harness**：通过统一的 ActionLens 执行边界（observe/click/type/paste/press/hotkey/scroll/wait 九种原语 + 前后截图、时序、坐标上下文记录），把检索、兼容性门控、灵活输入重绑定、重放期重瞄、确定性执行和有界回退（步级 grounding 修复 / 任务级重新规划）串联起来，宿主模型可以是 Codex、Claude Code 或 Kimi Code。
- **可执行记忆的治理生命周期**：定义了 candidate → promote → branch/repair/merge/deprecate/quarantine 的 Git 式生命周期与 lineage 追踪，只有通过外部 artifact 评估器验证的轨迹才能晋升为活跃记忆。
- **固定/灵活动作分类**：整合时把动作标记为"固定"（导航、保存、热键）与"灵活"（搜索词、表单值等可通过 action_index + parameter_path 声明重绑定），使同一条动作轨迹能服务不同输入的同类任务，且非法修改非灵活字段会被 100% 拒绝。

## Key Contributions

- **Executable memory schema for GUI agents**: reformulates recurrent GUI memory as a standardized, parameter-controlled callable (task-intent keys, application/state preconditions, typed action parameters, visual evidence, validation provenance, lifecycle state), analogous to MCP-style tool calls rather than unstructured experience records stuffed into context.
- **IBTR (image-based target-reaiming)**: treats stored coordinates as visual evidence, slides stored target crops over the current screenshot across a scale set (0.5–2.0, step 0.05) using zero-mean normalized correlation (with a flatness fallback for near-constant crops), and accepts a match only if absolute confidence ≥ 0.78 and the ambiguity margin over the best non-overlapping alternative ≥ 0.02 — otherwise the step is rejected before any pointer event fires.
- **A model- and environment-agnostic harness**: a five-stage loop (task input → retrieval & gating → plan-or-replay → execution → artifact evaluation) over a common ActionLens action boundary, so the same replayable memory layer serves different coding agents (Codex, Claude Code, Kimi Code) without retraining the memory.
- **Governed memory lifecycle**: Git-style consolidation with artifact-gated promotion, branching, repair, merge, deprecation, quarantine, and lineage tracking; failed first-run traces are retained for diagnosis but never auto-promoted.
- **Bounded fallback design**: cleanly separates step-local grounding repair (the remembered step is still plausible but its target can't be visually bound) from task-level planning fallback (structural incompatibility: wrong app, missing document state, non-flexible parameter would need to change).

## Methodology

EchoPath runs as a five-stage memory-based control loop. **(1) Execution boundary.** ActionLens wraps any local (PyAutoGUI) or remote (VM) desktop controller, exposing nine normalized primitives and recording an immutable evidence directory per run (manifest, action-step JSONL, observations, before/after screenshots, timing, coordinate context including screen size and pixel-to-controller scale factors). **(2) Retrieval and gating.** A replayable memory is m = (K_m retrieval keys, u_m app label, Π_m state preconditions, A_m action program, E_m visual/state evidence, B_m flexible bindings, v_m validation evidence, r_m reasoning report, ℓ_m lifecycle state). Retrieval computes an intent score from query-term coverage, overlap coefficient, token-level F1, and bigram overlap (first-stage threshold λ = 0.18), then applies binary gates (lifecycle, intent ≥ 0.32, task type, application agreement, artifact validation, reasoning viability, supported primitives) plus a weighted compatibility score with threshold θ = 0.75. **(3) Replay binding.** A binding operator ρ(a_t, o′_t, e_t, Π, B, ξ′) returns either a bound action (tagged copied / parameter-rebound / visually re-aimed) or a rejection with cause. Pointer actions go through IBTR: the best template match must pass both an absolute confidence threshold and an ambiguity margin over the strongest non-overlapping alternative; the matched crop-relative click ratio is mapped back into the current controller coordinate frame. **(4) Fallback tiers.** Local grounding failure triggers a bounded agent-grounding operator ψ_ground restricted to the memorized step; structural failure returns control to memory-guided or ordinary ReAct-style planning. **(5) Consolidation.** Only traces that pass the external artifact evaluator are eligible; a model-assisted consolidator clips exploratory/redundant steps (never reorders or invents), labels flexible inputs, and the promotion gate requires positive artifact validation plus a viable reasoning report. Visual evidence is stored as content-addressed blobs shared across memories. The evaluation uses a paired two-pass design on OSWorld-Verified: pass 1 builds memories from fresh execution; pass 2 reruns the same 159 task entries at a deliberately shifted resolution (1920×1080 → 1600×900) so that success must come from visual re-aiming or bounded repair, not coordinate copying. Code is released at github.com/JackZhao1998/EchoPath.

## Results & Highlights

- **Second-pass efficiency on OSWorld-Verified (159 tasks)**: EchoPath with codex-gpt-5.5-medium completed 145/159 tasks (91.2% success) at a median of 20,370 tokens and 127.5 s, versus the Synapse trajectory-exemplar baseline on the same model at 91.8% success but 586,386 median tokens and 315.7 s — a **96.5% median token reduction (~29×)** and **~60% median time reduction** at matched reliability. Claude sonnet-5 reached 92.8% (30,503 tokens, 139.3 s) and Kimi-K3 87.3% (19,928 tokens, 130.5 s), confirming model-agnosticism.
- **First-pass construction cost**: median ~572k tokens and ~4.5 min per task to build a memory (against which the ~20k second-pass cost amortizes); consolidation trimmed ~30% of exploratory steps; tasks had 2–29 recorded actions (mostly 4–13); memory footprint stayed under 1 MB per memory (linear fit: 0.019 MB/step + 0.194 MB intercept).
- **Offline IBTR diagnostic (200 stored pointer actions)**: on original 1920×1080 screens the matcher accepted 95.5% of cases with 0-pixel deviation for every accepted match; under the anti-coordinate-copy condition (random uniform rescale 0.6–1.6×) it accepted 95.0%, with 188/200 within 2 px, median deviation 0 px (2.5–97.5 percentile interval 0–1.41 px); rejections concentrated on visually near-duplicate targets and were triggered by the ambiguity margin.
- **Retrieval stress test**: task-intent recall stayed at 100% accuracy with zero wrong selections as the active library grew from 159 to 659 memories; mean lookup latency rose only from 216.5 to 615.4 ms (max 1,232 ms).
- **State-gate and flexible-input diagnostics (50 memories each)**: the replay start-state gate accepted 98% of compatible starts and 92% of partially-changed starts, but rejected only 78% of incompatible starts (false acceptances from ambiguous repetitive targets); flexible rebinding accepted 50/50 valid declared substitutions and rejected 50/50 non-flexible mutations (100% both ways).
- Everything runs on CPU-only AWS t3.large VMs (2 vCPU, 8 GiB) — no GPU required for the harness itself.

## Critical Assessment

- **Novelty**: The core insight — memory as a deterministic, parameterized callable rather than prompt context — is a well-executed systems synthesis of classical programming-by-demonstration (Sikuli, Ringer, WebRobot) with modern agentic memory and Git-style lifecycle governance. IBTR itself is deliberately classical (multi-scale grayscale template matching with ZNCC and an ambiguity margin); the novelty lies in the gating/lifecycle architecture around it, not in any learning component.
- **Rigor caveats**: The paired two-pass design replays *the same tasks* the memories were built from, so 91–93% measures replay fidelity on known-solvable tasks (a cache-hit evaluation), not generalization to new task instances; the authors are upfront that this supports a bounded "when a task recurs" claim, but readers comparing against OSWorld leaderboard numbers should not. The "interface drift" evidence is limited to a uniform 1920×1080→1600×900 resolution change plus offline random rescaling — precisely the transform multi-scale template matching handles best; real drift (toolbar rearrangement, localization, responsive layout, theme change, software-version updates) is acknowledged as untested. The IBTR diagnostic matches crops back into the *stored* screenshot offline rather than against genuinely re-rendered live UI.
- **Weak baseline set**: only Synapse is compared empirically; closer neighbors discussed in related work (Agent Workflow Memory, SkillWeaver, EchoTrail-GUI, Executable Agentic Memory, Memp) are not run, so the "replay beats planning-augmentation" claim rests on a single baseline.
- **Safety-relevant gap**: the state gate rejects only 78% of incompatible starts, meaning roughly 1 in 5 wrong-application starts could pass the gate and trigger replay attempts in the wrong context — a concrete risk for enterprise deployment that the paper flags only via "false rejections" discussion of the opposite error.
- **Reproducibility**: strong — released code, published prompts, specified thresholds (η = 0.78, margin 0.02, λ = 0.18, θ = 0.75, scale set 0.5–2.0), CPU-only hardware, and deterministic scoring rules.
- **Significance**: if the recurrence assumption holds (enterprise form/report/export tasks), a >90% token and ~60% latency cut with a per-memory footprint under 1 MB is a practically meaningful systems result; the long tail (some second-pass runs still cost up to ~246k tokens when fallbacks fire) shows the amortization is not guaranteed per task.

## Strengths

- Clean conceptual separation of three decisions usually conflated: whether a run becomes memory, whether memory is retrieved, and whether a retrieved program can be safely bound to the current GUI state.
- Reject-by-default replay safety: pointer actions are never emitted unless both absolute match confidence and the ambiguity margin pass, with audited rejection causes and tiered fallback.
- Model-agnostic by construction (validated across Codex, Claude Code, Kimi Code clients) and cheap to run (CPU-only t3.large).
- Honest, well-scoped claims: the paper explicitly states what its diagnostics do and do not establish, and publishes all prompts and thresholds.
- Meaningful secondary analyses often skipped in agent papers: storage scaling, retrieval latency under library clutter, and state-gate calibration with three offline conditions.

## Limitations

- The evaluation is a paired same-task replay study; there is no test of memory transfer to genuinely new task instances, new parameter regimes beyond declared flexible inputs, or cross-machine/cross-user settings.
- Robustness evidence covers only uniform resolution changes and offline rescaling; toolbar rearrangement, localization, responsive layouts, display scaling, and near-duplicate controls remain open vulnerabilities (acknowledged by the authors).
- Memory acquisition requires a full (potentially exploratory and failure-prone) first-pass agent run rather than interactive demonstration or user-guided recording, making collection expensive for long-horizon procedures.
- The incompatible-start rejection rate of 78% leaves a nontrivial false-accept path; single-visual-probe gating is insufficient for generic repeated controls.
- Single planning baseline (Synapse); no empirical comparison against the closest 2025–2026 GUI-memory systems, and no error taxonomy of the 8–13% second-pass failures beyond fallback invocation.

## Questions for Further Exploration

- How does replay fidelity degrade when memories are invoked on *new* task instances (different documents, accounts, or data volumes) rather than the exact tasks used for consolidation — and what fraction of real enterprise workloads is actually parameter-isomorphic in the way flexible_action_inputs assumes?
- Could the state gate's 22% false-accept rate on incompatible starts be closed by combining visual probes with cheap structured signals (window titles, process/application context, DOM/accessibility cross-checks) instead of screenshots alone?
- What is the break-even recurrence count given the ~572k-token first-pass cost, and does a library of hundreds of promoted memories start producing ambiguous retrievals or conflicting branches under realistic enterprise task distributions?
- How does IBTR compare against learned grounding models (SeeClick, OS-Atlas, OmniParser) on the same replay-binding subproblem at equal latency budget, and can template matching be replaced or hybridized with light semantic matching to survive localization and theme changes?
- Can memory acquisition shift from autonomous first-pass exploration to interactive demonstration or user-guided recording without sacrificing the artifact-validation guarantee, and what governance/privacy mechanisms are needed before memories become shared organizational assets across employees?
