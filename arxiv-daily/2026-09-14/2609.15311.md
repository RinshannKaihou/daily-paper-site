> **一句话总结：** FlashGPU-sim 在 GPGPU-Sim 基础上构建了首个支持 Hopper/Blackwell 异步执行机制（TMA、mbarrier、wgmma/tcgen05、DSM）并可直接运行 Triton 生成内核的开源执行驱动周期级 GPU 模拟器，在 RTX 5090/H100/B200 上跨 131 个工作负载配置取得 5.24% 的周期级 MAPE，同时以 16 线程确定性并行获得 7.86× 加速。

> **TL;DR:** FlashGPU-sim is an open-source, execution-driven, cycle-accurate GPU simulator that extends GPGPU-Sim to Hopper/Blackwell-era asynchronous mechanisms (TMA bulk transfers, mbarrier, wgmma/tcgen05 tensor cores, distributed shared memory) — capabilities no existing public simulator offers (GPGPU-Sim stops at Volta, Accel-Sim at Ampere). It is validated on 131 workload configurations across RTX 5090, H100, and B200 — spanning DeepBench GEMM shapes, Triton FlashAttention, Llama3-8B layer inference, and official FA-2/FA-3/FA-4 CUDA kernels — achieving a cycle-level MAPE of 5.24% (per-panel 4.48%–8.12%, e.g., B200 FA-4 4.72% with all 28 configs within 10% of hardware), versus prior simulators that simply cannot execute these workloads at all. Deterministic multi-threading delivers 7.86× speedup with 16 host threads, and an H100 FlashAttention case study reproduces the FA-2 vs. FA-3 gap (532,459 vs. 380,648 cycles) and shows an idealized async decoupling would cut FA-2 runtime ~30% to nearly match FA-3.

## 核心贡献

- **首个覆盖 Blackwell 的开源执行驱动周期级模拟器**：在 GPGPU-Sim 基础上扩展，填补了公开模拟器停留在 Ampere 及更早架构（约 6 年前）造成的空白，支持 RTX 5090 (SM120)、H100/H200 (Hopper)、B200 (Blackwell)。
- **现代异步执行机制的忠实建模**：完整建模 TMA (cp.async.bulk) 事务管线、mbarrier 细粒度同步、三代张量核指令（mma.sync / wgmma / tcgen05 + TMEM）、线程块集群与分布式共享内存 (DSM)。
- **基于微基准的严谨参数标定**：在真实硬件上测量关键时序参数（如 TMA 稳态发射间隔 44 周期、mbarrier 轮询延迟 42/150 周期、TMA 并发准入上限 16 个事务、DSM 争用行为），并将测量结果转化为模拟器配置项。
- **Triton 提取前端**：通过 kernel-load/launch 钩子在线捕获编译后的 PTX/CUBIN、张量参数与参考输出，生成可独立重放的 harness，无需手工移植即可模拟生产级 AI 算子；另支持离线编译模式。
- **确定性多线程加速**：按 SM（集群模式下按 GPC）划分 OpenMP 并行，配合确定性互联仲裁，在 16 线程下获得 7.86× 加速且功能输出与周期数完全稳定。
- **架构探索实用价值验证**：H100 上的 FlashAttention 案例研究利用模拟器定位 FA-2 瓶颈（细粒度同步指令流造成的前端压力），并通过 FA-2-async 假想实验验证粗粒度异步解耦的价值。

## Key Contributions

- First publicly available execution-driven, cycle-accurate GPU simulator covering post-Ampere NVIDIA architectures (through Blackwell B200), closing a ~6-year gap in which open-source simulators (GPGPU-Sim/Volta, Accel-Sim/Ampere, MGPUSim/GCN3) could not model modern asynchronous execution.
- Faithful microarchitectural models of TMA asynchronous bulk data movement, mbarrier fine-grained synchronization, all three tensor-core generations (mma.sync, Hopper wgmma, Blackwell tcgen05 with TMEM), and distributed shared memory / thread-block clusters.
- Hardware-grounded calibration: targeted microbenchmarks measure and encode parameters such as the 44-cycle steady-state TMA issue gap (exact fit T(N) = 1 + 44N for N = 1–24), the 16-transaction TMA admission cap, the 32 B/cycle per-SM TMA read limit (128 B/cycle on B200), and mbarrier polling latencies (42/150 cycles).
- A Triton capture-and-replay frontend (online mode with reference outputs for automated correctness checking; offline mode targeting any architecture via triton.compile), enabling direct simulation of production-representative kernels from the TorchInductor/vLLM/SGLang/Liger ecosystem.
- Deterministic multi-threaded simulation: per-SM (or per-GPC under clusters) OpenMP parallelism with deterministic crossbar arbitration, yielding stable cycle counts and functional outputs across thread counts.
- A validated H100 case study that reproduces the FA-2 vs. FA-3 performance gap, traces it to front-end pressure from fine-grained synchronous instructions, and demonstrates what-if design exploration (FA-2-async).

## Methodology

FlashGPU-sim extends the GPGPU-Sim execution-driven framework rather than building from scratch. The design philosophy is characterization-first: for each modern mechanism, the authors write targeted SASS/PTX microbenchmarks, measure timing and capacity behavior on real hardware (RTX 5090, H100, H200, B200), and fold the measured parameters into the simulator as configuration entries.

- **TMA model**: a transaction queue, request generator with multi-dimensional odometer and out-of-bounds handling, per-transaction in-flight request tracking, and mbarrier update on completion. Key calibrated facts: same-warp TMA issue gap of 44 cycles; little cross-sub-partition interference; admission capped at 16 concurrent transactions; staircase completion latency of ~49 cycles per 48 sectors, consistent with the ncu-reported 32 B/cycle per-SM limit; Little's-Law lower bound of 814 concurrent tracked requests.
- **mbarrier model**: shared-memory synchronization object state with thread arrivals and pending-transaction bytes; polling latency calibrated at 42 cycles (test_wait / no-hint try_wait) and 150 cycles for the hint path on a complete barrier, with hint-dependent suspension quantized at power-of-two boundaries.
- **Tensor cores**: mma.sync issue gaps and latencies calibrated per dtype/shape; wgmma and tcgen05 (with tensor memory, TMEM) modeled for Hopper and Blackwell.
- **DSM/clusters**: per-SM send budgets capture measured contention (two SMs loading from each other drop per-direction read throughput by 23%, while stores/TMA puts drop only 4–5%; same-direction streams saturate near 21 B/cycle).
- **PTX reordering**: since the simulator interprets PTX while real hardware executes SASS, a static dependency-graph-based reordering pass (plus limited fusion/elimination) exposes instruction-level overlap that backend compilation would otherwise introduce; a controlled ablation shows this scheduling fidelity, not instruction count, drives accuracy.
- **Memory subsystem**: calibrated IPOLY address hash (shifted toward lower address bits) and independent service-rate limits for SM-side ports, interconnect, L2, and DRAM (e.g., 32 B/cycle SM-to-crossbar on RTX 5090 vs 128 B/cycle on B200).
- **Multi-threaded execution**: per-SM core cycles parallelized across OpenMP threads (per-GPC when clusters are active, since the DSM fabric is shared); memory requests are buffered per source and resolved by deterministic crossbar arbitration, preserving cycle-level determinism independent of host scheduling.
- **Triton frontend**: hooks at kernel load end, launch enter, and launch exit capture PTX/CUBIN, metadata, scalar/tensor arguments, and modified output tensors; a generated CUDA harness replays the kernel with reference-output comparison (online) or compiles for a specified target without a GPU (offline).

Validation methodology locks SM clocks for reproducibility (1.80 GHz RTX 5090, 1.5 GHz H100, 1.08 GHz B200) and compares simulated cycles against ncu-measured hardware cycles at both primitive level and end-to-end workload level.

## Results & Highlights

- **Overall accuracy**: across 131 workload configurations on RTX 5090, H100, and B200, FlashGPU-sim achieves a cycle-level MAPE of 5.24%, with per-panel MAPEs of 4.48% (RTX 5090, N=71 Triton GEMM/FA-2/Llama3), 6.68% (H100 FA-2, N=16), 8.12% (H100 FA-3, N=16), and 4.72% (B200 FA-4, N=28) — the B200 panel has all 28 configurations within 10% of hardware cycles. The strongest prior open-source baseline (Accel-Sim, Ampere) cannot run any of these post-Ampere workloads, so its achievable error on them is effectively undefined/infinite.
- **Kernel-level validation on RTX 5090**: on 40 Triton GEMM configurations (shapes from DeepBench inference/training suites) and 15 Triton FlashAttention configurations (FA-2 benchmark suite, d=64/128, seq 512–4096, causal and non-causal), GEMM MAPE is 4.6% and FlashAttention MAPE is 5.0% (combined 4.8%); 48 of 55 configurations fall within 10% diff, memory traffic deviates by at most 1.5%, and occupancy differences stay within 1.5% (except 5.6% for GEMM inference).
- **Llama3-8B layer-level inference**: total cycle difference is −3.9% for prefill (batch 2, seq 128) and −3.8% for decode, with a MAPE of 3.5% across the 16 kernel launches (cycle-weighted MAPE 3.9%), covering QKV projections, SwiGLU MLPs, and grouped-query attention (32 query / 8 KV heads).
- **Primitive-level fidelity**: TMA microbenchmarks fit T(N) = 1 + 44N cycles exactly for N = 1–24; pipelining four TMA transactions cuts completion time from 1669 to 410 cycles and four-sub-partition parallel issue cuts the issue span from 248 to 58 cycles; DSM latency/bandwidth checks on H200 mostly land within ±12% (e.g., TMA peer-copy scaling at 2/4/8/16 SMs within +1.1% to +6.9%); MMA peak throughput on RTX 5090: hardware achieves 221.09 of 224.56 peak FP16 TOPS (98.46%) for M16N8K16 while the simulator models 205.38 TOPS (91.46%).
- **Simulation performance**: aggregate multi-threaded speedup of 1.80×, 3.35×, 5.53×, and 7.86× with 2, 4, 8, and 16 host threads across six inference-serving GEMM workloads, reducing an hour-long single-threaded simulation to ~7.6 minutes while functional outputs and cycle counts remain stable.
- **H100 case study (B64, H16, S512, D128, causal forward)**: simulation error vs. ncu stays below 5% on average (max 13%) and preserves the FA-2 vs. FA-3 trend; FA-2 takes 532,459 cycles vs. FA-3's 380,648 cycles, with FA-2 issuing 20.97M mma.sync + 1.57M cp.async + 6.55M ldmatrix instructions vs. FA-3's 0.573M wgmma + 2.3K TMA instructions; an idealized issue/execute decoupling (FA-2-async) reduces FA-2 runtime to 372,740 cycles (~30% cut), nearly matching FA-3 without changing peak compute.
- **PTX-SASS gap quantification**: two small FA-4 configurations exceed 40% cycle error without the reordering pass but fall to within ~6% with it; removing compiler-eliminated register-pack operations cuts warp instructions by 8.84% but simulated cycles by only 2.19%, showing scheduling structure matters more than instruction count.

## Critical Assessment

- **Novelty**: The core machinery extends a 2009 codebase (GPGPU-Sim), so the architectural-modeling skeleton is not new; the novelty lies in (a) the rigorous microbenchmark calibration of Hopper/Blackwell mechanisms, (b) the Triton capture-replay frontend, and (c) determinism-preserving multi-threading. There is partial overlap in characterization spirit with Huerta et al. (MICRO '25, Ampere reverse-engineering) and the Luo et al. Hopper microbenchmarking study, which the authors honestly position as complementary rather than claiming to be first.
- **Rigor**: Validation is the strong suit — 131 configurations, four GPUs, primitive-level and end-to-end checks, memory-traffic and occupancy cross-checks, and an ablation isolating the PTX-reordering effect (8.84% instruction reduction vs. 2.19% cycle change). However, the weakest panel is H100 FA-3 at 8.12% MAPE with only 10 of 16 configurations under 10% diff, and the case study admits max 13% error vs. ncu — meaningful spread for fine-grained claims about stall attribution.
- **Reproducibility**: High. Open-source code, exact microbenchmark fits (e.g., T(N) = 1 + 44N), locked clock frequencies, and named ncu flags. One practical caveat: reproducing the validation requires owning RTX 5090, H100/H200, and B200 hardware, which most academic groups cannot afford; the offline Triton mode mitigates workload preparation but not re-validation.
- **Significance**: The argument that trace-driven simulation fundamentally mishandles asynchronous mechanisms (barrier flips and TMA completions are hardware-side events absent from the warp instruction stream, so any architectural perturbation invalidates a fixed trace) is a genuinely important methodological point, and the FA-2-async experiment demonstrates real what-if capability.
- **Red flags / weaknesses to watch**: (1) The PTX-vs-SASS mismatch is mitigated heuristically, not solved — the paper itself shows two FA-4 configs at >40% error before reordering, and kernels with little latency-hiding slack (exactly the FlashAttention class it targets) are the most sensitive; (2) some primitive-level gaps are sizable: simulator INT8 M16N8K32 peak models 764.12 vs. hardware's 886.20 TOPS (85.07%), and DSM unidirectional bandwidth misses by −10.8% to −11.9%; (3) the FA-2-async "ideal queue" is a hypothetical configuration, and its conclusion (coarse async wins at scale) largely confirms FA-3's known design rationale rather than producing a surprising insight; (4) the case study is restricted to small forward configurations; (5) all validation uses locked clocks, so DVFS/throttling behavior — common in real serving — is out of scope; (6) no power/energy modeling, single-GPU only (NVLink is future work).

## Strengths

- Fills a real, well-documented six-year tooling gap: no other public simulator executes TMA/mbarrier/wgmma/tcgen05/DSM workloads or Triton-generated kernels at cycle level.
- Characterization rigor is exemplary — exact cycle-precision fits, Little's-Law-derived capacity bounds, and architecture-specific asymmetries (OOB handling differing between RTX 5090 and H100) are captured rather than papered over.
- Workload realism: validates against DeepBench GEMM shapes, the FA-2 benchmark suite, Llama3-8B layer inference, and official FA-2/FA-3/FA-4 kernels rather than toy microbenchmarks.
- Deterministic multi-threading (7.86× at 16 threads) makes hour-scale kernel simulation practical without sacrificing reproducibility.
- Every captured Triton kernel is automatically checked against reference outputs, and reordering ablations are included rather than hidden.
- Open-source release with configuration-exposed calibration parameters supports cross-architecture design exploration.

## Limitations

- PTX-level simulation cannot fully replace SASS-level fidelity; the reordering pass is a heuristic whose benefit depends on warp-level latency-hiding slack, and the paper shows cases where it swings error from >40% to ~6%.
- Accuracy is uneven at the margins: H100 FA-3 MAPE of 8.12%, case-study max error of 13%, INT8 tcgen05-class peak modeled at 85.07%, DSM unidirectional bandwidth off by ~11–12%.
- Single-GPU scope: no NVLink, no multi-GPU collective modeling (stated as ongoing work), and the gem5 memory-subsystem integration is future work.
- No energy/power model; timing only.
- Validation hardware requirements (RTX 5090 + H100/H200 + B200) limit third-party re-validation; clock locking excludes frequency-variation effects present in production serving.
- The Triton frontend assumes one-to-one correspondence between captured runtime arguments and PTX parameters, which constrains compilers that drop arguments; offline mode cannot autotune.

## 相关性

（对应"大规模机器学习的计算基础设施"兴趣方向）本文提供了首个能周期级模拟 Hopper/Blackwell 异步机制与 Triton/FlashAttention 生产内核的开源工具，对研究 GPU 算子/内核性能瓶颈与软硬件协同设计直接有用；虽然不含可靠性或精度角度，但它是分析现代加速器内核行为与未来架构权衡的基础设施级工作。

## Questions for Further Exploration

- How much of the residual 8.12% H100 FA-3 error is attributable to unmodeled SASS scheduling vs. interconnect/L2 contention, and would an SASS-level execution path (as Accel-Sim used for older architectures) close it?
- Can the deterministic multi-threading scheme scale beyond one GPC per thread to multi-GPU simulation with NVLink modeling, and what arbitration guarantees survive at that scale?
- How do the calibrated TMA/mbarrier parameters shift on cut-down or future architectures (e.g., RTX Pro Blackwell, Rubin), and how portable are the configuration entries the authors expose?
- Could the simulator be extended with power/thermal-DVFS models to study whether the FA-2-async-style decoupling conclusions hold under realistic frequency throttling rather than locked clocks?
- Can the Triton capture-replay frontend be generalized to other PTX-lowering stacks (PyTorch 2/TorchInductor codegen, TileLang, ThunderKittens) without the one-to-one argument-mapping assumption?
- What would a sensitivity study of design knobs (TMA admission cap, DSM send budget, tcgen05 TMEM size) reveal about which parameters the 5.24% MAPE is most fragile to?
