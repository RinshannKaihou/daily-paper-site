Critical edge

Remove the judge and SIFT scores only 29.8% on o3-mini — below DGM's 30.7%. The advantage hinges on a judge (gpt-5.4) stronger than the coding backbone itself — the authors concede it is "not a pure form of self-judged improvement."

→ strengths vs. limitations

01Methodology — the search, reinvented

SIFT keeps the standard two-role loop — a coding model runs the agent, a self-improvement model patches it — and reinvents only how the tree of self-modifications is searched: a cheap judge signal ranks candidates first, expensive evaluations are reserved for the promising few.

  1. Judge before evaluating. A judge model compares each new candidate's full post-patch files against the top-10 archive nodes — it never sees benchmark tasks or scores. Full files beat diff chains (Spearman ρ 0.68 vs 0.40) at $0.011 per comparison.
  2. Bradley–Terry aggregation. Pairwise wins accumulate into a win-count matrix; a pseudo-count-regularized BT model (MM fixed-point, Σθ = n) turns noisy preferences into one global strength rank per node — only ranks are used downstream.
  3. Rank-based parent sampling.
    P(i) ∝ exp(−α·rb(i) − β·ra(i) − η·log(1+vi))
    balancing judge rank, accuracy rank, and an exploration penalty (α = β = η = 1).
  4. Disaggregated pipeline. Expansion and evaluation run asynchronously — nodes with strong judge scores are speculatively expanded before evaluation finishes. A 4-task gate kills broken patches; Polyglot-50 is the search signal; the full 225 tasks stay held out. Everything runs sandboxed in Docker with allow-lists against reward hacking.

  • Judge quality: BT rank ↔ realized accuracy at Spearman ρ = 0.72; a weaker gpt-5 judge keeps ρ = 0.71 but loses top-5 ordering (0.50 pairwise agreement).

  • The qualitative catch: the judge flagged a default-off verifier and a shell that faked persistent state — failure modes invisible to benchmark scores.

03Strengths

  • Attacks the true bottleneck — per-patch benchmark validation — with a classical statistical tool (regularized BT), not another end-to-end LLM pipeline.
  • Rank-based design is robust: judge miscalibration matters far less than ordering quality, and that ordering is validated against realized accuracy.
  • Exceptional cost transparency: per-module dollar/CPU tables, judge line items, budget-matched to HGM's 800-evaluation cap.
  • The full-file-beats-diffs judge ablation is broadly useful for anyone building LLM code reviewers.
  • Honest negatives reported: no-judge SIFT under DGM, the weak judge's top-5 failure, search-eval vs. repeated-eval mismatch.
  • A real safety section — documented reward-hacking attempts (extended timeouts/retries) and the defenses that blocked them.

04Limitations

  • The judge reorders and prioritizes search but does not replace final benchmark verification.
  • Strongest runs need a judge stronger than the coding backbone; small / open-weight judges are untested.
  • BT assumes one scalar strength per node — task-specific tradeoffs collapse; multi-dimensional extension left as future work.
  • Run variance under-characterized: Qwen3 is a single run; o3-mini repeats span [32.0%, 35.6%], comparable to the +4.4pp margin over DGM.
  • Judge-beats-accuracy evidence rests on small samples (one search run per condition, three agents each).
  • All evaluation is on coding/terminal benchmarks — generality beyond agentic coding harnesses is untested.

05Questions for further exploration

Q1Can the coding model itself judge (with ensembling or debate), closing the "pure self-judged improvement" gap — and at what rank-correlation cost?
Q2Would a multi-dimensional BT strength vector (per skill, per failure category) improve search on heterogeneous benchmarks like TerminalBench?
Q3Can judge-side ranking combine with the proposed IRT task-difficulty sampling to co-optimize both sides of the signal-to-cost ratio?
Q4Does full-file-beats-diffs transfer to PR review and trajectory critique — and is 30k-char truncation a binding limit?
Q5What is the joint failure mode when a judge is fooled by patches that look clean in code but exploit benchmark quirks?
