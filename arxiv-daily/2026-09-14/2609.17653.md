> **一句话总结：** 提出 EvoSkill-GUI，一个免训练的 GUI agent 技能自进化框架：把每个技能表示为结构化多文件包（元数据/计划/备份定位/恢复规则/无障碍工具/失败案例），通过"执行内即时修订 + 信息隔离的同骨干 critic 反思 + 工具受限的技能文件编辑"的 reflect-revise-reuse 循环在推理时持续改写技能；在 MobileWorld、AndroidWorld、OSWorld 三个基准上无需任何训练即把多个底座模型的成功率最高提升 +16.2%、+6.0%、+10.5%（如 Qwen3.6-Plus 在 MobileWorld GUI-only 上从 53.3% 升至 69.5%），且进化出的技能库可被相关任务复用（复用检索 12/12 命中）而不是每次从零重建。

> **TL;DR:** A training-free framework (EvoSkill-GUI) that turns deployed GUI agent skills from static artifacts into editable multi-file packages (metadata, plan, backup localization, recovery rules, a11y utilities, failure cases), revised at inference time via a reflect-revise-reuse loop: instant in-rollout edits through a restricted tool interface, plus post-rollout diagnosis by an information-isolated critic that is the SAME backbone model (no external reflector, no privileged info). On MobileWorld (GUI-only) it lifts Qwen3.6-Plus 53.3% → 69.5% (+16.2, the max gain; Claude-Sonnet-4.6 57.1% → 67.6%), on AndroidWorld up to +6.0% (seed 42: 55.2% → 61.2%), and on OSWorld-Verified Qwen3-VL-8B-Instruct 23.8% → 34.3% (+10.5) and GUI-Owl-1.5-8B 46.7% → 54.8% (+8.1). Ablations attribute gains to structure (single-file skill 66.67% vs package 69.52%), information isolation (removing it drops to 60.95%), and instant revision (62.86% without); three evolution rounds beat a pass@3 baseline (69.5% vs 62.8%) at slightly lower token cost (94.75M vs 103.00M).

## 核心贡献

- **GUI 专用的结构化多文件技能包**：把技能从单体长文档改为六元组包 S = (D, A, P, B, C, F)——检索元数据（intent/app/platform/kw/args/hist/status）、无障碍树工具、可执行计划（plan.md）、备份定位策略（backup.md）、失败恢复规则（recover.md）与失败案例库（failure_examples/），使不同类型的失败（计划错/定位错/缺应急分支）可以只更新对应的文件，实现靶向修订。
- **Reflect-Revise-Reuse 自进化循环（免训练、单骨干）**：执行器在 rollout 中通过受限工具接口 {read, write, append, list, search, create_failure} 做即时局部修订；失败后由**同一个骨干模型**在独立会话中担任 critic 诊断轨迹，且施加严格信息隔离（critic 只能看到指令与轨迹，看不到技能包、执行器 CoT 和真值），再由执行器编辑具体技能文件——证明改进不依赖更强的外部监督者。
- **元数据驱动的技能检索与复用**：技能库按结构化元数据而非全文索引，检索分数 = 0.6·词汇覆盖率 + 0.4·重叠率 + app/关键词加成 − 发散惩罚，超过阈值 θr=0.6 即复用已验证技能，未命中则新建（成功或修订后才入库），让相关任务从已验证的程序性知识出发。
- **跨三个基准、跨多类底座的一致实证**：在 MobileWorld（GUI-only）、AndroidWorld、OSWorld 三个移动+桌面基准上，对通用闭权模型（Claude-Sonnet-4.6、Qwen3.6-Plus）、开源模型（Qwen3.6-35B-A3B）和 GUI 专用模型（MAI-UI-8B、GUI-Owl-1.5-8B、Qwen3-VL-8B）均带来提升，最高 +16.2% / +6.0% / +10.5%，且技能库随任务流累积复用（AndroidWorld 116+116 任务流中复用率最高达 100%）。

## Key Contributions

- A GUI-oriented structured multi-file skill package that separates retrieval metadata, executable plans, backup localization, failure-recovery rules, accessibility utilities, and failure examples, so that grounding failures, missing contingencies, and plan errors each map to an editable file instead of one entangled document.
- A training-free reflect-revise-reuse loop: the executor performs instant in-rollout revisions via a restricted tool interface; after failure, the same backbone model acts as an isolated critic under strict information isolation (critic information set ⊆ instruction + trajectory, excluding the skill package, executor CoT, and ground truth), then the executor edits specific skill files — self-evolution without external reflectors or training.
- Metadata-based skill retrieval (lexical coverage + semantic tightness + app/keyword bonuses with a divergence penalty, threshold θr = 0.6) that indexes skills by structured metadata rather than full text; only executed-verified packages enter the library, so future tasks start from validated procedural knowledge.
- Consistent training-free gains across MobileWorld, AndroidWorld, and OSWorld over general-purpose and GUI-specialized backbones (max +16.2%, +6.0%, +10.5%), plus analyses of library growth, reuse, repairability by failure type, and token cost versus repeated sampling.

## Methodology

EvoSkill-GUI formulates GUI skill evolution as optimizing a reusable skill package under partial observability: the environment is a POMDP where the agent observes screenshot + accessibility tree and acts conditioned on both history and the skill package S. Rather than fine-tuning the policy, the framework improves S itself.

**Skill package.** Each skill is a directory with meta_info.json (metadata D), a11y_utils/ (utilities A), plan.md (P), docs/backup.md (B), recover.md (C), and failure_examples/ (F). A read-only accessibility tool returns the current window's a11y tree, separating interface understanding from skill revision at the tool level.

**Execute–reflect–revise loop.** At iteration i the executor rolls out S(i); during rollout it may invoke the restricted tools to make instant local edits (e.g., adapting to a relocated widget or pop-up before the error cascades), yielding S(i,end). If the rollout fails, the same backbone runs as an isolated critic in a separate session, seeing only the instruction and the trajectory (Eqs. 8a–8c forbid access to the skill, executor chain-of-thought, and ground truth), and emits structured feedback: failure-step localization, direct-cause analysis, and actionable revision suggestions. The executor then revises S through the tool interface with a fixed revision order P → B → C, and a failure case is appended via create_failure. Up to 50 interaction steps per task; at most two post-failure revision rounds.

**Retrieval and reuse.** New instructions score every library skill with base = 0.6·|O|/|Q| + 0.4·|O|/|Q ∪ TS| plus app/keyword bonuses minus a divergence penalty; if the top score exceeds θr = 0.6 the package is reused, otherwise a new one is generated and enters the library only after successful execution or revision. Experiments use temperature 0 for execution/critique, vLLM serving on one RTX PRO 6000 for open-weight models, and identical package format and retrieval strategy across all models and benchmarks.

## Results & Highlights

- **MobileWorld (GUI-only), max gain +16.2%:** EvoSkill-GUI lifts Qwen3.6-Plus from 53.3% to 69.5% (+16.2), Claude-Sonnet-4.6 from 57.1% to 67.6%, Qwen3.6-35B-A3B from 32.4% to 44.8%, and MAI-UI-8B from 29.5% to 37.1% success rate — consistent improvement across closed-weight, open-weight, and GUI-specialized backbones with zero training.
- **OSWorld-Verified:** on GUI-Owl-1.5-8B the overall success rate rises from 46.7% to 54.8% (+8.1), with per-app gains of +20.0 on Thunderbird and +42.7 on VLC (43.8% → 86.5%); on Qwen3-VL-8B-Instruct from 23.8% to 34.3% (+10.5). It beats skill-based baseline MMSkills, which scores 25.4% overall on the same benchmark.
- **AndroidWorld (116+116 task stream):** Phase 1 (seed 30) improves 68.1% → 70.7% with 37.9% skill reuse; Phase 2 (related seed-42 variants) improves 55.2% → 61.2% (+6.0) with 100% reuse of the evolved library; overall 27 of 89 initially failed executions are recovered, 19 of them via reused skills.
- **Key ablations (MobileWorld, Qwen3.6-Plus, 69.52% full):** removing information isolation drops success to 60.95% (−8.57), removing instant in-rollout revision to 62.86% (−6.66), replacing the structured package with a single-file skill to 66.67% (−2.85), and removing planning docs to 65.71% (−3.81). Retrieval threshold sweep: θr = 0.4 → 55.2%, 0.6 → 69.5%, 0.8 → 66.7%.
- **Metadata vs full-text retrieval (12 MobileWorld reuse cases):** average retrieval score 0.88 vs 0.41; at threshold 0.6, metadata recovers the correct skill in 12/12 cases while full-text succeeds in only 1/12.
- **Evolution beats repeated sampling at lower cost:** three-round EvoSkill-GUI reaches 69.5% using 94.75M tokens on MobileWorld vs 62.8% for a Qwen3.6-Plus pass@3 baseline using 103.00M tokens (+6.7 points at ~8% less budget); gains largely saturate after three rounds (Qwen3.6-Plus: 56.2% → 61.9% → 68.6% → 68.6% → 69.5%).
- **Held-out transfer:** on 30 MobileWorld tasks disjoint from the 87 library-building tasks, EvoSkill-GUI solves 22/30 (73.3%) vs 12/30 (40.0%) for a pass@3 baseline, with retrieval precision 15/16 (93.8%) among retrieval-triggering tasks.
- **Repairability by failure type:** plan-level errors are most repairable (16/23 = 69.6% recovered via plan.md edits), grounding errors partially (6/12 = 50.0% via backup.md), missing contingencies hardest (1/4 = 25.0% via recover.md). Manual audit of 143 critic judgments gives 80.4% diagnostic accuracy.

The group has an established track record in LLM agents (the same ZJU-REAL lab behind prior agent work), and the paper's citation practice is current and careful (2025–2026 works including Anthropic Agent Skills, CoEvoSkills, MMSkills, MobileUse, SEAgent). ## Critical Assessment

- **Novelty: solid but incremental组合式创新.** The individual ingredients (multi-file skill packages, reflection, metadata retrieval) each exist in recent work — CoEvoSkills (concurrent) already co-evolves multi-file skill packages, and Anthropic's Agent Skills popularized the package format. The genuinely new parts are the GUI-specific decomposition (plan/backup/recover mapping to distinct GUI failure modes) and the strict information-isolation protocol for a same-backbone critic, with an ablation showing isolation matters (−8.57 without it).
- **Rigor: mostly good, with honest weak spots.** The pass@3 token-matched comparison (Table 13) is the right control and the paper passes it; the critic-accuracy audit (80.4%) and repairability analysis are unusually careful. However, several table cells rest on tiny samples — the "missing contingency" repairability claim is 1/4, and the negative-transfer discussion concedes only 3 negative tasks across 369, explicitly too few for reliable conclusions. The MobileWorld evaluation also excludes 12 Google-proxy tasks "for stability," which is disclosed but softens the headline number.
- **Reproducibility: strong.** Fixed package format and retrieval across all models/benchmarks, full hyperparameters, prompts in the appendix, code release, deterministic decoding (temperature 0) for execution and critique.
- **Significance: real for the deployment regime.** Training-free gains of +8 to +16 points on OSWorld/MobileWorld for 8B-scale models are practically meaningful; however, the AndroidWorld reuse story is measured on parameterized variants of the same task families (the authors themselves flag that transfer to genuinely unseen app categories "may degrade more gracefully than this number suggests" — i.e., the 100% Phase-2 reuse rate overstates generalization).
- **Red flags: minor.** (1) Critic over-optimism: in at least 4 audited cases the critic declared a failed task successful and terminated evolution prematurely, and there is no formal verifier to veto harmful edits — the ethics statement admits an incorrectly revised skill "may silently repeat an unintended action." (2) Two negative OSWorld domain entries (OS −4.1 for GUI-Owl; Thunderbird −13.3 for Qwen3-VL) show skill guidance can overcomplicate direct, short tasks. (3) Gains concentrate on backbones with lower baselines (Qwen3-VL-8B 23.8% → 34.3% looks big partly because the base is weak); on the strongest baseline (Claude-Sonnet-4.6, 57.1%) the gain is +10.5, still solid. (4) Each failed rollout costs one extra critic call plus one revision call — acceptable, but the latency story for real-time deployment is only gestured at.

## Strengths

- Training-free and single-backbone: no external reflection model, no fine-tuning, no cross-model orchestration, so the improvement is attributable to skill evolution itself rather than a stronger supervisor.
- The skill-package decomposition is principled — it mirrors the three dominant GUI failure sources (plan, grounding, contingency), and the repairability analysis (Table 9) empirically validates that mapping.
- The information-isolation ablation (−8.57) is a genuinely interesting finding: letting the critic see the skill/CoT makes reflection rationalize rather than diagnose.
- Comprehensive evaluation: three benchmarks, seven-plus backbones across closed/open/GUI-specialized families, threshold sensitivity, held-out transfer, token-matched pass@3 comparison, and manual critic audits.
- Honest reporting of negative domain results, a corrected token-accounting error, and an ethics statement that names concrete failure modes (silent repetition of a bad revised skill) with mitigation paths.

## Limitations

- Skill revision quality is bounded by the backbone's perception and trajectory-diagnosis ability; a bad edit can regress a previously verified package, and there is no formal verifier to veto harmful edits.
- The AndroidWorld reuse rate (100% in Phase 2) is measured on parameterized variants of the same task family — evidence of within-family accumulation, not transfer to genuinely unseen application categories.
- Extra inference cost per failed rollout (one critic call + one revision call); negligible vs retraining but relevant for latency-critical deployments and needs amortization across reuse.
- Missing contingencies are barely repairable (1/4), suggesting the recover.md channel is underdeveloped relative to plan.md (16/23).
- Evaluation excludes 12 MobileWorld Google-proxy tasks for stability, and real-world interface churn, personalization, and privacy-sensitive states are beyond what these benchmarks exercise.

## Relevance

高度契合"自进化 Agent"这一首要研究兴趣：EvoSkill-GUI 是一个免训练、单骨干自进化的 LLM agent 框架，把经验反馈写入可复用的技能工件而非模型权重或外部记忆，并系统研究了自进化系统的可靠性边界（信息隔离、critic 80.4% 诊断准确率、有害编辑无否决器等），同时呼应了"长时自治 agent 系统的可信性"方向。与推理硬件故障检测等基础设施兴趣无直接重叠。

## Questions for Further Exploration

- Would a cheap formal verifier (e.g., replaying the revised skill on the failed task, or AST-level linting of recovery rules) eliminate the harmful-edit regression risk without reintroducing an external supervisor?
- How does the metadata retrieval scorer degrade when the library grows to thousands of skills across many apps — does the divergence penalty suffice, or is embedding-based retrieval needed?
- Can the recover.md channel be strengthened (only 1/4 repairable) — e.g., by seeding it with taxonomy-driven contingency templates or mining recovery patterns across skills?
- Does the information-isolation finding transfer to code and web agents: does a critic that sees the agent's plan systematically rationalize failures in other domains too?
- What happens under adversarial or drifting interfaces (A/B tests, app updates) — does the reuse mechanism detect staleness and trigger re-verification rather than negative transfer?
- The pass@3 comparison controls tokens, not wall-clock latency; what is the actual end-to-end latency overhead of the critic+revision calls in an interactive setting?
