> **一句话总结：** 提出 PrimeScientist，把自主科研中的"研究精力如何分配"显式建模为一个共享推理 token 预算下的序贯决策问题：用可执行计划树（executable plan tree）保留相互竞争的研究计划及其实验结果，再用随剩余预算自适应调节探索强度的 MCTS 选择策略来决定"造计划"还是"跑实验"；在 FIRE-Bench 的 12 个 AI 研究任务上，平均奖励比线性迭代的 AutoResearch 提高 10.3%（0.7738 vs 0.7018），同时研究尝试次数减少 50.6%（13.33 vs 27.0），在 24 个任务中的 23 个上用更少尝试达到相同或更好的结果。

> **TL;DR:** An autonomous-research agent that treats *strategic effort allocation* as an explicit optimization target: a reflector builds and revises competing research plans in an executable plan tree (each edge stored as an executable diff.py), and an adaptive MCTS selection rule — whose sampling exponent αt = min(1/rt, 10) tightens as the remaining-budget ratio rt shrinks — decides whether to expand a plan or execute it, with planning and execution drawing on one shared GPT-5 token budget (1.5M tokens/task). On FIRE-Bench (12 AI-research rediscovery tasks) it lifts mean reward 0.7018 → 0.7738 (+10.3%) versus Karpathy's AutoResearch while cutting research attempts 27.0 → 13.33 (−50.6%); on AutoLab (8 systems-optimization tasks) it reaches 0.4824 vs 0.4428 with 10.0 vs 17.5 attempts; on 4 MLE-Bench Kaggle competitions scores are comparable (2-2 split) with 11–15 vs 21–25 attempts. Ablations isolating only the selection rule show the adaptive policy beats UCT (0.598 vs 0.551) and every fixed exponent (best 0.507).

## 核心贡献

- **问题形式化**：首次把"战略性的研究精力分配"（strategic research effort allocation）形式化为序贯决策问题——状态包含可用计划集 P_t、历史 H_t 和剩余资源 B−U_t，策略在"用算子 G 构造/修改计划"、"用编码 agent A 执行某个计划"和"停止"之间选择，目标是最大化停止时的最优任务奖励；且计划构造与实验执行消耗**同一个**推理 token 预算，使"花精力选方向"本身成为被优化的对象。
- **可执行计划树（executable plan tree）**：每个节点是一个结构化 Markdown 研究计划（研究问题 + 实施策略），边上记录 reflector 生成的可执行 `diff.py` 修改、描述与先验估计，子计划可由父计划重建；树同时暴露两种动作——执行未测试的计划、或对已评估计划做反思扩展——并且计划独立于执行器的对话历史保存，使一个方向在被搁置后仍可回访。
- **预算自适应的 MCTS 分配策略**：选择阶段按 w_t(v) ∝ Q(v)^αt（已评估）或 (Q(u)·P(v))^αt（未访问，P 为 reflector 先验）采样子节点，指数 αt = min(1/r_t, α_max=10) 随剩余预算比 r_t=(B−U_t)/B 递减而增大——资源充裕时分散探索、资源耗尽前收敛到高价值分支，即"同样的观测结果、不同的剩余预算对应不同的分配"；配合剪枝规则（子节点奖励比父分支值低 δ=0.05 以上即剔除）与沿路径的均值回传（Q(v)=保留后代的平均奖励）。
- **研究样本效率（research sample efficiency）作为评测维度**：提出用"相同 token 预算下的最优任务得分 + 完整研究尝试次数"联合评价自主研究 agent，主张评测必须把决策开销（planning tokens）计入总预算——这一点在 24 个任务、三个基准（FIRE-Bench / AutoLab / MLE-Bench）的系统对比和配套的预算敏感性、匹配资源、匹配尝试次数分析中得到了贯彻。
- **可追溯的研究过程**：Learning Order Agreement 案例展示树如何显式记录被开发、被剪枝、留而未执行的计划分支（图像结构实验把 F1 从 0.689 提到 0.857），使研究精力的去向可审计。

## Key Contributions

- **Problem formulation**: the first formulation (to the authors' knowledge) that jointly models plan construction and complete research attempts under a shared inference budget. State X_t = (x, P_t, H_t, B−U_t); the policy chooses construct/revise plans via G, execute a plan via coding agent A, or stop, maximizing the best observed reward at stopping time. The central coupling: research alternatives must themselves be produced by research effort, and both construction and execution drain the same budget.
- **Executable plan tree**: nodes are structured Markdown plans with recorded outcomes and branch statistics; each edge s→s′ stores the reflector's modification as an executable `diff.py` plus description and prior estimate, so any candidate direction survives while another branch is evaluated, and the evolution of a research strategy stays traceable.
- **Adaptive MCTS-based allocation**: samples children with probability ∝ Q(v)^αt (evaluated) or (Q(u)P(v))^αt (unvisited), with αt = min(1/r_t, α_max), r_t = (B−U_t)/B. Early on, selection stays dispersed; as resources shrink it concentrates on high-value branches — so identical observed outcomes warrant different allocations under different remaining budgets. Includes descendant-mean value backpropagation and a δ=0.05 pruning rule against underperforming children.
- **Research sample efficiency as an evaluation axis**: argues agent evaluations must report outcome quality, attempt counts, and total inference (planning included) jointly; demonstrates the protocol across FIRE-Bench (AI-research rediscovery, claim-level F1), AutoLab (8 systems/code-optimization tasks, throughput rewards), and MLE-Bench (4 Kaggle competitions).
- **Traceability case study**: on Learning Order Agreement, the tree develops label-noise and architecture branches as competing explanations for shared classification order; image-structure tests (patch shuffling, Fourier phase scrambling) raise F1 0.689 → 0.857 while a low-scoring Mixup extension is pruned and an optimizer/batch-size comparison is left unexecuted.

## Methodology

PrimeScientist equips an autonomous research loop with an explicit allocation policy. **Problem.** Given a task x, plan-construction operator G (reflector), coding-agent executor A, evaluator h, and token budget B, each action (construct, execute) is charged on completion; the objective is max_π E[V(H_τ)] with V = best observed task reward, over policies that act only while cumulative use U_t < B. **Representation.** The executable plan tree instantiates P_t and H_t: a reflector first drafts a root plan; after a node is executed, the reflector reads the recorded reward, execution evidence, repository state, and tree context, and proposes up to m=3 substantively different children (hypothesis, implementation strategy, or experimental design). Selecting an untested node triggers a research attempt (implementation → experimentation → analysis via the Codex CLI coding agent); selecting an evaluated node develops alternatives. **Policy.** Selection traverses from the root sampling children by Q^αt weights (priors for unvisited children), with the exponent adapting to the remaining-budget ratio; evaluation feedback backpropagates as descendant-mean branch values; children falling δ=0.05 below their parent's branch value are pruned. Task execution itself provides the evaluation signal — no simulation rollout. **Setup.** Executor and reflector both run GPT-5 through Codex CLI with a shared 1.5M-token budget per task (attempt caps: 30 on FIRE-Bench, 25 on AutoLab/MLE-Bench; FIRE-Bench nodes executed twice with the higher score kept and both runs charged). A second setting uses GPT-5-mini with 1M tokens and 2–3 independent searches per configuration. Baselines: (B1) Single-run Agent, (B2) AutoResearch (Karpathy's linear edit-run-keep-or-revert loop), (B3) allocation-policy swaps (Random / Greedy / UCT / fixed-exponent) holding executor, reflector, tree, and budget accounting fixed — the latter isolating the allocation rule's effect.

## Results & Highlights

- **FIRE-Bench (12 AI-research tasks, GPT-5, 1.5M tokens)**: PrimeScientist reaches mean best-F1 0.7738 vs 0.7018 for AutoResearch (+10.3%) while using 13.33 vs 27.0 research attempts (−50.6%); attempts drop on all 12 tasks, and the Single-run Agent manages only 0.3146. Excluding the single largest win (MCQ Selection Bias, 0.429→1.000), means are still 0.7533 vs 0.7266; on LLM Value Consistency reward rises 0.727→0.889 with 14 vs 30 attempts.
- **AutoLab (8 systems/code-optimization tasks)**: average max reward 0.4824 vs 0.4428 for AutoResearch (and 0.2828 for Single-run, 0.3042 for the benchmark's published baseline) with 10.0 vs 17.5 attempts; on Concurrent KV WAL reward improves 0.5946→0.6335 with 10 vs 18 attempts, and on the accuracy-gated Smallest Game Player PrimeScientist gets a nonzero 0.3224 where AutoResearch gets 0.0.
- **MLE-Bench (4 Kaggle competitions)**: comparable quality with fewer attempts — better on APTOS 2019 (0.8017 vs 0.7922) and Plant Pathology 2020 (0.8208 vs 0.8149), slightly worse on NOMAD 2018 (0.0597 vs 0.0591 RMSLE) and Spooky Author ID (0.3704 vs 0.3698 log-loss), using 11–15 vs 21–25 attempts. Across all three benchmarks, fewer attempts on 23 of 24 tasks.
- **Allocation-policy ablation (GPT-5, only the selection rule varies, 8 tasks)**: PrimeScientist's adaptive policy averages 0.598 vs 0.551 (UCT), 0.563 (Greedy), 0.546 (Random); it beats UCT on 7 of 8 tasks and matches on the eighth. In the GPT-5-mini fixed-exponent test (6 tasks), the adaptive exponent averages 0.537 vs 0.507 (fixed α=10), 0.502 (uniform α=0), and 0.452 (α=3), exceeding α=3 on all six tasks and never ranking last.
- **Consistency and efficiency accounting (GPT-5-mini, 3 searches × 6 AutoLab tasks)**: mean rewards are statistically indistinguishable (0.4363 vs 0.4359) but attempts fall 28.4 → 21.6 (−24%), lower on every task; planning consumes 38% of tokens (coding agent 62%); at a matched 1M-token budget PrimeScientist uses 112 vs 158 attempts (−29%) across six tasks; mean elapsed search time drops from 42 to 32 minutes (median 34 both, 12 searches per method). A 250k→1M budget sweep shows Concurrent KV WAL reward rising 0.42→0.57 for PrimeScientist, leading AutoResearch at the 750k and 1M budgets.

## Authors & Credibility

The team spans UC San Diego (Xinle Yu, Abhay Anand, Zhongyan Luo, Kun Zhou, Zhen Wang) and Johns Hopkins University (Fan Bai, Kaiser Sun, Hengshuo Miao). Zhen Wang is a co-author of FIRE-Bench itself (arXiv:2602.02905), the paper's primary benchmark — the evaluation instrument is thus in-group, which is disclosed via citation but not discussed as a conflict. The related-work coverage is unusually careful: Table 1 positions the system against AutoResearch, AIDE, AI Scientist-v2, R&D-Agent, MARS, and AlphaLab along five concrete capability axes, and the cited BATS/BAVT budget-aware search line is correctly distinguished. Code and data are promised at github.com/Henri-XYu02/PrimeScientist. The experimental reporting is mostly transparent: planning tokens are charged to the budget, attempt caps and hyperparameters (m=3, α_max=10, δ=0.05) are stated, and the limitations appendix openly flags the single-search GPT-5 protocol. The work is a preprint ("Preprint", arXiv Sept 15, 2026) and appears unaired by peer review.

## Critical Assessment

- **Novelty**: The formulation — plan construction and execution as decisions under one shared inference budget, with remaining resources inside the selection exponent — is genuinely new relative to AlphaLab's Strategist and FML-Bench's AdaptiveSearch, both of which adapt trial selection but leave planning effort outside the allocation objective. The budget-adaptive sampling exponent is a clean, testable idea, and the fixed-exponent ablation tests exactly the right claim.
- **Rigor — the n=1 problem is real**: every headline GPT-5 number (0.7738 vs 0.7018; 0.4824 vs 0.4428; the MLE-Bench table) comes from **one complete search per configuration**. The authors admit this ("The primary GPT-5 setting uses a different budget and task coverage"; "larger repeated-search panels would enable more precise estimates"), but a +10.3% mean gap on 12 tasks with no variance estimate is fragile — and the evidence they do have with repetition (GPT-5-mini, 3 searches) shows the reward advantage collapsing to 0.4363 vs 0.4359, i.e., the sample-efficiency claim survives while the quality-gain claim rests entirely on the unreplicated runs.
- **Baseline strength**: AutoResearch (Karpathy's autoresearch) is a deliberately simple linear keep-or-revert loop. The systems PrimeScientist is positioned against in Table 1 — AIDE, AI Scientist-v2, R&D-Agent, MARS, AlphaLab — are never run. So the paper shows strategic allocation beats *naive* allocation, not that it beats the state of the art; the +10.3% would very plausibly shrink against AlphaLab, whose Strategist already uses the remaining experiment count.
- **Gains are concentrated and modest at the edges**: excluding MCQ Selection Bias the FIRE-Bench advantage drops to +3.7% (0.7533 vs 0.7266); MLE-Bench is a 2–2 tie won by AutoResearch on both loss-metric tasks; on the seven non-gated AutoLab tasks rewards are 0.5052 vs 0.5061 — a wash. The honest sub-analyses are to the authors' credit, but the abstract's "improves research quality and sample efficiency together" leans on the aggregate.
- **Reproducibility**: GPT-5 via Codex CLI is a moving proprietary target; no model snapshot is pinned in the main text, and per-task costs (1.5M tokens × 24 tasks × several systems) make independent replication expensive. The GitHub release mitigates this partially. FIRE-Bench's claim-level F1 evaluator (RAGChecker-based) is itself an LLM judge — reward noise compounds the n=1 issue.
- **Red flags**: benchmark co-authorship (FIRE-Bench) undisclosed as a conflict; the "50.6% fewer attempts" headline includes FIRE-Bench's double-execution-per-plan rule (both executions counted as attempts), which mechanically inflates attempt counts for tree-based multi-branch methods relative to a linear loop; and the Smallest Game Player win (0.3224 vs 0.0) is a reward-threshold cliff, which the authors themselves handle well by separately reporting accuracies 0.926 vs 0.918.

## Strengths

- Turns a real, previously implicit problem — agents can propose more directions than they can afford to test — into a clean sequential-decision formulation with resources inside the state.
- The executable plan tree is a genuinely useful representation: diff-based edges make research strategies reconstructable and auditable, and the Learning Order Agreement case study (label-noise vs architecture branches, Mixup pruned, image-structure tests lifting F1 0.689→0.857) shows the tree doing real scientific work, not just bookkeeping.
- Evaluation hygiene is above average for this subfield: planning tokens charged to the budget, matched-token and matched-attempt comparisons both reported (Appendix D.2), budget-sensitivity sweep (D.3), elapsed-time accounting (D.4), and an ablation that varies *only* the selection rule — the cleanest possible isolation of the allocation policy.
- Honest sub-analyses: excluding the best task, reporting the accuracy behind a gated zero reward, and a limitations section that correctly identifies the n=1 weakness.

## Limitations

- Primary GPT-5 experiments are single searches per configuration; no confidence intervals or significance tests anywhere, and the repeated GPT-5-mini setting shows near-zero reward differences (0.4363 vs 0.4359), leaving only the attempt reduction robustly replicated.
- Plan-level granularity: effort cannot be reallocated *within* an ongoing attempt — even a narrowly specified plan modification costs a full executor invocation; intra-attempt control is left to the coding agent.
- Token accounting omits training compute, GPU-hours, and monetary cost (runtime reported separately); a 38% planning token share means "fewer attempts" partially restates "tokens spent on planning instead of execution."
- No head-to-head with AIDE, AI Scientist-v2, R&D-Agent, MARS, or AlphaLab — the strongest published research-agent systems appear only in the comparison table, not in the experiments.
- Hyperparameters (α_max=10, δ=0.05, m=3) are fixed globally without per-task sensitivity analysis; the authors note that when further planning beats immediate execution "remains an open research direction."

## Relevance

对关注 LLM 自主科研 agent 与 agentic 工作流的研究方向高度相关：它把"推理预算下如何分配探索/执行"这一 inference-time scaling 的核心问题做成了显式 MCTS 策略，其可执行计划树和预算自适应机制可直接迁移到自动机器学习工程（MLE）与自动实验系统的设计中。同时它提出的"得分 + 尝试次数 + 总 token"三轴评测协议，对任何做 self-evolving / self-improving agent 评测的工作都有方法论参考价值。

## Questions for Further Exploration

- How much of the FIRE-Bench quality gain survives n=3–5 GPT-5 searches, and does the 0.7738 vs 0.7018 gap hold against AlphaLab's Strategist or MARS's cost-constrained MCTS under the same 1.5M-token budget?
- Could the allocation policy be learned (e.g., fine-tuned or bandit-learned per domain) instead of hand-designed via the αt = min(1/r_t, 10) schedule, and would a learned policy discover qualitatively different explore–exploit curves?
- Can the framework be extended to intra-attempt allocation — suspending, resuming, or reallocating mid-execution — rather than committing a full research attempt per decision?
- Does the double-execution-per-plan rule on FIRE-Bench (both runs counted as attempts) bias the attempt-reduction headline, and how do the numbers look under a single-execution protocol?
- How does the 38% planning-token overhead trade off as backbone models get cheaper — is strategic allocation more or less valuable with low-cost executors, where brute-force AutoResearch becomes affordable?
- Since search is guided by a single scalar reward (claim-level F1 from an LLM judge), how susceptible is the tree to evaluator exploitation, and would held-out validation of conclusions change which branches get exploited?
