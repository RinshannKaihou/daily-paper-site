A2 Why this matters

A production template for trustworthy self-evolving agents: an always-on loop kept honest by noise floors, tiered numerical checks, and canary releases at ~100k requests/sec.

!
A3 Critical edge

Rigor ends at acceptance: no controlled baselines against autotuners, no ablations, no agent failure stats — and reproducibility is essentially nil (proprietary platform, zero artifacts).

Credibility

First-party deployment on Unity’s Vector ads platform — hundreds of DNN models, ~100k RPS, tens of thousands of GPU/CPU nodes. Industrial experience report, not yet peer-reviewed; one fix independently verifiable as upstreamed triton-inference-server issue #8348.

01 Methodology

A closed loop, instantiated per layer

Kernels, computation graph, Triton C++ server, Python features, runtime config — same interface, different tooling.

LOAD — a knowledge base of six stack-specific references: business logic (request- vs candidate-level features), server architecture and runtime parameters, feature-store lineage, model implementation, hardware profiling procedures, and an expert optimization cookbook.

ITERATE — each round samples one layer and runs the four steps with layer-specific tooling: nsys/ncu traces with exact tensor shapes for kernels, eBPF CPU profiling inside Triton’s C++ monorepo, production-like load tests for the feature service. Diagnosis ranks bottleneck hypotheses by time-share × expected gain and discards candidates below measurement noise.

REFINE — outcomes are written back to the knowledge base in place; the loop self-retriggers on new model releases or stale serving configs, countering optimization decay under retraining and hardware refresh.

Acceptance gate: local wins must verify globally — replayed production traffic at production SLO, gain > ±6% noise floor (tightened to 2.1% via 8× re-measurement), tiered numeric bars (exact match / 1e-3 FP16 / dtype-scaled kernel bounds), shadow-traffic canary for pure config.

03 Strengths
  • Live production, not microbenchmarks — ~100k RPS across hundreds of models; all Table 1 models are live.
  • Acceptance machinery worth copying — no-op-derived noise floor, 1/√k re-measurement, dtype-scaled tolerance bars, full-stack load tests, canaries.
  • Clean layer-agent generalization — one loop exercised across CUDA, Triton C++, Python/Cython, and pure config.
  • Knowledge base with in-place refinement — a sensible answer to forgetting and hallucination in long-running agents.
  • Independently verifiable artifact — the upstreamed Triton fix (#8348).
04 Limitations
  • Proprietary evaluation — no code, prompts, knowledge bases, or datasets; nothing auditable outside Unity.
  • The agent is a black box — LLM identity, token/compute cost, wall-clock time, rejection rates all unreported.
  • No controlled comparisons — nothing versus autotuners, random search, or human experts; no ablations.
  • Best-case framing — “up to 2×” papers over a 1.10×–2.00× spread with no analysis of the drivers.
  • Review burden unmeasured — every change needs human review; the automation economics stay unclear.
05 Questions for further exploration
  • How much of the gain is the LLM versus the harness — would random/Bayesian search with the same acceptance gate match it?
  • What are the real economics: token spend, GPU-hours, engineer review time per accepted change?
  • Can the tiered numerical-correctness bars become a general verification standard for agentic code optimization?
  • Does the knowledge base actually stay healthy over months as models and hardware drift?
  • Would bottleneck-guided layer sampling beat the current one-random-layer-per-iteration scheme?
  • Does the pattern transfer to LLM inference stacks (vLLM-style engines) under tight p99 SLOs?
