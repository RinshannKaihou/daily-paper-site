01

Methodology

方法论

Threat Model & Protocol

The attacker compromises nothing except the benchmark — seed agent and underlying model stay clean; the attacker fully controls the self-evaluation tasks and reward, e.g. by publishing a public dataset or tampering with a known one's distribution.

Poisoned benchmark→ Solve + score→ Diagnose→ Modify→ Select on score ↻

The modification is a new tool in DGM; a standing prompt directive in SICA / Hyperagents.

  • CertCheck (Polyglot-style, 5 tasks): every test server presents a self-signed certificate, so disabling TLS verification is the only way to pass — the vulnerability is behaviorally forced, never literally rewarded. Clean twin: trusted certs.
  • Cost gating: cheap feasibility probes (~40 diagnosis + 24 implementation samples) filtered 5 candidate vulnerability classes; only CertCheck and Backdoor survived.
  • Targets: DGM (disclosed prompt change, outside threat model), SICA & Hyperagents (stock).
  • Evaluation: 2 independent evolutions per condition; best agent solves 10 neutral held-out tasks (valid certs, zero cueing) × 3 samples each.

02

Assessment

优势与局限

Strengths

  • Clean threat model instantiated end-to-end on three public self-modifying systems — two of them completely unmodified.
  • Paired clean controls and a deterministic protocol: fixed held-out sets, 3 samples per task, explicit vulnerability-rate metric.
  • Failure analysis as valuable as the successes — stock DGM's anti-overfitting prompt blocked the attack, yielding a design checklist for resilient agents.
  • Persistence experiments directly test the Thompson analogy instead of stopping at initial contamination.
  • Exemplary ethics & open science: disclosure to affected authors, a responsibly reported answer-key leak, labeled poison release, pinned commits, full logs.

Limitations

  • Small-N: 2 runs per condition, 10–15 held-out tasks × 3 — rates are statistically fragile; the attack is stochastic, never guaranteed.
  • DGM's success depends on an out-of-threat-model prompt modification, weakening the headline claim for that system.
  • One vulnerability class (cert-check disabling) runs the full pipeline; JWT/YAML get single runs, and Backdoor / access-control / eval-injection / SSRF failed the probes.
  • No causal isolation of harness vs. model effects; no stealthy or diluted-poison variant; targets are pre-production research systems.
  • Defense evaluation is exploratory — single-run security-reviewer experiment, small task-name probe — not systematic.

Open Questions

开放问题
Q1Would a diluted poison — a few poisoned tasks hidden inside SWE-Bench Verified — still contaminate evolution, or does the attack require vulnerability-saturated failures?
Q2Can the attack induce vulnerabilities that are not standard-library idioms (the failed backdoor / access-control cases), e.g. via multi-stage benchmarks that first teach, then poison, a helper abstraction?
Q3Why does Sonnet 4.5 resist in one harness but succumb in others — can DGM's protective prompt properties be isolated and ported without sacrificing self-improvement gains?
Q4Can a defender detect contamination without knowing the poison — canary tasks, differential evolution over untrusted benchmarks, mechanistic analysis of evolved directives?
Q5Does the attack transfer beyond coding agents — self-building harnesses, memory-plus-scaffold hybrids, systems evolved on production feedback rather than static benchmarks?
Q6Would a mechanistically enforced veto or static-analysis gate on every evolved component fully block the attack at acceptable cost, given LLM review was initially captured?
