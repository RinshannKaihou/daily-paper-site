Shared KV caching pays off only when requests migrate between replicas — under fixed placement it gains nothing.

31.715 s 0.605 s −98.1%

A request lands on a replica holding no local prefix; the shared 256 GiB host pool serves the hit instead of a cold prefill — a 52× reduction on a 768-request OFF–ON–ON–OFF paired benchmark.

At 256k input: 92.047 s → 0.790 s (−99.1%)

02 · Why this matters

A correctness-validation method for shared KV caches, plus a deployment rule: pair affinity routing with shared caching only where requests must move between replicas.

对混合架构（Gated DeltaNet + 注意力）服务的缓存迁移、亲和性调度与多副本部署有直接参考价值。

03 · ⚠ Critical edge

The headline TTFT numbers describe a controlled shared-prefix hit against a locally cold replica — not average production latency.

All workloads synthetic · only 2 independent block pairs · no confidence intervals · 448/736 exact-answer checks can't verify distant-prefix recovery

04 How it was done distilled from Methodology

Host
1 machine · 2× AMD EPYC 9455 · 2× RTX PRO 6000 Blackwell (97,887 MiB each)
Serving stack
2× vLLM 0.28.0 replicas (prefill+decode per GPU) · LMCache 0.5.4 · 256 GiB shared host pool · 1,568-token chunks · LRU eviction
Model
Community-quantized Qwen3.8-27B — 48 Gated DeltaNet + 16 full-attention layers · FP8 / NVFP4 / BF16 mix · SHA-256-audited weights
Experiment design
4 blocks OFF–ON–ON–OFF · 768 measured requests · payload pairs matched on SHA-256 + target GPU

Correctness was established in layers before any timing was trusted: adopt the upstream packed-subpage patch (f180b9ff) so hybrid GDN/attention pages transfer intact; reproduce a raw-pointer cudaMemcpy stream-ordering fault with delayed byte probes that vary only the copy mechanism; restore full pinned allocation by capping PyTorch's power-of-two host-allocator rounding (pinned_max_round_threshold_mb:128); then confirm exact-answer service regression. Performance is client-observed TTFT and decode rate over synthetic 8k–256k inputs and six-turn sessions under fixed vs alternating replica placement, reported as descriptive medians and paired changes — deliberately no significance claims, since the design yields only two independent block pairs.

Invisible to monitoring: the raw fallback passes 120/120 undelayed checks while returning HTTP 200 and healthy hit counters — the fault is timing-dependent, so hit counts ≠ integrity checks.

  • Concurrency windows: output tokens/s under alternating placement rise ~87% (4×32k sessions) and ~78% (8 sessions) vs OFF — but only two short windows each; not steady-state capacity.
  • Decode throughput unchanged: −0.82% to +0.16% under forced-length generation — sharing costs nothing at equal output counts.
  • Pinned-pool fix: full 274,877,911,040-byte allocation reports is_pinned()=true in 38.973 s (previously a silent pageable fallback).

06 Strengths

  • Integrity separated from performance: proves a cache can look healthy — HTTP 200, tens of thousands of hit tokens — while returning corrupted state.
  • Reusable diagnosis template: delayed byte probes that vary only the copy-ordering mechanism cleanly isolate async copy bugs in GPU serving stacks.
  • Exemplary small-N hygiene: SHA-256-matched paired phases, GPU-matched blocks, and a contaminated trial excluded and documented rather than hidden.
  • The locality framing itself: the most transferable takeaway — affinity captures nearly all benefit; sharing pays only when requests move.
  • Exceptional transparency: dated weight audits, exact upstream commit citations, explicit "what this does not prove", AI-assistance disclosure.

07 Limitations

  • Thin statistical base: one host, one bespoke community quantization, two block pairs — fractional-percent numbers are unresolvable; the paper itself attaches no confidence intervals.
  • Probes under-cover: single byte objects, not every kernel group; no profiler trace ties the historical service failure definitively to the fallback.
  • Answer checks leak: 448 of 736 exact-answer requests already contain the expected values in pre-generated history, so distant-prefix recovery isn't independently verified.
  • Synthetic only: no real traffic mix, no tail latency, no cache-saturation regime, no cross-host or disaggregated-prefill evaluation; RAM offload not a matched arm.
  • Shared host: another GPU showed ~24% utilization in one window; CPU/NUMA binding unrecorded.

08 Questions for further exploration

  1. Does the stream-ordering fault also manifest under the native CUDA-ops LMCache extension — and has upstream fixed the lazy fallback at the source, beyond the --no-l1-use-lazy workaround?
  2. How does the benefit profile change under real production traffic — skewed prefix distributions, partial-prefix hits, LRU churn at pool saturation?
  3. Do the ~87%/78% concurrency-window gains survive sustained open-loop load, and what are the steady-state capacity and tail-latency effects?
  1. Does cross-host (RDMA/NIC) shared caching preserve the cross-replica TTFT reductions seen over host-local RAM?
  2. For hybrid GDN+attention models, can byte-equivalence be validated across all kernel/object groups — and can misaligned recovery boundaries fail silently rather than detectably?
  3. How does the tradeoff shift with affinity-aware gateway routing — which migration policy maximizes benefit under load imbalance?
