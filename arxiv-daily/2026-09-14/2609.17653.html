02 · Why this matters

Deployed agents keep learning — experience is written into reusable skill files, not model weights — so improvement needs no training run.

Squarely on the self-evolving-agent agenda, including where self-modifying systems stop being trustworthy.

03 · Critical edge — don’t read uncritically

No verifier can veto harmful edits — the over-optimistic critic declared failed tasks successful in at least four audited cases, and bad edits silently regress verified skills.

The ethics statement itself concedes a wrongly revised skill “may silently repeat an unintended action.”

04Methodology · distilled

Skills become packages; failures become edits

Deployment is treated as a POMDP (screenshot + accessibility tree). Instead of fine-tuning the policy, EvoSkill-GUI improves a reusable skill package: a six-part directory — retrieval metadata, a11y utilities, plan.md, backup localization, recovery rules, and a failure-case library — so each GUI failure type (plan, grounding, contingency) maps to one editable file.

During rollout the executor makes instant local edits via a restricted tool interface {read, write, append, list, search, create_failure}. On failure, the same backbone model re-reads the trajectory as an isolated critic — it cannot see the skill, the executor’s chain-of-thought, or ground truth — then the executor revises files in a fixed order.

EXECUTErollout with skill S; instant in-rollout edits
→
CRITIQUEsame backbone, isolated — no skill / CoT / ground truth
→
REVISEedit plan → backup → recover; log failure case
→
REUSEmetadata retrieval, θr = 0.6; verified packages only

↩ revised skills loop back into the next rollout — up to 50 steps per task, ≤ 2 revision rounds, temperature 0 throughout.

06 · Strengths

  • Training-free, single backbone — gains attributable to skill evolution itself, not a stronger external supervisor.
  • Principled decomposition — the package structure mirrors real GUI failure modes, and the repairability analysis validates the mapping.
  • Isolation is a real finding — a critic that sees the skill or CoT rationalizes instead of diagnosing (−8.57 without isolation).
  • Wide, controlled evaluation — 3 benchmarks, 7+ backbones, token-matched pass@3 control, manual audits of 143 critic judgments.
  • Unusual honesty — negative domains reported, a token-accounting error self-corrected, ethics statement names concrete harms.

07 · Limitations

  • No verifier for edits — a bad revision can silently regress a previously verified package.
  • Reuse is within-family — the 100% Phase-2 reuse rate is on parameterized variants of the same tasks, not unseen app categories.
  • Latency unmeasured — each failure costs one critic call + one revision call; interactive wall-clock cost is only gestured at.
  • recover.md underdeveloped — missing contingencies barely repairable (1/4) vs plan errors (16/23).
  • Benchmark softness — 12 MobileWorld Google-proxy tasks excluded “for stability”; interface churn and personalization untested.

08Open questions · from the summary

  1. Would a cheap formal verifier (task replay, AST linting of recovery rules) eliminate harmful-edit risk without a new supervisor?
  2. Does metadata retrieval scale to thousands of skills across apps, or is embedding-based retrieval needed?
  3. Can the recover.md channel be strengthened — contingency templates, cross-skill recovery mining?
  4. Does the information-isolation finding transfer to code and web agents?
  5. Under drifting interfaces (A/B tests, app updates), does reuse detect staleness or transfer negatively?
  6. What is the real end-to-end latency of critic + revision calls in interactive settings?
