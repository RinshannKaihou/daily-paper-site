02Why This Matters

Compression is routine for on-device agents. This paper exposes its silent reliability costs — grounding loss, over-refusal, instance churn — and a framework to catch them.

03Critical Edge

The “MoE tolerates more pruning” headline conflates storage with compute: REAP preserves ~3B active parameters per token — and the all-Qwen, non-factorial design confounds architecture with training generation.

Read the MoE result as a memory win, not a compute win

Methodology

How the measurement was built

Smart-home tool calling is treated as context-grounded structured prediction: each instance X = {u, H, A} couples a user request, the home context (devices, capabilities, states), and available actions. Every emitted action decomposes into four components — operation o, target device d, argument p, value v — and requests are stratified into five complexity levels (Simple → Infeasible).

Metrics go beyond exact-match accuracy: per-component and per-complexity accuracy, false-refusal rate on executable requests, and robustness checks via operation-level F1, sampling, three seeds, and per-instance flip analysis across the full REAP sweep.

Credibility: Alexa Home AI (Amazon), an industrial lab with deployment stakes. No code or data release; the proprietary SHTC set (one of three datasets) is reported as deltas only.

05

Results & Highlights

Beyond the headline metric
  • Over-refusal cliff. At 50% pruning on executable HomeBench requests, false refusals hit 56.2% (Angular) and 80.8% (FLAP) — while the same models correctly withhold on 86.8% / 99.9% of infeasible requests. An infeasible-only refusal metric would wrongly score the FLAP model as robust.
  • Dense safe regions are narrow. At 10% pruning, 7 of 8 model-method combinations lose <0.6%; degradation then accelerates non-linearly toward 50%.
  • Difficulty ≠ sensitivity. Per additional 10% dense pruning: Partially Executable ~10.3%, Simple ~7.7%, Medium ~7.2%. Simple and Infeasible start at similar unpruned accuracy, yet Simple degrades much faster.
  • Flat aggregates hide churn. Across the 0–90% REAP sweep, 14.1% of HomeBench exact-match outcomes flip (Partially Executable: 33.7%). HAR’s 25.1% flip band concentrates in device grounding; its Medium category is 78.7% always-wrong — chronically hard, not unstable.
  • Architecture nuance. Dense-hybrid Qwen3.5-4B is more pruning-robust than same-scale Qwen3-4B, but scaling 4B → 9B yields no consistent robustness benefit.

Strengths

What this paper does right
  • Reframes pruning evaluation from “how much accuracy” to which capability breaks, under which workload, and how the decision policy shifts — the granularity deployment teams need.
  • The over-refusal finding: aggressive pruning produces a safe-looking, near-always-refuse policy that aggregate and even infeasible-only metrics would score as robust.
  • Uniform, well-documented protocol — same healing data, hyperparameters, and compute for every pruned variant; degradation always measured against the model’s own SFT’d unpruned self.
  • Robustness checks above the genre’s bar: F1 vs accuracy, greedy vs sampling, three seeds, per-instance flipping across the pruning sweep.
  • A reusable taxonomy — action components × task complexity × refusal calibration — that future compression-for-agent papers can adopt directly.
07

Limitations

Where the evidence runs out
  • Qwen-family only — generalization to Llama, Gemma, or Mistral-style architectures is untested, and architecture comparisons are confounded with generation-level training differences.
  • The pruning grid is not factorial: FLAP/2SSP run only on Qwen3-4B and REAP only on the MoE, so method × architecture interactions cannot be estimated.
  • Restricted to smart-home tool calling, with thin strata — HomeBench Medium has just 245 instances; Complex exists only in SHTC, Partially Executable only in HomeBench.
  • The proprietary SHTC dataset reports only relative deltas; no code, prompts, or reproduction package is mentioned.
  • No deployment-cost measurements (latency, throughput, runtime memory) — REAP’s “70% pruning” saves storage, not per-token FLOPs, which the headline framing underplays.
  • All proposed remedies — grounding-aware pruning, failure-targeted healing, refusal calibration — are left as future work.
08

Questions for Further Exploration

Open threads pulled from the paper
  1. Do the specificity-before-intent pattern and the over-refusal cliff replicate beyond Qwen (Llama, Gemma) and beyond smart homes (calendar, enterprise APIs, GUI agents)?
  2. Can a grounding-aware pruning criterion — protecting the layers and neurons behind device resolution and value prediction — measurably delay the specificity cliff?
  3. How much of the MoE safe region survives when expert pruning is combined with reduced active experts per token, i.e. true compute reduction?
  4. Does failure-targeted healing data (distractor-rich device resolution, precise values, refusal calibration) recover more capability per SFT example than the balanced mixture?
  5. Would confidence calibration or constrained decoding at the execute/reject decision point mitigate over-refusal without retraining?
  6. What is the actual runtime Pareto curve — latency, throughput, memory vs accuracy and false-refusal rate — on edge hardware?
