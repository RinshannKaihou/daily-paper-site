Why this matters

First open tool that cycle-accurately simulates Hopper/Blackwell async mechanisms and production Triton/FlashAttention kernels — base infrastructure for kernel-bottleneck analysis and hardware–software co-design.

原文·相关性：对研究 GPU 算子/内核性能瓶颈与软硬件协同设计直接有用，是分析现代加速器内核行为的基础设施级工作。

Critical edge

The PTX-vs-SASS mismatch is patched by a heuristic reordering pass, not solved — and kernels with little latency-hiding slack, exactly the FlashAttention class it targets, are the most sensitive to it (two FA-4 configs swing from >40% to ~6% error).

01Methodology — distilled

Built on GPGPU-Sim's execution-driven core, not from scratch, with a characterization-first loop: each Hopper/Blackwell mechanism gets targeted SASS/PTX microbenchmarks on locked-clock hardware; measured parameters become simulator config entries.

microbench → locked-clock HW → config entry → simulate → vs ncu cycles · clocks: 1.80 / 1.5 / 1.08 GHz
Calibrated mechanism models
TMA transaction queue with per-transaction in-flight tracking (44cy issue gap, 16-txn admission cap, 32 B/cy/SM read limit); mbarrier polling at 42/150cy; all three tensor-core generations (mma.sync, wgmma, tcgen05+TMEM); DSM send budgets from measured contention.
PTX-reordering pass
The simulator interprets PTX while hardware runs SASS; a static dependency-graph reordering re-exposes compiler scheduling overlap. A controlled ablation shows scheduling structure — not instruction count — drives accuracy.
Deterministic multithreading + Triton frontend
Per-SM OpenMP parallelism (per-GPC under clusters) with deterministic crossbar arbitration keeps cycle counts bit-stable across thread counts; Triton hooks capture compiled PTX/CUBIN and reference outputs into replayable harnesses.

03Strengths

  • Closes a real six-year tooling gap — no other public simulator executes TMA / mbarrier / wgmma / tcgen05 / DSM workloads or Triton kernels at cycle level.
  • Calibration rigor is exemplary — exact cycle-precision fits, Little's-Law capacity bounds, architecture-specific asymmetries captured, not papered over.
  • Realistic workloads — DeepBench GEMM, FA-2 benchmark suite, Llama3-8B layers, official FA-2/3/4 CUDA kernels, not toy microbenchmarks.
  • Deterministic 7.86× multithreading makes hour-scale kernel simulation practical without sacrificing reproducibility.
  • Open-source release; every captured Triton kernel auto-checked against reference outputs; reordering ablations included, not hidden.

04Limitations

  • PTX ≠ SASS: reordering is a heuristic whose benefit depends on warp-level latency-hiding slack — the low-slack FlashAttention class is most exposed.
  • Uneven accuracy at the margins: H100 FA-3 8.12% MAPE (10/16 under 10%); case-study max error 13%; INT8 peak modeled at 85.07%; DSM unidirectional bandwidth off ~11–12%.
  • Single-GPU, timing only: no NVLink / multi-GPU collectives, no power/energy model; locked clocks exclude DVFS behavior common in real serving.
  • Re-validation barrier: reproducing the study needs RTX 5090 + H100/H200 + B200 hardware most groups cannot afford.
  • Triton frontend assumptions: one-to-one runtime-argument ↔ PTX-parameter mapping; offline mode cannot autotune.

05Questions for further exploration

Q1

Would an SASS-level execution path close the residual 8.12% H100 FA-3 error, or is it interconnect/L2 contention?

Q2

Can the deterministic multithreading scheme scale to multi-GPU / NVLink simulation, and which arbitration guarantees survive?

Q3

How do the calibrated TMA/mbarrier parameters shift on cut-down or future architectures (RTX Pro Blackwell, Rubin)?

Q4

Do FA-2-async-style decoupling conclusions hold under realistic DVFS throttling rather than locked clocks?

Q5

Can the capture-replay frontend generalize to TorchInductor / TileLang / ThunderKittens without the 1:1 argument-mapping assumption?

Q6

Which calibration knobs (TMA admission cap, DSM budget, TMEM size) is the 5.24% MAPE most fragile to?
