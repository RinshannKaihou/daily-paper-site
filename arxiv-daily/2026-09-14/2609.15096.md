> **一句话总结：** 北京大学团队开源的科研智能体 OpenAI4S 用"代码即动作、科研即会话"的双平面架构（持久 Python/R 内核 + 追加式动作账本 + 版本化工件/检查点）替代逐条工具调用的编排方式，在自建的 36 个科研场景基准（逆合成、分子动力学、蛋白 binder 设计、蛋白突变、催化剂筛选、矿物光谱）上以总体 7.83 分显著超过运行于 Claude Code 通用编码框架内的三个前沿模型基线（5.79–6.36 分），优势集中在长时程、计算密集型工作流，但环境规范与完全可复现性对所有系统（包括其自身）仍是未解难题。

> **TL;DR:** OpenAI4S is an open-source (MIT) scientific research agent that pairs a JSON control plane with persistent Python/R kernels where scientific actions are complete code cells, wrapped in an append-only Action Ledger, versioned artifacts, environment records and workspace checkpoints that make long studies inspectable, resumable and branchable. On its own 36-scenario benchmark (SciCodeBench-OpenAI4S: retrosynthesis, MD, protein binder design, protein mutation, catalyst SAR screening, mineral spectra analysis), scored by a deterministic-first pipeline on accuracy (0.4), workflow completeness (0.35) and reproducibility (0.25), OpenAI4S reaches an overall 7.83/10 vs 5.79 (Kimi-K3), 6.36 (GLM-5.2) and 6.12 (Opus-4.8) — all three baselines run inside the Claude Code harness — a +1.47 margin over the best baseline, growing to +3.68 on molecular dynamics (8.57 vs Opus-4.8's 4.89). The gains come mostly from reliable delivery (final artifact + report in 15/15 MD+binder scenarios vs 0/15, 3/15, 8/15 for the baselines), but the comparison is between unmatched complete systems (OpenAI4S itself runs the cheaper doubao-pro model), and full rerunnability remains weak for every evaluated system.

## 核心贡献

- **双平面执行架构**：单一智能体循环下分两条动作通道——控制平面用提供商原生 JSON 工具调用负责规划、权限、元数据与监控；科学运行时让模型编写**完整代码单元**，在持久 Python 和 R 内核中执行，避免"每个基本操作一次观测边界"的往返开销。
- **Python 单元内同步主机服务调用**：注入的 `host` 单例允许单元格在执行中同步调用 `host.llm`、`host.delegate`、`host.web_search`、`host.save_artifact`、`host.compute`（SSH/BYOC 远程 GPU）、`host.submit_output` 等审计服务，单元格阻塞-恢复式获得结果，中间值无需逐个返回外层模型。
- **科研会话管理**：追加式 Action Ledger 与逐单元执行记录、SHA-256 内容寻址的工件版本、内核代际环境清单、工作区检查点，共同支撑会话检查、分支/回退、带哈希清单的会话包导出（可导出 .ipynb）与"验证式恢复"（重放可重放单元，覆盖率不足时如实报告不完整而非谎称完整恢复）。
- **互补安全层**：可配置 OS 沙箱（macOS Seatbelt / Linux bubblewrap，默认阻断内核裸网络）、权限代理、启发式/LLM 代码预筛查、关键词触发的生物/化学安全轨迹筛查（仅 BLOCK 阻止执行），并附 604 个内置 Skill（43 个精选 + 561 个 MIT 许可 bioSkills）提供可运行代码配方。
- **仓库级科研智能体评测协议**：36 场景 × 6 任务的基准（SciCodeBench-OpenAI4S），三维评分（任务准确性 0.4 / 工作流完整性 0.35 / 可复现性 0.25），全二元判据、确定性检查优先于受限 LLM 评审（AND 合并）、访问扣留数据等硬失败触发 2.0 分封顶； withheld-data 检测器曾因原始字符串匹配产生 17 个误报，后改为语法树检测并统一重评了 155 次系统-场景评估。

## Key Contributions

- **Dual-plane harness**: one outer agent loop routes provider-native JSON control calls (permissions, metadata, services) and, otherwise, one complete Python/R code cell per turn; structured calls take priority over code fences, and there is no registered shell tool — shell execution lives inside kernel workers.
- **Code as the scientific action primitive**: a scientific action is a full code cell in a persistent kernel (lazy-started subprocess with its own namespace), so datasets, fitted models and simulation objects are reused across cells instead of being re-materialized each turn; long jobs go through `host.exec_background` with independent workers, polling and interruption.
- **Synchronous mid-cell host RPC (Python only)**: a `host_call → host_ack → host_response` exchange lets one cell retrieve, delegate to child agents (bounded: 48 concurrent children per node, 1,000 per session, depth 4), register artifacts and submit outputs without returning intermediate values to the outer model; R is a separate analysis channel without this interface.
- **Session-level provenance and bounded recovery**: append-only Action Ledger with per-cell records (source hash, language, generation, status, output, observed files, resource accounting), AST-inferred namespace dependencies with explicit uncertainty flags, content-addressed checkpoints with conflict-aware branch/revert, environment generations with build/verify/activate/rollback, and hashed session packages whose import is quarantined and read-only before activation.
- **Layered safeguards with documented failure behavior**: Seatbelt/bubblewrap sandboxing (auto mode degrades visibly; enforce mode refuses startup), permission broker with durable approvals, heuristic-by-default code screening, keyword-triggered bio/chem trajectory screener (ALLOW/ESCALATE/BLOCK; only BLOCK stops execution), SSRF guards and injection screening on host retrieval.
- **A repository-level evaluation protocol and benchmark**: 36 scenarios across six tasks scored on three weighted dimensions with binary criteria, deterministic checks taking precedence over a constrained zero-temperature LLM judge, and hard-failure caps — released publicly alongside the MIT-licensed system (>6,000 offline tests, PyPI and desktop distributions).

## Methodology

The system is organized around a **scientific computing runtime** rather than a tool catalogue. Figure 3 contrasts the two action granularities: in an atomic tool-use loop every elementary operation costs one model round trip (observation boundary), whereas an OpenAI4S Python cell composes file reads, sub-model calls, delegation, computation and artifact registration in place, blocking on each host RPC and resuming with the result.

Architecturally, a provider-neutral engine (Python stdlib; SQLite for session state; OpenAI Chat/Responses, Anthropic and Gemini adapters; shared by CLI and web workbench) owns `finalize_response` and dispatches both channels through one dispatcher that applies argument decoding, permission checks, approvals, returned-content screening, audit and activity events. Read-only control calls run in bounded parallel waves; mutating or unknown calls form a barrier. The engine's conservative ledger check rejects execution-shaped claims when no cell or tool has run, but one recorded execution is sufficient — it is weaker than the code-output contract enforced in `reusable_pipeline` / `codebase_change` completion modes, where submissions must provide hash-matched source files, entry points, an architecture summary and test evidence tied to an actually successful cell.

Reproducibility machinery is deliberately explicit about its limits: in-memory variables do not survive worker restarts; recovery hydrates durable workspace files and replays eligible cells from a recipe derived from source hashes, execution status, inferred dependencies and environment requirements, validating namespace coverage and artifact hashes before publishing a restored worker and reporting partial/failed outcomes honestly. Input lineage is coverage-dependent (instrumented Python reader/writer wrappers; an optional, default-off live-notebook lineage mode), and static dependency inference is a conservative estimate, not runtime observation.

The **evaluation methodology** defines a task as a general research problem and a scenario as a controlled variation of its core workflow (objective, input modality, method, budget, hard constraint, frozen protocol, or decision criteria) — e.g., all five mineral-spectra scenarios share a preprocessing + library-matching + NNLS-decomposition core, while instrument-mismatch adds blind axis calibration with held-out CV and reaction monitoring adds time-series trajectory analysis and endpoint detection. Each generated repository is scored by a six-stage pipeline (input assembly → static verification → AST workflow extraction → constrained semantic audit → score aggregation → cross-scenario aggregation) in which any failed signal fails its criterion (AND), inapplicable criteria are excluded, and violations such as accessing withheld evaluation data cap the overall score at 2.0. Baselines are the Claude Code general-purpose coding harness driven by three frontier models (Kimi-K3, GLM-5.2, Opus-4.8), against a human-designed GT reference ceiling (8.70).

## Results & Highlights

- **Overall macro score on the 36-scenario benchmark**: OpenAI4S 7.83/10 vs 5.79 (Kimi-K3), 6.36 (GLM-5.2) and 6.12 (Opus-4.8), all baselines inside the Claude Code harness — a **+1.47 margin over the strongest baseline** (GLM-5.2) — with the GT reference ceiling at 8.70.
- **Long-horizon tasks drive the gap**: on Molecular Dynamics (9 scenarios) OpenAI4S scores 8.57 vs the best baseline Opus-4.8 at 4.89 (**+3.68**); on Protein Binder Design 8.46 vs Opus-4.8's 7.58 (+0.88). On short-horizon Retrosynthesis the ranking flips: GLM-5.2 leads 7.62 vs OpenAI4S 7.54 (−0.08).
- **Paired per-scenario analysis (31 of 36 scenarios)**: mean paired differences of **+3.09 vs Kimi-K3 (win/tie/loss 25/3/3), +2.20 vs GLM-5.2 (24/0/7) and +2.54 vs Opus-4.8 (28/1/2)**; only **6.5%** of OpenAI4S scenarios score below 5, vs 61.3% / 45.2% / 51.6% for the three baselines, and empirical survival curves separate at every threshold.
- **Delivery reliability**: across the 15 MD + Protein Binder Design paired scenarios, OpenAI4S produces both a final-artifact manifest and a final report in **15/15 cases vs 0/15 (Kimi-K3), 3/15 (GLM-5.2) and 8/15 (Opus-4.8)**; in the 9 MD scenarios it delivers the final report in 9/9 while baselines frequently contain reporting modules but fail to materialize the report (Kimi 0/9, GLM 3/9, Opus 2/9).
- **Numerical traceability**: in the audited lysozyme protonation-state MD report, **95% of sampled report numbers were traceable to machine-readable evidence**.
- **Robustness and honesty counterexamples**: the ranking is stable under leave-one-task-out analysis with a weakest-task score of 7.01 (catalyst screening); however, in the budget-constrained catalyst-screening scenario OpenAI4S scores **4.4, below all three baselines at 4.9**, because its final package omitted the required report name, figure and dependency declaration despite a completed numerical run; and removing the protein domain shrinks the margin over GLM-5.2 to roughly **0.04 points**, showing the aggregate separation concentrates in long-horizon protein workloads.

## Critical Assessment

- **Novelty**: the individual ingredients — persistent kernels (TaskWeaver), code-as-action (CodeAct), programmatic tool calling, session state — all exist; the contribution is the integration with research-session provenance (append-only ledger, artifact/environment records, checkpoints, verified bounded recovery) applied to scientific workflows. This is honest system engineering rather than a new learning method, and the paper says so ("its contribution is this combination").
- **Rigor of the headline comparison — the central weakness**: this is a complete-system comparison, not a matched-architecture ablation. The baselines run Kimi-K3/GLM-5.2/Opus-4.8 inside Claude Code, while OpenAI4S runs the "more cost-efficient" **doubao-pro** model — so model, harness, prompts, Skills (604 bundled recipes are themselves scientific resources), tools and compute all differ simultaneously, and no causal attribution to any runtime component is possible (the paper concedes this explicitly).
- **Evaluator-designer alignment**: the benchmark and the system come from the same group, and the evaluator rewards exactly the properties OpenAI4S is built to preserve (trajectory retention, intermediate artifacts, bounded claims). Gains in claim calibration may partly reflect explicit instructions to report limitations and execution status — i.e., the agent is being scored on following its own house style. Semantic criteria remain LLM-judge-dependent.
- **Selective coverage in the paired analysis**: the five Protein Mutation scenarios enter the task aggregate but are excluded from scenario-level paired analyses (31/36), and Protein Mutation is one of the tasks where OpenAI4S loses to Kimi-K3 (7.96 vs 8.11).
- **Safety posture is fail-open by design**: a failed or unconfigured screening-model call returns ALLOW; default sandbox mode continues with visible degraded status when confinement cannot be established; ESCALATE is advisory and does not wait for a human. The paper discloses this, but a deployment reader should note the gap between "safeguards present" and "safeguards effective."
- **Reproducibility is not actually solved**: the abstract and discussion state plainly that environment specification and full rerunnability remain weak for every evaluated system, theirs included — in-memory state dies with the worker, recovery only replays eligible cells, and lineage/dependency inference has limited coverage. The 7.83 score is a repository-quality score under their protocol, "not a single measure of physical or biochemical prediction accuracy."
- **Red flags are limited**: no cherry-picked metric hiding — they surface their own losing catalyst scenario (4.4 vs 4.9) with stage-level detail, disclose the 17-false-positive evaluator bug, and pin claims to what the evidence supports. Missing: per-component ablations, matched-model baselines with dedicated scientific harnesses, and compute-cost reporting for the runs.

## Strengths

- Clean architectural thesis (dual plane: JSON orchestration vs persistent code cells) with the observation-boundary argument articulated precisely, plus fair acknowledgment that programmatic tool calling already enables such composition — the novelty claim is scoped accordingly.
- Provenance treated as a first-class engineering concern: append-only ledger, content-addressed artifacts with producing-cell and environment metadata, hashed session packages with quarantined import, and a recovery runner that reports incomplete coverage instead of overclaiming.
- Evaluation protocol is more defensible than typical LLM-judge scoring: binary criteria, deterministic checks with precedence, zero-temperature constrained judging, hard-failure caps, inapplicable-criteria exclusion, and disclosed evaluator debugging.
- Exceptional self-criticism: concrete counterexamples (losing scenario, ~0.04 margin without the protein domain), explicit capture/recovery limits, and a future-work list (matched-model scientific-harness baselines, portable session packages) that matches the real gaps.
- Fully open stack (MIT, source + PyPI + desktop + benchmark + evaluation pipeline) with >6,000 offline tests and provider-neutral adapters.

## Limitations

- The headline comparison confounds model, harness, Skills, tools and compute; OpenAI4S used doubao-pro while baselines used three frontier models, so the +1.47 overall margin cannot be attributed to the harness design itself without matched-model controlled experiments (acknowledged in the paper).
- The benchmark, evaluator and system are co-designed by the same authors; the scoring dimensions (trajectory retention, artifact preservation, bounded claims) reward OpenAI4S's design choices by construction.
- Scenario-level paired analysis omits the five Protein Mutation scenarios; heavy-compute tasks (MD, binder design, catalyst) emphasize workflow construction and delivery under bounded compute rather than end-to-end physical accuracy.
- Reproducibility remains partial for all systems: no cross-machine environment reconstruction from session packages yet, arbitrary Python/R objects are not serialized on restart, and static dependency inference can include unexecuted branches.
- Safety screening is keyword-triggered with fail-open defaults and advisory ESCALATE; biosecurity identity verification is prompt-level only.
- Aggregate separation depends heavily on the protein domain; on short-horizon tasks (retrosynthesis) the best baseline still leads.

## Questions for Further Exploration

- How much of the +1.47 overall margin survives when OpenAI4S's harness is run with the same frontier models (Kimi-K3, GLM-5.2, Opus-4.8) that drive the Claude Code baselines, or when Claude Code is augmented with the same 604 Skills?
- Which single mechanism — persistent kernels, the synchronous host RPC, the Action Ledger/artifact versions, or the delivery contract — accounts for most of the gain on long-horizon MD and binder workflows, per a component-ablation study?
- Can the verified-recovery recipe be extended to true cross-machine session reconstruction (rebuilding environments and services from the hashed package), and would that raise the reproducibility dimension score above its current weak level for any system?
- Does the LLM-judge portion of the evaluator remain stable when the judge model, prompt template or criterion ordering is varied, given known LLM-as-judge sensitivities?
- Would enabling the default-off independent review-and-repair layer improve scientific task accuracy without inflating unsupported claims, as the authors themselves propose testing?
- How do the fail-open safety defaults (ALLOW on screener failure, advisory ESCALATE, degraded sandbox continuing) behave under adversarial prompt-injection or malicious trajectory conditions, and what is the cost of flipping them fail-closed?
