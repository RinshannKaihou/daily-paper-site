Methodology 04

The object — a proof graph. Each algorithm is cast as a DAG whose nodes are assumptions (A), definitions (D), and theorems (T), ending at the problem statement (P). It only counts if Lean checks every step; a coverage test ties every line of code to a statement in the proof. 89 algorithms formalized (44 eviction, 26 speculative decoding, 19 pruning), their assumptions merged into one pool traceable to each source paper.

Three-stage harness.

  • 1 · Problem ID — mine the field's benchmark + citation network; a human keeps runnable algorithms; an LLM proposes one shared problem statement.
  • 2 · Formalization — one agent writes a proof document from the code (source of truth); a second transcribes it into Lean and proves it. Side product: exactness proofs for 8 published decoders, 5 previously only claimed.
  • 3 · Assumption moves — exactly one relax/strengthen per variant, ideally with a "dial" that recovers the parent; only the impact set is re-proved. Variants must be novel and parent-reproducing before any GPU time.

Evaluated on RULER-4K (13 tasks, 6,500 questions; Llama-3.1-8B-Instruct + Qwen3-8B; 2×–64× compression; bootstrap SDs), held-out RULER-8K/16K + LongBench; SparseGPT/Wanda pruning on four LLaMA models (10–50% sparsity); Spec-Bench on dedicated H200s; harness duel at identical model / evaluator / budget, 3 repeats.

Strengths 06

  • Turns design into search over a small, machine-auditable space — every change attributed to one named assumption, Lean-checked before any GPU time.
  • Empirically consequential: two fields pushed past every strong published baseline, with generalization on supersets, longer contexts, another dataset, and more models than the search saw.
  • The mutant study (Lean 100% vs benchmark 53.6%) is a crisp, quantified argument that proof checks catch what scores miss — including bugs that raise scores by silently breaking memory budgets.
  • Competitive with OpenEvolve/AIDE at equal budget, improving more steadily with far lower variance.
  • Exceptional reproducibility documentation: per-method protocols, hardware/checkpoint tables, error-bar derivations, prompt templates, full results for all 89 algorithms.

Limitations 07

  • Lean verifies proofs against the stated problem — not the statement against the field's actual meaning; human contract review remains necessary.
  • Only math-representable properties are provable (memory, sampling exactness — not answer quality); benchmarks stay the sole oracle for the quality-relevant half.
  • Assumption decomposition is LLM-chosen and non-canonical; pool stability across repeated formalizations is unmeasured.
  • Single-seed pruning runs; modest absolute gains; speculative decoding not SOTA (SVIP-LK slower at batch 32).
  • Harness comparison covers one model / parent / benchmark / budget; corpus construction is labor-intensive with no stated public release of code or the Lean corpus.

Questions for further exploration 08

  • Is the assumption pool stable across independent re-formalizations of the same 89 algorithms — would a different decomposition suggest materially different variants?
  • Does AutoAssumption ≈ OpenEvolve > AIDE hold with other backbone LLMs, parents, and larger budgets than 10 evaluated algorithms?
  • Can the method handle statistical contracts (quantization error bounds, provable eviction error floors) where the paper currently relies on benchmarks alone?
  • What would a cross-field "principal assumption" search over the merged pool actually discover, e.g. between eviction and speculative decoding?
  • Would adding calibration-seed variance to the pruning objective change the winner, given the 1.6% margin over Pruner-Zero?
  • Could Lean-checking be ported into code-level harnesses as a cheap pre-GPU filter, combining OpenEvolve's early jumps with assumption-level attribution?
