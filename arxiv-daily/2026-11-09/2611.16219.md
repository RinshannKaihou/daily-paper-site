> **一句话总结：** 针对工作站级 Blackwell（SM120，RTX PRO 5000）只有 warp 级 mxf8f6f4 张量核心、无 tensor memory/双 CTA MMA/集群组播且互联仅为 PCIe 的现实，本文将 GC-MoE 的"调度-计算-合并"单图融合算子重构为 swap-AB（FP4 权重占 A、FP8 激活占 B）的 warp 级块缩放主循环，并配以 MMA 立即数选尺度字节、自适应瓦片几何、去重拉取缓存、位置主序中继拷贝器与融合共享专家等机制，在 8×RTX PRO 5000（PCIe）上对 FlashInfer CuTe DSL W4A8 MegaMoE 平均加速 1.522×、对 Cake MegaMoE 加速 1.387×（18/18 全胜），融合共享专家变体对 Cake 加速 1.388×。

> **TL;DR:** This paper re-engineers the GC-MoE fused dispatch+grouped-GEMM+combine MoE decode operator for consumer/workstation Blackwell (SM120, e.g. RTX PRO 5000) over PCIe, where the only block-scaled tensor-core path is the warp-level `mma.sync.kind::mxf8f6f4` (no tcgen05 tensor memory, no two-CTA MMA, no cluster multicast). A swap-AB mainloop (FP4 weights on the fixed M=64 A operand, FP8 activations on the run-time N extent) plus scale-byte selection via MMA immediates, a compact-weights path, launch-time adaptive tile geometry, a deduplicating 64-bit pull cache, and full-width BF16 returns drained by resident relay copiers yield average speedups of 1.522× over the FlashInfer CuTe DSL W4A8 MegaMoE and 1.387× over Cake MegaMoE across 18 decode points and two model shapes (GLM5.2 and DSV4.1-Flash, 18/18 wins each) on 8×RTX PRO 5000; the fused shared-expert variant averages 1.388× over Cake, with cross-operator cosine agreement ≥ 0.99999976 (94/94 numerical cases pass).

## 核心贡献

- **面向 SM120 的全面重构而非简单移植**：针对 SM120 只有 warp 级 `mma.sync.aligned.kind::mxf8f6f4`（QMMA）、无 tcgen05 tensor memory、无两 CTA 协作 MMA、无集群组播、可分区 SM 预算小、互联为 PCIe 这四大结构性差异，重新推导了 GC-MoE 算子的每一个机制。
- **Swap-AB 块缩放主循环**：FP4 权重占据 QMMA 的 A 操作数（M=64 固定），FP8 激活占据 B（N 为 token 维度、运行时可变），使权重流水线与 token 数量解耦；四条 K32 尺度字节打包在一个 32 位寄存器中，由 MMA 指令的 byte-id 立即数直接选择，彻底消除内层循环中的移位/置换等尺度簿记指令。
- **双 FP4 操作数路径 + 自适应几何**：扩展路径（TMA 期间 FP4→8 位）与紧凑路径（原始 nibble、SMEM 减半、寄存器内用 `ld.shared.u16`+`prmt` 展开）按形状选择；瓦片宽度、流水深度、L1 交接位置（SMEM/全局/共享 32 行块）、寄存器上限均在启动时由路由行数与 SMEM 预算推导，并在图实例化前做驻留检查以防死锁。
- **流式专家粒度调度**：专家最后一行落地即发布；批量 `cp.async.bulk` 拉取引擎保持多路 PCIe 读在飞；按（源 rank, token）键控的 64 位生产者侧拉取缓存在 k≥R 时把同一 token 到多个本地专家的重复激活读取合并为一次 PCIe 读；k<R 时改用打包路由 + 镜像元数据，让计算分区本地读取尺度与路由权重。
- **全宽 BF16 回程与驻留中继拷贝器**：放弃早期 12 位编码方案，直通路径把连续目的行合并为单次 bulk store，中继路径按位置主序 arena 停靠、由常驻拷贝 CTA 以双缓冲 16 KB 传输排空并跟随 FC2 活跃队列，使慢专家不阻塞已完成输出。
- **共享专家折叠进计算角色**：FC1/FC2 编译进角色 2 的前四个 warp，复用路由主循环的动态共享内存，以完成计数器与命名屏障排序——融合共享专家不增加角色、图边或常驻 SMEM。
- **工程健壮性**：PTX 层重写（版本回退、占用指令修正、TensorMap 按值传入参数空间）均带"恰好匹配一次"断言；构建时校验 PTX 仍含 mxf8f6f4 MMA 与 `cp.async.bulk.tensor`，编译器升级破坏假设时立即报错。

## Key Contributions

- **A ground-up SM120 redesign, not a port.** The paper identifies four structural reasons the SM90/SM100 GC-MoE kernel fails on SM120 (warp-level-only block-scaled MMA; per-warp FP4 operand manufacturing; small partitionable SM budget; PCIe fabric where the BF16 return leg is 2× the forward payload) and re-derives the operator around them.
- **Swap-AB block-scaled mainloop.** FP4 weights sit in the QMMA A operand with the invariant M=64 extent; FP8 activations sit in B so the token extent (N) can change at run time without touching the weight pipeline. The four K32 scale bytes live in one packed 32-bit register and are selected by the instruction's byte-id immediates, removing all shift/logic/permute scale bookkeeping from the issue-bound persistent K loop.
- **Two FP4 operand paths and launch-time adaptive geometry.** An expanded path (TMA 4D TensorMap expands FP4→8-bit, 8 KB per K128 step) and a compact path (raw nibbles at 4 KB, expanded in registers via `ld.shared.u16` + `prmt` with explicit SW64 swizzle) are chosen per shape, along with tile tier (16/32/48/64/80/96), pipeline depth, handoff placement (SMEM vs global vs shared 32-row chunks), reserved return CTAs ℓ, and a 16-aligned register ceiling — all validated against a run-time SMEM model with a trap-on-exceed check and a co-residency check before graph instantiation.
- **Streaming, expert-granular dispatch.** Experts are published the instant their last row lands (release-add on per-expert arrive counters); a batched bulk-pull engine keeps several PCIe reads in flight (2 slots per warp); a 64-bit producer-side pull cache keyed by (source rank, token) deduplicates repeated activation reads when k ≥ R, while packed-route arrays and mirrored scale/route-weight metadata remove PCIe reads from the compute partition when k < R. A direct-scan path handles B ≤ 2 where control latency dominates.
- **Full-width BF16 returns with resident relay copiers.** Rather than compressing the 2H-byte return payload, the direct path coalesces runs of consecutive 128-byte destination rows into single `cp.async.bulk` stores, and the relay path parks finished rows in a position-major arena drained by Grelay resident copier CTAs (double-buffered 16 KB transfers, ordered by the FC2 active queue so a slow expert cannot stall completed output).
- **Shared experts folded into the compute role.** FC1/FC2 run on role 2's first four warps against the same dynamic SMEM the routed mainloop later reuses, ordered by per-token-tile completion counters and a named barrier — the fused variant runs the same three kernels with a different argument vector.
- **Reproducible, defensive implementation.** PTX rewrites (version 9.4→9.2 under CUDA 13.2, `.minnctapersm` and register-ceiling corrections, six TensorMaps passed by value as 128-byte param blobs) each assert exactly-one matches, and the build fails loudly if the block-scaled MMA or bulk-tensor instructions disappear from the generated PTX.

## Methodology

The operator executes one MoE layer as three persistent role kernels inside a CUDA Graph spanning two CUDA Green Contexts: role 1 (256 threads, dispatch context on 6 SMs by default) scans routes, pulls peer rows, and publishes experts; role 2 (192 threads = 4 math warps + 1 TMA producer + 1 utility warp, compute context) runs the grouped GEMM1+SwiGLU, GEMM2, return staging/relay, and the fused shared-expert FC1/FC2; role 3 (384/256 threads) combines the k partial sums in FP32 and writes BF16 y. A programmatic-dependency edge releases compute once dispatch CTAs have taken their seats, and all synchronization state lives in a symmetric workspace addressed by monotone epoch counters, so the captured graph replays without any per-layer reset.

The mathematical core is Equation (1)–(3): routed rows per expert r = Bk/L fixes the GEMM tile; per-assignment wire volume v = H + H/32 + 2H makes the BF16 return the dominant term on PCIe; the steady-state layer cost is a max of overlapping pull/GEMM/return terms, which the design minimizes by never letting any term serialize behind a global barrier. The mainloop issues QMMA atoms of m16n8k32, four math warps each owning one M16 slice of the 64-row weight tile, with NQMA = (Nout/8)·⌈r/tile_n⌉·(K/128)·4 instructions per expert tile (Eq. 7). Geometry is a pure, cached function of the launch shape: the SMEM budget model of Eq. (9)–(12) (mainloop + shared-expert double buffer + copier slots, taken as a max because phases never overlap inside a CTA) drives co-residency c ∈ {1,2,4} and the register ceiling Rcap. Implementation is in CuTe DSL with hand-written inline PTX for the QMMA, compiled at run time to sm_120a cubins keyed by toolchain identity, with four asserted PTX rewrites between the DSL and ptxas; child graphs are cached by SHA-256 over arg bytes (including TensorMap blobs), cubin hashes, and (smem, threads, grid) triples so the layer nests inside a larger decode graph.

Evaluation uses 8× NVIDIA RTX PRO 5000 72 GB (SM120) over PCIe, FlashInfer 0.7.3 and ptxas 13.2.78, with GC-MoE 0.6.0. All operators consume identical pre-quantized FP8 (E4M3) activations, MXFP4 weights, and routes, isolating scheduling/arithmetic from accuracy; latency is the max over ranks of each rank's median over 30 timed windows of 100 graph replays each (after 10 warmup windows). Two model shapes are used: GLM5.2 (H=6144, I=2048, 256 routed experts, top-k=8) and DSV4.1-Flash (H=5120, I=2304, 384 experts, top-k=6), at 9 decode batch sizes B=1..256 per rank.

## Results & Highlights

- **Routed decode latency, GLM5.2 (Table 5):** GC-MoE wins all 9 batch points, averaging **1.510× vs the FlashInfer CuTe DSL W4A8 MegaMoE and 1.376× vs Cake MegaMoE**; e.g. at B=128 (1024 tokens) GC-MoE takes **693.87 µs vs CuTe DSL's 1399.12 µs (2.016×) and Cake's 890.66 µs (1.284×)**, and at B=1 (8 tokens) **190.39 µs vs 268.47/320.95 µs (1.410×/1.686×)**.
- **Routed decode latency, DSV4.1-Flash (Table 6):** mean speedup **1.533× over CuTe DSL and 1.398× over Cake**; the B=256 point reaches **2.141× over CuTe DSL (965.46 µs vs 2067.47 µs) and 1.189× over Cake (vs 1147.47 µs)**. Across both models the routed operator averages **1.522× over CuTe DSL (33.34% mean latency reduction) and 1.387× over Cake (26.84%), 18/18 points won** against each baseline.
- **Fused shared-expert variant (Table 7):** average **1.388× over Cake (which also fuses one shared expert), 18/18 wins**, peaking at **1.700× (GLM5.2) and 1.753× (DSV4.1-Flash) at B=1**, falling to 1.051–1.145× at B=256 where the weight stream saturates HBM.
- **Effective bandwidth (Table 8):** the weight stream reaches **1145.1 GB/s per GPU at GLM5.2 B=32 vs Cake's 809.0 and CuTe DSL's 792.7 (1.42×/1.45×)**, and the inter-GPU payload rate at GLM5.2 B=128 is **24.1 GB/s per GPU — 2.0× CuTe DSL's 12.0 and 1.28× Cake's 18.8**; effective throughput at GLM5.2 B=256 is 142.9 TFLOPS/GPU vs Cake's 140.5.
- **Numerical accuracy (Table 9):** **94/94 numerical cases and 752/752 per-rank checks pass** across default, boundary, and asymmetric routing; minimum cosine similarity vs Cake is **0.99999976** (max |GC−Cake| rounds to 0.000000), while both operators show the same 0.976–0.977 cosine vs the dense BF16 reference — the gap is purely the MXFP4/FP8 quantization error, and the SM120 scheduling machinery is numerically invisible.

This is a direct follow-up to GC-MoE on SM90/SM100 (arXiv:2611.04222, cited as [1] and the starting point of the work), which gives the paper a coherent lineage: the same team that built the datacenter operator now documents what changes on the consumer part. The engineering depth is unusually verifiable: exact commit (GC-MoE 0.6.0, commit 141d287), pinned toolchain (FlashInfer 0.7.3, ptxas 13.2.78), environment-variable-controlled configuration, explicit operator constraint table (Appendix A: ranks 1–32, H 512–8192, I 256–4096, E4M3×MXFP4 block-(1,1,32) recipe), and a reproducibility note stating the geometry at each of the 18 points is fully determined by (R, E, k, B, H, I) and device SMEM. ## Critical Assessment

- **Novelty:** Real but incremental-relative-to-lineage. The genuinely new ideas are SM120-specific: the swap-AB orientation that makes the weight tile invariant while the token extent varies, scale-byte selection via MMA immediates (eliminating per-issue shf/prmt in the issue-bound loop), the 64-bit flag-and-pointer-fused pull cache, and folding the shared expert into the compute role's SMEM. Each is a well-motivated response to a named hardware constraint rather than generic tuning. The framing is honest that this is a re-derivation of prior GC-MoE for a new compute capability.
- **Rigor:** Strong on measurement hygiene — identical pre-quantized inputs, weights, and routes for all three operators; latency reported as max-over-ranks of per-rank medians over 30 windows × 100 replays; and the B=256 near-tie with Cake on GLM5.2 (1.017×, 1082.38 vs 1100.85 µs) is analyzed rather than hidden, attributing it to HBM-bound weight streaming (593 vs 583 GB/s) and the cost of stealing copier CTAs from the MMA grid. The claimed separation of "scheduling is numerically invisible" (cosine 0.99999976 vs Cake) from quantization error (0.976 vs BF16 reference) is a well-designed control.
- **Reproducibility:** Mixed. The constraint table, env knobs, and shape-determined geometry are excellent, and the PTX rewrites are asserted and self-checking. But no artifact/code link is provided, the baseline configurations (e.g., Cake "all lsa" mode) are only briefly specified, and the occupancy rewrites are explicitly tied to a specific ptxas behavior (13.2), acknowledged as needing revalidation on compiler upgrades — a fragility the authors admit.
- **Significance:** Niche but real. This is the first (to my reading) detailed treatment of block-scaled FP8×FP4 MoE decode on SM120-class parts over PCIe, a materially different regime from the NVLink/tcgen05 datacenter setting that FlashInfer/DeepGEMM-family kernels target. For workstation multi-GPU serving it is directly useful; for datacenter readers it is mostly of architectural interest.
- **Red flags / weaknesses to note:** (1) The advantage over the stronger baseline (Cake) shrinks monotonically with batch — from 1.69× at B=1 to 1.017× at B=256 on GLM5.2 — so the headline 1.387× average leans on small/mid batches; the authors state this openly. (2) Only two model shapes (GLM5.2, DSV4.1-Flash) and one hardware setup (8×RTX PRO 5000, one default 6-SM dispatch split) are tested; no sweep over the dispatch-SM split or over alternative H/I shapes exercises the adaptive geometry broadly. (3) The 12-bit return codec of the earlier version was dropped without an ablation quantifying the new mechanisms individually — e.g., no isolated measurements of the pull cache, mirrored metadata, or relay copiers, only aggregate payload-rate deltas at two batch points. (4) "Consumer Blackwell" is a slight stretch: the RTX PRO 5000 72 GB is a workstation part; genuinely consumer parts (fewer SMs/VRAM) may not satisfy the ≥32-SM compute-partition constraint. (5) Numerical acceptance thresholds (cosine 0.97) are lenient, though the Cake-agreement metric is the more meaningful check and passes at ~1.0.

## Strengths

- Correctly diagnoses *why* a datacenter Blackwell kernel cannot be ported to SM120 (four concrete structural reasons), and answers each with a mechanism tied to that reason rather than blanket retuning.
- The swap-AB mainloop is an elegant solution to the variable-token-extent problem: the weight TensorMap, SMEM tile, and swizzle stay shape-invariant, so adaptive geometry costs nothing in the weight pipeline.
- The scale-byte-immediate trick removes an entire class of instructions from the innermost loop on an issue-bound path — a textbook micro-architectural optimization with clear before/after reasoning.
- Exceptional engineering honesty: run-time SMEM model with trap-on-exceed, residency checks that reject rather than deadlock, PTX rewrites that assert exactly-one matches, and build-time validation that the block-scaled MMA and bulk-tensor instructions survived codegen.
- The evaluation controls for the right confound (identical quantized inputs and routes) and the accuracy section separates quantization error from operator error via cross-operator cosine agreement.
- Limitations are stated precisely (B=256 GLM5.2 near-tie, hand-derived geometry, ptxas coupling, single-node assumption) with concrete future-work directions attached to each.

## Limitations

- The routed advantage over Cake compresses to 1.02–1.19× at full per-rank capacity (B=256), where every operator becomes HBM-bound on the weight stream and the relay copier CTAs compete with the MMA grid for residency; the authors name this the open problem (a return path that consumes no MMA blocks, or a working-set-surviving weight stream).
- Only two model shapes on one 8-GPU workstation setup; the adaptive geometry's tier boundaries (Eq. 8) are exercised at just a handful of points, and no dispatch-SM-split sensitivity study is included.
- No per-mechanism ablations (pull cache, mirrored metadata, relay vs direct return, compact vs expanded weights are only contrasted through aggregate rate tables at selected batch points).
- Occupancy-critical PTX rewrites are coupled to ptxas 13.2 behavior; a compiler update forces revalidation (asserted, but still a maintenance hazard).
- The design assumes exactly one shared expert, a single-node PCIe fabric (multi-node untested), and the operator constraint range (H ≤ 8192, I ≤ 4096, k ≤ 32) excludes some very large or fine-grained MoE configurations.
- No public code or artifact link in the paper, so third-party reproduction depends on Alibaba releasing GC-MoE 0.6.0.

## Relevance

这篇论文与高效 LLM 推理内核（低精度 MoE decode、FP4/FP8 块缩放 GEMM、通信-计算重叠）方向高度相关：它系统展示了在无 NVLink、无 tcgen05 的工作站 Blackwell 上如何用 warp 级 MMA + Green Context 分区榨取 MoE 层延迟，对多卡工作站部署 MoE 模型（如 GLM、DeepSeek 变体）的工程实践有直接参考价值。

## Questions for Further Exploration

- How much of the 1.387× average over Cake survives on true consumer SM120 parts (e.g., fewer SMs, 16–24 GB VRAM) where the ≥32-SM compute partition and the 256 MB relay arena may not fit?
- What is the isolated contribution of each mechanism (pull cache, mirrored metadata, relay copiers, compact weights, shared-expert fusion)? A per-mechanism latency ablation would substantiate the design narrative.
- Can the return tail be folded into the finalize kernel (the authors' own future work) so no copier CTAs are reserved, and would that recover the B=256 GLM5.2 point currently tied with Cake?
- Would a learned or searched geometry policy beat the hand-derived tiers of Eq. (8), especially for model shapes between the two tested (e.g., H=4096, k=4, uneven E/R)?
- How does the design interact with multi-node fabrics (the untested case), and does the 64-bit pull cache's acyclic-wait argument still hold under uneven expert load across nodes?
- Does the swap-AB mainloop generalize to SM100/SM110 as a lower-occupancy fallback path, or to attention-style workloads where the "token extent" is also dynamic?
