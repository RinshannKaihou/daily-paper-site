Training the 58.36B-active @ 1.2T-total Ultra-128E MoE across 512 B300 GPUs with MXFP8 — 38.1% of the 2,250 TFLOP/s BF16 peak (random-routing reference).

Why this matters

A complete, honest engineering blueprint — FSDP→DDP+EP+PP migration, MXFP8 recipes, and routing-imbalance diagnostics — for anyone training large sparse MoEs.

对大规模稀疏 MoE 训练与真实吞吐评估是高价值参考。

Critical edge

Every headline number uses random routing — up to ~9% optimistic with a learned router — and the co-varying matrix (batch, PP, precision, recompute) permits no single-factor conclusions.

Methodology

  • Two taxes, separated. Costs that scale with total parameters ("capacity tax": weight storage, gradient sync, optimizer updates) are split from sparse-routing execution costs ("runtime tax"); every change is judged by complete-step time at fixed model/batch/topology, never isolated kernel wins.
  • The stack. DDP with resident rank-local partitions (one gradient sync per step) + expert parallelism + pipeline parallelism + a distributed optimizer sharding FP32 main weights across ranks.
  • Rowwise EP. Accepted token rows are written directly into each expert's destination buffer via NVSHMEM one-sided PUT/GET — no permute/unpermute, no host-visible split lists; routing counts never leave the GPU, making the steady-state loop synchronization-free.
  • Kernels & precision. Device-scheduled CUTLASS grouped GEMM executes uneven per-expert shapes without capacity padding; MXFP8 (E4M3 payload + one E8M0 scale per 32 values) transports the exact quantized format grouped GEMM consumes — no BF16 detour.
  • Measurement discipline. CUDA-event timing, Nsight traces, fresh-process repetitions, randomized/balanced execution orders; topology-agnostic checkpoints resume under any parallel layout.

  • Capacity tax eliminated: at fixed ~3.2B active, the legacy FSDP path collapsed ~50.5K → ~19.4K tokens/s/GPU as total experts grew 4.6B→47B, while DDP+EP8 held ~52K — ~2.7× at the 47B point.

  • Recompute trade: transient activation memory −64.0% (40.82 → 14.69 GiB) for −20.95% throughput.
  • Operand values alone change GEMM timing: all-zeros weights −39% vs random BF16 — a real caveat for FP8/MXFP8 kernel benchmarks.
Token Gerrymandering

With λLBL=0.05 the load-balancing loss keeps falling while worst max/mean expert imbalance climbs ~40 → ~46 — the Switch-style LBL is a signed cross-term, not a balance certificate.

Overlap can backfire

Overlapped forward +6.0%; concurrent rowwise communication stretches grouped GEMM by 22.9–27.0% — overlap can slow the overlapped kernels more than it hides.

Strengths

  • Names the capacity tax vs runtime tax framing — a vocabulary for why MoE throughput collapses on dense-oriented infrastructure.
  • Rowwise EP unification: direct placement removes permutation, GPU-resident metadata removes host syncs, one quantized row format flows from transport into grouped GEMM.
  • Token Gerrymandering carries an exact algebraic argument plus a checkpoint-branched experiment — required reading for MoE teams.
  • Exceptional measurement honesty: negative results quantified, best-case readings labeled, random-routing optimism stated (~1% / ~9%).
  • Transferable micro-findings: grouped-GEMM/BMM crossover at 256–512 rows/expert, Spearman ρ = −0.86 between load imbalance and GEMM throughput, ρ≈6 bandwidth argument against CPU activation offload.

Limitations

  • All measurements on B300 NVL8 (8-GPU NVLink domains); NVL72 and other accelerators unmeasured, cross-framework comparisons qualitative.
  • The throughput matrix co-varies batch, PP degree, precision, recompute — not a controlled scaling curve; no "MXFP8 gives X%" conclusion is possible.
  • No time-to-quality results at reported scales — a systems reference throughout.
  • Several claims are single instances: one-rank wave timeline, one-run operand-value table, LR sweeps without seed replication, 9-step 2.38T demonstration.
  • Post-training (SFT/preference/RL) reuse is a design sketch without benchmarks.

Questions for further exploration

  • Does Token Gerrymandering also arise under bias-controller (DeepSeek-V3-style) or expert-choice routing at the 1.2T scale — and can the requested-count histogram be regularized directly?
  • What is the time-to-quality throughput of the Ultra recipe with learned routing — how large is the ~9% gap at 128 experts and PP8?
  • Could SM-partitioned communication kernels (isolated copy engines, dedicated SM carve-outs) flip the overlap result and avoid the 22.9–27.0% concurrent-GEMM slowdown?
  • How does rowwise EP behave inside a 72-GPU NVL72 domain — does the block-oriented DeepEP v2 backend remain necessary?
  • Given up to 39% grouped-GEMM timing change from operand values alone, what benchmarking protocol (value-matched controls, recorded power/clocks) should become standard for FP8/MXFP8 kernels?
  • Does the exact collapse of multiple ungated shared experts into one wider MLP change optimal shared-width allocation under merge-rule initialization?
