> **一句话总结：** Veritas 在普通编码代理外壳（harness）之上加入三个机制——证据头（E）、领域规则库（R，19,603 条规则）、撰写原则（H，9 条）——自动为 agent 任务生成验证器：在 GLM-5.2 固定不变的前提下，其生成验证器与官方判定的一致性（κ*）在全部四个执行评分基准上超过七个主流外壳（τ²-bench 0.787 vs Claude Code 0.726），且三个机制可直接移植到其他外壳并最大提升 Claude Code 在 Terminal-Bench 上 +0.348（0.238→0.586）。

> **TL;DR:** Self-improvement loops are bottlenecked by hand-written verifiers, so the authors build Veritas (OpenCode + an evidence header, a 19,603-entry domain-rule library, and 9 authoring principles) to generate per-task verifiers from the task alone. With the model fixed at GLM-5.2, Veritas beats all seven plain harnesses (Codex CLI, OpenCode, pi, Terminus 2, Hermes, Claude Code, Gemini CLI) on every execution-scored benchmark: κ* 0.787 vs 0.726 (best baseline Claude Code) on τ²-bench (+0.061), 0.720 vs 0.693 (pi) on SWE-bench Verified, 0.465 vs 0.387 (Codex CLI) on Terminal-Bench, 0.548 vs 0.474 on TB-Science; mechanisms transfer unchanged to Claude Code (+0.348 on Terminal-Bench). The trade-off: delivered verifiers are too strict (accept only 45% of Terminal-Bench reference solutions), and the advantage reverses against Codex CLI when running GPT-5.6-sol. Read this if you care about reward hacking, benchmark verifier reliability, or scaling self-improvement loops to verifier-less tasks.

## 核心贡献

- **提出 Veritas，一个专为"生成验证器"而非"完成任务"设计的外壳（harness）。** 针对普通编码代理写验证器的三个结构性失败（看不见判断时的证据、漏掉任务文本未陈述的领域规则、验证器本身无测试可跑），分别加入三个机制：证据头 E、领域规则库 R、撰写原则 H。
- **证据头（E）：** 明确列出验证器在判断时刻能看到的输入（τ²-bench 上是消息列表 + 前后数据库快照），并规定状态比对（E0 vs Ef）优先于轨迹 τ——轨迹最容易被候选伪造。
- **领域规则库（R）：** 挂载在容器固定路径 `/rubric_lib` 的目录树，共 6 个域 19,603 条规则（finance 4,922 / finance-hard 5,085 / legal 4,363 / legal-hard 4,458 来自 PRBench 库半区，airline 77 + banking 698 来自 τ²-bench 训练侧），仅在证据含轨迹时激活，代理只实例化真正适用的规则。
- **撰写原则（H）：** 9 条通用规则，分三组（判什么：可观察的完成而非实现细节；怎么比：最弱比较原则、既反宽松也反严苛；怎么交付：必须写出文件并自检可加载）。其中最弱比较与输出自检两条由 32 轮自改进循环筛出（仅保留 4 处编辑）。
- **系统性实证：** 模型固定、仅换外壳的对照实验证明外壳本身决定验证器质量（τ²-bench 上纯外壳 κ* 从 0.16 到 0.73）；机制可移植且对最弱外壳帮助最大；并给出交付 vs 判断、过严 vs 过宽的失败剖析。
- **对六个基准官方验证器的审计（附录 B）：** 用构造候选实测暴露官方验证器缺陷（如 DeepSWE 106 个任务中 36 个对"金补丁删掉一个 hunk"仍给满分），并以此设计 G1–G5 门控，只把通过认证的官方判定当作 ground truth 标签。

## Key Contributions

- **Veritas, a harness purpose-built for verifier generation.** It diagnoses three structural reasons a plain coding agent writes bad verifiers (it assumes the verifier sees what it sees; it misses obligations that live in domain policy rather than the task text; it cannot test the verifier because no candidates or labels exist yet) and adds one mechanism per failure.
- **Evidence header (E).** States up front what evidence the verifier will receive at judgment time (per-benchmark contract), with derivation rules: state comparison (E0 vs Ef) is the gate when it can witness a requirement and the trajectory cannot overturn it; nothing outside the list may be used; unverifiable requirements are declared unchecked rather than checked by invented criteria.
- **Domain rule library (R).** A deterministic, no-model-in-the-loop directory tree of 19,603 entries across six domains (finance 4,922, finance-hard 5,085, legal 4,363, legal-hard 4,458 from the PRBench library half; airline 77 and banking 698 derived from τ²-bench outside the evaluation split), mounted at `/rubric_lib` and activated only when the evidence includes the trajectory, so only looked-up rules reach the verifier instead of 19,603 entries pasted inline.
- **Authoring principles (H).** Nine benchmark-agnostic rules in three groups (judge observable completion, not implementation; use the weakest comparison that still separates correct from wrong — exact equality forbidden where the task does not demand it; always deliver and self-check the artifact loads). Two of the nine came from a self-improvement loop over the harness itself (32 rounds, 4 edits kept, mechanical check rejecting task-specific edits).
- **A harness-vs-model decomposition study.** With the model fixed (GLM-5.2), plain harness κ* spans 0.16–0.73 on τ²-bench and −0.04 to 0.39 on Terminal-Bench, showing the harness, not just the model, determines verifier quality; the mechanisms transfer unchanged to Codex CLI and Claude Code.
- **Label certification and an official-verifier audit.** Gates G1–G5 (reference accepted, discriminating candidates exist, deleting one check is exposed, contradictions hand-adjudicated, three repeats agree) certify tasks before official verdicts are used as labels; the same constructed candidates expose confirmed defects in the official verifiers of six benchmarks (Appendix B.3).

## Methodology

Veritas formulates verifier generation as: given the task statement T and initial environment E0 (never a reference solution, official tests, labels, or any candidate), write a verifier V that at judgment time reads the benchmark-fixed evidence (trajectory τ, E0, final state Ef, in benchmark-specific combinations; Table 1) and returns PASS/FAIL (or a preference on pairwise benchmarks). The information boundary is enforced by construction — generation code never imports scoring code, and every package records content hashes.

The pipeline has four stages, identical for every harness compared: (1) **Packaging** — one adapter per benchmark builds a container spec; (2) **Generation** — the agent runs inside the task environment on the Harbor framework, whose interface makes the harness pluggable, and must write the verifier to a contract-specified file; (3) **Probe and one repair** — a benchmark-specific probe triggers at most one regeneration if the artifact crashes or accepts a known-wrong candidate (e.g., the untouched initial state); (4) **Delivery** — verdicts are computed later, outside the harness.

The three mechanisms are prompts/materials layered on this substrate (full text in Appendix E): **E** is placed first and constrains every assertion to listed evidence, with state-over-trajectory precedence because "an agent can write 'the booking is canceled' without canceling it, and only the database shows which is true"; **R** tells the agent to browse `/rubric_lib` (README → INDEX.tsv → category files) before writing any trajectory assertion and to annotate instantiated rules with stable IDs; **H** substitutes for the missing tests, capping both leniency (a no-op or fake completion must fail) and strictness (a correct-but-differently-written candidate must pass), plus delivery discipline. A 32-round self-improvement loop (fit/validation splits, edit kept only if validation agreement improves) refined H.

Evaluation uses six benchmarks. Four execution-scored: τ²-bench (58 certified fit/validation tasks, 166 candidates), SWE-bench Verified (138 tasks, 435 candidates), Terminal-Bench 4.0 (33 tasks, 189 candidates), TB-Science 0.1 (39 tasks, 219 candidates) — the two terminal benchmarks were frozen-out, never used for tuning. Two pairwise: LLMBar (75 pairs) and the JudgeBench coding subset (51 pairs), where the harness sees both responses and the verifier is scored only when both orders match the human label. Candidates are constructed: the reference run, the run minus its last database-changing action, the empty run, the gold patch, an empty patch, the gold patch with one line dropped, the oracle script cut short, or one corrupted output file. Agreement is measured by Cohen's κ over certified candidates; the headline κ* replaces every missing verdict (including a verifier that fails to run) with the verdict opposite to the label, so non-delivery is punished like an error. The self-improvement loop's test tasks are held back and the two terminal benchmarks serve as the closest thing to held-out results.

## Results & Highlights

- **Veritas beats all seven plain harnesses on all four execution-scored benchmarks (GLM-5.2, Table 2).** τ²-bench: κ* 0.787 vs 0.726 for the best plain harness (Claude Code), +0.061; SWE-bench Verified: 0.720 vs 0.693 (pi), +0.027; Terminal-Bench: 0.465 vs 0.387 (Codex CLI), +0.078; TB-Science: 0.548 vs 0.474 (OpenCode), +0.074. On the pairwise benchmarks it ties the best on JudgeBench (0.980) and is one pair behind the best on LLMBar (0.920 vs Terminus 2's 0.933).
- **The harness alone moves verifier quality as much as the ranking implies.** With the same model behind every plain harness, κ* ranges from 0.164 (Gemini CLI) to 0.726 (Claude Code) on τ²-bench and from −0.043 (Terminus 2) to 0.387 (Codex CLI) on Terminal-Bench; no plain harness is best everywhere.
- **Ablations confirm each mechanism matters where its target failure occurs (τ²-bench, Table 4).** Full 0.787; removing H collapses to 0.250 — below plain OpenCode's 0.563, because more information without authoring principles makes the agent write more assertions and reject correct candidates; removing R drops to 0.472; removing E to 0.726. On SWE-bench, E matters for delivery: without it κ* falls 0.741→0.579 while candidates without a verdict rise 15→46 and judged-subset κ barely moves (0.807→0.779); R is never activated there since SWE evidence includes no trajectory.
- **The mechanisms are pluggable and help weakest harnesses most (Table 3).** Added unchanged to Codex CLI and Claude Code they improve 5 of 8 execution-scored harness-benchmark pairs (9 of 12 counting Veritas's own 4/4), and none of the other three falls by more than 0.050. Claude Code on Terminal-Bench gains +0.348 (0.238→0.586, becoming the best harness there) and +0.321 on TB-Science (0.144→0.465), largely by delivering verifiers it previously failed to deliver; the τ²-bench gain shrinks from +0.224 on OpenCode to +0.063 on the stronger Codex CLI.
- **The advantage survives model swaps for 2 of 3 other families (Table 5).** Versus each vendor's own harness: with Qwen3.7-Plus, Veritas leads on all four execution benchmarks (Terminal-Bench 0.680 vs Qwen Code 0.508, +0.172); with Gemini 3.5 Flash it also leads on all four (Terminal-Bench 0.533 vs Gemini CLI 0.327, +0.206). With GPT-5.6-sol the order reverses — Codex CLI wins SWE (0.720 vs 0.692), Terminal-Bench (0.311 vs 0.277) and TB-Science (0.540 vs 0.423) — and under Veritas GPT-5.6-sol delivered verifiers for 0 of 47 banking τ²-bench tasks, so τ² is not reported for it.
- **Delivery can matter more than judgment.** On Terminal-Bench, pi has the best judged-subset agreement of any harness (κ 0.671) yet leaves 67 of 189 candidates without a verdict, collapsing its κ* to 0.048; Veritas leaves only 7 candidates without a verdict, against 34–57 for Terminus 2, Gemini CLI, Hermes and Claude Code.
- **Generated verifiers err strict, official verifiers err lenient.** On Terminal-Bench Veritas accepts only 0.45 of reference solutions (false rejection dominates) while rejecting the no-op on 0.97 of tasks; Claude Code with the mechanisms rejects the no-op on every task; on the 89 cut/corrupted candidates its TNR is 0.94 vs 0.89 for Veritas and 0.63–0.91 for plain harnesses. Appendix B.3's audit finds the opposite bias in official verifiers (e.g., DeepSWE gives full marks to the gold-patch-minus-one-hunk on 36 of 106 tasks; MCP-Atlas's shared model judge flips its verdict on identical temperature-zero input on 72 of 500 tasks).
- **The mechanisms add no measurable cost.** On τ²-bench Veritas uses 97.0M prompt + 2.5M completion tokens over 58 tasks vs 104.5M + 2.6M for plain OpenCode (93–94% cache hit rate both). Run-to-run variation: two runs of the same config differ by 0.083 κ* for plain Claude Code and 0.040 with E, R, H added.

## Critical Assessment

- **Novelty: solid and well-scoped.** Test/rubric generation exists for code (Otter, SWT-Bench, CodeT) and long-form text, but generating executable verifiers for agent tasks whose evidence is dialogue plus environment state — with no reference solution and no candidate in view — and treating the *harness* (rather than the model) as the object of study is a genuinely fresh framing, cleanly executed.
- **Rigor: careful label hygiene, but statistically thin.** Each configuration is run once (repeats reported for only two configs, with run-to-run κ* spread up to 0.083 — larger than the +0.027 SWE-bench winning margin), and task counts are small (33–138 per benchmark). The τ²-bench and SWE-bench rows are the fit/validation tasks the mechanisms were designed on — the authors admit this and point to the terminal benchmarks as held-out, which is honest but weakens the headline table. κ* punishes non-delivery as an error, which inflates Veritas's margin on delivery-heavy Terminal-Bench; to their credit they also report judged-subset κ and missing-verdict counts.
- **Reproducibility: above average, not complete.** Prompts, contracts, harness versions, gate definitions and rule-library provenance are all in the paper, but there is no stated code or library release, and the G1–G5 certification pipeline plus constructed candidates would need reimplementation.
- **Significance: real but preliminary for its stated goal.** The paper motivates Veritas with self-improvement loops, yet never tests the generated verifiers *inside* such a loop (deferred to future work); the delivered verifiers accept only 45% of Terminal-Bench reference solutions, so plugging them in today would likely throttle a loop with false rejections. The transfer results are encouraging but uneven: the mechanisms *hurt* Claude Code on τ²-bench (0.726→0.688) and SWE-bench (0.557→0.524), and the whole advantage reverses under GPT-5.6-sol, where Veritas fails to deliver on 47/47 banking tasks — an unexplained failure mode for a paper whose thesis is delivery discipline.
- **Red flags / quirks to note:** the abstract's "9 of 12 harness–benchmark pairs" folds Veritas's own 4/4 into the 5/8 transfer record of the other two harnesses; the self-improvement loop kept only 4 of 32 edits and two of those affect benchmarks (MCP-Atlas, DeepSWE) not scored in Section 4; ground truth is still the official verdicts of verifiers the paper itself shows are defective — a certified-but-imperfect label source, which the authors acknowledge can penalize a correctly stricter generated verifier; and constructed candidates (no-ops, corrupted files, mutilated gold patches) may be easier to classify than real agent attempts.

## Strengths

- One-mechanism-per-failure design with ablations that line up exactly with the diagnosis (H for judgment, E for delivery on SWE, R for unstated domain rules on τ²-bench).
- The G1–G5 certification gates convert "trust the official verifier" into an auditable protocol, and the appendix audit of six benchmarks' official verifiers is valuable independent contribution (e.g., DeepSWE 36/106 hunk-removal leniency, MCP-Atlas judge nondeterminism on 72/500 tasks).
- Mechanisms are portable, cheap (no token overhead), and help weak harnesses most — a practical recipe rather than a bespoke system.
- The failure analysis goes beyond leaderboard numbers: delivery-vs-judgment decomposition, strict-vs-lenient asymmetry between generated and official verifiers, and four worked case studies with verifier source excerpts.

## Limitations

- Small benchmarks (33–138 tasks), single runs, and run-to-run variation (up to 0.083 κ*) comparable to some winning margins; no significance testing.
- Verifiers are far too strict for production use in a loop (only 45% of Terminal-Bench references accepted), and the loop-integration experiment — the motivating application — is absent.
- Advantage is model-dependent: reversed against Codex CLI under GPT-5.6-sol, with an unexplained 0/47 delivery failure on banking τ²-bench tasks.
- Candidates are synthetic (no-op, truncate, corrupt); real agent attempts may distribute differently. Official verdicts remain the ground truth despite demonstrated official-verifier defects, and benchmark contamination of the underlying model cannot be ruled out.

## Relevance

这篇论文直接命中"Self-Evolving Agents & Automated Research"方向中"automated benchmark and reward design"与 reward hacking 可靠性主题：它把自改进循环的验证器瓶颈变成可自动生成的产物，并系统量化了外壳设计对生成验证器质量的影响。对任何关注 agent 评估可靠性、奖励 hacking 或为无验证器任务构建自改进循环的工作都有直接参考价值。

## Questions for Further Exploration

- Do Veritas-generated verifiers actually improve self-improvement rounds end-to-end — i.e., does higher κ* against (defective) official labels translate into better policy improvement, especially given the 55% false-rejection rate on Terminal-Bench references?
- Why does GPT-5.6-sol fail to deliver on all 47 banking τ²-bench tasks under Veritas while delivering all 11 airline tasks — is the rule library, the contract, or the model's harness-following behavior at fault?
- Can the strictness bias be fixed without sacrificing the no-op rejection rate (0.97) — e.g., weakest-comparison principles applied to state checks, or calibration against generated near-miss candidates?
- How do generated verifiers fare on real agent attempts rather than constructed candidates, where correct-but-unusual solutions are more common?
- Could the G1–G5 certification gates be run cheaply enough to accompany every new benchmark release, given the audit found confirmed defects in 27/82 Agents' Last Exam and 57/146 τ²-bench official verifiers?
- Does the rule-library approach scale to open-ended domains beyond finance/legal/airline/banking, where no expert rubric corpus exists to seed R?
