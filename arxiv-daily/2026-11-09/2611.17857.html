Fuse-All MoE Inference Kernel with Load Balancing on TPUs ↗

Rupeng Liu, Bangsheng Tang, Zongwei Zhou, Chengji Yao, et al. 5 authors · Meta SuperIntelligence Lab (MSL)
Mixture-of-Experts TPUv7 · Ironwood Inference Kernel Load Balancing Pallas FP4 / W4A8
Key Metric — Skewed Prefill, EP16
2.3× → 1.09×

Kernel time vs. balanced-kernel reference under a measured skewed workload — the imbalance penalty drops from +130% to +9%.

Why This Matters

Fusion, FP4 precision, and load balancing co-designed for MoE serving — the “stable destinations, mobile producers” pattern transfers directly to GPU stacks (DeepEP, vLLM, SGLang).

Critical Edge

The headline 12–34.5% serving gain explicitly bundles serving-stack changes — no controlled backend swap isolates what the kernel alone delivers, and ablations remain future work.

Methodology — How It's Built

Written in Pallas, compiled by Mosaic into statically scheduled TPUv7 programs; DMAs are issued ahead of use and gated by completion semaphores — no runtime scheduler in the loop.

  • One launch, five stages: indexed token gather (HBM→VMEM), gate/up matmul, gated activation, down-projection, direct DMA writes to final token-slot rows. Intermediates never touch HBM.
  • Precision: FP4 e2m1 weights (8 per uint32) with FP32 block scales; W4A8 or W4A16 modes; BF16 shared accumulators bound VMEM.
  • Pipelining: circular weight rings (16 resident tiles → 16× fewer weight reads), three rotating send buffers, 16 KiB SMEM metadata windows.
  • Synchronization: four invariants — entry readiness, source lifetime, tail completion, final EP rendezvous — and no periodic cross-rank barriers.
  • Balancing toolbox: row bucketing, hot-expert interleaving, chipmate redistribution (≤1 expert move per chip per call), static placement, preloaded hot-expert copies.
  • Symmetric EP8TP2 decode: experts split across both TensorCores; partials cross the die-to-die bridge with one-tile delayed reduction.
  • Setup: 2×2×2 Ironwood slice; 256-expert, top-8, d=f=4096 FP4 model; Megablox EP16 baseline.

Model quality: all production evaluations passed with no numerical issues observed — reported as production acceptance, not bitwise equivalence.

Strengths
  • Central abstraction — the fixed token-slot output contract decouples where work runs from where results land, so balancing composes with fusion instead of fighting it.
  • Joint optimization of compute, communication, and imbalance, with regime-specific designs for prefill vs. decode.
  • Safety-first systems engineering: buffer-lifetime rules, a four-part sync contract, bounded SMEM windows, receive accounting.
  • Exceptional measurement honesty — kernel / full-layer / serving timings separated; analytic vs. measured numbers labeled.
  • Practical FP4 plumbing: block/global scales, prescale-vs-postscale selection, honest BF16-accumulator tradeoff treatment.
Limitations
  • Ablations planned, not completed — per-mechanism contributions to the prefill recovery and decode gain are unquantified.
  • Serving gain (12–34.5%) bundles serving-stack changes; no kernel-attributed controlled comparison was run.
  • Decode result is a self-comparison — only "up to 21.3%" (no minimum), capped at 512 tokens.
  • Preloaded cross-chip copies: decode-only, disabled by default, cannot split a dominant expert across chips.
  • Configuration under-documented; no code release; a single model shape on a single 8-chip slice.
  • Baseline replicates full input tables per device — excluded upstream all-gather costs are acknowledged as significant.
Questions for Further Exploration
  1. How much of the 12–34.5% serving gain survives a controlled backend swap?
  2. What is the minimum decode-latency reduction across 32–512 tokens — and does EP8TP2 still help at 1–2K verification batches?
  3. Does the BF16 shared accumulator measurably degrade accuracy on long-K accumulations?
  4. What skew parameters define the "measured skewed" workload — and what happens when calibrated hot experts go cold?
  5. Would split-token preloaded copies change the capacity/balance tradeoff for dominant experts?
  6. Can the chipmate planner's cost proxy model the ~24 MiB weight-transfer cost it currently ignores?
