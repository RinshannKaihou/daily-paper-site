> **一句话总结：** Starscream 针对 AMD Instinct GPU 的 chiplet/NUMA 分区模式（CPX+NPS4）提出"正交分片"原则：不再把张量并行简单拉深到更多虚拟 GPU，而是在 GPU 内部沿正交维度新增一层分片——序列维度切分 KV cache 消除复制、二维 GEMM 分片保持算术强度、分层 collective 利用 USR 相对 XGMI 的 10 倍带宽差——在 MI300X 上使 decode 阶段 self-attention 内核最高提速 4 倍、融合 GEMM 提速 1.43 倍（对比 SPX/NPS1 基线），而朴素分片反而因 KV 复制导致 OOM。

> **TL;DR:** AMD 研究团队指出，把 vLLM/Megatron 式的张量并行原样搬到 MI300X 的 CPX/NPS4 分区模式（一块物理 GPU 变 8 个虚拟 GPU、4 个 NUMA 域）会触发 KV cache 复制、GEMM 算术强度坍缩和扁平 all-reduce 三重瓶颈，性能反而低于不分区。Starscream 的解法是层级化正交分片：跨物理 GPU 保持原 TP 维度，GPU 内部沿正交维度切分——注意力按序列长度分片 KV（decode 时只搬 query，其数据量不到注意力总读取量的 0.1%；prefill 时搬 KV，仅为 query all-gather 的 1/16），GEMM 用 RowParallel/ColumnParallel 互换实现二维分片（tile 算术强度翻倍），all-reduce 拆成 USR 上 reduce-scatter/all-gather + XGMI 上对等 XCD all-reduce 三阶段，并用 symmetric memory 把通信融合进计算内核。在 MI300X（Llama3-70B/405B、GPT-OSS-120B，16K–128K 上下文、batch 1–1024）上 self-attention decode 最高提速 4 倍、融合 GEMM 提速 1.43 倍（vs SPX/NPS1），MI355X DPX/NPS2 同样有效；但注意这是内核级数字，端到端收益论文仅定性描述，且 batch 很大时增益收窄至约 1.08 倍。

## 核心贡献

- **正交分片原则（Orthogonal Sharding Principle）**：分区的正确用法不是把现有跨 GPU 分片"拉深"到虚拟 GPU，而是保持每个物理 GPU 上的工作负载与理想分片一致，再在物理 GPU 内部沿一个**正交维度**对虚拟 GPU 分片；该维度按三个权衡点选择——保持核内矩阵形状（高算术强度）、消除内存冗余（KV/参数复制）、利用分层带宽（USR 约 10 倍于 XGMI）最小化跨 die 通信。
- **序列长度分片的注意力**：KV cache 按 token 轮转分布在各 XCD 上而非复制，彻底消除 KV 冗余；decode 阶段选 query all-gather（query+聚合元数据 < 注意力读取数据的 0.1%），prefill 阶段选 KV all-gather（GQA 头比使 KV 体积小 16 倍，仅占 4.4% 数据量），把跨 die 流量从基线的 75% 远程访问降到 5% 以下。
- **二维 GEMM 分片（collective 互换）**：利用 "GEMM→reduce-scatter" 与 "all-gather→GEMM" 可互换的性质，让物理 GPU 用 RowParallelLinear 时 XCD 用 ColumnParallelLinear（或反之），保持 tile 近似方形；例如 FC2 层 K/4×N/2 的 tile 比 K/8×N 的瘦长 tile 算术强度高 2 倍。
- **三阶段分层 all-reduce**：Phase 1 各物理 GPU 内部经 USR 做 reduce-scatter，Phase 2 同位置 XCD 跨物理 GPU 经 XGMI 做 peer-XCD all-reduce（参与者从 64 个虚拟 GPU 降到 8 个物理 GPU），Phase 3 GPU 内经 USR all-gather；两层网络各自跑满峰值带宽。
- **计算-通信融合**：借助 PyTorch symmetric memory，让计算内核直接把输出写到目标 NUMA 分区，消除独立 collective 内核的 HBM 读写、workgroup 批量同步和 kernel launch 三重"税"。
- **系统性瓶颈剖析**：论文先定量给出朴素分片的三重病灶——GQA 模型 8 路分区下 KV cache 复制放大到 8 倍（KV 本身在长上下文下已是参数的 3 倍内存）；64 路分片时每虚拟 GPU 持 K/64×N 瘦矩阵；并行度从 4 到 8 通信量增 2.3 倍、64 路时增 21 倍——并指出 FSDP2 训练存在同样病理。

## Key Contributions

- **Orthogonal sharding principle**: partitioning should not deepen the existing inter-GPU sharding dimension; it should add a new intra-GPU dimension chosen to (1) preserve kernel tile shapes and arithmetic intensity, (2) eliminate memory redundancy (replicated KV caches/parameters), and (3) exploit the two-tier bandwidth hierarchy (on-package USR links are ~10x the bandwidth of inter-GPU XGMI).
- **Sequence-length-sharded attention**: round-robin KV cache placement across XCDs eliminates KV replication entirely; phase-aware data movement all-gathers only the tiny query side during decode (<0.1% of attention's data consumption) and the 16x-smaller KV side during prefill, cutting cross-die traffic from ~75% remote accesses to under 5%.
- **2D GEMM sharding via collective interchange**: substituting "GEMM→reduce-scatter" with "all-gather→GEMM" (RowParallelLinear ↔ ColumnParallelLinear) at the XCD level keeps tiles balanced — e.g., K/4×N/2 tiles with 2x better arithmetic intensity instead of skinny K/8×N shards.
- **Three-phase hierarchical all-reduce**: intra-GPU reduce-scatter over USR → inter-GPU peer-XCD all-reduce over XGMI (8 physical participants instead of 64 virtual ones) → intra-GPU all-gather over USR, so each network tier runs at its own peak bandwidth.
- **Compute-communication fusion**: kernels (GEMMs, attention, RMSNorm) write directly to the destination NUMA region via PyTorch symmetric memory, removing the HBM round-trip, bulk synchronization, and launch overhead of discrete collective kernels.
- **Anatomy of naive sharding failures**: quantifies KV-cache replication (up to 8x on 8-way partitioning; KV already costs 3x parameter memory in long-context serving), communication inflation (2.3x more data movement for 2x more parallelism; 21x at 64-way), and arithmetic-intensity collapse — and shows FSDP2 training suffers the identical pathologies.

## Methodology

The paper first characterizes the MI300X chiplet topology (8 XCDs on 4 IODs, per-XCD L2 slices, shared Infinity Cache per IOD, USR ring between IODs, 5.3 TB/s aggregate HBM3, 192 GB capacity) and its partitioning modes: CPX computes-partitions at XCD granularity into 8 virtual GPUs, NPS4 splits HBM into 4 NUMA domains. In isolation CPX+NPS4 avoids L2-coherence flushes (>20% faster computation, ~3x lower launch latency), but any model exceeding one partition's capacity forces sharding, and current frameworks (vLLM, TensorRT-LLM, PyTorch FSDP, Megatron-LM) treat virtual GPUs as independent devices — naively extending unidimensional TP/SP/FSDP sharding.

Starscream's design keeps inter-physical-GPU sharding untouched and adds an orthogonal intra-GPU dimension, instantiated for TP inference as: (1) self-attention with KV sharded along sequence length across XCDs, choosing query all-gather for decode and KV all-gather for prefill based on which side is smaller; (2) 2D GEMM sharding by interchanging row/column-parallel linear layers at the XCD level; (3) hierarchical collectives that decouple USR and XGMI tiers; (4) compute-communication fusion through symmetric memory so producers write straight into the consumer's NUMA region.

Evaluation uses Triton-based unified-attention kernels on vLLM-v1 and HIP paged-attention on vLLM-v0, Stream-K GEMMs in Triton, on MI300X (CPX/NPS4 vs SPX/NPS1) and MI355X (DPX/NPS2 vs SPX/NPS1). Workloads: decode self-attention for GPT-OSS-120B, Llama3-70B, Llama3-405B across 16K–128K contexts and batch 1–1024, plus 200+ GEMM shapes from SOTA GQA- and MoE-based models. The authors ported the best SPX-tuned kernel configuration to CPX without re-tuning workgroup sizes or flash-attention segmentation, treating results as conservative lower bounds.

## Results & Highlights

- **Self-attention decode speedup (Figure 8A)**: on MI300X in CPX/NPS4, Starscream's sequence-length sharding reaches **up to 4.0x speedup** for self-attention kernels versus the SPX/NPS1 baseline across GPT-OSS-120B / Llama3-70B / Llama3-405B (contexts 16K–128K, batch 1–1024), while naive sharding in CPX/NPS4 is consistently *slower* than SPX/NPS1 and hits out-of-memory (red × markers) at batch sizes where both SPX/NPS1 and Starscream still run — KV-cache replication on 8-way partitioning amplifies KV memory (already 3x parameters in long context) up to 8x.
- **Fused GEMM speedup (Figure 9)**: GEMMs fused with intra-GPU collectives via inter-XCD peer-mapping deliver **1.43x** faster execution than SPX/NPS1 GEMMs on MI300X (CPX/NPS4), with consistent gains on MI355X in DPX/NPS2 across 200+ GEMM shapes; the 2D-sharded (collective-interchanged) variants beat their own 1D counterparts purely from better tile shapes.
- **Batch-size regimes (Figure 10, Llama3-405B FC2, all-gather+GEMM)**: up to **1.41x speedup** at low-latency batch 1–16, narrowing to **~1.08x** for throughput batches 32–2048, and diminishing beyond batch 2048 where FP16 working sets exceed per-XCD L2 capacity on MI300X.
- **Cross-die traffic reduction (Llama3-405B, 128K context, 64 virtual GPUs)**: during decode, query heads + aggregation metadata account for **<0.1%** of data consumed by attention; during prefill, KV all-gather is only **4.4%** of total data — a **16x** reduction versus query all-gather — and cross-die traffic drops from ~75% remote memory accesses in SPX/NPS1 to **under 5%**.
- **Partitioning-isolation context**: flat all-reduce cost grows with degree — doubling P from 4 to 8 raises per-GPU movement from 3·M·N to 7·M·N elements (2.3x for 2x parallelism), and 64-way sharding exchanges with 63 peers, i.e., **21x** more communication than the 4-GPU baseline; hierarchical collectives cut the XGMI all-reduce scope from 64 virtual to 8 physical participants.

## Authors & Credibility

All three authors (Sumanth Gudaparthi and Smeet Chheda as equal contributors, with Ganesh Dasika) are at AMD Research and Advanced Development — the vendor that builds the evaluated hardware, giving them deep access to MI300X/MI355X partitioning modes and ARC tooling. The work cites AMD's own partitioning white papers for the 10x USR/XGMI bandwidth ratio and >20% compute-time overhead claims, and one author (Gudaparthi) also appears on the referenced multi-GPU performance-taxes paper (arXiv:2511.02168), indicating an ongoing research program. Implementation is grounded in real, widely-used stacks (vLLM v0/v1 paged attention, Triton, Stream-K GEMMs, PyTorch symmetric memory), and the authors pledge to open-source upon acceptance. As a vendor paper it is naturally AMD-only in scope, but the claims are tied to concrete kernel-level measurements rather than projections.

## Critical Assessment

- **Novelty**: solid but incremental in framing. NUMA-aware hierarchical collectives, sequence-dimension KV sharding, and row/column-parallel interchange are individually known ideas (Ring Attention, DeepSpeed-Ulysses, Helix all shard along sequence/head dimensions over uniform fabrics); the genuine novelty is composing them at the *intra-package* tier that AMD partitioning exposes, and the clean "three tradeoffs" framing that generalizes the recipe. The Helix and Ring/Ulysses positioning is honest — complementary outer layers — but no empirical head-to-head with those baselines is provided.
- **Rigor**: kernel-level evaluation is thorough (3 models, 16K–128K contexts, batch 1–1024, 200+ GEMM shapes, two GPU generations), and the authors transparently flag their conservative setup (no CPX-specific workgroup/segmentation tuning, visible dips at batch 32/64). However, the headline "substantial end-to-end throughput gains" is asserted, not tabulated — no tokens/s end-to-end serving numbers, no TTFT/TPOT latency breakdown, and no accuracy/numerical-equivalence verification of the restructured collectives appears in the text.
- **Reproducibility**: medium. Code is only promised "upon acceptance" at submission time, and the results depend on AMD-internal knowledge of partitioning modes; the naive-sharding baseline is the community frameworks' default behavior, which is a fair choice, but there is no comparison against, e.g., RCCL's own CPX tuner or a tuned TensorRT-LLM-class engine in the partitioned setting.
- **Significance**: the "up to 4x" is a best-case small-batch regime where SPX hotspotting is worst; by the authors' own Figure 10 the GEMM advantage shrinks to ~1.08x in the throughput regime that actually matters for serving economics, and attention gains also narrow at large batch. The geomean speedups are shown in Figure 1B/8A but never quantified in the text — the 4x headline should be read accordingly.
- **Red flags**: FSDP2 training pathology is analyzed persuasively (Section III-E) but never implemented or measured — training claims are extrapolation. The MI355X evaluation uses only DPX/NPS2 (2-way), not the aggressive 8-way CPX/NPS4 that motivates the whole design. Vendor authorship plus an AMD-hardware-only evaluation limits evidence for the "generalizes across future architectures" claim.

## Strengths

- Identifies a real and timely systems problem: chiplet NUMA is now a first-class GPU property, and existing LLM frameworks are provably topology-oblivious under partitioning (down to concrete OOM failures from KV replication).
- The orthogonal-sharding principle is genuinely general — it explains *why* naive extension fails and gives a constructive recipe (kernel shape, memory redundancy, communication overhead) applicable to TP, SP, FSDP, and future architectures, rather than a one-off kernel trick.
- Careful phase-aware algorithm selection (query all-gather for decode vs KV all-gather for prefill) grounded in the GQA head-count asymmetry, with quantified data-movement justification (<0.1% vs 4.4%).
- Hierarchical all-reduce is mathematically equivalent to the flat collective, so correctness is by construction; the three-phase decomposition also unlocks ring-topology-specific optimizations inside the package.
- Honest, conservative evaluation methodology explicitly labeled as lower bounds, with both an intra-family ablation (1D vs 2D sharding quadrants in Figure 9) and cross-generation validation on MI355X.

## Limitations

- No end-to-end serving results (throughput, latency SLOs, goodput) — all quantitative evidence is per-kernel; compounding effects are asserted qualitatively.
- Training (FSDP2) and other sharding strategies are analyzed but not implemented or benchmarked; the case study is TP inference only.
- Gains shrink materially at high batch: ~1.08x for GEMMs in the throughput regime and diminishing returns beyond batch 2048 due to per-XCD L2 thrashing in FP16.
- Evaluation confined to AMD Instinct MI300X/MI355X (and MI355X only in 2-way DPX/NPS2); no NVIDIA or other-vendor partitioning comparison, so cross-architecture generality is argued, not shown.
- Code not yet released at submission; CPX-specific kernel tuning explicitly deferred, and per-figure geomean numbers are not stated in text, making precise comparison from the prose alone difficult.

## Relevance

本文直接命中"LLM 高效推理/训练系统 + 新硬件拓扑"的交叉兴趣：它把 AMD MI300X/MI355X 的 chiplet 分区模式当作新的存储/通信层级，重新设计张量并行的 KV 分片、二维 GEMM 分片与分层 collective，对任何关注多 GPU/多 die LLM serving、长上下文 decode 延迟和 NUMA 感知并行策略的工作都是可直接借鉴的工程蓝图。

## Questions for Further Exploration

- What are the end-to-end serving metrics (tokens/s per GPU, TTFT/TPOT at fixed SLOs) for Starscream vs SPX/NPS1 across real workload traces, and how much of the 4x kernel-level attention speedup survives at the full-model level?
- Can the orthogonal-sharding recipe be instantiated for FSDP2 training as the paper suggests (sharding hidden/sequence dimensions to avoid expanding all-gather scope), and what speedup does it deliver on pretraining or fine-tuning workloads?
- How does Starscream compose with outer-layer inter-GPU strategies like Ring Attention, DeepSpeed-Ulysses, or Helix — is there an optimal split of the sequence/head dimensions across the two hierarchy tiers?
- Does the approach extend to MLA (DeepSeek-style) and clustered-head attention (CHAI) where the KV/query size asymmetry differs from GQA, and to FP8/FP4 working sets that change the L2-thrashing batch threshold?
- Would GPU-aware scheduling of virtual GPUs to NCCL/RCCL communication groups (or the RCCL CPX tuner) capture part of the hierarchical-collective gains without custom kernels, and how much of Starscream's advantage is kernel fusion versus topology-aware sharding alone?
- As future GPUs pack more XCDs per package (deeper intra-GPU hierarchies, possibly multi-level USR), does the two-tier decomposition generalize to a recursive N-tier collective, and where does the orchestration overhead start to dominate?
