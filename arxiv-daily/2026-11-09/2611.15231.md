> **一句话总结：** TQIR 将 QTIP 格点量化改造为算法-硬件协同设计：离线格点搜索时直接把候选码字约束在 INT8/INT4 网格上（FP-Encoded INT-Decoding），在线解码器直接输出整数权重供 INT GEMM 使用，配合激活侧 H128 子空间 Hadamard 变换（LLaMA-2-7B 运行时 Hadamard 运算减少 49.5%）和子空间对齐的 128×2 格点平铺，在 TSMC 16nm 上以 0.0509 mm² 实现 307.2 Gweights/s 解码器，面积效率达 Ecco 的 13.93 倍，并让 7B 模型在 76.8 GB/s 带宽下从 FP16 的 5.49 tokens/s 提升到 2-bit 存储的 43.89 tokens/s。

> **TL;DR:** TQIR is an algorithm-hardware co-design that turns QTIP's ultra-low-bit trellis-coded quantization into an edge-ready integer datapath: offline Viterbi search is done in floating point but constrained to candidates exactly reproducible as INT8/INT4 codewords, so the online decoder (TSMC 16nm, 307.2 Gweights/s in 0.0509 mm², 13.93x the normalized area efficiency of Ecco and 1.52x Codeword Decomposition) feeds integer GEMM directly with no FP16 weight reconstruction. Moving the reverse Hadamard transform to the activation side plus an H128 subspace transform cuts LLaMA-2-7B runtime Hadamard ops by 49.5%, and reshaping the 256-weight trellis tile to 128×2 aligns with the subspace boundary, improving S2W4A4 WikiText2 perplexity from 6.196 to 6.134. On LLaMA-2-7B weight-only quantization, S4 INT8 decoding exactly matches QTIP's FP16 reconstruction (5.16 WikiText2) while enabling integer inference; ideal token rate rises from 5.49 (FP16) to 21.94 (S4W8A8, 5.53 ppl) up to 43.89 tokens/s (S2W4A4, 6.60 ppl) under a 76.8 GB/s LPDDR5T model.

## 核心贡献

- **FP 编码、INT 解码（FP-Encoded INT-Decoding）**：离线格点匹配在浮点域进行失真评估，但每个候选码字先被约束（clip + 移位）到 INT8（[−127,127]）或 INT4（[−7,7]）网格上再放大回浮点参与 Viterbi 搜索，因此运行时解码可精确重建整数权重，彻底移除在线 FP16 权重重建与逐权重归一化。
- **激活侧逆 Hadamard 变换 + H128 子空间变换（SHT）**：把逆变换从权重侧搬到激活侧（类似 QuaRot 的做法），既平滑激活离群值又保持权重通路全整数；将隐藏维划分为 128 元独立子空间后，LLaMA-2-7B 每个 Transformer 块的运行时 Hadamard 蝶形对从 540,672 降至 273,280（减少 49.5%），且困惑度与全局变换持平。
- **子空间对齐的格点编码**：发现 QTIP 原始 16×16 格点平铺在子空间划分后只覆盖单个子空间的局部、导致可测的困惑度退化；将其重塑为沿子空间边界的 128×2 平铺（H128 下），S2W4A4 的 WikiText2 困惑度从 6.196 降到 6.134、C4 从 8.041 降到 8.013，而不增加格点维度、比特率或解码复杂度。
- **带宽匹配的硬件实现**：可配置解码器单周期输出 256 个权重，一条数据通路支持 S4W8A8 / S3W4A4 / S2W4A4 三种模式（1MAD 计算码的 LCG 常数用 CSD 移位加实现、模 2³² 用截位实现、尾比特绕回用固定布线实现，无需码本 SRAM）；格式定制版解码器利用相邻比特窗重叠做跨输入公共子表达式消去（CSE）；四蝶形对 H128 单元（0.00127 mm²、2.33 mW）借助输出平稳式调度的 248 周期准备窗口，在 112 周期内完成变换，完全隐藏于 PE 执行之下。
- **解码器-PE-带宽三级速率匹配分析**：在 76.8 GB/s LPDDR5T-9600 下，S4/S3/S2 分别需要 153.6/204.8/307.2 Gweights/s；256 权重/周期 @ 1.2 GHz 恰好同时打满 S2 模式的内存带宽、解码器与 PE 阵列（43.89 tokens/s，利用率 100%）。

## Key Contributions

- **FP-Encoded INT-Decoding**: accuracy-sensitive trellis matching runs offline in floating point, but every Viterbi candidate is first mapped (clip + power-of-two shift) onto the target INT8 [−127,127] or INT4 [−7,7] grid and rescaled for FP distortion evaluation, so the online decoder reproduces integers exactly — eliminating per-weight FP16 reconstruction, normalization, and the FP→INT mismatch of post-decoding quantization. The shared scale s_W = c_b is forwarded once to the GEMM output scaling instead of multiplying every weight.
- **Activation-side reverse Hadamard + H128 Subspace Hadamard Transform (SHT)**: relocating the reverse transform to the activation path (as in QuaRot) preserves a fully integer weight path and smooths activation outliers before quantization; partitioning the hidden dimension into B=128-element subspaces (H'_B = I_{N/B} ⊗ H_B) reduces per-block butterfly pairs on LLaMA-2-7B from 540,672 to 273,280 (49.5% saving) with perplexity matching the global transform.
- **Subspace-aligned trellis encoding**: an identified interaction between subspace rotation and TCQ layout — QTIP's 16×16 tile spans only a slice of each subspace. Reshaping the same 256 weights into a 128×2 tile that follows the subspace boundary improves S2W4A4 WikiText2 perplexity 6.196 → 6.134 and C4 8.041 → 8.013, consistently across H32–H256, with zero change to trellis dimension, bit rate, or the online decoder.
- **Bandwidth-matched hardware**: a configurable 256-weights/cycle decoder covering S4W8A8/S3W4A4/S2W4A4 with one datapath — storage format only changes the bit-window stride, reconstruction format only the final range mapping; the 1MAD LCG constant (a = 34,038,481) is realized in CSD shift-add form, mod 2³² by bit truncation, and tail-biting by fixed wiring (no codebook SRAM, no state controller). Format-customized decoders exploit overlap between adjacent S-bit shift windows via Cross-Input CSE for area gains; a pair-folded 4-butterfly-pair SHT (0.00127 mm², 2.33 mW) hides its 112-cycle latency inside a 248-cycle scheduling window of the output-stationary 16×16 PE array.
- **Decoder–PE–bandwidth rate matching**: under an ideal 76.8 GB/s LPDDR5T-9600 model, S4/S3/S2 storage require 153.6/204.8/307.2 Gweights/s decoded rates; at 1.2 GHz the 256-weights/cycle decoder and PE array simultaneously saturate memory, decoder, and PE for S2 (43.89 tokens/s, 100% utilization; S3/S4 at 67%/50% of worst-case clock).

## Methodology

The work starts from QTIP's trellis-coded quantization with the 1MAD computed code: a 16-bit trellis state window x is pushed through an LCG p(x) = (ax + b) mod 2³² (a = 34,038,481, b = 76,625,530), the four output bytes are summed and mean-centered to u(x) ∈ [−510,510], and QTIP uses u(x)/σ_u as an FP16 codeword. TQIR modifies the candidate generation: for target format b, q_b(x) = clip(u(x)/2^{d_b}, Q_b) with d_b = 2 (INT8) or 6 (INT4), and the FP-domain candidate is w_H,b(x) = c_b·q_b(x), where the power-of-two contraction and restoration approximately cancel so trellis matching still runs in floating point. Viterbi search selects the minimum-distortion path over these integer-reproducible candidates; only 2/3/4-bit transitions are stored.

At runtime the decoder emits W_INT = q_b(x) plus the shared scale s_W = c_b; with activation quantization A_INT and scale s_A, the layer output is Y = s_W·s_A·(W_INT·A_INT), folding both scales into output requantization so the GEMM stays integer. Because weights live in the Hadamard-transformed domain, TQIR moves the reverse transform to the activation side (H applied to activations before quantization) and replaces the global N-point FWHT (N log₂ N ops) with the H128 subspace transform (N log₂ B ops), chosen as the knee point from a block-size sweep (H16 collapses to WikiText2 ppl 2933; H64 saves 56.7% but loses 0.10 ppl; H128 saves 49.5% with zero loss). Trellis sequences are then reshaped so the 256-weight encoding tile aligns with a single 128-element subspace (128×2 for H128).

On the hardware side, the decoder is synthesized in TSMC 16nm (Design Compiler, PrimeTime PX): 256 parallel INT Weight Decoding Units share one 1MAD structure, a format-controlled bitshift-window extractor supplies 256 state windows per cycle (fixed slicing implements tail-biting), and the LCG multiply is hardwired via CSD. Format-customized variants apply Cross-Input CSE: an S-bit format adds only S new bits per decoded weight, so shared low-bit partial products P_i = (A·C_i) mod 2³² are computed once and reused across neighboring lanes. The decoder rate is co-sized with a 16×16 row-wise output-stationary dot-product PE array (256 weights/cycle consumption, no width-conversion buffer) and with the memory: TPS = min(TPS_BW, TPS_dec, TPS_PE). Evaluation covers LLaMA-2-7B and LLaMA-3-family (8B, 3.1-8B, 3.1-8B-Instruct, 3.2-3B) with WikiText2/C4 perplexity, zero-shot tasks (ARC-C/E, BoolQ, WinoGrande), and weight-only comparisons against GPTQ, GPTVQ, QuIP#, AQLM, VPTQ, and QTIP.

## Results & Highlights

- **Decoder area efficiency (TSMC 16nm)**: the configurable decoder delivers 307.2 Gweights/s (256 weights/cycle at 1.2 GHz) in 0.0509 mm² at 53.0 mW — 6034.5 GB/s/mm² of decoded-output bandwidth per 16nm-normalized area, which is 13.93× Ecco (7nm, 3.19 mm², 433.2 GB/s/mm² normalized) and 1.52× Codeword Decomposition (40nm, 3978.1 GB/s/mm² normalized).
- **Integer decoding costs (almost) nothing in quality** (LLaMA-2-7B, weight-only, QTIP global-Hadamard setup, seq len 4096): S4 with INT8 reconstruction exactly matches FP16 reconstruction at WikiText2 ppl 5.16; S3 INT4 is 5.30 vs 5.29 FP16 (Δ0.01); S2 INT4 is 6.03 vs 6.02 (Δ0.01).
- **Weight-only comparison on LLaMA-2-7B WikiText2**: TQIR 4-bit 5.16 vs QTIP 5.17, QuIP# 5.19, AQLM 5.21, GPTQ 5.49; at 3-bit TQIR 5.30 stays near QTIP 5.28 and beats GPTVQ 5.44/QuIP# 5.41/VPTQ 5.43; at 2-bit TQIR 6.01 trails QTIP 5.86 but crushes scalar GPTQ (50.75) and stays comparable to QuIP# 6.19 / VPTQ 6.13 / AQLM 6.64.
- **Hadamard placement matters enormously**: under S2W4A4 with per-channel activation quantization, weight-side transformation catastrophically degrades WikiText2/C4 ppl to 2425/2473, while the proposed activation-side placement reaches 6.484/8.406; with group-wise (g=32) quantization the gap narrows to 6.195 vs 6.270 (WikiText2) and 8.036 vs 8.156 (C4).
- **H128 subspace transform**: cuts LLaMA-2-7B runtime Hadamard butterfly pairs per transformer block by 49.5% (540,672 → 273,280) while matching global-transform perplexity (6.20/8.04 on WikiText2/C4 for S2W4A4); the aligned 128×2 tile then improves this to 6.134/8.013.
- **End-to-end integer-GEMM deployment (WikiText2)**: LLaMA-2-7B FP16 baseline 5.47 → S4W8A8 5.53 (half the weight fetch of W8A8), S3W4A4 5.81 (25% less storage than 4-bit), S2W4A4 6.60; LLaMA-3-8B FP16 6.14 → 6.27 / 7.02 / 8.73; ordering holds across LLaMA-3.1-8B, 3.1-8B-Instruct, and 3.2-3B.
- **Ideal token-rate ceilings (7B model, 76.8 GB/s LPDDR5T-9600)**: FP16 5.49 TPS (14 GB/token) → S4 21.94 TPS (3.5 GB/token, 0.6 GHz) → S3 29.26 TPS (2.625 GB/token, 0.8 GHz) → S2 43.89 TPS (1.75 GB/token, 1.2 GHz), where S2 simultaneously saturates memory bandwidth, decoder, and PE array.
- **CSE trade-off**: format-customized decoders gain 61.2%/8.0%/2.2% area efficiency for S4/S3/S2 but consume more energy per decoded weight (0.324 vs 0.183 pJ/weight for S4; 0.396 vs 0.173 for S2), positioning customization as an area optimization for fixed-format deployment.

## Critical Assessment

- **Novelty**: The individual ingredients are largely recombinations — activation-side Hadamard is standard in QuaRot/SpinQuant-style methods, and trellis coding is QTIP's. The genuinely new pieces are (a) constraining trellis candidates to integer-reproducible grids during offline Viterbi search (elegant, and the Δ0.01 ppl ablation shows it is nearly free), (b) the subspace-aligned tile reshaping insight, and (c) the CSD/CSE hardware realization of 1MAD. As a system co-design, the contribution is real; as an algorithm paper alone it would be incremental.
- **Rigor**: Algorithmic ablations are unusually thorough (decoded-format isolation, Hadamard placement, subspace size sweep H16–H256, tile-shape alignment, configurable-vs-customized hardware, cross-model verification including an instruction-tuned checkpoint). However, the headline token-rate numbers (43.89 TPS) are analytical bandwidth ceilings that explicitly exclude KV-cache, activation, and control traffic — real batch-one decode for 7B at 2k+ context would lose a meaningful fraction to KV reads, so the "8×" FP16→S2 speedup is an upper bound, and the paper says so only in a table caption-level caveat.
- **Reproducibility**: No code release is mentioned; the LCG constants, CSD decomposition, and mode definitions are specified precisely enough to reimplement, and synthesis flows are standard, but the scheduling claims (SHT hidden under the layer schedule) depend on the specific output-stationary array from their prior work, which is not public.
- **Significance**: The comparison against Ecco is somewhat apples-to-oranges — Ecco is variable-rate entropy coding (Huffman) at 7nm normalized to 16nm by quadratic scaling while TQIR is fixed-rate; the authors concede the ratios "characterize decoder-area efficiency rather than complete-accelerator efficiency." Power is also not technology-normalized (53 mW vs Ecco's 4820 mW is not a like-for-like number).
- **Red flags / weak points**: The 2-bit story is weaker than the abstract suggests — TQIR S2 (6.01) loses to QTIP (5.86) weight-only, and the deployed S2W4A4 point degrades badly on newer models (LLaMA-3-8B: 6.14 → 8.73; LLaMA-3.2-3B: 7.82 → 11.09 WikiText2), so the bandwidth-optimal mode is only credible on older/denser models. The zero-shot table (Table VII) is confined to four tasks and shows 2-bit ARC-Challenge dropping from 43.43 to 37.88 — the paper honestly flags this but the perplexity-focused narrative underplays it. Table VIII's quantization baselines are compared in the weight-only FP16-activation QTIP setting rather than the W4A4 deployment setting where activation-quantization interactions bite. No ablation of the H128 + group-32 activation quantizer interaction beyond two granularities, and no long-context or generation-quality evaluation beyond seq 2048/4096 perplexity.

## Strengths

- Clean decoupling of S (storage) / W (weight format) / A (activation format) precisions into three named operating points with one hardware datapath — a practical engineering contribution edge deployments can actually use.
- The FP-Encoded INT-Decoding trick is simple, provably exact at reconstruction, and costs at most 0.01 perplexity — a rare "free lunch" that removes the FP16 weight path entirely.
- Systematic evidence chain: each design choice (integer candidates, transform placement, subspace size B, tile shape) has its own controlled ablation with the mechanism explained (e.g., H16's 2933 ppl from insufficient cross-channel mixing; 16×16 tiles covering only subspace slices).
- The hardware section is concrete and honest about what is measured (synthesis area/power) versus modeled (ideal bandwidth ceilings), including the 50%/67%/100% utilization accounting at the worst-case 1.2 GHz clock.
- Cross-model generalization check (LLaMA-2-7B, LLaMA-3-8B, 3.1-8B, 3.1-8B-Instruct, 3.2-3B) and an instruction-tuned checkpoint, which many quantization papers skip.

## Limitations

- All throughput results are analytical min(bandwidth, decoder, PE) ceilings; no chip, FPGA, or even cycle-accurate full-model simulation validates the 43.89 TPS figure or the SHT latency-hiding claim end-to-end.
- The 2-bit S2W4A4 mode shows steep degradation on LLaMA-3-family models (WikiText2 6.14 → 8.73 on LLaMA-3-8B; 7.82 → 11.09 on LLaMA-3.2-3B) and trails QTIP weight-only at 2 bits (6.01 vs 5.86).
- Evaluation covers only LLaMA-family dense models up to 8B, perplexity at ≤4096 sequence length, and four zero-shot tasks; no MoE, no long-context, no generation-quality or downstream-task evaluation at the deployment operating points.
- Baseline hardware comparisons rely on cross-technology area normalization (quadratic 7nm→16nm for Ecco) and unnormalized power; Ecco's variable-rate entropy coding and Codeword Decompression's 1 weight/cycle solve different problems than fixed-rate 256 weights/cycle.
- Only symmetric activation quantization is considered (per-channel for A8, group-32 for A4); changing decoded-weight precision at runtime requires reloading a re-encoded trellis stream, so the "configurable" decoder is configurable per-deployment rather than dynamically.

## Relevance

这篇论文把超低位格点量化（QTIP）落到边缘端整数推理硬件上，直接命中"低比特 LLM 压缩 × 算法-硬件协同设计"这条主线：对关心 2-4 bit 权重量化、Hadamard 旋转量化（QuaRot/QuIP# 一系）以及带宽受限的 batch-one 自回归解码加速的研究方向高度相关，其"离线浮点搜索 + 在线整数精确重建"的思路对任何面向 INT GEMM 的压缩格式设计都有借鉴价值。

## Questions for Further Exploration

- How much of the ideal 43.89 TPS survives once KV-cache reads, activation traffic, and attention computation are included at realistic context lengths (2k-32k) — does S2W4A4 still beat S3W4A4 end-to-end?
- Can the subspace-aligned trellis idea be extended to mixed subspace sizes (e.g., H256 for outlier-heavy layers, H64 for clean ones) to reclaim some of the S2 quality loss on LLaMA-3 models?
- Does FP-Encoded INT-Decoding transfer to other computed-code families (e.g., QTIP's 3INST) or to additive/vector quantization methods like AQLM and VPTQ, whose codewords are not generated by a deterministic integer recurrence?
- What is the energy/area cost of the full accelerator (decoder + SHT + 16×16 PE array) versus the decoder-only 0.0509 mm² figure, and how does it compare against a fused entropy-decoding datapath like Ecco at the same technology node with normalized power?
- How does group-32 INT4 activation quantization interact with the H128 subspace transform for MoE models or models with stronger activation outliers than LLaMA (e.g., Mistral/Qwen families)?
