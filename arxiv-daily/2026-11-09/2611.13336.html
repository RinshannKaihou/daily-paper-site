A harness built to generate verifiers — not complete tasks — beats all seven plain coding agents on every execution-scored benchmark.

为"生成验证器"而非"完成任务"而生的代理外壳：三个可移植机制（证据头、19,603 条领域规则库、9 条撰写原则）让模型固定不变时，验证器与官方判定的一致性在四个执行评分基准上全面超过七个主流外壳。

Methodology

  • Task framing: given only the task statement T and initial environment E₀ — never a reference solution, tests, or labels — write a verifier that reads benchmark-fixed evidence (trajectory τ, E₀, final state E_f) and returns PASS/FAIL. The boundary is enforced by construction: generation code never imports scoring code; content hashes are recorded.
  • Four-stage pipeline, identical for every harness: Packaging (per-benchmark container spec) → Generation (agent runs in the task environment on Harbor, writes the verifier to a contract file) → Probe + one repair (regenerate once if it crashes or accepts the untouched initial state) → Delivery (verdicts computed outside the harness).
  • E — evidence header: fixes what the verifier sees at judgment time; state comparison (E₀ vs E_f) gates and cannot be overturned by the trajectory — "an agent can write 'the booking is canceled' without canceling it; only the database shows which is true."
  • R — domain rule library: 19,603 rules across 6 domains at /rubric_lib, browsed (README → INDEX.tsv → category files) only when evidence includes the trajectory.
  • H — nine authoring principles: judge observable completion, not implementation; weakest comparison that still separates correct from wrong; always deliver and self-check. Refined by a 32-round self-improvement loop (4 edits kept).
  • Scoring: Cohen's κ over certified candidates; headline κ* counts every missing verdict as an error.

  • The harness alone moves verifier quality: with the model fixed, plain-harness κ* spans 0.164–0.726 on τ²-bench and −0.043–0.387 on Terminal-Bench; no plain harness is best everywhere.
  • Mechanisms are portable: added unchanged to Claude Code → +0.348 on Terminal-Bench (0.238→0.586, becomes the best harness there) and +0.321 on TB-Science.
  • Delivery can matter more than judgment: pi has the best judged-subset κ (0.671) but leaves 67/189 candidates with no verdict → κ* 0.048; Veritas leaves only 7.
  • Strict vs lenient: rejects the no-op on 97% of Terminal-Bench tasks, accepts only 45% of references — while audited official verifiers err lenient (DeepSWE: full marks for gold-patch-minus-one-hunk on 36/106 tasks; MCP-Atlas flips on 72/500).
  • Model swaps: leads with Qwen3.7-Plus and Gemini 3.5 Flash on all four benchmarks; under GPT-5.6-sol the order reverses (0/47 banking tasks delivered).
  • No cost overhead: 97.0M prompt tokens on τ²-bench vs 104.5M for plain OpenCode.

Strengths

  • One-mechanism-per-failure design, with ablations that line up exactly with the diagnosis (H → judgment, E → delivery on SWE, R → unstated domain rules).
  • G1–G5 certification gates turn "trust the official verifier" into an auditable protocol; the six-benchmark official-verifier audit is a valuable independent contribution.
  • Mechanisms are portable, cheap (no token overhead), and help the weakest harnesses most — a practical recipe, not a bespoke system.
  • Failure analysis goes beyond leaderboard numbers: delivery-vs-judgment decomposition, strict-vs-lenient asymmetry, worked case studies with verifier excerpts.

Limitations

  • Small benchmarks (33–138 tasks), single runs; run-to-run spread up to 0.083 κ* — larger than the +0.027 SWE-bench winning margin. No significance testing.
  • Far too strict for production loops (45% reference acceptance); the motivating loop-integration experiment is absent.
  • Advantage is model-dependent: reversed against Codex CLI under GPT-5.6-sol, with an unexplained 0/47 delivery failure on banking τ²-bench tasks.
  • Candidates are synthetic (no-op / truncate / corrupt); official verdicts remain ground truth despite demonstrated defects; contamination can't be ruled out.

Questions for Further Exploration

  • Does higher κ* against (defective) official labels translate into better end-to-end self-improvement?
  • Why does GPT-5.6-sol deliver 0/47 banking τ²-bench tasks but all 11 airline tasks?
  • Can the strictness bias be fixed without sacrificing the 0.97 no-op rejection rate?
  • How do generated verifiers fare on real agent attempts, where correct-but-unusual solutions are common?
  • Could G1–G5 gates run cheaply enough to accompany every benchmark release (audit found defects in 27/82 ALE, 57/146 τ²-bench verifiers)?
  • Does the rule-library approach scale to open-ended domains with no expert rubric corpus to seed R?
