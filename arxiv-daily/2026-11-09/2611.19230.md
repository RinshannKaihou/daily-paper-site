> **一句话总结：** Amazon 的 CompoundingKernel 用"模型外共享归档 + LLM 控制器 + 并行子代理"的演化式搜索，从每个问题的 PyTorch 定义（零参考内核、官方分数不进入搜索）出发，为 SOL-ExecBench（B200）全部 235 道题写出站点验证正确的内核，截至 2026-11-11 在 L1、L2、Quantization 三个公开榜均排名第一，209 道公开题上比基准 PyTorch baseline 几何平均快 4.40×，并发现"可靠测量的速率而非代理数量"才是搜索规模的瓶颈。

> **TL;DR:** A fixed frontier model (Claude Opus 5.5) inside a four-loop agent system evolves GPU kernels for all 235 NVIDIA SOL-ExecBench problems on B200, starting only from each problem's PyTorch definition (no reference kernels, official scores never enter the search). As of 2026-11-11 it holds #1 on the public L1, L2, and Quantization boards, with every problem site-verified correct and a 4.40× geometric-mean speedup over the benchmark's PyTorch baseline on the 209 public-board problems (median 3.78×; L1 4.04×, L2 3.62×, Quantization 9.19×). Against a coded UCB-style tree search on 38 paired problems, the LLM controller won 35 of 38 at equal wall time — but by making 2.4× as many correct attempts, not better per-attempt picks; one warm-restart fix raised fleet evaluation throughput 3.6×, leading to the paper's central lesson: the rate of reliable measurements, not agent count, limits search scale.

## 核心贡献

- **从零到榜一的内核搜索系统**：为 SOL-ExecBench（B200）全部 235 道题（来自 124 个真实模型、3,957 个 workload）写出站点验证正确的内核；截至 2026-11-11 在 L1（SOL 均值 0.823339）、L2（0.819260）、Quantization（0.909670）三个公开榜排名第一，209 道公开题上 89 道单题第一、193 道进前十。
- **严格的信息隔离（"from zero" 指搜索而非模型）**：每次搜索冷启动，只有问题的 PyTorch 定义、形状与数据类型；代理看不到任何参考内核、官方分数、排名或提交结果，奖励只用自测 B200 时间（对官方 baseline 的几何平均加速比）。人只在系统外层决定发什么、何时发。
- **模型外的共享记忆归档**：每题一个 append-only 账本重建的 SQLite 归档，保存每个正确内核及其谱系（父节点边）；只有评估器能为"正确"内核追加节点，代理只读 SQL。控制器可扩展任意节点（不只当前最优），慢内核成为垫脚石——32% 的最终最优内核曾在某步扩展过低于当时最优 0.9× 的父节点。
- **四层嵌套循环架构**：①子代理循环（拿一个父内核+一个方向，编译并在 B200 上计时）→ ②LLM 控制器循环（读归档、选父或开新根、给每个空闲槽写方向）→ ③团队循环（lead/helper 代理在 warm restart 修 harness，归档不丢）→ ④人类外循环（决定发送与算力分配）。上千个代理会话同时运行。
- **模型外的判定与反 reward-hack 机制**：12 道发送前检查（全 workload 正确性、未发布形状与压力输入的鲁棒性、内存安全、精度规则、reward-hack 检查、构建时限、站点彩排、审计等）；搜索过程中自己发现并封禁了"运行时计时选路"这类作弊（Quant/030 为此付出 6% 的本地性能代价），98.4% 的被评估候选是正确的。
- **可量化的系统与搜索设计结论**：warm restart 将构建移出 GPU 锁后吞吐提升 3.6×（锁时间/候选降 71%）；LLM 控制器在等时间内以 2.4× 的正确尝试次数胜过编码 UCB 树（35/38）；强制使用参考资料无 measurable 收益（233 对，比值 0.981）——"更可靠的每小时尝试"胜过"更多指导"。

## Key Contributions

- A complete agent system that went from PyTorch definitions to a site-correct kernel for all 235 SOL-ExecBench problems and simultaneously holds #1 on the L1, L2, and Quantization public boards (as of 2026-11-11), with 4.40× geometric-mean speedup over the benchmark baseline on the 209 public problems.
- A clean information-isolation design: the search loops never see official scores, ranks, or reference kernels; the reward is local geometric-mean speedup over the published baseline times, so leaderboard position cannot leak into learning.
- An external archive as the agents' only shared memory: an append-only ledger per run rebuilt atomically into a read-only SQLite database storing every correct kernel as a tree node with its lineage, timings, profiles, and robustness verdicts; agents hold no state, so warm restarts (harness fixes) never lose progress.
- The "slower kernels as stepping stones" mechanism with evidence: 17% of best paths contain a step at least 10% slower than its parent, and 32% built at some step on a parent below 0.9× the then-best; case studies (Quant/030: a 1.52× CuTe DSL rewrite became the ancestor of 93% of the run's nodes and the path eventually reached 27.36×) show why expanding any archive node, not just the incumbent, pays off.
- Verified-at-scale engineering lessons: moving builds out of the GPU lock raised evaluated candidates/hour 3.6× (lock time per candidate −71%) at ~98% correct share, identifying measurement reliability — not agent count — as the scaling bottleneck; passing parents as files instead of prompt text cut first-prompt context 88–96%.
- Honest negative/null results: mandatory reference docs/skills gave no measured lift (geomean ratio 0.981 over 233 pairs, p ≈ 0.24), and a structural-steering instruction for stuck runs was a screening null (−0.30% to +0.05%) — siding with goal-only prompting over harness-supplied knowledge.

## Methodology

CompoundingKernel runs one evolutionary search per problem, organized as four nested loops. **Loop 1 (child):** each child agent receives one parent kernel (or none, for a fresh root) plus a single direction; it makes one change, compiles, and times the kernel on a dedicated B200 under the benchmark's own harness (10 warm-up + 50 timed iterations, L2 flushed). Correctness is decided by checks outside the model; only correct kernels are appended to the archive, and a child stops at its first correct kernel (cap N = 1). **Loop 2 (controller):** a per-problem LLM controller (Claude Opus 5.5, fixed throughout) re-reads the archive via read-only SQL each round, picks a parent node or opens a new root, and issues one distinct direction per free child slot; it keeps no internal state. **Loop 3 (team):** lead and helper agents monitor the fleet and fix the harness; fixes go live at warm restarts that relaunch agents onto the same run and archive (agents-only relaunch costs minutes). **Loop 4 (humans):** people decide which kernels to send to the public board and when, and from 2026-10-25 allocated child slots by each problem's gap to #1 — but no score, rank, or calibration ever enters the search.

The reward is the geometric-mean speedup of a correct kernel over the benchmark's published baseline times across workloads (the SOL score is shown only as context because it flattens at high speedups). Local pods run with unlocked SM clocks (~1,965 MHz vs. the site's locked 1,500 MHz), so local times read fast; a calibration for humans only corrects for this when choosing sends. Verification is a 12-check gauntlet before any send: per-workload official-tolerance correctness, robustness on unshipped shapes and stress inputs (multi-seed at send time), compute-sanitizer memory checks, precision rules (e.g., emulating fp32 on faster units is allowed; dropping below the declared dtype is not), reward-hack checks, build-time limits, a site rehearsal, a checklist review, and a daily audit of agent shell commands. Comparative evidence comes from paired A/B runs: LLM controller vs. a coded UCB-style tree (same children, no directions, width narrowing 4→2→1), mandatory vs. optional references, structural steering of stuck runs, sibling-design sharing, and engine choice — mostly on pre-final harness versions with one run per arm, with confounds stated.

## Results & Highlights

- **Board standings (SOL-ExecBench, B200, as of 2026-11-11):** #1 on L1 with public SOL mean 0.823339 (vs. #2 at 0.812832), #1 on L2 with 0.819260 (vs. #2 at 0.818372), and #1 on Quantization with 0.909670 (vs. #2 at 0.909664); per-problem, #1 on 89 of 209 entered problems and top-10 on 193. All 235 problems (including FlashInfer-Bench, verified as private rows) have a site-verified correct kernel.
- **Headline speedup:** on the 209 public-board problems, the kernels are **4.40× faster than the benchmark's PyTorch baseline** (geometric mean; median 3.78×; site timing of public rows). Per board: L1 4.04×, L2 3.62×, Quantization 9.19×; 39 problems reach ≥10×, 2 reach ≥100×, and the maximum is L1/094 at 1062×. Against torch.compile (default mode, local timing) the geomean over all 235 is 11.19× (Quantization 30.26×).
- **Controller vs. coded UCB-style tree (Phase 1 harness, 38 paired problems, 24 h per arm):** the LLM controller was better on **35 of 38** problems at equal wall time (geomean best-speedup ratio 1.143, sign-test p ≈ 7×10⁻⁸), but at equal candidate count the tree was better on 23 vs. 15 — the controller's win comes from making **2.4× as many correct attempts** in the same time, not from better per-attempt selection.
- **Fleet throughput:** one warm restart that moved builds out of the GPU lock raised evaluated candidates per hour **3.6×** (matched hours, same GPUs/slots) while GPU-lock time per scored candidate fell 71%; the correct share stayed ~98%, and 98.4% of evaluated candidates were correct overall (as of 2026-11-02). Over a thousand agent sessions ran concurrently.
- **Search dynamics:** in the first 15% of the run's time each board gained 73–85% of its total rise in mean best local SOL (L1 0.747→0.893, L2 0.682→0.899, Quantization 0.835→0.938, FlashInfer 0.750→0.853), and the first 2% of evaluated candidates delivered 81% of the pooled gain; median problem gain was 0.27 local SOL (L1), 0.39 (L2), 0.25 (Quantization).
- **Kernel character:** 214/235 kernels are CUDA C++ (13 CuTe DSL, 6 Triton, 2 mixed), median ~7,000 lines; by source text match 77% name tcgen05 tensor-core instructions, 72% issue TMA copies, 94% contain inline PTX, and none uses Hopper's wgmma — Blackwell-native code rather than library wrappers.
- **Null result on guidance:** making optional references mandatory raised their use 4.3× but the gated/control geomean ratio over 233 pairs was **0.981** (p ≈ 0.24; control ahead on 126 vs. 107); in the final run only 1.19% of child sessions ever opened the team's skill and 0.83% the public wiki.

## Authors & Credibility

The work is by a 12-person Amazon team (correspondence: Qian Qu, quqian@amazon.com); Benoit Dumoulin is a known Amazon ML infrastructure researcher. As an industrial system report backed by a fleet of B200 pods and over a thousand concurrent Claude agent sessions, it has resources far beyond typical academic budgets. Credibility is strengthened by unusually forthright practices: every headline number carries an "as-of" date and an explicit timing basis (site vs. local); board screenshots are archived in an appendix; the benchmark's own authors report that 14.5% of agent submissions elsewhere were rejected reward hacks, and this team documents the reward hacks its own search found (per-shape runtime timing selection on Quant/030, banned at a 6% local cost) and a bug in its own scorer that under-counted workloads. Code (search loop, benchmark interface, checks) and the 235 final kernels are slated for release, though the agent prompts are explicitly not published. The leaderboard results are independently reproducible in the sense that the NVIDIA site scores every public row itself.

## Critical Assessment

- **Novelty:** the components are assembled rather than invented — an archive of programs with parent sampling descends from the Darwin Gödel Machine / AlphaEvolve line, the LLM meta-controller from Hyperagents, and new-roots-on-stall from ForgeKernel (the related-work table itself lists 25 similar systems, several also targeting SOL-ExecBench with B200 fleets, e.g., Cursor × NVIDIA on 27 B200s). The genuine novelty is the integration at scale plus the information isolation (no official scores in the search) and the measured negative results on harness guidance.
- **Rigor of the headline A/B:** the coded UCB-style tree is a somewhat weak comparator — its children get no directions, it waits for whole batches, and its width narrows 4→2→1, leaving slots idle. The authors are honest that the controller wins on attempt rate (2.4×), i.e., largely on slot utilization, not per-pick intelligence; at equal candidate counts the tree actually led 23–15. Readers should treat "LLM controller beats coded tree" as "a full-batch scheduler with LLM-written directions beats this particular narrowing tree," not as evidence of LLM planning superiority.
- **Confounded throughput claim:** the 3.6× evaluated-candidates-per-hour gain bundles several changes shipped in one warm restart ("builds moved out of the lock, shell start to milliseconds, profiling optional, infrastructure validation"), and the authors admit "we have not yet tested the limit directly by varying the number of agents." The mandatory-references A/B also had two confounds cutting against the gated arm (a watchdog bug costing host time; 12.3% vs. 8.2% of children ended by throttling), so a small benefit of guidance is not ruled out.
- **Leaderboard margins are razor-thin and time-stamped:** Quantization #1 is 0.909670 vs. 0.909664 — a margin of 0.000006 — and L2 is 0.819260 vs. 0.818372; the team temporarily lost #1 on L2 and Quantization on 2026-11-07/11-08 and regained it by publishing more rows late on 2026-11-10. The #1 claims are a snapshot of a live contest, not a settled result.
- **"From zero" needs its qualifiers:** the model was pretrained on public code and agents could read CUTLASS headers, the web, and a public wiki; humans steered compute (slot allocation by gap-to-#1) and injected a few approved prompt notes. The isolation of official scores is real, but the framing undersells how much prior knowledge (model pretraining + CUDA ecosystem) is doing.
- **Correctness is tested, not proved:** the paper states formal/SMT tools don't model Blackwell's asynchronous tensor-core ops (tcgen05, TMA, mbarrier; best formal candidate covered ~16% of problems), and robustness checks covered 94.9% of new bests rather than every candidate — 1.8% of checked bests came back NOT_ROBUST. Two public problems still end slower than the baseline (L2/037 at 0.30× partly because review rejected a library fallback; L1/030 at 0.96×), and 21 of 209 are below 1.5×.
- **Reproducibility:** agent prompts are withheld, the compute budget (B200 fleet scale, total API spend) is not quantified, and design tests ran with one run per arm on pre-final harnesses — an academic group cannot easily replicate, and the variance of single-arm comparisons is unknown.

## Strengths

- Delivers a complete, site-verified artifact: correct kernels for all 235 problems and simultaneous #1 on three public boards of an NVIDIA-run benchmark that scores submissions itself — the strongest form of external validation available in this domain.
- The verification engineering is exemplary: 12 layered checks, robustness testing on unshipped shapes, an admitted-and-fixed own-scorer bug, self-caught reward hacks before anything was sent, and a documented preference for robustness over raw speed (dropping a 1.62× L2/077 best for a ~0.48× fallback).
- Publishes negative and self-limiting results (mandatory references: ratio 0.981; structural steering: null; per-attempt selection parity with the tree) with p-values, confounds, and single-run caveats stated — rare honesty for a leaderboard report.
- The stepping-stone analysis (17% of best paths pass through a ≥10% regression; 32% expand a sub-0.9×-of-best parent) is concrete quantitative evidence for keeping full lineages in evolutionary search rather than greedy hill-climbing.
- Clean systems ablations with measured impact: 3.6× throughput from lock restructuring, robustness checks per candidate 0.66→0.27 with 94.9% best coverage, first-prompt context −88–96% from file-based parents.

## Limitations

- All evidence is from one benchmark (SOL-ExecBench on B200), one model (Claude Opus 5.5 in every agent role), and one cold-started final run; transfer to other hardware, benchmarks, or models is untested.
- Correctness rests on statistical testing outside the model, not proof; robustness checks skip most candidates (about 1 in 40 overall), and formal verification was ruled out for Blackwell's async tensor-core instructions.
- Local timing reads ~1.19× fast vs. the site's locked clocks and the host factor varies by kernel, so local reward is only an approximation of official score (e.g., Quant/029's fast local kernel failed the site's 300 s build limit three times).
- Design tests (controller vs. tree, mandatory references, steering) ran once per arm on pre-final harness versions or short screens, with acknowledged confounds (watchdog bug, unequal throttling), so their verdicts may not hold at the final harness or full horizon.
- Compute cost is never quantified (1,000+ concurrent agents plus a B200 fleet for weeks), agent prompts are unpublished, and ranks are volatile snapshots with margins as thin as 6×10⁻⁶ SOL on Quantization; plain GEMM/MLP and full-layer problems remain furthest from the speed-of-light bound (mean SOL 0.766/0.772 vs. 0.909 on Quantization).

## Relevance

对研究"LLM 代理系统 + 演化式程序搜索 + 可靠外部验证"的方向高度相关：它展示了固定前沿模型在严格隔离官方分数的条件下，通过归档式谱系搜索在大规模 GPU 内核优化上达到公开榜第一，并用受控 A/B 证明"每小时可靠测量数"而非代理数量决定扩展上限——这些系统设计与反 reward-hack 经验可直接迁移到其他代码生成与自动科学发现流水线。

## Questions for Further Exploration

- Would the controller-vs-tree result flip or shrink if the tree arm kept slots full (no width narrowing, no batch waiting) and children received coded directions — i.e., how much of the 2.4× attempt-rate advantage is the LLM versus the scheduler?
- What is the true scaling law of gain vs. reliable-measurement rate: does the 3.6× throughput jump translate into a proportional final-SOL gain, and where does the curve saturate?
- Can the archive's lineage statistics (e.g., "share of descendants" of dip nodes) be turned into a predictive parent-selection policy that beats the current LLM controller's choices per attempt, given that per-attempt selection currently only ties the UCB tree?
- How much of the Blackwell-native style (tcgen05/TMA/PTX patterns in 77%/72%/94% of kernels) comes from the base model's pretraining versus the search, and does the pipeline transfer to non-NVIDIA hardware (e.g., TPU, Ascend) where that prior is weaker?
- Since the first 2% of candidates delivered 81% of the pooled gain, is there an early-stopping or budget-reallocation rule that could reach ~95% of final SOL at a small fraction of the compute?
- Can cheaper verification (surrogate correctness models, build-time prediction like the Quant/029 unity-build fix) raise the reliable-measurement rate further without reopening reward-hack holes?
