> **一句话总结：** 本文提出 Obaleth——一个以 MLIR/Triton 插件形式实现的编译器，把 GPU 发起的通信（put/signal/wait）放进与计算相同的内核中间表示，用 Queue IR 在与硬件无关的调度层上自动完成提交批量化、链合并、发布重排、完成时机规划与原子/内存序消除，在 H100 上把 8 字节消息速率做到 NVSHMEM 的 3.3 倍、NCCL GIN 的 4.2 倍，256 GPU all-to-all 快 1.25×/2.3×，每 rank 显存仅 4–22 MiB（库需 266–584 MiB），并在 vLLM 中以 384 行适配器服务 Qwen3-235B（16×B200, EP16），比 DeepEP 快至 1.29×、TPOT 降低 10–24%。

> **TL;DR:** Obaleth is a compiler (MLIR dialects + passes shipped as a Triton plugin, with CUDA/HIP device-library output) that represents GPU-initiated RDMA communication in the kernel IR and specializes the transport code to workload, shapes, and network topology. Against NVSHMEM 3.4.5 and NCCL GIN on H100, it cuts 8 B two-node round trip to 9.98 µs (vs 12.74/13.12 µs), reaches 243 M msg/s at 64 CTAs (3.3× NVSHMEM, 4.2× NCCL GIN), runs 256-GPU all-to-all 1.25×/2.3× faster, and allocates 4–22 MiB/rank vs 266–584 MiB. Integrated in vLLM via a 384-line adapter, it serves Qwen3-235B-A22B (BF16, EP16, 16 B200) 1.15–1.29× faster than DeepEP 2.5.0 with 10–24% lower time-per-output-token, though DeepEP wins from 64 tokens/rank and the TTFT p95 tail is 1.4–2.0× worse.

## 核心贡献

- **把 RDMA 传输纳入编译器 IR**：首次（据作者所知）在编译器中间表示中显式表达 GPU 发起的网络传输。语义层 `put`/`put_inline`/`signal`/`wait` 操作端点（endpoint）与区域（region），经与后端无关的 Queue IR（`post_put`/`post_inline`/`post_signal`/`submit`/`poll`，即"提交与完成的调度"）逐层下降，最终落到 mlx5（ConnectX）、AWS EFA、host-proxy 与 peer-memory（NVLink/xGMI）四类后端，支持 GPU 或 CPU 提交者，覆盖 NVIDIA 与 AMD GPU。
- **库做不到的通信优化**：内核 IR 能看到"调用之后是什么/还有谁在发/缓冲区活多久"这三类事实，由此实现提交批量化（一条链只付一次预留/门铃/完成）、独立链合并（coalescing）、发布重排（所有 payload 排在 signal 前，NIC 只 stall 一次）、issuer 分析（单发射者 ⇒ 免预留原子与等待）、按缓冲区复用距离规划完成轮询（每 k 次迭代才 poll 一次）、epoch 省略等十余个 pass。
- **两级采用模型**：Tier-1 生成 NVSHMEM 风格的即插即用设备库（LLVM bitcode + relocatable archive + 头文件），可被 CUDA/CuTe DSL/Triton 内核直接链接；Tier-2 在自定义 Triton 内核中把通信与计算（如 FP8 量化 + 分发）融合，换取更大优化空间。框架级"模式适配器"只需陈述事实（token 上界、hidden size、top-k、专家布局），无需手写任何通信内核。
- **跨厂商实测**：在 H100（NVLink + 200 Gb/s IB，CPU 辅助门铃）、B200（400 Gb/s ConnectX-7，GPU 直响门铃）与 AMD MI355X（Pollara RoCE，GPU-direct 或 host proxy）上统一跑通，pass 全部作用于 Queue IR、对后端透明。

## Key Contributions

- **RDMA as IR.** Layered MLIR dialects representing GPU-initiated communication inside the same IR as computation: semantic operations (put / put_inline / signal / wait, with tokens for ordering, `wait(t, reuse=P)` for buffer lifetimes), a backend-agnostic Queue IR of submissions and completions, and lowering to mlx5, AWS EFA, host-proxy, and peer-memory backends with GPU and CPU submitters, on NVIDIA and AMD GPUs. Descriptor formats, opcodes, ordering scopes, and completion formats are fixed at compile time; only queue addresses stay runtime data.
- **Library-impossible optimizations, driven by IR facts.** Submission batching collapses a chain to one reservation/doorbell/CQE; coalescing merges independent chains on one endpoint into a single submission; publication ordering rewrites P1 S1 … PK SK into P1…PK S1…SK so the NIC stalls once instead of K times; issuer analysis proves (from an injective endpoint-index function of the program ID) that no reservation atomic or producer wait is needed; completion planning defers polls to the buffer reuse distance; epoch elision turns intermediate signals into same-size no-ops. Framework-pattern passes (valid extents, shape specialization, storage planning, dead-communication removal) exploit facts vLLM already knows.
- **Tiered adoption.** Tier-1: a generated drop-in NVSHMEM-style device library linkable from CUDA, CuTe DSL, and Triton. Tier-2: custom Triton kernels fusing communication with computation (e.g., an FP8 MoE dispatch kernel in ~15 lines). A 384-line vLLM adapter states only the application configuration — no hand-written or hand-tuned communication kernel, unlike DeepEP.
- **Open source**, implemented as an out-of-tree Triton plugin (Triton 3.8.0) whose passes run after TTIR-level optimization and whose planning decisions join Triton's JIT cache key.

## Methodology

Obaleth extends Triton with a builtins module (`obaleth.language`) that emits communication operations into TTIR; its MLIR passes then rewrite these through three levels. (1) Semantic level: operations act on endpoints (a stream of operations between two peers, backed by an RC/SRD queue pair, proxy ring, or peer mapping) and regions (ordinary, not necessarily symmetric allocations). Tokens order operations; a signal ordered after transfers is "strong" and carries visibility, a standalone one is "weak"; guarantees are minimal by design so the compiler has room to reorder, merge, and elide. (2) Queue IR: a backend-agnostic schedule where one submission = one queue reservation + one or more command chains (each closed by its own signal) + one doorbell + at most one completion. Passes query transport capabilities (ordered delivery, remote atomics, inline payloads, aggregate completions) and adapt, so N optimizations over M backends avoid N×M implementations. (3) Backend lowering to Triton loads/stores/atomics plus inline PTX/AMDGCN for memory ordering: mlx5 with WQEs at compile-time-constant offsets and strong signals as remote CAS or fenced writes; EFA (unordered SRD, no remote atomics) retires the payload before posting the epoch; host proxy writes compact 32-byte commands to a host-pinned ring when GPUs cannot ring doorbells; peer memory becomes warp-cooperative 8-byte copies ending in a block barrier instead of a system fence. The evaluation runs on three platforms (Table 6: H100 4/node + 200 Gb/s IB, CPU-assisted doorbells; B200 8/node + 400 Gb/s ConnectX-7, GPU-direct doorbells; MI355X + Pollara RoCEv2), against NCCL 2.31.2/2.32.3 (GIN device API, GDAKI, proxy) and NVSHMEM 3.4.5 (IBRC/IBGDA) each at its best configuration, DeepEP 2.5.0 in the same vLLM build, plus Triton-distributed and NVSHMEM4Py from the DSLs. Timings use `%globaltimer` / CUDA events, medians of five interleaved runs of ≥1000 iterations after 200 warmups, with payload and flag verification; model outputs are validated against an independent FP32 reference before timing.

## Results & Highlights

- **8-byte message rate (H100, point-to-point, 2 nodes):** Tier-2 reaches 243 M msg/s on 64 CTAs — **3.3× NVSHMEM's rate and 4.2× NCCL GIN's** (2.8× NVSHMEM at 16 CTAs), ringing one doorbell per window where the libraries ring one per put. With queue reclamation, streaming reaches 213 M msg/s on 16 queues (vs NVSHMEM's 257 M, which posts from 128–256 threads) and the NIC limit of 256 M msg/s on 64 queues.
- **Round-trip latency:** 9.98 µs for an 8 B two-node round trip vs **12.74 µs (NCCL GIN) and 13.12 µs (NVSHMEM)**; from CuTe DSL/Triton, Tier-1 round trip is 10.8 µs vs 12.7/13.0 µs for the CUDA-called libraries in the same runs. On AMD MI355X (host proxy), 28.3 µs vs 36.6 µs for rocSHMEM GDA at 8 B.
- **All-to-all:** on 256 H100 GPUs, 1.25× faster than NVSHMEM and **2.3× faster than NCCL GIN** (256 B/peer); bus bandwidth at 16 KiB/peer is 1.6× NCCL GIN's and 1.2× NVSHMEM's. On 8 GPUs at 256 B/peer: 1.32× NVSHMEM's packaged collective, 1.52× NCCL GIN. From 64 KiB/peer the exchange becomes NIC-bound and the device APIs converge within 4% (from 1 MiB). On MI355X, 1.24–1.70× rocSHMEM and 2.2–2.5× RCCL on 8/16 GPUs.
- **Resource use:** runtime allocates **4–22 MiB device memory per rank (8–256 GPUs), ≥12× less** than NCCL's 266–426 MiB or NVSHMEM's 584 MiB (512 MiB of which is the mapped symmetric heap); the all-to-all RDMA kernel uses 60 registers/thread vs 128 in library kernels (ping-pong: 62 vs 210–221). From the DSLs, 4 MiB/rank vs 2.1 GiB (NVSHMEM4Py) and 1.6 GiB (Triton-distributed).
- **Pass ablation (Tier-2 streams of 64 B put + signal):** defaults are 8.4× faster than all-switchable-passes-off with one chain and **23.9× with 16 chains**; completion planning gives 76% of the single-chain gain, coalescing + publication ordering give 71% of the 16-chain gain (the 16-chain round drops 43.8 → 4.3 µs via coalescing then publication ordering); with every switchable pass off, Tier-2 still beats NCCL GIN 11.5 vs 14.7 µs at 256 B. On MI355X GPU-direct, the passes make a pipelined 64 B stream 3.8–5.7× faster.
- **vLLM serving, Qwen3-235B-A22B (BF16, EP16, 16 B200, GSM8K requests):** requests answered **1.15–1.29× faster than DeepEP** (e.g., 5.66 vs 7.31 s at 1 req/s); time per output token 10–24% lower (21.9 vs 28.7 ms at 1 req/s; 33.4 vs 37.3 ms at 4 req/s); accuracy comparable (123/124 vs 124/128 correct at 1/4 req/s). On FP8 Qwen3-30B-A3B (4 GPUs, one node): 1.21–1.48× faster; on long GovReport prompts: 1.33× faster. Over three Ling-1T decode steps (EP16), Obaleth's NICs transmit **5.6× fewer packets** and its send/await kernels take 4.3× less GPU time than DeepEP's; storage planning recovers 16 GiB/GPU (45% more KV-cache capacity, within 5% of DeepEP's) and valid extents cut bytes sent by 58%.
- **Where it loses (reported honestly):** DeepEP's kernels are faster from 64 tokens/rank (by up to 1.7×) — the compiled NVLink send programs spill registers from eight tokens; TTFT p95 is 1.4–2.0× worse than DeepEP's; the fused dispatch form of Listing 1 runs at 0.78–0.93× the separate-kernel speed in BF16 (0.44–0.82× with FP8 quantization); NVSHMEM keeps the pure no-completion streaming rate on 16 queues (257 vs 213 M msg/s).

## Authors & Credibility

The four authors come from Koç University, Turkey (Baydamirli, Oktay-affiliation 2 is fal.ai for Ismayilov, Unat) with an industrial connection to fal.ai; Baydamirli and Ismayilov are equal contributors. The group has a track record in exactly this area: DaCe's multi-GPU backend (Baydamirli et al., 2024) and a dissection of GPU-initiated communication costs (arXiv 2610.01380, 2026) whose measured per-call overheads (0.7 µs minimal 8-B path, up to 4.6 µs library issue time, 3.7× system-scope fence cost) directly motivate this paper's passes. This is a preprint (arXiv, 13 Nov 2026, cs.DC), not yet peer-reviewed; experiments ran on the EuroHPC MareNostrum 5 supercomputer and B200/MI355X clusters, with ERC funding acknowledged. The paper is unusually transparent: it pins exact library versions (including using NVSHMEM 3.4.5 on H100 because 3.8.0 is 2.1 µs slower there), reports regimes where baselines win, and discloses AI-assisted implementation/writing (Section 8). Code is on GitHub.

## Critical Assessment

- **Novelty:** Strong and well-positioned. Table 1's landscape is convincing: prior compilers either keep transport opaque (Triton-distributed links NVSHMEM bitcode; CoCoNet/Mercury schedule collectives but delegate transport to NCCL) or are single-node (Iris, TileLink, Mosaic, ParallelKittens). Making the NIC submission/completion schedule itself a compiler IR artifact — with a transport-capability query interface so passes are backend-generic — is the genuinely new part; the claim "no compiler represents GPU-initiated network transport in its IR" survives the related-work sweep (Pallas exposes remote DMA only on TPU).
- **Rigor:** Above average. Median-of-five interleaved runs with ≥1000 iterations, warmup, post-timing payload/flag verification, per-library best configurations, an independent FP32 output reference before timing vLLM, and a proper cumulative + leave-one-out pass ablation that unmasks pass interactions (epoch elision's gain grows from 7% to 2.4× once issuer analysis removes the GPU bottleneck). Baseline treatment is mostly fair: each library runs its best transport and issue width, and the NVSHMEM version pin is justified with measurements.
- **Reproducibility:** Good in principle (open source, Table 6 pins drivers/CUDA/ROCm/Triton/library versions), but the hardware bar is high: conclusions depend on H100 clusters with CPU-assisted doorbells, B200 with GPU-direct doorbells, and MI355X + Pollara NICs, so most readers can only reproduce the vLLM/DSL parts. The paper also omits the GitHub URL itself (just "Code is available on GitHub").
- **Significance:** Real and timely — decode-heavy MoE serving is exactly where small-message latency dominates, and the 16 GiB/GPU storage-planning win plus 5.6× packet reduction matter operationally. But scope claims should be tempered: at ≥64 KiB/peer everything converges (NIC-bound), so the benefit is confined to small/medium messages and latency-bound phases, which the title/abstract do not spell out.
- **Red flags:** (1) The flagship vLLM result uses one EP configuration at request rates that "saturate neither engine," and the authors themselves note two TP8 replicas of Qwen3-235B would serve long reports with 2.4× Obaleth's throughput — i.e., the chosen deployment favors the method. (2) The large-batch regression vs DeepEP (up to 1.7× slower from 64 tokens/rank, register spills from 8 tokens in NVLink send programs) shows the compiled kernels are not yet competitive in the throughput regime, and TTFT p95 is 1.4–2.0× worse — a tail-latency cost buried in prose. (3) Part of the H100 lead over NCCL GIN comes from NCCL's host-forwarded doorbells on that platform (the B200 gap with GPU doorbells shrinks to 1.11–1.16×), so some of the headline 2.3× is deployment-specific. (4) AMD and EFA evaluations are explicitly preliminary ("we leave full AMD and EFA evaluations to future work"), and the host-proxy path on MI355X applies few passes. (5) Aggressive reordering/elision rests on static analysis (issuer analysis asserts its assumed grid extents at runtime — good — but epoch elision making receivers see epochs up to k−1 iterations late is a subtle protocol change integrators must reason about); no formal correctness argument or stress/fault-injection tests are presented.

## Strengths

- First system to put the full GPU-initiated transport path (WQE construction, doorbells, completions, ordering) under compiler control, with a clean separation (semantic ops → Queue IR → backend) that keeps passes portable across mlx5, EFA, proxy, and peer memory, and across NVIDIA and AMD.
- The optimizations are principled and each removes a *measured* library cost (reservation atomics, system-scope fences, per-call completions, per-signal NIC ordering points), with an ablation that quantifies every pass and their interactions.
- Dramatic resource efficiency (4–22 MiB/rank vs 266–584 MiB; 60 vs 128 registers) is a systems win beyond speed, especially for multi-tenant serving.
- The tiered adoption model and the 384-line vLLM pattern adapter lower the integration barrier: existing CUDA/CuTe/Triton kernels can link the generated library without rewrite, and frameworks need only state facts they already know.
- Honest, well-instrumented evaluation: baseline versions pinned and justified, losing regimes reported, outputs validated against an FP32 reference, AI-usage disclosed.

## Limitations

- Benefit is bounded to small/medium messages and latency-bound phases: from 64 KiB/peer all-to-all is NIC-bound and device APIs converge within 4%; DeepEP wins the throughput regime (from 64 tokens/rank, up to 1.7×), with register spills in the compiled NVLink send programs as the identified cause.
- Tail latency: TTFT p95 is 1.4–2.0× worse than DeepEP in the serving experiments; the fused dispatch form is slower than the separate packing kernel (0.78–0.93× BF16, 0.44–0.82× FP8).
- Platform sensitivity: H100 uses CPU-assisted doorbells (kernel-module restriction), and part of the NCCL GIN gap there comes from its host-forwarded doorbells; the B200 GPU-direct comparison shows smaller (1.11–1.16×) gaps.
- Coverage: full AMD (beyond preliminary MI355X two-node results) and EFA evaluations deferred to future work; no training workloads (only serving/inference), no fault-tolerance or congestion stress tests, and no formal correctness proof for the reordering/eliding passes.
- Tier-2's best results require (re)writing kernels in Triton with Obaleth operations — adoption cost for existing CUDA/HIP codebases — and the compiler's specialization joins Triton's JIT cache key, multiplying compiled variants across live shapes.

## Relevance

本文与「LLM/MoE 推理系统与分布式通信优化」方向高度相关：它直接攻击专家并行（EP）dispatch/combine 与解码阶段的小消息延迟瓶颈，并给出 vLLM + Qwen3 的端到端收益与显存节省，是"用编译器替代手写通信库"这一路线的代表性工作。对任何关注 Triton/MLIR 生态、GPU 间通信（NVSHMEM/NCCL/DeepEP）或大规模 MoE 服务效率的人都是必读级参考。

## Questions for Further Exploration

- Can the register-spill problem in compiled NVLink send programs (which lets DeepEP win from 64 tokens/rank) be fixed by layout-aware lowering or a hybrid plan that switches to library-style bulk paths at large batches — and would that close the up-to-1.7× gap without losing the decode advantage?
- Why exactly is TTFT p95 1.4–2.0× worse than DeepEP: is it the shape-specialization recompilation at prefill-sized batches, the capacity-one decode plans, or the dispatch packing kernel split?
- How do the passes behave under real cluster congestion and incast (many senders, one expert-hot rank) — do coalesced batches and deferred completions interact badly with NIC back-pressure or PFC?
- Epoch elision lets receivers observe epochs up to k−1 iterations late: what is the end-to-end impact on consumer kernels that poll flags, and can a receiver-side hint recover opportunistic early consumption?
- The 45%-more-KV-cache storage planning depends on the pattern declaring how expert kernels read inputs — can this be inferred automatically from Triton expert kernels rather than stated by the adapter, and does it survive expert-kernel changes (e.g., TMA-based readers)?
- Does the Queue-IR approach extend to upcoming transports (ULL, CX-9 dynamic-reparse WQEs, HBM-attached NICs) where descriptor costs differ, and can the same machinery generate collective algorithms rather than point-to-point plans?
