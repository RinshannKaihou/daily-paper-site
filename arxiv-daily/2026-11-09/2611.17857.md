> **一句话总结：** Meta 提出 Fuse-All MoE —— 一个用 Pallas 编写的 TPUv7 融合内核，把 token 收集、gate/up 投影、门控激活、down 投影和直接写回全部融合在一次 expert launch 中（中间结果常驻 VMEM），并配合行分桶、热专家交错调度、chipmate 专家重分配、预加载热专家副本与对称 EP8TP2 解码等负载均衡手段；在 2×2×2 Ironwood 切片、256 专家 top-8 的 FP4 模型上，将实测倾斜 prefill 负载的内核耗时从平衡基准的 2.3× 降到 1.09×，解码内核延迟最高降低 21.3%（对比自家融合 EP16），配合 serving 栈优化后整体吞吐比 Megablox EP16 基线提升最高 34.5%。

> **TL;DR:** Meta SuperIntelligence Lab presents Fuse-All MoE, a Pallas kernel for TPUv7 (Ironwood) that fuses token collection, both expert projections, gated activation, and direct token-slot output writes into one launch (intermediates stay in VMEM, FP4 weights with W4A8/W4A16 arithmetic), wrapped in a stable output contract that lets scheduling and expert placement move without changing routing semantics. On a 2×2×2 slice with a 256-expert, top-8, d=f=4096 FP4 model, imbalance handling cuts a measured skewed EP16 prefill workload from 2.3× to 1.09× of the balanced-kernel reference time; symmetric EP8TP2 decode reduces kernel latency by up to 21.3% vs. their own fused EP16 across 32–512 tokens; and the integrated system improves serving throughput by 12–34.5% over the Megablox EP16 baseline (gains include serving-stack changes, not the kernel alone). Worth reading for the co-design of fusion, ownership, and load balancing — but note the ablations are listed as future work and the kernel-vs-stack attribution is not isolated.

## 核心贡献

- **全融合 expert 计算管线**：把索引式 token 收集（HBM 直读入 VMEM）、gate/up 矩阵乘、门控激活、down 投影和最终目的地址直写合并为一次 expert launch，消除了 HBM 中的分组激活中间张量、独立激活内核和接收端 scatter-add 重分发缓冲。
- **稳定的 token-slot 输出契约**：输出目的地由 token 所属 rank 和路由槽位决定（与哪个设备执行该专家无关），因此调度顺序和专家放置可以自由变化而不破坏路由语义；每个 (token, slot) 恰好有一个生产者，直写无需辅助接收缓冲。
- **一套互补的负载均衡机制**：行分桶（选最小可覆盖有效行的预编译桶以减少 padding 计算）、热专家交错调度（用长计算掩盖其他专家的权重加载）、目的地交错（平滑输出流量突发）、chipmate 专家重分配（每芯片对每次调用最多移动一个专家）、静态放置（按观测负载置换 checkpoint 列）、预加载热专家副本（跨芯片、home-or-holder 决策）。
- **对称 EP8TP2 解码变体**：把每个芯片拥有的专家按 N 维（W1）/ K 维（W2）切分到两个 TensorCore，部分和经片内 die-to-die bridge 交换后延迟归约，缓解解码时"激活专家数主导成本"的芯片内不均衡。
- **低精度与流水线工程**：FP4 e2m1 权重（每 uint32 打包 8 个）+ FP32 块尺度，W4A8/W4A16 双模式；VMEM 循环权重环（同专家连续 16 个 tile 全驻留可减少 16 倍权重读取）、3 个轮转发送缓冲、有界 SMEM 元数据窗口（16 KiB）。
- **诚实的测量协议**：明确区分 expert-launch、完整 MoE 层和 serving 三级计时，并给出解析式 roofline/强度模型（BF16 峰值 2307 TFLOPs/s ÷ 7.38 TB/s ≈ 313 FLOPs/byte 拐点）。

## Key Contributions

- **Fully fused expert-compute-and-return pipeline**: indexed token-row DMAs gather inputs straight from HBM into VMEM; gate/up matmul, gated activation, and down-projection execute in one launch; results are direct-DMAd to their final token-slot rows. This removes grouped-activation materialization in HBM, the separate activation kernel, and receive-side scatter-add buffers (Table 3).
- **Stable token-slot output contract**: destinations are fixed by token ownership (`destination(t)=floor(t/c)`, `output_row(t,s)=local_token(t)*k+s`), not by which device computes the expert. Expert sorting, tile scheduling, chipmate redistribution, and preloaded copies all change the *producer* while destinations — and hence routing semantics — stay unchanged. Unique output ownership guarantees exactly one writer per (token, slot) row.
- **A toolbox of imbalance mechanisms**, each scoped to a regime: row bucketing (smallest precompiled bucket covering valid rows + alignment padding, e.g. 41 valid rows at offset 8 → a 64-row bucket instead of a 128-row allocation), hot-expert interleaving with a dedicated W1 VMEM bank, destination interleaving to de-burst output traffic, intra-chip expert redistribution (at most one expert move per chipmate pair per invocation; inputs already replicated so no token exchange), static placement by checkpoint permutation, and preloaded hot-expert copies (one extra expert slot per chip, home-or-holder runtime decision, decode-only and disabled by default).
- **Symmetric EP8TP2 decode**: W1 partitioned across matching gate/up channels, W2 across the reduction dimension; both cores compute the same tiles with matched valid-row bounds, exchange partials over the on-chip bridge, and delay reduction by one tile to overlap communication — directly attacking the decode regime where the number of active experts (weight streaming), not token count, dominates cost.
- **Low-precision dataflow with explicit accuracy caveats**: FP4 e2m1 weights (8 per uint32 word along K) with FP32 block scales plus per-projection global scales; W4A8 (FP8 activations, K-block absmax quantization) or W4A16 (BF16); the FP4 path casts FP32 matmul results into a BF16 shared accumulator (saving 16 KiB/row for an 8192-column accumulator vs. FP32), with the authors explicitly flagging that layer- and model-level accuracy validation is essential.
- **Measurement discipline**: a validation protocol separating expert-kernel, full-layer, and serving timings; analytic FLOP/traffic models (e.g. weight-only intensity 4Tk/A FLOPs/byte); and per-mechanism ablation plans — although the ablations themselves are explicitly listed as "further validation, not completed results."

## Methodology

The kernel is written in Pallas and compiled by Mosaic into statically scheduled TPU programs; it explicitly issues local/remote DMAs ahead of use and waits on completion semaphores. Section 3 builds the base EP16 kernel (experts statically partitioned across sixteen TensorCore devices on eight TPUv7 chips; each expert computed entirely by its owner):

1. **Fusion boundary (§3.1)**: five stages — collect token rows (indexed DMAs), gate/up matmul, gated activation (writing directly into the down-projection's VMEM input), down-projection matmul, and direct writes — run in one launch. Transport writes but never sums rows; postprocessing outside the launch performs per-expert RMS-style normalization and the router-weighted sum. Routing and upstream input exchange remain outside.
2. **Precision (§3.2)**: packed FP4 e2m1 weights with FP32 block scales (shape [experts, K_blocks, 1, N]) and per-projection global scales; scale application point depends on whether block width divides the inner K step (postscale vs. prescale folded into BF16 slices); W4A8 quantizes activations per K-block absmax; BF16 shared accumulators bound accumulator memory.
3. **Pipelining and weight residency (§3.3)**: the outer loop processes expert tiles of at most t_m rows, prefetching next inputs/weights while computing current tiles; circular weight rings give same-expert caching (full residency of both projections with L consecutive tiles cuts that expert's weight reads L-fold); three rotating send buffers plus drain-before-reuse rules; destination metadata held in bounded 1024-entry SMEM slabs (16 KiB total) rather than full 8·M-byte arrays.
4. **Synchronization (§3.4)**: four invariants — entry readiness (before first remote activity), source lifetime (send-buffer reuse waits on DMA completion), tail completion, and a final EP rendezvous with receive-count draining — with no periodic cross-rank barriers in the loop.
5. **Imbalance handling (§4)**: row bucketing, hot/non-hot tile interleaving (skew metric = max over devices of busiest-expert load / mean expert load), destination interleaving sort key `(local_token*P + destination)*k + slot`, chipmate redistribution with regime-specific planners (row-load based for prefill, active-expert-count gap ≥ 2 for small batches) that transfer full W1/W2+scales into the receiver's HBM, static placement, and preloaded one-copy hot experts.
6. **Symmetric EP8TP2 decode (§4.6)**: each chip's experts are TP2-partitioned across its two TensorCores; both cores process the same input rows with complementary weight halves (H_p = act(XW_gate,p) ⊙ (XW_up,p), Z = P_0 + P_1); cooperative alternating input gathers forwarded over the on-chip bridge; partial reduction delayed one tile; each routed row still has exactly one final writer.
7. **Serving configuration (§4, §5)**: in prefill-decode disaggregated serving, EP16 is selected for prefill at T ≥ 1024 and symmetric EP8TP2 for decode at T ≤ 512 (an explicit PD-specific choice, not a general token-count switching policy).

**Evaluation setup (§5)**: TPUv7 (Ironwood) 2×2×2 slice (8 chips, 16 TensorCore devices); FP4 model with 256 experts, top-8 routing, d=f=4096 (W1 4096×8192, W2 4096×4096; 16 MiB + 8 MiB packed weights per expert); Megablox grouped-matmul EP16 as the serving baseline; decode kernel results compare symmetric EP8TP2 against their own fused EP16. The protocol requires precompiled/warmed shapes, synchronized completion, matched routes/topology, and separate reporting of expert-launch, full-layer, and serving timings.

## Results & Highlights

- **Skewed prefill balancing (EP16, measured skewed workload)**: imbalance handling reduces kernel runtime from **2.3× to 1.09×** the same fixed balanced-workload reference time — i.e., the skew penalty over a balanced kernel drops from +130% to +9%.
- **Symmetric EP8TP2 decode (kernel-operation latency, 32–512 global tokens)**: up to **21.3% latency reduction** relative to the authors' own fused EP16 kernel (a kernel-vs-kernel comparison, distinct from the whole-stack serving result).
- **End-to-end serving throughput (vs. Megablox-based EP16 baseline, same 2×2×2 slice)**: **12–34.5% improvement** across request mixes and batch sizes — the authors explicitly state these gains include serving-stack changes and do not isolate the MoE kernel's contribution.
- **Weight-reuse analytics**: with both projections resident in VMEM rings, L = 16 consecutive tiles cut that run's weight reads **16-fold** (per-expert packed footprint: 16 MiB W1 + 8 MiB W2 + 0.375 MiB FP32 scales at block width 512); weight-only arithmetic intensity is 4Tk/A FLOPs/byte, ranging from **4 FLOPs/byte at 32 global tokens to 1024 FLOPs/byte at 8192 tokens** (vs. ridge points of ~313 FLOPs/byte BF16 / ~625 FP8 on Ironwood: 2307 TFLOPs/s ÷ 7.38 TB/s HBM), showing why decode is weight-bandwidth-bound and prefill can approach compute-bound.
- **Memory savings from fusion/precision choices**: BF16 shared accumulator saves **16 KiB per row** for an 8192-column accumulator vs. FP32; bounded SMEM metadata windows cut destination/output-row arrays from 8·M bytes (top-8 at 32,768 tokens → 262,144 indices ≈ 1 MiB just for token indices) to **16 KiB** of slab-window SMEM.
- **Model quality (§5.4)**: all production evaluations passed with no numerical issues observed — reported as production acceptance, not bitwise equivalence; detailed evaluation-suite settings and error summaries remain to be documented.

## Authors & Credibility

The five authors (Rupeng Liu, Bangsheng Tang, Zongwei Zhou, Chengji Yao, Yejin Lee) are at **Meta SuperIntelligence Lab (MSL)**, an industrial systems team with production TPU/JAX infrastructure; the paper claims production use of the kernel (§5.5 mentions a rollout record with monitored correctness/performance signals). The related-work coverage is accurate and careful — they correctly distinguish MegaBlocks (GPU block-sparse, Gale et al., MLSys 2023) from JAX Megablox (Pallas grouped matmuls on TPU), position against GShard/Switch/Expert-Choice routing (they preserve token-choice top-k rather than changing routing), and scope their contribution relative to DeepEP (GPU expert-parallel dispatch/combine), SGLang, and vLLM. The hardware numbers (TPU7x: 2 TensorCores + 4 SparseCores per chip, 64 MiB VMEM per TensorCore, 192 GiB HBM at ~7.38 TB/s, 2307/4614 TFLOPs/s BF16/FP8, 1,200 GB/s bidirectional ICI) are cited to Google Cloud docs and the Ragged Paged Attention TPU paper (arXiv:2604.15464). This is a preprint (arXiv:2611.17857v1, 13 Nov 2026) with no peer review yet. Credibility is bolstered by unusually explicit scoping statements — e.g., "uniform routing provides a bound, not representative skew," figures labeled "dependency schematic, not a measured timeline," and ablations labeled incomplete — though several evaluation details remain undocumented (see Critical Assessment).

## Critical Assessment

- **Novelty**: The individual ingredients (kernel fusion, weight-resident pipelining, expert replication, TP sharing) each have precedent (MegaBlocks, Tutel, Megablox, DeepEP). The genuinely novel piece is the **co-design of a fixed token-slot output contract with producer mobility**: because destinations depend only on token ownership, scheduling, chipmate redistribution, and preloaded copies can all move work without touching routing semantics or completion accounting. This is a real architectural insight, well argued. The symmetric TP2 decode with bridge-exchanged partials and delayed reduction is a solid TPU-specific contribution.
- **Rigor — mixed**. Strong points: three-level timing discipline (kernel vs. full-layer vs. serving), roofline accounting at consistent chip-level scope, explicit safety invariants (entry readiness, source lifetime, receive completion), and honest flags on the BF16 accumulator risk and the ~66K–70K instruction-overlay observation "requiring remeasurement." Weak points: **the headline serving number (12–34.5%) is explicitly not kernel-attributed** — §5.2 says the gains "include serving-stack changes and do not isolate the MoE kernel's contribution," and kernel attribution "requires a controlled backend swap" that was not performed. The **decode comparison (21.3%) is a self-comparison** against the authors' own fused EP16 kernel, not against the Megablox baseline used for serving, and only the *maximum* reduction is reported — the minimum across 32–512 tokens is not given.
- **Reproducibility — weak for a preprint**: Table 5's own note says "Scale-block width, full model/deployment configuration, and source revisions remain to be documented"; §2.4 admits exact baseline launch/HBM-transfer counts "require compiled-trace confirmation"; §5.4's model-quality claim is a single sentence with settings "to be documented"; no code or artifact release is mentioned. The skewed prefill workload's routing distribution — the crux of the 2.3×→1.09× result — is described only as "measured skewed," without a histogram or skew parameter.
- **Missing ablations**: §5.3 lists eight ablation categories (fusion boundary, weight reuse, staging depth, direct-write issue, row specialization, load management, preloaded copies, precision) and states plainly they are "further validation, not completed results." So the contribution of each mechanism — e.g., how much of the prefill recovery comes from row bucketing vs. hot-expert interleaving vs. chipmate moves — is unknown.
- **Red flags / data quirks to note**: (a) the chipmate-redistribution planner "does not explicitly model transfer cost" — the paper's own Figure 12 example moves a 4-row expert (loads 24/12 → 20/16) while transferring ~24 MiB of packed W1/W2 plus scales, which can be a net loss for short schedules; (b) preloaded cross-chip copies are bounded to one expert slot per chip, are decode/verification-only (≤512 tokens), and are **disabled by default** — yet the cross-chip mechanism features prominently in the design narrative; (c) only a single model shape (256 experts, top-8, d=f=4096) and a single 2×2×2 slice are evaluated, so scaling to larger EP meshes (where cross-chip imbalance is worse) is untested; (d) the baseline replicates the full input-row table in every device's HBM and relies on upstream all-gather — costs the paper excludes from the kernel but which their own future-work section (§6.1, consumer-directed exchange) implies are significant.
- **Significance**: If the numbers hold, a 34.5% serving-throughput gain on Ironwood-class TPUs is highly significant for MoE serving economics, and the design pattern (stable destination contract + mobile producers) transfers to other accelerator stacks. But the unfinished attribution and ablation work means the reader cannot currently tell how much survives a controlled comparison.

## Strengths

- Elegant central abstraction: the fixed token-slot output contract cleanly decouples *where work runs* from *where results land*, letting load balancing compose with fusion instead of fighting it.
- True joint optimization of the three MoE bottlenecks (compute, communication, imbalance) rather than kernel-only tuning; regime-specific designs for prefill (row-load scheduling) vs. decode (active-expert-count awareness, symmetric TP2).
- Careful, safety-first systems engineering: explicit buffer-lifetime rules, four-part synchronization contract, bounded SMEM windows, receive-accounting invariants — the kind of detail that suggests real production hardening.
- Exceptional measurement honesty for a systems preprint: separates kernel/full-layer/serving timings, labels analytic numbers vs. measured ones, flags uniform routing as unrepresentative, and openly lists what is not yet done.
- Practical low-precision plumbing: FP4 packing + FP32 block/global scales with prescale/postscale selection by block-width divisibility, and an honest treatment of BF16 accumulator truncation tradeoffs.

## Limitations

- Ablations are planned, not completed (§5.3); per-mechanism contributions to the 2.3×→1.09× prefill recovery and the 21.3% decode gain are unquantified.
- The serving-throughput improvement (12–34.5%) bundles serving-stack changes with the kernel; no controlled backend-swap attribution.
- Decode kernel results are only reported as "up to 21.3%" vs. the authors' own fused EP16 — no per-token-count table, no comparison against Megablox at kernel level, and the path is limited to ≤512 tokens with token count divisible by device count.
- Cross-chip preloaded expert copies: one copy per chip, decode-only, disabled by default, helps only calibration-identified hot experts, and cannot split a dominant expert across chips (the split-token extension is unimplemented).
- Configuration under-documentation (scale-block width, deployment config, source revisions), no model-quality numbers beyond "production evaluations passed," and no stated code release — reproducibility is currently limited.
- Single model geometry and single 8-chip slice; upstream activation exchange (full input-table replication) is acknowledged as future work (§6.1), and the routing-skew sensitivity of the overall system to the slowest chip remains.

## Relevance

对关注大模型推理效率与系统优化的研究方向高度相关：这篇工作展示了 MoE 推理内核在 TPU 上的融合、低精度（FP4/W4A8）与负载均衡协同设计，其"稳定输出契约 + 生产者可移动"的思路对 GPU 上的 MoE serving（如 DeepEP、vLLM/SGLang 栈）同样有借鉴意义。若关注推理成本、kernel 工程或 PD 分离 serving，这是一篇值得精读的系统论文。

## Questions for Further Exploration

- How much of the 12–34.5% serving-throughput gain survives a controlled backend swap that isolates the Fuse-All kernel from the accompanying serving-stack changes?
- What is the *minimum* (not just maximum 21.3%) decode-latency reduction across the 32–512 token range, and does symmetric EP8TP2 still help at 1–2K-token verification/speculative-decode batches beyond the current 512-token limit?
- Does the BF16 shared accumulator in the FP4 path measurably degrade accuracy for long-K accumulations (multiple outer K tiles), and what is the accuracy/latency Pareto frontier vs. an FP32 accumulator?
- What routing-skew parameters (e.g., Zipf exponent, hot-expert concentration) characterize the "measured skewed prefill workload," and how does the 2.3×→1.09× recovery degrade under adversarial or drifting routing where the calibration-chosen hot experts become cold?
- Would the unimplemented split-token preloaded-copy extension (disjoint rows of one expert on home and holder chips) change the one-copy-per-chip capacity/balance tradeoff for dominant experts?
- Can the chipmate-redistribution planner's cost proxy be improved to model the ~24 MiB weight-transfer cost it currently ignores, and would that change the move-acceptance rate for short decode schedules?
