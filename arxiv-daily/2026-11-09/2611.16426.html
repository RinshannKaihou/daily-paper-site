SoScale turns FP4 scale-code selection into Hessian-weighted layer reconstruction — winning all six model–format groups.

把层级式 FP4 量化（MXFP4/NVFP4/HiF4）中的 scale-code 选择改造为 Hessian 加权的层级重建问题，并与 GPTQ 式误差补偿交错执行；在 Qwen3-8B/14B 的 W4A4 实验中，全部 6 个 model-format 组均取得最佳平均准确率。

SoScale: Second-Order Scale Search for FP4 Quantization ↗

Why this matters

A drop-in offline fix that keeps shipping FP4 hardware formats (MXFP4 / NVFP4 / HiF4) fully intact — no serving-time overhead, directly deployable for LLM inference.

Critical edge

▲Gains are modest (+0.21–0.77 pp) with no error bars or repeated runs, and the "wins every group" headline partly rests on post-hoc selection between two SoScale variants.

Methodology

Post-training, offline, format-agnostic: optimize weight scale codes for a fixed pretrained model without retraining or touching the FP4 format.

Objective

Minimize layer reconstruction loss, not element-wise MSE — weight errors are penalized by their effect on calibrated layer outputs (H = XᵀX from 128×2048-token WikiText calibration):

ℓi,b(c) = ei,b(c)ᵀ Hb ei,b(c)

Scale search

Each weight block scores every hardware-legal scale code in a small window around the default code, using a block-local Hessian surrogate; pick the argmin. One abstraction instantiates MXFP4 (E8M0 exponent), NVFP4 (E4M3 + FP32 tensor scale), and HiF4.

Interleaved recovery

GPTQ-style: after a block commits, its error is propagated to future blocks via the damped inverse Hessian UᵀU = (H + λI)⁻¹ so the next search runs on compensated weights.

Serving

Activations: per-token dynamic FP4, or direct RTN in the deployment-oriented “-w” setting. Optional Hadamard rotation. Embeddings, LM head, norms stay BF16. No serving-time search.

  • Best SoScale variant tops all 6 model–format groups; gains over local ScaleSearch run 0.47–1.10 pp.
  • Deployment setting (direct-RTN activations): SoScale-w beats ScaleSearch-w in every group by 0.08–1.92 pp.
  • Motivating evidence: searched MXFP4 scale moves 0.125 → 0.0625 on a real weight block; default scaling leaves the two outermost FP4 levels unoccupied.
Ablation isolates the mechanism: MSE search + GPTQ recovery alone is marginal on MXFP4 and actually hurts NVFP4 (0.7270 < 0.7281) — the Hessian-aware objective, not the recovery, is the key ingredient.

Strengths

  • Optimizes the quantity that matters — layer-output fidelity — while staying inside hardware-legal scale codes; no format change, no serving-time overhead.
  • Clean format-agnostic formulation demonstrated on all three practically relevant hierarchical FP4 formats.
  • Genuinely informative ablation: shows MSE + recovery can hurt, pinpointing the Hessian objective as the source of gains.
  • The “-w” deployment setting anticipates real hardware constraints and still wins every group (up to +1.92 pp).
  • Honest, format-dependent reporting (Hadamard helps MXFP4 most) rather than a one-size-fits-all claim.

Limitations

  • Only two models from a single family (Qwen3-8B/14B); no Llama/Mistral-class or 70B+ models — generalization unverified.
  • Margins as low as +0.21 pp with no error bars; some per-task regressions (ARC-C on 8B/MXFP4: 0.5171 → 0.5000).
  • Best variant switches between SoScale and SoScale w/ Had. per format–model; no selection rule offered.
  • No offline-cost or sensitivity analysis (window size, damping λ, single WikiText calibration shard); activation side under-optimized.
  • No code release at preprint time.

Questions for further exploration

  • Do gains persist at 32B/235B or Llama-class models, against baselines that jointly learn rotations and scales?
  • What is the offline wall-clock/memory cost versus GPTQ and ScaleSearch, and how does accuracy scale with window size and λ?
  • Can activations benefit from the same layer-aware treatment, given direct RTN sometimes beats the searched rule?
  • Why does Hadamard help MXFP4 most — can the decision to rotate be predicted from block statistics?
  • Would wider-than-block Hessian coupling close the remaining 0.8–3.6 pp gap to BF16?
