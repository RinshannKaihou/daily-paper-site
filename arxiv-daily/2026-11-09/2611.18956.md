> **一句话总结：** AI2 与华盛顿大学把 Olmo-core 的训练栈从 FSDP 重构为 DDP + 专家并行（EP）+ 流水线并行（PP）+ 分布式优化器，配合 NVSHMEM 行级 EP、免同步的 GPU 常驻路由元数据、grouped GEMM 与 MXFP8，在 B300 节点上支持 12.9B 到 1.2T 总参数的训练（512 GPU 时达 858 useful-model TFLOP/s/GPU），并识别出 "Token Gerrymandering"（路由器学会作弊压低负载均衡损失却加剧失衡）等对社区有普适价值的系统发现。

> **TL;DR:** A 169-page systems report from Ai2/UW that rebuilds Olmo-core's MoE training stack on DDP + expert/pipeline parallelism with NVSHMEM-based rowwise EP, synchronization-free GPU-resident routing metadata, device-scheduled grouped GEMM, and integrated MXFP8. On NVL8 B300 nodes the stack trains 12.9B-to-1.2T total-parameter models on 16–512 GPUs, reaching 858 useful-model TFLOP/s/GPU (38.1% BF16-reference MFU) at 1.2T; in the motivating 8-layer 8×B300 capacity sweep, the legacy FSDP path's throughput collapsed from ~50.5K to ~19.4K tokens/s/GPU as total expert parameters grew 4.6B→47B at fixed active size, while the new DDP+EP8 path held ~52K. Two widely transferable findings: the router can hack the Switch-style load-balancing loss ("Token Gerrymandering" — LBL falls while max/mean imbalance rises from ~40 to ~46 in a checkpoint-branched run), and overlapping communication with compute can slow the overlapped kernels (up to +15.1% expert-GEMM stretch) more than it hides. Headline throughputs use random routing, so they are systems references, not time-to-quality results.

## 核心贡献

- **用 DDP 取代全量重分片的 FSDP 来消除"容量税"（capacity tax）**：MoE 的权重存储、梯度同步和优化器更新都随总参数量增长而非激活参数量。作者把训练栈重构为：DDP（每 rank 常驻模型分片 + 每步一次梯度同步）+ 专家并行 EP（路由专家分片到各 rank）+ 流水线并行 PP + 分片 FP32 主权重的分布式优化器。
- **NVSHMEM 行级（rowwise）专家并行**：token 行通过 GPU 发起的一侧通信直接写入目标专家缓冲区，绕过传统 all-to-all 路径的 permute/unpermute 排布变换与主机可见的 split list；配合 GPU 常驻路由元数据与设备调度的 grouped GEMM，实现完全免同步（synchronization-free）的稳定训练循环。
- **深度集成的 MXFP8 低精度训练**：E4M3 数据 + 32 值块缩放（E8M0）同时降低 GEMM 计算、保存激活（名义上每值 2 字节降到 33/32 字节，约 −48.4%）和 dispatch 载荷；FP32 主权重始终是唯一真值来源。分派路径直接传输量化后的表示，通信与专家计算共享同一数据布局。
- **拓扑无关的 checkpoint**：每个保存分块以全局 FP32 张量坐标描述，跨运行改变并行布局后可恢复训练。
- **两个普适性发现**：(1) **Token Gerrymandering** —— 证明 Switch 式负载均衡损失是有符号交叉项而非"均衡性证书"，路由器可以在压低 LBL 的同时加剧真实路由失衡（有解析证明 + checkpoint 分支实验）；(2) **通信-计算重叠的悖论** —— 并发的行级通信会把 grouped GEMM 拉慢 22.9–27.0%，重叠调度可能净变慢。
- **完备的生产吞吐矩阵**：在 16–512 块 B300 上给出 Tiny→Ultra 五档配置（含 batch、EP/PP 拓扑、精度、重算策略）的可复现操作点，并用 DeepEP v2 后端以 9 步实验演示 2.38T 总参数的可达容量。
- **诚实的负结果报告**：CPU 激活卸载、wave overlap、两批重叠、MoE megakernel、自然布局 MXFP8 Wgrad、CUDA Graph 全部试过且量化了不采用的原因。

## Key Contributions

- **Replaces full-reshard FSDP with a DDP-based stack to eliminate the "capacity tax"** — costs (weight storage, gradient sync, optimizer updates) that scale with total rather than active parameters. The new stack combines DDP (resident rank-local partitions, one gradient sync per step), expert parallelism (EP), pipeline parallelism (PP), and a distributed optimizer that shards FP32 main weights and optimizer states.
- **NVSHMEM-based rowwise EP**: each accepted token row is written directly into its expert's destination buffer via GPU-initiated one-sided communication, eliminating the permute/unpermute layout transformations and host-visible split lists of block all-to-all dispatch; combined with GPU-resident routing metadata and device-scheduled grouped GEMMs this makes the steady-state loop fully synchronization-free.
- **Closely integrated MXFP8 training**: E4M3 payload + one E8M0 scale per 32 values cuts GEMM compute, saved activations (2 → 33/32 bytes/value, ≈48.4% nominal reduction), and dispatch payloads, with FP32 main weights as the single source of truth; dispatch transports the quantized representation that grouped GEMM consumes directly, with no intervening BF16 materialization.
- **Topology-agnostic checkpoints**: every saved chunk is described by its coordinates in the global FP32 tensor, so a run can resume on a different parallel layout.
- **Two transferable findings**: (1) *Token Gerrymandering* — the Switch-style LBL scalar is a signed cross-term between hard route counts and soft score mass, not a balance certificate; the model can drive LBL down while requested routing becomes more imbalanced (analytic argument + checkpoint-branched run); (2) overlapping communication with computation can slow the overlapped kernels more than it hides (concurrent rowwise communication stretches grouped GEMM by 22.9–27.0%).
- **A complete production throughput matrix** (Section 14): measured operating points from Tiny (1.59B@12.91B, 16 GPUs) to Ultra (58.36B@1.200T, 512 GPUs), plus a 9-step 2.38T capacity demonstration via the optional DeepEP v2 backend.
- **Documented negative results** with quantified reasons: CPU activation offload (PCIe-limited, ρ≈6), wave overlap, two-batch overlap, a persistent MoE megakernel, natural-layout MXFP8 Wgrad, and CUDA Graph replay.

## Methodology

The report is organized as a measurement-driven systems design study on NVIDIA B300 (NVL8, 8 GPUs per NVLink domain) hardware. The core decomposition separates the **capacity tax** (costs following total parameter size) from the **runtime tax** (costs of sparse routing and execution), and evaluates every component change by its effect on complete-step time and throughput at fixed model/batch/topology rather than isolated kernel wins.

**Parallelism (Sections 3–7):** DDP keeps each rank's model partition resident across the whole gradient-accumulation window; EP shards routed experts across ranks and moves only selected token rows to the owning rank; PP splits layers when one rank cannot hold them; a distributed optimizer shards FP32 main weights, gradients, and optimizer states. Rank groups are mapped onto NVLink (intra-node) and InfiniBand (inter-node, with IBGDA for GPU-initiated transfers).

**Rowwise EP (Section 5):** instead of packing tokens into contiguous per-destination blocks (permute → all-to-all → unpermute), a GPU-resident route map indexes each row directly into its expert's slot using NVSHMEM PUT/GET. Routing counts never leave the GPU, removing per-step device-to-host synchronizations (Section 8); device-scheduled CUTLASS grouped GEMM executes the uneven per-expert shapes without capacity padding (Section 9). A block-oriented DeepEP v2 backend covers expert groups spanning nodes.

**MXFP8 recipe (Section 11):** selected linears run on Blackwell's block-scaled tcgen05.mma path with round-ceiling scaling; loss/gradient-norm trajectories track BF16 in a checkpoint-branched continuation. **Recompute (Section 13):** per-block activation recompute trades throughput for memory in the largest recipes. **Measurements** use CUDA-event timing, Nsight traces, fresh-process repetitions, and randomized/balanced execution orders; Appendix B records full run configurations and evidence limits, and the authors bundle experiment artifacts (including a reproducer for the operand-value timing effect).

## Results & Highlights

- **Capacity tax reproduced and eliminated (Figure 4; 8-layer BF16 model, top-4, one 8×B300 node):** at fixed ~3.2B active parameters, the legacy FSDP path's throughput fell from ~50.5K to ~19.4K tokens/s/GPU as total expert size grew 4.6B→47B (dense baseline 61–63K), while the new DDP+EP8 path held ~54.5K→52K — roughly 2.7× the old path at the 47B-total point (a composed-system result, not an isolated ablation).
- **Production throughput matrix (Table 30, random routing, seq len 8192, top-4 + 1 shared expert, B300):** Tiny-64E 1.59B@12.91B reached 903 TFLOP/s/GPU (40.1% MFU, BF16, EP1/PP1, 16 GPUs); Medium configurations (7.38B active, 70.22B–137.27B total) stayed in a narrow 843–855 TFLOP/s band; Large-128E 15.14B@295.99B reached 768 TFLOP/s (34.1% MFU); Ultra-128E 58.36B@1.200T (MXFP8, EP8/PP8, per-layer recompute, 512 GPUs) reached 858 TFLOP/s/GPU (38.1% MFU vs the B300 BF16 peak of 2,250 TFLOP/s). An experimental 9-step Ultra-256E run (58.41B@2.380T, DeepEP v2, EP32) demonstrates reachable capacity only.
- **Learned routing costs up to ~9% (Appendix B.10):** learned-router companion runs show a ~1% throughput gap at Tiny (no EP) and ~9% at Small (EP8) versus the random-routing reference.
- **Recompute trade-off (Figure 62; matched 4×B300 config):** block recompute cut peak active memory 103.03 → 76.90 GiB (−25.4%), with the transient activation component shrinking 40.82 → 14.69 GiB (−64.0%) at a fixed 62.21 GiB persistent floor, for 20.95% lower throughput (54.68K → 43.22K tokens/s/GPU).
- **Grouped GEMM vs capacity-padded BMM (Figure 38; 16 local experts, d=h=4096, BMM at 1.25× capacity):** BMM's regular kernels win below a crossover of 256–512 routed rows per expert (M=4K–8K total); above it grouped GEMM wins everywhere, and at M=128K BMM takes 28.9% longer — more than its 25% padded work. The common 16K–96K rows/rank operating range sits entirely above the crossover.
- **Imbalance hurts GEMM throughput (Figure 40; 100 matched-work load histograms):** Spearman ρ = −0.86 (95% bootstrap CI [−0.90, −0.80]) between entropy-deficit load imbalance and grouped-GEMM throughput; median normalized throughput falls from ~96% (balanced) to ~89% (most concentrated).
- **Token Gerrymandering (Figure 42; step-17k / 71B-token checkpoint branch):** with λ_LBL = 0.05 the unscaled LBL (sum over 47 MoE blocks) keeps falling while the worst max/mean expert-count imbalance climbs from ~40 to ~46; re-branching with λ_LBL = 0.005 stops the rise.
- **Overlap can backfire (Figure 23 + Table 9; two-node DeepEP v2, EP-MP=16, 128 experts, top-8):** the four-wave overlapped forward took 60.248 ms vs 56.819 ms without waves (+6.0%), with expert compute stretched +15.1% (52.901 vs 45.976 ms); in a separate rowwise diagnostic, concurrent dispatch/combine slowed grouped GEMM by 22.9–27.0%, although the overlapped pair still beat sequential (7.768→5.833 ms and 7.560→5.868 ms).
- **Operand values change GEMM timing (Table 34; one B300, matched shape/layout/dtype):** relative to normal-random BF16 weights, all-zeros reduced grouped-GEMM time by 39%, constant fill by 34%, and random-sign-fixed-magnitude by 16% (dense GEMM: −21% with zeros). A related power-limit stress run saw median SM clocks fall 1174→960 MHz and grouped-GEMM throughput 1366→1163 TFLOP/s.
- **CPU activation offload is bandwidth-infeasible (Section 15):** one routed block produces 3.96 GB of candidate activations in 10.3 ms (≈384 GB/s) against a 63 GB/s link — ρ≈6; eight GPUs offloading together would push ~3 TB/s into host memory.
- **Recipe findings (Sections 16–18, 20):** batch-size scaling with exponent α = 0.53 (only +2.1% over √N for a doubling) removed visible loss-curvature breaks more consistently than α = 0.5; scaling expert learning rates by √(K/N) did not help (best C4 validation loss 2.873 unscaled at LR 8e-4 vs 2.878 sparsity-scaled at 2e-3, 0.43B@2.51B MoEs trained 150B tokens each); training from scratch is preferred over upcycling given the OLMoE finding that scratch models overtake upcycled ones near 600B sparse tokens; and any number of ungated shared experts collapses exactly to one wider shared MLP (SwiGLU width-sum equivalence).

## Authors & Credibility

The team is from the Allen Institute for AI (Ai2) and the University of Washington, led by Tianhua Tao (UW/Ai2) with the core OLMo/OLMoE infrastructure group — Dirk Groeneveld, Iz Beltagy, Pete Walsh, Tyler Romero, Jacob Morrison, Yashas Samaga, Akshita Bhagia, Taira Anderson, and senior leads Hannaneh Hajishirzi and Noah A. Smith. This is the organization that built OLMo, OLMo 2, and OLMoE, so the authors have direct custody of the codebase they describe rather than reporting on a third-party system. The 169-page report is unusually rigorous about evidence limits: every headline number carries its configuration and caveats, an explicit "Statement of AI Assistance" discloses that AI tools assisted with code, drafting, experiments, and visualization (with the authors retaining responsibility), and appendices document measurement protocols, artifact provenance, and the web/code releases. The presence of an entire section (15) on optimizations they tried and rejected — with quantified reasons — is a credibility signal rarely seen in systems papers.

## Critical Assessment

- **Novelty:** The individual ingredients (DDP + EP + PP + distributed optimizer, grouped GEMM, FP8, NVSHMEM) are not new; the contribution is the tightly integrated rowwise-EP design (no permutation, sync-free, quantized transport consumed directly by grouped GEMM) plus genuinely novel analyses — Token Gerrymandering (with an exact algebraic argument, not just an anecdote) and the operand-value dependence of GEMM timing. Both findings have practical consequences beyond Olmo.
- **Rigor:** Very high on the measurement-methodology side (fresh-process repetitions, bootstrap CIs, randomized execution order, balanced controls, honest Nsight transcription caveats). But the headline Table 30 numbers use **random routing**, which the authors themselves show is optimistic by ~9% at Small with EP8 for a learned router; and rows differ in batch, PP degree, precision, and recompute, so the matrix is explicitly *not* a controlled scaling curve (Ultra-128E vs Large-128E mixes MXFP8 + recompute + 64Mi vs 32Mi batch + PP8 vs PP4, preventing any precision-only conclusion).
- **Reproducibility:** Strong — configurations, timing protocols, and artifacts are documented per experiment, checkpoints are layout-agnostic, and the operand-value reproducer is bundled. Weak spots: some Table 30 configurations were "launched more than once" with lower-rate repeats attributed to suspected but *unestablished* environmental problems, and the selected rates are best-observed readings rather than repetition averages.
- **Significance:** The 1.2T @ 858 TFLOP/s/GPU result is a solid, well-characterized operating point on B300; the 2.38T figure is only a nine-step capacity demonstration and should not be quoted as a sustained capability. The training-recipe findings (α = 0.53, sparsity-scaled expert LR, upcycling) are useful but lightly evidenced — the LR sweeps are single runs without seed replication (the authors say the comparison is "directional"), α = 0.53 comes from internal tuning runs that are not plotted, and the no-upcycling decision leans on the *published OLMoE study* rather than new experiments at this scale.
- **Red flags / caveats to keep in mind when citing:** (1) MFU percentages use the BF16 peak (2,250 TFLOP/s) even for MXFP8 runs, so 38.1% is not FP8-peak utilization; (2) the Megatron-Core MoE comparison is qualitative — they acknowledge GB200/GB300 NVL72 results report higher per-GPU throughput but on different platforms and domain sizes; (3) the operand-value timing effect (Table 34) is a single run with fixed case order and no power/clock telemetry, characterizing that run only; (4) no time-to-quality results are reported at the production scales — this is a systems reference throughout.

## Strengths

- Names and cleanly separates the **capacity tax vs runtime tax** framing, which explains *why* MoE throughput collapses on dense-oriented infrastructure and gives the community a vocabulary for the problem.
- Rowwise EP is an elegant unification: direct placement removes permute/unpermute, GPU-resident metadata removes host syncs, and the quantized row format is shared between transport and grouped GEMM with no BF16 detour.
- The Token Gerrymandering analysis (LBL scalar = signed cross-term, provably able to fall while imbalance rises, confirmed by a checkpoint-branched experiment) is a finding every MoE team should read.
- Exceptional measurement honesty: negative results are quantified, best-case readings are labeled as such, random-routing optimism is quantified (~1%/~9%), and every figure states what it does not establish.
- Practical, transferable micro-findings: the grouped-GEMM/BMM crossover at 256–512 rows per expert, the −0.86 Spearman correlation between load concentration and GEMM throughput, and the ρ≈6 PCIe-vs-production bandwidth argument against activation offload.

## Limitations

- All measurements are on NVIDIA B300 NVL8 nodes with 8-GPU NVLink domains; behavior on larger NVLink domains (NVL72) or other accelerators is not measured, and cross-framework comparisons with Megatron-Core/DeepSpeed-MoE/DeepEP are qualitative, not head-to-head.
- The production matrix is not a controlled scaling curve: batch, PP degree, precision, and recompute policy all co-vary across rows, so no single-factor conclusion (e.g., "MXFP8 gives X%") can be drawn from Table 30.
- No model-quality (loss/benchmark) results at the reported scales — throughput-only; the authors are explicit that these are systems references, but readers wanting time-to-quality will not find it here.
- Several quantitative claims rest on single instances: the wave-overlap timeline is one rank and one iteration; the operand-value table is one run; LR sweeps lack seed replication; the 2.38T point is nine steps.
- The post-training discussion (SFT/preference/RL reuse) is a design sketch without benchmarks.

## Relevance

这篇论文直接命中 LLM 预训练系统与 MoE 高效训练方向：它给出了从 FSDP 迁移到 DDP+EP+PP 的完整工程蓝图、MXFP8 低精度训练配方以及 Token Gerrymandering 等路由失衡诊断方法，对任何需要在大规模 GPU 集群上训练稀疏 MoE 模型（或评估其真实吞吐）的工作都是高价值参考。

## Questions for Further Exploration

- Does Token Gerrymandering also appear with the post-batch bias controller (DeepSeek-V3-style) or expert-choice routing at the 1.2T scale, or only with Switch-style LBL — and can the requested-count histogram be regularized directly instead?
- What is the *time-to-quality* throughput of the Ultra recipe with learned routing (the ~9% EP8 gap at Small suggests the 858 TFLOP/s reference is optimistic — how large is the gap at 128 experts and PP8)?
- Could SM-partitioned communication kernels (Lancet/COMET-style isolated copy engines or dedicated SM carve-outs) flip the overlap result so that the 22.9–27.0% concurrent-GEMM slowdown is avoided while still hiding dispatch latency?
- How does rowwise EP behave inside a 72-GPU NVLink domain (GB200/GB300 NVL72), where the intra-node path could cover far larger EP groups — does the block-oriented DeepEP v2 backend remain necessary?
- Given the operand-value timing effect (up to 39% grouped-GEMM time change from weight values alone), what benchmarking protocol — fixed-magnitude operands, recorded power/clocks, or value-matched controls — should become standard for FP8/MXFP8 kernel evaluations?
- Does the exact collapse of multiple ungated shared experts into one wider MLP (Section 20) change optimal shared-width allocation when combined with routed/shared merge-rule initialization (Section 21)?
