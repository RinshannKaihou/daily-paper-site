> **一句话总结：** 提出 NVLinkOneSided——在单一 NVLink 域内让每个源 GPU 仅凭本地路由信息、不经任何元数据交换就把 token 直接推入目标 GPU 的"按源 rank 分区"（rank-major）工作区，并以 FENCE（标志位+内存栅栏）和 SENTINEL（数据即标志）两种协议做生产者-消费者同步；在 8×B300 上对 DeepSeek-V4.1-Flash / Kimi-K3 的 MoE 层，dispatch+combine 往返比 DeepEP V2.5 快 1.2–3.0×（1 token/rank 时 17.4 µs vs 47.9 µs），整层比 DeepEP+DeepGEMM 最快快 2.4×，且在 ≤128 token/rank 的解码批次上胜过融合的 DeepGEMM MegaMoE。

> **TL;DR:** MoE 推理在小批量下，EP dispatch/combine 的延迟由同步等固定开销而非数据搬运主导。本文利用 NVLink 对称内存实现单侧（one-sided）all-to-all：源 rank 直接把 token 写入目标 rank 的 rank-major 缓冲区，分组 GEMM 用槽位索引就地读取，免去元数据交换和逐专家重排。在 DeepSeek-V4.1-Flash 与 Kimi-K3 的路由专家层（8×B300 与 GB200 NVL72）上，all-to-all 比 DeepEP V2.5 快 1.75–3.00×（≤128 token/rank）与 1.17–1.63×（≥256），MoE 层比 DeepEP+DeepGEMM 基线最快快 2.4×（36.7 µs vs 74.7 µs @1 token/rank），并在最高 128 token/rank 上优于融合的 MegaMoE（最多 30%），但 256 以上被 MegaMoE 反超（4096 token/rank 时慢约 35%）。已进入 FlashInfer3 并集成于 vLLM、SGLang、TensorRT-LLM。

## 核心贡献

- **单侧 EP all-to-all（NVLinkOneSided）**：每个源 rank 只靠本地路由结果，就把 token 直接写入目标 GPU 对称内存中的工作区，不再先交换 token 计数 / 专家 id 等元数据——消除了小批量下占主导的同步往返。
- **rank-major 布局与就地计算**：每个目标 rank 的 dispatch 工作区按源 rank 分区，token 每个目标 rank 只发送一次（最多 min(k, P) 次而非 k 次）；分组 GEMM（FC1/FC2）通过 TMA gather4 槽位索引直接就地读取，不需要物化成按专家排列的副本。
- **两种同步协议**：FENCE 用系统级内存栅栏 + 每对等端的完成标志，面向大批量高吞吐；SENTINEL 让数据本身充当到达标志（Lamport 式，32 位字初始化为哨兵值，整字到达保证），面向小批量低延迟；两者交叉点在 256 token/rank。
- **精度无关与可集成性**：dispatch 搬运的是量化后的 token（支持 BF16/FP8/MXFP8/NVFP4），接口对激活量化格式与 MoE 计算后端均解耦，经 FlashInfer 的 MoEEpCommunication 接口暴露，可整体捕获进 CUDA 图（PDL 级联内核）。
- **内存占用显著更小**：DeepSeek-V4.1-Flash、8 GPU、4096 token/rank 下，dispatch（MXFP8）+combine（BF16）工作区共约 480 MiB，而 DeepEP V2.5+DeepGEMM 需 242 MiB 通信缓冲 + 约 1020 MiB 的 expert-major GEMM 输入。

## Key Contributions

- **One-sided EP all-to-all (NVLinkOneSided):** each source rank pushes its tokens directly into rank-major workspaces in the symmetric memory of target GPUs using only its own routing information — no metadata (token counts, expert ids) travels ahead of the data, removing the fixed synchronization cost that dominates small inference batches.
- **Rank-major layout with in-place compute:** the dispatch workspace of each rank has one region per source rank; a token occupies one slot per target rank regardless of how many of that rank's experts it selects (sent at most min(k, P) times instead of k), and the FlashInfer Prims-TS grouped GEMMs read tokens in place through slot indices (TMA gather4), eliminating the per-expert permute/copy pass that NCCL/DeepEP-style designs require.
- **Two synchronization protocols:** FENCE publishes per-peer completion flags after a system-scope release fence (high-throughput regime); SENTINEL uses the payload itself as the arrival flag — every 32-bit word is initialized to a sentinel bit pattern and each aligned word is guaranteed to arrive whole over NVLink — with expert-id slots (sentinel 0x88888888) broadcast to all ranks telling which landing slots will receive tokens. Unlike NCCL's LL protocol, no flag words are interleaved with the data.
- **Format-agnostic, backend-decoupled interface:** dispatch moves already-quantized activations (BF16, FP8, MXFP8, NVFP4), so any quantization scheme works; FENCE can additionally quantize partial results to FP8 before combine (dequantizing before the reduction) to halve combine bytes. The whole layer (dispatch, indexing, FC1, FC2, finalize, combine) is CUDA-graph capturable with Programmatic Dependent Launch, and every peer wait carries a timeout + trap instead of hanging.
- **Much smaller workspaces:** for DeepSeek-V4.1-Flash on 8 GPUs with up to 4096 tokens/rank, dispatch (MXFP8) + combine (BF16) workspaces hold 160 MiB + 320 MiB, versus DeepEP V2.5 + DeepGEMM's 242 MiB shared communication buffer plus an expert-major GEMM input of ~1020 MiB (~6x the hidden-state memory, due to alignment padding).

## Methodology

The design rests on three observations. (1) In DP-attention + EP-MoE serving (DeepSeek-V3 style), each rank routes its own tokens, so dispatch destinations are fully known locally — the sender can choose the slot itself. (2) Within one NVLink domain (HGX B300 board, or a GB200/GB300 NVL72 rack = up to 72 GPUs at 900 GB/s per direction per GPU), CUDA Virtual Memory Management lets ranks map peers' allocations into a symmetric memory region accessed with ordinary loads/stores/atomics, and each aligned 32-bit word stored to peer memory is observed whole or not at all — guarantees RDMA cannot offer. (3) At decoding batch sizes, dispatch/combine round trips take tens of microseconds even though the payload would take <1 µs at NVLink bandwidth; the gap is fixed cost (metadata exchange, producer-consumer synchronization, extra data passes), so the fix is structural, not faster links.

Concretely, dispatch writes each token (quantized hidden states, scaling factors, all k expert ids and router weights) into its own region of every target rank's workspace, taking slots by atomically incrementing a per-target counter (FENCE) or deterministically landing token i in slot i of its region (SENTINEL). MoE compute then runs as: an indexing kernel that builds per-expert slot-index lists (skipping slots with invalid expert ids), FC1 (up/gate + activation) gathering input via TMA gather4 directly from the workspace, FC2 (down projection) on the expert-grouped FC1 output, and a finalize kernel that gathers FC2 outputs per token, applies router weights, and writes partial sums into the combine workspace at the token's original slot — restoring the rank-major layout so combine needs no metadata either: the source rank pulls partial results from the recorded (target rank, slot) pairs and sums them. Synchronization is needed twice per layer (end of dispatch before MoE compute; end of MoE compute before combine); FENCE does one system-scope fence per rank per step plus flag publish/spin, while SENTINEL has each block poll the words of its landing/combine slots, copy them out, and reset them to the sentinel. Both kernels maximize NVLink bytes in flight via 16-byte vectorized accesses with data-level and instruction-level parallelism (unrolled multi-target stores; tree reduction of multi-target loads).

Evaluation uses the routed-expert layers of DeepSeek-V4.1-Flash (latent MoE, hidden 5120, 384 experts top-6) and Kimi-K3 (hidden 3584, 896 experts top-16) at 1–4096 tokens/rank with perfect routing (main tables) and Zipf skew (α up to 1.25), on 8 NVLink-connected B300 GPUs and on one GB200 NVL72 rack (EP scaled 8→64 ranks). Their layer pairs the all-to-all with Prims-TS grouped GEMMs (MXFP4 weights, MXFP8 activations); baselines are DeepEP V2.5 (its own test settings), DeepEP+DeepGEMM (DE+DG), and the fused DeepGEMM MegaMoE persistent kernel. Measurements run 10 warm-up + 100 timed iterations in one CUDA graph with L2 flushed per iteration, phases timed from CUPTI records and IKET in-kernel timestamps (instrumentation overhead ≤6%); all-to-all outputs match a reference bitwise and layer outputs to relative L2 error ≤5.7e-3.

## Results & Highlights

- **All-to-all latency (DeepSeek-V4.1-Flash, 8×B300, round trip = dispatch + combine):** at 1 token/rank, SENTINEL takes 17.4 µs and FENCE 27.6 µs versus 47.9 µs for DeepEP V2.5 — a 1.75× (FENCE) to 2.75× (SENTINEL) speedup; across models and batches NVLinkOneSided is 1.75–3.00× faster than DeepEP up to 128 tokens/rank and 1.17–1.63× from 256 tokens/rank (e.g., Kimi-K3 @1 token/rank: 17.2 µs vs 49.3 µs DeepEP; @4096 tokens/rank: 501.1 µs FENCE vs 600.3 µs DeepEP).
- **MoE layer latency vs DeepEP+DeepGEMM (8×B300):** up to 2.4× faster at every batch — at 1 token/rank DeepSeek-V4.1-Flash takes 36.7 µs vs 74.7 µs (Kimi-K3: 42.1 µs vs 99.7 µs), with the gain coming mostly from dispatch+combine (18.1 µs vs 48.6 µs total communication).
- **MoE layer vs fused MegaMoE:** the unfused NVLinkOneSided layer is faster up to 128 tokens/rank, by up to 30% (DeepSeek-V4.1-Flash @16 tokens/rank: 70.5 µs vs 90.3 µs); from 256 tokens/rank MegaMoE leads by up to 35% at 4096 tokens/rank (766.1 µs vs 1185.2 µs), since its single persistent kernel overlaps NVLink transfers with Tensor Core work.
- **Protocol crossover and bandwidth:** SENTINEL wins below 256 tokens/rank and FENCE above; at 4096 tokens/rank FENCE sustains 68–71% of the 900 GB/s unidirectional NVLink bandwidth.
- **Low-precision payloads (FENCE, 4096 tokens/rank, DeepSeek-V4.1-Flash):** NVFP4 dispatch is 3.0× faster than BF16 against a byte ratio of 3.5×, MXFP8 is 1.8× against 1.9×; FP8 combine halves the bytes but yields only 1.4× because a kernel must first read and quantize each BF16 partial result — with per-element E4M3 showing no statistically significant accuracy loss on downstream tasks.
- **Large-EP scaling on GB200 NVL72 (DeepSeek-V4.1-Flash):** at 1 token/rank the SENTINEL round trip stays at 16.6–17.8 µs from 8 to 64 GPUs (no per-peer handshake), while FENCE grows 43.0→47.6 µs and DeepEP 44.7→54.2 µs; at 128 tokens/rank the layer drops from 181.7 µs (8 GPUs) to 102.6 µs (64 GPUs, 6 experts/rank instead of 48) and stays 23–26% below MegaMoE at 1 token/rank.
- **Robustness to routing skew (Zipf, 1024 tokens/rank, busiest rank, DeepSeek-V4.1-Flash):** with load imbalance 1.91 at α=1.25, NVLinkOneSided communication costs 160.4 µs vs 267.1 µs for DeepEP, because a token reaches a target rank once however many of that rank's experts it selects (received bytes track tokens, ≤P/min(k,P)× the perfect-routing volume, rather than token–expert pairs).
- **Memory footprint:** dispatch + combine workspaces of 160 MiB (MXFP8) + 320 MiB (BF16) for DeepSeek-V4.1-Flash at 8 GPUs / 4096 tokens/rank, versus 242 MiB + ~1020 MiB for DeepEP V2.5 + DeepGEMM.

All thirteen authors are NVIDIA engineers (Bo Li and Chulian Zhang are the corresponding contacts), including Julien Demouth, a long-time NVIDIA CUDA/cuBLAS senior leader, and specialists from inference-kernel teams. This is a systems paper from the vendor that builds the hardware (Blackwell NVLink5, symmetric memory, TMA, IKET profiling) it optimizes for — the strongest possible position for correctness of the low-level claims, and the work is productized rather than a prototype: NVLinkOneSided ships in FlashInfer3 behind the MoEEpCommunication interface and is already integrated into vLLM, SGLang, and TensorRT-LLM. The paper includes an AI-usage disclosure (assistants helped draft text and write benchmark/plotting scripts; all numbers author-verified) and unusually careful measurement hygiene: bitwise-verified all-to-all outputs, ≤5.7e-3 relative L2 error for the layer, L2 flush per iteration, CUDA-graph back-to-back replays, and a quantified ≤6% IKET instrumentation effect. ## Critical Assessment

- **Novelty:** the individual ingredients (one-sided symmetric-memory writes, Lamport/sentinel synchronization, rank-major de-duplication) each have precedents — NCCL's LL protocol pairs data with flags, UB-X computes dispatch offsets from a replicated routing matrix with a sentinel combine, and Shen et al. build barrier-free collectives from LL-style synchronization — but the specific combination (metadata-free rank-major push + TMA-gather in-place grouped GEMM + a clean FENCE/SENTINEL latency-throughput split behind a framework-agnostic interface) is a genuine and well-executed systems contribution, with an honest related-work map of how close UB-X and Perplexity's kernels already are.
- **Rigor:** measurement methodology is among the more careful I have seen for microbenchmarks (bitwise output checks, L2 flush, CUPTI+IKET phase attribution with overhead quantified). However, the headline MoE-layer tables use *perfect routing* (each token's k selections on consecutive ranks, spread evenly) — an idealized pattern that maximizes the de-duplication benefit; the Zipf study covers only 1 and 1024 tokens/rank and shows the communication advantage persisting, but the main tables remain best-case. The MegaMoE loss at ≥256 tokens/rank is reported honestly rather than hidden.
- **Reproducibility:** good in principle (shipped code in FlashInfer3, exact model configs, latency tables in the appendix), but the evaluation needs B300/GB200 NVL72 hardware that few labs have; no Hopper/NVLink4 results are given, and the whole 32-bit-word-arrival and symmetric-memory foundation is Blackwell-NVLink-specific.
- **Significance:** the decoding-regime win is real and relevant (MoE all-to-all at 1–256 tokens/rank is a known serving bottleneck), but it is demonstrated only at the layer level — there are no end-to-end serving numbers (tokens/s per user, SLO-constrained throughput), so the impact on, say, a DeepInfer-style deployment is extrapolated, not measured. The 2.4× over DE+DG also partly conflates the communication win with different GEMM backends (Prims-TS with MXFP4 weights vs DeepGEMM); the clean comm-only comparison is the 1.2–3.0× all-to-all result.
- **Red flags:** mild. (1) The scope restriction to a single NVLink domain excludes exactly the multi-node regime where DeepEP's hierarchical NVLink+RDMA design matters, so the baseline is being compared on the authors' home turf (DeepEP was run with "the settings of its own tests", the right gesture, but its low-latency kernels are RDMA-oriented). (2) The FP8-combine accuracy claim is one sentence with no task names or numbers. (3) Kimi-K3 on 64 GPUs is missing ("–") because Prims-TS needs ≥k experts per rank (14 < 16), quietly revealing a compute-backend constraint inside a communication paper. (4) SENTINEL's advantage is engineered to evaporate exactly where MegaMoE's fusion wins, so no single method dominates the full batch range — the paper says so, but a reader of the abstract alone ("up to 2.4×") could over-generalize.

## Strengths

- Attacks the correct bottleneck for MoE decoding: fixed synchronization and layout-conversion costs rather than raw bandwidth, supported by an IKET-based breakdown that shows SENTINEL shortens the work *around* the peer wait, not the wait itself.
- The rank-major layout gives two compounding wins — bytes (de-duplication to min(k, P) sends per token) and memory (workspaces ~6× smaller than DeepEP V2.5 + DeepGEMM's expert-major GEMM input) — while remaining GEMM-compatible via TMA gather4 slot indexing.
- Clean separation of concerns: communication is decoupled from quantization format and MoE backend behind FlashInfer's MoEEpCommunication, and the design composes with CUDA graphs + PDL; both protocols include timeouts so a failed peer traps instead of hanging the engine.
- Comprehensive ablation surface: two protocols, two models with very different k (6 vs 16), 1–4096 tokens/rank, Zipf skew, payload-format sweep (BF16/MXFP8/FP8/NVFP4 dispatch, FP8 combine), and 8→64 GPU EP scaling on NVL72, with full latency tables in the appendix.

## Limitations

- Single NVLink domain only: both protocols rely on direct peer loads/stores and whole-32-bit-word arrival, which RDMA does not provide; cross-node EP is out of scope, and the dispatch workspace (one region per source rank) grows linearly with EP size.
- Loses to the fused MegaMoE from 256 tokens/rank (up to 35% slower at 4096) because separate kernels cannot overlap communication with Tensor Core work; the fused one-sided variant is left as future work.
- SENTINEL's per-slot overhead (write, poll, copy-out, reset of P·T̂ expert-id slots per step) grows with batch, forcing the FENCE/SENTINEL crossover at 256 tokens/rank and a per-batch protocol choice.
- Layer-level microbenchmarks with synthetic (perfect or Zipf) routing; no end-to-end serving results, no accuracy table for FP8 combine, and evaluation limited to Blackwell-class hardware (B300, GB200 NVL72).
- The Prims-TS grouped GEMM requires at least k experts per rank, which blocked the Kimi-K3 64-GPU configuration (896/64 = 14 < k = 16).

## Relevance

直接命中"高效 LLM 推理系统"方向：MoE 解码批次的 dispatch/combine 延迟是当前 EP serving 的核心瓶颈，本文给出已在 FlashInfer3/vLLM/SGLang/TensorRT-LLM 落地的通信原语与两种同步协议设计，对理解 NVLink 对称内存、单侧通信与低精度传输在推理内核中的工程权衡非常有参考价值。

## Questions for Further Exploration

- How does NVLinkOneSided compose with a multi-node hierarchy — could SENTINEL-style in-band completion be adapted to GPU-initiated RDMA (GIN) where word-arrival guarantees are absent, or is a hybrid NVLink-domain + RDMA-tier design the only path?
- What are the end-to-end serving gains under a real SLO (e.g., DeepSeek-V4.1-Flash decode at ~250 tokens/s/user with speculative decoding), where router distributions, KV-cache pressure, and non-uniform per-rank token counts deviate from the perfect-routing microbenchmark?
- How large is the accuracy cost of FP8 combine (per-element E4M3) across downstream tasks and larger k (e.g., Kimi-K3's 16 partial sums), given the paper's single qualitative claim?
- Would a fused one-sided variant (dispatch + grouped GEMM + combine in one persistent kernel, as sketched in future work) preserve the metadata-free rank-major push while closing the ≥256-token/rank gap to MegaMoE, or does fusion inevitably reintroduce layout coupling?
- How does SENTINEL's broadcast of expert-id slots to all P peers scale to NVL144-class domains (P = 72–144), where the P·T̂ polling/reset cost per step grows quadratically in aggregate traffic?
- Can the slot-counter-free deterministic landing (token i → slot i) be combined with dynamic expert replication or capacity-factor overflow handling under extreme Zipf skew without re-introducing a metadata exchange?
