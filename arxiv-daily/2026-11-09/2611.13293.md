> **一句话总结：** NVIDIA 与德州农工提出的 TKNP 解码架构将"权重放置"与"注意力所有权"解耦——稠密层（QKV/输出投影 + MLP）只在持有该层块权重的单节点内以 NVLink 域内 TP 执行，而每个节点对自己所属请求的本地 KV cache 做请求级并行注意力——在 vLLM 上以 Llama 3.1 405B（64 张 H100）实测，长上下文高并发解码的完成吞吐最高达 DCP 的 1.7 倍、数据并行的 2.06 倍，且 KV 容量是 DP 的 5.0 倍。

> **TL;DR:** A decode-pool parallelism for prefill–decode-disaggregated serving that shards one balanced copy of model weights across nodes as layer blocks (dense projections/MLP run on the weight-owning "active root" with intra-node TP8) while every node computes attention for its own requests against locally owned KV cache, so only current-token activations cross InfiniBand and dense all-reduces stay on NVLink. Implemented in vLLM and measured on Llama 3.1 405B with RULER long-context workloads (32K/64K/96K, 1,024 output tokens) on up to 64 H100s, TKNP reaches up to 2.06× the completion throughput of a DP baseline (N independent TP8 replicas) and up to 1.7× over vLLM's DCP at matched GPU count, with 5.0× DP's usable KV capacity on 8 nodes; DP still wins at low concurrency, and Nemotron-4 340B gains are smaller (1.54× over DP, 1.32× over DCP at 64K context).

## 核心贡献

- **解耦权重放置与注意力所有权**：利用"注意力对 KV cache 的计算不含参数"这一事实（所有可学习参数都在投影和 MLP 里），请求属主节点只需收到当前 token 的投影后 Q/K/V 即可独立完成完整注意力，无需跨节点合并部分 softmax 结果，也无需复制模型权重。
- **平衡的层块权重放置**：把单一模型副本按权重字节数（含端点参数与量化差异）切成连续层块分给各节点（每节点约 1/N 权重），使全网节点获得近似相等的 KV cache 预算——8 节点上可用 KV 容量约为 DP 的 5.0 倍，与 PP/DCP 等容量最优布局持平。
- **通信效率**：跨节点通信收缩为匹配 TP rank 之间的点对点 scatter/gather（按请求+注意力头双维度切分），单个 gather 张量约为跨节点 TP all-reduce 操作数的 1/(N·T)（Llama 3.1 405B、batch 128、4 个 TP8 节点上为 128 KiB vs 4 MiB），稠密 all-reduce 全部留在 NVLink 域内。
- **双活跃根微批（dual-active-root microbatching）**：以移位放置存第二份权重（每节点 2/N），两个微批由不同活跃根服务、共享 worker 交替做注意力以填充稠密计算间隙，吞吐再提升最高 11.1%（对 DCP 优势从 1.53× 升至 1.7×）。
- **系统级实测**：在 vLLM 0.19.0 上实现并以 Llama 3.1 405B / Nemotron-4 340B、最多 64 张 H100（FP8 权重 + BF16 KV）对 DP/TP/PP/DCP 四类基线做等 GPU 数对比，并验证贪心解码下输出 token 与 DP 基线完全一致。

## Key Contributions

- **Decouples weight placement from attention ownership.** Because attention over the KV cache is parameter-free (all layer weights live in the projections and MLP), a request's owner node only needs the projected Q/K/V of the current token; each node computes complete attention for its own requests against its resident KV cache, with no cross-node merging of partial attention results and no weight replication.
- **Balanced layer-block weight placement.** A single model copy is split into contiguous layer blocks balanced by weight bytes (including endpoint parameters and quantization differences), giving every node an approximately equal KV budget — usable KV capacity reaches 5.0× that of DP on 8 nodes, on par with PP and DCP, while avoiding TP's KV-head replication.
- **Token-parallel communication analysis.** Cross-node traffic reduces to peer-wise scatter/gather of projected head-space tensors between matching TP ranks (sharded by request and head, volume independent of context length); each TKNP gather is 1/(N·T) of the full-batch hidden-state operand a cross-node TP all-reduce would move (128 KiB vs 4 MiB for Llama 3.1 405B at batch 128 on four TP8 nodes), and DCP's per-rank partial output (512 KiB) shrinks 75% to 128 KiB per remote TKNP owner.
- **Dual-active-root microbatching.** A second, shifted weight copy (block b on nodes b and (b+N/2) mod N; each node stores ≈2/N of the model) gives every block two candidate roots; two microbatches with distinct roots overlap one batch's attention with the other's dense computation, adding up to 11.1% throughput when the pool is large enough (≥8 nodes) that partial weight replication is affordable.
- **At-scale evaluation in vLLM.** Implemented on vLLM 0.19.0 (dedicated inter-node communication groups, owner-aware scheduler with per-owner KV budgets, CUDA-graph replay over the distributed decode path) and compared against DP, TP, PP, and vLLM DCP at matched GPU counts on Llama 3.1 405B and Nemotron-4 340B, FP8 weights with selected parameters in BF16, on up to 64 H100 GPUs, with greedy-decoding token equivalence verified against DP.

## Methodology

TKNP targets the **decode pool** of a prefill–decode disaggregated serving stack; an external prefill server (fixed 2-node TP8×DP2 in all experiments) writes each request's initial KV cache directly onto its assigned decode owner in TKNP's head layout.

**Architecture (single-copy).** The decode pool has N nodes × T GPUs. Each node stores one stationary, contiguous block of layers (≈1/N of model weights) sharded across its local TP ranks. For layer ℓ, the weight-owning node becomes the *active root* b(ℓ): it runs QKV projection, output projection, and MLP for the **full batch** using intra-node TP (preserving weight-read amortization across the whole batch). Independently, every node is the *owner* of a subset of requests: it holds those requests' complete KV cache for every layer (heads sharded across its TP ranks), applies RoPE, appends the new K/V, and computes complete attention for its requests at every layer — attention thus spans heads within nodes and requests across nodes.

**Per-layer execution.** Root scatters projected QKV tensors of shape [B_g, (H_q+2H_kv)d_h/T] to each owner g; owners return attention outputs of shape [B_g, H_q/T, d_h]; root gathers them in batch order and finishes output projection, norms, residual, and MLP. Block boundaries pass hidden + residual activations to the next weight-owning node, which becomes the new root; weights and KV cache never move. Root's own requests incur no network transfer.

**Scheduling.** Capacity-aware request assignment sends each waiting request to the eligible node with the lowest KV load (by current usage or reserved context length); ownership is fixed until completion, so no KV migration; because decode attention cost scales with resident KV length, balancing KV load also balances per-layer attention time.

**Communication model.** With balanced assignment B_g ≈ B/N, per-layer scatter/gather payload per matching-rank group is C_ℓ = 2s(H_q+H_kv)d_h·ΣB_g/T — versus DCP, which all-gathers FP32 log-sum-exp statistics and reduce-scatters corrected partial outputs for the full batch; TKNP's per-owner output tensor is ≈1/N of DCP's (Eq. 5). Versus dense TP spanning nodes, each TKNP gather is 1/(N·T) of the [B, D] all-reduce operand.

**Dual-active-root microbatching.** For even N, block b is stored on nodes b and (b+N/2) mod N, yielding two distinct roots per block; the batch splits into two microbatches, each request keeping one owner for all layers; shared workers alternate attention between microbatches, overlapping one root's dense phase with the other's attention. Costs: second weight copy (KV capacity ↓), extra scheduling/synchronization, smaller dense batches.

**Evaluation setup.** vLLM 0.19.0, PyTorch 2.9.1, CUDA 12.9, NCCL 2.27.5, FlashAttention-3, Linux 5.15.0-88; nodes of 8×80 GB H100 (4th-gen NVLink, dual Sapphire Rapids) linked by 8×400 Gb/s InfiniBand; decode pools of 4 or 8 nodes (32 or 64 GPUs). Baselines at matched GPU count: DP (N independent TP8 replicas), TP (spanning all 8N GPUs), DCP (TP8N + DCP-N, since vLLM's DCP reuses the TP group), PP (TP8 per stage, ~N microbatches). Workloads: synthetic RULER with fixed ISL (32K/64K/96K) and 1,024 output tokens at batch 4–128 with prefix sharing disabled, plus a mixed-length pool from L-Eval + LongBench v1 + LongBench v2 (8,223–126,848 tokens; mean 32,898, median 19,048) under Poisson arrivals (0.5/1/2 req/s) and synchronized bursts. Metrics: completion throughput (all output tokens / release-to-drain wall time, including admission waves), queue wait, p95 active-request ITL, mean completion time, and a 100 ms/output-token completion SLO.

## Results & Highlights

- **Completion throughput vs DP:** On Llama 3.1 405B with RULER 64K-context workloads on 32 H100s (batch up to 128, 1,024 output tokens), TKNP improves completion throughput by **up to 2.06× over the DP baseline** (N independent TP8 replicas) at matched GPU count; DP leads below the capacity-crossover point (small batches / short contexts).
- **Completion throughput vs DCP:** On the same model at 32K context on 64 H100s (8-node decode pool), single-copy TKNP beats vLLM DCP by up to **1.53×**, and dual-active-root microbatching raises this to **1.7×** — a capacity-matched comparison (both ≈5.0× DP's usable KV capacity on 8 nodes), so the gain comes from distributed-execution efficiency, not extra cache. On Nemotron-4 340B at 64K context on 32 H100s, TKNP achieves up to **1.54× over DP and 1.32× over DCP**.
- **Scaling efficiency:** Doubling the decode pool from 4 to 8 nodes for the 128-request/32K Llama 3.1 405B workload raises single-copy TKNP throughput by **1.81× (90.5% scaling efficiency)** versus **1.37×** for DCP, whose attention aggregation and dense collectives span the larger inter-node group.
- **Microbatching gain:** Dual-active-root microbatching adds **up to 11.1%** throughput over single-copy TKNP, largest at high concurrency (and shifts the DCP speedup from 1.53× to 1.7×), at the cost of a second weight copy (~2/N of the model per node) and reduced KV capacity.
- **KV capacity:** Usable KV capacity for Llama 3.1 405B is **5.0× DP on 8 nodes** (4.4× on 4 nodes, 3.3× on 2 nodes) for TKNP ≈ PP ≈ DCP; motivation: a TP8 node spends 454 GiB on FP8 weights leaving only 106 GiB for KV, while batch 128 at 32K needs 2,016 GiB of BF16 KV — 19× one node's budget.
- **Microbenchmarks justifying the split:** at batch 128/32K, attention is ~70% of single-layer decode latency; TP1→TP8 cuts attention latency 7.6× (5.38→0.71 ms) but TP64 adds nothing (KV-head limit = 8); a batch-128 MLP all-reduce costs 6.5× more at TP64 than TP8 and end-to-end MLP latency rises 55%; four PP microbatches of 32 cost 3.17× one batch-128 MLP invocation.
- **Communication volumes:** for Llama 3.1 405B at batch 128 on four TP8 nodes, each TKNP remote-owner gather moves **128 KiB** vs DCP's **512 KiB** per-rank partial output (75% reduction); each gather is 1/(N·T) of the 4 MiB cross-node TP all-reduce operand. DCP additionally exchanges 8 KiB LSE statistics per rank; TKNP instead dispatches 144 KiB of QKV per remote owner.
- **Tail latency / SLO under mixed lengths:** on the L-Eval + LongBench v1/v2 mixed workload (8.2K–126.8K tokens; 12.5% of requests >64K contribute 36.1% of input tokens) at a 100 ms/output-token completion SLO, TKNP achieves **full (100%) SLO attainment at 1 request/s while DP and DCP both fall below 90%**, and retains higher attainment at 2 req/s alongside the highest throughput at every arrival rate.
- **Correctness:** under greedy decoding, TKNP's generated tokens match the DP baseline exactly.

## Critical Assessment

- **Novelty** is real but incremental in spirit: request-level attention ownership already exists in SGLang's data-parallel attention and Helix; TKNP's distinctive move is *balancing a single weight copy across the same nodes that own KV* so every node contributes both KV capacity and attention bandwidth. The cleanest idea in the paper is exploiting the fact that attention is parameter-free, which makes weight/attention placement orthogonal.
- **Rigor** is generally strong (capacity-matched DCP comparison, matched prefill config, identical arrival traces), but the DCP baseline is only as good as vLLM's implementation, which forces DCP-N to ride on a TP8N group whose dense collectives cross InfiniBand — a coupling the authors themselves identify, and they explicitly propose fixing it (balanced layer-block placement for DCP) as future work. Some of TKNP's 1.7× over DCP may therefore be recoverable by a better DCP rather than being intrinsic to request-parallel attention; the paper is honest about the mechanism but the headline framing doesn't stress it.
- **Workload quirks:** prefix sharing is disabled throughout the evaluation; production traffic with shared system prompts would change the KV-capacity arithmetic that drives TKNP's advantage. The fixed-length RULER experiments dominate, with only one mixed-length benchmark pool and Poisson/burst arrival rates of just 0.5–2 req/s.
- **Nemotron-4 340B uses linear RoPE scaling beyond its original context window**, so those runs "characterize decode performance rather than long-context accuracy" (their own caveat) — the model is being run outside its trained regime purely as a load generator.
- **Reproducibility:** stack versions and configurations are reported in detail, but no code or artifact release is mentioned, and the hardware (H100 + 8×400 Gb/s InfiniBand) is inaccessible to most academics; the paper also acknowledges that larger NVLink domains (e.g., NVLink-switched pods) would shift the intra-/inter-node communication balance that TKNP's design exploits.
- **Overclaiming check:** headline numbers are "up to" 2.06×/1.7× at the highest concurrency points; the paper does show and discuss the regime where DP wins (low concurrency, short context), which is commendable, but a deployment summary should note the crossover rather than the peak.
- **Missing ablations:** no isolation of scatter/gather overhead as a function of interconnect bandwidth (e.g., degraded or Ethernet-only links), no sensitivity study of layer-block granularity or of the KV-load balancing heuristic under skewed request lengths, and the adaptive scheduler that would replace dual-root microbatching's memory cost is deferred to future work.

## Strengths

- A crisp, well-measured diagnosis: dense layers amortize weight reads across the batch and belong inside one NVLink domain, while attention cost grows with every active request's KV cache — supported by single-layer latency breakdowns (attention ≈70% of layer latency at batch 128/32K; MLP latency grows only 1.24× from batch 1→128 vs 22× for attention).
- The design follows directly from the diagnosis, and each mechanism (balanced blocks, capacity-aware ownership, request-parallel attention) is justified with concrete tensor-shape communication math rather than hand-waving.
- Dense all-reduces stay on NVLink and attention needs no cross-node partial-result merging — a genuinely clean point in the design space relative to TP-spanning-DCP.
- Evaluation at real scale (405B parameters, 64 H100s, FP8) against four baseline families at matched GPU counts, with an apples-to-apples capacity-matched DCP comparison and a greedy-decoding output-equivalence check.
- Honest reporting of the DP-favorable low-concurrency regime and of microbatching's memory/complexity costs.

## Limitations

- TKNP only pays off for long-context, high-concurrency decode pools; at small batches or short contexts, per-layer scatter/gather synchronization can outweigh the benefit (stated by the authors).
- Dual-active-root microbatching trades KV capacity (second copy, 2/N weights per node) and adds scheduling/synchronization complexity for a ≤11.1% gain.
- Dense (non-MoE) models only; combining TKNP with expert parallelism to remove data-parallel-attention weight replication in MoE serving is left to future work, as is supporting requests whose KV cache exceeds a single node (DCP-style sharding remains necessary there).
- Single hardware point: H100 nodes over InfiniBand; larger NVLink domains would rebalance the interconnect hierarchy the design leans on.
- Prefix sharing disabled in all experiments; long-context *accuracy* not addressed (Nemotron runs beyond its native context via linear RoPE scaling); no prefill-side or TTFT analysis.

## Relevance

对"大规模机器学习的计算基础设施"方向高度相关：TKNP 的核心正是推理侧的通信与互连设计（NVLink 域内 collectives vs 跨节点 InfiniBand scatter/gather、张量级通信量分析）和解码池的容量感知调度，直接服务于长上下文高并发 LLM 服务这一基础设施难题。

## Questions for Further Exploration

- How much of TKNP's 1.7× advantage over DCP survives once DCP is decoupled from vLLM's TP-group coupling using the authors' own suggested balanced layer-block placement — i.e., is request-parallel attention intrinsically better, or better-placed?
- How does the design behave with realistic prefix sharing (shared system prompts, prefix caching), and can capacity-aware assignment be extended to prefix-aware placement to recover lost KV dedup?
- What happens on Ethernet-only or lower-bandwidth interconnects — is the scatter/gather volume (independent of context length) small enough to keep TKNP ahead, and where is the bandwidth knee?
- Can adaptive schedulers that jointly weigh KV occupancy and attention cost capture the dual-root overlap benefit without the second weight copy's memory cost?
- Does the parameter-free-attention argument extend to MoE serving combined with expert parallelism, eliminating attention-weight replication in data-parallel attention designs like Helix?
- How do speculative decoding and multi-token verification interact with the per-layer scatter/gather path — can draft tokens be batched into the same transfers to amortize synchronization?
