Plumbline: When the Loss Lies, Validating LLM Training Correctly ↗

Ruochen Wen · Hongyang Wang · Siwei Li · Wenbo Chen · et al. (11 authors, Amazon)

  • LLM training correctness

Key metric · Day-0 scan

32/ 61 problems

were silent — the run kept training with a falling loss. 3 frameworks × 5 MoE models scanned; 42 fixed or reported upstream, 8 first raised here.

Why this matters

Silent faults train and serve the wrong model while dashboards stay green — reusable checks and a failure taxonomy for exactly this class. 静默数据腐化 + 极限性能优化下的可靠性：损失照常下降，训练出的却是错误模型。

Critical edge

No false-negative analysis — the paper never quantifies what the checks miss, and one silent fault sailed through convergence checks. Plumbline finds many silent faults; it does not certify correctness.

01Methodology

  • Premise: validate each run at the exact configuration its user trains with — faults can need a specific setting or many steps to appear.
  • Lifecycle checks (exact / bitwise): container image commit; collectives vs closed form; data pipeline vs the official chat template + tokenizer; build & load vs the official release with NaN-prefilled params so a skipped weight shows; bitwise save/resume; lr=0 export must equal the checkpoint bitwise; optimizer step recomputed in fp32/fp64.
  • Architecture (step check): per-layer-group one-step gradient error s vs the model's own fp32 Hugging Face reference on CPU — sharing no kernel, layout, or packing with the framework. Fail when s > 4·max(F1, F2): F1 = run-to-run noise floor, F2 = bf16-vs-fp32 precision floor.
  • Convergence: published recipe dry-run on GSM8K, then 100-step runs on three workloads — Tülu 3, Dolci-Think-SFT, LongReward-10k.
  • Fixed verdicts: pass/fail rules frozen per system version — the agent cannot redefine correctness; a human approves plans; a second agent rebuilds findings; inconclusive never passes; bounds validated by fault injection.
  • Scope: 3 frameworks (AutoModel, Megatron-SWIFT, Miles) × 5 MoE models = 13 combinations, on B200 nodes, Sept–Oct 2026.

  • Transposed experts (gpt-oss-20b, MXFP4): loading transposed all 32 experts' down projections — loss started at 17.08 vs 1.48, still fell, and passed convergence checks.
  • Resume drift (GLM-5.3-Flash): optimizer lost its step count — 3.7% loss drift vs 0.02% run-to-run noise (~185×), caught bitwise.
  • Stuck AdamW (bf16 in-place): 92% of sampled weights a step should change kept their value, loss looked normal.
  • Double reduction (DeepSeek-V4-Flash): query-norm weights received 8× their correct gradient at tensor-parallel 8.
  • 8-node OOM → 1 node: reproduced in ~3 min; a closed-form memory formula matched all 16 logged OOM requests; root cause in ~0.5 node-hours vs a cited 34.7 engineer-hour average.

Lifecycle + architecture checks caught 29 of the 32 silent faults first; ≥16 of those sat in runs that passed convergence checks. 50 of 61 diagnoses reached the exact code; 27 causes lay in framework dependencies, 28 in model-specific parts.

03Strengths

  • References chosen outside the code under test — the official release, not the framework's own runs — closing the shared-fault blind spot of TrainCheck / TrainVerify / OpGuard-style differential checking.
  • Empirically separated threshold: clean ≤3.44× vs defective ≥4.35× around the 4× bound, plus fault injection against tolerances that could hide a fault.
  • Identical checks and rules across all 13 framework–model combinations — modularity that actually paid off.
  • Diagnosis by reuse: 8-node OOM reproduced on 1 node in ~3 minutes, root cause in ~0.5 node-hours.
  • Honest reporting — per-pattern silent counts, first-found attribution, dependency causes, candid AI-usage disclosure.

04Limitations

  • Every check needs a trusted reference — DeepSeek-V4.1-Flash has no HF training implementation, so its layers get no step-check verdict; Day-0 degrades exactly where models are newest.
  • Step check runs only the model's first layers; depth-dependent faults fall to convergence checks, which caught just 1 silent fault in 21 problems.
  • No quantified false-negative rate; the transposed-experts run passed a whole check level.
  • Human-in-the-loop by design — not autonomous.
  • Self-reported evaluation: Sept–Oct 2026, 5 MoE models (no dense), internal Amazon infrastructure; tool not yet released; total Day-0 scan cost unreported.
  • Convergence gate judges "followed recipe, trained stably" only — loss level and prior-run comparison are not part of the verdict.

05Questions for further exploration

  • What is the false-negative rate if a known taxonomy of silent faults were deliberately seeded into the 13 combinations?
  • What does a full Day-0 scan cost in GPU node-hours, and how does it scale with the settings swept?
  • Can "one setting changed vs unchanged recipe" be promoted to a trusted verdict with a formal bound?
  • Do the seven failure patterns transfer to dense models, RL post-training (GRPO/PPO), and pretraining scale?
  • How would agent-invented checks be validated without the human reviewer becoming the bottleneck?
  • Could the bitwise save-resume and exact data checks become upstream CI gates in Megatron-LM / export paths?
