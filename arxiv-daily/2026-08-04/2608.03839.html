TRAINING-FREE SPECULATIVE DECODING · LLM INFERENCE · AGENT / TOOL-CALLING

Oilbird.

Training-free speculative decoding with keys the verifier already computes.

Tao Jin · Phuong Minh Nguyen · Zhenzhu Yan · Teeradaj Rachapat · Naoya Inoue 　JAIST & Tohoku University
◆ Key finding

The strongest exact-match drafters don't have a coverage problem — they have an addressing problem. About half of what they miss is already in the pool, just lexically unreachable. Oilbird tags each committed token with the hidden state the verifier already computed (a copy, never an extra forward) and re-keys the same pool, turning "present but unreachable" into "matched."

Key metric
4.4×
wall-clock speedup on API-Bank, Llama-3.1-8B — the fastest drafter in the harness, trained or not.
SuffixDecoding (best training-free) — 3.88× EAGLE-3 (trained draft model) — 2.03× GOOSE (host tree decoder) — 2.37×
Why this matters

A lossless, training-free speedup that drops into an existing multi-source tree decoder. No draft model to train, no verifier change, no relaxation — the new semantic source rides inside the tree's own 60-node budget.

Critical edge
  • Headline is on API-Bank, the most repetitive benchmark. EAGLE-3 beats Oilbird on all 5 non-repetitive workloads.
  • Advantage dies above batch ~8–16; the key is negative per-node-bought in 19 of 20 batched cells. Batch-1 tool only.
  • Store grows unbounded (~8 KB/token, ~2.6 GB on longest run); eviction is future work.

01

Diagnose first, design second.

可识别性差距

Before proposing anything, the authors measure what the strongest exact-match drafter actually misses on the traffic itself — no drafter in the loop. Across 10 benchmarks and 2 model families they find that the problem is addressing, not coverage: roughly half of the missed tokens are already sitting in the pool, the lexical key just can't reach them. They call this the identifiability gap.

92%
of positions have their next two tokens present verbatim in a strictly-past trace (API-Bank).
6.8%
of generated positions are the gap — present in the pool but lexically unreachable.
80.8%
of those gap positions the per-position hidden-state key recovers (Llama-3.1-8B).
22.6%
recovery from a static token-embedding key — i.e. per-position granularity is the point.

Each gap position is followed by a 6.4-token verbatim run a neighbour could match. So the missing signal isn't one stray token — it's whole phrases the drafter walks past because the suffix doesn't align. That asymmetry is what makes a per-position semantic key worth its retrieval tax.

02

The method, in four moves.

四步：存储 · 检索 · 合并 · 验证

Oilbird is one extra draft source slotted into GOOSE (the authors' multi-source tree decoder, to appear at COLM). The whole point is that the new source costs no extra forward pass — the hidden state it keys on was already computed by the verifier.

STORE

(x_i, h_i) per committed position

One record per token the verifier commits. h_i is the hidden state at layer ℓ = round(0.85L), normalized to half precision (~8 KB/token at 8B). Filled by serving — a copy, not a forward. Prompts are never stored; a request can't draft from itself.

RETRIEVE

Per-position, similarity-sized

Query top-8 by cosine whenever lexical match is non-empty — extending a chain, never opening one. Threshold θ=0.8; copy depth D(s) = 48 if s≥0.90; 8 if s≥0.82; 0 else. Self-calibration mutes the key where its drafts rarely land.

MERGE

Budget-neutral, root-rewalking

Each retrieved chain re-walks the lexical tree from the root and only pays for divergent nodes: cost(γ,T)=|γ|−π(γ,T). Semantic chains get a fixed reservation of 16 of 60 nodes, taken out of (not added to) the lexical allocation. Root-attachment measurably underperforms (Table 5).

VERIFY

One masked-greedy forward

The whole tree is covered by a single forward; the longest accepted path is committed with its bonus token. The same forward supplies both the store's hidden states and the recycled rejected-branch pool — verification is unchanged and greedy.

The honesty is notable: the authors describe the semantic key as the smallest of the three sources (outweighed 1.9–5.3× by the lexical ones) and call it an "extender, not a drafter" — it can't open chains on its own. That framing is the opposite of the headline-chasing you usually get from a speedup paper.

05

Where it does — and doesn't — work.

边界与代价
◇ Where it pays
  • Highly repetitive tool-calling traffic — API-Bank, ToolAlpaca, τ-bench: the same situations recur, so the pool is rich and the gap is wide.
  • Batch-1 interactive serving — the regime every reported headline lives in.
  • As an extender on top of a lexical drafter — that's the role it was designed for, and the only role it claims.
  • Structured / templated output — the "frame + minted value" pattern the key exploits is even more pronounced in JSON/SQL.
⚠ Where it costs
  • Chat, math, open-ended text — EAGLE-3 leads Oilbird on all 5 non-repetitive workloads (Table 6); GSM8K moves only +1.1%.
  • Batched serving — speculation's edge falls from 1.3–1.6× (batch 1) to 0.8–1.1× (batch 32).
  • Long-running deployment — store grows unbounded; eviction / index / quantization explicitly future work.
  • Per-tenant governance — hidden states aren't encryption; the store is effectively a cache of user content, ~2.6 GB on the longest benchmark.
  • Constant retrieval tax — 4.8–5.8% of every verification cycle, paid whether the key fires or not (mostly the rejected-branch pool).

The applicability is bounded by sole-source share: above ~9% the semantic arm beats GOOSE; below ~3% it loses. That's a refreshingly precise statement of where the method stops helping.

06

Red flags worth probing.

需追问的可疑点

The evaluation hygiene is above the norm for the subfield (token-for-token auditing, bootstrap CIs, leakage-excluded pools), but four points deserve scrutiny before accepting the headline at face value.

P1

The headline 4.4× is on API-Bank — the single most repetitive benchmark — and EAGLE-3's 2.03× there is suspiciously low versus its 2.93× on ToolAlpaca and its wins on every non-repetitive workload. The comparison may flatter Oilbird precisely where its design is strongest.

P2

EAGLE-3 numbers come from the authors' own re-runs, not EAGLE-3's authors. The protocol note is transparent, but a reader can't fully rule out an unfavourable re-run. How sensitive is Oilbird's lead to running EAGLE-3 in its own released harness?

P3

There's an asymmetric benchmark cell: EAGLE-3's API-Bank speedup uses the full 597-request set while some Qwen cells are 100-request subsets under a 4096-token KV cap. Apples-to-apples is not guaranteed across every row.

P4

No code release is mentioned and the audit script is internal. Independent replication depends on reconstructing GOOSE's tree machinery — a non-trivial dependency that the speedup numbers themselves don't surface.

Open questions the paper itself raises: does the gap close under sampling decoding (where losslessness is already relaxed)? Can the store be bounded without collapsing the 80%+ gap recall? Does the key still help once a trained drafter joins the tree as a fourth source, or does the trained model already cover the gap positions the semantic key recovers?
