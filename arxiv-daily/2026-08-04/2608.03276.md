> **一句话总结：** TaskPress 提出以任务级"元查询"(task guide) 替代具体用户查询来引导 KV cache 剪枝，并复用量化 scale factor 作为 Value 重要性的零开销信号，在 LongBench 与 RULER 上以最高 16× 压缩（int4 + 75% 剪枝）显著超越 SnapKV / PyramidKV / KVZip 等基线，同时支持缓存跨查询复用、避免每查询重复 prefill。

> **TL;DR:** TaskPress is a task-guided, query-agnostic KV cache eviction framework that compresses context once (using a high-level "meta-query" task guide plus repurposed quantization scale factors) and reuses the compressed cache across many downstream queries, achieving the best average accuracy on LongBench (LLaMA-3.1-8B: 46.42 vs KVZip 44.76 vs SnapKV 43.03 at 50% eviction) and the best accuracy at 75% eviction on RULER-16K (68.4 vs KVZip 62.2 vs SnapKV 42.8), with an 80× lower eviction latency than context-reconstruction baselines and only a 1.2% TTFT overhead.

## 核心贡献

- **任务级而非查询级的剪枝视角**：将 KV cache 压缩从"查询时"前移到"任务时"，用一段自然语言任务指南（task guide）作为元查询，构造一次性、跨查询可复用的压缩缓存，避免查询相关方法（SnapKV / PyramidKV / Quest）每个新查询都要重做 prefill 的问题。
- **量度 scale factor 复用为零开销信号**：把 KV 量化（int4）每 token 已算好的 scale factor γᵢ 当作 Value 通道异常值的代理，无需额外计算；该信号与注意力图近正交（Pearson 0.06±0.23），与 value norm 强相关（0.79±0.10）。
- **乘性 Key×Value 重要度融合**：Key 重要性来自任务指南对 context 的平均池化交叉注意力，Value 重要性来自 scale factor，二者相乘同时要求"任务可检索 + 语义信息丰富"。
- **针对未知任务的进化式任务指南发现**：用 GEPA 风格的进化算法（K=2, N=3, G=4 代）从少量校准查询自动推断任务意图，约 25.2 分钟一次性离线成本，使方法可用于开放域部署。
- **极低开销的端到端实现**：任务指南长度 Lt≪Lc，复杂度 O(Lt·Lc) 相比 KVZip 重建法 O(Lc²) 带来约 80× 加速；64-token 任务指南在 75% 剪枝下 TTFT 仅 +1.2%。

## Key Contributions

- **Task-time (not query-time) pruning paradigm**: reframes KV cache compression around a reusable task-level "meta-query" rather than a specific user query, so one compressed cache serves an entire stream of future queries aligned with the task.
- **Zero-cost Value importance via quantization reuse**: repurposes the already-computed per-token quantization scale factor γᵢ = max(|vᵢ|)/(2^(b-1)−1) as an outlier / Value-norm proxy, removing any extra forward computation; this signal is shown to be near-orthogonal to the attention map.
- **Multiplicative Key×Value scoring**: final retention score sᵢ = sᵢ^key · sᵢ^value forces tokens to be both task-retrievable (high Key score from task-guide cross-attention) and semantically rich (high Value outlier score).
- **Evolutionary task-guide discovery for unknown tasks**: a GEPA-style prompt optimizer (top-K=2 selection, N=3 offspring, G=4 generations, ~25 min offline) infers a meta-query purely from a small calibration query set when the task cannot be named a priori.
- **Negligible-overhead deployment**: O(Lt·Lc) eviction (Lt≪Lc) vs O(Lc²) for context reconstruction (KVZip), yielding ~80× lower eviction latency and only +1.2% TTFT at 75% eviction with a 64-token guide.

## Methodology

TaskPress operates in four stages during a single prefill:

1. **Task-Guided Key Importance (Sec 3.2).** A natural-language task guide T (length Lt) is appended to the context (length Lc). The attention map A ∈ ℝ^(Lt×Lc) between the guide and context is sliced out; per-context-token Key importance is the average over the Lt task rows plus a 1D average pool of kernel size K to capture local dependency (Eq. 1). The guide's own KV is evicted immediately after prefill, so it never participates in decoding.

2. **Value Importance from Quantization Scale (Sec 3.3).** Under standard per-token int4 quantization, the scale factor γᵢ = max(|vᵢ|)/(2^(b-1)−1) is already in memory from the serving pipeline. Because the bit-width b is constant, γᵢ ∝ max(|vᵢ|) and is used directly as sᵢ^value — a strictly zero-overhead outlier score.

3. **Multiplicative KV Scoring (Sec 3.4).** The retention score is sᵢ = sᵢ^key · sᵢ^value (Eq. 3). The product (vs. normalized add or harmonic mean) is shown to win in an ablation (e.g., RULER-4K: multiply 65.81 vs normalized-add 59.90 vs harmonic-mean 64.14). The top-|I| indices are kept per head with a uniform budget.

4. **Task Guide Formulation (Sec 3.5).** Two modes:
   - *Zero-shot initialization (3.5.1)*: prompt an off-the-shelf LLM (Gemini) with "Generate a task guidance for {task} in 2–3 sentences." This already serves as a strong static baseline.
   - *Evolutionary discovery (3.5.2)*: for unknown tasks, an LLM mutator (Gemini-2.0-Flash) runs Algorithm 1 over a small calibration set Dcal, using mutation + crossover prompts; the fitness is downstream task accuracy. The whole loop costs ~25.2 min once (41.4 s of API + ~1459.7 s of local calibration on a single A100 40GB).

Combined with int4 KV quantization (4×) and 75% eviction, the total compression reaches 16×. Implementation is built on the public `kvpress` repository, so all baselines (SnapKV, PyramidKV, StreamingLLM, ExpectedAttention, ThinK, KVZip) share the same harness.

## Results & Highlights

- **LongBench / LLaMA-3.1-8B (Table 1), 14-task average.** At 50% eviction TaskPress scores **46.42** vs KVZip **44.76** vs SnapKV **43.03** vs PyramidKV **40.83** (+3.39 over SnapKV, +1.66 over KVZip). At 75% eviction TaskPress scores **43.08** vs KVZip **38.24** vs Expected Attention **38.22** vs SnapKV **39.37** (+3.71 over SnapKV, +4.84 over KVZip). At 75% eviction combining TaskPress with ThinK (each 50%) reaches **44.70**.
- **LongBench / Qwen3-8B (Table 1).** At 50% eviction TaskPress **45.15** vs SnapKV **42.78** vs KVZip **44.21**; at 75% TaskPress **42.68** vs SnapKV **38.82** vs KVZip **38.00** (+3.86 over SnapKV).
- **LongBench / Qwen3-32B (Table 2), Single+Multi-Document QA.** TaskPress+ThinK **42.57** vs SnapKV **35.95** vs KVZip **35.74** — at 32B scale the gap widens to +6.62 over SnapKV.
- **RULER-16K / LLaMA-3.1-8B (Table 4), 13-subtask average.** At 75% eviction TaskPress **68.4** beats KVZip **62.2**, SnapKV **42.8**, PyramidKV **39.2**, ExpectedAttention **44.1** (+6.2 over KVZip). At 50% eviction TaskPress **79.0** is second to KVZip **85.3** — TaskPress trades a small accuracy gap for a far cheaper pipeline.
- **Eviction latency (Fig. 4, left).** TaskPress achieves roughly an **80× latency improvement** over KVZip's context reconstruction, because eviction is O(Lt·Lc) vs KVZip's O(Lc²).
- **Prefill cost (Table 6), 64K context, 64-token guide.** TTFT rises only **+1.2%** (9.66s → 9.78s) while peak memory drops **−15.1%** (38.55 GB → 32.72 GB).
- **Decoding cost (Table 5).** At 75% eviction TPOT falls **35%** (50.1 → 32.8 ms/token) and throughput rises **53%** (19.9 → 30.5 tokens/sec).
- **Multi-query end-to-end latency (Table 7), 8K context, 75% eviction.** At 200 queries TaskPress takes **48.06 s** vs query-dependent latency-optimized **50.24 s** and memory-optimized **115.39 s** (+2.18 s / +67.33 s gains). TaskPress also uses **236.88 MB** of KV cache vs **1,184.4 MB** for the latency-optimized query-dependent strategy (5× smaller, because the latter holds both full and compressed caches).
- **Evolutionary refinement (Table 3).** Evolving the known zero-shot guide adds up to **+3.08** on Qasper (LLaMA-3.1-8B) and **+1.88** on HotpotQA (Qwen3-8B); evolving from scratch on unknown tasks still matches SnapKV (e.g., HotpotQA 58.49 vs 57.45).
- **Scale-factor-as-Value-norm proxy (Sec 4.3.2).** Pearson correlation of γᵢ with the value norm is **0.79 ± 0.10** while its correlation with the attention map is **0.06 ± 0.23** — i.e., complementary, near-orthogonal signals that the multiplicative score exploits.
- **Robustness (Tables 10–13).** Accuracy is stable across guide-source models (Gemini / Claude / ChatGPT all within ~1.2 points on NarrativeQA), across synonym-level and sentence-level paraphrases (std <1% on NarrativeQA, ~1.3% on Qasper), and across moderate task drift (HotpotQA guide on NarrativeQA loses only ~0.7–1.8 points).

## Critical Assessment

- **Novelty (genuine).** The conceptual move from *query-dependent* to *task-time, query-agnostic* pruning is a real and useful reframing for multi-query/multi-turn serving, and the trick of reusing quantization scale factors as a Value-outlier signal is both novel and elegantly zero-cost. The Key×Value multiplicative score is incremental but well-motivated by the 0.79 / 0.06 correlation argument.
- **Rigor (strong, with caveats).** Ablations are unusually thorough — Key vs Value, score unification (multiply / normalized-add / harmonic-mean), guide source model, granularity, paraphrasing, task drift, MK-2/3 failure analysis with measured attention mass (3.01×10⁻⁴ in MK-1 collapses to 1.2×10⁻⁵ in MK-2, below the 5.0×10⁻⁵ background noise). However, the evolutionary optimization in Table 3 repurposes **50 calibration samples from the test set** because "LongBench lacks a dedicated validation split" — the authors exclude them from final eval, but with no held-out validation this risks mild overfitting of the evolved guide and is the single weakest methodological point.
- **Reproducibility (high).** Public `kvpress` base, exact prompts, hyperparameters, and guides in the appendix. The one external dependency is the Gemini API for guide generation/mutation (paid, non-deterministic), though Table 10 shows the source model barely matters.
- **Significance (high for serving, moderate for single-turn).** The headline wins are largest precisely where query-dependent methods hurt most: multi-query / multi-turn workloads (Table 7). For one-shot single-query inference the advantage over SnapKV is real but smaller, and at 50% RULER TaskPress (79.0) actually loses to KVZip (85.3) — the paper is honest that the 75% regime is where TaskPress clearly leads.
- **Red flags / overclaiming.** The "**5× memory**" framing in Sec 4.2.4 is somewhat favorable: it compares against the *latency-optimized* query-dependent strategy, which by design retains both the full and compressed caches. The fairer comparison (memory-optimized) is also reported, but the 5× headline could be misread. The MK-2/3 collapse is a genuine failure mode that the authors own and explain via attention dilution rather than hide. The "+80× latency improvement" is against the quadratic KVZip baseline only, not against SnapKV-style methods.
- **Coverage gaps.** LongBench is heavily weighted toward QA and summarization; code, structured reasoning, and agentic long-context workloads are not evaluated, leaving open how task-guided pruning behaves when the "task" is itself ill-defined (e.g., open coding assistance).

## Strengths

- Decouples compression from the query, enabling genuine cache reuse across turns/queries — a property uniquely valuable for production serving.
- Zero-cost Value importance signal: the int4 scale factor is already computed by every modern quantized serving stack, so the gain is essentially free.
- Strongest results exactly at the aggressive 75% eviction / 16× total compression regime where competing methods degrade sharply (e.g., RULER 68.4 vs SnapKV 42.8).
- Negligible prefill overhead (+1.2% TTFT) and large decoding gains (−35% TPOT, +53% throughput) make the method deployment-ready.
- Excellent ablation discipline: every design choice (multiply vs add, Key-only vs Key×Value, guide source, granularity, paraphrase, task drift) is tested, and the MK-2/3 failure is analyzed at the attention-mass level.

## Limitations

- **Task-dependent, not fully task-agnostic.** If a user query drifts outside the guide's semantic scope (e.g., a coding question in a summarization session), the compressed cache can be insufficient; Table 13 quantifies this degradation.
- **Attention dilution in dense-needle settings.** On RULER MK-2/MK-3 the target-key attention mass collapses below background noise (1.2×10⁻⁵ vs 5.0×10⁻⁻⁵ mean), dropping MK-2 to 10.6 and MK-3 to 1.0 at 75% eviction — by far the worst in the table.
- **Reliance on quantization statistics.** In full-precision (FP16/BF16) deployments the scale factor must be computed on-the-fly; the authors show this adds only ~2.7% (0.26 s on a 64K prefill), but it slightly undercuts the "zero-cost" claim for non-quantized serving.
- **Evolution cost and external dependency.** The ~25-minute evolutionary search calls the Gemini API and is a one-time offline cost, but it still requires a paid external model and a calibration query set that, for LongBench, had to be carved out of the test set.
- **Benchmark coverage.** LongBench/RULER emphasize QA, summarization, and retrieval; behavior on code, math, and agentic long-context tasks is untested.

## Relevance

对长上下文 LLM 推理效率、KV cache 压缩与服务系统方向高度相关：TaskPress 的"任务级元查询 + 量度 scale factor 零开销复用"思路为多查询/多轮部署场景提供了可落地的缓存复用方案，且复用了主流 int4 量化栈，可作为后续 long-context serving、Agent 记忆压缩等研究的重要基线与启发。

## Questions for Further Exploration

- How does TaskPress behave on non-QA long-context workloads (code completion over large repos, multi-step math, agentic tool-use traces) where the "task" is itself emergent rather than summarizable in 2–3 sentences?
- Can the evolutionary guide discovery be replaced by a gradient-based soft-prompt optimizer, or by learning the guide from query embeddings without an LLM mutator, to remove the paid API dependency?
- Does the multiplicative Key×Value score generalize to channel-wise pruners (ThinK, Quest) beyond the specific combination tested, and is there a principled (information-theoretic) justification for multiplication over the harmonic mean?
- How sensitive is the method when queries drift *gradually* within a long conversation (not the abrupt cross-task drift in Table 13) — is there a cheap online signal to detect when the compressed cache must be rebuilt?
- Can the MK-2/3 attention-dilution failure be repaired without abandoning query-agnosticism, e.g., by a second-stage dense-token rescoring using the actual query only when entropy of the guide's attention exceeds a threshold?
