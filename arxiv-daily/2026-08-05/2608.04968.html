EvolveNet: Collaborative Harness Evolution for Agent Self-Improvement

Jun Nie · Yonggang Zhang · Qianshu Cai · Yiu-ming Cheung · Xinmei Tian · Bo Han
HKBU & USTC & HKUST · github.com/junnie00/EvolveNet ↗

Data-local agents evolve and compose executable harness edits — not weights — into one shared program, lifting accuracy 8.3–33.4 points.

Why this matters

Extends test-time harness evolution from single-agent to parallel multi-client collaboration — reframing federated agent improvement as a program-composition problem, not a communication-efficiency one.

Critical edge

Harness growth is unbounded under the gate — it ballooned 14 → 253 lines in 3 rounds with no mechanism retirement, leaving long-horizon accumulation (T≫3) entirely untested.

How it works

SPECIALIZE → AGGREGATE → REDISTRIBUTE

A recurring three-phase loop. A frozen model and K data-local clients; each client holds a workload Dk that cannot be pooled.

① Specialize
client-side · parallel

Every client branches from the same shared harness h⁽ᵗ⁾ and evolves a specialist on its local shard. Returns a program diff, not a workload.

② Aggregate
server-side

Decomposes diffs into "mechanisms," attaches per-item behavioral evidence, classifies each by scope, and composes them in place on one byte-for-byte copy.

③ Redistribute
commit gate

Candidate survives only if |Fval| ≥ |Bval| on a disjoint validation slice — else one revision, then rollback. Shared base stays invariant.

Setup: solver = deepseek-v4-flash · K=5 clients (3 on LCB) · T=3 rounds · child processes pinned to a fixed hash seed so "a score difference reflects a behavioral difference, not sampling noise." A static auditor rejects any candidate touching the model, endpoint, credentials, or gold.

What crosses the wire

▼ prior · centralized / fed.

Pool workloads, or federate weights / adapters / text insights — the unit is data or parameters.

▲ EvolveNet · this work

Broadcast one harness; federate program diffs — a few hundred lines, kilobytes, model-size-independent.

▲ consequence

The aggregation space is a programming language; whether two contributions combine is a fact about execution, not arithmetic.

The core technical move — scope-typed adoption

Source-code edits have no arithmetic mean and single harmless edits can conflict when combined. EvolveNet turns winner-take-all conflicts into conditional coexistence by typing each mechanism's scope:

GLOBAL

Evidence spans ≥2 domains or fixes a domain-independent failure (malformed output, execution error). One shared implementation.

HOME(dk)

Evidence lies in exactly one client's domain — entered as a guarded branch keyed on the observed dispatch key. Copied verbatim.

⊥ REJECT

Evidence is a single item — a one-question quirk, not a mechanism. Discarded.

Strengths & limitations

honest, specific — does not overclaim
+ Strengths
  • Conceptually clean reframing of federated agent improvement around an executable shared artifact — not parameters, adapters, or text insights.
  • Scope-typing (GLOBAL / HOME / reject) turns winner-take-all conflicts into conditional coexistence — a genuinely new move with no parameter-space counterpart.
  • Exceptional measurement hygiene: pinned hash seed, full-request caching, paired per-item tests with Holm correction, pre-registered gold audit.
  • Honest limitations that don't overclaim — the wall-clock comparison admits collaboration "does not make a fixed budget cheaper" but makes a larger search affordable.
  • Five diverse settings with a natural specialization axis; largest gains appear where workloads are most heterogeneous.
  • Full artifact transparency: prompts, adoption-rule text, shard definitions, and excluded-item lists all released.
− Limitations
  • Supervised, not label-free. Labels drive client-side selection and server-side gating — not comparable to label-free test-time evolution.
  • Requires a labeled, representative validation slice plus an inference-time-observable dispatch key — stronger than typical federation.
  • Bounded empirical scope: only T ≤ 3 rounds, K ≤ 7 clients; long-horizon accumulation and bloat control are open.
  • Aggregator comparisons are single-snapshot, counterfactual within one round — no multi-seed end-to-end replay.
  • Locality ≠ privacy: program edits may leak client-specific info; no threat model or leakage quantification provided.
  • BIRD gold ambiguity (9/40 hard items) caps reachable score; gold audit is a single LLM pass.
  • HOME-scope isolation (Props. 1–2) holds only for the subset of edits respecting the no-shared-state hypothesis; reported merges rewrite shared prompts outside it.

Open questions

where the paradigm must prove itself next
Q1 · LONG-HORIZON

Does behavior hold at T ≫ 3? Can a size-/latency-aware gate or automated mechanism retirement keep the harness from bloating (already 14 → 253 lines)?

Q2 · KEY LEARNING

Can the dispatch key κ(x) be learned at inference when unobservable — and does Proposition 1's isolation guarantee survive imperfect estimation?

Q3 · PRIVACY

How much client data leaks through edits? What threat model + mitigation (diff sanitization, canary DBs) would turn locality into real privacy?

Q4 · GLOBAL CONFLICTS

Does scope-typing extend to conflicting GLOBAL mechanisms — beyond arbitrate-by-evidence — e.g. per-input runtime selection between two global impls?

Q5 · REPLAY

Would multi-seed end-to-end replay of each aggregation variant change the Table 3 ordering, given the single-snapshot caveat?

Q6 · LABEL-FREE

Can the paradigm work without a server validation slice — using self-consistency or execution-based surrogate verdicts for the commit gate?
