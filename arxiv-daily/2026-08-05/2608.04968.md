> **一句话总结：** EvolveNet 提出"协作式 harness 演化"范式——把共享 harness 广播给数据本地的多个 agent 部署，各 client 在本地并行演化出专家程序，服务器再用"证据引导 + 作用域类型化"的方式聚合程序差分（而非工作量/权重），在五个基准上将共享 harness 提升 8.3–33.4 个百分点，且在最异构的 DS-1000 上 68.5% 的成绩既超过保留 K 个专家做路由（64.0%），也超过集中式演化（67.3%）。

> **TL;DR:** EvolveNet reverses centralized harness evolution: it broadcasts a shared harness to K data-local clients that each evolve a specialist, then aggregates the *program adaptations* (not workloads or weights) via evidence-guided, scope-typed composition. On BIRD, DS-1000, LiveCodeBench, SWE-bench Verified, and ClawEval it lifts the shared harness by +13.4/+13.0/+33.4/+20.0/+8.3 points over the unevoled harness, beats routing (delegation 64.0% vs. EvolveNet 68.5% on DS-1000), and beats equal-budget centralized evolution (67.3% vs. 70.7% on BIRD) while keeping every workload local.

## 核心贡献

- **提出"协作式 harness 演化"新范式**：把经验抽取从中心化优化器移到数据本地的 agent 部署中。系统边界上流转的对象从"含经验的工作量"变为"学到的可执行程序适配"，从而让分布式经验在一个共享 harness 中累积，同时多条本地演化轨迹可以并行展开（§4）。
- **识别并解决程序聚合这一核心技术难题**：与参数空间聚合不同，源代码编辑没有算术平均，且单看无害的编辑在组合后可能冲突、冗余或失效。EvolveNet 设计了**证据引导 + 作用域类型化（scope-typed）**的聚合算子，相对公共基线对 harness 差分进行分解，把跨域证据支撑的机制提升为 GLOBAL、把单域证据的机制条件化为 HOME(dk)，从而把许多"冲突"转化为条件共存（§4.3，含 Proposition 1、2 关于作用域隔离的陈述）。
- **建立剥离本地演化随机性的评估协议**：用"成对（paired）评估"——把竞争性的聚合规则施加到同一份本地演化出的 client 快照上，再用逐题翻转（per-item flip）和 McNemar/Wilcoxon 检验做结论，而非靠总分排名（§5、§6.1、§6.4）。
- **设计行为级承诺门控与回滚**：聚合产物在独立验证片上必须满足 |Fix| ≥ |Brk| 才提交，否则允许一次修订，再失败则回滚到上一轮共享 harness，保证提交轨迹在该准则下非递减（§4.4）。
- **跨五个设置验证可累积性与可扩展性**：并行 client 阶段的串行深度由最慢分支而非求和决定，整网传输量仅是几百行程序（KB 级），且多 client 配置不掉点（§6.8、Fig. 3）。

## Key Contributions

- **A new paradigm — collaborative harness evolution.** Instead of pooling workloads into one optimizer, EvolveNet broadcasts a shared harness to data-local clients, lets each evolve a specialist on its own workload, and aggregates only the returned *program adaptations*. This decouples experience extraction from workload centralization and lets distributed experience accumulate in one shared executable artifact while parallel local searches reduce serial depth (Eq. 3, 7).
- **Evidence-guided, scope-typed program aggregation.** The central technical contribution: because source-code edits have no arithmetic average and can conflict, the aggregator diffs each client against the common base, decomposes deltas into "mechanisms," attaches per-item behavioral evidence (Fk newly-solved, Bk newly-broken), assigns each a GLOBAL / HOME(dk) / reject scope (Eq. 13–14), and composes them in place. Two propositions formalize scope isolation and disjoint-scope conflict resolution (Props. 1–2).
- **Behavioral commit gate with rollback.** A candidate merge is committed only if on a disjoint validation slice |Fval| ≥ |Bval| (Eq. 17); otherwise one revision, then rollback to the previous shared harness — preserving the invariant that every round starts from one shared program state.
- **A paired evaluation protocol** that applies competing aggregation rules to one identical client snapshot, isolating the rule's effect from the σ≈3-point run-to-run client-quality variance (Sec. 6.1, 6.4).
- **Empirical demonstration across five heterogeneous settings** that adaptations compose (not just route), experience accumulates across agents, and the benefit transfers to a different model stack.

## Methodology

EvolveNet runs a recurring **SPECIALIZE → AGGREGATE → REDISTRIBUTE** cycle (Algorithm 1), instantiating the local-evolution loop of TTHE (Nie et al., 2026) with an LLM proposer that edits harness source from execution traces.

- **Setup.** A frozen model M and K data-local clients; client k holds workload Dk that cannot be pooled. Objective: a single shared harness h⋆ maximizing accuracy on a target distribution Ptarget, using only local evolution + server aggregation. The accessible mixture is Pclient = Σ πk Pk; Ptarget may include domains held by no client.
- **Local evolution (client side).** Each round t, every client receives the same h^(t), applies a local evolution operator E on its shard, and returns a specialist h_k^(t) with the invariant S_k(h_k) ≥ S_k(h^(t)) (the broadcast is always retained in the candidate pool). Clients are assigned distinct proposer roles (conservative repair / independent exploration / adversarial audit) by index to avoid converging on the same edits.
- **Common-base program deltas.** Because all clients branch from h^(t), each contribution is ∆k = diff(h^(t), h_k^(t)). The aggregator edits a byte-for-byte copy of h^(t), decomposing deltas into semantically coherent "mechanisms" (a retry rule, a schema probe, etc.).
- **Behavioral evidence.** Each delta is shipped with Fk (items the broadcast failed but the specialist solved) and Bk (items broken). Evidence constrains — but does not causally map to — line-level edits.
- **Scope-typed adoption (Eq. 14).** GLOBAL if evidence spans ≥2 domains or addresses a domain-independent failure mode (malformed output, execution failure); HOME(dk) if evidence lies in exactly one client's domain — entered as a guarded branch keyed on the observed dispatch key κ(x); ⊥ (reject) if evidence is a single item (a one-question quirk). HOME-scoped edits are copied verbatim rather than paraphrased. Propositions 1–2 state the exact isolation conditions under which home-scoped mechanisms cannot interfere off-domain.
- **Adoption procedure (5 steps).** Diff → read traces → group edits into mechanisms with credited items → classify scope → compose (one GLOBAL impl, HOME guards, both sides of disjoint-scope conflicts retained; only GLOBAL conflicts arbitrated by graded evidence).
- **Commit gate (Eq. 17).** Candidate ĥ^(t+1) compared item-by-item against h^(t) on a disjoint validation slice; committed iff |Fval| ≥ |Bval|; one revision allowed on failure, else rollback. Gate consumes only per-item verdicts, so it can be computed without centralizing validation items (each client returns two integers).
- **Preserving the shared base.** Existing prompt rules are treated as load-bearing invariants; new mechanisms are integrated as localized extensions, and program growth is budget-constrained.
- **Implementation.** Frozen solver = deepseek-v4-flash (also drives proposers and the merger); K=5 clients (K=3 on LiveCodeBench); T=3 rounds; E=G=1 per round; replies cached on full request, child processes pinned to a fixed hash seed so score differences reflect behavior not sampling noise. A static auditor rejects any candidate that changes the model, endpoint, credentials, or reads gold at inference.

## Results & Highlights

- **Main held-out accuracy (Table 1), unevoled → EvolveNet after T=3 rounds:** BIRD **57.3% → 70.7% (+13.4)**, DS-1000 **55.5% → 68.5% (+13.0)**, LiveCodeBench **33.3% → 66.7% (+33.4)**, SWE-bench Verified **37.5% → 57.5% (+20.0)**, ClawEval **65.8 → 74.1 (+8.3)** mean task score. All five gains significant under paired tests (McNemar on binary benchmarks, Wilcoxon on ClawEval): BIRD p=5.4e-4 (win 26/lose 6), DS-1000 p=6.2e-6 (win 30/lose 4), LCB p=2.0e-3 (win 10/lose 0), SWE-V p=0.021 (win 9/lose 1), ClawEval p=0.022 (better 18/worse 7); all survive Holm correction.
- **Aggregation beats routing (Table 3, DS-1000, identical client snapshot):** EvolveNet scope-typed merge **68.5%** vs. delegation (keep K programs, dispatch) **64.0%** (win 15/lose 6), vs. GLOBAL-only merge **66.5%**, vs. select-best client **59.5%**. The composition contribution is real: GLOBAL-only alone already exceeds delegation, and domain conditioning adds a further +2.0 points.
- **Improvement over strongest single client everywhere (Appendix E):** EvolveNet beats select-best end-to-end on all five settings; margins widen with workload heterogeneity — from +1.4 on BIRD (eleven databases share one task shape) to +23.4 on LiveCodeBench. Combined via Fisher's method p=0.0027.
- **Experience actually accumulates across agents (Sec. 6.5):** On DS-1000 the five clients' gains union to 20 held-out items; the merged harness retains **18 (90.0% retention)**, including items solved by exactly one parent client. Two items are solved by the merged harness and by no individual client — composition produced behavior no single trajectory reached. On Pytorch (a domain no client trained on) EvolveNet solves 10/15 vs. 8/15 for the unevoled harness and select-best.
- **Beats centralized evolution at equal budget (Sec. 6.6, BIRD):** EvolveNet **70.7%** vs. equal-serial-depth centralized optimizer **68.7%** (its no-gating variant fails outright) and equal-total-budget centralized population (5 parallel branches × 3 rounds = 15 proposer sessions, matching EvolveNet) **67.3%**, which never improved on its first round's best branch.
- **Not tied to one model stack (Sec. 6.7):** Re-running the full BIRD pipeline with solver/proposer/merger swapped to MiMo-V2.5 reproduces every qualitative behavior; merged harness **72.7%** vs. select-best 72.0% vs. unevoled 62.7%.
- **Wall-clock scaling (Sec. 6.8):** Client phase parallelizes **1.93× (K=2), 3.96× (K=5), 5.37× (K=7)** vs. serial; full BIRD run K=5 takes 6110 s end-to-end while exploring five specialist trajectories. Per-client network payload is a few-hundred-line program (kilobytes), independent of model size.
- **Per-library DS-1000 breakdown (Table 2):** EvolveNet improves on every library including Pytorch (no specialist): e.g. Matplotlib 76.7→83.3, Sklearn 45.8→58.3, Scipy 42.9→61.9.

## Authors & Credibility

- Jun Nie (HKBU & USTC), Yonggang Zhang (HKUST), Qianshu Cai (HKUST & USTC), Yiu-ming Cheung (HKBU), Xinmei Tian (USTC), Bo Han (HKBU) — established ML research groups with a track record in this exact area (the authors are the same group behind TTHE: Test-time Harness Evolution, Nie et al. 2026, which EvolveNet builds on for its local loop).
- Code released at https://github.com/junnie00/EvolveNet. Prompts (specialist instruction, scope-typed adoption rule), shard/split sizes, audit criteria, and excluded-item lists are all released with the code — a high level of artifact transparency.
- Methodological discipline is unusually explicit: a pre-registered gold audit (criteria frozen 2026-07-22 before any end-to-end run), falsification-tested audit criteria, deterministic scoring (pinned hash seed + full-request caching) so that "a score difference reflects a behavioral difference rather than sampling noise," paired tests with Holm correction, and an honest variance measurement (Sec. 6.1) that sets the resolution of all downstream claims.
- BIRD served as the development benchmark where the operator/gate/loop were selected; DS-1000 was designated in advance as the primary confirmation benchmark; the operator was frozen and the remaining four settings run end-to-end once.

## Critical Assessment

- **Novelty:** High and well-articulated. The core move — shifting the aggregation boundary from raw workloads to executable program adaptations, then doing *program-space* (not parameter-space) aggregation — is genuinely different from FederatedSkill (skill diffs), Fed-SE (adapters), Federation over Text (insight libraries), and model merging (Task Arithmetic / TIES / DARE). The framing of "the aggregation space is itself a programming language, and whether two contributions combine is a fact about execution" is the paper's sharpest conceptual contribution.
- **Rigor:** Strong. The paired-snapshot protocol (Sec. 6.4) is the right experimental design for isolating an aggregation operator from σ≈3-point client-quality variance — the authors explicitly note that aggregate-score ranking would invert the true ordering on DS-1000 (select-best: 69% val / 59.5% test vs. merged: 63% val / 68.5% test). Deterministic scoring via hash-seed pinning and full-request caching is an engineering detail most papers omit but that is load-bearing for per-item claims.
- **Reproducibility concerns:**
  - The Table 3 aggregation comparison rests on a **single client snapshot per rule** — the authors acknowledge this and corroborate via Table 2 per-library breakdown and the §6.5 retention analysis, but multi-seed replay of the aggregator variants would strengthen it.
  - The paired comparison is explicitly a **counterfactual within one round**, not |variants| independent end-to-end runs (deliberate, but a scoping caveat).
  - Aggregation and gating depend on a labeled server-side validation slice representative of the deployment — a **stronger data requirement than parameter-space federation**, which the authors own up to in §7.
  - The BIRD held-out set is a **custom 150-item set** with an LLM-only gold audit (no independent human adjudication; an earlier stricter version rejected 60% with no discriminative power). The criteria and list are frozen and released, but the audit is still a single LLM pass, and 9/40 hard items have ambiguous gold that caps the reachable score.
- **Significance:** If the paradigm holds beyond T=3, K≤7, it reframes federated agent improvement: the shared artifact is a program, not a weight tensor, and the bottleneck becomes a program-composition problem rather than a communication-efficiency problem. The scope-typing principle (GLOBAL vs HOME(dk)) and evidence-grounded adoption are plausibly transferable to richer agent ecosystems.
- **Red flags / things to probe:**
  - **Artifact growth is unbounded under the gate as defined.** The BIRD shared harness grew 14 → 253 lines and DS-1000 grew 17 → 409 over three rounds; "nothing in the current gate penalizes a merge that ties on accuracy while adding lines." A strict tie-rejecting gate is *not* the fix (replay forgoes 14 DS-1000 / 5 LCB items), but the lack of a size/latency-aware gate or mechanism retirement means long-horizon accumulation (T≫3) is untested and the harness may bloat into unmaintainability.
  - **Domain conditioning depends on an observable dispatch key** κ(x) at inference. This is fine for databases/libraries/repositories but on LiveCodeBench the key is benchmark-difficulty metadata — a property of that benchmark, not of real deployments where the domain label may be unknown or ambiguous. The paper flags this but it limits generality.
  - **The "HOME-scoped mechanisms cannot interfere off-domain" guarantee (Props. 1–2)** holds only under stated hypotheses (no state writes read outside the guard, no prompt text touched outside it). The §6.9 merge reports show the aggregator does rewrite shared prompt structure in some cases (e.g., adopting a second client's SQL-dialect fix into the first client's retry structure), so the propositions are aspirational guarantees on a subset of edits, not on the whole merge.
  - **Locality ≠ privacy.** Program edits can encode client data (the paper itself shows "a probe hard-coded to one client's schema"). No threat model or leakage quantification is provided; the locality framing should not be read as a privacy claim.
  - **Marginal on the most homogeneous benchmark.** On BIRD, the lead over equal-budget centralized evolution (70.7 vs. 67.3/68.7) is within one noise band; the authors are honest about this ("within one noise band, but the mechanism difference is visible in the artifacts"), but it means the headline BIRD gain over centralized baselines is not individually decisive.

## Strengths

- Conceptually clean reframing of federated agent improvement around an *executable* shared artifact rather than parameters, adapters, or text insights.
- The scope-typing idea (GLOBAL vs HOME vs reject) turns winner-take-all conflicts into conditional coexistence — a genuinely new move with no parameter-space counterpart.
- Exceptional measurement hygiene: pinned hash seed, full-request caching, paired per-item tests with Holm correction, pre-registered gold audit, and an explicit variance measurement that calibrates every downstream claim.
- Honest, specific limitations section that does not overclaim (e.g., the wall-clock comparison admits collaboration "does not make a fixed budget cheaper in absolute wall-clock" but makes a larger search affordable at bounded serial depth).
- Five diverse settings with a natural specialization axis (databases, libraries, repositories, task families, difficulty bands), and the largest gains appear exactly where workloads are most heterogeneous — matching the theory.
- Full prompt and adoption-rule text, shard definitions, and excluded-item lists released.

## Limitations

- **Supervised, not label-free.** Labels are used for client-side candidate selection and server-side gating; numbers are not comparable to label-free test-time harness-evolution work.
- **Requires a labeled, representative server-side validation slice** and an inference-time-observable dispatch key — both stronger requirements than typical federation.
- **Bounded empirical scope:** only T ≤ 3 rounds and K ≤ 7 clients observed; long-horizon accumulation, mechanism retirement, and bloat control are open.
- **Aggregator comparisons are single-snapshot, counterfactual** within a round; no multi-seed end-to-end replay of each aggregation variant.
- **Locality is not privacy:** program edits may leak client-specific information; no threat model provided.
- **BIRD gold ambiguity** (9/40 hard items) caps reachable score; gold audit is a single LLM pass without independent human adjudication.
- **On the most homogeneous benchmark (BIRD)** the lead over centralized baselines sits inside the measured noise band; the decisive wins are on heterogeneous settings (DS-1000, LCB).
- **HOME-scope isolation guarantees (Props. 1–2)** hold only for the subset of edits that respect the no-shared-state hypothesis; the reported merges include shared-prompt rewrites outside that subset.

## Relevance

对关注"LLM agent 自我改进 / harness 演化 / 多智能体协作"方向的研究者高度相关：它把 test-time harness evolution 从单 agent 顺序改进扩展到多数据本地 client 的并行协作演化，并提出程序空间（而非参数空间）聚合这一新问题，可作为自演化智能体、联邦智能体系统、以及 agent 工程化（agent engineering）方向的参考基线与思路来源。

## Questions for Further Exploration

- How does EvolveNet behave at T ≫ 3 rounds? Does a size-/latency-aware gate or automated mechanism retirement keep the shared harness from bloating (BIRD already grew 14 → 253 lines in 3 rounds)?
- Can the dispatch key κ(x) be *learned* at inference when it is not observable (e.g., a domain classifier), and does Proposition 1's isolation guarantee still hold under imperfect key estimation?
- How much client-specific information leaks through program edits? What threat model and mitigation (e.g., diff sanitization, canary databases) would turn locality into a meaningful privacy guarantee?
- Does scope-typed aggregation extend to *conflicting* GLOBAL mechanisms — beyond the current "arbitrate by graded evidence" — for instance via per-input runtime selection between two global implementations?
- Would multi-seed end-to-end replay of each aggregation variant (Delegation / GLOBAL-only / EvolveNet) change the Table 3 ordering, given the single-snapshot caveat?
- Can the paradigm work in a label-free regime (no server validation slice) — e.g., using self-consistency or execution-based surrogate verdicts for the commit gate?
- How does EvolveNet compose with parameter-space federation if the underlying model is also being fine-tuned concurrently at each client?
