> **一句话总结：** OpenForgeRL 用一个轻量代理拦截 harness 的模型调用并记录为训练轨迹，再配合 Kubernetes 远程容器编排，使任意推理 harness（Codex/OpenClaw/Kimi-Agent 等）× 任意环境都能用 veRL/GRPO 端到端训练；仅用数百到数千任务训出的 OpenForge-Claw 和 OpenForge-GUI 在 ClawEval/QwenClawBench/MCPAtlas 与 OSWorld/Online-Mind2Web/WebVoyager 六项基准上几乎全面超过同等规模开源模型，GUI 设定下甚至追平数倍大的模型。

> **TL;DR:** OpenForgeRL is an open framework that makes any stateful inference harness (Codex, OpenClaw, ZeroClaw, Kimi-Agent, Molmo-Web) trainable end-to-end by inserting a lightweight proxy that intercepts and records the harness's LLM calls as RL trajectories, plus a Kubernetes orchestrator that runs each rollout in its own remote Azure container. Trained on only 343 claw RL tasks and 252/900 GUI RL tasks, OpenForge-Claw (30B-A3B) reaches 31.7 pass3 / 55.9 pass@3 on ClawEval (vs. Qwen3-Coder-30B-A3B's 30.4 / 49.7) and 33.7 on QwenClawBench (vs. 24.3), while OpenForge-GUI (8B) hits 37.7 on OSWorld-Verified (vs. UI-TARS-1.5-7B's 27.4) and 63.0 on Online-Mind2Web (vs. MolmoWeb-8B's 35.3), matching or beating models several times larger while exposing that simpler harnesses learn far better than complex ones and that RL improves self-verification but not error recovery.

## 核心贡献

- 提出 **OpenForgeRL**：一个 plug-and-play 的训练接口，由两个轻量组件构成——(1) 一个包裹推理服务器、拦截 harness 所有生成请求并记录 prompt-response 对的 **proxy**；(2) 一个基于 Kubernetes（建立在 Orchard 之上）、在 Microsoft Azure 上弹性创建/销毁 rollout 容器 pod 的 **orchestrator**。两者把任意 harness × 任意环境接入标准 RL 代码库（如 veRL），消除"训练-部署不一致"。
- 在 6 个基准上做了广泛实证：文本工具/Claw 域（ClawEval、QwenClawBench、MCPAtlas）与多模态 GUI 域（OSWorld-Verified、Online-Mind2Web、WebVoyager），几乎在所有基准上超过同等规模开源模型，GUI 设定下追平或超过数倍大的模型。
- 配套一个**数据/任务合成 pipeline**（propose→prune→build→test→refine），用真实资产池种子化、用独立 LLM/VLM 验证每个任务端到端可执行，缓解 claw/computer-use 等数据稀缺域的训练数据问题。
- 利用"在真实部署 harness 中训练"这一特性，首次系统分析 **harness 选择与 RL 如何塑造 agent 行为**：简单、对齐良好的 harness（ReACT/ZeroClaw）远比复杂的（OpenClaw/Codex）易学；单 harness 训练可迁移到未见 harness，多 harness 同时训练更佳（Codex 上 +20.3）；RL 把通用 shell 调用从 22.6% 降到 13.9%、提升 self-verification 与 tool coverage，但 error recovery 依然薄弱。
- 承诺开源代码、数据与模型。

## Key Contributions

- **OpenForgeRL framework**: a plug-and-play rollout interface with (i) a lightweight proxy that wraps the inference server, intercepts every generation request issued by a harness container, and reconstructs standard training samples `τ = (s0^H,a0,r0),...,(sT^H,aT,rT)` with discounted reward `rt = γ^(T-t)·rT` (γ=1.0), and (ii) a Kubernetes orchestrator (built on Orchard) that elastically manages rollout container pods on Microsoft Azure, keeping rollouts decoupled from training nodes.
- **Broad empirical validation across 6 benchmarks** spanning text tool/claw agents and multimodal GUI (browser + computer-use) agents, beating similar-size open models on nearly all benchmarks and matching or surpassing models several times larger in the GUI setting.
- **A task/environment synthesis pipeline** (propose → prune → build → test → refine) that grounds candidate instructions in real assets (ClawHub, X API, AgentNet, Synthetic-Computer-Use, WebGym), prunes duplicates, builds a Dockerfile + verifier per task, and iteratively patches defects until a separate open LLM/VLM passes it — yielding only hundreds-to-thousands of verified tasks but strong signal.
- **First systematic study of how harness choice and RL shape agent behavior**, enabled by training in real deployment harnesses: simpler harnesses (ReACT/ZeroClaw) are far easier to learn than complex ones (OpenClaw/Codex); single-harness training transfers to unseen harnesses and multi-harness training is best; RL improves reliability (self-verification, tool coverage, plan completion) but error recovery stays weak.
- Code, data, and models pledged to be released.

## Methodology

OpenForgeRL targets the two structural obstacles that keep harness-based agents off-limits to open training stacks: (1) harnesses turn inference into a stateful, multi-process procedure (nested tool calls, subagents, long-horizon context) that trainers cannot natively express, and (2) harness rollouts need dedicated containerized CPU/memory environments that cannot be co-located on training nodes at scale.

**Architecture (Figure 2).** Given an inference server (e.g., vLLM), OpenForgeRL launches:
- A **proxy server** that wraps the inference server, intercepts all generation requests from rollout containers, routes them to the RL framework's engines, and records the exchanged `(prompt, response)` pairs plus the terminal reward `rT` (typically task success).
- A **rollout orchestrator** (built on Orchard/Peng et al. 2026) that creates, allocates, and deletes Kubernetes container pods on cloud providers (Microsoft Azure), elastically scaling concurrent rollouts.

When a rollout finishes, trajectory reconstruction assembles the recorded pairs into standard samples `τ = (s0^H,a0,r0),...,(sT^H,aT,rT)` with `rt = γ^(T-t)·rT` (γ=1.0); for group-based algorithms like GRPO, advantage is computed by comparing average sample rewards across trajectories in the same group.

**Three practical challenges addressed:**
- *Rollout orchestration* — Kubernetes lifecycle management on Azure for elastic concurrency.
- *Asynchronous rollout & timeouts* — instead of capping turns (which Codex doesn't even expose and which is defined inconsistently across harnesses), a generous **wall-clock timeout** per rollout job; on timeout the job is terminated and an error signal returned so training keeps collecting from surviving rollouts.
- *Error handling* — following DAPO, trajectories ending in environment/harness/network errors (unrelated to policy) are discarded entirely, since a partial rollout can inject misleading signal (e.g., a correct prefix that gets a negative reward). Better credit assignment for partial rollouts is left to future work.

**Data synthesis pipeline (Section 3.3, Figure 3).** For data-scarce domains (claw, computer-use), a human-curation-like pipeline spawns parallel agents that (1) propose candidate instructions grounded in real reference assets (web/X API search, file DB, ClawHub, AgentNet's 22k instructions, Synthetic-Computer-Use assets); (2) prune low-quality/duplicate tasks; (3) build an executable environment (custom Dockerfile, virtual display via Xvfb for GUI) and a verifier script; (4) test by rolling out a separate open LLM/VLM; (5) refine defects until all checks pass. Each task ships as `task instruction + test.sh + artifacts + Dockerfile`, supporting both SFT (distillation from a stronger teacher) and RL.

**Training recipes.** Claw: Qwen3-30B-A3B-Thinking backbone, SFT distilled from MiniMax-M2.5 (N=3 rollouts/task, keep successes), then GRPO from the SFT checkpoint; 4 harnesses (ReACT, ZeroClaw, OpenClaw, Codex); 892 SFT / 343 RL tasks; veRL backend, Azure rollout cloud, batch 8, group 8, 8×B200 GPUs. GUI: Qwen3-VL-8B-Thinking backbone, SFT distilled from Kimi-K2.5; computer-use uses a modified Kimi-Agent harness with screenshot-only observations and added bash + str-replace-editor tools; browser-use adapts Molmo-Web (JSON action space, Browser-Use Stealth Browsers cutting CAPTCHA/IP blocks from 40% to ~0); 795 computer SFT / 252 RL tasks and 1496 browser SFT / 900 RL tasks.

## Results & Highlights

Concrete quantitative claims (all from the paper's Tables 2-5):

- **ClawEval (pass3 / pass@3, 2026-04-08 release):** OpenForge-Claw(SFT+RL) reaches **31.7 / 55.9**, up from OpenForge-Claw(SFT) **21.7 / 52.1** and from the Qwen3-30B-A3B-Thinking base **14.3 / 39.8**; it also beats Qwen3-Coder-30B-A3B-Instruct (**30.4 / 49.7**) and crushes similar-size dense baselines (LLaMA-4-Scout-17B 0.6/16.8, Mistral-Small-3.1-24B 3.1/19.3, Qwen3-32B 6.8/31.7). (Frontier closed models remain far ahead: Claude Opus 4.6 70.8/80.8, GPT 5.4 60.2/75.8.)
- **QwenClawBench (pass@1, solved with OpenClaw):** OpenForge-Claw(SFT+RL) **33.7** vs. OpenForge-Claw(SFT) 32.1, Qwen3-Coder-30B-A3B 24.3, and Qwen3-30B-A3B base 21.8.
- **MCPAtlas (pass@1, 89-task no-credential-server config, claim-coverage ≥0.75, Gemini 2.5 Pro judge):** OpenForge-Claw(SFT+RL) **28.1** vs. Qwen3-Coder-30B-A3B 19.1 and Qwen3-30B-A3B base 12.4.
- **OSWorld-Verified (pass@1, 30 steps):** OpenForge-GUI(SFT+RL) **37.7**, up from SFT 34.4, beating UI-TARS-1.5-7B (27.4), Qwen3-VL-8B (29.4), OpenCUA-7B (28.2); still well behind Kimi-K2.5 (63.3) and GPT 5.4 (75.0).
- **Online-Mind2Web (pass@1, AgentTrek protocol, o4-mini judge):** OpenForge-GUI(SFT+RL) **63.0**, a large jump from SFT 57.4 and far above Qwen3-VL-8B (38.7) and MolmoWeb-8B (35.3) — and notably achieved with only 2.5k tasks vs. MolmoWeb's 200k+.
- **WebVoyager (pass@1, GPT-4o judge):** OpenForge-GUI(SFT+RL) **72.3**, up from SFT 61.5 and above Qwen3-VL-8B (49.2) and UI-TARS-1.5-7B (66.4); here MolmoWeb-8B (78.2) still edges it out — the one benchmark where a same-size open baseline wins.
- **Harness difficulty (Table 4, ClawEval pass@1):** with SFT+RL, ReACT* **45.1**, ZeroClaw **48.5**, OpenClaw **20.9**, Codex **32.5** — OpenClaw is dramatically harder and gains only moderately from RL despite consuming far longer prompts.
- **Cross-harness generalization (Table 5, deltas over base):** ZeroClaw-only training lifts unseen OpenClaw **+3.3** and Codex **+4.6**; training on ZeroClaw+OpenClaw+Codex together lifts ZeroClaw to 48.5 (+16.0), OpenClaw to 20.9 (+9.5), and Codex to 32.5 (**+20.3**).
- **RL behavioral effects (Figure 5):** on ZeroClaw, generic shell calls drop from **22.6% → 13.9%** of all tool calls, redistributed to dedicated service tools, with average trajectory length shortening 13.0 → 12.2; on Codex, self-verification rises 54 → 60 and tool coverage 48.4 → 56.2, but error recovery stays the weakest capability (26 → 50 on a 0-100 scale, still lowest among measured capabilities).
- **Browser anti-blocking:** integrating Browser-Use Stealth Browsers cut CAPTCHA/IP-block rate from **40% → ~0%** during browser-use rollouts.

## Critical Assessment

- **Novelty:** The core technical idea — intercept harness LLM calls via a proxy + run rollouts in remote containers — is engineering rather than algorithmic novelty, and the authors say as much ("a first step towards designing a training flow that natively supports complex harnesses"). The genuinely novel contribution is the breadth (any harness × any environment including vision GUI) and the harness-behavior analysis that this enables; prior open work (and the noted concurrent Polar) covered only SWE-bench-style coding.
- **Rigor:** Evaluation is broad and mostly apples-to-apples, with careful protocol reuse (official ClawEval loop, OpenClaw for QwenClawBench, AgentTrek+o4-mini for Online-Mind2Web). However the headline comparisons are deliberately scoped to **similar-size open baselines** — against frontier closed models the gap is large (ClawEval pass@3: 55.9 vs. Claude Opus 4.6's 80.8; OSWorld 37.7 vs. GPT 5.4's 75.0), and the framing ("match or surpass models several times larger") is true only in the GUI setting and only against *open* larger models (e.g., Qwen3-VL 235BA22B at 38.1 OSWorld is essentially tied, not surpassed).
- **Cherry-picking / honest exceptions:** The authors are commendably honest that MolmoWeb-8B (78.2) still beats OpenForge-GUI (72.3) on WebVoyager — they say "nearly all benchmarks," not all. But Online-Mind2Web's +27.7 over MolmoWeb is the standout and deserves scrutiny: MolmoWeb's number (35.3) is borrowed from another paper under a possibly different protocol, while OpenForge-GUI uses AgentTrek+o4-mini.
- **Missing ablations:** There is no ablation isolating the proxy/trajectory-reconstruction design itself (e.g., effect of the wall-clock timeout threshold, the DAPO-style discard-all-on-error rule vs. partial-credit alternatives, or γ choice), and the partial-rollout credit-assignment problem is explicitly deferred. The data-synthesis pipeline is validated only end-to-end; there is no isolation of the test/refine stages' contribution.
- **"Open" framing caveats:** Although the framework is open-source, every SFT teacher and several evaluators are proprietary — MiniMax-M2.5 (claw SFT), Kimi-K2.5 (GUI SFT), GPT-4.1 (browser success judge), GPT-4o (WebVoyager judge), o4-mini (Online-Mind2Web judge), Claude Opus 4.6 (generating SKILL.md files for Codex/OpenClaw tool exposure). Reproducing the exact models therefore depends on paid API access; only the *training infrastructure* is fully open.
- **Data quirk:** MCPAtlas results rest on only **89 tasks** (the subset fully supported by the default 20 servers), so the 28.1 number is over a small, narrow slice; the paper is transparent about this but readers should weight it accordingly.
- **Reproducibility:** Strong on protocol documentation (harness versions, eval judges, thresholds all specified) and the data/code/model release pledge; weak on cost accessibility — training requires 8×B200 GPUs and Microsoft Azure rollout containers, putting it out of reach for most academic groups despite the "lowers the barrier" claim.
- **Red flags:** None severe. The harness naming (ZeroClaw/OpenClaw/ClawEval/QwenClawBench/ClawHub) appears to be a 2026-era rebrand of what readers may recognize as the MCP/tool-use assistant ecosystem; the heavy reliance on a synthetic data pipeline for the headline claw and computer-use gains is a mild concern about distribution match to real user tasks, though the test/refine loop mitigates it.

## Strengths

- Genuinely general: a single interface handles text tool-use, MCP servers, browser-use, and full desktop computer-use, with both LLM (30B-A3B) and VLM (8B) backbones — breadth rare in open agent-training work.
- Eliminates the train-deploy mismatch by training inside the real harness instead of a reimplemented simplified loop, which is the right architectural call and a prerequisite for the behavioral analysis.
- Data-efficient: GUI gains come from ~2.5k tasks vs. MolmoWeb's 200k+, and claw gains from only 343 RL tasks — strong evidence that harness-native RL extracts more signal per task.
- The harness-difficulty and cross-harness-generalization studies (Tables 4-5) are the most insightful part and are only possible because of the framework's harness-agnostic design.
- Honest reporting: explicitly admits WebVoyager loss to MolmoWeb, admits error recovery stays weak after RL, and scopes claims to similar-size open baselines rather than overclaiming against frontier closed models.

## Limitations

- Frontier gap remains large on every benchmark (e.g., OSWorld 37.7 vs. GPT 5.4's 75.0; ClawEval pass@3 55.9 vs. Claude Opus 4.6's 80.8) — the work narrows but does not close the open-vs-closed gap.
- Error recovery is the weakest learned capability even after RL; the authors hypothesize it needs dedicated data/methods, leaving this open.
- Heavy reliance on proprietary teachers/judges (MiniMax-M2.5, Kimi-K2.5, GPT-4.1/4o, o4-mini, Claude Opus 4.6) undermines the fully-open reproducibility story.
- High compute bar (8×B200 + Azure containers) limits who can actually run the pipeline.
- No ablation of the proxy/orchestrator design choices (timeout, error-discard, γ); partial-rollout credit assignment explicitly deferred.
- MCPAtlas headline rests on only 89 tasks; Online-Mind2Web's large delta comes against a borrowed MolmoWeb number possibly judged under a different protocol.
- Browser-use training depends on Browser-Use Stealth Browsers to bypass CAPTCHAs/blocks, which is a moving third-party dependency and a potential TOS gray area for real-website training.
- Concurrent work (Polar) overlaps in the software-engineering slice; OpenForgeRL's differentiation rests on the broader claw+GUI scope and the behavior analysis.

## Relevance

直接命中智能体训练/强化学习与多模态 GUI agent 方向：OpenForgeRL 提供了在真实推理 harness（Codex/OpenClaw/Kimi-Agent/Molmo-Web）中端到端 RL 微调的开源范式，对研究工具使用、浏览器/桌面操作类 agent 的训练-部署一致性、harness 设计与 RL 可靠性提升均有参考价值，且其数据合成 pipeline 可复用于数据稀缺的 agent 域。

## Questions for Further Exploration

- How would partial-rollout credit assignment (instead of DAPO-style discard-all-on-error) change sample efficiency and the learning of error-recovery behaviors specifically?
- Does the proxy-interception approach generalize to harnesses whose control flow is non-deterministic or that cache/fuse multiple model calls (e.g., speculative subagents), where prompt-response pairing may be ambiguous?
- Can the error-recovery weakness be closed with targeted synthetic failure-and-recover trajectories in the data-synthesis pipeline, and does that transfer across harnesses?
- What is the marginal value of each data-synthesis stage (propose/prune/build/test/refine) — is the test-and-refine loop doing most of the work, or is the proposal-pool quality (ClawHub, AgentNet) the dominant factor?
- Since frontier closed models still lead by 20-40 points, is the open-vs-closed gap in harness-trained agents primarily a base-model gap, a data gap, or a harness-engineering gap (e.g., the SKILL.md shim used to expose custom tools to Codex/OpenClaw)?
- How stable are the browser-use results given the dependence on stealth-browser anti-blocking — does performance degrade on websites that successfully detect the agent?
