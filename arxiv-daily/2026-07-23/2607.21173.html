Automated Synthesis & Adversarial Validation of Executable Causal Research Pipelines

Irena Girshovitz· Dan Zeltzer· Ran Gilad-Bachrach | Tel Aviv University · UC Berkeley School of Public Health | 2026-07-23
Key finding

ARA turns untestable causal identification assumptions into executable adversarial tests — so invalid claims get surfaced as protocol alarms instead of silently returned as numbers.

Key metric · safety-critical
0/33

Sign flips at ARA's final checkpoint, in both explicit and vague prompt conditions.

Vanilla baseline 1 / 33 (vague)
Why this matters

It converts the silent failure of “code runs but assumptions are invalid” into a visible protocol-level alarm — the right primitive for safe automated causal science.

Relevance · medical / privacy-restricted data
Critical edge

The headline rests on a single sign flip out of n=33 — and ARA's validity flags are model-generated with no expert ground truth, so the core safety claim is itself unvalidated.

Authors concede “small counts, including the observed sign flip, should be interpreted cautiously.” No ablation isolates which component (Reviewer loop vs. SCM validation vs. auditor) drives the modest gains.

Section 01 · Pipeline

→Methodology

ARA is an end-to-end pipeline with four sequential phases. Phases 1 and 2 communicate only through a finalized study protocol and share no other state — a deliberate isolation that prevents ground-truth leakage into the analysis code.

Phase 1
Adversarial protocol design

PI agent vs. Reviewer agent in a LangGraph loop. ≥2 review rounds, explicit approval gating. Grounded via Tavily search + Chroma RAG. gpt-5.2 / gpt-5.2-chat.

Phase 2a
SCM synthetic data

One baseline dataset (assumptions hold) + ≤3 failure-scenario datasets with planted violations. Schema-matched stress tests, not calibrated-variance copies.

Phase 2b
Analysis code generation

5 agents (spec, planner, coder, auditor, fixer). Claude Opus 4.6, temp 0.0. Ground-truth params isolated from coder. Up to 12 iterations, 5 repairs each.

Phase 3
Real-data deployment

Script proceeds to the real dataset only after passing synthetic validation gates: syntax → smoke → auditor consistency → ground-truth recovery.

Section 02 · Contribution

→Core move

  • Identification as code. Parallel-trends, exclusion, continuity become runnable tests, not prose.
  • Validity-first evaluation. A system should declare when a causal claim is unwarranted — not just return a number.
  • Withholding is a feature. Missing CIs are split into technical failures vs. deliberate validity-driven withholdings.

Section 04a

+Strengths

  • Unusual honesty. Openly reports that vanilla wins on several metrics and cleanly separates technical failures from validity-driven withholdings.
  • Transferable design pattern. The test-driven metaphor — assumptions as adversarial executable tests — is adoptable without the full ARA stack.
  • Engineering transparency. Model versions, temperatures, retry policies, chunk sizes, cost-per-run, and a failure taxonomy are all disclosed.
  • Well-motivated safety frame. Sign flips as the most safety-relevant metric; directional agreement distinguished from numerical agreement.
  • Solves a real bottleneck. Synthetic data supports protocol development where EHR / claims / registry data cannot be shared.

Section 04b

!Limitations

  • Fragile headline. n=33; a single sign flip carries the safety claim; proportion CIs are wide.
  • Validity flags unvalidated. Model-generated concerns lack ground-truth expert labels in this work — the safety claim is itself untested.
  • Weak baseline. Vanilla is a minimal single prompt with no protocol/audit/refinement; marginal value of the adversarial machinery is not isolated.
  • No ablations. Reviewer loop vs. SCM validation vs. auditor contributions are not decomposed.
  • Cost & complexity. ~80–90× cost, 2k+ API calls, more failure points; final checkpoint is a terminal loop output, not a guaranteed approved script.
  • Model-locked. Results depend on gpt-5.2 / Claude Opus 4.6; cross-model robustness unassessed.

Section 05 · Open questions for further exploration

?What still needs answering

What is the expert-validated precision/recall of ARA's causal-validity flags — when it raises a concern or downgrades a claim, how often is it actually right?

How much of the gain comes from the adversarial Reviewer loop vs. SCM validation vs. the auditor — and would a single-pass protocol-then-code condition capture most of it at far lower cost?

Does the zero-sign-flip advantage survive at n=100+ and across underrepresented identification strategies?

How sensitive are results to the model family — would open-weight models change the numerical-agreement vs. validity-screening trade-off?

Can SCM stress tests be calibrated to realistic empirical variance so that synthetic-passing code generalizes to real data?

Is there a principled way to score validity-driven withholding separately from technical failure, so safety-oriented systems aren't penalized for correctly refusing?
