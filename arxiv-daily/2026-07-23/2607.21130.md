> **一句话总结：** 本文提出一个基于 AIfES 的开源软硬件协同设计框架，利用 RISC-V 标准 Zfh/Zvfh float16 扩展，在资源受限的单核 RISC-V 上实现完整的端侧训练，相比 float32 内存占用减少约 50% 而精度损失极小，且在 NaxRiscv FPGA 软核上 Zfh 仅带来 +1.15% LUT6 / +0.05% FF 的硬件开销。

> **TL;DR:** An open-source hardware-software co-design enabling full Float16 on-device training (ODT) on resource-constrained RISC-V single-cores via standard Zfh (scalar) and Zvfh (vector) extensions. Built on the AIfES embedded framework with hand-optimized NMSIS-DSP float16 kernels, it cuts memory ~50% versus Float32 with negligible accuracy loss on MNIST (F16 97.29% vs F32 96.88% with SGD) and FashionMNIST, while Zfh support on a dual-issue RV64GC NaxRiscv FPGA softcore costs only +1.15% LUT6 / +0.05% FF at 175 MHz with no frequency degradation. The only framework combining RISC-V support, full ODT, float16, batch size ≥1, and open-source; introduces a 4-lane VPU architecture for Zvfh (validated so far only on the ISA Simulator, not on FPGA silicon).

## 核心贡献

- **首个面向单核 RISC-V 的完整 Float16 ODT 开源框架**：基于 AIfES 扩展，通过标准 Zfh（标量）与 Zvfh（向量）float16 扩展实现完整端侧训练，是同时满足 RISC-V 支持、完整 ODT 能力、float16、batch size ≥1、开源五项的唯一方案（见表 1）。
- **显著内存节省与精度保持**：float16 相比 float32 内存占用减少约 50%，在 MNIST/FashionMNIST 上精度差异极小（多数情况下 ≤0.7 个百分点）。
- **支持迁移学习与微调**：通过新增层冻结（layer-freezing）能力，使迁移学习与微调场景成为可能，进一步降低工作内存。
- **低开销硬件实现**：在双发射 RV64GC 超标量乱序 NaxRiscv FPGA 软核上实现 Zfh，仅 +1.15% LUT6、+0.05% FF @175MHz，且无最大频率下降。
- **提出 Zvfh VPU 架构**：为同一超标量乱序核设计了 VLEN=64-bit、4 lane 的向量处理单元，对 float16 相对标量提供 4× 原始加速，并采用微操作拆分方式处理寄存器分组。

## Key Contributions

- **First open-source full Float16 ODT framework for RISC-V single-core**: Extends AIfES with hand-optimized Zfh/Zvfh float16 math primitives, and is the only framework (Table 1) that simultaneously offers RISC-V support, full ODT capability, float16, batch size ≥1, and open-source licensing — outperforming feature-wise PULP-Trainlib (batch-size-1 only) and AIfES (no float16/RISC-V).
- **~50% memory reduction with minimal accuracy loss**: Float16 halves parameter storage versus Float32; work memory drops further when using SGD or last-layer-only training.
- **Transfer learning / fine-tuning enabled**: Layer-freezing support plus an enhanced AIfES-Converter (PyTorch/TensorFlow → C) lets users import pretrained models and freeze specific layers.
- **Minimal hardware cost for Zfh**: On a dual-issue RV64GC super-scalar out-of-order NaxRiscv, Zfh costs only +1.15% LUT6 and +0.05% FF at 175 MHz on a Xilinx XC7K325T, with no Fmax degradation — achieved via Nan-Boxing and float64-widened compute path.
- **Architectural design for a Zvfh Vector Processing Unit**: A 4-lane VPU with VLEN=64-bit is proposed for the same core, merging the vector and float physical register files, handling vector-register-grouping (LMUL) by micro-op splitting at issue/renaming, and avoiding micro-op blow-up for instructions like `vrgather.vv`.

## Methodology

The paper is a hardware-software co-design spanning two open-source foundations.

**Software side (Section 2):**
- Base framework is **AIfES** (a modular embedded DNN training/inference library). The authors extend it with RISC-V Zfh and Zvfh hand-optimized math primitives sourced from **NMSIS-DSP** (Nuclei's open-source library, RISC-V analog of CMSIS-DSP), whose vector-length-agnostic float16 routines guarantee portability across any Zvfh-capable core.
- Manual vectorization is preferred over compiler auto-vectorization, citing prior work ([6], [7]) showing manual kernels still outperform auto-vectorized scalar code.
- **AIfES-Converter** is enhanced to convert PyTorch/TensorFlow models into AIfES C models, with optional **layer-freezing** for transfer learning / fine-tuning scenarios.
- Float16/Zvfh kernels are selected at compile time.

**Hardware side (Section 3):**
- Target is the **NaxRiscv**: an open-source, SpinalHDL-written, configurable RV64GC super-scalar out-of-order core for FPGA. The chosen configuration is dual-issue with a 32-entry issue queue, two integer ALUs, one FPU, one LSU, a 64-entry re-order buffer, a Gshare branch predictor, and two 16 kB 4-way L1 caches.
- **Zfh support**: The decoder, LSU, and FPU are extended to handle the 36 Zfh instructions. Since the FPU already supported float32/float64, float16 is added via the same Nan-Boxing load/store and float64-widened compute strategy used for float32.
- **Zvfh VPU**: A lane-based architecture (4 lanes) with input/output crossbars that route operands by format/mask/opcode. VLEN=64-bit is chosen to balance parallelism vs. hardware reuse, yielding a raw 4× float16 speed-up over scalar. The VPU is tightly integrated via SpinalHDL plugins, and the vector + float register files (and parts of their RATs) are merged to limit overhead. Vector register grouping (LMUL) is handled by splitting most vector instructions into micro-ops at issue/renaming, except instructions like `vrgather.vv` whose data-dependent source/destination relations would explode the micro-op count.

**Evaluation protocol**: Software training experiments are run on the **RISC-V ISA Simulator** (not FPGA hardware). Hardware cost for Zfh is reported from Vivado 2021.1 synthesis on Xilinx XC7K325T-2FFG900C.

## Results & Highlights

- **Feature uniqueness (Table 1)**: Theirs is the only framework with ✓ RISC-V support, ✓ full ODT, ✓ float16, ✓ batch size ≥1, ✓ open-source — vs. [11] (no full ODT, batch 1, closed), [2] (no RISC-V, closed), PULP-Trainlib [8] (batch 1 only), and AIfES [13] (no float16, no RISC-V).
- **Float16 vs Float32 accuracy (Table 2)** on a 5-layer MLP, batch 128:
  - MNIST, SGD, lr=1e-3: **F16 97.29% val. acc. vs F32 96.88%** (+0.41% for float16).
  - MNIST, Adam, lr=1e-3: **F16 96.78% vs F32 97.32%** (-0.54%).
  - FashionMNIST, SGD, lr=1e-3: **F16 86.85% vs F32 87.53%** (-0.68%).
  - FashionMNIST, Adam, lr=1e-4: **F16 88.25% vs F32 88.54%** (-0.29%).
- **Memory savings (Table 3)** for a 3-layer MLP transfer-learning scenario (MNIST→EMNIST): parameter memory is halved — **F16 50.43 kB vs F32 100.85 kB** (a flat 50% reduction). With frozen layers 1-2 and SGD, F16 gradients drop to 52.74 kB vs 105.23 kB (F32), ~50% again; Adam gradient memory is roughly halved too (e.g., 154.06 kB vs 307.40 kB).
- **Zfh hardware cost (Section 3.2)** on a dual-issue RV64GC NaxRiscv on Xilinx XC7K325T-2FFG900C (Vivado 2021.1): **+1.15% LUT6 and +0.05% FF at 175 MHz**, with no maximum operating frequency degradation.
- **Zvfu raw speed-up**: VLEN=64-bit with 4 lanes yields a raw **4× speed-up over scalar execution for float16 operands** (architectural projection, not yet measured on FPGA).

## Critical Assessment

- **Novelty**: Genuine but incremental. The combination is the contribution — individual pieces (AIfES, Zfh, NMSIS-DSP, NaxRiscv) all pre-exist; the novelty is stitching them into the first open-source full-Float16 ODT pipeline for single-core RISC-V with batch >1. The Zvfh VPU micro-op-splitting design (especially the `vrgather.vv` exemption) is a more original hardware contribution.
- **Rigor**: Mixed. Accuracy experiments are run only on the **RISC-V ISA Simulator**, not on actual silicon or even FPGA, so no end-to-end wall-clock training times, throughput, or energy numbers are reported — only accuracy and memory. The 4 float16-vs-float32 deltas in Table 2 (ranging from +0.41% to -0.68%) are plausibly within run-to-run noise with **no statistical significance, variance bars, or multiple seeds reported**. Only MLPs are tested; **no CNN/transformer or larger model** is evaluated, so the "minimal degradation" claim is narrow.
- **Reproducibility**: Strong on the software side (open-source repo, named library versions, ISA simulator) and reasonable on hardware (named FPGA part, Vivado version, frequency). However, the Zvfh VPU is **architecturally described but not yet synthesized/measured** — so the headline 4× speed-up is a projection, and the VPU area/timing cost is not reported.
- **Significance**: Practically useful for the TinyML / edge-RISC-V community, filling a real gap (PULP-Trainlib is multi-core only; AIfES lacks float16). The ~50% memory reduction is the most valuable, verifiable claim.
- **Red flags**: The TL;DR-worthy Zvfh speed-up and area numbers are *not measured*; the conclusion and future work concede this. The accuracy deltas are small enough that on a single seed they are not convincing evidence of parity with Float32 — a fair reader should treat "minimal performance degradation" as plausible-but-unproven. The baseline comparison (Table 1) is a *feature checklist*, not a head-to-head performance benchmark, so "outperforms" claims should be read as feature-coverage only.

## Strengths

- First open-source framework unifying RISC-V, full ODT, float16, batch>1, and open-source licensing — addresses a concrete gap left by PULP-Trainlib (batch 1) and AIfES (no F16/RISC-V).
- Clean, modular integration via AIfES + NMSIS-DSP, with PyTorch/TensorFlow import path and layer-freezing for practical transfer learning.
- Zfh hardware cost is genuinely low and well-quantified (+1.15% LUT6, no Fmax loss) — a strong, concrete result for HW designers.
- Honest scoping: VPU evaluation is explicitly deferred to future work rather than overclaimed.
- Vendor-neutral, standards-based (Zfh/Zvfh/RVV) approach ensuring portability, unlike memory-mapped or custom-ISA accelerators.

## Limitations

- Software results come only from the **ISA Simulator**; no on-device (FPGA/silicon) execution time, throughput, or energy measurements.
- The **Zvfh VPU is not yet implemented or synthesized** — its area cost and real-world speed-up are future work.
- Model zoo is shallow: only **MLPs on MNIST/FashionMNIST/EMNIST**; no CNNs, transformers, or larger datasets to stress-test float16 stability.
- Accuracy comparisons lack **variance, multiple seeds, or significance testing**; the reported deltas are within plausible noise.
- No comparison against quantized/hybrid ODT baselines ([2], [11]) on equal footing — only a feature-checklist Table 1.
- No discussion of float16 numerical instability mitigations (loss scaling, etc.), which matters for deeper networks and optimizers like Adam.

## Relevance

对关注端侧训练（On-Device Training）、嵌入式/边缘 AI 部署以及 RISC-V 生态的研究者高度相关：它提供了首个支持 float16、batch≥1 且开源的单核 RISC-V 完整 ODT 框架，直接服务于 TinyML 与资源受限设备上的个性化/迁移学习场景，是软硬件协同设计与低精度训练方向的具体参考实现。

## Questions for Further Exploration

- How do float16 training stability and accuracy scale to **CNNs, transformers, or larger datasets** (CIFAR, ImageNet subsets) where float16 numerical range is more strained?
- What are the **actual on-FPGA wall-clock training times and energy/epoch** once the Zvfh VPU is synthesized — does the projected 4× translate to real speed-up given on-device training being backward-pass/memory-bound?
- Does adding **loss scaling or stochastic rounding** close the small accuracy gap to float32, particularly for Adam?
- How does the framework compare head-to-head (training time, memory, accuracy) against **PULP-Trainlib** on multi-core and against **quantized/hybrid ODT** ([2], [11]) on the same workload?
- What is the **synthesized area and timing cost of the full Zvfh VPU** on the NaxRiscv target, and how does it scale with VLEN and lane count?
- Can the layer-freezing + float16 combination support **federated/personalized learning** loops on MCU-class RISC-V parts with severe RAM limits?
