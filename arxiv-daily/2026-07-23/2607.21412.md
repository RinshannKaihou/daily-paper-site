> **一句话总结：** 本文提出开源的 Euclid-MCP 服务器，通过引擎无关的 Horn 子句中间表示 Euclid-IR 将自然语言规则编译为 SWI-Prolog，在 1,000 用户规模的 RBAC 基准上把 8B 小模型的准确率从 2/5 提升到 5/5（480B 云端大模型也只有 2/5），同时延迟降到 963 ms、输出 token 仅 12 个，论证了"语义 RAG 不适合规则执行"这一主张。

> **TL;DR:** Euclid-MCP is an open-source MCP server that wraps SWI-Prolog behind a tiny 4-tool surface (reason / diagnose / what_if / check_kb) and an engine-agnostic Horn-clause IR (Euclid-IR), letting any MCP-capable LLM delegate deduction instead of guessing. On a 1,000-user synthetic RBAC benchmark (1,053 facts), llama3.1:8b + Euclid-MCP scores 5/5 vs. 2/5 for both the 8B baseline and a 480B cloud model, while being ~7x faster (963 ms vs. 6,966 ms) and ~14x more output-token-efficient (12 vs. 165 tokens); on small KBs (5-50 facts) all systems tie at 5/5, so the value only emerges at scale.

## 核心贡献

- 提出 **Euclid-IR**：一种引擎无关的 Horn 子句中间表示，语法面向人类与 LLM 双重可读（变量用 `$x`、规则用 `head IF body`、闭世界否定 `NOT`、`?` 起头的查询），刻意不支持析构/cut/列表以保持确定性与可移植到 Datalog/SMT 等其他后端。
- 构建 **Euclid-MCP** 开源服务器（`pip install euclid-mcp`，亦提供 Docker 镜像）：基于 FastMCP，将 Euclid-IR 自动降级为 SWI-Prolog 子进程执行，并对输入大小（500 KB）、超时（30 s）和允许的谓词做沙箱化处理。
- 设计 **四工具紧凑接口** —— `reason`（带证明树推理）、`diagnose`（why / why_not / what_needs 三种模式）、`what_if`（`+`/`-` 修改做反事实分析）、`check_kb`（语法/未定义谓词/循环规则校验），共同构成 `translate-run-inspect-repair` 闭环。
- 在一个真实的 **IT 安全合规用例**（CIS AWS 基准 + 内部 IAM 策略 + 数据分级）上验证：小知识库约 578 事实（30 用户、50 资源），大知识库约 3,872 事实（200 用户、300 资源），覆盖单跳/多跳/时序/跨策略/阈值/资源审计共 10 条规范化查询 + 3 条诊断 + 3 条 what-if。
- 通过对照实验论证 **"语义 RAG 本质上不适合规则执行"**：RAG 只能返回"相似"规则，无法保证逻辑充分性、一致性，也无法给出形式化证明；Euclid-MCP 则每次返回确定答案与证明树。

## Key Contributions

- **Euclid-IR**, an engine-agnostic intermediate representation for Horn-clause logic: human- and LLM-readable (variables as `$x`, `head IF body`, closed-world `NOT`, `?`-prefixed queries), deliberately excluding disjunction/cut/lists to stay minimal, deterministic, and lowerable to Prolog today and Datalog/SMT later.
- **Euclid-MCP**, an open-source Python MCP server (FastMCP, `pip install euclid-mcp`, Docker image bundling SWI-Prolog) that compiles Euclid-IR to a temporary `.pl` file, runs `swipl` as a subprocess, and returns structured JSON solutions plus proof trees, with sandboxing (500 KB input cap, 30 s timeout, allow-listed predicates).
- A **compact 4-tool MCP surface** — `reason`, `diagnose` (modes: why / why_not / what_needs), `what_if` (counterfactual `+`/`-` edits), `check_kb` (KB validator) — implementing a `translate-run-inspect-repair` loop and exposing proof trees for auditability.
- A **realistic IT security & compliance use case** (CIS AWS Foundations Benchmark + internal IAM role hierarchy, environment tiers, data classification) with small (~578 facts, 30 users, 50 resources) and large (~3,872 facts, 200 users, 300 resources) knowledge bases, plus 10 canonical queries, 3 diagnostics, and 3 what-if scenarios.
- An **empirical argument that semantic RAG is fundamentally unsuited for rule enforcement**, positioning Euclid-MCP as a shared, stable, auditable reasoning substrate that both RAG assistants and agent systems can call via MCP.

## Methodology

The system follows a **hybrid cognitive architecture**: a lightweight LLM only translates natural-language problems into Euclid-IR facts/rules/queries, and all multi-step deduction is delegated to a deterministic SWI-Prolog backend invoked as a subprocess. The architecture has three layers:

1. **LLM client** — any MCP-capable application generates Euclid-IR and renders returned proof trees.
2. **Euclid-MCP server** (Python + FastMCP) — parses/normalizes Euclid-IR, lowers it to Prolog (mapping `IF`→`:-`, `AND`→`,`, `NOT`→`\+`, `?`→`?-`, capitalizing `$x`-style variables), runs sandboxing, and exposes the 4 tools.
3. **Inference backend** — SWI-Prolog executed via `subprocess.run()` with a 30 s timeout; solutions and proof trees are captured as JSON.

The **translate-run-inspect-repair loop**: `check_kb` validates the KB → LLM emits Euclid-IR → `reason` returns bindings + proof trees → `diagnose` explains success/failure → LLM repairs and re-runs → `what_if` explores hypothetical edits. Two transports are supported: stdio (default MCP) and a standalone HTTP API (`/reason`, `/diagnose`, `/what-if`, `/check-kb`) for n8n/Zapier/Make integration.

Evaluation has two arms: (i) qualitative expressivity on the CIS/IAM compliance KB; (ii) two quantitative reasoning benchmarks — a small-scale 5-task suite (genealogy/taxonomy/RBAC, 5-15 facts each) and a large-scale synthetic RBAC benchmark (1,000 users, 7 roles, 17 base permissions, 1,053 facts) — comparing llama3.1:8b (A), qwen3-coder:480b-cloud (B), and llama3.1:8b + Euclid-MCP (C).

## Results & Highlights

- **Large-scale RBAC accuracy (1,000 users, 1,053 facts):** C (8B + Euclid-MCP) achieved **5/5**, versus **2/5** for A (llama3.1:8b alone) and **2/5** for B (qwen3-coder:480b-cloud) — both raw LLMs, regardless of size, hallucinate systematically on counting/inheritance at scale.
- **Counting hallucinations:** For Q1 "count users with `delete_repo`" (ground truth 31), A returned **1** and B returned **1**; C returned exactly **31**. For Q3 "count users with `deploy`" (ground truth 103), A returned **100** and B returned **901**; C returned exactly **103** — both LLMs are off by orders of magnitude or by a near-miss that is still wrong.
- **Latency on large KB:** C averaged **963 ms** per query vs. **6,966 ms** for A and **3,695 ms** for B — roughly **7.2x faster than the 8B baseline and 3.8x faster than the 480B cloud model**, because the LLM only emits a short query rather than reasoning over 1,000 facts.
- **Output-token efficiency on large KB:** C averaged **12 output tokens** vs. **165** (A) and **212** (B) — the LLM emits a query, not a fallacious chain-of-thought.
- **Small-scale benchmark (5-15 facts):** all three conditions tie at **5/5 accuracy**; Euclid-MCP is slightly costlier on input tokens (254 vs. 131) and comparable on latency (2,542 ms vs. 4,772 / 2,180 ms) — overhead is **not justified** when facts fit in context and chains are shallow.
- **Scalability of the KB itself:** the same policy rules scale unchanged from ~30 users / ~50 resources (~578 facts) to ~200 users / ~300 resources (~3,872 facts) without rule edits.

## Critical Assessment

- **Novelty (moderate):** The genuinely new artifact is Euclid-IR as an *engine-agnostic* layer above Prolog — a real differentiator vs. PrologMCP [12] and LogicLease [4], which bind directly to Prolog. However, the four-tool surface and the translate-run-inspect-repair loop are fairly conventional MCP design patterns, and the authors do not implement or benchmark any non-Prolog backend, so "backend-agnostic" is currently a design claim, not a demonstrated property.
- **Rigor (weak-to-moderate):** The empirical study has real weaknesses. (1) **Baselines are thin** — only two LLMs are compared, and the paper's central rhetorical target (semantic RAG) is never actually run; Table 5 is a *qualitative* comparison, with no RAG numbers, no retrieval system named, and no shared benchmark. (2) **No comparison to PrologMCP or LogicLease** despite citing them as closest related work. (3) **No standard reasoning benchmarks** (e.g., ProofWriter, FOLIO, bAbI) — evaluation is confined to the authors' own synthetic RBAC KB, which risks confirming the system on its home turf. (4) **No statistical significance, single runs, no variance**, and the "qwen3-coder:480b-cloud" identifier is presented without provenance.
- **Reproducibility (strong):** Open-source code, PyPI package, Docker image, public KB and benchmark scripts, and a clearly documented IR spec make this one of the more reproducible system papers — a genuine plus.
- **Significance (practical, not theoretical):** The core claim — "LLMs hallucinate at >few-hundred facts; delegate to a deterministic engine" — is well supported by the large-RBAC numbers (5/5 vs. 2/2, exact counts vs. off-by-901) and is useful practitioner guidance. The framing of Euclid-MCP as a *shared substrate* for multiple agents is interesting but asserted, not demonstrated (no multi-agent experiment).
- **Red flags:** Self-citation to the project GitHub repo as reference [1]; reliance on blog posts as related work; the 480B "cloud" model is unnamed beyond its identifier; the "no disjunction/cut/lists" restriction is acknowledged as a real expressivity ceiling but its impact on the CIS/IAM use case is not stress-tested.

## Strengths

- Clean, genuinely engine-agnostic IR design with explicit, well-justified omissions (no cut, no lists, closed-world negation) that keep lowering deterministic.
- Strong, reproducible artifacts: PyPI package, Docker image, public repo with the full CIS/IAM KB and benchmark scripts.
- The large-RBAC result is a clean, memorable demonstration: exact counts (31, 103) where both LLMs are wrong, at lower latency and ~14-18x fewer output tokens.
- The 4-tool loop (validate → translate → run → inspect → repair → explore) is a genuinely usable practitioner workflow, and `diagnose` with why/why_not/what_needs plus `what_if` counterfactuals goes beyond what RAG can offer.
- Honest about the small-KB regime: the paper openly concedes that Euclid-MCP is *not* worth the overhead when facts fit in context and chains are shallow.

## Limitations

- **Horn-clause only:** no disjunction, cut, list pattern matching, `findall/bagof`, dynamic `assert/retract`, modules, or strings — real expressivity ceiling for data-structure-heavy or non-monotonic domains.
- **Scalability untested beyond ~4K facts:** the authors flag that 100K+ facts will need indexing, tabling, or a Datalog engine, none of which is implemented or measured.
- **Backend dependency:** only SWI-Prolog is wired up; the "Datalog/SMT alternative backend" promise is unfulfilled.
- **Integration overhead:** real-world deployment needs Euclid-IR generation, error handling, and proof-tree rendering around the server — acknowledged but not quantified.
- **Benchmark coverage:** synthetic RBAC only, no standard logical-reasoning benchmarks, no head-to-head with PrologMCP/LogicLease, and the central anti-RAG argument is made qualitatively.

## Relevance

对于关注 **LLM agent 工具化与可信推理** 的研究者，Euclid-MCP 提供了一个将"确定性符号推理"作为 MCP 工具暴露给大模型的简洁范本，其引擎无关 IR 与 translate-run-inspect-repair 闭环可作为构建可审计、防幻觉 agent 的参考架构；而其在大规模 RBAC 上"小模型 + 符号后端 > 480B 云端大模型"的实证结论，对合规、安全策略、访问控制等需要精确计数与可解释证明的场景具有直接的工程价值。

## Questions for Further Exploration

- How does Euclid-MCP perform on **established logical-reasoning benchmarks** (ProofWriter, FOLIO, bAbI, RuleTaker) rather than the authors' own synthetic RBAC KB?
- What is the **quantitative** gap vs. a real semantic-RAG pipeline (e.g., a strong embedding + LLM judge on the same CIS/IAM KB) — the paper's central claim is currently argued qualitatively in Table 5?
- How does it compare head-to-head with **PrologMCP** and **LogicLease** on identical workloads, given they are named as the closest related systems?
- What happens to latency and correctness beyond **10K-100K facts** — does tabling/indexing or migration to a Datalog engine actually preserve the sub-second SLA?
- Can the **diagnose / what-needs** tools be benchmarked for explanation *correctness* (not just presence), e.g., against human expert judgments or a held-out ground-truth rationale set?
- Does the **shared-substrate** claim for multi-agent compliance hold empirically — does routing several agents through one Euclid-IR KB measurably reduce policy drift vs. each agent re-encoding rules?
- How brittle is the LLM-to-Euclid-IR translation step under adversarial or ambiguous natural-language policies, and what is the repair-loop's convergence rate?
