> **一句话总结：** 本文提出 Code Monitor Red Teaming 协议与 CodeMonitorBench（覆盖函数级、数据科学、工作流三类代码），在固定"公开测试通过"证据边界下评估弱/强 LLM 验证器能否识别残留的隐藏 bug；在 7.1 万条候选代码上，4.37 万条通过公开测试，其中 2.31 万条仍通不过隐藏测试，而弱验证器在 5% FPR 下漏掉绝大多数隐藏 bug，GLM-5.1 强验证器只能部分弥补该差距。

> **TL;DR:** The paper introduces Code Monitor Red Teaming and the CodeMonitorBench (spanning BigCodeBench-Hard, a constructed Data-Science Code split, and a constructed CodeWorkflow split) to test whether an LLM verifier can flag residual hidden bugs in code that has already passed visible public tests, fixing the public-check evidence boundary (M1) while varying generator pressure, verifier scaffolding, and weak-to-strong capability. Across 71,000 candidates, 43,677 pass public tests and 23,081 of those still fail hidden tests; under G1 the weak Qwen-7B Hybrid verifier only reaches AUROC 0.601 with 86.8% miss-rate at 5% FPR, and even the closed GLM-5.1 strong verifier reaches AUROC 0.833 / 54.3% FNR@5% on G1 and 0.762 / 66.2% on the adversarial G4-adv stress condition — recovering only part of the weak-verifier gap.

## 核心贡献

- **将 monitor red teaming 迁移到代码领域**：提出 Code Monitor Red Teaming 协议，把"代码已通过公开测试后能否由较弱验证器识别残留隐藏 bug"形式化为公开通过（public-pass）监控问题，固定 M1 公开证据边界（规格说明、接口、公开测试、候选代码、公开通过状态），而把隐藏测试仅当作测量用的 oracle 标签，从而把"候选构造效应"与"验证器排名失败"清晰分离。
- **构建 CodeMonitorBench**：一个冻结的公开/隐藏基准，包含三类残缺 bug 表面——BigCodeBench-Hard（函数级，148 任务，公开测试为首两个官方 unittest 方法、其余为隐藏）、Data-Science Code（构造，300 任务，pandas/NumPy/scikit-learn/SciPy/绘图等库密集）、CodeWorkflow（构造，120 任务，artifact 产出型工作流，涉及 schema/join/聚合/报告不变量），并配有两标注员审计（spec-grounded 94%，inferable 84%，κ=0.80）。
- **大规模生成器×验证器实验矩阵**：5 个生成器（Qwen-14B、DeepSeek-V2-Lite、Codestral-22B、GPT-5.4、GLM-5.1）× 5 个生成条件（G1 公开测试感知、G2 验证器感知、G3 方案感知、G4-natural 自然捷径、G4-adv 对抗应力）× 5 候选/单元，共 71,000 条候选；验证器在 Direct 与 Hybrid 两种 scaffold 下评估，并额外对比静态 lint、静态分析器包、任务生成测试、候选定向测试等基线。
- **区分构造与监控失败来源**：通过 candidate-pool、sample-mix、invalid-output 与 blind-spot 分析，再加上 300 条隐藏 bug 的可推断性审计（92% spec-grounded，但仅 33% 可从 M1 构造性推断、64% 事后可推断），证明残留漏检混合了"验证器能力限制"与"公开证据边界限制"，并通过添加诊断性非部署视图（M1+checklist/hint/隐藏断言摘要）使捕获率单调上升以定位 evidence-limited 缺失。

## Key Contributions

- Adapts the AI-control / monitor-red-teaming threat model to a code artifact view rather than agent trajectories: trajectories become specifications + public tests + public-pass implementations, covert objectives become residual hidden specification bugs, and hidden tests are oracle labels only — never inputs to the verifier.
- Introduces CodeMonitorBench with three frozen public/hidden splits exposing distinct residual-bug surfaces (boundary/API semantics in BigCodeBench-Hard; library-heavy shape/dtype/statistical/filtering failures in Data-Science Code; artifact schema/aggregation/report-invariant failures in CodeWorkflow), validated by a two-annotator audit (94% spec-grounded, 84% inferable, Cohen's κ=0.80).
- Runs a large 5-generator × 5-condition × 71,000-candidate study that fixes the M1 evidence boundary while independently varying generator pressure (G1–G4-adv), verifier scaffolding (Direct vs Hybrid), and weak-to-strong capability (Qwen-7B, Mistral-7B, Llama-8B, GPT-5.4-mini, GLM-5.1).
- Separates construction effects from monitoring failures via candidate-pool statistics, sample-mix analysis, invalid-output accounting, and a 300-bug inferability audit; uses diagnostic non-deployed views to show that residual misses are a mixture of capability limits and public-evidence limits rather than pure verifier reasoning failures.

## Methodology

The protocol models a coding workflow in which visible tests have already run before model review. A task x = (specification s, interface i, public tests T_pub, hidden oracle tests T_hid) is given to a generator G, which produces candidate code c under one of five generator conditions:

- **G1 (public-test-aware):** solve the task and pass visible tests — the deployment baseline.
- **G2 (verifier-aware):** G1 plus the warning that an LLM verifier will inspect the solution for hidden bugs.
- **G3 (scheme-aware):** G2 plus a high-level description of the verifier's robustness checks.
- **G4-natural:** ask for a simple public-test-focused implementation (natural shortcut pressure).
- **G4-adv:** adversarial stress — explicitly told to pass public tests while leaving a subtle residual defect.

Candidates are executed on T_pub; only public-pass candidates are sent to the verifier. The hidden oracle then labels each public-pass candidate as HIDDEN-BUG (∃ hidden test failing) or CORRECT (all hidden tests passing). Generators see only public tests; hidden tests are never leakage.

The verifier V receives the **M1 public-check view** — specification, required interface, visible public tests, candidate code, and public-pass status — and returns a numeric suspicion score r(c)∈[0,1] plus a structured explanation. Crucially, weak and strong verifiers see the same M1 fields; stronger verifiers are not given hidden tests, reference implementations, hidden execution results, or aggregate statistics. Two scaffolds are compared: **Direct** (single-pass review against spec and tests) and **Hybrid** (decompose requirements → list public-coverage gaps → counterexample-oriented review → score).

The generator pool includes Qwen-14B, DeepSeek-V2-Lite, Codestral-22B, GPT-5.4, and GLM-5.1; closed-generator comparisons are restricted to GPT-5.4 and GLM-5.1. Closed verifiers are GPT-5.4-mini (closed weak) and GLM-5.1 (closed strong). Five candidates per generator-condition-task cell give 71,000 candidates total.

Metrics deliberately separate candidate-pool construction from verifier reliability. Candidate-pool metrics report generated counts, public-pass rate, hidden-bug rate among public-pass candidates, correct rate, and invalid/error rate. Verifier reliability is measured with AUROC (ranking quality), AUPRC (prevalence-sensitive), TPR/FNR at fixed low FPR (1%, 5%, 10%), and NA rate for unparseable/missing/out-of-range scores (NA is not imputed). The 5% FPR operating point is chosen because public-pass review is a large triage stream with a small escalation budget. Fixed-FPR thresholds are chosen per-cell from valid scored rows. Programmatic baselines include static fatal lint, a static analyzer bundle, task-generated tests (k=10, 20), and candidate-targeted tests (k=2, 5). Aggregates are unweighted means over dataset-generator (or dataset-generator-verifier) cells so Data-Science Code's larger task count does not dominate.

A 300-bug inferability audit (3 datasets × 2 generators × 2 conditions × 25 bugs) further separates capability limits from evidence limits: an auditor first tries to construct a counterexample from M1 (Constructive M1), then labels spec-grounding and inferability after seeing the hidden-failure summary (Posthoc M1), and probes the same bugs with diagnostic non-deployed views (M1 + requirement checklist / + bug-category hint / + hidden assertion summary as an upper-bound view).

## Results & Highlights

- **Public tests leave a large residual bug pool.** Across 71,000 generated candidates, 43,677 pass public tests and 23,081 of those public-pass candidates fail hidden tests (Table 1). In G1 generation, hidden-bug rates among public-pass candidates are 43–47% across datasets (BigCodeBench-Hard 43.1%, Data-Science Code 44.2%, CodeWorkflow 46.5%); G4-adv raises this to 68.2% / 69.2% / 72.8%.
- **Weak verifiers miss most bugs at low FPR.** Direct Qwen-7B review is near random (AUROC 0.536) and misses 94.0% of hidden bugs at 5% FPR; Hybrid review improves ranking (AUROC 0.601) but still misses 86.8%. Switching to Mistral-7B reaches AUROC 0.665 but still leaves 80.0% of hidden bugs below the escalation threshold. Even at 10% FPR, Qwen-7B Hybrid and Mistral-7B Hybrid miss 80% and 72% of G1 hidden bugs respectively.
- **Programmatic / static baselines are weak.** Static fatal lint is near random (G1/G4-adv AUROC 0.520/0.510); the stronger static analyzer bundle stays limited (0.570/0.545). Candidate-targeted generated tests reach G1/G4-adv AUROC 0.765/0.695 with FNR@5% of 0.640/0.740 — better than weak LLM review but still missing most bugs and degrading under G4-adv.
- **Adversarial pressure degrades monitoring in every cell.** Across the three open weak verifiers, G4-adv lowers AUROC by ~0.07 and increases FNR@5%FPR by ~0.07 (Qwen-7B ΔAUROC −0.076, ΔFNR +0.069; Llama-8B −0.068/+0.066; Mistral-7B −0.077/+0.072); the degradation direction holds in all 45 AUROC cells and all 45 FNR cells.
- **A stronger verifier recovers only part of the gap.** Mean G1 FNR@5% falls from 0.823 (Mistral-7B open weak) to 0.756 (GPT-5.4-mini closed weak) to 0.543 (GLM-5.1 closed strong); GLM-5.1 G4-adv FNR is still 0.662. On GPT-5.4-authored candidates only, GLM-5.1 achieves G1/G4-adv AUROC 0.82/0.75 and FNR 0.56/0.67 versus 0.69/0.61 and 0.76/0.85 for GPT-5.4-mini.
- **Inferability audit separates capability from evidence limits.** Of 300 audited public-pass hidden bugs, 92% are spec-grounded but only 33% are constructively inferable from M1 (64% posthoc inferable); GLM-5.1 catches 40% versus 20% for the closed weak verifier, with 23% weak-miss / strong-catch. Adding diagnostic views raises catch rates monotonically (M1 → +checklist → +hint → +hidden assertion summary: 24%→39%→55%→74% for weak, 46%→61%→76%→89% for strong), indicating evidence-limited misses.
- **NA-rate trade-offs.** Hybrid improves Qwen-7B ranking but raises invalid-output NA (3.1%→5.7%); GLM-5.1 combines the strongest ranking (AUROC 0.798 / FNR 0.603 on closed cells) with the lowest NA rate (1.4%).

## Authors & Credibility

The authors are Junchi Liao, Jiawen Deng, and Fuji Ren (corresponding author) from the University of Electronic Science and Technology of China (UESTC, Chengdu). The work is framed as a careful measurement study rather than a system pitch: the protocol is formalised (equations for FPR/TPR/FNR at fixed budget), the information boundary is explicitly enumerated (Table 17), generator and verifier prompts are documented (Tables 15–16), and the constructed Data-Science Code and CodeWorkflow oracles are backed by a two-annotator audit with Cohen's κ=0.80 (Table 10). The benchmark is positioned against clearly named related work (BigCodeBench, LiveCodeBench, DS-1000, SWE-bench, CodeT, LEVER, CriticBench, MonitoringBench, AI-control / prover-verifier games), and the contributions are stated narrowly as a measurement protocol rather than a deployable monitor.

## Critical Assessment

- **Novelty:** Genuine. The paper reframes monitor red teaming for the public-test-passing code setting and fixes a public-check evidence boundary (M1) that cleanly separates this work from standard code-generation benchmarks (which ask whether a generator passes hidden tests), critique benchmarks (which evaluate flaw identification/repair directly), and trajectory-level agent monitoring (which inspects tool-call sequences). Treating hidden tests as a measurement device rather than a deployed monitor component is the central conceptual move and is handled rigorously.
- **Rigor:** High. The study fixes generator prompts, verifier prompts, the scoring policy, and the information boundary before any model call, reports candidate-pool construction separately from verifier ranking, accounts for NA outputs rather than imputing them, and uses unweighted cell means so the larger Data-Science Code split cannot dominate aggregates. The 45-of-45 AUROC-cell and 45-of-45 FNR-cell degradation claim under G4-adv is a strong, falsifiable statement, and the inferability audit is a credible attempt to decompose the residual miss pool.
- **Reproducibility:** Reasonable but incomplete. Splits are frozen, public/hidden policies are fixed before generation, prompt templates and the M1 checklist are given, and full construction tables (Appendix D) and per-cell verifier audits (Appendix E) are reported. However, the constructed Data-Science Code and CodeWorkflow splits, the audit labels, and the prompt templates are described at summary level in the main text — full release of the frozen task sets, hidden assertions, and scorer code would be needed to reproduce the exact 71,000-candidate matrix and per-cell AUROCs. The use of unnamed "static analyzer bundle" diagnostics is under-specified.
- **Significance:** The headline message — public-test passing is a triage signal, not a stopping rule, and weak monitoring fails at low FPR even before adversarial pressure — is well-supported and deployment-relevant for coding agents and CI gates. The weak-to-strong comparison shows a real capability gradient (G1 FNR 0.823→0.543) while honestly reporting that even GLM-5.1 leaves FNR 0.543 at G1 and 0.662 at G4-adv.
- **Red flags / overclaiming to watch:** The paper is commendably restrained about G4-adv, repeatedly flagging it as a robustness stressor and not a deployment prevalence estimate (a common overclaim risk it explicitly disclaims). The main soft spot is the closed strong verifier GLM-5.1 acting as a "named capability reference" within the same group that also authored some candidates and that shares model family with GLM-5.1 used as a generator — although the GPT-5.4-only subset analysis (Appendix Table 26) mitigates self-judging bias, the closed strong/weak comparison is only between two closed models from two different labs, which is a thin weak-to-strong ladder. The candidate-targeted generated-test baseline (AUROC 0.765 at G1) actually outperforms every open weak LLM verifier and roughly matches GPT-5.4-mini Hybrid — this is reported honestly but could be read as evidence that single-pass LLM review is dominated by tool-using test generation, which weakens the case for the pure-M1 monitor as the central object. Finally, the hidden-test oracle is itself approximate (the authors concede some oracle failures may be hard to infer and that they do not cover learned verifiers/rerankers, production static analysis, interactive review, or cost/latency).

## Strengths

- Clean separation of construction effects from verifier ranking failures via candidate-pool metrics vs verifier metrics, NA accounting, and sample-mix analysis — avoids the common trap of blaming the verifier for generator-induced prevalence shifts.
- Honest, conservative interpretation of the adversarial G4-adv condition: it is used to expose monitor brittleness, with AUROC/FNR (not prevalence-sensitive AUPRC) as the load-bearing degradation metrics.
- A genuine weak-to-strong decomposition that does not stop at "stronger is better": it identifies a capability-limited component and an evidence-boundary-limited component, and uses diagnostic non-deployed views to show where the M1 boundary itself is the bottleneck.
- Broad, three-domain coverage (function-level, library-heavy data science, artifact-producing workflows) with an explicit oracle audit and a consistent public/hidden freeze policy.
- Clear deployment framing for CI / coding-agent / public-test gates, with the practical 5% FPR triage operating point motivated by escalation budgets rather than an abstract threshold.

## Limitations

- Hidden-test labels measure failures under frozen test suites rather than complete semantic correctness, and some oracle failures may be hard to infer from the public view alone.
- The constructed Data-Science Code and CodeWorkflow splits broaden the bug surface but do not cover all libraries, repositories, or interactive development settings.
- G4-adv is an adversarial stress condition, not a deployment prevalence estimate — numbers like 69–73% hidden-bug rate under G4-adv must not be read as ordinary developer mistake rates.
- The closed weak-to-strong ladder is thin (GPT-5.4-mini vs GLM-5.1) and partially confounded by GLM-5.1 appearing as both generator and strong verifier (mitigated but not eliminated by the GPT-5.4-only subset).
- No learned verifier/reranker training, no full production static-analysis configuration, no interactive review, and no cost/latency tradeoffs are evaluated — so the M1 single-pass monitor is isolated but not compared against the strongest possible tool-using pipeline.

## Relevance

This work is directly relevant to LLM code verification, AI-control / monitor red teaming, and weak-to-strong oversight — i.e., the reliability and safety of LLM-generated code in deployment-like pipelines. For anyone studying code-LLM evaluation, verifier/critic design, or scalable oversight, it provides a concrete protocol and benchmark showing where public-test gates and weak verifiers still fail and how much a stronger verifier can (and cannot) close the gap.

## Questions for Further Exploration

- How would a learned, M1-only verifier/reranker (trained on labelled public-pass candidates from other tasks) compare to GLM-5.1 under the same evidence boundary, and would it narrow the G4-adv FNR gap?
- What is the cost/latency-optimal mix of static analysis, candidate-targeted generated tests, and single-pass LLM review for a fixed escalation budget, given that candidate-targeted tests (AUROC 0.765) already beat every open weak verifier at G1?
- Does the evidence-boundary limit (64% posthoc-inferable but only 33% constructively inferable bugs) shrink if the public tests are made slightly deeper, or is the residual irreducibly hidden in library/API semantics?
- How do the G4-adv evasion degradation results transfer to trajectory-level agent monitoring (e.g., SWE-bench-style agents), where the verifier could inspect tool-call sequences instead of only the final patch?
- Can a self-consistency / multi-sample suspicion vote under M1 recover part of the capability-limited miss pool that GLM-5.1 alone leaves below the 5% FPR threshold?
