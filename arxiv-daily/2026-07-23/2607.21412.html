01 Methodology

A hybrid cognitive architecture: a lightweight LLM only translates natural-language problems into Euclid-IR facts/rules/queries; all multi-step deduction is delegated to a deterministic SWI-Prolog backend run as a subprocess.

  • LLM clientany MCP-capable app generates Euclid-IR and renders returned proof trees.
  • Euclid-MCP server (Python + FastMCP)parses / normalizes Euclid-IR, lowers it to Prolog (IF→:-, AND→,, NOT→\+, ?→?-, $x variables capitalized), enforces sandboxing (500 KB cap, 30 s timeout, predicate allow-list), exposes 4 tools.
  • Inference backendSWI-Prolog via subprocess.run(); solutions + proof trees captured as JSON.
check_kb→reason→diagnose→repair→what_if   ·  the translate-run-inspect-repair loop

Four-tool surface: reason (proof-tree deduction), diagnose (why / why_not / what_needs), what_if (counterfactual +/− edits), check_kb (syntax, undefined predicates, cyclic rules). Two transports: stdio (default MCP) and a standalone HTTP API for n8n / Zapier / Make.

03 Strengths

  • Engine-agnostic IR by design. Explicit, well-justified omissions (no cut, no lists, closed-world negation) keep lowering deterministic and portable.
  • Strong reproducible artifacts. PyPI package, Docker image, public repo with the full CIS/IAM KB and benchmark scripts.
  • Memorable large-RBAC result. Exact counts (31, 103) where both LLMs are wrong, at lower latency and ~14–18× fewer output tokens.
  • Usable practitioner loop. validate → translate → run → inspect → repair → explore; diagnose + what_if go beyond what RAG offers.
  • Honest about the small-KB regime. Openly concedes overhead is not worth it when facts fit in context.

04 Limitations

  • Horn-clause only. No disjunction, cut, list pattern matching, findall/bagof, dynamic assert/retract, modules, or strings — a real expressivity ceiling.
  • Scalability untested beyond ~4K facts. 100K+ will need indexing, tabling, or a Datalog engine — none implemented or measured.
  • Backend dependency. Only SWI-Prolog is wired; the "Datalog/SMT alternative backend" promise is unfulfilled.
  • Integration overhead unquantified. Real deployment needs Euclid-IR generation, error handling, and proof-tree rendering around the server.
  • Benchmark coverage. Synthetic RBAC only; no standard benchmarks, no head-to-head with PrologMCP / LogicLease; the anti-RAG argument is qualitative.

05 Questions for further exploration

  1. How does Euclid-MCP perform on established logical-reasoning benchmarks (ProofWriter, FOLIO, bAbI, RuleTaker) rather than the authors' own synthetic RBAC KB?
  2. What is the quantitative gap vs. a real semantic-RAG pipeline (strong embedding + LLM judge on the same CIS/IAM KB) — currently argued only qualitatively in Table 5?
  3. How does it compare head-to-head with PrologMCP and LogicLease on identical workloads, given they are the closest related systems?
  4. What happens to latency and correctness beyond 10K–100K facts — does tabling/indexing or migration to a Datalog engine preserve the sub-second SLA?
  5. Can diagnose / what-needs be benchmarked for explanation correctness (not just presence) — e.g. against human expert judgments or a held-out ground-truth rationale set?
  6. Does the shared-substrate claim for multi-agent compliance hold empirically — does routing several agents through one Euclid-IR KB measurably reduce policy drift?
  7. How brittle is the LLM-to-Euclid-IR translation step under adversarial or ambiguous natural-language policies, and what is the repair-loop's convergence rate?
