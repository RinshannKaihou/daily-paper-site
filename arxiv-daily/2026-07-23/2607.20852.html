02 Why this matters

Maps exactly where public-test gates and weak LLM verifiers fail in real code pipelines — and how much a stronger verifier can, and cannot, close the gap.

03 Critical edge

The candidate-targeted generated-test baseline (AUROC 0.765) beats every open weak LLM verifier and roughly matches GPT-5.4-mini — single-pass M1 review may be dominated by tool-using test generation.

Plus a thin weak-to-strong ladder: only GPT-5.4-mini vs GLM-5.1, with GLM-5.1 appearing as both generator and verifier.
01

Methodology — a fixed evidence boundary

Visible tests have already run before review. The verifier sees only the M1 public-check view — specification, interface, public tests, candidate code, and public-pass status.

Hidden tests are oracle labels only, never inputs to any verifier. This fixes the candidate-construction effect so verifier ranking can be measured cleanly. Five generators × five conditions × five candidates = 71,000 candidates; only public-pass candidates reach the verifier.

Two scaffolds are compared: Direct (single-pass review) and Hybrid (decompose → coverage gaps → counterexample-oriented review → score). Weak (Qwen-7B, Mistral-7B, Llama-8B) and closed (GPT-5.4-mini, GLM-5.1) verifiers see identical M1 fields.

  • G1Public-test-aware — solve & pass visible tests. Deployment baseline.
  • G2Verifier-aware — G1 + warning that an LLM inspects for hidden bugs.
  • G3Scheme-aware — G2 + description of the verifier's checks.
  • G4-natNatural shortcut — simple public-test-focused implementation.
  • G4-advAdversarial stress — pass public tests, leave a subtle residual defect.

  • Programmatic baselines are weak. Static fatal lint ≈ random (AUROC 0.520); the static-analyzer bundle stays limited (0.570). Candidate-targeted tests reach 0.765 / 0.695 (G1/G4-adv).
  • Inferability audit separates capability from evidence limits. Of 300 bugs, 92% are spec-grounded but only 33% are constructively inferable from M1 (64% posthoc). Diagnostic views raise catch rates monotonically: 24%→74% (weak), 46%→89% (strong).
  • NA-rate trade-off. Hybrid improves Qwen-7B ranking but raises invalid-output NA (3.1%→5.7%); GLM-5.1 pairs the strongest ranking with the lowest NA (1.4%).
03

Strengths & Limitations

＋ Strengths
  • Construction vs. ranking cleanly separated via candidate-pool metrics, NA accounting, and sample-mix analysis — avoids blaming the verifier for generator-induced prevalence shifts.
  • Conservative G4-adv reading — used only to expose monitor brittleness; AUROC/FNR (not prevalence-sensitive AUPRC) carry the degradation claim.
  • Genuine weak-to-strong decomposition distinguishing a capability-limited component from an evidence-boundary-limited one via non-deployed diagnostic views.
  • Three-domain coverage (function-level, library-heavy data science, artifact workflows) with a two-annotator oracle audit (κ=0.80) and a frozen public/hidden policy.
  • Practical deployment framing at the 5% FPR triage point, motivated by real escalation budgets, not abstract thresholds.
－ Limitations
  • Oracle is approximate — hidden tests measure failures under frozen suites, not complete semantic correctness; some failures may be hard to infer from M1.
  • Constructed splits don't cover all libraries, repositories, or interactive development settings.
  • G4-adv is a stressor, not a prevalence estimate — 69–73% hidden-bug rates must not be read as ordinary developer mistake rates.
  • Thin closed weak-to-strong ladder (GPT-5.4-mini vs GLM-5.1), partially confounded by GLM-5.1 acting as both generator and verifier.
  • No learned verifiers/rerankers, no full production static analysis, no interactive review, no cost/latency tradeoffs — the M1 single-pass monitor is isolated, not compared to the strongest tool-using pipeline.
04

Questions for further exploration

  1. Would a learned, M1-only verifier/reranker (trained on labelled public-pass candidates) narrow the G4-adv FNR gap versus GLM-5.1 under the same evidence boundary?
  2. What is the cost/latency-optimal mix of static analysis, candidate-targeted tests, and single-pass LLM review for a fixed escalation budget — given tests (0.765) already beat every open weak verifier at G1?
  3. Does the evidence-boundary limit (64% posthoc- but only 33% constructively-inferable) shrink if public tests are slightly deeper, or is it irreducibly hidden in library/API semantics?
  4. Do the G4-adv evasion results transfer to trajectory-level agent monitoring (e.g., SWE-bench), where the verifier could inspect tool-call sequences rather than only the final patch?
  5. Can a self-consistency / multi-sample suspicion vote under M1 recover part of the capability-limited miss pool that GLM-5.1 alone leaves below the 5% FPR threshold?
