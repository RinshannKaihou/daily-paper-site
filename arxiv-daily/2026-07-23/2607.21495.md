> **一句话总结：** 本文指出非工程用户通过低代码/对话式平台创建AI智能体会造成"可靠性鸿沟"——智能体在用户眼里像静态生产力工具，运行起来却像依赖模型、工具、检索、权限等易变生态的活微服务——并提出了一个由依赖映射、就绪契约、定时检查、诊断与生命周期治理组成的轻量级持续保障框架，辅以9类失效分类法和原型审计器（hosted custom GPT）在6个场景上的可行性验证。

> **TL;DR:** A position paper arguing that democratized AI agent creation (by non-engineering "citizen developers" via low-code/no-code/conversational platforms) creates a reliability gap: agents look like static productivity artifacts to users but behave like live microservices dependent on changing models, tools, retrieval sources, permissions, prompts, and schedules. The authors propose a lightweight continuous-assurance framework (dependency mapping, readiness contracts, scheduled/change-triggered checks, diagnostics, lifecycle governance) backed by a 9-class failure taxonomy, and demonstrate feasibility with a prototype auditor implemented as a hosted custom GPT evaluated on six author-defined scenarios. The paper is explicitly a feasibility study and reports no quantitative metrics (no coverage, false-positive rate, or time-to-recovery); the six-scenario assessment is qualitative and author-defined, with independent validation deferred to future work.

## 核心贡献

- **定义"工业可靠性鸿沟"并给出失效分类法。** 指出去中心化创建的、长期运行的AI智能体会因模型权重更新、检索索引过期、API schema漂移、权限失效、归属不清等原因而**静默退化**——用户/创建者往往看不到日志与依赖链。据此提出覆盖模型依赖、工具调用、检索、权限凭据、输出契约、工作流调度、语义退化、归属、治理共9类的失效分类法（Table I）。
- **提出轻量级持续保障框架（5要素）。** 依赖图 → 就绪契约 → 定时/变更触发的保障检查 → 诊断 → 生命周期治理；核心设计原则是**"专长翻译"（expertise translation）**：把领域专家用任务级语言表达的期望（源可达、查询新鲜、工具返回正确字段、输出满足schema、存在有效owner与升级路径）自动翻译成可重复执行的就绪检查，让组织在"每个agent创建者都去学DevOps/MLOps"与"无人监控"之间找到第三条路。
- **原型审计器 + 场景化可行性评估。** 将分类法与就绪契约实现为一个hosted custom GPT原型，强调**证据纪律**（区分 confirmed finding / reproducible risk / unknown / N/A，绝不臆测私有配置）。在一个公开GitHub仓库中提供审计器指令、就绪契约模板、匿名化场景与期望发现，供透明复现。通过6个故障注入式场景评估，验证该思路能把可观测症状转化为有证据约束、可执行的就绪判定，而非简单的pass/fail。

## Key Contributions

- **Identifies the "industrial reliability gap" and a 9-class failure taxonomy.** Long-lived, citizen-created agents fail for reasons that differ from both static documents and traditional software: updated model weights, stale retrieval indices, shifted API schemas, expired permissions, broken schedules, unclear ownership. The taxonomy (Model dependency, Tool invocation, Retrieval, Permission/credential, Output contract, Workflow/scheduling, Semantic degradation, Ownership, Governance) is derived from DevOps dependency categories [5] extended with organizational (ownership, governance) classes, conceptually rooted in the authors' prior visibility work [6,7].
- **A lightweight continuous-assurance framework (5 elements).** (1) Dependency map (models, prompts, tools, APIs, retrieval sources, files, permissions, schedules, downstream consumers); (2) Readiness contract (the minimum observable conditions under which the agent is considered operational); (3) Scheduled or change-triggered assurance checks; (4) Diagnostics that classify failures by taxonomy and estimate operational impact; (5) Lifecycle governance (ownership, escalation, criticality, auditability, retirement). The guiding principle is **expertise translation** — converting a domain expert's task-level success criteria into reliability artifacts runnable by an assurance layer, so citizen creators never need to master DevOps/MLOps/AgentOps.
- **A prototype auditor with evidence-disciplined, scenario-based assessment.** Implemented as a hosted custom GPT, the auditor distinguishes *confirmed findings* from *risks*, *unknowns*, and *N/A* checks to avoid overclaiming access to private settings, hidden dependencies, or retrieval indexes. Inspectable components (instructions, declared properties, readiness-contract template, anonymized scenarios, expected findings) are released publicly; the authors transparently disclose that a hosted GPT cannot be fully exported or externally inspected [8,9].

## Methodology

The paper is structured as **taxonomy → framework → prototype**, not as a benchmark study.

1. **Failure taxonomy (Section II, Table I).** Failure classes were derived from dependency categories reported in the DevOps literature [5] and extended with organizational classes (Ownership, Governance) motivated by a real industrial deployment described in the introduction — a citizen-built agent handling sensitive workflows in the legal department of a major aerospace company, where no one could answer "if this agent stops working correctly, how will it be detected, and who will be alerted?". A guiding principle is that failures should be evaluated by **structure and human perceptibility**, not just immediate execution success, shifting the diagnostic lens from binary execution errors to operational-level shifts beneath the user interface.

2. **Continuous-assurance framework (Section III, Figure 1).** Five elements: dependency map, readiness contract, scheduled assurance checks, diagnostics & alerts, lifecycle governance. The illustrative readiness contract for a document-analysis agent specifies five observable conditions: (1) declared source documents and retrieval index reachable; (2) representative queries return current/relevant material; (3) required tools/APIs execute and return expected fields; (4) output satisfies required structure and mandatory fields; (5) agent has a valid owner and escalation path. Failure of any condition is evidence the agent should not be treated as fully ready — not proof that every future answer will be wrong. Assurance policies are intended to be **criticality-based** (lightweight checks for informal productivity agents; stricter contracts, audit trails, and escalation for agents in recurring operational/legal/financial/customer-facing workflows).

3. **Prototype auditor and scenario-based assessment (Section IV, Table II).** The auditor is a hosted custom GPT that, given an agent description, configuration evidence, task examples, and optional execution transcripts, identifies declared/implicit dependencies, derives a readiness contract, classifies failures, and produces remediation guidance. Evaluation used **scenario-based fault assessment** [10] rather than model-accuracy benchmarking. Each scenario had an *author-pre-defined* expected readiness finding; success required the auditor to (1) assign the issue to the correct taxonomy class, (2) distinguish confirmed evidence from risks/unknowns, (3) avoid claims about unavailable private configuration, and (4) produce a concrete owner/administrator-executable remediation action.

The methodology is explicitly a feasibility check, not a measurement of coverage, false-positive rate, or operational effectiveness.

## Results & Highlights

No quantitative results reported. The paper is a position/feasibility study and provides **only qualitative, scenario-based evidence**; the authors explicitly state the assessment is "an initial feasibility assessment rather than a measurement of coverage, false-positive rate, or operational effectiveness," and defer those measurements to future work.

The qualitative evidence offered is the six-scenario assessment (Table II), in which the prototype auditor produced readiness decisions consistent with the expected failure class and available evidence:

- **Retrieval failure** ("required source document unavailable") → auditor returned *"Not ready: restore the source or rebuild the index"* — confirmed finding, correct taxonomy class.
- **Output-contract failure** ("expected output field is missing") → *"Not ready: enforce schema-level validation"* — confirmed finding.
- **Tool-invocation failure** ("tool or API error appears in transcript") → *"Not ready: check the action schema and returned fields"* — confirmed finding.
- **Ownership failure** ("agent has no valid owner") → *"Not ready for operational use until ownership is reassigned"* — confirmed finding.
- **Retrieval/Governance mixed** ("source freshness cannot be verified") → *"Readiness unknown: perform owner-side freshness tests"* — correctly reported as unknown rather than overclaimed.
- **Governance/inspectability limit** ("private GPT configuration is not inspectable") → *"Do not claim verification; list evidence required for confirmation"* — correctly flagged as not externally verifiable, demonstrating evidence discipline rather than hallucinating access to private settings.

The headline qualitative claim: across these six scenarios the auditor supported **evidence-grounded readiness decisions instead of binary pass/fail judgments** — confirmed operational failures were classified as "not ready," while unverifiable properties were reported as "unknown / not externally verifiable." No accuracy percentage, coverage number, false-positive rate, latency, or time-to-recovery figure is reported anywhere in the paper.

## Critical Assessment

- **Novelty (moderate):** The reframing of citizen-created agents as *live microservices that look like static productivity artifacts*, and the *readiness contract* abstraction (translating task-level expectations into repeatable observable checks), are genuinely useful framing contributions for the citizen-development era. However, every individual technical ingredient — dependency mapping, scheduled checks, diagnostics, lifecycle governance — is standard DevOps/MLOps/AgentOps practice ([4] AgentOps, [5] DevOps mapping). Novelty is in the *packaging for non-engineers* and the *expertise-translation principle*, not in any new algorithm, metric, or technique.
- **Rigor (weak):** The entire empirical claim rests on **six author-defined scenarios** with author-pre-defined expected findings — a textbook confirmation-risk design in which the same authors wrote both the test cases and the answer key. There is no independent ground truth, no held-out data, no coverage estimate, no false-positive rate, no time-to-recovery measurement. The paper honestly admits this ("validation against independently reported agent failures is left to future work"), but it means the evaluation cannot support any generalization claim about the auditor's reliability.
- **Reproducibility (partial):** The core artifact is a **hosted custom GPT**, which by OpenAI's platform design cannot be fully exported or externally inspected [8,9]; the authors disclose this and release only the inspectable components on GitHub. The end-to-end artifact is therefore not independently runnable, and the auditor's runtime behavior cannot be fully audited — a notable irony for an *assurance* tool.
- **Significance (timely but unproven):** As a position/vision paper it targets a real, fast-growing industrial problem (low-code platforms putting agent creation in the hands of thousands of domain experts with no reliability training). The thesis — "democratized AI agent creation requires democratized assurance" — is sound and well-argued. But the paper is far from a validated solution; it is closer to an extended problem statement plus a proof-of-concept.
- **Red flags:** (1) The empirical evaluation is self-graded on six self-authored scenarios. (2) A **self-referential assurance gap**: the LLM-based auditor is itself subject to the exact model drift, API changes, and tool failures it is meant to detect in other agents — the authors acknowledge this ("the auditor itself ... is vulnerable to the same drifts") but do not resolve it; "meta-assurance" is left entirely to future work. (3) The motivating aerospace legal-department story is anecdotal and unattributed, carrying real rhetorical weight without being checkable.

## Strengths

- Identifies and clearly articulates a genuine, under-addressed industrial problem: the mismatch between how users *perceive* citizen-created agents (static artifacts) and how they *behave* (live microservices with fragile, evolving dependencies).
- The **expertise-translation** principle is a practical, well-motivated design goal — it correctly avoids the unrealistic assumption that every domain-expert agent creator should learn reliability engineering.
- Strong **evidence discipline** in the prototype design: the explicit distinction between confirmed findings, risks, unknowns, and N/A — and the instruction never to infer readiness for uninspectable private configuration — is exactly the right behavior for an assurance tool and is demonstrated in the "unknown" / "not externally verifiable" scenario outcomes.
- Honest, non-overclaiming tone: the authors repeatedly and explicitly bound what the evaluation does and does not show, and disclose the hosted-GPT inspectability limitation rather than hiding it.
- Public release of inspectable components (instructions, readiness-contract template, anonymized scenarios) on GitHub enables partial scrutiny and reuse.

## Limitations

- **No quantitative evaluation:** no detection coverage, false-positive rate, false-negative rate, latency, or time-to-recovery is measured; the paper is upfront that these are deferred to future work.
- **Self-graded, author-defined scenarios:** the six scenarios and their expected findings were written by the same authors who ran the auditor, so the "consistent with expected" result carries confirmation risk and cannot generalize.
- **Tiny, hand-picked sample:** six scenarios is too small to estimate any statistical property of the auditor, and the authors say so.
- **Non-distributable, non-inspectable core artifact:** the hosted custom GPT cannot be fully exported or externally verified [8,9], so independent end-to-end reproduction is impossible; only the inspectable logic is public.
- **Self-referential assurance gap:** an LLM-based auditor is itself vulnerable to model drift, API changes, and tool failures, and the paper provides no independent automated meta-assurance mechanism.
- **Taxonomy not validated:** the 9-class taxonomy is derived from DevOps literature plus the authors' own organizational observations; its completeness or inter-annotator agreement is never tested against real agent-failure corpora.
- **No human-in-the-loop study:** the paper does not evaluate whether non-engineering users can actually understand or act on the readiness findings — again deferred to future work.

## Relevance

对于关注 **LLM Agent / 智能体工程化与可靠性** 的研究者而言，本文切中了一个正在快速放大的真实痛点——低代码/无代码平台让大量非工程用户在生产环境中创建并依赖AI智能体，却缺乏配套的可观测与保障机制。提出的"就绪契约 + 持续保障"思路（尤其是把任务级期望翻译成可重复检查、并强调证据纪律、拒绝臆测私有配置）对Agent Ops、智能体评测与生命周期治理方向有直接的方法论启发，适合作为该方向的立场性参考；但因缺乏量化评估，更接近问题陈述与概念验证，而非可直接复用的技术方案。

## Questions for Further Exploration

- How would the auditor perform under **independent, third-party-reported real-world agent failures** (e.g., from post-mortems of production citizen-built agents), and what detection coverage / false-positive rate would it achieve on such a corpus?
- Can the **9-class taxonomy** be validated empirically — e.g., by collecting a large set of real democratized-agent failures and measuring inter-annotator agreement on class assignment, or testing whether the classes are mutually exclusive and collectively exhaustive?
- How should **criticality-based assurance policies** be calibrated: what concrete thresholds (usage frequency, blast radius, data sensitivity) should determine whether an agent gets lightweight checks versus strict contracts, audit trails, and escalation?
- How can the **self-referential assurance gap** (an LLM auditor vulnerable to the same drifts it detects) be closed — via fixed regression suites, multi-agent cross-checking, or platform-level telemetry — and can any of these be made provably independent of the auditor's own LLM?
- Does the **readiness contract** abstraction transfer beyond custom-GPT-style platforms to function-call/tool-calling agents built on open frameworks (LangGraph, AutoGen, CrewAI), where dependencies and permissions are far more programmatically inspectable — and does inspectability materially change the evidence-discipline trade-offs?
- What does a meaningful **human-in-the-loop study** with actual non-engineering agent creators show about whether they can interpret and act on "unknown / not externally verifiable" findings without engineering support?
