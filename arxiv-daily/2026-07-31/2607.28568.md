> **一句话总结：** 清华大学与 Frontis.AI 提出开源全栈系统 OpenMLE（任务环境 OpenMLE-Gym + 算子级 SFT/RL 训练 OpenMLE-ERL + 经验引导的长程进化搜索 OpenMLE-Evo），训练出 35B 的"元进化"agent 模型 Frontis-MA1，在 MLE-Bench Lite 上单卡 RTX 4090(12GB) 12 小时预算内将 Medal Average 从基座模型的 39.39% 提升到 60.61%（OpenMLE-Evo）乃至 71.21%（OpenMLE-Evo-Max），超过 GPT-5.5+Codex 的 68.18% 达 3.03 个百分点，并在保留测试集 NatureBench Lite 上验证训练与搜索两个组件均可独立迁移。

> **TL;DR:** The paper introduces OpenMLE, a full open stack (OpenMLE-Gym: 5,758 quality-gated executable ML-engineering tasks; OpenMLE-ERL: execution-grounded SFT+RL for four shared program-transformation operators Draft/Improve/Debug/Crossover; OpenMLE-Evo: experience-guided evolutionary search) used to post-train a 35B "meta-evolution" agent, Frontis-MA1, whose learned operators are the same operators the search harness later composes. On MLE-Bench Lite (22 tasks, 12-hour/task budget on a single RTX 4090 capped at 12GB VRAM), Frontis-MA1-35B improves Medal Average from 39.39% (Qwen3.6-35B-A3B base) to 60.61% under the shared OpenMLE-Evo harness, and to 71.21% with OpenMLE-Evo-Max — exceeding GPT-5.5+Codex (68.18%) by 3.03 points and approaching GPT-5.6 Sol / Kimi K3 (72.73%). On the held-out NatureBench Lite, holding the harness fixed the trained model raises Match-SOTA from 50% to 70%, and holding the model fixed the trained search framework raises it from 20% to 50%.

## 核心贡献

- 提出 OpenMLE 全栈框架：OpenMLE-Gym 统一了 5,758 个质量筛选后的可执行 MLE 任务（156 个精选锚点 + 3,362 个 Kaggle 数据集任务 + 2,240 个 Kaggle 竞赛任务），配套隔离沙箱执行与任务专属评估器。
- 提出 OpenMLE-ERL：将 Draft（起草）、Improve（改进）、Debug（修复）、Crossover（交叉重组）四个原子式程序演化算子作为可训练目标，通过执行落地的监督微调（26,259 条样本）与强化学习（自适应奖励边界 + 熵优势上尾加权 + 异步 rollout）联合训练，而非只训练端到端轨迹。
- 提出 OpenMLE-Evo：用结构化"经验卡片"记录每个候选节点的谱系、性能与执行结果，结合质量/进步/新颖度三因子的非贪心父节点选择，以及按算子类型的按需记忆合成，替代原始 AIRA-Evo 的贪心分数选择与全量记忆合成。
- "元进化"闭环：同一套算子既被训练又被推理时的进化搜索复用，使 Frontis-MA1 本身成为其自身搜索算法的变异引擎；开源模型权重、数据集、训练/评估代码与沙箱基础设施。

## Key Contributions

- **OpenMLE-Gym**: a unified suite of 5,758 quality-gated executable ML-engineering tasks (156 curated anchors + 3,362 Kaggle-dataset tasks + 2,240 Kaggle-competition tasks) with isolated sandbox execution, structured feedback, and task-specific evaluators, built via an automated construction-and-filtering pipeline (executability validation + LLM-based semantic quality gate).
- **OpenMLE-ERL**: trains four reusable, shared atomic operators (Draft, Improve, Debug, Crossover) via execution-grounded SFT (budget-adaptive collection producing a 26,259-example corpus) and RL (adaptive per-task reward bounds, an entropic upper-tail advantage that gives the best candidate ~4x stronger learning signal, and asynchronous group rollout to remove straggler stalls) — decoupling the local skills the model learns from the search algorithm used at inference time.
- **OpenMLE-Evo**: an evolutionary search harness that stores structured, queryable experience cards and a task-global experience board, selects parents by a three-factor utility (validation quality, improvement-over-parent, method-family novelty) instead of score-only fitness, and defers LLM-based memory synthesis until an operator actually needs it (operation-triggered, bounded, operator-conditioned context).
- **Frontis-MA1-35B/30B and full-stack release**: trained and released a 35B primary model plus a 30B cross-model-replication companion, together with the datasets, sandbox infrastructure, training/eval code, and final checkpoints, positioned as filling a gap where (per the paper's own audit of 20 public systems, Table 11) essentially no prior public work jointly ships data + sandbox + training code + RL method + eval + weights.

## Methodology

OpenMLE formalizes MLE as an environment where, at each search step, an inference-time controller selects an operator $a_t \in \{$Draft, Improve, Debug, Crossover$\}$, builds an operator context $c_t$ from zero or more parent programs and their execution feedback, and the policy $g_\theta(\cdot \mid \tau, a_t, c_t)$ proposes a program $p_t$ that a sandbox executes and a task-specific evaluator scores. Each OpenMLE-Gym task is an environment instance defined by task/state (spec, public data, hidden evaluator, budget, workspace), action (submitted program + requirements), transition (sandboxed execution), observation (status, score, logs, error type, artifacts), and reward (the task-specific evaluator's score); a shared backend returns six feedback modes (success, runtime error, missing code, missing submission, scoring failure, timeout) at scale over CPU/GPU Docker workers.

OpenMLE-ERL post-trains the operators in two stages. Execution-grounded SFT uses a budget-adaptive, difficulty-aware collection rule: sampled programs are executed and retained by validity/score until either an accepted-example quota is hit or the task's execution budget is exhausted, combining a "parallel path" of full Draft solutions (17,245 examples) with an "evolutionary path" that retains useful local revision steps traced back from valid Debug/Improve/Crossover endpoints (9,014 examples), totaling 26,259 SFT examples. RL then converts heterogeneous raw task scores into a bounded, comparable "base reward" via clipped, exponentiated adaptive bounds derived from each task's own on-policy score frontier (rather than fixed leaderboard bounds), and further reshapes the reward with an entropic advantage $A_i^{ent} \approx \exp(\beta r_{proc,i}) / (\frac{1}{G-1}\sum_{j\neq i}\exp(\beta r_{proc,j})) - 1$ that concentrates learning signal on the best candidate in each rollout group (measured 4.0x stronger mean processed advantage than without entropic weighting). RL removes synchronization stalls by consuming asynchronously completed generation-execution groups from a queue rather than waiting on the slowest sandbox job, and selects which parent program each operator practices on via a fitness-proportional utility $F(p) = norm(R_p) + norm(Var_{c \in child(p)} R_c) + norm(C_p)$ combining parent reward, child-reward variance (informativeness), and a visit-based cooling term (anti-monopolization).

OpenMLE-Evo composes the trained operators into an AIRA-Evo-style population search but redesigns how execution evidence is used. After each sandbox evaluation, a deterministic node-level "experience card" (provenance, performance, outcome, resource usage) is created and aggregated into a task-global "experience board" tracking method-family statistics, underexplored directions, and error signatures. Parent selection uses $U_i = \lambda_s \tilde{s}_i + \lambda_\Delta \bar{\Delta}_i + \lambda_n \nu_i$ (normalized validation score, normalized improvement over the strongest parent, and method-family novelty) with softmax sampling, rather than AIRA-Evo's near-greedy score-based sampling. Rich natural-language memory is synthesized by an LLM only on-demand, for the specific parent(s)/ancestors/siblings selected for an upcoming Improve/Crossover/Debug call, and cached — avoiding AIRA-Evo's practice of eagerly summarizing every evaluated node regardless of whether it is ever revisited. The resulting operator-conditioned context for e.g. Improve concatenates the selected node's own record with a vertical trace of recent ancestors and a horizontal set of the most informative siblings, rather than an ever-growing full history.

## Results & Highlights

- **MLE-Bench Lite, model effect (holding harness = OpenMLE-Evo fixed)**: Frontis-MA1-35B reaches **Medal Average 60.61%** (Human Rank 0.7647) versus its **Qwen3.6-35B-A3B base at 39.39%** (Human Rank 0.5828) — a **+21.22 percentage point** gain from execution-grounded post-training alone.
- **MLE-Bench Lite, system-level result**: Frontis-MA1-35B + **OpenMLE-Evo-Max reaches 71.21% Medal Average / 0.8126 Human Rank**, exceeding **GPT-5.5 + Codex at 68.18% / 0.7833** by **3.03 points**, and approaching GPT-5.6 Sol and Kimi K3 (both 72.73%).
- **Cross-model replication (30B)**: under the identical OpenMLE-Evo harness, Frontis-MA1-30B improves **Qwen3-30B-A3B-Thinking-2507 from 34.85% to 53.03%** Medal Average (**+18.18pp**), reaching 66.67% / 0.8053 Human Rank with OpenMLE-Evo-Max.
- **Harness effect (holding model = Frontis-MA1-35B fixed)**: OpenMLE-Evo (60.61%) outperforms the original, untrained-operator **AIRA-Evo harness at 53.03%** on the same checkpoint — a **+7.58pp** gain attributable to the trained search framework alone.
- **Search efficiency vs. original AIRA-Evo** (same 35B checkpoint/seed, 12-hour budget, 66 matched task-runs): OpenMLE-Evo cuts total model-token consumption **129.3M → 75.3M (−41.7%)** and prompt tokens **83.5M → 41.5M (−50.3%)** while raising new-best validation updates per million tokens **1.77 → 3.27 (+84.3%)** and the Improve-sets-new-best rate **4.73% (44/931) → 9.36% (72/769)**.
- **NatureBench Lite transfer (10-task subset, All M = Match-SOTA)**: holding the search adapter fixed, Frontis-MA1-35B reaches **70% (7/10)** versus its Qwen3.6-35B-A3B base's **50% (5/10)**; holding the base model fixed, the trained OpenMLE-Evo adapter reaches **50% (5/10)** versus original AIRA-Evo's **20% (2/10)** — evidence that both the post-trained model and the trained search framework transfer beyond competition-style MLE.
- **Compute-budget caveat (Table 11, self-reported)**: several other public agentic MLE systems report *higher* raw Medal Rate on MLE-Bench Lite under larger budgets — e.g., MLEvolve **80.30%** (12h, 1×H200) and AIBuildAI **77.27%** (24h, 1×A100) — versus Frontis-MA1-35B + OpenMLE-Evo-Max's **71.21%** under a markedly tighter 12h/1×RTX-4090-12GB budget; the paper itself notes (footnote 3) that its comparisons use each system's reported per-run compute and are not FLOPs-normalized.

## Critical Assessment

**Novelty**: The "meta-evolution" framing — training the same Draft/Improve/Debug/Crossover operators via execution-grounded SFT+RL that a search harness later composes at inference time — is a genuinely distinctive coupling of post-training and evolutionary test-time search, going beyond prior work (AIRA, AIDE, MLE-Dojo, MLE-Smith) that either trains full trajectories, uses frozen general models as operators, or focuses only on environment/task construction.

**Rigor**: The controlled-comparison design is a real strength (matched-harness, matched-model, and independent cross-model replication on a second 30B backbone). However, the mechanism analysis in Sections 6.5–6.6 relies heavily on a handful of hand-picked illustrative case studies (four named tasks: nomad2018-predict-transparent-conductors, the-icml-2013-whale-challenge-right-whale-redux, leaf-classification, mlsp-2013-birds) rather than a systematic per-component ablation isolating structured experience cards, three-factor parent selection, and on-demand memory synthesis individually — the paper itself concedes in Figure 18's caption that "the full framework also changes targeted Memory, [so] the end-to-end difference from original AIRA-Evo should not be attributed to the three [selection] weights alone." A further inconsistency: in Table 1's matched-harness comparison, GLM-5.2 + OpenMLE-Evo raises Medal Average over GLM-5.2 + Claude Code (62.12% vs. 59.09%) but *lowers* both Valid Rate (19.67/22 vs. 21.00/22) and Human Rank (0.7069 vs. 0.7948) — a genuine metric divergence the narrative text does not address when claiming OpenMLE-Evo "consistently converts the same model into a stronger MLE system."

**Reproducibility**: Strong relative to the field — released weights, the full 26,259-example SFT corpus, sandbox code, and training/eval pipelines, positioned explicitly against a landscape where (Table 11) no comparable system ships Data + Sandbox + Train code + RL method + Eval + Weights together. A real limitation, acknowledged in a footnote, is that full task-package source data is released for only 1,415 of the 5,758 Gym tasks due to licensing; the remaining 4,343 ship only `prepare.py`/`metric.py` scripts, so full Gym reconstruction depends on re-acquiring the original Kaggle assets.

**Significance**: The headline "exceeds GPT-5.5 + Codex" claim is real but budget-scoped — it holds under a constrained per-task budget (single RTX 4090, 12GB VRAM, 12h) that is explicitly not normalized against the accelerators/budgets used by comparison systems; the paper's own Table 11 shows other public agentic systems (MLEvolve, Famous-Agent 2.0, both 80.30%) exceeding Frontis-MA1's 71.21% under larger H200/A100 budgets, so the result is best read as "best-in-class under a tight, low-VRAM compute budget" rather than an absolute new SOTA.

**Red flags**: No ablation isolates the SFT-only contribution from the subsequent RL contribution to the +21.22pp Medal Average gain; the NatureBench Lite transfer study uses a hand-curated 10-task subset chosen to "favor moderately tractable tasks," which the authors themselves flag as limiting the breadth of the transfer conclusion.

## Strengths

- Rare full-stack open release (data, sandbox, training code for both SFT and RL, evaluation harness, and final weights), self-audited against ~20 comparable public systems in Table 11.
- Careful, multi-angle controlled comparisons (matched harness, matched model across four frontier backbones, and independent 30B cross-model replication) that make causal attribution of gains to training vs. search more credible than typical single-number leaderboard claims.
- Genuine held-out transfer evidence on NatureBench Lite, a benchmark built from real Nature-family papers rather than Kaggle-style competitions, reducing the risk that reported gains are narrowly overfit to MLE-Bench's task distribution.
- Detailed, transparent engineering description of non-trivial design choices (budget-adaptive SFT collection, adaptive per-task reward bounds, entropic upper-tail advantage, asynchronous rollout, operation-triggered memory synthesis) with quantified ablation-style comparisons against the un-shaped variants (e.g., Figure 8's entropic-weighting comparison).

## Limitations

- (Authors' own, Section 8) The system learns primarily from final execution scores, not from richer signals about hypothesis quality, generalizability, or reasoning process — so it is better at optimizing known solution paths than at judging which untried research directions are worth pursuing.
- (Authors' own) Evolutionary search remains an external harness composing trained operators rather than a unified agent that can freely initiate its own actions; the evolutionary system itself is not yet an object of learning/evolution.
- (Authors' own) The agent only improves external ML artifacts (Kaggle-style pipelines), not the language models or evolutionary system itself — a narrower slice of "AI4AI" than full recursive self-improvement.
- (Authors' own) The three-factor parent-selection utility uses fixed, hand-set weights rather than a learned, task-adaptive policy, leaving most of the recorded experience-card metadata underutilized.
- Transfer evidence is confined to a 10-task NatureBench Lite subset and small per-modality MLE-Bench groups (e.g., only 2 audio and 2 multimodal tasks), limiting how far the meta-ability/transfer claims can be generalized.
- No compute/FLOPs-normalized comparison against higher-scoring public systems reported in the paper's own Table 11.

## Relevance

该论文提供了一个训练"会自我进化的 MLE agent"的完整开源技术栈（可执行任务集、沙箱、SFT/RL 训练代码、经验引导的进化搜索、开源权重），对研究 LLM agent 的执行反馈式后训练、进化搜索与"元进化"耦合机制具有很高的复现与借鉴价值，也为 AI4AI/递归自我改进方向提供了一个具体可执行的中间基准。

## Questions for Further Exploration

- How much of the +21.22pp Medal Average gain is attributable to the SFT warm-start alone versus the subsequent RL stage — would an SFT-only Frontis-MA1 variant already close most of the gap to the fully trained model?
- Why does the GLM-5.2 matched-harness comparison show OpenMLE-Evo achieving a higher Medal Average but a lower Human Rank and Valid Rate than Claude Code, and is this instability present in other model/harness combinations not reported in the main tables?
- Would the reported "exceeds GPT-5.5+Codex" result survive a compute-normalized comparison (matched GPU-hours or FLOPs rather than "single RTX 4090, 12h") against the higher-scoring Table 11 systems (MLEvolve, Famous-Agent 2.0, AIBuildAI)?
- Does the non-greedy three-factor parent-selection utility (quality/progress/novelty) generalize with its current fixed weights across task modalities, or would learned, task-conditional weighting (as the authors suggest as future work) change which OpenMLE-Evo mechanism matters most?
- How would OpenMLE-Evo's structured-experience mechanism perform on the full 90-task NatureBench rather than the curated, "moderately tractable" 10-task subset used here?
- Can the meta-evolution loop be extended so the trained operators also propose modifications to the evolutionary search algorithm itself, as the authors flag under "evolving the evolutionary system" in their limitations?
