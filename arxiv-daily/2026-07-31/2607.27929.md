> **一句话总结：** Meta-Task 把"合成终端任务"本身重新定义成一个 Terminal-Bench 格式的终端任务，让智能体在真实 Docker 容器里端到端地设计、实现并自验证任务包，仅用 3,221 条合成轨迹微调就让 Qwen3-14B/32B 在 Terminal-Bench 2.0 上分别达到 22.5% 和 31.8% 的 Avg Pass@1，超过训练数据量大得多的同期方法。

> **TL;DR:** Meta-Task reframes terminal-task synthesis as itself a Terminal-Bench-format task executed end-to-end by an agent inside a Docker container (explore examples → search materials → design → implement → self-validate), combined with multi-phase diversity control and LLM-as-Judge trajectory filtering. Fine-tuning Qwen3-32B on only 3,221 filtered SFT trajectories reaches 31.8% Avg Pass@1 on Terminal-Bench 2.0, beating Nemotron-Terminal-32B (27.4%, trained on 490.5K trajectories) and TerminalTraj-32B (22.0%, 50.7K trajectories), and even surpassing the 15x-larger Qwen3-Coder-480B-A35B (23.9%).

## 核心贡献

- **把任务合成本身变成一个终端任务**：不同于以往"生成-验证"分离的流水线，Meta-Task 将"合成一个 Terminal-Bench 任务包"封装成标准的 Terminal-Bench 格式任务（instruction、Docker 环境、参考解、验证测试），由智能体在真实容器里探索样例、检索资料、设计并实现任务，再迭代自验证直至通过，从而天然获得执行落地性（execution grounding）和高可扩展性。
- **解耦的多维度多样性控制**：将目标任务需求拆解为技术领域（39 个类别）、指令写作风格（10 种场景模板）、难度（4 级）三个正交维度，单相模式即可产生 1,560 种基础组合；进一步引入多相（multi-phase）机制，让智能体基于约 2,000 个技术主题种子和约 120 种场景约束动态设计全新的（类别，场景）组合，理论多样性空间扩展到 24 万+ 种子组合。
- **可选的外部材料支持**：内置搜索下载工具，可从 GitHub、HuggingFace 检索真实开源素材，或直接使用预置的领域数据，增强任务的真实感和多样性。
- **两层质量过滤**：先用执行结果（是否通过全部验证测试）过滤合成任务与轨迹，再用 LLM-as-Judge 在轨迹级别筛除"注释泄题"或"交互过短、学习信号不足"的轨迹，最终从 14,040 条采样轨迹中仅保留 3,221 条作为 SFT 训练数据。
- 实验表明：仅用 3,221 条训练轨迹（远少于 TerminalTraj 的 50.7K 和 Nemotron-Terminal 的 490.5K），Meta-Task-32B 即可达到 31.8% Avg Pass@1，逼近 GPT-5（35.2%）和 Gemini 2.5 Pro（32.6%），显著缩小小规模开源微调模型与全尺寸闭源系统之间的差距。

## Key Contributions

- **Redefining task synthesis as a terminal task itself (the "meta-task")**: instead of separating generation and execution verification into distinct stages (as in TermiGen, Nemotron-Terminal, SkillSynth), Meta-Task packages a synthesis request as a standard Terminal-Bench task (instruction + Docker environment + example tasks + output templates + verification tests). An agent then explores, searches, designs, implements, and iteratively self-validates a complete task package (instruction.md, Dockerfile, solution, tests) inside a live container until all checks pass — giving inherent execution grounding and eliminating hallucination issues of pure LLM generation.
- **Decoupled, multi-phase diversity control**: three orthogonal dimensions — category (39 technical domains, e.g., Database Systems, Reverse Engineering, ML Training), scenario/instruction-writing style (10 templates from "minimal" one-liners to "emergency" urgent notes), and difficulty (4 levels) — yield 39×10×4 = 1,560 base combinations. A multi-phase mode further lets the agent dynamically design novel (category, scenario) pairs from ~2,000 topic seeds and ~120 scenario-style constraints, extending the effective diversity space beyond 240,000 seed combinations.
- **Optional external material grounding**: a configurable search-and-download tool retrieves real GitHub/HuggingFace materials, plus support for pre-supplied domain data, to ground synthesized tasks in authentic development scenarios rather than pure hallucination.
- **Two-stage quality filtering**: (1) execution-based filtering keeps only trajectories whose agent-produced solution passes all verification tests; (2) LLM-as-Judge filtering (same backbone model in thinking mode) removes trajectories with suggestive code annotations/solution leakage or trivially short interactions lacking learning signal. This reduces 14,040 sampled trajectories to 5,004 passing execution, and finally to 3,221 after LLM-as-Judge screening.
- **Implementation**: uses open-source Qwen3.5-397B-A17B-FP8 as the backbone for both task synthesis (paired with the Claude Code agent scaffold via vLLM) and trajectory sampling (Terminus-2 scaffold), with LoRA fine-tuning (rank 64/alpha 128) of Qwen3-14B/32B via the SWIFT framework.

## Methodology

Meta-Task is a three-stage pipeline (Figure 2):

1. **Stage 1 — Meta-Task Generation**: A meta-task instruction combines fixed components (defining *how* to synthesize: target file descriptions, workflow, output format requirements, best practices, a self-validation checklist) with variable components (defining *what* to synthesize: category, scenario, difficulty — either sampled from the 1,560 single-phase combinations or dynamically designed via the multi-phase mechanism from topic/scenario seeds). Each meta-task's Docker environment is pre-configured with a task-skeleton template (placeholder file structure), one example task randomly drawn from a pool of 100 reference tasks (synthesized by Claude Opus 4.6 and manually verified), and optionally the search-and-download tool and/or pre-supplied domain materials.
2. **Stage 2 — Agent Synthesis**: An agent (e.g., Claude Code scaffold) is launched inside the built Docker container and must explore the example/template, search for real-world materials, design a problem, and implement a complete task package (instruction, Dockerfile, solution, tests). It then validates its own output by executing the solution, running tests, and checking cross-component consistency, looping until all checks pass — critically, this entire process happens with real stdout/stderr feedback inside a live terminal, unlike generation-only pipelines.
3. **Stage 3 — Quality Filtering**: A teacher model (Qwen3.5-397B-A17B, via Terminus-2 scaffold) samples solution trajectories on the validated synthesized tasks. Execution-based filtering keeps only trajectories that pass all verification tests; LLM-as-Judge (same model, thinking mode) then removes trajectories with solution leakage/hints or insufficient learning signal (too-short interactions). Surviving trajectories form the final SFT dataset.

Training uses LoRA (rank 64, alpha 128, all linear modules, lr 1e-4, cosine schedule, 5 epochs, sequence length 40,960, BF16) on 8× A100 80GB GPUs with DeepSpeed ZeRO-3, applied to Qwen3-14B and Qwen3-32B base models. Evaluation follows the official Terminal-Bench 2.0 protocol using the Harbor orchestration framework with the Terminus-2 agent scaffold, non-thinking mode, temperature 0.7, top-p 0.8, top-k 20, presence penalty 1.5; results are averaged over 3 independent runs.

## Results & Highlights

- **Main benchmark result (Terminal-Bench 2.0, Table 2)**: Fine-tuning lifts Qwen3-14B from a 5.2% base Avg Pass@1 to **22.5%** (+17.3 points), and Qwen3-32B from 4.1% to **31.8%** (+27.7 points).
- **Beats concurrent fine-tuned baselines at the same scale with far less data**: Meta-Task-32B (31.8%, 3,221 trajectories) outperforms Nemotron-Terminal-32B (27.4%, trained on 490.5K trajectories) and TerminalTraj-32B (22.0%, trained on 50.7K trajectories) — roughly 150x and 16x more training data, respectively — and approaches LiberCoder-235B-A22B (31.0%), which uses a model with >7x more total parameters. At 14B scale, Meta-Task-14B (22.5%) beats Nemotron-Terminal-14B (20.2%) and TerminalTraj-14B (19.1%).
- **Outperforms a much larger un-fine-tuned open model**: Meta-Task-32B (31.8%) surpasses Qwen3-Coder-480B-A35B (23.9%), a model with over 15x more parameters, and narrows the gap to closed-source frontier systems — approaching GPT-5 (35.2%) and Gemini 2.5 Pro (32.6%), though still trailing GPT-5.3-Codex (64.7%) and Claude Opus 4.6 (62.9%).
- **Ablation on quality filtering (Table 3, Qwen3-32B)**: filtering 5,004 execution-passed trajectories down to 3,221 via LLM-as-Judge yields +3.3 points Avg Pass@1 (28.5% → 31.8%) and +3.4 points Pass@3 (39.3% → 42.7%), despite using fewer trajectories — demonstrating quality over quantity.
- **Scaling behavior (Figure 3)**: consistent Avg Pass@1/Pass@3 gains as training data scales from 0→3,221 trajectories for both 14B and 32B; the 32B model benefits more from the same data (steeper improvement curve); Pass@3 consistently exceeds Pass@1, indicating diverse problem-solving strategies.
- **Task quality vs. baselines (Figure 4a)**: using the official Terminal-Bench review pipeline (Claude Opus 4.6 as automated reviewer scoring 19 criteria) on 50 sampled tasks per method, Meta-Task achieves the highest implementation compliance (66–72%) with strong proposal acceptance (54–58%), while CLI-Gym scores higher on proposal acceptance (64%) but only 43% on implementation due to lacking solution scripts.
- **Synthesis efficiency and reliability**: ~15,000 complete task packages synthesized with a >85% average synthesis success rate; sampling 14,040 trajectories on these tasks with the teacher model yields a 35.6% execution pass rate (5,004/14,040), which the authors note reflects task difficulty rather than synthesis unreliability.
- **Decontamination check**: n-gram overlap (n=3,5,8), TF-IDF cosine similarity, and technical-entity matching between synthesized tasks and Terminal-Bench test tasks found no high-risk pairs (near-zero n-gram scores), manually verified.
- **Error analysis (Table 4, 146 model-attributable failed trajectories)**: dominant failure mode is Context Compaction Loss (47.3% — losing task constraints after context summarization), followed by Flawed Self-Verification (32.9% — inline checks pass but miss edge cases caught by the test suite), Step Budget Exhaustion (15.1%), and Repetitive Strategy Loop (4.8%). Notably 80.1% of all failures involve the agent marking a task complete despite an incorrect solution.

No comparison against SkillSynth/CLI-Gym/TermiGen was run under identical training-data budgets — all cross-method numbers in Table 2 for competitors are cited from their original reports (marked with *), which is a caveat for the "less data, better performance" claim (see Critical Assessment).

## Critical Assessment

**Novelty**: The core idea — treating "generate a Terminal-Bench task" as itself a Terminal-Bench-format task solvable by an agent, thereby fusing generation and execution verification into one grounded loop — is a genuinely clever reframing (a form of self-referential bootstrapping) that meaningfully differs from prior staged pipelines (TermiGen's multi-agent staged generation, Nemotron-Terminal's dataset adaptation, SkillSynth's skill-graph sampling). It is a data-efficiency-first contribution rather than a new architecture or training algorithm.

**Rigor**: The ablation in Table 3 isolating the LLM-as-Judge filtering effect is a genuine controlled comparison (same base tasks, same model, same eval), and is a strength. The decontamination analysis against Terminal-Bench test tasks is a good, often-skipped due-diligence step. However, several important comparisons are not apples-to-apples: **all competitor numbers in Table 2 are cited from the original papers (marked with *), not reproduced under the authors' own evaluation setup**, and each competing method used a different amount of training data, different backbone-fine-tuning budgets, and in some cases a different agent scaffold (e.g., TermiGen-32B uses BashAgent, LiberCoder uses OpenHands, while Meta-Task uses Terminus-2) — so the "3,221 trajectories beat 490.5K trajectories" headline conflates data efficiency with scaffold/model differences that are not controlled for. The paper does not report how much the choice of agent scaffold alone (Terminus-2 vs. BashAgent vs. OpenHands) contributes to score differences.

**Reproducibility**: Hyperparameters (Appendix A, Table 5) and evaluation settings are disclosed in reasonable detail (LoRA rank/alpha, learning rate, sequence length, sampling temperature/top-p/top-k). However, the framework depends on a specific stack (Qwen3.5-397B-A17B-FP8 backbone via vLLM, Claude Code scaffold, Harbor scheduling, Terminus-2 for sampling) that is compute-intensive to replicate, and the ~15,000 synthesized tasks / 3,221 filtered training trajectories are not stated to be released publicly in the excerpted text — reproducibility for third parties without the same compute and proprietary-adjacent scaffold access is uncertain.

**Significance**: The claimed data efficiency (3,221 vs. 50.7K–490.5K trajectories from competitors) is a meaningful practical result if the comparison holds, since data/compute cost for synthesis pipelines is a real bottleneck; the fact that a 32B model closes much of the gap to GPT-5/Gemini 2.5 Pro is a strong practical signal.

**Red flags / weaknesses to note**: (1) the low execution pass rate of the teacher model on its own synthesized tasks (35.6%, i.e., 5,004/14,040) is interpreted charitably as "task difficulty" but could equally indicate that a meaningful fraction of synthesized tasks are malformed, under-specified, or unsolvable even by a capable model — the paper doesn't fully disentangle these two explanations; (2) the error analysis (Table 4) shows the fine-tuned agent itself frequently self-reports task completion incorrectly (80.1% of failures), which is a known miscalibration issue the authors flag but don't address with any mitigation in this paper; (3) domain/seed curation for diversity (topic lists, scenario constraints) is manually curated (acknowledged explicitly in Limitations), which could bias task distribution toward the authors' own notion of "diverse," despite the large combinatorial seed space; (4) the framework is Linux/Docker-only (explicitly stated limitation), so generalization to Windows/macOS terminal environments is untested.

## Strengths

- Elegant, execution-grounded reframing of task synthesis as a terminal task itself, avoiding the internal-consistency/hallucination problems of decoupled generate-then-verify pipelines.
- Strong empirical data efficiency: matches or beats methods trained on 16–150x more trajectories.
- Careful two-stage filtering pipeline with a clean, controlled ablation (Table 3) demonstrating quality-over-quantity.
- Thorough auxiliary analyses: task-quality review against baselines (Figure 4a), skill coverage across 12 competency areas (Figure 4b), t-SNE domain diversity visualization (Figure 4c), trajectory turn-length distribution (Figure 4d), and an explicit decontamination check against the test benchmark.
- Transparent error analysis identifying concrete, actionable failure modes (context compaction loss, flawed self-verification) rather than vague "future work" statements.
- Multi-phase synthesis mechanism is a genuinely scalable extensibility story (adding new topics trivially expands diversity) rather than a fixed, hand-authored template set alone.

## Limitations

- Explicitly stated by the authors: the framework is restricted to Linux-based terminal task synthesis within Docker containers; extension to Windows/macOS ecosystems (different toolchains, shells, system APIs) is left to future work.
- Seed sources for diversity (topic lists, scenario constraints) are manually curated rather than mined from broader real-world developer activity (e.g., Stack Overflow, GitHub issues, technical documentation), which the authors acknowledge could further expand coverage.
- Competitor results in the main table are cited from external reports under differing scaffolds/data budgets rather than reproduced in a fully controlled head-to-head setting.
- The teacher model's low execution pass rate (35.6%) on its own synthesized tasks raises unresolved questions about how many synthesized tasks are simply too difficult versus subtly broken.
- Fine-tuned models still substantially trail top closed-source systems (GPT-5.3-Codex 64.7%, Claude Opus 4.6 62.9% vs. Meta-Task-32B 31.8%), so the practical capability ceiling from this data-synthesis approach alone remains well below frontier performance.
- Dominant failure mode (context compaction loss, 47.3% of failures) suggests the trained models' long-horizon context management is still fragile, an issue orthogonal to task-synthesis quality that this training approach doesn't directly fix.

## Relevance

该工作针对终端/命令行智能体训练数据稀缺、可靠性差的问题，提出了一种以真实执行为基础、数据效率极高的合成范式，对做 agentic SFT 数据合成、终端/CLI 智能体评测（Terminal-Bench 系列）或 LLM-as-Judge 数据过滤研究的读者有较高参考价值；其"任务合成即任务"的自指式设计思路也可能启发其他领域的智能体自举式数据生成方法。

## Questions for Further Exploration

- How would Meta-Task-synthesized data compare against TerminalTraj/CLI-Gym/Nemotron-Terminal/SkillSynth under a fully controlled setting (same backbone, same agent scaffold, same trajectory budget) rather than citing their originally reported numbers?
- What fraction of the teacher model's 64.4% execution failures on synthesized tasks (5,004/14,040 pass) are due to genuinely unsolvable/malformed tasks versus appropriately hard-but-valid tasks — could a task-level (not just trajectory-level) difficulty audit clarify this?
- Would scaling the multi-phase seed space (topic lists, scenario constraints) via automated mining from Stack Overflow/GitHub issues (as the authors suggest) meaningfully shift the skill-coverage distribution in Figure 4b, e.g., increasing currently underrepresented categories?
- Can the dominant failure modes identified (context compaction loss, flawed self-verification, miscalibrated task-completion self-assessment) be mitigated by targeted training signal (e.g., explicit self-verification RL) rather than only by more/better SFT data?
- How does Meta-Task's approach extend, if at all, to non-Linux or non-Docker-based terminal environments, and what synthesis/verification changes would that require?
- Is the ~85% synthesis success rate stable across all 39 categories and 4 difficulty levels, or concentrated in easier domains — i.e., does difficulty correlate with synthesis failure rate?
