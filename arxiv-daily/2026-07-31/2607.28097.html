From Expert Reduction to Behavioral Divergence: Tracing Numerical State through Sparse MoE Inference

Tianyang Zhu (independent researcher)  ·  2026-07-31  ·  arXiv 2607.28097

sparse-mixture-of-experts floating-point-reproducibility deterministic-inference runtime-conformance llm-inference-nondeterminism

Permuting only the summation order of six frozen MoE expert outputs flips model output between layoffs and hiring narratives.

Key metric
0/192

route divergences under Scheme C (BF16-rounded operand, exactly promoted to FP32, FP32 accumulator) — the other three schemes (P32, A, B) diverge from the native reference on 192/192 of the same 192 trajectories.

Why this matters

Offers MoE inference-engine builders a three-factor framework — operand precision, accumulator precision, reduction order — for regression-testing runtime and backend migrations.

Critical edge

All quantitative results come from a single checkpoint on one CPU runtime; the paper explicitly warns these numbers should not be assumed to transfer to GPU/NPU tensor-core reduction trees.

01 Methodology

The paper runs native DeepSeek-V4-Flash on the Colibri runtime's non-DSpark CPU path (AMD Ryzen AI MAX+ 395, greedy decoding). Each token routes to six experts plus one shared expert, so the 6! = 720 possible orders for summing the six weighted expert terms are exhaustively enumerable at a single chosen MoE site.

At that site the author freezes everything upstream — prompt prefix, selected expert IDs, gate values, the six weighted terms, shared-expert output, full persistent state — and varies only how those six numbers are added and at what precision.

Four aggregation schemes decouple operand precision from accumulator precision:

  • P32 — raw FP32 operands, FP32 accumulator (counterfactual control)
  • C — BF16-rounded operands exactly promoted back to FP32, FP32 accumulator
  • A — FP32 operands, rounded to BF16 after every addition
  • B — BF16 operands and accumulator throughout (the runtime's actual native behavior)

Six protocols probe different scopes — a single-layer 720-permutation sweep, exact FP32/FP64 reconstructions of intermediate execution state, and a 768-trajectory persistent-decode comparison — all checked against deterministic-replay controls (hash-matched reruns) that rule out ordinary decoding randomness as an explanation.

Single-layer fork compresses hundreds of branches into a handful of text basins

At layer 5 on the prompt "why the sheep": scheme A's 720 raw permutations collapse into 10 distinct 8-token continuations; scheme B's 720 permutations (360 exact structural classes, via a proven first-pair-swap symmetry) collapse into 11. Every one of these 720/720 (A) and 360/360 (B) branches still differs from the native reference at the state level.

+ Strengths

  • Isolates one mechanism — cross-expert reduction order — with an unusually thorough freeze of every other variable (prefix, experts, gates, terms, shared output, persistent state).
  • Two independent, complementary state-boundary reconstructions (FP32 intra-token, FP64 cross-token), each bitwise-exact over a multi-step decode horizon.
  • Deterministic-replay controls (13-prompt native check, 10-branch × 2-run SHA-256 replay) proactively rule out decoding randomness as an alternative explanation.
  • Unusually candid scoping — an explicit "claim ledger" separates basin-volume possibility from deployment incidence throughout.
  • Full reproducibility artifact released: scripts, hash manifests, per-protocol output tables.

− Limitations

  • Single checkpoint (DeepSeek-V4-Flash), single runtime (Colibri, non-DSpark), single CPU host — no GPU/NPU or cross-architecture results.
  • No frozen-route mediation experiment isolates routing as the unique causal link between numerical and token divergence.
  • No real-hardware or production-deployment measurement of how often any given permutation actually occurs.
  • The three "depth" prompts and layer-5 fork point are hand-selected without preregistration; the 50-prompt breadth cohort is staged, not independently sampled.
  • Scheme C's order-invariance is validated only for the evaluated six-term states — not proposed as a general exact-summation algorithm, and its runtime overhead is unmeasured.
  • No end-to-end downstream task or benchmark accuracy is measured — all significance is token/state/route agreement.

? Questions for Further Exploration

  • Would a frozen-route mediation intervention confirm routing as the unique causal mediator, or reveal pathways that bypass routing entirely?
  • How does the divergence rate change on real GPU/NPU tensor-core reduction trees versus the sequential CPU accumulation studied here?
  • Does scheme C's order-invariance hold for other checkpoints with different expert counts, router distributions, or non-mHC architectures?
  • What is scheme C's runtime overhead relative to native scheme B in a production-scale deployment?
  • Would a preregistered, systematic sweep across layers and a larger random prompt set reveal whether the reported basin counts are typical or extreme cases?
  • Can the full-persistent-state boundary still mediate continuation equivalence when the immediate next token itself differs across branches?
