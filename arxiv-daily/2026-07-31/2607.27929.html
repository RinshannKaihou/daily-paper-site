Terminal Agents · Agentic Data Synthesis · arXiv 2607.27929 · 30 Jul 2026

Turning task synthesis itself into a terminal task lets 3,221 self-verified trajectories outperform models trained on 150× more data.

一句话总结：Meta-Task 把"合成终端任务"本身重新定义成一个 Terminal-Bench 格式的终端任务，让智能体在真实 Docker 容器里端到端地设计、实现并自验证任务包，仅用 3,221 条合成轨迹微调就让 Qwen3-14B/32B 在 Terminal-Bench 2.0 上分别达到 22.5% 和 31.8% 的 Avg Pass@1，超过训练数据量大得多的同期方法。

Beats Nemotron-Terminal-32B (27.4%, 490,500 trajectories — ~150×) and TerminalTraj-32B (22.0%, 50,700 trajectories — ~16×), and edges past the 15×-larger, un-fine-tuned Qwen3-Coder-480B-A35B (23.9%). Base Qwen3-32B scores only 4.1%.

Why This Matters

Terminal-agent training data is scarce and costly to verify; this shows small, execution-grounded datasets can rival systems trained on far more data.

中文原文（Relevance）：该工作针对终端/命令行智能体训练数据稀缺、可靠性差的问题，提出了一种以真实执行为基础、数据效率极高的合成范式，对做 agentic SFT 数据合成、终端/CLI 智能体评测（Terminal-Bench 系列）或 LLM-as-Judge 数据过滤研究的读者有较高参考价值；其"任务合成即任务"的自指式设计思路也可能启发其他领域的智能体自举式数据生成方法。

▲ Critical Edge

All competitor numbers in the headline comparison are cited from the original papers under different scaffolds and data budgets, not reproduced head-to-head — so "3,221 beats 490,500" conflates data efficiency with uncontrolled model/scaffold differences.

Methodology

1

Meta-Task Generation — fixed instructions defining how to synthesize (target files, workflow, self-validation checklist) are combined with variable specs defining what to synthesize: category (39 domains), scenario style (10 templates), difficulty (4 levels) — 1,560 base combinations. A multi-phase mode dynamically designs new (category, scenario) pairs from ~2,000 topic seeds × ~120 scenario constraints, extending the space past 240,000 combinations. Each Docker env is pre-loaded with a skeleton template, one example task from a 100-task reference pool (built by Claude Opus 4.6, manually verified), and optional search/download tooling.

2

Agent Synthesis — an agent (Claude Code scaffold) runs inside the live container: explores the example, searches real GitHub/HuggingFace materials, designs a problem, and implements a full task package (instruction, Dockerfile, solution, tests) — iterating against real stdout/stderr feedback until self-validation passes.

3

Quality Filtering — a teacher model (Qwen3.5-397B-A17B, Terminus-2 scaffold) samples solution trajectories on the validated tasks. Execution-based filtering keeps only tests-passing trajectories (14,040 → 5,004); LLM-as-Judge (same model, thinking mode) then removes solution-leakage or too-short trajectories (5,004 → 3,221).

Training/eval: LoRA (rank 64, alpha 128) on Qwen3-14B/32B via SWIFT, 8×A100 80GB, DeepSpeed ZeRO-3, lr 1e-4, 5 epochs, seq length 40,960. Evaluated on the official Terminal-Bench 2.0 protocol (Harbor + Terminus-2, non-thinking mode, T=0.7), averaged over 3 runs.

Fewer trajectories, higher score: +3.3 pts Avg Pass@1 and +3.4 pts Pass@3 from judge-filtering — quality over quantity.

  • Synthesis efficiency: ~15,000 complete task packages synthesized at >85% average success rate; the teacher model's own execution pass rate on these tasks is 35.6% (5,004/14,040) — authors attribute this to task difficulty, not synthesis unreliability.
  • Task quality (Fig. 4a): Claude Opus 4.6 as automated reviewer (19 criteria, 50 sampled tasks/method) rates Meta-Task highest on implementation compliance (66–72%); CLI-Gym scores higher on proposal acceptance (64%) but only 43% on implementation, lacking solution scripts.
  • Decontamination: n-gram (n=3,5,8), TF-IDF cosine similarity, and entity matching against Terminal-Bench test tasks found no high-risk overlaps, manually verified.
  • Error analysis (146 failed trajectories, Table 4): Context Compaction Loss 47.3%, Flawed Self-Verification 32.9%, Step Budget Exhaustion 15.1%, Repetitive Strategy Loop 4.8% — and 80.1% of all failures involve the agent marking the task complete despite an incorrect solution.

Strengths

  • Elegant, execution-grounded reframing of task synthesis as a terminal task itself, avoiding the hallucination/consistency problems of decoupled generate-then-verify pipelines.
  • Strong empirical data efficiency: matches or beats methods trained on 16–150× more trajectories.
  • Clean, controlled ablation (Table 3) isolating the LLM-as-Judge filtering effect — a genuine quality-over-quantity demonstration.
  • Thorough auxiliary analyses: task-quality review vs. baselines, skill-coverage across 12 competency areas, t-SNE diversity plot, trajectory-length distribution, and an explicit decontamination check.
  • Transparent error analysis naming concrete, actionable failure modes rather than vague "future work" statements.
  • Multi-phase synthesis is a genuinely scalable extensibility story — new topics trivially expand diversity — not a fixed, hand-authored template set.

Limitations

  • Restricted to Linux-based terminal task synthesis inside Docker; Windows/macOS extension is left to future work.
  • Diversity seeds (topic lists, scenario constraints) are manually curated, not mined from real-world developer activity (Stack Overflow, GitHub issues).
  • Competitor numbers in the main table are cited from external reports under differing scaffolds/data budgets, not reproduced in a controlled head-to-head.
  • The teacher model's low execution pass rate on its own synthesized tasks (35.6%) leaves open how many tasks are too difficult vs. subtly broken.
  • Fine-tuned models still trail top closed-source systems by a wide margin (31.8% vs. GPT-5.3-Codex 64.7%, Claude Opus 4.6 62.9%).
  • Dominant failure mode (context compaction loss, 47.3%) shows long-horizon context management stays fragile — an issue this data-synthesis approach doesn't directly fix.

Questions for Further Exploration

  1. How would Meta-Task data compare against TerminalTraj/CLI-Gym/Nemotron-Terminal/SkillSynth under a fully controlled setting — same backbone, scaffold, and trajectory budget?
  2. What fraction of the teacher model's 64.4% execution failures are genuinely unsolvable/malformed tasks versus appropriately hard-but-valid ones?
  3. Would scaling the multi-phase seed space via automated mining from Stack Overflow/GitHub issues shift the skill-coverage distribution toward currently underrepresented categories?
  4. Can the dominant failure modes (context compaction loss, flawed self-verification, miscalibrated completion judgment) be mitigated by targeted training signal, e.g. self-verification RL, rather than more SFT data alone?
  5. How does the approach extend to non-Linux or non-Docker terminal environments, and what synthesis/verification changes would that require?
  6. Is the ~85% synthesis success rate stable across all 39 categories and 4 difficulty levels, or concentrated in easier domains?
