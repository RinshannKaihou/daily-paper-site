> **一句话总结：** RESOLVE 把 GPU kernel 验证拆成两半——用 NVBit 二进制插桩做"确定性测试"（计数/追踪/扰动三遍扫描，暴露调度相关的并发 bug）保证并发正确性，再由 LLM 智能体把 kernel 归约成低并发版本并在 Kuiper/F* 中对实数代数规范证明等价来保证功能正确性；在 100 个 KernelBench L1 kernel、约 2.5× 加速的融合 MLP kernel（Triton/Gluon/CUTLASS）和 LUCE/FlashMoE/FastMoE 三个生产级 mega-kernel 上验证，发现 4 个此前未报告的问题（含 2 个明确 bug），修复后 3/4 的性能代价 ≤2%。

> **TL;DR:** RESOLVE (Microsoft Research + UC Riverside + Math Inc.) validates optimized GPU kernels by splitting the problem: concurrency correctness is checked by binary-level determinism testing (NVBit perturbs warp/CTA scheduling on compiled SASS, no source needed), while functional correctness is established by LLM agents reducing both candidate and reference to low-concurrency forms and proving them equivalent in Kuiper/F* against a shared algebraic specification over the reals — sidestepping numeric tolerances entirely. On a corpus of 100 GPT-5.6-optimized KernelBench Level 1 kernels (the baseline being KernelBench's own tolerance tests, which all candidates already passed), the determinism tester alone flags 2 candidates that silently perform no memory work (empty ELU kernels — tolerance testing's false negatives), and 11 of 14 kernels carried through the full workflow pass reduction+proof at a median cost of 142.96 min and 5.72M tokens per kernel. In a mutation study the tester catches 92/143 injected synchronization faults, and on three production mega-kernels (LUCE, FlashMoE, FastMoE) it exposes 4 previously unreported issues, with agent-repaired fixes costing ≤2% latency in 3 of 4 cases (FastMoE +10.5%).

## 核心贡献

- **高效的二进制级确定性测试**：基于 NVBit 对编译后的 SASS 做插桩，通过"计数 → 追踪 → 扰动"三遍扫描，只在追踪到的冲突内存访问处插入延迟（按内存区域 global/shared 与线程层级 warp/CTA/跨 CTA 分作用域），无需源码或编译器配合，适用于 CUDA、Triton、Gluon、CUTLASS 等任何语言编译出的 NVIDIA 二进制。100 个 RKB kernel 的测试中位数仅 1.47 分钟。
- **位级等价的并发归约**：智能体重写候选与参考 kernel，去除异步流水线、同步与并发结构（barrier/atomic/cooperative launch/warp 原语一律拒绝），归约结果必须与原 kernel 在所有测试输入上位级一致才被接受——测试提供了"每次执行"的精确 oracle，归约通常可达单线程。
- **自动化等价证明**：智能体仅凭受信任的参考实现撰写代数规范，将两侧归约程序翻译为 Kuiper（构建在 F*/Pulse 并发分离逻辑之上），证明二者满足同一"紧"规范。借助 Kuiper 的近似关系（ε）把浮点推理与实数推理解耦，因此位级输出不同但语义相同的合法优化也能被接受。
- **三层递进的评测**：KernelBench L1 采样语料（广度）→ 三种语言（Triton/Gluon/CUTLASS）写就的 SOTA 融合 GEMM/MLP kernel（语言覆盖）→ LUCE/FlashMoE/FastMoE 三个生产级 mega-kernel（深度），共发现 4 个此前未报告的问题，且变异测试定量刻画了检测能力（92/143）。

## Key Contributions

- **Binary-level determinism testing** that perturbs execution timing directly on SASS via NVBit — no source or compiler required, covering any language or library — using three passes (counting, tracing, perturbation) that place delays only where traced conflicts can occur, cutting median testing time on RKB to 1.47 min/kernel.
- **Bitwise concurrency reduction**: agents rewrite both candidate and reference into forms with as little concurrency as possible (barriers, atomics, cooperative launches, warp primitives rejected), accepted only when output is bitwise equivalent to the original on every tested input — an exact per-execution oracle that requires no tolerance.
- **Automated equivalence proof**: agents draft an algebraic specification from the trusted reference alone and prove both Kuiper translations satisfy it, using Kuiper's approximation relation to decouple floating-point from real-number reasoning; this accepts valid optimizations whose bits differ, unlike tolerance testing whose threshold choice "decides which bugs stay visible".
- **Evaluation across three regimes** — sampled KernelBench L1 kernels, state-of-the-art fused GEMM/MLP kernels in Triton, Gluon, and CUTLASS, and three production mega-kernels (LUCE, FlashMoE, FastMoE) — finding four previously unreported issues, two of them clear bugs, all repaired by agents and re-validated by RESOLVE.

## Methodology

RESOLVE rests on one decomposition: ML kernels are *intended* to be deterministic, so **concurrency correctness** (does the schedule change the output?) can be validated by testing with a bitwise, per-execution oracle, while **functional correctness** (do candidate and reference compute the same function?) is deferred to formal proof over the reals.

1. **Testing for determinism (§3).** The determinism tester treats the kernel as a black box, runs it a fixed number of times on tensor inputs drawn from ten families of distributions (degenerate/sparse/sentinel values, cancellation, quantization boundaries), and hashes *all of memory* after each run — comparisons are equality-only, so no full memory copy is kept. Three NVBit passes over the compiled binary: (i) *counting* memory-reference operand events per problem to size buffers (activity spans four orders of magnitude, 10⁸–beyond 10¹¹); (ii) *tracing* addresses and threads to inventory potential conflicts by memory region (shared/global) and hierarchy level (within-warp/within-CTA/across-CTA), sampling whole CTAs when the trace cap (200M records) is exceeded; (iii) *perturbation* — inserting stalls of up to a configured cycle count before traced memory instructions with a configured probability (defaults: 4 unperterted runs, delays up to 5,000 cycles at p=0.8, 200M-record cap), then comparing every perturbed run byte-for-byte against an unperturbed baseline, stopping at the first difference.
2. **Bitwise concurrency reduction (§4).** An agent rewrites each kernel (candidate and reference) to minimize concurrency: barriers/atomics/cooperative launches/warp primitives are rejected even inside headers and macros; splitting into multiple simple kernel launches is encouraged; repeated statements become loops; shared code becomes functions. The reduction is accepted only if its output is bitwise identical to the original on every tested input — no epsilon, no normalization. Tensor-core instructions are kept rather than reduced away (Kuiper provides semantics for them), so the floor is "little concurrency by instruction", not always single-thread.
3. **Automated equivalence proof (§5).** Both reduced programs are translated into Kuiper, a verification language over a subset of CUDA built on F*/Pulse concurrent separation logic. Agents construct an algebraic specification from the *trusted reference alone* (so the candidate cannot influence the criterion), using Kuiper's approximation relation (ε) — introduced for literals and preserved by arithmetic and library functions — to prove both sides perform "the same algebraic computation" over the reals, even when floating-point reordering makes bits differ. The spec must be *tight* (the output is a function of the inputs over the reals); tightness is validated by human review. A successful run yields three facts: kernel ≡ reduction ≡ verified program ≡ shared spec S.

Everything is agent-driven (GitHub Copilot CLI; mostly GPT-5.6 and Claude Opus 5) on a 4×H100 PCIe server (sm_90, CUDA 13.0); the main agent only orchestrates via file handoffs.

## Results & Highlights

- **KernelBench L1 (RKB corpus, 100 GPT-5.6-optimized candidates that had all passed KernelBench's tolerance tests):** the determinism tester alone classifies 15 as deterministic and bitwise identical (no full pipeline needed), and flags **2 candidates that perform no memory accesses at all** — elementwise ELU problems 31 and 32 where the agent erroneously produced an *empty kernel* — demonstrating concrete false negatives of tolerance-based validation. Of the 14 kernels carried through the full workflow, **11 pass** reduction+proof, 2 are inconclusive (missing Kuiper features: inline PTX `approx`/`rnd`, `exp`/`log1p` subnormal flush, `thread_local _expf` for SELU) and 1 is inconclusive (a sigmoid rewritten from a degree-11 to a degree-10 Taylor approximation cannot be proven without numeric-tolerance reasoning).
- **Mutation study (RKB-Mutant):** injecting one synchronization fault per kernel (barrier/wait removed, moved, or scope-narrowed; write destinations aliased) yields **143 runnable mutants, of which the determinism tester flags 92 (64.3%)** — 90 by output mismatch, 2 needing a delay. Average time to test one mutant is 405 s (range 88–4,567 s) vs a 256 s clean run. All 51 misses are decomposed: 3 inject into dead code, 28 inject races that never change the final value (the very reason RESOLVE separates determinism from race detection), and 26 place the conflict *within a single warp*, beyond what NVBit-only perturbation can interleave.
- **Fused MLP kernel (Qwen-style MLP: hidden 8,192, FFN intermediate 29,568, 4,096 rows):** agent-written single-kernel fusions in Triton, Gluon, and CUTLASS run **~2.5× faster than the 3-kernel eager PyTorch reference**; none of the three is bitwise-identical to the reference (fusion reorders reductions), yet Gluon — bitwise-identical to Triton — is carried through specification and F* proof. Compute Sanitizer runs clean on all three, which "neither proves the kernel is deterministic nor that it computes the reference function".
- **Mega-kernels:** all three production kernels (LUCE: 24 hybrid DeltaNet+attention decoder layers in one launch; FlashMoE: MoE routing+dispatch; FastMoE: capacity pruning) behave nondeterministically; delta debugging exposes **4 previously unreported issues** — a LUCE grid-barrier bug (block 0 resets arrival counters while other blocks may still be arriving), a LUCE scratch-buffer aliasing bug (attention blocks computing the same global address via block/head offsets), and arrival-order-dependent token dropping in FlashMoE (atomic slot reservation) and FastMoE (atomiCAdd pruning). Repairs and warmed-latency cost (Table 4): LUCE barrier −1.4%, LUCE scratch −1.6% (both *faster*), FlashMoE +0.8%, FastMoE +10.5%; the fixed FastMoE is bitwise identical to a straightforward PyTorch reference.
- **Cost (Table 2, medians over 14 RKB kernels, wall clock):** determinism testing 1.47 min (1.05–19.20); reduction 29.31 min (12.56–74.40; 39.1K in / 8.1K out tokens); spec & proof 112.18 min (44.55–250.20; 5.54M in / 65.6K out tokens); **total 142.96 min (58.16–343.80) and 5.72M input tokens per kernel** — the proof stage consumes ~142× the input tokens of reduction.
- **Trace budget (Figure 5):** the conflict inventory saturates by 100M–400M records; at a 50M cap the inter-block indicator disappears entirely; the 200M default takes a mean of 107–133 s per kernel to trace and analyze, and two CTAs suffice to expose every conflict on this suite.

## Authors & Credibility

The author list combines strong PL/systems-verification credentials: **Madan Musuvathi** (Microsoft Research; CIVL, KLEE, cloudcroft line of concurrency-testing work), **Tyler Sorensen** (GPU memory-consistency modeling, GPUHarbor), **Sebastian Burckhardt**, **Gabriel Ebner**, and **Abhinav Jangda** (Microsoft Research), **Guido Martínez** (Math Inc.), who with Sorensen and others authored **Kuiper** [28], the very verification substrate RESOLVE builds on, plus first author **Ashkan Vedadi Gargary** (UC Riverside). The team also built SuperCollider [43], the prior schedule-perturbation tool this work extends from compiler passes to binaries. The paper is unusually candid about failure modes (inconclusive kernels, the Mirage kernel they "could not diagnose", the debatable FastMoE bug status) and explicitly credits agents while noting the scientific arguments and verification are human-owned. Credibility: high.

## Critical Assessment

- **The proof stage's soundness leans on unverified human review of the specification.** The paper states "we inspected every specification by hand and found each one to be tight" — for 14 RKB kernels plus the Gluon MLP. A spec that is not tight reduces the guarantee to "both programs are safe", with no functional postcondition; there is no automated tightness certification, and the authors defer this to future work. At 14-kernel scale hand review is plausible; as a claim about an autonomous optimization loop it is the weakest link, and the paper is right to flag it but does not quantify reviewer effort or error risk.
- **The RKB full-pipeline sample is small and its selection is under-specified.** 85 of 100 candidates need the full workflow, but only 14 are carried through ("we draw two samples from each input distribution, which keeps the study tractable") — the sampling procedure is not shown to be unbiased, so the 11/14 pass rate should not be read as a corpus-level success rate.
- **Detection power has a hard binary-level ceiling.** 26 of the 51 mutation-study misses are intra-warp conflicts that NVBit perturbation cannot interleave (SASS warp-synchrony instructions like BSSTY/BSSYNC bracket the control flow), and asynchronous loads cannot be slowed at all; SuperCollider-style compiler support would be needed. The 64.3% catch rate is honest and well-decomposed, but "language-agnostic" comes at the price of this blind spot, which the paper plainly acknowledges.
- **Two of the four "issues" are arguably design choices, not bugs.** FlashMoE's atomic slot reservation and FastMoE's atomicAdd pruning drop different tokens depending on block arrival order; the paper itself notes "every reference implementation we know of routes tokens nondeterministically... whether that should be treated as a bug is under discussion", and fixing FastMoE costs +10.5% latency — a real engineering trade-off, not a free win. Counting these toward "four unreported issues" slightly inflates the bug headline, though the two LUCE defects (grid-barrier counter reset, scratch aliasing) are unambiguous.
- **Kuiper coverage gaps materially limit end-to-end applicability today**: inline PTX, subnormal-flushing `exp`/`log1p`, `thread_local _expf`, and `argmax` are unsupported, producing 2–3 inconclusive RKB kernels and blocking FlashMoE's proof entirely (reduced to 25 lines but unspecifiable); LUCE cannot even be reduced because its Hopper warpgroup (128-thread) matrix-multiplies exceed the reducer's single-warp floor.
- **Cost is nontrivial and agent-heavy**: a median of ~143 minutes and 5.7M input tokens per kernel, with the proof stage dominating (112 min, 5.54M tokens). The authors frame RESOLVE as a component of autonomous optimization systems rather than an interactive bug hunter, which is the right framing, but teams should not expect cheap per-kernel validation.

## Strengths

- The central decomposition is genuinely elegant: determinism buys an *exact per-execution oracle* (bitwise equality) for the concurrency half, while the ε-approximation relation buys *tolerance-free* functional comparison for the numerical half — each technique is matched to the property it can actually establish.
- Truly language-agnostic testing: everything operates on the compiled NVIDIA binary, so Triton, Gluon, CUTLASS, and CUDA kernels are validated uniformly, and the determinism tester "can be pointed at code in any shape" including inside frameworks.
- Rigorous, falsifiable evaluation practice: the mutation study quantifies detection power (92/143) and every one of the 51 misses is individually explained; inconclusive outcomes are reported as inconclusive rather than massaged into passes.
- Real bugs in deployed-scale systems: the LUCE grid-barrier and scratch-aliasing bugs were found in a production hybrid-attention model, with agent-authored repairs re-validated by the same pipeline (and two repairs came out slightly *faster*).
- Honest accounting of costs and trade-offs, including token counts, wall-clock medians, latency deltas per repair, and the open question of whether arrival-order-dependent MoE token dropping is a bug at all.

## Limitations

- **Intra-warp schedule perturbation is out of reach for NVBit-only instrumentation** (needs compiler support à la SuperCollider), asynchronous loads cannot be delayed, and conflicts between CTAs that are never co-resident cannot be exposed — a structural coverage gap for binary-level testing.
- **The proof half is only as good as Kuiper's language coverage**: inline PTX, subnormal flush-to-zero, thread-local `_expf`, and argmax are unsupported, so several realistic kernels end inconclusive; tensor cores are kept rather than reduced, and warpgroup instructions (>1 warp) exceed the reducer's capability (LUCE).
- **Specification tightness is certified by hand**, not automatically; a weak spec collapses the guarantee to mere safety, and numerical rewrites that change approximation degree (e.g., sigmoid Taylor degree 11 → 10) are currently rejected outright, pending CPU-style error-budget reasoning for floating-point expressions.
- **Determinism-rejecting kernels are excluded by design**: legitimate nondeterminism (e.g., atomicAdd-based FP reduction order) is rare in the corpus (1 of 100 RKB kernels) but would be flagged as incorrect.
- **Pipeline economics**: ~143 min and 5.7M tokens per kernel (median), plus human spec review, is far from per-commit continuous validation at scale.

## Relevance

这篇论文直击"AI 智能体大规模生成与优化 GPU kernel"这一新兴趋势的核心信任问题——KernelBench 候选全部由 GPT-5.6 生成、连修复都由智能体完成，而容差测试连"空 kernel"这种错误都会放行。对关注 AI 系统可靠性与 LLM 基础设施（kernel 工程、MoE/注意力 mega-kernel）的读者而言，它展示了"测试定并发、证明定功能"的务实验证架构，值得作为智能体 kernel 优化流程中质量门禁的参考设计。

## Questions for Further Exploration

- Can specification tightness be certified automatically (e.g., by checking the spec against the reference via property-based testing, or by machine-checkable tightness obligations in Kuiper), removing the human-review bottleneck?
- Would compiler-assisted perturbation (SuperCollider-style) inside warps, combined with RESOLVE's binary-level reduction and proof, close the 26 intra-warp mutation misses without giving up language agnosticism?
- Can the CPU-style numeric-tolerance reasoning for floating-point expressions be ported to Kuiper so that rewrites like the sigmoid Taylor degree-10 variant can be accepted with a concrete error budget instead of being rejected?
- Is arrival-order-dependent token dropping in capacity-bounded MoE routing (FlashMoE/FastMoE) best treated as a bug, a spec-level choice, or an acceptable nondeterminism — and what would a standardized contract for MoE routers look like?
- How does the pipeline's cost (median 142.96 min, 5.72M tokens per kernel) scale to full model-serving kernel suites, and can the proof stage's 5.54M-token footprint be cut by reusing the verified-kernel corpus (e.g., Martínez and Sorensen's audited KernelBench solutions) as proof libraries?
