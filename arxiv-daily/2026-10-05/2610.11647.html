Key metric · displacement

−19.9pp

drop in use of the installed skill once a similar same-job skill joins the list (95% CI [−23.1, −16.7]). Task completion: +1.9 pp, not significant — the loss is invisible to pass/fail.

Why this matters

Explains why an installed Claude Code skill silently stops working — and hands skill authors, platforms, and benchmarks a low-cost, immediately actionable fix.

Critical edge

Core functions are LLM-extracted and mostly LLM-judged — “fidelity” is fidelity to a model’s reading of skill prose, never validated against what human skill authors intended.

  1. Reconstruct installations. From 55,698 distinct skills (207,863 valid SKILL.md files deduplicated to 43,986 families) in commit-pinned snapshots, 1,006 installation lists define what a session actually loads — project, nested, personal, and plugin scopes.
  2. Mine & judge pairs. Cosine similarity over the name+description the model sees at routing time yields 822,109 candidates; an LLM judge labels same-job / near-duplicate / related / unrelated, with a similarity floor calibrated on 615 double-judged pairs (recall ≥95%, judge re-run κ = 0.93).
  3. Build cases. For 312 experimental pairs: a drafted developer-style request, a ≤15-file starter repo, and per-requirement checks. Each skill’s “core functions” (26,198 total, 8.4/skill) are extracted blind — exclusive vs shared — so fidelity loss becomes measurable.
  4. Controlled runs. 312 pairs × {only-A, A+B, unrelated A+C, order swap, personal/plugin scope} × {Sonnet 4.6, Haiku 4.5, Opus 5}, pass@1 in offline containers — ≈$8.6k of API. Paired, Holm-corrected analysis; RQ3 tests a pre-tool hook denying B’s first read; 193 pairs re-run on Codex as an external check.

Human raters validate every LLM-assisted step (Krippendorff’s α 0.66–0.88). Full artifact released: github.com/troin/conflict, including all 6,368 run logs.

  • Prevalence: 63.7% of installed skills have their most-similar listmate be a same-job skill by another author; ≥23.5% are actually co-installed with one — the “1 in 4” headline. In the 489 whole-collection-copying projects: 37% vs 19% elsewhere.
  • Similarity, not skill count: the unrelated A+C control shifts use only −5.9 pp and fidelity −0.2 pp, isolating the effect to the similar twin.
  • Substitution, not interference: with B co-installed, 12.1% of runs use only B and 38.0% use neither; substituted runs lose 8.0 pp of fidelity while runs that did use A carry only 20% of the loss.
  • Scope beats order: a personal same-name B erases A from the listing, yet models still read A’s files in 29.2% of runs; reversing list order moves use just +0.6 pp. Disclosure is near-zero — the final reply names the skill that ran in 0.9% of substitutions (Opus 5: 21.0%).
  • The decision point is the first read: 97% of B-first reads happen before any file is modified. Denying that read flips 96% of runs back to A (Sonnet 100%, Haiku 94.6%, Opus 99%), recovering +9.1 pp exclusive-fidelity at no completion cost.
  • Not Claude-specific: Codex with three OpenAI models shows −18.2 pp on the same pairs — and models differ sharply (Opus 5 uses both skills in 36.8% of runs; Haiku 4.5 uses neither in 56.4%).

Strengths

  • Genuinely novel question with a clean framing: substitution vs interference, and an exclusive-vs-shared core-function split that makes invisible loss measurable and falsifiable.
  • Scale plus determinism discipline: commit-pinned snapshots, a recall-calibrated similarity floor, stratified sampling with CIs, near-perfect judge reproducibility (κ = 0.93).
  • Strong causal hygiene: paired within-pair-and-model design, unrelated-skill control, listing-order swap, Holm corrections, negative controls, sensitivity analyses.
  • Moves from observation to intervention — the hook experiment shows the first read is the decision point and a cheap guard fixes it on every model.
  • Full artifact release including all run logs and judging prompts — rare for agent experiments at this scale.

Limitations

  • “Fidelity” rests on LLM-extracted core functions and a majority-LLM judge; poorly written skills may get mismeasured requirements, with no check against author intent.
  • One run per (model, configuration, pair); the 88.9% re-run agreement bounds but does not eliminate per-cell noise.
  • Full design on Claude Code only; the Codex check covers 193 pairs, and Gemini CLI / Copilot are untested despite the generalizing claims.
  • Synthetic LLM-drafted requests over ≤15-file repos; only the 48% of pair skills that run offline are studied — script-heavy and API-dependent skills are underrepresented.
  • Prevalence comes from public repositories; personal and plugin skills — precisely where same-name overrides fire — are structurally under-observed, and the guard is tested only in the authors’ own harness.

Questions for further exploration

  • Does fidelity measured against real skill-author intent differ from fidelity to LLM-extracted core functions?
  • With three-plus co-installed same-job skills, 36.0% of runs already use neither — is a global skill router or install-time dedup better than a first-read guard?
  • Would a platform-side “which skill ran” pin change user trust, given 0.9% disclosure in substitutions today?
  • Does the +9.1 pp guard gain hold on platforms with different precedence rules (Gemini CLI is project-first; Copilot lists both) and on real user requests?
  • Can skill authors mechanically test name/description routing collisions against a corpus of popular skills before publishing?
