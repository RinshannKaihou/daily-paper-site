> **一句话总结：** 字节跳动在生产参数服务器（PS）架构上部署 RDMA 的经验论文：在 RPC 框架 Archon 之下构建软件通信层 ByteExpress（含 RDMA 感知分配器 bemalloc、QP 多路复用、接收信用与每引擎软件发送窗口），在今日头条推荐推理集群（300 PS + 124 ranker，25 Gbps ConnectX-5）上将 PS Fetch 平均/P99 延迟较 Linux TCP 降低 35.7%/43.7%、总 CPU 占用相对降低 10.69%；在 124 PS + 346 trainer 的训练作业中将 P99 参数推送延迟从 TCP 的 1.03 s 降至 268 ms（−74.0%），且观测期内无 PFC 停顿。

> **TL;DR:** This is a production-experience paper from ByteDance on deploying hardware RDMA under its parameter-server-based inference (Toutiao recommendation) and training systems via ByteExpress (BE), a software layer between the Archon RPC framework and RNICs. Its central, honest finding is that hardware offload alone is not enough: on the 346-trainer training workload, RDMA with only hardware congestion control (DCQCN + PFC) is *worse* than the deployed Linux TCP baseline (P99 push 1.12 s vs 1.03 s, with PFC stalls), and it is the software send window that cuts P99 push latency to 268 ms (−74.0% vs TCP). On the production Toutiao inference cluster (300 parameter servers, 124 rankers, 25 Gbps ConnectX-5), BE reduces mean PS Fetch latency from 12.6 ms (TCP) to 8.1 ms (−35.7%), P99 from 63.1 ms to 35.5 ms (−43.7%), and total CPU usage from 57.45% to 51.31% (−10.69% relative). The paper distills three transferable lessons: zero-copy is an interface/memory-management problem (solved by the bemalloc allocator with buffer-ownership transfer), scaling requires controlling distinct resources at distinct layers (QP multiplexing, receive credits, per-engine send window), and reliable transport is only one part of availability (RPC-level timeouts, replica selection, and TCP fallback live above the transport).

## 核心贡献

- **系统与部署**：提出 ByteExpress（BE）——架在 Archon RPC 框架与 RNIC 之间的软件通信层，采用 socket 式接口，将消息翻译为 verbs 操作；在字节跳动数十个数据中心、支撑今日头条/TikTok/西瓜视频的生产系统上稳定运行两年以上。
- **bemalloc 分配器**：在 rpmalloc 之上扩展内存注册与 memory-region 追踪（约 3,000 行 C），让应用动态分配的缓冲区直接 RDMA 可达，通过"缓冲区所有权移交"实现应用线程与通信层之间的零拷贝，注册内存占用在推理节点上稳定在约 2.2 GB。
- **分层可扩展机制**：QP 多路复用（一个引擎一个 QP 服务多个逻辑连接）缓解 RNIC QP 上下文缓存压力；接收信用（credit，批量化 k = d/2）保护已投递的接收缓冲容量；每引擎软件发送窗口 W_s 限制在途字节数——这是训练负载收益的关键。
- **恢复机制**：保留 Archon 的 RPC 级超时（连接 10 ms/请求 40 ms）、重试、副本选择与 TCP 回退，配合 keepalive 序号连接监测、RNIC 端口亲和性、跨 mini-pod 副本复制与故障目的地隔离（5 分钟内 30 次连接失败或 50 次请求失败即隔离）。
- **三条可迁移的部署经验**：零拷贝是接口与内存管理问题；扩展性要求在不同层控制不同资源（接收信用 ≠ 网络拥塞控制 ≠ 链路层流控）；可靠传输只是服务可用性的一部分。

## Key Contributions

- **ByteExpress (BE)**: a production-proven software communication layer between the Archon RPC framework and RDMA NICs. Applications keep a socket-like RPC abstraction; BE translates messages into verbs on Reliable Connection (RC) transport, chosen over UD based on measured throughput (RC reaches 191.36 Gbps vs UD's 114.70 Gbps at 200 Gbps link rate / 4 KB MTU with ib_send_bw).
- **bemalloc**: an RDMA-aware allocator extending rpmalloc (~3,000 lines of C) that amortizes memory registration over 4 MB blocks and supports buffer-ownership transfer, enabling zero-copy for large, variable-size messages with dynamically allocated application buffers.
- **Layered scaling mechanisms**: QP multiplexing (one engine = one QP per remote address, thread-domain-aligned with I/O threads) to avoid QP-context cache misses; receiver-credit flow control with credit batching (k = d/2) to protect posted receive capacity; and a configuration-based per-engine software send window (W_s) that bounds outstanding bytes on top of DCQCN and PFC.
- **RPC-assisted recovery**: connection monitoring via monotonic keepalive sequence numbers, RNIC port affinity (MLNX_OFED 5.0), replicated deployment across mini-pods, quarantining of repeatedly failing destinations, and TCP fallback that restores high throughput within one minute.
- **Three operational lessons** backed by production measurements: zero-copy communication is an interface and memory-management problem; scaling requires controlling distinct resources (receive capacity, outstanding data) at distinct layers; reliable transport is only one part of service availability.

## Methodology

**System stack.** Applications issue RPCs through Archon, ByteDance's existing RPC framework, which uses socket-like endpoints. BE maps each RPC channel (socket) onto an *engine* — a software state machine owning one QP and its work-request chain (partitioned into in-flight / pending / free segments), with a scheduler coordinating multiple engines per I/O thread. This multiplexes many logical connections over few QPs without requiring applications to share RPC channels.

**Zero-copy memory management.** BE cannot use a fixed receive-buffer layout because message sizes vary with user attributes (KB to MB) and application threads may hold received buffers while computing. bemalloc wraps rpmalloc: it allocates 4 MB blocks from the OS, registers them with the RNIC, and serves dynamic allocations from registered memory; ownership of received buffers passes to application threads and back without copies. Registration cost is amortized because registered blocks are cached and reused after the pool reaches steady state (footprint stabilizes near 2.2 GB on a production inference node, sampled every 30 s).

**Large-message transfer.** For large payloads, BE exchanges destination-buffer metadata via SEND/RECV (omittable if valid remote-buffer metadata is cached), then writes payload fragments with one-sided WRITE operations to addresses p, p+S, ..., producing a contiguous message at the receiver; the final fragment uses WRITE_WITH_IMM so its immediate data doubles as the completion flag under relaxed memory ordering. Fragment size trades scheduling granularity against per-request overhead: 2 KB fragments saturate a 25 Gbps link with one QP, while >8 KB fragments are needed for near-line rate at 100 Gbps.

**Flow and congestion control.** Three mechanisms address different bottlenecks: (1) DCQCN (hardware rate control) and PFC (link-level backpressure) remain enabled; (2) receiver credits — senders consume one credit per SEND/WRITE_WITH_IMM, receivers replenish in batches of k = d/2 after ibv_post_recv() — protect posted receive capacity against RNR events; (3) a per-engine software send window W_s bounds outstanding bytes per engine, absorbing incast bursts that DCQCN alone does not react to quickly enough. The design deliberately does not add adaptive congestion-control algorithms; the window is configuration-based, tuned per workload.

**Availability.** BE detects QP errors via completion polling and verbs return codes, plus keepalive messages carrying monotonically increasing sequence numbers. On failure, Archon first retries with RNIC port affinity (MLNX_OFED 5.0 feature), then selects a nearby replica in another mini-pod, and finally falls back to TCP. RPC-level timeouts (T_c = 10 ms connection, T_r = 40 ms request) probabilistically retry requests on top of these transport-level signals.

**Evaluation.** Production inference: a Toutiao recommendation dashboard, 300 parameter servers + 124 rankers, each with 25 Gbps Mellanox ConnectX-5, measured at the 21:00–22:00 daily peak against the deployed Linux kernel TCP stack. Production training: an internal job on TCP and RDMA clusters, 124 parameter servers + 346 trainers (mean/P99 message 20 KB / 50 KB). Microbenchmarks: eRPC and perftest RC/UD comparisons at 25 Gbps/1 KB, 100 Gbps/4 KB, and 200 Gbps/4 KB; allocator benchmarks comparing bemalloc against jemalloc, rpmalloc, tcmalloc, and mimalloc (large: 64 KB–1 MB; small: 16 B–16 KB; 1–8 threads; ~10% cross-thread ops); synthetic worker/PS incast tests for the send window.

## Results & Highlights

- **Production inference latency (Toutiao recommendation, 300 PS + 124 rankers, 25 Gbps ConnectX-5, 21:00–22:00 peak):** RDMA reduces mean PS Fetch latency from 12.6 ms (TCP) to 8.1 ms (−35.7%) and P99 from 63.1 ms to 35.5 ms (−43.7%, a 27.6 ms drop) (Table 6, Figure 16).
- **Production inference CPU (same workload):** total CPU usage falls from 57.45% (TCP) to 51.31% (RDMA), a 10.69% relative reduction, driven by software interrupts (0.16% vs 1.70%, −90.6%) and system time (4.18% vs 7.08%, −41.0%); user time barely moves (47.0% vs 48.7%, −3.5%) (Table 5).
- **Production training (124 PS + 346 trainers, 25 Gbps):** with the software send window, P99 push latency is 268 ms vs TCP's 1.03 s (−74.0%) and P99 fetch is 338 ms vs 650 ms; without the window, RDMA hardware-only is *worse* than TCP (P99 fetch 1.04 s vs 650 ms; P99 push 1.12 s vs 1.03 s) with PFC stalls (~1 s per 30 s) — the window is what makes RDMA win (Table 7).
- **Send-window effect on PFC (synthetic worker/PS incast):** the server count before PFC is observed rises from 63 (no software control) to 1,218 with a 4 KB window (567 at 8 KB, 273 at 16 KB), showing an out-of-band-data limit delays lossless-fabric collapse in this setup (Table 4); smaller windows improve P99 pull latency at some bandwidth cost (Figure 15).
- **QP multiplexing and thread domains (microbenchmarks):** fragmentation with 2 KB fragments lets one QP saturate a 25 Gbps link, while >8 KB fragments are needed for near-line rate at 100 Gbps (Figure 10); with 8 I/O threads, the 512-byte message rate drops sharply beyond 64 QPs due to provider-side spin locks inside ibv_post_send(), and per-thread thread domains restore the rate (Figure 11).
- **bemalloc allocator:** tracks rpmalloc closely in operations/second and peak memory across 1–8 threads (large 64 KB–1 MB and small 16 B–16 KB mixes), posts the highest operation rates among the evaluated allocators, at the cost of peak memory usage up to ~50% higher than alternatives (Figure 4); registered memory stabilizes near 2.2 GB (Figure 5).
- **End-to-end throughput comparison (1 MB messages, 32-byte responses):** BE achieves latency and throughput comparable to or better than eRPC and RC/UD perftest across 25 Gbps/1 KB, 100 Gbps/4 KB, and 200 Gbps/4 KB configurations (Figures 8–9).
- **Recovery:** TCP fallback restores high throughput within one minute in the reported deployment; quarantine policy (M = 30 connection or N = 50 request failures within 5 minutes) diverts traffic from repeatedly failing destinations.

## Authors & Credibility

The team combines an academic systems group with ByteDance's infrastructure engineers. First author Yibo Huang (Fudan University; work done while interning at ByteDance) has prior CoNEXT (SkyRMIO, PicTCP) and ANCC publications on RDMA virtualization and PTE interconnects. Senior co-authors include Yibo Zhu (ByteDance, known for large-scale ML-infrastructure work) and Chuanxiong Guo (ByteDance networking), plus veteran networking researchers Jie Wu (listed at University of Michigan) and Yang Xu (Fudan). The measurements come from real production systems (Toutiao/TikTok/Xigua serving infrastructure, tens of data centers, over two years of deployment), which lends strong operational credibility; the explicit citation of the authors' own earlier tools (eRPC-style design points, Colie, DCPQN) and honest reporting of unfavorable results (RDMA hardware-only being slower than TCP) reinforce trustworthiness.

## Critical Assessment

- **Weak production baseline.** The only production comparison is against the deployed Linux kernel TCP/IP stack; the authors themselves admit the results "do not compare all possible TCP tuning choices or alternative user-space transports" and that the measurements "leave open how much of the gap a differently configured TCP baseline could recover." A tuned user-space TCP stack (or eRPC in production) could shrink the headline 35.7%/43.7% latency wins.
- **The headline training number depends entirely on one knob.** Table 7 shows RDMA hardware-only (DCQCN + PFC) is *worse* than TCP (P99 push 1.12 s vs 1.03 s); the celebrated −74.0% comes from the software send window. This is honestly reported, but it means the contribution is a well-tuned static configuration, not an intrinsic RDMA advantage — and no adaptive policy or automatic W_s selection is offered.
- **Metric proxy caveats, acknowledged but thin.** Inference gains are PS Fetch/Push latencies, not end-to-end recommendation-service latency; the CPU savings are "not separately quantified" as to how the freed capacity is used. The training evaluation uses request P99 latency as a *proxy* for communication stalls rather than measuring end-to-end training throughput.
- **Availability is architectural, not quantified.** The paper states the recovery mechanisms "describe the recovery architecture, not an end-to-end availability guarantee"; "no PFC pauses" holds only "during the reported measurement interval," and Section 9 concedes the need to "characterize recovery more systematically." There is no tail-recovery-time distribution or availability SLO data.
- **Reproducibility is limited.** Both headline workloads are internal ByteDance jobs on proprietary cluster topologies (mini-pods, Colie, watch-dog tooling); bemalloc's evaluation is a synthetic microbenchmark. External groups cannot reproduce the production numbers, and the microbenchmarks deliberately "do not isolate the contribution of each optimization" in the full stack.
- **Missing ablations.** There is no production ablation for QP multiplexing or receive credits individually (their evidence is microbenchmark-level, e.g., Figures 10–11), and the credit scheme with shared receive queues explicitly "does not enforce the per-peer receive-capacity bound" — a scalability/fairness loose end.
- **Strengths that deserve credit:** the negative hardware-only result (Table 7) is exactly the kind of unflattering data most deployment papers omit, and the layered framing of credit/window/PFC as *separate* controls is a genuinely useful conceptual contribution.

## Strengths

- Rare production-scale evidence: tens of data centers, 2+ years, serving Toutiao/TikTok/Xigua; the inference cluster alone is 300 PS + 124 rankers on 25 Gbps hardware, measured at the daily peak, not a lab testbed.
- Intellectually honest: reports that RDMA without the software window loses to TCP (P99 push 1.12 s vs 1.03 s), quantifies the "HW only vs HW+SW" ablation (Table 7), and repeatedly marks the limits of its own measurements.
- Practical, generalizable lessons (interface-level zero-copy via ownership transfer; separate controls for receive capacity vs outstanding data; RPC-level recovery above a reliable-but-brittle transport) that transfer beyond RDMA to any kernel-bypass deployment.
- Well-designed component engineering: bemalloc matches rpmalloc performance while adding registration transparently; thread domains solve a real, measured provider lock-contention problem (Figure 11).
- Useful microbenchmark grounding for design choices (RC vs UD across MTU/link rates; fragmentation size vs line rate).

## Limitations

- Scope is parameter-server Fetch/Push workloads with variable-size messages; it does not address collective-communication patterns (all-reduce) dominant in LLM/GPU training, so the lessons may not transfer directly to that setting.
- Single production baseline (kernel TCP) and no production comparison against alternative user-space transports or RDMA frameworks.
- The send window is static and manually configured per workload; the paper has not "established the stability or fairness of the combined controls across arbitrary workloads."
- Availability guarantees are qualitative: no end-to-end availability numbers, no recovery-time distribution beyond the one-minute TCP-fallback anecdote.
- Shared-RQ configuration trades the per-peer capacity bound for flexibility; shared-buffer QP coordination "requires additional coordination" that is not fully solved.
- Internal, non-reproducible workloads; evaluation artifacts (Archon, bemalloc, production traces) are not released.

## Relevance

对关注大规模分布式训练/推理系统与 ML 基础设施（通信栈、网络效率、参数服务器架构）的读者，这是一篇少见的“生产环境一手经验”论文，直接回答了“RDMA 上生产到底难在哪、收益到底多大”。其分层控制（硬件 DCQCN/PFC 之上叠加软件发送窗口）与零拷贝接口设计的教训，对任何做 GPU 集群通信或推理服务优化的工作都有直接参考价值。

## Questions for Further Exploration

- How would an *adaptive* per-engine send window (reacting to PFC/RTT signals) compare to the static, workload-tuned W_s — could it remove the manual per-workload configuration while preserving the 74.0% training win?
- What fraction of the 35.7%/43.7% inference latency gap would a carefully tuned user-space TCP stack (or eRPC-style transport) recover, given the authors' own caveat about the kernel-TCP baseline?
- Do the same layered-control lessons (credits vs send window vs DCQCN/PFC) hold for collective-communication workloads (all-reduce on GPU clusters), or does the fan-in/fan-out structure of PS Fetch/Push make them unique?
- Can recovery be characterized systematically — e.g., tail distributions of time-to-recovery across failure modes (node, persistent path, unavailable replica) — to convert the qualitative availability architecture into an SLO-backed guarantee?
- How does bemalloc's ~50% higher peak memory footprint trade off at extreme scale, and could registration be delegated to providers (e.g., on-the-fly MR registration APIs) to eliminate the allocator-level workaround?
