Segment-wise, non-prefix KV-cache reuse lifts RAG hit rates from 3.3% to 63.9% — but multi-document reasoning collapses.

KV-Repurpose: A Testbed for Evaluating Non-Prefix KV-Cache Reuse

Taiga Ikeda · Daisuke Miyashita · Jun Deguchi — Kioxia Corp. | 2026-10-09 | kv-cache llm-inference-serving rag long-context systems

Key metric

63.9%

token-level cache-hit rate at a 30 GB cache

Exact prefix caching manages 3.3% at equal capacity — and only 17.9% even with a 1 TB cache. A ~19× hit-rate gap on a Zipfian RAG workload (GPT-OSS-120B, single H200).

Why this matters

RAG documents rarely match a request’s prefix, so KV caches miss and prefill is wasted — hurting TTFT. This open testbed shows when naive reuse is safe, and when it silently breaks the model.

Critical edge

The headline 63.9%-vs-3.3% gap is partly definitional — the synthetic workload caps prefix caching near 20% by construction, and no CacheBlend/EPIC comparison is run.

Methodology

{prefix}<delim>{doc}<delim>{q} → split at delimiter tokens → per-segment cache lookup → hit: skip prefill · reuse unrotated KV + re-apply RoPE → miss: prefill only that segment
  • Segment matching, not prefix matching: one segment miss never blocks reuse of later segments; reuse is keyed purely by delimiter structure, so one document cache serves any system prompt, chat history, or timestamp.
  • Proxy server emulates RAG: pseudo-retrieval over gold LongBench Pro contexts, LRU eviction, and a context-only preprocessing request that generates caches free of user-prefix content (the leakage fix).
  • Testbed, not a technique: <900 lines of Python on vLLM 0.20.0, Apache-2.0; Guidellm load generation, Prometheus/Grafana monitoring, NVMe-tiered KV storage.
  • Evaluation: GPT-OSS-120B on one H200; 2,500-request Zipfian workload (20% / 50% fixed datetime prefix); quality = LongBench Pro (25 tasks) + 7 LongBench sets, averaged over 3 runs vs a full-recompute baseline.

Oracle document selection only partially recovers multi-hop (2Wiki 0.57 vs recompute 0.78) — the gap persists.

  • TTFT crossover at ~16K tokens: reuse wins beyond ~16K contexts and sustains higher throughput at high request rates (contexts to 128K).
  • Cross-segment leakage: 35 of 100 names placed before a cached segment resurfaced in outputs; zero leakage with context-only cache generation.
  • Illustrative Wikipedia extrapolation: 1% cache capacity → est. 42.9% prefill saving, while prefix caching is capped at ~20% under the same assumptions (authors’ own label: illustrative).

Strengths

  • Complete, usable open-source testbed (Apache-2.0, <900 LoC): scheduling, proxy, pseudo-retrieval, LRU eviction, load emulation, monitoring in one artifact.
  • Honest evaluation that reports where the approach fails (multi-doc QA) as prominently as where it wins; 3-run averages; sensible recompute baseline.
  • Useful negative result: the 35% name-leakage finding directly motivates a concrete design rule — generate caches from document-only prompts.
  • >100B-model scale with NVMe-tiered cache — a scale no prior position-independent-caching study covered.
  • Clean system-level result: TTFT/throughput gains land exactly where the mechanism predicts (>16K contexts, high request rates).

Limitations

  • Naive baseline: no combination with or comparison against CacheBlend/EPIC-style corrections — the multi-doc degradation is a property of naive reuse, not of non-prefix reuse in general.
  • Single model, single GPU (GPT-OSS-120B on H200); the authors themselves state results may not generalize to other architectures.
  • Unexplained collapse: the multi-doc gap remains unresolved; the oracle diagnostic conflates reduced concatenation with removal of irrelevant docs.
  • Synthetic workload: Zipfian sampling with an engineered fixed-prefix share; no production traces.
  • Assumption-stacked extrapolation (15 KB KV per content byte, 20% revisit rate, 10-turn chats) bounds prefix caching at 20% by assumption.
  • Delimiter control required: segmentation needs control over prompt construction; drop-in adoption in existing deployments is not demonstrated.

Questions for further exploration

  • Can CacheBlend/EPIC-style selective recompute close the multi-doc gap (0.50 → 0.80) at acceptable TTFT cost inside this testbed?
  • Is the degradation RoPE misalignment, attention-sink displacement, or normalization statistics — and does it vanish without attention sinks?
  • Can segment-wise reuse and exact prefix caching cooperate in one system (reuse the shared prefix, repurpose only the document segment)?
  • Would a learned segment-boundary detector replace hardcoded delimiters on uncontrolled production prompt formats?
  • Can cross-segment leakage be measured at scale and certified away (e.g., bounds on cross-attention mass) for multi-tenant cache repositories?
