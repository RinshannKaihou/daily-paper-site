> **一句话总结：** 首个针对 coding agent 中"同职技能共存冲突"的实证研究：从 20,947 个仓库快照挖出 822,109 候选技能对、确认 1,639 对，并在 Claude Code 上以 312 对实验技能对 × 3 个 Claude 模型跑 6,368 次 agent 运行（169,294 次工具调用、542 小时）；发现共存一个同职相似技能会使已安装技能的使用率下降 19.9 个百分点、其独占核心要求的满足率下降 5.6 pp，而任务完成率几乎不变（+1.9 pp，不显著）——冲突藏在成功背后；冲突在"第一次读取技能"时即已决定（97% 的运行此时还未改任何文件），一个拒绝首次读取的 pre-tool hook 能让模型 96% 的情况下切回已安装技能，把独占核心函数保真度拉回 +9.1 pp。

> **TL;DR:** This is the first empirical study of conflicts between co-installed agent skills that do the same job, on Claude Code. The authors mine 822,109 candidate pairs from snapshots of 20,947 repositories, confirm 1,639 pairs with an LLM judge, and run a controlled experiment on 312 pairs × 3 Claude models (Sonnet 4.6, Haiku 4.5, Opus 5) in 6,368 runs. Against the only-installed-skill baseline (only-A), adding a similar skill B (A+B) lowers the use of A by 19.9 pp while task completion stays flat (+1.9 pp, n.s.) — but fidelity on A's exclusive core functions falls 5.6 pp; an unrelated control skill (A+C) shifts use by only 5.9 pp, isolating the similarity effect. Where a skill is installed decides the winner (a personal skill overrides a project skill of the same name, yet models still read A's files in 29.2% of runs), the final reply names which skill ran in only 0.9% of substitution runs, and the conflict is decided at the first read of a skill — a pre-tool hook denying that first read made the model switch back to A in 96% of denials and recovered 9.1 pp of exclusive-function fidelity, with no task-completion cost.

## 核心贡献

- **首个技能共存冲突的大规模实证研究**：基于 20,947 个 GitHub 仓库的快照（commit hash + git object id 固定，防事后改写），用 GPT-6 Astra 做嵌入检索（Qwen3-Embedding-0.6B 余弦相似度，校准相似度下限：跨项目 0.72 / 项目内 0.52，召回 ≥0.9）+ 逐对 judge，从 822,109 候选对中确认 1,639 对"同职技能"对；分层随机抽样（3,754 对）给出患病率估计。
- **患病率估计（Finding 1/2）**：约 1/4 的已安装技能（≈10,100 个家族，≥23.5%，95% CI [21.2, 25.7]）在同一安装列表里已有一个做同样工作的技能；整包拷贝技能集合的 489 个项目中有 37% 的被判技能存在同职冲突（列表外仅 19%）；冲突对以 normative 技能为主（跨项目 60%、项目内 56%），capability 次之（31%/35%），script-bearing 约 9%。
- **"核心函数"（core functions）度量框架**：对每个技能独立抽取"没有它一个合格模型就不会满足、且可从输出核查"的要求（3,115 个技能共 26,198 条，平均 8.4 条/技能），并标注 exclusive（B 不要求）vs shared；保真度（fidelity）= 主核心函数满足比例。这一指标能把"任务仍通过但已安装技能的约定丢失"从任务完成率中分离出来。
- **受控实验定位冲突机制（RQ1–RQ3）**：312 对 × {only-A, only-B, A+B, swapped（仅反转列表序）, personal/plugin scope, A+C 无关对照} 配置，6,368 次运行、169,294 次工具调用、542 agent 小时（约 $8,560 API 费用）；逐对-逐模型配对分析 + Holm 校正。
- **决策点定位与修复（Finding 5）**：冲突在运行中"第一次读取技能"时决定——97% 的运行在此时还没改任何文件；一个拒绝首次读取 B（当 A 未用时）的 pre-tool hook 让模型在 96% 的拒绝案例中改用 A，把独占核心函数保真度提升 9.1 pp（95% CI [+6.0, +12.1]），任务完成率不受损（+4.1 pp，CI [−1.3, +9.6]）。
- **可复现工件**：完整复现包开源（github.com/troin/conflict），含数据规则与 prompts、安装列表重建脚本、312 对案例与核查、实验 harness、全部 6,368 条运行日志与分析脚本。

## Key Contributions

- First empirical study of conflicts between co-installed agent skills doing the same job: 822,109 candidate pairs mined from 20,947 repository snapshots, 1,639 confirmed pairs, and a stratified sample showing ~1 in 4 installed skills already has a same-job skill in its installation list.
- A requirement-level measurement framework ("core functions", exclusive vs shared) that separates fidelity loss of the installed skill from task completion, exposing conflicts that pass/fail benchmarks cannot see.
- A controlled, paired experiment (312 pairs, 3 models, 6,368 runs, 542 agent-hours) with an unrelated-skill control (A+C), a listing-order swap, and scope manipulations that attribute the loss to substitution (runs that never use A), not interference.
- Localization of the conflict decision point at the first read of a skill, plus a practical mitigation: a pre-tool hook that denies that read restores 9.1 pp of exclusive-core-function fidelity at no task-completion cost.
- Implications for three audiences: benchmarks should score exclusive core functions (co-installation looks harmless to pass-rate-only benchmarks); platforms should guard the first read and disclose which skill ran; skill authors should use distinctive names and task-specific descriptions.

## Methodology

The study targets Claude Code (largest public skill ecosystem) and proceeds in four stages (their Fig. 2). (1) **Installation reconstruction**: from a corpus of 55,698 distinct skills (219,817 SKILL.md files, filtered to 207,863 valid ones, deduplicated into 43,986 families via 5-grams Jaccard ≥ 0.8) in 20,947 repository snapshots, an LLM (GPT-6 Astra) types each repo, and 1,006 installation lists (4,342 with ≥2 skills) define which skills a session in that repo would actually load (project, nested, personal/dotfiles, plugin scopes). (2) **Pair mining**: candidate pairs come from cosine similarity of the name+description text the model sees when choosing (top-10 per skill, same-family excluded; 439,860 cross-project + 382,249 within-project candidates), then the pair judge decides "same job / near-duplicate / related / unrelated" from names, descriptions, and bodies; a similarity floor calibrated on 615 double-judged pairs keeps recall ≥95% (0.72 cross-project, 0.52 within-project); re-judging 200 pairs reproduces the verdict almost perfectly (Cohen's κ = 0.93). (3) **Case building**: for 312 experimental pairs (nested sampling, ±5%, covering all cells), GPT-6 Astra drafts a developer-style request, starting repository (≤15 files), per-core-function checks, and a task-completion check; each skill's core functions are extracted blind (one skill at a time, never its partner) and must be unique, quoted, and checkable; scripts decide 367 of 921 primary core functions, an LLM judge the rest, masked to configuration and skill identity. (4) **Controlled runs**: each (model, configuration, pair) runs once in an offline container (pass@1), on Claude Sonnet 4.6, Haiku 4.5, and Opus 5 — configurations: only-A, only-B, A+B, swapped (listing order reversed via a one-character rename), personal scope, plugin scope, and A+C with an unrelated control skill (median description similarity 0.435 over 200,000 random pairs). Measures: skill use (via Skill tool or file reads), fidelity (share of primary core functions fulfilled), task completion, and disclosure in the final reply; analysis is paired within pair and model with 95% CIs and Holm correction. RQ3 locates the first read of each skill in the tool-call record and tests a pre-tool hook that denies B's first read while A is unused (187 pair-model combinations, each with and without the hook, randomized). Two human raters independently validate every LLM-assisted step (Krippendorff's α 0.66–0.88 across steps). An external check re-runs 193 pairs on Codex with three OpenAI models ($8,550 full-design cost on Claude Code).

## Results & Highlights

- **Prevalence (Finding 1)**: An estimated 63.7% of installed skills (95% CI [61.3, 66.0], ≈26,100 families) have their most similar same-list skill be a same-job skill by another author, and at least 23.5% (CI [21.2, 25.7], ≈10,100 families) are co-installed with a same-job skill — the "nearly one in four" headline. In the 489 projects that copy a whole skill collection, 37% of judged skills have a same-job skill in the same list vs 19% outside such lists. Normative skills dominate confirmed pairs (60% cross-project, 56% within-project), ahead of capability (31%/35%) and script-bearing (~9%).
- **Impact (Finding 3, RQ1)**: Co-installing the similar skill B lowers the share of runs that use the installed skill A by 19.9 pp (95% CI [−23.1, −16.7]) while task completion does not drop (+1.9 pp, CI [−1.0, +4.9]) — the conflict hides behind success. Fidelity of A falls 2.6 pp (CI [−4.4, −0.8]) overall but 5.6 pp (CI [−7.3, −3.8]) on core functions exclusive to A; the unrelated control skill A+C shifts use by only 5.9 pp (CI [−8.5, −3.3]) and fidelity by −0.2 pp, so similarity — not mere extra skill count — causes the loss. With B co-installed, 12.1% of runs use only B and 38.0% use neither skill (vs 30.3% neither under only-A); substituted runs lose 8.0 pp of fidelity while runs that use A (where interference would show) carry only 20% of the loss.
- **Selection and disclosure (Finding 4, RQ2)**: For same-name skills, a personal-directory B removes A from every listing, yet models still read A's files in 29.2% of runs; a plugin B is used in only 2.9% of runs (vs 58.0% for the same pair in-project). Reversing the listing order changes the use of A by only +0.6 pp (CI [−2.0, +3.3]) — in contrast to the position bias reported for tool selection. Disclosure is near-zero: among the 113 runs where B replaced A, the final reply names the skill used in 0.9%; over all A+B runs it names a skill in 7.7% and flags multiple suitable skills in 3.2% (Opus 5: 21.0% and 9.4%).
- **Decision point and guard (Finding 5, RQ3)**: In 79 pair-model combinations (63 pairs), A+B and swapped open different skills first (median 6 vs 6 tool calls apart); runs opening B first fulfill 9.4 pp fewer exclusive core functions of A (CI [−15.0, −4.0], Holm p = 0.004), and 97% of B-first runs change no file before that read. The pre-tool hook made the model switch to A after 96% of first-read denials (179 cases; Sonnet 4.6: 100%, Haiku 4.5: 94.6%, Opus 5: 99%), raised exclusive-core-function fidelity by 9.1 pp (CI [+6.0, +12.1]) and all applicable core functions by 6.6 pp, and left task completion unchanged (+4.1 pp, CI [−1.3, +9.6]) — recovering everything the B-first read costs.
- **External validity check**: On Codex with three OpenAI models over the same 193 pairs, the similar skill lowers A's use by 18.2 pp (vs 20.1 pp on Claude Code) and fidelity by 3.4 (vs 4.6) — the effect is not Claude-Code-specific. Models differ sharply: in A+B, Opus 5 uses both skills in 36.8% of runs and neither in 15.5%, whereas Haiku 4.5 uses neither in 56.4%.

## Authors & Credibility

The authors are from UNSW Sydney (Chaoliang Yan, Zihao Xu, Yuekang Li, Shangzhi Xu), Griffith University (Yi Liu), Nanyang Technological University (Gelei Deng), and the University of Wollongong (Siqi Ma) — a group with a track record in LLM-agent security and empirical software engineering (several cited prior works by the same group: the 31,132-marketplace-skill security study, agent-as-a-judge work, and LLM-based mining of software repositories). The paper reads like a careful ICSE/FSE-style empirical study: preregistered loss measures, stratified sampling with confidence intervals, a calibrated retrieval floor, double-judged calibration samples, two human raters validating every LLM step with reported Krippendorff's α, Holm corrections, negative controls, sensitivity analyses, and a full artifact release (github.com/troin/conflict with all 6,368 run logs). The stated budget (~$8,550 API cost, 542 agent-hours) and the honest threats-to-validity section add to credibility.

## Critical Assessment

The core construct is LLM-authored at two levels: core functions are extracted by GPT-6 Astra, and most of them (554 of 921 primary ones) are judged by an LLM rather than a script. The authors mitigate this well — blind extraction, human validation with α of 0.77–0.88 on the key steps, and a masked output judge — but "fidelity" remains fidelity-to-an-LLM's-reading of a skill's prose, and a skill whose instructions are vague or over-broad would yield weak core functions regardless of agent behavior. Second, each (model, configuration, pair) cell is a single run (justified as pass@1; a 512-combination re-run subset agrees 88.9% on skill use, ICC 0.78/0.84), so per-pair noise is nontrivial even though the paired design and 312 pairs absorb much of it. Third, the full design runs on one platform; the Codex replication covers only 193 pairs and three outcome numbers, and Gemini CLI / GitHub Copilot are discussed but not measured, even though the abstract and conclusion generalize to "coding agents". Fourth, the 312 experimental pairs are a subset of the 1,639 confirmed pairs filtered to those whose skills run offline (only 48% of installed skills in confirmed pairs pass the runnability check) and whose requests an LLM could draft — real-world task requests and real user-written skill bodies may behave differently. Finally, the headline prevalence estimate ("1 in 4") rests on public repositories only; the authors acknowledge that personal skills and unshared plugins — precisely where overriding duplicates lurk — are underrepresented, and the "37% in copied collections" figure comes from only the 489 collection-copying projects. None of these undercut the central finding (the A+C control and the hook intervention are convincing), but the 9.1 pp guard gain deserves replication outside the authors' own harness.

## Strengths

- Genuinely novel question with a clean framing: substitution vs interference, and an "exclusive vs shared core function" split that makes the invisible loss measurable and falsifiable.
- Impressive scale and determinism discipline: commit-pinned snapshots, 822,109 candidates, a recall-calibrated similarity floor, stratified sampling with CIs, and near-perfect judge reproducibility (κ = 0.93).
- Strong causal hygiene: paired within-pair-and-model comparisons, an unrelated-skill control (A+C), a listing-order swap that separates order from scope, Holm corrections, and sensitivity analyses over which core functions are counted.
- The RQ3 hook experiment moves the paper from observation to intervention: it shows the first read is the decision point and that a cheap guard fixes the loss for every model — actionable for platform builders.
- Full artifact release including all run logs and the judging prompts, which is rare for agent experiments of this size.

## Limitations

- Fidelity depends on LLM-extracted core functions and a majority-LLM judge; skills with poorly written instructions may get mismeasured core functions, and no experiment validates core functions against what human skill authors intended.
- One run per (model, configuration, pair); the 88.9% re-run agreement bounds but does not eliminate per-cell noise.
- Full design on Claude Code only; Codex check limited to 193 pairs; other skill-loading agents (Gemini CLI, Copilot) untested despite the generalizing claims.
- Experimental cases are LLM-drafted synthetic requests over ≤15-file repositories, and only the 48% of pair skills that run offline are studied; script-heavy or API-dependent skills are underrepresented.
- Prevalence estimates come from public repositories; personal and plugin skills (where same-name overrides actually fire) are structurally under-observed.
- The guard is the authors' own pre-tool hook evaluated on the 187 combinations where B was opened first; interaction with production hook systems and with more than two co-installed skills is untested (a three-skill probe shows 36.0% of runs use neither skill and 0.1% only C, but no mitigation is studied there).

## Relevance

这篇论文直接研究我们每天都在用的 Claude Code 技能机制：项目技能、个人技能和插件共存时的静默冲突，正好解释了"装了技能却像没装一样"的失效模式，对技能作者、agent 平台设计和 skill 基准评测都有立即可用的启示（尤其 pre-tool hook 守卫首次读取这一低成本修复）。

## Questions for Further Exploration

- Do core functions extracted from real skill-authoring intent (e.g., interviews with skill authors) match the LLM-extracted ones, and does fidelity-to-author-intent differ from fidelity-to-GPT-extracted-requirements?
- How does the conflict scale with three or more co-installed same-job skills, where 36.0% of runs already use neither skill — is a global skill-router or deduplication at install time more effective than a first-read guard?
- Would a platform-side "which skill ran" pin in the final reply (disclosure) change user trust or downstream task behavior, given that models disclose in only 0.9% of substitutions today?
- Does the 9.1 pp guard gain hold on non-Claude platforms with different skill-precedence rules (Gemini CLI is project-first, Copilot lists both), and on real user issue reports rather than LLM-drafted requests?
- Can skill authors mechanically test their name/description for routing collisions against a corpus of popular skills before publishing?
