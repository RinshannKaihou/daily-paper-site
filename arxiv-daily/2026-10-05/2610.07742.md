> **一句话总结：** NYU 的 CLEAVE 编译器把内核优化拆成两步——在符号 shape 的计算图上做超优化搜索（引入带符号分割数 s 的 Split 算子实现 Split-K 类代数变换），再对每个等价图做迭代分块 + 水平融合的算子调度——从而在 9 个常见 LLM 子图上生成比 torch.compile/Welder/Mirage/TensorRT 中最优基线快至 2.8×（几何平均 1.6×）的内核，编译时间比联合搜索的 Mirage 快 5.9×，且在 FlashInfer-Bench 的 303 个动态 workload 上以一次编译取得对 FlashInfer 手写 FA2/FA3 后端 1.4×/1.7× 的几何平均加速。

> **TL;DR:** CLEAVE is an ML kernel compiler built on "symbolic decoupling": an algebraic phase superoptimizes the computation graph over symbolic shapes (validated by cheap probabilistic testing on tiny tensors, with a new Split operator whose symbolic split count enables Split-K), and a separate scheduling phase decides tiling via iterative tiling and horizontal fusion, lowering the top-k candidates to TileLang and profiling them. On 9 common LLM subgraphs (A100/H200), CLEAVE-generated kernels are up to 2.8× faster than the best of torch.compile, Welder, Mirage, TensorRT, cuBLAS, FlashAttention and FlashMLA (1.6× geomean), while compiling 5.9× faster than Mirage (8–14 min vs Mirage's 121–324 min per subgraph, with Mirage OOMing on two). On 303 dynamic attention workloads captured from FlashInfer-Bench, one compilation per operator yields 1.4×/1.7× geometric-mean speedup over FlashInfer's handwritten FA2/FA3 backends.

## 核心贡献

- **符号解耦（symbolic decoupling）**：将"代数变换"与"算子调度"沿自然边界分离——代数变换的有效性只依赖计算图本身，与 shape 和调度无关，因此可在符号 shape 的图上一次搜索完成，再由调度器对每个等价图绑定具体 shape。这避免了 Mirage 式联合搜索的爆炸空间。
- **带符号分割数的 Split 算子**：扩展 Mirage 的代数超优化，引入 `Split(A : m,k, dim=1, s)` 把归约维切成 s 份（s 为符号变量），使超优化器只需决定"在哪切、怎么合并"，s 的具体值留给调度阶段；配合"可归约性（eventually-reduced）剪枝"限制搜索空间，只允许切分最终会被归约掉的维度。
- **符号 shape 上的廉价等价性检查**：把 tensor 维度替换为符号变量后，随机测试只需在小型实例化张量上运行，测试成本与具体 shape 的张量大小解耦，使大 shape（如 head_dim=128 的 MHA）也能被搜索覆盖——论文指出 Mirage 在 head_dim=128 时找不到优化图、head_dim=64 时才能找到。
- **迭代分块 + 水平融合的调度算法**：基于 itGraph（迭代瓦片图）表示，先按输出瓦片大小做 threadblock 间调度，再迭代地对归约节点做瓦片内调度；把消费同一上游生产者的归约（如 attention 中的 Rowsum 和第二个 Matmul）放进同一循环做水平融合，避免在 SMEM 中物化完整中间张量，从而能融合长序列的归约链。
- **动态算子一次编译**：对随请求变化的 batch/序列长度，按代表性具体 shape 调度、codegen 时用符号做循环边界，一份编译产物服务全部 303 个捕获 shape，无需重新编译。
- **系统性评估**：9 个子图（prefill + decode）、GPT-2/Llama-3 8B/Qwen3-32B 端到端单层、FlashInfer-Bench 303 个动态 workload、编译可扩展性对比与消融，代码开源（github.com/nyu-systems/cleave）。

## Key Contributions

- **Symbolic decoupling**: separates algebraic transformation from operator scheduling along a natural line — the validity of a graph rewrite is a property of the graph alone, independent of schedule and tensor shapes — so the algebraic search runs once over graphs with symbolic dimensions, and a dedicated scheduler binds concrete shapes per candidate. This shrinks the joint search space that makes Mirage fail on common kernels.
- **A Split operator with symbolic split count**: extends algebraic superoptimization with `Split(A : m,k, dim=1, s)` that partitions a reduction dimension into a symbolic s parts (two-kernel split+combine decomposition), letting the algebraic phase decide *where* to split without fixing *how much*; reducibility-based pruning restricts splits to dimensions that are eventually reduced, scaling the search beyond TASO-style rule mining.
- **Cheap equivalence checking via symbolic shapes**: representing every dimension as a symbol makes probabilistic (random-testing) equivalence checks run on small tensors, so search cost no longer grows with concrete tensor sizes — CLEAVE finds optimizations for MHA with head_dim=128 where Mirage (which tests on concrete shapes) only succeeds at head_dim=64.
- **Iterative tiling + horizontal fusion scheduler**: an itGraph-based algorithm that partitions output tiles across threadblocks, tiles each reduction to an explicit iteration loop (keeping only one tile of each intermediate live, cutting SMEM from [b_O, N] to [b_O, b_R]), and fuses reductions sharing an upstream producer (Rowsum + V-Matmul over the same Exp tile) into the same loop — enabling fusion of consecutive-reduction graphs (attention) that Welder cannot fuse once sequence length ≥ 512.
- **One-shot compilation for dynamic workloads**: scheduling on one representative concrete shape, then re-emitting loop bounds and memory offsets symbolically at codegen, so a single compiled kernel serves all 303 captured shapes of an operator from FlashInfer-Bench.
- **Comprehensive evaluation** across subgraph, end-to-end transformer-layer, and dynamic-operator benchmarks, with compile-time scalability measurements and component ablations.

## Methodology

**Two-phase pipeline over a computation subgraph.** CLEAVE takes a kernel subgraph with concrete shapes and runs: (1) an *algebraic transformation phase*, (2) an *operator scheduling phase*, then (3) memory planning, TileLang code generation and profiling.

**Phase 1 — Algebraic transformation with symbolic shapes.** Each tensor dimension is replaced by a symbol (dimensions forced equal by broadcasting are merged into one symbol; extent-1 broadcast dims are kept distinct). The extended Mirage-style superoptimizer enumerates equivalent graphs within a bounded size, starting from a disconnected graph and incrementally inserting nodes; the new Split operator (symbol s) lets the search insert Split-K partitions without fixing partition size. Two extensions make this sound and scalable: (a) shape validity of inserted nodes is checked for all instantiations of each symbol, guarded by the probabilistic checker; (b) "reducibility-based pruning" — the authors define a dimension as *eventually-reduced* if all its elements feed one output element, and prune any candidate where Split or a reduction breaks this set, which is what enables finding Split-K rewrites. Equivalence is validated by probabilistic testing on small concrete instantiations. For each surviving graph, concrete shapes are recovered by propagating original input shapes, and every valid Split value is enumerated as a concrete candidate graph (each independently scheduled; at runtime both split and combine kernels run).

**Phase 2 — Operator scheduling over itGraphs.** A tile program is modeled as an *iterative tile graph* (itGraph): a hierarchy of loop nodes (inner loops are sequential, accumulating into the same output tile; the outermost loop is parallel, each iteration writing a distinct output tile) with tmap annotations mapping full tensors to per-iteration slices. Scheduling runs in two steps: (1) *inter-threadblock scheduling* — divide the output tensor extent by a candidate output tile size, build the tmap by range-based data-dependency analysis (reusing Welder's analysis); (2) *intra-threadblock scheduling* — repeatedly identify "last-wave" reduction nodes, group those sharing upstream nodes, build inner itGraphs that tile each reduction by its reduction tile size b_R, and horizontally fuse groups by wrapping their upstream subgraph in a shared inner loop (validity checked by exact tmap-match during backward propagation). Candidate tile-size configurations are enumerated from hardware constraints (Tensor Core / coalescing minimums via GetMinReductionRange), each candidate is checked with an analytical cost model (similar to Welder's, simulating one threadblock's SMEM allocation across iterations to estimate peak SMEM and GMEM traffic), and the top-k are lowered and profiled.

**Memory planning and codegen.** Unified memory/layout planning decides RMEM vs SMEM placement, hoists loop-invariant inputs (zero-tmap nodes like Q′) to avoid redundant GMEM loads, propagates Tensor Core layout constraints from Matmul nodes, and applies swizzled SMEM layouts. Codegen lowers each itGraph level to TileLang (v0.1.5) as an iteration function (iter) plus a wrapper (wrap) implementing the loop and slicing logic. For dynamic operators, shapes varying along dynamic axes are re-emitted symbolically (loop bounds [n/b], tile offsets computed at runtime); tile sizes are predicted larger than actual inputs and out-of-range threadblocks are skipped, so one cubin serves all shapes.

**Motivating examples.** FlashAttention requires the algebraic move of the division after V-Matmul (breaking the all-to-all softmax→P dependency so only one tile of S and P is live at a time) plus iterative tiling over the V reduction; FlashDecoding/Split-K requires partitioning the K/V reduction for parallelism — two rewrites the authors show appear "coupled" only when stated with concrete b; symbolic decoupling makes both discoverable independently of partition size and schedule.

## Results & Highlights

- **Subgraph performance (9 subgraphs, prefill shapes, A100 + H200, FP16 accumulation, vs torch.compile eager, TorchEager, Mirage, Welder, TensorRT, cuBLAS, FlashAttention, FlashMLA):** CLEAVE-generated kernels are **up to 2.8× faster than the best baseline on each individual subgraph, with a 1.6× geometric-mean speedup**; on decode shapes it is 2.1× faster than itself without Split-K, and enabling Split-K on the four decode operators adds a further **1.15×–2.99×**.
- **Compilation scalability (Table 1, A100, per subgraph averaged across shapes):** with Split-K enabled CLEAVE compiles each subgraph in **8–14 minutes**, vs **Mirage's 121–324 minutes** on the only 4 subgraphs where Mirage produces valid code (Mirage also runs out of memory on two subgraphs and cannot generate code for GQA, MQA, or MLA at all); with Split-K disabled CLEAVE takes 1–5 minutes, comparable to Welder's 1–4 minutes (which, however, misses all algebraic optimizations like Split-K).
- **Dynamic operators (FlashInfer-Bench, 9 paged/ragged attention operators, 303 captured workloads on NVIDIA SOL-ExecBench):** CLEAVE is faster than FlashInfer's handwritten **FA2 backend on all nine operators, by 1.16×–2.04× (1.4× geometric mean)**, and faster than **FA3 on seven of nine with a 1.7× geometric mean**; it is slower only on the two MLA operators (0.85×–0.89×), where FA3 merges partial results inside a single cooperative kernel while CLEAVE pays a second kernel launch.
- **End-to-end (single transformer layer, H200, Fig. 10):** speedups over torch.compile of **2.45× on GPT-2, 1.47× on Llama-3 8B, and 1.43× on Qwen3-32B**; the paper attributes the shrinking gains on larger models to time being dominated by linear layers whose vendor kernels are already well tuned (Welder there is at parity with torch.compile; Mirage cannot fully support GQA-based models on Llama-3/Qwen3-32B).
- **Ablation (Fig. 12, geomean across 9 subgraphs and shapes):** removing tensor-core layout constraints costs 6%; **disabling iterative tiling degrades performance by 40%; disabling algebraic transformation degrades it by 44%; disabling both costs 47%** — both halves of symbolic decoupling contribute substantially.
- **Porting algebraic graphs to other compilers (Fig. 14):** feeding CLEAVE's algebraically transformed graphs to Welder improves Welder on 4 subgraphs (though still below CLEAVE), but adding them to torch.compile makes it *worse* — TorchInductor's log shows it can no longer identify the fusion patterns it found on the original graph. Mirage additionally failed to optimize MHA with head_dim=128 while succeeding at head_dim=64, which the authors tie to concrete-shape testing cost.

## Critical Assessment

- **Correctness is probabilistic, not verified.** Equivalence of candidate graphs rests on random-input testing (as in TASO/Mirage), and although the paper insists symbolic decoupling "does not lose the correctness guarantee," a probabilistic checker can in principle admit an unsound rewrite; there is no formal proof or SMT certificate for the discovered transformations. For a compiler that emits production serving kernels, this is a real (if inherited) weakness that the paper does not quantify (e.g., no measurement of checker false-positive rates).
- **A required manual annotation.** The Split/reducibility pruning pipeline currently "require[s] the user to annotate the input tensors for which dimensions are eventually-reduced"; the authors admit data-dependency analysis could automate it, but as released, using CLEAVE on a new operator involves non-trivial expert input — a caveat to the "automated" framing.
- **Simplified cost model and single backend.** The analytical cost model "assumes all buffers are located in SMEM for simplicity," which can mispredict kernels that spill or that would prefer RMEM-resident intermediates; and all results flow through one codegen backend (TileLang v0.1.5) on NVIDIA A100/H200 only — the much-discussed Tensor Core layout handling (Appendix B) is entirely NVIDIA-specific, and there is no evidence the approach transfers to other vendors.
- **End-to-end evidence is thin.** The headline "end-to-end" claim is measured on a *single transformer layer*, not full-model serving with KV-cache management,通信 or scheduling overheads; on the largest model (Qwen3-32B) the advantage over torch.compile already narrows to 1.43×, and the paper's own explanation (linear layers dominate; vendor kernels are near-roofline) caps how much further the approach can matter for large dense models.
- **Honest negative results, but they bound the claim.** CLEAVE loses to FlashInfer FA3 on both MLA operators (0.85×–0.89×) because FA3's single cooperative kernel avoids CLEAVE's split/combine second launch — showing the two-kernel Split decomposition still pays a launch tax in exactly the regimes (large-batch decode) where kernel launch overhead matters most. Also commendable: the paper reports that Mirage OOMs on two searches and that algebraic rewriting actively *hurts* torch.compile rather than hiding it.
- **Baseline fairness.** Baselines are pinned research-prototype commits (Mirage e9890e1, Welder af53ab1) alongside mature vendor stacks (TensorRT 10.5.1.29, cuBLAS 12.8); comparisons to handwritten kernels are appropriately against FlashInfer's FA2/FA3 and FlashMLA rather than strawmen, which strengthens the dynamic-workload claim.

## Strengths

- The central idea — decoupling algebraic search (shape-independent) from scheduling (shape-dependent) and representing split factors symbolically — is simple, well-motivated, and demonstrably effective at taming a search space that makes Mirage OOM or time out.
- Symbolic-shape equivalence testing is an elegant fix for superoptimization's scaling wall: testing on small tensors lets the search cover head_dim=128 attention graphs that concrete-shape search cannot reach.
- The scheduling algorithm genuinely reproduces expert-kernel structure (FlashAttention-style single-pass fused attention with iterative tiling and horizontal fusion) automatically, and the itGraph/tmap formalism is described precisely enough to reimplement.
- One-compile-serves-all dynamic operators with runtime loop bounds is a practical win for serving, validated on 303 real captured workloads via FlashInfer-Bench rather than synthetic shapes.
- Broad, layered evaluation (subgraph, end-to-end, dynamic, compile time, ablation, cross-compiler grafting in Fig. 14) with unusually candid negative results.

## Limitations

- NVIDIA-only evaluation (A100, H200) and a single TileLang backend; other DSL backends are only "planned."
- Correctness guarantee is probabilistic testing, with no formal verification fallback or soundness measurement.
- Eventually-reduced dimension annotation is manual in the current system.
- Workload coverage is limited to 9 transformer-style subgraphs (Matmuls, RMSNorm+MatMul, SwiGLU, MHA/GQA/MQA/MLA attention) and attention-dominated dynamic operators; no convolution, MoE routing, or quantized kernels.
- Per-shape performance relies on profiling top-k candidates, so total compile cost grows with k, and the SMEM-only cost-model assumption may misrank candidates for memory-heavy kernels.
- Gains over torch.compile shrink to ~1.43× on Qwen3-32B-scale models where tuned GEMM dominates; MLA-class decode still trails a hand-tuned cooperative kernel (FA3).

## Relevance

这篇论文正对用户"大规模 ML 计算基础设施——算子与内核"方向的核心：它展示了如何用符号解耦的编译器自动生成媲美 FlashAttention/FlashDecoding 级手写内核的 GPU 算子，并给出内核自动优化的可扩展搜索方案。其"一次编译服务全部动态 shape"的机制和 Split-K 自动代数变换，对推理 serving 栈中内核层的正确性与性能工程都有直接参考价值。

## Questions for Further Exploration

- Can the "eventually-reduced" annotation be fully automated via data-dependency analysis, and would automation ever mislabel dimensions and yield unsound or missed rewrites?
- Could probabilistic equivalence testing be replaced or augmented with formal certificates (SMT/e-graph based), and at what search-time cost — especially since symbolic shapes already shrink the test inputs?
- How does the symbolic-decoupling pipeline transfer to non-NVIDIA targets or to TileLang alternatives (Triton, CUTLASS DSL), given that Tensor Core layout propagation is currently hand-derived per backend?
- Can the Split operator generalize beyond reduction-dimension parallelism — e.g., to quantized/mixed-precision kernels where split partial results change accumulation precision, connecting to numerical-stability concerns?
- The paper shows CLEAVE's algebraic graphs hurt torch.compile but help Welder: what minimal scheduling-interface contract must a downstream compiler satisfy to consume algebraically transformed graphs without losing its own fusion patterns?
