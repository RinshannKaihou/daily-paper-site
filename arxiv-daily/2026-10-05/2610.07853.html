One bf16 rounding step at export silently reverts most low-learning-rate fine-tuned ternary codes — collapsing GSM8K accuracy to near zero.

“Lost in the bf16 Cast: Exporting Ternary Language Models Can Revert Most Low-Learning-Rate Code Changes”

Falcon-E-1B-Base, GSM8K greedy strict accuracy: online fp32-latent evaluation vs. the documented bf16 export. 96.3% of 4,055,607 code additions reverted. (BitCPM-CANN-0.5B: 36.13% → 0.39%.)

Why this matters

If you fine-tune and deploy BitNet / Falcon-E / BitCPM-class ternary models, standard export can silently destroy your work — and both tested fixes are cheap to replicate.

低学习率微调的码字修改大多落在 bf16 舍入单元内——标准导出会无声回滚，甚至摧毁任务准确率；两条修复路径都容易复现。

Critical edge

The headline collapse lives in a constructed low-LR regime (rates matched by nominal LR-to-bf16-ULP ratio): at 32× the learning rate, the same pipeline shows no detectable strict-accuracy harm.

Methodology

Fix A · fixed export: write the training quantizer’s codes directly Fix B · projection: nudge bf16 inputs ≤8 ULP inside thresholds (μ=2⁻¹⁶), labs’ tools untouched

Audit. Released bf16 latents re-quantized with fp32 absmean arithmetic, then compared against each lab’s deployed ternary codes; the unmodified onebitllms 0.0.4 exporter reproduces all four Falcon-E releases byte-for-byte.

Fine-tuning. Full fine-tune of three official ternary models on GSM8K, fp32 latents, learning rates matched by nominal LR/bf16-ULP ratio (3.125×10⁻⁵ / 10⁻⁴); comparisons declared before runs, paired row bootstraps, pre-registered 4-point non-inferiority margins.

Mechanism. At low LR, newly-crossing latents clear the ternary threshold by only 0.1–0.4 bf16 ULP — still inside the old rounding cell. Export’s round-to-nearest sends them back: ~91–96% of code additions revert; all 31,895,216 of 2B-4T’s mismatched codes sit within 0.5 ULP of a threshold.

An operational artifact of the released weights, not “lost weights” — the stock exporter reproduces the Falcon-E releases exactly.

  • Both remedies are non-inferior (pre-declared 4-point margin) to online evaluation on all three models — e.g. BitCPM fixed − online = +0.39 [−1.86, +1.17].
  • Projection is exact and cheap: reproduces the online codebook on every coordinate (up to 2.08×10⁹ codes); 546 tensors converge in ≤2 iterations, ~10 CPU-minutes total.
  • It’s a low-LR property: at 32× the rate, BitCPM strict accuracy is essentially unchanged (+0.20 [−2.04, +3.04]) and only 4.0% of changed codes revert.
  • Selection is by threshold distance, not edit count: randomized far-vs-near intervention gives lift +0.0372/+0.0391 (2B-4T seeds) and +0.109 (Falcon-E); the effect generalizes to BoolQ (+0.035) and MATH (+0.041).

Strengths

  • A genuine end-to-end causal chain: release audit → ULP-level mechanism → catastrophic task consequence → two verified remedies → a deployment checklist.
  • Pre-registration hygiene rare in systems work: declared comparisons, frozen rules, labeled post-hoc analyses, paired row bootstraps throughout.
  • The projection is elegant and cheap — labs’ tools untouched, bounded moves, verified against each tool’s own output on every coordinate.
  • A randomized distance-selection intervention (role-swapped pairs, bitwise-identical starting compute) converts correlation into causal evidence in two model families.
  • Scoring-rule honesty: strict vs. last-number exposes that 2B-4T’s “restored” story is metric-dependent.

Limitations

  • Constructed low-LR regime: higher-rate endpoints show no detectable strict-accuracy harm — external validity to common fine-tuning practice (e.g. LoRA) is untested.
  • 512 dev prompts carved from the GSM8K training split, greedy decoding only; no fresh held-out evaluation; sensitivity to batch configuration.
  • BitNet 2B-4T’s audit is circumstantial (no fp32 master), and part of its evaluation shared a GPU with a production job.
  • Non-inferiority ≠ equivalence: the 4-point margin is resolution-based, and projection guarantees hold only for these exact tool versions and host (852 threshold decisions moved on a second backend).
  • One recipe family (full FT, 300 steps); PyTorch bf16 GPU kernels only; RL fine-tuning exposure remains a hypothesis.

Questions for further exploration

  1. Does export reversion also corrupt RL fine-tuning (GRPO/PPO) on ternary models, where many small steps accumulate?
  2. Do LoRA merges concentrate code changes near thresholds the same way, and does the reversion arithmetic apply at merge time?
  3. Would a rounding-aware training objective (penalizing latents within 0.5 bf16 ULP of a threshold) remove the reversion regime outright?
  4. How much of the strict-vs-last-number divergence is genuine format damage vs. GSM8K parsing — would an LLM-as-judge rank the export differently?
  5. Do CANN/integer-kernel backends drift the same way, and can code-level census checks be wired into CI for ternary release pipelines?
