Validating GPU kernels without source or numeric tolerances: binary-level determinism testing covers concurrency — LLM reduction + Kuiper/F* proof cover function.

RESOLVE: Language-Agnostic Validation of GPU Kernels Through Testing, Reduction, and Proof

Ashkan Vedadi Gargary · Guido Martínez · Sebastian Burckhardt · Gabriel Ebner, et al.

  • GPU kernels
  • Formal verification
  • Determinism testing
  • LLM agents

Key metric
4 issues · 2 clear bugs

Previously unreported, found in production mega-kernels (LUCE, FlashMoE, FastMoE).

All agent-repaired and re-validated; latency cost ≤2% in 3 of 4 cases (FastMoE +10.5%).

Why this matters

LLM agents write GPU kernels at scale, and tolerance tests pass even empty kernels — this test-plus-proof pipeline is a credible quality gate for trusting them.

Critical edge

Proof soundness hinges on hand-reviewed specification tightness with no automated certification — the weakest link for autonomous optimization loops.

01

Methodology

One bet: ML kernels are intended to be deterministic — so concurrency can be settled by testing with an exact oracle, function by proof.

A · Concurrency — test
compiled SASS→ count→ trace→ perturb→ bitwise verdict
  • NVBit instruments the binary — no source, no compiler: CUDA, Triton, Gluon, CUTLASS alike.
  • Many runs over 10 input-distribution families; all of memory hashed, equality-only compared.
  • Delays (up to 5,000 cycles, p=0.8) inserted only at traced conflict sites; every perturbed run byte-compared to baseline.
B · Function — reduce + prove
candidate + reference→ LLM reduction→ Kuiper (F*/Pulse)→ equivalence proof
  • Agent minimizes concurrency (barriers/atomics/warp primitives rejected); accepted only if bitwise-identical on every input.
  • A tight algebraic spec is drafted from the trusted reference alone; the ε-approximation relation decouples floats from reals, so reordered-but-valid arithmetic still proves.
  • Chain of trust: kernel ≡ reduction ≡ verified program ≡ spec.

Agent-driven throughout (Copilot CLI; GPT-5.6, Claude Opus 5) on 4×H100 — humans own the scientific argument.

02

Results

KernelBench L1 · RKB corpus — 100 GPT-5.6 candidates, all tolerance-test passers

  • 15 deterministic & bitwise identical — no full pipeline needed.
  • 2 flagged as doing no memory work at all: empty ELU kernels (#31, #32) — tolerance testing’s false negatives.
  • 11 / 14 through the full workflow pass reduction + proof; 3 inconclusive (Kuiper coverage gaps; a Taylor degree-11→10 rewrite).

Mutation study · RKB-Mutant

  • 92 / 143 injected synchronization faults caught (64.3%); all 51 misses explained — 3 dead code · 28 races that never change the output · 26 intra-warp, beyond NVBit’s reach.

Fused MLP & production mega-kernels

  • Agent-written Triton / Gluon / CUTLASS single-kernel fusions run ~2.5× faster than eager PyTorch; Gluon carried to a full F* proof. Compute Sanitizer runs clean on all three — which proves neither property.
  • All three mega-kernels (LUCE, FlashMoE, FastMoE) are nondeterministic; delta debugging exposes the 4 unreported issues. Repairs: LUCE grid-barrier −1.4% · LUCE scratch-aliasing −1.6% (both faster) · FlashMoE +0.8% · FastMoE +10.5%.

03

Strengths

  • Exact per-execution oracle: bitwise equality settles concurrency; the ε-relation settles numerics without any chosen threshold.
  • Language-agnostic by construction — pointed at compiled NVIDIA binaries, it validates Triton, Gluon, CUTLASS, and CUDA uniformly.
  • Falsifiable practice: detection power quantified (92/143), every miss individually explained, inconclusives reported as inconclusive.
  • Production-scale yield: two unambiguous LUCE bugs found, agent-repaired, re-validated — and two repairs came out slightly faster.
04

Limitations

  • NVBit cannot interleave intra-warp conflicts (26 mutation misses) or delay async loads — a structural blind spot of binary-only testing.
  • The proof ceiling is Kuiper’s coverage: inline PTX, subnormal flush, _expf, argmax unsupported; LUCE cannot even be reduced (warpgroup MMA).
  • Spec tightness is certified by hand; a loose spec collapses the guarantee to mere safety, and tolerance-changing rewrites are rejected outright.
  • Economics: ~143 min + 5.7M tokens per kernel plus human review — far from per-commit validation; legitimately nondeterministic kernels are rejected by design.
05

Questions for Further Exploration

  • Can spec tightness be certified automatically — property-based checks against the reference, or machine-checkable obligations in Kuiper?
  • Would SuperCollider-style compiler-assisted in-warp perturbation close the 26 intra-warp misses without sacrificing language agnosticism?
  • Can FP error-budget reasoning be ported to Kuiper, so rewrites like the degree-10 Taylor sigmoid prove with a concrete bound instead of being rejected?
  • Is arrival-order-dependent MoE token dropping a bug, a spec choice, or acceptable nondeterminism — what would a standardized router contract look like?
  • Can the proof stage’s 5.54M-token footprint shrink by reusing verified-kernel corpora (e.g., audited KernelBench solutions) as proof libraries?
