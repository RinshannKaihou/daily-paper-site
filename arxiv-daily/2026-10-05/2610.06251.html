Key finding · arXiv:2610.06251 · 2026-10-05

A batch-shared early-stop statistic in HQQ KV-cache quantization lets an unrelated companion question change a target’s greedy-decoded answer.

Shared Stopping Decisions Change Answers in HQQ Cache Quantization

Seunghui Jwa · Minsu Oh · Chanjun Park · Yeo-Chan Yoon — Jeju National University / Soongsil University

  • KV-cache quantization
  • batch-invariance
  • LLM serving
  • reproducibility
  • HQQ

Key metric

170/384

44.3% of matched test comparisons change output text from swapping only the batch companion — every comparator under matched controls sits at 0/384.

Why this matters

If you run batched LLM inference or reproducible benchmarks, request-local quantization is not request-independent — shared stopping decisions belong in deployment audits.

Critical edge

The headline 44.3% is a text-change rate, not an error rate: only 8/246 resolved answers flip — five of them wrong→correct.

一句话总结

HQQ KV 缓存量化的遗留近端优化器用跨请求共享的平均重建误差决定所有请求何时停止更新——同批无关问题即可改变目标问题的更新次数与贪心解码答案；换 companion 使 170/384 次比较文本改变（全部对照 0/384），固定 20 次迭代预算可零调参修复，但 padding/SDPA 层面的批依赖依然存在。

Methodology

Pinned stack: Transformers 5.17.0 + HQQ 0.2.8.post1; 4-bit group-wise KV cache (group 64, ≤20 legacy proximal updates, FP16 fitting).

  1. Freeze everything but the cache. BF16 weights, greedy decoding, prompts, position IDs, explicit masks, padded batch shape; a two-request batch (target + companion a/b) runs twice with identical target input.
  2. Record update counts for every layer and every key/value compression call.
  3. Three-gate causal replay. Own counts must reproduce native output (recording is side-effect free); the other run’s counts must transfer its complete token/EOS sequence and raw + reconstructed cache fingerprints; both directions must pass.
  4. Frozen test set. 128 GSM8K + 64 HotpotQA targets × 2 fixed companions = 384 comparisons per model (Llama-3.1-8B-Instruct, Qwen3-8B); scorers frozen before generation.
  5. Repairs & extensions. Fixed 4/20-update budgets, request-local stopping, no-optimization, FP32 stopping test, six-seed padding+SDPA rebatching, and a 3-model Q/K/V weight-compression study.

Two 8B models × frozen 128 GSM8K + 64 HotpotQA targets with two fixed companions each.

  • Replay causality is airtight: all 170 changed pairs transfer the complete token sequence and raw/reconstructed cache fingerprints, in both directions.
  • Correctness impact is small and bidirectional: 8/246 resolved final-number flips (5 correct→wrong, 3 wrong→correct); the official GSM8K parser changes judgment in 16/256 pairs, no QA judgment changes.
  • FP32 stopping is not a fix: differing-count calls drop 10,543→3,171, yet 129/256 math pairs still change — including 23 whose initial caches were identical.
  • Cost is a wash: fixed-20 compression 6.22 ms vs native 6.35 ms vs no-opt 0.52 ms (geometric mean, 96 real KV tensors, RTX A6000); no HQQ configuration consistently beats BF16 on quality.
  • Natural rebatching boundary: under padding + SDPA, fixed-20 cuts text changes 54.9%→46.6% but BF16 still changes 36.1% — kernel/padding numerics dominate.
  • Generalizes to weight compression: joint vs separate Q/K/V changes math text 162/256 (Llama), 184/256 (Qwen), 208/256 (Mistral), with 7/3/7 confirmed correctness flips.

Strengths

  • Genuine causal identification: bidirectional count replay with full fingerprint and token transfer (170/170) is far stronger than the correlation-style rebatching studies common in this literature.
  • Pre-registration-style discipline: frozen scorers, prompts, and exact-match criteria; unresolved extraction cases retained; every adverse result printed in the main tables.
  • Practical, already-upstream repair: fixed iteration count needs no tuning, and its cost was measured on real tensors rather than asserted.
  • Honest boundary mapping: the paper itself shows stopping repairs do not fix padding/SDPA nondeterminism and that FP32 still leaves 129/256 math pairs changing.
  • Public artifact with executable audits: all 384 test-set records, 9,216 weight-study answers, and verification scripts.

Limitations

  • Two-request batches only: the frequency of companion-dependent stopping under realistic large-batch or continuous-batching serving is unknown, and results are tied to one pinned legacy optimizer revision.
  • Not a demonstrated quality loss: answer-correctness impact is small and bidirectional (8/246 resolved flips) — this is primarily a determinism and audit problem.
  • Questions reused across methods: no condition provides an independent accuracy measurement; the six-seed contrast is conditional (p = 0.03125 by exact enumeration), not population-level.
  • No throughput or memory conclusions: timings exclude generation latency and rolling recompression; the weight study runs a BF16-reconstructed model rather than int4 kernels.
  • Synthetic padding control cannot estimate a real serving failure rate.

Questions for further exploration

  1. How often do companion-dependent stopping decisions flip answers under realistic continuous batching with large, heterogeneous batches?
  2. Do maintained HQQ paths or TorchAO’s int4 runtime still contain a shared early-stop statistic, or is the pinned legacy optimizer superseded?
  3. Can a per-request stopping test keep iterative fitting’s benefit at fixed-budget cost, closing the 12.9 ms vs 7.8 ms synthetic-benchmark gap?
  4. Is adaptive stopping in quantization ever accuracy-positive, or pure variance — fixed budgets matched or beat native everywhere measured?
  5. How do stopping-level and padding/SDPA-level batch effects compose under natural rebatching — is a fully batch-invariant numerical stack the real prerequisite?
