Request Order Matters: Cache-History Sensitivity in Selective KV-Cache Reuse for Rolling Agents

Key metric · answer variation
69.0%→26.1%

Same prompt, five request orders, identical 5% recompute budget over 7,735 rolling updates: CacheBlend token top-k vs document-aligned spans. Same ~5.7× median TTFT speedup either way.

Why this matters

Long-running agents inherit cache state from every prior request; swapping token-level recomputation for contiguous spans removes that hidden confounder at zero latency cost.

同等 5% 重计算预算下，把 token top-k 换成连续 span 重计算，跨请求顺序的答案变化率从 69.0% 降到 26.1%。

Critical edge

Every headline number comes from one verbatim-copy task, one model, one 5% budget, one GPU — and document-aligned itself still falls to 54.3% fidelity under reversed order: robust, not immune.

01 Methodology

Setup. Qwen3-8B (greedy, temp 0) on LMCache 0.5.1 / vLLM 0.23.0 with prefix cache disabled — isolating the non-prefix, CacheBlend-style reuse path.

  • Rolling workload: an agent window of 84 documents built from 8,995 real records (7,515 Yahoo Finance prices, 792 FNSPID headlines, 688 SEC EDGAR titles); each call evicts the oldest doc and appends one new → 7,735 updates, ~7.2–7.7K-token prompts.
  • Deterministic task: verbatim field extraction, so answers compare exactly.
  • Sensitivity protocol: the identical sequence replayed in 5 orders (chronological, reversed, 3 fixed shuffles), cache retained across requests; metrics = answer variation (10 pairwise order comparisons) + fidelity to full prefill; 500-request cache-reset control.
  • Equal-budget ablation: five policies recompute exactly the same token counts (median 386–387/request; 188,562 vs 188,721 total), so only where tokens are recomputed differs.

  • Rerun check: an independent repeat of the chronological order reproduced every answer exactly — variation is order-driven, not run-to-run noise.
  • Not immune: document-aligned drops to 54.3% fidelity under the reversed-order stress test.

03 Strengths

  • New failure mode, well framed: persistent KV reuse makes serving a closed-loop system; request order is an uncontrolled confounder that CacheBlend / EPIC / KVLink never evaluated.
  • Impeccable hygiene: exact token-count matching across policies, deterministic greedy decoding with a reproduced identical run, cache-reset causal control, Wilson CIs, explicit p-values.
  • Memorable paradox: capturing 99.7% of KV deviation yields 38.6% fidelity, while 4.8% capture gains +50.8 points — a direct strike against deviation-ranked token selection.
  • Honest nulls: no chronological-order advantage, no added value from boundaries or ranking, and “robust but not immune” stated plainly.
  • Real provenance: 8,995 actual market/news/filing records driving a deterministic 7,735-update stream, with ~5.7× TTFT measured end-to-end.

04 Limitations

  • Narrow envelope: one model (Qwen3-8B), one verbatim-extraction task, one domain (U.S. equities), one 5% ratio, one NVIDIA L4 — generality untested; higher budgets (10–20%) where top-k might self-repair are never tried.
  • Residual risk: 54.3% fidelity under reversed order and 26.1% answer variation (~1 in 4) may still be unacceptable for reproducibility-critical agents (monitoring, audits).
  • Framing oversells: the ablation shows the real finding is “recompute contiguous spans”; document alignment is a convenient instantiation, not the mechanism.
  • Thin ablation scope: 500 requests under 2 of 5 orders; no sensitivity to window size, prompt length, or arrival patterns; no mechanism-level account of why contiguity repairs cross-chunk attention.
  • Proxy metric, no artifacts: fidelity to full prefill is a proxy — downstream agent quality is never measured; no code/data release mentioned; version-pinned LMCache/vLLM stack.

05 Questions for further exploration

  • Does the token-top-k collapse vanish at 10–20% budgets — is there a budget–contiguity trade-off curve per workload?
  • Does the effect transfer to generative agent tasks (tool-calling, planning), and how should “fidelity” be defined there?
  • Why does contiguous recomputation repair cross-chunk attention — is damage concentrated at attention sinks near document starts (as EPIC / LegoLink suggest)?
  • Can schedulers make cache history part of the API — pinning request-to-cache-state assignments, or exposing cache lineage for reproducibility?
  • Would training-time interventions (reused-chunk noise fine-tuning) combined with span-level recomputation close the remaining gap to full prefill?
