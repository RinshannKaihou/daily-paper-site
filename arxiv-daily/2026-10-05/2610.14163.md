# AutoEnvScaling: Automating the Data Flywheel with Terminal Agents

> **一句话总结：** 把"设计 RL 训练环境"本身变成一个 terminal 任务——让 proposer agent 在沙箱里读取 solver 的历史 rollout、自主构建/验证/校准 Harbor 训练环境，8 个前沿模型平均有效环境率从 Prompt 的 39% 提到 86%（DeepSeek-V4-Flash 从 3.5% 到 89.0%，约 25 倍），用生成环境训 Qwen3.5-35B-A3B 在 Terminal-Bench 2.1 上比匹配的静态 Tmax 池高 +4.3 点，而单个模型身兼 proposer+solver 的递归自改进运行将 Terminal-Bench 2.1 从 41.1 提升到 53.3（+12.2）。

> **TL;DR:** AutoEnvScaling treats RL environment design as a terminal task: a proposer agent works in a sandbox with solver rollouts, builds complete Harbor environments (instruction + execution env + reference solution + tests), and is validated (reference passes, empty solution fails, 13-gram contamination check) and calibrated (mean reward 0.25–0.75 against the current solver) before entering the training pool. Compared to prompt-only generation across 8 frontier proposers, the valid-environment rate rises from 39% to 86% on average (DeepSeek-V4-Flash: 3.5% → 89.0%, ~25x) at up to 75% lower cost per valid environment for 6 of 8 models. RL on these environments lifts Qwen3.5-35B-A3B by +4.3 points on Terminal-Bench 2.1 over the matched static Tmax pool (38.9 vs 34.6), and a single Qwen3.6-35B-A3B policy acting as both proposer and solver gains +12.2 on Terminal-Bench 2.1 (41.1 → 53.3, +6.1 over static Tmax) and raises Terminal-Bench 4.0 from 1.6 to 3.2 — a demonstration of recursive self-improvement where the environment builder co-evolves with the solver.

## 核心贡献

- **把环境设计变成 terminal 任务**：proposer 不再走固定的生成流水线，而是像人类研究员一样在沙箱中读 solver 的失败/成功 rollout、写代码、起子容器、跑测试，端到端地产出完整 Harbor 环境（instruction.md、environment/、solution/、tests/），决定"建什么、何时建、何时算完成"。
- **solver 引导的数据飞轮**：每个 episode 的 assignment 是训练池中的父环境及其 pass rate 和最常见失败，proposer 据此构建更简单（solver 一直失败）或更难（solver 已能稳定通过）的变体；环境只有通过验证+校准（对当前 solver 平均奖励落在 0.25–0.75）才能入池，训练池随 solver 进步而演化。
- **统一奖励与共训（DPPO）**：solver 奖励 = 测试通过率（式 1），proposer 奖励 = {−1 验证失败, −0.25 校准失败, +1 双过}（式 2）；开权重的模型用同一策略扮演两个角色，分组分别中心化计算优势，proposer 还可通过 harness 优化（memory/skills/工具，闭源模型可用）或权重训练跨轮提升。
- **递归自改进（RSI）演示**：单一 Qwen3.6-35B-A3B 策略既当 proposer 又当 solver，从同一 Cold-Start 检查点出发，Terminal-Bench 2.1 升 12.2 点、Terminal-Bench 4.0 从 1.6 升到 3.2；去掉 proposer 侧训练（只保留权重共享）会先升后崩。
- **跨域可行性验证**：同一流水线在 7 个域（terminal、软件工程、工具调用、浏览器、computer use、GPU kernel、专业工作流）接受 1,489 次生成中的 1,061 次（71.3%）。

## Key Contributions

- A framework that turns environment design into a terminal task: the proposer agent inspects solver rollouts, builds and tests environments end-to-end inside a sandbox (workspace, child containers, web access, Harbor `create-task` protocol), rather than following a pre-fixed generation pipeline.
- A solver-guided data flywheel for terminal RL: every new environment is validated (reference solution gets full reward, empty solution fails, 13-gram contamination check) and calibrated (mean reward in 0.25–0.75 on the current solver) before admission, so the training pool tracks what the solver can and cannot do; proposer improvement can come from harness optimization alone (closed weights) or from weight training (DPPO with role-specific group-centered advantages).
- A demonstration of recursive self-improvement with a single policy: one Qwen3.6-35B-A3B checkpoint is both proposer and solver, trained on both rewards, and its own updated rollouts seed the next environment-generation round — with an ablation showing that removing proposer training collapses the loop.
- Breadth of evidence: 8 frontier proposers for generation quality, 2 solver scales (Qwen3.5-9B / 35B-A3B) with 2 external proposers, a self-play RSI run, a HiL-Bench study on teaching agents when to ask for help, and a 7-domain cross-domain feasibility study.

## Methodology

**Environment design as a terminal task.** The proposer works in a sandbox containing (i) the solver's past rollouts with verifier outputs, (ii) previously generated environments, (iii) the proposer's own memory and tools (persistent across rounds; rollouts/environments refresh each round), and (iv) restricted web access (egress blocks Terminal-Bench pages). Each episode starts from an assignment naming a parent environment plus the solver's pass rate and most common failure; the proposer builds simpler variants where the solver keeps failing and harder ones (longer horizon, extra skills) where it succeeds. Design is end-to-end: it writes the environment's files, launches child containers to build the image, runs the reference solution and tests, and revises until Harbor's oracle check passes; it may also run the current solver on a draft to estimate difficulty.

**Validation and calibration.** The host builds the environment and runs tests on the proposer's reference solution (must get full reward) and an empty solution (must get less than half); instructions sharing a 13-gram with a held-out task are flagged for contamination (following Tmax). Because both checks can be gamed by shared code between reference and tests, a `harbor_check` runs the proposer's model against the official Terminal-Bench rubric. Calibration keeps environments only if mean reward on the current solver falls in 0.25–0.75, so the solver sometimes solves and sometimes fails. Reward design: solver gets the fraction of tests passed (Eq. 1); proposer gets −1 if validation fails, −0.25 if validation passes but calibration fails, +1 if both pass (Eq. 2).

**Training the proposer and solver.** Both roles act in a terminal with the same trajectory interface. When the proposer has open weights, one policy plays both roles and is trained with DPPO (group size 16, 16 prompts per batch, max sequence length 128k), with proposer advantages centered within proposer groups and solver rewards centered across attempts on the same environment (following self-play practice), dropping groups with no reward variance (DAPO-style). The solver trains every step; every k solver steps the proposer generates new environments and trains on those trajectories. The proposer also performs harness optimization (per Continual Harness): it merged validation steps into faster scripts and cached useful GitHub/Docker Hub images as a web-cache skill.

**Experimental design.** (1) Generation-quality study: Prompt vs Prompt+Env Feedback (build-verify-revise loop, following RST/Environment Evolution) vs AutoEnvScaling across 8 frontier proposers; valid = builds, reference passes, empty fails. (2) Curriculum study: Qwen3.5-9B and Qwen3.5-35B-A3B trained with GPT-5.6-sol or Claude Opus 5 as fixed-weight proposers; the Tmax baseline pool is *regenerated with the same proposers* for a matched comparison; evaluation is avg@5 on held-out Terminal-Bench 2.1. (3) RSI study: Qwen3.6-35B-A3B as both roles; the base model only produces valid environments 32.3% of the time, so it is cold-started on 600 high-quality proposer trajectories (raising the valid rate to 86.8%) before the co-evolution loop. (4) Behavior study: training on 500 AutoEnvScaling-generated software-engineering tasks with underspecified instructions and withheld details behind an `ask_human` tool, evaluated on held-out HiL-Bench.

## Results & Highlights

- **Valid-environment rate (8 frontier proposers, Fig. 4/Table 2):** mean valid rate is 86% for AutoEnvScaling vs 39% for Prompt and 57% for Prompt+Env Feedback; the largest gain is DeepSeek-V4-Flash, 3.5% with Prompt → 89.0% with AutoEnvScaling (~25x). Within the GPT-5.6 family, prompt-based rates degrade from 92 (terra) to 17% (Luna) as capability drops while AutoEnvScaling stays at 84–92%. Cost per valid environment drops for 6 of 8 models (paper headline: up to 75% lower), e.g. GPT-5.6-sol $0.90 (Prompt) → $0.50 (AutoEnvScaling, 1.8x lower) and DeepSeek-V4-Flash $0.08 → $0.03.
- **Generated environments are richer and harder (Fig. 5):** vs Prompt+Env Feedback, AutoEnvScaling environments average 20.4 data files vs 3.5 (5.8x), solver trajectories of 47.2 turns vs 33.8 (1.4x), and solver pass rate drops from 61.0% to 51.0% (1.3x harder).
- **Curriculum beats static pools (Table 3, held-out Terminal-Bench 2.1, avg@5):** Qwen3.5-9B: base 19.1; Tmax 27.2±1.4 (GPT-5.6-sol) / 29.2±2.1 (Claude Opus 5); AutoEnvScaling 33.5±1.9 / 36.6±1.7 — +6.3 and +7.4 over the matched static pools. Qwen3.5-35B-A3B: base 26.1; Tmax 34.6±1.9 / 35.5±1.6; AutoEnvScaling 38.9±2.4 / 39.3±1.6 — +4.3 and +3.8. Removing past solver trajectories from the proposer's workspace drops the 35B-A3B score by 3.6 points (GPT-5.6-sol) and 6.7 points (Claude Opus 5), leaving it 0.7 above and 2.9 below Tmax respectively — solver feedback is the active ingredient.
- **Recursive self-improvement (Fig. 6):** Qwen3.6-35B-A3B as both proposer and solver rises from the 41.1 Cold-Start checkpoint to 53.3 on Terminal-Bench 2.1 (+12.2; +6.1 over static Tmax at 47.7) over 300 RL steps, and lifts Terminal-Bench 4.0 from 1.6 to 3.2 while Tmax stays at 1.4. Training dynamics (Fig. 7): 3.1x higher usable-group rate than Tmax and 42% less rollout-collection time per training step. The no-proposer-training ablation (weights shared, proposer side untrained) improves at first, then collapses as environment validation errors accumulate.
- **Teaching when to ask for help (HiL-Bench, Table 5):** training Qwen3.6-35B-A3B on 500 generated software-engineering tasks reaches 33.9% task success and 55.3 Ask-F1 on held-out tasks, vs 6.8% / 29.6 when RL uses the 100 official tasks; both beat the best frontier model in this setting (Claude Opus 5: 7.5% success, 14.4 Ask-F1). Cold start alone raises the ask rate from 1.8% to 71.4% but only 10.1 Ask-F1 — most gain comes from asking better questions.
- **Cross-domain feasibility (Appendix C, Table 8):** 1,061 of 1,489 completed generation runs accepted (71.3%) across seven domains; terminal and software engineering reach 100% acceptance for GPT-6-astra/GPT-5.6-sol, while browser use (26.2% for Claude Opus 5), computer use (40.3% GPT-6-astra) and professional workflows (33.3% GPT-6-astra) vary widely by agent.

## Critical Assessment

**The strongest evidence is the matched-baseline design, but the RSI headline is a cold-start delta.** The curriculum comparison is unusually careful: they regenerate the Tmax pool with the *same* proposers instead of citing the original Tmax numbers, and Table 3 reports confidence intervals. However, the abstract's "+12.2 on Terminal-Bench 2.1" is measured against the paper's own Cold-Start checkpoint (41.1 → 53.3); against the matched static Tmax baseline the gain is +6.1 — real, but half the headline. The Cold-Start itself is produced by fine-tuning on 600 high-quality proposer trajectories (and the HiL-Bench run uses 75 Claude Opus 5 trajectories), so the "self-improvement" loop is bootstrapped by frontier-model data, not started from zero self-generated capability — the base model alone manages only a 32.3% valid-environment rate.

**Validation is self-referential in exactly the place that matters.** The admission checks (reference passes, empty solution fails) are the standard but weak pair the authors themselves note misses incorrect solutions or rejects valid ones; the escalation path, `harbor_check`, has *the proposer's own model* review the task against the rubric — the same model that wrote the task reviews whether its task is sound, so systematic self-consistent errors (tests that only exercise the reference's shortcuts, per the paper's own example) can pass all gates. Calibration to the current solver (0.25–0.75 band) is a good curriculum idea but also means "1.3x harder" (pass rate 61.0% → 51.0%) is partly by construction, not an independent quality measure.

**The cost story cuts both ways.** The "up to 75% lower cost per valid environment" applies to six of eight models; for the two strongest proposers, cost per valid environment *rises* (Claude Opus 5: $0.72 with Prompt vs $1.18 with AutoEnvScaling; GPT-5-astra: $1.79 vs $2.73), because frontier models already have high valid rates under prompting and the sandbox overhead is not recouped. The cost win is concentrated in weaker proposers — which is precisely where the valid-rate win is also concentrated, so the two headline numbers come from overlapping, mostly low-capability models (DeepSeek-V4-Flash drives the 25x).

**Scope of downstream claims.** RL training gains are demonstrated only in the terminal domain (Terminal-Bench) plus one behavior study; the 7-domain study (71.3% accepted) establishes only technical admission — builds, reference passes, do-nothing fails — which the authors explicitly say "confirm feasibility under executable checks, not task quality under independent review." The RSI evidence is a single run (no seed variance reported), gains are shown over ~300 RL steps, and Terminal-Bench 4.0 remains near-floor even after training (3.2, from 1.6). To the authors' credit, Appendix A.1 states all of these limitations candidly.

## Strengths

- Clean conceptual contribution: unifying environment design and solving as terminal tasks lets one policy improve both, and the harness-optimization path means even closed-weight frontier models (GPT-5.6, Claude Opus 5) can act as improving proposers.
- The assignment-from-failures mechanism is a concrete, inspectable curriculum signal: environments are built from what the current solver actually fails at, and the Table 3 ablation (−3.6/−6.7 points without solver feedback) shows it is load-bearing.
- Matched comparisons throughout: regenerated Tmax pools with identical proposers, same Cold-Start checkpoint for the RSI run, CI intervals on the main tables.
- Honest failure analysis: the no-proposer-training collapse (Fig. 6/20) is reported as evidence for the proposer reward r_P rather than hidden, and the limitations section (A.1) explicitly disclaims long-run RSI and correctness guarantees.
- Breadth: 8 proposers, 2 solver scales, 2 external proposers, 7 domains, plus a qualitative protocol study (Fig. 8) showing three different proposers designing environments from the same solver failure.

## Limitations

- Environment correctness is not guaranteed: reference/do-nothing checks cover a small part of agent behavior, generated tests can miss wrong solutions or reject valid ones, and the fallback reviewer is the proposer's own model — no independent verifier, human audit, or measurement of environment error rates after admission.
- Downstream RL gains are shown only for the terminal domain and one HiL-Bench behavior study; cross-domain results are admission-only, and the authors state this.
- The RSI result is one run of one model (Qwen3.6-35B-A3B) at ~300 steps with no seed replication; whether gains continue with longer training is unestablished, and Terminal-Bench 4.0 performance stays very low.
- Heavy frontier-model bootstrap: cold start needs 600 curated proposer trajectories (valid rate 32.3% → 86.8%), and cost per valid environment actually increases for the strongest proposers.
- Compute footprint is substantial (DPPO with 128k-token sequences, group size 16, repeated sandbox-based environment building), and the pipeline is currently specific to the Harbor task format.

## Relevance

这篇工作直接命中当前 agent RL 的核心瓶颈——训练环境供给，把"造环境"交给 agent 自己完成并与 solver 共同进化，与你关注的 LLM 自改进/递归自改进主线高度相关；其 matched-baseline 实验设计和"没有 proposer 训练就崩"的消融也值得在评估任何 self-improvement loop 时借鉴。

## Questions for Further Exploration

- How would an *independent* verifier (a different model family, or held-out human review) score the accepted environments — what fraction of calibrated, admitted environments are actually wrong or reward-hackable, and does training on them produce Reward hacking artifacts?
- Does the RSI loop survive multiple seeds and longer horizons (beyond 300 steps), and does the Terminal-Bench 4.0 score continue rising or plateau at the current near-floor level?
- Can the loop start from a checkpoint *without* the 600-trajectory frontier cold start, e.g., via self-play from the raw 32.3% valid-rate base model, or is the frontier bootstrap essential?
- Since calibrated "hardness" is defined relative to the current solver, does the environment pool drift toward tasks at the solver's frontier while neglecting long-horizon diversity — and would cross-domain joint training (the paper's own future-work item) resolve or worsen this?
- For closed-weight proposers, how much of the gain comes from harness optimization (scripts, cached images, memory) versus simply having a terminal sandbox — is there an ablation isolating the harness components?
