Diagnostic loop for LLM-generated numerical code

RIDGE lets LLM-generated pricing code diagnose itself against no-arbitrage rules, then pivot method entirely when Monte Carlo can't scale.

RIDGE: An Autonomous Framework for Validation and Method Discovery in LLM-Generated Option Pricing ↗
Cheng, Cheng, Liu, Oosterlee · 2026-07-28 · arXiv:2607.25199 ·
LLM code generation quant finance option pricing stochastic volatility autonomous validation
Key Metric
~1010
Monte Carlo paths needed to hit the 10−5 implied-vol target on Heston–Hull–White — computationally infeasible, which is exactly what pushed RIDGE's diagnosis to swap Monte Carlo for a new semi-analytic PDE method (final score 118/120).
Why This Matters
Demonstrates that an automated validation loop can drive real methodology discovery, not just bug-fixing — a blueprint for trustworthy LLM-generated scientific code.
Critical Edge
The 100–120-point diagnostic scores are heuristic and self-assigned by the very same LLM performing the diagnosis — not an independently verified accuracy metric.

REPOSITORY

generation operator ΦR revises  ⇽  validation operator VR = ΓR ∘ μR measures + diagnoses, repository R grows each iteration

RIDGE treats validation as a closed loop, not a one-shot unit test. Each iteration carries a triple — blueprint, code implementation, and a growing repository of diagnostic knowledge — through the pipeline above, halting once residuals fall below tolerance. Findings are classified into six categories: [BUG], [CONSISTENCY], [METHOD-ALGO], [METHOD-HYPER], [METHOD-CHOICE], or [EXPECTED]. That last pair of tags is the mechanism that matters most: [METHOD-CHOICE] lets the framework recognize a persistent residual as a methodological dead end rather than a bug worth another patch — which is precisely what triggers the Monte Carlo → conditional characteristic-function PDE (CCF-PDE) pivot for the two non-affine models (HHW, G-SVJD), derived via conditioning on the variance path and the Feynman–Kac theorem. [EXPECTED] lets it stop chasing residuals that have a theoretical explanation instead of over-tuning forever.

Strengths

  • Clear operator-theoretic formalization, with an explicit implementation-error vs. scheme-error decomposition.
  • A diagnostic taxonomy that separates "the code is wrong" from "the method is unsuitable," and demonstrates both occurring in practice.
  • HHW/G-SVJD case studies are a strong existence proof that validation feedback can drive representation-level method change, not just parameter tuning.
  • Validation-operator ablation plus cross-generator tests (DeepSeek, ChatGPT) isolate the loop's own contribution from any one LLM's capability.
  • Repository knowledge visibly transfers across model families — Bates needs only 5 iterations against Heston's 10.

Limitations

  • Diagnostic scores are heuristic and self-assigned by the same LLM doing the diagnosing — the authors themselves say these are not validation criteria.
  • Scope is confined to Fourier/COS-based option pricing; no evidence the framework transfers to other scientific-computing domains.
  • The convergence proof (Proposition 1) is asymptotic and rests on drift assumptions unverified for any real LLM generator.
  • Only frontier-tier LLMs were tested (Claude Opus 4.8, DeepSeek-v4-pro, ChatGPT gpt-5.5) — no experiment with a weaker/smaller model.
  • No comparison against simpler non-LLM baselines (property-based or metamorphic testing) that might catch the same violations more cheaply.

Questions for Further Exploration

  • Would RIDGE's iteration trajectory hold up with a weaker/smaller LLM as generator, or does it implicitly rely on frontier-level reasoning to interpret diagnostic reports?
  • How sensitive is the [METHOD-CHOICE] pivot (MC → CCF-PDE) to the exact wording of the repository entry that triggers it?
  • Can the heuristic 20-point-per-category scoring be replaced or validated against an objective, model-independent accuracy metric?
  • How would RIDGE behave on model classes with no reference values, degeneration limits, or affine approximations at all for Block III to anchor against?
  • Does the repository's accumulated expertise generalize beyond the COS/Fourier paradigm — to finite-difference solvers, tree methods, or ML-based pricing surrogates?
