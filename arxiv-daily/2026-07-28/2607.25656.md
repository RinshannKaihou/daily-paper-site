> **一句话总结：** OrchBench 把"编排质量"从"多智能体真实执行"中剥离出来评测：给定语义化生成的任务依赖 DAG、上下文长度限制和智能体预算，只要求被测模型输出一份编排计划（任务分配+跨智能体信息转移/保留比例），再用一个确定性模拟器（而非真实调用工作智能体）打分，在 MultiAgentBench 上与 Claude Code 真实执行质量的 Pearson 相关系数达 r=0.816，但只需真实执行 1.3% 的 token 和 10.3% 的时间；论文进一步发现，随着任务规模从 10 扩到 1000，编排质量瓶颈主要来自"跨智能体信息转移覆盖率"下降（如 500→1000 任务时 Claude 的转移覆盖率从 0.981 骤降到 0.441），而非智能体数量不足——增加智能体数量的收益迅速饱和。

> **TL;DR:** OrchBench isolates orchestration-plan quality from worker execution: given a semantically generated task DAG (10 to 1,000 subtasks), a per-agent context limit, and an agent budget, a planner model only outputs an orchestration plan (task assignment + cross-agent information transfer/retention ratios), which a deterministic simulator scores for quality, makespan-efficiency, and token-efficiency without invoking any worker LLM. Across nine planners (GLM-5.1, DeepSeek-V4-Pro/Flash, Qwen3.6-35B-A3B, Kimi-K2.6, Doubao-Seed-2.0-Mini, plus frontier models Gemini-3.1-Pro-Preview, Claude-Opus-4.8, GPT-5.5) evaluated on MultiAgentBench-derived DAGs, the simulated final score correlates with real Claude Code execution quality at Pearson r=0.816 (p=0.047) while costing only 1.3% of the tokens and 10.3% of the wall-clock time (up to 74x/9.7x token/time reduction on MultiAgentBench, 389x/110x on WideSearch). The headline finding: agent count is nearly uncorrelated with quality at large scale (Pearson −0.021 at n=100 tasks) while cross-agent transfer coverage remains strongly predictive (0.614–0.952 across scales) — coordination failures, not agent scarcity, are the dominant bottleneck as workflows grow (transfer coverage falls from 0.981 to 0.441/0.398 for Claude/DeepSeek between 500 and 1,000-task DAGs).

## 核心贡献

- 将"多智能体编排评测"形式化为一个独立于工作智能体执行的标准化问题：把任务分解与依赖结构（DAG）视为固定输入，被测规划器只需产出编排计划 π=(α, R)（子任务到智能体的分配 α，以及跨智能体信息转移与保留比例 R），从而把编排质量与执行者能力、工具可靠性、环境噪声解耦。
- 构建 OrchBench：一个可扩展的基准，从真实种子任务（Finance Agent、DS-1000、Qasper、BIRD-SQL）出发，通过"生成器-双裁判-修订器"循环构造语义合理、结构可控（10 到 1,000+ 子任务、可调并行度 k99/n）的依赖 DAG，并配套一个确定性模拟器：模拟器复现依赖解析、智能体调度、上下文获取/压缩、子任务执行、状态更新六阶段生命周期，输出质量、makespan、token 消耗等可解释指标，且不再调用规划器模型本身。
- 系统研究了从 10 到 1,000 子任务规模下六个基座模型 + 三个前沿模型产生的编排策略，揭示了此前被端到端评测掩盖的"协调瓶颈"：保持任务关键信息的完整传递比单纯增加智能体数量更重要；随着任务规模增长，并行带来的收益被协调失败逐渐抵消。同时通过模拟-真实相关性验证（r=0.816）、跨框架鲁棒性（Claude Code/SWE-mini/OpenHands/Crush）、留一模型交叉验证等多组实验证明模拟器忠实反映真实编排质量。

## Key Contributions

- **Reframing orchestration evaluation as execution-independent.** OrchBench treats task decomposition/dependency structure (a DAG) as a fixed input and asks the planner to output only an orchestration plan π=(α, R) — subtask-to-agent assignment α and cross-agent information-transfer/retention ratios R — decoupling orchestration quality from worker reasoning, tool execution, and environmental noise.
- **A scalable, semantically-grounded DAG benchmark + deterministic simulator.** DAGs (10 to 1,000+ subtasks, controllable parallelism k99/n) are built from real seed tasks (Finance Agent, DS-1000, Qasper, BIRD-SQL) via a generator/dual-judge/refiner loop; a six-stage simulator (dependency resolution, agent scheduling, context acquisition, context management/compression, subtask execution, state update) deterministically scores any plan without re-invoking the planner or any worker LLM.
- **A systematic study across 9 planners and scales from 10 to 1,000 subtasks** showing that (a) preserving task-critical information across agents matters more than raw agent count, and (b) parallelism benefits diminish and eventually reverse as coordination failures (missing information transfers) accumulate at scale — a bottleneck invisible to conventional end-to-end MAS evaluation.
- **Extensive validation that the simulator tracks real execution:** structural- and outcome-level correlations against real Claude Code runs on MultiAgentBench (Pearson r=0.816 on final score), cross-framework robustness (Claude Code, SWE-mini, OpenHands, Crush), and leave-one-model-out stability checks — while requiring only ~1.3% of tokens and ~10.3% of wall-clock time versus full execution.
- **Downstream applications enabled by cheap simulation:** task-conditioned model selection (ranking candidate models per task before running them), model-ranking under limited real-execution budgets (prioritizing tasks with high cross-model disagreement), task-difficulty estimation from structural DAG features, and simulator-guided workflow refinement that measurably improves real execution scores.

## Methodology

**Problem formulation.** Given a raw-task pool, OrchBench first converts a seed task into a DAG G=(V,E) with a per-agent context limit L; each node v is a subtask with input/execution/output token budgets, a time budget, and a compression-sensitivity class (robust/balanced/fragile). Given G, L, and a max agent budget A_max, the tested planner F_θ outputs a JSON `workflow_script` (agent pools, task-matching rules, transfer rules) which a deterministic interpreter expands into a concrete plan π=(α,R): α assigns each subtask to one of ≤A_max agents; for a cross-agent dependency edge, R(u,v)=e∈(0,1] specifies the retention ratio of information carried from parent u to child v. Declared transfers that don't correspond to a real edge are invalid; required transfers the plan omits are recorded as "missing transfers."

**DAG construction.** A seed judge filters raw tasks for DAG-suitability; a generator builds an initial DAG toward a target subtask count n and a target natural-parallelism level k99/n, where k99(G) = min{k : ms_k(G) ≤ C(G) + 0.01(W(G) − C(G))} (fewest workers needed to reach 99% of the max possible makespan reduction, with W = total work, C = critical-path time). A structural judge and a semantic judge iteratively check format/validity and semantic faithfulness/parallelism-match respectively, feeding repair advice back to the refiner until both accept (Algorithm 2, bounded by a retry budget K). DAG-level rejection rate is 34.3% (24/70 sampled DAGs failed at least one judge check; Table 14 lists 6 representative failure modes such as "redundant verification/templates" at 9.6% frequency and "artificial global synchronization" at 5.0%).

**Deterministic simulator (Algorithm 1).** The simulator processes subtasks in topological order. For each subtask v, its agent waits for all parents and agent availability (Eq. 1). Same-agent dependencies reuse results with no cost; cross-agent dependencies apply the declared retention ratio e and record communication tokens and retained quality; missing declared transfers multiply the upstream contribution's quality by a penalty factor λ (default λ=0.5, swept in Appendix F-III). Context management compresses an agent's stored memory when it exceeds L, using per-item compression-sensitivity classes (Eq. 2–3). After execution, the simulator reports macro-averaged terminal-task quality Q, a makespan-efficiency term E_time = min{1, C/M}, and a token-efficiency term E_token = min{1, T_single/T} (T_single = single-agent serial-execution token cost). The final orchestration **Score = (Q + E_time + E_token)/3** (Eq. 7).

**Experimental setup.** Problem pool built from Finance Agent, DS-1000, Qasper, and BIRD-SQL; 240 task DAGs generated for main experiments (n∈{10,20,50,100}); MultiAgentBench used specifically for simulation-to-real correlation studies with larger DAGs (n∈{200,500,1000}). Six validation models (GLM-5.1, DeepSeek-V4-Pro, DeepSeek-V4-Flash, Qwen3.6-35B-A3B, Kimi-K2.6, Doubao-Seed-2.0-Mini) plus three frontier models (Gemini-3.1-Pro-Preview, Claude-Opus-4.8, GPT-5.5) are evaluated. Default hyperparameters: A_max=100, λ=0.5 (Appendix F-III), decoding temperature 0.1, 16,000-token completion cap, one primary planning call plus one repair call on invalid output.

## Results & Highlights

- **Simulation-to-real correlation (main claim).** On MultiAgentBench vs. real Claude Code dynamic-workflow execution, the simulated **final score correlates with real task quality at Pearson r=0.816 (p=0.047), Spearman ρ=0.771 (p=0.103)** (Table 2), while real time and token consumption are much more weakly/negatively correlated (Pearson r=−0.264 for time, r=−0.607 for token usage), meaning the simulator's efficiency proxies do not directly track real resource use — only the aggregate quality-weighted score does.
- **Efficiency gain vs. full execution.** Simulation uses only **1.3% of the tokens and 10.3% of the wall-clock time** of real execution on the validation set (abstract); Table 8 reports concrete per-task averages: on WideSearch, real execution uses 17.35M tokens / 56.13 minutes vs. 44.61K tokens / 0.51 minutes for OrchBench (≈389x token, ≈110x time reduction); on MultiAgentBench, 383.09K tokens / 5.61 minutes (real) vs. 5.16K tokens / 0.58 minutes (simulated) — a ≈74x token, ≈9.7x time reduction.
- **Agent count vs. transfer coverage (key scientific finding, Table 5).** Pearson correlation between declared agent count and quality (Agents–Q) drops from 0.468 at n=10 to **−0.021 at n=100 tasks** — agent count becomes essentially uninformative about quality at scale — whereas Coverage–Q (successful cross-agent transfers vs. quality) stays consistently informative, 0.614–0.952 across all scales.
- **Extreme-scale coordination collapse (Figure 5, n∈{200,500,1000}, A_max=100).** Between 500 and 1,000-task DAGs, cross-agent **transfer coverage falls from 0.981 to 0.441 for Claude-Opus-4.8 and from 0.981 to 0.398 for DeepSeek-V4-Flash**, producing 872.3 and 907.4 missing transfers respectively; only Gemini-3.1-Pro-Preview retains near-complete coverage and substantially higher quality at 1,000 tasks.
- **Diminishing returns from more agents (Figure 4).** Sweeping the requested max-agent cap A_max from 1 to 64 (averaged across 6 base planners, 50 DAGs): more than doubling agent count from A_max=16 to A_max=64 leaves the aggregate score nearly unchanged, while quality plateaus around ~0.75–0.8.
- **Main results table across scales (Table 4).** No single model wins at every scale: **GPT-5.5 leads at n=10 (Score=0.810)**, **GLM-5.1 leads at n=20 (0.746)**, **Claude-Opus-4.8 leads at n=50 (0.644)**, **Gemini-3.1-Pro-Preview leads at n=100 (0.573)**; the missing-transfer count range widens dramatically with scale, from [0.00, 0.43] at n=10 to [0.07, 22.70] at n=100.
- **Single- vs multi-agent tradeoff (Table 6, Table 19).** Under a tight context limit L=16k, multi-agent orchestration improves quality by +0.302 over a single agent (0.423→0.725) and final score by +0.115 (0.535→0.650); this advantage nearly vanishes at L=128k (+0.007 quality, final scores 0.682 vs 0.693) — multi-agent orchestration mainly helps when working state exceeds a single context window.
- **Cost-efficient model/task selection (Table 7, Table 11).** Ranking tasks by cross-model simulated-score disagreement and real-executing only the top-5-disagreement tasks achieves Spearman ρ=0.754 and pairwise ranking accuracy 0.800, vs. ρ=0.176/accuracy 0.613 for random task selection. For task-conditioned model selection on MultiAgentBench, OrchBench's Top-1 coverage is 61.5% overall (vs. 38.6% for a historical-best baseline) and 50.0% on coding tasks (vs. 28.6%).
- **Simulator-guided refinement improves real execution (Table 9).** Adding one simulator-selected cross-role handoff to a baseline MultiAgentBench workflow (DeepSeek-V4-Flash executor, DeepSeek-V4-Pro evaluator, 20 tasks) raises simulated quality from 0.1452 to 0.5111 and the mean **real-execution score from 3.754 to 4.150 (out of 5)**.
- **Ablation validates the transfer/compression mechanisms' discriminative power (Table 10).** Comparing Gemini-3.1-Pro-Preview (strong planner) vs. Doubao-Seed-2.0-Mini (weak planner): under the full benchmark, ΔQuality=0.247 and ΔScore=0.079; removing the missing-transfer penalty shrinks these gaps to ΔQ=0.011/ΔScore=0.001; auto-completing omitted transfers plus lossless compression collapses the gap almost entirely (ΔQ=−0.001, ΔScore=0.008, both models reaching Q≈0.933) — confirming that transfer-coverage and compression penalties are what let the benchmark distinguish strong from weak orchestration.

## Critical Assessment

**Novelty:** The core idea — evaluate orchestration plans via a deterministic simulator rather than executing the full MAS — is a genuinely useful decomposition that existing benchmarks (MASBENCH, PerspectiveGap, OrchRM, WorFBench) only partially address; those either mix orchestration with execution quality or only test structural correctness without simulating post-assignment execution consequences. This is a real methodological contribution, not just a new dataset.

**Rigor — but the headline correlation is fragile.** The paper's own leave-one-model-out analysis (Table 3) is a red flag worth flagging explicitly: the headline Pearson r=0.816 (p=0.047, barely significant) is computed over just six models, and **removing a single model (GLM-5.1) drops the correlation to r=0.421 with p=0.500 — statistically indistinguishable from no correlation.** Other single-model removals swing r between 0.677 and 0.949. A correlation claim that is this sensitive to one data point out of six should be read with real caution, even though the paper reports it transparently rather than hiding it.

**Cross-framework generalization is uneven.** Figure 3 shows OrchBench correlates well with Claude Code (Pearson 0.82) and SWE-mini (0.73) but much more weakly with OpenHands (0.63 Pearson, and the OpenHands-vs-Claude-Code cross-check is only 0.09/0.27), suggesting the simulator's fidelity is not uniform across execution frameworks and may be tuned closer to the Claude Code/MultiAgentBench setting used for its main validation.

**Real time/token metrics don't transfer.** The paper itself states (and Table 13 confirms) that simulated time and token consumption "cannot be reliably predicted" across frameworks — cross-framework time correlation is essentially zero (Pearson −0.104) — so only the composite quality-weighted final score, not the individual efficiency sub-metrics, should be treated as validated against reality.

**DAG-generation quality is imperfect and this is honestly reported.** A 34.3% DAG rejection rate and named failure modes (e.g., "redundant verification or repeated templates" at 9.6% frequency, "artificial over-decomposition" at 6.3%) show that even the accepted DAG pool contains some proportion of semantically un-natural structures, particularly at larger scale — Table 16 shows redundancy and dependency-correctness rule-based scores dip noticeably at n=500 (e.g., redundancy 57.50 vs. ~90+ at smaller n).

**Missing-transfer factor λ=0.5 is a hand-tuned hyperparameter** whose value directly controls how much model separation the benchmark exhibits (Table 20: λ=1 nearly erases the Gemini-Doubao quality gap to 0.011, λ=0 gives a large but noisy gap); the choice of λ=0.5 as "a balanced default" is a defensible but ultimately subjective design decision that shapes the benchmark's discriminative power.

**The real-world-improvement evidence (Table 17) is thin.** The claim that providing a generated DAG improves actual agent-run accuracy relies on just 10 real tasks, moving accuracy from 2/10 (20%) to 3/10 (30%) — a one-task difference, presented without confidence intervals, that should not be over-read as strong statistical evidence even though it's directionally consistent with the paper's thesis.

**Reproducibility:** Full prompt templates (seed-filtering, refinement, semantic-judge, planner-evaluation, LLM-as-judge) are given in the appendix, and the simulation algorithm (Algorithm 1) is fully specified with explicit equations, which is commendable. However, no explicit code/artifact release is confirmed in the visible text, and several cost-accounting constants (e.g., 2.5% compression token cost, 1,200-token agent startup cost, 5,000-token communication chunking) are simulator design choices whose real-world calibration is not deeply justified beyond the aggregate correlation study.

**Significance:** If the simulator's fidelity holds up under broader/independent replication, this is a practically valuable tool for cheap early-stage MAS orchestration screening (74–389x cost reduction is large), and the "transfer coverage matters more than agent count" finding is an important, non-obvious result for MAS system design. But the fragility of the core correlation claim under leave-one-out testing tempers how strongly this validation should be trusted at face value.

## Strengths

- Clean conceptual separation of orchestration planning from worker execution, addressing a genuine gap in MAS evaluation methodology.
- Large (74x–389x) and clearly quantified reductions in token/time cost versus full execution, demonstrated on two independent benchmarks (MultiAgentBench, WideSearch).
- Transparent reporting of validation weaknesses (leave-one-model-out correlation drop, cross-framework time/token non-transferability) rather than only favorable numbers.
- Systematic scale sweep (10 to 1,000 subtasks) reveals a previously under-examined coordination-failure phenomenon (missing cross-agent information transfers) that scales badly and is largely invisible to end-to-end evaluation.
- Multiple concrete downstream applications demonstrated (cost-efficient model selection, task-difficulty estimation, simulator-guided plan refinement with measured real-execution improvement) rather than a benchmark left purely as a leaderboard.

## Limitations

- The headline simulation-to-real correlation (r=0.816) is computed over only six models and is highly sensitive to single-model removal (dropping to r=0.421, non-significant, when GLM-5.1 is excluded), raising questions about how robust this validation is with a larger/independent model set.
- Cross-framework correlation is uneven (strong for Claude Code/SWE-mini, markedly weaker for OpenHands), so the simulator's fidelity may not generalize evenly across all MAS execution frameworks.
- Simulated time and token-usage metrics do not reliably predict real resource consumption across frameworks (near-zero cross-framework correlation), limiting the efficiency sub-metrics to being screening heuristics rather than validated predictors.
- DAG generation itself has a non-trivial ~34% rejection rate and known residual failure modes (redundant verification layers, artificial over-decomposition) that can persist into the accepted benchmark pool, especially at larger scales.
- The missing-transfer penalty factor λ and several simulator cost constants are manually chosen design parameters that materially affect the benchmark's discriminative power, rather than being derived from first principles or fit to real execution data.
- The real-world-benefit demonstration (DAG-assisted actual agent runs, Table 17) is based on only 10 tasks, too small a sample to be strong standalone evidence.

## Relevance

该工作与多智能体系统评测、任务编排/调度策略设计、以及"如何用低成本仿真代替昂贵真实执行做基准测试"的方法论高度相关，特别适合关注 LLM-agent 编排效率、上下文管理与跨智能体信息传递问题的研究方向参考。

## Questions for Further Exploration

- How does the r=0.816 simulation-to-real correlation hold up with a substantially larger and more diverse set of planner models (beyond the six/nine used here), given the demonstrated fragility to single-model removal?
- Could the simulator's quality/compression model (Eq. 2–3, geometric-mean parent quality × compression-sensitivity function) be learned or calibrated directly from real execution traces rather than hand-specified, and would that improve cross-framework transfer of the efficiency metrics?
- What specific architectural or prompting interventions would most directly reduce the "missing transfer" failure mode at extreme scale (1,000+ subtasks), beyond simply adding more agents?
- Would the benchmark's coordination-failure findings replicate on non-DAG-shaped real workflows (e.g., tasks with cyclic negotiation or dynamic re-planning) that fall outside the fixed-DAG assumption?
- How sensitive is the "transfer coverage matters more than agent count" conclusion to the specific λ=0.5 missing-transfer penalty, and would a differently-calibrated penalty change which models are judged "best" at each scale?
