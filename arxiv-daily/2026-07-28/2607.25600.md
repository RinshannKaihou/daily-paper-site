> **一句话总结：** 论文提出 BeyondUncertainty，用黑盒 LLM 的一次性口头置信度（verbalized confidence）作为检索路由信号，在 6 个 QA 数据集、3 个模型家族共 27,000 次策略实例上，平均 token-F1 达到 0.483，优于"总是检索"(0.467) 和"从不检索"(0.401)，同时检索段落数比总是检索减少 20.4%，但由于额外的探测调用，总 token 消耗反而增加 28.2%。
>
> **TL;DR:** BeyondUncertainty elicits a provisional answer plus verbalized confidence, routes low-confidence questions to top-5 TF-IDF retrieval, and evaluates on NQ/HotpotQA/2WikiMultiHopQA/SQuAD/TriviaQA/MuSiQue with GPT-5.5, Gemini-3.5-flash, and Claude-sonnet-5. It reaches 0.483 mean F1 vs. 0.467 for always-retrieve and 0.401 for no-retrieval, cuts retrieved passages by 20.4%, beats a route-count-matched random baseline in 17/18 dataset-model cells (avg +0.024 F1), but increases total token usage by 28.2% relative to always-retrieve — a retrieval-saving, not token-saving, method.

## 核心贡献

- 提出一个模型无关的黑盒路由接口：让 LLM 先输出结构化的"临时答案 + 口头置信度 + 简短状态摘要"（JSON 格式，不暴露隐藏思维链），再用一个在验证集上选定并在测试前冻结的、按模型家族区分的阈值 τ_m 决定是否检索。
- 构建了一个 27,000 策略实例（3,000 道题 × 3 模型 × 3 策略）的成对评测，覆盖单跳/多跳 6 个 QA 基准和三家模型（OpenAI gpt-5.5、Gemini gemini-3.5-flash、Claude claude-sonnet-5），并保留 API 失败和结构化输出解析失败（不做事后过滤）。
- 通过"路由数量匹配的随机对照"（route-count-matched random control）分离出"选中的题目是否更有价值"和"检索的题目数量本身"这两个效应，证明置信度确实带来了超越检索频率的题目级别分配价值（17/18 个 cell 上占优，平均 +0.024 F1）。
- 诚实地展示了该方法的核心权衡：置信度作为绝对概率校准很差（ECE 0.426–0.528），但作为序数路由信号有效（AUROC 0.628 预测检索收益）；且额外探测调用使总体 token 开销不降反升 28.2%。

## Key Contributions

- A model-agnostic black-box routing interface that elicits a structured provisional answer, verbalized confidence, and state summary in one call, then uses a validation-frozen, per-model-family threshold τ_m to gate retrieval — no access to logits, hidden CoT, or fine-tuning required.
- A large paired evaluation: 27,000 executed policy rows (3,000 questions × 3 model families × 3 policies: No Retrieval, Always Retrieve, BeyondUncertainty) across NQ, HotpotQA, 2WikiMultiHopQA, SQuAD, TriviaQA, and MuSiQue, with API/parsing failures retained in the denominator rather than filtered out.
- A route-count-matched random control (via stable SHA-256 ordering) and a non-deployable oracle, both constructed post hoc from paired static-policy outputs with zero additional model calls, isolating "which questions are chosen" from "how many questions are routed."
- A clear-eyed accounting of the quality-cost trade-off: confidence routing is retrieval-saving (fewer passages) but not token-saving (more total tokens due to the probe call), explicitly separating ordinal decision utility of confidence from its poor absolute calibration.

## Methodology

BeyondUncertainty operates as a two-stage pipeline (Figure 1). For each question q, a black-box model first emits an observable state s0 = (â0, c0, d0, m0): a provisional answer, a verbalized confidence c0 ∈ [0,1], a suggested retrieval action d0 (logged but not used for routing), and a short (≤2 sentence) state summary — all requested as compact JSON without Markdown fences or hidden chain-of-thought. Uncertainty is defined as u0 = 1 − c0. The frozen router is R(q,m) = 𝕀[c0 < τ_m]; missing/unparseable confidence is conservatively mapped to retrieval. If R=0, the provisional answer â0 is returned directly. If R=1, a deterministic TF-IDF retriever (English stop-word removal, uni+bigrams) returns the top-5 passages from a dataset-specific corpus (built from deduplicated title-passage pairs in the dev/test contexts, 6,299–17,687 documents per dataset, Table 2), and the same model is called again with question + passages for a final answer.

Three model family aliases are accessed via one OpenAI-compatible gateway between July 8–11, 2026: gpt-5.5, gemini-3.5-flash, and claude-sonnet-5, with frozen thresholds τ_m = 1.0, 1.0, and 0.9 respectively (Table 1) — selected on held-out validation F1 before test evaluation and never touched afterward. Because none of the gateways exposes token log-probs, verbalized confidence is the only usable black-box uncertainty signal. Three primary policies are run for every question-model pair: No Retrieval (one call, no context), Always Retrieve (top-5 passages + one call), and BeyondUncertainty (one probe call, plus a second call only when routed to retrieval) — yielding 3,000 × 3 × 3 = 27,000 policy rows / 9,000 paired instances. The primary metric is normalized token-level F1 (EM reported in supplement); token usage sums gateway-reported input+output tokens across all calls including the probe. Within each of 18 dataset-model cells, paired two-sided Wilcoxon signed-rank tests compare the three policies pairwise (54 tests total), jointly corrected via Holm's procedure. The paper is explicit that this is a single-decision instantiation of uncertainty propagation — it does not implement iterative uncertainty trajectories, learned routing, or selective abstention, and does not claim to prove monotonicity between confidence and retrieval benefit (RQ1 only tests whether confidence orders quality).

## Results & Highlights

- **Aggregate F1 (Table 4, 9,000 paired instances):** BeyondUncertainty achieves 0.483 mean F1, vs. 0.467 for Always Retrieve and 0.401 for No Retrieval — a +0.082 absolute gain over no-retrieval and +0.016 over always-retrieve. It retrieves 3.952 passages/instance on average vs. 4.966 for Always Retrieve, a 20.4% reduction in retrieved passages.
- **Token cost trade-off:** mean token usage rises from 1201.5 (Always Retrieve) to 1539.8 (BeyondUncertainty) per instance, a 28.2% increase — the probe call more than offsets the passage savings, so the method is "retrieval-saving but not token-saving."
- **Route-count-matched control (RQ3):** at matched retrieval counts per dataset-model cell, confidence routing (0.483 F1) beats random routing (0.459 F1) in 17 of 18 cells, average advantage +0.024 F1; the sole exception is MuSiQue–OpenAI (≈ −0.001), where OpenAI's near-saturated routing rate (≥95.8% retrieval in every dataset) leaves little room for selection.
- **Calibration vs. ordinal utility (RQ1, Table 3):** probe confidence correlates with final F1 (ρ = 0.276–0.309 across the three model families) but is poorly calibrated as an absolute probability (ECE5 = 0.426–0.528); mean confidence (0.849 OpenAI, 0.875 Gemini, 0.655 Claude) is far above exact-match rates (0.364, 0.375, 0.232). Uncertainty predicts positive retrieval benefit with AUROC = 0.628 (per-model range 0.588–0.633) against a 0.354 positive-benefit base rate.
- **Statistical significance (Table 5, Table 6):** after one joint Holm correction over 54 tests, Always Retrieve and confidence routing each beat No Retrieval in 11/18 cells; but confidence routing vs. Always Retrieve is significant in only 3/18 cells (NQ-OpenAI and SQuAD-Claude favor confidence routing; NQ-Gemini favors always-retrieve) — the paper explicitly cautions the aggregate gain is "an average improvement across heterogeneous settings rather than evidence of universal dominance."
- **Retrieval can hurt:** Always Retrieve underperforms No Retrieval for Gemini on 2Wiki and TriviaQA, and for Claude on TriviaQA — confirming that indiscriminate retrieval sometimes degrades an otherwise-correct parametric answer, and that BeyondUncertainty beats both static policies in exactly these three settings.
- **Oracle headroom:** a non-deployable oracle (best of the two static-policy outputs per example) reaches 0.523 F1, 0.040 above BeyondUncertainty, indicating meaningful room for better retrieval-benefit prediction.
- **Failure robustness:** the full artifact retains 152 API errors and 232 structured-output parse failures (scored as zero) in the denominator; MuSiQue has the lowest coverage at 94.4%. Recomputing on successful rows only shifts F1 slightly (0.409/0.472/0.488 for N/A/S) but preserves the ordering and the ~0.016 confidence-vs-always gap.

## Critical Assessment

**Novelty:** The core idea — using verbalized confidence as a black-box routing signal — is explicitly positioned as incremental relative to AdaRAGUE (Moskvoretskii et al. 2025), which the paper cites as already showing "simple uncertainty signals can be competitive." The contribution here is narrower: a controlled, model-agnostic, cross-provider comparison with a route-count-matched control to isolate allocation value from frequency effects, rather than a fundamentally new signal or mechanism.

**Rigor:** Genuinely strong in several respects — pre-registered/frozen thresholds selected only on validation data, Holm correction across 54 tests, retained (not filtered) API/parsing failures, and a dedicated route-count-matched control to address the obvious confound that "fewer questions retrieved" alone could explain any F1 change. The paper is also unusually candid that only 3 of 18 confidence-vs-always-retrieve comparisons survive multiplicity correction, actively pushing back against overclaiming its own headline number.

**A concrete red flag:** the model "aliases" (gpt-5.5, gemini-3.5-flash, claude-sonnet-5) are gateway-reported names accessed through a third-party OpenAI-compatible endpoint between July 8–11, 2026, and the paper itself states these "should not be interpreted as independent verification of direct-provider model versions" — meaning the actual underlying models are not independently confirmed, which is a real reproducibility and validity concern for a paper making cross-model-family claims.

**A specific missing ablation:** the route-count-matched control is explicitly acknowledged as not execution-matched — it recombines already-computed static-policy outputs rather than running an actual randomized router through the same two-call structured-probe pipeline, so it "does not establish a fully controlled causal effect of confidence" (the authors' own words). A directly executed randomized controller with the same probe/token overhead is flagged as needed future work but not done here.

**Weak/uneven baseline behavior:** OpenAI's router is nearly non-functional as an adaptive mechanism — it routes ≥95.8% of questions to retrieval in every single dataset, meaning for 1 of the 3 model families the method is effectively indistinguishable from Always Retrieve. This is disclosed transparently but does undercut the "27,000 instances, 3 model families" framing, since a third of that evidence contributes little to the adaptivity claim.

**Significance:** Modest but honest. The paper does not oversell — it explicitly concludes the method is "retrieval-saving but not token-saving," which is an important negative result given that token/inference cost (not just retrieved-passage count) is usually the practically relevant efficiency metric in production RAG systems. The 20.4% passage reduction is real but the 28.2% token increase somewhat undermines the practical value proposition unless passage-serving cost (e.g., a paid retrieval API or heavy index) dominates over LLM token cost.

**Reproducibility:** Above average for this class of paper — deterministic TF-IDF corpus construction, SHA-256-based deterministic route-matching, request-level provenance, and released code, though tied to a moving-target commercial gateway makes exact quantitative replication difficult over time.

## Strengths

- Deliberately simple, model-agnostic design requiring only a single structured black-box call — no logits, hidden CoT, or fine-tuning needed, making it broadly applicable to proprietary APIs.
- Large-scale, carefully controlled evaluation (27,000 policy rows) with pre-registered thresholds and a genuine route-count-matched control to separate "which questions" from "how many questions."
- Unusually transparent statistical reporting: Holm-corrected significance, retained failures, and per-cell heterogeneity are all surfaced rather than hidden behind an aggregate number.
- Clear articulation of the calibration-vs-decision-utility distinction (poorly calibrated ECE but useful ordinal ranking, AUROC 0.628), which is a conceptually useful framing for the broader adaptive-RAG literature.
- Honest, non-oversold conclusion that explicitly separates "retrieval-saving" from "token-saving," avoiding a common overclaiming pitfall in efficiency papers.

## Limitations

- The retrieval corpus is a small, benchmark-derived local TF-IDF index (6,299–17,687 documents per dataset) rather than a production-scale open-domain retriever (e.g., full Wikipedia), so results may not transfer to real-world RAG deployments with noisier, larger corpora.
- Confidence-guided routing increases total token usage by 28.2% relative to always-retrieve — the method solves passage over-retrieval but introduces a new inference-cost problem via the probe call.
- Model aliases are gateway-reported and not independently verified against the direct provider, and the underlying models could change or be re-routed by the gateway over time, threatening exact reproducibility.
- OpenAI's router saturates near 96–100% retrieval across all datasets, effectively collapsing to Always Retrieve for one of the three tested model families and limiting the generalizability of the adaptivity claim.
- The route-count-matched control and oracle are post-hoc recombinations of static-policy outputs, not execution-matched randomized baselines, so the causal claim about confidence's allocation value is softer than a fully controlled ablation would provide.
- Cell-level statistical significance is weak: only 3 of 18 confidence-vs-always-retrieve comparisons survive multiplicity correction, so the aggregate +0.016 F1 gain rests on a small number of significant cells plus many non-significant numerical improvements.

## Relevance

该工作涉及黑盒 LLM 的不确定性估计与自适应检索路由，方法轻量（单次探测调用即可判断是否检索）且评测严谨（大规模成对实验 + 统计校正 + 消融对照），适合关注 RAG 系统效率优化、LLM 置信度校准、以及黑盒 API 场景下自适应推理策略设计的读者；其"检索节省但token不节省"的诚实负面结论对实际工程决策（是否值得引入这类路由器）也有直接参考价值。

## Questions for Further Exploration

- Would an execution-path-matched randomized controller (same probe + two-call structure, but random routing decision) confirm the +0.024 F1 allocation advantage, or does some of that gain come from the probe call itself providing extra "thinking time" rather than confidence per se?
- Can a cheaper confidence probe (e.g., a smaller/distilled model producing just the confidence score) preserve the routing benefit while eliminating the 28.2% token overhead, achieving genuine token savings?
- How does the method perform on a production-scale open-domain retriever (dense or hybrid, not local TF-IDF), where retrieval quality itself is more variable and the "irrelevant context degrades quality" effect may be stronger or weaker?
- Why is OpenAI's gpt-5.5 confidence distribution so concentrated (≥95.8% routed to retrieval everywhere) compared to Gemini and Claude — is this a genuine epistemic property of the model, an artifact of prompt sensitivity, or a decoding/temperature effect (note OpenAI's endpoint rejects temperature 0)?
- Could combining verbalized confidence with a cheap secondary signal (e.g., query complexity or sampling consistency) close some of the 0.040 F1 gap to the oracle without a second full model call?
