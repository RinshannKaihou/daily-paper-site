Controlled rank / module / precision sweep on a 60M-parameter model

LoRA rank 16 recovers 83.7% of full fine-tuning's accuracy on a 60M-parameter T5, using under 1% of its parameters — going bigger barely helps.

How Small Can You Go? A Controlled Study of LoRA Rank, Target Modules, and Quantization Trade-offs for Text-to-SQL on a 60M-Parameter Model ↗
Rathor, Azzam · 2026-07-28 · arXiv:2607.25583 ·
LoRA QLoRA quantization text-to-SQL T5-small WikiSQL
Key Metric
83.7%
of full fine-tuning's 71.2% exact-match accuracy recovered by LoRA r=16 on {q,v} — using just 589,824 of 60,506,624 parameters (0.965% of the base) and 31% less peak memory (1.60GB vs. 2.31GB).
Why This Matters
Gives PEFT practitioners a concrete, quantified answer for how large a LoRA rank actually needs to be on small text-to-SQL models.
Critical Edge
Training used only 5,000 of WikiSQL's ~56,000 examples, so "rank saturates at r=16" may just reflect an undertrained model rather than an intrinsic property of the task.

Methodology

Reference config: LoRA r=8, {q,v}, FP16 — three axes are varied one at a time relative to it:
AXIS 1 · RANK
r ∈ {2, 4, 8, 16, 32}, α=2r, dropout 0.1, frozen biases
AXIS 2 · MODULES
{q,v} → {q,k,v,o} → {q,v}+FFN
AXIS 3 · PRECISION
FP16 → INT8 (LLM.int8()) → NF4 (QLoRA, double quant)

T5-small (60M params) is fine-tuned on WikiSQL, serialized as translate English to SQL: <question> table: <headers> with the gold SQL as target — but on only 5,000 training examples and 500 validation examples (not WikiSQL's full ~56K split), deliberately small so the full 11-configuration sweep stays tractable on one GPU. Zero-shot and full fine-tuning (all 60.5M params updated) anchor the accuracy floor and ceiling. AdamW, lr=5e-4, batch size 8, 3 epochs, beam search (num_beams=4). Every configuration runs with 3 seeds (42, 123, 456) on a single NVIDIA T4 GPU via Kaggle Notebooks — the full sweep completes in ~35 minutes. Exact-match (EM) accuracy is the primary metric; execution accuracy is reported too, but computed over just 25 of 500 examples and flagged by the authors themselves as high-variance and secondary.

Memory drops 62% vs. FP16 LoRA and 74% vs. full fine-tuning for both quantized variants, at ≤0.6 points of EM cost. But latency gets worse under quantization, not better — attributed to T4 dequantization overhead, and not diagnosed further by the authors.

The configuration ranking (full fine-tuning > r=32 ≈ r=16 > r=8 > r=4 > r=2) holds across all three seeds. Low-rank LoRA is far noisier than quantized configs — suggesting quantization has a regularizing effect at this model scale.

Strengths

  • Genuinely controlled single-variable design — only one axis changes per configuration relative to a fixed reference, making comparisons cleanly interpretable.
  • Joint accuracy + system-cost reporting (parameters, memory, latency, throughput) with an explicit Pareto-front framing, not the accuracy-only tables common in PEFT papers.
  • 3-seed variance analysis with reported std, revealing low-rank LoRA is meaningfully noisier than higher-rank or quantized configurations.
  • Full, low-barrier reproducibility: single T4 GPU, ~35 minutes, open code/configs/logs.
  • Honest, repeated acknowledgment of scope limits (single model, single benchmark, single-table task) rather than extrapolating to "small models" broadly.

Limitations

  • Single base model (T5-small) and single benchmark (WikiSQL, single-table only) — the authors explicitly say conclusions shouldn't generalize beyond this setting.
  • Only 5,000 of WikiSQL's full training examples over 3 epochs, yielding a 71.2% EM full fine-tuning ceiling well below literature values (80%+) — may confound "early rank saturation" with an undertrained-model artifact.
  • Execution accuracy measured over only 25/500 (5%) executable examples, flagged by the authors as high-variance and secondary.
  • QLoRA's higher inference latency (921ms INT8, 614ms NF4 vs. ~380ms FP16) is reported but not deeply diagnosed.
  • No comparison to other PEFT methods (adapters, prefix-tuning, BitFit) — discussed in Related Work but never empirically benchmarked.

Questions for Further Exploration

  • Does the r=16 rank-saturation point shift with WikiSQL's full ~56K-example training set instead of 5,000 — is saturation a property of task complexity or of an undertrained regime?
  • How do these rank/module/quantization trade-offs transfer to multi-table benchmarks (Spider, BIRD), where "intrinsic task dimensionality" is presumably higher?
  • Would the QLoRA latency penalty persist on more recent GPUs with better native low-bit kernel support, or is it specific to the T4's dequantization path?
  • How would other PEFT methods (adapters, prefix-tuning, BitFit) compare on the same accuracy/memory/latency axes — would LoRA still dominate the Pareto front?
  • Does "module expansion is a weaker lever than rank" hold for decoder-only architectures, where attention and FFN structure differ from T5's encoder-decoder design?
