> **一句话总结：** 通过对319个真实Python/Java bug报告做基于扰动的Kernel SHAP归因分析，作者发现在claude-4-sonnet（65.2%修复率）、gpt-oss-20b（51.7%）、qwen3-32b（40.7%）三个模型上，成功修复始终对应跨"Bug描述+堆栈+测试"等多组件的"扩散型注意力"（OR=2.07，q=2.41×10⁻¹⁴），失败修复则表现为对Version信息等元数据的"局部化注意力"（OR=0.40，q=9.60×10⁻¹⁵）；新构建的100份开发者标注数据集进一步显示，模型注意力与开发者认为重要的章节/短语对齐程度越高，修复越可能成功（章节级Spearman ρ：成功0.60 vs失败0.34，p=0.036）。

> **TL;DR:** This paper presents the first empirical study of attention allocation in LLM-based Automated Program Repair (APR), using perturbation-based Kernel SHAP analysis over 319 real Python/Java bugs from SWE-bench Verified and Multi-SWE-bench, evaluating claude-4-sonnet (65.2% fix rate), gpt-oss-20b (51.7%), and qwen3-32b (40.7%). Successful repairs are characterized by "diffused attention" spread across multiple bug-report components such as Bug description, stacktrace, and test (OR=2.07, q=2.41e-14), whereas failed repairs show "localized attention" concentrated on less-diagnostic metadata such as Version information (OR=0.40, q=9.60e-15). A newly collected 100-bug developer-annotation dataset further shows that repair success correlates with stronger model-developer attention alignment (section-level Spearman ρ: 0.60 for successful vs. 0.34 for failed repairs, p=0.036; phrase-level F1@20: 0.19 vs. 0.08, p=0.031).

## 核心贡献

- 首个针对LLM-based APR中"注意力如何分配"的实证研究：用基于扰动的方法（而非直接读取内部注意力权重）分析模型在真实多章节bug报告上的行为，克服了以往研究只分析短任务描述、无法处理bug报告长且异构（自然语言+代码混合）的局限。
- 在319个Python/Java bug（SWE-bench Verified + Multi-SWE-bench）上，同时刻画了"章节级"（Bug description/Reproduction/Expected behavior/Actual behavior/Version information/Additional information）和"细粒度组件级"（自然语言 vs. 代码：堆栈、测试、类/方法、import等）两层注意力模式，并系统比较成功修复与失败修复之间的差异。
- 识别出三种可复现的注意力结构——扩散型（diffused）、局部型（localized）、无注意力型（no-attention）——并用Fisher精确检验+FDR校正的逻辑回归量化每种结构与修复成功率的关联，同时用bug难度作为控制变量做稳健性检验。
- 构建并公开了首个"开发者关注点"标注数据集（100份bug报告，4位有5年以上经验的开发者手工标注章节重要性评分与关键短语），首次让"模型注意力 vs. 人类开发者认为重要的信息"这一问题在APR场景下变得可量化。

## Key Contributions

- The first empirical study of how LLMs allocate attention over real, multi-section bug reports during automated program repair, using perturbation-based (model-agnostic) attention estimation rather than requiring access to internal attention weights — enabling analysis across both proprietary (claude-4-sonnet) and open-source (gpt-oss-20b, qwen3-32b) models.
- A two-level characterization of attention over 319 Python/Java bugs (248 from SWE-bench Verified, 71 from Multi-SWE-bench): section-level (Bug description, Reproduction, Expected/Actual behavior, Version information, Additional information) and fine-grained component-level (natural-language vs. code sub-components such as stacktraces, tests, class/method definitions, imports/variables), each compared between successful and unsuccessful repairs.
- Identification of three recurring attention structures — diffused, localized, and no-attention — with statistically quantified associations (Fisher's exact test, Benjamini-Hochberg FDR correction, logistic-regression odds ratios) to repair success, robust to controlling for bug difficulty (Easy/Medium/Hard).
- The first annotated developer-attention dataset for APR: 100 bug reports (50 Python, 50 Java) manually rated by four experienced developers for section importance (Likert 1-5), top-2 section selection, and verbatim key-phrase highlighting, used to measure human-model attention alignment and its relationship to repair success.

## Methodology

The study uses **319 real-world, single-function bugs** under a function-level perfect fault-localization setting: 248 Python bugs from *SWE-bench Verified* and 71 Java bugs from *Multi-SWE-bench*, each manually curated to be solvable and to carry a difficulty label (144 Easy, 164 Medium, 11 Hard). Three LLMs are studied: *claude-4-sonnet* (proprietary) and the open-source *gpt-oss-20b* and *qwen3-32b*, all run with a standardized repair prompt, temperature 0, and reasoning modes disabled where available, to isolate the effect of input perturbations from sampling noise.

Bug reports are manually grouped into six recurring sections (Bug description, Reproduction, Expected behavior, Actual behavior, Version information, Additional information). For **RQ1** (section-level attention), each section is treated as a binary maskable feature; the model regenerates a patch under every coalition of masked sections, and **Kernel SHAP** over CodeBLEU similarity between the masked-input patch and the full-input patch estimates each section's marginal contribution, normalized into a per-report attention score that sums to 100. Differences between successful and unsuccessful repairs are quantified with **Cliff's δ** and tested with the **Mann-Whitney U** test.

For **RQ2** (fine-grained code/NL components), each section is further decomposed via NLTK sentence tokenization (five NL categories: Description, Version, Expected/Actual behavior, Reproduction, Additional information) and regex-based extraction of four code categories (Stacktrace, Test, Class/method, Imports/variables), manually verified by the first author. Component-level perturbation uses UniXcoder embedding similarity between the outputs with and without each component masked. Because per-component perturbation is far more expensive (2,873 total perturbations across the dataset), **RQ2 and RQ3 analyses are conducted primarily on qwen3-32b only**, with a partial replication on gpt-oss-20b restricted to the 71-bug Java subset. Associations between attention-structure patterns (diffused/localized/no-attention) and repair success are tested with Fisher's exact test, FDR-corrected (Benjamini-Hochberg), and quantified via logistic-regression odds ratios, including a version that controls for bug difficulty as a covariate.

For **RQ3** (human-model alignment), the authors constructed a new annotation dataset: a stratified sample of 100 bugs (50 Python, 50 Java), each labeled by one of four developers (5+ years of Python/Java experience, 25 bugs each) via a custom Streamlit tool, rating each section's importance (1-5 Likert), selecting the top-2 most important sections, and quoting key phrases. Inter-rater agreement was measured on a 40-bug overlap subset (Spearman = 0.817, Cohen's κ = 0.77, average top-2 overlap 1.475/2). Section-level alignment is measured via Hit@1/Hit@2 (overlap of top-attended vs. developer-selected sections) and Spearman correlation between developer importance ratings and model attention scores; phrase-level alignment uses Precision@k/Recall@k/F1@k (k=10,20) between developer-highlighted phrases and model-attended text spans.

## Results & Highlights

- **Fix rates (319-bug dataset):** claude-4-sonnet solves 208/319 (65.2%), gpt-oss-20b solves 165/319 (51.7%), and qwen3-32b solves 130/319 (40.7%) — a >24-point spread between the strongest and weakest model on the identical bug set (Table 1).
- **CodeBLEU similarity to ground truth:** successful repairs closely match developer patches (median CodeBLEU 91% for claude-4-sonnet, 85% for gpt-oss-20b, 84% for qwen3-32b), while failed repairs are substantially different (mean CodeBLEU ~30% for claude-4-sonnet, ~29% for gpt-oss-20b, ~31% for qwen3-32b) — roughly a 55-61 percentage-point gap between success and failure.
- **Section-level effect sizes (RQ1, Cliff's δ, all three models):** *Bug description* attention is significantly higher in successful repairs (δ=0.54 claude-4-sonnet, 0.51 gpt-oss-20b, 0.50 qwen3-32b; Mann-Whitney p<0.05 for all), while *Version information* attention is significantly higher in unsuccessful repairs (δ=-0.53, -0.20, -0.42 respectively).
- **Attention-structure odds ratios (RQ2, qwen3-32b, Fisher's exact + FDR):** Diffused attention is strongly positively associated with repair success (OR=2.07, 95% CI [1.68,2.52], q=2.41×10⁻¹⁴), while Localized attention is negatively associated (OR=0.40, 95% CI [0.33,0.50], q=9.60×10⁻¹⁵); the same direction holds separately for Python (OR=1.66 diffused / 0.40 localized) and Java (OR=1.86 / 0.65). After controlling for bug difficulty via logistic regression (Table 4), the effect is essentially unchanged (diffused OR=2.00, localized OR=0.38).
- **Human-model alignment (RQ3, 100-bug annotated subset):** successful repairs show significantly stronger section-level alignment with developer judgments than failed repairs — Spearman ρ 0.60 vs. 0.34 (Δ=0.26, p=0.036), Hit@1 0.57 vs. 0.33 (p=0.028) — and stronger phrase-level alignment — F1@20 0.19 vs. 0.08 (p=0.031), Precision@20 0.42 vs. 0.18 (p=0.027), Recall@20 0.13 vs. 0.05 (p=0.048).
- **Developer vs. model priorities:** both developers and the qwen3-32b model most frequently rank *Bug description* as top-2 important (79% of bugs for developers vs. 61% for the model, 54% overlap), followed by *Reproduction* (43% vs. 34%, 30% overlap); *Version information* is ranked in the LLM's top-2 nearly twice as often as by developers (11% vs. 6%), consistent with the RQ1/RQ2 finding that over-attending to version metadata is associated with failure.

## Critical Assessment

**Novelty:** Genuinely fills a gap — prior attention-interpretability work in code tasks (e.g., Kou et al. on code generation) analyzed short, single-purpose task descriptions, not the long, heterogeneous, multi-section bug reports actually used in real APR pipelines. Combining perturbation-based SHAP attribution with a purpose-built developer-annotation dataset is a solid, original combination for this specific problem.

**Rigor:** The statistical approach is careful: Cliff's δ alongside Mann-Whitney p-values (RQ1), Fisher's exact test with Benjamini-Hochberg FDR correction across many simultaneous hypotheses (RQ2), and a difficulty-controlled logistic regression sensitivity check (Table 4) that confirms the diffused/localized effect is not an artifact of bug difficulty. Inter-rater agreement for the manual annotation is reported (Spearman 0.817, κ=0.77) via a genuine pilot study.

**Reproducibility:** Deterministic decoding (temperature 0), a standardized repair prompt across all models, and a released replication package (Zenodo DOI) with the annotation tool support reproducibility.

**Significance / red flags — paper-specific:** The more expensive RQ2/RQ3 fine-grained analyses are run almost entirely on a single model, **qwen3-32b**, with only a partial validation on gpt-oss-20b limited to the 71-bug **Java subset**; claude-4-sonnet — the model with the highest fix rate (65.2%) and thus the most successful repairs to analyze — is entirely absent from RQ2 and RQ3. This is an explicit, cost-driven design choice the authors disclose, but it means the paper's most detailed claims about *why* repairs succeed (fine-grained component attention, developer alignment) are validated on the weakest of the three models, not the strongest. Additionally, the dataset's difficulty labels are heavily skewed (144 Easy, 164 Medium, only 11 Hard), and the authors themselves report that the overall chi-square test of difficulty vs. repair success is *not* statistically significant (p=0.06) — so "difficulty," while used as a control variable, is not itself a well-powered confound check. The 100-bug developer dataset also has each bug annotated by only one of four developers (no redundant annotation except a 40-bug overlap subset used solely to measure agreement), so the "ground truth" of what's important largely reflects single-annotator subjectivity, a limitation the authors acknowledge directly.

## Strengths

- Uses real, function-level bugs drawn from two established, GitHub-derived APR benchmarks (SWE-bench Verified, Multi-SWE-bench) rather than synthetic or toy examples, with manually verified single-function difficulty labels.
- Cross-model (1 proprietary + 2 open-source) and cross-language (Python + Java) design, with RQ1 run on all three models and RQ2 partially replicated on a second model for Java, showing the diffused-vs-localized pattern is consistent across models and languages.
- Introduces genuinely new ground truth — a human-annotated developer-attention dataset — addressing a documented gap in existing APR benchmarks, which do not capture what information developers consider most important for bug-fixing.
- Statistically disciplined: effect sizes reported alongside significance tests, multiple-testing correction applied, and a difficulty-controlled robustness check included rather than relying on raw p-values alone.
- Concrete, illustrative case studies (e.g., the near-duplicate matplotlib bugs #16344 vs. #16420 that receive divergent repair outcomes despite similar content) ground the abstract statistical findings in interpretable examples.

## Limitations

- Perturbation-based attention (masking input, measuring output change via CodeBLEU/embedding similarity) is a black-box behavioral proxy, not a direct measurement of internal model attention weights or reasoning — the authors acknowledge this as a construct-validity approximation.
- Fine-grained (RQ2) and alignment (RQ3) findings are derived almost entirely from qwen3-32b, with limited cross-model validation (only a Java-subset check on gpt-oss-20b); generalization to claude-4-sonnet or to agentic/multi-round APR systems (e.g., SWE-Agent, AutoCodeRover) is untested.
- Bug-report decomposition into NL/code categories relies on regex heuristics and NLTK sentence tokenization, manually verified by a single author rather than cross-checked by multiple annotators.
- The 100-bug developer-annotation dataset uses one annotator per bug (agreement measured only on a 40-bug overlap), so the "developer ground truth" partly reflects individual subjective judgment.
- All results rely on single-sample, temperature-0 greedy decoding per bug; repair success/failure and associated attention patterns are not validated against repeated sampling or pass@k, and masking a section necessarily changes prompt structure (not just content), a threat the authors themselves flag.
- The Hard-difficulty subset (11 bugs) is too small for reliable difficulty-stratified conclusions, and the paper's own difficulty-vs-success chi-square test is not significant (p=0.06).

## Relevance

这篇论文用可解释的扰动式归因方法系统研究了LLM在真实bug报告上的注意力分配规律，并首次给出开发者-模型注意力对齐的人工标注数据集，对关注LLM可解释性、注意力机制以及LLM辅助软件工程/agentic coding系统的读者有直接参考价值。

## Questions for Further Exploration

- Would the diffused-vs-localized attention distinction, and its correlation with repair success, replicate on modern agentic APR systems (e.g., SWE-Agent, AutoCodeRover, OpenHands) that iteratively retrieve and re-read context, rather than single-shot function-level repair?
- Does the human-developer attention alignment finding hold up if claude-4-sonnet (the strongest model, excluded from RQ2/RQ3) were analyzed directly, given it has the most successful repairs to compare against developer annotations?
- Can the developer-attention dataset be used prescriptively — e.g., via attention-aware prompt reordering, section reweighting, or fine-tuning — to actually raise fix rates, beyond the purely correlational relationship reported here?
- How sensitive are the reported attention-success associations to non-zero-temperature sampling and multiple repair attempts (pass@k), rather than single deterministic greedy decodes?
- Would the same section/component attention patterns hold on less-curated, noisier real-world bug reports outside the manually vetted SWE-bench Verified / Multi-SWE-bench subsets, or on languages beyond Python and Java?
