> **一句话总结：** RSIBench-Data 通过固定训练/服务/评测基础设施（共享 Tinker LoRA SFT + Harbor/E2B 沙盒），让四个前沿智能体（Claude Code Opus-4.8/Sonnet-5、Codex gpt-5.6-sol/terra）在六个基准上反复"诊断-造数据-验证-训练"，发现智能体在 58.33% 的设置中能靠反馈超越自己的首次尝试，但在继续搜索的 23 个设置中有 78.26% 最终成绩低于历史最佳峰值，且最强模型在 SWE-bench Pro 上也只能达到 9.00%（基座模型为 0%）。

> **TL;DR:** RSIBench-Data isolates LLM agents' data-centric research capability by freezing the surrounding post-training stack (Qwen3.5-35B-A3B-Base target, shared Tinker-backed LoRA SFT, Harbor+E2B official evaluation) and tasking four frontier agents with iteratively diagnosing, synthesizing, and validating training-data strategies across six benchmarks (SWE-bench Verified/Multilingual/Pro, Terminal-Bench 2.0, GPQA Diamond, AIME 2026). Agents beat their own first valid attempt in 58.33% of settings (14/24), but among the 23 settings where search continues past the best observed score, 78.26% (18/23) end with a lower-scoring final attempt — e.g., Codex gpt-5.6-sol's Terminal-Bench 2.0 selection score rises from 7.87% to a 15.73% peak, then regresses to 13.48% (final official score 20.22% via historical-best checkpoint selection, vs. a 1.12% unadapted base-model score) — and even the best agent only reaches 9.00% on SWE-bench Pro against a 0.00% base-model floor.

## 核心贡献

- 提出"数据为中心研究智能体"（data-centric researcher agent）这一新的评测对象：智能体需针对固定目标模型形成能力缺陷假设、设计并验证训练数据策略、从检查点反馈中学习，而不是像以往基准那样把数据、优化、部署、评测糅在一起。
- 构建 RSIBench-Data：固定基座模型（Qwen/Qwen3.5-35B-A3B-Base）、共享 Tinker 后端的 LoRA SFT 训练/服务接口、Harbor 编排的 E2B 沙盒官方评测，以及跨智能体统一的预算（16 小时 + 500 美元 Tinker 额度），从而把"数据研究能力"从基础设施差异中剥离出来，形成可审计的 4 智能体 × 6 基准矩阵。
- 通过轨迹级分析揭示"发现-可靠性鸿沟"（discovery-reliability gap）：智能体确实能发现更优的数据策略（58.33% 设置中后续尝试优于首次尝试），但无法稳定地把新反馈转化为持续改进（78.26% 的继续搜索最终跌破历史最佳）；并归纳出四类使轨迹更强的做法——准确的能力诊断、基于验证信号的监督、行为对齐的数据、以及对强检查点的保留。

## Key Contributions

- Formalizes **data-centric research for recursive self-improvement (RSI)** as an automatable closed loop: an LLM agent forms a capability-gap hypothesis, turns it into executable/verifiable training data, and revises its strategy using controlled training-and-evaluation feedback — distinct from benchmarks that give agents free rein over the whole post-training stack (optimization, serving, implementation).
- Introduces **RSIBench-Data**, a controlled benchmark with a genuinely fixed infrastructure boundary: shared Tinker-backed LoRA SFT training/serving and Harbor+E2B-sandboxed official evaluation, so that submitted training-data strategies (not training code or system choices) are the only thing that varies across agents. Table 1 in the paper explicitly contrasts this against DataComp, DataComp-LM, AgoraBench, DCA-Bench, DataEnvGym, Curation-Bench, PostTrainBench, and Agent²RL-Bench, none of which jointly satisfy executable-experience synthesis, feedback-driven revision, and service-isolated train/serve/eval.
- Provides empirical evidence of a **discovery–reliability gap**: agents improve on their first valid attempt in 58.33% of the 24 agent-benchmark settings, but 78.26% of continued searches (18/23) finish with a final candidate below their own historical-best selection score, and the rest merely re-touch the same peak — meaning a strong candidate can appear early or mid-run even as later feedback-driven revisions fail to improve on it.
- Identifies four recurring **mechanisms behind stronger trajectories** (Table 3): diagnosing the real capability gap rather than over-trusting local revisions, embedding executable/decidable validation signals rather than model self-judgment, matching supervision granularity to the actually-evaluated behavior (e.g., real vs. synthetic task-completion actions), and preserving historical-best checkpoints against later regressions.

## Methodology

RSIBench-Data separates a **fixed infrastructure boundary** from the **data-synthesis research loop** that the agent controls (Figure 2):

- **Fixed stack**: a shared base model (`Qwen/Qwen3.5-35B-A3B-Base`), a whitelisted LoRA SFT training config trained through Thinking Machines Lab's Tinker backend, a common serving/sampler interface, and official evaluation delegated to Harbor-orchestrated E2B sandboxes with each benchmark's own runner, verifier, and scoring rule (Mini-SWE-Agent for the three SWE-bench variants, Terminus-2 for Terminal-Bench 2.0/GPQA Diamond/AIME 2026). Agents submit training artifacts (data + a whitelisted config), never training code, and cannot swap in a different optimizer, serving stack, or evaluator.
- **Agent inputs**: target benchmark description and success criteria, task-matched public seed repositories (SWE-smith, SWE-Gym, swe-factory, endless-terminals, tmax, synthetic-data-kit — no ready-made training corpus is provided), tool/environment schemas, available base-model diagnostics, and a fixed resource-budget contract (16 wall-clock hours + $500 Tinker budget per main run). Evaluation-only tasks/labels are explicitly withheld from training data to prevent test-set leakage into supervision.
- **Closed loop**: in each round the agent (1) diagnoses a capability gap, (2) synthesizes targeted training experience (tasks, executable states, success/failure/recovery trajectories), (3) validates/filters/curricula-orders this data, submits it plus a config, (4) receives a LoRA-SFT checkpoint trained via the shared backend, and (5) observes *permitted selection feedback only* (scores, trajectories, verifier outcomes, execution diagnostics — not full official-eval details) to decide whether to continue and how to revise. After exhausting attempts within budget, the agent picks one final checkpoint using only this selection history; only then is it evaluated officially on fresh task splits, reporting both raw score and improvement over the untrained base model (Δ_off).
- **Experimental matrix**: 4 agents (Claude Code with Opus-4.8 and Sonnet-5 at high reasoning effort; Codex CLI with gpt-5.6-sol and gpt-5.6-terra at max reasoning effort, Claude Opus-4.8 fixed as the external rollout model for all agents) × 6 benchmarks (SWE-bench Verified, SWE-bench Multilingual, SWE-bench Pro, Terminal-Bench 2.0, GPQA Diamond, AIME 2026), each run scored once (one representative run per setting) with fixed 100-instance subsets for the SWE-bench variants and GPQA Diamond, full sets for Terminal-Bench 2.0 (89 tasks) and AIME 2026 (30 problems, 4 decodes each).
- A separate **reasoning-effort ablation** (Section 5.4) compares Claude Code Sonnet-5 at "high" vs. "max" reasoning effort on SWE-bench Verified, holding everything else fixed, and an exploratory **same-family RSI pilot** (Section 5.5) uses a Claude-Code-with-kimi-k2.6 researcher agent to improve the instruction-tuned Moonshot `Kimi-K2.6` model itself on a fixed SWE-bench Pro subset.

## Results & Highlights

- **Best-vs-base gap remains weak on several benchmarks**: the best agent reaches only **9.00% on SWE-bench Pro** (Codex gpt-5.6-sol, vs. a **0.00%** unadapted base-model score), **22.00% on SWE-bench Multilingual** (Claude Code Sonnet-5, vs. **7.00%** base), and **20.22% on Terminal-Bench 2.0** (Codex gpt-5.6-sol, vs. **1.12%** base) — showing that even the winning training-data strategy leaves large headroom on executable, long-horizon tasks.
- **No agent dominates the suite**: best-to-worst spreads across the four agents are 8.00 points on SWE-bench Pro, 13.00 on GPQA Diamond and SWE-bench Verified, 14.60 on Terminal-Bench 2.0, 17.00 on SWE-bench Multilingual, and 20.00 on AIME 2026; the three SWE-bench-style benchmarks are each won by a different agent (Claude Code Opus-4.8 on Verified at 46.00% vs. Codex gpt-5.6-sol's 33.00%, Claude Code Sonnet-5 on Multilingual at 22.00%, Codex gpt-5.6-sol on Pro at 9.00%).
- **Discovery is common but reliability is rare**: a later candidate outperforms the agent's first valid candidate in 14 of 24 settings (58.33%); but among the 23 settings where the agent kept searching after first reaching its best observed selection score, 18 (78.26%) finished with a final attempted candidate below that peak, and only 5 merely returned to the same peak — none improved past it.
- **Regression can be costly, not just harmless**: on Terminal-Bench 2.0, Codex gpt-5.6-sol's selection score rises from 7.87% to a 15.73% peak by $69.07 cumulative Tinker cost, then falls to 13.48% after spending another portion of budget; Claude Code Sonnet-5 improves from 4.49% to 7.87% but then spends an additional $81.77 without refreshing the frontier, ending with only a 5.62% official score.
- **Similar scores can hide very different costs**: across the 24 main settings, median wall-clock time is 6.55 hours and median valid-candidate Tinker cost is $62.51, but the range spans 1.14–14.91 hours and $4.80–$363.77; e.g., Codex gpt-5.6-sol reaches 65.00% on GPQA Diamond in 2.42 hours for $10.37, while Claude Code Sonnet-5 spends 8.87 hours and $156.93 on Terminal-Bench 2.0 to score only 5.62%.
- **Reasoning effort trades breadth for depth**: on SWE-bench Verified with Claude Code Sonnet-5, raising reasoning effort from "high" to "max" (holding rollout model, target model, benchmark subset, and budget fixed) raises the mean selection score over the first four comparable attempts from 35.5% to 44.0%, the first-candidate score from 25% to 36%, the historical-best selection score from 44% to 49%, and the final official score from 35% to 52% — while completing one fewer valid attempt but submitting a much larger dataset (149 vs. 50 training records, 2,681 vs. 595 trainable assistant turns, $401.70 vs. $181.70 in candidate-loop Tinker cost).
- **Exploratory same-family pilot fails to beat the base model**: an RSI pilot where a Claude-Code-driven researcher (backed by kimi-k2.6) trains the Kimi-K2.6 model on itself improves its own candidate score from 8% to a 22% peak across 7 attempts on a fixed SWE-bench Pro subset, but every checkpoint remains below the 33% score of the unadapted Kimi-K2.6 model on the same subset — a genuine negative result the authors attribute to insufficient RSI capability when the target is already a strong instruction-tuned model.

The paper builds directly on well-known infrastructure (Anthropic's Claude Code, OpenAI's Codex CLI, Thinking Machines Lab's Tinker fine-tuning API, and the E2B sandbox project) and standard benchmark suites (SWE-bench Verified/Multilingual/Pro, Terminal-Bench 2.0, GPQA Diamond, AIME 2026), giving the setup external credibility. ## Critical Assessment

**Novelty**: Genuinely useful reframing — Table 1's protocol-level comparison against eight prior benchmarks (DataComp, DataComp-LM, AgoraBench, DCA-Bench, DataEnvGym, Curation-Bench, PostTrainBench, Agent²RL-Bench) makes a credible case that none jointly enforce executable-experience synthesis, feedback-driven revision, *and* service-isolated train/serve/eval — RSIBench-Data is the first to require all three simultaneously.

**Rigor**: The paper is honest about its own limits, which is a strength, but the underlying rigor is still thin: every one of the 24 main agent-benchmark settings is scored from a **single representative run**, so there are no error bars or variance estimates anywhere in the main results, and the headline reasoning-effort finding (35%→52% official score) is explicitly flagged by the authors themselves as "not... a fully isolated causal estimate" from a single comparison. The paper also concedes that checkpoint selection and official evaluation draw from the *same* task subset, so reported scores measure fresh-environment performance but not generalization to statistically held-out tasks — a real methodological gap for a benchmark whose whole point is measuring research capability.

**Reproducibility**: Code is open-sourced, but faithful reproduction requires paid, closed, managed services (Tinker LoRA SFT, Harbor+E2B sandboxes) and proprietary agent harnesses (Claude Code, Codex CLI) whose versions/prompts can change over time; the reported $500–$2,000-per-run budgets make large-scale independent replication expensive for most academic groups.

**Significance**: The "discovery–reliability gap" (58.33% first-attempt-beating discovery rate vs. 78.26% post-peak regression rate) is a meaningfully important, non-obvious negative result for the recursive-self-improvement narrative — it shows current frontier agents can stumble onto good training-data strategies but cannot reliably use additional feedback to refine them, which has direct implications for anyone hoping to run unattended RSI loops today.

**Red flags / weak points**: The authors themselves note that "researcher identity" conflates the underlying LLM, agent scaffold, and configured reasoning effort, so the main matrix cannot attribute performance differences to any single factor (e.g., is Codex's Terminal-Bench win due to gpt-5.6-sol's model quality, the Codex CLI harness, or its max-reasoning-effort setting?). Absolute scores on several benchmarks remain very low (9% on SWE-bench Pro, ~20% on Terminal-Bench 2.0), leaving unclear how much of the observed "ceiling" reflects genuine research-capability limits vs. simply the difficulty of the underlying tasks for a 35B target model under a 16-hour/$500 budget.

## Strengths

- Careful separation of the fixed infrastructure boundary (Tinker + Harbor/E2B) from the agent-controlled research loop, which is exactly the ambiguity that made prior automated post-training benchmarks hard to interpret.
- Broad, heterogeneous benchmark coverage spanning software engineering (three SWE-bench variants), terminal use (Terminal-Bench 2.0), scientific QA (GPQA Diamond), and math (AIME 2026), letting the paper show that "broad task-family similarity does not induce a stable ranking" (the three SWE-style tasks are won by three different agents).
- Transparent resource accounting — every run reports both wall-clock hours and Tinker dollar cost, enabling genuine efficiency analysis (Figure 4's cost-vs-score Pareto plots) rather than score-only leaderboards.
- Rich qualitative trajectory analysis (Figures 6–7, Table 3, Appendix B.6) that ties process-level decisions — diagnosis accuracy, validation grounding, behavior-aligned supervision, checkpoint preservation — to concrete score changes, going beyond a single aggregate number.
- Willingness to report an outright negative result: the exploratory Kimi-K2.6 same-family RSI pilot never beats its own base model despite visible strategy evolution across seven attempts, which the authors report plainly rather than omitting.

## Limitations

- Single run per agent-benchmark setting throughout the main matrix — no repeated trials, so reported deltas (especially the reasoning-effort ablation) cannot rule out run-to-run noise.
- Checkpoint selection and official evaluation share the same task subset (explicitly acknowledged in Section 6), so the benchmark measures performance in fresh environments but not generalization to a statistically held-out split.
- "Researcher identity" bundles the underlying LLM, agent scaffold, and reasoning-effort configuration together, preventing clean attribution of which factor drives a given agent's strength or weakness on a given benchmark.
- High infrastructure cost ($500 per main run, up to $2,000 for the exploratory RSI pilot) and reliance on managed third-party services (Tinker, Harbor, E2B, Claude Code, Codex CLI) limit independent, low-cost reproduction and long-term stability of exact numeric results as these external tools evolve.
- Absolute performance ceilings remain low on several benchmarks (SWE-bench Pro, Terminal-Bench 2.0, SWE-bench Multilingual), so it is not yet clear whether the observed discovery-reliability gap is a fundamental agent limitation or partly an artifact of the fixed 35B target model and tight budget.

## Relevance

该工作直接触及"用 LLM 智能体自动化数据为中心的后训练研究"这一自我提升（RSI）核心问题，其固定基础设施、隔离研究能力的评测协议设计，以及"发现常见但可靠性差"的核心发现，对研究 agentic 后训练、数据合成策略与自动化科研评测的读者都很有参考价值。

## Questions for Further Exploration

- Would open-weight, non-proprietary agent scaffolds (rather than Claude Code / Codex CLI) reproduce the same 78.26% post-peak regression rate, or is this specific to these two agent harnesses?
- Could an explicit stop/rollback policy component — separate from the agent's own judgment — close much of the discovery-reliability gap without changing the underlying LLM?
- How would results change if checkpoint selection and official evaluation used disjoint task splits, as the authors themselves suggest is needed to measure true generalization?
- Does the depth-vs-breadth tradeoff found in the reasoning-effort ablation (larger dataset, fewer attempts, better final score) generalize beyond SWE-bench Verified to the other five benchmarks?
- Would scaling the target model beyond Qwen3.5-35B-A3B-Base (or testing multiple target model families) change which data-synthesis strategies prove effective, and would it change the observed discovery-reliability gap?
- What specifically caused Claude Code Opus-4.8 to score *below* the base model on SWE-bench Multilingual (5.00% vs. 7.00% base) — is this diagnosable as a case of harmful training-data strategy, and could the benchmark's mechanism taxonomy (Table 3) be extended to explain regressions below baseline, not just below a previous peak?
