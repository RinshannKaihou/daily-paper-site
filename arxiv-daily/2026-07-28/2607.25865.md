> **一句话总结：** OmniQEC 用 LLM 驱动的"快-慢"双循环智能体框架直接以电路级逻辑错误率（而非代码级指标 kd²/n）为优化目标搜索 qLDPC 码，在 98 个物理比特预算下发现的码即超过 BB [[72,12,6]] 基准，在 240 比特预算下超过 BB [[144,12,12]] 基准，且消融实验证明慢循环（电路级反馈）是取得该优势的关键。

> **TL;DR:** OmniQEC is an LLM-orchestrated AI-scientist system that discovers qLDPC quantum error-correcting codes by directly optimizing circuit-level logical error rate (LER) instead of code-level proxies like Φ_code = kd²/n. Using a fast loop (cheap code-level screening across BB, trivariate-bicycle, lifted-product, and generalized-LP families) and a slow loop (Stim-based circuit synthesis + BP-OSD/BP-LSD/Relay-BP decoding), OmniQEC's discovered codes beat the bivariate-bicycle (BB) [[72,12,6]] baseline at a total-qubit budget of N=98, and the best Claude Opus 4.8 campaign beats BB [[144,12,12]] at N=240, with one frontier code achieving 29.23x lower LER than the BB [[72,12,6]] reference at p=0.002.

## 核心贡献

- 提出 OmniQEC：一个将 QEC 码发现建模为 LLM 驱动的迭代生成-评估-精炼过程的"AI 科学家"框架，首次将电路级逻辑错误率（而非代码级指标）作为发现过程的直接优化目标。
- 设计"快-慢"双循环架构：快循环（秒级）用代码搜索智能体产生候选构造程序（lifted-product、BB、trivariate-bicycle、generalized-LP），并用代码表征模块计算 k、d、Φ_code 等指标做低成本筛选；慢循环（分钟到小时级）将筛选出的高潜力候选编译成校验子提取电路，用真实解码器（BP+OSD、BP+LSD、Relay-BP）采样估计电路级 LER，并将结果反馈回编排器指导后续迭代。
- 在四个 qLDPC 构造族、三种 LLM 后端（Claude Opus 4.8、GPT-5.5、DeepSeek-V4-Pro）、14 个物理比特预算（N=20 到 288）上系统评测，发现的码在 N=98 即超过 BB [[72,12,6]] 参考码，最强的 Claude 活动在 N=240 超过 BB [[144,12,12]]。
- 揭示代码级指标 Φ_code = kd²/n 与电路级 LER 排序存在系统性错配：在 N=144 时，三种后端发现的最佳码的 Φ_code（2.25、5.56、3.36）均低于 BB 参考码的 Φ_code=6，但电路级 LER 却优于 BB 参考码，说明单纯优化代数指标不足以保证实际性能。
- 通过消融实验定量证明慢循环（电路级反馈）对发现质量至关重要：去除慢循环反馈后，三个后端的最终迭代平均错误抑制 -log10(p_LER) 从 4.61/5.17/4.07 大幅下降到 2.14/3.20/0.84。

## Key Contributions

- Introduces OmniQEC, an "AI-scientist" framework that casts QEC code discovery as an LLM-orchestrated iterative generate-evaluate-refine process, directly targeting circuit-level logical error rate (LER) rather than code-level proxies.
- Designs a dual-loop discovery architecture: a fast loop (seconds per candidate) where a code-search agent proposes executable construction programs (lifted-product, BB, trivariate-bicycle, generalized-LP) and a code-characterization module computes k, d, and Φ_code for cheap screening; a slow loop (minutes to hours) where a circuit-synthesis module compiles promising candidates into syndrome-extraction circuits and a circuit-evaluation module estimates LER via noisy sampling and configurable decoders (BP+OSD, BP+LSD, Relay-BP), feeding this evidence back to the orchestrator.
- Systematically evaluates OmniQEC across 4 qLDPC construction families, 3 LLM backends (Claude Opus 4.8, GPT-5.5, DeepSeek-V4-Pro), and 14 total-physical-qubit budgets (N=20 to 288), showing discovered codes surpass the BB [[72,12,6]] reference already at N=98, and the strongest campaign surpasses BB [[144,12,12]] at N=240.
- Demonstrates a rank mismatch between the code-level figure of merit Φ_code = kd²/n and circuit-level LER performance — discovered codes with lower Φ_code than the BB baseline nonetheless achieve lower (better) circuit-level LER, arguing that code-centric proxies are an unreliable stand-in for implementation-level performance.
- Provides an ablation study isolating the fast and slow loops' respective contributions, and a cost/token analysis showing LLM-side API cost scales weakly with qubit budget and instead depends mainly on backend choice.

## Methodology

OmniQEC frames QEC discovery as a structured, iterative search directed by an LLM orchestrator (instantiated with GPT, Claude, or DeepSeek backends). The user specifies a design objective — target code family, physical-qubit budget N, connectivity, native gate set, and ancilla resources — which the orchestrator translates into a discovery task run over T=60 dual-loop iterations.

**Dual-loop strategy** (the paper's central design choice, motivated by the high cost of circuit-level evaluation relative to the large code search space):
- **Fast loop**: A code-search agent (LLM-guided program search) proposes 24 construction programs per iteration, each instantiated with 20 random seeds (up to 480 candidate code instances per iteration before validity checking/deduplication). Each program is a parameterized construction rule (e.g., for CSS codes, rules generating binary check matrices H_X, H_Z with H_X H_Z^T = 0 over F_2) covering BB, trivariate-bicycle (TB), lifted-product (LP), and generalized-LP (GLP) code families. A code-characterization module verifies validity and computes exact quantities (block length n, logical qubits k, check weights/degrees) plus decoder-assisted estimates of code distance d (via BP+LSD, OSD) and the code-level figure of merit Φ_code = kd²/n. This stage takes seconds per candidate.
- **Slow loop**: The top-ranked candidates are passed to a circuit-synthesis module, which schedules the required two-qubit interactions via edge-coloring of the associated Tanner graph (producing conflict-free parallel layers), then compiles a complete Stim circuit including state preparation/reset, native entangling gates, ancilla measurements, detector definitions, and logical-observable annotations. A circuit-evaluation module converts this into a detector error model, samples noisy syndrome data at a fixed physical error rate (p=0.005 during search), and applies configurable decoders (BP+OSD used as the main decoder; BP+LSD and Relay-BP also integrated) to estimate the circuit-level LER p_LER (defined per syndrome-extraction round, per logical qubit). This stage takes minutes to hours and is reserved for a selected subset of top candidates.

The resulting circuit-level evidence, together with the code-construction program, code-level properties, and decoding records, is distilled into an evolving "discovery memory" that the orchestrator uses to refine subsequent candidate-generation prompts, closing the self-evolving reasoning loop. The framework is decoder-agnostic and modular — new synthesis/evaluation tools can be swapped in without restructuring the loop.

**Experimental setup**: 3 LLM backends (Claude Opus 4.8, GPT-5.5, DeepSeek-V4-Pro), 4 code families, 14 qubit budgets (N=20–288, chosen to bracket the BB [[144,12,12]] reference at N=144/288 circuit-implementation budgets), T=60 iterations per (backend, budget) pair, fixed hyperparameters across all runs.

## Results & Highlights

- **Scaling frontier vs. BB baseline**: Across all three LLM backends, discovered codes form a clear resource-performance frontier where -log10(p_LER) increases roughly linearly with N. All three backends surpass the BB [[72,12,6]] reference code, with the first crossover occurring at N=98 total physical qubits. At larger budgets the frontiers diverge by backend: both GPT and Claude exceed the harder BB [[144,12,12]] reference at N=240, whereas DeepSeek does not surpass this reference within the explored range (N up to 288).
- **Code-level proxy mismatch**: At N=144, the best codes found by DeepSeek, Claude, and GPT have Φ_code = 2.25, 5.56, and 3.36 respectively — all lower than the BB [[72,12,6]]-style reference's Φ_code = 6 — yet all of these codes outperform the BB reference in circuit-level LER, directly demonstrating that the widely-used code-centric figure of merit Φ_code = kd²/n does not reliably rank circuit-level (implementation-level) performance.
- **Physical-error-rate sweep validation**: Re-evaluating 21 frontier codes (7 per backend, plus the BB [[72,12,6]] reference) over p in [0.002, 0.01] under identical syndrome-extraction/decoding protocols, the strongest discovered candidate achieves an LER that is 29.23-fold lower than the BB [[72,12,6]] reference at p=0.002, and 1.66-fold lower at p=0.01 — showing the advantage persists beyond the single p=0.005 operating point used during search. Fitted LER-scaling exponents Γ (p_LER ∝ p^Γ) for representative discovered codes are Γ=5.20 ([[48,4,8]], GPT), Γ=5.60 ([[58,2,7]], Claude), and Γ=5.57 ([[48,4,8]], DeepSeek), versus Γ=3.79 for the BB [[72,12,6]] reference — a materially steeper error-suppression scaling.
- **Ablation of the dual-loop design**: At the final iteration, the full OmniQEC workflow's top-5 candidates reach mean error suppression -log10(p_LER) = 4.61±0.54 (Claude), 5.17±0.09 (GPT), 4.07±0.28 (DeepSeek). The fast-loop-only variant ("w/o slow", ranking by code-level Φ_code alone with no circuit-level feedback) collapses to 2.14±0.10, 3.20±0.40, and 0.84±0.16 respectively — a large regression, especially for DeepSeek (4.07 → 0.84). The no-feedback variant ("w/o slow & fast") reaches 3.86±0.66, 4.25±0.19, 2.83±1.50. Across backends and checkpoints, the full workflow attains the highest mean suppression (4.27) and lowest variance (0.79), versus variance of 1.24–1.26 for the ablated variants — evidence that circuit-level feedback (the slow loop) is the primary driver of both stronger and more stable discovery, not just the fast loop's broader search.
- **Cost**: Token usage (input+output+reasoning) varies only weakly with the physical-qubit budget N (roughly 1.1M–1.55M tokens per full 60-iteration run across N=40–240), while USD cost per run ranges roughly $9–14 depending on N and backend. Claude gives the best cost-performance balance; DeepSeek is cheapest but yields the weakest performance frontier.

## Critical Assessment

**Novelty**: The core idea — replacing code-centric proxies (Φ_code = kd²/n, or bare [[n,k,d]]) with direct circuit-level LER as the discovery objective — is a genuine and well-motivated departure from prior RL-based, Bayesian-optimization-based, and LLM-program-search QEC discovery methods, all of which the paper itself characterizes as "predominantly code-centric" (citing refs [29–38]). The demonstrated Φ_code/LER rank mismatch (Section III.B) is the paper's most convincing piece of evidence for this framing, since it is a *quantitative, paper-specific* observation (Φ_code = 2.25/5.56/3.36 vs. BB's 6, yet lower LER) rather than a generic claim.

**Rigor**: The scaling study is reasonably thorough — 3 backends × 4 code families × 14 qubit budgets × 60 iterations, with an ablation (fast-only vs. no-feedback vs. full) that isolates the slow loop's contribution and a physical-error-rate sweep (21 codes re-evaluated over p ∈ [0.002, 0.01]) that checks robustness beyond the single p=0.005 search operating point. The reported variance reduction (0.79 for the full workflow vs. 1.24–1.26 for ablations) is a specific, checkable claim.

**Reproducibility concerns**: (1) The only baseline compared against is the human-designed bivariate-bicycle (BB) code family ([[72,12,6]] and [[144,12,12]]) — there is no head-to-head comparison against the RL-based, Bayesian-optimization, or other LLM-program-search QEC discovery methods the introduction itself cites as prior AI approaches (refs [29–38]), so the claim that circuit-level-grounded discovery outperforms code-centric AI discovery is argued conceptually via the Φ_code/LER mismatch, not tested directly against those competing methods' outputs. (2) Code distance d is not exactly computed but "estimated or bounded using decoder-assisted tools" (BP+LSD, OSD), so the reported Φ_code values themselves carry some approximation uncertainty. (3) Results depend on proprietary, versioned commercial LLM APIs (Claude Opus 4.8, GPT-5.5, DeepSeek-V4-Pro) that will be deprecated or silently updated over time, making exact replication of the reported discovery trajectories difficult even with the same code released. (4) The full physical-error-rate sweep and scaling-exponent fit was only performed on 21 of the many discovered codes (7 per backend, hand-selected as "frontier" codes), so the bulk of the Fig. 2 frontier is validated at only the single p=0.005 operating point.

**Significance**: If the Φ_code/LER mismatch generalizes, it has real implications for the broader AI-for-QEC-discovery literature, which the paper argues has been optimizing a proxy that "does not always align with the circuit-level LER ranking" — a meaningful methodological critique of the field, not just an incremental performance number. The practical crossover at N=98 (within reach of current reconfigurable processors like Helios, per the paper's own reference [79]) is a concrete, near-term-relevant result.

**Red flags**: DeepSeek's substantially weaker frontier (failing to beat BB [[144,12,12]] at all, and collapsing to -log10(p_LER)=0.84 in the fast-loop-only ablation) shows the method's benefit is highly backend-dependent — a less capable or differently-tuned LLM backend may not reproduce the headline results, which somewhat undercuts the "framework" framing since much of the payoff appears contingent on strong proprietary reasoning models (Claude, GPT) rather than the architecture alone.

## Strengths

- Directly measured, paper-specific evidence (not just argument) that a widely-used code-level figure of merit (Φ_code = kd²/n) can mis-rank circuit-level performance — a useful cautionary finding for the AI-QEC-discovery community.
- Clean ablation design (full workflow vs. fast-only vs. no-feedback) with quantitative mean/variance breakdowns that isolate the slow loop's specific contribution rather than just reporting an end-to-end number.
- Validation extends beyond the single search-time operating point (p=0.005) via a full physical-error-rate sweep and scaling-exponent (Γ) fits, showing the advantage is not an artifact of tuning to one noise level.
- Transparent reporting of LLM-side token usage and dollar cost per backend/budget, which is often omitted in "AI scientist" papers but matters for practical adoption.
- Modular, decoder-agnostic architecture (Stim + BP-OSD/BP-LSD/Relay-BP) built on established, independently checkable QEC tooling rather than a fully opaque end-to-end model.

## Limitations

- Single baseline family (BB codes) for comparison; no comparison to other human-designed qLDPC constructions (hypergraph-product, balanced-product, Floquet codes) or to prior AI-driven QEC discovery methods (RL, Bayesian optimization) at the circuit level.
- Code distance d is estimated/bounded via decoder-assisted heuristics rather than computed exactly, introducing uncertainty into the reported code-level metrics.
- Strong backend dependence: DeepSeek-V4-Pro underperforms substantially relative to Claude/GPT and fails to beat the harder BB [[144,12,12]] reference, meaning reported gains are not backend-invariant.
- Results rely on proprietary, versioned commercial LLM APIs, limiting exact long-term reproducibility as these models are updated or deprecated.
- Circuit-level validation across the full physical-error-rate range was performed on only a curated subset (21 of many discovered codes), not the entire Fig. 2 frontier.
- The paper focuses solely on quantum-memory experiments (code discovery for storage), not logical operations, lattice-surgery protocols, or other fault-tolerant primitives — explicitly flagged by the authors themselves as future work.

## Relevance

对关注 LLM-agent 用于科学发现（AI Scientist 范式）以及量子纠错码自动化设计的读者有较高参考价值，其"电路级证据优于代码级代理指标"的核心论点也可能迁移到其他需要"设计目标与真实评估目标不一致"的自动化科学发现场景。

## Questions for Further Exploration

- Would OmniQEC's discovered codes still outperform BB references if compared against codes found by prior RL-based or Bayesian-optimization-based QEC discovery methods evaluated under the same circuit-level LER protocol, rather than only against a human-designed BB baseline?
- How sensitive is the reported Φ_code/LER rank mismatch to the accuracy of the decoder-assisted code-distance estimates — would exact distance computation (where feasible) change the conclusion?
- Since DeepSeek's frontier is markedly weaker, what specific reasoning behaviors (reflection depth, tool-use patterns, exploration-exploitation balance per Section III.B) differentiate a "successful" orchestrator backend from a weaker one, and can this be distilled into a smaller/cheaper model?
- Would the dual-loop architecture extend cleanly to discovering codes and circuits for logical operations or lattice surgery, where the "slow loop" evaluation (multi-logical-qubit circuits) would be substantially more expensive than single-code-block quantum-memory evaluation?
- How does the discovery process's cost/performance trade-off change if the slow-loop circuit evaluation itself is made cheaper (e.g., via improved statistical estimation of logical performance, as the authors suggest as future work), and would that allow the fast loop to be bypassed with more slow-loop evaluations instead?
