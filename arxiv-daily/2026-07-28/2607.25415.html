Key Finding

A single static prompt beats online RL harness control across a 729-configuration action space — in nearly every domain tested.

A Control System, a Dataset, and a Recipe for Making Frozen LLM Agents Learn a Domain ↗

Debjyoti Paul · 28 Jul 2026 ·

Single-author, no institutional affiliation listed · positioned against Meta-Harness (built on Claude Code) and HyperAgents (Meta AI), both 2026 · described as one of a companion two-paper release.

Key Metric

96%vs62%

DSPy-static vs. REINFORCE success rate — tool-use domain, AWS Bedrock Haiku — and DSPy-static gets there on 285 tokens/episode vs. REINFORCE's 680 (2.4× fewer).

Why This Matters

Offers LLM-agent builders an honest counter-example: bootstrap with a static, metric-optimized prompt before investing in online harness control.

原文（Relevance）：对于关注LLM agent工程化落地、DSPy/prompt优化、以及"harness优化 vs. 在线RL控制"权衡的场景，这篇论文提供了一个诚实的反例和可复用的729维动作空间设计+多目标奖励框架，同时其公开的120任务数据集和4620条轨迹日志可作为对比自建控制器的基准。

Critical Edge

By the paper's own math, 25–60 episodes is provably too few for a 729-action space — and the obvious fix, warm-starting the online controllers from the static baseline, was never tested.

一句话总结 · Chinese Abstract (source)

Methodology

Six discrete levers define the harness: prompt style (direct / structured / reflective), tool-or-retrieval intensity (never / when-needed / always), memory (none / similar successes / successes+failures), planning depth (none / brief plan / plan-and-revise), verification (none / final check / stepwise), and step budget (2 / 4 / 6) — 35×3 = 729 total configurations. DSPy assembles each configuration into a concrete Signature + Module (Predict, ChainOfThought, or a two-pass draft-then-revise module), with a reward blending task success, verifier score, policy compliance, cost, latency, and an unsupported-claim penalty.

Four controllers are compared: Random (uniform lower bound), an ε-greedy contextual bandit (linear value estimate, optimistic init), REINFORCE (softmax policy, entropy regularization, moving-average baseline), and DSPy-static (one fixed configuration, optimized once via BootstrapFewShot).

  • Matrix: 3 domains (synthetic CRM tool-use, HumanEval coding, HotpotQA retrieval) × 2 providers (Ollama qwen2.5:7b, AWS Bedrock Haiku) × 4 optimizers — 2,460 episodes.
  • Plus a Bedrock Sonnet spot check (2 seeds × 40 episodes = 960 episodes).
  • Plus a dedicated 300-episode/run sample-efficiency follow-up on tool-use/Bedrock Haiku (2 seeds, 1,200 episodes).
  • Success is verifier-defined per domain: unit tests (coding), state-diff vs. mock backend (tool-use), exact-match + token-F1 (retrieval QA, fully local corpus).

  • Dataset: 120 verifiable tasks (96 train / 24 held-out: 40 CRM tool-use, 40 HumanEval, 40 HotpotQA), 4,620 logged episodes total across main matrix, spot check, and follow-up.
  • Total measured spend: $7.62 across the whole study.
  • No standalone hallucination table — the unsupported-claim penalty is folded into pooled reward/success numbers, not reported separately.

Strengths

  • Reports a result that contradicts its own starting hypothesis, with a dedicated 5–12× longer follow-up rather than post-hoc rationalization.
  • Three concretely diagnosed and fixed bugs (bandit cold-start tie-break, crash isolation, cache-based token undercounting), specific enough to be independently useful.
  • Multi-objective reward (compliance, cost, latency, unsupported-claim penalty) rather than a single accuracy number.
  • Cross-domain, cross-provider evaluation with released trajectory-level logs — unusually thorough for a single-author paper.
  • Auditable action-space design (six named levers, 729 configs) avoids the "arbitrary self-modifying harness code" problem attributed to Meta-Harness/HyperAgents.

Limitations

  • Main-matrix budgets (25–60 episodes/run) are, by the paper's own admission, provably below what a 729-action space needs.
  • OpenAI, an intended third provider, dropped out (API key rejected 2026-07-26) — "provider-agnostic" rests on just Ollama and Bedrock, at non-comparable budgets.
  • Tool-use domain is a synthetic mock CRM backend (τ-bench style), not a real production tool-use environment.
  • Unsupported-claim/hallucination metric is a lexical-overlap heuristic, scoped only to the retrieval domain.
  • Aggregate spend ($7.62) exceeded the paper's own $5 per-run cap when summed across the whole study.
  • No warm-start experiment (bandit/REINFORCE initialized from the static config) was actually run — proposed as future work only.

Questions for Further Exploration

  1. Does warm-starting bandit/REINFORCE from the DSPy-static configuration close the gap within a practical episode budget, as speculated but not tested?
  2. How does the static-vs-adaptive gap change under genuine task-distribution shift, the scenario RECIPE.md cites as the case for online control?
  3. Would a hierarchically-structured action space reduce the Ω(M) sample requirement enough to make online control competitive at 25–60 episodes?
  4. How sensitive are the reported success rates to the reward weights (ws, wv, wc, wu, w$, wℓ), which aren't swept or ablated?
  5. Does the unsupported-claim lexical-overlap heuristic actually track hallucination rate, or would a stronger detector shift which controller wins?
  6. On a real, non-synthetic tool-use system, does the DSPy-static advantage hold, or is it partly an artifact of the mock backend's narrower state space?
