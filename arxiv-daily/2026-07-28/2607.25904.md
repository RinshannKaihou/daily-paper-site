> **一句话总结：** 本文提出交互式奖励智能体 IRA，用"先提出任务完成条件、再调用系统/应用/GUI工具逐条核验环境真实状态"的 propose-then-verify 框架取代仅看首尾截图的被动式 VLM 评判器，在新建的 321 条轨迹基准 GUI-RewardBench 上取得 86.9% 准确率，比最强被动基线 DistRL（78.8%）高 8.1 个百分点，并能作为 RL 奖励信号在 OSWorld 上训练出 34.0% 的成功率（脚本奖励基线为 34.9%）。

> **TL;DR:** IRA reframes GUI task-completion judging as an interactive propose-then-verify process: a VLM first proposes task-grounded completion conditions, then a ReAct-style agent verifies each condition by calling system/application/GUI tools against the live post-execution environment (files, configs, app states), not just screenshots. On the new GUI-RewardBench (321 trajectories, 10 Ubuntu app categories), IRA with GPT-5.5 reaches 86.9% accuracy and 84.9% F1, beating the strongest passive VLM baseline DistRL (78.8% acc / 76.7% F1) and WebRL (47.0% acc, 0.6% recall). As an RL reward, IRA trains a Qwen3.6-35B-A3B GUI agent to 34.0% OSWorld success (vs. 34.9% with ground-truth scripts), and even on 33.5% on automatically generated OOD tasks with no evaluation scripts at all.

## 核心贡献

- **交互式"提出-核验"评估范式**：不再让 VLM 直接对首尾截图打分，而是先让 VLM 根据任务指令和首尾截图生成一组具体的、任务相关的完成条件（如"某文件应以 res.png 格式导出到桌面"），再针对每条条件用 ReAct 式的思考-动作-观察循环调用系统命令、应用专用校验工具、GUI 交互工具从真实环境中取证，直至证据充分才下达该条件的二元判决。
- **GUI-RewardBench 基准**：构建了 321 条在 Ubuntu 桌面环境下经多次重放验证为"状态稳定"的任务轨迹，覆盖 LibreOffice Calc/Impress/Writer、Chrome、GIMP、VS Code、Thunderbird、VLC、OS 级配置及多应用协作等 10 个类别，并按验证难度分为可见状态（40 条）、隐藏状态（89 条）、产物核验（192 条）三类。
- **全面超越被动式评判基线**：在三种不同骨干模型（Qwen3.6-35B-A3B、GPT-5.4、GPT-5.5）上，IRA 均显著优于 WebRL、ZeroGUI、DigiRL、DistRL 等被动评判方法，且开源骨干 Qwen3.6 经 IRA 框架后可逼近甚至在召回率上超过闭源模型。
- **可作为可扩展的 RL 奖励信号**：把 IRA 用作在线策略优化中的奖励模型，在完全没有人工标注评测脚本的自动生成任务上仍能得到接近脚本奖励的训练效果（33.5% vs. 34.9%），证明该方法能把评估能力扩展到任意新任务而无需逐任务写脚本。
- **人机一致性验证**：在 855 条自动生成任务中抽样 100 条，IRA 判决与人工标注的一致率达 94.0%，Cohen's κ = 0.84（"几乎完全一致"），表明该框架在缺乏基准真值脚本时依然可靠。

## Key Contributions

- **Propose-then-verify evaluation paradigm**: instead of asking a VLM to directly judge success from initial/final screenshots, IRA first has a VLM (condition proposer) derive an explicit set of task-grounded completion conditions `C = P_θ(T, I_init, I_final) = {C_i}`, then verifies each condition via a ReAct loop `a_{i,t} = IRA(C_i, H_i^{t-1})` that calls tools against the actual post-execution environment state `S_env` until the accumulated evidence is sufficient to assign a binary verdict `y_i ∈ {0,1}`; the scalar reward is `r_ira = (1/N) Σ y_i`.
- **GUI-RewardBench**: 321 stable evaluation trajectories built via trajectory replay across multiple VM instances (327 candidates sampled, replayed 3x, 6 unstable ones dropped) using UI-TARS-1.5 and EvoCUA-8B as trajectory generators, spanning 10 Ubuntu desktop app categories with a mix of visible-state (40), hidden-state (89), and artifact-verification (192) tasks and paired ground-truth verification scripts.
- **Tool-equipped evidence acquisition**: three complementary tool groups — generic system tools (`execute_vm_command`, `get_vm_file`, `get_terminal_output`, `get_directory_listing`, `get_accessibility_tree`), application-specific verifiers (e.g., `check_word_file`, `check_excel_file`, `check_ppt_file`, `get_vlc_config`, `get_thunderbird_prefs`, `get_vscode_settings`), and GUI interaction tools (click/type/scroll via computer-use actions) — loaded on demand per application.
- **RL reward signal validated at scale**: replacing ground-truth evaluation scripts with IRA in an RL training pipeline (DART method, Qwen3.6-35B-A3B backbone) yields comparable OSWorld success rates, and extends to automatically-generated out-of-distribution tasks that have no evaluation scripts to begin with.
- **Human agreement study**: on 100 tasks sampled from an 855-task auto-generated pool, IRA (GPT-5.5 backbone) verdicts agree with independent human annotations at 94.0% (κ = 0.84), including category breakdowns (Chrome, VSCode, Thunderbird, GIMP, OS all ≥90.9%, with several at 100%; LibreOffice lower at 85.7%/κ=0.62).

## Methodology

IRA formalizes GUI task evaluation as a two-stage process operating on evidence `S = (S_traj, S_env)`, where `S_traj = (I_init, I_final)` are initial/final screenshots and `S_env` is the interactive post-execution environment (files, configs, app states, command outputs, accessibility trees).

1. **Condition proposal**: a VLM condition proposer `P_θ` reads the task instruction `T` plus `I_init`/`I_final` and emits a set of atomic, task-grounded completion conditions `C = {C_i}_{i=1}^N` — each a concrete, necessary requirement (e.g., a specific file's existence, a configuration value, an application setting, a GUI element's state). The system prompt explicitly forbids adding conditions beyond what the task requires.
2. **Iterative per-condition verification**: for each condition `C_i`, IRA runs a ReAct-style Thought→Action→Observation loop, maintaining a condition-specific history `H_i^t`. At each step it decides what evidence is missing, picks exactly one tool call `a_{i,t}`, receives an observation `o_{i,t} = Tool(a_{i,t}, S_env)`, and appends it to history. The prompt enforces an evidence hierarchy (visible states → screenshots; application states → specialized tools; hidden states → CLI/file tools; GUI inspection only as a last resort via the `computer` tool) and forbids repeated calls, speculation beyond evidence, skipping the Thought step, or multiple tool calls per turn. A condition is marked satisfied (`y_i=1`) only when the accumulated observations provide explicit environment-state evidence; ambiguous/unverifiable conditions default to unsatisfied (conservative evaluation).
3. **Aggregation**: the final reward is `r_ira = (1/N) Σ y_i`; for binary classification, rewards >0.8 are treated as "success." A dedicated `final_answer` tool outputs reward, verdict (Success/Partial Success/Failure), and reasoning exactly once per episode.

GUI-RewardBench itself is built by generating trajectories with two GUI agents (UI-TARS-1.5, EvoCUA-8B), replaying the recorded action sequences on multiple fresh VM instances, and keeping only trajectories whose final states are reproducibly stable across replays (321 of 327 candidates survived). Each retained trajectory is paired with its original task-specific evaluation script as ground truth. A separate automated task-generation pipeline (Appendix A.7) groups tasks by shared initial `config`, then prompts an LLM to synthesize new feasible instruction variants under the same environment setup, producing 855 additional tasks across nine app categories (used for the human-agreement study, not the main 321-trajectory benchmark).

## Results & Highlights

- **Main benchmark comparison (Table 1, GUI-RewardBench, 321 trajectories)**: the strongest passive VLM baseline, DistRL (Wang et al. 2025a), achieves 78.8% accuracy / 76.7% F1. IRA with GPT-5.5 reaches **86.9% accuracy and 84.9% F1** (TP=118, FP=8, TN=161, FN=34) — an +8.1pp accuracy gain over DistRL. IRA with GPT-5.4 gets 85.4% acc / 84.2% F1, and IRA with the open-source Qwen3.6-35B-A3B backbone gets 85.0% acc / 83.9% F1 with the highest recall of all methods (79.6%). By contrast, WebRL (Qi et al. 2025) — designed for web agents — collapses on this benchmark to 47.0% accuracy with just 0.6% recall (TP=1, FN=170), and ZeroGUI reaches only 67.0% accuracy.
- **Matched-backbone ablation (Table 2)**: holding the backbone fixed, IRA improves accuracy over the VLM-only setting by **+8.4pp (GPT-5.5: 78.5%→86.9%)**, **+9.1pp (GPT-5.4: 76.3%→85.4%)**, and **+6.2pp (Qwen3.6-35B-A3B: 78.8%→85.0%)**, at a cost of ~3.3 tool-call steps for the GPT backbones (14.9K/59.5K median/mean tokens for GPT-5.5) versus 8.2 steps for Qwen3.6 (~139.1K mean tokens), which leans much more heavily on GUI exploration (50.5% of tool calls vs. 6.4% for GPT-5.5).
- **RL training with IRA rewards (Table 3)**: using the DART RL method with Qwen3.6-35B-A3B as the policy, training on OSWorld tasks with ground-truth scripts yields 34.9% OSWorld success; substituting IRA as the reward on the *same* OSWorld tasks yields 34.0% (only 0.9pp below the oracle); training on automatically generated, out-of-distribution tasks with IRA as the *only available* reward (no scripts exist for these tasks) still yields 33.5% — just 1.4pp below the ground-truth-script setting.
- **Human–IRA agreement**: on 100 tasks sampled from 855 auto-generated instructions, IRA (GPT-5.5) agrees with independent human labels 94.0% of the time, Cohen's κ = 0.84. The contingency table shows 0 cases where humans marked success but IRA marked failure, versus 6 cases of the reverse (human failure, IRA success) — i.e., IRA's residual errors skew toward false positives rather than false negatives on this sample.
- **Qualitative case studies**: e.g., a LibreOffice Calc task completed via command line without the visible spreadsheet view refreshing — the VLM-only evaluator wrongly predicts failure from the stale screenshot, while IRA inspects the underlying file and verifies the updated values; a VLC "minimal interface persists after restart" task where IRA locates and checks the Qt config file (`qt-minimal-view=1`) rather than trusting the final screenshot alone.
- **Failure mode analysis (Appendix A.11)**: remaining IRA errors are attributed mainly to *misaligned completion-condition formulation* rather than insufficient evidence gathering — e.g., accepting "Standard" Chrome Safe Browsing when "Enhanced" was required (wrong protection granularity), rejecting a valid dark terminal theme because it wasn't exactly "Solarized Dark" (over-literal interpretation), and crediting a GIMP horizontal-flip operation as complete without checking whether the edited image was actually saved (missed persistence requirement).

## Critical Assessment

**Novelty**: The propose-then-verify decomposition is a clean and well-motivated idea — separating "what must be true" (task-grounded condition proposal) from "how do we check it" (tool-mediated evidence acquisition) directly targets a real, previously under-addressed gap: passive VLM judges cannot see file contents, configs, or app state that don't appear in a screenshot. This is a genuine, non-trivial architectural contribution rather than a prompt-engineering tweak.

**Rigor**: The evaluation protocol is reasonably careful — GUI-RewardBench trajectories are filtered for replay-stability (327→321 after 3x replay), and each live evaluation run is scored against the task-specific ground-truth script's *live* re-execution (not the originally recorded label), which correctly accounts for UI drift and non-determinism. The ablation study (Table 2, Figure 6) isolating VLM-only vs. GUI-only vs. full IRA under matched backbones is a good design that reveals a paper-specific nuance the authors are honest about: "GUI interaction helps only when the backbone uses it reliably" — Qwen3.6's GUI-only precision improves but recall collapses sharply, showing that unstructured interaction alone can hurt an unreliable backbone, and that the full propose-then-verify structure (not mere environment access) is what fixes this.

**Reproducibility**: The appendix documents the full tool set (Table 4), hyperparameters (temperature 0.0, max 30 evaluation steps, retry policy), and evaluation formulas (Cohen's κ derivation), which is above-average transparency. However, GUI-RewardBench's construction relies on two specific trajectory-generation agents (UI-TARS-1.5, EvoCUA-8B) and Ubuntu-specific VM tooling, and the project page/code release status is not stated in the visible text — reproducing the exact 321-trajectory benchmark by a third party would require access to the same VM images and generation pipeline.

**Significance / red flags**: A specific weak-baseline concern: WebRL is explicitly noted by the authors as "designed for web-related tasks," which plausibly explains its catastrophic 0.6% recall on this desktop-app benchmark — it is included as a comparison point but is arguably a mismatched baseline for a desktop GUI-RewardBench, inflating IRA's apparent margin over "existing evaluators" in aggregate even though the more informative comparison is against DistRL (78.8%/76.7% F1), the strongest passive method. The RL experiment (Table 3) has only three settings and no repeated seeds/variance reported, so the "34.0% vs. 34.9%" (only 0.9pp gap) and "33.5%" OOD numbers, while suggestive, rest on single runs rather than statistically characterized differences — a missing ablation the paper does not address. The failure-case appendix (A.11) is unusually candid, explicitly cataloguing IRA's own false positives/negatives (wrong protection tier, over-literal theme matching, missed save/persistence requirements) rather than only showcasing successes — a genuine strength for intellectual honesty, but it also reveals that IRA's errors are systematic (condition-formulation ambiguity) rather than incidental, meaning the reported 86.9%/94.0% numbers likely represent a ceiling that is sensitive to how literally user instructions are read.

## Strengths

- Directly addresses a concrete, demonstrated failure mode of passive VLM evaluators (Figure 1's LibreOffice Impress export example is a clear, non-contrived illustration).
- Consistent gains across three backbones of different scale/openness (Qwen3.6-35B-A3B, GPT-5.4, GPT-5.5), showing the framework's benefit is not backbone-specific.
- New benchmark (GUI-RewardBench) with an explicit, principled category taxonomy (visible/hidden/artifact-verification) rather than an undifferentiated task pool.
- Practical downstream validation: IRA is shown to substitute for hand-written RL reward scripts with only a small (~1pp) success-rate gap, including on genuinely out-of-distribution generated tasks with no scripts available at all.
- Unusually transparent error analysis with concrete, labeled failure categories and step-by-step trajectory traces.

## Limitations

- Verification cost is non-trivial and backbone-dependent: Qwen3.6 needs ~8.2 tool-call steps and ~139K mean tokens per task versus ~3.3 steps/~60-120K tokens for GPT backbones — a real efficiency/accuracy trade-off not fully resolved.
- Remaining errors are dominated by completion-condition misalignment (wrong granularity, over-literal semantic matching, missed implicit persistence requirements) — a class of error that is not obviously fixable by more tool access, suggesting a ceiling tied to instruction ambiguity resolution rather than evidence acquisition.
- The 321-trajectory benchmark, while diverse (10 categories), is confined to Ubuntu desktop applications; generalization to mobile or web-only GUI environments is not evaluated in this paper.
- RL results are reported as single point estimates (34.9% / 34.0% / 33.5%) without variance across seeds, making it hard to assess whether the gaps are statistically meaningful.
- The paper does not report the cost/latency of the condition-proposal step itself in isolation, nor a sensitivity analysis of how condition-proposal quality (vs. verification quality) individually drives the accuracy gains.

## Relevance

该工作提供了一个可迁移的"提出条件-工具核验"范式，对做 GUI/多模态智能体自动化评测、RL 奖励建模或需要将被动式 VLM 评审升级为可验证证据链路的研究方向具有直接参考价值，其失败案例分析（条件粒度错配、过度字面解读）也提示了指令消歧和隐式需求推断是后续改进的重点方向。

## Questions for Further Exploration

- How does IRA's accuracy degrade as task complexity increases (e.g., beyond the 50 trajectories with >20 steps in GUI-RewardBench), and does verification cost scale linearly or worse with trajectory length?
- Could the condition-proposal step itself be made interactive (e.g., asking clarifying questions or considering multiple candidate interpretations) to address the dominant "misaligned completion condition" failure mode identified in Appendix A.11?
- How sensitive is the 94.0% human-agreement figure to the choice of GPT-5.5 as both the reward-agent backbone and the trajectory-generation critic — would agreement remain high with a different, non-GPT verifier judging GPT-5.5-generated conditions?
- Would IRA's tool-based verification transfer to web or mobile GUI environments where "environment state" (cookies, app storage, mobile OS settings) differs structurally from the Ubuntu desktop file/config/VM-command primitives used here?
- Since WebRL's 0.6% recall stems from a domain mismatch (web-agent training vs. desktop benchmark), would a fairer set of passive baselines (e.g., a VLM judge specifically fine-tuned on desktop screenshots) narrow the reported gap, and is the paper's headline "outperforms existing evaluators" framing sensitive to this baseline choice?
