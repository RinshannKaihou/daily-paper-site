Interactive Reward Agent: GUI Task Evaluation via Environment‑State Verification

Key Finding

IRA judges GUI task completion by proposing explicit conditions, then verifying each against live environment state — not screenshots alone.

本文提出交互式奖励智能体 IRA，用"先提出任务完成条件、再调用系统/应用/GUI工具逐条核验环境真实状态"的 propose‑then‑verify 框架取代仅看首尾截图的被动式 VLM 评判器。

Why This Matters

Gives GUI-agent and RL-reward researchers a transferable propose-then-verify evaluator, cutting reliance on hand-written per-task success scripts.

Critical Edge ↓ limitations

The RL reward gaps (34.9% vs. 34.0% vs. 33.5% success) are single-run point estimates with no seed variance — the headline gains may not be statistically real.

Methodology 01

propose → verify → aggregate

IRA splits GUI-task judging into two stages over evidence S = (Straj, Senv): paired init/final screenshots plus the live post-execution environment (files, configs, app state, command output, accessibility tree).

C = Pθ(T, I_init, I_final) = {Cᾑ}  →  aᾑ,t = IRA(Cᾑ, Hᾑ^(t-1))  →  r_ira = (1/N)Σyᾑ
  • 1 · Condition proposalA VLM reads the instruction + screenshots and emits atomic, task-grounded completion conditions (e.g. "file exported as res.png to Desktop"). Adding conditions beyond the task is explicitly forbidden.
  • 2 · Per-condition verificationA ReAct Thought→Action→Observation loop calls one tool at a time against the real environment, following an evidence hierarchy: screenshots → specialized app verifiers → CLI/file tools → GUI inspection as last resort. Ambiguous evidence defaults to unsatisfied.
  • 3 · AggregationReward is the mean of binary per-condition verdicts; a dedicated final_answer tool reports reward, verdict, and reasoning exactly once.

Cost trade-off: GPT backbones need ~3.3 tool-call steps (~15K–60K tokens); Qwen3.6 needs ~8.2 steps (~139K mean tokens) and leans on GUI exploration for 50.5% of calls vs. 6.4% for GPT-5.5.

Human–IRA agreement (100 of 855 auto-generated tasks, GPT-5.5 backbone): 94.0% agreement, Cohen's κ = 0.84. All 6 disagreements were human-fail/IRA-success — zero were human-success/IRA-fail, i.e. residual errors skew toward false positives.

Strengths +

what holds up
  • Targets a concrete, demonstrated failure mode: passive VLM judges can't see file contents, configs, or app state absent from a screenshot (Fig. 1's LibreOffice Impress export case).
  • Consistent gains across three backbones of different scale/openness (Qwen3.6-35B-A3B, GPT-5.4, GPT-5.5) — the benefit isn't backbone-specific.
  • New benchmark with a principled taxonomy (visible / hidden / artifact-verification) rather than an undifferentiated task pool.
  • Substitutes for hand-written RL reward scripts within ~1pp, including on genuinely out-of-distribution tasks with no scripts at all.
  • Unusually candid error analysis with labeled failure categories and step-by-step traces (Appendix A.11).

Limitations −

where it strains
  • Verification cost is backbone-dependent and non-trivial — Qwen3.6 burns ~2.5× the tool-call steps and far more tokens than the GPT backbones.
  • Remaining errors are dominated by condition-formulation mismatches (wrong granularity, over-literal matching, missed persistence checks) — not fixable by more tool access.
  • The 321-trajectory benchmark is confined to Ubuntu desktop apps; mobile/web GUI generalization is untested.
  • RL results are single point estimates (34.9% / 34.0% / 33.5%) with no seed variance, so statistical significance of the gaps is unclear.
  • WebRL (0.6% recall) is a domain-mismatched baseline for a desktop benchmark, arguably inflating IRA's aggregate margin versus "existing evaluators."

Questions for Further Exploration ?

  1. How does accuracy degrade as trajectory length grows past the benchmark's 50 tasks with >20 steps, and does verification cost scale linearly with it?
  2. Could condition proposal itself become interactive (clarifying questions, multiple candidate readings) to attack the dominant "misaligned condition" failure mode?
  3. How sensitive is the 94.0% human-agreement figure to using GPT-5.5 as both the reward-agent backbone and the trajectory-generation critic?
  4. Would tool-based verification transfer to web or mobile GUIs, where "environment state" (cookies, app storage, OS settings) differs structurally from Ubuntu desktop primitives?
  5. Since WebRL's collapse stems from domain mismatch, would a fairer passive baseline (a VLM judge fine-tuned on desktop screenshots) narrow IRA's reported margin?
