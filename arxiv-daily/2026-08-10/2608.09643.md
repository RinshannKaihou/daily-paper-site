> **一句话总结：** 作者在五个开源代码模型的残差流上各训练了一个线性探针（仅用 SVEN 的四类 Python CWE），零样本迁移到 PatchEval 中 147 个 CWE 类型完全未见过的真实 CVE 后，探针把「有漏洞函数」排在「其补丁版本」之上的成对胜率为 61–67%，稳定高于同一模型任何 prompt（no-shot / few-shot / CoT）读 logits 得到的 33.6–57.8%，而模型写出来的 YES/NO 文字裁决在 72–97% 的成对样本上完全相同、根本无法区分两者。

> **TL;DR:** A single logistic probe fit on residual-stream activations of an open-weight code reviewer (Qwen2.5-Coder 7B/14B, DeepSeek-Coder 33B, Devstral-Small, Llama-3.1-8B), trained only on four SVEN Python CWEs (022/078/079/089), transfers zero-shot to 147 single-function PatchEval CVEs whose CWEs were never seen in training and ranks the vulnerable function above its own fix 61–67% of the time (Wilson 95% CI above 0.5 for all five models). The same model's prompted YES/NO verdict read from logits reaches only 33.6–57.8% — at or below chance for no-shot and few-shot — and read as written text it emits the *identical* verdict on the vulnerable and fixed function in 72–97% of pairs, so it cannot rank them at all. In-distribution the probe hits AUC 0.771–0.846 and accuracy 0.717–0.770 at τ=0.5 versus prompted accuracy 0.488–0.524, a 21–28 point gap. Worth reading if you care about activation probes as a cheap self-hostable security triage layer; the OOD effect is real but modest, and the probe's edge over chain-of-thought specifically is significant on only 1 of 5 models.

## 核心贡献

- **提出一个可自托管的安全审查设定**：闭源编码 agent（Claude Code、Cursor、Codex）写的代码无法读内部状态，但可以让一个**开源模型作为 reviewer** 去读 agent 的输出——reviewer 自己的激活是可读的。问题被明确成「读激活能否恢复出『问同一个模型』所丢失的安全信号」。
- **跨 CWE 类型的泛化实验设计**：训练只用 SVEN 里 Python 覆盖充分的四个 CWE（路径穿越 022、命令注入 078、XSS 079、SQL 注入 089），评测用 PatchEval 中**整个 CWE 标签集与训练四类完全不重叠**的 234 个真实 Python CVE，并且训练/评测划分与 5 折交叉验证都按**仓库分组**（GroupKFold），避免代码重复导致的泄漏。
- **给出「提示词读法比提示词本身更重要」的证据**：连续的 YES/NO logit 比值几乎从不打平（agree ≤1%），因此永远可排序但接近随机；模型写出来的文字裁决则在绝大多数成对样本上完全一致（72–97% 打平），成对准确率只有 1–13%。探针的优势本质上是「它总能给出一个连续分数」。
- **五个模型、四个架构族上一致复现**，且比较时对提示词一方取「每个模型的最优 prompt×读法」，用配对 McNemar 检验，人为让基线更强。
- **诚实报告负结果**：C/C++ 为主的 CWE 类别在初步实验中处于随机水平；探针对 CoT+logits 的优势在 5 个模型中只有 1 个显著。

## Key Contributions

- **Framing:** treats an open-weight model as a *readable proxy reviewer* over a closed-weight coding agent's output — the deployment story is a post-write hook that flags diffs worth human re-review, not a full detector.
- **A single linear probe per model** on the residual stream (hooked at the input of `layers[L].input_layernorm` via nnsight), with a sweep over layer, token pooling (mean / max / last / sliding-window-max, window 16), and L2 strength C ∈ {1e-2, 1e-1, 1}, selected by 5-fold GroupKFold AUC. All five models select C=1e-2; selected layers are early-to-mid (7 for DeepSeek-33B, 11 for Qwen-7B, 17 for Llama-3.1-8B, 21 for Qwen-14B and Devstral).
- **A strict OOD protocol:** train on SVEN-Python, test zero-shot on PatchEval CVEs with *no* CWE overlap, project-grouped splits, paired win-rate with Wilson intervals and exact-binomial sign tests, ties dropped.
- **A carefully constructed prompted comparator:** 3 prompts × 2 readouts, with the probe compared against each model's *best* configuration under paired McNemar (a tie counts as an incorrect prompted verdict).
- **Diagnosis of why prompting fails here:** the failure is not weak prompts but verdict collapse — the model says the same thing about the vulnerable and the patched function.

## Methodology

**Reviewer models.** Five instruct-variant open-weight code LLMs across four architecture families: Qwen2.5-Coder 7B and 14B, DeepSeek-Coder 33B, Devstral-Small-2505, Llama-3.1-8B. All loaded in float16 with no quantisation on a single 80 GB H100, explicitly to avoid a quantisation confound across the comparison.

**Data.** Training: SVEN (He & Vechev, 2023), restricted to the four CWEs with substantial Python coverage — CWE-022, 078, 079, 089 — which the author calls SVEN-Python (152-sample held-out eval split). SVEN natively supplies paired before-fix (vulnerable) / after-fix (secure) functions, which is what makes a paired ranking metric possible. Evaluation: 234 Python CVEs from PatchEval (Wei et al., 2025) whose *entire* CWE label set is disjoint from the four training CWEs. The remaining 169 overlapping CVEs form a "seen" reference reported only in Appendix A.2.

**Probe fitting.** Residual-stream activations are extracted with nnsight; a logistic probe is trained in PyTorch, with layer/pooling/L2 chosen by 5-fold GroupKFold AUC in scikit-learn. Crucially, *both* the train/eval split and the CV folds are grouped by repository — every project lands entirely in train or entirely in eval — citing Allamanis (2019) and Ding et al. (2025) on duplication-driven inflation of code-model evaluations.

**Metric.** For each CVE, score the vulnerable function (p̂_vul) and its post-fix counterpart (p̂_fix); the CVE counts as a win if the risk gap p̂_vul − p̂_fix > 0, with exact ties dropped. The headline slice is the 147 CVEs fixed by changing a **single** function, since the probe scores one function at a time and that slice needs no pairing heuristic. For multi-function patches, vulnerable functions are matched to fixes by file path and definition name (unmatched vulnerable functions dropped) and matched-pair gaps are averaged into one risk gap per CVE, keeping the CVE as the unit of analysis.

**Prompted comparator.** The prompt asks the model, as a security code reviewer, whether a function contains a vulnerability and to answer YES or NO, in three variants: no-shot, few-shot (worked vulnerable/fixed examples from *held-out* weakness types), and chain-of-thought ending in an explicit verdict (generated with vLLM). Two readouts: (a) the renormalised YES-vs-NO probability at the answer token — a continuous score directly comparable to the probe; (b) the literal "yes"/"no" string the model writes. Comparison against the probe uses paired McNemar on the same CVEs against each model's best prompt-and-readout.

## Results & Highlights

- **OOD headline (147 unseen single-function CVEs, paired win-rate):** Devstral-Small 66.9% (CI 58.6–74.3, p=9.9e-05), Qwen2.5-Coder 14B 66.2% (57.8–73.7, p=2.4e-04), Llama-3.1-8B 63.4% (55.2–70.9, p=0.002), Qwen2.5-Coder 7B 61.2% (52.8–68.8, p=0.011), DeepSeek-Coder 33B 60.8% (52.7–68.5, p=0.012). Every Wilson interval clears the 50% chance line, but the two weakest models' lower bounds are only 52.7–52.8 — a thin margin on n=147.
- **Probe vs. best prompting, same CVEs (Table 3):** Qwen2.5-Coder 7B probe 61.2% vs. no-shot 43.8%, few-shot 44.5%, CoT 57.8% (+3.4 over its best prompt); DeepSeek-Coder 33B probe 60.8% vs. 33.6 / 35.4 / 44.7 (+16.1 over its best); Devstral-Small 66.9% vs. 48.6 / 45.6 / 53.1 (+13.8); Llama-3.1-8B 63.4% vs. 50.3 / 49.3 / 56.2 (+7.2); Qwen2.5-Coder 14B 66.2% vs. 49.0 / 56.5 / 55.5 (+9.7). The probe wins numerically on all 5 models and all 3 prompts, but by paired McNemar it significantly beats no-shot on only 3/5, few-shot on 4/5, and **CoT on only 1/5 (DeepSeek-Coder 33B)** — the honest reading is that the clear gap is over naive prompting, not over reasoning-then-answer.
- **In-distribution (SVEN-Python, n=152, Table 1):** probe AUC 0.846 / 0.821 / 0.844 / 0.771 / 0.787 and accuracy@0.5 of 0.763 / 0.737 / 0.770 / 0.737 / 0.717 across the five models, versus prompted YES/NO accuracy of 0.524 / 0.518 / 0.488 / 0.500 / 0.500 — i.e. the prompted baseline is at pure chance on a balanced paired set, a **21–28 point** gap. Note DeepSeek-Coder 33B's prompted accuracy of 0.488 is *below* chance.
- **Verdict collapse (Appendix A.3, Table 6):** the written-token readout produces the same verdict on both functions in 90–97% of pairs (no-shot), 86–93% (few-shot), 72–86% (CoT); the fully correct pattern (YES on vulnerable, NO on fix) occurs on only **1–13%** of pairs over the full slice. The logit readout almost never ties (agree ≤1%) but sits at 34–58% correct, i.e. at or below chance. This is the paper's most interesting single result: prompting doesn't just underperform, it is *unrankable*.
- **Full unseen set (n=234, single- + multi-function):** 66.4% (Qwen-7B), 69.4% (Qwen-14B), 61.6% (DeepSeek-33B), 64.7% (Devstral), 66.7% (Llama-3.1-8B), all p<0.001 — slightly *higher* than the single-function slice, so the pairing heuristic does not appear to be inflating the headline.
- **Seen-CWE reference (n=169, Appendix A.2):** 75.9 / 79.8 / 64.5 / 67.1 / 66.3% — roughly 10–14 points above the unseen slice for the Qwen models, quantifying the generalisation cost. The author explicitly flags that the seen slice mixes single- and multi-function CVEs so it is not a strict like-for-like comparison.
- **Compliance quirk:** DeepSeek-Coder 33B refuses or fails to emit a verdict on 16% (no-shot), 9% (few-shot), 2% (CoT) of items, so its prompted win-rates are computed on a smaller compliant set — which arguably makes its dramatic 33.6% no-shot number less damning than it looks.

## Authors & Credibility

Single author, Ivan Wiryadi, listed as **Independent** (no institutional affiliation), correspondence to a personal Gmail address. Venue is the Second Workshop on Technical AI Governance Research (TAIGR) @ ICML 2026 — a workshop paper, so lighter peer review than a main-track submission, and the 4-page main body reflects that. The paper is technically literate about the relevant literature: it cites the right probing lineage (Alain & Bengio; Azaria & Mitchell; Marks & Tegmark; Orgad et al.; McKenzie et al. 2025 for the high-stakes-interaction probe and the logit-readout method), the right code-security baselines (Ullah et al. ICSE 2025), and correctly positions itself against LPASS (Ibanez-Lissen et al. 2025), which probed compressed LLMs on C/C++ while training and testing on the *same* weakness types. The LLM-usage statement is unusually forthright: Claude was used "extensively" for writing, editing, coding, and parts of the analysis, with the author retaining design and framing decisions. No code or data release is mentioned anywhere in the paper.

## Critical Assessment

**Novelty (moderate).** The core mechanism — a linear probe on the residual stream beats the model's own verbalised answer — is by now a well-established result in the honesty/hallucination literature, and LPASS already applied linear probes to vulnerability detection. The genuine increments here are narrow but real: (i) Python instead of C/C++, (ii) *held-out CWE types* rather than train/test on the same weakness classes, (iii) real disclosed CVEs from PatchEval rather than synthetic benchmarks, and (iv) the paired vulnerable-vs-fix framing that exposes verdict collapse. That is an honest, well-scoped delta for a workshop paper, not a conceptual breakthrough.

**Rigor (good for the venue, with one soft spot).** The project-grouped splits are the right call and are explicitly motivated; the Wilson intervals, sign tests, and paired McNemar are appropriate; giving the prompting baseline its best-of-6 configuration and counting ties as prompting errors are both choices that cut against the author's own thesis, which is a good sign. The soft spot is that the probe's hyperparameters (layer, pooling, C) were swept by CV AUC on SVEN, while the prompted comparator gets no equivalent search budget — three hand-written prompts is a shallow search next to a layer×pooling×C sweep. The "tie counts as incorrect" rule is defensible for a ranking task but does penalise the token readout by construction; the author partly defuses this by reporting the logit readout separately, which never ties and is still beaten.

**Reproducibility (weak).** No code, no probe weights, no prompt texts verbatim, no data-processing scripts. The stack (nnsight, vLLM, HF Transformers, scikit-learn, float16 on one H100) and the selected layer/pooling per model in Table 4 are enough to make a re-implementation plausible, but the exact SVEN-Python filtering and the PatchEval CWE-disjointness filter would have to be reconstructed by hand, and the paired-function matching by file path and definition name is exactly the kind of heuristic where two implementations diverge.

**Significance (limited but directionally useful).** A 61–67% paired win-rate is not a deployable detector, and the author says so: the probe only ranks a function against its own fix, which is a comparison you do not have at review time. The concrete deployment claim in the abstract — a self-hosted control that "flags changes worth re-reviewing" — requires a calibrated absolute threshold that the paper does not produce. There is also no comparison against the obvious non-LLM incumbent: **no static analyzer (Bandit, Semgrep, CodeQL) is run on the same PatchEval slice**, even though the intro cites CASTLE to argue static analyzers are unreliable. That omission is the single biggest missing baseline; a linear probe at 63% is only interesting if Semgrep does not already do better on these CVEs for free.

**Red flags / paper-specific concerns.**
- The abstract's "beats the same model's prompted YES/NO win-rate... under every prompt we try" is true *numerically* but the significance table shows CoT survives on 4/5 models; the phrasing invites over-reading, though the Limitations section then admits "its advantage over the strongest prompting... is narrow and not always significant."
- DeepSeek-Coder 33B's prompted numbers are computed on a reduced compliant subset (up to 16% no-verdict), so the model with the largest apparent probe advantage is also the one whose baseline is most compromised by instruction-following failure rather than by security blindness.
- The C/C++-dominant CWEs "scored at chance in preliminary runs" and were dropped from training — this is disclosed, but it means the four surviving CWEs (path traversal, command injection, XSS, SQLi) are all lexically distinctive injection-style flaws. A probe that fires on `os.system(` / `eval(` / raw string concatenation into SQL would score well in-distribution and might partially transfer via superficial surface features; there is **no shallow-feature control** (e.g. a bag-of-tokens or TF-IDF logistic baseline on the same functions) to rule that out.
- No ablation on probe architecture (the author names attention-based probes as untried) and no random-direction / shuffled-label control to establish the null distribution of the win-rate metric.
- n=147 for the headline; the two lowest models' CIs bottom out at ~52.7%, so the "every model beats chance" claim rests on a handful of pairs for those two.

## Strengths

- The evaluation design anticipates the standard criticisms of code-model papers: project-grouped splits against duplication leakage, held-out CWE types against memorised weakness signatures, real CVEs instead of synthetic micro-benchmarks, and a seen-CWE reference slice quarantined in the appendix rather than smuggled into the headline.
- The comparator is deliberately made strong (best-of-3-prompts × 2-readouts per model, paired McNemar), and the author states outright that "picking the comparator's best configuration only makes the test harder for the probe."
- The verdict-collapse finding (72–97% tie rate; 1–13% fully-correct pairs) is a clean, quantified, and independently useful observation about why LLM-as-security-reviewer setups underperform — it reframes the failure as a *readout* problem rather than a knowledge problem.
- Consistency across four architecture families and a 7B–33B size range makes the effect unlikely to be a single-model artifact.
- Limitations are stated without hedging, including the negative C/C++ result and the non-significance of the probe's edge over CoT.

## Limitations

- **Paired-only signal.** The metric requires access to both the vulnerable function and its fix. Real review has no fix to compare against, so the paper measures a ranking ability that the stated use case cannot consume; turning it into a calibrated absolute-threshold detector is named as the main remaining step.
- **Small and narrow data.** Training is four CWEs from SVEN with a 152-sample eval split; evaluation is 147 (headline) / 234 (full) CVEs. The author concedes "we also worked with limited set data."
- **Python only**, and only for injection-style weaknesses; C/C++-dominant classes were at chance and it is unresolved whether that is a language, sample-size, or weakness-type effect.
- **No static-analysis baseline** and no shallow-lexical-feature control, so the probe's advantage is established only against the same model's prompting.
- **Not tested on agent-generated code.** The whole motivation is triaging what Claude Code / Cursor / Codex emit, yet the corpora are human-written open-source functions and their historical patches; wiring the probe into a post-write hook is explicitly future work.
- **Probe architecture unexplored** — logistic only, no attention probes, no probe-architecture comparison.
- **No artifact release**, which for a 4-page workshop result with hand-tuned per-model layers is a meaningful barrier.

## Relevance

如果你关注「用可解释性方法（linear probe / activation steering）为 LLM 输出做安全或可靠性护栏」，这篇提供了一个数据干净、检验规范的小规模证据点：模型内部状态确实携带了它嘴上说不出来的安全信号。对做 LLM-as-judge / 代码审查 agent 的人，附录里「文字裁决在 72–97% 的成对样本上完全一致、而 logit 几乎从不打平」这一条比主结果更有直接的工程启发——它说明评测时读 logit 还是读文本，可能比换提示词重要得多。

## Questions for Further Exploration

1. How does a bag-of-tokens / TF-IDF logistic baseline on the same functions score on the 147 unseen CVEs? Without that control it is hard to separate "the model represents security" from "injection-flaw patches change distinctive tokens."
2. How does Semgrep / CodeQL / Bandit score on the same paired slice? The probe's practical value depends entirely on whether it adds signal over the free incumbent, not over the model's own prompt.
3. Can the paired win-rate be converted into a calibrated single-function score — e.g. by calibrating on a held-out distribution of *benign* functions from the same repositories — and what precision/recall does that yield at a review-triage operating point?
4. Does the probe direction transfer *across models* (fit on Qwen-7B, applied to Llama-8B after an affine map), or is it model-idiosyncratic? That would say a lot about whether there is a shared "insecure code" representation.
5. Why do the selected layers vary so much (7 for DeepSeek-33B vs. 21 for Qwen-14B and Devstral), and is the signal actually localised or is the layer sweep fitting noise on a 152-sample CV?
6. On actual coding-agent output (the stated deployment target), what fraction of flagged diffs are true positives — and does the probe fire on the agent's characteristic failure modes, which may differ distributionally from historical human CVEs?
7. Would training on all SVEN CWEs including the C/C++-dominant ones, with more data, lift those classes off chance — separating the language effect from the sample-size effect the author leaves open?
