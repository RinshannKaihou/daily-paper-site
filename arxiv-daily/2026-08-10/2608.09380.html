01Methodology

Evolution runs outside the execution path.

πobsπplanπmemπactπverπrecπstopπbud observation · planning · memory · action · verification · recovery · stopping · budget

A long-horizon task is an executable contract g = ⟨d, U_g, M_g, S_g, V_g, β_g⟩ — objective, permitted executors, metrics, admissible evidence sources, verification protocol, and resource budget. The agent loop is a state recursion x_{t+1} = f_π(x_t, o_t, a_t, e_t) governed by the eight Loop Policy components, optimized as a constrained program: maximize value score q(π) subject to verification risk and resource-budget constraints.

Archived or online traces are distilled by an operator Φ into typed evidence — each item pointing at one specific policy component, with direction and measured metric change.

An LLM generator proposes candidate Bundles; Champion–Challenger paired evaluation runs them under identical task conditions; a conjunctive four-constraint gate (benefit ∧ evidence-quality ∧ tail-risk ∧ resource-cost) decides release. Two governance rules make attribution clean: registration ≠ release ≠ activation — a candidate gets a version index only to enter history, and only gate-passed release plus task-boundary activation touch execution. One Champion controls a run start-to-finish. Online mode stages updates with canary rollback; offline mode runs multi-generation population search, then freezes the winner.

03Strengths & Limitations

Strengths

  • Registration ≠ release ≠ activation — task-boundary activation guarantees every trace attributes to exactly one policy version, which is what makes paired evaluation meaningful.
  • Careful formalization — task contract, trace, evidence tuple, Bundle, and typed histories are all defined precisely enough to implement.
  • Honest cost reporting — inference cost including evolution overhead appears in a dedicated table rather than hidden.
  • Both Δ columns reported — the weak-baseline problem is at least visible to a careful reader.
  • Risk metrics shown — drawdown and survival alongside returns; improvement isn't pure variance-seeking.
  • Code released at github.com/yoyoshikc/OpenLoopEvolve.

Limitations

  • Single benchmark, single model, three seeds — no evidence of cross-task, cross-host, or cross-model transfer, despite portability being the central claim.
  • The evolved policy is never shown — no qualitative example of what the LLM changed, no lineage diagram, no per-component analysis.
  • Total tokens more than double vs native, and the reported total undercounts candidate-generation calls.
  • OLE-offline is a frozen policy at evaluation — really offline loop search, not deployment-time self-evolution; only the weaker online mode tests that story.
  • Gate thresholds, rollback frequency, and pass-rate unreported — the governance machinery is impossible to assess empirically.
  • No self-evolution baseline run (Reflexion, ExpeL, SE-Agent, AFlow) — comparison is only against no-evolution controls.

04Questions for Further Exploration

Were the archived traces used by OLE-offline drawn from the same YC-Bench tasks/seeds used for final evaluation? How much of the +88% survives a held-out split?
What does an ablation with the robust gate disabled (accept every Challenger) look like? If ungated evolution performs comparably, the "verifiable" claim collapses.
How many of the 12 online candidates passed the gate, and how many triggered CanaryMonitor rollback? A headline feature with zero reported statistics.
Does the evolved Loop Policy transfer? Loading the YC-Bench-evolved Bundle into WebArena or τ-bench would test the portability claim.
Would a single LLM rewrite of the loop prompt from the same evidence recover most of the gain at a fraction of the 24–30M evolution tokens?
Why does Fixed-π0 underperform the native loop by 29%? If π0 is simply a bad prompt, part of the "evolution gain" may be recovery back to native competence.
