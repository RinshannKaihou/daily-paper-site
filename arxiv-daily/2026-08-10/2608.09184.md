> **一句话总结：** 针对基于命令行的 SONiC 网络运维场景，本文提出执行驱动的双路径持续学习智能体——提案侧通过可检索的操作记忆提升候选可行动作覆盖率，选择侧通过会话级 LoRA 自适应后果预测器改善条件选择质量——在 140 轮多回合 SONiC 操作会话上同时提升了候选覆盖率和 top-1 执行成功率。

> **TL;DR:** A dual-path execution-grounded agent for CLI-based SONiC network operations separates candidate proposal from consequence-aware selection: the proposal-side path abstracts reusable operational lessons into retrievable memory (improving feasible-action coverage without touching the proposal LLM), while the selection-side path applies session-level LoRA updates to a Qwen3-0.6B consequence predictor using real SSH feedback; over 140-turn multi-turn SONiC sessions with Qwen3-1.7B/8B/14B proposal models, the full framework beats single-proposal, self-consistency, and no-adaptation baselines on top-1 execution success, and the two adaptation paths yield complementary gains.

## 核心贡献

- **执行驱动的双路径框架**：首次将 CLI 网络运维中的 top-1 失败显式分解为"提案侧覆盖率不足"与"选择侧误排序"两类来源，并据此设计互补的双路径自适应机制（公式 11：top-1 成功 = 可行动作覆盖率 × 条件选择正确率）。
- **提案侧操作记忆**：用一个轻量级 LLM 记忆抽取器，将原始执行反馈（成功/失败/恢复记录）蒸馏为结构化、可检索的操作经验（含类型、意图、适用条件、推荐/规避命令模式），通过嵌入相似度 Top-R 检索注入提案提示，在不修改提案 LLM 权重的前提下提升候选动作集中可行动作的存在概率。
- **选择侧会话级 LoRA 自适应**：冻结提案 LLM 与效用/风险评分头，仅对后果预测器（基于 Qwen3-0.6B）施加低秩更新（ΔW = UV），用每轮真实 SSH 执行产生的状态-动作-后果样本进行监督，纠正会话特定的误排序，同时保持基础判断的稳定性。
- **效用与风险感知的重排序**：对每个候选动作同时预测任务进展得分 r̂ 与操作风险得分 ρ̂（如 `clear bgp *` 在仅需恢复单邻居时被判为高风险），按 r̂ − λρ̂ 选出最终执行动作，兼顾效率与安全。
- **执行落地的反馈闭环**：当 top-1 动作失败时，按排序依次执行其余候选以收集额外执行证据，所有执行记录汇入记忆缓冲区与 LoRA 训练集，形成"预测-执行-修正"的持续学习循环。

## Key Contributions

- **Execution-grounded dual-path decomposition**: Explicitly factorizes top-1 failure into a proposal-side coverage gap (the candidate set lacks any feasible action) and a selection-side misranking error (a feasible action exists but is not ranked first), motivating two complementary adaptation targets via Eq. (11): `Pr(y*=1) = Pr(c=1) · Pr(y*=1|c=1)`.
- **Proposal-side operational memory without weight edits**: A lightweight memory extractor distills accumulated execution records (failed commands, recoveries, successes) into compact, structured lessons (type, intent, applicability condition, prefer/avoid patterns). These are retrieved via Sentence-BERT cosine similarity and injected into the proposal prompt to raise feasible-action coverage, leaving the proposal LLM frozen.
- **Selection-side session-level LoRA on the consequence predictor**: Only the consequence predictor (Qwen3-0.6B) receives low-rank updates `W_t = W_0 + U_t V_t` trained on per-turn state-action-consequence samples from real SSH feedback; the proposal LLM and the utility/risk heads stay frozen, giving session-level plasticity without catastrophic disturbance of previously reliable judgments.
- **Utility- and risk-aware reranking**: Each candidate is scored by both predicted task progress `r̂` and operational risk `ρ̂` (e.g., `clear bgp *` is risk-penalized when a single peer needs recovery), and the action maximizing `r̂ − λρ̂` is executed, integrating safety into selection rather than relying on linguistic plausibility.
- **Closed-loop feedback collection**: On a top-1 failure, lower-ranked candidates are executed in ranked order solely to gather execution-grounded evidence; these records feed both the memory buffer (periodic extraction) and the LoRA update (per-turn), enabling continual within-session improvement.

## Methodology

The method is formalized as a multi-turn action-level decision process over a SONiC environment. At each turn t the agent receives a natural-language intent q_t and environment observation o_t, summarized into a decision context x_t = (q_t, o_t, H_{t-1}).

1. **Candidate proposal (Eq. 4)**: Given retrieved memory M_t, the proposal generator produces K=5 complete, distinct CLI candidates A_t = {a^(1), ..., a^(5)}.
2. **Consequence prediction (Eq. 5-6)**: For each candidate, a Qwen3-0.6B consequence predictor estimates the device-side consequence ẑ, from which two heads derive predicted utility r̂ and risk ρ̂.
3. **Reranking & execution (Eq. 7-8)**: The top-ranked action a* = argmax(r̂ − λρ̂) is executed via SSH; a task-specific verifier returns the real consequence z* and binary outcome y* ∈ {0,1}.
4. **Execution record collection**: If y*=0, remaining candidates are executed in ranked order to collect additional (state, action, consequence, outcome) tuples D_t; these never alter the recorded top-1 outcome.
5. **Selection-side adaptation**: The predictor θ_t is updated via LoRA (Eq. 14-15) minimizing the discrepancy between predicted and observed consequences over D_t, after every turn.
6. **Proposal-side adaptation**: At a fixed interval, the memory extractor distills the buffer B into structured operational lessons and updates the memory bank M; retrieval into future proposals uses Sentence-BERT embedding similarity (Eq. 13).

The consequence scoring module is initialized from 300 manually annotated execution records (with utility and risk labels). Algorithm 1 gives the full operation loop.

## Results & Highlights

- **Experimental scale**: Evaluated over a fixed sequence of 140 interaction turns covering CLI query, configuration, and diagnosis operations, with K=5 candidates per turn and a SONiC environment accessed through real SSH. (All methods share the same request sequence, initial states, candidate budget, SSH interface, and verifier rules.)
- **Proposal models**: Qwen3-1.7B, Qwen3-8B, and Qwen3-14B serve as proposal generators; the consequence predictor is built on Qwen3-0.6B. Larger proposal models achieve higher absolute top-1 success (read from Fig. 3/4), while the full dual-path framework wins at every scale.
- **Coverage vs. selection (Fig. 3)**: Multi-candidate proposal (K=5) lifts the feasible-action coverage diagnostic Recall@5 above the single-proposal baseline across all three scales, confirming that candidate coverage alone is insufficient — consequence-aware selection plus execution-grounded adaptation is required to convert available feasible actions into top-1 successes.
- **Baselines outperformed (Fig. 3)**: The full framework exceeds the single-proposal baseline (executes the first generated candidate), the self-consistency baseline (samples K=5 and votes without any execution feedback), and the no-adaptation baseline (both retrieval and predictor adaptation disabled), on top-1 success for Qwen3-1.7B, 8B, and 14B.
- **Complementary adaptation paths (Fig. 5, Qwen3-8B)**: Proposal-side-only (retrieval, fixed predictor) improves feasible-action coverage consistently; selection-side-only (fixed proposals, LoRA predictor) improves conditional selection quality but is bounded by available candidates. The full framework combining both achieves the highest success rate, empirically validating the Eq. (11) decomposition.
- **Sustained within-session improvement (Fig. 4)**: Over 140 turns the full framework shows monotonically sustained improvement in sliding-window top-1 success across all three scales, whereas the no-adaptation variants (dashed baselines) remain flat.

## Critical Assessment

- **Novelty**: The core insight — separating CLI-operation failure into proposal coverage vs. selection misranking and adapting each with a different mechanism (retrieval memory vs. LoRA) — is reasonable and well-motivated, but each individual component (multi-candidate generation, retrieval-augmented memory, LoRA fine-tuning, risk-aware reranking) is an established technique; the contribution is the composition and the coverage-selection decomposition.
- **Rigor**: The decomposition in Eq. (11) is mathematically clean and the ablation (Fig. 5) genuinely isolates the two paths on a fixed Qwen3-8B proposal model, which is the right experiment to validate the factorization. However, all results live in figures rather than numeric tables, and the paper reports no standard deviation, confidence intervals, or repeated-seed variance, making magnitude claims hard to verify precisely.
- **Reproducibility**: The 140-turn SONiC sequence, verifier rules, and 300-record annotation set are described but not released; the SONiC environment setup and the exact verifier that labels y ∈ {0,1} are task-specific and non-trivial to replicate. Hyperparameters λ (risk penalty), R (retrieved items), LoRA rank, and memory-update interval are mentioned conceptually but their precise values are not all stated.
- **Significance**: The setting (CLI-based SONiC operations with real SSH feedback) is practical and safety-relevant for intent-based networking. The continual-learning framing is a genuine step beyond one-shot config-generation work. That said, the scale is modest (single-device sessions, 140 turns, one environment) and generalization to multi-device fleets is left as future work.
- **Red flags**: The figure-derived success numbers cannot be cross-checked against any in-text table; the "SONiC Project" reference is dated 2026 and ReasoningBank [12] is cited as ICLR 2026, which is consistent with the preprint timing but means some supporting literature is very recent. No failure-case analysis or safety-incident reporting is provided despite the explicit risk-awareness framing.

## Strengths

- Clean, well-justified problem decomposition that directly motivates the dual-path design.
- Practical, real-SSH execution-grounded feedback loop — not a simulated text-generation task.
- Honest, targeted ablation isolating proposal-side vs. selection-side gains.
- Risk-aware reranking integrates operational safety (e.g., penalizing `clear bgp *`) rather than treating all syntactically valid commands as equal.
- Freezing the proposal LLM and updating only the small (0.6B) predictor with LoRA is a parameter- and safety-efficient design choice.

## Limitations

- Small, single-environment evaluation (140 turns, single SONiC device); no multi-device, multi-vendor, or larger-scale network scenarios.
- Results are reported only as figures with no numeric tables, variance, or statistical significance tests; exact success-rate deltas are hard to pin down.
- Key hyperparameters (λ, LoRA rank, retrieval budget R, memory-update interval) and the verifier definition are under-specified.
- The consequence predictor is bootstrapped from 300 manually annotated records, introducing a labeling bottleneck and potential annotation bias.
- No analysis of failure modes, safety incidents, or cases where LoRA adaptation degraded previously reliable predictions (catastrophic forgetting risk is acknowledged but not measured).
- No comparison against networking-specific LLM baselines such as NetConfEval or NetKeeper; baselines are limited to single-proposal, self-consistency, and a no-adaptation ablation.

## Relevance

与 LLM 智能体在网络运维（intent-based networking / NetGPT）以及智能体记忆与持续学习（retrieval memory、LoRA 在线自适应）方向高度相关，可作为"执行驱动反馈闭环如何同时改善候选覆盖与动作选择"的参考范式，其风险感知重排序与记忆蒸馏思路对通用工具调用型智能体同样有借鉴价值。

## Questions for Further Exploration

- How do the two adaptation paths behave under multi-device fleet operations, where session-level LoRA updates learned on one device may transfer poorly (or harmfully) to another?
- What is the catastrophic-forgetting profile of the selection-side LoRA — does adapting to a new command family degrade accuracy on previously mastered patterns, and can an Elastic Weight Consolidation-style regularizer help?
- How sensitive are the results to the risk penalty λ and the LoRA rank, and is there a regime where selection-side adaptation alone saturates because coverage becomes the binding constraint?
- Could the structured operational memory be shared across sessions and operators, and would cross-session retrieval introduce stale or conflicting guidance (e.g., different SONiC versions with different CLI dialects)?
- How does the framework compare against networking-specific baselines (NetConfEval, NetKeeper) and against a full-model online update, rather than only single-proposal and self-consistency?
- Can the consequence predictor's risk head be calibrated to produce actionable probabilities rather than relative scores, enabling threshold-based human-in-the-loop safety gates?
