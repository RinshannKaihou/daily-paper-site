> **一句话总结：** Macaron-V1 把"体验式智能"拆成架构/算法/基础设施三层协同设计——冻结 744B GLM-5.2 底座、挂 4 个 rank-16 LoRA 专家（Chat/Agent/Coding/GenUI），由 L0 自己每轮输出一个受约束解码的路由标签（6448 样本 trace 上 99.12% 准确率、路由+摘要开销占三跳总时延 32%）；在自研 UI4A 组件原生 GenUI 基准上以 87.8 Final Score 大幅领先 Opus 4.8 的 75.9 与底座 GLM-5.2 的 67.1，但在 VitaBench(60.0 vs Qwen3.7 Max 61.2)、ClawGym(77.7 vs GPT-5.5 82.5)、DeepSWE(58.4 vs GPT-5.5 70.0)等 5/12 行落后，且标题里的"持续学习/递归自我改进"在本次发布中**没有跨代实验**（RSI 实验全程冻结模型、不做任何优化器步）。

> **TL;DR:** Macaron-V1 is a systems report for an "agent-model family": a frozen 744B GLM-5.2 base + four 1B-labeled LoRA specialists (7.688B stored values each) composed by a Proxy that routes one specialist per user turn, with the chat adapter L0 acting as its own router (99.12% on a 6,448-sample trace, 0.54s route + 0.97s summary ≈ 32% latency overhead). Headline win is generative UI: 87.8 Final Score on the authors' own 161-case UI4A-Bench vs 75.9 for Opus 4.8 and 67.1 for the GLM-5.2 base (+20.7 over base), with Constraint Adherence 94.2 vs 82.2. It also leads TerminalBench 2.1 (87.6 vs GPT-5.5's imported 83.4) and its own ChatBench (58.3 vs GPT-5.5 55.5), but *loses* on VitaBench, VitaBench2, ClawGym, SWE-Verified, DeepSWE and SWE Atlas QnA. The much-advertised recursive self-improvement result — 122/122 coverage on a base-failure TerminalBench slice vs 11/122 for the best single configuration — is a **frozen-model harness-configuration search with zero gradient steps**, and the paper says so explicitly. Read it if you care about multi-adapter serving economics, harness-as-training-target design, or honest systems reporting; skip it if you want evidence that continual learning compounds.

## 核心贡献

- **Mixture-of-LoRA (MoL) 架构**：冻结大底座 + 少量专家 LoRA，由 MoL Proxy 在每个用户轮次显式选择**一个**专家（不是 token 级混合、不做权重合并）。设计准则是"技能与思维模式相近的任务合并进一个 LoRA，差异大的分开"。serving harness 已开源。
- **三跳生命周期 route → answer → summary**：L0 在 24-token 预算下用受约束解码输出 L0–L3 之一；专家回答后再输出 ≤192 token 的摘要存在服务端，作为跨专家共享上下文；工具结果轮次"粘住"同一专家，跳过路由与摘要。
- **Own-view（每专家会话视图）**：每个专家看到自己的完整历史轨迹（含工具调用/结果）+ 其他专家轮次压缩后的 192-token 摘要。由于时间线只追加且渲染确定，重入某专家时前缀逐字节一致，引擎原生 prefix cache 自然命中——KV 复用是"涌现"的，不需要改 vLLM/SGLang。
- **模型–Harness 协同设计**：UI4A（组件原生 GenUI，模型写普通 React/TSX，受运行时边界约束，Action 四元组 Origin/State/Execution/Visibility 含 NoAI 边界）、REPL agent harness（持久 Python 命名空间 + save_tool/promote_tool 的"验证后提升"复用机制）、HCP（版本化 TOML 运行时契约，把模型选择/工具白名单/skills/hooks/会话状态做成可移植可审计工件）。
- **MindForge 三阶段 RSI 循环**：Discovery（模型自造更难任务，需带可验答案或 rubric）→ Expansion（固定 model–HCP 对执行、审计失败归因到模型/任务/配置）→ Update（轨迹筛选后 GRPO 更新 LoRA，同时注册新 HCP）。本文只实验了 Expansion 一段。
- **基础设施**：MinT（adapter revision 与 policy record 分离，10⁶ 条可寻址 adapter 目录）、LongStraw（response-only 长上下文回放，把计算图上界压到最长响应而非整个 prompt+响应组）、稀疏底座 rollout–learner 失配控制（R3 路由重放、DSA 实现对齐、IcePop 式残差过滤）。
- **两个自建 Personal Intelligence 基准**：Macaron ChatBench（46 例，六条"宪法公理" + persona/scenario 双层条件化的动态 rubric）与 Macaron LivingBench（40 个场景、≤10 轮、四层噪声系统、need/process 双评委按 0.7/0.3 合成）。

## Key Contributions

- **MoL as an interoperability contract, not a bigger model.** Base frozen, adapters portable and separately versioned; new capability enters as a registered adapter rather than a base retrain. Three independent release clocks (base / specialists / harness).
- **Router-free routing.** No separate router model and no keyword rule library — the chat adapter L0 emits the canonical label under a constrained-decoding grammar, so routing quality improves with L0 rather than with a hand-tuned classifier.
- **Emergent per-adapter KV reuse** derived from deterministic own-view reconstruction, plus an opt-in experimental same-request route-decode overlay that trims router-only tokens and continues decoding under the target LoRA.
- **Harness as a first-class training target**, with HCP making prompts/tools/hooks/skills addressable fields that a model can propose edits to — "self-iteration in language space rather than parameter space."
- **A deliberately bounded RSI experiment** that isolates configuration search from weight updates, and reports the confound rather than hiding it.
- **Two trajectory-level Personal Intelligence benchmarks** built from de-identified product conversations and product failure taxonomies, plus UI4A-Bench (161 cases, headless-Chromium compile + render + browser-driven interaction probing).
- **Unusually disciplined evidence hygiene**: starred vs unstarred cells, "logical stored-tensor count" vs "release-facing 748B label", and repeated explicit statements of what each number does *not* establish.

## Methodology

**Architecture.** Macaron-V1-Venti = frozen 744B GLM-5.2 base + four LoRA specialists (rank 16, alpha 32, identical attention/MLP target modules), each with 7,688,042,496 stored values in the released adapter headers. L0 = Chat (also the routing entry), L1 = Agent (long-horizon tool use, absorbs the Preview's OpenClaw adapter), L2 = Coding (SWE-style + terminal), L3 = GenUI (UI4A, TSX/React/SolidJS). Macaron-V1-Tall = Qwen3.6-35B-A3B base + four rank-64/alpha-128 adapters at 3,775,651,840 values each ≈ 50.1B. A third build, Macaron-V1-Coding-Venti, merges the coding LoRA into the base and is excluded from all result tables.

**Serving loop.** Each user turn runs Route (L0, 24-token constrained decode into exactly one of four legal labels; the router prompt treats the request as quoted untrusted text and checks wrapper families in priority order GenUI → code/terminal → personal-agent) → Answer (specialist generating from its own-view) → Summary (≤192 tokens, stored server-side, never returned to the client). Short-circuits: tool-result turns lock to the previous adapter; the Proxy checkpoints conversation state before each turn and rolls back on engine failure so undelivered turns never enter history. The Proxy is engine-agnostic, exposes Chat Completions / Responses / Anthropic Messages, and hides internal base and adapter names behind the single model name `Macaron-V1-Venti`.

**Harness components.** UI4A replaces schema-native GenUI (their prior Macaron-A2UI) with component-native code generation: the model imports from a curated registry (Radix, shadcn, Recharts, KaTeX, lucide-react) or writes raw HTML/CSS, and every gesture is a structured Action with a Visibility field including a NoAI boundary. The REPL harness gives the L1 agent a persistent Python namespace so dependent intermediates never round-trip through the model as text; helpers are staged with `save_tool` and only become callable after `promote_tool` passes a private validation run against a held-out reference (promotion order is load-bearing because promoted helpers are live in *both* serving and MindForge rollouts). HCP is a versioned TOML artifact carrying runtime/model selection, tool allowlists, MCP servers, hooks, prompts, skills, session snapshots and environment contracts; the current Python SDK is wrapper-mode only (no full semantic validation or native materialization).

**RL formulation.** Policy π_φ(a_t | o_≤t; θ, c) with θ = frozen sparse base, φ = LoRA parameters, c = versioned harness configuration. Two update paths are deliberately kept separate: GRPO updates φ from selected trajectories; configuration search selects a new c without treating HCP as a learned parameter. Adapter selection is a Proxy-mediated route hop, explicitly *not* an action in the policy's action space.

**Infrastructure.** MinT separates an immutable *adapter revision* (serving tensor layout) from a mutable *policy record* (trainer checkpoint, optimizer state, rollout records); trainer state never crosses the serving boundary. LongStraw bounds live memory by M_weights + M_prefix(P) + M_grad + max_i M_graph(R_i) + M_score(ΣR_i), capturing the shared prompt without autograd and replaying one response at a time — "exact" means the stated token positions under a response-only transaction, not parameter-wise equivalence to full-sequence backprop. Sparse-base controls are path-selected alternatives, not a pipeline: R3 replays rollout expert ids (excluding unmappable tokens from the policy-gradient term), DSA alignment fixes rotary layout / normalized q-k inputs / deterministic top-k / frozen-indexer defaults, and IcePop-style filtering zeroes importance weight for tokens whose train-vs-rollout ratio leaves a trusted interval.

**Evaluation.** Twelve benchmark rows across Personal Intelligence, agent, coding/terminal, and GenUI against Opus 4.8, GPT-5.5, Gemini 3.1 Pro, GLM-5.2, Qwen 3.7 Max, and Minimax M3. Within each row, unstarred values share task set and protocol; starred values are imported from public leaderboards. SWE and terminal evaluations use the Claude Code scaffold, not the production MoL harness; UI4A-Bench baselines run adapter-free UI4A.

## Results & Highlights

- **Generative UI is the real result.** On UI4A-Bench (161 cases, identical runtime/viewports/judge/scoring across models), Macaron-V1-Venti scores **87.8 Final Score vs 75.9 for Opus 4.8 (+11.9), 72.1 for GPT-5.5 (+15.7), and 67.1 for its own GLM-5.2 base (+20.7)**. At the Layer level it leads the strongest baseline by **+12.0 in Constraint Adherence (94.2 vs Opus 4.8's 82.2)**, +6.6 in Visual Quality (90.0 vs GPT-5.5's 83.4), and only **+1.6 in Interaction (95.0 vs 93.4)** — note Visual Quality carries 38% of the composite weight, so the headline gap is dominated by the most judge-subjective dimension, and only the mobile 390×844 viewport contributes to the primary visual score.
- **Personal Intelligence wins are small and in-distribution.** ChatBench: **58.3 vs GPT-5.5's 55.5 (+2.8)** and GLM-5.2's 54.5. LivingBench: **64.0 vs Opus 4.8's 63.8 — a +0.2 margin** that the authors themselves say "should not be interpreted as established superiority" absent interval estimates. Both benchmarks are the authors' own, contrastively selected (cases where models fail or succeed uniformly are dropped), and ChatBench uses a private GLM-5.2 judge from the same family as the base.
- **On external agent benchmarks it loses more rows than it wins.** VitaBench **60.0 vs Qwen 3.7 Max 61.2**; VitaBench2 **46.0 vs Gemini 3.1's 50.2**; ClawGym **77.7 vs GPT-5.5's 82.5 and Opus 4.8's 80.5**; τ³-Bench 69.3 vs GLM-5.2's 69.1 (a +0.2 nothing-burger over its own base); PinchBench 94.0 (best-observed run) vs Qwen 3.7's imported 93.4.
- **Coding is mixed; terminal is the one strong external row.** TerminalBench 2.1 **87.6 vs GPT-5.5's imported 83.4 (+4.2) and base GLM-5.2's 82.7 (+4.9)**. But SWE-Verified **85.6 vs Opus 4.8's imported 88.6 (−3.0)** (still +5.2 over base 80.4), DeepSWE **58.4 vs GPT-5.5's 70.0 (−11.6)**, SWE Atlas QnA **49.5 vs Opus 4.8's 57.3 (−7.8)**.
- **The RSI headline is a coverage ceiling, not a learning result.** On 122 simulation tasks from 29 TerminalBench 2.1 families that the frozen GLM-5.2-FP8 base fails outright (pre-sweep coverage is 0/122 *by construction*), adaptive harness-configuration search reaches **122/122 cumulative unique coverage across 69 jobs / 450 attempts (3.69 per task)**, while the two full-set single-configuration sweeps reach only **4/122 (3.3%) and 11/122 (9.0%)** — and 97 of the run's 109 harness errors fall in exactly those two jobs. Phase pooled pass rates: 12.0% (retry control) → 6.1% (portfolio sweep) → 64.5% (skill/HCP search) → 81.2% (+ stop-gate hooks), a 13× per-attempt yield ratio the paper explicitly refuses to call causal. **No optimizer step is taken anywhere in this run.**
- **MoL's systems win is storage, and only storage.** 744B base + ~30.8B adapters ≈ 774.8B logical parameters vs 2.976T for four merged base copies = **26.0% of the replicated layout, a 74.0% reduction** — but the authors explicitly make *no* comparative latency or throughput claim vs independently deployed merged specialists. Routing costs 0.54s (route) + 0.97s (summary) on top of 3.17s answer = **32% of the three-hop total** on Venti; 0.20s + 0.32s vs 1.24s = 30% on Tall.
- **Routing accuracy 99.12% (6,391/6,448) on Venti and 99.04% on Tall**, 100% canonical-label compliance, zero parse errors, per-class 97.11% (L1) to 100% (L2), errors concentrated at the L0/L1 chat-vs-personal-agent boundary. The trace is **drawn from LoRA training data, not a held-out split** — the paper calls it an implementation diagnostic, not a generalization estimate. A separate full-stack integration run on a balanced 480-sample subset gets 97.5%.
- **Routing does not visibly hurt quality, but the test is underpowered.** Vita delivery, five seed-level aggregates per arm, unpaired: direct L1 0.636±0.026, routed KV-off 0.650±0.030, routed KV-on 0.632±0.019 on Venti; 0.410 / 0.398 / 0.386 on Tall. The paper concedes this shows "no detected degradation" but "does not establish equivalence."
- **Tall beats its own base on all seven shared rows**, from **+1.3 on LivingBench (48.4 vs 47.1)** to **+25.4 on UI4A-Bench (59.3 vs 33.9)**; ChatBench 54.9 vs 48.0, PinchBench 86.2 vs 82.5, ClawGym 64.0 vs 58.6, SWE-Verified 75.4 vs 73.4, TerminalBench 56.2 vs 52.5. But this is an end-to-end system comparison (adapters + routing + harness + parameter footprint all differ), not a parameter-matched ablation.
- **Text-only adapters mostly preserve multimodality — except one row.** Tall MoL vs native base: OCRBench 89.60 vs 88.80, MMBench-EN 86.68 vs 86.08, MMMU 61.22 vs 59.89, MME cognition 671.07 vs 604.64 (+66.43), but **MME perception 1732.57 vs 1785.56 (−52.99)**. No repeat-level variance, no vision-agent tasks, no ablation.
- **Two honest negative results.** (i) On BFCL v4 (200 tasks), the REPL substrate scores **49.5% vs 54.0% for plain function calling** — observe-before-commit APIs punish batched dependent calls, so the production harness keeps discrete calls as a fallback. (ii) Qualitative character-stability degradation after multiple preference-drift events in long LivingBench sessions, documented but never quantified.
- **Long-context / serving receipts (imported from companion reports, not rerun):** CP8 LayerSplit cuts cold 900K-token needle-test TTFT from **107.1s to 49.2s** on 8×B300; DCP8+EAGLE reaches 8.6ms TPOT / 110 tok/s at concurrency 1 and 18.0ms / 757 tok/s at concurrency 16; FlashMLA sparse attention produced clean outputs on **48/48** long-context configs vs **6/48** for the default DSA decode path on GLM-5.1. MinT adapter-only handoff is **18.3× faster than a merge path for Qwen3-4B (rank 32) and 2.85× for Qwen3-30B (rank 16)**. R3 cuts mean out-of-route scoring from 0.0097% to 0.0013%. LongStraw completes exact 2,097,152-position response-only replay on 8×H20 CP8 (Qwen3.6-27B) and a 2,097,152-token-prompt online G=2 GLM-5.2 transaction on 32×H20.
- **UI4A representation efficiency:** 672 vs 1,224 output tokens on 48 paired gallery cases (**~45% lower, lower on all 48 pairs**), with "up to ~6× faster time-to-first-render" on interactive cases — a descriptive length comparison that controls for neither quality nor latency. The REPL case study resolves a multi-step order/SLA/revenue task in **6 turns vs 48** with both arms returning the exact-match answer 8208.

## Authors & Credibility

Mind Lab / Mindverse, the team behind the Macaron consumer agent product, with 75+ named contributors (mostly English-alias names) and an institutional-report style rather than a small-author-list research paper. Weights are on HuggingFace (`mindlab-research/Macaron-V1-Venti`) and the MoL serving harness is open-sourced (`MindLab-Research/Mixture-of-LoRA-Harness`), which is meaningfully more than most industrial "tech reports" release. The work leans heavily on companion reports the team also authored (MinT, LongStraw, UI4A, the REPL harness, R3, DSA integration), several of which are cited as blog posts on macaron.im rather than peer-reviewed artifacts — so a large fraction of the infrastructure claims are internally attested and not independently checkable. Acknowledgements to the vLLM, SGLang, TileRT and NVIDIA Megatron teams suggest real engineering depth. The base models are third-party (GLM-5.2, Qwen3.6), so the paper is honest that its general capability is inherited, not earned.

## Critical Assessment

**Novelty (moderate).** Per-turn LoRA routing over a frozen base is not new — the paper itself cites task/sequence/token-level mixture-of-adapter work (Dhasade et al. 2026; Shah & Wagle 2026) and multi-tenant LoRA serving (Punica, S-LoRA). What *is* genuinely fresh: (a) making the chat adapter its own router under a constrained-decoding grammar, so no separate router artifact exists; (b) the own-view construction, where per-adapter prefix-cache reuse falls out of deterministic timeline rendering with **zero engine modification** — that's an elegant, cheap idea; (c) UI4A's component-native middle ground between HTML-native and schema-native GenUI. The "recursive self-improvement" framing is the least novel and least supported part.

**Rigor (unusually self-aware, but the design motivation is untested).** The single most damning admission is in §2.1: the entire MoL premise is cross-task interference from joint post-training, and **"the present release does not include the budget-matched single-LoRA comparison needed to quantify that interference, so we treat it as a design motivation rather than an empirical finding."** So the central architectural bet has no ablation. Similarly: no ablation isolating the L2 adapter's contribution to the SWE rows (the paper says these "evaluate the released coding system end to end"); no ablation attributing UI4A-Bench gains to the L3 adapter vs the UI4A runtime vs the base; no controlled experiment separating gains from weights, configuration, or their interaction (§3.2.4 flags this as "required" future work); no repeat-level variance on the multimodal table; no judge-sensitivity study for the GLM-5.2 judge scoring a GLM-5.2-derived model. The Vita three-arm comparison has n=5 unpaired seeds with seed identifiers discarded — that's not enough to detect a several-point regression. Against all that, the paper's epistemic discipline is genuinely rare: it distinguishes the release label 748B from the stored-tensor count, marks imported leaderboard cells, states that 122/122 is "a coverage ceiling under adaptive configuration selection, not a held-out estimate," and repeatedly writes "this does not establish X." I would rather read ten of these than one paper with bolded wins everywhere.

**Reproducibility (partial by construction).** Weights and serving harness are public; adapter hyperparameters (rank/alpha/targets) are in the paper; Appendix B.6 gives training hyperparameters. But §7.2 concedes there is **no complete per-specialist training specification**, and MinT explicitly provides "model-state lineage, not complete experimental reproducibility." The internal benchmarks (ChatBench 46 cases, LivingBench 40 scenarios) are not released, and LivingBench's simulator adapts its trajectory to each tested model — so different models literally receive different event sequences, which the paper defends as "a common policy rather than an identical fixed event sequence" but which nonetheless makes exact replication of any baseline's score impossible for outsiders.

**Significance (real but narrower than the title).** The paper's title promises continual learning; the paper delivers an architecture that *affords* continual learning plus one snapshot. §7.2: "The released Macaron-V1-Venti snapshot cannot, by itself, distinguish a compounding RSI effect from a single round of self-generated-data training." The 74% storage reduction and the emergent KV reuse are practically useful today for anyone running multi-specialist agent services; the UI4A-Bench result is a real capability gap over frontier models on a task frontier labs have not optimized for. The collective-intelligence claim is entirely aspirational — only the four in-house specialists are tested.

**Red flags.**
1. **Benchmark asymmetry.** The two benchmarks where Macaron wins most decisively (ChatBench, LivingBench, UI4A-Bench) are all authored by the same team, and ChatBench/LivingBench "share source domains and failure taxonomies with the RSI loop" — i.e. the model was optimized against the same distribution it is evaluated on, which the paper admits makes them "less independent of the training process than a frozen external test set." On the six genuinely external benchmarks, Venti loses five.
2. **Judge family collusion.** ChatBench uses a private GLM-5.2 judge on a GLM-5.2-derived model, flagged but unquantified: "no human or cross-family judge study is available."
3. **Contrastive case selection.** ChatBench "retains cases on which candidate models take distinguishable strategies," which mechanically inflates observed gaps and makes the 58.3-vs-55.5 margin uninterpretable as a product-wide difference.
4. **Mixed-provenance results table.** Table 8's starred cells come from public leaderboards under their own protocols; e.g. TerminalBench 2.1's "win" over GPT-5.5 compares a locally-run Macaron number under the Claude Code scaffold against an imported 83.4.
5. **PinchBench reports the best observed run** while other rows report pass@1 or three-run averages — the 94.0 is not comparable to the starred baselines it sits next to, as the paper concedes.
6. **Data governance gap.** §7.2 states plainly that the report does not document consent/opt-in basis, de-identification procedure, re-identification audit, retention controls, or ethics review for the de-identified product conversations used in ChatBench — and there is no standalone safety or red-team evaluation. For a system pitched at intimate personal assistance (the LivingBench case study involves an elderly parent's suspected hip fracture), that is a material omission, honestly labeled.
7. **The 10⁶-entry adapter catalog** is measured only as artifact addressability (all entries built with zero errors; a 256-entry audit sample across 100 shards) and explicitly does not mean a million behaviorally distinct policies or a million resident adapters.

## Strengths

- Best-in-class evidence hygiene for an industrial model report: every table caption states what the numbers do *not* establish, provenance markers separate reproduced from imported values, and negative results (BFCL v4 49.5% vs 54.0%; long-session character drift; MME perception −52.99) are reported rather than buried.
- The own-view / emergent-prefix-cache design is a genuinely clever engineering result — deterministic prompt reconstruction turns cross-turn KV reuse into a free property of unmodified vLLM/SGLang, and the design keeps each specialist from ever seeing another specialist's raw trace.
- Real artifact release: Venti weights and the MoL serving harness are public, which makes the routing and serving claims independently checkable even though the training data is not.
- The RSI expansion experiment is a well-posed question well answered: the 4/122 and 11/122 single-configuration sweeps versus 122/122 adaptive coverage is a striking demonstration that "the base can't do this task" often means "this configuration didn't elicit it," and the authors resist over-reading it.
- Benchmark design is thoughtful — LivingBench's four-layer noise system (user / world / tool / observation, with a recovery cue injected when a model presents tampered tool data as fact) and its need/process dual-judge split (0.7/0.3) catch a real failure mode: the case study meets all needs with a full outcome score but only 0.593 process quality.
- UI4A-Bench actually drives the rendered card in a headless browser and scores zero when a declared interaction requirement produces no evidence, instead of skipping it — stricter than screenshot-similarity GenUI evaluation.

## Limitations

- **No cross-generation continual-learning evidence at all.** One snapshot, one partial RSI stage, no measured retention/transfer/cumulative improvement — the paper's stated central objective is entirely future work.
- **No collective-intelligence evidence.** Only the four in-house specialists are evaluated; cross-owner, third-party, or personalized adapter composition is untested, as are compatibility, provenance, privacy, and tool-visibility checks it would require.
- **Missing the ablation that justifies the architecture** (budget-matched single-LoRA vs four-LoRA), plus per-specialist ablations across every reported row.
- **Routing is measured on training-derived data**, so its 99.12% is an implementation diagnostic; no routing audit exists for PinchBench or ClawGym specifically, and the router's benchmark-family examples are acknowledged as non-exhaustive.
- **Single-intent-per-turn routing.** A message packing "discuss this, then write code, then show me a UI" is routed wholesale to one specialist; the decomposing orchestrator exists only as an unshipped exploratory branch.
- **Infrastructure numbers are imported**, not rerun as Macaron-V1 experiments: the LongStraw receipts use stored responses and deterministic rewards (the GLM row is a single G=2 transaction with five generated tokens per response), and the MinT 1.04T Kimi K2 run is explicitly *not* evidence that Macaron-V1 was trained that way.
- **MoL's advantage is proven only for stored-parameter residency**; no TTFT or throughput comparison against four independently deployed merged specialists is offered, and the sharded DCP path exhibited systematic corruption while heterogeneous prefill–decode-disaggregation snapshots were excluded from quantitative comparison.
- **LivingBench compresses arbitrary calendar horizons into ≤10 turns**, so it tests stateful reasoning under evolving conditions — not the weeks-long retention that "continual learning after deployment" implies.
- No safety/red-team evaluation, no documented data-consent basis, no per-specialist training spec.

## Relevance

如果你关注 agent 系统的**架构与 serving 经济学**（多专家 LoRA 共享底座、prefix cache 复用、路由开销量化）或**harness 作为一等训练对象**（HCP/REPL/GenUI 的可搜索配置空间），这篇是近期少见的、把系统数字和边界条件写清楚的工业报告，其"配置搜索能把 0/122 变成 122/122"的结论对"模型能力缺失 vs 未被激发"这个判断有直接方法论价值。反过来，如果你想找的是 continual learning / RSI 的实证证据（跨代增益、遗忘曲线、专家群体的涌现协同），这篇明确没有——它自己在 §7.2 把这些全部列为下一代的开放问题。

## Questions for Further Exploration

1. What happens to the 122/122 coverage number when the discovered configurations are held fixed and evaluated on *unseen* tasks from the same 29 TerminalBench families? The paper measures a search ceiling; the generalization number is the one that decides whether AutoResearch is learning or overfitting to 122 items.
2. Does the missing budget-matched comparison actually favor MoL? A single LoRA trained on the union of the four specialists' data, at 4× the rank, would directly test the cross-task-interference premise — and it is cheap relative to what was already spent.
3. How much of the +20.7 UI4A-Bench gap over the GLM-5.2 base is the L3 adapter versus the UI4A runtime? Baselines run "adapter-free UI4A," so the runtime is shared — but the paper never reports Venti-without-L3 under the same runtime, which would isolate the specialist's contribution.
4. Is the LivingBench 0.2-point win over Opus 4.8 stable under a cross-family judge? Running ChatBench/LivingBench with a non-GLM judge (or a human panel on a subsample) is the single highest-value robustness check available.
5. Does per-turn routing become a liability as conversations lengthen? Every specialist re-entry carries only 192-token summaries of other specialists' turns; one would expect degradation on tasks requiring detailed cross-specialist state, and the documented long-session character drift may be exactly that mechanism surfacing.
6. What is the actual serving cost curve of MoL vs merged replicas under realistic mixed load? The 74% storage reduction is real, but adapter swapping, per-turn routing hops, and the invalidated adapter-specific KV on every switch could erase it at high concurrency — the paper deliberately declines to measure this.
7. If L0's full KV were shared across all specialists (the sketched-but-unshipped design in §2.8), does the correctness concern about mixing a chat adapter's KV into a specialist's computation show up as measurable quality loss, or is it a phantom worry?
