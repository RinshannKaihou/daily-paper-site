> **一句话总结：** SkillSentry 把 skill 文档解析成一个带步骤依赖、工具/参数约束和终止条件的 DSL，再从历史成功/失败轨迹中挖掘"验证过的动作模式 + 失败模式 + 步骤级建议与警告"，通过 agent runtime hook 在每个动作执行前做 FSM 进度检查与软拒绝（soft-deny），在 SkillsBench 衍生的 15 个 skill、1200 条查询上把四种 agent-模型组合的平均任务成功率从 62.6% 提到 77.7%（相对 +24.1%），重复运行标准差降低 41.1%，额外 token 开销仅 8.7%。

> **TL;DR:** SkillSentry is a runtime-assurance wrapper that turns an agent "skill" document into a DSL-specified FSM (steps, `depends_on`, tool/parameter constraints, termination set), enriches it with action patterns, failure patterns and step-level hints mined by GPT-5.4 from past successful/failed traces, and enforces it through pre-action hooks in Claude Code and Codex. On 15 SkillsBench-derived skills (1200 augmented queries), it lifts mean task success from 62.6% to 77.7% (+15.1 pts, +24.1% relative) and cuts run-to-run SD by 41.1% at +7.8% inference turns / +8.7% tokens. The only baseline is the unassisted base agent — no comparison to Reflexion/ExpeL/AgentSpec — and the paper's own ablation shows that simply dumping the same mined guidance into the system prompt already recovers 0.693 of the 0.741 (Haiku) result, so the hook/FSM machinery itself is worth only ~4.8 pts.

## 核心贡献

- **面向 skill 的运行时指导 DSL**：把自然语言 skill 文档形式化为 `steps / depends_on / constraints (tool, parameter) / logical_actions / on_enter (suggestions, warnings) / failure_patterns / termination` 的结构化表示，其中"骨架"来自文档解析，"经验"字段来自轨迹挖掘。
- **执行经验挖掘五阶段流水线**：动作模式抽取 → 轨迹摘要 `Σ(τ,G)=⟨S_align, S_skip, A_unalign, s_fail, y⟩` → 经验字段诊断（FP/FN/MC/OK）→ 字段编辑（ADD/UPDATE/REMOVE）→ 语法与一致性校验，用 GPT-5.4 作为 miner。
- **步骤感知的运行时保障**：由 `depends_on` 构造 FSM，pre-action hook 拦截每个待执行动作；进入步骤时注入该步的 suggestions/warnings，命中未满足依赖的动作或失败模式时"软拒绝"一次并给出提示，termination checker 在收尾前核对必需步骤是否全部完成；遵循 fail-open 原则，checker 异常则放行。
- **自演化闭环**：新查询执行产生的新轨迹回流到 miner，迭代更新 guidance（论文用 10 轮 × 5 条查询模拟部署后的查询流）。
- **系统评估**：15 个 skill × 4 个 agent-模型组合（Claude Code + Haiku-4.5 / Opus-4.6，Codex + GPT-5.2 / GPT-5.4），含效果、开销、自演化、消融与跨模型迁移五个 RQ；原型 5072 行 Python，匿名仓库开放。

## Key Contributions

- A DSL that fuses a *skill specification* (steps, dependencies, tool/parameter constraints, required-for-termination steps) parsed from the skill document with *execution experience* (validated logical actions with regex `command_match`, failure patterns plus reasons, per-step suggestions/warnings) mined from labeled traces.
- An LLM-based miner that diagnoses each experience field as FP (too restrictive), FN (too weak), MC (missing coverage) or OK, then applies ADD/UPDATE/REMOVE edits — an explicit, auditable update operator rather than free-form prompt rewriting.
- A step-aware assurance layer built on the hook APIs already exposed by Claude Code and Codex, so no agent internals are modified: it tracks an FSM over skill steps, injects on-enter guidance in-context, soft-denies out-of-order or failure-associated actions once, and gates termination on required-step completion.
- A self-evolution loop where post-deployment traces continuously refine the guidance, plus a cross-model generalization study showing guidance transfers between backbones of the same agent.

## Methodology

The pipeline has two stages. **Initialization**: an LLM parser (GPT-5.4) converts the natural-language skill document into the DSL's specification fields, with lightweight structural validation (unique step ids, valid dependency references, acyclic dependency graph, valid constraint types, termination steps ⊆ step set); validation errors are fed back for revision. In parallel, a miner reads historical successful traces `T+` and failed traces `T-`. From `T+` it extracts validated action patterns per aligned step and groups alternative realizations of the same logical action; from `T-` it extracts failure-associated patterns with reasons. Traces are compressed into step-level summaries before diagnosis to cut noise from long reasoning and repeated trials.

**Self-evolving / runtime**: the FSM is derived from `depends_on`. A step `s_i` completes only when *all* of its logical actions `LA(s_i)` have been matched by observed actions (any one alternative pattern per logical action suffices). Before execution, each planned action is classified: matches an activated step's logical action → allow and advance; matches a logical action of a step whose dependencies are unmet → temporarily deny with a re-planning hint naming the missing prerequisite; matches a failure pattern for the first time → deny once with the failure reason, but allow if the agent insists (treating experience as advisory, not hard policy); matches nothing → allow, but the FSM does not advance. The termination checker rejects completion until all `termination` steps are done.

**Evaluation design**: from SkillsBench's 87 tasks, each of the four agent-model configs ran every task 5×; tasks failing all five runs were dropped as "beyond basic capability", and the intersection across configs left 15 skills. Each skill's single query was augmented to 8 task instances (original + 7 manual variants, each with a hand-adapted deterministic verifier) × 10 paraphrases (GPT-5.4) = 80 queries; 5 instances (50 queries) form the evolution stream, 3 instances (30 queries) the held-out test set. Guidance evolves for 10 iterations of 5 queries; the final guidance is evaluated 5× on `Q_test`, reporting mean and SD. Paired t-tests report p<0.05.

## Results & Highlights

- **Headline effectiveness**: averaged over 15 skills and 4 configs, task success rises from 62.6% (base agent) to 77.7% (SkillSentry) — **+15.1 points, +24.1% relative**. Per config: Haiku-4.5 0.572 → 0.741 (+29.5% rel), Opus-4.6 0.661 → 0.811 (+22.7%), GPT-5.2 0.604 → 0.752 (+24.5%), GPT-5.4 0.668 → 0.805 (+20.5%). The only baseline in this table is the unassisted agent.
- **Gains concentrate on weak skills**: `excitation-signal-design` under Haiku goes 0.120 → 0.373 (+210.8% rel), `d3-visualization` 0.127 → 0.380 (+199.2%), `weighted-gdp-calc` 0.267 → 0.573 (+131.6%). Already-strong skills saturate: `glm-calibration` 0.887 → 1.000 (Haiku) and reaches 1.000 in all four configs; `spring-boot-migration` under GPT-5.4 only moves 0.980 → 1.000.
- **Stability**: mean SD across repeated runs drops 41.1% overall (41.2% / 39.5% / 46.5% / 36.9% for Haiku / Opus / GPT-5.2 / GPT-5.4). Across 60 skill×config pairs, SD is lower in 50 and tied in 2 — implying it is *worse* in 8 pairs, which the paper does not analyze (e.g. `jackson-security` under Opus: 0.600±0.033 → 0.700±0.053).
- **Ablation is the most informative table, and it undercuts the framing** (Haiku row): base 0.572 → w/o On-Enter 0.600 → w/o Failure-Patterns 0.636 → **System-Prompt Delivery 0.693** → full 0.741. So putting the *same* mined guidance statically into the system prompt — no hooks, no FSM, no interception — already captures ~12.1 of the 16.9-point gain (~71%); step-timed delivery adds only +4.8 pts (+5.8% relative, and +4.3 / +4.2 / +3.7 pts for Opus / GPT-5.2 / GPT-5.4). Removing on-enter suggestions/warnings collapses performance to 0.600, barely above the 0.572 base, i.e. the FSM + failure patterns + termination checker alone buy ~2.8 pts.
- **Overhead**: +7.8% inference turns (Haiku 20.2 → 22.2; GPT-5.4 27.8 → 30.4) and +8.7% tokens (Haiku 796K → 886K; Opus 1.30M → 1.38M). SkillSentry's own computation is 0.3–1.1% of wall-clock (≈0.8% mean) — but this excludes the offline evolution cost (50 executions plus GPT-5.4 mining per skill per config).
- **Self-evolution**: for `macroeconomic-timeseries-detrending` under Haiku, success rate improves ~58.2% relative over 10 iterations, with most gain in early iterations and shrinking SD; only this one skill/config curve is in the paper, the rest are on the anonymous site.
- **Cross-model transfer**: guidance evolved on one backbone and applied unchanged to the other within the same agent beats base by +22.6% (Haiku), +16.6% (Opus), +17.9% (GPT-5.2), +11.5% (GPT-5.4), retaining 94.2% of natively evolved performance (e.g. Opus 0.661 base → 0.771 cross → 0.811 native). Strong→weak transfer helps more than weak→strong.

## Authors & Credibility

All four authors (You Lu, Xinyu Huang, Bihuan Chen, Xin Peng) are from the College of Computer Science and Artificial Intelligence in China — the affiliation string is truncated, but Bihuan Chen and Xin Peng are well-known Fudan University software-engineering researchers with a long record at ICSE/ASE/FSE on program analysis, dependency and reliability tooling. The paper's framing (runtime enforcement, DSL, FSM, fail-open, threats-to-validity section, paired t-tests) and the citation of ICSE 2026 / ASE 2025 work reads like an ICSE/FSE submission under double-blind review; the artifact is an anonymous.4open.science repository. This is a competent SE-methodology group working on LLM agents rather than an LLM-modeling lab, which shows in the engineering rigor and in the relatively thin treatment of learning-side baselines.

## Critical Assessment

**Novelty (moderate).** The individual ingredients are familiar — ExpeL already distills successful/failed traces into reusable natural-language experience, AgentSpec already enforces DSL-specified runtime constraints, Trace2Skill already distills failure lessons into skills. The genuine novelty is the *composition*: aligning mined experience to individual skill steps and delivering it exactly when the FSM enters that step, plus a termination gate. That is a real and useful idea, but the paper's claim of being "the first runtime assurance framework for skill-oriented agent execution" leans on a narrow definition of the problem.

**Rigor (mixed).** Positives: 5 repeats × 5 evolution runs, mean+SD reported everywhere, held-out split at task-instance level so paraphrases never straddle train/test, paired t-tests, fail-open design, and an ablation that the authors did not have to include. Negatives, all specific to this paper: (1) **The only quantitative baseline is the do-nothing agent.** Section VI-A explicitly declines to compare against AgentSpec/ShieldAgent because "prior approaches detect safety violations", which is fair, but there is no excuse for skipping ExpeL/Reflexion/ProTeGi-style offline optimization — the System-Prompt Delivery variant is essentially a hand-rolled ExpeL and it already reaches 0.693/0.741 of the gain. (2) **The headline "24.1%" is a relative improvement stated in the abstract in a way that reads as absolute**; the absolute number is +15.1 points. Same for "reduces SD by 41.1%" and the 210.8% skill-level figure. (3) **A missing ablation that matters**: there is no "skill specification only, no mined experience" variant, so we cannot separate the value of the DSL/FSM (the contribution the title sells) from the value of GPT-5.4-written hints (which the ablation suggests dominates). There is also no separate w/o-termination-checker and w/o-procedure-checker split. (4) **Selection bias in the benchmark**: skills where any config failed 5/5 were removed, so the evaluation is deliberately restricted to the regime where the method works by construction; the reported averages should not be read as expected gains on arbitrary skills. (5) **The dataset is self-augmented** — 7 of 8 task instances per skill and their deterministic verifiers were manually written by the authors, and the 9 paraphrases per instance come from GPT-5.4, the same model used as parser and miner; paraphrase-level replication inflates the effective n (1200 queries are really 120 distinct tasks). (6) **Only one skill/config is shown for RQ3 self-evolution and one for the runtime breakdown**, with the remainder deferred to a URL — a convenient place for less flattering curves.

**Reproducibility (fair-to-good).** 5072 LOC prototype plus prompts in an anonymous repo; SkillsBench is public; verifiers are deterministic. The blockers are the hand-adapted verifiers for the 7 manual variants per skill (unclear whether released and how they were validated), and the reliance on Claude-Opus-4.6 / GPT-5.4 hook APIs, whose behavior drifts.

**Significance (solid but bounded).** For anyone shipping skill-based agents, the practical takeaway is real: step-scoped, just-in-time hints beat a long system prompt, and hooks are enough to implement it without touching the agent. The mechanism also degrades gracefully (fail-open, soft-deny once). Bounded by the paper's own admissions: it assumes the agent picks the right skill, assumes the skill document is correct, needs a verifier to label traces, and cannot handle workflows that interleave steps from multiple interdependent skills.

**Red flags.** Relative-vs-absolute framing in the abstract; no learning-based baseline; the soft-deny-once rule means a determined agent can always re-issue a failure-associated action, so "assurance" is advisory rather than enforced; and the token-overhead claim (8.7%) silently excludes the offline evolution and mining budget, which is the dominant cost of adopting the system.

## Strengths

- The ablation and generalization studies are genuinely informative and were not necessary for the paper's story — the authors report the System-Prompt Delivery number that most weakens their own framing.
- Engineering is deployment-realistic: pure hook integration into two shipping agents, fail-open on checker exceptions, soft-deny rather than hard-block, negligible in-loop compute (~0.8%).
- The variance result is arguably more valuable than the mean: reliability, not peak capability, is the actual pain point for skill-based agents, and SD drops in 50 of 60 pairs.
- The DSL is concrete and inspectable (regex `command_match`, explicit `depends_on`, explicit termination set), and the FP/FN/MC/OK diagnosis makes guidance updates auditable rather than a black-box prompt rewrite.
- Cross-model transfer retaining 94.2% of native performance is a practically important finding: guidance can be amortized across backbones within an agent.

## Limitations

- Assumes correct skill selection and a correct skill document; no assurance for interleaved multi-skill workflows (authors acknowledge this).
- Requires deterministic verifiers to label traces for mining; the fallback ("use LLM-based evaluators") is untested in the paper.
- Evaluated only on skills the agent can already sometimes complete, by explicit construction of the benchmark filter.
- No comparison to offline trace-optimization methods (ExpeL, Reflexion, Trace2Skill) despite being the closest related work.
- Offline evolution cost (50 executions + GPT-5.4 mining per skill per config) is never quantified.
- Single benchmark family (SkillsBench), 15 skills, 120 distinct tasks; skills are mostly analysis/scripting tasks with crisp step structure, which is the friendliest possible setting for FSM-based procedure checking.

## Relevance

对关注 LLM agent 可靠性、skill/SOP 工程化以及 Claude Code / Codex hook 生态的研究与实践来说，本文给出了一个可直接借鉴的结论：把从轨迹里挖出的经验按步骤定时注入，比一次性堆进 system prompt 更有效（+5.8% 相对），而且用现成 hook 即可落地。其消融数据也为"到底是 DSL/FSM 有用还是 LLM 写的提示词有用"这一问题提供了少见的量化证据，适合归档到 agent reliability / runtime guardrail 主题下。

## Questions for Further Exploration

- If the mined experience were simply appended to the skill document (an offline, zero-infrastructure baseline), how much of the 77.7% would survive? The System-Prompt Delivery row suggests most of it — is the hook layer worth its operational complexity outside high-stakes skills?
- What happens with a "specification-only" guidance (DSL + FSM, no mined suggestions/warnings/failure patterns)? That is the missing ablation needed to justify the DSL as the central contribution.
- In the 8 of 60 pairs where SD increased, what went wrong — does soft-deny occasionally push the agent into a worse re-planning basin?
- How does the FSM handle legitimate alternative decompositions (an agent that fuses steps 2 and 3 into one tool call)? Unmatched actions are allowed but do not advance the FSM, which could trigger spurious termination denials and wasted turns.
- Does the mined guidance overfit to the 5 evolution task instances? A cross-task-family transfer test (evolve on one skill's task distribution, test on structurally different queries for the same skill) would be more convincing than paraphrase-level generalization.
- Can the miner's FP/FN/MC diagnosis be replaced with a cheaper non-LLM signal (e.g. coverage statistics over aligned traces), given that mining currently requires GPT-5.4 over full traces?
