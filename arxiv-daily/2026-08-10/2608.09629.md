> **一句话总结：** 论文把自进化 agent 的"外部优化契约"（目标、可用操作、预算、数据边界、评测）与"任务特定的优化元策略"（怎么收集证据、怎么改、怎么选、何时停）拆开，提出让前沿模型在线自行组合元策略的 Open-Ended Optimization（OEO）；在 8 个 benchmark×target 设置、14 次对比中，GPT-5.5 驱动的 OEO 相对 SkillOpt 与 GEPA 取得 12 胜 1 平 1 负（唯一败绩仅 0.21 个百分点），且只用了 SkillOpt 目标交互 token 预算中位数的 34.3%；但换成中等能力优化器（Qwen3.5-27B）后 SkillOpt 反超 9.68/3.50 个百分点，弱模型甚至无法在 OEO 接口上产出合法动作——说明"规定式流水线"是随能力而变的脚手架，而非必需品。

> **TL;DR:** The paper separates the framework-owned *optimization contract* from the task-specific *optimization meta-policy*, and tests whether a frontier optimizer can compose the latter online. Open-Ended Optimization (OEO) with GPT-5.5 as optimizer beats two structurally different prescribed baselines — SkillOpt (staged, bounded-patch pipeline) and GEPA (Pareto reflective evolutionary search) — in 12 of 14 head-to-head cells across SearchQA, SpreadsheetBench, OfficeQA and LiveMathematicianBench with Qwen3.5-4B/GPT-5.5 targets: e.g. LiveMath/GPT-5.5 0.6855 vs SkillOpt 0.5000 (+18.55 pts) and vs GEPA 0.4032 (+28.23 pts), with only a 0.21-pt loss to GEPA on SearchQA/GPT-5.5, while consuming a median 34.3% of SkillOpt's configured target-interaction token budget. A zero-interaction one-shot GPT-5.5 rewrite control fails to reproduce the gains (LiveMath/Qwen 0.2742, *below* the 0.3065 initial skill), and a frozen-protocol capability ladder shows the delegation reverses at medium optimizer capability (SkillOpt +9.68 pts on LiveMath, +3.50 on SearchQA) and is blocked entirely for a weak optimizer. Worth reading if you build or evaluate skill/prompt self-evolution harnesses; the headline efficiency claim covers target-model tokens only, not optimizer tokens.

## 核心贡献

- **概念拆分**：明确区分 *optimization contract*（框架必须持有：目标、初始 skill、目标模型、可用选择数据 D_sel、允许的任务侧操作集 O、资源预算 B、冻结评测器、密封 final split）与 *optimization meta-policy*（证据调度、诊断、修改空间、候选保留、调度与停止），把"该不该规定流水线"从"提示词好坏"提升为系统级责任分配问题。
- **OEO 协议**：一个契约强制执行的 agent 循环（Algorithm 1）——优化器每轮观察当前 skill、历史 H、已提交 checkpoint K 与剩余预算，选择 INSPECT / RUNTARGET / REVISE / SELECT / STOP 中的一个；runner 只做合法性校验、计费、以及阻止访问密封集，不规定反思模板、编辑语言、候选调度或停止规则。
- **双代表性对照**：同时对比 pipeline-centric 的 SkillOpt（固定 rollout/reflection 批次、成功/失败分离诊断、有界 patch 算子、验证门控提交）与 search-centric 的 GEPA（自由文本变异 + Pareto 演化池），从而说明结论不是针对某一种流水线设计。
- **两个关键控制实验**：(a) static-input-matched 零交互一次性重写，证明收益不能被"前沿模型先验直接改写"解释；(b) 冻结协议的优化器能力阶梯（Qwen3.5-4B / Qwen3.5-27B / GPT-5.5），刻画出委派的能力边界。
- **过程 vs 行为的解耦诊断**：重建每个 byte-distinct 提交状态，定义最大归一化编辑量、Markdown section breadth、revision churn（式 2）三项路径指标，以及 pass/fail agreement、correct-set Jaccard J_C、gain-set Jaccard J_G 三项行为指标，发现规定式流程改变"路径"比改变"最终行为"更一致。

## Key Contributions

- Formalizes the split between the externally governed **optimization contract** and the **optimization meta-policy**, with action selection written as `a_t = µ^(q)(z_t; M_opt, C, I_q)` over state `z_t = (s_t, H_t, K_t, b_t)`, making "who owns the procedure" a measurable systems variable rather than a prompt-engineering detail.
- Introduces **OEO**, a contract-enforced loop where the optimizer composes evidence gathering, revision, checkpoint selection and stopping online; "open-ended" means online procedural composition under unchanged external constraints, not absence of constraints.
- Runs the comparison against **two deliberately non-overlapping forms of prescription** (bounded-patch staged pipeline vs free-form mutation in an evolutionary loop), so the result cannot be attributed to one weak comparator — and indeed GEPA beats SkillOpt in 3 of its 6 confirmatory cells.
- Establishes a **capability boundary**: delegation is not an optimizer-independent wrapper; it inverts at medium capability and fails to execute at weak capability.
- Provides **process-level trajectory instrumentation** showing path metrics and behavioral metrics are near-decoupled (Spearman ρ = 0.3095 between final-text distance and behavioral distance across the 8 settings).

## Methodology

Setup is persistent natural-language *skill* optimization: a target model `M_tgt` solves benchmark tasks using a reusable Markdown skill artifact, and an optimizer model `M_opt` improves that artifact from interaction evidence. All three procedures start from a byte-identical initial skill, share the same dataset snapshot, split, target endpoint, evaluator and permitted task-facing operations within each benchmark–target pair. Selection may only use the permitted `valid_seen` split; the sealed `valid_unseen`/`test` split is evaluated exactly once after selection and supplies the reported pass rate.

Three procedures are compared. **SkillOpt** fixes rollout and reflection batching, separates success/failure diagnosis, restricts revisions to bounded patch operators, gates commits on strict validation improvement, and keeps a rejected-edit memory. **GEPA** allows free-form trace-conditioned textual mutation but the framework owns parent selection, minibatch evaluation cadence, Pareto pool retention and termination; the aligned condition evolves only the common persistent skill, starts from the identical artifact, disables optional merging, and returns one validation-selected candidate. **OEO** exposes the same permitted operations through a generic contract-enforcing interface and delegates everything procedural.

Resource accounting separates optimizer-side tokens from target-model tokens spent during optimization and checkpoint-selection rollouts; SkillOpt's configured allocations define the common reference budget and the other two report realized use as a fraction of it. Because model calls are atomic, small overshoots are possible, so the paper compares sealed performance and realized token use separately rather than claiming matched realized cost.

Controls: the **one-shot control** receives the byte-identical initial skill plus the same static step-0 information as OEO (benchmark/target identity, interface spec, objective, budget fields, evaluator and output requirements, tool-availability description), then has tools disabled — it cannot inspect examples, run the target, see trajectories or scores, or revise twice. The **capability ladder** freezes prompts, target endpoint, data, seed, action interface and protocol, varying only the optimizer across Qwen3.5-4B / Qwen3.5-27B / GPT-5.5, with weak and medium OEO caps matched to realized frontier-OEO token budgets; invalid actions are *not* repaired and count as operational failures. All GPT-5.5 calls go through the GitHub Copilot Responses API.

## Results & Highlights

- **Headline sweep:** across 14 head-to-head comparisons over 8 benchmark–target settings, GPT-5.5-driven OEO records **12 wins, 1 tie, and 1 loss of 0.21 percentage points**. Against SkillOpt it is 7 wins / 1 tie over 8 settings; against GEPA 5 wins over 6 confirmatory settings. OEO improves the initial skill in **all 8** settings, SkillOpt in 7, GEPA in 5 of 6.
- **Largest margin (LiveMath / GPT-5.5 target, n=124):** OEO **0.6855** vs SkillOpt **0.5000** (**+18.55 pts**) and vs GEPA **0.4032** (**+28.23 pts**), from a shared initial skill of 0.3871. This single setting carries most of the headline narrative.
- **Smallest margin / only loss (SearchQA / GPT-5.5, n=1,400):** OEO **0.8714** vs GEPA **0.8736** (**−0.21 pts**) and vs SkillOpt 0.8657 (+0.57). On SearchQA the three methods are effectively tied, so the "delegation wins" claim generalizes weakly on the largest-n benchmark.
- **SpreadsheetBench (n=280):** with a GPT-5.5 target, OEO and SkillOpt **tie at 0.7607** (initial 0.3964) while OEO spends only **6.1%** of the reference target-token budget; with a Qwen3.5-4B target, OEO reaches **0.2464** vs SkillOpt **0.1964** (+5.00 pts) — and notably SkillOpt *regresses below* the 0.2107 initial skill here.
- **Token use:** OEO uses a median **34.3%** of SkillOpt's configured target-interaction token budget and stays under 100% in every setting; on OfficeQA and LiveMath GEPA consumes ~100–105% in all 4 runs while OEO uses **19.7%–59.4%** and scores higher. Caveat reported by the authors: OEO *exceeds* SkillOpt's configured **optimizer**-token budget in 3 settings and hits 98.9% in a fourth — the saving is selective target interaction, not uniform cost reduction.
- **Zero-interaction control (Table 3):** the one-shot GPT-5.5 rewrite helps on SearchQA (+2.07 and +5.00 pts over initial) but remains **6.14 and 3.57 pts below OEO**; on LiveMath it *lowers* both initial scores (Qwen 0.3065 → **0.2742**; GPT-5.5 0.3871 → **0.3468**) while OEO gains **+34.68 and +29.84 pts**. Even crediting the 2 disclosed item-level timeouts as correct, the GPT-5.5 one-shot only reaches 0.3629, leaving OEO ahead by 32.26 pts.
- **Capability ladder (Table 4, Qwen3.5-4B target):** at medium capability SkillOpt leads by **9.68 pts on LiveMath (0.5887 vs 0.4919)** and **3.50 pts on SearchQA (0.7157 vs 0.6807)**; at weak capability OEO is **blocked** (no executable action, no rollout) while SkillOpt completes — though weak SkillOpt on SearchQA scores **0.6579, below the 0.6693 initial skill**, so executability ≠ usefulness. Moving medium → frontier raises OEO by **+16.13 / +7.07 pts** vs SkillOpt's **+2.42 / +0.64**, quantifying OEO's much higher capability sensitivity.
- **Path vs behavior (Table 5 / Figure 3):** OEO shows larger max normalized edit, larger max section breadth and higher revision churn in **all 8** paired runs, yet pass/fail agreement is **0.7016–0.9629** and correct-set Jaccard **0.3778–0.9581**. SearchQA/GPT-5.5 reaches 0.9629 agreement and 0.9581 J_C despite different histories; conversely OfficeQA/Qwen has close aggregate scores but J_C of only **0.5000**, and SpreadsheetBench/Qwen only **0.3778** — similar scores can hide complementary correct-item sets. Final-text distance vs behavioral distance correlate at only **ρ = 0.3095**.

## Authors & Credibility

Two authors, Hui Xue and Fan Yang, both Microsoft Research. The comparator SkillOpt is itself a Microsoft-affiliated line of work (refs [16, 17], including an official Microsoft project repository), so the paper is in part an internal critique of its own group's pipeline — which cuts both ways: strong access to the reference implementation and its configured budgets, but also privileged knowledge of how to align (or mis-align) it. GEPA is an external, independently published baseline (ICLR 2026), which strengthens the comparison. The evaluation stack (SearchQA, SpreadsheetBench, OfficeQA, LiveMathematicianBench) mixes an old QA set with three recent agentic/enterprise/math benchmarks. No code or artifact release is mentioned anywhere in the paper; the appendix documents protocol but not availability.

## Critical Assessment

**Novelty (moderate-high, conceptual more than technical).** OEO is not a new algorithm — it is deliberately the *absence* of one, a contract-enforced agent loop with five actions. The contribution is the clean contract/meta-policy factorization and the experimental design that isolates it. That framing is genuinely useful and is more disciplined than most "let the LLM do it" papers, because permitted operations, data boundary and evaluator are held byte-identical.

**Rigor (mixed).** The single most important weakness is stated plainly in Appendix A.1: *"Each reported numerical score corresponds to one completed optimization run."* There are no seeds, repeats, confidence intervals or variance estimates anywhere. On LiveMath a single item is 0.81 pts and on OfficeQA 0.58 pts, so the +2.33 pt OfficeQA margins are 4 items and the +2.91 pt GEPA margin is 5 items — well inside plausible run-to-run noise for a stochastic frontier-model optimizer called through the GitHub Copilot Responses API (no temperature/seed control described). The 18.55-pt LiveMath gap is large enough to survive this concern; most of the other cells are not. The paper's own "12 wins, 1 tie, 1 loss" tally therefore over-reads: strip the cells whose margin is under ~3 pts and the score sheet becomes roughly 5 clear wins and 8 near-ties.

**Selective reporting.** The 2 SpreadsheetBench GEPA cells are post-hoc checkpoints matched to OEO's token use, explicitly excluded from the confirmatory count — but they are still printed in Table 2 with the 0.4964 GPT-5.5 number, and GEPA's *native full-budget* SpreadsheetBench result is never reported. Given SpreadsheetBench/GPT-5.5 is the one setting where OEO fails to beat SkillOpt (tie at 0.7607), the missing full-budget GEPA cell is exactly the number a skeptic wants.

**Design choice that flatters the conclusion's second half.** "Invalid actions are not repaired and count as operational failures" is what produces the dramatic *blocked* result for the weak optimizer. A single format-repair retry, a constrained decoding grammar, or a few-shot action example would likely unblock Qwen3.5-4B, and the paper offers no such ablation. The claim "a weak optimizer cannot operate through the unchanged OEO interface" is thus partly an artifact of interface engineering rather than a fact about optimizer capability. Similarly, the aligned GEPA condition *disables optional merging*, a handicap justified for artifact alignment but never quantified.

**Missing internal ablations.** OEO bundles at least four freedoms — optimizer-directed evidence scheduling, unbounded edit space, checkpoint SELECT, and adaptive STOP. No experiment attributes the gain to any one of them. The most interesting hypothesis raised by the data (OEO wins big exactly where the initial skill is very weak, e.g. LiveMath initial 0.3065/0.3871, and ties where it is strong, e.g. SearchQA 0.7857) is never tested; a plausible alternative story is "unbounded rewrites help when the artifact needs replacing, bounded patches suffice otherwise," which would substantially reframe the headline.

**Efficiency claim needs an asterisk.** "Median 34.3% of the budget" is target-interaction tokens only. OEO overshoots SkillOpt's optimizer-token budget in 3 of 8 settings, and optimizer tokens are GPT-5.5 tokens — the expensive ones. The paper discloses this honestly in-text but the abstract does not.

**Reproducibility (low-to-moderate).** GPT-5.5 behind a Copilot endpoint, no released code or skill artifacts mentioned, no seeds, single runs, and benchmark versions (LiveMath is a *live* benchmark, so its snapshot matters) all make exact replication unlikely. The diagnostic definitions in A.4 are precise enough to reimplement, which is a plus.

**Significance (high if it holds).** If prescribed pipelines really are capability-dependent scaffolding, a lot of harness engineering in the self-evolving-agent literature is transient. The capability-ladder crossover is the paper's most durable and most useful result, and it is stated with unusual honesty for a paper whose headline is "you may not need the pipeline."

**Red flags:** n=1 runs with sub-5-pt claimed wins; a headline efficiency metric that excludes the dominant cost; one benchmark (LiveMath, n=124) supplying the dramatic numbers; GEPA's full-budget SpreadsheetBench result absent; no OEO component ablation; no retry policy for the "blocked" condition.

## Strengths

- The contract/meta-policy distinction is crisp, operational, and immediately reusable as a way to describe any self-evolution harness.
- Two structurally opposite prescribed baselines instead of one, and the paper points out that GEPA beats SkillOpt in 3 of 6 confirmatory cells — pre-empting the "weak comparator" objection with evidence rather than assertion.
- The zero-interaction control is the right control and is well-matched (byte-identical skill, identical static step-0 information, tools then disabled), and it produces the most convincing single result in the paper: the one-shot rewrite *regresses* on both LiveMath targets.
- The negative result (medium-capability crossover, weak-capability block) is reported prominently rather than buried, and the conclusion is explicitly conditional ("delegate only to an optimizer that can carry it").
- The trajectory diagnostics are a real methodological contribution: churn (eq. 2), section breadth, and gain-set Jaccard J_G separate "different text" from "different behavior," and the finding that similar scores can hide 0.3778 correct-set Jaccard is a genuinely useful warning for anyone benchmarking self-evolving agents on aggregate pass rate alone.
- Honest footnotes (the 2 LiveMath timeouts, the optimizer-token overshoot, the descriptive-only Spearman) rather than silent smoothing.

## Limitations

- Single run per cell; no variance, seeds, or significance testing, while several headline margins are 4–6 evaluation items.
- Small sealed splits for three of four benchmarks (n = 124, 172, 280); only SearchQA has n = 1,400, and that is precisely where all methods tie.
- Only one artifact type (a natural-language Markdown skill) and one optimizer family at the frontier (GPT-5.5); no test of whether delegation transfers to memory, tool policies, or code artifacts.
- The capability ladder covers 2 benchmarks, 1 target model, 3 optimizer sizes — thin evidence for a claim as general as "prescription becomes scaffolding as capability declines."
- No checkpoint instrumentation for GEPA, so the process-vs-behavior analysis is restricted to the OEO–SkillOpt pair.
- Cost accounting is not matched end-to-end; sealed performance and realized tokens are compared separately by construction.
- No ablation of OEO's internal freedoms, and no analysis of why gains concentrate on low-initial-score settings.

## Relevance

如果你关注 agent 自进化 / skill-prompt 优化框架（GEPA、DSPy、SkillOpt 这一系）以及"LLM 作为优化器"的能力边界，这篇给出了一个可直接复用的责任划分抽象（contract vs meta-policy）和一个反直觉但可信的能力阶梯结论：前沿模型可以自组织优化流程，中等模型反而需要流水线兜底。其 path-vs-behavior 诊断（correct-set Jaccard 低至 0.3778 而聚合分数接近）对任何只看 pass rate 的 agent 评测实验都是直接的方法论警告。

## Questions for Further Exploration

- Would a single format-repair retry or constrained action decoding unblock the weak Qwen3.5-4B optimizer under OEO? If so, how much of the "capability boundary" is interface engineering rather than reasoning capability?
- Does the win margin correlate with the initial skill's headroom? LiveMath (initial 0.3065/0.3871) yields +18.55/+34.68 while SearchQA (initial 0.7857) yields ties — is OEO's advantage "unbounded rewrite when the artifact is bad" rather than "better online meta-policy"?
- Which OEO freedom matters: evidence scheduling, unbounded edits, checkpoint SELECT, or adaptive STOP? A leave-one-out ablation would convert a systems observation into a design rule.
- What happens under end-to-end matched *dollar* cost, counting optimizer tokens at frontier prices? Does the 34.3% target-token saving survive?
- Since OEO and SkillOpt reach complementary correct sets in some settings (OfficeQA/Qwen J_C = 0.5000, SpreadsheetBench/Qwen J_C = 0.3778), can their selected skills be ensembled or merged for a score above either?
- Does the conclusion transfer beyond natural-language skills — to executable tool libraries (Voyager-style), to memory stores, or to multi-agent workflow graphs (ADAS/AFlow), where invalid-action rates and verification costs differ sharply?
- Given GEPA's full-budget SpreadsheetBench result is missing, does GEPA close the gap there when allowed its native selection?
