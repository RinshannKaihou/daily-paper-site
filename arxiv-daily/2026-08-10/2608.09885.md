> **一句话总结：** SHE 把 LLM agent 的"安全护栏"（harness）拆成系统提示、规则库、安全记忆、工具策略四个可独立编辑的构件，用 rollout 轨迹的失败诊断做归因路由并只做局部编辑，在 Agent-SafetyBench 上把平均 ASR 从静态 SafeHarness 的 17.1% 降到 5.5%（3.1×），同时平均攻击下效用 UA 从 31.6% 提到 47.6%，并零额外演化迁移到 AgentHarm（Harm Score 19.8%→9.8%）。

> **TL;DR:** SHE treats the agent harness as an evolvable object rather than a fixed deployment artifact. It decomposes the harness into four artifacts with disjoint safety responsibilities (System Prompt, Rule Bank, Safety Memory, Tool Policy), then runs an attribution-guided loop that turns failed rollout trajectories into structured diagnoses (harm domain / attack surface / failure mode), routes each diagnosis to the responsible artifact, applies bounded local edits, and accepts a candidate harness only if safety strictly improves and utility does not regress. On Agent-SafetyBench (first 200 tasks, DeepSeek-V3.2 agent, 6 attack conditions), SHE (evolved) reaches 5.5% average ASR vs 17.1% for the static SafeHarness baseline (3.1× reduction) and 19.2% for PROGENT, while raising average utility-under-attack from 31.6% to 47.6% and cutting clean unsafe-behavior rate from 42.8% to 19.8%. On held-out AgentHarm the same evolved harness drops Harm Score from 18.0% (SafeHarness) to 9.8% with Benign non-refusal essentially unchanged (77.8% vs 68.2%). Worth reading if you build agent guardrails; be aware the evolution model and the Agent-SafetyBench judge are the same model (GPT-5.5) and the "evolved" baselines were not re-evolved on SHE's split.

## 核心贡献

- **把安全 harness 当作可演化对象**：现有 harness-level 防护（Task Shield、Progent、AgentGuard、SafeHarness、LlamaFirewall）部署后是静态的，安全边界依赖人工设计的规则；SHE 让 harness 从历史 rollout 轨迹中自己学出并持续细化安全边界。
- **功能解耦的四构件表示** H = (P_sys, R_bank, M_safe, Q_tool)：系统提示定义全局行为契约与信任边界；规则库存结构化安全规则（allow/warn/block/sanitize/judge 五种干预）；安全记忆只存"反复演化后仍未解决"的失败案例的对比式边界；工具策略定义工具权限与运行时执行点（pre-call policy + runtime detector）。解耦的目的是让失败可以被归因到单一构件，从而做局部编辑而不扰动其他组件。
- **归因驱动的演化循环**：结构化风险诊断（三维标签：harm domain / attack surface / failure mode）→ 构件路由 → 有界编辑（每条编辑须写明目标构件、修改范围、更新操作、学到的内容、支撑轨迹）→ 有效性检查（ValidEdit 专门拦截 reward hacking、无依据的能力删除、表面安全增益）→ best-harness 选择（严格要求 S↑ 且 U 不降），被拒绝的编辑连同拒绝理由回灌给下一轮。
- **实证结论**：安全提升可以来自架构演化而非改权重，且学到的边界能跨风险（AgentHarm）与跨模型（Kimi K2.6 / GLM-5.2 / MiniMax M2.7）迁移。
- **可诊断的案例证据**：论文给出 R17 学到的"应用获取边界"——允许推荐与官方商店指引，禁止代用户在设备上自动安装并禁止虚假的"已安装"完成声明，说明学到的是语义边界而非一刀切拒绝。

## Key Contributions

- Reframes agent safety as an **architectural property that can evolve**, not a fixed set of hand-written rules baked in at deployment time.
- A **functional decomposition** of the harness into four editable artifacts with explicit, non-overlapping safety responsibilities, which is what makes failure attribution and localized (non-global) editing possible.
- An **attribution-guided evolution loop** (Algorithm 1) with three safeguards that distinguish it from naive prompt evolution: a validity check against reward-hacking edits, a strict monotone safety-utility acceptance rule, and a rejection-feedback buffer `F_rej` that prevents re-proposing rejected edits.
- A **special update rule for Safety Memory**: an entry is written only when a failure pattern survives two rounds of evolution or recurs after artifact updates — i.e., memory is the fallback for what rules and policies could not fix.
- Evidence for **generalization without re-evolution**: held-out benchmark transfer (AgentHarm) and cross-agent-model transfer (harness evolved on DeepSeek-V3.2, applied to three other agent models).
- An **evolution-model ablation** showing the loop is not GPT-5.5-specific: DeepSeek-V3.2 and GLM-5.2 as evolution models also improve the seed harness, converging at different points on the safety-utility frontier.

## Methodology

The system is formalized as (π_θ, E, H) where only H — the non-parametric harness — is optimized; the base policy, environment, and evaluation protocol Ω are held fixed. Each task x_i produces a rollout trajectory τ_i recording user task, constructed context, model responses, tool calls, tool observations, harness decisions, and final response; Ω maps (x_i, τ_i) to an outcome o_i = (o_safe, o_util).

Each round k: (1) roll out a fixed evolution subset under the current best harness H_best; (2) select risk-relevant cases I^(k); (3) for each, the evolution model produces a structured diagnosis z_i containing trajectory evidence plus three risk dimensions — harm domain (privacy exfiltration, financial loss, physical harm, cyber/vulnerable code, availability, legal/ethical, misinformation), attack surface (clean user goal, user/context input, tool output or retrieved content, tool spec/registry poisoning, memory/history, multiple channels), and failure mode (unsafe compliance, tainted-context compliance, unauthorized tool use, unsafe side effect / blind trust, task failure or over-refusal); (4) route z_i to the responsible artifact(s) r_i; (5) generate a bounded edit set Δ^(k) conditioned on rejected-edit feedback F_rej; (6) run ValidEdit to check schema conformance and reject unsupported restrictions, unnecessary capability removal, or superficial safety gains; (7) build the candidate H̃ = H_best ⊕ Δ^(k) and accept it only if S_Ω(H̃) > S_Ω(H_best) **and** U_Ω(H̃) ≥ U_Ω(H_best), else restore H_best and append (Δ^(k), reason) to F_rej.

Experimental setup: Agent-SafetyBench (2,000 tasks, 349 environments, 8 risk categories) restricted to the first 200 tasks following SafeHarness's ordering. Fifteen fixed task IDs (11, 18, 22, 28, 46, 49, 56, 61, 74, 75, 89, 100, 120, 174, 199) form the evolution split; the remaining 185 are held-in evaluation. Each task runs under six conditions — clean, context poisoning, indirect injection, tool tampering, memory injection, composite — giving 90 task-condition instances and, at two replications each, 180 trajectories per round. Twenty evolution rounds. Base agent: DeepSeek-V3.2. Evolution model and Agent-SafetyBench full-trajectory judge: GPT-5.5. AgentHarm judge: GPT-4o. Temperature 0 everywhere. Metrics: Clean UBR (unsafe behavior on non-attacked tasks), ASR, UA (utility under attack); AgentHarm reports Harm Score, Harm Refusal, Benign non-refusal.

## Results & Highlights

- **Held-in Agent-SafetyBench average ASR: SHE (evolved) 5.5% vs static SafeHarness 17.1% (3.1× reduction), PROGENT 19.2%, Memskill-SafeHarness 19.6%, System prompt 28.5%, LlamaFirewall 31.5%, No defense 34.6%.** Utility moves the same direction rather than trading off: average UA 47.6% for SHE vs 31.6% for SafeHarness (+16.0 pts, the paper's "50.6% higher UA" in relative terms) and 38.7% for No defense.
- **Clean UBR: 19.8% for SHE (evolved) vs 42.8% for SafeHarness and 42.9% for No defense (-23.0 pts).** Notably SafeHarness's clean unsafe-behavior rate (42.8%) is statistically indistinguishable from having no defense at all — its ASR gains come entirely from the attacked conditions, which makes it a weaker headline comparator than the 3.1× framing suggests.
- **Evolution over the seed harness is a real but much smaller delta than the baseline delta:** SHE (seed, no evolution) already achieves 8.6% ASR / 25.7% clean UBR / 33.5% UA. Evolution buys ASR 8.6%→5.5% (-3.1 pts), clean UBR 25.7%→19.8% (-5.9), UA 33.5%→47.6% (+14.1). So roughly two-thirds of the safety gain over SafeHarness comes from the *decomposed seed design*, and the *evolution loop* mostly buys utility recovery.
- **Per-attack breakdown is not uniformly favorable.** On tool tampering SHE (evolved) has ASR 8.2% vs SafeHarness's 4.9% — SHE is actually worse on that column, though its UA there is 38.6% vs SafeHarness's 14.1%. On composite attack SHE is 1.1% ASR vs SafeHarness 3.8% and Memskill-SafeHarness 8.6%; on memory injection 6.0% vs SafeHarness 29.8%.
- **Held-out AgentHarm (no re-evolution): Harm Score 9.8% for SHE (evolved) vs 18.0% for SafeHarness, 19.8% for SHE (seed), 36.4% for LlamaFirewall, 51.9% for No defense.** Harm Refusal 86.4% vs 78.4% (seed) and 74.4% (SafeHarness). Benign non-refusal 77.8% vs 77.9% (seed) — i.e., the safety gain costs essentially nothing in over-refusal, whereas SafeHarness sits at 68.2%.
- **Artifact-replacement ablation (evolved → seed, one artifact at a time):** replacing evolved Safety Memory hurts most (ASR 5.5%→7.7%, UA 47.6%→40.7%, clean UBR 19.8%→26.4%); System Prompt 7.0%/44.9%; Tool Policy 7.3%/47.0%; Rule Bank 6.4%/47.2%. All four degrade, confirming the gains are learned rather than inherited — but each individual degradation is only 0.9–2.2 ASR points, so no single artifact dominates.
- **Evolution-model ablation:** DeepSeek-V3.2 as the evolution model converges at round R03 with clean UBR 17.6% / ASR 4.3% / UA 40.4% — *strictly safer than the reported GPT-5.5 headline* (19.8% / 5.5% / 47.6%) — while GLM-5.2 (R05) lands at 24.0% / 5.9% / 36.0%. The headline configuration is therefore the utility-preserving point, not the safest one; the paper is upfront about this.
- **Evolution history (Appendix B):** only 5 of 20 rounds produced accepted updates (R00, R03, R04, R05, R17), with a 11-round plateau from R05 to R16 where every candidate was rejected by the joint safety-utility rule.

## Critical Assessment

**Novelty (moderate-to-good).** The individual pieces are not new — trajectory-driven artifact evolution is GEPA/EvoTest/SkillOpt, and harness-level guardrails are SafeHarness/Progent/AgentGuard. The contribution is the specific claim that *functional decoupling is a prerequisite for safe evolution*, and Figure 4's framework-evolution ablation directly tests it (evolving coupled frameworks like LlamaFirewall and SafeHarness reduces ASR but regresses clean safety or utility). That is the paper's most interesting result and it is unfortunately reported only as a figure without a numeric table.

**Rigor (the weakest part).** Three concrete problems. (1) **Judge–optimizer collusion:** GPT-5.5 is both the evolution model that writes the harness edits and the full-trajectory judge that scores Agent-SafetyBench. ValidEdit is intended to catch "evaluator-specific shortcuts," but ValidEdit is itself run by the evolution model, so the anti-reward-hacking check has the same blind spots as the optimizer. The AgentHarm transfer (GPT-4o judge) partially mitigates this and is the more trustworthy headline number. (2) **The "evolved" baselines are not actually evolved on this task distribution** — Appendix A states PROGENT and Memskill-SafeHarness "retain the artifacts/configurations evolved under the data and benchmark specified by their own implementations; they are not re-evolved on SHE's 15-task split." Comparing a method evolved on the target distribution against methods evolved on a different distribution is not an apples-to-apples "evolved baseline" comparison, and it inflates the adaptive-baseline gap. (3) **No variance reporting anywhere** — two rollout replications per task-condition pair, no error bars, no seeds, no significance tests, on 185 held-in tasks. A 3.1-point ASR delta between seed and evolved could plausibly sit inside noise.

**Data quirks.** In Table 2, the PROGENT row (39.2 / 51.1 / 75.1) is numerically identical to the System prompt row across all three AgentHarm metrics — either a copy-paste error or an unexplained coincidence, and it is not discussed. Also, evolution uses only 15 of 2,000 Agent-SafetyBench tasks, and evaluation uses only the first 200 of 2,000 tasks; whether the "first 200" ordering is risk-balanced is inherited from SafeHarness without verification.

**Missing ablations.** No ablation on the number of evolution rounds vs. cost (20 rounds × 180 trajectories = 3,600 evolution rollouts plus a full held-in re-evaluation on every valid candidate — the compute bill is never stated). No ablation isolating the ValidEdit check or the F_rej rejection-feedback buffer, both of which are argued to be important. No over-refusal measurement on a dedicated benign-only suite for Agent-SafetyBench (Clean UBR measures unsafe behavior, not unnecessary refusal); benign non-refusal only appears for AgentHarm. Cross-model transfer (Figure 3) has no accompanying table, so the transfer claim cannot be quantitatively checked.

**Significance (good).** If the decoupling claim holds, it is directly actionable for anyone shipping an agent harness: the four-artifact schema in Appendix C (rule records with harm domain / trigger / intervention / benign exemption / priority / supporting trajectories; contrastive safety-memory entries; pre-call policies plus runtime detectors) is concrete enough to reimplement without the evolution loop and still get most of the seed-harness gain.

**Red flags.** Same model as optimizer and judge; unequal treatment of adaptive baselines; a duplicated baseline row; no variance; the abstract's "3.1× ASR reduction" is measured against a baseline (SafeHarness) whose clean-condition safety is no better than no defense at all.

## Strengths

- The safety-utility acceptance rule is *strictly monotone* (S must improve, U must not degrade), which is a genuinely stronger selection criterion than the scalarized objectives most self-evolving-agent papers use, and the evolution history shows it doing real work: 15 of 20 rounds were rejected.
- Utility is not sacrificed for safety — the usual failure mode of guardrail papers. SHE's UA (47.6%) exceeds even the no-defense baseline (38.7%), and AgentHarm benign non-refusal stays at 77.8% while SafeHarness pays 68.2%.
- The Figure 5 case study is a good demonstration that the loop learns *semantic boundaries* ("recommend apps, do not install them, and do not claim you installed them") rather than keyword blocklists or blanket refusals.
- Held-out benchmark transfer plus cross-model transfer, with no re-evolution in either case, is the right generalization protocol and rules out the most obvious form of overfitting to the 15 evolution tasks.
- Unusually good reproducibility detail: exact evolution task IDs, judge template, artifact field schemas, round-by-round acceptance history, temperature-0 determinism.

## Limitations

- Evolution set is 15 tasks / 90 task-condition instances — tiny, and the entire safety-boundary corpus is learned from ~180 trajectories per round.
- Only the first 200 of Agent-SafetyBench's 2,000 tasks are used at all; coverage of the benchmark's 8 risk categories and 349 environments in that slice is not reported.
- Single base agent (DeepSeek-V3.2) for the main evolution run; the cross-model results are transfer-only, so it is unknown whether evolving *on* GPT-5.5 or Kimi would yield a different harness.
- The evolution model must read full trajectories and rewrite structured artifacts, so the method inherits a strong-frontier-model dependency at development time (though not at deployment time).
- No adaptive adversary: attacks are the six fixed Agent-SafetyBench conditions, so nothing tests whether an attacker who sees the evolved Rule Bank/Tool Policy can route around it — a natural concern for a defense whose boundaries are learned from a finite failure set.
- Safety Memory's role as "unresolved failure" storage means the harness monotonically accumulates text; no analysis of context-length growth, rule conflicts, or artifact pruning over longer horizons.

## Relevance

与 LLM agent 安全、guardrail 设计和自演化 agent 系统的关注点高度契合：它把 "safety harness" 从静态配置变成可用轨迹反馈优化的对象，四构件 schema（规则库/工具策略/安全记忆的字段定义）即使不跑演化循环也可以直接复用到自己的 agent 防护栈里。同时它也是一个很好的方法论警示样本——优化器与评判器同为 GPT-5.5、基线未在同一分布上重新演化，这两点在设计自己的 self-evolving 实验时值得刻意避开。

## Questions for Further Exploration

- How much of the reported gain survives if the Agent-SafetyBench judge is switched to a model outside the evolution model's family (e.g., evolve with GPT-5.5, judge with Claude or DeepSeek)? The AgentHarm/GPT-4o numbers hint the answer is "most of it," but this needs a direct held-in test.
- What happens if PROGENT and Memskill-SafeHarness are re-evolved on the same 15-task split with the same rollout budget? That is the only fair adaptive-baseline comparison and it is currently absent.
- Does the harness keep improving past 20 rounds, or does the R05–R16 plateau indicate the 15-task evolution set is exhausted? A rounds-vs-performance curve on a larger evolution set would separate "loop converged" from "evolution data exhausted."
- Is the evolved harness robust to an adaptive attacker with white-box access to the Rule Bank and Tool Policy — i.e., does localized boundary learning create narrow, enumerable rules that generalize worse than a coarse but broad guardrail?
- Can the four-artifact decomposition be validated causally, e.g., by measuring cross-artifact interference directly (edit artifact A, measure behavior change attributable to B's responsibility) rather than inferring it from the coupled-framework ablation in Figure 4?
- What is the total compute/API cost of one evolution run, and how does the safety-per-dollar compare against simply fine-tuning the base policy on the same failure trajectories?
