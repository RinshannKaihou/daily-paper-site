> **一句话总结：** Scale AI 提出 HarnessOpt-Bench，用一个"保留测试集 + 受信执行沙箱 + 固定评估预算"的协议，评测 5 个前沿 LLM 作为优化器去改写 4 个下游任务智能体 harness 的能力；结果显示优化器模型之间的差距(平均 +0.142)明显大于其编码 harness 的影响(平均 +0.079)，原生 harness 并无稳定优势，Claude Opus 5 在 3 个有能力的种子任务上稳居第一档。

> **TL;DR:** HarnessOpt-Bench is a held-out, budget-bounded benchmark where an optimizer LLM (paired with a coding harness) edits a target agent's seed harness under a fixed evaluation budget and is scored by normalized gain over the seed on an inaccessible test split. Across 111 scored runs spanning OfficeQA, BrowseComp-Plus, Terminal-Bench, and GAIA, the optimizer *model* matters about 1.8x more than the coding *harness* (0.142 vs 0.079 mean gain swing), native harnesses give no consistent edge (shared wins 11, native wins 9 of 20 pairs), and claude-opus-5 lands alone in tier 1 (LSS-λ +0.228); the strongest config captures ~0.63 of OfficeQA headroom while the weakest (gpt-5.6-terra, LSS-λ -0.174) is unresolved from zero on two tasks.

## 核心贡献

- **提出可控的 harness 优化基准。** 定义了一个约束式随机程序优化问题：优化器(一个 LLM + 一个编码 harness)接收目标智能体的种子 harness、带打分的 dev/validation 反馈和固定的目标评估预算，编辑 harness 后提名最终候选；最终用候选在"搜索全程不可见的测试集"上相对种子的归一化增益打分。
- **受信、可复现的评估协议。** 基于 VeRO 构建，用受信执行环境强制评估边界、隔离保留集状态、计量目标智能体资源使用、用 Git 提交版本化每个候选以供审计；四个任务固定 20/40/40 的 dev/val/test 切分，种子基线和多种现成 harness 的成绩都一并记录。
- **对优化器模型与编码 harness 的受控比较。** 在共享 harness (opencode) 与各模型原生 harness (claude-code/codex/kimi-cli) 下评测 5 个前沿模型(claude-opus-5、claude-sonnet-5、gpt-5.6-sol、gpt-5.6-terra、kimi-k3)，产出 111 个计分 run，并在 GAIA 上额外加测 goose、mini-swe-agent 两个 harness。
- **揭示尚存的能力差距。** 在 OfficeQA 上沿 GPT 与 Claude Opus 两代际阶梯跟踪，前者增益从 +0.03 单调升到 +0.49；轨迹分析显示"探索更广"与增益正相关(ρ 从 +0.34 到 +0.88)，而"读执行 trace"与增益负相关(-0.31 到 -0.64)。

## Key Contributions

- **A controlled benchmark for harness optimization.** Formalizes harness optimization as a constrained stochastic program-optimization problem (Algorithm 1). An optimizer receives a pinned seed harness H0, graded dev/validation feedback under partition-specific disclosure, and a fixed evaluation budget B; it nominates a final candidate scored by normalized gain g = (E(H+) - E(H0)) / (1 - E(H0)) on a held-out test partition that is never visible during search.
- **A trusted, reproducible evaluation protocol.** Builds on VeRO with a sandboxed optimizer that can only write the target agent's harness, a per-case evaluation sandbox, a model API gateway enforcing allow-lists and per-scope budgets, and immutable Git commits for every candidate. The four tasks use exact, byte-verified 20/40/40 splits and K=3-round pooled baselines.
- **A paired controlled comparison of optimizer models vs coding harnesses.** Five frontier optimizer models are run under both a shared harness (opencode) and each model's native harness, plus two extra harnesses on GAIA, yielding 111 scored runs and a balanced grid that isolates the model effect (LSS-λ) from the scaffold effect.
- **Empirical findings on the structure of the capability.** Model choice moves gain ~1.8x more than harness choice (0.142 vs 0.079); native harnesses show no consistent advantage; gains separate strongly by tier; broader lever exploration correlates with gain while trace-reading does not; and case-pass budgets (not call caps) are the binding constraint.

## Methodology

HarnessOpt-Bench frames harness optimization as a constrained, stochastic program-optimization problem (Algorithm 1). The optimizer interacts with a trusted server: at each step it either commits a candidate harness H′, or picks an existing candidate H and a case subset Q and requests an evaluation F_θ(H, Q) → (ŝ, φ), observing outputs through a partition-specific disclosure policy π_D. Search ends when the budget B is exhausted or the optimizer nominates a candidate H⁺.

**Candidates and invariants.** A candidate H is an executable codebase; no semantic partition is imposed between prompts, tools, memory, and control flow. The optimizer may edit any file subject to a fixed execution interface and a few immutable paths. The task fixes invariants θ = (M, E, V): the pinned target model M, the per-case environment E, and the verifier V. Changing θ defines a different task, not a different candidate.

**Evaluation and disclosure.** Cases are split into disjoint dev/validation/test (20/40/40). Development reveals case inputs, per-case outcomes, and traces (for diagnosis); validation reveals only an aggregate score (for selection); the test partition reveals nothing during search and is scored only after nomination. The objective is normalized gain g = (E_θ(H⁺) − E_θ(H0)) / (1 − E_θ(H0)); because H0 is pinned and test disclosure is empty, the optimizer never observes the quantity it maximizes.

**Budget.** The primary budget components are 100 evaluation calls per partition and four full case passes on each of dev and validation, plus a cap on total target-model tokens. The optimizer's own inference is metered but uncapped.

**The suite (4 tasks).** OfficeQA Pro (target: deepseek-v4-flash, baseline 0.341, split 49/98/99); BrowseComp-Plus (deepseek-v4-flash, 0.462, 33/66/66); Terminal-Bench 2.0 (grok-build, 0.241, 17/36/36); GAIA (gpt-5.4-mini, 0.000 because the seed is a non-functional stub, 33/66/66). Three of four seeds are competent-but-naive Python agents with deliberate headroom; GAIA's is a stub, so gain there equals the raw held-out score.

**Optimizers and scoring.** Five optimizer models × {shared harness opencode, native harness} = 10 core configurations, plus goose and mini-swe-agent on GAIA. Each configuration is run twice; each held-out evaluation is the mean of three attempts per test case (matching the K=3 baseline pooling). The paper defines a task-specific resolution band from re-scoring the same candidate and treats smaller differences as unresolved rather than formally significant, and reports a composite LSS-λ score from an additive task+model fit on the balanced shared-harness grid.

## Results & Highlights

- **Model choice dominates coding-harness choice.** Holding task and harness fixed, changing the optimizer model moves gain by **0.142 on average**; holding task and model fixed, changing the harness moves it by **0.079 on average** — a model contrast ~1.8x larger. Both exceed the per-task resolution bands (OfficeQA ±0.045, BrowseComp-Plus ±0.066, Terminal-Bench ±0.054, GAIA ±0.035).
- **Native harnesses have no consistent advantage.** Across the 20 model–task pairs run under both, the shared harness (opencode) wins **11**, the native harness wins **9**, and **0** are tied; in 11 of the 20 pairs the difference exceeds the task resolution band but the direction varies by model and task.
- **Per-task best (normalized gain, Table 1).** OfficeQA: claude-opus-5 / opencode = **0.63** (best column); BrowseComp-Plus: claude-opus-5 / opencode = **0.48**; Terminal-Bench: claude-opus-5 / opencode = **0.29**; GAIA (gain = raw held-out score since seed baseline is 0.000): gpt-5.6-sol / codex = **0.49**.
- **Task-adjusted model effect (LSS-λ, Table 4, resolution ±0.058).** claude-opus-5 = **+0.228** (tier 1 alone); claude-sonnet-5 = +0.029 (tier 2); kimi-k3 = -0.014 (tier 2); gpt-5.6-sol = -0.069 (tier 2); gpt-5.6-terra = **-0.174** (tier 3).
- **Extremes separate, the middle does not.** The strongest config captures roughly **two thirds of OfficeQA headroom and half of BrowseComp-Plus headroom**, while the weakest is unresolved from zero on BrowseComp-Plus and Terminal-Bench; intermediate configurations often differ by less than their round-to-round variation.
- **Generational ladder on OfficeQA (Figure 3).** Across 5 GPT releases gain rises monotonically from **+0.03 to +0.49** with three of four steps exceeding the resolution band; across 5 Claude Opus releases gain ranges **+0.37 to +0.59** (non-monotonic but first-to-last spread exceeds the band).
- **Broader exploration correlates with gain.** The fraction of eight pre-specified OfficeQA harness levers touched during search correlates positively with gain on every task, ρ from **+0.34 (GAIA) to +0.88 (OfficeQA, BrowseComp-Plus)**.
- **Trace-reading is not associated with gain.** The share of actions reading evaluation output correlates negatively with gain across all four tasks (−0.31 to −0.64); detailed trace spans were requested only **16 times by 7 of the 111 cells**.
- **Case-pass budgets bind, not call caps.** The median optimizer uses **8 of 200 calls (4%)** but **82% of its case-pass allowance**; **55 of 100 cells** exhaust at least one partition's case budget.
- **On GAIA, the native-harness effect is concentrated, not absent.** Both GPT models are 4–5 resolution bands better under codex (native minus best shared: **+0.179** for gpt-5.6-sol, **+0.131** for gpt-5.6-terra), while both Claudes and Kimi sit within a band or two of zero either way.
- **Visible validation scores are optimistic.** Most cells in Figure 13 fall below the identity line: the submitted candidate's test score is lower than the best validation score observed during search, justifying the held-out test partition.

## Authors & Credibility

All seven authors are at **Scale AI Research**, and the paper explicitly builds on the authors' own prior system VeRO (Ursekar et al., "VeRO: A harness for agents to optimize agents," ICML 2026), which supplies the trusted execution infrastructure reused here. The benchmark itself is positioned as complementary to concurrent end-to-end optimizers (MetaHarness, Agentic Harness Engineering, HarnessX) whose method-specific seeds/budgets/protocols make them hard to compare directly. The empirical design is unusually disciplined for an agent-benchmark paper: pinned seeds, byte-verified disjoint splits, K=3-round pooled baselines, two replicates per configuration, explicit task-specific resolution bands rather than overclaimed significance, 111 scored runs, and a transparent LSS-λ composite with two cross-checking estimators that produce the identical ordering. Artifacts (seed agents, split manifests, build configs, evaluation harness) are stated to be released.

## Critical Assessment

- **Novelty.** The core conceptual move — fixing the target model/environment/verifier, holding out the test partition throughout search, and varying the optimizer model and coding harness factorially — is a genuinely useful methodological contribution that prior harness-optimization work (MetaHarness, Agentic Harness Engineering, HarnessX) did not isolate. It is more of an evaluation/benchmarking contribution than a new optimization method, which the paper is honest about.
- **Rigor.** Strong on controlled comparison (balanced shared-harness grid for LSS-λ, byte-verified splits, K=3 pooling, two replicates, explicit resolution bands). The honesty about "tiers rather than a complete ranking" and the refusal to over-claim significance is commendable. The three-estimator agreement check on LSS-λ ordering is a nice robustness detail.
- **Weak / uneven baselines.** The GPT-5.6-terra tier-3 result (LSS-λ −0.174, unresolved from zero on two tasks) raises the question of whether the frontier is being represented fairly; only one member of the GPT-5.6 family is strong, and the paper does not explain *why* terra lags sol so dramatically beyond naming the release. A reader cannot tell if this is a real capability gap or a harness/tooling mismatch. Relatedly, the GAIA seed is a non-functional stub, so "gain = raw held-out score" and GAIA is explicitly excluded from the LSS-λ fit — meaning the headline model ranking rests on only three competent-seed tasks.
- **Missing ablations.** The paper does not vary seed complexity systematically (it flags this as a limitation), so "diagnosis-and-refinement" and "construction-from-scratch" regimes are conflated in the suite rather than controlled. There is no systematic ablation of the budget itself (e.g., what happens at 2x or 0.5x the case-pass allowance), even though the "case passes bind" finding suggests gain is budget-sensitive. The optimizer's own inference is uncapped, so the results favor optimizers willing to spend more tokens; the search-cost figure (Figure 9) is shown but not folded into the ranking.
- **Data quirks.** The seeds are "deliberately untuned" (~130-line OfficeQA agent, non-functional GAIA stub), which maximizes headroom but means the benchmark measures improvement over a weak prior rather than over a realistically engineered agent — the off-the-shelf harness columns in Table 3 (e.g., opencode already at 0.727 on OfficeQA vs the seed's 0.341) suggest that simply swapping in a stock harness captures much of the gain without any optimization. The paper frames these columns as "context, not the reference," but a skeptic could read them as evidence that the benchmark rewards rebuilding a known-good harness more than genuine optimization.
- **Reproducibility.** High in principle: immutable dataset references, committed split manifests, Git-versioned candidates, lockfile-pinned deps, sandboxed per-case evaluation with dataset-declared timeouts, and released seeds/manifests/build configs. The caveat is that re-running requires non-trivial compute (target-model token caps, per-case sandboxes) and access to frontier models behind allow-lists, so independent reproduction is feasible but expensive.
- **Significance.** The benchmark fills a real gap: it is the first to make optimizer-model vs coding-harness comparison a controlled, held-out, budget-bounded measurement. The finding that the optimizer model matters ~1.8x more than the coding harness, and that native harnesses confer no consistent edge, is actionable for anyone evaluating frontier models on agentic self-improvement.
- **Red flags.** Hack-resistance is claimed ("designed to be hack-resistant, not hackproof"); the authors acknowledge repeated dev/validation feedback could still reward evaluator-specific strategies and call for future per-run jitter. The narrow task count (4), single pinned target model per task, and Python-only candidates limit how much "harness optimization as a general capability" can be inferred from the headline numbers.

## Strengths

- Clean, controlled factorial design that finally separates optimizer-model effects from coding-harness effects, which prior end-to-end optimizers conflated.
- Trusted execution protocol (sandboxed optimizer that can only write the harness, isolated per-case eval sandboxes, model API gateway, Git-versioned candidates) is a genuinely useful template for hack-resistant agent benchmarks.
- Intellectual honesty throughout: explicit resolution bands, "tiers not rankings," validation scores flagged as optimistic, two cross-checking LSS-λ estimators, and an Ethics Statement that names the dual-use tension.
- Rich trajectory analysis (lever coverage, trace-reading share, action profiles, search-cost frontiers) gives process-level insight, not just a leaderboard.
- The generational-ladder experiments on OfficeQA turn the benchmark into a capability-progress signal across model releases, not just a single snapshot.

## Limitations

- Only **4 tasks** and **1 pinned target model per task**; generalization across languages (Python only), runtimes, agent architectures, and target models is untested.
- The headline LSS-λ ranking is computed over only the **3 competent-seed tasks** (GAIA excluded because its stub seed makes gain a raw score), so the model ordering rests on a narrow base.
- Seeds are deliberately weak; the off-the-shelf harness columns show much of the "headroom" can be captured by swapping in a stock harness, so the benchmark may reward reconstruction of known-good patterns over genuine optimization.
- Seed complexity is not varied systematically, conflating the "improve a mature agent" and "build from a stub" regimes.
- The optimizer's own inference is uncapped, biasing toward higher-spend optimizers; search-cost figures are reported but not incorporated into the ranking.
- Hack-resistance is acknowledged as incomplete; repeated dev/val feedback could reward evaluator-specific strategies, and the authors call for future per-run jitter in cases, tools, and verifiers.
- Two replicates per configuration do not estimate dispersion; ranges are reported descriptively, not as confidence intervals.

## Relevance

高度相关：本文把"harness 优化"（用 LLM 改写智能体外围的提示/工具/控制流/记忆以提升其评测成绩）首次变成一个受控、留出测试、预算受限的可测量能力，正是当前 LLM 智能体与自我改进方向的核心议题；其受信执行环境与留出评估协议也可直接用于评估其他自改进/meta-优化系统。

## Questions for Further Exploration

- How does the optimizer-model ranking change when the optimizer's own inference budget is capped to match, rather than left uncapped? Would the ~1.8x model-vs-harness gap shrink under equal compute?
- Since off-the-shelf harnesses already capture a large share of the seed headroom (e.g., opencode at 0.727 vs the OfficeQA seed's 0.341), how much of an optimizer's gain is genuine optimization vs reconstruction of a known-good harness? Would seeding with a mature agent invert the lever-coverage correlation?
- Why does gpt-5.6-terra lag gpt-5.6-sol so dramatically (tier 3 vs tier 2, often unresolved from zero)? Is it a model-capability gap, a tooling mismatch under the shared harness, or a release-specific failure mode?
- Would introducing per-run jitter in cases, tools, and verifier implementation (as the authors propose) collapse any of the current rankings, particularly the broader-exploration-correlates-with-gain finding, which could partly reflect exploitation of stable evaluator artifacts?
- Does the negative correlation between trace-reading and gain survive on tasks where per-case summaries localize failures poorly (e.g., long-horizon terminal tasks with sparse rewards), or is it specific to these four fairly summarizable benchmarks?
