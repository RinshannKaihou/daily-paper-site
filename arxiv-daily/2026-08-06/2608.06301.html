Critical Assessment · Data quirks
01 / METHOD

How the benchmark is wired

HarnessOpt-Bench frames harness optimization as a constrained stochastic program. An optimizer (an LLM paired with a coding harness) receives a pinned seed harness H₀, graded dev/validation feedback, and a fixed evaluation budget — then nominates a final candidate H⁺.

A candidate is an executable codebase; no semantic wall separates prompts, tools, memory, or control flow. The task fixes invariants θ = (M, E, V): the pinned target model, per-case environment, and verifier. The optimizer can edit anything except the execution interface and a few immutable paths.

The optimizer never observes the quantity it maximizes: test disclosure is empty throughout search, scored only after nomination.

g = ( Eθ(H⁺) − Eθ(H₀) ) / ( 1 − Eθ(H₀) ) // normalized gain over the seed on a never-visible test split

Cases split 20 / 40 / 40. Dev reveals inputs, outcomes, traces (diagnosis). Validation reveals only an aggregate score (selection). Test reveals nothing. Each held-out evaluation is the mean of K=3 attempts per case; two replicates per config.

03 / ASSESSMENT

Strengths vs. limitations

+ Strengths

  • Controlled factorial design finally separates optimizer-model effects from coding-harness effects — prior end-to-end optimizers conflated them.
  • Trusted-execution template: sandboxed optimizer (writes only the harness), per-case eval sandbox, API gateway with allow-lists, Git-versioned candidates.
  • Intellectual honesty: explicit resolution bands, "tiers not rankings," validation scores flagged optimistic, two cross-checking LSS-λ estimators.
  • Rich trajectory analysis — lever coverage, trace-reading share, action profiles, search-cost frontiers — process insight, not just a leaderboard.
  • Generational-ladder runs on OfficeQA turn the benchmark into a capability-progress signal across model releases.

– Limitations

  • Only 4 tasks, 1 pinned target model each; Python-only, single runtime/architecture — generalization untested.
  • Headline LSS-λ ranking rests on only 3 competent-seed tasks (GAIA's stub seed forces its exclusion).
  • Seeds are deliberately weak; off-the-shelf harnesses capture much headroom — may reward reconstruction over optimization.
  • Seed complexity not varied systematically — "improve a mature agent" and "build from a stub" regimes are conflated.
  • Optimizer inference is uncapped, biasing toward higher-spend optimizers; search-cost not folded into ranking.
  • Two replicates per config — no dispersion estimate; ranges are descriptive, not confidence intervals.
Authors · Credibility
All seven authors are at Scale AI Research; the benchmark explicitly builds on the authors' own VeRO system (ICML 2026), which supplies the trusted-execution infrastructure. The empirical design is unusually disciplined for an agent-benchmark paper: pinned seeds, byte-verified disjoint splits, K=3 pooling, two replicates, explicit per-task resolution bands rather than overclaimed significance, and a transparent LSS-λ composite with three estimators that produce the identical ordering. Artifacts (seeds, split manifests, build configs, eval harness) are stated to be released. The authors concede the suite is "designed to be hack-resistant, not hackproof."
04 / OPEN

Questions for further exploration

Q1 · COMPUTE PARITY

How does the ranking shift when the optimizer's own inference is capped to match instead of uncapped? Does the 1.8× model-vs-harness gap shrink under equal compute?

Q2 · GENUINE vs RECONSTRUCTION

If off-the-shelf harnesses already capture most seed headroom, how much gain is true optimization vs reconstruction? Would seeding with a mature agent invert the lever-coverage correlation?

Q3 · THE TERRA PUZZLE

Why does gpt-5.6-terra lag gpt-5.6-sol so dramatically (tier 3 vs 2, often unresolved from zero)? Real capability gap, shared-harness tooling mismatch, or release-specific failure mode?

Q4 · JITTER ROBUSTNESS

Would per-run jitter in cases, tools, and verifier implementation collapse any current rankings — particularly the exploration-correlates-with-gain finding, which could partly reflect exploitation of stable evaluator artifacts?
