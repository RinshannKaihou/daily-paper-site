01Methodology · the correction-accumulation loop

MERIT runs an online loop over a stream of queries. Every method starts from the same cached initial prediction (Spider 58.90% / BIRD 38.40%) so only the repair strategy varies. Memory is updated only at episode finalization — current-query attempts stay local.

STEP 01
Feedback
Oracle returns CORRECT / DENOTATION MISMATCH / EXECUTION ERROR + observable DBMS error text.
STEP 02
Classify
Deterministic ordered-rule classifier maps the failure into 8 coarse error types. No SQL AST parsing.
STEP 03
Retrieve
Type-conditioned hybrid: 0.75·dense + 0.25·BM25, per-pool min-max norm. ≤3 pos + 1 neg.
STEP 04
Repair
Frozen LLM emits one greedy revision from a single user-message prompt with retrieved memories.
STEP 05
Finalize
On success: +1 positive entry (failed→correct). On K=7 exhaust: ≤1 negative entry (last direction).
"Causal" = temporal availability. Only finalized earlier episodes are retrievable; "causal" denotes time-restricted memory, not causal inference.
Oracle-assisted regime. Repair uses a denotation-level correctness signal — stronger than what real deployments provide. Authors acknowledge this scope.
Memory entry shape: ⟨context, failure type, SQL transform, polarity, provenance⟩. Each episode contributes at most one entry.
Type-Reliability-Aware variant applies hard type filtering only for SYNTAX / SCHEMA LINKING / EXECUTION and a 0.10 soft bonus otherwise.

03Strengths & Limitations · side by side

Strengths

  • Exceptionally clean experimental design: identical backbone, identical cached initial predictions, identical feedback and budget — only repair strategy and stream order vary.
  • Paired query-cluster bootstrap with 95% CIs preserving per-query outcomes across seeds; a statistically principled comparison on identical query sets.
  • Honest, self-limiting reporting: explicitly foregrounds where MERIT does not beat baselines rather than cherry-picking the Spider win.
  • Schema-locality ablation yields a clean, actionable finding — same-database experience is consistently valuable, especially on BIRD's larger schemas.
  • Training-free, single open backbone, full prompts and classifier rules in appendices — high reproducibility for the core protocol.

Limitations

  • Oracle-assisted regime: requires denotation-level correctness during repair — stronger than real-world feedback; DBMS-error-only regime untested.
  • Single backbone (Qwen2.5-7B-Instruct), single language, dev-set-only evaluation. No multilingual / conversational / production-DB transfer claim.
  • Not reliably separated from untyped Dynamic RAG — polarity separation and hard type conditioning are not proven necessary.
  • Deterministic classifier is coarse (~48% accuracy, Macro-F1 ≈ 0.32–0.36); dominant RESULT-MISMATCH bucket conflates semantic errors.
  • No comprehensive sensitivity study over retrieval mixture (0.75/0.25 fixed), allocation (3 pos + 1 neg fixed), or fallback threshold (≥3 fixed).
  • Not cheaper than stateless repair in total tokens; cost accounting omits embedding, indexing, retrieval latency, and maintenance overhead.

04Open Questions · where this leads next

  1. Would a learned or calibrated failure classifier (Macro-F1 > 0.6) finally let hard type-conditioned retrieval beat untyped Dynamic RAG, or is the RESULT-MISMATCH bucket inherently too coarse to partition?
  2. How do gains change under a realistic DBMS-error-only regime (no denotation oracle), where the polarity signal must be approximated — does the positive-memory advantage collapse?
  3. Is the BM25-vs-dense dataset-dependence explained by schema size, and would a schema-aware mixture weight recover the lost Spider BM25 penalty while keeping the BIRD benefit?
  4. Does scaling the backbone (Qwen2.5-32B / 72B) widen or narrow MERIT's advantage, given that stronger models may already internalize the repair patterns it retrieves?
  5. Can the schema-locality finding be exploited explicitly via a per-database memory index with bounded growth, closing the BIRD gap to Reflexion-style at lower cost?
  6. Since current-query attempts cannot be retrieved, does limited intra-episode reuse of the best same-query prior attempt (with anti-leakage guards) help without violating the "causal" framing?
