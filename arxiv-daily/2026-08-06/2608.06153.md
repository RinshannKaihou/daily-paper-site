> **一句话总结：** 提出 GSE 框架，通过显式建模技能间关系的 Skill Relation Graph（SRG）与"聚类合并+回放验证"的泛化机制，把编码 Agent 的技能进化从局部更新重构成全局优化问题，在 Bug 触发测试生成与误报 Bug 报告过滤两项任务上稳定超越 Live-SWE-agent、Trace2Skill 与人工技能，F1 最高提升 93.8%（测试生成）与 66.7%（误报过滤），并在字节跳动内部 Agent 上带来 61.4% 的 F1 提升。

> **TL;DR:** GSE reframes coding-agent skill evolution as a global optimization problem: it co-evolves inter-skill relationships via a Skill Relation Graph (SRG) and turns trace-local updates into reusable skills through cluster-based consolidation plus replay-driven validation. On a 108-bug Java benchmark (from Multi-SWE-Bench) and an industrial 500-report Go dataset (IndustrialBugs), GSE beats the strongest baseline (Live-SWE-agent / Trace2Skill) on OpenHands and mini-SWE-agent — e.g., on OpenHands test generation lifting F1 from 0.22 to 0.31 (+40.9%) and on OpenHands false-positive filtering lifting precision from 0.29 to 0.55 (+89.7%) and F1 from 0.43 to 0.70 (+62.8%) — while using fewer downstream tokens than every competing method and yielding +61.4% F1 on ByteDance's proprietary bug-triage agent.

## 核心贡献

- **把技能进化重构为全局优化问题：** 指出现有方法（Trace2Skill、Live-SWE-agent）把技能更新当作独立局部操作，会引入相互冲突或过拟合的技能，从而随着技能库增长逐步退化整体质量。GSE 是首个把"技能内容 + 技能间关系"同时作为一等演化对象的框架。
- **Skill Relation Graph（SRG）：** 用有向图显式建模技能间的 `dependency`、`co-usage`、`conflict` 三类语义关系。当某个提案修改技能时，GSE 通过邻居检索 + 全库语义分析找到受影响技能，并生成配套的"辅助演化提案"以保证全局一致性。
- **DSL 化的演化提案 + 局部回放验证：** 用领域特定语言严格结构化每个提案（target skill / operation / content / rationale / expected behavior / relationship updates），并在合并前先回放原始失败用例过滤掉无效提案。
- **聚类合并 + 回放驱动的泛化机制：** 把针对同一技能集或语义相似的提案聚类，由 merge agent 抽象出更通用的能力（如把"集合大小 bug""权限 bug"抽象为"value-triggered / state-triggered"分类能力）；再用历史相关用例回放，只有保持或提升性能的候选技能库才被接受，直接对抗过拟合与回归。
- **跨基准、跨 Agent、跨语言的实证：** 在 Java（Multi-SWE-Bench 派生，108 个真实 bug、9 个项目）和 Go（与工业伙伴构建的 IndustrialBugs，500 份报告、8 个生产仓库）上，覆盖 OpenHands、mini-SWE-agent 与字节内部 Agent，并采用 one-project-held-out 协议验证跨项目泛化。

## Key Contributions

- Reframes automated skill evolution as a global optimization problem over an interconnected skill bank, arguing (and demonstrating via ablation) that local-only updates accumulate incompatible, overfitted skills.
- Introduces the Skill Relation Graph (SRG), a directed graph whose edges encode `dependency`, `co-usage`, and `conflict`; evolution proposals are propagated to neighboring and semantically related skills via auxiliary proposals, preserving global consistency.
- Defines a DSL-based evolution proposal schema and gates every proposal with a local replay check that discards proposals failing to fix their originating trace before any generalization cost is incurred.
- Adds a skill generalization stage (Algorithm 1): cluster proposals by affected-skill set or semantic similarity, abstract shared capability patterns with a merge agent, then accept the candidate skill bank only if replay on relevant historical cases preserves or improves performance.
- Releases two complementary evaluation surfaces — a Java bug-revealing test-generation benchmark derived from Multi-SWE-Bench (108 verified triggerable focal methods across 9 projects) and IndustrialBugs, a proprietary Go false-positive-filtering dataset (500 reports, 132 real bugs, 368 false alarms, 8 production repos) — and validates across OpenHands, mini-SWE-agent, and an industrial proprietary agent under a one-project-held-out protocol.

## Methodology

GSE is a feedback loop layered on a skill-augmented coding agent. The agent's expected success rate is treated as a function of the skill bank D, and the goal is to find D* maximizing expected success over the task distribution. The pipeline has three stages.

**1. Trace Collection.** The base agent (OpenHands or mini-SWE-agent) is instrumented to record reasoning blocks, tool calls, parameters, environment feedback, and task outcome. A trace-simplification step strips token-heavy but causally low-value content (full `find`/`grep` results, raw file dumps, info-level compile/test logs) while preserving commands, targeted paths, key errors/warnings, and reasoning — producing a "semantic-rich" trace.

**2. Evolution Proposal Generation.** An update agent (powered by DeepSeek-V4-Flash) first performs hierarchical failure diagnosis, classifying the root cause as a navigation failure, reasoning failure, or execution failure, and formulates a root-cause hypothesis. This yields one of two evolution forms: general capability enhancement (workflow/decision-making) or reusable problem-pattern capture (bug-triggering patterns, library constraints). To preserve compatibility, GSE consults the SRG (nodes = skills, edges ∈ {dependency, co-usage, conflict}); for each proposal it identifies affected neighbors plus semantically related skills retrieved by metadata (capability category, task type, execution stage) and content analysis, then emits auxiliary proposals that co-evolve affected skills and their relationships. Proposals are expressed in a DSL (Figure 2) specifying target skill, operation, content, rationale, expected behavior, and relationship updates. Each proposal is locally validated by applying it to a temporary candidate bank and replaying the originating failure; failures are discarded immediately.

**3. Skill Generalization (Algorithm 1).** Locally validated proposals are clustered: those modifying existing skills use the affected-skill set as the key; those introducing new skills are clustered by semantic similarity of rationale and expected behavior. A merge agent abstracts common patterns and removes case-specific detail (e.g., consolidating "minimize collection size" and "preserve auth state" into a "Determine Bug Triggering Mechanisms: value-triggered vs. state-triggered" skill). Each resulting candidate bank is replayed against relevant historical cases (cases where affected skills were previously activated, or all cases that generated the clustered proposals for new skills); the candidate is committed only if it preserves or improves performance, which is the mechanism that blocks regressions and overfitting. State is persisted in SQLite and the skill bank is versioned via Git worktree for reproducibility and concurrency safety.

## Results & Highlights

All numbers are from the paper's Tables 1-5; LLM temperature is set to zero and evaluation uses a one-project-held-out protocol.

- **Bug-revealing test generation (Table 1), OpenHands:** GSE reaches precision 0.35 / recall 0.28 / F1 0.31, beating the strongest baseline (0.33 P / 0.17 R / 0.22 F1, held by Human-Skill for precision and Live-SWE-agent for recall/F1) by +6.1% precision, +64.7% recall, and +40.9% F1.
- **Bug-revealing test generation (Table 1), mini-SWE-agent:** GSE reaches precision 0.55 / recall 0.29 / F1 0.38 vs. the strongest baseline 0.43 P / 0.22 R / 0.29 F1, i.e., +27.9% precision, +31.8% recall, and +31.0% F1; F1 improvement over the base agent spans 31.0%–93.8%.
- **False-positive filtering (Table 2), OpenHands:** GSE reaches precision 0.55 / recall 0.95 / F1 0.70 vs. the strongest baseline 0.29 P / 0.84 R / 0.43 F1 (Trace2Skill) — a +89.7% precision gain, +13.1% recall, and +62.8% F1.
- **False-positive filtering (Table 2), mini-SWE-agent:** GSE improves precision 0.26→0.30, recall 0.84→0.97, F1 0.39→0.46 over the strongest baseline (+15.4% precision, +19.8% recall, +17.9% F1).
- **Ablation (Table 3, OpenHands):** Removing the SRG drops F1 from 0.31→0.27 (test gen) and 0.70→0.59 (filtering); removing generalization drops F1 to 0.27 and 0.54 respectively — both components are load-bearing, with generalization being especially critical on filtering (0.70→0.54).
- **Cost (Table 4):** GSE's evolution cost is 401.55K tokens/case vs. 357.64K for Trace2Skill (+12.28%), but downstream task execution is the cheapest of all methods at 593.21K tokens/case — actually 4.3%–4.4% fewer than Human Skills / Live-SWE-agent / Trace2Skill, because evolved skills induce more efficient reasoning.
- **Industrial deployment (Table 5):** On ByteDance's proprietary bug-triage agent (base F1 0.43), GSE reaches precision 0.56 / recall 0.97 / F1 0.71 — a +61.4% F1 gain over human-written skills (0.44) and +65.1% over the base agent, showing the method transfers to a strong, domain-tuned agent rather than only weak open-source harnesses.
- **Data-leakage check:** The authors verified that none of GSE's bug-triggering tests match the benchmark reference tests, and the industrial partner confirmed IndustrialBugs repos are excluded from public LLM training corpora.

## Authors & Credibility

The work is a collaboration between Tianjin University (Chen Yang, Jiashuo Tian, Ziqi Wang, Xinyin Liu, Junjie Chen) and Tsinghua University (Meiru Ye). The senior author group has a track record on LLM-based testing — including "Reflective unit test generation for precise type error detection" (Yang et al., 2025) and "Characterizing and mitigating false-positive bug reports in the Linux kernel" (Tian et al., 2026) — which directly grounds both evaluation tasks. The involvement of an unnamed "internationally leading IT and AI technology company" (identified in the abstract as ByteDance) supplies a genuine industrial dataset (IndustrialBugs, 500 reports labeled by original committers across 8 production repos, 12.8–186.3 KLoC), which materially strengthens ecological validity beyond typical academic benchmarks. The human-skill baseline was authored by 6 senior engineers with 6–10 years of experience, making that baseline non-trivial rather than a strawman. Implementation is built on official OpenHands/mini-SWE-agent with a lightweight skill-loading shim, baselines reuse released artifacts, and all methods share the same LLM (DeepSeek-V4-Flash), tools, environment, and per-task budget — a careful harness-isolation design.

## Critical Assessment

- **Novelty:** The framing of skill evolution as global optimization is genuinely useful, and the SRG with explicit `dependency`/`co-usage`/`conflict` edge types plus DSL-encoded relationship updates is a concrete, reusable mechanism rather than a vague "use an LLM to coordinate" hand-wave. The replay-driven acceptance gate is a clean, framework-agnostic safeguard against regressions.
- **Rigor:** The one-project-held-out protocol, zero-temperature LLM setting, shared LLM/agent/budget across methods, and the reference-test matching check for data leakage are all methodologically sound. The ablation cleanly attributes gains to SRG and generalization separately.
- **Weak / cherry-picked baselines — partial concern.** Human-written skills are an honest, strong baseline (6 senior engineers), but the authors themselves note existing public skill banks (Anthropic Skills, SkillsBench, SWE-Skills-Bench) were not directly applicable, so the human baseline is custom-built and not externally reproducible. More importantly, both Live-SWE-agent and Trace2Skill are adapted off their primary use case (Live-SWE-agent was built to evolve tools/scaffolds, not skills; Trace2Skill's "merge at once" is a deliberately naive integration), so the comparison somewhat favors GSE's dedicated skill pipeline. A reader should treat the headline percentage ranges (e.g., recall "+31.8%–180.0%") cautiously: the 180% upper bound comes from OpenHands where the base recall is only 0.06–0.17, so large relative deltas sit on small absolute denominators.
- **Missing ablations / analyses:** There is no analysis of SRG quality (precision/recall of inferred edges, how often auxiliary proposals actually fire, graph size growth over time), no breakdown of which of the three relation types contributes most, and no sensitivity study on the clustering threshold or replay-set size. The merge agent and update agent prompts are not released, limiting reproducibility despite the SQLite/Git-worktree versioning claims.
- **Dataset scale and balance:** The Java test-generation benchmark is only 108 focal methods across 9 projects, and IndustrialBugs is class-imbalanced (132 real bugs vs. 368 false alarms) — the very high recall numbers (0.95–0.97) on filtering partly reflect that the agent can default toward "real bug," so the precision gains are the more meaningful signal. The paper does not report per-project variance or confidence intervals, so some of the smaller deltas (e.g., mini-SWE-agent filtering F1 0.39→0.46) could be within noise even at temperature 0, given LLM non-determinism across API calls.
- **Significance:** Real — the cross-harness, cross-language, and industrial-deployment evidence is more convincing than single-benchmark skill papers, and the "global optimization" framing is a good conceptual contribution that other skill-evolution work will likely adopt. But the absolute F1 on test generation (0.31–0.38) is still low, indicating bug-revealing test generation remains a largely unsolved problem and GSE is an incremental, not transformative, step there.
- **Red flags:** None severe. The "internationally leading IT company" is named in the abstract as ByteDance but anonymized in the body — a minor inconsistency. No artifacts/data release is mentioned, which is the main reproducibility risk.

## Strengths

- Conceptually clean reformulation of skill evolution as global optimization, with the SRG as a first-class, co-evolved object rather than an afterthought.
- Replay-driven acceptance gate is a principled, model-agnostic defense against the exact failure mode (overfitting + regression) that the paper diagnoses.
- Strong and broad experimental coverage: two tasks, two open-source SOTA harnesses, one industrial proprietary agent, two languages (Java + Go), one-project-held-out generalization protocol, and an industrial dataset labeled by original committers.
- Cost analysis (Table 4) is unusually honest: GSE is cheaper at inference time than every skill-bearing baseline, which strengthens the practical deployment claim rather than just reporting accuracy.
- Ablation isolates the two mechanisms and shows both matter, with the generalization stage being especially decisive on filtering.

## Limitations

- Small absolute scale on the headline benchmark (108 Java focal methods) and no reported per-project variance or confidence intervals, despite LLM API-level non-determinism even at temperature 0.
- Live-SWE-agent and Trace2Skill are evaluated off their primary design intent (tool/scaffold evolution and one-shot merging respectively), which inflates GSE's relative advantage; a within-design comparison (e.g., Live-SWE-agent on tool evolution vs. GSE) is missing.
- SRG quality is never measured: no metrics on edge- inference accuracy, conflict detection precision, graph growth, or how often auxiliary proposals actually propagate and help.
- No artifacts, prompts, or datasets are stated to be released; IndustrialBugs is proprietary by necessity, but the Java benchmark, DSL schema, and merge/update agent prompts could be open-sourced and are not.
- Clustering and replay-set heuristics (similarity threshold, historical-case selection) are under-specified, making the generalization stage the least reproducible component.
- Absolute F1 on test generation remains low (≤0.38), so the practical bug-detection utility is still limited even with GSE.
- Only DeepSeek-V4-Flash is used; sensitivity to the underlying LLM is not studied.

## Relevance

直接命中"编码 Agent 自我进化 / 技能学习"方向：GSE 把技能库当全局优化对象、用 SRG 显式建模技能间依赖与冲突、用聚类+回放防止过拟合，对研究 LLM Agent 的长期自适应与可组合技能体系高度相关，尤其是它把"局部经验"抽象成"可复用能力"的泛化机制对自进化 Agent 设计有直接借鉴价值。

## Questions for Further Exploration

- How sensitive are the gains to SRG edge quality? If the dependency/co-usage/conflict edges are noisy or missing, does GSE degrade gracefully, or does propagation amplify errors?
- What is the per-relation-type contribution (dependency vs. co-usage vs. conflict)? Could the SRG be pruned to only `conflict` edges without losing much?
- How does GSE behave under distribution shift between evolution-time and evaluation-time projects — do generalized skills transfer to a held-out language (e.g., evolve on Java, evaluate on Python) or a held-out domain?
- Can the replay-driven acceptance gate be made cheaper (e.g., via a learned regressor predicting replay outcome) to cut the +12.28% evolution-token overhead?
- Does the framework extend to agentic RL-style skill acquisition (cf. Skill1, SkillRL) where skills are policies rather than prompts, and where the SRG would need to model policy-level compatibility?
- How stable are the small absolute deltas (e.g., mini-SWE-agent filtering F1 0.39→0.46) under non-zero temperature and across LLM providers, given no variance is reported?
