> **一句话总结：** EvoMem 在 AlphaEvolve 风格的进化式代码搜索（GigaEvo）之上加了一层跨 run 持久记忆——把历史 run 中成功的变异事件蒸馏成带 provenance 的"记忆卡片"，在新任务变异时检索至多 3 张作为**建议**注入 prompt；在剔除同 benchmark 记忆的跨任务迁移设定下，9 个 benchmark 平均目标指标相对提升 6.40%、搜索速度平均 5.93×（HotpotQA EM 0.5389→0.6015，KernelBench 2.4941→2.7049），Circle Packing(32) 消融中完整方法闭合 97.4%±3.6% 的目标差距，而随机记忆只有 5.6%、纯检索无重排只有 18.7%。

> **TL;DR:** EvoMem adds a persistent cross-run memory layer to an AlphaEvolve-style evolutionary code-search loop (GigaEvo baseline, Gemini 3 Flash backbone): successful mutation events are distilled offline into structured, provenance-carrying "memory cards," and at mutation time at most k=3 task-filtered cards are injected as soft advice. Against the identical no-memory GigaEvo baseline on 9 held-out benchmarks (memories from the target benchmark are excluded), it reports +6.40% average relative target-metric gain and 5.93× average search speedup — e.g. HotpotQA exact match 0.5389 → 0.6015 (+11.79% relative), KernelBench 2.4941 → 2.7049 (+16.89%), AlgoTune 461.51 → 495.37 (+7.90%) — and in the single Circle Packing (32) ablation (5 trials/condition) closes 97.4% ± 3.6% of the gap to the best-known fitness 2.9370 versus 5.6% for random memory and 53.7% for generic advice.

## 核心贡献

- **提出 EvoMem**：面向 LLM 驱动进化程序搜索的持久化记忆架构，跨 run、跨任务复用"变异知识"，而不是复用具体程序。核心主张是成功的变异策略（数值稳定技巧、剪枝规则、数据布局改动、prompt 结构）比它诞生的那份代码更具一般性。
- **两阶段读写分离**：写阶段（run 结束后离线）从程序谱系中抽取候选 idea、DBSCAN 聚类去重、LLM 决策 store/discard/merge、并做 origin analysis 筛出"高价值 idea"；读阶段（每次变异前）先做 LLM 任务范围过滤，再在多语义视图（mechanism / task context / explanation）上做 lexical + embedding 混合检索，返回至多 3 张卡片。昂贵操作全部离线，变异时开销有界。
- **保守的晋升与合并规则**：一个 idea 只有在能定位引入点、优于最强父代、极少产生更差后代、且有额外信号（兄弟对比、后代扩散、复现）时才进入高价值快照；抽象 idea 卡片只在描述"同一机制"时才合并，不因来自同一任务而合并；模糊情况保留新卡（偏向 recall）。
- **可审计性设计**：每个候选程序都记录它用了哪些 card id，从而能回溯到源程序，并统计下游 fitness delta（用中位数聚合，因为进化 fitness 变化稀疏且重尾）。
- **机制级审计而非只看端到端指标**：报告了记忆库覆盖率（HoVer 100%、Heilbronn 81.3%、KernelBench 仅 5.4%、Kissing Number 仅 3.3%）以及"idea 是否真被写进子程序"的接受率审计（默认检索 4.05% vs 随机记忆 0.25%，程序级 9.43% vs 0.69%）。

## Key Contributions

- A persistent memory architecture for LLM-based evolutionary program search that stores *abstracted mutation tactics* with provenance rather than replaying prior programs, implemented as a drop-in extension to the open-source GigaEvo pipeline.
- A write/read split: an offline post-run write phase (extraction → enrichment → origin analysis → conservative dedup/merge) and a bounded online read phase (LLM task-scope filter → multi-view hybrid retrieval → ≤3 cards → advice block in the mutation prompt).
- A memory-card schema (card_id, description, task_summary, metric_context, explanations, keywords, source_program_ids, provenance, aliases, links, usage_stats, retrieval_views, optional code/fitness) plus write- and read-phase pseudocode, making the system auditable and reimplementable.
- A cross-task transfer evaluation protocol: build the bank from a memory-generation set (Circle Packing 26, Heilbronn, Kissing Number 11D, HotpotQA, HoVer, GSM8K, 7 AlgoTune tasks, 5 KernelBench kernels), then evaluate on a held-out set with all memories from the target benchmark removed.
- A controlled 6-condition ablation on Circle Packing (32) separating "memory content" from "extra prompt text" and "retrieval machinery," plus a lineage-dynamics analysis showing memory-guided mutations are more often valid (47.9% vs 40.2%) and more reproductively successful (0.87 vs 0.73 direct children per mutation).

## Methodology

EvoMem sits on top of GigaEvo, an open-source AlphaEvolve-style loop (MAP-Elites archive, LLM mutation operator, evaluator-in-the-loop selection). The intervention is deliberately narrow: parent selection, mutation generation, validation, scoring, and population update are byte-identical between control and treatment; the only difference is whether the memory advice channel in the mutation prompt is populated.

The formal data flow is `P_r --extract--> C_r --write--> M --select(p,τ,µ)--> I_p ↪ mutation prompt`, where `P_r` are the programs of run r, `C_r` the extracted cards, `M` the persistent bank, and `I_p` the small instruction list for parent program p under task τ with metric description µ.

**Write phase.** After a run, completed programs are filtered (roots, invalid outputs, missing fitness/mutation metadata dropped) and normalized into records with fitness, generation, parentage, task context, mutation strategy, code, and improvement descriptions. Two analyzers exist: a default mode where an LLM classifies each recorded improvement as a genuinely new idea, a revision, or a reformulation (updating the working collection while appending provenance and keeping old wordings as aliases), and a *fast analyzer* used when a run yields many near-duplicate descriptions — DBSCAN over sentence embeddings (eps=0.25, min_samples=2) groups candidates, then an LLM refines ambiguous multi-member clusters. Usage attribution uses `Δf = f(child) − max_{p∈parents} f(p)`, computed only when both child and parents pass the task-specific validity check, aggregated by median. Origin analysis then promotes a smaller "high-value" snapshot. Dedup compares each incoming idea against multiple textual views with a weighted score `score(c) = Σ_q w_q s_q(c)` (largest weights on the description and description–explanation views), and an LLM policy decides store/discard/merge.

**Read phase.** Before each mutation, a structured request is built from (parent program, task description, metric description, mutation mode, local context). An LLM first selects which *source tasks* in memory are plausibly relevant, narrowing the search space; a bounded selector loop (max_iters=3) then issues keyword, identifier, and field-aware vector queries (top_k per tool between 3 and 5), merges hits by card id, and may issue one focused follow-up query. The selected ≤3 cards become a truncated advice block; their ids are attached to the child program for later usage tracking. Memory is advice, never a hard constraint, which the authors argue limits negative transfer.

**Experimental setup.** All mutation/insight/lineage LLM calls use Gemini 3 Flash at temperature 0.7 via OpenRouter; prompt-evolution tasks (HotpotQA, HoVer, GSM8K) use Qwen3-8B as the *evolved* system's LLM. Embeddings are all-MiniLM-L6-v2. MAP-Elites uses a single island, archive size 75, 5 elites and 8 mutants per generation, most experiments at 30 generations (≈240 mutants). Hardware is a single A100-80GB node. Each memory-bank session extracted 99.71 ± 38.68 ideas per run and inserted 12.76 ± 7.51 after filtering. Token cost: ≈7.19M input / 0.89M output per evolution run, plus ≈0.68M input / 25k output for memory generation (i.e., memory adds roughly 9% input-token overhead offline). Search speedup is defined as the ratio of evaluated candidates the baseline vs. the memory run needs to reach *the baseline's* final best score.

## Results & Highlights

- **Aggregate transfer (Table 1, 9 benchmarks):** average relative target-metric gain **+6.40%** and average search speedup **5.93×** over the matched no-memory GigaEvo baseline, with min-gain average 1.64% and max-gain average 16.37%.
- **HotpotQA (200-sample fixed test set, exact match):** baseline 0.5389 → memory **0.6015** (Table 5), i.e. **+11.79% average relative gain** (range 5.16%–27.41%), with average search speedup 5.75×.
- **KernelBench (GPU-kernel target metric):** baseline 2.4941 → memory **2.7049**, **+16.89% average gain** — but the range is 0.00%–65.93% and the speedup range is 0.05×–9.00×, so the mean is driven by one outlier run and at least one memory run was ~20× *slower* to reach the baseline score.
- **AlgoTune (scientific-code speedup):** baseline 461.51 → memory **495.37**, **+7.90%** (range 6.22%–9.57%), average speedup 8.58× (min 0.82×).
- **Circle Packing (32):** baseline 2.7870 → memory **2.9289** (+5.21% avg, range 0.48%–9.29%), average speedup **9.26×** (max 22×) — the largest speedup in the table.
- **HoVer:** 0.7900 → **0.8080** (+2.42%, tightest range 2.28%–2.56%), speedup 2.71×; also the only benchmark with **100% memory-bank coverage**.
- **Kissing Number (12D):** an explicit **null on quality** — 840.0000 for both baseline and memory (0.00% gain, min = max = 0), with only a claimed 6.78× speed-to-reach-baseline-score; bank coverage was the lowest at 3.3%.
- **Ablation, Circle Packing (32), 5 trials/condition (Table 3), target-gap closure toward f\* = 2.9370:** no memory 2.8151 ± 0.0683 (0.0% ± 56.0%); random memory 2.8219 (**5.6%**); generic advice 2.8805 (**53.7%**); no task filtering 2.8714 (46.2% ± 94.2%); retrieval-only without re-ranking 2.8379 (18.7% ± 181.3%); **full EvoMem 2.9338 ± 0.0044 (97.4% ± 3.6%)**, whose *worst* run (2.9278) still beats the baseline mean, and whose SD is ~15× smaller than baseline.
- **Retrieval-quality audit:** default relevance-based retrieval reaches a **4.05%** idea-acceptance rate vs **0.25%** for random selection from the same bank (**16.2×**, +3.80 pp absolute; 6.23% vs 0.30% in group 1, 1.88% vs 0.20% in group 2). Program-level: at least one accepted idea in **136/1,442 (9.43%)** programs vs **10/1,451 (0.69%)** under random memory (13.7×).
- **Lineage dynamics (Table 4):** memory-associated mutations produce valid candidates 47.9% vs 40.2% (+7.7 pp), 0.87 vs 0.73 direct children (1.20×), 2.57 vs 2.21 descendants (1.16×), mean within-run objective rank 0.504 vs 0.429, best lineage rank 0.997 vs 0.667.

## Critical Assessment

**Novelty (moderate).** Persistent memory for agents (A-MEM, General Agentic Memory) and retrieval-augmented method memory for scientific ML (AgenticSciML) already exist; the specific contribution is grounding memory in *evolutionary lineage evidence* — an idea is promoted only if it can be traced to an introduction event that beat its strongest parent and spread into elites. That provenance-driven promotion rule is the genuinely new bit; the retrieval stack itself (DBSCAN + MiniLM + hybrid lexical/vector + LLM re-rank) is conventional.

**Rigor (mixed, with one serious gap).** The headline Table 1 reports average/min/max but **never states how many matched run pairs each benchmark used**, and there are no standard deviations, confidence intervals, or significance tests anywhere in the main results. Given that the only place n is stated (the ablation, n=5) shows a baseline SD of ±0.0683 on a mean of 2.8151 — larger than the entire reported 5.21% gain on the same task — the Table 1 numbers should be read as suggestive, not established. Averaging *ratios* for the speedup column also structurally inflates it: 22× and 0.05× cannot be meaningfully averaged into "5.93×." The Kissing Number (12D) row is the tell — identical final metrics (840.0000 both) yet a claimed 6.78× "speedup," which is what happens when the speed metric is "candidates to reach the baseline's own final score" on a task where the score plateaus early.

**Data quirk / possible leakage.** Circle Packing (26), Heilbronn, HotpotQA, and HoVer appear in *both* the memory-generation set and the evaluation set. The authors say they exclude "all memories produced from that benchmark," but Circle Packing (26) and Circle Packing (32) are listed as separate evaluation entries while (26) is also a memory-generation task — whether (26)-derived memories were excluded when testing (32) is never stated, and Table 2 explicitly shows Hexagon Packing being helped by "Circle/geometric optimization" memories. For near-identical task families this is closer to same-task warm-starting than cross-domain transfer.

**The acceptance audit undercuts the causal story.** A 16.2× relative improvement over random retrieval sounds decisive, but the absolute acceptance rate is **4.05%** — roughly 96 out of 100 retrieved cards are never materially incorporated into the child program, and only 9.43% of audited programs contain any accepted idea. It is hard to reconcile a 97.4% gap closure on Circle Packing (32) with a mechanism that visibly fires in under one in ten programs. The most parsimonious reading of Table 3 is different from the authors': *generic advice alone* closes 53.7% of the gap, so more than half the effect may come from simply adding an extra "here is some advice" section to the mutation prompt, independent of memory content. The paper does not test whether the generic-advice condition's text was matched in length or specificity to the retrieved advice.

**Missing ablations.** The ablation covers exactly one task (Circle Packing 32) — the authors justify this by cost, which is fair, but it means the k=3 card budget, the max_iters=3 retrieval loop, the median-vs-mean usage aggregation, the DBSCAN hyperparameters, and the fast-vs-default analyzer are all entirely untested. There is a single LLM backbone (Gemini 3 Flash) with no evidence the effect survives a different mutation model, and no comparison to any *external* memory-augmented baseline (ShinkaEvolve, OR-Agent's reflection memory, A-MEM) — the only competitor is the authors' own memory-off configuration.

**Significance.** If the effect holds, "memory as a first-class component of evolutionary coding systems" is a cheap and architecturally clean win (≈9% offline token overhead, no change to the evaluator). The variance-reduction result (SD 0.0683 → 0.0044) is arguably more valuable than the mean gain and is under-emphasized: for expensive evaluator-in-the-loop search, reliable convergence matters more than a few percent of headroom.

**Red flags.** Anonymized primary affiliation with no code URL in the text; abstract hedges heavily ("positive average improvements... for most evaluated settings") in a way the results tables' framing does not; no n, no error bars, and no significance testing in the headline table; a 65.93% max-gain outlier folded into a KernelBench mean presented alongside benchmarks with 2 pp spreads.

## Strengths

- The control is unusually clean by construction: treatment and control differ only in whether the advice channel is populated, with evaluator, parent selection, validation, and scoring literally unchanged. This is a better-designed intervention than most agent-memory papers manage.
- Mechanism-level auditing (bank coverage, idea-acceptance vs. random memory, lineage reproductive statistics) goes well beyond the usual "the number went up" reporting, and the authors publish the *unflattering* coverage numbers (KernelBench 5.4%, Kissing Number 3.3%) rather than hiding them.
- The ablation is well chosen even if narrow: including both "random memory" and "generic advice" conditions is exactly the right way to separate content from prompt-length effects, and few papers bother.
- Full experimental parameters (Appendix F) are exhaustive down to DBSCAN eps, per-tool top-k, timeouts, driver version, and dataset sample counts — genuinely reproducible if the code is released.
- Honest reporting of a null (Kissing Number 12D, 0.00% gain with min = max = 0) and of high variance.
- Table 2's qualitative transfer examples are concrete and checkable (e.g., a KernelBench card advising "use vendor primitives, reserve Triton for profitable fusion" leading to F.conv3d + fused bias/ReLU), which makes the transfer claim legible rather than hand-wavy.

## Limitations

- Small memory bank (roughly 13 promoted ideas per source run), fixed memory influence, and a simple single-file code-evolution setting; repository-scale evolution is left to future work.
- No component-level decomposition — the authors explicitly frame the work as an end-to-end evaluation because each ablation condition requires fresh evaluator-in-the-loop runs.
- High run-to-run variance inherent to temperature-0.7 evolutionary search, acknowledged but not quantified in the main results table.
- Sensitivity to the memory pipeline's own quality (extraction, clustering, summarization, retrieval and their hyperparameters) is acknowledged as an unmeasured risk.
- Only one mutation LLM, one embedding model, one hardware configuration, and 30 generations per run; scaling behavior of memory (does a 10× larger bank help or drown retrieval?) is untested.
- The 200-sample HotpotQA/HoVer evaluation sets are small enough that a 0.5389 → 0.6015 exact-match shift is roughly 12 questions.

## Relevance

如果你关注 LLM agent 的长期记忆、AlphaEvolve 系进化式代码/算法搜索，或 GPU kernel 与科学计算的自动优化，这篇给出了一个"记忆不改变进化算子、只做有界建议注入"的干净接口设计，以及少见的机制级审计（覆盖率、idea 接受率 vs 随机基线、谱系繁殖统计）。其消融中"通用建议就能闭合 53.7% 差距"这一点，对任何用 RAG 增强 agent prompt 的工作都是一个值得警惕的对照信号。

## Questions for Further Exploration

1. How many matched baseline/memory run pairs back each row of Table 1, and do the gains survive a paired significance test given the ±0.0683 baseline SD observed in the ablation?
2. Was the memory bank for Circle Packing (32) purged of Circle Packing (26) memories, or only of (32)'s own? The distinction determines whether the strongest result is cross-task transfer or same-family warm-starting.
3. Why does a 4.05% idea-acceptance rate produce a 97.4% gap closure? Is the effect carried by a handful of high-leverage accepted ideas, or is most of the benefit actually the prompt-perturbation effect visible in the generic-advice condition?
4. Was the "generic advice" ablation matched to retrieved advice in token length and specificity? If not, the 53.7% vs 97.4% comparison conflates content quality with prompt formatting.
5. Does the effect survive a swap of the mutation backbone (e.g., a stronger reasoning model, or a small RL-trained model as in ThetaEvolve/FM-agent)? Memory may be substituting for backbone weakness rather than adding knowledge.
6. What happens as the bank grows by 10–100×? The LLM task-scope filter is the only thing keeping retrieval tractable, and its cost and precision at scale are unreported.
7. Can the same memory be run *within* a single long evolution rather than only across runs, and does the sharp variance reduction (SD 0.0683 → 0.0044) indicate a loss of exploration diversity that would hurt on open-ended problems with no known optimum?
8. Does negative transfer ever appear? The 0.05× KernelBench speedup and 0.31× Circle Packing (26) / Heilbronn minima suggest it does — what characterizes the runs where memory actively hurts?
