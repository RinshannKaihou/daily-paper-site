> **一句话总结：** 论文把"错误记忆已经污染了执行"这一场景形式化为 post-failure memory recovery，提出依赖引导的回滚修复——从运行时 provenance 构建"记忆-动作"类型化依赖图、前向追踪受污染节点、用独立可信证据保留仍然成立的节点、规则化规划删除/隔离/失效、只重放与答案相关的计算——在自建 150 例受控基准上恢复率 85.3%（最强基线 LLM-judge repair 77.3%），在改编自 LongMemEval-V2 的 50 例迁移集上 68.0%（次优 AgentTrace-style 54.0%），且 token 消耗不到 LLM-judge 的一半。

> **TL;DR:** Dependency-guided rollback repair treats a diagnosed faulty agent memory as a provenance root, traces its downstream claims/plans/tool-actions/derived memories in a typed memory-to-action graph, keeps nodes with independent trusted support, and replays only the answer-relevant subgraph. On the authors' 150-case controlled tool-use benchmark it recovers 85.3% of cases vs. 77.3% for the strongest baseline (LLM-judge repair, a Reflexion/Self-Refine adaptation) with 12.7k vs. 28.2k total tokens, and on a 50-case LongMemEval-V2-derived stress test it reaches 68.0% recovery vs. 54.0% for AgentTrace-style plus the best claim-invalidation F1 (0.669 vs. 0.603). The headline weakness the paper itself concedes: on the controlled benchmark its claim-invalidation F1 is only 0.566, far below LLM-judge's 0.946.

## 核心贡献

- **提出并形式化 post-failure memory recovery 任务**：输入是用户会话 U、活跃记忆库 M、失败执行轨迹 T 和上游检测器给出的已诊断错误记忆集合 F；输出是修正后的答案、修复后的轨迹和修复后的活跃记忆库。核心主张是 "fault removal is not state recovery"（删掉错误源头 ≠ 恢复状态）。诊断本身被明确排除在工作范围之外。
- **依赖引导回滚修复方法（五阶段）**：① 构建类型化异构依赖图（节点分 user input / execution step / memory record；边含 initiate、cite、support、produce、delete、update、consolidate、supersede、derive，纯时序 chain 边被排除出传播集合）；② 从每个错误记忆的 provenance seed 前向可达求原始受影响候选集 A₀；③ 独立支持检查，凡有 F ∪ A₀ 之外的可信前驱（当前轮显式指令、未被诊断的活跃记忆、成功的工具观测、未受影响的已验证断言）即保留；④ 规则化回滚规划：M_del = F、M_quar = (A ∩ V_mem) \ F，未被支持的轨迹节点标记 invalid；⑤ 选择性重放：只重放"修复后仍可能影响最终答案"的节点闭包 A_ans，其余保持 invalid 但不重算。
- **构造两套评测**：150 例受控基准（shopping 48 / travel 49 / customer support 53；四种故障类型 poisoned 42、stale 34、wrong-user 34、summary-drift 40；128 例单故障、22 例 2–3 故障），以及从 LongMemEval-V2 改编的 50 例多故障迁移压力测试（45 例含 2–4 个故障）。
- **七指标评估协议**：recovery、recurrence（在已恢复案例上重跑最后一轮是否复发）、faulty removal、benign preservation、claim-invalidation F1、replay ratio、LLM call count / token 数——刻意把"修得好"和"修得贵"分开衡量。
- **诚实的负面结论**：作者明确写出 "the results do not imply uniformly better trace reconstruction"，并指出受控集上 recurrence 不是最低、claim-inv F1 明显落后于 LLM-judge。

## Key Contributions

- Formalizes **post-failure memory recovery** as a distinct problem from memory auditing/deletion (MemAudit, PoisonedRAG-style defenses) and from response-level self-correction (Reflexion, Self-Refine): once a faulty record has already been consumed, one must decide which consequences to invalidate, which remain independently justified, and which must be regenerated.
- Proposes a five-stage pipeline whose graph construction is **fault-agnostic** — edges are instantiated deterministically from runtime provenance fields (`used_ids`, `generated_memory_ids`, `derived_from`, `supersedes`) rather than inferred by an LLM, and never from `F` or benchmark annotations.
- Introduces **independent-support checking** as the antidote to over-invalidation from naive reachability, with a deliberately conservative trust policy: preserved candidates are not recursively reused to validate others, preventing mutually dependent affected nodes from bootstrapping each other's validity.
- Defines **answer-relevant replay**: A_ans = {v ∈ A ∩ V_step : v ⇝ v_final in G⁻}, where G⁻ severs deleted and quarantined memories. Nodes outside A_ans stay invalidated but are never recomputed — this is the explicit cost lever.
- Releases a controlled benchmark with paired clean/faulty traces plus node-level affected-state annotations (evaluation-only, withheld from all repair methods), and a transfer set adapted from LongMemEval-V2.

## Methodology

The runtime is assumed to be instrumented: every execution step records `step_type` (memory read, claim, plan, tool action, tool observation, final answer, memory write/delete/update/consolidate), `used_ids`, `generated_memory_ids`, `invalidated_memory_ids`, tool metadata, and timestamps; every memory record carries `source`, `derived_from`, `supersedes`, and lifecycle timestamps. From these fields a directed heterogeneous graph G = (V, E) is built over V_U ∪ V_T ∪ V_M. The propagation edge set E_prop deliberately excludes pure temporal chain edges — "occurring later is not evidence of contamination" — so an unrelated valid suffix is not swept up.

Given F, each faulty memory m is mapped to a reachability seed r(m): if a failed mutation (delete/update/consolidate) produced it, that mutation step is the seed; else the producing step via a `produce` edge; else, when m predates the recorded execution, the memory node itself. Only dependents timestamped no earlier than r(m) are considered. A₀ is the union of forward-reachable sets, intentionally recall-favoring and over-approximate.

Support checking then prunes A₀. For each semantically checkable candidate v, sufficient evidentiary predecessors are collected through `support`, `derive`, `supersede`, and provenance-marked-sufficient `cite` relations; TrustedSupport(v) holds iff some admissible p ∈ Pred_sup(v) lies outside F ∪ A₀. Diagnosed faults are never preservable. Actions inherit their plans' verdicts and observations inherit their generating actions'.

The deterministic (non-optimization-based) planner sets M_del = F, M_quar = (A ∩ V_mem) \ F, V_inv = A ∩ V_step, then computes V_replay = ExecClosure(A_ans ∪ {v_final}) and V_preserve = V_step \ (V_inv ∪ V_replay). The executor replays V_replay in original trace order under M⁻ = M \ (M_del ∪ M_quar), supplies V_preserve as fixed context, withholds invalidated claims until replacements exist, never regenerates observations directly (it re-issues the generating tool action), and always regenerates v_final. The paper is candid that rollback repairs agent-maintained state only — irreversible external side effects require a resettable, idempotent, or compensating tool interface.

All methods use GPT-4o at temperature 0, seed 42, single run, sharing the same tools, faulty store, failed trace, and diagnosed fault IDs; plan-based methods use the same shared rollback executor. Six baselines: No repair, Full memory reset, Delete retrieved memories, MemAudit-style, LLM-judge repair (Reflexion/Self-Refine-inspired), AgentTrace-style (causal-graph localization).

## Results & Highlights

- **Controlled benchmark recovery (150 cases, GPT-4o):** Ours 0.853 vs. LLM-judge repair 0.773 (+8.0 pts) and AgentTrace-style 0.607 (+24.6 pts); memory-centric baselines are far weaker — Full memory reset 0.407, Delete retrieved memories 0.340, MemAudit-style 0.320, No repair 0.000.
- **Cost (Table 18, controlled benchmark):** Ours uses 12,697.55 total tokens / 5.70 LLM calls / 0.123 replay ratio vs. LLM-judge repair's 28,175.28 tokens / 9.80 calls / 0.217 replay ratio — i.e. higher recovery at 45% of the tokens, a 41.8% cut in LLM calls and a 43.3% cut in replay ratio. AgentTrace-style is cheaper still (10,508.94 tokens, 4.69 calls, 0.091 replay) but loses 24.6 recovery points.
- **State repair:** Ours removes 100.0% of diagnosed faulty memories and preserves 100.0% of benign memories; Delete retrieved memories preserves only 0.789 (Ours is ~1.27× as much benign state), Full memory reset preserves 0.000, and AgentTrace-style has 0.000 faulty removal by construction.
- **Where Ours loses on the controlled set:** claim-invalidation F1 is 0.566 vs. 0.946 for LLM-judge repair and 0.853 for AgentTrace-style; recurrence is 0.266 vs. 0.121 for LLM-judge (and 0.071 for the paper's own w/o-selective-replay ablation).
- **Transfer to adapted LongMemEval-V2 (50 cases):** Ours 0.680 recovery vs. AgentTrace-style 0.540 (+14.0 pts) and LLM-judge repair 0.260; here Ours also wins claim-inv F1, 0.669 vs. 0.603 (AgentTrace) and 0.369 (LLM-judge), with 1.000 faulty removal and 0.993 benign preservation, at 0.179 replay ratio / 8.22 LLM calls (73.4% of LLM-judge's replay ratio, 77.3% of its calls).
- **Ablations (controlled):** removing the rollback planner drops recovery 0.853 → 0.713 and raises recurrence 0.266 → 0.430 and LLM calls 5.70 → 9.19; removing selective replay barely changes recovery (0.853 → 0.840) but explodes replay ratio 0.123 → 0.755 and LLM calls 5.70 → 24.01 (55,018 tokens) while *improving* recurrence to 0.071; removing support checking *raises* recovery to 0.880 while dropping benign preservation 1.000 → 0.986 and raising replay ratio by 25.2%.
- **Slices:** per-domain recovery ranges 0.729 (shopping, recurrence 0.400) to 0.943 (customer support). Per-fault-type: summary-drift 0.950 (claim-inv F1 0.870), stale 0.941 but recurrence 0.781, poisoned 0.810 with recurrence 0.000 and lowest claim-inv F1 0.341, wrong-user hardest at 0.706 with the highest LLM count 7.12.
- **Backbone sensitivity:** under Gemini-3.6-Flash, LLM-judge repair actually edges out Ours on recovery, 0.740 vs. 0.733 (the paper notes this is one extra case), though Ours has lower recurrence (0.091 vs. 0.108) and perfect benign preservation; under Qwen3.6-27B Ours leads 0.660 vs. 0.613.

## Critical Assessment

**Novelty (moderate).** The individual ingredients — forward dynamic slicing, provenance graphs, transactional undo — are decades old and the paper says so. The genuinely new pieces are (a) the problem formulation that couples persistent-store repair with execution-trace repair, and (b) the independent-support filter that makes reachability usable without over-invalidating. Against MemoRepair, which already does cascade withdrawal and predecessor-closure republication in agentic memory, the delta is the heterogeneous trace (plans, tool actions, observations, answer) and the answer-relevance criterion. That is a real but incremental extension, and notably MemoRepair is *not* run as a baseline — the closest prior system is discussed and then omitted from Tables 2 and 4, which is the single biggest evaluation gap.

**Rigor (mixed, but self-aware).** Positives: every method receives identical inputs and shares the same rollback executor; graph construction is fault-agnostic and never touches benchmark annotations; the paper flags that recurrence is computed only over recovered cases so low-recovery methods look deceptively good. Negatives: **single run at temperature 0, no seeds/variance/confidence intervals** on a 150-case set where 8.0 points ≈ 12 cases; the AgentTrace-style baseline is described in Appendix H as having "persistent memory cleanup disabled," which mechanically forces its 0.000 faulty-removal score — it is a localization method conscripted into a repair role, not a fair repair baseline; and MemAudit-style is granted an "oracle-assisted diagnostic fallback only when its audit candidate set is empty," an unusual hybrid whose 0.320 recovery is hard to interpret. The most damaging internal result is the ablation: **removing support checking *increases* recovery from 0.853 to 0.880**, so the component the method leans on rhetorically is a net negative on the headline metric, justified only by a 1.4-point benign-preservation gain and lower replay. The claim-inv F1 asymmetry is also striking — 0.566 (controlled) vs. 0.669 (transfer) — and the abstract foregrounds the transfer number while relegating the controlled deficit to a clause; the paper explains the transfer win as an artifact ("these trajectories are dominated by poisoned memories on the answer path, so the claim steps requiring repair largely overlap with the answer-relevant region"), which is an honest admission that the F1 win is benchmark-shaped rather than methodological. Stale faults show 0.781 recurrence, meaning nearly 4 in 5 "recovered" stale cases fail again on re-run — a large hole for a method whose selling point is durable state repair. The 3-fault bucket reports 1.000 recovery on n = 5, statistically meaningless.

**Reproducibility (weak-to-moderate).** Schemas (Appendix A), replay prompt contracts (Appendix B), rule tables (Appendix C), fault injection (Appendix D), metric definitions (Appendix E), and baseline implementations (Appendix H) are all documented in enough detail to reimplement. But no code/data link is visible, GPT-4o is a proprietary and drifting backbone, the controlled benchmark is entirely self-constructed by the authors, and the LongMemEval-V2 subset is filtered to "cases for which our pipeline can construct reliable clean data" — a selection the authors correctly warn "should not be used to claim general LongMemEval-V2 performance."

**Significance (real but scoped).** The premise is right and under-served: production agent memory systems do not currently have a story for what happens after a poisoned record has already been consumed. The engineering prerequisite — full runtime provenance emitted by an instrumented agent — is heavy and the paper admits that inferring lifecycle edges from raw NL logs is out of scope, which limits drop-in applicability to existing stacks. The entire evaluation also presupposes a perfect upstream detector supplying F, so end-to-end deployment numbers would be strictly lower.

**Red flags.** (1) MemoRepair discussed as closest work but never benchmarked. (2) Abstract cherry-picks the transfer-set F1 win while the controlled-set F1 is 0.38 below the baseline. (3) A hobbled AgentTrace-style baseline (memory cleanup disabled) inflates the faulty-removal contrast. (4) No variance reporting anywhere. (5) The support-check ablation contradicts the component's motivation on the headline metric.

## Strengths

- Correct and clearly stated problem framing: "fault removal is not state recovery" cleanly separates this from the crowded memory-detection and self-refinement literatures.
- Deterministic, rule-guided planner rather than an LLM deciding what to roll back — cheaper, auditable, and the reason token cost lands below the LLM-judge baseline instead of above it.
- The chain-edge exclusion and the non-recursive preservation rule are small design decisions with clear failure-mode reasoning behind them.
- Cost is treated as a first-class metric (replay ratio, LLM calls, total tokens), and the selective-replay ablation makes the recurrence-vs-cost trade-off explicit (0.071 recurrence at 24.01 calls vs. 0.266 at 5.70) instead of hiding it.
- Unusually candid discussion throughout: recurrence caveat, upper-bound framing of the controlled results, the poisoned-fault explanation for the transfer F1 win, and an explicit limitations note on the LongMemEval-V2 subset.
- Backbone sensitivity across three models, including a case where the baseline wins — reported rather than buried.

## Limitations

- Requires a fully instrumented agent runtime emitting typed provenance; incomplete provenance under-traces contamination and spurious edges over-invalidate. No robustness study on noisy or partial provenance.
- Diagnosis is assumed given. Real deployments must pair this with a detector whose false positives (benign memories deleted) and false negatives (contamination never traced) would compound; none of that error is modeled.
- Cannot undo irreversible external side effects; re-execution needs resettable/idempotent/compensating tool interfaces, which the controlled benchmark presumably provides but real APIs often do not.
- Recurrence is not best-in-class on the controlled set (0.266), and the stale-fault slice at 0.781 recurrence suggests answer repair and durable state suppression can diverge sharply.
- Claim-invalidation F1 of 0.566 on the controlled set indicates the method invalidates a materially different claim set than the gold annotation — it recovers answers without reconstructing traces faithfully, which the paper concedes.
- Both benchmarks are small (150 / 50) and partly author-constructed; the multi-fault buckets (n = 17, n = 5) are too small to support the robustness claims made from them.
- Single-run results with no variance; GPT-4o-era backbone; no MemoRepair comparison; no code release visible.

## Relevance

如果你关注 LLM agent 的长期记忆可靠性、记忆投毒/漂移防御，或者 agent 运行时的可观测性与 provenance 设计，这篇给出了一个少见的"事后状态恢复"视角：不是检测和删除，而是把数据库回滚 / 程序切片的思路搬进记忆-执行混合图，并把重放成本当作一等公民来优化。对做 agent memory 系统或 agent 可靠性评测的人，它的七指标协议（尤其把 recurrence 与 recovery 分开、把 replay ratio 与 token 一起报）比方法本身更值得借鉴。

## Questions for Further Exploration

- How does the pipeline degrade when F is produced by a real detector rather than an oracle? A joint detector-plus-repair curve (precision/recall of F vs. end-to-end recovery) is the missing headline experiment.
- Why does removing support checking improve recovery? Is the checker preserving nodes that are formally supported but semantically stale, and would a soft/graded trust score (the `trust_score` field the paper records but explicitly does not use) fix it?
- Why is stale-fault recurrence 0.781 while poisoned-fault recurrence is 0.000? Does quarantining rather than deleting stale records leave a retrievable shadow, or does replay re-derive staleness from unrefreshed tool state?
- How would a direct comparison against MemoRepair (Zhao et al. 2026a) under both papers' metrics resolve the overlap in cascade-repair claims?
- Can the answer-relevance criterion be extended to multi-turn horizons — i.e. replay what is relevant to *future* likely queries, not just the current v_final — and would that close the recurrence gap without paying the 0.755 replay ratio of the no-selective-replay variant?
- Does the approach survive concurrent or interleaved sessions where two users' memory lifecycles touch the same records, given that wrong-user faults are already the hardest slice (0.706)?
- What is the storage and latency overhead of emitting the full provenance schema in a production agent, and does a lossy/sampled provenance log preserve enough structure for tracing?
