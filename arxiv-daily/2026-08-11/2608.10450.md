> **一句话总结：** EvoX Genesis 把"持久性"从 agent 转移到软件项目本身——用 (accepted version, repo path) 二元组定义"局部软件世界"，让有限寿命的 agent 递归委派、由父节点验证后才推进版本历史；用 DeepSeek V4 Flash 在 123.4 小时、1,019 个 agent episode、仅 44.38 美元 token 成本下从零构建出 248,989 行 Rust C 编译器（c-testsuite 220/220、LLVM 32/36、Csmith 93/93 执行通过），并把 13 个 MESA Fortran 模块重写为约 8.99 万行 Rust，6 个数值负载相对原 Fortran 实现取得 1.55–6.87× 加速且校验和误差 ≤3.1e-9。

> **TL;DR:** Genesis makes the *project* persistent instead of the agent: a "local world" is a pair (accepted version, repository path), finite-lived agents propose changes, recursive delegation moves work across paths, and only parent-validated changes advance the version history. In three single-run case studies it built a 248,989-line Rust C compiler from an empty repo with DeepSeek V4 Flash (220/220 c-testsuite, 32/36 LLVM cases, 93/93 Csmith programs executed, 2,904 Rust tests, US$44.38, 123.4 h), continued a GLM 5.2-built compiler across a foundation-model swap (DeepSeek continuation: 1,820/1,820 retained LLVM cases vs GLM's 1,445/1,448), and rewrote 13 MESA modules from Fortran to Rust with 1.55×–6.87× median speedups over the **Fortran reference baseline** (EOS lookup and Newton solve bit-exact; worst checksum drift 3.1e-9). Note: there is no agent-system baseline anywhere in the paper.

## 核心贡献

- **提出"持久递归世界"形式化模型**：局部世界 w = (v, p)，其中 v 是被接受的软件版本（固定完整项目状态与可继承历史），p 是仓库相对路径（决定 agent 的起点、责任范围与修改权限）。路径不是仓库的部分副本，也不是额外的软件状态。
- **区分三类事件**：局部 agency（Δᵢ = Aᵢ((v,p), gᵢ)）、递归委派（(v,p) ⇝ (v,q)，不推进版本）、被接受的软件事件（(v,p) → (v′,p′)，才推进持久历史）。这把"agent 的生命周期"与"软件开发过程的生命周期"两个常被混为一谈的时间尺度显式解耦。
- **工程实现 EvoX Genesis**：目录作用域节点从版本控制的 CONTEXT.md 组装上下文，接受的更改通过 Git commit 与受保护的 archive reference 落盘，候选更改隔离在 agent 专属分支/worktree 上；调度器状态、BEAM 监督进程与临时 worktree 只是执行基础设施，不承载项目身份。
- **三阶段评估设计**：Formation（从无实现的仓库长出复杂系统）、Continuation（agent 全部换掉、甚至基座模型换掉后能否续开发）、Redevelopment（把已有科学软件换实现语言但保住被审计的数值行为）。
- **实证结果**：C 编译器从零构建、跨基座模型续开发、MESA Fortran→Rust 迁移三个案例，全部在"项目持久、agent 短命"这一组织方式下完成。

## Key Contributions

- A minimal **version–path formalism** for long-horizon software development, separating transient agency, recursive delegation, and accepted software events. Only the third advances persistent history; rejected code leaves the version untouched, though failure information explicitly written into CONTEXT.md / tests / constraints / provenance *can* survive into a later accepted version.
- **EvoX Genesis**, a released implementation where finite-lived manager and executor agents operate in path-scoped contexts; leaf executors edit code, managers decompose and review, and acceptance is parent-mediated using tests, constraints, and integration evidence.
- **Greenfield formation at scale**: a clean-room C compiler (`jcc`) in Rust with a Clang-compatible CLI, object-file/linker integration, LLVM IR export, C11 target, x86 and x86-64 back ends — with direct use or translation of Clang/LLVM source prohibited.
- **Continuity across foundation-model replacement**: two continuation branches from the same completed GLM 5.2 compiler (commit `37216cfa254a`), one continuing with GLM 5.2 and one switching to DeepSeek V4 Flash, both under identical controller limits (max depth 8, retry 15, 2,048 root turns, 128 delegated turns, 150k-token compression threshold) on the same machine.
- **Scientific-software redevelopment**: 13 MESA module directories (139,414 physical Fortran lines in scope) reimplemented as a Rust workspace, with a six-workload numerical audit rather than a "it compiles" claim.
- **Unusually candid measurement caveats**: the paper explicitly defines "archived episode," "retention" (commit lies in ancestry of the final repo, *not* independent correctness), wall time vs. summed agent-hours, and states that dollar figures are token charges only, excluding hardware, storage, controller overhead, networking, and labour.

## Methodology

Genesis situates every agent by two coordinates: an **accepted version** `v` that fixes the complete inheritable project state, and a **repository-relative path** `p` that fixes where local responsibility begins. An agent may inspect the whole project at `v` but starts at `p` and inherits the context, constraints, validation results, reusable skills, and provenance records associated with that location.

A finite-lived agent `Aᵢ` receives an episode objective `gᵢ` and emits a candidate change `Δᵢ`. It may take many model–tool turns within one supervised episode, but its private conversation and scratch state are deliberately *not* carried forward as the identity of any later agent. Instead, a parent agent may spawn a child at a different path in the same version — `(v,p) ⇝ (v,q)` — recursively, so recursion localizes work *without* advancing history. Only when the responsible parent accepts a returned contribution does a software event `(v,p) → (v′,p′)` occur (usually `p′ = p`; renames/moves/deletions can remap the path). Concretely: context lives in version-controlled `CONTEXT.md` files per directory node, accepted state lives in Git commits plus protected archive refs, and candidates live on isolated agent branches/worktrees.

The evaluation is three case studies, each with a different starting condition and validation target:

1. **Formation** — DeepSeek V4 Flash, xhigh reasoning effort, 150k-token compression threshold. Root session started from commit `41e087ce90f3` containing only `.gitignore` and `genesis.toml`; a second root phase inherited the generated repo plus a handoff summary. External evaluation sources: c-testsuite, LLVM test programs, LZ4, SQLite, plus Csmith programs generated and executed by a committed harness.
2. **Continuation** — both branches fork from the same completed GLM 5.2 `jcc` world with identical objectives, evaluation families, and controller limits on one dedicated machine.
3. **Redevelopment** — a lightly modified MESA fork at commit `461dcba94f33` used read-only as reference; DeepSeek V4 Flash reimplements 13 mapped module directories as Rust crates. Higher-level engines (`star`, `astero`, `binary`) are explicitly out of scope. Numerical validation uses six standalone workloads; each reported runtime is the median of 25 post-warm-up measurements per implementation, with build flags, CPU pinning, and a separate 40-run burn check deferred to the Supplementary Information.

## Results & Highlights

**Formation (C compiler from an empty repository, DeepSeek V4 Flash):** 123.4 hours wall time, 1,019 archived agent episodes, delegation depth 5, final repository of **248,989 physical lines across 750 tracked text files**, at a provider-recorded **US$44.38** in model-token charges (4.13B input tokens, 97.4% cache hit rate). Episode retention was **929/1,015 retained** in the final accepted ancestry. External validation: **220/220 c-testsuite cases (100%)**, **32/36 evaluated LLVM cases (88.9%)**, **93/93 Csmith programs executed (100%)**, **8/8 LZ4 checks**, SQLite compiled with SQL sanity queries passing, **2,904 Rust workspace unit tests**, and **106/106 internal corpus cases**. Agent-time allocation shifted between phases: initialization (140.0 h) was 41% front end / 26% IR & optimization / 20% back end / 13% integration+cross-cutting, while optimization (401.3 h) shifted to 35% / 20% / 34%.

**Continuation (same compiler world, model swap):** starting from the same 105.4k-line GLM 5.2 compiler, the **GLM 5.2 branch** reached 117.0k lines (net +10.0k: −6.4k deleted, +16.5k added), used 98 agents, observed depth 4, passed **1,445/1,448 of its retained LLVM SingleSource set**, and grew Rust unit tests from 1,136 to **1,226 (+90)** at 543.6M input tokens / **US$168.35 estimated**. The **DeepSeek V4 Flash branch** reached 133.2k lines (net +23.2k: −2.8k, +25.9k), used 178 agents, observed depth 8, passed **1,820/1,820 of its retained LLVM set**, grew tests to **1,350 (+214)**, at 902.8M input tokens / **US$7.49**. c-testsuite stayed at **220/220 across all three snapshots**. The paper explicitly refuses to treat this as a model ranking because the retained LLVM sets differ and the budgets were unmatched.

**Redevelopment (MESA Fortran → Rust):** 33.22 hours, 272 agents, **89,946 physical Rust lines** (including tests and benches) covering 13 modules mapped from 139,414 physical Fortran lines; **1,052 tests passed, 0 failures, 18 ignored**, at **US$10.64** in token charges (96.0% overall mean cache hit rate). Across all six audited workloads Rust had the lower median runtime: **Newton solve 6.87× (bit-exact)**, **ROS2 integration 5.30× (5.1e-15 relative checksum difference)**, **opacity lookup 1.98× (1.3e-13)**, **EOS lookup 1.60× (bit-exact)**, **2D interpolation 1.58× (4.9e-12)**, **end-to-end burn 1.55× (3.1e-9)** — all checksum deltas < 1e-8 against the **Fortran reference baseline**. The dependency graph changed substantially: of the mapped module dependencies, 40 were retained in both graphs, 102 were MESA-only (absent as direct Rust crate dependencies), and 1 was newly Rust-only.

## Authors & Credibility

All four authors are at the Department of Data Science and Artificial Intelligence, The Hong Kong Polytechnic University; Ran Cheng is the corresponding author and a well-established researcher in evolutionary computation (the EvoX ecosystem). The work is a direct successor to the group's **EvoGit** (arXiv 2506.02049), which used a Git graph for decentralized multi-agent code evolution — Genesis replaces that decentralized recombination with hierarchical, parent-mediated acceptance. A project website (genesis.evox.group) and an evidence/archive package are advertised, which is above the norm for agentic-SE papers. Related-work coverage is current and appropriately positioned against SWE-bench/SWE-agent/OpenHands, memory systems (Reflexion, Voyager, SWE-MeM), AGENTS.md-style repository context, and evaluator-guided program evolution (FunSearch, AlphaEvolve, ERA).

## Critical Assessment

**Novelty (moderate-to-high on framing, low on components).** The authors concede the point themselves: memory, short-lived workers, and hierarchical task decomposition are individually not new. What is new is the insistence that the *accepted project state* — not an agent process — is the persistent object, plus the clean version–path algebra that makes "delegation does not advance history" a formal invariant. That framing is genuinely clarifying, but it is closer to a well-argued architectural stance than a new algorithm.

**Rigor (this is the weak spot).** There is **no agent-system baseline anywhere in the paper**. Genesis is never compared to OpenHands, SWE-agent, a flat (non-recursive) manager-worker organization, a long-context single agent, or the authors' own EvoGit. The only quantitative baseline in the entire work is the *Fortran MESA reference* in the speedup table — which is a compiler/runtime comparison, not an agent-architecture comparison. Every headline claim therefore rests on capability demonstration, not on controlled attribution. Sample size is **n = 1 per regime** (one DeepSeek formation run, one GLM continuation, one DeepSeek continuation, one MESA run), so nothing can be said about run-to-run variance or failure rate. The ablations that would matter — hold code fixed and vary accepted non-code records; fresh vs. persistent agents with project state fixed; flat vs. recursive organization; acceptance-gate removal — are all **listed in §5.2 as future work**, which is honest but leaves the central causal claim ("persistent recursive worlds *enable* this") unestablished.

**Specific data quirks worth flagging.** (1) The Csmith result is reported as "**93/93 executed**", not "93/93 passed" — for a differential-testing tool whose entire purpose is miscompilation detection, "executed" is a materially weaker word, and it is the phrasing used in both the figure and the body text. (2) The LLVM denominators are wildly inconsistent across experiments: **36** evaluated cases in formation vs. **1,448 / 1,820** retained SingleSource manifests in continuation. The authors flag that snapshots differ, but a reader skimming the figures could easily conflate 32/36 with 1,820/1,820. (3) Figure 4a plots MESA repository lines topping out at ~1.391M while the text reports 89,946 Rust lines; the caption explains this is "the size of the generated repository," but the two numbers differ by more than 15×, which is confusing at best. (4) The cost figures are not comparable: US$762.59 for GLM initial development vs. US$44.38 for the entire DeepSeek formation run reflects vendor pricing and unmatched budgets, and the paper correctly declines to normalize them — but the abstract still leads with "only US$44," which is the number that will be quoted.

**Reproducibility (mixed).** Commit hashes, controller limits, model settings, and measurement protocols are given, and an archive is promised. But the authors state outright that the archives "record objectives, accepted repository histories, agent records and resource summaries, but **not a complete audit log of every human action**," and that they "do not treat missing intervention records as proof of zero human involvement." That is admirable candour, and it also means the degree of human steering in a 123-hour run is not verifiable from the artifacts.

**Significance.** If the demonstrations hold up, this is a meaningful existence proof that a >100-hour, 250k-line, cross-model software project can be carried by repository state rather than agent state — a useful counterweight to the "bigger context window / better memory" default. The MESA result is the more scientifically interesting one, because preserving bit-exact or ≤1e-8 numerical behaviour through a full language change is a much sharper success criterion than "tests pass."

**Red flags.** Zero agent baselines; n=1 everywhere; all mechanism ablations deferred; "executed" doing load-bearing work in the Csmith claim; a title verb ("Enable") that the evidence does not license, since nothing shows the *persistent recursive* organization is necessary rather than merely sufficient.

## Strengths

- The version–path formalism is genuinely minimal and does real work: it makes the distinction between "delegating" and "committing" precise, which most multi-agent coding papers leave implicit.
- Scale and duration are real: 123.4 h, 1,019 episodes, delegation depth 5, ~249k lines — most agentic-SE evaluations top out at issue-level patches.
- The MESA study picks a validation target that cannot be gamed by test generation: bit-exact / ≤1e-8 agreement with an existing scientific reference across six workloads, with medians over 25 post-warm-up runs and CPU pinning.
- Exceptional metric hygiene in the prose: retention is defined as ancestry membership rather than correctness; line counts are described as repository size rather than complexity; dollar figures are scoped to token charges; separate benchmarks are reported separately rather than fused into one score.
- §5.2 states the limits of the causal claim more plainly than most reviewers would demand, and names the exact ablations needed.

## Limitations

- **No comparison system at all.** Without a flat-organization or persistent-agent control, the contribution of recursion, of CONTEXT.md persistence, and of parent-mediated acceptance is entirely unresolved.
- **Single runs.** No success-rate estimate, no variance, no reporting of failed runs (if any were attempted).
- Compiler correctness evidence is broad but shallow in places: 36 LLVM cases in the formation run, 93 Csmith programs "executed", and SQLite validated only by "compiled + SQL sanity queries passed" — far from a conformance claim for a C11 compiler.
- MESA scope excludes the hard parts (`star`, `astero`, `binary` engines); the migrated 13 modules are the numerical/physics foundation layer, and 102 of the original dependency edges vanished in the Rust version, so the port is a re-architecture rather than a faithful translation.
- Speedups are host-, build-flag-, and harness-specific, and Fortran-vs-Rust performance is confounded by compiler and build configuration rather than being an agent-quality metric.
- Human involvement is not fully audited; the initial specification, tools, validation sources, and controller limits are human-supplied, and "autonomous" is explicitly bounded.
- Persistence claims cover project-specific state only; the paper does not audit erasure of provider-side state (e.g., server-side caching across episodes at 96–98% cache hit rates raises a fair question about how "fresh" successive agents really are).

## Relevance

如果你关注 long-horizon coding agents、multi-agent 编排与 agent memory 的架构选型，这篇提供了一个和"更长上下文 / 更强记忆"截然相反的设计范式：把状态外化到 Git 版本历史与目录级 CONTEXT.md，让 agent 彻底短命可换。对 LLM-as-engineer 的系统设计、以及科学计算代码（Fortran→Rust）自动迁移的评估方法论都有直接借鉴价值，但它是能力演示而非受控实验，不宜当作"递归优于扁平"的证据引用。

## Questions for Further Exploration

- What happens under a **flat** (depth-1) organization with the same model, budget, and task contract? Is depth 5–8 doing real work, or is it a byproduct of context-window pressure and the 150k compression threshold?
- Which persistent records carry the continuity? The authors' proposed experiment — freeze executable code, perturb or delete accepted `CONTEXT.md` / constraints / provenance, and re-run — would isolate whether the non-code records matter at all.
- How much of the apparent efficiency comes from 96–98% prompt-cache hit rates? If provider-side caching is what makes 1,000-episode runs affordable, the "$44" figure is a property of the vendor's infrastructure, not the architecture.
- What is the failure mode when the acceptance gate is wrong — i.e., when a parent accepts a change that passes local tests but breaks a distant module? The 929/1,015 retention figure hints at ~8.5% discarded work, but the paper does not characterize *rejected* episodes.
- Does the Csmith harness perform differential testing against a reference compiler, or only check for execution without crashing? This single question determines how much the compiler-correctness claim is worth.
- Can the same organization survive a *hostile* inheritance — e.g., continuing a repository built by a different system entirely, or by humans — rather than one Genesis produced itself?
