03 Why this matters

▸ A counter-design to the bigger-context-window default: externalize state into Git history and CONTEXT.md so agents stay finite, swappable, and model-agnostic.

No agent-system baseline anywhere in the paper — every headline number is a capability demo, not a controlled attribution.

05

How it works

Version–path formalism

Genesis situates every agent by two coordinates: an accepted version v that fixes the full inheritable project state, and a repository-relative path p that fixes where local responsibility begins. An agent may inspect the whole project at v but starts at p, inheriting the context, constraints, validation results, and provenance recorded there.

A finite-lived agent emits a candidate change, but its private scratch is deliberately not carried forward as any later agent's identity. A parent may spawn a child at another path in the same version — (v,p) ∱ (v,q) — so recursion localizes work without advancing history. Only when the responsible parent accepts a returned contribution does a software event (v,p) → (v′,p′) occur. Concretely: context lives in version-controlled CONTEXT.md files per directory node; accepted state lives in Git commits plus protected archive refs; candidates live on isolated agent branches/worktrees. The agent's lifetime and the project's lifetime are explicitly decoupled.

07

Strengths & limitations

▸ Strengths

  • Minimal formalism, real work. The version–path algebra makes "delegating" vs "committing" precise — most multi-agent papers leave it implicit.
  • Genuine scale. 123.4 h, 1,019 episodes, depth 5, ~249k lines — far past the issue-level patches that dominate agentic-SE benchmarks.
  • Ungameable target. MESA validates against bit-exact / ≤1e-8 agreement with a scientific reference over 6 workloads, medians of 25 runs with CPU pinning.
  • Exceptional metric hygiene. Retention = ancestry not correctness; dollars scoped to tokens; benchmarks kept separate, not fused into one score.
  • Honest limits. §5.2 names the exact ablations needed, more plainly than most reviewers would demand.

⚠ Limitations

  • No comparison system at all. Without a flat-organization or persistent-agent control, the contribution of recursion, CONTEXT.md, and parent-mediated acceptance is entirely unresolved.
  • Single runs (n = 1). No variance, no failure rate, no reporting of failed attempts.
  • Broad but shallow compiler evidence. 36 LLVM cases; Csmith "executed" not "passed"; SQLite by SQL sanity only — not a C11 conformance claim.
  • MESA excludes the hard parts. The 13 modules are the numerical foundation; 102 dependency edges vanished, so it is a re-architecture, not a faithful port.
  • "$44" may be a vendor property. 96–98% cache hit rates mean affordability may rest on provider infrastructure, not the architecture.
  • Human & provider state unaudited. Missing intervention records and server-side caching across episodes are both unverified.
08

Open questions

What the evidence does not settle
Q1 · STRUCTURE

What happens under a flat (depth-1) organization with the same model, budget, and task contract? Is depth 5–8 doing real work, or is it a byproduct of context-window pressure and the 150k compression threshold?

Q2 · CONTINUITY

Freeze the executable code, perturb or delete accepted CONTEXT.md / constraints / provenance, and re-run — do the non-code records carry continuity at all?

Q3 · VALIDITY

Does the Csmith harness do differential testing against a reference compiler, or only check crash-free execution? This single detail decides how much the compiler-correctness claim is worth.

Q4 · INHERITANCE

Can Genesis survive a hostile inheritance — continuing a repo built by a different system, or by humans — rather than one it produced itself?
