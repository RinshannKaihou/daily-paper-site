> **一句话总结：** GeoForge 用「工作流图记忆 + 动作级经验 + 自适应技能 SOP」三级非参数记忆，把已完成的遥感执行轨迹蒸馏成可复用的任务条件先验，在不更新任何 LLM 权重的前提下把 Earth-Bench 上 DeepSeek-V3.1 的任务准确率从 Earth-Agent 的 52.23% 提到 77.09%、ThinkGeo 答案准确率从 GeoEvolver 的 46.88% 提到 60.98%，但参数准确率（Parameter Accuracy）在多数骨干上反而低于 Earth-Agent。

> **TL;DR:** GeoForge is a training-free, self-evolving Earth-observation (EO) agent that distills completed tool trajectories into a three-level non-parametric memory (Workflow Graph, Action-Level Experiences, Adapted Skill SOP) and retrieves a task-conditioned prior at inference. On Earth-Bench it beats Earth-Agent on 4/5 backbones (DeepSeek-V3.1: 77.09% vs 52.23%, +24.9 pts; GPT-5: 74.33% vs 63.16%), on ThinkGeo it lifts Answer Accuracy from GeoEvolver's 46.88% to 60.98%, and on GeoPlan-Bench it reaches F1_key 0.77 vs EarthAgent-MAS 0.63 — while its Parameter Accuracy actually *drops* below Earth-Agent on GPT-5 (22.20 vs 25.91) and DeepSeek-V3.1 (26.88 vs 31.36).

## 核心贡献

- **提出训练无关的自演化 EO 智能体框架 GeoForge**：不动骨干 LLM 权重，把每次完成的遥感任务轨迹蒸馏进一个结构化的「非参数执行状态」，形成 执行 → 蒸馏 → 复用 的闭环。
- **三级互补记忆设计**：Workflow Graph Memory 编码全局工具调用顺序与 EO 依赖（数据发现 → 模态感知输入组织 → 地理产品生成 → 时空聚合 → 科学解释）；Action-Level Experiences 存储「触发条件 → 纠正动作」的局部修正对；Adapted Skill SOP 保存可复用的任务分解、数据约束和参数语义。
- **感知上下文驱动的工具空间收缩**：先推断任务的传感模态/时空上下文，再对 MCP 工具空间做任务感知过滤，避免智能体在庞大异构工具库中盲目搜索。
- **安全门控的记忆更新（safety gate ψ）**：只有真实调用了工具、答案完整、调用数不超上限、无重复爆炸、且不含禁止代码模式的轨迹才允许写回记忆；SOP 采用「替换式合并」而非只增不减，经验库用等价类去重做保新性合并。
- **在三个 EO 智能体基准（Earth-Bench、ThinkGeo、GeoPlan-Bench）× 五种骨干 LLM 上的系统评测**，同时报告最终答案准确率与轨迹级指标（Tool-Any-Order / In-Order / Exact-Match），并给出组件消融、Top-k 与检索阈值敏感性分析和错误类型分布。

## Key Contributions

- A **training-free self-evolving EO agent** that keeps all learned execution knowledge *outside* the backbone LLM, so improvements transfer across GPT-5, GPT-4o, Gemini-2.5-Flash, DeepSeek-V3.1 and Qwen3-Max without any fine-tuning.
- A **three-level non-parametric memory** that explicitly separates global operation order (graph), local corrective rules (experiences), and procedural/data constraints (SOP) — the paper's central argument against prior work (GeoEvolve evolves algorithms; GeoEvolver accumulates flat interaction experience) is that EO validity constraints live at *different decision levels*.
- A **hybrid retrieval score** for workflow nodes, `s_G = α·J_tool + β·J_text + λ_C·1[task-type match] − λ_L·max(0, |z_i| − L_0)`, where the last term explicitly penalizes long tool sequences to bias toward parsimonious workflows — a direct response to the redundant-call failure mode illustrated in their case study.
- A **safety-gated distillation operator** producing at most 3 lessons, 1 revised SOP and 2 workflow candidates per episode, with an incomplete-answer detector and a forbidden-pattern filter that rejects code-like or non-MCP content.
- **Evidence-grounded execution discipline**: retrieved memory is injected as a *planning prior only*; every data-grounded question must still issue tool calls (typically starting with a data inventory), and final answers must be supported by current observations rather than by memory.

## Methodology

An EO task is formalized as `x = (q, d, Y)` — a scientific request, a data collection, and an answer space — over an operation library `T`. A trajectory `τ = (q, a_1, o_1, ..., a_m, o_m, y)` is *valid* only if it respects remote-sensing dataflow: modalities/observations are identified before product generation, returned artifacts are propagated to downstream tools, and aggregation happens only after spatial/temporal compatibility checks. Because expert trajectories are unavailable at inference, GeoForge approximates these priors with external memory.

**Workflow Graph Memory** is a directed, reliability-aware graph `G = (W, A, U)`. Each node stores task type, workflow description, an *order-preserving compressed* tool sequence (repeated tool names collapsed, separating reusable structure from data-driven repetition), parameter hints, cautions, provenance, and success/failure counts. Retrieval combines tool-sequence Jaccard and lexical Jaccard with a task-type bonus and a length penalty; only nodes above score and support thresholds are serialized into the prompt, explicitly labeled as planning priors.

**Action-Level Experiences** store items `e = (trigger, correction, source ops, provenance, metadata)`. Retrieval is a gated relevance model combining lexical affinity and coarse task-type consistency, with two hard indicators: nonzero lexical overlap and `|a_i| > 0`, i.e. the experience must be grounded in actual executable operations (this filters free-form reflections). A rewrite-and-filter operator `R_Θ` re-contextualizes retrieved items against the current task, and consolidation admits only candidates whose normalized form falls outside existing equivalence classes.

**Adapted Skill SOP** holds `s_j = (task, workflow, data/argument constraints, sensor-modality semantics, failure-prevention rules)`. Injecting the whole library would be high-recall/low-precision, so GeoForge compresses it per query with an LLM adapter bounded by length `L_S`. SOP updates are *replacement-style*, not append-only.

At inference the agent builds `C_q = Trunc[G_q ‖ E_q ‖ S_q ‖ H_q]`, where `H_q` is deterministic EO guidance (inspect data assets first, group inputs by modality/acquisition time, prefer batch ops, propagate product paths, verify spatial support and temporal alignment before aggregation). Execution is standard ReAct over the *filtered* MCP tool space; a regex-first, LLM-fallback normalizer maps the free-text response to a benchmark option (the paper explicitly notes the normalizer creates no evidence). Implementation uses LangChain/LangGraph, temperature 0.1, 120 s tool timeout, recursion limit 80, top-3 experience retrieval and top-1 workflow retrieval at threshold 0.6.

## Results & Highlights

- **Earth-Bench, DeepSeek-V3.1 backbone**: GeoForge reaches **77.09% accuracy vs Earth-Agent's 52.23%** (+24.86 pts) and vs GeoEvolver's 59.68% (+17.41 pts); Tool-Any-Order rises to **83.58% vs 77.98%** for Earth-Agent.
- **Earth-Bench, GPT-5 backbone**: **74.33% vs 63.16%** (Earth-Agent), 70.85% (GeoEvolver) and 67.61% (OpenEarth-Agent); Tool-Any-Order **79.39% vs 71.16%**. Gemini-2.5-Flash: **67.91% vs 55.06%** (Earth-Agent), with Tool-Any-Order jumping **61.80% → 80.35%**. Qwen3-Max: **69.72% vs 47.37%**.
- **ThinkGeo**: Instruction Alignment **97.27% vs 86.49%** (best baseline GPT-4-1106) and 80.12% (GeoEvolver); Tool Accuracy **80.31% vs 76.58%** (GeoEvolver); Answer Accuracy **60.98% vs 46.88%** (GeoEvolver, +14.1 pts); Answer w/ ImgGen **62.43% vs 53.74%**. Counter-example: **Argument Accuracy 33.96% is *below* GeoEvolver's 35.42% and GPT-4-1106's 36.96%**.
- **GeoPlan-Bench**: Recall_key **1.00 vs 0.66** (EarthAgent-MAS), Precision_key **0.70 vs 0.68** (GeoEvolver), F1_key **0.77 vs 0.63**, Structural **0.79 vs 0.68**, Holistic **1100.65 vs 1068.27**.
- **Ablation (Table 3)**: full model 74.33% accuracy / 85.89 Tool-A-O / 70.01 Tool-I-O / 51.18 Tool-E-M. Removing **Skill SOP** costs the most accuracy (74.33% → **52.66%**, −21.7 pts); removing the **Workflow Graph** costs the most trajectory quality (Tool-A-O 85.89 → 75.69, Tool-I-O 70.01 → 61.74, Tool-E-M 51.18 → 45.09); removing **Experiences** gives 70.21%. Memory-free baseline: 52.23%.
- **Cross-modality generalization (Table 4)**: average accuracy **61.85% vs 47.84%** for Earth-Agent (+14.0 pts), Spectrum **77.00% vs 50.00%** (+27.0), Products **71.26% vs 45.98%** (+25.3) — but **RGB drops to 37.29% vs Earth-Agent's 51.43% and Manus's 47.62%**, an outright loss the text does not discuss.
- **Parameter Accuracy on Earth-Bench is a mixed-to-negative result**: GPT-5 22.20 vs 25.91 (Earth-Agent), DeepSeek-V3.1 26.88 vs 31.36, Qwen3-Max 25.67 vs 26.27; only GPT-4o (33.81 vs 27.92) and Gemini (25.46 vs 23.43) improve.
- **Qualitative case (Figure 3)**: on an NBR fire-hotspot query, the baseline emits ~25 tool calls and terminates with "Sorry, need more steps", while GeoForge executes `get_filelist → calculate_batch_nbr → calc_batch_image_hotspot_tif → analyze_hotspot_direction*11` and answers correctly (B). Error-distribution analysis (Figure 4) attributes gains mainly to reduced tool-planning errors, with residual reasoning errors eliminated for most backbones; remaining failures shift toward execution-trace and parameter errors.
- **Sensitivity**: Top-k = 3 and min-retrieve-score = 0.6 are optimal; larger k slightly degrades trajectory quality via redundant guidance, and an overly strict threshold reduces Tool-Exact-Match.

## Critical Assessment

**Novelty (moderate).** The individual ingredients — ReAct, experience banks, workflow graphs, SOP distillation, safety gates — all exist (Memento, MemSkill, SAGE, AFlow, GeoEvolver). The contribution is the *decomposition by decision level* plus EO-specific dataflow priors, which is a sensible but incremental combination. The paper is honest about positioning against GeoEvolve/GeoEvolver.

**Rigor (weak in places).** Several concrete problems: (1) **The ablation table is internally inconsistent with Table 1.** The full-model ablation row reports accuracy 74.33 (matching GPT-5) but Tool-A-O 85.89 / Tool-I-O 70.01 / Tool-E-M 51.18, whereas Table 1's GPT-5 GeoForge row reports 79.39 / 61.98 / 47.39 with the *same* 74.33 accuracy. Meanwhile the no-memory row's accuracy 52.23 is exactly Earth-Agent's DeepSeek-V3.1 number. The backbone used for Table 3 is never stated, and these mismatches are unexplained. (2) **Table 2's backbone is unspecified**, so GeoForge's 60.98% ThinkGeo answer accuracy is compared against raw GPT-4o (9.78%) and Claude-3.7-Sonnet (8.97%) — a plain-LLM-vs-full-agent comparison that inflates the apparent margin; only GeoEvolver is a fair comparator there. Claude-3.7-Sonnet's 22.31 Instruction Alignment is an implausibly weak number suggesting a harness/parsing failure rather than a model capability limit. (3) **Recall_key = 1.00 on GeoPlan-Bench is a saturated metric** — perfect key-tool recall at 0.70 precision is consistent with over-calling tools, which is precisely the pathology GeoForge claims to fix. (4) **No seeds, no variance, no confidence intervals** anywhere; single-run numbers with 15-25 pt claimed gains. (5) **Order dependence is untested**: a self-evolving system's final memory depends on the order in which benchmark tasks are seen, and the paper never reports how performance varies with task ordering, nor how many tasks are needed before memory pays off (no learning curve). (6) **Evaluation is transductive** — memory is distilled from trajectories on the same benchmark the system is then scored on. The safety gate keys on answer *completeness*, not correctness, so there is no explicit label leakage, but repeated exposure to the eval distribution is a form of test-time adaptation that baselines do not get; a held-out-task protocol is missing. (7) **No cost accounting**: no token counts, latency, or number of LLM calls for the distillation loop, despite parsimony being a stated goal.

**Reproducibility (low-to-moderate).** LangChain/LangGraph, temperature 0.1, top-3/top-1 retrieval and threshold 0.6 are given, but α, β, λ_C, λ_L, L_0, L_S, L_max, R_max, N_E are all left as symbols in the main text (deferred to an appendix not included in the body). No code, no released memory bank, no MCP tool-server specification.

**Significance (moderate-to-high if it holds).** Training-free improvements of this magnitude across five heterogeneous backbones — including a closed frontier model (GPT-5) and open weights (DeepSeek-V3.1, Qwen3-Max) — would be practically valuable for scientific-agent deployment where fine-tuning is infeasible.

**Red flags.** The RGB regression (37.29 vs 51.43) and the Parameter Accuracy regressions on three of five backbones are visible in the tables but absent from the narrative, which claims consistency. GPT-4o is the clearest counterexample: GeoForge's 57.98% accuracy *loses* to GeoEvolver's 65.59%, and its Tool-In-Order collapses to 37.31 vs Earth-Agent's 53.20 — yet the text says "best accuracy on four backbones" without discussing why the fifth fails so badly. Table 1's `–` entries for OpenEarth-Agent across all trajectory metrics mean that baseline is compared on accuracy only.

## Strengths

- The EO-specific dataflow prior (`H_q`) is concrete and domain-grounded rather than generic prompt engineering: modality grouping, product-path propagation, and spatial/temporal compatibility checks before aggregation map directly onto real remote-sensing pipeline failure modes.
- Separating *what order* (graph), *what to fix locally* (experience), *what procedure and constraints* (SOP) is a clean and testable decomposition, and the ablation actually shows the three components fail in *different* ways — SOP removal hurts accuracy, graph removal hurts trajectory metrics — which is stronger evidence than a monotone ablation would be.
- The safety gate and the `|a_i| > 0` retrieval indicator are sensible defenses against the classic self-evolving-agent failure of accumulating ungrounded self-reflections.
- Trajectory-level metrics (Tool-Any-Order / In-Order / Exact-Match) are reported alongside accuracy, so improvements can be attributed to planning rather than answer-format luck.
- The Figure 3 case study is genuinely illustrative: 25+ tangled calls ending in failure vs a 4-stage workflow producing the right answer.

## Limitations

- No held-out or cross-benchmark memory-transfer experiment: memory distilled on Earth-Bench is never tested on ThinkGeo or GeoPlan-Bench, so it is unclear whether the learned knowledge is EO-general or benchmark-specific.
- No learning curve, no memory-size scaling, no task-ordering sensitivity — the three questions that matter most for any self-evolving system.
- Compute/latency/token overhead of per-episode distillation is never quantified.
- Parameter grounding is not solved and in several settings gets worse; the authors themselves note residual failures concentrate in execution-trace and parameter errors.
- Modality coverage is uneven: strong on Spectrum and derived Products, notably worse on plain RGB imagery.
- Single-run results without variance, and key hyperparameters relegated to an appendix.
- No safety/robustness analysis of memory poisoning: a plausible-but-wrong workflow that passes the completeness-based gate can be distilled and then reused, and nothing in the paper measures how often that happens.

## Relevance

如果你关注 **LLM 智能体的非参数记忆 / self-evolving agent** 与 **科学领域工具编排（tool-use trajectory quality）**，这篇是一个值得读的具体案例：它把「记忆分层」这个抽象主张落到了可验证的消融上（去 SOP 掉准确率、去图掉轨迹质量），并且同时报告答案准确率与轨迹级指标，比只报最终 accuracy 的同类工作更有参考价值。对遥感/地学 agent 方向的读者，其 EO dataflow 约束（模态对齐、产品路径传播、时空兼容性校验）可以直接借鉴为 prompt-level 先验。

## Questions for Further Exploration

1. Why does GPT-4o regress (57.98% vs GeoEvolver's 65.59%, Tool-In-Order 37.31 vs 53.20)? Is the injected memory context exceeding a usable context budget, or is the SOP adapter producing guidance that GPT-4o over-literally follows?
2. Does the memory transfer? Train memory on Earth-Bench, evaluate zero-shot on ThinkGeo/GeoPlan-Bench, and report the delta against memory built in-domain.
3. How does performance scale with the number of episodes seen, and how sensitive is the final memory to task ordering (e.g. shuffle seeds × 5)?
4. Can the completeness-based safety gate be attacked? Inject a confidently-wrong-but-complete trajectory and measure downstream contamination rate.
5. Why does the ablation table's full-model trajectory metrics (85.89/70.01/51.18) disagree with Table 1's GPT-5 row (79.39/61.98/47.39) at identical accuracy — different backbone, different subset, or a reporting error?
6. Recall_key = 1.00 with Precision_key = 0.70 on GeoPlan-Bench: is the planner over-generating candidate tools, and does the λ_L parsimony penalty actually bind at inference?
7. What is the marginal token/latency cost per task of the distillation loop, and does a cheaper distiller (small local model) preserve the gains?
8. Would the same three-level memory decomposition help outside EO (e.g. bioinformatics or CAD tool chains), or is the benefit tied to the specific rigidity of remote-sensing product dependencies?
