> **一句话总结：** SkillZip 把自演化 agent 的 SKILL.md 解析成"接口/工作流/工具协议/带作用域规则/输出契约"的类型化契约，再用带硬覆盖约束的最小描述长度目标做确定性优化（"讲一次、引多次"），在完全不跑任何任务 rollout 的前提下，把 SkillOpt 演化出的技能平均压缩 31.2%（对比基线 SkillReducer 仅 9.2%），三个 benchmark 宏平均分 0.577 反而略高于未压缩技能的 0.570、压缩耗时从 1331s 降到 207s（LiveMath）。

> **TL;DR:** SkillZip formulates skill compression as a typed minimum-description-length objective with a hard coverage constraint, so it never needs tasks, rollouts, rewards, or verifiers. On skills evolved by SkillOpt across BFCL-v4 Web Search, LiveMathematicianBench, and SpreadsheetBench with three backbones (Qwen3.7-Max, Qwen3.6-Plus, Kimi-K2.6), it compresses 31.2% on average versus 9.2% for the closest baseline SkillReducer, while scoring 0.577 macro-average versus 0.544 for SkillReducer and 0.570 for the uncompressed evolved skill — and it uses 0 rollouts versus SkillReducer's 40–80, giving a 3.5x end-to-end speedup (286s vs ~1000s average).

## 核心贡献

- **提出"评估无关"的技能压缩问题设定**：压缩过程只能读技能文本、被引用文件和补丁序列，禁止访问下游任务、执行轨迹、奖励和行为验证器；这些资源只在压缩之后用于测量泛化，从而切断"在有限评估集上反复调优"带来的选择效应（作者显式引用 adaptive data analysis 的 holdout reuse 问题）。
- **把技能形式化为类型化契约** C(S) = ⟨I, G, T, C, O, E⟩：接口（名称、目的、触发条件、排除条件）、工作流（动作、顺序、决策、循环、回退、停止条件）、工具协议（工具名、必需参数、前置条件、错误处理）、带作用域与 guard 的规则（must / must_not / prefer）、输出契约（字段、校验、终止条件）、支撑证据（示例、模板、rationale）。类型化让"哪些合并是安全的"变成结构判断而非词元重要性判断。
- **最短忠实解释目标**：min L(K) + L(R|K) s.t. 每个抽取出的必需单元 a ∈ A_req 都被覆盖。该硬约束直接给出 Prop. IV.1（解析契约保持）与 Corollary IV.2（稀有规则保持与压缩时任务分布无关）——一条只出现一次的 guard 或输出字段不会因为"没被采样任务激活"而被删掉。
- **四类共享决策统一在同一目标下**：等价需求合并（式 7）、规则作用域提升（式 8）、重复工作流抽取为共享过程（式 9）、公共规则 + guarded delta 编码例外（式 10）。每个候选都要通过"定义开销 + 引用开销 + 作用域标注开销"的显式成本测试，非正收益候选直接丢弃。
- **两种运行模式**：One-shot SkillZip（一次 schema 约束的抽取调用 + 完全确定性的最小成本覆盖优化 + 模板化渲染 + 可选结构审计恢复）；Zip-on-Write（每个自演化补丁在 ABSORB / REFINE / EXTEND / REFACTOR 四种解释中选目标增量最小者，只检索 O(dk) 个同类型、同作用域及祖先作用域候选，不重放任务、不重解析全历史，并周期性 global repack）。
- **附录级可复现规格**：给出仓库文件划分、CLI（compress / update / audit / inspect）、sidecar JSON schema、三个 system prompt（抽取 / 补丁 / 独立审计）、写前日志的原子提交协议，以及一个 936→638 token 的 LiveMath 技能压缩前后完整对照示例。

## Key Contributions

- **A new problem framing.** Prior work either filters low-salience tokens (prompt compression) or validates candidate rewrites with rollouts (SkillReducer). SkillZip argues that multi-round *evolved* skills are a different regime: their bloat is repeated *representation* (the same invariant copied into branches, a workflow restated after each failure, progressively narrower exceptions), not irrelevant background — so the goal shifts from content filtering to knowledge consolidation.
- **Typed contract + hard coverage constraint.** Coverage is type-sensitive: a tool name does not cover its required arguments, and a general rule does not cover a conflicting guarded exception. Spans the parser cannot interpret confidently become *locked residuals*, copied verbatim and excluded from deletion.
- **MDL objective adapted to procedural knowledge.** Unlike SEQUITUR/Re-Pair-style sequence compression, the objective refuses to merge identical-looking clauses under incompatible guards and refuses to delete a unique rule with zero repetitions.
- **Zip-on-Write with a local-update equivalence proof.** Prop. A.2: if a patch introduces no profitable abstraction spanning both affected and unaffected regions, local optimization over the affected type–scope neighborhood yields the same update as rerunning the batch optimizer.
- **Empirical study of skill growth itself (RQ1).** Skills grow ~5.6x / 3.1x / 6.7x their seed length by round 5 on BFCL-v4 / LiveMath / SpreadsheetBench (avg ~5.2x), which is the motivating measurement, not just a claim.

## Methodology

**Pipeline (one-shot, Algorithm 1).** (1) A *deterministic* scanner parses front matter, headings, nested lists, code blocks, tables, and file references into blocks with stable hash IDs, `heading_path`, and line ranges; Markdown nesting seeds a scope tree, numbered lists and temporal markers give high-confidence workflow hints. Code fences and tables stay atomic. (2) A schema-constrained LLM call recovers the typed contract; every unit must cite source block IDs, and the host rejects unsupported citations, polarity mismatches, unknown tool names, and dangling workflow edges. The extractor is deliberately *not* asked to compress — interpretation is separated from optimization so the optimization is deterministic given fixed units. (3) Candidate reuse proposal uses hard structural blocking on `(type, modality, tool/output namespace, scope family)`: exact matches by hashing, near-duplicates by an embedding index verified by a frozen cross-encoder returning equivalence / left implication / right implication / conflict / unrelated. Conflicts create *exception* edges, never merges. (4) Selection: equivalent-unit clustering via union–find, rule placement via a bottom-up dynamic program over the scope tree, workflow reuse via weighted set packing (greedy by saving-per-covered-token plus pairwise exchange; an exact ILP exists for small instances to measure the approximation gap). (5) Rendering with fixed templates, plus an optional structural audit that reparses *only* the compressed skill (the audit parser never sees the original) and restores the shortest source span covering any missing trigger, guard, workflow edge, tool argument, polarity, or output field, marking it `locked=true`.

**Length model.** L̂(x) = |Render(x)|_tok + λ_d·n_def + λ_r·n_ref + λ_s·d(x), where d(x) is scope depth. The λ values equal the actual token cost of the template delimiters and are explicitly *not* fitted on downstream tasks — an important detail for the evaluation-free claim.

**Experimental protocol.** For each model–benchmark pair, a manually authored seed skill is evolved with SkillOpt on an evolution split disjoint from the test set, then frozen and given identically to every compression method. All conditions share the same model snapshot, scaffold, system prompt, tool definitions, interaction budget, and decoding config. One-shot SkillZip always uses Qwen3.7-Max as the compressor; Zip-on-Write uses the agent's own backbone. All LLM calls use greedy decoding at temperature 0. Baselines: No Skill, Human Skill, Evolved Skill (fidelity reference), and SkillReducer run with its native structure-aware pipeline.

## Results & Highlights

- **Compression rate (Table I):** SkillZip achieves 27.1% (Qwen3.7-Max), 29.7% (Qwen3.6-Plus), and 36.9% (Kimi-K2.6), averaging **31.2%**, versus SkillReducer's 10.5% / 3.6% / 13.4%, averaging **9.2%** — a 3.4x higher compression ratio on the same frozen evolved skills.
- **Task accuracy (Table I, macro-average over BFCL-v4 / LiveMath / SpreadsheetBench):** SkillZip **0.577** vs SkillReducer **0.544** vs uncompressed Evolved Skill **0.570**. SkillZip matches or improves the evolved skill in 5 of 9 model–benchmark cells despite being ~31% shorter. Largest single gains: LiveMath on Kimi-K2.6 **0.457 vs 0.433** evolved (+0.024) and **vs 0.384** for SkillReducer (+0.073); LiveMath on Qwen3.6-Plus **0.435 vs 0.392** evolved (+0.043).
- **SkillReducer regressions:** on Qwen3.7-Max BFCL-v4 SkillReducer scores **0.828**, *below* both the evolved skill (0.869) and even the No-Skill condition (0.833); on Qwen3.6-Plus BFCL-v4 it scores **0.621** vs 0.685 evolved and 0.623 No Skill.
- **Compression cost (Table II):** average wall-clock drops from **1331s → 207s** on LiveMath, **1082s → 332s** on Spreadsheet, and **587s → 318s** on BFCL-v4; averaged over datasets **286s vs ~1000s, a 3.5x speedup**. SkillZip uses 4–8 compressor LLM calls and **0 rollouts**; SkillReducer uses 3 calls plus **40–80 validation rollouts**. The paper notes its own SkillReducer timing is an *optimistic lower bound* because some rollouts hit a warm evaluation cache.
- **Cross-model transfer (RQ4, Fig. 6):** on LiveMath, overall retention **0.97 for SkillZip vs 0.91 for SkillReducer**, with the gain concentrated in off-diagonal (source ≠ target) pairs; on BFCL-v4 the two are reported as comparable.
- **Continual mode (RQ5, Fig. 5, 16 rounds on LiveMath):** uncompressed SkillOpt grows the skill to 2.5x / 3.1x / 3.7x seed length on Qwen3.6-Plus / Qwen3.7-Max / Kimi-K2.6; Zip-on-Write activated at round 1 caps it at roughly **1.6x–1.9x, a 38%–50% reduction** at the endpoint, with final accuracy 0.409 / 0.488 / 0.441 versus 0.395 / 0.476 / 0.438 uncompressed. Activating at round 8 instead only reaches 2.6x vs 1.9x on Kimi-K2.6 — redundancy is cheaper to prevent than to remove.
- **Qualitative case (Appendix C.E):** a LiveMath skill compresses 936 → 638 tokens (32%); the evolved source literally contains the "output only the single valid value / discard extraneous roots" rule twice, the "verify each intermediate product and sum" rule twice, and two near-identical "verify each candidate against all constraints" rules.

## Critical Assessment

**Novelty (moderate-high).** The specific move — treating an evolved skill as a typed contract and running MDL with a *hard* coverage constraint so rare rules survive by construction — is genuinely new relative to both prompt compression (LLMLingua family, query-conditioned) and evaluation-guided skill compression (SkillReducer). The individual ingredients (MDL, Re-Pair, scope-lifting DP, set packing, NLI-based relation checking) are all standard; the contribution is the composition and the problem framing, not new algorithms.

**Rigor (mixed).** The headline fidelity claim rests on a **0.577 vs 0.570 macro-average gap — 0.007, roughly 1.2% relative** — and the paper reports **no error bars, no seeds, and no repeated runs anywhere**. With temperature-0 decoding, run-to-run variance is reduced but not eliminated for agentic tool-calling, and BFCL-v4/SpreadsheetBench subsets are small enough that a 0.007 delta is very plausibly noise. The honest reading is "no systematic degradation," which the authors do write in the body text, but the abstract's "effectiveness and superiority" is stronger than the evidence.

**Baseline concerns.** SkillReducer's compression rate of **3.6% on Qwen3.6-Plus** is implausibly low for a method whose stated design *moves supplementary material to on-demand references* — either the token accounting excludes deferred reference files (which would systematically flatter SkillZip's single-artifact comparison) or SkillReducer was run without tuning on a skill regime it was never designed for. The paper does argue the latter fairly ("SkillReducer is more naturally positioned as a first-pass debloating method for general public skills"), but it never reports the deferred-content token budget, so a reader cannot verify the comparison is apples-to-apples. Similarly, No Skill beats SkillReducer on BFCL-v4 for Qwen3.7-Max, a red flag that the baseline configuration may be broken rather than merely mismatched.

**Missing ablations.** This is the largest gap. The objective has four decision types (equivalence merging, scope lifting, workflow reuse, exception encoding) plus a structural audit plus locked residuals, and **not one of them is ablated**. There is no measurement of how much compression each contributes, no version with the hard coverage constraint relaxed (which would directly test the rare-rule-preservation claim's practical value), and no ablation of the optional audit-and-restore step. The λ_d / λ_r / λ_s length-model constants and the repack triggers (θ_repack, ρ, B) are never swept. There is also no measurement of contract-extraction quality against human annotation, even though Section V explicitly claims "contract recovery can be evaluated against human annotations" as a design benefit.

**Unverified claims stated as properties.** Appendix D.D concludes the idempotence argument with "This property **will be tested** empirically by applying one-shot compression twice" — future tense in the submitted paper. The extraction step's own failure modes (an LLM parser hallucinating or dropping a requirement) are acknowledged in the "Boundary of the Guarantee" sections but never quantified, which matters because the entire preservation guarantee is *relative to the parser output*.

**Reproducibility (good on spec, unverified in practice).** Appendix B/C are unusually generous: full sidecar schema, all three system prompts, CLI, transaction protocol, cache-key design. But there is no released code, the three backbones are proprietary API models (Qwen3.7-Max, Qwen3.6-Plus, Kimi-K2.6), and the evolved skills that serve as inputs are themselves the output of a separate system (SkillOpt) on unreleased evolution splits — so exact reproduction is effectively impossible outside Alibaba.

**Significance (high if it holds).** RQ1 alone (~5.2x average skill growth over 5 rounds) is a useful and citable measurement of a real operational pathology, and the Zip-on-Write "turn it on at round 1" finding is immediately actionable for anyone running a persistent-skill agent loop.

## Strengths

- The evaluation-free constraint is stated as an auditable *evidence contract* ("compression observes no benchmark tasks, rollouts, rewards, or behavioral verifier"), and Appendix B suggests the repo be structured so the claim is checkable from file access and logs — an unusually falsifiable framing.
- The conservative failure mode is designed in, not hoped for: ambiguous spans become locked residuals, so the method under-compresses rather than silently deleting an unverified rule.
- Cost analysis identifies the right bottleneck — environment interaction (40–80 rollouts) dominates end-to-end cost, not the number of compressor LLM calls — and the reported baseline time is explicitly flagged as an optimistic lower bound for the competitor, which is intellectually honest.
- The before/after skill in Appendix C.E is concrete enough to see exactly what the method does (two literal duplicate rules removed, two near-paraphrases folded, free-text "Approach" normalized into a numbered workflow) and exactly what it costs (the compressed text is noticeably telegraphic, dropping articles and connectives).
- Separating the LLM (interpretation) from the optimizer (deterministic min-cost covering) makes the compression decisions traceable and auditable per candidate, with logged before/definition/reference/exception/residual/after token costs.

## Limitations

- **Guarantee is parser-relative.** Preservation holds for the contract the LLM parser extracted, not for the source text; a requirement the parser silently misreads is unprotected, and parser accuracy is never measured.
- **No behavioral equivalence.** The method cannot claim two rendered skills induce identical model behavior — it only claims structural coverage. The 5-of-9 cells where SkillZip trails the evolved skill (e.g., Qwen3.7-Max SpreadsheetBench 0.519 vs 0.525) show the gap is real, if small.
- **Single-skill scope.** Everything is per-skill; cross-skill redundancy in a library of many skills (an obvious source of duplication in real agent deployments) is out of scope.
- **Compressor asymmetry.** One-shot mode always uses Qwen3.7-Max as compressor while Zip-on-Write uses the agent's own backbone, so one-shot results conflate "SkillZip works" with "a strong model did the extraction"; there is no one-shot experiment with a weaker compressor.
- **Compressed text readability.** The rendered output drops function words ("Give simplest exact form", "expression output simplified expression itself"), which conflicts somewhat with the stated goal of remaining a human-inspectable, diffable artifact.
- **Benchmark breadth.** Three benchmarks, one of which (LiveMath) carries most of the accuracy gains, and RQ4/RQ5 are run on subsets (LiveMath + BFCL-v4 for transfer; LiveMath only for continual mode).
- **Approximation gap unquantified.** Workflow selection is greedy set packing; the exact ILP is described as available for small synthetic instances but no measured gap is reported.

## Relevance

如果你关注 agent 长期记忆/技能库的上下文成本与可维护性，这篇给出了一个不依赖 rollout、可确定性复现、且能挂进自演化循环增量运行的工程方案，"Zip-on-Write 从第 1 轮就开"的结论可以直接迁移到任何持久化 SKILL.md 的 agent 系统。方法论上，把"类型化契约 + 硬覆盖约束"作为压缩安全边界的思路，也适用于 prompt/记忆/工具描述等其他随时间单调增长的上下文资产。

## Questions for Further Exploration

- How accurate is the schema-constrained contract extraction itself? A per-type precision/recall against human annotation would convert the "parser-relative" guarantee from a caveat into a quantified bound.
- What does an ablation of the four decision types show — is most of the 31.2% coming from trivial exact-duplicate removal (as the Appendix C.E example suggests) rather than from scope lifting and workflow abstraction?
- If SkillReducer's deferred reference files are counted in its token budget, does its 9.2% compression rate change materially, and does the comparison survive?
- Does the accuracy parity hold with multiple seeds and confidence intervals, or is 0.577 vs 0.570 within run-to-run noise?
- Can the objective be extended across a *library* of skills, sharing procedures between skills rather than only within one?
- What happens under adversarial or badly written source skills where the scope tree implied by Markdown nesting contradicts the semantic scope of the rules?
- Does the claimed idempotence Zip(Zip(S)) = Zip(S) actually hold empirically, given that rendering compresses phrasing and reparsing may recover a slightly different contract?
