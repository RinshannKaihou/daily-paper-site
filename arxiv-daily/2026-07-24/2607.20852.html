Why this matters

A benchmark for the overlooked middle ground between code generation and code review.

Defines “residual-bug monitoring after public tests pass” as a distinct evaluation target — directly relevant to LiveCodeBench, SWE-bench, and BigCodeBench designers, and to teams deploying LLM coding agents.

Critical edge

G4-adv is a robustness stressor, not a prevalence estimate.

Adversarial overfit cells reach 68–73% hidden-bug rates, but the authors explicitly warn: do not read these as real-world LLM bug rates. Hidden tests are a frozen oracle, not full semantic correctness.

02Results & highlights

  • Public-pass ≠ correct. Across three domains, G1 hidden-bug rates: 43.1% BigCodeBench-Hard · 44.2% Data-Science · 46.5% CodeWorkflow; rising to 68–73% under G4-adv.
  • Weak verifiers collapse at low FPR. Direct Qwen-7B ≈ random (AUROC 0.536, misses 94.0% @5% FPR). Hybrid scaffold lifts to 0.601; Mistral-7B Hybrid reaches 0.665, still missing 80%.
  • Adversarial pressure is monotone. G4-adv lowers AUROC ~0.07 and raises FNR ~0.07 — consistent across all 90 cells (45 AUROC + 45 FNR).
  • Strong verifier ≠ solved. GLM-5.1 holds a clean capability gradient (FNR: Mistral 0.823 → mini 0.756 → GLM 0.543), but still carries G4-adv FNR 0.662.
  • Inferability audit (n=300). 92% spec-grounded, but only 33% constructively findable from M1 pre-failure; diagnostic views lift catch-rate 24% → 74% — proof some misses are evidence-limited, not capability-limited.

01Methodology

  • Fixed information boundary M1. Verifier sees only spec + interface + public tests + candidate + public-pass status. Hidden tests act as oracle labels, never as monitor input — decouples bug construction from verifier ranking.
  • Generator conditions G1→G4-adv. G1 public-aware; G2 verifier-aware; G3 scheme-aware; G4-natural shortcut; G4-adv explicitly asked to pass public tests while hiding residual defects — a brittleness stressor.
  • Verifier scaffolds. Direct (single-pass score) vs Hybrid (decompose requirements + boundary cases, then counterexample-driven review). Same evidence, different reasoning structure.
  • Two-tier metrics. Candidate-pool (public-pass rate, hidden-bug rate, invalidity) kept separate from verifier metrics (AUROC, AUPRC, TPR/FNR @ fixed low FPR, NA rate). Main op-point: 5% FPR.

03Strengths & limitations

Strengths

  • M1 boundary cleanly prevents “verifier peeking at answers.”
  • Three orthogonal failure axes — each with its own control table.
  • Fixed-FPR op-point + 1/5/10% sensitivity + NA column + bootstrap CIs.
  • Inferability audit (Table 6/7) empirically separates “uninferable” from “uninferred.”

Limitations

  • Hidden tests ≠ full semantic correctness — frozen-suite labels only.
  • Data-Science & CodeWorkflow splits don’t cover all libraries / repo-scale / interactive dev.
  • No learned verifier/reranker, no interactive review, no cost/latency tradeoff.
  • Model versions are 2026 fictional placeholders; transferability unverified.

04Questions for further exploration

  1. Learned verifier ceiling under M1? Table 7 shows monotone gains from diagnostic views — where does a trained public-pass residual-bug discriminator top out without breaking the evidence boundary?
  2. Is the G4-adv failure-mode distribution stable across generator families (boundary, API misuse, numeric/statistical, join, schema shifts)?
  3. Can interactive multi-turn counterexample generation close NA and miss gaps without leaving M1? Hybrid already raises NA from 3.1% → 5.7% — is structured output itself a cost?
  4. What is the cost-vs-miss optimal FPR for small teams (expensive review) vs large platforms (cheap review)? Paper supplies 1/5/10% but no tradeoff curve.
  5. The 36% posthoc-uninferable residual — is this a hard theoretical ceiling on M1 monitoring for any verifier?
  6. Cross-family self-audit bias? Generator–verifier same-family bias was sidestepped via GPT-5.4 subset; is it still negligible at scale?
