Key finding

Democratized AI agents behave like fragile microservices — they demand continuous assurance, not one-time validation.

Toward Continuous Assurance for the Democratization of AI Agent Creation in Industry

Natan Levy · Hebrew University of Jerusalem · Harel Berger · Ariel University
arxiv.org/abs/2607.21495 ↗

01 Key metric

6/6scenarios

9failure classes · 5framework elements — prototype auditor matched the expected failure class on every author-defined scenario without overclaiming on uninspectable config.

02 Why this matters

Low-code platforms let business users build mission-critical agents no one monitors — assurance must be as democratized as creation.

03 Critical edge

Evaluation uses author-defined scenarios with author-defined expected findings — no held-out data, no independent ground truth, no detection-coverage or false-positive measurement.

Anchor incident

A citizen-built agent in the legal department of a major aerospace company handled sensitive workflows — yet no one could answer: “if this agent stops working, how is it detected?”

Methodology § 01

A position paper that reframes reliability as an operational-composition problem, backed by a hosted custom-GPT prototype.

Failure classes were derived from DevOps dependency categories (Amaro et al. 2025) and extended with organizational classes — ownership and governance — motivated by the aerospace incident. Evaluation used scenario-based fault assessment (Riedmaier et al. 2020), each scenario judged against four success criteria.

  • Model dependency — drift, deprecation, version change
  • Tool invocation — API/schema breakage, auth failure
  • Retrieval — stale, missing, or rotated sources
  • Permission / credential — expired or over-scoped access
  • Output contract — missing fields, format drift
  • Workflow / scheduling — broken triggers, dead schedules
  • Semantic degradation — silent behavioral decay
  • Ownership — no accountable owner
  • Governance — no audit, escalation, or retirement rule

Results & highlights § 02

  • Taxonomy coverage. 9 classes mapped 1-to-1 to readiness checks; binary execution checks miss the silent-degradation modes.
  • 6/6 scenario feasibility. Readiness decisions matched the expected failure class and available evidence — incl. correctly flagging an uninspectable private GPT config as not externally verifiable.
  • Evidence discipline. Confirmed failures → Not ready + remediation; unverifiable cases → Readiness unknown rather than false pass/fail.
  • Criticality-based policy. Lightweight rules for informal agents; strict contracts/audit/escalation for legal, financial, customer-facing.

The 5-element framework § 03

  • Dependency map
  • Readiness contract — min observable conditions for “operational”
  • Scheduled / change-triggered checks
  • Diagnostics — classify failures per taxonomy
  • Lifecycle governance — ownership, escalation, retirement

Strengths § 04

  • Concrete anchor. Problem stated from a credible industrial incident, not abstract motivation.
  • Practitioner artifacts. 9-class taxonomy + readiness-contract template + public GitHub repo lower adoption barrier.
  • Evidence discipline as a design requirement — refusing to overclaim on uninspectable config is a meaningful correctness property.
  • Criticality-based guidance realistic for heterogeneous agent inventories.
  • Clean conceptual lineage from the authors’ prior security visibility work.

Limitations § 05

  • No quantitative metrics — detection coverage, FP/FN rates, time-to-recovery all absent.
  • Author-defined ground truth. 6/6 matches author-authored expectations is weak evidence.
  • Assurance-of-the-assessor unresolved. The LLM auditor inherits the very drifts/failures it detects; meta-assurance deferred.
  • Hosted-GPT not fully exportable — reproducibility rests on static artifacts, not runnable code.
  • Taxonomy intentionally non-exhaustive; semantic-degradation detection via “representative prompts” is underspecified.
  • MLOps/AgentOps integration demonstrated only conceptually.

Open questions for further exploration § 06

  1. How to verify readiness of hosted agents (e.g. custom GPTs) without platform vendors exposing private config — is a telemetry-API standard needed?
  2. When the LLM auditor itself drifts, how to build meta-assurance (fixed regression suites, multi-agent cross-checks)?
  3. How to systematically select “representative prompts” to catch semantic degradation while controlling false positives?
  4. Does the 9-class taxonomy have discriminative validity on real enterprise agent-failure data — what sample size & labeling to measure coverage/FPR?
  5. How to auto-classify criticality tiers and wire them into change-management, access-control, and audit-compliance flows?
  6. Does the framework extend to multi-agent / agent-of-agents graphs where dependencies and ownership propagate dynamically?
