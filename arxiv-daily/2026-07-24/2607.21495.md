> **一句话总结：** 本文指出非工程师（citizen developer）通过低代码/无代码平台创建的 AI agent 虽然看似静态生产力工具，实则像微服务一样依赖不断变化的模型、工具、检索源与权限，从而产生"可靠性鸿沟"；作者提出一个轻量级的持续保障框架（依赖映射 + 就绪契约 + 定时检查 + 诊断 + 生命周期治理），并用一个托管 GPT 原型审计器在 6 个场景中验证了其可将可观测症状转化为有据可依的就绪决策。

> **TL;DR:** As low-code/no-code platforms let non-engineering org users build business-critical AI agents that behave like fragile microservices, the authors define a 9-class failure taxonomy and a 5-element continuous-assurance framework (dependency map, readiness contract, scheduled checks, diagnostics, lifecycle governance); a hosted custom-GPT prototype auditor correctly classified all 6 author-defined scenarios into the expected failure class without overclaiming on unverifiable private configuration, evidencing that democratized agent creation needs democratized assurance.

## 核心贡献

1. **可靠性鸿沟的定义与失败分类法（Taxonomy）**：首次系统刻画"工业级 AI agent 民主化创建"带来的可靠性错配——agent 对用户像静态生产力工具，对运维则像依赖易变生态的实时微服务。基于 DevOps 依赖类别并扩展了组织维度（ownership、governance），提出 **9 类失败分类**（模型依赖、工具调用、检索、权限凭证、输出契约、工作流调度、语义退化、所有权、治理），每类对应一个 readiness check。
2. **持续保障框架（Continuous-Assurance Framework）**：提出 **5 要素**轻量流程——依赖映射、就绪契约（readiness contract）、定时/变更触发检查、诊断分类、生命周期治理。核心设计原则是"专长翻译"（expertise translation）：让领域专家用任务级语言定义成功标准，保障层自动将其翻译为可靠性工件，无需每个创建者掌握 DevOps/MLOps/AgentOps。
3. **原型审计器与场景化评估**：实现了一个托管 custom GPT 形式的原型审计器，强调"证据纪律"（evidence discipline）——区分 confirmed finding / reproducible risk / unknown / not-applicable，避免对不可见的私有配置做过度断言。在 **6 个场景**的故障注入评估中，全部产出与预期失败类一致的决策，并给出可执行的修复指引。

## Key Contributions

- **Failure taxonomy for long-lived democratized agents** — A 9-class taxonomy extending DevOps dependency categories with organizational classes (ownership, governance), each paired with a concrete readiness check; designed to capture the silent-degradation failure modes that binary execution checks miss.
- **A 5-element continuous-assurance framework** — Dependency map, readiness contract, scheduled/change-triggered checks, diagnostics, and lifecycle governance, built around the principle of *expertise translation* so non-engineering creators do not need to master DevOps/MLOps/AgentOps.
- **A prototype auditor with evidence discipline + scenario-based evaluation** — A hosted custom-GPT auditor that distinguishes confirmed findings from risks/unknowns and refuses to infer readiness on uninspectable private configuration; evaluated on 6 scenarios with author-defined expected findings, producing consistent, actionable readiness decisions.

## Methodology

**Problem framing.** The paper opens from a real industrial incident: a citizen-built agent in the **legal department of a major aerospace company** was handling sensitive workflows, yet no one could answer "if this agent stops working, how will it be detected?" — exposing the systemic gap between agent creation democratization and reliability practice.

**Taxonomy construction.** Failure classes were derived from dependency categories reported in the DevOps literature (Amaro et al. 2025) and extended with organizational classes (ownership, governance) motivated by the aerospace observation. The taxonomy is explicitly *not* claimed to be exhaustive — it targets dependency-related failure modes.

**Framework design (5 elements).**
1. *Dependency map* — models, prompts, tools, APIs, retrieval sources, files, permissions, schedules, downstream consumers.
2. *Readiness contract* — minimum observable conditions for "operational" status (source access, tool invocation, retrieval freshness, output format, representative behavioral checks). An illustrative document-analysis agent contract lists 5 observable conditions.
3. *Scheduled assurance checks* — run periodically or after model/source/permission/tool changes.
4. *Diagnostics* — classify failures per taxonomy, estimate operational impact.
5. *Lifecycle governance* — ownership, escalation, criticality, auditability, retirement rules; policies should be **criticality-based** (lightweight for informal productivity agents, stricter contracts/audit trails/escalation for legal, financial, customer-facing workflows).

**Prototype.** Implemented as a hosted custom GPT. Transparency/reproducibility supported via a public GitHub repository (https://github.com/NatanLevy/continuous-agent-assurance) containing auditor instructions, declared properties, readiness-contract template, anonymized scenarios, expected findings, and redacted execution results. The hosted GPT artifact itself cannot be exported as a conventional source package because OpenAI's platform does not provide a complete inspectable export.

**Evaluation protocol.** Scenario-based fault assessment (Riedmaier et al. 2020). For each scenario a success required satisfying **4 criteria**: (1) correct taxonomy class, (2) confirmed evidence distinguished from risks/unknowns, (3) no claims about unavailable private config, (4) concrete remediation action executable by owner/admin.

## Results & Highlights

- **Taxonomy coverage:** The framework defines **9 failure classes** mapped 1-to-1 to readiness checks (Table I), covering model, tool, retrieval, permission, output-contract, workflow/scheduling, semantic-degradation, ownership, and governance failures.
- **Scenario-based feasibility:** Across **6 evaluated scenarios** (Table II), the prototype auditor produced readiness decisions *consistent with the expected failure class and available evidence* in every case — including correctly marking an uninspectable "private GPT configuration" as *not externally verifiable* rather than claiming verification.
- **Evidence discipline demonstrated:** Confirmed operational failures (missing source document, missing output field, tool/API error, no valid owner) were classified as *Not ready* with concrete remediation, while the unverifiable source-freshness case was reported as *Readiness unknown: perform owner-side freshness tests* — illustrating evidence-grounded decisions over binary pass/fail.
- **Framework scope:** **5 framework elements** plus an illustrative 5-condition readiness contract, with criticality-based policy guidance explicitly differentiating low-criticality informal agents from operational/legal/financial/customer-facing agents requiring stricter contracts.

## Critical Assessment

The paper is best understood as a **position/framework paper with a feasibility prototype**, not an empirical benchmark. Its central reframing — that reliability in democratized agent creation is *not only a model-evaluation problem* but an operational-composition problem (missing sources, stale retrieval, expired permissions, shifted tool schemas, broken schedules, unclear ownership) — is well-motivated and is the strongest contribution. The taxonomy-to-readiness-check mapping is concrete and actionable.

However, several paper-specific weaknesses temper the claims:

- The "evaluation" is **scenario-based with author-defined scenarios and author-defined expected findings**; there is no held-out data, no independent ground truth, and no measurement of detection coverage, false-positive rate, or time-to-recovery. The authors explicitly state this is "an initial feasibility assessment rather than a measurement of coverage."
- Quantitative validation is essentially absent — the headline result is that 6/6 author-authored scenarios matched author-authored expectations, which is a weak form of evidence.
- The **assurance-of-the-assessor problem** is acknowledged but unresolved: an LLM-based auditor assessing other LLM agents is itself vulnerable to the same model drifts, API changes, and tool failures it is meant to detect. The paper defers meta-assurance (regression suites, multi-agent cross-checking, platform telemetry) to future work.
- The prototype cannot be distributed as a conventional source package because hosted custom-GPT configuration is not fully inspectable/exportable, limiting independent replication of the runtime behavior.
- The taxonomy is admittedly non-exhaustive and the mapping from DevOps dependency categories is somewhat derivative; the organizational classes (ownership, governance) are the genuinely novel additions.

## Strengths

- **Timely, well-scoped problem statement** tied to a concrete, credible industrial anecdote rather than abstract motivation.
- **Practitioner-actionable artifacts**: the 9-class taxonomy, the readiness-contract template, and the public GitHub repository lower the barrier for organizations to adopt the ideas.
- **Evidence discipline as an explicit design requirement** is a mature engineering stance — the auditor's refusal to overclaim on uninspectable private configuration is a meaningful correctness property often missing in LLM-based assessment tools.
- **Criticality-based policy guidance** (lightweight vs. strict contracts) is realistic for heterogeneous organizational agent inventories.
- Clean conceptual lineage from the authors' prior structural-visibility work in security to agent reliability.

## Limitations

- No quantitative metrics on detection coverage, false-positive/negative rates, or time-to-recovery.
- Evaluation scenarios and expected findings are author-defined; independent validation against real-world reported agent failures is left to future work.
- The LLM auditor is part of the assurance chain and inherits the same failure modes it monitors; no independent automated meta-assurance mechanism is provided.
- Hosted-GPT platform constraints prevent full inspectable export, so reproducibility relies on the released static artifacts rather than runnable code.
- Taxonomy is intentionally non-exhaustive; semantic-degradation detection in particular relies on "representative prompts," which is underspecified for open-ended agents.
- The framework is presented at a conceptual/architectural level; integration with existing MLOps/AgentOps stacks is not demonstrated.

## Relevance (Chinese)

本文对当前企业级 LLM agent 落地具有较强现实针对性：

- **直接对应企业痛点**：随着 Copilot Studio、GPTs、Dify、Coze 等低代码平台让业务人员（法务、采购、HR、财务）自行搭建 agent，企业正在累积大量"无人值守"的关键 agent。本文提出的可靠性鸿沟与失败分类法，可作为企业 agent 治理与可观测性建设的起点。
- **与 AgentOps / LLMOps 生态互补**：框架不要求每个 agent 创建者成为 SRE，而是用"就绪契约 + 定时检查"把可靠性能力下沉到保障层，这与当前 AgentOps 监控（如 AgentOps、LangSmith、Helicone）的方向一致，但更强调组织维度（所有权、治理、退役）。
- **对评估方法论的启示**：作者用"证据纪律"区分 confirmed / unknown，避免对不可见私有配置过度断言——这一原则对任何基于 LLM 的自动化审计/红队工具都有借鉴价值。
- **可作为后续研究的选题库**：meta-assurance（审计器自身的保障）、人机协同反馈、语义退化的可操作检测、以及与现有 MLOps 平台的集成，均是明确的研究空白。
- 局限：作为 position paper，缺乏量化基准，落地价值需在企业真实 agent 库存上进一步验证。

## Questions for Further Exploration

1. 如何在不依赖平台厂商开放私有配置的前提下，对 hosted agent（如 custom GPTs）进行可验证的就绪性审计？是否需要平台级 telemetry API 标准化？
2. 当 LLM 审计器自身发生模型漂移或工具失效时，如何构建**meta-assurance**（如固定回归测试集、多 agent 交叉校验）来保障审计链的可信度？
3. 就绪契约中的"代表性 prompt"如何系统化选取，才能在 open-ended agent 上有效捕获语义退化而控制误报？
4. 失败分类法（9 类）是否在真实企业 agent 故障数据上具有**判别有效性**？需要多大规模、何种标注的独立数据集才能测量 detection coverage 与 false-positive rate？
5. 保障策略的 criticality 分级（轻量 vs. 严格）如何在组织内自动化判定，并与现有的变更管理、访问控制、审计合规流程集成？
6. 框架是否能扩展到 multi-agent / agent-of-agents 架构，其中依赖图与所有权在多个 agent 之间动态传播？
