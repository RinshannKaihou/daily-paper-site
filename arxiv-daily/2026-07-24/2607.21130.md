> **一句话总结：** 作者基于 AIfES 框架构建了一个开源、完全 float16 的端侧训练库，针对支持 Zfh/Zvfh 的 RISC-V 单核（在 NaxRiscv 超标量乱序 FPGA 软核上扩展 Zfh），实现相对 float32 约 50% 的内存下降且精度损失极小，并支持 batch≥1 与层冻结以适配迁移学习/微调。

> **TL;DR:** This paper presents an open-source float16 on-device-training (ODT) library built on AIfES, extended with RISC-V Zfh/Zvfh hand-optimized kernels (NMSIS-DSP) and an AIfES-Converter that imports PyTorch/TensorFlow models with layer-freezing support. On the RISC-V ISA Simulator, float16 training of a 5-layer MLP on MNIST/FashionMNIST stays within ~0.7 percentage points of float32 validation accuracy, while a 3-layer MLP transfer-learning config shows a flat ~50% parameter-memory cut (50.43 kB vs 100.85 kB) and even larger gradient-memory savings when freezing layers and using SGD. On a dual-issue RV64GC NaxRiscv FPGA softcore (Xilinx XC7K325T, 175 MHz), adding the 36-instruction Zfh extension costs only +1.15% LUT6 and +0.05% FF with no frequency loss, and the authors sketch a 4-lane, VLEN=64 Zvfh VPU projected to give 4× scalar speedup for f16 — though the VPU's measured performance is left as future work.

## 核心贡献

- **首个在 RISC-V 单核上同时具备"全 float16 ODT + batch≥1 + 开源"的框架**：Table 1 中,在所列对比项里,本文是唯一同时满足 RISC-V 支持、完整 ODT 能力(前向+反向)、float16 支持、batch≥1 以及开源的方案——PULP-Trainlib 限 batch=1,AIfES 缺 float16/RISC-V 支持,Decentor-V 与全量化训练[2]则缺 float16 或 RISC-V 支持。
- **在 AIfES 基础上引入 Zfh/Zvfh 手工优化数学原语**：集成 NMSIS-DSP 库,并通过编译期在 Zfh(标量)与 Zvfh(向量)实现间切换;AIfES-Converter 被增强以把 PyTorch/TensorFlow 模型转成 RISC-V float16 C 代码,并提供层冻结选项以支持迁移学习/微调。
- **量化验证 float16 训练的精度代价极小**:在 MNIST/FashionMNIST 上以 5 层 MLP、batch 128、Adam、交叉熵、lr 1e-3 训练,float16 与 float32 的验证准确率差异均控制在约 0.7 个百分点以内(Table 2)。
- **给出 Zfh 在超标量乱序 FPGA 核上的低开销实证**:在 RV64GC NaxRiscv(Xilinx XC7K325T-2FFG900C,175MHz)上,Zfh 的 36 条指令扩展仅带来 +1.15% LUT6、+0.05% FF,且不降低最高工作频率。
- **提出一个 Zvfh 向量处理单元(VPU)架构**:lane 结构 + 输入/输出 crossbar、VLEN=64、4 lane(理论对 f16 有 4× 标量加速)、寄存器分组(LMUL)通过指令发射/重命名阶段拆分为微操作以利于乱序执行;这是首个面向超标量乱序核的 Zvfh 开源实现讨论。

## Key Contributions

- **First RISC-V single-core framework that is open-source, full float16 ODT, and batch-size ≥ 1 simultaneously**: in the Table 1 landscape, only "Ours" ticks RISC-V support, full ODT, float16, batch≥1, and open-source all at once — PULP-Trainlib is open and float16 but capped at batch=1 on multi-core, AIfES supports full ODT and batch≥1 but lacks float16/RISC-V specialization, and the quantized-training lines [11]/[2] drop either float16 or RISC-V.
- **AIfES extension with hand-optimized Zfh/Zvfh math primitives plus a model-import tool**: NMSIS-DSP kernels are integrated and selected between Zfh and Zvfh at compile time; the AIfES-Converter is enhanced to convert PyTorch/TensorFlow models into RISC-V float16 C, with an optional layer-freezing path for transfer learning/fine-tuning.
- **Empirical evidence that float16 training matches float32 accuracy within ~0.7 points**: training a 5-layer MLP (512-256-128-64-10, ReLU) on MNIST/FashionMNIST with batch 128 / Adam / cross-entropy / lr 1e-3, float16 validation accuracy is within 0.68 points of float32 across all four dataset/optimizer cells.
- **A documented low-cost Zfh silicon footprint on a super-scalar out-of-order core**: extending the dual-issue RV64GC NaxRiscv with the 36 Zfh instructions costs +1.15% LUT6 and +0.05% FF on a Xilinx XC7K325T-2FFG900C at 175 MHz, with no drop in maximum operating frequency — making Zfh alone a credible hardware-level enabler for f16 ODT.
- **An architecture proposal for a Zvfh VPU** (lane-based, 4 lanes, VLEN=64, register grouping handled as micro-ops at issue/rename, tightly integrated via SpinalHDL plugins) — the first discussion of strict Zvfh support on a super-scalar out-of-order RISC-V core, which existing open-source VPUs (RISC-V², Vicuna2, Ara2) do not provide.

## Methodology

The work is a hardware-software co-design with two tracks, both building on existing open-source artifacts rather than greenfield development.

**(Software track — extending AIfES).** AIfES is taken as the base because its modularity lets hardware-specific math primitives be plugged in. The authors use the NMSIS-DSP library (Nuclei System Technology, inspired by ARM CMSIS-DSP), whose primitives are optimized for standard RISC-V Zfh/Zvfh extensions and are vector-length agnostic, so the same kernels run on any Zvfh-compliant core. A compile-time switch selects between the Zfh and Zvfh backends. The pipeline (Figure 1) is: dataset + DNN → AIfES-Converter (converts to RISC-V float16, optional layer freezing, optional NAS or pre-training, code generation) → user application built on the extended AIfES library. Manually vectorized kernels are preferred over auto-vectorization, citing prior work showing manual vectorization still beats GCC/LLVM auto-vectorized scalar kernels on RISC-V.

**(Hardware track — extending NaxRiscv).** NaxRiscv is an open-source configurable RV64GC super-scalar out-of-order core written in SpinalHDL; the chosen config is dual-issue with a 32-entry issue queue, two integer ALUs, one FPU, one LSU, a 64-entry reorder buffer, a Gshare branch predictor, and two 16 kB 4-way L1 caches (I/D). For Zfh, the decoder, LSU, and FPU are extended to handle the 36 instructions; because the FPU already supports float32/float64 via NaN-boxing and exponent-bias extension, float16 reuses the same unpacking-to-IEEE-then-extend-to-float64 policy. For Zvfh, the authors describe a lane-based VPU (Figure 4): four lanes (each a 32-bit slice holding FPU + integer ALU), fed by an input crossbar that routes source operands by format/mask/opcode and drained by an output crossbar; with VLEN=64 and XLEN=64, the float and vector physical register files (and parts of their allocation tables) are merged to cut overhead; register grouping (LMUL) is handled by splitting vector instructions into micro-operations at issue/rename so each has single physical register operands and can execute out of order, except for instructions like vrgather.vv whose (LMUL)² destination-source relations resist clean slicing.

**(Evaluation setup).** Software correctness and accuracy are measured on the RISC-V ISA Simulator, not on the FPGA core — a 5-layer MLP on MNIST/FashionMNIST (batch 128, Adam/SGD, cross-entropy, lr 1e-3 or 1e-4), plus a 3-layer MLP (32-16-10) transfer-learning config pretrained on MNIST and fine-tuned on EMNIST to measure memory. FPGA resource numbers come from Vivado 2021.1 on the XC7K325T-2FFG900C.

## Results & Highlights

- **Float16 validation accuracy within ~0.7 points of float32 (Table 2)**: MNIST/SGD/lr-1e-3 → 97.29% (f16) vs 96.88% (f32) — float16 actually higher; MNIST/Adam/lr-1e-3 → 96.78% vs 97.32%; FashionMNIST/SGD/lr-1e-3 → 86.85% vs 87.53%; FashionMNIST/Adam/lr-1e-4 → 88.25% vs 88.54%. All four cells stay within a 0.68-point band; on MNIST/SGD float16 is +0.41 points *ahead* of float32, indicating the difference is well within run-to-run noise.
- **Flat ~50% parameter-memory cut, larger gradient savings when freezing (Table 3)**: 3-layer MLP transfer-learning config — model parameters drop from 100.85 kB (f32) to 50.43 kB (f16), exactly 50.0%. Gradient/optimizer/activation memory with no frozen layer: SGD 202.60 kB (f32) → 101.43 kB (f16), Adam 404.77 kB → 202.75 kB. Freezing layers 1-2 cuts gradient memory further: SGD 105.23 kB → 52.74 kB (f32 vs f16), Adam 307.40 kB → 154.06 kB — so combined freezing + Adam + f16 reduces work memory to ~38% of the f32/Adam/no-freeze baseline.
- **Zfh FPGA overhead on a super-scalar out-of-order core (Section 3.2)**: adding all 36 Zfh instructions to the RV64GC NaxRiscv costs +1.15% LUT6 and +0.05% FF on a Xilinx XC7K325T-2FFG900C at 175 MHz, with **no degradation of the 175 MHz maximum operating frequency** — the lowest overhead figure the paper can point to for enabling f16 at the hardware level on this class of core.
- **Feature-coverage table (Table 1)**: among the five compared ODT frameworks ([11], [2], PULP-Trainlib [8], AIfES [13], and this work), only "Ours" satisfies all five of RISC-V support, full ODT, float16, batch≥1, and open-source; the previously strongest open options each miss one axis (PULP-Trainlib: batch=1; AIfES: no float16 / no RISC-V).
- **Projected VPU throughput**: with VLEN=64 and four lanes, a raw 4× speedup over scalar execution is expected for float16 operands — but this is a design projection, not a measured benchmark (see Limitations).

## Critical Assessment

- **Novelty**: Real but incremental. The Table 1 feature combination (RISC-V + full float16 ODT + batch≥1 + open-source) is genuinely unfilled in the prior art, and the Zvfh-on-super-scalar-out-of-order discussion is the first such open-source proposal (RISC-V² targets integer vector, Vicuna2 is a scalar in-order core, Ara2 implements full RVV but is a vector core rather than a single-core ODT target). However, the individual ingredients — AIfES as a base, NMSIS-DSP for kernels, NaN-boxing for float16 reuse of an f32/f64 FPU — are all standard; the contribution is integration, not a new algorithm or a new ISA.
- **Rigor — software**: Adequate for a 4-page conference paper but thin. The accuracy claim rests on four cells on two MNIST-family datasets with one architecture (an MLP). There are no CNNs, no transformers, no larger ImageNet-scale models, no timing/latency numbers, and no training-time (wall-clock) measurements at all — only final validation accuracy. Because the SW results come from the ISA Simulator, the "minimal performance degradation" claim is purely about model accuracy, not training speed, and the reader should not infer runtime benefits from the tables.
- **Rigor — hardware**: The Zfh numbers (+1.15% LUT6, +0.05% FF, 175 MHz unchanged on XC7K325T) are concrete and credible. The Zvfh VPU, by contrast, is **described but not evaluated** — Section 3.3 is architectural design discussion, and the conclusion explicitly states that "evaluating the performance gains brought by vector kernels on our VPU-enhanced NaxRiscv FPGA target" is future work. So the headline "4× speedup" is a VLEN/LMUL projection, not a benchmark.
- **Comparisons**: Table 1 is feature-presence, not performance — there is no head-to-head training-time or memory comparison against PULP-Trainlib or quantized-ODT baselines with numbers on both sides. The reader cannot tell from the paper whether float16 here is faster, slower, or comparable to a quantized-INT8 ODT scheme of the same footprint.
- **Stability claim**: "Minimal model performance degradation" is supported, but with Adam the f16-vs-f32 gap on MNIST is 0.54 points — within noise — and on FashionMNIST/Adam it is 0.29 points; the paper does not report variance or multiple seeds, so the "~0.7 points" ceiling is a single-run observation, not a confidence interval.
- **Significance**: Practical for the TinyML/edge-ODT community as a ready-to-use open-source starting point and as evidence that Zfh is cheap enough to be a default hardware feature; limited as a research result because the more interesting half (Zvfh VPU performance) is not yet measured.

## Strengths

- Cleanly fills a real gap: no prior open-source ODT framework had all five of RISC-V support, full float16 ODT, batch≥1, and open-source licensing simultaneously.
- The Zfh FPGA overhead numbers (+1.15% LUT6, +0.05% FF, no frequency loss) are exactly the kind of concrete silicon-cost evidence that hardware designers need to justify adding a feature, and they are reported on a real, targetable FPGA part with a named Vivado version.
- Honest scoping: the paper repeatedly separates what was measured (ISA-simulator accuracy/memory, Zfh FPGA area) from what was only designed (Zvfh VPU performance), and the conclusion names the missing evaluation as future work rather than implying it is done.
- The micro-op strategy for LMUL register grouping (split at issue/rename to foster out-of-order execution, while excluding instructions like vrgather.vv that would explode to (LMUL)² micro-ops) is a non-trivial, defensible architectural choice specific to the out-of-order setting.
- Layer-freezing support plus a PyTorch/TensorFlow model converter makes the framework immediately usable for the most realistic edge scenario — pretrain off-device, fine-tune on-device — rather than only from-scratch training.

## Limitations

- **The Zvfh VPU is designed but not benchmarked**: the 4× speedup is a VLEN/LMUL projection; no end-to-end training-time or kernel-cycle numbers are reported for the vector path. This is the single biggest gap relative to the title's "Co-Design" framing.
- **Software results come from the ISA Simulator**, not from silicon or even FPGA execution: there are no wall-clock training times, no real-memory (as opposed to model-size) measurements, and no power numbers.
- **Model and dataset coverage is narrow**: only MLPs (5-layer for from-scratch, 3-layer for transfer learning) on MNIST/FashionMNIST/EMNIST. No CNNs, no transformers, no ImageNet-scale data, so the "minimal degradation" claim is untested beyond small fully-connected nets where float16 is known to behave well.
- **No multi-seed variance** is reported for the accuracy comparison; the worst cell (MNIST/Adam, −0.54 points) is within plausible seed noise, so the precision parity is plausible but not statistically established.
- **No head-to-head performance comparison** with PULP-Trainlib or with quantized-INT8 ODT (e.g., [2]) — Table 1 is feature-presence only, so the practical advantage over alternatives is asserted, not measured.
- As a **4-page IEEE PRIME 2026 paper**, the depth on each track is necessarily limited; the VPU section is essentially a design sketch with no implementation results.

## Relevance

这篇论文对端侧学习(TinyML / On-Device Training)、RISC-V 生态和边缘 AI 硬件设计三条线都有直接价值:它给出一个开箱即用、可迁移到真实 RISC-V 单核的开源 float16 训练框架,适合作为在 MCU/FPGA 级设备上做微调与迁移学习的起点;它用具体的 FPGA 资源数据(+1.15% LUT6 / +0.05% FF、175MHz 不降)证明在超标量乱序核上把 Zfh 作为默认特性是低成本的,对芯片选型有参考意义;它讨论的 Zvfh VPU 架构(面向乱序核、LMUL 微操作拆分)对正在做 RISC-V 向量加速器的研究者也是有用的参考。需要量化对比或更大模型(CNN/Transformer)结果才能更深入引用的工作,应把这份论文定位为"框架 + 架构提案"而非完整的性能评测。

## Questions for Further Exploration

- Does the Zvfh VPU actually deliver the projected 4× over scalar on f16 training kernels once synthesized onto the XC7K325T — and at what area/frequency cost relative to the +1.15%/+0.05% Zfh baseline? This is the headline gap.
- How does float16 ODT hold up on larger or more sensitive architectures (CNNs on CIFAR/ImageNet, small transformers) where float16 is known to be less benign than on MLPs — is loss scaling or mixed precision needed, and can the AIfES extension support it?
- What are the real wall-clock training times and energy numbers on actual RISC-V silicon (or FPGA), as opposed to the ISA Simulator, and how do they compare head-to-head with PULP-Trainlib and with quantized-INT8 ODT schemes of comparable memory footprint?
- How sensitive are the Table 2 accuracy numbers to random seed? A multi-seed run with confidence intervals would establish whether the "minimal degradation" claim is statistically robust or within noise.
- Does the micro-op strategy for LMUL register grouping scale cleanly to LMUL=8, and how does it interact with the (LMUL)² pathological cases like vrgather.vv in practice — is there a threshold above which the design should switch from splitting to a dedicated handler?
- Can the layer-freezing + SGD + float16 combination push edge fine-tuning memory low enough for sub-megabyte MCU targets, and what accuracy does that configuration cost on harder transfer tasks?
