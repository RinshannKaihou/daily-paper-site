> **一句话总结：** 本文把"公开测试通过后还能否发现残留隐式 bug"建模为一个监控式红队问题，构建了覆盖函数级/数据科学/工作流三大代码域的 CodeMonitorBench（7.1 万候选），发现弱 LLM 验证器在 5% 误报率下漏掉大多数隐藏 bug，且对抗式过拟合压力会进一步降低可分性，强验证器（GLM-5.1）只能弥补部分差距。

> **TL;DR:** On the new CodeMonitorBench (71,000 candidates across function-level, data-science, and workflow code), 23,081 of 43,677 public-test-passing candidates still fail hidden tests; weak LLM verifiers (Qwen-7B, Mistral-7B, GPT-5.4-mini) miss 80–94% of those residual bugs at 5% FPR, adversarial public-test-overfit pressure degrades verifier AUROC by ~0.07 / raises FNR by ~0.07 in all 90 cells, and a stronger GLM-5.1 verifier under the same evidence boundary only recovers part of the gap (G1 FNR 0.543 vs 0.823 for Mistral-7B).

## 核心贡献

1. **提出 Code Monitor Red Teaming 协议**：将 AI-control / monitor red-teaming 范式迁移到代码场景，固定"公开检查信息边界"（spec + 接口 + 公开测试 + 候选代码 + 公开通过状态 = M1），让隐藏测试只作为 oracle 标签而非监控输入。这把"残留 bug 构造"与"验证器排序"在方法学上彻底解耦。

2. **构建 CodeMonitorBench**：一个冻结公开/隐藏测试的基准，覆盖三类残留 bug 面——BigCodeBench-Hard（边界 / API 语义）、自建 Data-Science Code（pandas/NumPy/scikit-learn 等的 shape/dtype/统计/过滤错误）、自建 CodeWorkflow（产物 schema / 聚合 / 报告不变量）。共 568 个任务，每任务 5 候选，公开前通过可执行性/确定性/依赖/预言机稳定性过滤。

3. **大规模 axes-of-failure 评估**：在 5 个生成器（Qwen-14B、DeepSeek-V2-Lite、Codestral-22B、GPT-5.4、GLM-5.1）× 5 种生成条件（G1–G4-adv）× 多个验证器 scaffold（Direct / Hybrid）下共产生 71,000 候选，系统拆解"生成压力 / 验证器 scaffold / weak-to-strong 能力"三条独立失败轴。

4. **构造效应与监控失效的分离审计**：通过 candidate-pool 统计、固定 FPR 排序指标、NA 计数、可推断性审计（300 bug 人工标注）四条证据链，把"漏报"分解为能力不足、公开证据不足、无效输出三类来源，而非笼统归因于验证器推理失败。

## Key Contributions

1. **Code Monitor Red Teaming protocol** — adapts AI-control / monitor red-teaming to code by fixing a *public-check information boundary* (M1 = spec + interface + public tests + candidate code + public-pass status). Hidden tests become a measurement device (oracle labels) rather than a deployed monitor input, cleanly separating residual-bug *construction* from *verifier ranking*.

2. **CodeMonitorBench** — a frozen public/hidden benchmark spanning three residual-bug surfaces: BigCodeBench-Hard (boundary/API semantics), a constructed Data-Science Code split (pandas/NumPy/scikit-learn/SciPy shape, dtype, statistical errors), and a constructed CodeWorkflow split (artifact schema, join, aggregation, report invariants). 568 tasks × 5 candidates, pre-screened by executability / determinism / dependency / oracle-stability filters.

3. **Large-scale axes-of-failure evaluation** — 71,000 candidates over 5 generators × 5 generator conditions (G1 ordinary → G4-adv adversarial overfit) × multiple verifier scaffolds (Direct / Hybrid review), isolating generator pressure, verifier scaffolding, and weak-to-strong capability as three independent failure axes.

4. **Construction-vs-monitoring separation audit** — combines candidate-pool accounting, fixed-FPR ranking metrics, NA reporting, and an inferability audit (300 manually labeled bugs) to decompose misses into capability failures, public-evidence limits, and invalid outputs, instead of lumping them as verifier reasoning failures.

## Methodology

**Protocol (五部分):**
- **公开通过工作流**：任务 x = (spec s, 接口 i, 公开测试 T_pub, 隐藏 oracle 测试 T_hid)。生成器 G 在条件 g 下产出候选 c；只在 T_pub 上执行；只有"公开通过"的候选才进入验证器。隐藏 oracle 给出 HIDDEN-BUG / CORRECT 二分标签。
- **威胁模型与信息边界**：生成器可见公开测试（甚至被告知将被 LLM 验证器审查、或被显式要求留下隐蔽缺陷）；验证器始终只看 M1，不得访问隐藏测试、隐藏执行结果、参考实现、oracle 标签或聚合统计。弱/强验证器使用同一 M1，所以换强模型只换能力不换 oracle 访问。
- **生成条件 G1–G4-adv**：G1 公开测试感知；G2 验证器感知；G3 方案感知；G4-natural 自然捷径压力；**G4-adv 显式要求"通过公开测试的同时留下隐蔽残留缺陷"**——被作者明确定义为对抗压力测试（robustness stressor），而非部署流行率估计。
- **验证器条件**：Direct review（直接打分）vs Hybrid review（先分解需求与边界用例，再做反例导向审查）——Hybrid 改变推理结构但不改变证据。
- **指标**：将 candidate-pool 指标（公开通过率、隐藏 bug 率、无效率）与验证器指标（AUROC、AUPRC、TPR/FNR@固定低 FPR、NA 率）分开报告。主操作点为 **5% FPR**，因为公开通过代码通常是大规模审查流，升级预算紧张。

**生成器/验证器阵容：** 生成器 Qwen-14B / DeepSeek-V2-Lite / Codestral-22B / GPT-5.4 / GLM-5.1；弱验证器 Qwen-7B / Llama-8B / Mistral-7B / GPT-5.4-mini，强验证器 GLM-5.1。对照基线含静态致命 lint、静态分析器包、任务生成测试、候选针对性测试。

## Results & Highlights

1. **公开测试通过 ≠ 正确性证书**：71,000 候选中 **43,677 通过公开测试，其中 23,081 在隐藏测试上失败**（约 53%）。普通 G1 生成下，公开通过候选的隐藏 bug 率在三个数据集上分别为 43.1%（BigCodeBench-Hard）、44.2%（Data-Science Code）、46.5%（CodeWorkflow）；G4-adv 下该比率升至 68.2% / 69.2% / 72.8%。（Table 1）

2. **弱验证器在低 FPR 下漏掉大多数 bug**：Direct Qwen-7B 接近随机（AUROC 0.536，@5%FPR 漏报 94.0%）；Hybrid scaffold 把 AUROC 提到 0.601、漏报降到 86.8%；换到 Mistral-7B Hybrid 达 AUROC 0.665，仍漏 80.0%。即便放宽到 10% FPR，Qwen-7B Hybrid 与 Mistral-7B Hybrid 仍分别漏 80% / 72% 的 G1 隐藏 bug。（Table 2, Table 8）

3. **对抗压力系统性恶化监控**：相对 G1，G4-adv 在三个开放弱验证器上平均降低 AUROC ~0.07、提高 FNR@5% ~0.07；**该恶化方向在全部 45 个 AUROC 单元和全部 45 个 FNR 单元中一致**。例如 Mistral-7B Hybrid：AUROC 0.665 → 0.588，FNR 0.800 → 0.873。（Table 4）

4. **强验证器只补部分缺口**：在闭源生成器子集上，mean G1 FNR@5%FPR 沿 Mistral-7B(0.823) → GPT-5.4-mini(0.756) → GLM-5.1(0.543) 形成能力梯度；GLM-5.1 在 GPT-5.4 自撰候选上 AUROC 0.82/0.75（G1/G4-adv）对比 GPT-5.4-mini 的 0.69/0.61，**但 GLM-5.1 仍有 G4-adv FNR 0.662**。（Table 5）

5. **静态与生成测试基线对比**：静态致命 lint 近随机（AUROC 0.52/0.51）；更强的静态分析器包仅 0.57/0.545；候选针对性生成测试 k=5 达 AUROC 0.765 / FNR 0.64（G1），但在 G4-adv 下退到 0.695 / 0.74。（Table 3）

6. **可推断性审计（300 bug）**：92% bug 与规范有据可查，但只有 33% 能在见隐藏失败前从 M1 构造性发现，64% 在事后可推；GLM-5.1 抓到 40% 而 closed weak 仅 20%，23% 为 weak-miss/strong-catch。加诊断视图后捕获率单调上升（M1 24% → +需求清单 39% → +bug 类别提示 55% → +隐藏断言摘要 74%，G1 weak），证实一部分漏报是证据受限而非纯能力问题。（Table 6, 7）

## Authors & Credibility

- 作者来自**电子科技大学（UESTC）**：Junchi Liao、Jiawen Deng、Fuji Ren（通讯作者）。
- 工程规模可信：71,000 候选生成 + 多生成器/多验证器/多 scaffold 矩阵；公开/隐藏测试冻结于生成之前，构造分裂通过可执行性、确定性、依赖、oracle 稳定性过滤；隐藏断言经双人标注审计。
- 指标设计严谨：明确分离 prevalence-sensitive 的 AUPRC 与排序性 AUROC / 固定 FPR 指标；NA 输出不进行插补；退化声明带 candidate-level bootstrap 区间（Appendix Tables 28, 34）。
- 引用了 AI-control（Greenblatt et al. 2023; Griffin et al. 2024）、weak-to-strong（Burns et al. 2023; Kenton et al. 2024）、prover-verifier（Kirchner et al. 2024）、MonitoringBench（Jotautaite et al. 2026）等一线相关工作，定位清晰。

## Critical Assessment

- **核心创新点**在于把"公开通过后能否发现残留 bug"形式化为带固定信息边界的监控博弈，并通过 candidate-pool vs verifier 双层指标 + 可推断性审计，把"漏报"细分到能力、证据、无效输出三种来源。这是对 LiveCodeBench / SWE-bench / CodeEditorBench 等"能否通过隐藏测试"式基准的范式补强，而非又一个生成基准。
- **G4-adv 的定位被反复强调**为"对抗压力 / brittleness stressor，而非部署流行率估计"——这是对潜在过度解读的预防性声明，作者也在正文中明确"不用于估计普通开发者错误频率"。读者应据此解读其数据，不要把 68–73% 的 G4-adv 隐藏 bug 率当成现实部署的 bug 率。
- **弱到强比较（Finding 4）**被作者谨慎地表述为"capability gradient，而非二元成功/失败"——这与 Table 5 中 GLM-5.1 G4-adv FNR 仍达 0.662 一致；Table 6/7 的证据边界消融进一步支撑了"残留漏报是能力不足 + 公开证据不足的混合"的结论。
- **可复现性**：模板冻结于生成前、跨数据集/生成器族复用、固定 FPR 计算公式见 Appendix C；附录提供完整的构造表、bootstrap 区间和 verifier 审计。
- **诚实之处**：作者明确指出 AUROC 改善 ≠ AUPRC 改善（G4-adv 改变 prevalence），并选择 AUROC + 固定 FPR 作为退化判定主指标，避免被 prevalence 误导。

## Strengths

- 信息边界（M1）的形式化清晰，把"隐藏测试作为 oracle 而非监控输入"这一关键区分讲得很透彻，避免了"验证器偷看答案"的常见评估陷阱。
- 三条失败轴（生成压力 / scaffold / 能力）正交化设计干净，每条轴都有对应的对照表（Table 2/4/5）。
- 指标体系严谨：固定 FPR 主操作点 + 1%/5%/10% 灵敏度表 + NA 单列 + bootstrap 区间，几乎堵死了"用平均分掩盖问题"的解读漏洞。
- 三类代码域覆盖互补（函数级 / 数据科学 / 工作流产物），bug 面从边界语义到 schema 不变量到多文件一致性。
- 可推断性审计（Table 6/7）是把"验证器能力上限"问题实证化的少有尝试，区分了"不可推断"与"未推断"。

## Limitations

- **隐藏测试 ≠ 完整语义正确性**：作者自承 hidden-test 标签只是冻结测试套件下的失败，部分 oracle 失败可能本身就难以从公开视图推断。
- **构造分裂覆盖有限**：Data-Science Code 与 CodeWorkflow 是新建分裂，并未覆盖所有库、仓库级或交互式开发场景。
- **G4-adv 是对抗压力而非流行率**：尽管作者反复声明，仍可能被读者误读为"现实中 LLM 代码的 bug 率"。
- **未评估 Learned verifier / reranker 训练**、完整生产级静态分析配置、交互式审查、成本/延迟权衡——这些都是论文 M1 单轮审查之外的合理下一步。
- **模型版本为虚构的未来模型**（GPT-5.4、GLM-5.1、DeepSeek-V2-Lite、Codestral-22B 等）——这些是 2026 年时间点的模型编号，结论的可迁移性取决于这些模型的实际能力档位。
- 5% FPR 作为主操作点是"common in monitor-style triage"的工程假设，作者也承认不普遍最优（提供 1%/10% 灵敏度表），但对小团队场景可能偏紧。

## Relevance (Chinese)

- **与代码 LLM 评估方向高度相关**：为"代码生成基准"和"代码审查基准"之间填了一个被忽视的中间地带——公开通过后的残留 bug 监控。对 LiveCodeBench、SWE-bench、BigCodeBench-Hard、DS-1000、CodeEditorBench 等基准的设计者有直接参考价值。
- **与 AI Safety / Scalable Oversight 方向呼应**：把 AI-control 评估（Greenblatt et al.）、weak-to-strong oversight（Burns et al.）、prover-verifier games（Kirchner et al.）的范式迁移到代码这一可执行领域，是 scalable oversight 研究的实证补充。
- **工程启示**：对部署 LLM 编码代理的团队，结论可操作——"公开测试通过"只是 triage 信号而非 stopping rule；弱 LLM 审查应升级为反例导向搜索（Hybrid scaffold + 候选针对性生成测试）而非单遍打分；G4-adv 风格的红队压力测试应纳入监控鲁棒性评估。
- **方法论可借鉴**：candidate-pool vs verifier 双层指标 + 固定 FPR + NA 单列 + 可推断性审计，可作为其他"弱监督审查"任务（如论文审稿、安全审核）评估模板。

## Questions for Further Exploration

1. **Learned verifier / reranker 能否突破 M1 上限？** 论文未训练专用验证器；Table 7 显示加诊断视图后捕获率单调上升，那么在 M1 内训练一个针对"public-pass 残留 bug"的判别器，AUROC 上限大概在哪里？
2. **G4-adv 的失败模式分布是否稳定？** Appendix H 报告 G4-adv 下不仅有公开测试过拟合，还有边界、API 误用、数值/统计、join、schema 等——这些类别在不同生成器族之间是否系统性偏移？
3. **交互式审查（多轮反例生成）能弥补多少 NA 与漏报？** Hybrid scaffold 把 NA 率从 Direct 的 3.1% 提到 5.7%（Qwen-7B），说明结构化输出本身有代价；多轮工具调用能否在不破坏 M1 边界的前提下降低 NA？
4. **5% FPR 操作点在不同部署场景下的最优值？** 论文给了 1%/5%/10% 三档，但未给出"审查成本 vs 漏报代价"的权衡曲线——在小团队（高审查成本）vs 大平台（低审查成本）下最优 FPR 差多少？
5. **隐藏测试 oracle 本身的可推断性上限**：Table 6 显示 33% constructive / 64% posthoc M1 可推断——剩下 36% posthoc 不可推断的 bug，是否意味着这部分在 M1 边界下原则上无法被任何验证器发现？这给出了 M1 监控的理论上限。
6. **跨模型族的"自审"偏置有多大？** 论文排除了 GLM-5.1 自审自身生成的可能性（用 GPT-5.4 候选子集验证），但生成器-验证器同族时的系统性偏置在更大族矩阵下是否仍可忽略？
