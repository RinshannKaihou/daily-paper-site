> **一句话总结：** 本文将 PTME（精度 P / 时间 T / 峰值内存 M / 能耗 E）四维硬件级实测框架引入轻量级 LLM 的本地推理评测，覆盖 6 个 1B–7B 量化模型、3 个基准、5 个边缘级资源封套，证明参数量/FLOPs/加载内存等静态代理只能预测"成本"而完全无法预测"精度"，并基于 Pareto 前沿给出了边缘场景下"中等模型（Qwen2.5/Phi-3）最优"的实证选型指南。

> **TL;DR:** On a CPU-only desktop mimicking 5 edge-class resource envelopes (E1: 1 P-core @ 1.5 GHz / 5 GB → E5: 8 P-cores @ 2.5 GHz / 16 GB), the authors run 6 quantized lightweight LLMs (TinyLlama-1.1B … Mistral-7B) via Ollama v0.23.2 on HumanEval / GSM8K / MMLU-Pro and directly measure Precision, Time, peak RSS Memory, and Intel-RAPL Energy. Static proxies (params, FLOPs, loaded memory) correlate strongly with cost (Pearson R ≈ 0.95–1.0, loaded-memory-vs-RSS R ≈ 0.998–1.0) but weakly with precision (R ≈ 0.36–0.48); a four-objective Pareto analysis shows no single model dominates—e.g., Qwen2.5-1.5B matches or beats Mistral-7B on HumanEval/GSM8K at roughly one-third the time and energy; tightening the envelope leaves precision invariant but inflates time/token ~5.3–6.3× more than energy/token (~2.7–3.5×), penalizing the largest model most.

## 核心贡献

1. **将 PTME 框架系统化引入轻量级 LLM 部署评测。** 把精度（P）、端到端时间（T）、峰值驻留内存（M）、CPU 包能耗（E）作为四个一阶指标同时直接测量，明确反对"参数量/FLOPs/单独延迟"等代理指标作为部署决策依据。
2. **三个研究问题的实证回答：**
   - **RQ1**：静态代理可以一阶近似推理**成本**（时间/内存/能耗），但**无法预测精度**——这是论文反复强调的核心发现。
   - **RQ2**：固定资源封套下没有任何单一模型在所有 PTME 维度占优；四目标 Pareto 前沿揭示了被"只看精度"或"只看效率"评估所掩盖的非支配配置。
   - **RQ3**：收紧资源封套会推高物理成本但不改变精度；延迟被放大的程度强于能耗；大模型受惩罚最重。
3. **可复现的实验协议与 Pareto 决策工具。** 给出基于 Docker + `cpupower` 的资源封套施加方法、Intel RAPL 能耗窗口测量、温启动丢弃 + 冷却间隔的噪声抑制，以及 paired 非参数统计检验（Cochran's Q / McNemar / Friedman / Nemenyi，α = 5%）。代码与数据公开于 `https://github.com/tharada0126/llm_ptme.git`。

## Key Contributions

- **Operationalizes the PTME framework** (Precision, Time, peak Memory, Energy) for lightweight-LLM inference via direct hardware-level measurement (wall-clock, peak RSS, Intel RAPL CPU-package counters), with accuracy evaluated strictly outside the measurement window to avoid interference.
- **Empirically settles three research questions.** (i) Static proxies (params, FLOPs, loaded memory) approximate *cost* (R ≈ 0.95–1.0) but not *precision* (R ≈ 0.36–0.48). (ii) Under a fixed envelope, no model dominates on all four PTME axes; a four-objective Pareto front exposes non-dominated configurations hidden by single-metric rankings. (iii) Tightening the envelope leaves precision invariant (deterministic decoding) but inflates cost—latency more than energy, largest model penalized most.
- **Reproducible protocol and decision-support tooling.** Docker-enforced CPU-set / memory / frequency caps reproduce edge-class envelopes E1–E5 on one desktop; paired non-parametric statistics (Cochran's Q, McNemar, Friedman, Nemenyi at 5%) handle matched binary/continuous outcomes. Code/data released at `github.com/tharada0126/llm_ptme`.

## Methodology

**模型与基准。** 6 个量化轻量级 LLM（默认 Ollama 量化）：TinyLlama-1.1B (Q4_0)、Qwen2.5-1.5B (Q4_K_M)、Gemma-2B (Q4_0)、Phi-2 2.7B (Q4_0)、Phi-3-mini 3.8B (Q4_0)、Mistral-7B (Q4_K_M)。三个基准覆盖代码生成（HumanEval, pass@1, 全部 164 例）、数学推理（GSM8K, exact-match, 随机抽样 200/1319）、多任务理解（MMLU-Pro, 选择题准确率, 每类抽 20 共 280/12032）。子采样把约 200 天的全量评测压到约 7 天。

**PTME 指标定义。** P = 正确样本占比；T = `t_end − t_start` 含 prompt 处理与自回归解码；M = `[t_start, t_end]` 区间峰值 RSS（含子进程）；E = `E_pkg(t_end) − E_pkg(t_start)`，由 Intel RAPL CPU 包域计数器读取。T、E 按总 token 数归一化，TTFT 按输入 token 归一化。

**资源封套设计。** Intel Core i7-12700K（8 P-core + 4 E-core，64 GB DRAM，Ubuntu 24.04，CPU-only）上用 Docker `--cpuset-cpus` / `--memory` 与 `cpupower frequency-set` 模拟 5 个边缘封套：E1（1 P-core @ 1.5 GHz, 5 GB）到 E5（8 P-core @ 2.5 GHz, 16 GB），对应从低端 SBC 到笔记本级设备。Ollama 线程数 = 分配 P-core 数。

**测量流程。** 每个配置 (model, dataset, envelope, decoding) 丢弃一次温启动、固定冷却间隔、贪心解码（temperature = 0）。Algorithm 1 描述 PTME 测量，Algorithm 2 描述 Ollama 推理调用，Algorithm 3 描述数据集特定的精度判定（HumanEval 跑隐藏测试，GSM8K 抽末尾数字精确匹配，MMLU-Pro 取选项匹配）。多模型比较用 Cochran's Q + McNemar（精度）与 Friedman + Nemenyi（连续指标），显著水平 5%。

## Results & Highlights

1. **代理指标对成本预测强相关、对精度预测弱相关（RQ1, Table VII）。** 在 E1–E5 所有封套中，参数量/FLOPs/加载内存与 T/tok、M、E/tok 的 Pearson R 在 0.95–1.0 之间（加载内存 vs 实测内存高达 R ≈ 0.998–1.0）；但与精度的 R 仅 0.357（参数）、0.358（FLOPs）、0.481（加载内存），Spearman ρ ≈ 0.524。结论：代理可以筛模型，但不能判断模型够不够准。
2. **小模型反超大模型——单点最能说明问题（Table V, E1 HumanEval）。** Qwen2.5-1.5B 取得 48.8% pass@1，耗时 25.81 s、能耗 520.06 J；Mistral-7B 仅 42.7%，耗时 131.49 s、能耗 3372.01 J。也就是说 Qwen2.5 同时更准、快 5.1×、省能 6.5×。GSM8K 上 Phi-3-mini 最优（66.5% vs Mistral 仅 29.0%）。
3. **四目标 Pareto 非支配集随任务而变，单指标评估会选错模型（Table VIII）。** 非支配集：HumanEval = {TinyLlama, Qwen2.5}；GSM8K = {TinyLlama, Qwen2.5, Phi-3}；MMLU-Pro = {TinyLlama, Qwen2.5, Phi-3, Mistral}。在 MMLU-Pro 上 Qwen2.5 以 28.2% 精度达到 Mistral（34.6%）约 1/3 的时间与能耗，且二者精度差异在统计上不显著，因此"最大模型"在很多边缘场景并非最优选择。
4. **收紧资源封套放大延迟强于能耗（RQ3, Fig. 6）。** 平均而言 E1 相对 E5 的 token 归一化时间为 5.3–6.3×、TTFT 为 4.8–8.1×，但 token 归一化能耗仅 2.7–3.5×，说明更宽封套在更高平均功率下运行；同时精度在所有封套下完全相同（验证贪心解码的确定性）。这意味着优化延迟 ≠ 优化能耗，且边缘部署存在"能量预算变小、单次推理能耗变大"的双重负担。
5. **大模型受封套收紧惩罚最重。** 从 3D 轨迹（Fig. 7）可见，TinyLlama 与 Qwen2.5 始终聚集在低成本区，而 Mistral 随封套收紧急剧向高成本区漂移，可能在边缘条件下抵消其精度优势。

## Critical Assessment

- **核心论点证据扎实。** "代理预测成本但不预测精度"在单一封套内即成立（Fig. 2 中精度散点 vs 成本拟合线的鲜明对比），且 Spearman ρ 仅 0.524 进一步说明即便排序信息也很弱；该结论对 6 个跨家族模型均成立，具有说服力。
- **MMLU-Pro 子采样偏激进。** 每类 20 题共 280 题的子集，配合 1B–7B 这种精度本就较低（最高 34.6%）的轻量模型，单题差异即影响约 0.36 个百分点，使精度统计比较的置信度受限——作者也承认目标是趋势分析而非细粒度排名，并以 Polo et al.[30] 的 ~2% 估计误差作为辩护，但 MMLU-Pro 的 10 选项难度比原 MMLU 更吃样本量。
- **Mistral 在 MMLU-Pro 仅比 Qwen2.5 高 6.4 个百分点就被判为"统计不显著"。** 280 题的样本对中等效应量的检验功效确实有限，"非显著 = 等价"的解读偏乐观。
- **资源封套是"桌面 + Docker 约束"而非真实边缘硬件。** 作者明确把结论限定为相对趋势，且 RQ3 的封套敏感性应解读为"在该平台上对收紧资源的响应"，不外推到具体设备——这种克制是恰当的，但读者需注意。
- **能耗仅覆盖 CPU 包域。** RAPL 排除了 DRAM、存储、外设与潜在 GPU；在纯 CPU 评测下这是合理主导项，但论文结论"directly measuring energy"在系统级能耗意义上并不完整。
- **单一推理后端 + 单一解码配置。** Ollama v0.23.2 + temperature = 0 保证了可比性，但也限制了向 vLLM/llama.cpp 或采样解码的外推；FLOPs 用 THOP 在 [1,128] 单 forward 估算，与实际自回归总成本不可直接比较，作者已声明。

## Strengths

- 把"精度"作为一阶维度与物理资源同列，避免了 Green AI 文献常见的"能耗 vs 准确率"二选一陷阱。
- 四目标 Pareto + 配对非参数统计（Cochran's Q/McNemar/Friedman/Nemenyi）给出了方法学上的严谨比较框架，远胜常见的"表里 bold 一个最大值"做法。
- 5 个封套的系统性收紧设计（核心数 / 频率 / 内存）使得 RQ3 的"封套敏感性"成为真正可量化的发现，而非泛泛而谈。
- 全栈可复现：固定 Docker 软件栈 + 运行时硬件约束 + 公开代码 + Supplementary 完整 PTME 表 + Spearman 补充，质量高于一般 workshop/preprint。
- "延迟被放大大于能耗"与"边缘部署双重能耗负担"是有反直觉价值的实务洞察。

## Limitations

- 桌面 + Docker 模拟 ≠ 真实手机/SBC/嵌入式设备；ARM、不同 ISA、不同内存带宽未被覆盖。
- 仅 CPU 推理，未涵盖日益普遍的 GPU 边缘设备（Jetson、NPU、Apple Silicon）——在这些平台上时间、能耗、内存行为会显著不同。
- Intel RAPL 仅 CPU 包域，缺系统总能耗；DRAM、主板、外设能耗未计入。
- 模型集合有限（6 个，全为 ≤7B），未触及 7B–13B 或 MoE 轻量模型；任务集仅三个客观可判定的基准，未覆盖开放生成、Agent、多轮对话。
- 单一后端（Ollama）、单一量化策略（默认 Q4）、单一贪心解码，未探索更优量化（Q5/Q8/FP16）或采样对 PTME 的影响。
- 未给出对"封套收紧导致平均功率上升"的根因拆解（频率？缓存？内存带宽？），机理分析偏弱。

## Relevance (Chinese)

- **对端侧/本地 LLM 部署的直接指导意义。** 随着推理负载从云端向 PC 与边缘迁移，能耗、延迟、内存成为硬约束。本文给出的实证（中等量化模型 Qwen2.5/Phi-3 在边缘封套下性价比最高）可直接服务于本地推理产品选型、嵌入式 LLM 工程与绿色 AI 决策。
- **方法学价值高于单一数值结论。** PTME 四维 + Pareto + 配对统计的评测范式可迁移到模型压缩（量化/剪枝）、推理引擎对比（llama.cpp/vLLM）、硬件对比（ARM/x86/NPU）等更广场景，是一份可复用的评测蓝图。
- **与可持续 AI / 碳足迹议程强相关。** 论文承接 Strubell 2019、Green AI、Henderson 2020 的脉络，把"推理期能耗"放在与训练期同等重要的位置，对接企业 ESG 与监管侧的能耗披露需求。
- **对本仓库（arxiv-daily）的读者画像（LLM/边缘/能效研究者）契合度高**，是一篇工程友好、可被立即复现与扩展的工作。

## Questions for Further Exploration

1. 在 ARM（如 Raspberry Pi 5、Snapdragon）或 NPU（Jetson Orin、Apple Neural Engine）上，PTME 四维的相对排序与 Pareto 前沿是否会重塑？时间-能耗解耦现象是否仍然成立？
2. 若能耗改测系统级（含 DRAM、存储、外设），"延迟放大大于能耗"的结论是否会被逆转？RAPL CPU 包域能在多大程度上代表总能耗？
3. 不同量化精度（Q5_K_M / Q8_0 / FP16）与不同后端（llama.cpp、vLLM、MLC-LLM）下的 PTME 表现如何？默认 Q4 的选择是否掩盖了精度-能耗的更优折中点？
4. GSM8K 上 Qwen2.5（53.5%）与 Phi-3（66.5%）的差距在更大样本下是否显著？MMLU-Pro 280 题的检验功效是否足以支撑"非显著 = 等价"的部署建议？
5. 采样解码（temperature > 0）下，精度本身成为随机变量，PTME 的方差结构与贪心解码有何不同？是否需要引入 E[pass@k] 这类指标？
6. 在多轮对话 / Agent / 长上下文场景中，TTFT 与 per-token 成本的主导关系会如何变化？KV-cache 内存是否会成为新的非支配约束？
7. "封套收紧 → 平均功率上升"的机理是什么？是频率、缓存命中率、还是内存带宽瓶颈？是否可以通过调度策略部分缓解？
