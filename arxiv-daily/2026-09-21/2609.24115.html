Why this matters为何重要

Shifts agent testing from tool-call syntax to database-state and policy compliance — a reusable recipe for training-data mix and edge-case evaluation design.

Critical edge审慎一面

The headline metric is LLM-judged — the paper’s own audit finds only 40–60% of judged “successful” runs actually correct, with no significance testing.

作者自证：10 个被判「成功」的 airline 运行仅 6 个复核正确。相对比较可信（共享同一裁判），强模型上的小幅绝对增益可能落在裁判噪声区间。

Methodology方法

A closed loop from policy document to verified test case; each task is the tuple ⟨q, w, A, S⟩ — task, tool workflow, assertions, violated rules.

  1. Rule extraction — an LLM pulls the top-5 atomic compliance rules from the policy doc P (audited F1 93.3% vs human annotation).
  2. Tool-graph sampling — builds a resource-compatible tool DAG; samples a workflow as NODE / CHAIN / DAG.
  3. Violation enumeration — takes the rule power set (≤ 2⁵ = 32 subsets); an LLM consistency filter drops incompatible combos. |S|=0 is a happy path.
  4. Database grounding — an iterative SQL agent samples a synthetic DB state satisfying the scenario; the DB itself is generated by a “Generalist Populator” agent.
  5. Dual verification — deterministic-SQL data grounding (no hallucinated IDs) + feasibility check (expected denial achievable); failures are discarded and the pipeline restarts.

Training loop. gpt-5.4 expert trajectories (only perfect runs, 120 attempts/benchmark) → LoRA SFT (rank 64, 3 epochs). The same scenarios also drive evolutionary harness optimization (system-prompt / docstring mutation) for black-box models. Evaluated with TED (gpt-4.1 judge), 8 trials per scenario.

Strengths优势

  • Real gap. Enterprise agents fail on policy/state-dependent refusals, not call syntax; prior synthetic generators ignore both DB state and compliance rules.
  • Verification measurably works. 0% final-task rejection vs 20–90% for adapted baselines, with concrete hallucination examples shown (fabricated airport codes, reused reservation IDs).
  • Unusually broad sweep. 6 open models (3B–35B, dense & MoE) × 3 benchmarks × 5 data conditions, plus a black-box harness use case (gpt-5.4 / gpt-4o-mini).
  • Above-norm candor. Publishes its own judge-error rates, the non-monotonic ablations, and which ablations fail to isolate components.
  • Cheaper at inference. The EdgeGen harness learns a generic discover→verify→confirm→write protocol instead of hard-coded rules — fewer tool calls and tokens.

Limitations局限

  • Metric fragility. Only 40–60% of LLM-judged “successes” verified correct; 10–15 held-out scenarios per benchmark, no error bars or significance tests.
  • Gains concentrate on small models. Marginal or mixed for Qwen3.5-9b/35B and gpt-5.4 (the harness even trails human-curated optimization by 2–4% on gpt-5.4).
  • Brittle complexity curve. 2-violation training drops Qwen2.5-3B below base (0.24 vs 0.35); scaling to 60 tasks shows validation–test divergence.
  • Coverage ceiling. Capped at top-5 rules (≤32 subsets) — won’t scale to enterprise policy sheets; requires a formal policy doc; coding/web agents untested.
  • Expensive & closed-model-coupled. 144.3 s + ~22.6k tokens per task (vs 0.8 s naive), ~180 B200 GPU-hours; experts and judge are proprietary frontier models.

Questions for further exploration探索问题

  • Can rule enumeration scale beyond 5 rules to enterprise policy sheets — constraint solvers or symbolic feasibility checks instead of LLM filters?
  • How much of the judged gain survives human re-annotation — would final DB-state diffs replace the LLM judge?
  • Why is |S|=2 actively harmful for Qwen2.5-3B but neutral-to-positive for Qwen3.5-4b — data volume, curriculum, or assertion ambiguity?
  • Do the gains transfer to RL or preference optimization, and does the verify-then-write protocol emerge without harness co-optimization?
  • Does the pipeline work where policy is implicit in documentation — coding agents, web navigation?
  • Can synthetic validation be made an unbiased estimator of human-curated test performance (the n=60 divergence)?
