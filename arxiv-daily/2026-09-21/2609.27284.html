Why this matters

Fine-grained MoE sparsity plus a dual-mode reasoning switch approaches 2×-active models on math and agents — an open-weights reference for efficient LLM design.

Weights are released; quantization (W4A16 / W8A16 / KV-FP8) and vLLM / SGLang / TensorRT-LLM recipes are documented.

Critical edge — before you adopt

Four winning benchmarks are internal and unverifiable, and the throughput claim ships with no baseline — the efficiency narrative is only half-substantiated.

Also undisclosed: GPU-hours, quantized-accuracy tables, safety-eval numbers, per-mode latency.

01

How it’s built

4 moves
A · Sparse backbone

Fine-grained MoE: 1 shared + 64 routed experts, 8 active per token; GQA (32 query / 8 KV heads), SwiGLU, 128K vocab, 256K context. Ablation note: zero shared experts clearly hurts; more than one gives diminishing returns.

B · Pretrain — 20T tokens, 3 stages

Foundation (20T @ 4K ctx) → fast annealing (300B @ 8K, LR ↓ 8e-6) → NTK-aware RoPE long-context (32K at α=50, then 256K at α=1000). Plus +250B curated STEM tokens with difficulty grading.

C · Post-train — 4 stages

Reasoning SFT (math / code / logic / science) → GRPO RL with verifiable rewards only (36-language sandbox, >1000 concurrent runs, 150K prompts, multiple-choice excluded, KL constraint dropped) → all-scenarios SFT (8 domains, five-role agent data engine) → all-scenarios RL with generative reward models (16 sub-topics, 30+ scoring services).

D · Dual-mode serving

Same weights, two gears: /think full CoT (default) vs /no_think empty think-block. Served via vLLM / SGLang / TensorRT-LLM with TP / EP / FusedMoE.

03

Strengths

  • Open-weight sweet spot: 13B active makes single-GPU / low-latency deployment realistic while 256K context and 80B capacity are retained — a rare spot in the landscape.
  • Agent wins on third-party benchmarks: BFCL v3, ComplexFuncBench, C³-Bench all clearly ahead — not just internal suites.
  • Graceful long-context decay: only ~2.8 RULER-QA points lost into 64K–128K, vs ~6.4 for Qwen3-A22B — the RoPE schedule seems to work.
  • Verifiable-reward discipline: multiple-choice excluded, sandbox execution, unit/format normalization — lower reward-hacking risk than verbal rewards.
  • Practical deployment story: quantization formats, mainstream engines, parallelism docs, a written /think–/no_think API contract.
04

Limitations

  • Coding is the weakest axis: LiveCodeBench 65.9 vs 70.7 (slow), 27.4 fast; FullStackBench 67.8 vs DeepSeek-R1’s 71.6.
  • Internal-benchmark reliance: LengthCtrl / InsCtrl / ComplexNLU / Word-Task / ArtifactsBench are not yet publicly verifiable.
  • Efficiency story half-told: no per-mode latency or cost, no throughput baseline, no quantized-accuracy tables, no compute disclosure.
  • Year-to-year math variance: AIME2025 (76.8) trails even in the strongest domain — small-active models are brittle here.
  • Asserted, not ablated: KL removal, 2:2:1:1 domain mix, 250B STEM boost, one-shared-expert rule are qualitative; no safety evals despite a safety RL track.
05

Questions for further exploration

  1. How much of the BFCL v3 advantage comes from the five-role agent data engine vs the sandbox reward — is there an ablation separating data from RL?
  2. What is the measured latency and cost per token of fast vs slow thinking — and could a learned router match slow-mode accuracy at fast-mode cost?
  3. Does KL-free GRPO stay stable on open-ended all-scenarios tasks, or does reward hacking re-emerge outside the four reasoning domains?
  4. How do W4A16 / W8A16 / KV-FP8 quantizations actually affect AIME / GPQA accuracy, given “lossless” is claimed without a table?
  5. Can the 73.9 RULER retention hold at 256K with α=1000, and what does long-context retention cost on short-context benchmarks?
  6. Will Tencent release the missing Qwen3-A22B baselines (CRUX-I, CMATH) and the ArtifactsBench harness for independent verification?
