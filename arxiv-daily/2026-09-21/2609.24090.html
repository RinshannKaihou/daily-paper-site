Methodology· 方法 · distilled

  1. Task facts. Every value is a versioned tuple — fingerprint, validity predicate, status ∈ VALID / RENEWED / INVALID. Large artifacts live behind content digests, so change is detected at field granularity without copying payloads.
  2. Step contracts. Each step binds inputs, preconditions, outputs, a field-level dependency mask Mi, a machine-executable equivalence criterion Ei, and a version. Masks come from static analysis, read/write tracing, perturbation, or human declaration.
  3. Invariant domains (Alg. 1). Constrained perturbation + boundary search inside a side-effect-free sandbox (shadow DBs, digital twins) yields a conservative reuse region with confidence ci. Domains are bound to component/contract/criterion versions — any bump forces revalidation.
  4. Change chain + equivalence barrier. An inverted field index finds consumers; a three-condition check plus on-site source re-read issues a renewal record without re-invoking the component; otherwise only masked-affected fields re-execute. If old &8801; new under Ei, propagation stops.
  5. Submission-time gate. Payments and irreversible writes re-read permission/version facts at commit: the version delta must be empty or covered by equivalence evidence or a still-valid domain. Computation being fresh ≠ action being safe.

Strengths· 优势

  • Targets a real, expensive deployment problem: blind downstream invalidation wastes LLM calls, tool calls, and latency on semantically irrelevant perturbations.
  • Contract-equivalence reuse handles LLM non-determinism that defeats both exact caching and fuzzy similarity.
  • Version-bound domains prevent the classic stale-cache-after-upgrade failure, shown concretely via the rule-document bump scenario.
  • The submission gate is a genuinely useful agent-safety pattern: a fresh computation is not a safe action, and the 1,200-proposal test demonstrates it sensibly.
  • Clear formalism (Eqs. 1–15) and an unusually honest limitations section.

Limitations· 局限

  • Evaluation scale: three scripted internal case studies — no public benchmark, no code release, no variance behind the Table 2 aggregates.
  • Domain construction requires a side-effect-free verification environment (shadow DB, digital twin) — unavailable for many third-party APIs.
  • Each output field needs a deterministic machine-executable equivalence rule — hard for free-form NL, and the structured-extraction layer is itself unevaluated.
  • High-dimensional joint domains may fall back to minimal re-execution: worst case converges to the baseline it criticizes.
  • Masks are hand-authored and unmeasured — one false-negative Mi[a,b]=0 silently skips invalidation, with no runtime detection described.
  • On-site validation assumes the source is re-readable; partitions or outages defer renewals.

Questions for further exploration· 待探索

  1. Is there a runtime mechanism (e.g. periodic perturbation audits) that catches a missed dependency before a mask error causes staleness?
  2. What is the measured developer cost of contracts, masks, and equivalence criteria — and can they be auto-induced from execution traces?
  3. Under silent server-side model updates without a version bump, does confidence ci degrade fast enough under distribution shift?
  4. How does it compare head-to-head with differential dataflow or semantic caching in LLM serving frameworks on the same workloads?
  5. Could the equivalence criterion itself be learned from decision outcomes — and what would the safety story be without a deterministic criterion?
