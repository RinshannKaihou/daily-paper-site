> **一句话总结：** SAP 团队提出 EdgeGen：从 Agent 的政策文档中自动抽取合规规则、用规则幂集枚举违规场景、经 SQL Agent 在合成数据库中落地状态并通过数据接地与可行性双重校验，全程无人工标注地生成"边界案例"训练/评测任务；在 τ²-bench airline 上为 Qwen2.5-3B 带来 +42% 相对平均进度提升（0.258→0.366），且在全部 18 个模型×基准组合上均优于未微调基线，而人类标注数据微调反而使 3/6 个模型在 airline 上退化（最多 −13.16%）。

> **TL;DR:** EdgeGen is a fully automated, closed-loop pipeline that turns an agent's natural-language policy document into database-grounded, policy-violating test tasks: it extracts compliance rules, enumerates their power set as violation scenarios, samples tool workflows (NODE/CHAIN/DAG), grounds each scenario in a synthetic relational database via an iterative SQL agent, and validates every task with two checks (data grounding + feasibility). Fine-tuned on expert (gpt-5.4) trajectories for these synthetic edge cases, Qwen2.5-3B gains +42% relative mean progress (0.258→0.366) on τ²-bench airline versus the untuned base, beating human-curated data (which degrades 3 of 6 models there, up to −0.05 / −13.16% on Gemma-4-e2b) and adapted TaskBench/FuncBenchGen baselines; EdgeGen wins mean progress in all 18 model-benchmark pairs. The same data used to optimize the agent harness lifts Gemma-4-e4b airline mean progress from 0.43 to 0.56 (+30%) with fewer tool calls and tokens.

## 核心贡献

- **违规驱动的任务生成框架**：不同于 Self-Instruct/APIGen/TaskBench 等生成"happy-path"通用任务的方法，EdgeGen 从 Agent 政策文档 P 中抽取原子合规规则 R（每域取最重要 5 条），枚举规则幂集（至多 2^5=32 个子集）作为违规场景 S，并用 LLM 一致性检查器过滤逻辑不相容组合，系统性覆盖"该拒绝而未拒绝"类策略边界。
- **数据库接地 + 双重验证的闭环**：每个测试用例为四元组 ⟨q, w, A, S⟩（任务描述 / 工具调用序列 / 自然语言断言 / 被违反规则集）；由迭代式 SQL Agent 在合成关系数据库中采样满足场景的状态 ρ，再经两道独立校验——数据接地（用确定性 SQL 核实标识符与事实，杜绝幻觉 ID）与场景可行性（期望响应可由现有工具达成）——不合格即丢弃并从工具图阶段重启。配合 LLM 驱动的合成数据库生成器，整条链路无需生产日志或人工标注。
- **双用途闭环优化**：合成任务既可经 gpt-5.4 专家演示 + 成功轨迹过滤后做 LoRA SFT（每基准 120 次尝试），也可用于黑盒模型的 harness（系统提示词/工具 docstring）自动演化优化。
- **实证发现**：显式覆盖策略违规对数据质量至关重要——人类标注或通用合成数据微调可能"有害"，而 EdgeGen 数据在 6 个模型（Qwen2.5/3.5、Gemma-4 系列）×3 个基准上一致提升；复杂度消融显示 1 个违规场景收益最大（Qwen2.5-3B 最大进度 +0.32），复杂度并非越高越好。

## Key Contributions

- **EdgeGen framework**: a violation-driven synthetic task generation pipeline that (1) extracts compliance rules from the agent's policy document, (2) enumerates rule combinations (power set, capped at 5 rules → 32 subsets), (3) grounds each scenario in executable database states via a scenario-aware SQL agent, and (4) verifies every task for data grounding and feasibility before admission.
- **Fully automated closed loop**: combining synthetic database generation (a "Generalist Populator" LLM agent that performs API write operations with precondition checks) with EdgeGen task construction yields high-quality training and evaluation data without human annotation or production logs.
- **Empirical evidence that edge-case coverage matters**: across 18 model-benchmark pairs (6 models × 3 benchmarks), EdgeGen SFT improves mean progress over the base model in 100% of pairs, while human-curated finetuning regresses on 3 of 6 models in the airline domain and TaskBench regresses on 4 of 6; the same data transfers to harness optimization for black-box models.
- **Complexity and scaling analysis**: an ablation over violations-per-task (happy path / 1 / 2 / 3) and a training-budget sweep (10/30/60 tasks) show that benefit is non-monotonic in scenario complexity, with single-violation tasks delivering the largest gain.

## Methodology

**Problem formulation.** A tool-calling agent deployment is characterized by three artifacts: a tool set T (with typed inputs/outputs), a natural-language policy document P, and a relational database D. Policies are formalized as atomic compliance constraints R = {r1...rn}, each corresponding to a single verifiable assertion about agent behavior (e.g., "verify user identity before modifying a reservation"). A test case is a tuple x = ⟨q, w, A, S⟩: user task q grounded in concrete database values, an ordered tool-invocation workflow w, natural-language assertions A serving as evaluation targets, and the set S of policy rules the task violates or stress-tests. A test case is valid only if it satisfies data grounding (no fabricated identifiers/facts; verified by deterministic SQL over D) and scenario feasibility (the expected policy-compliant response — e.g., a denial — is achievable with the available tools and state).

**Five-stage pipeline.**
1. **Rule extraction**: an LLM extracts the top-5 compliance rules from P (prompt in Appendix A.2.1; audited at F1 = 93.3% against manually annotated ground truth, Table 9).
2. **Tool graph construction and path sampling**: a DAG G = (V, E) over tools with edges where Out(ti) ∩ In(tj) ≠ ∅ (resource-type compatibility, following Shen et al. 2024); an LLM selects a valid workflow w ~ p(w | P), sampled as a NODE (single tool), CHAIN (linear), or DAG (branching) structure.
3. **Violation scenario generation**: scenarios are subsets S ⊆ P(R) (power set of rules, ≤ 2^5 = 32); an LLM-based consistency checker removes logically incompatible combinations, yielding feasible set P*(R). |S| = 0 is a happy-path task; |S| ≥ 2 produces multi-rule interactions.
4. **Scenario-aware database sampling**: an iterative SQL agent grounds the scenario: ρ ~ π_SQL(D | w, S), sampling database rows that satisfy both the execution structure and the constraint configuration; if no valid ρ exists, resample w and S. The database itself is generated by a Generalist Populator agent that executes API write operations with preconditions checked against current state (rejected operations leave state unchanged), yielding a coherent relational DB. EdgeGen is agnostic to the database source.
5. **Test case generation + verification**: an LLM writes the task summary q and assertions A referencing concrete DB entities; a verifier then runs two independent checks — data grounding (SQL agent executes deterministic queries to confirm every identifier/fact) and feasibility (state supports the expected denial/operation) — failing tasks are discarded and the pipeline restarts from Stage 1.

**Training and harness optimization.** For SFT, expert demonstrations come from gpt-5.4 (8 rollouts per task, 120 attempted rollouts per benchmark, only progress-rate-1 traces retained), converted to each model family's conversation format and trained with LoRA (rank 64, AdamW 2e-5, 3 epochs, max 13,384-token sequences on B200/H200). For black-box harness optimization, the same synthetic scenarios drive an evolutionary harness search (Lee et al. 2026-style): a proposer mutates system prompts, tool descriptions, or code across generations, selected on a synthetic validation split. Evaluation uses the TED framework (user simulator + LLM-as-a-judge, both gpt-4.1), 8 trials per scenario, reporting mean and maximum progress rate.

## Results & Highlights

- **Airline SFT headline**: on τ²-bench airline, EdgeGen finetuning gives Qwen2.5-3B a +42% relative mean-progress improvement (0.258 → 0.366) over the untuned base — the strongest result of any method on that domain. By contrast, human-curated finetuning *degrades* 3 of 6 models on airline (up to −0.05 points, −13.16% on Gemma-4-e2b: mean progress 0.38 → 0.33), and adapted TaskBench regresses on 4 of 6 models (e.g., Qwen3.5-4b 0.87 → 0.76 mean).
- **Universality**: EdgeGen improves mean progress over the base model in **all 18 model-benchmark pairs** (Table 10 aggregate win rates: 100% vs Base, 100% vs FuncBenchGen, 94.12% vs TaskBench, 86.67% vs Human-Curated, 81.25% vs Naive). On ToolSandbox, relative mean-progress gains over base range from +10.9% (0.605 → 0.671) to +23.4% (0.528 → 0.652).
- **Harness optimization for black-box models**: on τ²-bench airline with Gemma-4-e4b, the EdgeGen-optimized harness lifts mean progress from 0.4301 (base harness) to 0.5608 (+30% relative), also +10% over the harness optimized on human-curated data (0.5083), while using fewer tool calls (6.9 vs 8.8) and fewer tokens (85.0k vs 121.0k); max progress reaches 0.8208 vs 0.6167 (human-curated) and 0.6552 (base). For gpt-5.4, EdgeGen-harness is within 2–4% relative of the human-curated-optimized harness (mean 0.7979 vs 0.8397) at lower cost (7.9 tools / 66.3k tokens vs 8.9 / 78.8k).
- **Baseline quality gap**: adapted FuncBenchGen produced only a single valid expert rollout on ToolSandbox (the vast majority of its generated tasks were infeasible or invalid); per-task rejection rates (Table 12) are 0% for EdgeGen versus 20–90% for FuncBenchGen and 30–60% for TaskBench/Naive — at the cost of generation time (144.3 s and 22,575 tokens per airline task vs 0.8 s / 16,817 tokens for Naive).
- **Complexity ablation (Table 3)**: finetuning on happy-path trajectories alone yields no gain for Qwen3.5-4b (0.88 vs 0.89 base max progress) but a single-violation diet gives the best result (0.92, +0.03). For Qwen2.5-3b, one violation produces +0.32 (0.35 → 0.67), but two violations *drops below base* (0.24, −0.10) and three returns to 0.38 — complexity is non-monotonic.
- **Data scaling**: with budgets n ∈ {10, 30, 60} tasks, human-curated test mean progress peaks at n = 30 (Qwen3.5-4b 0.800; Gemma-4-e2b 0.315) and declines at n = 60 (0.704 / 0.276), even as synthetic-validation progress keeps improving — validation gains do not consistently transfer.
- **Honest failure accounting (human studies)**: of 10 "successful" airline runs flagged by the LLM judge, only 6 were verified correct (2 loosely-defined assertions, 1 judge error, 1 missing task detail; ToolSandbox: 4/10); root-cause analysis of failed runs attributes 66.7–75% to genuine agent issues, 16.7–26.7% to invalid tasks (including 2 airline tasks with contradicting dates), 0–6.7% to invalid data, and 0–8.3% to judge errors.

## Authors & Credibility

The paper comes from a 10-person team at **SAP** (all @sap.com), an enterprise-software company whose core business is exactly the kind of policy-constrained, database-backed workflows this paper targets — giving the "enterprise compliance edge cases" motivation strong industrial grounding. The team spans applied research and engineering roles; Daniel Dahlmeier is a well-known NLP researcher (formerly Salesforce Research, NTU). Several co-authors (e.g., Penny Chong, Jiyuan Shen, Atin Ghosh, Daniel Dahlmeier) also appear in the cited TED evaluation-framework work (Chong et al., ICLR 2026), so the group has a track record on agent evaluation infrastructure. The paper is candid about LLM usage in paper preparation (A.1), releases its datasets under Apache 2.0, documents all artifact licenses (A.7), and reports compute (~180 GPU-hours B200 compute for finetuning; ~30 GPU-days for evaluation). The two source benchmarks are used under MIT and Apple's custom research license; τ²-bench and ToolSandbox evaluation is permitted for research use. Credibility is above average for an industrial agent-data paper, though the code release status is stated as "code & data — Apache 2.0" with an anonymized-submission note, so external reproducibility of the full pipeline remains to be confirmed.

## Critical Assessment

**Novelty is real but incremental in mechanism.** The individual ingredients — LLM rule extraction, tool-graph sampling (borrowed from TaskBench), SQL-agent database grounding, LLM-as-verifier — are each established; the genuine novelty is the *violation-driven enumeration over a policy-rule power set* as the organizing principle for task diversity, plus the insistence on database-grounded, feasibility-checked tasks. That framing is a useful corrective to happy-path-only synthetic data, and the paper's most valuable finding is arguably negative: *human-curated data can be actively harmful* for policy-heavy domains (3/6 models degrade on airline).

**Metric fragility is the biggest concern — and the authors half-admit it.** The headline "mean progress" metric is judged by gpt-4.1 LLM-as-a-judge, and the paper's own Study A finds only 60% (airline) and 40% (ToolSandbox) of judge-approved "successful" EdgeGen runs are actually correct, with loosely-defined assertions being the top artifact. All baselines share this judge, so *relative* comparisons are more trustworthy than absolute numbers, but a 40–60% false-positive rate on the primary metric means effect sizes (especially the small gains on stronger models, e.g., Qwen3.5-9b airline mean 0.87 → 0.92) are within plausible judge-noise territory. No statistical significance testing is performed — Appendix A.11 explicitly says comparisons are "descriptive, not statistical significance" — and with only 10–15 evaluation scenarios per benchmark (8 trials each), confidence intervals on a 10-scenario mean must be wide.

**Baseline adaptations may be unfairly weak.** FuncBenchGen and TaskBench are re-implemented on top of the authors' SQL agent and environments; FuncBenchGen yielding exactly one valid rollout on ToolSandbox is presented as evidence of baseline infeasibility, but it could equally reflect a poor adaptation (the authors note its original pipeline "is not directly compatible with our benchmarks"). The adapted baselines also lack the database-grounding machinery that is EdgeGen's core contribution, so the comparison partially measures the pipeline's own ingredients against themselves.

**Ablations reveal brittleness the headline abstracts over.** The complexity ablation is non-monotonic and model-inconsistent (2-violation training *hurts* Qwen2.5-3b below base: 0.24 vs 0.35), the ablation "does not independently isolate the contributions of database grounding and verification" (authors' own words), and the n = 60 scaling run shows synthetic-validation progress diverging from test progress — a warning sign that the validation splits used for harness/model selection are distribution-shifted from the human-curated test sets. The gpt-5.4 harness result (EdgeGen *trails* human-curated optimization by 2–4%) shows the advantage is not universal even within the paper.

**Scope limits.** All three domains are customer-service-style, policy-dense benchmarks from just two benchmark families; rule extraction caps at 5 rules (2^5 subsets), an arbitrary ceiling that sidesteps combinatorial explosion but also limits coverage of real enterprise policy sheets with dozens of interacting rules. The strong headline (+42%) is on the smallest, weakest model; for larger models the paper itself concedes "the potential for improvement is smaller" and that real-life test cases may be too simple to show violation-training benefits.

## Strengths

- Attacks a real, well-motivated gap: enterprise tool agents fail on policy/state-dependent *refusals*, not just tool-call syntax; existing synthetic generators ignore both database state and compliance rules.
- The two-stage verification (deterministic-SQL data grounding + feasibility check) measurably works: 0% rejection rate on final tasks versus 20–90% for the adapted baselines, with concrete hallucination examples from TaskBench/FuncBenchGen shown in Appendix A.3 (fabricated airport codes, placeholder reservation IDs reused across samples).
- Unusually broad empirical sweep for this literature: 6 open models (3B–35B, dense and MoE) × 3 benchmarks × 5 training-data conditions, plus a second, independent use case (harness optimization for black-box gpt-5.4/gpt-4o-mini).
- Intellectual honesty above the norm: the paper reports its own judge-error rates (human Study A), attributes most failures to genuine agent limitations (Study B), publishes the non-monotonic complexity and scaling results, and states explicitly which ablations do *not* isolate components.
- Rule-extraction quality is audited against human annotation (P 94.6% / R 92.1% / F1 93.3% overall), rather than assumed.
- Practical efficiency result: the EdgeGen-optimized harness is *cheaper at inference* (fewer tool calls/tokens) than the human-curated-optimized one, because it learns a generic discover→verify→confirm→write protocol instead of hard-coding case-by-case rules into prompts.

## Limitations

- Requires a structured, reasonably formal policy document; sparse, ambiguous, or informal specs yield incomplete rule sets and reduced edge-case coverage (authors' own limitation). Coding and web-navigation agents are untested.
- Heavy dependence on LLM calls at every stage (rule extraction, feasibility filtering, generation, verification); verification is imperfect — human study found loosely-defined assertions and missing task details in admitted "successful" runs, and 2 of 15 sampled airline failures traced to invalid generated tasks (contradicting dates).
- Small evaluation scale: 10–15 held-out human-curated scenarios per benchmark (a supplementary 21-scenario airline set in A.14), no error bars or significance tests; several headline deltas on stronger models are a few hundredths of a progress point.
- Rule enumeration is capped at the top-5 rules → at most 32 subsets, which does not scale to large real policy documents and may miss higher-order rule interactions.
- Gains concentrate on smaller models; for Qwen3.5-9b/35b and gpt-5.4 the improvements are marginal or mixed, and the data-scaling study shows benefits plateau/regress at 60 tasks with validation-test divergence.
- Generation is expensive relative to naive synthesis: 144.3 s and ~22.6k tokens per airline task (vs 0.8 s for Naive), plus ~180 GPU-hours (B200) for the SFT experiments in this paper alone.
- Expert trajectories come from gpt-5.4 and judging from gpt-4.1 — proprietary frontier models — so the pipeline's output quality is coupled to closed-model availability and their biases.

## Relevance

这篇论文与你的兴趣高度相关：它直击 tool-calling agent 的合成数据与评测痛点——不只测"能否调对工具"，而是测"是否遵守数据库状态与业务策略"，并给出了可复用的规则枚举 + SQL 接地 + 双重验证的自动化流水线。其"人类标注数据微调反而有害、单违规场景收益最大"的反直觉发现，对你设计 agent 训练数据配比与边界案例评测都有直接参考价值。

## Questions for Further Exploration

- Can violation-scenario enumeration scale beyond 5 extracted rules to enterprise policy documents with dozens of interacting constraints (e.g., via constraint-solvers or symbolic feasibility checking instead of LLM consistency filters)?
- How much of the judge-based mean-progress gain survives human re-annotation, given Study A's 40–60% false-positive rate on "successful" runs — would outcome-grounded programmatic checks (final DB state diffs) replace the LLM judge?
- Why is two-violation training actively harmful for Qwen2.5-3b (0.24 vs 0.35 base) while neutral-to-positive for Qwen3.5-4b — is it data volume, curriculum, or assertion ambiguity at higher |S|?
- Does the EdgeGen-trained gain transfer to RL or preference optimization (the paper only tests rejection-sampled SFT), and does the discover→verify→confirm→write protocol emerge without harness co-optimization?
- Would the pipeline work for non-customer-service domains (coding agents, web navigation) where "policy" is implicit in documentation rather than a crisp rule sheet?
- The validation-test divergence at n = 60 suggests the synthetic validation split is a biased model selector — can synthetic validation be made an unbiased estimator of human-curated test performance?
