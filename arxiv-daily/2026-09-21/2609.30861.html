02 Why This Matters

Any agent that rewrites its own skill library accumulates brittle edits. These three regularizers drop into existing pipelines — the native updater and evaluator stay untouched.

为会被 agent 反复改写的技能库 / 记忆库提供一套可逐条移植的「dropout 生成 + 局部复杂度整备 + 配对反例验证」三段式机制。
03 Critical Edge

Every headline number comes from one unnamed proprietary LLM with no code release — and single-trajectory comparisons carry no seed variance or significance testing, so the generality claim rests on thin statistical support.

04 Methodology three regularizers, one insertion point

SkillEvoReg acts only at the candidate-update boundary S̃(t+1) = U(Sₜ, τₜ): the native updater proposes, the framework regularizes. Skills are segmented into atoms; masked atoms are always restored and frozen evaluation always sees the complete state.

STEP 1

Training-time skill dropout

Mask a subset of skill atoms for the update rollout; diff the proposal against the masked view and reconcile only the learned change back onto the complete incumbent — the discrete analogue of neural dropout.

→
STEP 2

Complexity-aware local regularization

An observable structural-complexity signal (lexical size, control flow, code dependencies) triggers bounded reconciliation — NoOp / Merge / Rewrite / Delete — restricted to the candidate plus related atoms only.

→
STEP 3

Causal counterexample validation

Attack a source case along the candidate’s own change direction; confirm regression only when the incumbent still passes the attacked case (four-way paired check), then at most one scope-constrained repair.

Plug-and-play across three heterogeneous systems: SkillOpt (single-document) · SkillEvoBench (multi-skill library, controlled second pass) · ContinualSkillBench (CREATE/MODIFY-SKILL growth). Same proprietary LLM, native harnesses, fixed inference config throughout.

06 Strengths
  • Crisp problem formalization — three dissociable failure modes, backed by a transparent longitudinal pilot with LLM-judge-free lexical diagnostics.
  • The regularization analogy is operationalized, not decorative — each mechanism maps explicitly to dropout, capacity control, or adversarial validation.
  • Generality demonstrated — the same three roles plug into three heterogeneous native updaters with per-framework integration tables.
  • Compactness wins everywhere — skill tokens and complexity decrease in every one of the 8+ reported settings, capability mostly preserved or improved.
  • Unusually honest — LiveMath negative traced to dataset bias; web-search token costs carefully separated from skill-context savings.
07 Limitations
  • One unnamed proprietary LLM in all experiments; no code release, no shared software core — external replication is blocked.
  • One evolved trajectory per condition — no seed variance, no significance tests; Finance +0.47 and SearchQA +0.68 sit within plausible run-to-run noise.
  • Delivery-vs-final framing flatters — like-for-like finals are mixed (see Critical Edge above).
  • Short horizons only (8 epochs / 50 tasks); evolution-side compute cost of dropout rollouts and CCV attacks is unreported.
  • Hyperparameters asserted, not ablated — CCV thresholds, dropout mask ratio, complexity budgets, 1-repair cap; C(S) is a hand-crafted proxy validated only through outcomes.
08 Questions for Further Exploration
Is there an inverted-U dose–response for the skill-dropout mask ratio, and does the optimum transfer across base models and skill formats?
Does CCV stay reliable when the native evaluator is a stochastic LLM judge — how do the 0.05 / 0.1 thresholds behave under the noise level the paper itself reports?
Can SkillEvoReg compose with concurrent safeguards (GSE, SkillCommit, Trace2Skill, SkillAdam) — do repair and consolidation stack or conflict?
Could validation-selected “delivery” be replaced by a principled early-stopping rule driven by CCV signals and complexity growth?
How does the hand-crafted complexity C(S) compare with learned or embedding-based skill-quality signals at equal downstream accuracy?
Do the compactness gains persist when skill states are executable code rather than prose, given the asymmetry of C(S)’s code terms?
