> **一句话总结：** 提出 Growing Harness——一个从"无策略空脚手架"（只暴露固定 LLM 和工具接口、不含任何解题控制器）出发、以失败为导向自动"生长"出智能体编排代码的训练范式：每次失败由函数级执行 DAG 定位到有界代码面，离线优化器在编辑预算内联合修复一个失败窗口（只允许改 trace 涉及的函数、禁止写入任务 ID/答案、确定性控制逻辑进代码、语义判断保留给 LLM），候选先在失败窗口重跑、再经"成功优先"的 held-out 门控，任何降低门控集成功率的修复序列整体事务性回滚；在 BrowseComp-Plus 与 WebArena-Verified × 3 个部署模型（gpt-oss-120b/20b、Qwen3.5-4B）共 6 个设置中 5 个取得最高平均成功率（第 6 个仅差 0.7 pp），相对 Tool-Calling 减少 76.0–91.8% 的 LLM 调用、降低 74.4–98.6% 的部署成本，且 WebArena-Verified 上成功率跨模型规模稳定在 44.7–45.3%（而 Tool-Calling 在 4B 上跌至 6.7%）。

> **TL;DR:** Growing Harness treats the agent harness — the executable code orchestrating LLM and tool calls — as the only learnable object. Training starts from a strategy-free scaffold (a `main(task)` stub with fixed LLM/tool interfaces and no controller) and repeatedly: (1) records a function-level execution DAG for each failure, (2) has an offline optimizer (GPT-5.6-terra / GPT-5.4) jointly repair a bounded window of failures via trace-scoped edits (only traced functions + `main` may change, edit budget L=10), and (3) accepts a candidate only if it fixes enough window failures AND does not drop held-out gate-set success, with transactional rollback otherwise. On WebArena-Verified with Qwen3.5-4B it reaches 45.3% success vs 6.7% for the ReAct-style Tool-Calling baseline (+38.6 pp), using 5.4 vs 37.8 LLM calls per task and $0.10 vs $7.26 per 50-task run; across all three deployment models its WebArena success stays flat at 44.7–45.3% while Tool-Calling collapses from 30.0% (120B) to 6.7% (4B). Ablations on BrowseComp-Plus show removing function-level trace guidance halves final success (36.0% → 18.0%), removing gate validation causes late-training regression (gate success 30% → 16%), and single-failure windows cost 8 pp.

## 核心贡献
- **问题重述：把"智能体学习"形式化为可复用程序生长**——在固定 LLM（M）和固定工具（T）下，唯一可学习对象是编排代码 h；训练从 strategy-free 脚手架 h₀ 出发（只有任务入口和接口，无 ReAct/ Self-Ask 式预置控制器），让控制结构从任务反馈中涌现。
- **Trace-local program growth（三大机制的组合）**：① 函数级执行 DAG 把每个失败定位到参与执行的函数集合 F(τᵢ)，优化器的编辑范围被限制在 {main} ∪ F(τᵢ)、编辑预算 d_fun ≤ L，使每步优化的搜索面不随全局程序规模增长；② 失败窗口课程（容量 K）：一次联合修复 K 个活跃失败、解出的任务离窗、未解的带新 trace 留窗、达到 R_max 次退役，促使优化器学到跨任务共享的行为而非实例特例；③ 成功优先的 held-out 门控：每修复 Q 个任务就在 50 题门控集上评估，接受条件是 SR_G(新) ≥ SR_G(检查点)，否则连代码带任务游标、窗口、计数器一起事务性回滚。
- **确定性与语义的分工原则**：解析、校验、状态更新、条件化查询改写、错误恢复、停止判定等确定性可复用控制进代码；解释、综合、模糊比较、答案生成等开放语义决策保留 LLM 调用——这是"调用数降 76–92%"的直接来源。
- **实证结论**：6 个 benchmark–model 设置中 5 个平均成功率最高；相对 Tool-Calling，LLM 调用减少 76.0–91.8%、部署成本降低 74.4–98.6%；WebArena-Verified 上成功率跨 4B–120B 稳定在 44.7–45.3%，而 Tool-Calling 从 30.0%（120B）跌到 6.7%（4B）——收益最大的恰是最小模型。
- **结构涌现分析**：同一 h₀ 在两个任务族上长出完全不同的控制器——BrowseComp-Plus 长成所有任务共享的"检索+证据核验流水线"，WebArena-Verified 长成"确定性解析器 + 分站点控制例程（购物/Reddit/地图）+ 通用浏览器兜底循环 + 完成态校验器"的分层控制器；支持"低先验承诺"设计目标。

## Key Contributions
- **Reformulates agent learning as reusable program growth**: with model M and tools T fixed, the harness h is the sole learnable object; training starts from a strategy-free scaffold exposing only the task entry point and fixed interfaces, with no predefined controller — executable structure emerges from task feedback.
- **Trace-local program growth**: function-level execution DAGs localize each failure to the set of invoked functions; the optimizer's edits are confined to {main} ∪ traced functions under an edit budget L, so per-step optimization cost depends on the active execution slice, not total program size; a bounded failure-window (capacity K) forces joint repairs that transfer; a success-first held-out gate rejects and transactionally rolls back (code + cursor + window + counters) any repair sequence that lowers gate success.
- **Deterministic-vs-semantic division of labor**: parsing, validation, state updates, conditional query refinement, error recovery, and stopping become code; interpretation, synthesis, fuzzy comparison, and answer generation stay as LLM calls — the direct cause of the 76.0–91.8% call reduction.
- **Empirical evidence across scales**: best mean success in 5 of 6 benchmark–model settings (worst case −0.7 pp); on WebArena-Verified success is flat at 44.7–45.3% from 120B down to 4B while Tool-Calling falls to 6.7% at 4B — the small-model regime where harness growth matters most.
- **Emergent architecture analysis**: the same seed scaffold grows a shared retrieval/verification pipeline on BrowseComp-Plus but a layered site-specialized web controller (deterministic resolvers + learned control routines + generic browser fallback + completion validator) on WebArena-Verified.

## Methodology
**Problem formulation.** A deployed agent is h(x; M, T): a fixed LLM backend M, fixed tools T, and executable harness code h. Tasks are split per benchmark into 200 training tasks (execution experience), 50 gate tasks (checkpoint acceptance), and 50 final-evaluation tasks (reporting only; the optimizer never sees its outcomes or traces).

**Strategy-free scaffold.** h₀ is a minimal program that exposes `main(task, max_llm_calls)` and the fixed LLM/tool interfaces but returns an empty answer — it encodes no task-solving controller, yet retains generic LLM access so any inference-time agent remains representable in the hypothesis class.

**Function-level traces.** Each execution records a DAG Gᵢ whose nodes are harness-function invocations, LLM/tool calls, returns, or runtime errors (with inputs, outputs, parent, duration). The trace τᵢ = (xᵢ, Gᵢ, yᵢ, oᵢ, uᵢ) yields F(τᵢ) = functions invoked in the failing run, which bounds the editable surface: At = {main} ∪ ⋃ F(τᵢ). The optimizer may add reusable helpers but must leave untraced functions untouched, preserve signatures, and may not encode task identifiers, expected answers, or fixed solutions. d_fun ≤ L caps modified + newly introduced functions.

**Failure-window curriculum.** A bounded window Wt holds up to K current failures (task + latest trace + attempt count). The optimizer jointly repairs all window failures; re-execution splits them into solved Pt (leaves) and unresolved Ut (stay with incremented attempts; retired at R_max); fresh failures refill. If an entire window exhausts its budget with no accepted repair, the last checkpoint is restored — preventing ineffective repair sequences from persisting.

**Offline optimization.** The optimizer model M_opt (GPT-5.6-terra High for BrowseComp-Plus; GPT-5.4 for WebArena-Verified — deliberately stronger than the deployment models) receives the current harness, window traces, and offline diagnostic artifacts (evaluator feedback, retrieved-doc IDs, evidence, action statistics) unavailable at deployment, and emits a complete candidate harness. Prompt guidance steers deterministic, reusable control into code and leaves semantic reasoning as LLM calls. Candidates must compile, preserve interfaces, and satisfy scope/budget constraints before evaluation.

**Held-out gate and transactional rollback.** h₀ is first evaluated on the gate set G; after every Q window tasks solved via repair, the current harness is re-evaluated on G and accepted iff SR_G is no lower than the latest checkpoint's; otherwise the entire repair sequence since that checkpoint rolls back — restoring code, task cursor, window, counters, and training records. Gate acceptance is success-first: lower online cost cannot buy acceptance. After the stream and window are exhausted, one final gate evaluation either keeps the tail changes or restores the checkpoint.

**Hyperparameters.** BrowseComp-Plus: K=8, R_max=5, Q=1, L=10, deployment LLM during training gpt-oss-20b. WebArena-Verified: K=4, R_max=5, Q=8, L=10, training deployment gpt-oss-120b. Both: 1 candidate per step, 50 online LLM calls/task budget enforced by the harness.

**Evaluation protocol.** 3 independent runs; every final task gets one single-attempt rollout per run; success = fraction of successful task–run pairs; task-level cluster bootstrap (10,000 replicates, seed 42) gives 95% CI half-widths; cost counts deployed-agent calls only (judge and optimizer excluded), with cache-read tokens estimated via longest shared prefix within a task. BrowseComp-Plus uses an LLM equivalence judge; WebArena-Verified uses its deterministic evaluator.

## Results & Highlights
- **Largest headline win — small model on WebArena-Verified:** with Qwen3.5-4B, Growing Harness scores 45.3 ± 13.4% success vs 6.7 ± 4.9% for Tool-Calling (+38.6 pp), vs 0.0% for WebDreamer and 3.3% for AgentOccam; it uses 5.4 vs 37.8 LLM calls per task (−85.7%) and $0.10 vs $7.26 per 50-task run (−98.6%).
- **Flat scaling curve on WebArena-Verified:** success stays within 44.7–45.3% across gpt-oss-120b, gpt-oss-20b, and Qwen3.5-4B (45.3/44.7/45.3), whereas Tool-Calling degrades 30.0% → 12.7% → 6.7% — recurring browser control runs in code instead of being reconstructed by a weak model each episode. At 120B the gap is 45.3 vs 30.0 (+15.3 pp) at $0.10 vs $2.72 per run.
- **BrowseComp-Plus:** with gpt-oss-120b, 49.3 ± 11.7% vs Tool-Calling 40.0 ± 11.6% (+9.3 pp) with 6.0 vs 32.7 LLM calls and $0.87 vs $6.70 per run (−87%); with Qwen3.5-4B, 29.3 ± 11.8% vs 12.0 ± 7.1% (+17.3 pp) at $0.81 vs $8.33. The one losing setting is gpt-oss-20b: 39.3 ± 12.6% vs 40.0 ± 11.7% (−0.7 pp) — still at 6.0 vs 24.8 calls and $0.52 vs $2.03.
- **Aggregate efficiency claim:** relative to Tool-Calling across the six settings, LLM calls drop 76.0–91.8% and online cost drops 74.4–98.6% while mean success is highest in 5 of 6 settings.
- **Ablations (BrowseComp-Plus, gpt-oss-20b deployment, GPT-5.6-terra optimizer, 10 steps, single run):** full method 36.0%; w/o function-level guidance (unconstrained whole-program edits) 18.0% — halved, with five stalled steps before a lower plateau; w/o gate validation 22.0% — gate success rose to 30% then fell to 16%, directly exhibiting the regression rollback targets; w/o failure-window (K=1, single-failure repairs) 28.0% (−8 pp), supporting joint multi-failure repair for reusable behavior.
- **Discovered structures (post-hoc abstraction, Fig. 6):** the BrowseComp-Plus harness converges on one shared retrieval-and-verification pipeline reused by every task (task parser → retrieval planner → evidence collector → evidence reader → final adjudicator); the WebArena-Verified harness grows deterministic resolvers plus specialized handlers for Shopping/Reddit/Map around a general LLM-guided browser loop, adding branches without rewriting shared paths — consistent with its steadier training curve and few rollbacks.

## Authors & Credibility
- The team is from the Shenzhen Institutes of Advanced Technology (CAS), University of Chinese Academy of Sciences, Shenzhen University of Advanced Technology, and the University of Macau (Institute of AI and Brain Sciences). Laizhen Li and Jiarui Li contributed equally; Xitong Gao (SIAT) is the corresponding author. This is a systems-flavored academic group; the work reads as a serious engineering-plus-research effort with an unusually careful measurement protocol for an agent paper (3 runs, cluster-bootstrap CIs, explicit cost accounting with per-model token prices, cache-read modeling, no best-of-run selection).
- Weaknesses on credibility: the evaluation footprint is small (50 final tasks per benchmark), the baselines are the authors' own adaptations of published methods, and the closest competing harness-optimization systems (AutoHarness, Meta-Harness, VeRO — all cited) are discussed only positionally, not benchmarked. No code release is mentioned in the paper.

## Critical Assessment
- **The headline "best in 5/6 settings" outruns its own error bars.** With 50 final-eval tasks, CI half-widths are ±11–13 pp. On BrowseComp-Plus with gpt-oss-120b, the +9.3 pp win (49.3 ± 11.7 vs 40.0 ± 11.6) has heavily overlapping intervals; only the small-model WebArena-Verified gaps (+32.0 to +38.6 pp) clearly clear the noise. The claim is directionally credible but statistically fragile in half the settings.
- **The efficiency story is not fully costed.** Total Online Cost excludes both the judge and the offline optimizer — which is a much stronger model (GPT-5.6-terra High / GPT-5.4) than the deployment LLMs. The paper never reports how many optimizer tokens/rounds each harness required, so the amortization break-even ("value depends on reusing the learned harness enough to offset offline optimization," acknowledged in the conclusion) is unquantified. In effect this is distillation of a frontier optimizer's control policy into cheap code plus a small model — a fair framing the paper could have stated more explicitly.
- **Ablations are thin where they matter most.** All three ablations are single-run, 10-step, on one benchmark (BrowseComp-Plus) with one deployment model; the deltas (−8 to −18 pp) are large enough to be believed, but the WebArena-Verified mechanisms (rollback frequency, handler branching) are never ablated, and no variance is reported for ablation numbers.
- **Baseline adaptation may be unfair to the weakest competitors.** AgentOccam scores 2.0–6.7% on WebArena-Verified here, far below the strong results in its own ICLR paper, and WebDreamer/AgentOccam were "adapted to the seed interface, accessibility-tree observation space, unified LLM budget." Tool-Calling (ReAct-style) is the meaningful reference and it is treated consistently, but the WebDreamer/AgentOccam rows mostly pad the frontier plot. Critically, AutoHarness and Meta-Harness — the two closest harness-optimization systems — get no empirical comparison at all; the novelty claim ("open-ended global growth from a strategy-free scaffold") is argued in related work, not demonstrated head-to-head.
- **The evaluation scope is narrowed in ways that flatter the method.** WebArena-Verified is restricted to shopping/reddit/map sites via stratified sampling (dropping, e.g., the GitLab subdomain), and each specialist harness is trained and tested within a single task family. Cross-family generalization of a grown harness — the interesting scientific question for "reusable specialist agents" — is untested; the learned code plausibly contains benchmark-coupled logic (e.g., a hard snippet budget `[:9000]` in the motivating repair example looks like an environment-specific constant).
- **Gate acceptance on 50 tasks is noisy.** The accept rule SR_G(new) ≥ SR_G(checkpoint) with a 50-task gate set and Q=1 (BrowseComp-Plus: gate evaluated after every repair) means near-tie candidates are accepted/rejected on noise; the paper does not discuss false-accept/false-reject rates, and this interacts with the single-run evaluation culture of the whole pipeline.
- **Training setups differ across benchmarks** (deployment LLM during training: 20b vs 120b; optimizer: GPT-5.6-terra vs GPT-5.4; K=8 vs K=4; Q=1 vs Q=8), so the Figure 3 training-dynamics comparison is confounded — a caveat the authors themselves concede, but it undercuts the "task family shapes the controller" conclusion somewhat.

## Strengths
- **The right deployment target.** Treating LLM calls and dollars as first-class metrics (with provider prices, cache modeling, judge exclusion all spelled out) matches how agents are actually deployed, and the success–cost frontier is the clearest in the recent agent literature.
- **The gate rollback is not decorative.** The w/o-gate ablation shows the exact failure mode it prevents (gate success 30% → 16% late in training), which is rare, direct evidence that a continual-optimization safeguard pays for itself — resonant with recent evidence that agent-optimizer gains fail to compound.
- **Same seed, two different emergent controllers.** Growing a shared pipeline on one benchmark and site-specialized handlers on the other from an identical strategy-free scaffold is the paper's most convincing qualitative evidence for low-prior-commitment growth, and the post-hoc abstractions (Fig. 6) make the learned programs inspectable rather than a black box.
- **Small-model robustness.** The 44.7–45.3% flat success band across 4B–120B on WebArena-Verified is a genuinely useful finding for on-device / resource-constrained agent deployment — the stated motivation.
- **Engineering hygiene:** atomic checkpointing and full-state serialization for resumable training, transactional rollback restoring cursor/window/counters (not just code), explicit anti-cheat constraints on the optimizer (no task IDs, no expected answers), and a stated budget all make the pipeline auditable.

## Limitations
- 50-task final sets per benchmark produce ±11–13 pp confidence half-widths, leaving several headline comparisons statistically unresolved; per-benchmark specialization means two separately trained specialists, and nothing shows a harness trained on one family helps another.
- Offline optimizer cost (a frontier model) is excluded from all headline cost numbers; the amortization break-even is acknowledged but never computed, and no optimizer token/round counts are reported.
- Ablations are single-run, one benchmark, one deployment model; no ablation on WebArena-Verified; no comparison against AutoHarness/Meta-Harness or prompt-optimization baselines (GEPA/DSPy) under matched budgets.
- WebArena-Verified is restricted to 3 of its websites; baselines are re-implementations adapted to the authors' seed interface (AgentOccam's numbers look anomalously low).
- Learned code contains environment-tuned constants (e.g., snippet cap raised to 9000 chars), raising transfer questions; deployment requires sandboxing and permission boundaries for grown code, which the authors flag but do not address; no code release is mentioned.

## Relevance
这篇论文与你的最高优先级方向 Self-Evolving Agents & Automated Research 直接对口：它把"自我改进智能体"落实为对智能体编排代码本身的持续优化，并专门用 held-out 门控 + 事务性回滚解决" successive local gains 不复利、改 A 坏 B"的持续学习退化问题。对长期运行的自主研究循环而言，"失败 trace 定位 + 有界编辑 + 回滚门控"是一套可直接借鉴的安全自改架构，且其"确定性控制进代码、语义决策留给 LLM"的成本结构分析对低成本长跑的 autonomous loop 很有参考价值。

## Questions for Further Exploration
- What is the amortization break-even: how many reused tasks per task family are needed before the offline optimizer's (GPT-5.6-terra/GPT-5.4) token cost is repaid, and how does that scale with harness size?
- Does a harness grown on one task family transfer at all to a related family (e.g., full WebArena with GitLab included, or BrowseComp-Plus with a refreshed corpus), or does the environment-tuned code (hard-coded snippet budgets, site-specific resolvers) fail fast under shift?
- How sensitive is gate-based acceptance to gate-set size and noise — with Q=1 and a 50-task gate, what are the false-accept rates, and would a paired significance test or larger gate change the accepted-harness trajectory?
- Under identical budgets, how does trace-local growth compare head-to-head with AutoHarness, Meta-Harness, or GEPA-style prompt optimizers — and do the mechanisms (trace locality, multi-failure windows, rollback) compose with them?
- As the harness grows, does trace-localization quality degrade (failures increasingly caused by stale helpers outside the current trace slice), and should the edit scope occasionally expand to untraced functions?
- Can specialists grown for different task families be composed or merged into one harness, or does the shared `main` make multi-family growth fundamentally harder than per-family training?
