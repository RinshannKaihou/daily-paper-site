> **一句话总结：** ActGov 把 LLM agent 的运行时上下文抽象到有限的二维语义记录空间（形成层级 L1–L3 × 七种语义范围），部署前由 LLM 提议策略并用 Z3 SMT 求解器验证无冲突，运行时对每个候选工具调用做确定性的任务范围授权检查——在 AgentDojo/AgentDyn 上将间接提示注入的 ASR 压到 ≤0.007（AgentDojo 上 0.000），同时干净任务效用仅小幅下降（如 Qwen3.6-flash 在 AgentDyn 上保持 0.667 不变），显著优于效用归零的 CaMeL/ACE 和大幅掉点的 Progent/DRIFT。

> **TL;DR:** ActGov is a runtime enforcement framework that stops indirect prompt injection in tool-calling LLM agents by checking every proposed tool call against a formally verified, task-scoped authorization policy. LLMs draft policies offline from tool specs, benign traces, and attack traces; Z3 verifies soundness before deployment, so the runtime only evaluates a finite set of abstracted records (no online LLM security reasoning). On AgentDyn, ActGov cuts attack success rate (ASR) from 0.046 to 0.004 on Qwen3.6-flash and from 0.111 to 0.007 on GPT-4o-mini while keeping clean utility at 0.667 (unchanged) and 0.433 vs 0.467 respectively — whereas CaMeL and ACE reduce ASR to 0 but drop utility to 0.000, and Progent/DRIFT retain only 0.15–0.30 clean utility. On AgentDojo, ActGov reaches ASR 0.000 on all four backends with clean utility ≥0.612. Main weakness: policies do not transfer — an AgentDojo-trained policy set collapses clean utility to 0.100 when deployed on AgentDyn (vs 0.767 no-defense).

## 核心贡献

- **统一语义抽象**：提出有限的二维记录空间 R（形成层级：L1 确定性 / L2 有界语义 / L3 组合逻辑 × 语义范围：action、permission、parameter、history、binding、external、domain），将非结构化的运行时上下文映射为可验证的离散记录，使"授权"成为可形式化定义的属性。
- **ActGov-Policy（部署前）**：LLM 作为策略提议者，从工具规格、良性轨迹和已知攻击轨迹中归纳三层策略（Task-Perm 任务级权限、Hard-Invariant 全局硬约束、Procedural-Obligation 程序性义务），每次迭代都经 Z3 SMT 求解器验证（SAT = 存在策略漏洞的反例，触发重写；全部 UNSAT = 可部署），保证策略集逻辑一致且不违反预设安全断言。
- **ActGov-Runtime（部署后）**：在 agent 与外部工具之间拦截每个候选工具调用，把执行上下文确定性地抽象为记录集，再对照已冻结的策略逐条检查——LLM 只负责把上下文解析为预定义的布尔/类别特征（如参数来源），不做端到端的安全判断，避免推理幻觉，运行时零 SMT 求解开销。
- **实证结果**：在 AgentDojo（629 个安全测试用例）和 AgentDyn（560 个用例、动态开放任务）上、四种模型后端（Qwen3.6-flash、MiniMax-M2.5、DeepSeek-v4-pro、GPT-4o mini）上系统评估，ASR 降至 ≤0.007，效用保持第一梯队，并给出策略生成器选择与训练数据规模的分析（RQ3）及跨域迁移实验。

## Key Contributions

- A **unified semantic abstraction**: a finite 2D record space (formation levels L1 deterministic / L2 bounded-semantic / L3 composite × seven semantic scopes: action, permission, parameter, history, binding, external, domain) that turns unstructured runtime context into a discrete, policy-checkable state, formalizing the agent + enforcement layer as a finite state machine M = (H, C, R, P, V, T).
- **ActGov-Policy**: an offline LLM-driven pipeline that proposes layered policies (Task-Perm, Hard-Invariant, Procedural-Obligation) from tool specs, benign traces, and observed attack traces, with every candidate bundle checked by a Z3 SMT solver — a SAT result yields a counterexample exposing a policy gap and triggers another refinement round; deployment only when all queries return UNSAT.
- **ActGov-Runtime**: a per-action enforcement monitor that intercepts each candidate tool call, deterministically abstracts its context into the record schema (the LLM is confined to extracting predefined categorical features such as parameter provenance, never making end-to-end security judgments), and blocks any call violating the frozen policy set — no online SMT solving, low latency, deterministic verdicts.
- Extensive evaluation on AgentDojo and AgentDyn across four LLM backends, comparing against Progent, DRIFT, CaMeL, and ACE, plus analyses of policy-generator choice, training-data scale, and cross-benchmark policy transferability.

## Methodology

**Threat model.** Indirect prompt injection (IPI): the initial user instruction is trusted; attacker-controlled content (emails, webpages, tool observations) tries to steer the agent into proposing unauthorized tool calls. The attacker cannot modify the trusted user task, tool specifications, or the ActGov enforcement layer, and cannot produce external effects without passing pre-execution validation.

**Formulation.** An agent execution is a sequence of states H (history) and candidate tool calls C. At each step, ActGov-Runtime resolves the baseline task permission perm_m and abstracts the environment/history state into a finite record set r_t ∈ R. The evaluation function V: R × P → {allow, deny} deterministically produces the authorization verdict; the external tool executes iff v_t = allow. The LLM's generative reasoning is decoupled from authorization: it only fills in the record schema (acting as a "semantic parser" for bounded, categorical features), while authorization logic is interpreted strictly by the deterministic error space.

**Orthogonal 2D record schema.** Records are classified along two axes. Formation level: L1 (computed directly from explicit structured system state), L2 (LLM extracts the value from unstructured text into a predefined record, e.g., whether a parameter originates from an untrusted source), L3 (standard Boolean logic over L1/L2 values, capturing conditional/temporal dependencies). Semantic scope: seven scopes (action, permission, parameter, history, binding, external, domain) describing what authorization-relevant property the record describes (e.g., pending_obligation ∈ history/L1; trusted_endpoint ∈ external/L2).

**Layered policies.** P = P_TP ∪ P_HI ∪ P_PO: Task-Perm binds the trusted user task to the minimum required tool permissions (baseline boundary); Hard-Invariant encodes global properties (e.g., no outbound network actions derived from untrusted injected content regardless of task); Procedural-Obligation covers conditional rules (weak target binding or uncertain argument provenance) that mandate specific prerequisites before execution.

**Verified policy generation.** The LLM operates exclusively as policy proposer over three data sources (tool specs/capability constraints, benign traces for over-restrictive rules, attack failures for missing security conditions). Each candidate bundle is checked in Z3 by searching the finite record domain for a legal assignment satisfying P_bundle but violating a predefined security assertion (a SAT witness is a concrete policy-gap counterexample); the policy set is frozen only when all assertions return UNSAT. In the main evaluation, GPT-5.5 proposes policies over 10 refinement rounds combined with human-in-the-loop review; two fully automated RQ3 variants remove the human review.

**Runtime.** ActGov-Runtime intercepts candidate calls, instantiates the record set from the current execution context, and evaluates P_TP first, then P_HI and P_PO — permitting execution only if the action is within the task boundary and violates no policies. To avoid hallucinated judgments, the LLM is confined to function-exclusive extraction of specific records (e.g., categorical parameter provenance) so policies evaluate over structured, finite values.

**Experimental setup.** AgentDojo (629 security test cases; workplace, banking, travel, Slack) and AgentDyn (60 user tasks × 23 injection tasks = 560 test cases; dynamic, open-ended, third-party instructions in the environment). Four backends: Qwen3.6-flash, MiniMax-M2.5, DeepSeek-v4-pro, GPT-4o mini. Baselines: no defense, Progent (privilege-based tool-call policies), DRIFT (dynamic trace-isolation rules), CaMeL (information-flow control), ACE (abstract-plan mapping); VerGuard excluded because its source code is not publicly available. Equal train/test splits; RQ1/RQ2 policies evaluated on the unseen test split; RQ3 uses AgentDyn with DeepSeek-v4-pro as the fixed evaluation agent. Metrics: Clean Utility, Attacked Utility, Attack Success Rate (ASR), following the native AgentDojo/AgentDyn scorers.

## Results & Highlights

- **AgentDyn, ASR reduction with utility preserved (Table 2):** On Qwen3.6-flash, ActGov cuts ASR from 0.046 (no defense) to 0.004 while keeping Clean Utility identical at 0.667 and Attacked Utility at 0.586 vs 0.650. On GPT-4o-mini, ASR drops from 0.111 to 0.007 with Clean Utility 0.433 vs 0.467. On MiniMax-M2.5, ASR 0.036 → 0.004 with Clean 0.617 vs 0.650. On DeepSeek-v4-pro, ASR 0.086 → 0.007, at a larger utility cost (Clean 0.600 vs 0.767).
- **Baseline collapse on AgentDyn (Table 2):** CaMeL and ACE achieve ASR 0.000 but score 0.000 Clean Utility on all four backends (they block essentially everything); Progent retains only 0.150 Clean / 0.011 ASR on Qwen3.6-flash and 0.217 Clean / 0.014 ASR on DeepSeek-v4-pro; DRIFT 0.033 Clean / 0.000 ASR (Qwen) and 0.300 Clean / 0.039 ASR (DeepSeek) — all dominated by ActGov's utility-at-matched-security profile.
- **AgentDojo, perfect ASR (Table 3):** ActGov attains ASR 0.000 on all four backends (e.g., Qwen3.6-flash: Clean 0.714 / Attacked 0.673 vs no-defense 0.857/0.857 with ASR 0.069; DeepSeek-v4-pro: 0.755/0.713/0.000 vs 0.878/0.839/0.061; GPT-4o-mini: 0.612/0.606/0.000 vs 0.653/0.690/0.036). The strongest baseline here is Progent on DeepSeek-v4-pro (0.816 Clean, ASR 0.008) — competitive, but ActGov still halves its residual ASR.
- **Policy generator and data scale matter (Table 4, AgentDyn, DeepSeek-v4-pro as agent):** with identical 50% training split, DeepSeek-v4-pro as generator yields Clean Utility 0.533, versus 0.317 (Qwen3.6-flash) and 0.283 (MiniMax-M2.5) — all at near-zero ASR (≤0.007). Shrinking the training split from 50% to 25% drops Clean Utility from 0.533 to 0.500 at constant ASR 0.007.
- **Policies do not transfer across benchmarks (Table 5, DeepSeek-v4-pro):** deploying the AgentDojo-trained policy set on AgentDyn collapses Clean Utility to 0.100 (vs 0.767 no defense) though ASR stays 0.000; symmetrically, AgentDyn-trained policies on AgentDojo yield Clean 0.224 (vs 0.878) with ASR 0.000 — out-of-domain policies default to severely conservative behavior.

## Authors & Credibility

The four authors are from Southern University of Science and Technology (SUSTech); the submission lists institutional email addresses and appears to be a group focused on systems security (the last author, Yinqian Zhang, is a well-known researcher in systems/security, e.g., side channels and secure systems). The work is positioned at the intersection of LLM agent safety and formal policy verification, engaging seriously with the relevant literature (CaMeL and ACE from NDSS 2026, Progent, DRIFT, VerGuard, AgentDojo/AgentDyn). The paper includes an explicit "Use of Generative AI Tools" disclosure: ChatGPT/Codex for polishing, LaTeX, and code debugging, plus LLM assistance inside the experimental policy-construction pipeline (prompt templates described in the main paper), with the authors asserting they verified all reported results against experiment artifacts. That transparency is a credibility positive; no code release is mentioned, which somewhat limits verifiability.

## Critical Assessment

**Novelty.** The core idea — separate "action proposal" (LLM, untrusted) from "action authorization" (deterministic, verified) via a finite semantic record space — is a clean and sensible framing, and the offline-verify/online-check split against Z3 is a real architectural contribution compared to per-trace online reasoning (VerGuard) or structural isolation (CaMeL/ACE). However, it is an engineered composition of known ingredients: LLM policy synthesis with formal checking (VerGuard, Progent), provenance tracking (CaMeL), and task-scoped least privilege. The distinctive piece is the 2D finite record schema that makes the runtime check finite and deterministic.

**Rigor — several caveats.** (1) The no-defense ASRs are strikingly low to begin with (0.036–0.111 on AgentDyn, 0.031–0.069 on AgentDojo), so the absolute security headroom ActGov demonstrates is small; the honest headline is "utility-preserving near-zero ASR," not "defeats a 60% attack rate." (2) The headline configurations (RQ1/RQ2) use GPT-5.5 as policy proposer with human-in-the-loop review over 10 refinement rounds — so the deployed policies are human-approved, and Table 4 shows what full automation actually buys: Clean Utility falls to 0.283–0.533 (vs 0.600 with HITL) on the same evaluation agent. The gap between the HITL system and the autonomous variant deserves more prominence than it gets. (3) The CaMeL/ACE rows (0.000 utility everywhere) rely on "native benchmark scorers"; whatever the protocol fairness, presenting two baselines at literally zero utility on every model invites suspicion that they are misconfigured or mismapped to the scorers rather than genuinely useless — the paper's argument that they "incur substantial utility loss especially on AgentDyn" is contradicted by its own table showing zero even on AgentDojo's structured tasks. (4) The L2 "bounded semantic" records are still LLM-extracted; the paper confines extraction to categorical outputs but never measures extraction error rates, so a misread provenance label could silently flip an allow/deny in either direction — an unquantified soundness hole in the "deterministic" enforcement story.

**Reproducibility.** No code or policy-set release is mentioned; policy generation is tied to a specific proprietary generator (GPT-5.5) with human review, and VerGuard is excluded for exactly the no-public-code reason the authors themselves invoke — a standard they do not yet meet themselves.

**Significance.** The cross-transfer experiment (Table 5) is the paper's most intellectually honest moment: it shows the approach currently behaves as a per-benchmark whitelist with near-perfect in-domain behavior and catastrophic out-of-domain utility (0.100–0.224 clean). Until policies generalize, deployment value is limited to well-instrumented, stable tool ecosystems.

## Strengths

- Deterministic, low-latency runtime: after offline Z3 verification, enforcement is a finite-state check over abstracted records — no online LLM or SMT cost on the critical path.
- The strongest utility-security trade-off in the comparison: near-zero ASR (≤0.007 AgentDyn, 0.000 AgentDojo) while CaMeL/ACE buy security at exactly zero utility and Progent/DRIFT lose most clean utility on AgentDyn.
- Well-designed formal backbone: the 2D record schema (formation × semantic scope) and three-layer policy decomposition give a reusable vocabulary for agent authorization policies.
- Honest limitation section: the authors proactively quantify the out-of-domain policy collapse (Table 5) and the data-scale sensitivity (Table 4) instead of hiding them.
- Broad evaluation: two benchmarks, four model backends, three research questions, and an explicit evaluation-integrity protocol (train/test split discipline, frozen policy before test evaluation).

## Limitations

- **No policy generalization:** generated policy sets are benchmark-specific; cross-domain deployment preserves safety (ASR 0.000) but craters utility (Clean 0.100 on AgentDyn with AgentDojo-trained policies, 0.224 on AgentDojo with AgentDyn-trained policies).
- **Dependence on comprehensive policy-generation data:** the refinement loop needs a sufficiently rich set of benign tasks and attack scenarios; utility degrades measurably with smaller training splits (0.533 → 0.500 at 25% split) and with weaker generators (0.533 vs 0.283–0.317 Clean Utility).
- **Residual LLM trust in L2 extraction:** the semantic parser that fills bounded records is still an LLM; extraction mistakes are unmeasured and could cause false allows or false blocks.
- **Human-in-the-loop in the main results:** policy sets used in RQ1/RQ2 were human-reviewed; fully automated generation (RQ3) achieves markedly lower utility, so the autonomous-policy story is not yet demonstrated.
- **Low no-defense ASR baselines** limit the demonstrable security gain; and VerGuard (the closest formal-verification competitor) could not be compared due to unavailable code.

## Questions for Further Exploration

- Can the record schema and policy layers be made benchmark-agnostic — e.g., learned over a tool-ecosystem corpus rather than per-benchmark train splits — so that out-of-domain utility does not collapse to 0.100–0.224?
- What is the empirical error rate of L2 bounded-semantic extraction, and can extraction confidence be surfaced as an L3 "uncertain provenance" record that triggers procedural obligations instead of silent allow/deny?
- How much of the HITL review could be replaced by adversarial policy fuzzing (automatically generating SAT counterexamples as new attack traces), closing the 0.600 → 0.283–0.533 utility gap of fully automated generation?
- Would the enforcement layer compose with structural defenses (CaMeL-style information flow) so that security does not depend on extraction fidelity at all?
- The baselines CaMeL and ACE score exactly 0.000 utility everywhere — is that a scoring-protocol artifact or a genuine design incompatibility with these benchmarks, and what would a fair-tuned configuration look like?
