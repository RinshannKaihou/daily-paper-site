> **一句话总结：** 本文提出 Continuity Kernel (CK)——一个面向长生命周期 AI 智能体的"激活契约"控制平面，将不可信组件的状态提案与原子化激活解耦，通过 17 阶段的精确前驱头校验和四种终止判定（Commit/Reject/Quarantine/Defer）保证只有经授权的提案才能推进权威分支头；在一个 Python 可执行有界模型上对 2,808,230 个可达状态、5,526,474 次状态变更转移做了穷举 BFS 搜索，零不变量违反。

> **TL;DR:** The paper argues that for persistent AI agents, storage retention is not authority, and defines "continuity" as an unbroken, authorized lineage of accepted branch heads. It specifies the Continuity Kernel (CK): an activation contract where untrusted models/tools propose typed candidates off-commit and a deterministic control plane validates an exact predecessor head plus pre-state authority in a short transaction, recording one of four dispositions. A Python executable bounded model exhaustively explores 2,808,230 reachable states and 5,526,474 state-changing transitions with zero invariant violations, but the work is a specification/model-checking contribution, not a deployed-system benchmark — there is no comparison against a running agent framework on a real workload.

## 核心贡献

- **存储保留 ≠ 权威性**：明确提出智能体状态治理是"基础设施激活契约"问题。仅把每个版本写进存储并不能决定哪个版本是权威的；一个对象当且仅当从当前分支头可达时才具有权威性。
- **Continuity Kernel 激活契约**：把"提交前的候选评估"（慢、可失败、含模型调用/网络抓取）与"原子激活"（短事务）解耦。不可信的提案方只能针对精确前驱头提案，无法自我授权。
- **17 阶段激活谓词 + 四种终止判定**：定义了严格有序的激活检查向量（TargetLookup → Allocation → ExpectedHead → … → WellFormedness），只接受全 Pass，并只产生 Commit/Reject/Quarantine/Defer 四种终态，每种对提案标识符都是终态、可重放。
- **类型化的生命周期语义**：为分支创建、写者交接（writer handoff，含 Fence/Retarget/Abort）、模式迁移、前向恢复各自定义了类型化转移，避免把这三者混为"加载检查点"导致分支分裂或旧凭证复活。
- **有界模型验证**：用 Python 标准库构建可执行有界模型，BFS 穷举到深度 7，覆盖 2,808,230 可达状态、5,526,474 状态变更转移、8,880,248 次转移尝试，零不变量违反，且 100% 命中所有命名的协议覆盖见证。

## Key Contributions

- **Separation of retention from authority.** A formal system model partitions agent state into isolated branches keyed by (subject, branch) and defines an object as authoritative iff reachable from the current committed branch head. Storage namespaces (Accepted, Candidate, Attempt, Quarantine, Projection) coexist, but only the Accepted namespace reachable from the head confers authority.
- **An owner-bound, exact-head activation protocol.** Untrusted proposers (models, tools, operators, memory services) sign proposals τ = ⟨pid, target, expected, ops, a, req⟩ targeting an exact predecessor head (or typed absence for genesis). Authorization is always evaluated against the pre-state context Γ, never the proposed successor, so a proposal cannot authorize itself by injecting its own privileges into `a`.
- **Four terminal dispositions with stable identity.** Each owner-bound pid receives exactly one of Commit / Reject / Quarantine / Defer. Only Commit atomically installs the complete accepted unit {candidate state, authority, lineage, head, effects, outcome, receipt}; every non-Commit disposition leaves authoritative state untouched. Resubmission after Defer/Quarantine requires a new pid linked to the old attempt.
- **Typed lifecycle transitions instead of "load checkpoint".** Branch creation (genesis with absence proof), writer handoff (directory-serialized Fence → Activate gap that prevents two active writers even on crash), schema Migration (pinned deterministic migrator, forward-only), and masked forward Restoration are distinct typed transitions. Restoration cannot truncate lineage, revive an old writer/credential, or undo an external action.
- **Calibrated four-level receipts.** Receipts distinguish Structural authenticity, kernel-Attested reason, independent Replay, and durable Inclusion proofs — explicitly noting that a signature on a receipt does not prove the storage transaction committed.
- **Formal, conditional safety propositions.** Under nine explicit assumptions (A1–A9: boundary/cryptography, atomic serialization, complete context/time, lifecycle order & non-recycled scopes, verification objects), three propositions hold: owner-bound stable outcome, single exact continuation, and at-most-once accepted effect.

## Methodology

The paper is a **systems specification + model-checking** contribution, not an empirical ML evaluation. Its method has three layers:

1. **Formal system model (Section 2).** Agent state is partitioned into branches k = (sid, bid) holding typed component state X[k] (memory records, profiles, tool configs, policy objects). The kernel configuration is C = ⟨X, B, Γ, S, t⟩, where B is the branch directory, Γ the pre-state authority context, S persistent metadata stores (outcomes, receipts, lineage, effects, quarantine), and t trusted transaction time. The complete head type h = ⟨sid, bid, seq, root, v, parentRef, lineageRef⟩ is canonical; two heads are equal iff every encoded field agrees. CK introduces **no new low-level transaction engine** — it relies on existing substrates (relational DB transactions, conditional object manifests, consensus state-machine logs) to execute its single atomic step; the contribution is the activation contract enforced within that step.

2. **Activation protocol (Section 3).** Preparation (off-commit, slow, fallible) authenticates ownership, acquires exactly the evidence declared by the proposal (one-to-one, no omissions or injections), runs the pinned transition function, and seals the candidate. Activation then evaluates the ordered 17-stage vector Gkind in a single serialized transaction, accepting only an all-Pass vector. Candidate construction follows a strictly cycle-free order: Pᵦ → WellFormedness → receipt rC → head h′ → accepted unit Uaccept. Four receipt variants (rP, rA, rQ, rC) are normatively fixed, each with a closed stage-reason map (Table 10). An acyclic hash graph (Appendix B) guarantees every digest edge points left, so the audited construction graph is cycle-free.

3. **Bounded executable model (Section 5).** A Python (stdlib-only) model at `artifacts/bounded_model.py` performs exhaustive BFS over a finite abstraction: one active branch, shared admission/creation contexts, one honest and one adversarial proposer, 13 proposal IDs, 4 effect IDs, source + two target writers, and integer versioning. It simulates all five closed transition kinds, exact-head concurrency races, self-authorizing proposals, missing/malformed evidence, two-stage freshness expiration, resubmissions, watermark reclamation, writer fencing, retargeting, and masked restoration. Three propositions (owner-bound stable outcome, single exact continuation, at-most-once effect) are checked as invariants at every reachable state.

## Results & Highlights

- **Zero invariant violations over the full reachable state space.** Across all 2,808,230 reachable states (depth-7 BFS) and 5,526,474 state-changing transitions, the model found **zero** encoded invariant violations and reached 100% of the named coverage witnesses (Commit/Reject/Quarantine/Defer all reached; 17 activation stages evaluated in normative order; self-authorizing proposal rejected at pre-state; freshness revalidated twice; safe watermark reclamation; at-most-one successor per head; stale/abandoned writer blocked; full handoff lifecycle; masked restoration with protected current fields).
- **Self-authorizing proposals rejected 395,905 times.** When the adversarial proposer injected its own required permissions into the authority-change sequence `a`, the Authorization stage evaluated AuthorizeΓ(τ, W) against the pre-state context and returned RejectUnauthorized for 395,905 transitions (4.46% of all 8,880,248 attempts), directly demonstrating the anti-self-authorization property.
- **Concurrency/replay isolation dominates the outcome distribution.** Of 8,880,248 total transition attempts: Commit (head advance) = 916,956 (10.33%); IdReuseConflict = 1,673,300 (18.84%); ReclaimedEffects = 842,195 (9.48%); RejectStaleHead = 770,555 (8.68%); Defer (Missing Evidence) = 418,375 (4.71%); RejectUnauthorized = 395,905 (4.46%). Concurrency and identifier-reuse protections (RejectStaleHead + IdReuseConflict + ReclaimedEffects) together account for 37.00% (3.28M transitions), which the authors cite as evidence the protocol actively isolates concurrent races and stale proposals rather than letting them silently succeed.
- **Single-threaded transition throughput.** On a standard single-threaded CPython 3.13.9 harness, kernel transition evaluation achieved **31,132 transitions/sec** with an **average evaluation latency of 32.12 µs per transition** (this is the abstract-model evaluation cost, not a deployed-storage number).
- **No quantitative results on a real agent workload or benchmark.** There is no end-to-end comparison against MemGPT, Mem0, MemOS, MemTX, or any deployed agent framework on a real task; no latency/throughput measurement against a production storage engine (PostgreSQL/FoundationDB/Raft); and no human-or-LLM evaluation of agent behavior under CK governance. The "results" are model-checking statistics of the specification, which the authors acknowledge explicitly in RQ4.

## Authors & Credibility

- Authors are **Jun He and Deying Yu**, affiliated with **OpenKedge.io** (no university affiliation listed). The same authors published the broader "Persistent Cognitive Identity (PCI)" position/architecture manuscript [7], of which this paper is a narrower, more formal subsystem contribution — so this is part of an ongoing single-group research program rather than an independent replication.
- The paper is unusually rigorous in its self-scoping: it lists nine explicit assumptions (A1–A9), states that its propositions are *conditional* serialization arguments that "establish neither content truth nor correctness of policy, canonicalization, cryptography, or storage implementations," and devotes Section 5.3 / RQ4 to enumerating exactly what the model does NOT prove (physical storage crashes, WAL failures, network partitions, storage-engine bugs).
- The formal apparatus (typed digests, closed stage-reason maps, acyclic hash graph, total lifecycle postconditions in Appendix C) is internally consistent and detailed enough to be implementable, which is a genuine strength for a specification paper. However, no reference implementation beyond the bounded model checker is provided, and there is no third-party adoption or deployment evidence.

## Critical Assessment

- **Novelty:** Genuine and well-positioned. The framing "retention ≠ authority" and the activation-contract separation cleanly distinguish CK from the closest related work: MemTX/MemTxn stage *belief* or *memory-update* commits, whereas CK specifies a typed *branch-head* transition with pre-state authority and four-way outcomes, and composes RIFL-style linearizable retries, OCC, and consensus fencing into a single agent-state contract. The four-level receipt calibration (Structural/Attested/Replay/Inclusion) and the explicit "signature ≠ durable inclusion" caveat are a thoughtful contribution to the agent-memory governance literature.
- **Rigor:** Strong on the formal side (closed maps, acyclic construction order, conditional propositions with proofs in Appendix B), but the evaluation is **model-checking of an executable specification, not validation of a running system**. The bounded abstraction fixes only 13 proposal IDs, 4 effect IDs, one branch, one honest + one adversarial proposer, and integer versioning — so the "2.8M reachable states" reflect a deliberately small finite domain, not a realistic state space. A reviewer should not read "zero invariant violations over 2.8M states" as evidence of correctness at scale; it is evidence of internal consistency within the chosen finite bounds.
- **Reproducibility:** Good in principle — the model is pure Python stdlib (`artifacts/bounded_model.py`) and the state-space numbers (depth, state counts, timing) are reported precisely enough to re-derive. But no artifact release is confirmed in the text, and the *production realization* (the actual storage-engine integration the paper claims to be substrate-agnostic over) has no reference implementation, so the implementability claims are unverified.
- **Significance:** Conceptually significant for the agent-infrastructure subfield if adopted; practically unproven. The paper does not demonstrate that the 17-stage, double-freshness, prospective-unit-construction overhead (32.12 µs/transition in single-threaded Python) is acceptable in a real high-throughput agent loop, nor that the contract composes correctly with a concrete substrate under faults.
- **Red flags / overclaiming:** The authors are commendably restrained — they explicitly label the model's limits in RQ4 and state the propositions are conditional. The main overclaim risk is **framing**: an abstract headline ("2.8M states, zero violations") could be misread as an empirical systems result when it is a finite-domain model-checking result. The closest baselines (MemTX arXiv:2607.23929, MemTxn arXiv:2607.27834) are discussed only qualitatively, with no head-to-head capability or performance comparison — a notable missing ablation given that the paper's novelty rests on differentiating from them. There is also no adversarial evaluation beyond the single self-authorizing-proposal injection; richer attack classes (Byzantine evaluators, collusion, clock manipulation) are out of scope by assumption A6 but not discussed empirically.

## Strengths

- Crisp, load-bearing conceptual distinction: *authority is reachability from the committed head*, not storage presence — this reframes a real gap in current agent-memory systems (MemGPT/Mem0/MemOS optimize retrieval but do not define which version is authoritative under concurrent mutation).
- Honest, explicit assumption surface (A1–A9) and conditional propositions; the paper never claims the model proves physical-storage correctness.
- The typed lifecycle treatment (handoff Fence→Activate gap preventing split-brain on crash; forward-only Restoration that cannot revive old credentials) is a concrete, implementable safety design rather than vague architecture-speak.
- Four-level receipt calibration correctly separates cryptographic signature from durable transactional inclusion — a subtlety many agent-memory papers conflate.
- Acyclic, fully-specified hash-construction order (Appendix B, Table 12) makes the lineage auditable and the proof structure checkable.

## Limitations

- **No deployed-system evaluation.** All numbers come from an executable finite abstraction; there is no measurement against PostgreSQL conditional updates, FoundationDB OCC, or Raft under faults, despite these being named as the realization substrates.
- **Small bounded domain.** 13 pids × 4 eids × 1 branch × 2 proposers is far from a production state space; scaling behavior and state-space explosion beyond depth 7 are not characterized.
- **No baseline comparison.** MemTX and MemTxn — the explicitly identified closest related systems — are compared only narratively; no shared benchmark, capability matrix, or overhead comparison is provided.
- **Narrow threat model.** Only the self-authorizing-proposal attack is exercised; Byzantine evaluators, colluding proposers, and trusted-time manipulation are excluded by assumption rather than defended against.
- **Performance overhead unvalidated at scale.** 17 sequential stage checks, double freshness validation, and prospective-unit construction add commit-time cost that the authors themselves flag as needing storage-level optimization (single-pass SQL procedures, batched multi-key compare-and-swap), but no such optimization is measured.
- **External side-effect atomicity is explicitly out of scope.** CK cannot make a remote API call or robot actuation atomic with a state update — an honest limit, but one that means the contract covers only internal state, not the end-to-end agent effect chain.
- **Single-author-group provenance.** Both this paper and the PCI framework it builds on [7] are by the same two authors at OpenKedge.io; independent replication or adoption is not yet evidenced.

## Relevance

对一个关注"长生命周期智能体的记忆/状态治理与可靠性"的研究方向高度相关：它把数据库事务、乐观并发控制和共识 fencing 的思想系统性地引入智能体状态管理，正弥补了当前 MemGPT/Mem0/MemOS 等工作"只优化检索、不定义权威版本"的缺口，可作为构建可信赖智能体存储层的理论基础。若你的兴趣集中在纯模型能力（如推理、对齐、微调）而非系统/基础设施层面，则本文的工程契约式风格可能偏离主线，但其"激活契约"思路对设计多智能体协同与工具状态一致性仍有借鉴价值。

## Questions for Further Exploration

- How does CK's 17-stage activation overhead (32.12 µs/transition in Python) translate to a production substrate — e.g., a single-pass PostgreSQL stored procedure or a batched FoundationDB transaction? Is the contract practical at 10k+ proposals/sec?
- Can the bounded model be extended beyond 13 pids / 4 eids / 1 branch to characterize state-space explosion, or replaced by a symbolic/SPIN-style model checker to lift results from finite-domain to unbounded?
- A head-to-head capability and overhead comparison against MemTX (arXiv:2607.23929) and MemTxn (arXiv:2607.27834) on a shared agent-memory workload would directly substantiate the claimed differentiation. Is such a benchmark feasible?
- How should CK compose with external side effects that cannot be made idempotent (e.g., non-reversible payments, physical actuation)? The outbox-intent pattern is sketched but not specified — what is the weakest connector contract that preserves at-most-once accepted effects?
- Under a Byzantine evaluator (violating assumption A6's trusted-time/policy correctness), which of the three propositions still hold, and what minimal additional mechanism (e.g., evaluator quorum) restores them?
- Does the activation-contract pattern generalize beyond agent memory to other versioned-authority domains — e.g., multi-agent policy rollout, tool-credential lifecycle, or federated agent state synchronization across substrates?
