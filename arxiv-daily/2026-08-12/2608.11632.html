§ 01

Methodology

specification + executable model · not an empirical ML eval

The Continuity Kernel (CK) is a control plane — an activation contract — not a new storage engine. It relies on existing substrates (relational DB transactions, conditional object manifests, consensus logs) to execute one atomic step; the contribution is the contract enforced within that step.

Agent state is partitioned into branches k=(sid,bid); configuration C=⟨X,B,Γ,S,t⟩ fixes the canonical head type. An object is authoritative iff reachable from the current committed branch head — storage presence alone confers nothing.

Untrusted proposers sign typed candidates off-commit; activation then evaluates an ordered 17-stage vector in a single serialized transaction, accepting only an all-Pass result and emitting one of four terminal dispositions.

  1. Formal model (§2). Branches hold typed component state; authority = reachability from head; pre-state context Γ is always evaluated, never the proposed successor — so a proposal cannot self-authorize.
  2. Activation protocol (§3). Off-commit preparation (slow, fallible) is separated from a short atomic transaction. Candidate construction follows a strictly cycle-free order; an acyclic hash graph guarantees every digest edge points left.
  3. Bounded model (§5). A Python stdlib model (bounded_model.py) exhaustively BFS-explores a finite abstraction, simulating all five transition kinds, concurrency races, self-authorizing proposals, freshness expiry, and masked restoration — checking three propositions as invariants at every state.

§ 03

The Four Terminal Dispositions

each terminal & replayable per proposal id

Commit

Atomically installs the full accepted unit; the only disposition that advances the head.

Reject

Authorization / head / evidence failure; authoritative state untouched.

Quarantine

Suspicious but non-terminal data; isolated, head untouched. Resubmit with new pid.

Defer

Missing evidence; recoverable. Requires a new pid linked to the old attempt.

§ 04

Strengths & Limitations

balanced read

Strengths

  • Crisp load-bearing distinction: authority = reachability from the committed head, not storage presence — reframes a real gap left by MemGPT/Mem0/MemOS.
  • Honest, explicit assumption surface (A1–A9); never claims the model proves physical-storage correctness.
  • Typed lifecycle design — handoff Fence→Activate gap prevents split-brain on crash; forward-only Restoration cannot revive old credentials.
  • Four-level receipt calibration correctly separates cryptographic signature from durable transactional inclusion.
  • Acyclic, fully-specified hash-construction order (Appendix B) makes lineage auditable and the proof checkable.

Limitations

  • No deployed-system evaluation. Numbers come from a finite abstraction; no measurement against PostgreSQL / FoundationDB / Raft under faults.
  • Small bounded domain (13 pids × 4 eids × 1 branch × 2 proposers); state-space explosion beyond depth 7 is uncharacterized.
  • No baseline comparison — MemTX / MemTxn (the closest related systems) are compared only narratively.
  • Narrow threat model — only the self-authorizing-proposal attack is exercised; Byzantine / collusion excluded by assumption.
  • Performance overhead unvalidated at scale; 17 stages + double freshness + prospective-unit construction need storage-level optimization.
  • External side-effect atomicity (payments, actuation) is explicitly out of scope.
  • Single-author-group provenance (OpenKedge.io); no independent replication yet.

Questions for Further Exploration

  1. Does the 17-stage overhead (32.12 µs) hold at 10k+ proposals/sec on a single-pass PostgreSQL procedure or batched FoundationDB transaction?
  2. Can the bounded model extend beyond 13 pids / 4 eids / 1 branch, or be replaced by a symbolic / SPIN-style checker to lift results from finite-domain to unbounded?
  3. A head-to-head capability & overhead comparison vs MemTX (2607.23929) and MemTxn (2607.27834) on a shared workload — feasible?
  4. How should CK compose with non-idempotent external effects? What is the weakest connector (outbox-intent) contract that preserves at-most-once accepted effects?
  5. Under a Byzantine evaluator (violating assumption A6), which of the three propositions still hold, and what minimal mechanism restores them?
