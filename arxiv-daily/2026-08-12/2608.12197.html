Key finding

Compound netlist editing collapses from ~80% toward 0% as edits accumulate — even reasoning can’t preserve circuit structure.

NetlistBench 用 2,342 个用例、规范化电路 IR 精确匹配判分，发现局部删除/参数编辑可达 96%–100%，但多步复合编辑随步数从 ~80% 急剧退化为 0%，表明网表结构保持是 LLM 电路设计自动化中被忽视的独立瓶颈。

Key metric
0%

Floor of 15-step compound editing — 3 of 6 models collapse here (DeepSeek-V4-Flash, Qwen3.6-Flash, Qwen3-30B), down from ~80% at 3 steps. Claude Sonnet 4.6 holds highest at 26%.

Why this matters

Quantifies a real gap in LLM-driven EDA: models break netlist structure under multi-step edits, blocking trustworthy automated circuit-editing tools.

⚠ Critical edge

Scope is narrower than the framing: only analog CMOS is tested — generalization to the industrial post-layout decks where LLM-EDA tools must actually operate is entirely untested.

Methodology

A structure-aware oracle, not string match

Built from two SPICE sources: AnalogGenie (2,838 flat CMOS netlists, ~58k device instances; Simple / Medium / Complex bins) and ALIGN (931 hierarchical netlists, 21 topology families, 3–4 subcircuits each).

Each case is a deterministic triplet (source, instruction, target) covering recognition (800 cases, 8 families) and manipulation (1,542 cases, 16 families: single edits, flat compound chains of 3/6/9/12/15 dependent edits, hierarchical ops).

Both model output and reference parse to a canonical circuit IR — device set, ordered terminal–node bindings, normalized parameters, top directives, subcircuit ports. Scoring is exact match up to semantics-preserving normalization, catching node renames, dropped/duplicated devices, and locality loss that string-match or final-simulation checks miss. Equivalence-judgment labels are additionally VF2 graph-isomorphism audited.

Reproducibility
Templated, construction-time-validated cases · seeded generators · per-family prompt templates · public oracle & runners · github.com/WoshiMayou/NetlistBench (Apache-2.0 / CC BY 4.0). Caveat: evaluated proprietary models are unpinned API snapshots.

Strengths
  • Clean isolation of representation-level netlist ops from high-level design reasoning — fills a real gap left by end-to-end circuit-LLM benchmarks.
  • Deterministic, VF2-audited ground truth; fully reproducible via a public repo.
  • Canonical-IR oracle catches exactly the failures (node rename, dropped device, terminal rebinding, locality loss) that string/simulation checks miss.
  • Long-horizon sweep (3–15 dependent edits) yields a striking, interpretable degradation curve.
  • Honest mitigations: reasoning helps but doesn’t close the gap; PySpice helps inconsistently (sig. for one model, null for another).
  • Statistical care — Wilson CIs, McNemar paired tests — above the LLM-benchmark norm.
Limitations
  • Narrow circuit domain — analog CMOS only; no .param/.model/behavioral/parasitic/PDK syntax; no RF/power/digital/mixed-signal.
  • Block-level netlists that fit context windows; no extracted post-layout decks or long-context retrieval.
  • Single query per case; sampling/temperature variance unquantified; reasoning results are single-sample.
  • Proprietary API models without version pinning undermine long-term numerical reproducibility.
  • Templated, unambiguous instructions don’t reflect the linguistic ambiguity of real designer prompts.
  • No error-mode breakdown by circuit size (5 vs 36–69 devices) or perturbation type.
Open questions

Questions for further exploration

  1. How do pass rates and error modes scale with circuit size (5 vs 36–69 devices) within one operation family?
  2. Would a graph-structured circuit representation outperform raw SPICE/PySpice text on compound edits, and by how much?
  3. Can a decompose-edit-verify loop (structural check + feedback after each atomic edit) recover long-horizon reliability, at what compute cost?
  4. Do structure-preservation failures transfer to digital/RF/power/mixed-signal and extracted post-layout decks with parasitics?
  5. How stable are model rankings under multi-sample decoding and across API versions, given the single-sample protocol?
