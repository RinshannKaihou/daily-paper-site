> **一句话总结：** ADEPT 是一个面向深度学习测试充分性评估的统一开源框架，将神经元覆盖（NC 系列）、惊奇充分性（LSA/DSA）、输入分布覆盖（IDC）、决策边界覆盖（DBC）以及源码/模型级变异得分（SLMS/MLMS）等代表性指标整合到一致的预处理-缓存-打分工作流中，以解决这些指标实现高度碎片化、难以复现与对比的实际痛点。

> **TL;DR:** ADEPT (SPLASH Companion '26, Auburn University) is a Python/Keras tool paper that unifies fragmented deep-learning test-adequacy metrics — the NC-series (NC, TKNC, KMNC, NBC, SNAC), surprise adequacy (LSA/DSA), Input Distribution Coverage (IDC), Deep Boundary Coverage (DBC), and source-/model-level mutation score (SLMS/MLMS) — behind one template-based plug-in interface, YAML config, an intermediate-artifact cache, and structured JSON reporting. It is a *framework/engineering* paper and reports no comparative quantitative experiments of its own; its evidence is the integrated architecture (Fig. 1), the metric-config table (Table 1), a worked CLI example, and a public Zenodo release + demo video.

## 核心贡献

- **统一框架 ADEPT**：将十余年来分散提出的 DL 测试充分性指标（神经元覆盖率及其变体、惊奇充分性、输入分布覆盖、决策边界覆盖、源码/模型级变异得分）整合到单一、一致的工作流中，解决了各原型在安装、预处理、执行与配置上的严重异构问题。
- **模板化指标插件接口**：每个指标实现为遵循同一框架抽象的独立模块，保留各自特定的处理与打分逻辑；新指标只需实现该模板接口即可接入，具备良好的可扩展性。
- **可复用的中间产物缓存**：针对神经元剖面、激活迹、VAE 编码器、决策边界模型、变异体等"生成昂贵但可跨次复用"的产物提供缓存管理组件，支持用户选择复用或重新生成，显著降低重复评估开销并保留可复现性与实验可追溯性。
- **一致的配置与报告**：基于 YAML 的配置管理（含各指标默认值兜底）以及结构化 JSON 报告（充分性得分、预处理时间、打分时间、缓存利用率），使得不同指标可在同一评估设置下被检视与对比。
- **公开可用**：代码与 `environment.yml` 发布于 Zenodo (https://aub.ie/ADEPT_video 演示视频)，降低研究者和从业者复现与采用这些指标的工程门槛。

## Key Contributions

- **A unified framework, ADEPT**, that integrates representative DL test-adequacy metrics that have been published over the past decade as independent, hard-to-reconcile research prototypes (neuron-coverage family, surprise adequacy, input-distribution coverage, boundary coverage, and source-/model-level mutation score) under one consistent execution workflow.
- **A template-based metric plug-in interface**: each metric is an independent module conforming to a common framework-level abstraction (unified entry point, preprocessing, scoring) while preserving metric-specific execution logic, giving well-defined extension points for adding new metrics.
- **A reusable intermediate-artifact cache**: caches costly-to-generate-but-reusable artifacts (neuron profiles for KMNC/NBC/SNAC, activation traces for LSA/DSA, VAE latent models for IDC, decision-boundary models for DBC, generated mutant models for SLMS/MLMS), keyed by target model, dataset, metric, and creation time, letting users reuse or regenerate them.
- **Consistent configuration and reporting**: YAML config files with sensible per-metric defaults (used when no config is supplied) and structured JSON output capturing the adequacy score plus preprocessing time, scoring time, and cache-utilization metadata, enabling apples-to-apples comparison across metrics.
- **A public, reproducible release** on Zenodo (records/21682100) with `environment.yml` and a YouTube demo video, directly targeting the well-documented practitioner pain point that existing DL testing tools suffer from heterogeneous workflows, high adoption barriers, limited integration, and missing/maintenance-starved public implementations.

## Methodology

ADEPT is a framework/tool, not an empirical study, so its "methodology" is its architecture. The paper (Section 2 + Figure 1) describes four cooperating components:

1. **Unified Metric Interface.** Each adequacy metric is wrapped as a plug-in module behind a single CLI entry point (`python -m adequacy.cli run --metric ... --model ... --dataset ... --test-data ... --test-labels ... --config ...`). The user supplies the test dataset, target (Keras) model, optional training data, and metric name; ADEPT internally dispatches to the right processing pipeline, so users never manually coordinate metric-specific execution requirements. New metrics are added by implementing the template interface.

2. **Metric-Specific Processing modules.** Because metrics need very different preprocessing, each gets a dedicated module: KMNC/NBC/SNAC require neuron profiling over the training set; LSA/DSA require activation-trace extraction and density estimation; IDC relies on a separately trained VAE plus combinatorial-interaction testing over latent features; DBC performs bisection-based decision-boundary extraction; MLMS is implemented à la DeepMutation++ and SLMS à la DeepCrime (generating mutants and computing the killed/total ratio).

3. **Cache Management.** Reusable artifacts are stored keyed by (target model, dataset, metric, creation time). When compatible cached artifacts exist, ADEPT prompts the user to either reuse them (skip processing, go straight to scoring) or regenerate them, trading off speed against reproducibility.

4. **Adequacy Scoring & Reporting.** Coverage-based metrics (NC-series, DBC, IDC interaction coverage) report covered proportions; LSA/DSA derive scores from activation-trace distributions; SLMS/MLMS report the classic mutation score MS = |killed mutants| / |all mutants|. Each run emits a structured JSON report with the score plus timing and cache metadata.

Supported metric families: NC-series (NC, TKNC, KMNC, NBC, SNAC), surprise adequacy (LSA, DSA), IDC, DBC, and mutation scores (SLMS, MLMS). Inputs are NumPy `.npy` files; models must be Keras-based. Metric behavior is tuned via YAML config files (Table 1 documents representative parameters such as `train_fraction`, `exclude_layer`, `layer_names`, `var_threshold`, `beta`, `max_per_pair`, `vae_model_dir`, `ways`, `num_mutants`, `mode`, `mutation_operators`, `cache_mutants`).

## Results & Highlights

No quantitative results reported.

This is an engineering/tool paper: it presents no experiments comparing metrics, no benchmark accuracy/robustness figures, and no measurements of ADEPT's own runtime or cache-speedup. The evidence it offers instead is qualitative and structural:

- **Coverage of the metric space**: ADEPT integrates 4 distinct adequacy *paradigms* — structural (NC-series: NC, TKNC, KMNC, NBC, SNAC), input-space (LSA/DSA surprise adequacy; IDC feature-interaction coverage), boundary-based (DBC), and mutation-based (source-level SLMS à la DeepCrime, model-level MLMS à la DeepMutation++) — under one workflow, whereas prior public implementations (DeepXplore, IDC, DeepCrime) each cover only a single metric.
- **Engineering properties**: template-based plug-in extensibility for new metrics, YAML configuration with documented per-metric defaults (Table 1, 11 parameters across metric groups), reusable caching of intermediate artifacts keyed by model/dataset/metric/time, and structured JSON reporting (score + preprocessing time + scoring time + cache utilization).
- **Availability & reproducibility**: source code on Zenodo (record 21682100) with a pinned `environment.yml`, plus a demo video (https://aub.ie/ADEPT_video), and a worked end-to-end CLI usage example in Section 3.
- **Practitioner motivation**: the paper grounds its motivation in a recent empirical interview study (You et al., ICSE 2025 [18]) reporting that DL practitioners find existing testing tools difficult to use due to heterogeneous workflows, high adoption barriers, limited integration, and missing implementations.

## Critical Assessment

- **Novelty**: The contribution is engineering/integration, not a new metric. Unifying existing metrics is genuinely useful given the documented fragmentation, but the intellectual novelty is modest — there is no new adequacy criterion, no new scoring theory, and no new empirical finding about *which* metric works best.
- **Rigor**: This is the main weakness. The paper does **not** validate that ADEPT's integrated metrics reproduce the original papers' reported numbers — there is no reproduction table (e.g., "ADEPT's KMNC on model X matches DeepGauge's published KMNC"). Nor does it measure the framework's own value proposition quantitatively: the cache-reuse speedup, which is the single most concrete engineering claim, is never benchmarked (no "reuse gives Nx speedup, here is the wall-clock table"). Without at least one such measurement, the cache component's benefit is asserted rather than demonstrated.
- **Reproducibility**: Strong on packaging (Zenodo DOI, `environment.yml`, demo video, public GitHub) but narrow on scope — inputs are restricted to NumPy `.npy` arrays and models to **Keras only**. PyTorch / JAX / ONNX users cannot use ADEPT as-is; this is a meaningful adoption limitation the paper does not bound or address.
- **Significance**: Real but incremental. If maintained and extended, ADEPT could become a useful community benchmark harness; as a 6-page companion paper it is a position/tool artifact, not a landmark.
- **Red flags / specific gaps**: (1) No ablation on cache hit-rate sensitivity to the (model, dataset, metric, creation-time) key — e.g., how a model checkpoint change invalidates the cache is unspecified. (2) Table 1 lists config parameters but gives no recommended ranges or sensitivity guidance (e.g., DBC's `beta` convergence threshold, IDC's `ways` t-way strength). (3) The claim that mutation score "à la DeepMutation++ / DeepCrime" is faithfully reimplemented is unverified. (4) No discussion of statistical determinism for mutation-based metrics (number of mutants, RNG seeding) beyond a `num_mutants` config knob. (5) Future work is a single sentence ("incorporate more metrics"); no roadmap for PyTorch support or for a head-to-head metric-effectiveness benchmark.

## Strengths

- Addresses a real, well-cited problem (fragmented, hard-to-reuse DL testing metrics) corroborated by a recent practitioner interview study (ICSE 2025).
- Clean, sensible four-component architecture (interface, processing, cache, scoring) that genuinely matches the heterogeneity of the underlying metrics.
- Template-based plug-in design makes adding new metrics low-friction, which is the right property for a "continuously evolving platform."
- Cache-reuse mechanism is the most practically valuable idea — reusing neuron profiles, activation traces, VAEs, boundary models, and mutants across repeated evaluations is exactly the kind of redundancy that plagues these metrics.
- Honest, well-structured related-work taxonomy organized by classical coverage perspectives; correct attribution to originating works.
- Public, DOI-archived artifact with environment pinning and a demo video — meets the bar for a companion-track tool paper.

## Limitations

- **No quantitative evaluation**: no metric-reproduction validation, no cache-speedup benchmark, no cross-metric effectiveness comparison. The paper is description-only.
- **Keras-only / `.npy`-only**: excludes the large PyTorch/JAX ecosystem and any non-NumPy data pipelines; a major scope ceiling not discussed.
- **Cache-key semantics underspecified**: how partial changes (model fine-tuning, a new data split) interact with the `(model, dataset, metric, time)` key and cache invalidation is not defined.
- **Mutation-metric fidelity unverified**: reimplementations "à la" DeepMutation++/DeepCrime are not checked against the originals, and RNG/mutant-count determinism is not discussed.
- **No sensitivity/usage guidance** for the config parameters in Table 1 — users are left to guess good values for `beta`, `ways`, `var_threshold`, etc.
- **6-page format** necessarily leaves depth on the table; no case study or end-to-end worked example with real numbers showing ADEPT selecting or prioritizing a test subset.
- **Author-maintained future-work** is thin ("incorporate more metrics"); no commitment to non-Keras backends or to becoming the community benchmark harness the paper aspires to.

## Relevance

ADEPT 与深度学习测试/可信性评估直接相关：它为神经元覆盖、惊奇充分性、决策边界、变异得分等"如何衡量测试集本身是否充分"的指标提供了统一、可复现的工程入口，对于从事 DL 鲁棒性、测试用例优先级排序与测试集质量评估的研究者是一个有价值的工具基座（尽管它本身不提出新指标，也未做定量对比实验）。

## Questions for Further Exploration

- Does ADEPT's reimplementation of each metric (KMNC, LSA/DSA, IDC, DBC, SLMS/MLMS) numerically reproduce the values reported in the original papers on a shared benchmark (e.g., MNIST/ACPU/CIFAR-10 with a common Keras model)? A reproduction table is the obvious missing validation.
- What is the measured wall-clock speedup from cache reuse for the most expensive metrics (SLMS/MLMS mutant generation, IDC VAE training, DBC boundary search), and how sensitive is it to cache-key granularity (e.g., model checkpoint hash vs. model path)?
- How should the cache key handle partial changes — a fine-tuned model, a new data split, a different random seed — to avoid silently stale or incorrectly invalidated artifacts?
- Given Keras-only support, what is the migration path to PyTorch/JAX/ONNX, and is a backend-agnostic abstraction (e.g., via ONNX or a hook-based activation API) feasible without sacrificing per-metric processing fidelity?
- Across the integrated metrics, which best predict real fault-detection / robustness on a held-out set of bugs (e.g., DeepCrime real faults), and can ADEPT be extended into a head-to-head metric-effectiveness benchmark rather than just an execution harness?
- For the config parameters in Table 1 (e.g., DBC `beta`, IDC `ways`, LSA `var_threshold`), what are stable recommended ranges, and how much does the adequacy score vary with each — i.e., which knobs actually matter?
