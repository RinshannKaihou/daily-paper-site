Methodology

A differential-testing-inspired contrastive design. For every task the authors fix the instruction, repository state, verifier, agent framework, and model — then vary only the skill setup, running two paired comparisons: audited-skill vs no-skill, and audited-skill vs a semantically-matched public skill.

A run yields a correctness outcome (deterministic verifier) and a cost outcome (tokens + time). Two failure classes follow: functional failure (target FAILs while a reference PASSes) and efficiency regression (both PASS, but cost explodes past a conservative threshold T=2.0, which excludes token↔time tradeoffs).

Subjects are SkillsBench (84 tasks, 11 domains) and SWE-Skills-Bench (490 repo-based SE tasks). The comparison space is expanded 25× by retrieving public skills from smithery.ai and skillsmp.com (all-MiniLM-L6-v2, cosine ≥ 0.7). All execution uses OpenCode 1.15.1 + Claude Opus 4.6. From 665 labeled candidates, group-consensus refinement yields 307 confirmed cases, which SkillTRIAGE then attributes in three stages: input normalization → differential-evidence extraction → attribution reasoning.

Strengths & Limitations

▲ Strengths

  • Contrastive framing isolates the skill as the cause — the conceptual gap the field was missing.
  • Taxonomy grounded in real annotated trajectories with worked examples (openpyxl ESM, LangChain AM, net-exports IRF).
  • Crisp design rule: context-overhead regressions are 43/46 from the always-loaded skill body — keep mandatory bodies short, lazy-load the rest.
  • SkillTRIAGE exposes cited evidence (section, step, artifact diff), not just a label — right design for a debugging aid.
  • Honest, measured claims; repeatedly distinguishes what the tool can and cannot do.

▼ Limitations

  • Single stack: one runtime (OpenCode 1.15.1), one primary model (Claude Opus 4.6) — generalization unverified.
  • T=2.0 threshold under-explored for sensitivity; the EP/CO split could shift at other cutoffs.
  • The 665→307 refinement relies on manual judgment whose exact rules are not fully formalized.
  • Accuracy materially weaker on cross-skill (63.0%) and EP-subset (64.4%) cases.
  • Reference-run-as-pseudo-oracle means failures breaking every config are invisible.
  • No longitudinal study of skill updates or marketplace churn — a snapshot.

Open Questions for Further Exploration

  1. Does the taxonomy hold across GPT-class vs Claude-class vs open-weight models and other agent runtimes?
  2. How does the TIF / EP / CO distribution shift at alternative thresholds (T = 1.5, 2.5, 3.0)? Is "EP dominates" robust to the cutoff?
  3. Can skill-task compatibility become a cheap pre-execution gate preventing a meaningful fraction of the 86 TIF cases before tokens are spent?
  4. For the 67 Excessive Verification cases, can a budget-aware "verification budget" recover cost without sacrificing correctness?
  5. Would fine-tuning a smaller model on SkillTRIAGE traces approach GPT-5.5 accuracy at far lower cost?
