> **一句话总结：** 本文用差分测试式的对照实验（有/无技能、跨技能对比）在 SkillsBench 与 SWE-Skills-Bench 上确认了 307 例技能诱导的 Agent 失败（125 例功能性失败 + 182 例效率回退），发现绝大多数功能性失败来自"看似相关却误导实现"的技能而非无关技能（Task-Implementation Fault 占 68.8%），效率回退主要由 Excessive Procedure（62.6%）而非单纯的 prompt 长度造成，并据此构建了 SkillTRIAGE 归因工具。

> **TL;DR:** Using a differential-testing-style contrastive setup (no-skill vs audited-skill, and cross-skill), the authors mine 307 confirmed skill-induced failures on SkillsBench and SWE-Skills-Bench (125 functional + 182 efficiency regressions) with OpenCode 1.15.1 + Claude Opus 4.6, and show that on-topic skills — not obviously irrelevant ones — drive most functional failures (Task-Implementation Fault = 68.8%), that Excessive Procedure (not prompt length) dominates efficiency regressions (62.6% of 182 at the T=2.0 threshold, with Excessive Verification alone at 67 cases), and that their SkillTRIAGE tool matches manual exact subcategories for 88.8% (functional) and 72.5% (efficiency) of cases.

## 核心贡献

- **首次系统化研究"技能诱导的 Agent 失败"**：将"加载了某个技能后任务失败或代价大幅上升"这一类问题独立出来，区别于 base-agent 能力不足或普通运行方差。
- **差分测试式对照实验框架**：固定任务、验证器、仓库/容器状态、模型与 agent 框架，仅改变 skill 设置（无技能 vs 被审计技能；或跨语义匹配技能），用 reference run 作为伪 oracle，把失败/回退归因到具体技能。
- **大规模对照数据集**：通过从 smithery.ai、skillsmp.com 检索语义匹配的公开技能（all-MiniLM-L6-v2，top-5、cosine ≥ 0.7），把对照空间从原始的 826 个配对扩展到 20,664 个（约 25×），最终确认 307 例技能诱导失败（125 功能性 + 182 高置信度效率回退）。
- **两类失败的根本原因分类法（taxonomy）**：功能性失败分 4 大类（APM/EM/TIF/AM，7 个子类），效率回退分 3 大类（CO/EP/DO，7 个子类），每个案例唯一归类，并通过组内共识定稿。
- **SkillTRIAGE 归因工具**：把人工分类法操作化为三阶段流程（输入归一化 → 差分证据抽取 → 归因推理），产出类别、子类、自然语言理由、引用证据与修复建议，支持技能市场/平台的规模化筛查。
- **可操作的设计建议**：技能作者应把"必须项"与"示例/默认值/模板/可选工作流"分离；平台应做技能-任务兼容性检查、代价感知的技能打包与选择、预算感知的验证策略。

## Methodology

The study is built around a **differential-testing-inspired contrastive design**. For each task the authors fix the task instruction, repository/container state, data files, verifier, agent framework, and model, and vary only the *skill setup*. Two kinds of paired comparisons are run:

- **With/no-skill**: audited-skill run vs. the same task executed with no skill.
- **Cross-skill**: audited-skill run vs. a run using another *semantically matched* public skill.

A run produces two observable outcomes: a *correctness* outcome (deterministic verifier pass/fail) and a *cost* outcome (token use + execution time). Two failure classes follow naturally:

- **Functional failure**: target run FAILs while a reference run PASSes.
- **Efficiency regression**: both runs PASS, but the target run costs substantially more. Formally a PASS/PASS pair is flagged at threshold T iff `min(r_tok, r_time) > 1.0 ∧ max(r_tok, r_time) > T`, with T = 2.0 as the conservative primary threshold; this excludes token↔time tradeoffs and small fluctuations. Each regression is labeled token-dominant, time-dominant, or joint.

**Study subjects** are SkillsBench (84 tasks, 11 domains, no/curated/self-generated skills) and SWE-Skills-Bench (490 repository-based SE tasks, no/curated skills), both with deterministic programmatic verifiers. To broaden the comparison space the authors augment each curated skill with up to 5 public candidates retrieved from smithery.ai and skillsmp.com via all-MiniLM-L6-v2 embeddings (cosine ≥ 0.7). The agent only loads retrieved skills through the normal loading interface when it judges them relevant — they are not forced into context.

**Execution** uses OpenCode 1.15.1 with Claude Opus 4.6; each pair records loaded skill, trajectory, verifier outcome, token use, and execution time. After collection, 665 labeled candidates (315 functional, 350 efficiency) are refined by removing ambiguous, verifier-narrow, and duplicate cases, and each remaining case is manually labeled by group consensus, yielding 307 final analysis cases.

**SkillTRIAGE** operationalizes the manual taxonomy as an attribution procedure in three stages: (1) input normalization into a shared task view plus target/reference run views with deterministic evidence gates; (2) differential-evidence extraction — five differential signals (DS1–DS5: environment/runtime-state change, skill-induced origin, path match, artifact produced/omitted, construction-difference) for functional failures, and phase-level + action-tag cost deltas (exploration / pipeline / verification / dependency-repair / reference-loading) for efficiency regressions; (3) attribution reasoning that selects the root cause best explaining both the target outcome and the target/reference divergence, returning category, subcategory, cited evidence, and a repair suggestion.

## Results & Highlights

- **Dataset scale and yield**: From the expanded 20,664 potential paired comparisons, the executed evaluations produced 665 labeled candidates refined down to **307 confirmed skill-induced failures** — 125 functional failures and 182 high-confidence efficiency regressions (Table II). This is a 25× expansion of the comparison space over the original 826 paired comparisons (Table I).
- **Functional failures are mostly *on-topic* skill faults**: Only **2/125 (1.6%)** are Applicability Mismatch (obviously irrelevant skills), whereas **Task-Implementation Fault accounts for 86/125 (68.8%)** of functional failures (Table III). Within TIF, Incorrect Required-Element Fill (IRF) = 46 (36.8%) and Required-Element Omission (RRO) = 36 (28.8%). Artifact Misplacement = 24 (19.2%), Environment Mismatch = 13 (10.4%).
- **Efficiency regressions are dominated by procedure, not prompt length**: At T = 2.0, **Excessive Procedure = 114/182 (62.6%)**, Context Bloat = 46 (25.3%), Dependency Resolution = 22 (12.1%) (Table IV). Within EP, Excessive Verification = 67 (36.8%) and Heavy Implementation Pipeline = 30 (16.5%).
- **When context overhead is the cause, the skill body is almost always to blame**: Skill-Body Context Bloat (SBCB) = **43/46** of context-overhead cases; Supplementary-Material Bloat = only 3.
- **SkillTRIAGE attribution accuracy**: On functional failures it matches the manual high-level category for **117/125 (93.6%)** and the exact subcategory for **111/125 (88.8%)** (Table V); within the largest TIF subset it reaches 76/86 (88.4%). On efficiency regressions it matches the category for **145/182 (79.7%)** and the exact subcategory for **132/182 (72.5%)** (Table VI); exact-subcategory agreement within EP is 78/114 (68.4%).
- **Motivating evidence from prior benchmarks** is cited: SkillsBench reports pass-rate drops on **16 of 84** tasks, and SWE-Skills-Bench reports cases with token overhead up to **451%**, motivating the failure-attribution question.

## Critical Assessment

- **Novelty**: High. The unit of analysis — attributing an agent's functional failure or cost regression to a *specific loaded skill document* under controlled contrastive comparison — is genuinely new. Prior skill benchmarks (SkillsBench, SWE-Skills-Bench) measure *aggregate utility*; this paper studies *failure mechanisms*, and the contrastive design is the right tool for that.
- **Rigor**: Strong on labeling discipline (group consensus, dataset refinement, independent SkillTRIAGE check) and on the deterministic-verifier requirement. The efficiency-regression threshold formula (`min > 1.0 ∧ max > T`) is well motivated — it correctly excludes token/time tradeoffs.
- **Weak baselines / missing ablations**: The T = 2.0 threshold is *asserted* as "conservative" but sensitivity to the threshold is only weakly explored; the paper does not report how the taxonomy distribution shifts at, say, T = 1.5 or T = 3.0, so the reader cannot judge how much the 114-EP / 46-CO split is an artifact of the chosen cutoff. SkillTRIAGE is evaluated with a *single* frontier model (GPT-5.5) and 2-of-3 voting; there is no ablation against cheaper models or against single-run attribution, so the cost/value tradeoff of the tool itself is unclear. The selection funnel (665 candidates → 307 cases) is described at the count level but the *filtering criteria* for ambiguous/verifier-narrow/duplicate cases are not fully formalized — a reader cannot reproduce the refinement.
- **Reproducibility concerns**: The reference runs are "pseudo-oracles," not ground truth — the paper is honest about this, but it means a case is only counted as a skill-induced failure if *some* configuration succeeded; failure modes that defeat every skill (including no-skill) are structurally invisible. The agent/model stack is a single point (OpenCode 1.15.1 + Claude Opus 4.6); model-dependence is acknowledged under external validity but not tested.
- **Significance**: The taxonomy and the SkillTRIAGE idea are directly useful for skill-marketplace screening and for skill-author guidelines, and the two strongest findings (on-topic skills cause most functional failures; procedure, not prompt length, dominates regressions) are actionable and non-obvious.
- **Red flags / overclaiming**: Minimal. The cross-skill exact-subcategory accuracy drops to **63.0% (34/54)** and within-EP to **64.4% (29/45)** — the paper reports these honestly rather than hiding them, but it does mean SkillTRIAGE is currently a *triage* aid, not a reliable automatic labeler for cross-skill cases. The 451% and 16/84 motivating numbers are borrowed from cited benchmarks, not reproduced here.

## Strengths

- The contrastive (differential-testing) framing cleanly isolates the skill as the cause, which is the conceptual contribution the field was missing.
- The taxonomy is grounded in real, annotated trajectories with concrete worked examples (the openpyxl ESM case, the LangChain AM case, the net-exports IRF case), making it teachable.
- The finding that *context-overhead regressions are almost entirely from the always-loaded skill body* (43/46) is a crisp, actionable design rule: keep mandatory skill bodies short, lazy-load the rest.
- SkillTRIAGE exposes *cited evidence* (skill section, trajectory step, artifact diff, cost-heavy step), not just a label — this is the right design for a debugging aid.
- Honest, measured claims; the paper repeatedly distinguishes what the tool can and cannot do.

## Limitations

- Only **two benchmarks**, **one agent runtime** (OpenCode 1.15.1), and **one primary model** (Claude Opus 4.6); generalization to other models (e.g., open-weight agents) and other harnesses is unverified.
- The **T = 2.0 threshold** is the primary lens for all efficiency-regression findings, and sensitivity to this threshold is under-explored.
- The 665 → 307 refinement step relies on **manual judgment** (acknowledged as a threat to internal validity) whose exact rules are not fully formalized.
- SkillTRIAGE's accuracy is materially **weaker on cross-skill cases** (63.0% exact subcategory) and on the EP subset (64.4%), limiting its use as a fully automatic labeler.
- The reference-run-as-pseudo-oracle design means **failures that break every configuration are invisible** to the dataset.
- Despite the marketplace motivation, there is **no longitudinal study** of skill updates or of churn at platform scale; the work is a snapshot.

## Relevance

这项研究直接命中"LLM Agent 与可复用技能（skill）"这一核心方向：它揭示了看似相关的技能如何在不改变模型参数的情况下诱导功能性失败与效率回退，并给出了可操作的设计准则（分离必须项与示例、lazy-load 补充材料、代价感知的技能选择）——对于评估和改进 agent 技能生态、技能市场筛查与 SkillTRIAGE 式归因工具都有直接参考价值。

## Questions for Further Exploration

- How stable is the failure taxonomy across different frontier models (e.g., GPT-class vs Claude-class vs open-weight) and across different agent runtimes, given that all 307 cases come from a single model + harness?
- How does the TIF / EP / CO distribution shift at alternative efficiency-regression thresholds (T = 1.5, 2.5, 3.0)? Is the "EP dominates" finding robust to the cutoff?
- Can skill-task compatibility checks be turned into a cheap *pre-execution* gate (e.g., extracting required fields/paths from the task and diffing against skill defaults) that prevents a meaningful fraction of the 86 TIF cases before any tokens are spent?
- For the 67 Excessive Verification cases, can a budget-aware "verification budget" policy recover most of the cost without sacrificing the correctness gains that verification sometimes provides?
- Does fine-tuning a smaller model on SkillTRIAGE's differential-evidence traces approach GPT-5.5's attribution accuracy at much lower cost, making automatic triage economically viable at marketplace scale?
