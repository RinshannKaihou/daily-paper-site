01 / Method Three views off one program graph

The source stays the editing anchor; GraphIR is supplementary context rendered into the mutation prompt — never the artifact being edited.

STEP 01

State construction

From parent P, build G(P)=(I,O,M,T,F,E) via two-stage interface typing, AST module/operation matching, fixed trigger-to-label facts, and FX producer-consumer edges.

STEP 02

Serialization

Fixed field order: input → output → modules → operations → facts → edges. FX edges preferred over static; counts bounded to keep the prompt compact.

STEP 03

Mutation integration

Prompt P(Ppar, G, H) places source before GraphIR. Mutation stays open-ended — no fixed grammar. Child is re-traced so new parts show up next round.

G(P) = (I, O, M, T, F, E)
I,O  → input / output contracts
M   → architectural modules
T   → tensor operations
F   → structural facts
E   → dependency edges
skeleton (M, T, E) — how data flows

03 / Verdict Strengths against limitations

Honest read: principled framing and broad coverage, bounded by narrow benchmark provenance and a single backbone LLM.

Strengths pro

What lands well.

  • Clean problem framing. "Representation mismatch" between code and mutation state is fresh and concretely formalized.
  • Three-view decomposition maps onto exactly what a mutator must know: what may change, what must stay valid, how edits propagate.
  • NAS-Dependency is reusable — deterministic, oracle-verified Gold, six orthogonal dimensions, no LLM judge.
  • Broad coverage: six benchmarks, five domains, four backbone families.
  • Mechanistic ablations for ordering, node facts, edges — each with a plausible story.

Limitations risk

Where to push back.

  • Single LLM (Qwen3-Plus). No GPT-/Claude-class or scale-robustness study — gains may be model-tied.
  • Narrow benchmark source. NAS-Dependency built only from MNIST1D-Shuffle CNN traces; one architecture family.
  • Larger discovered models on MNIST1D (28.74K vs 15.27K CodeGRAG) — accuracy/size Pareto not always favorable.
  • "-style" baselines are author-adapted representations, not full reproductions of original systems.
  • Hard tasks unsolved: quickselect 15.87%, floyd_warshall 35.75%; loses to Spark/EvoPrompting on some.

04 / Open Questions worth chasing

Where the work invites a next step rather than closing the door.

Q1

Does the advantage hold across LLM families and scales (GPT-4-class, Claude-class, smaller open models), or is it partly Qwen3-Plus-specific?

Q2

How does GraphIR behave on Transformers / GNNs / diffusion U-Nets, where FX tracing breaks under dynamic control flow?

Q3

Can the validity envelope become predictive — blocking invalid edits pre-evaluation — to cut the ~20% invalid-candidate rate?

Q4

Is the accuracy/size trade-off fundamental, or would a parameter-budget term in the prompt recover smaller architectures?
