> **一句话总结：** 作者提出 GraphIR，一种面向变异对齐的架构感知中间表示（包含计算骨架、变异表面、有效性包络三个视图），通过静态分析与 PyTorch FX 执行追踪从可执行神经网络代码中提取，集成到 OpenEvolve 后在 CLRS 上将平均准确率从 Spark 的 83.91% 提升至 89.21%（30 个任务中赢下 22 个），同时端到端 NAS GPU 时长在跨任务聚合下最低。

> **TL;DR:** GraphIR is a mutation-aligned, architecture-aware intermediate representation that supplements executable neural-network code with a computation skeleton, mutation surface, and validity envelope; integrated into OpenEvolve with Qwen3-Plus, it raises average accuracy on the 30-task CLRS benchmark from 83.91% (Spark) to 89.21% (winning 22/30 tasks) and attains the best score on each of 20News, CartPole-v1, Yeast, and Breast Cancer Wisconsin Diagnostic while achieving the lowest aggregated relative end-to-end NAS GPU time (1.379x vs 2.634x for OpenEvolve).

## 核心贡献

- **识别并形式化了 LLM 引导的代码级 NAS 中的"表示失配"问题**：可执行代码提供了开放式的变异基底，但并未显式暴露架构层面的候选状态（张量依赖、可编辑组件、兼容性约束），导致 LLM 必须从实现细节中推断变异语义。
- **提出 GraphIR 架构感知中间表示**：由六元组 G(P)=(I, O, M, T, F, E) 构成（输入/输出契约、架构模块、张量操作、结构事实、依赖边），提供三个互补视图——计算骨架 (M,T,E)、变异表面 (M,T,F)、有效性包络 (I,O,E)。源程序仍是编辑锚点，GraphIR 作为补充上下文。
- **构建 NAS-Dependency 基准**：包含 120 道题、覆盖六个依赖推理维度（Typed Edge / Fan-out / Partition / Producer / Next-hop / Interface-Failure），全部由真实 OpenEvolve 演化迹确定性生成，Gold 答案经 SourceOracleV2 二次校验，无 LLM 参与生成。
- **跨六个下游基准（五个领域）验证**：CLRS（算法推理）、MNIST1D-Shuffle（一维序列）、20Newsgroups（文本分类）、CartPole-v1（强化学习）、Yeast 与 Breast Cancer Wisconsin Diagnostic（表格分类），在搜索质量与端到端效率上一致改进。

## Key Contributions

- **Identifies and formalizes the "representation mismatch" in LLM-guided code-based NAS**: executable code supports open-ended mutation but does not explicitly expose the architecture-level candidate state (tensor dependencies, editable components, compatibility constraints), forcing the LLM to infer mutation semantics from implementation details.
- **Proposes GraphIR**, an architecture-aware intermediate representation organized as G(P)=(I, O, M, T, F, E) — input/output contracts, modules, tensor operations, structure facts, and dependency edges — that yields three complementary views: the computation skeleton (M,T,E), the mutation surface (M,T,F), and the validity envelope (I,O,E). The source program remains the editing anchor; GraphIR serves as supplementary architectural context rendered into the mutation prompt.
- **Introduces NAS-Dependency**, a 120-question benchmark covering six dependency-reasoning dimensions (Typed Edge / Value Fan-out / Partition / Producer Occurrence / Dependency Next-hop / Interface-Failure), deterministically constructed from real OpenEvolve evolution traces with oracle-verified Gold answers and no LLM in question/answer generation.
- **Validates across six downstream benchmarks spanning five domains** (CLRS, MNIST1D-Shuffle, 20Newsgroups, CartPole-v1, Yeast, Breast Cancer Wisconsin Diagnostic), showing consistent improvements in search quality and end-to-end NAS efficiency.

## Methodology

GraphIR targets the setting where the search candidate is an executable PyTorch program and the mutation operator is an LLM. The pipeline has three components:

**1. GraphIR state construction** (Algorithm 1). Given a parent program P, GraphIR builds G(P)=(I, O, M, T, F, E):
- **Interface contracts I, O** are initialized in two stages: deterministic source-pattern classification assigns a profile-specific default (graph-structured contract for graph processors, generic PyTorch contract otherwise); then PyTorch FX symbolic tracing with synthesized example inputs recovers observed input/output shapes that override defaults.
- **Modules M and operations T** come from AST analysis of the editable region, matching constructor calls and tensor methods against fixed neural-module and operation vocabularies (linear, convolutional, normalization, recurrent, attention, regularization, pooling; activations, shape transforms, reductions, masking, matmul, etc.).
- **Structure facts F** are produced by fixed trigger-to-label rules (e.g., convolutional module -> "convolution/local-mixing"; recurrent module -> "state-update"; explicit addition -> "additive-merge"), never LLM summarization. Source-level and execution-grounded facts are merged and deduplicated.
- **Dependencies E** prioritize producer-consumer edges from the traced FX graph; if tracing fails, conservative assignment-level static dependencies are used. Module-constructor and non-tensor attribute dependencies are excluded to suppress spurious edges.

**2. Rendering.** The state is serialized in a fixed field order (input contract, output contract, modules, operations, facts, edges), with FX edges preferred over static edges, lookup/index nodes filtered, and entity counts bounded to keep the mutation prompt compact.

**3. Mutation integration.** At iteration t, the prompt is constructed as P(P^par_t, G_t, H_t). The primary configuration places source code before GraphIR so the executable remains the editing anchor; mutation stays open-ended (no fixed grammar or operator set). After the child is generated, GraphIR is reconstructed so newly introduced components become visible in later iterations.

The construction is explicitly distinguished from generic program graphs (ASTs, CFGs, DFGs, CPGs) and from deep-learning compiler IRs (which target tracing/lowering/execution rather than mutation), and from learned architecture embeddings (NGE/GATES/NASGEM) since GraphIR does not encode a fixed search space.

## Results & Highlights

GraphIR is evaluated along three axes (reasoning, downstream evolution, ablations).

**RQ1 — NAS-Dependency (held-out 76 questions, Qwen3-Plus, temperature 0):**
- GraphIR achieves the highest macro average of **0.5040**, vs **0.4712** (CPG-style), **0.4499** (GraphCode-style), **0.4193** (CodeRAG-style), and **0.4060** (Code Only) — a +0.098 absolute macro improvement over code-only prompting.
- On Producer Occurrence (exact match): GraphIR **0.5385** vs next-best **0.4615** (CPG-style and GraphCode-style) and **0.3077** (Code Only).
- On Dependency Next-hop (set F1): GraphIR **0.3611** vs **0.3056** (CPG-style) and **0.1667** (Code Only).
- On Interface/Failure (exact match): GraphIR **0.2500** vs **0.1667** for all four baselines.

**RQ2 — Downstream architecture evolution:**
- **CLRS (30-task algorithmic reasoning, zero-shot transfer):** OpenEvolve+GraphIR reaches the highest average accuracy **89.21%** and DFS accuracy **94.68%**, vs Spark **83.91%/83.74%**, EvoPrompting **80.88%/68.14%**, OpenEvolve **62.69%/32.54%**, and Triplet-GMPNN **75.98%/47.79%**. Excluding the DFS evolution task it still averages **89.03%** and wins **22/30** tasks, with comparable model size (**467.4K** vs Spark 470.2K and Triplet-GMPNN 467.3K).
- **MNIST1D-Shuffle CNN (controlled representation ablation, 100 iterations, 10 seeds):** GraphIR achieves **71.55 ± 2.14%** test accuracy and **68.68 ± 2.53%** OOD accuracy, beating CPG-style (70.10% / 67.95%), GraphCode-style (68.03% / 66.20%), and CodeGRAG-style (66.40% / 64.87%), while requiring less end-to-end NAS GPU time (**1.639 ± 0.089 h**) than CPG-style (2.124 h) and GraphCode-style (2.411 h).
- **Cross-task efficiency-performance (4 benchmarks: 20News, CartPole-v1, Yeast, Breast Cancer):** GraphIR attains the best raw score on every task (e.g., CartPole-v1 **500.00** vs EvoPrompting 488.65; 20News **59.57** vs EOH 58.05; Breast Cancer **97.35**), and the highest aggregated mean relative performance **100.000** with the lowest relative NAS GPU hours **1.379**, compared to OpenEvolve (92.323 / 2.634), EvoPrompting (98.196 / 3.623), EOH (88.036 / 10.697), and FunSearch (85.822 / 10.836).
- **Backbone robustness on MNIST1D-Shuffle** (Table 3): GraphIR averages **69.05%** across Linear/MLP/CNN/GRU (CNN best run **74.20%**, MLP **71.90%**, GRU **70.80%**, Linear **59.30%**).

**RQ3 — Ablations:**
- **Source-state ordering** (Table 4): Code->GraphIR yields **74.20%** accuracy with **6** shape errors in **1.605 GPU-h**, vs GraphIR->Code **66.30%**, **17** shape errors, **2.326 GPU-h** — supporting source-first ordering.
- **State components** (Table 5): Removing edge relations drops accuracy to **71.53%** (and shape mismatches rise to 14.33); removing node facts drops accuracy to **67.13%** — node facts (explicit architecture semantics) are the more important component.

## Authors & Credibility

Authors are from the National Key Laboratory of Human-Machine Hybrid Augmented Intelligence at Xi'an Jiaotong University, MiLM Plus (Xiaomi Inc.), and Zhongguancun Academy / Zhongguancun Institute of Artificial Intelligence. The work builds transparently on the open-source OpenEvolve evolutionary coding agent and uses Qwen3-Plus as the mutation LLM with stated generation parameters (temperature 0, max 1536 tokens, ≤2 retries). The NAS-Dependency benchmark uses deterministic, oracle-verified Gold answers (no LLM judge), and the evaluation protocol fixes the pipeline, prompt, LLM, search budget, and seed while varying only the representation — a reasonably controlled comparison. Related work (EvoPrompting, LLMatic, NADER, LM-Searcher, Spark) is cited and positioned honestly, and the per-task CLRS tables (including losses on floyd_warshall and quickselect) are disclosed in full.

## Critical Assessment

- **Novelty**: Genuine. The framing of a "representation mismatch" between executable code and mutation-aligned architecture state is a fresh angle, and GraphIR's three-view decomposition (skeleton / surface / envelope) is more principled than simply dumping a code-property graph.
- **Rigor**: Strong on the reasoning benchmark (deterministic scoring, oracle-verified Gold, controlled inputs differing only in the added representation). Weaker on the downstream comparisons because the "-style" baselines (CodeRAG-style, CPG-style, GraphCode-style) are the authors' own adaptations rather than full reproductions of the original systems, so they may understate those methods. EvoPrompting and Triplet-GMPNN numbers on CLRS come from their original papers rather than re-runs under the shared protocol — a minor apples-to-oranges risk the authors flag.
- **Reproducibility**: Reasonable. Built on public OpenEvolve and Qwen3-Plus; per-task numbers, split statistics (Dev-44 / Held-out-76), and the deterministic construction pipeline are described in detail. However, the SourceOracleV2 analyzer is acknowledged to be an incomplete Python interpreter (AST-parses only), and per-seed raw candidate archives are not clearly committed.
- **Significance**: High if the claim generalizes — representation as a first-class design choice in LLM-guided NAS is a useful conceptual contribution, and the cross-task efficiency numbers are striking (best score on all four cross-task benchmarks at the lowest aggregated GPU time).
- **Red flags / specific concerns**:
  - The NAS-Dependency benchmark is generated **only** from MNIST1D-Shuffle CNN evolution traces, so its six dimensions reflect one architecture family in one task setting; generalization to transformers, GNNs, or large-scale vision models is untested.
  - **Single LLM (Qwen3-Plus)** is used throughout; no robustness check across GPT-class, Claude-class, or open models of different scales, leaving open whether GraphIR's gains come from representation or from interactions with this specific model.
  - On hard CLRS tasks GraphIR still fails (quickselect **15.87%**, floyd_warshall **35.75%**), and on some tasks it loses to Spark or EvoPrompting (e.g., floyd_warshall Spark 32.91 < EvoPrompting 61.43; find_maximum_subarray_kadane Spark 85.64 > GraphIR 82.52), so the win is not uniform.
  - GraphIR uses **10 seeds** on MNIST1D-Shuffle while baselines use 3; although mean±std is reported, the asymmetry in compute could matter for "best observed run" style tables (Table 4).
  - GraphIR's discovered models on MNIST1D are **larger** on average (28.74K params vs 15.27K CodeGRAG-style, 21.52K CPG-style), so part of the accuracy gain may come from capacity rather than purely better architecture reasoning.
  - End-to-end NAS GPU time is measured on a single NVIDIA RTX 3090 with 100 iterations; scaling behavior to larger budgets or larger backbones is not explored.

## Strengths

- Clean, well-motivated problem statement (representation mismatch) with a concrete, implementable solution.
- Three-view decomposition maps directly onto the three things a mutation operator must know: what may change, what must stay valid, and how a local edit propagates.
- NAS-Dependency is a genuinely useful diagnostic: deterministic, oracle-verified, six orthogonal dimensions, and reusable beyond GraphIR.
- Broad empirical coverage (six benchmarks, five domains, four backbone families) with strong aggregate numbers.
- Honest ablations isolating source-state ordering, node facts, and edge relations, with a plausible mechanistic story for each.
- Deterministic, LLM-judge-free scoring on the reasoning benchmark removes a common source of evaluation noise.

## Limitations

- Single-LLM evaluation (Qwen3-Plus only); no cross-model robustness study.
- NAS-Dependency source diversity is narrow (MNIST1D-Shuffle CNN traces only).
- Discovered architectures are larger on MNIST1D; the accuracy/size Pareto is not always favorable.
- "-style" baselines are author-adapted representations, not full system reproductions.
- Hard reasoning tasks (quickselect, floyd_warshall, kmp_matcher) remain far from solved even with GraphIR.
- No investigation of scaling behavior beyond 100 evolution iterations or beyond an RTX 3090.
- Static analyzer (SourceOracleV2) is not a complete Python interpreter; programs that fail AST parsing drop out of dependency-graph questions.

## Relevance

对关注神经架构搜索（NAS）与大模型引导代码演化交叉方向的研究者，GraphIR 提供了一个直接可落地的"表示工程"思路——把可执行代码与变异对齐的架构状态解耦，与本仓库关注的 LLM 驱动 NAS、代码表示学习、自动化模型设计等主题高度契合，可作为后续工作改进搜索效率与候选有效性的参考基线。

## Questions for Further Exploration

- Does GraphIR's advantage hold across LLMs of different families and scales (e.g., GPT-4-class, Claude-class, smaller open models), or is the gain partly specific to Qwen3-Plus?
- How does GraphIR interact with richer architecture families (Transformers, GNNs, diffusion U-Nets) where FX tracing frequently breaks due to dynamic control flow?
- Can the validity envelope be made predictive rather than descriptive — i.e., proactively block edits that would violate an interface contract before evaluation, reducing the ~20% invalid-candidate rate observed on MNIST1D-Shuffle?
- Is the accuracy/size trade-off on MNIST1D a fundamental property of mutation-aligned states, or would adding a parameter-budget term to the prompt recover smaller architectures?
- Could the NAS-Dependency benchmark be extended beyond CNN traces to cover the producer/interface reasoning of attention and normalization layers, where shape coupling is more subtle?
