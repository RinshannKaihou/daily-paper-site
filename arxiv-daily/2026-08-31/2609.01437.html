Frontier LLMs can build their own agent harnesses to near-human quality — but self-evolution gains barely survive held-out tasks.

Why this matters

First systematic measurement of whether LLMs can build and improve their own agent infrastructure — with quantified evidence that feedback gains rarely generalize.

Critical edge

The “near-human” comparison is apples-to-oranges — three of five reference systems are external leaderboard numbers run with different, stronger executors.

Methodology

From weak seed to frozen harness

The model that develops the harness is separated from the model that executes it: (creator, dev env) → harness H, then frozen H runs hidden tasks. Scored on capability (native benchmark metrics) and efficiency (executor tokens only).

S0 · Seed

Weak seed, policy-free

A runnable floor with passive primitives only — no agent loop, tool policy, state, verifier, or stopping rule. Scores 0.0 on all five benchmarks unmodified, so any nonzero score must come from the creator’s control logic.

S1 · Creation (RQ1)

Build a full harness

Six frontier creators get the seed, a task-family spec, and 1–3 dev cases; hidden tasks and answers stay withheld. The frozen harness runs avg@3 under Self-Eval (executor = creator) and Unified-Eval (fixed Gemini 3.1 Pro).

SWE-bench Pro 731 · Terminal-Bench 2.1 89 · MLE-bench 75 · EQ-Bench3 46 · BrowseComp 1,296

S2 · Evolution (RQ2)

Iterate from feedback

Creators improve their own Code harness against a 100-task SWE-Pro + 89-task Terminal-Bench feedback set — budget of 10 full evaluations, at most 2 diagnostic probes — then every version is re-scored on 630 disjoint held-out tasks.

S3 · Anti-gaming

Checkable constraints

Score path isolated from the harness: credit only from real repo diffs / final environment state, never self-reported status. Every reported run audited post-hoc — no violations found.

  • Executor compatibility dominates. Under a fixed Gemini executor, Opus’s SWE-Pro score collapses 69.3 → 33.0 (it hard-codes a 120-step limit around its original executor); its duplicate-query rate jumps 10.1% → 88.2%. Conversely Qwen gains +17.6 on BrowseComp.
  • The bottleneck is often the harness, not the model. 77.8% of failed Data tasks trace to harness defects; 124/387 Writing features are confirmed dead code; self-test count predicts score at only Spearman 0.13–0.26 (n.s.) vs 0.57 for revision calls.
  • Efficiency doesn’t buy quality. MLE-bench token use varies ~19× — GPT-5.5 reaches 19.1 medal rate with 29.3M tokens while DeepSeek reaches 19.6 with 208.4M. Gemini adds the fewest lines (+1,006 LOC) yet posts the best Terminal-Bench score (68.8).
  • Evolution: visible gains, fragile generalization. All five creators improve on the visible feedback pair (e.g. Qwen 41.0 → 55.7), but held-out gains shrink to +1.43…+4.44 (mean +3.11). Same-commit noise is ±4.75; 27/64 version switches sit inside the noise band; only 2/9 declared versions are held-out optimal. Open questions ↓
  • Feedback use is superficial. The median declared version changes 8 files and none touch the verifier; creators inspect only 0.5%–40.2% of feedback tasks. Bright spot: Opus traced 99 reported successes vs 48 real passes and added a completion gate.

Strengths

What holds up

  • Evaluates the artifact that actually determines deployed agent quality — the harness — on both capability and executor-token cost.
  • Elegant weak-seed floor (0.0 everywhere): every point of score is attributable to the creator’s control logic, not benchmark boilerplate.
  • Checkable, audited anti-gaming constraints (real repo diffs, final environment state) — rare rigor in agentic benchmarks.
  • Cleanly separates adaptation (visible feedback) from generalization (630-task held-out), exposing that version selection on noisy feedback is unreliable.
  • Concrete failure forensics: dead-code censuses, the 120-step hard-code, the 99-reported-vs-48-pass completion gate.

Limitations

Where it wobbles

  • n = 1 trajectory per creator-runtime cell (nine lineages, one unfinished) — no uncertainty estimates; held-out covers SWE-Pro only.
  • Human references are unpaired: three of five are external leaderboard numbers obtained with different, stronger executors — indicative, not controlled.
  • Unified-Eval reduces but cannot remove executor-model differences; behavioral comparisons stay descriptive.
  • Fixed development environment: Seed 2.0 Pro’s 22.8 may reflect poor fit with a rival’s dev env — no ablation separates the two.
  • Measures model-external learning only; proprietary, versioned APIs mean exact replication decays quickly.

Questions for further exploration

What to probe next

  • Would the held-out collapse persist with multiple trajectories per cell and a proper matched-budget search baseline?
  • Would a standardized runtime interface for budgets and stopping rules make harnesses portable across executors (the Opus 120-step failure)?
  • Can harness-defect attribution itself be automated and fed back as structured diagnosis, given creators inspect ≤40.2% of feedback tasks?
  • Are smaller, verification-heavy harnesses (Gemini’s 1,006-LOC best artifact) a better explicit design target than over-built ones with dead code?
  • What would a properly paired human-harness control under one common executor show on SWE-Pro and BrowseComp, where the gap is largest?
  • Can an evolved harness itself host further evolution, or does the fixed dev environment cap the recursion?
