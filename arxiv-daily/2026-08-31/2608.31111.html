arXiv 2608.31111·Benchmark·Vague-goal self-evolution

Given only vague goals, agents reliably close the training loop but rarely retain real capability gains.

Aspire: Can Models Self-Evolve from Vague Goals?

Yuhao Wu, Wenzxuan Zhang, Shen Yan, Wenliao Huang, et al. — ByteDance Seed · SUTD · M-A-P · TokenWave.AI  ·  2026-08-31

self-evolving-agents llm-benchmark post-training agent-harness hidden-evaluation 2026-08-31

Key metric

3 / 24

final checkpoints above base · final-only protocol

Across 24 weight-evolution runs only 3 beat the base model — the other 21 roll back. Under adaptive feedback, just 1 of 30 cells retains a gain.

Why this matters

Formalizes the missing self-evolution axis — deciding what to optimize and how to verify — and charts where autonomous training loops actually break.

⚠ Critical edge

The sole retained gain (Terra math, 20.10 vs 17.86) was measured on the same fixed slice used for feedback — selection evidence, not an independently confirmed capability gain.

Methodology

  • Campaign formalism: Γ = (G, EG, J, A, B, Σ) — a vague natural-language goal, a hidden evaluator, a rubric judge, a typed action contract, a compute budget, and a predeclared terminal selection rule. The agent sees only a released projection; items, answers, and rubrics stay controller-only.
  • 520 expert-authored hidden items across 6 vague goals (math 120, humanities 110, health 100, logic/reliability 80, science 75, writing 20). GPQA / MMLU-Pro / MedQA serve only as format-difficulty references — zero item copying — plus blind difficulty calibration, exact + semantic dedup, overlap audits, and immutable versioning.
  • No shell access. One typed tool: search/import/synthesize data, launch SFT or GRPO(LoRA), build own validation sets, branch/stop. The controller enforces budgets (≤40 GPU-hours per final-only run) and safe rollback — a checkpoint is kept only if it beats the incoming state, so Δret ≥ 0 is a selection outcome, not a guarantee.
  • Three studies: RQ1 vague-goal vs explicit-task prompting on PostTrainBench (Claude Opus 4.8) · RQ2 weight evolution from Qwen3.5-4B/9B — final-only (24 runs) and adaptive-feedback (30 cells with GPT-5.6 Luna/Terra/Sol as external decision models) · RQ3 one-step harness evolution with weights frozen against the engineered Qwen-Agent.

  • Rising trajectories can be regression recovery: of 62 checkpoint transitions, 28 rise / 13 tie / 21 fall — Qwen3.5-4B Self's math climbs 0.79 → 1.75 → 2.38 while far below its 17.86 base.
  • Blind continuation can end near-worthless: three final-only runs burn 26.6–32.3 GPU-hours over 16–20 training jobs, submitting checkpoints scoring 0.159, 2.540, and 0.
  • Failure mode — numeric-label SFT → format collapse: 21,000 single-digit training targets produce single-digit answers on all 279 evaluation outputs (scores 0, 0, 0, 6.141, 0) — training-induced regression, not evaluator error.
  • RQ1 behavior shift under vague goals: +2,109 s thinking per run, LoRA use 24.1% → 89.8%, feedback density 0.57 vs 2.63 evals per training start (a 4.6× difference in feedback opportunities).

Strengths

  • A new, well-motivated axis: separating WHAT-to-optimize from HOW-to-optimize is a clean formalization that PostTrainBench, AIIA4AI-Bench, and MLE-bench conspicuously assume away.
  • Serious benchmark hygiene: items authored from scratch with reference-guided construction, blind multi-model difficulty calibration, dedup, overlap audits, scorer binding, immutable versioned manifests.
  • Auditable execution: every candidate records parent, data, update spec, and provenance; foreign artifacts are rejected; budgets and terminal rules are predeclared.
  • Negative results with mechanism: rollback/retention decomposition, a 62-transition recovery-vs-improvement analysis, and a traced SFT format collapse — actionable failure modes, not a leaderboard.
  • Two complementary protocols cleanly separate "can it produce a good final checkpoint" from "can it use sparse feedback to search," with external decision models isolating decision-model effects.

Limitations

  • Small run counts: Avg@2 per model-goal pair (final-only) and one canonical run per adaptive cell; the Terra-math retention lacks an independent confirmation slice.
  • Narrow coverage: writing goal has only 20 items; RQ2 never tests whether unrelated capabilities survive updates, so capability preservation is unmeasured; RQ3 is one-step only (no recursive H1→H2).
  • RQ1 is observational: matched-run differences are descriptive; official reference numbers come from different systems and metadata — not a controlled causal estimate.
  • Sealed evaluation: items, rubrics, and traces are controller-only, preventing fully independent verification of scoring quality.
  • Environment abstraction: the single typed tool removes infrastructure friction by design — results measure goal operationalization under this scaffold, not messy real-world co-evolution.

Questions for Further Exploration

  • Would a held-out confirmation slice (or refreshed evaluation versions) confirm the single retained gain is a real capability improvement rather than feedback-guided selection on a fixed slice?
  • Can numeric-label SFT format collapse be detected cheaply from the agent's own validation data (output-format invariants), or does it require external evaluation — a missing self-verification mechanism harness evolution should add?
  • Does the vague-goal aggregate penalty persist under matched systems with rerun controls, and does it shrink with more feedback queries per training start?
  • Does rollback to the base checkpoint mask catastrophic forgetting that a broader capability-preservation evaluation would reveal?
  • Can harness and weight evolution be composed under the same information boundary — and does co-evolution finally beat the engineered reference?
  • With 20 writing items and one evolution step, what slice size and step count are needed before harness differences exceed runtime variance (per-execution dispersion unreported)?
