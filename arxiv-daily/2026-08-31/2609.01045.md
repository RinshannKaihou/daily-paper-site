> **一句话总结：** 提出 AgentFactory 框架，把智能体系统的设计形式化为“基础模型微调（LoRA/QLoRA/全参 + 数据集选择 + 超参）× 工作流结构（可执行代码）”的联合空间多目标优化问题，用 GPT-4o 等 LLM 充当优化器做迭代搜索（规划→微调→工作流设计三阶段流水线）；在 5 大领域 8 个基准上，相比最强自动化基线 AFlow/ADAS 平均提升 9.1%，其中 MedQA 提升 19.6%、FinEval 提升 18.7%（Llama-3.1-8B 设定下 MedQA 65.4 vs Reflexion 47.2、FinEval 58.5 vs AFlow 39.8），同时在 GPT-4o-mini 设定下把推理成本从 AFlow 的 $2.13 降到 $0.68（约降 68%）。

> **TL;DR:** AgentFactory reframes automated agentic system design as multi-objective optimization (accuracy, cost, latency) over the *joint* space of fine-tuned foundation models and code-based workflows, using an LLM (e.g., GPT-4o) as the optimizer in a three-stage plan→tune→design pipeline. Across 8 benchmarks in 5 domains (MMLU, DROP, HumanEval, MBPP, GSM8K, MATH, MedQA, FinEval), it averages 68.9 with Llama-3.1-8B-Instruct vs 59.8 for AFlow and 56.7 for ADAS (+9.1), reaching 65.4 on MedQA (vs Reflexion 47.2) and 58.5 on FinEval (vs AFlow 39.8); with GPT-4o-mini it scores 83.9 avg vs AFlow 78.5 while cutting inference cost to $0.68 vs ADAS's $2.37. The ablation attributes the gains to combining both spaces (+12.7% over fine-tuning-only, +8.2% over workflow-only), though baselines never receive fine-tuning access.

## 核心贡献

- **联合搜索空间的形式化：** 首次把智能体系统优化形式化为对偶空间 S = {(m, w)} 上的多目标优化——模型空间 M = {(b, d, h)}（基础模型 b、指令微调数据集 d、微调超参 h，微调方式 φ ∈ {LoRA, QLoRA, 全参微调}；无法本地微调的第三方模型记 d=∅, h=∅），工作流空间 W 采用 ADAS 式可执行代码表示，优化目标包含精度、成本、延迟多个评价函数 G = {G1,…,Gp}。
- **LLM 充当优化器的迭代算法（Algorithm 1）：** 优化器 L_θ 基于“元提示 + 历史优化轨迹 O_{k−1}（解—评估对序列）”生成下一候选系统 s_k = L_θ(O_{k−1}, M, I_meta)；当所有指标达到目标阈值 G(s_k,T) ≥ G_target 或达到最大步数 K_max 时终止，最后用标量化函数 F 在轨迹中选出 Pareto 最优解 s*。
- **三阶段优化流水线（Planning → Tuning → Workflow Design）：** Planning 阶段由 LLM 输出结构化方案（Insights / 模型规格 / 工作流设计要点）；Tuning 阶段将微调配置交给 OpenRLHF 后端执行（带 ≤20K 样本、单次 ≤4 小时、4×A6000 的资源约束，并有微调模型缓存避免重复训练，可动态调整 batch size 等超参）；Workflow Design 阶段生成可执行的工作流代码（ prompting 策略、工具调用、控制流一体），比图结构表示更能表达复杂控制逻辑。
- **多目标成本感知优化：** 框架在满足精度目标后主动压低成本——案例研究中 FinEval 的运营开销从 $1.14 降至 $0.60 才终止；GPT-4o-mini 设定下可在 Llama-3.1-8B 与 GPT-4o-mini 之间自动选择更划算的模型。
- **大规模实证：** 8 基准 × 5 领域 × 2 种基础模型设定 × 5 种优化器 LLM，每组实验重复 3 次；消融实验（图 5）证明联合优化显著优于单空间优化。

## Key Contributions

- **Joint model + workflow search space:** Formalizes agentic system optimization as multi-objective optimization over S = {(m, w)}, where the model space M = {(b, d, h)} covers base-model choice, instruction fine-tuning dataset, and hyperparameters (LoRA / QLoRA / full fine-tuning), and the workflow space uses executable code representations — whereas prior automated methods (PromptBreeder, TextGrad, GPTSwarm, ADAS, AFlow) keep the model fixed and search workflows only.
- **LLM-as-optimizer algorithm (Algorithm 1):** The optimizer L_θ generates the next candidate system s_k = L_θ(O_{k−1}, M, I_meta) from the solution-evaluation trajectory, terminating when all metrics meet their targets G(s_k, T) ≥ G_target or at K_max steps, then returns the Pareto-optimal solution via a scalarization F.
- **Three-stage pipeline (Planning → Tuning → Workflow Design):** Planning emits a structured plan (insights, model specification, workflow outline); Tuning executes fine-tuning configs on an OpenRLHF backend under explicit constraints (≤20K samples, ≤4h per session, 4×A6000 48GB GPUs, model caching to avoid redundant training); Workflow Design generates executable code (following ADAS) that captures prompting strategies, tool usage, and control flow.
- **Cost-aware multi-objective optimization:** After the accuracy target is met, the optimizer explicitly minimizes cost — in the FinEval case study it drove operational expense from $1.14 down to the $0.60 target before terminating at iteration 17, and in the GPT-4o-mini setting it can pick between Llama-3.1-8B and GPT-4o-mini for the best performance/cost trade-off.
- **Extensive empirical study:** 8 benchmarks across 5 domains (general reasoning, coding, math, medicine, finance), 2 foundation-model settings, 5 candidate optimizer LLMs, each experiment repeated 3 times, plus an ablation quantifying each pipeline component.

## Methodology

**Problem formulation.** Given task T and evaluation functions G = {G1, …, Gp} (accuracy, cost, latency), AgentFactory searches for an agentic system in S = {(m, w)} with m ∈ M and w ∈ W. A model m = (b, d, h) is a base model b ∈ B, an instruction fine-tuning dataset d ∈ D, and fine-tuning hyperparameters h ∈ H (batch size, learning rate), with tuning method φ ∈ {LoRA, QLoRA, full fine-tuning}; third-party models that cannot be fine-tuned locally use d = ∅, h = ∅. The workflow space W admits graph structures (GPTSwarm), neural architectures (DyLAN), or executable code (ADAS) — the authors choose code-based representations for expressive control flow and to exploit modern LLM code generation.

**Optimization loop.** The trajectory O_{k−1} = {(s_i, G(s_i, T))} records every candidate and its metric vector. Because the search space is non-differentiable and only partially observable, gradient or evolutionary methods are deemed unsuitable; instead an LLM optimizer with meta-prompt I_meta produces s_k = L_θ(O_{k−1}, M, I_meta). Termination occurs when G(s_k, T) ⊇ G_target (component-wise) or k = K_max; the final answer is s* = argmax_{s∈O_K} F(G(s, T)) for a user-specified scalarization F.

**Three-stage pipeline.** (1) *Planning*: the optimizer integrates the meta-prompt, task description, model configs, workflow frameworks, and previous trajectory into a plan with three parts — Insights (design rationale), Model specs (foundation model, dataset, tuning method, hyperparameters), and Workflow outline (Fig. 2 shows the prompt template). (2) *Tuning*: the LLM emits concrete tuning configurations (dataset selection, sample requirements, methodology, hyperparameters) executed by the tuning backend; initial configs may fail on hardware limits, so the framework iteratively adjusts (e.g., batch-size reduction or more efficient tuning methods). (3) *Workflow Design*: from code templates, the optimizer generates structured executable code; Fig. 3 shows a GSM8K workflow with a Reflexion-style loop and specialized tools (calculator, evaluator) for numeric computation.

**Experimental setup.** Benchmarks: 1,000 randomly sampled instances each from MMLU and DROP; complete HumanEval and MBPP; the full GSM8K test set; 617 MATH problems at difficulty level 5 (following [14], spanning Combinatorics & Probability, Number Theory, Pre-Algebra, Pre-calculus); complete MedQA and FinEval. Manual baselines: direct LLM invocation (IO), CoT, CoT-SC (5 samples), Reflexion (3 rounds), LLM Debate (3 rounds); automated baselines: ADAS and AFlow. Two settings: all methods on Llama-3.1-8B-Instruct, and all methods on GPT-4o-mini (AgentFactory alone may use both models). Fine-tuning data curated from benchmark training splits: CodeBagel (Python segments), MathInstruct, IndustryInstruction (Health-Medicine and Finance-Economics subsets), presented to the optimizer as descriptive triples (name, size, characteristics). Fine-tuning on Llama-3.1-8B-Instruct via OpenRLHF with ≤20K samples, ≤4h per session, on 4×A6000 (48GB) GPUs, with caching. Optimizer candidates: GPT-4o (2024-08-06), GPT-4o-mini (2024-07-18), Claude-3.5-Sonnet (2024-10-22), Gemini Pro 1.5, DeepSeek V3; optimization capped at 20 iterations; every experiment repeated 3 times.

## Results & Highlights

- **Llama-3.1-8B setting, main table (Table 1):** AgentFactory averages **68.9** across the 8 benchmarks vs **59.8 for AFlow** and **56.7 for ADAS** — a **+9.1** gain over the strongest automated baseline (plain IO is 43.5, CoT 51.9, Reflexion 56.0). Per-benchmark: MMLU 79.8, DROP 67.4, HumanEval 84.4, MBPP 70.8, GSM8K 92.2 (vs AFlow 89.4), MATH 44.6 (vs AFlow 31.1, +13.5), MedQA 65.4 (vs Reflexion 47.2, +18.2), FinEval 58.5 (vs AFlow 39.8, +18.7). The paper's headline: average +9.1% over automated methods, with **+19.6% on MedQA and +18.7% on FinEval**, where workflow-only optimization showed limited effectiveness.
- **GPT-4o-mini setting (Table 1):** AgentFactory averages **83.9** vs **78.5 for AFlow** and 76.7 for ADAS, at an average inference cost of **$0.68 vs ADAS $2.37 / AFlow $2.13 — a claimed cost reduction of up to 68%** (the optimizer deliberately prefers cheaper models when possible). It reaches 86.8 on MedQA (vs AFlow 77.5) and 78.2 on FinEval (vs AFlow 67.8). Exceptions exist: AFlow beats it on DROP (79.9 vs 79.3), and Reflexion edges GSM8K (93.1 vs 95.8 in AgentFactory's favor — actually 95.8 vs 93.1 for AgentFactory; the true exception is DROP).
- **Ablation (Fig. 5, Llama-3.1-8B base):** relative to the IO baseline, the full pipeline surpasses the **fine-tuning-only variant by 12.7%** and the **workflow-only variant by 8.2%** on average; fine-tuning alone contributes particularly large gains on the domain-specific benchmarks (MedQA, FinEval), validating the joint-space design.
- **Optimizer sensitivity (Table 2):** average performance tracks optimizer capability — GPT-4o 68.7, Claude-3.5-Sonnet 67.1, Gemini Pro 1.5 66.3, DeepSeek V3 63.3, GPT-4o-mini 58.0 — with GPT-4o and Claude-3.5-Sonnet producing comparable outcomes, suggesting robustness to the choice of similarly capable optimizers.
- **FinEval case study (Fig. 4):** starting from basic IO at **62.3%** accuracy, a Multi-expert Cross-validation Workflow lifted it to **66.7%** (iterations 1–4); domain-specific financial fine-tuning jumped to **72.5%** (iteration 5); adding mathematical instruction data to the fine-tuning mix pushed to **74.6%** (iteration 11); a Multi-Reasoning design exceeded the 75% target (iterations 13–17), after which the optimizer reduced cost from **$1.14 to the $0.60 target**, terminating at iteration 17.

## Critical Assessment

- **Baseline asymmetry conflates search quality with data access.** The central comparison is unfair by construction: ADAS and AFlow optimize workflows with a *frozen* model, while AgentFactory additionally fine-tunes on training splits of the very benchmarks being evaluated (CodeBagel, MathInstruct, IndustryInstruction's Health-Medicine/Finance-Economics subsets). The ablation itself shows fine-tuning is the dominant driver of the domain gains (MedQA/FinEval "particularly significant"), so the headline +19.6%/+18.7% largely measures the privilege of fine-tuning access, not superior automated design. A manual fine-tune + AFlow baseline — the obvious "how much does the search actually add" control — is absent.
- **Cost accounting is incomplete.** The reported "Cost" column covers deployment inference only. The one-time optimization overhead is substantial and unreported: up to 20 iterations of GPT-4o-driven planning over 8 benchmark evaluations × 3 repeats, plus 4-hour fine-tuning sessions on 4×A6000 GPUs. Also, latency is one of the three formalized objectives, yet no latency numbers appear anywhere — the multi-objective claim about efficiency is only half-empirically demonstrated (cost yes, latency no).
- **"Lower cost" holds only against the most expensive baselines.** In the Llama setting, AgentFactory costs $0.26 vs $0.03 for plain IO and $0.07 for CoT — i.e., it is 3.5–8.7× more expensive than simple prompting; the 68% cost reduction is relative to ADAS ($2.37) and AFlow ($2.13) in the GPT-4o-mini setting only.
- **No statistical rigor despite 3 repeats.** The paper states each experiment was repeated three times "to ensure statistical reliability" but reports no variance, standard deviation, or significance tests for any table; several margins (e.g., 83.9 vs 78.5 average, or DROP 79.3 vs 79.3-level differences) cannot be assessed for noise.
- **Nonstandard benchmark subsets limit external comparability.** MMLU and DROP are randomly subsampled to 1,000 instances, and MATH is restricted to 617 difficulty-5 problems — fine for internal comparison but not directly comparable to published leaderboard numbers.
- **Contamination risk unaudited.** Fine-tuning on CodeBagel's Python segments before evaluating on HumanEval/MBPP is a plausible leakage channel; the paper does not audit overlap between the fine-tuning corpora and the coding test sets (using "training splits" mitigates this for MMLU/MATH-style data but CodeBagel is third-party and unverified).
- **Novelty is compositional, not fundamental.** LLM-as-optimizer ([31] Yang et al.), code-based workflow search (ADAS), and instruction fine-tuning are each established; the contribution is their joint formalization plus engineering. That is a legitimate and useful contribution, but the paper's framing ("new paradigm") overstates it, and no code release undermines reproducibility of a system whose behavior depends on specific API model snapshots (GPT-4o 2024-08-06, Claude-3.5-Sonnet 2024-10-22).

## Strengths

- The joint model × workflow formulation is the right generalization of workflow-only optimization, and the paper is (to my knowledge) the first to give it a clean multi-objective statement with target thresholds and a scalarized Pareto selection step.
- Unusually broad evaluation: 8 benchmarks across 5 domains, two foundation-model regimes, five optimizer LLMs, and a transparent ablation that cleanly quantifies each component (+12.7% over fine-tuning-only, +8.2% over workflow-only).
- The FinEval case study is genuinely informative — it shows the optimizer's actual trajectory (workflow-only plateau at 66.7%, then fine-tuning jumps to 72.5%, cross-domain math data to 74.6%, then cost shaving $1.14 → $0.60), which is more interpretable than a single number.
- Practical constraints are realistic and stated (≤20K fine-tuning samples, ≤4h per session, model caching, 20-iteration budget), and the cost-aware model-switching behavior (preferring Llama-3.1-8B or GPT-4o-mini when adequate) is a concrete deployment-relevant capability.
- The optimizer-independence check (Table 2) addresses a real robustness concern for LLM-as-optimizer methods.

## Limitations

- All automated baselines are denied fine-tuning, so the joint-search advantage on domain tasks (MedQA, FinEval) cannot be decomposed into "better search" vs "more data access" from the reported tables.
- No latency measurements despite latency being a formal objective; no reporting of optimization-time cost (optimizer API spend + fine-tuning compute).
- No variance or significance analysis despite 3 repeats; no code or artifacts released.
- Evaluated only on QA/code-style benchmarks with accuracy as the primary metric — no agentic benchmarks requiring tool use over long horizons (e.g., web or software-engineering tasks), where workflow control flow matters most.
- Optimizer performance is tightly coupled to frontier proprietary LLMs (GPT-4o avg 68.7 vs GPT-4o-mini 58.0 — a 10.7-point swing), raising questions about cost-effectiveness when the optimizer itself is expensive.
- Fine-tuning experiments are limited to Llama-3.1-8B-Instruct as the tunable base; scaling behavior of the joint search (e.g., 70B-class models, or mixing two tunable models) is untested.

## Relevance

这篇论文正中你的最高优先级方向 "Self-Evolving Agents & Automated Research"：它用 LLM 作为优化器在模型+工作流联合空间中做自动迭代设计，本质上是一个带外部评估反馈的自动智能体构造闭环，与自进化智能体架构和自动化 benchmark 设计直接相关；其"成本/延迟目标 + 精度目标"的多目标优化形式化，对长时程自主系统的可靠性权衡也有参考价值。

## Questions for Further Exploration

- How much of the MedQA/FinEval gain survives if ADAS or AFlow is also granted the same fine-tuning corpora and budget — i.e., what is the isolated contribution of the joint search itself?
- Since the latency objective is formalized but never measured, how does AgentFactory trade accuracy against actual wall-clock latency when a latency target is imposed?
- Does the optimizer overfit to the evaluation set over 20 iterations of feedback (each iteration sees G(s, T) on the test distribution)? Would a held-out validation split change the reported numbers?
- How does the framework behave on long-horizon agentic benchmarks (SWE-bench, WebArena) where workflow control flow and tool orchestration dominate, rather than single-shot QA accuracy?
- Can the fine-tuning step be replaced with cheaper adaptation (prompting, RAG, or a routing layer) in domain tasks, given the ablation suggests fine-tuning carries most of the domain gain?
- What is the total optimization cost (optimizer API calls across 20 iterations × 3 repeats + 4×A6000 hours) per task, and at what usage volume does the upfront optimization cost amortize against the per-query savings?
