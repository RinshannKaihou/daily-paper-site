Security gap analysis · arXiv 2609.00267 · 2026-08-31

Under an untrusted-model standard, default agent runtimes fail all four delegation threats — a 160-line capability broker blocks all four.

Delegation Without Trust: An Empirical Gap Analysis of Identity, Authorization, and Runtime Governance in Multi-Agent LLM Systems
Panduranga Sai Varma Dantuluri, Jyotirmoy Sundi · VotalAI · arXiv 2609.00267
agent-security multi-agent systems authorization prompt-injection delegation
Key metric
8,100→1.5
Mean tool actions reachable by a compromised sub-agent: 8,100 under bearer delegation vs 1.5 under the broker — exactly its delegated sub-task, across 2,000 randomized scenarios.
Why this matters

Any security that depends on the model not being hijacked is not security. Long-running autonomous agents holding real credentials must enforce authority outside the model.

Critical edge

The problem framing is aligned with the authors’ own product by construction — and with the reference code unreleased, the headline numbers are not independently checkable.

Methodology Results Strengths & Limits Questions

01 Methodology

Three movements: derive requirements from an untrusted-model threat model, measure the gap, then compose mature primitives into a broker and attack it.

1 · Threat model → 8 requirements

  • Every agent’s model is untrusted — injection may fully control its output. Four adversaries: confused deputy (T1), token theft/replay (T2), injection privilege escalation (T3), compromised sub-agent (T4).
  • Goals G1–G5 (no authority beyond delegation, monotone narrowing, stolen-credential inertness, prompt revocability, chain attribution) yield requirements R1–R8; R8 — enforcement outside the model — is load-bearing.

2 · Gap analysis, heterogeneous by design

  • A default runtime (one broad bearer credential forwarded unchanged; model-gated authorization) is built and each adversary is run against it.
  • LangGraph 1.2.10 executed against a real compiled StateGraph; CrewAI 1.15.13 / AutoGen 0.7.5 by code inspection; MCP authz spec (rev 2026-07-28) by specification analysis. Nine standards mapped to R1–R8 cell by cell.

3 · The broker & its evaluation

OIDC grant → per-hop issuer-mediated exchange → attenuated + SVID-bound + short-lived token → complete mediation at every tool call → tamper-evident log → chain-propagating revocation
  • ~160 lines of stdlib Python: macaroon-style HMAC capability tokens with append-only caveats (authority can only narrow).
  • Four evaluation axes: defense effectiveness, 11 direct attacks on the broker’s own design + fuzzing, blast radius over 2,000 randomized scenarios, and overhead over 2×10⁵ calls each.

On the same scenario harness: the default runtime is breached by every adversary; the broker blocks every one. Framework coverage is worse than the broker gap suggests.

Beyond the headline

  • 0 of 200,000 forged/mutated tokens accepted; all 11 direct design attacks resisted (forging, caveat stripping/widening, re-binding, replay, scope-widening via exchange, revoked/expired children).
  • One boundary case succeeds by design and is reported: a stolen token works if the attacker can present the victim’s SVID — sender-constraining reduces to workload-identity strength.
  • ~2.6 µs per authorization decision (~3.9×10⁵/s), ~5.4 µs per token exchange on a laptop — negligible next to content-safety inference (production guardrail check ~190 ms).
  • The invariant, not the ratio: defended reach is bounded by the task; undefended reach equals the environment and grows without bound.

03 Strengths

What holds up
  • The right evaluation standard — untrusted-model security, stated once and applied consistently, including to the paper’s own claims.
  • Empirical where possible, honest where not — LangGraph executed; CrewAI/AutoGen inspection and MCP spec analysis labeled per row.
  • R1–R8 is a reusable artifact — makes the “no single standard composes these” claim checkable cell by cell, and separates this credential-layer scope from policy-engine work (Progent, FORGE, PAuth, AC4A).
  • Attacks its own design, not just strawman runtimes; the boundary case that succeeds by design is disclosed as such.

04 Limitations

What does not
  • No live model in the loop — scripted agent nodes; real injected-LLM driving tool calls through the broker is untested.
  • Reference implementation not released — every headline number rests on the authors’ own harness; no third-party reproduction.
  • Toy cryptography — HMAC stands in for real sender-constraining; “SPIFFE-style” identity is not actual mTLS/SPIFFE attestation.
  • Synthetic world — the 8,100-action environment is author-designed; no mapping to a real production tool surface.
  • Not integrated into the evaluated frameworks; developer cost of routing all tool calls through the broker is unaddressed.
  • Vendor paper — Section 8’s production claims come from the authors’ commercial product and are not evaluated.

05 Questions for further exploration

  • With a real injected LLM — not a scripted node — does the model reliably route tool calls through the PEP, or can it bypass mediation by calling tools directly?
  • What is the actual deployment cost of workload-identity attestation for ephemeral, dynamically spawned sub-agents, given sender-constraining collapses to exactly that assumption?
  • Can the R1–R8 matrices become a live conformance suite that re-runs automatically as LangGraph, CrewAI, AutoGen and the MCP spec evolve?
  • How should this credential-layer broker compose with per-call policy engines (Progent, FORGE, PAuth, AC4A)? The composition is sketched but never evaluated.
  • Does “defended reach is bounded by the task” survive natural-language sub-task scopes — and who audits the mapping from task text to tool/resource tuples?
