> **一句话总结：** ByteDance Seed 等提出 HarnessDev 基准，把评测单元从"任务输出"换成"可运行的 agent 执行框架（harness）"：6 个前沿 LLM（Opus 4.8、GPT-5.5、Gemini 3.1 Pro、DeepSeek V4 Pro、Qwen 3.7 Max、Seed 2.0 Pro）从一个只能解析任务、不能解题的"弱种子"出发，为 5 个下游基准（SWE-bench Pro 731 题、Terminal-Bench 2.1 89 题、MLE-bench 75 题、EQ-Bench3 46 题、BrowseComp 1,296 题，共 2,207 实例）从零构建完整 harness（Creation），再基于下游执行反馈迭代改进自己的 harness（Evolution）；结果发现自建 harness 在写作、ML 实验上追平甚至超过人类工程参考（MLE-bench 奖牌率 32.9 vs MLEvolve 24.0），但在搜索/研究类差距巨大（BrowseComp 52.4 vs 92.2），而 Evolution 的增益在 630 个 held-out 任务上缩水到 +1.43~+4.44，且换一个执行模型后 9 条演化谱系中仅 1 条仍正增长。

> **TL;DR:** HarnessDev is a benchmark that shifts agent evaluation from task outputs to runnable infrastructure: a creator LLM must build a full agent harness from a deliberately weak seed (which scores 0.0 on all five downstream benchmarks) and then iteratively improve it from execution feedback. Across six frontier creators and five benchmarks (2,207 instances; SWE-bench Pro, Terminal-Bench 2.1, MLE-bench, EQ-Bench3, BrowseComp), Creation under Self-Eval reaches 67.8 avg for Opus 4.8 — near the human-engineered reference avg of 68.2, matching it on writing (EQ-Bench3 84.6 vs 83.7) and exceeding it on MLE-bench (32.9 vs 24.0) — but collapses to 52.4 vs 92.2 on BrowseComp; under a fixed Gemini executor, Opus's SWE-Pro score falls from 69.3 to 33.0. Evolution yields visible feedback-set gains (e.g., Qwen 41.0→55.7, DeepSeek 47.2→60.6 pair-score) that shrink to +1.43..+4.44 on 630 held-out SWE-Pro tasks, and with a fixed runtime only 1 of 5 lineages still improves — robust self-evolution of harnesses remains unsolved.

## 核心贡献

- **评测对象转移**：提出首个把"评测单元"从单次任务输出改为**可运行、可持久化执行框架（harness）**的基准。harness 被冻结后在 hidden 下游任务上复用，从能力（capability，任务成功率）和效率（efficiency，executor token 开销）两个轴打分。
- **两阶段设计**：Creation（RQ1）从统一的"弱种子"（只含被动原语、无任何任务策略，未修改时 5 个基准全 0 分）+ 1–3 个开发用例出发构建完整 harness；Evolution（RQ2）从创作者自己 RQ1 的 Code harness 出发，用 100 题 SWE-Pro + 89 题 Terminal-Bench 反馈集迭代，预算 10 次全量评估，最后在 630 个不相交的 SWE-Pro held-out 任务上另行评估。
- **防作弊的可检验约束**：分数路径与 harness 隔离（SWE-Pro 只认任务工作目录里的真实 repo diff，Terminal-Bench 只认最终环境状态），每次运行后审计合规，作者报告所有结果均无违规通道。
- **六个前沿模型 × 五基准的实证刻画**：发现 harness 质量按任务族剧烈分化（写作/ML 实验追平或超过人类参考、搜索/研究差距最大）、自建 harness 高度依赖执行模型、77.8% 的 Data 失败归因于 harness 缺陷而非模型能力、生成代码中大量"死机制"（124/387 Writing 特性是死代码）。
- **Evolution 的悲观但严谨的结论**：可见反馈集上的增益在 held-out 上缩水甚至反转；同一 commit 的重跑噪声达 ±4.75 分，9 条谱系中仅 2 处切换有超出噪声的明确正增益，只有 2/9 的声明版本是 held-out 最优。

## Key Contributions

- **A new unit of evaluation**: HarnessDev scores the *frozen, reusable harness* a model builds (not a one-off answer), on two axes — capability (held-out task success) and efficiency (executor tokens consumed; creator tokens excluded).
- **Two-stage protocol with a policy-free seed**: Creation starts every creator from the same weak seed (passive primitives only; scores 0.0 unmodified), so any nonzero score must come from control logic the creator adds; Evolution chains from the creator's own RQ1 Code harness with a 10-full-evaluation budget, at most two diagnostic probes, and a post-freeze evaluation on 630 disjoint SWE-Pro instances never shown to the creator.
- **Checkable anti-gaming constraints**: the score path is isolated from the harness (SWE-Pro credit requires a real repository diff in the task workdir; Terminal-Bench credit only the final environment state), and every reported run is audited post-hoc — no violation was found.
- **A broad empirical map of harness engineering**: six frontier creators (Opus 4.8, GPT-5.5, Gemini 3.1 Pro, DeepSeek V4 Pro, Qwen 3.7 Max, Seed 2.0 Pro), four domains, five downstream benchmarks, 2,207 unique instances, with SELF-EVAL (executor = creator) and UNIFIED-EVAL (fixed Gemini 3.1 Pro executor) ablations.
- **Honest negative findings on evolution**: feedback-set gains shrink or reverse on held-out tasks; repeated-run noise (±4.75 pair-score points on the same commit) swamps most version-to-version deltas; only 2/9 declared final versions are held-out optimal.

## Methodology

The benchmark separates the model that *develops* the harness from the model that *executes* tasks inside it: `(L_C, D) → H` (creator LLM plus development environment produces harness H), then `(H, L_E, x) → y → score` (a frozen executor L_E runs H on downstream task x, and evaluator J scores y). H contains the execution loop, tool policy, context management, persistent state, lifecycle/recovery, and verification — the six control modules the seed omits.

**Creation (RQ1).** Every creator receives the same weak seed H_seed — a runnable compatibility layer that parses task/model config, exposes passive primitives (paths, files, search, process, LLM gateway, artifact I/O), performs one non-acting pass, and writes an audit envelope; it has no agent loop, tool policy, task decomposition, state, verifier, or stopping rule. The creator also gets a task-family specification, tool/permission constraints, a design tutorial, and 1–3 development cases; hidden tasks, answers, and official scores stay withheld. The frozen harness is then run on the benchmark. Each creator–benchmark pair is independently repeated 3 times (avg@3). SELF-EVAL sets executor = creator; UNIFIED-EVAL runs every generated harness with Gemini 3.1 Pro as the fixed executor to isolate harness compatibility from executor capability. Constraint compliance is enforced structurally (credit comes only from real repo diffs / final environment state, never self-reported status) and audited after every run.

**Evolution (RQ2).** Starting from the creator's own frozen RQ1 Code harness H_0, the creator receives results from a designated feedback set — a 100-task SWE-Pro subset plus all 89 Terminal-Bench tasks — and a budget of ten post-H_0 full-evaluation pairs (each candidate must complete both benchmarks in the same commit), plus at most two fixed-subset probes (the same first five tasks of both benchmarks; diagnostic only). Nine lineages are run: five self-runtime (creator = executor) and four fixed-Gemini ablations, yielding 73 official versions and 64 adjacent version switches. The reported pair score is the unweighted mean of SWE-Pro-100 and Terminal-Bench-89 percentages. After all trajectories end, *every* official version is additionally evaluated on a 630-instance SWE-Pro held-out split disjoint from the feedback set — separating adaptation to observed feedback from held-out generalization.

**Metrics.** Capability = each benchmark's native metric (SWE-Pro % resolved, Terminal-Bench accuracy, MLE-bench medal rate, EQ-Bench3 rubric score, BrowseComp accuracy). Efficiency = executor-model tokens (total and mean per task). Creation compares against the zero-score seed and against verified human-engineered reference systems (e.g., Claude Fable 5 + a public coding-agent setup for SWE-Pro at 80.0; OpenAI agent setup + GPT-5.6 Sol at 88.8 on Terminal-Bench; MLEvolve + Gemini 3.1 at 24.0 on MLE-bench; Kimi Writer + Opus 4.8 at 83.7 on EQ-Bench3; OpenAI browsing stack + GPT-5.6 Sol at 92.2 on BrowseComp — three of the five are external leaderboard numbers). Models run through their official APIs or OpenRouter; all creators use Claude Code 2.1.177 as the development environment except GPT-5.5 (Codex 0.144.3).

## Results & Highlights

- **Creation approaches but does not reach human-engineered systems, with huge domain variance.** Under Self-Eval, Opus 4.8 posts the best avg of 67.8 vs the human-reference avg of 68.2 (weak seed: 0.0; GPT-5.5: 55.1; Gemini 3.1 Pro: 55.6; DeepSeek V4 Pro: 46.3; Qwen 3.7 Max: 46.6; Seed 2.0 Pro: only 22.8). Writing approaches the reference (Opus EQ-Bench3 84.6 vs human Kimi Writer 83.7) and ML experimentation exceeds it (Opus MLE-bench medal rate 32.9 and Gemini 32.4 vs MLEvolve 24.0), but Search shows the largest gap (Opus BrowseComp 52.4 vs 92.2, −39.8 points) and Code stays behind (Opus SWE-Pro 69.3 vs 80.0; Terminal-Bench 64.8 vs 88.8).
- **Executor compatibility dominates: fixing the executor reorders the leaderboard.** Under Unified-Eval (fixed Gemini executor), Opus's SWE-Pro score collapses from 69.3 to 33.0 because it hard-codes a 120-step limit around its original executor, and its Writing score falls 84.6→74.2; conversely Qwen gains +17.6 on BrowseComp and +12.9 on MLE-bench under Gemini, and DeepSeek's MLE-bench rises 19.6→32.4. Opus's Search harness's duplicate-query rate rises from 10.1% to 88.2% when the executor changes.
- **The bottleneck is often the harness, not the model.** 77.8% of failed Data tasks are attributed to harness defects; 441 of 2,325 executed Data tasks produce degenerate submissions that *no* generated harness detects (validation is mostly syntactic). Dead mechanisms are rampant: 18 of 108 Code component instances are never observed at runtime, 124 of 387 Writing features are confirmed dead code, and 36 Data mechanisms sit on dead paths. Self-test count correlates with downstream score at only Spearman 0.13–0.26 (not significant), whereas revision calls reach 0.57 (p ≤ .0005).
- **Efficiency is wildly uneven and does not buy quality.** MLE-bench token use varies by ~19× across harnesses; GPT-5.5 reaches a 19.1 medal rate with 29.3M tokens while DeepSeek V4 reaches 19.6 with 208.4M — an order-of-magnitude cost gap for the same score. Code artifacts add 17,111 net LOC in total, yet Gemini adds the fewest lines (1,006) and gets the best Terminal-Bench score (68.8) — edit size does not predict performance.
- **Evolution: visible gains, fragile generalization.** All five self-runtime creators improve on the visible feedback pair (Qwen 41.0→55.7; DeepSeek 47.2→60.6; Opus 71.1→74.1; GPT-5.5 59.2→65.1; Gemini 59.9→68.7), but held-out-630 gains shrink to +1.43..+4.44 (best: Opus 63.02→67.46, +4.44; mean +3.11). Under fixed Gemini, only Opus still improves on held-out; three lineages regress (GPT-5.5's declared final version drops 42.22→31.90 on held-out, a final-gap of 16.51 vs its lineage's best held-out score).
- **Version selection and stability are unreliable.** Of 64 official switches, 8 regress on both benchmarks, 27 gains sit inside the repeated-run noise band (same commit varies by ±4.75 pair-score points), only 2 show clear positive evidence beyond noise, and 1 contains no executable code change. Feedback and held-out scores move in the same direction only 34 times (53.1%), and only 2/9 declared versions are held-out optimal — repeatedly optimizing a noisy visible score can favor a lucky run.
- **Feedback use is superficial.** The median declared version changes 8 files (+476/−38 lines); 58/64 switches change execution or control flow, but only 4 change state and none modify the standalone verifier. The dedicated trajectory interface is called only twice, explicitly inspected cases cover 0.5%–40.2% of the 189 feedback tasks, and one GPT-5.5 candidate passes all five Terminal probes yet scores 0.584 on the full set. The clearest positive example: Opus found that 99 of 100 runs reported success while only 48 passed, traced this to premature completion, and added a completion gate.

## Authors & Credibility

The paper comes from **ByteDance Seed** (with the National Innovation Institute of Frontier Technology branding on the title page), jointly with Singapore University of Technology and Design, Georgia Tech, M-A-P, and TokenWave.AI. Core contributors are Yuhao Wu, Jingyuan Zhang, and Jiajun Shi; corresponding authors include Yuhao Wu, Shen Yan, Wenhao Huang (ByteDance), Ge Zhang (UMich), and Wenxuan Zhang (SUTD) — a team with a track record in agent and LLM evaluation work. Credibility signals are strong: the protocol uses frozen harnesses, avg@3 repetition for Creation, a fixed-executor ablation, post-hoc audits of every reported run for constraint compliance (none violated), and release of the seed, audit artifacts, and held-out splits (project page: self-developing-agents.github.io). The authors are unusually candid about their own negative results (evolution mostly fails to generalize) and explicitly position the work against concurrent benchmarks (Meta-Agent Challenge, HarnessOpt-Bench, Evo-Bench). Caveats: it is an industrial-lab benchmark where several "human reference" rows are external leaderboard numbers, and the evaluated models are the authors' own ecosystem's competitors — no direct conflict, but Seed 2.0 Pro's remarkably low Creation score (22.8 avg) invites scrutiny of dev-environment fit.

## Critical Assessment

**Novelty.** The core reframing — evaluate the *persistent execution system* rather than the task output — is genuinely valuable and well executed, and the Creation/Evolution split with self-vs-fixed runtime is more complete than concurrent efforts: HarnessOpt-Bench (closest concurrent work) optimizes a provided harness from a near-empty GAIA seed, Evo-Bench scores only final revisions on a fixed runtime, and the Meta-Agent Challenge covers only Creation-like construction. That said, the space is crowded (VeRO, Meta-Harness, HarnessFix, Harness-RL, SEW, HarnessCompass are all cited 2026 works), so the contribution is a benchmark + careful study, not a method.

**Rigor — mostly high, with real limits.** The anti-cheating design (score path isolated from harness, audits after every run, real-diff credit) is the best part of the paper. But the Evolution study rests on **one trajectory per creator-runtime cell** (nine lineages total, one main-runtime cell unfinished), which the authors admit supports no uncertainty estimates; with same-commit repeated-run noise of ±4.75 points, most of the 64 switches (27 inside the noise band) are simply uninterpretable, so headline claims like "gains shrink on held-out tasks" are directionally credible but statistically thin.

**The human-reference comparison is apples-to-oranges, and the paper knows it.** The "human-engineered reference" row that Opus nearly matches (67.8 vs 68.2) mixes systems paired with *different, stronger executors*: SWE-Pro 80.0 is "public coding-agent setup + Claude Fable 5", Terminal-Bench 88.8 and BrowseComp 92.2 are starred values taken from OpenAI's GPT-5.6 release report, not re-run. Figure 4's "distance to human reference" framing therefore conflates harness quality with executor capability — the paper flags this in captions and appendix, but the abstract-level narrative ("approaching human-engineered references") still benefits from the framing.

**Missing/weak ablations.** All creators except GPT-5.5 share Claude Code 2.1.177 as the development environment; there is no experiment separating whether Seed 2.0 Pro's 22.8 avg reflects harness-building inability or a poor fit with a rival's dev environment. The "77.8% of failed Data tasks attributed to harness defects" number is load-bearing for the headline but its attribution methodology is only sketched in the main text. Cost is measured but never collapsed into a score, so the 19× MLE-bench token spread is descriptive rather than optimized against.

**Reproducibility.** Good intent (seed, audit artifacts, held-out splits to be released), but results depend on proprietary, versioned frontier models via commercial APIs — exact replication will decay quickly, and avg@3 cannot control provider-side model drift.

**Red flags.** (1) Three of five human references are external reports with different executors; (2) Evolution's n=1-trajectory design vs its fairly strong conclusions; (3) one collapsed EQ-Bench3 cell (46.5 vs 69.7 depending on excluding a zero-valued first harness) and two collapsed Code cells handled via post-hoc sensitivity means — the avg@3 aggregation is fragile at the edges.

## Strengths

- Shifts the evaluation target to the artifact that actually determines deployed agent quality — the harness — and makes it measurable on both capability and executor-token cost.
- The weak-seed design is elegant: a policy-free, runnable floor (0.0 on all five benchmarks) guarantees that all score comes from the creator's control logic, cleanly separating harness design from benchmark boilerplate.
- Checkable, audited anti-gaming constraints (real repo diffs, final environment state, no self-reported credit) — rare and commendable in agentic benchmarks.
- The Evolution protocol cleanly disentangles adaptation (visible feedback) from generalization (post-freeze 630-task held-out), exposing that version selection on noisy feedback is unreliable (only 2/9 declared versions held-out optimal).
- Rich, honest behavioral analysis: dead-code censuses (124/387 Writing features), trajectory audits, the 99-report-vs-48-pass completion-gate example, and the 120-step hard-code that tanks Opus under a new executor are concrete, memorable failure modes.

## Limitations

- Evolution has a single trajectory per creator-runtime cell (nine lineages, one unfinished), and post-freeze held-out evaluation covers SWE-Pro only — no uncertainty estimates or population-level claims are possible.
- Human references are unpaired, uneven, and not guaranteed optimal; three of five are external leaderboard numbers obtained with different executor models, so "distance to human reference" is indicative, not a controlled comparison.
- Unified-Eval reduces but cannot remove executor-model differences, since harness–model interaction is complex; behavioral comparisons are descriptive with limited benchmark coverage.
- The four domains (code, data, writing, research) cover many but not all real deployments; the development environment D is fixed, so whether an evolved harness can itself host further evolution is untested.
- The benchmark measures model-external learning only — the authors explicitly do not claim it captures what parameter training could provide.

## Relevance

这篇论文正中你的第一优先方向「Self-Evolving Agents & Automated Research」：它评测的正是 LLM 能否从弱种子自主构建并基于执行反馈持续改进自己的 agent harness（自修改 agent 架构），且对长程自主系统"反馈集上涨、held-out 上跌"的可靠性问题给出了目前最系统的量化证据，是设计自演化实验协议时值得直接借鉴的基准与方法学。

## Questions for Further Exploration

- Would Evolution's held-out collapse persist with multiple trajectories per cell and a proper matched-budget search baseline (the authors list matched-search evaluation as future work)?
- Is the executor-transfer failure (e.g., Opus's hard-coded 120-step budget) fundamentally an abstraction problem — would a standardized runtime interface for budgets/stopping rules make harnesses portable across executors?
- The 77.8% harness-defect attribution for Data failures: can failure attribution itself be automated and fed back as a structured diagnosis signal, given that creators currently inspect only 0.5%–40.2% of feedback tasks and call the trajectory interface only twice?
- Dead mechanisms (18/108 Code instances never fire; 124/387 Writing features are dead code) suggest generated harnesses are over-built — would smaller, verification-heavy harnesses (like Gemini's 1,006-LOC best Terminal-Bench artifact) be a better explicit design target?
- The human-reference rows pair harnesses with stronger executors; what would a properly *paired* human-harness control under a common executor show on SWE-Pro and BrowseComp, where the gap is largest?
