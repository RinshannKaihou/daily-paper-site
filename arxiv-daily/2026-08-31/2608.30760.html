Frozen Qwen3-VL-32B executor. Beats the strongest experience-augmented baseline by +9.7 pts; cross-executor gains up to +30.3 (GPT-5.2). Total learner training ≈ 71 GPU-hours.

Why this matters

Self-evolving agents get a stable, RL-free improvement loop — and failure-aware supervision beats piling on success data (+2.6 vs +0.4).

Critical edge

Of the +25.4 headline gain, +16.4 comes from the unlearned static library alone — the celebrated learning loop adds just +9.0.

§01Methodologylearner–library co-evolution
  1. Setup — frozen executor + persistent library of skill cards (action-pattern sequence + usage spec: preconditions, effects, recovery strategies). A trainable learner S emits structured edits (ADD / REVISE / MERGE / REMOVE): library guides trajectories → trajectories train learner → learner edits library.
  2. BPE-style cold start — frequent adjacent action subsequences mined from successful trajectories are merged (byte-pair-encoding style) into structured cards.
  3. Stage 0 — oracle SFT — skill generation from an empty library, evidence-based editing, and cross-batch consolidation (dedupe, merge overlapping patterns); teacher Qwen3-7-Max.
  4. Stage 1 — failure-aware SFT — same-task success/fail contrast batches from 8 heterogeneous executors isolate behavioral differences; learner records invalid conditions + recovery strategies.
  5. Stage 2 — Skill OPD — student samples its own edit rollouts; a frozen 32B teacher supplies Top-K token distributions (KT=32, KS=8); truncated forward KL — no task reward, no PPO/GRPO machinery, fixes offline SFT’s train–inference mismatch.
  6. Cost — ~7 GPU-h SFT + 64 GPU-h OPD (8×A100-40GB, FSDP + vLLM); ~2,250 SFT examples per benchmark.

  • Cross-executor generality: +30.3 on GPT-5.2 (32.0→62.3), +25.4 on Qwen3-VL-32B, +15.3 on Gemini-3-Flash — the largest matched improvements reported among experience-augmented methods — but only +2.4 on the already-strong GPT-5.4 (65.3→67.7).
  • Failure-aware learning is the active ingredient: at equal data volume, success-only Stage 1 adds just +0.4 (42.3→42.7) vs +2.6 with failure supervision; Long-horizon 8%→14%.
  • Execution quality, not just scores: failure-free episodes 13.3%→25.7% (300 episodes); skills recover 91 no-skill failures at 15 regressions (net +25.3 pp; 12 long-horizon episodes solved vs 0 baseline); EB-Habitat 58 recoveries vs 32 regressions.
  • With a GPT-5.4 executor: 67.7% EB-ALFRED / 72.0% EB-Habitat — vs proprietary Qwen3.5-Flash’s 37.0 / 38.0.
  • The library abstracts macro-procedures: 29 cards on EB-ALFRED (13 single + 16 composite; HeatAndStoreFoodItem expands to 15 actions), 15 on EB-Habitat — granularity adapts to the environment.

+Strengths

  • Clean formulation: skill maintenance as a trainable update policy co-evolving with a persistent library, executor frozen — composable with any executor, including proprietary ones.
  • Skill OPD is genuinely novel: on-policy distillation adapted to structured library editing — sidesteps RL instability, fixes SFT distribution mismatch, zero reward engineering.
  • The failure-aware claim is validated by a controlled ablation at equal data volume, not asserted.
  • Exceptional analysis depth: paired episodes with 95% bootstrap CIs, per-skill benefit-risk quadrants (flags harmful low-frequency skills like Drop), candid failure studies.
  • Cheap and auditable: ~71 GPU-hours total, full hyperparameters published, public project page.

−Limitations

  • Two simulated, discrete-action benchmarks only; transfer to continuous control or real robots is untested and the skill-card formalism may not extend.
  • Absolute numbers trail executor post-training by ~21 pts (ELITE 70.8%, ORBIT 72.4% vs 49.7% on EB-ALFRED); whether gains stack with post-training is unmeasured.
  • Value concentrates on weak executors (+2.4 on GPT-5.4 vs +30.3 on GPT-5.2); 0 pp net on EB-Habitat Spatial; EB-ALFRED Long still 24.0%.
  • Supervision depends on frontier proprietary models (8 executors + Qwen3-7-Max teacher); the API cost of ~3,000 trajectories/benchmark is unreported — flattering the “lightweight” framing.
  • Single-teacher OPD (the teacher is also the executor — unaddressed circularity); headline averages are single-run, no variance; long-run library stability (bloat, drift, collapse) uncharacterized.
§03Questions for further exploration
  1. Can Skill OPD take a task-reward signal (e.g., value-weighted edit acceptance) without reintroducing RL instability — or does pure teacher-KL cap library quality at the teacher’s editing ability?
  2. Do the gains stack with executor post-training (ELITE, ORBIT, RoboAgent), or does a stronger executor shrink the marginal value of library evolution to zero, as GPT-5.4 (+2.4) suggests?
  3. Over many more OPD rounds than reported, does the library keep improving, saturate, or accumulate noisy edits that eventually degrade execution — the key reliability question for long-running self-evolving systems?
  4. Could the learned policy replace the BPE pattern-mining cold start that supplies +16.4 of the +25.4 total — or is the static bootstrap essential?
  5. Can failure-aware skill cards extend to continuous/low-level action spaces and real robots, where “rejected action” feedback is noisier and recovery is physically grounded?
