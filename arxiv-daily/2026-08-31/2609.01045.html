arXiv 2609.01045 2026-08-31 Automated Agent Design

Jointly searching fine-tuned models and code workflows, an LLM optimizer gains +9.1 average over the strongest workflow-only automated design.

AgentFactory: Towards Automated Agentic System Design and Optimization

Enci Zhang, Haofeng Wang, Yuesheng Zhu, Xiaole Cui, et al. · Peking University Shenzhen Graduate School · Guibao Lu (corresponding)

llm-agents automated-agent-design multi-objective-optimization llm-fine-tuning self-evolving-agents
Key Metric
+9.1

Average over 8 benchmarks (Llama-3.1-8B): 68.9 vs AFlow 59.8 and ADAS 56.7 — including +19.6% on MedQA (65.4 vs Reflexion 47.2) and +18.7% on FinEval (58.5 vs AFlow 39.8). With GPT-4o-mini: 83.9 avg at $0.68 inference cost, a claimed −68% vs ADAS.

Why This Matters

An automated agent-construction feedback loop — an LLM optimizer over models plus workflows with external evaluation — directly relevant to self-evolving agent systems and reliability trade-offs.

Critical Edge

The comparison is unfair by construction: baselines optimize workflows with a frozen model, so headline domain gains largely measure fine-tuning privilege, not search quality.

Methodology LLM-as-optimizer loop

Joint search space S = {(m, w)}: a model m = (b, d, h) — base model, instruction fine-tuning dataset, hyperparameters (φ ∈ {LoRA, QLoRA, full}; third-party models get d = ∅, h = ∅) — paired with a workflow w as executable code (ADAS-style), chosen over graphs for expressive control flow.

  • Optimization loop: the trajectory records every (candidate, metric vector) pair; the optimizer LLM generates sk = Lθ(Ok−1, M, Imeta); terminate when all objectives meet Gtarget or at Kmax = 20 steps; Pareto selection via a user scalarization F.
  • Three-stage pipeline: Planning (insights / model specs / workflow outline) → Tuning (OpenRLHF backend; ≤20K samples, ≤4h per session on 4×A6000, model caching; configs auto-adjust on hardware failure) → Workflow Design (prompting, tool calls, control flow as code).
  • Multi-objective: accuracy, cost, and latency (the last formalized but never measured); after accuracy targets are met the optimizer explicitly drives cost down.
  • Evaluation: 8 benchmarks × 5 domains, two base settings (Llama-3.1-8B-Instruct; GPT-4o-mini), 5 candidate optimizer LLMs, 3 repeats; baselines IO, CoT, CoT-SC, Reflexion, LLM Debate, ADAS, AFlow.

Results beyond the headline

  • Llama-3.1-8B: MATH 44.6 vs AFlow 31.1 (+13.5); GSM8K 92.2 vs 89.4; HumanEval 84.4, MBPP 70.8, MMLU 79.8, DROP 67.4. Gains concentrate on domain benchmarks where workflow-only search stalled.
  • GPT-4o-mini setting: 83.9 avg vs AFlow 78.5; the optimizer deliberately picks cheaper models — MedQA 86.8 vs 77.5. The one exception: AFlow wins DROP (79.9 vs 79.3).
  • Ablation (vs IO baseline): the full pipeline beats the fine-tuning-only variant by +12.7% and the workflow-only variant by +8.2%; fine-tuning dominates the domain gains (MedQA, FinEval).
  • Optimizer sensitivity: GPT-4o 68.7, Claude-3.5-Sonnet 67.1, Gemini Pro 1.5 66.3, DeepSeek V3 63.3, GPT-4o-mini 58.0 — comparable outcomes for similarly capable optimizers, but a 10.7-point spread overall.

Strengths

  • The right generalization: first clean multi-objective statement of joint model × workflow search, with target thresholds and a scalarized Pareto selection step.
  • Unusually broad evaluation: 8 benchmarks, 5 domains, two foundation-model regimes, five optimizer LLMs, plus a transparent ablation quantifying each component.
  • The FinEval case study is genuinely informative — it exposes the optimizer’s real trajectory (workflow plateau → fine-tuning jump → data mix → cost shaving), more interpretable than a single number.
  • Realistic, stated constraints: ≤20K samples, ≤4h sessions, caching, 20-iteration budget; cost-aware model switching is deployment-relevant.
  • Optimizer-independence check (Table 2) addresses a real robustness concern for LLM-as-optimizer methods.

Limitations

  • Baseline asymmetry: automated baselines are denied fine-tuning, so domain gains cannot be decomposed into “better search” vs “more data access”; no manual-fine-tune + AFlow control exists.
  • Cost accounting is incomplete: inference only — optimization overhead (up to 20 GPT-4o iterations × 3 repeats + 4×A6000 hours) unreported; latency formalized but never measured; and $0.26 in the Llama setting is still 3.5–8.7× pricier than plain prompting.
  • No statistical rigor despite 3 repeats; no code or artifact release; ADAS/AFlow re-implemented rather than official.
  • Nonstandard subsets (MMLU/DROP sampled to 1,000; MATH difficulty-5 only) limit external comparability; CodeBagel → HumanEval/MBPP contamination unaudited.
  • Single-shot QA/code benchmarks only — no long-horizon agentic tasks (SWE-bench, WebArena) where workflow control flow matters most; tunable base limited to Llama-3.1-8B.

Questions for Further Exploration

  • How much of the MedQA/FinEval gain survives if ADAS or AFlow is granted the same fine-tuning corpora and budget — i.e., the isolated contribution of joint search itself?
  • Since latency is formalized but never measured, how does AgentFactory trade accuracy against actual wall-clock latency when a latency target is imposed?
  • Does the optimizer overfit the evaluation set over 20 feedback iterations — would a held-out validation split change the reported numbers?
  • How does the framework behave on long-horizon agentic benchmarks (SWE-bench, WebArena) where control flow and tool orchestration dominate?
  • Can fine-tuning be replaced by cheaper adaptation (prompting, RAG, routing) in domain tasks, given the ablation suggests it carries most of the gain?
  • What is the total optimization cost per task, and at what usage volume does it amortize against per-query savings?
