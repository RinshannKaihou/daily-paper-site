> **一句话总结：** UCSD 团队将自动建模智能体 AIBuildAI-2.5 的三大效率短板（奖励稀疏、无资源感知调度、全量调用昂贵 LLM）分别用"LLM 先验 + 实测奖励"的 judge/selector 树搜索、资源感知调度器、按 agent 角色的三级模型路由（Haiku 4.5/Sonnet 4.6/Opus 4.7）解决，在 MLE-Bench 75 个 Kaggle 任务上以 73.3% 奖牌率登顶（次优 70.7%、MLEvolve 61.3%），在 AIRS-Bench 六项 AI 研究任务上全面超越 MLEvolve（ZINC 溶解度 MAE 降低 29.8%、QM9 Cv MAE 降低 20.8%、SICK-NLI 准确率 +5.1%），且模型路由以约 44% 的成本（−56%）达到或超越全 Opus 配置的任务分数。

> **TL;DR:** AIBuildAI-2.5 is an autonomous agent that builds ML models via tree search over candidate training pipelines, and fixes three efficiency gaps of prior agents: (1) sparse/noisy rewards from few executed candidates are compensated by an LLM judge (0–5 scores on expected improvement over parent, grounding in measured sibling/parent results, and feasibility) plus a global selector that fuses these priors with measured rewards; (2) a resource-aware scheduler launches ranked training jobs according to live GPU/CPU headroom; (3) a router assigns each agent role the cheapest sufficient model from a pool of Claude Haiku 4.5 / Sonnet 4.6 / Opus 4.7, grounded in a cross-run routing knowledge system. On MLE-Bench (75 Kaggle tasks, 24-hour budget, 1× A100) it ranks first on the official leaderboard with a 73.3% medal rate vs 70.7% for the runner-up and 61.3% for tree-search baseline MLEvolve; on all six AIRS-Bench autonomous-research tasks it beats MLEvolve under identical budgets (e.g., ZINC solubility MAE 0.0645 vs 0.0919, −29.8%; QM9 Cv MAE 0.0270 vs 0.0342, −20.8%; SICK-NLI accuracy 0.927 vs 0.882, +5.1%); and per-role routing matches or beats the best fixed Claude tier on all three tested MLE-Bench tasks while cutting total cost by 56% relative to an all-Opus configuration.

## 核心贡献

- **诊断先前的自主建模智能体的三大效率缺陷**：真实算力预算下能执行训练的候选程序太少，导致树搜索的奖励信号稀疏且带噪（MCTS/UCT 式规则难以有效选节点）；缺少资源感知的训练作业调度，拉低硬件利用率；每次 agent 调用都由单一昂贵 LLM 服务，推理成本虚高。
- **LLM 引导的树搜索（核心方法贡献）**：judge 对每个待执行叶子按三个维度打 0–5 整数分——相对父节点的期望提升、与父节点/兄弟/叔伯节点实测结果的锚定程度、单个训练时段内的计算可行性——并对表现出 reward hacking（伪造指标、泄漏验证集）的候选直接打 0 分；selector 结合 judge 分数与全局搜索状态对整个叶子池排序，偏好架构多样性、折损死胡同谱系、抑制近重复候选，并随预算消耗从探索转向利用。LLM 先验与已测奖励的组合取代了单纯依赖 MCTS 式奖励的选点规则。
- **资源感知作业调度器**：按 selector 排出的顺序、依据 GPU 显存/利用率与 CPU 阈值启动训练作业，使多个候选在不超过算力的前提下并发执行，缩短 wall-clock 时间。
- **按角色的成本感知模型路由**：router agent 基于任务、数据与搜索状态为每个 agent 角色选择"最便宜的够用模型"，并引入两项路由专属输入——per-run memory（谱系中廉价模型编码的祖先表现不佳时升级 coder 到更强模型）与跨 run 累积的 router knowledge system（蒸馏知识卡 + 逐任务证据记录）。
- **实证结果**：MLE-Bench 奖牌率 73.3% 排名第一；AIRS-Bench 六项任务全部优于 MLEvolve（同预算同硬件的受控对比）；路由配置以不到一半成本匹配最强固定模型配置。

## Key Contributions

- Identifies three unaddressed efficiency weaknesses shared by prior autonomous AI-model-building agents: (i) only a handful of candidates can be executed under realistic budgets, so tree-search rewards are scarce and noisy; (ii) no resource-aware scheduling of training jobs; (iii) every agent call is served by a single expensive frontier LLM.
- Proposes LLM-guided tree search: a judge scores each pending candidate leaf on three evidence-grounded dimensions (expected improvement over parent, grounding in measured results of the parent and sibling/uncle nodes, feasibility within one training slot; automatic zero score for reward hacking), and a selector ranks the whole pool from judge scores plus search state, favoring architectural diversity, discounting dead-end lineages, suppressing near-duplicates, and shifting from exploration to exploitation as the budget shrinks. The LLM prior is combined with — not replaced by — the measured rewards.
- Adds a resource-aware scheduler that launches ranked training jobs whenever GPU memory/utilization and CPU thresholds leave enough headroom, increasing concurrent training runs under a fixed compute envelope.
- Introduces per-role, per-node model routing over a three-tier pool (Claude Haiku 4.5, Sonnet 4.6, Opus 4.7), driven by a dedicated router agent with two routing-specific inputs: a per-run memory (escalating the coder to a stronger model when a lineage coded by a cheap model underperformed) and a cross-run router knowledge system (distilled knowledge cards plus per-task evidence records) inherited from the AIBuildAI-2 knowledge architecture.
- Delivers state-of-the-art empirical results: first place on the MLE-Bench leaderboard (73.3% medal rate), wins on all six AIRS-Bench tasks against MLEvolve under controlled identical budgets, and frontier-matching task scores at roughly half the cost via routing.

## Methodology

**Problem formulation.** Autonomous AI model building is cast as a code search problem: a tree where each node is a candidate program (a full training-and-inference pipeline), expanded by generating child programs from parents; executing a node yields reward R(n), the trained model's validation score. Unlike typical code-search domains (e.g., GPU-kernel optimization, scored in seconds), every evaluation here requires training a full model — hours of wall-clock time on a search GPU — so the search tree is far smaller and rewards are noisier, demanding higher quality per generated child and per selection decision.

**Agent workflow.** Following AIBuildAI's division of labor, core expansion uses three agents: a designer reads the task and proposes N = 7 deliberately-varied initial modeling strategies (the root's children); a coder turns a strategy or revision instruction into working code, debugging in an isolated workspace until the program runs end-to-end; a reviser reads a finished node together with its program, reward, and logs, and proposes one or more concrete textual revision instructions (architecture changes, pipeline revisions, bug fixes) without writing code itself. Three auxiliary agents complete the loop: a setup agent (environment), a data-split agent (creates one global validation set shared by all nodes so rewards R(n) are comparable across the tree), and an aggregator that selects or ensembles the strongest completed nodes into the final submission at termination. Agents draw on the hierarchical AIBuildAI-2 knowledge base (skills, playbooks, per-task lessons) and external tools (paper search, curated corpus retrieval).

**LLM-guided selection.** The search maintains a pending pool of implemented-but-unexecuted leaves. The judge acts locally: from a leaf's revision instruction and surrounding tree, it emits three 0–5 integer scores (expected improvement over parent, how well the claim is anchored in the parent's measured results and sibling/uncle outcomes, computational feasibility), and assigns a zero to any candidate exhibiting reward hacking (fabricated metrics, validation leakage). The selector acts globally: it orders all leaves using judge values, the live tree, and remaining resources — favoring architectural diversity, discounting lineages whose parents hit dead ends, suppressing near-duplicates, and trading exploration against exploitation as budget decreases. Because the judge calibrates against outcomes observed so far and the selector re-orders the pool whenever a node finishes, the search signal is LLM prior + measured rewards, in contrast to Monte-Carlo-style tree search (e.g., MLEvolve's UCT rule) which relies on rewards alone.

**Resource-aware scheduler.** The scheduler holds the selector's ordered pool and repeatedly: launches the head job if nothing is running; otherwise checks for resource bottlenecks (GPU memory or utilization near capacity, CPU above threshold) and launches only when free resources meet a preset threshold; then waits a stabilization window before the next decision so a freshly launched job reaches steady-state usage first.

**Model routing.** Every agent role is assigned a model per search node by a dedicated router agent that sees the same context as the routed agent plus (1) per-run memory — which model served each earlier agent and the score its node reached, enabling within-run escalation or diversification — and (2) the two-level router knowledge system shared across runs (distilled cards: "model X is sufficient/insufficient for role Y under condition Z", backed by per-task evidence records with cost, metric, and submission validity). The router picks the cheapest pool model judged sufficient before that model is invoked.

**Baselines and settings.** The principal baseline is MLEvolve, which expands nodes with a single LLM call and selects via UCT (root of Monte Carlo tree search) over mean backed-up rewards with an exploration bonus, plus a fusion step that recombines strong branches when progress stalls. On MLE-Bench (75 Kaggle-style tasks with raw datasets and real competition grading), AIBuildAI-2.5 routes over Claude Haiku 4.5 / Sonnet 4.6 / Opus 4.7, seeds N = 7 initial drafts, and runs a 24-hour wall-clock budget on Linux x86-64 with 24 vCPUs, 256 GB RAM, and one NVIDIA A100, evaluated under the official MLE-Bench leaderboard protocol. On AIRS-Bench (six autonomous-research tasks in three categories — molecules/proteins: QM9 heat capacity and ZINC constrained solubility; text classification: SICK-NLI and Yelp review rating; time series: solar photovoltaic power and Wikipedia web traffic), the baseline agent MLEvolve runs with a Claude Opus 4.7 backbone under the identical 24-hour budget and hardware, following the official AIRS-Bench protocol.

## Results & Highlights

- **MLE-Bench: first on the leaderboard.** AIBuildAI-2.5 attains a 73.3% medal rate across the 75 Kaggle-style tasks, topping the official leaderboard — 2.6 points above the runner-up at 70.7% — and clearly ahead of ML-Master 2.0 (56.4%), Leeroo (50.7%), tree-search baseline MLEvolve (~61.3%), InternAgent (36.4%), R&D-Agent (35.1%), and AIRA-dojo (31.6%). The authors attribute the margin over MLEvolve specifically to LLM-guided selection and resource-aware scheduling completing more training runs along promising directions under the benchmark's fixed per-task budget.
- **AIRS-Bench: wins all six autonomous-research tasks vs MLEvolve under identical budget/hardware.** Molecules/proteins: QM9 Cv MAE 0.0270 vs 0.0342 (−20.8%) and ZINC constrained-solubility MAE 0.0645 vs 0.0919 (−29.8%). Text classification: SICK-NLI accuracy 0.927 vs 0.882 (+5.1%) and Yelp rating accuracy 0.704 vs 0.690 (+1.4%). Time series: solar power MAE 708.1 vs 751.1 (−4.0%) and web-traffic MASE 0.9170 vs 0.9517 (−3.6%). Because budgets and hardware were controlled, the gap is attributable to the search strategy itself.
- **Routing matches frontier quality at roughly half the cost.** On three MLE-Bench tasks spanning tabular/textual/image data (spaceship-titanic, random-acts-of-pizza, dog-breed), routing against fixed all-Opus / all-Sonnet / all-Haiku configurations: on spaceship-titanic it reaches accuracy 0.823 vs 0.811 for Opus at at most half of Opus's cost, earning a gold medal and top leaderboard rank; on random-acts-of-pizza its AUC 0.636 edges out Opus's 0.634 (Haiku: 0.602); on dog-breed it attains the lowest log-loss among all configurations — 60% lower than Haiku, the most competitive fixed tier on that task — at about half of Opus's cost. Summed over the three tasks, routing cuts cost by 56% relative to all-Opus while remaining comparable or better than the strongest fixed tier on every task; cheap Haiku-only runs visibly sacrifice performance on random-acts-of-pizza and dog-breed.

## Authors & Credibility

The paper comes from the AI Build AI group at UC San Diego: Peijia Qin, Ruiyi Zhang, Qi Cao, and Han Guo (equal contribution), with Li Zhang and corresponding author Pengtao Xie (Department of Electrical and Computer Engineering, with co-affiliation to the School of Medicine). This is the third iteration of a documented research line — AIBuildAI (arXiv 2604.14455), AIBuildAI-2 (arXiv 2605.27873), and now AIBuildAI-2.5 — so the team has direct prior experience with the exact system family being improved, and the evaluation leans on established third-party infrastructure: OpenAI's MLE-Bench benchmark and its publicly maintained leaderboard, plus Meta AI Research's AIRS-Bench. Credibility positives: code is publicly released (github.com/aibuildai/AI-Build-AI, v2.5-latest tag) with usage documentation, benchmarks are public, the official leaderboard protocol is followed, and the AIRS-Bench comparison is explicitly run under controlled identical budgets and hardware. Caveats: the running header says "AIBuildAI Team" (corporate-style attribution), no external users have yet validated the released system, and the headline number depends on commercial Claude API models whose behavior may drift.

## Critical Assessment

- **No component ablation on the main benchmark.** The 73.3% MLE-Bench medal rate is a system-level result that bundles judge/selector guidance, the scheduler, routing, the inherited AIBuildAI-2 knowledge base, and the aggregator's ensembling — the paper never isolates how much each contributes on MLE-Bench (e.g., no run with UCT selection instead of judge+selector, or without routing). The only controlled attribution evidence is AIRS-Bench (search strategy) and the three-task routing study; the scheduler's effect on hardware utilization is asserted qualitatively, never measured (no GPU-utilization or jobs-completed statistics are reported).
- **Thin baseline on the generalization experiment.** AIRS-Bench compares against exactly one agent (MLEvolve with an Opus 4.7 backbone) on six tasks; no MARS, ML-Master, R&D-Agent, or AIRA-dojo runs there, and +1.4% on Yelp and −3.6% MASE on web traffic are small margins for which no variance estimates are given.
- **No repeated runs or error bars anywhere.** MLE-Bench appears to be a single run per task with stochastic LLM judges and coders; a 2.6-point medal-rate gap over the runner-up (≈2 medals on 75 tasks) is within plausible run-to-run noise, and the paper provides no seeds, repeats, or confidence intervals to rule that out.
- **Leaderboard comparability caveat.** Cross-system leaderboard numbers are taken from the official MLE-Bench table, where competing systems were likely evaluated with different backbone LLMs and possibly different compute envelopes; the paper's 24-hour/1×A100 setting guarantees self-consistency, not apples-to-apples fairness against every listed competitor.
- **Self-referential lineage advantage.** The knowledge base and router knowledge system accumulate across runs and tasks within the same family (AIBuildAI → AIBuildAI-2 → AIBuildAI-2.5). Cross-run accumulated knowledge plausibly helps on MLE-Bench task types, but there is no experiment quantifying how much of the gain comes from this inheritance versus the new mechanisms.
- **Trust in LLM judgments.** The judge's grounding and feasibility scores, and the router's "cheapest sufficient" verdicts, are LLM outputs without any calibration study (e.g., how often judge scores correlate with realized improvement); the reward-hacking defense is simply "the judge assigns zero," with no reported detection rate or false-negative analysis on a benchmark known for leak-prone Kaggle tasks.
- **Redeeming rigor.** To the authors' credit, the AIRS-Bench comparison is genuinely controlled (same 24-hour budget, same hardware, same backbone class for the baseline), the data-split agent fixes one global validation set so rewards are comparable across nodes, and MLE-Bench grading is done by the official competition-derived protocol rather than self-reported metrics.

## Strengths

- Clear problem decomposition: the paper maps three concrete failure modes (sparse rewards, idle hardware, uniform expensive inference) onto three targeted mechanisms, and the design rationale for each (why MCTS rules fail with a handful of executed leaves; why per-call routing beats per-query routing for agent workflows) is well argued.
- The judge + selector design is a sensible answer to the reward-scarcity regime: an LLM prior estimates the value of unexecuted candidates before the cost of training is paid, then fuses with measured rewards as they arrive — a real departure from pure UCT/heuristic selection under tiny evaluation budgets.
- Strong headline empirics on third-party infrastructure: first place on the public MLE-Bench leaderboard with a 73.3% medal rate, and wins on all six AIRS-Bench tasks under controlled conditions, spanning molecules, text, and time series.
- The routing study reports the metric AND the USD cost per configuration, showing routing can even beat the strongest fixed tier (accuracy 0.823 vs Opus's 0.811 on spaceship-titanic) while costing about half — evidence that cheap models suffice for most agent roles if assignment is per-node and escalation is available.
- Honest scoping of the scheduler as heuristic, with a concrete research agenda (job colocation/MPS, pre-execution resource prediction, resource-aware code generation) and a thoughtful discussion of extensions to autonomous research code generation and scientific discovery.

## Limitations

- No ablations decomposing the contributions of judge/selector, scheduler, routing, and the inherited knowledge base on MLE-Bench; the reader cannot tell which mechanism buys the 73.3% versus 61.3% MLEvolve margin.
- Single-run evaluations with no variance quantification; several margins (2.6 medal-rate points over the runner-up; +1.4% Yelp; −3.6% MASE) are small enough that noise matters.
- AIRS-Bench generalization tested against only one baseline agent on six tasks.
- Scheduler remains threshold-heuristic (GPU memory/utilization near capacity, CPU above threshold); no measured hardware-utilization or scheduling-overhead results, as the authors themselves acknowledge.
- High replication cost: 75 tasks × 24-hour A100 runs plus commercial Claude Opus 4.7 / Sonnet 4.6 / Haiku 4.5 API spend makes independent reproduction expensive, and leaderboard results are tied to specific commercial model versions that may be deprecated.
- The reward-hacking guard and the router's sufficiency judgments are unquantified LLM behaviors; the data-split agent's single global validation set could be fragile on small datasets even though final grading follows the official protocol.

## Questions for Further Exploration

- How much does each mechanism contribute on MLE-Bench? An ablation swapping judge+selector for UCT, disabling routing, or disabling the scheduler would attribute the 73.3% vs 61.3% gap.
- Is the 2.6-point medal-rate lead over the runner-up robust across repeated runs, or within run-to-run noise given stochastic LLM agents?
- How often does the judge's 0–5 expected-improvement score actually correlate with realized reward, and what is the empirical reward-hacking detection (and false-positive) rate on leak-prone Kaggle tasks?
- Does the cross-run router knowledge system keep paying off as the task distribution shifts away from the tasks it accumulated knowledge on, or does it overfit to Kaggle-style tabular/image tasks?
- Could the resource-aware scheduler be combined with pre-execution resource prediction and GPU sharing (MPS, MUX-style colocation) to further increase concurrent training runs, and would that change the exploration-exploitation trade-off the selector controls?
- The framework is claimed to transfer to autonomous research code generation (AlphaEvolve/FunSearch-style program discovery) — does LLM-guided selection still help when evaluations are cheaper and rewards less noisy than full model training?
