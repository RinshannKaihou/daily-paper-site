> **一句话总结：** 本文系统刻画了决定 GPU kernel 位级（bitwise）行为的因素（浮点归约顺序、部分和精度、FMA 融合与舍入位置），首次对闭源库 cuBLAS 的算术做了黑盒重建——用 Triton 实现的 GEMM 家族在 GB300/GB200/H100 上与 cuBLAS 逐位一致（10 万+ 随机 fp16 形状 100% 字节匹配），并在 Triton 编译器中强制平衡树归约（27 个 kernel 中 19 个与自由顺序模式差距 <10%）、构建了首个跨 NVIDIA PTX 与 AMD GCN 的可靠静态位级等价检查器并接入 autotuner 做静态剪枝，还顺带发现了 cuBLAS split-K 尾部丢项的真实 bug。

> **TL;DR:** The paper nails down what decides the bitwise behavior of GPU reductions and GEMMs, then does three things with that knowledge: (i) the first black-box reconstruction of a closed-source library's arithmetic — a Triton GEMM family (fp16/bf16/fp8) that matches cuBLAS byte-for-byte on 110,813 random fp16 shapes on GB300 (100% outside a genuine cuBLAS split-K tail bug they discovered, which drops K mod 64 terms), plus 99.81%/99.82% byte-match rates over 626,522/648,720 fp16+fp8 shapes on GB200/H100; (ii) compiler-enforced balanced-tree reduction in Triton with a layout optimization keeping 19 of 27 kernels on GB300/H100 within 10% of free-order performance (vs the ~20% cost typically reported for fixed order), and on realistic 96 fused-epilogue LLM shapes the bit-exact kernel runs at 95–168% of the cuBLAS+separate-epilogue baseline vs 85–125% for torch.compile; (iii) the first sound static bitwise-equivalence checkers over NVIDIA PTX and AMD GCN (validated on 51,152 + 4,500 configs with zero false merges), integrated into Triton's autotuner as a pruning predicate so the search stays inside one bit-equivalence class.

## 核心贡献

- **位级行为的机理刻画与形式化描述符（GEMMDesc）**：证明浮点归约顺序是决定数值位的主导因素，并用"依赖树"（dependence tree，T = T_smem ∘ T_warp ∘ T_reg）形式化归约结构；给出 GEMM 形式化描述符 GEMMDesc，记录真正决定归约顺序的参数（如 split-K 中 K 轴的切分点 k_cuts、span、partial_dtype/merge_dtype、instruction_k、GEMV 的 layout 等），不含任何纯速度旋钮——两台机器拿到同一描述符就必须产出相同的位。还证明了流水线深度（num_stages）与 warp 特化不改变归约树。
- **首个对闭源库算术的黑盒重建（到位级正确）**：通过运行时剖析 + 对抗性数值探针（+L、−L 与半 ulp 以下的 r 值在轴上"行走"读出分组边界），从 cuBLAS 逆向出 (SM 版本， 张量形状) ↦ GEMMDesc 的函数（"arch profile"表，靠 825 万次 cost-model 查询枚举全部可达答案），重建为 Triton GEMM 家族，在 GB300/GB200/H100 上对 cuBLAS 12/13 达到 100% 逐位匹配（排除其自发现的 cuBLAS bug 形状）。
- **Triton 编译器中的首个平衡树归约强制（"inner tree"模式）+ 数据布局优化**：在编译器后端钉住归约顺序，并利用"顺序已钉住 ⇒ 全部合法布局都成为免费性能旋钮"这一性质做布局优化（把归约轴收进单个 warp 以省掉跨 warp 的 barrier + shared memory 往返），把强制顺序的性能代价压到可接受范围。
- **首个可靠（sound）的静态位级等价检查器，覆盖 NVIDIA PTX 与 AMD GCN 两家指令集，并接入 autotuner**：对编译后的 kernel 汇编做符号化抽象解释（仿射地址求值、循环折叠为 fold 节点、交换子节点规范化 + 自底向上哈希签名），无法建模的构造退化为不透明语法从而保证不误合并；作为 Triton autotuner 的静态剪枝谓词，使搜索在一个位级等价类内进行。
- **发现并定位了 cuBLAS 的一个真实缺陷**：nvjet split-K 路径（ALGO_ID 66）在很深的 K 下丢弃 K mod 64 个尾部项（如 K=8648 时全 1 输入返回 8640 而非 8648），在 GB200/GB300/H100 与 cuBLAS 12.8.5/13.1.1 上均复现。

## Key Contributions

- **A mechanistic account of bitwise behavior.** FP reduction order is shown to dominate the bits; reductions are formalized as dependence trees built at three levels (within-thread registers, within-warp shuffles, cross-warp shared memory), and pipelining depth and warp specialization are proven to leave the tree unchanged. A formal descriptor `GEMMDesc` captures everything that fixes a GEMM's reduction order (split-K cuts/spans, partial/merge dtypes, instruction_k, use_fast_accum, GEMV lane layout) while excluding pure speed knobs like BLOCK_M/N/K — equal descriptors owe equal bits on any machine.
- **First black-box reconstruction of a closed-source library's arithmetic to bit-level correctness.** Using runtime profiling plus adversarial numerical probes (a +L/−L cancelling pair and a sub-half-ulp residual r walked along the K axis to read out group boundaries and split spans), the authors recover cuBLAS's (SM version, shape) ↦ GEMMDesc function as enumerable "arch profile" tables (via a scan of 8.25M cost-model queries), then rebuild the arithmetic as a Triton GEMM family over fp16/bf16/fp8.
- **First balanced-tree reduction enforcement in Triton's compiler backend plus a data-layout optimization.** The "inner tree" mode pins lane-shuffle trees by counting offsets up from 1 (identical tree regardless of layout); the layout pass then moves a reduction axis inside one warp to skip the cross-warp stage, provably bit-identical because association is now layout-independent.
- **First sound static equivalence checkers for compiled GPU kernels, spanning two vendors.** A symbolic abstract-interpretation walk over PTX (NVIDIA) and AMDGCN (AMD) with affine address evaluation and exactness-proven bitwise rules, canonicalized into hashed tree signatures; unmodeled constructs become opaque so equivalence is never falsely claimed. Integrated into Triton's autotuner as a static pruning predicate — the first autotuning that searches within a single bitwise-equivalence class.
- **A real cuBLAS bug found and isolated** (Appendix D): the nvjet split-K path silently drops the K mod 64 tail at very deep contraction lengths, reproduced standalone with no Triton involved.

## Methodology

The paper proceeds in four layers, each building on the previous. (1) **Characterization**: floating-point addition is commutative but not associative, so a GPU reduction's bits are fixed by its dependence tree — the DAG of additions. The tree is built at three scopes (thread registers, warp lane shuffles, cross-warp shared memory); thread count, elements per thread, and warp count each move it. For tensor-core GEMMs the authors adopt (and empirically validate across all Section 7 measurements) the semantic that one matrix instruction folds instruction_k products plus the incoming accumulator into a single exact sum with one fp32 rounding, so the surviving reduction order is the chain of ⊕fp32 steps across instructions. Four algorithm families — plain GEMM, split-K, chained chunks, GEMV — are each parameterized into GEMMDesc. (2) **Black-box reconstruction**: for each (SM version, library generation) the cost model's answers are finite, so recovering cuBLAS means recovering one descriptor per reachable answer. Runtime profiling (launches, grid, workspace) narrows a shape to a family; numerical probes then pin the grouping — e.g., in a K=576 fp16 GEMM on GB300, walking the +L/−L pair along the axis shows the output flips at m=192 and m=383, revealing three split parts of 192. (3) **Compiler enforcement**: an `inner_tree` attribute in Triton's backend makes the lane-exchange butterfly count offsets up (1,2,4,… instead of …,4,2,1), fixing the tree shape independent of layout; a guard-heavy layout-optimization pass (Algorithm 1) then relocates a reduction's operand so the reduced axis sits inside one warp, eliminating two barriers and a shared-memory round trip while preserving bits by construction. (4) **Static checking**: a ~2,500-line Python checker walks PTX (and its AMDGCN twin) over a symbolic thread, mapping registers to dependence-tree nodes; addresses are evaluated as affine forms over a symbol basis with bitwise operations admitted only under exactness proofs (trailing-zero rules for shifts, launch-bound powers of two for tid masks); loop-carried accumulations fold into single nodes keyed on chunk size (dropped for exact tensor-core K loops); commutative children are sorted and trees hashed to signatures, with balanced reductions collapsing to (combine, leaf template, height, first butterfly offset). The checker plugs directly into Triton's existing autotuner pruning hook. Evaluation runs on GB300 (sm_103), GB200 (sm_100), H100 (sm_90), and gfx942 (CDNA3) with cuBLAS 13, Triton 3.8, PyTorch 2.12, CUDA 13, using a static set of 390 realistic (M,N,K) shapes read from 16 open-weight models' configs (attention/MLP/MoE/LM-head/LoRA layers), a fuzzing set of 110,813 random shapes, and 97 kernels from public benchmark suites plus TorchInductor-generated and hand-written microkernels.

## Results & Highlights

- **Bit-exact reconstruction of cuBLAS**: On GB300 (cuBLAS 13, fp16), the Triton GEMM family returns byte-identical outputs on 110,753 of 110,813 random shapes at ten input draws each — 100% of shapes where cuBLAS computes the full sum, across all eight algorithm families the library dispatches to (nvjet single-pass, nvjet split-K, cutlass per-MMA, cutlass split-K per-MMA, three-level chain, three GEMV variants); the 60 remaining shapes are a genuine cuBLAS bug (below). On GB200 and H100 the bit-match rate is 99.81% (626,522 shapes) and 99.82% (648,720 shapes) over fp16+fp8, with every miss attributable to the same bug; GB300 fp8 alone: 42,793 shapes, 99.93%.
- **A real cuBLAS split-K tail bug**: at very deep K the nvjet split-K path (ALGO_ID 66, tile family 64x8_64x16_1x1) drops exactly K mod 64 terms — with all-ones inputs at K=8648 the fp32 output reads 8640, not 8648; over a 496,906-shape sweep under cuBLAS 13.1.1 on GB300, 1,062 shapes came back non-identical and every one of the 5,709 observed losses across all configurations was exactly K mod 64. Ordinary sizes are hit too: 32×32, 64×64, and 128×128 GEMMs all lose 8 terms at K=11,528.
- **Performance of the bit-exact GEMM vs cuBLAS** (390 realistic LLM shapes): above 5 GFLOP, the bit-exact Triton GEMM runs at 56–93% of cuBLAS, versus 61–88% for the free-order Triton GEMM that torch.compile generates — i.e., the bitwise constraint costs little relative to a same-language baseline; the large-tensor-accelerated arm reaches 69–91%.
- **Fused epilogue flips the story**: over 96 realistic fused-GEMM+epilogue shapes in six groups, the bit-exact fused kernel runs at 95–168% of the cuBLAS-GEMM-plus-separate-epilogue-kernel baseline, beating torch.compile's fused pair at 85–125% — its kernel half runs 1.8× as long as the baseline's kernel half but wins the pair by eliminating one launch.
- **Cost of enforced balanced-tree reduction**: 19 of 27 kernels on GB300/H100 finish within 10% of the free-order (fully autotuned) mode; on H100 the layout optimization carries 6 of 10 kernels to or past free-order, by up to +42% on a column-sum matmul epilogue; on GB300 it passes the free mode once and otherwise reaches 57–99%. This substantially undercuts the ~20% throughput loss previously reported for order-fixing rewrites.
- **Checker soundness and partition quality**: across 51,152 compiled configurations on GB300 (47 Triton kernels, five FP formats) and 4,500 on gfx942, every pair the checker certified equivalent returned identical bytes on every draw — zero false merges; it recovers the exact partition on the GEMM family and TorchInductor fused kernels, over-splits by only 1.0–2.5× on reductions/normalizations, though up to 23× on gemm_kgroup (bf16) and 10× on FlashAttention.

## Critical Assessment

- **Novelty**: Genuinely strong on the reconstruction and checking halves. Black-box recovering a closed library's reduction order to bit-level correctness and re-expressing it in Triton is new, as are sound static cross-vendor equivalence checkers for compiled GPU kernels. Determinism itself is not new (DeepSeek-V4, RepDL, LayerCast, oneMKL conditions all cited), and the paper is honest about that lineage.
- **Rigor**: High — soundness of the checker is by construction (unmodeled constructs go opaque), empirically gated over 51k configurations, and the cuBLAS bug is isolated with a no-Triton reproducer and power-checked against a deliberately broken kernel. One caveat: the tensor-core single-rounding semantics for fp16/bf16/tf32 is an assumption validated only by measurement agreement, not vendor documentation; the authors flag the fp8 exception (mma.sync vs tcgen05.mma diverge on GB300) themselves.
- **The "matches or exceeds torch.compile" headline needs unpacking**: as a standalone GEMM the bit-exact kernel is still well below cuBLAS (56–93% above 5 GFLOP), and footnote 4 concedes torch.compile emits its own Triton GEMM rather than reproducing cuBLAS's algorithm, so it is a convenient but not dominant speed baseline. The "exceeds" results come from the fused-epilogue setting where removing one kernel launch dominates — the fused kernel itself runs 1.8× longer than the baseline's kernel half. Fair, but easy to over-read from the abstract.
- **Scope limits the checker's pruning value**: over-splitting is exact on GEMMs but 6.7–23× on kernels outside the paper's focus (gemm_reduce_sum, gemm_softmax, flash_attention at 10×), so autotuner pruning saves little exactly where config spaces are largest for non-GEMM workloads.
- **Missing measurements the paper admits**: cross-machine descriptor robustness is argued theoretically but not measured ("due to resource limitations"); no end-to-end ML training/inference or RL rollout-engine-agreement benefit is quantified despite the motivating examples (up to 9 pp accuracy swings, RL objective mismatch); soundness is relative to PTX/AMDGCN, not SASS — ptxas or driver-time assembly could still move bits below the checked level.
- **Maintenance burden**: arch profiles are per (SM version, library generation); every new GPU or cuBLAS release requires re-running the 8.25M-query enumeration and probe campaigns. The ~100 μs host-side descriptor overhead per call (vs ~20 μs pointer launch) also matters only for sub-100 μs GEMMs — but that is exactly the small-batch serving regime determinism targets.

## Strengths

- Complete vertical story: theory (dependence trees, GEMMDesc) → reconstruction (cuBLAS, bit-exact) → enforcement (compiler pass) → verification (sound static checkers) → integration (autotuner pruning), with each layer validating the previous.
- The numerical probing technique for reading a black box's grouping structure out of ulp-level cancellation behavior is elegant and reusable beyond cuBLAS.
- Found, isolated, and responsibly disclosed a real cuBLAS correctness bug with a standalone reproducer — an independent contribution.
- Counterintuitive and useful performance finding: with epilogue fusion, bitwise determinism and speed can be pursued together (95–168% of baseline), against the community's ~20%-cost expectation.
- Honest limitation section; negative results (over-split ratios, fp8 divergence) are reported rather than buried.

## Limitations

- Reconstruction is tied to specific cuBLAS generations (12.x/13.x) and SM architectures; portability of the descriptor across machines is claimed but unmeasured, and each new hardware/library generation needs a fresh profiling campaign.
- The checker's soundness is relative to PTX/AMDGCN assembly, not the SASS actually executed; vendor driver updates below that level remain outside the guarantee.
- Standalone bit-exact GEMM remains 7–44% slower than cuBLAS above 5 GFLOP; the wins require fusion scenarios.
- Attention and epilogue-heavy GEMM fusions get only a theoretical treatment (Appendix F) — the FlashAttention reduction order is described, not enforced or checked at scale.
- No demonstrated end-to-end benefit for training or RL engine agreement; the motivating 9-percentage-point batch-invariance swing is cited from prior work, not reproduced under the new scheme.

## Relevance

对关注大模型训练/推理基础设施与系统可复现性的研究非常对口：位级确定性直接关系 LLM 推理的 batch invariance、RL rollout/训练引擎的 log-prob 一致性，以及多机训练结果可复现，而本文提供了从 GPU kernel 层（Triton、cuBLAS、autotuner）一揽子解决该问题的机理、工具与实测代价。其中对 Triton 编译器与 autotuning 的改造也属于 GPU kernel 优化与编译器方向的具体工程贡献。

## Questions for Further Exploration

- How stable is a recovered arch profile across cuBLAS point releases and driver updates in practice — could the probe campaign be made cheap enough to run in CI as a regression check?
- Can the checker be pushed below PTX to SASS (undocumented format) to close the assembly-to-machine-code gap, or could a formal vendor contract replace the empirically validated single-rounding tensor-core semantics?
- What is the end-to-end effect on RL training when rollout and training engines are pinned to one descriptor — does the log-probability agreement measured in prior work translate into measurably more stable policy optimization?
- Could TorchInductor adopt inner-tree enforcement plus checker-based pruning so every compiler-generated kernel ships deterministic by default, and what would that cost across the full Inductor kernel corpus (where over-splitting is currently up to 10–23× on attention-style kernels)?
- Does the black-box probing methodology extend to cuDNN/rocBLAS convolutions and to attention kernels, where the scale factor between the two GEMM reductions breaks the pure-reduction model of Section 3?
