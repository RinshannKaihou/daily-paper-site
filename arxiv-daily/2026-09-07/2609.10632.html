Methodology — verification is the contribution

L1 → L5 · reference = executable spec

numbat is independently implemented in Zig — no reference source incorporated — and the burden of proof runs one way: when a level disagrees, numbat changes to match the reference, never the reverse. Verification escalates through five levels:

  1. L1
    Operatornumeric gradient checks (1e-4) + CPU↔CUDA equivalence; initializer & Philox RNG by known-answer tests.
  2. L2
    Moduledetection loss with task-aligned assignment, autocast batch-norm — known-answer vs reference on fixed inputs.
  3. L3
    Step1-rank vs N-rank bitwise gradient identity; AMP↔F32 kinetics (4.2% mean loss deviation over 285 steps, after fixes).
  4. L4
    Trajectory30-epoch same-machine reference run; an automated gate polls every 10 min and kills runs leaving a 20% band.
  5. L5
    Outcomeofficial COCO protocol only — weights scored by the reference's own validator, so numbat cannot flatter itself.

Acceptance case · YOLO-NB-M — 25.9M-param YOLOv8m-class detector, trained from random init on COCO train2017 (118,287 imgs) · 2,464 steps/epoch · ~30 checkpoint-resume segments with full RNG/optimizer/EMA state continuity.

Strengths

what earns trust

  • Transferable answer to “how would you know your training stack is wrong?” — reference-as-spec, five escalating levels, automated trajectory gate.
  • Divergence catalog is mechanism-level (exact initializer gains, loss-scale dynamics, RNG stream structure) — and shows divergences compose.
  • Exceptional evidentiary honesty: scored by the competitor's validator, disclosed evaluator offset (−0.011…−0.014), negative results foregrounded.
  • Measured diagnostic coverage (raise-site ledgers, not hand lists) caught three phantom error codes; release rule: interrogate the shipped artifact.
  • Full artifact release — weights, per-epoch metrics, run manifest — endpoint regenerable without numbat.

Limitations

what to hold against it

  • Single seed (0) for both headline and baseline — no variance estimate; “parity” is not distributional.
  • Reference trajectory covers 30 of 500 epochs; beyond it, equivalence rests on a class-level published endpoint from unmatched hardware.
  • 3-GPU DDP stays ≈30% behind (≈108 vs 154 img/s); implemented overlap/NCCL paths regress on the 6-core host.
  • Peak memory ≈1.9× reference (13.5 vs ~7 GiB/GPU).
  • One detector family only; framework source proprietary, SDK commercial — internals cannot be independently audited.

Questions for further exploration

open threads worth pulling

  1. How much of the −1.3% endpoint gap is seed variance vs residual divergence? Would a 3-seed, 500-epoch replication on matched hardware settle it?
  2. Can the trajectory differential oracle become a product — e.g., a CI gate for PyTorch-recipe ports — and is L1–L3 + outcome scoring enough when L4 references are too costly to record?
  3. Should loss-scaler state join the checked recipe surface at larger world sizes, given collapse from OR-reduced overflow flags?
  4. Does rank-folded augmentation seeding matter more at larger world sizes — and for LLM pretraining data-order shuffling?
  5. Could an independent party run the five-level protocol against an open stack (Burn, tinygrad) to prove the method — not just numbat — transfers?
  6. Would ledger-derived coverage measurement, applied to PyTorch-family projects' error-handling surfaces, reveal similar phantom gaps?
