Key finding

An autonomous Claude Opus 5 agent re-engineered its authors' own hand-tuned exact minimum-cut solver — 21.49× faster at 32 threads.

让自主智能体在作者本人已深度手工调优的共享内存精确最小割求解器（VieCut）上，独立跑完「假设 → 实现 → 基准测试 → 保留/回退」的完整算法工程循环。

01 · Key metric

21.49×

geometric-mean speedup at 32 threads — 23.0 s → 1.07 s over the 49 jointly-solvable instances.

1 thread: 3.44× (25.0 s → 7.28 s)
peak memory: 492 GiB → 193 GiB
total agent cost: ≈ $350

02 · Why this matters

A ~$350 agent, given a frozen benchmark and correctness assertions, delivered verified speedups on a mature, hand-tuned HPC code — a transferable engineering recipe.

冻结基准 ＋ 正确性断言 ＋ 每实验一 commit 的台账——该方法论可直接迁移到其他代码与其他指标。

03 · Critical edge

Tuning and reporting use the same 53 instances: the 127× DIMACS headline is workload tuning, not generalization — held-out gains remain unmeasured.

— self-declared by the paper, §4.1

2 sessions· 44 experiments· 23 accepted / 21 reverted· 1 commit per experiment· ≈ $350 API· 1.1M output tokens· bottleneck: benchmark machine time, not agent reasoning

Methodology — the AAE loop 04

1 · MODELhot paths, hardware, times→ 2 · DESIGNfalsifiable hypothesis "X → Y by ≈Z"→ 3 · ANALYZEpredict gain, filter weak bets→ 4 · IMPLEMENTminimal change, one commit→ 5 · EXPERIMENTfrozen 53-instance benchmark→ 6 · EVALUATEkeep if geo-mean improves, else revert↺

Target

VieCut (IPDPS 2019), the authors' own shared-memory exact minimum-cut solver: heuristic λ̂ bound (label propagation + Padberg–Rinaldi), Nagamochi–Ibaraki contraction with parallel CAPFOREST, bucket priority queue, OpenMP. Already 2.5–12.9× ahead of prior solvers on real-world graphs — a deliberately hard starting point.

Guardrails

Benchmark, metric, inputs, time budget and dependencies are frozen; the agent may only edit code. Correctness assertions — identical minimum-cut values on all 53 instances — gate every benchmark run. Session state lives in an on-disk ledger (hypothesis, commit, metric, decision), not the context window.

Rig & data

AMD EPYC 7702P · 1 TiB RAM · g++ 13.3 -O3 -march=native · OpenMP · 53 instances = 33 regenerated DIMACS cores + 20 real-world k-cores (largest: uk-2007-05, 68M vertices / 3.1B edges). Agent: Claude Opus 5, seeded with no curated optimization list. Framework open-source (CHSZLab).

Unlike OpenTuner-style auto-tuning of a fixed parameter space, the agent edits the code itself — reaching changes with no tuning knob at all (data-structure swaps, repartitioning parallel work).

Strengths 06

  • Transferable protocol — frozen benchmark + correctness assertions + one-commit-per-experiment ledger applies to any codebase and metric.
  • Wins dissected change-by-change with per-change factors and mechanisms (bucket-queue blow-up, contraction serialization) — not just a headline number.
  • Exceptional honesty: the in-sample caveat, "validation, not proof" on correctness, and the 21/44 discard rate are all in the paper's own text.
  • Reproducibility engineered in: deterministic instance generators (from a parameter table), cross-validated cut values, open-source framework, public baseline.
  • Rare, useful economics: ~$350 / 1.1M tokens for a 21× parallel speedup on a competition-grade code.

Limitations 07

  • No held-out evaluation; fitted thresholds (heap cutoff at max(n, 10⁴), <10⁴-vertex routing) may not transfer to other workloads.
  • The 6.26×/127× DIMACS factors repair design-envelope violations — on the instance class the code was built for, gains are 1.28×/1.63×.
  • "DIMACS cores" are modern reimplementations from prose (original generators unpublished), scaled until the baseline slowed; the set is baseline-shaped.
  • Correctness is empirical — matching cut values + assertions + human review of 23 diffs — not a proof.
  • n = 1: one model, one machine, one run per instance; no comparison to OpenTuner, other agents, or humans under the same budget.
  • The agent stays inside the NOI-contraction framework — it cannot discover an asymptotically better algorithm.

Open questions 08

  • How much of 3.44× / 21.49× survives on held-out instances or shifted workloads, and how fast do the fitted thresholds degrade?
  • Would filling the community knowledge base of prior sessions cut the 21/44 discard rate?
  • AAE vs. OpenTuner, AlphaEvolve-style search, or other frontier models under the same budget?
  • Can correctness upgrade from assertion-matching + human diff review to mechanized proof of the queue and contraction invariants?
  • Does the method transfer to metrics beyond running time — solution quality, memory, Pareto trade-offs?
  • Could AAE bootstrap the first practical implementations of near-linear-time minimum-cut theory (Li 2021; Henzinger et al. 2024)?
