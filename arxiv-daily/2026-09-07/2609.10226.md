> **一句话总结：** Φ-Bench 用 85 个源自真实系统论文和开源仓库（vLLM、Megatron-LM、FlashInfer 等）的任务，按"单文件内核补全 → 多文件长程实现 → 全仓库端到端优化"三级难度评测前沿 LLM 的基础设施工程能力，最强的 Claude Opus 5 综合得分仅 36.53%，硬件/边缘类任务最好成绩只有 5.4%，说明 LLM 距离自主优化自身运行基础设施还很远。

> **TL;DR:** Φ-Bench is an 85-task benchmark (55 Kernel Function Completion, 20 Long-Horizon Implementation, 10 End-to-End Optimization) grounded in 2,260 systems papers and 1,852 real GitHub repository artifacts, testing whether LLMs can engineer the LLM infrastructure stack itself. On Φ-Bench the best model, Claude Opus 5, scores only 36.53% overall versus 28.12% for the runner-up Kimi K3 and 13.31% for the weakest DeepSeek V4 Pro; long-horizon repository-level implementation is the weakest format (Opus 5: 21.60% on LHI vs 37.16% on KFC), and Hardware & Edge is near-unsolved (best score 5.4%). Trajectory analysis shows what separates winners from losers: cheap local hypothesis screening, variable/noise control, and cautious attribution of experimental outcomes — capabilities current models only partially possess.

## 核心贡献

- **提出 Φ-Bench 基准**：首个面向"LLM 基础设施工程"的系统性基准，共 85 个任务、覆盖 9 大基础设施主题（训练、推理与服务、压缩、内核、I/O、硬件与边缘、数据基础设施、系统优化、系统保障），全部源自前沿系统论文和真实开源仓库，而非人工编造的编程题。
- **三级递进的任务格式**：KFC（内核函数补全，单文件、接口给定）→ LHI（长程实现，多文件、只给 feature 不给实现路径）→ E2EO（端到端优化，全仓库可改、只给系统级目标），开放式程度逐级提升，能区分"写高效计算原语""仓库级工程开发""假设驱动的开放优化"三种能力。
- **可扩展的基准构建方法学**：从 4,112 个来源（2,260 篇顶会论文 + 1,852 个仓库工件）自底向上构建三层覆盖分类法（410 个细粒度标签 → 62 个中层主题 → 9 个顶层类别），并用三条互补的任务合成管线（PR/Issue 复原、Agent 辅助合成 + 迭代测试生成、专家人工策展）保证任务的真实性与可扩展性。
- **严谨的评测协议**：性能任务用 AB-BA 配对测量（≥5 对）+ 对数归一化奖励（达到参考解 2 倍性能得满分）；实现任务用二值指标且必须通过构建、全部测试、编辑约束；并有基于规则的监控器 + Proctor Agent 双重反作弊机制（软断网劫持 pip/URL + 提示词约束）。
- **对 8 个前沿模型的系统评测与轨迹分析**：揭示各模型能力极不均衡，并从优化轨迹中提炼出优秀模型的三种关键行为——建立实验基础（低成本本地假设筛选）、控制变量与噪声、谨慎归因实验结果。

## Key Contributions

- **Φ-Bench benchmark**: 85 real-world tasks spanning nine LLM infrastructure categories, derived from top-tier systems papers (2023–2026) and public repositories rather than synthetic prompts — the first benchmark explicitly targeting open-ended, long-horizon LLM infrastructure engineering.
- **Graduated task formats**: Kernel Function Completion (KFC, 55 tasks, single-file, specified interface), Long-Horizon Implementation (LHI, 20 tasks, multi-file, feature specified but implementation path open), and End-to-End Optimization (E2EO, 10 tasks, whole-repository editable, only a system-level objective given) — isolating local kernel implementation, repository-scale development, and hypothesis-driven optimization abilities respectively.
- **Taxonomy-guided, scalable construction**: a three-level coverage taxonomy built from 2,260 papers and 1,852 repository artifacts (410 fine-grained tags → 62 middle-level topics → 9 top-level categories), plus three synthesis pipelines — PR/Issue-grounded reconstruction, agent-assisted synthesis with an iterative test-generation agent loop, and expert curation.
- **Rigorous evaluation design**: correctness-gated scoring with an AB-BA paired measurement protocol (≥5 pairs), a log-normalized performance reward (full credit at 2× the reference solution), hard validity gates (reference must reach ≥1.15× baseline performance; the starter/no-op solution must fail at least one test), and dual anti-cheating mechanisms (rule-based trajectory monitor + proctor agent, plus soft network disconnection of pip/URLs).
- **Systematic evaluation and trajectory analysis of 8 frontier models**, exposing sharp capability imbalances (Hardware & Edge nearly unsolved) and distilling the behaviors that distinguish strong from weak optimizers: experimental foundations, variable/noise control, and cautious attribution.

## Methodology

**Source collection and taxonomy.** The authors collect papers from top-tier systems conferences (2023–2026) and issues/PRs from widely used LLM infrastructure repositories, filtering with an LLM-based pipeline for artifacts directly related to LLM training/inference implementation, acceleration, or resource optimization. This yields 2,260 papers and 1,852 engineering artifacts (4,112 retained sources), which an LLM labels into a three-level taxonomy: 410 fine-grained tags clustered into 62 middle-level topics and 9 top-level categories. The taxonomy serves as the primary index guiding which topics get tasks in which format, and Figure 3 shows Φ-Bench covering substantially more of the topic space than KernelBench, KernelBenchX, TritonBench, FlashInfer-Bench, ISO-Bench, SOL-ExecBench, KernelBench-Hard, and CUDAHercules.

**Task synthesis (three routes).** (1) PR-/Issue-grounded: the repository state before a real merged change is the task input, the post-change implementation is the reference solution, and adapted unit tests become the evaluation harness. (2) Agent-assisted: agents scan repositories for high-value implementation sites, remove a code segment or whole module, and an agent loop analyzes execution flow, tracks covered branches, and iteratively generates tests for uncovered paths. (3) Expert-curated: human annotators construct tasks from influential papers and conference challenges where repository history offers no complete reference, manually designing tests and workloads.

**Quality control and metrics.** Every task ships a natural-language specification, full repository, executable workloads/tests, and an evaluation harness (all visible to the agent except the harness itself). For performance tasks, the reference must hit ≥1.15× stable speedup in the official environment and the starter must not beat baseline; for implementation tasks, the reference must pass all tests and the starter must fail at least one, with ≥5 test cases covering normal, boundary, error, and regression behaviors. Performance is scored as s = median(t_base/t_cand) over AB-BA pairs, mapped to reward min(1, ln(s/s_ref)/ln s_ref) — zero at or below the reference, 1.0 at s ≥ s_ref². Implementation tasks are binary pass/fail gated on build, tests, and forbidden-edit constraints.

**Evaluation setup.** Eight frontier models (claude-opus-5, claude-sonnet-5, gpt-5.6-sol, qwen3.8-max, qwen3.7-max, kimi-k3, glm-5.2, deepseek-v4-pro) at maximum reasoning effort and maximum context, each with its strongest scaffold (GPT-5.6 Sol on Codex; all others on Claude Code). Each task runs on 8 CPU cores, 32 GiB RAM, one NVIDIA H20 GPU. One submission is allowed per KFC task; up to 16 candidate submissions per LHI/E2EO task with the best taken. Anti-cheating combines soft network disconnection (hijacked pip/URLs return blocking warnings) with explicit prompting; the rule-based detector flagged only three retrieval attempts (all DeepSeek V4 Pro hitting PyTorch's website), and the proctor agent confirmed no actual hacking occurred.

## Results & Highlights

- **Headline: nobody passes one-third of the benchmark.** On the full 85-task Φ-Bench, Claude Opus 5 tops the leaderboard at 36.53%, followed by Kimi K3 at 28.12% (−8.41 pts), Qwen3.8 Max at 27.73%, and GPT-5.6 Sol at 24.51%; DeepSeek V4 Pro trails at 13.31% (−23.22 pts vs Opus 5) — despite every model having full repository and test-case access.
- **Long-horizon implementation is the weak spot across the board.** By task format, Claude Opus 5 scores 37.16% on KFC but only 21.60% on LHI (−15.56 pts); Kimi K3 drops from 26.09% (KFC) to 19.55% (LHI). E2EO scores are higher in relative reward terms (Opus 5: 62.94%; Kimi K3: 56.41%) but DeepSeek V4 Pro collapses to 1.97% there.
- **Hardware & Edge is nearly unsolved.** The best score across all eight models in the Hardware & Edge category is 5.40% (Qwen3.7 Max); Claude Opus 5 manages only 3.90%, and GPT-5.6 Sol, Claude Sonnet 5 both score 0.00 — current models lack understanding of the hardware side of AI infrastructure.
- **Reasoning budget ablations cut both ways.** Across 20 LHI tasks at varying reasoning efforts, all three tested models (Claude Opus 5, Kimi K3, GPT-5.6 Sol) peak at max effort, but gains are non-monotonic — GPT-5.6 Sol is notably unstable at intermediate levels, and Kimi K3 loses about 45% of its score at the low setting relative to max, showing its performance leans heavily on test-time compute.
- **Case study (nanoGPT MoE E2EO task, minimize validation bits-per-byte under wall-clock and parameter-count constraints):** Claude Opus 5 lands a low BPB on its first valid submission and keeps improving; in one documented transition it detects that a learning-rate change worsened BPB from 1.3646 to 1.3932 (same seed, same steps), infers that prolonged very-low LR is harmful, and a warmup–stable–decay schedule then improves BPB to 1.3248.
- **Error-mode analysis: persistence beats caution.** High scorers produce more total errors (Claude Opus 5: n=175; Qwen3.8 Max: n=179; GLM-5.2: n=185) than weak models (Claude Sonnet 5: n=26), i.e., they keep iterating; Python runtime errors exceed 50% of errors for most models, while Claude Opus 5's errors skew toward CUDA execution errors, indicating it writes correct Python within unfamiliar repositories on early attempts.

## Authors & Credibility

The benchmark comes from a joint USTC–StepFun team (with co-authors from Peking University, HKUST, Yale, and UPenn); first authors Leilei Ding, Shumin Wang, and Yuting Huang are USTC students (Ding's work done as a StepFun intern), and corresponding authors are Daxin Jiang (StepFun Chief Scientist) and Yanyong Zhang (USTC). StepFun is the producer of Step-series frontier models, and the benchmark includes StepFun-adjacent competitor models (Kimi K3, GLM-5.2, DeepSeek V4 Pro) ranking below Claude Opus 5 — the team publishes an unfavorable-but-honest result for the domestic model cohort, which lends credibility. The paper ships a public leaderboard, GitHub repository, and Hugging Face release, and the methodology sections (QC gates, AB-BA measurement, proctoring) reflect genuine systems-benchmarking practice rather than marketing. Evaluation infrastructure choices (single H20 GPU, fixed CPU/RAM) are fully disclosed.

## Critical Assessment

- **Novelty**: Real. Existing kernel benchmarks (KernelBench, TritonBench, FlashInfer-Bench) test isolated operators with predefined interfaces, and repo-level ones (ISO-Bench, CUDAHercules) pre-specify the target component and bottleneck; Φ-Bench's LHI/E2EO formats that hide the implementation site and optimization target are a genuine step toward open-ended evaluation. The taxonomy (built bottom-up from 2,260 papers + 1,852 artifacts) is itself a contribution.
- **Rigor**: Mostly strong — AB-BA paired measurement, correctness gating, hard validity gates, and dual proctoring exceed community norms. However, **the scaffold is confounded**: GPT-5.6 Sol runs on Codex while all seven other models run on Claude Code, so part of Claude Opus 5's 8.41-pt lead over Kimi K3 could be scaffold fit rather than model capability (Claude Code is Anthropic's own product, tuned for Claude models).
- **Sample size and aggregation**: 85 tasks total means several category-level claims rest on tiny cells — Hardware & Edge contains only ~2–3 tasks (per Figure 4's task matrix), so the widely quoted "best model only 5.4% on Hardware & Edge" is computed over a near-single-task sample; the same applies to Compression (~5 tasks) and Data Infrastructure. The overall score averages heterogeneous reward types (binary implementation vs log-normalized speedup) across cells of very different sizes.
- **Contamination is under-addressed**: tasks are reconstructed from public GitHub PRs/issues of famous repositories, so the exact fixes plausibly appear in training corpora. Soft network disconnection and the proctor agent block *retrieval at eval time*, not *memorization*; the paper reports no contamination analysis (e.g., performance on pre- vs post-cutoff artifacts).
- **Best-of-16 selection**: LHI/E2EO scores take the best of up to 16 candidate submissions, which measures agentic search under a generous budget rather than single-shot engineering skill — fine if stated, but it inflates absolute numbers relative to the "can LLMs engineer infrastructure" framing.
- **Reproducibility**: good on artifacts (leaderboard/GitHub/HF, fixed H20 hardware, disclosed scaffolds); weaker on the E2EO iteration and reasoning-budget findings, which rest on one nanoGPT task and 20 LHI tasks respectively — the case-study takeaways (experimental foundations, cautious attribution) are qualitative narratives from three hand-picked trajectories.
- **Red flags**: minor — "Claude Opus 5 leads in five of nine categories" is emphasized while per-category task counts are small; the 1.97% DeepSeek E2EO outlier is reported without deeper diagnosis.

## Strengths

- Unusually strong grounding in reality: every task traces to a real paper artifact, merged PR, or expert-curated research problem, avoiding the artificial flavor of synthetic coding benchmarks.
- The three-format graduated design (KFC → LHI → E2EO) cleanly separates local implementation skill, repository-scale navigation, and open-ended optimization — the LHI-vs-KFC gap is one of the paper's most informative measurements.
- Serious measurement engineering: AB-BA pairing with ≥5 repetitions, median ratios, log-normalized rewards, reference/starter validity gates, and two-layer anti-cheating with a reported (near-zero) violation count.
- The trajectory analysis goes beyond score tables: the three distilled behaviors (cheap local hypothesis screening; variable and noise control, e.g., Opus catching an Inductor compilation-cache artifact before rejecting a change; cautious attribution, e.g., DeepSeek wasting a submission by applying torch.compile without checking checkpoint compatibility) are actionable targets for agent and model design.
- Honest negative results for essentially every lab's models, with public artifacts and leaderboard.

## Limitations

- Small task counts per category (85 tasks / 9 categories / 3 formats) make category-level rankings statistically fragile; Hardware & Edge conclusions rest on ~2–3 tasks.
- Scaffold confound: GPT-5.6 Sol is the only model evaluated on Codex rather than Claude Code, muddying cross-model comparisons.
- Single-GPU environment (NVIDIA H20) and single-seed-style protocols; performance-optimal solutions may differ on other hardware, and no variance is reported for the headline scores.
- No training-data contamination analysis despite tasks being reconstructed from public, likely-memorized pull requests.
- The iteration and reasoning-budget studies cover one E2EO task and 20 LHI tasks for three models — too thin to support general claims about "test-time compute scaling for infrastructure engineering".
- Only 10 E2EO tasks, yet this is the format the paper's narrative (autonomous infrastructure optimization) most depends on.

## Relevance

这个基准直接命中"LLM 能否工程化其自身运行基础设施"这一核心问题：它把 agent 评测从孤立的内核写题推进到仓库级长程实现与端到端性能优化，其分类法（训练/推理/内核/I/O/编译/调度等 9 大类）和评测协议（AB-BA 配对测量、防作弊、轨迹分析）对构建系统类 coding-agent 评测很有参考价值。对关注 agentic engineering、test-time scaling 和 LLM 系统优化能力评估的研究来说是必读工作。

## Questions for Further Exploration

- How much of Claude Opus 5's lead survives if every model is run on a neutral, identical scaffold (e.g., an open-source agent harness) instead of Claude Code vs Codex?
- What is the contamination rate — do models score systematically higher on tasks whose reference PRs predate their training cutoffs than on post-cutoff ones?
- Do the three distilled optimizer behaviors (local hypothesis screening, variable/noise control, cautious attribution) emerge from explicit agent-scaffolding changes (e.g., forcing a local-validation step before submission) even for weaker models like Qwen3.7 Max or DeepSeek V4 Pro?
- Can the Hardware & Edge results be trusted with only ~2–3 tasks, and what does a scaled (50+ task) hardware-aware benchmark reveal about where exactly models fail — instruction selection, memory layout, occupancy, or something upstream?
- How do scores shift on other GPUs (A100/H100/B200), and does the E2EO ranking of models stay stable when the best-of-16 submission budget is cut to best-of-1?
- Since Kimi K3 loses ~45% of its score at low reasoning effort while Claude Opus 5 does not, is robustness to reduced test-time compute a trainable property, or an artifact of distillation/post-training choices?
