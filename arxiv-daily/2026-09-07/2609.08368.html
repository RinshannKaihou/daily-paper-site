GLM-5 744B-A40B weight update, P2P RDMA vs NCCL broadcast at 16 nodes per side (H100 cluster, 1 GB buckets, steady state).

Advantage scales with fleet width, not model size — on a single node P2P is up to ~70% slower than broadcast, which remains the default.

Why this matters

Async scheduling, token-level train–rollout fidelity, and cross-cluster weight sync are the hardest engineering bottlenecks in scaled RL — Miles quantifies each.

若要搭建或选型 RL 训练框架（对比 verl / slime / OpenRLHF），Miles 的设计与量化数据是很有价值的参考。

Critical edge

The flagship result is a single unreplicated 100-step run: no seed variance, no comparison against verl / OpenRLHF / NeMo-Aligner — the quality cost of full asynchrony is left untested.

The authors themselves downgrade the reward rise (0.438 → 0.556 moving average) to "an observation rather than a measured improvement."

Methodology

distilled · not transcribed

Miles is organized by data path, not hypothesis — three decoupled stages share one asynchronous loop on disjoint GPU pools. ROLLOUT — SGLang engines generate multi-turn trajectories; the router pins each session to the engine already holding its KV prefix, new sessions land on the least-loaded engine, and agent environments attach via three nested plug-in layers (Harbor, τ-bench, OpenENV, E2B, Modal…). TRAIN — Megatron-LM (default for large MoE, TP×PP×CP×EP) or PyTorch FSDP (loads a Hugging Face directory as-is), with GRPO, GSPO, REINFORCE++ and PPO behind one typed loss interface. WEIGHT SYNC — a bucketed pipeline converts Megatron shards to HF layout, then delivers them by NCCL broadcast, P2P RDMA (CPU-resident SGLang replica for re-sharding), or disk-delta that publishes only changed bytes. Fidelity between stages is structural: TITO makes the server — not the harness — own tokenization; R3 records and replays every MoE expert assignment; true-on-policy mode pins bitwise-identical kernels.

Strengths

▲ what holds up
  • Train–rollout fidelity as a first-class constraint — TITO token exactness, R3 routing replay, bitwise true-on-policy — where most RL frameworks leave it implicit.
  • P2P weight transfer is well-motivated and well-measured — −85–86% at 16–32 nodes/side on 744B–1T models, with the honest counterpoint that single-node P2P loses to broadcast by up to ~70%.
  • Unusual engineering honesty — explicit limits section, four-level evidence grading for diffusion recipes, refusal semantics instead of silent fallbacks, OPD accuracy claim discounted against its own standard error.
  • Composable breadth — LoRA RL, distillation, SFT and diffusion RL reuse the same rollout / trainer / weight-update components behind small typed interfaces; native ROCm (MI300X–MI355X) and day-0 recipes for six frontier models incl. 1T+ MoE.
03′

Limitations

▽ what to watch
  • One unreplicated 100-step run — no baseline framework, no seed variance, no sync-vs-async ablation on the same workload; the quality cost of staleness is unquantified.
  • True-on-policy covers only dense Qwen3 0.6B/4B — the flagship run uses truncated importance sampling with nonzero (0.0369) train–inference KL.
  • TITO records no images or video — vision-language models must bypass it; computer-use screenshots unsupported: a major gap for multimodal agentic RL.
  • Uneven transfer coverage — P2P name-mapping limited to Qwen2/3, Qwen3-MoE, GLM4-MoE, DeepSeek-V3/V3.2 families; disk-delta is Megatron-only; FSDP lacks LoRA and beyond-host-RAM offload.
  • Marquee features Beta or unreleased — MXFP8/NVFP4 tested on only 1–3 models, multi-LoRA and Kimi K3 / Qwen3.8 recipes still open PRs; loosest replay setting can silently merge distinct tool-call histories.

Questions for Further Exploration

open threads
  1. Does fully async training cost reward versus synchronous Miles on the identical GLM-5.2 / terminal-bench-2 workload — do the 0.0369 mean KL and buffer staleness translate into a measurable gap at matched compute?
  2. How does wall-clock-to-target-reward compare against verl, AReaL or NeMo-Aligner on the same model and tasks — not just against Miles' own broadcast baseline?
  3. Can R3's ~60 MB per-32K-trajectory routing overhead be compressed or sparsified — and does the GLM-5.2 run (which leaves R3 off) actually need it once MTP and FP8 rollout are in play?
  4. How would TITO extend to vision-language sessions, and what does the loosest replay-comparison setting cost harnesses that fork and compact context (e.g. Claude Code)?
  5. Does the on-policy distillation length collapse (−56% tokens at unchanged accuracy on DAPO) persist at longer horizons with nonzero task reward, or is it a transient of the reverse-KL-only regime?
