> **一句话总结：** RadixArk 开源的 Miles v0.1 是一个面向前沿规模后训练（post-training）的全栈生产级系统：以 SGLang 做多轮 agentic rollout、以 Megatron-LM/FSDP 双后端做训练、以三种权重同步传输（NCCL 广播 / P2P RDMA / 磁盘增量）适配不同部署拓扑，并通过 TITO 会话服务器（token 级精确）与 R3 专家路由重放解决训练-推偏移；在 64 张 GB300 上对 GLM-5.2 744B-A40B 做全异步 agentic RL，训练步中位耗时 263 秒，P2P 权重同步把 744B 模型的更新时间从 58.3 秒压到 8.5 秒（−85.5%）。

> **TL;DR:** Miles v0.1 (open-sourced by RadixArk, built on slime + SGLang) is a full-stack, production-oriented RL post-training system: fully asynchronous agentic rollout with session-affinity routing (96% prefix-cache hit rate), a token-in-token-out (TITO) session server that guarantees the trainer sees exactly the tokens the policy sampled, MoE rollout-routing-replay (R3), a shared low-precision quantization contract (FP8/MXFP8/NVFP4) across rollout and training, and three weight-sync transports — on H100 clusters P2P RDMA cuts a GLM-5 744B-A40B weight update from 58.30 s (NCCL broadcast) to 8.48 s (−85.5%) at 16 nodes per side. The end-to-end case study trains GLM-5.2 744B-A40B with fully asynchronous GRPO on terminal-bench-2 coding tasks across 64 NVIDIA GB300 GPUs at a median 263 s per step, with train–inference log-prob KL averaging 0.0369 over 100 steps. It is a system report, not a research paper: the flagship reward curve comes from a single 100-step run with no baseline framework comparison and no seed variance.

## 核心贡献

- **全栈 agentic RL 训练系统**：覆盖 rollout（SGLang 引擎 + 会话亲和路由）、训练（Megatron-LM 与 PyTorch FSDP 双后端）、权重同步（广播 / P2P RDMA / 磁盘增量三种传输）的完整闭环，并支持全参 RL、LoRA RL、on-policy 蒸馏、SFT 与 true-on-policy 对齐，同一架构还扩展到扩散模型（Miles-Diffusion）。
- **完全异步（fully asynchronous）训练调度**：rollout 与训练使用分离的 GPU 池并行推进，配合有界数据缓冲区（staleness 上限、按组过滤）与"样本粒度"补位规则，消除同步调度中慢轨迹造成的双向空转。
- **TITO（token-in-token-out）会话服务器**：由服务端而非 harness 掌控分词，逐轮记录精确 token ID、log-prob 与路由专家，支持线性和分支两种会话扩展规则，从结构上消除多轮 agentic RL 中训练视图与实际采样轨迹的静默偏差。
- **R3（rollout routing replay）**：把 MoE 每个 token 的专家分配当作 rollout 数据记录并在训练时精确重放，规避训练/推理数值差异导致的路由翻转（文献报告该失配可引发灾难性训练崩溃）。
- **低精度契约**：FP8 blockwise / MXFP8 / NVFP4 以"同一量化逻辑贯穿检查点转换、前向、rollout、权重导出四个阶段"的端到端契约方式落地，配合按张量 BF16 例外与 four-over-six 方案。
- **工程可信度体系**：模型家族注册制（CPU/GPU 双重验证 append-only 不变量）、diffusion 配方四级证据等级（fully gated / proxy gated / verified / not verified）、以及启动期随机填充 + bit-exact 比对的权重校验。

## Key Contributions

- **A full-stack agentic RL post-training system**: one loop covering SGLang rollout engines with session-affinity routing, a trainer with two interchangeable backends (NVIDIA Megatron-LM default, PyTorch FSDP for direct Hugging Face loading), and three weight-synchronization transports (NCCL broadcast, P2P RDMA, disk-delta) chosen by deployment topology; the same components compose into full-parameter RL, LoRA RL, on-policy distillation, SFT, and true-on-policy alignment, and port to diffusion models (Miles-Diffusion).
- **Fully asynchronous RL scheduling**: rollout and training run concurrently on disjoint GPU pools; a bounded data buffer with a staleness limit, per-group filtering, and a sample-granularity replacement rule removes the straggler-induced idle time of turn-taking schedules, with buffer metrics (queue size, staleness) exposing which stage is the bottleneck.
- **Token-in-token-out (TITO) session server**: the server, not the agent harness, owns tokenization — it checkpoints exact token IDs, log-probabilities, and routed experts per turn, tokenizes only the appended suffix, supports linear and branching (tree) session histories, and makes replay comparison configurable so harnesses that reserialize tool calls do not silently discard valid prefixes.
- **Rollout routing replay (R3)**: treats each token's MoE expert assignments as rollout data the trainer replays exactly instead of recomputing, mitigating the router-flip mismatch reported to destabilize MoE RL catastrophically; enabled per recipe (~60 MB of routing tensors per 32K-token trajectory at 60 layers, k=8).
- **End-to-end low-precision contracts**: MXFP8 and NVFP4 recipes enforce identical quantization at checkpoint conversion, trainer forward, SGLang rollout, and live weight export, with per-tensor BF16 exceptions, dequantized backward, and the four-over-six block scaling option; A100 falls back to BF16 only.
- **Verified-coverage discipline**: day-0 support for six frontier models (Kimi K3, DeepSeek-V4, GLM-5.2, Qwen3.8, Inkling, Nemotron 3 Ultra), native ROCm support on four AMD Instinct SKUs, explicit evidence levels per diffusion recipe, and a start-of-training weight check that pre-fills engine tensors with random noise so a silently dropped tensor cannot pass.

## Methodology

The report is a system walkthrough organized by data path rather than a hypothesis-driven study. The RL loop has three decoupled stages. (1) **Rollout**: SGLang engines generate multi-turn trajectories; the SGLang router pins each session to the engine (or DP-attention rank) holding its KV prefix ("affinity"), and new sessions land on the least-loaded engine. Agentic environments attach through three nested plug-in layers (agent / generate / rollout functions), with shipped connectors for Harbor, NeMo Gym, OpenEnv, HUD, Strands, τ-bench, and Prime Intellect Verifiers, and sandbox backends spanning AgentENV, Daytona, E2B, and Modal. (2) **Training**: either Megatron-LM (TP×PP×CP×EP parallelism, default for large MoE) or FSDP (loads a Hugging Face directory as-is); five advantage estimators (GRPO, GSPO, REINFORCE++ in two forms, PPO) behind a typed loss interface; importance-ratio corrections via truncated importance sampling (default clamp [0,2]) or clip-or-pop; memory managed by whole-actor offloading (pinned host memory or node-local disk) plus bucketed optimizer-state streaming from NVMe. (3) **Weight update**: a shared bucketed pipeline (512 MB default buckets) converts Megatron shards to Hugging Face layout, then a chosen transport delivers them — broadcast, P2P RDMA with a CPU-resident SGLang model replica used for re-sharding via SGLang's own weight-loading functions, or disk-delta updates that publish only changed bytes (XOR or idempotent overwrite encodings) to a shared filesystem. Fidelity mechanisms sit between the stages: TITO for token exactness, R3 for expert-routing exactness, and an optional true-on-policy mode pinning bitwise-identical kernels (FlashAttention-3, batch-invariant GEMMs, deterministic cuBLAS/NCCL) so rollout and training log-probabilities agree exactly — currently registered only for dense Qwen3 0.6B/4B. Beyond the core loop, on-policy distillation folds a per-token reverse-KL estimate (student minus teacher log-prob at the sampled token, one-sample or top-K) into the advantage rather than the loss. The evaluation methodology is primarily internal: log-prob agreement between SGLang and Megatron, timing microbenchmarks, and one end-to-end reference run.

## Results & Highlights

- **GLM-5.2 744B-A40B reference run (64 NVIDIA GB300 GPUs, fully asynchronous GRPO on terminal-bench-2)**: median training-step time of **263 s over the first 30 measured steps** (the step-0 warm-up of 1,042 s is clipped); with 32 GPUs generating and 32 training, roughly 90–100 requests generate concurrently against a 128-trajectory in-flight limit, and session affinity holds the **prefix-cache hit rate at 96%**. The parallel layout is TP2/PP4/CP4/EP8 with a single data-parallel replica, forcing ~279 GB of optimizer state per rank to stream to node-local disk.
- **Weight-sync speedups (H100 clusters, 1 GB buckets, steady-state average)**: P2P RDMA vs NCCL broadcast on **GLM-5 744B-A40B: 58.30 s → 8.48 s (−85.5%) at 16 nodes/side**; on **Kimi K2 1T-A32B: 53.28 s → 7.23 s (−86.4%) at 32 nodes/side** (including ~884 ms of on-GPU requantization); on **Qwen3-30B-A3B: 2.67 s → 2.16 s (−19.1%) at just 2 nodes/side**. The advantage scales with fleet width, not model size; on a single node P2P is *slower* than broadcast by up to ~70%, so broadcast remains the default.
- **Optimizer-state streaming (Qwen3-30B-A3B)**: cuts actor offload time from **24 s to 5.2 s** and reload from **8.9 s to 1.3 s**, at the cost of slower weight updates (mitigable by BF16 Adam moments) and checkpoint-resume restrictions.
- **On-policy distillation (Qwen3.5-35B-A3B, zero task reward, 5 steps on held-out DAPO prompts)**: response length falls from **14,070 to 6,132 tokens (−56%)** while accuracy moves from **84.0% to 85.2%** — a 1.2-point shift inside the evaluation's ~1.6-point standard error, which the authors themselves frame as "length reduction with no reliable accuracy change," not a benchmark win.
- **Miles-Diffusion (LTX-2.3 recipe, streaming reward scoring)**: rollout time drops from **157.4 to 87.6 s per step** and total step time from **321.9 to 252.1 s**, by deserializing gigabyte-scale video-trajectory tensors as raw bytes in worker processes as each microgroup arrives.
- **True-on-policy alignment**: on supported configs (dense Qwen3 0.6B/4B) the absolute log-prob difference between rollout and training is **exactly zero** (bitwise-identical kernels), with the reward curve matching the baseline on DAPO prompts at reduced throughput.

## Authors & Credibility

The work comes from RadixArk, with core contributors Tom Chen, Mao Cheng, Shi Dong, Kangrui Du, Yanbin Jiang, Jiajun Li, Yiming Li, Tao Lin, Yusheng Su, Andy Ye, Yueming Yuan, and Zhichen Zeng, plus a long acknowledgment list overlapping the SGLang ecosystem (Ying Sheng et al.). It builds directly on slime (THUDM) and SGLang (NeurIPS 2024), and its deeper technical claims (R3, P2P transfer, FP8/MXFP8/NVFP4, INT4 QAT, OPD support) are backed by separate LMSYS org blog posts and prior arXiv work (e.g., Ma et al. 2510.11370 for MoE router mismatch; Thinking Machines' on-policy distillation and batch-invariance posts). The system is open source (github.com/radixark/miles), the case-study launch script is published, and several quantitative claims are precise enough (per-node counts, bucket sizes, clipping notes) to be reproducible in principle by a team with an H100/GB300 budget. This is a credible industrial systems team writing in the SGLang/LMSYS tradition: a system report with explicit evidence levels rather than a peer-reviewed methods paper.

## Critical Assessment

- **Novelty**: The individual pieces are mostly expert integrations rather than new algorithms — TITO formalizes and productizes token-exactness ideas discussed in the SGLang community, R3 comes from Ma et al., OPD from Thinking Machines, and the loop design inherits from slime. The genuine novelty is compositional: the end-to-end quantization "contract" across four stages, the three-layer environment plug-in taxonomy, and the P2P transfer plan with a CPU-resident SGLang replica for re-sharding.
- **Rigor**: Mixed, and the paper knows it. The headline case study is a **single 100-step run on a single task distribution (terminal-bench-2) with no seed replication and no comparison against any competing framework** (verl, OpenRLHF, NeMo-Aligner, AReaL, or even synchronous Miles) — the authors explicitly downgrade the reward rise (0.438 → 0.556 moving average) to "an observation rather than a measured improvement," which is honest but leaves the central efficiency-vs-quality claim (does full asynchrony + staleness hurt final reward?) untested. The throughput claims rest on one configuration each ("some measurements come from one configuration rather than many," as the introduction admits).
- **Reproducibility**: Good for an industrial system — open source, published launch scripts, CI-gated metrics history, bit-exact deterministic diffusion tests, and the noise-prefill weight check. But reproduction requires serious hardware (64 GB300s or multi-node H100), and several advertised features are not actually on main: the Kimi K3 and Qwen3.8 day-0 recipes, the multi-LoRA operation-driven backend, and the Tinker-compatible frontend are open pull requests.
- **Significance**: For practitioners running agentic RL at scale, the P2P weight-sync numbers and the 744B-on-64-GPU recipe are immediately useful reference points; the TITO/R3 fidelity analysis is a valuable checklist even for people who never use Miles.
- **Red flags**: Coverage claims are broader than verified coverage — "supported" ranges from full-scale validated runs down to "unit tests alone," and the paper itself says the model page, not the report, records the level per checkpoint. MXFP8/NVFP4 are Beta with tests on only 1–3 models each (Qwen3-30B-A3B, DeepSeek-V3.2/V4). The 96% cache-hit and 263 s median describe the system's own favorable configuration with no external baseline for either number.

## Strengths

- Treats train–rollout fidelity as a first-class design constraint (TITO token exactness, R3 expert-routing replay, true-on-policy bitwise alignment, pessimistic staleness definition), which most RL frameworks leave implicit.
- The P2P weight-transfer design is well-motivated and well-measured: −85–86% update time at 16–32 nodes per side on 744B–1T models, with an honest counterpoint that single-node P2P loses to broadcast by up to ~70%.
- Unusual engineering honesty: explicit limits section, four-level evidence grading for diffusion recipes, refusal semantics (runs refuse colocated async, abort mode with session server, unmatched model families) instead of silent fallbacks, and the OPD accuracy claim correctly discounted against its standard error.
- Breadth with composability: LoRA RL, on-policy distillation, SFT, and diffusion RL all reuse the same rollout/trainer/weight-update components behind small typed interfaces, so users replace one layer without forking.
- Multi-vendor and day-0 posture: native ROCm on MI300X–MI355X with per-PR CI, and same-day recipes for six frontier models including 1T+ class MoE.

## Limitations

- The flagship result is one unreplicated 100-step run; no baseline framework comparison, no seed variance, and no synchronous-vs-asynchronous controlled ablation on the same workload, so the quality cost of staleness in fully async mode is unquantified.
- True-on-policy alignment covers only dense Qwen3 0.6B/4B; the case study therefore runs with truncated importance sampling and a nonzero (mean 0.0369) train–inference KL rather than exact alignment.
- The TITO session server does not record images or video, so vision-language models must bypass it and drive SGLang directly — a major gap for multimodal agentic RL; screenshots for computer-use are also unsupported.
- Weight-transfer coverage is uneven: P2P needs a unified Megatron–SGLang weight-name mapping (currently Qwen2/Qwen3 dense, Qwen3-MoE, GLM4-MoE, DeepSeek-V3/V3.2 derivatives only), disk-delta is Megatron-only and incompatible with colocation/LoRA/PD-disaggregation, and FSDP lacks LoRA and beyond-host-RAM offload entirely.
- Several marquee features are Beta or unreleased (MXFP8/NVFP4 formats, multi-LoRA, the day-0 LoRA recipes for Kimi K3 / 2.4T Qwen3.8), and the loosest replay-comparison setting can silently merge distinct tool-call histories — the paper flags but does not solve the identifier reconciliation.
- Diffusion-side, two shipped Wan2.2 LoRA recipes are explicitly "not verified," and the reported streaming-reward speedup is measured only on LTX-2.3.

## Relevance

对于关注大模型 RL 后训练基础设施的兴趣方向，这篇报告直接命中核心：多轮 agentic RL 的异步调度、token 级保真（TITO/R3）、MoE 低精度契约与跨集群权重同步都是当前规模化 RL 训练系统最关键的工程瓶颈。如果需要搭建或选型 RL 训练框架（或对比 verl/slime/OpenRLHF），Miles 的设计与量化数据是很有价值的参考。

## Questions for Further Exploration

- What is the quality cost of fully asynchronous training versus synchronous Miles on the identical GLM-5.2/terminal-bench-2 workload — does the 0.0369 mean train–inference KL and buffer staleness translate into a measurable reward gap at matched compute?
- How does end-to-end throughput (wall-clock to target reward) compare against verl, AReaL, or NeMo-Aligner on the same model and task distribution, rather than against Miles' own broadcast baseline?
- Can the R3 routing-tensor overhead (~60 MB per 32K-token trajectory) be compressed or sparsified, and does the GLM-5.2 run — which leaves R3 off — actually need it once MTP and FP8 rollout are in play?
- How would TITO extend to vision-language sessions (image/video tokens), and what does the loosest replay-comparison setting cost in practice for harnesses like Claude Code that fork and compact context?
- Does the on-policy distillation length collapse (−56% tokens at unchanged accuracy on DAPO) persist at longer horizons and with nonzero task reward, or is it a transient of the reverse-KL-only regime?
