> **一句话总结：** 提出 AutoMIP——一个把"持久化想法池 + 算法树"耦合起来的自研究的 LLM agent 技能：想法池保存互补且未验证的研究方向，算法树记录每个方向的可执行实验状态与工件，使 agent 能在 12 小时长程运行中精炼、切换方向并恢复兼容的历史状态；在 MIPLib Open 集上为 31/60 个实例找到新的最优解（超过 Codex 的 29、EvoX 的 15），在 MINLPLib 上解决 52/60（86.7%），且总 token 消耗比最强基线低 24–32%。

> **TL;DR:** AutoMIP is an agent skill for long-horizon autoresearch on NP-hard MILP/MINLP problems that couples a persistent pool of complementary research ideas with an algorithm tree that preserves each direction's executable state (code, solver configs, artifacts), so the agent jointly decides *what to explore* and *where to resume*. On the MIPLib Open set (60 instances, 12-h budget) it attains the goal (a strict improvement over the best known solution) on 31/60 instances vs 29 for the direct Codex agent and 15 for EvoX, with the best final objective on 18 instances vs 5 for Codex, while using 32.0% fewer tokens (734,057 vs 1,078,847); on MINLPLib it solves 52/60 (86.7%) vs 45/60 (75.0%) for Codex. Ablations show removing the idea pool drops success from 15/20 to 12/20 and removing the algorithm tree to 10/20.

## 核心贡献

- **框架层贡献（AutoMIP）：** 首个面向 MILP/MINLP 的系统性自研究框架，把 autoresearch 显式建模为"研究方向 × 可执行实验状态"的联合选择问题，而非仅生成下一个候选解。
- **持久化想法池（PoolThink）：** 每轮初始化 5–10 个互补研究方向（按假设/策略族区分，如邻域搜索、结构分解、模型加强；同方向内的参数调整只算局部精炼不算新想法），池记录含身份、假设、支持证据、启动所需工件、失败风险与状态（unused/used）；至少 5 个候选被用过后才触发刷新，并保留历史。
- **算法树搜索层：** 树的 L 边表示当前方向的局部精炼，R 边表示切换到池中一个未用方向；切换时通过"兼容父节点集合" C_t(q_t) = {v ∈ H_t : K_t(v, q_t)=1} 找到工件满足新方向启动需求的历史状态，恢复其工件后继续实验；用连续 R 边计数 r(v) 防止无进展的反复切换。
- **验证层与防幻觉协议：** 每个候选解必须重新加载原始 MPS 文件、用 Gurobi 等等价求解器独立校验目标值/约束/完整性，明确禁止只信求解器日志或上报未校验解。
- **实证结果：** 在 MIPLib Open/Hard 与 MINLPLib 三个 60 实例基准上，AutoMIP 在成功率、达到目标的速度、最终解质量三个维度全面超过 Codex、Loop、AutoEoH、EvoX 四类基线，且 token 消耗更低；消融实验证明想法池与算法树缺一不可。

## Key Contributions

- **A joint direction–state formulation of autoresearch.** AutoMIP treats autoresearch as the coupled selection of (i) the next research direction and (ii) the compatible historical experimental state to execute it from, formalized as an exploration state M_t = (T_t, F_t, c_t, A_t) over an algorithm tree, a frontier, a current node, and reusable artifacts.
- **Persistent idea pool (PoolThink).** A generation-indexed pool of 5–10 complementary research directions that differ in hypothesis/strategy family (neighborhood search, structural decomposition, model strengthening); parameter tweaks within the same hypothesis are deliberately treated as local refinements, not new ideas. The pool is refreshed only after at least five candidates have been used or committed, preserving history across the run.
- **Tree-guided algorithm search with state restoration.** L-edges refine the current direction; R-edges switch to an unused pool idea by sampling q ~ Uniform(U_t). On a switch, the layer computes the compatible parent set C_t(q_t) = {v ∈ H_t : K_t(v, q_t) = 1} (nodes whose saved artifacts satisfy the new direction's starting requirements), restores the selected parent's artifacts, and continues from there; a consecutive-switch counter r(v) prevents thrashing between directions.
- **Verification layer with independent checking.** Candidate solutions are reloaded against the original MPS and verified with a real solver (e.g., Gurobi) for objective value, constraints, bounds, and integrity — the paper explicitly forbids trusting solver logs alone or reporting unverified solutions, guarding against LLM-fabricated "solutions".
- **Strong empirical gains on community benchmarks.** New best solutions on 31/60 MIPLib Open instances, 30/60 Hard-set fixed targets in a 1-hour budget, and 52/60 on MINLPLib, beating four baseline paradigms (direct coding agent, iterative loop, evolutionary heuristic design, evolutionary computation) at lower token cost; ablations isolate complementary roles of the two structures.

## Methodology

**Problem setting.** A task is a MILP/MINLP instance (given as an MPS file) with a contract C = (S, E, B, τ): an executable candidate snapshot interface S, an evaluator E (feasibility, objective value, runtime), a budget B (43,200 s = 12 h for Open/MINLPLib; 3,600 s = 1 h for the Hard set's fixed-target task), and a stopping predicate τ. AutoMIP is implemented as a reusable "skill" (prompt protocol) that wraps a coding agent (primarily Codex with GPT-5.5; also Claude Code with Claude Sonnet 5), all running locally on an Apple M4 Pro (12 CPU cores, 24 GB RAM).

**Three-layer loop.**
1. *Review-and-ideation layer (PoolThink):* reviews the task structure, current code, execution logs, prior attempts, and (optionally) literature, then generates and screens 5–10 complementary candidate directions; pool records track status and the artifacts each candidate requires, so pool maintenance (what to explore) is separated from execution (where to start).
2. *Algorithm-search layer:* at each step decides d_t ∈ {L, R}. L continues refining the current node (diagnostics, local repairs, seeds, window variants). R is triggered when progress stalls, the core hypothesis is refuted, or no admissible refinement remains, and consumes an unused pool idea. The parent p_t for an L-step is the current node; for an R-step it is selected from compatible historical nodes (current-node ancestry plus reusable frontier nodes), preferring historical parents when consecutive R-switches accumulate, with backtracking limits (R-chains of length two must switch parents; no node may stay right-chain longer than three).
3. *Verification layer:* executes the registered experiment, evaluates feasibility/objective/runtime, independently re-verifies the solution against the original MPS with a general-purpose solver, writes the outcome back into the tree node, the idea pool record, and the frontier (open / backtractable / stalled / closed / right_chain_len), and terminates when the budget B is exhausted or τ is satisfied.

**Benchmarks and metrics.** MIPLib Open set (60 instances; success = first feasible solution strictly improving the best known or incumbent solution) and Hard set (60 instances; success = attaining a known historical objective target within 3,600 s), plus a supplied 60-instance MINLPLib subset (12-h horizon). Metrics: success counts in disjoint time intervals, win counts (lowest final objective among methods), average runtime, and average token consumption. Baselines: Codex (direct coding agent), Loop (iterative refinement keeping the best-so-far), AutoEoH (LLM evolutionary heuristic design), EvoX (GPU-accelerated evolutionary computation), and AutoMIP instantiated on Codex.

## Results & Highlights

- **MIPLib Open set (60 instances, 12-h horizon):** AutoMIP attains the improvement goal on 31/60 instances — more than any baseline (Codex 29, AutoEoH 26, Loop 25, EvoX 15). Within the first 3,600 s it completes 24 tasks vs 13 for Codex, 15 for Loop, 12 for AutoEoH, and 6 for EvoX; by three hours it already matches Codex's final 12-hour count (29). On the 28 instances solved by both AutoMIP and Codex, AutoMIP finishes earlier on 24 (85.7%) with an average speedup of ×2.18. It also wins the best final objective on 18 instances vs 5 (Codex), 4 (Loop), 3 (AutoEoH), and 1 (EvoX) — while consuming 32.0% fewer tokens than Codex (734,057 vs 1,078,847).
- **MIPLib Hard set (fixed-target, 1-h budget):** AutoMIP reaches 14 targets within 600 s vs 6 for Codex, and 27 within 1,800 s vs 17 for Codex; 90% of its eventual 30 successes are already obtained at the 30-minute mark, and its final total is 30/60 vs 29 (Codex), 22 (Loop), 19 (AutoEoH), and 15 (EvoX). On the 27 Hard instances completed by both AutoMIP and Codex, AutoMIP is faster in 20 cases (average speedup ×2.00; ×2.61 vs Loop, ×2.02 vs AutoEoH), with 24.3% lower token usage than Codex (145,646 vs 192,485).
- **MINLPLib (60-instance subset, 12-h horizon):** AutoMIP solves 52/60 (86.7%) vs 45/60 (75.0%) for Codex, 40 for Loop, 29 for AutoEoH, and 31 for EvoX; its solved set strictly contains all 45 Codex successes plus 7 additional nonlinear instances. By 10,800 s it has already completed 50 instances — exceeding Codex's final 12-hour count of 45. It achieves the best final objective on 16 instances vs 11 for Codex and 9 for Loop, and on the 45 jointly solved instances finishes earlier on 31 (average speedup ×1.24).
- **Ablations (20 shared Open-set instances):** Full AutoMIP completes 15/20 (75.0%) vs 12/20 (60.0%) for NoPool (idea pool removed; new directions generated only at switch time) and 10/20 (50.0%) for NoTree (tree replaced by a linear execution history, preventing state reuse). Best final objectives: 9 instances for AutoMIP vs 4 (NoPool) and 2 (NoTree). Within the first 3 hours AutoMIP completes 13 tasks — already more than the final 12-hour counts of either ablation — with the fewest tokens overall (1,070,460 vs 1,558,655 for NoPool, a 31.3% reduction, and 1,683,805 for NoTree, a 36.4% reduction). The two components are complementary: the pool preserves diverse directions, the tree enables compatible-state reuse.
- **Cross-agent portability (20 instances):** the same AutoMIP skill completes 15/20 with Codex (GPT-5.5) and 12/20 with Claude Code (Claude Sonnet 5), with 9 wins vs 6; both configs make early progress (9 vs 7 completions in the first hour; 14 vs 10 by three hours). Attempts with DeepSeek Harness, Gemini CLI, and DeerFlow could not sustain the required 12-hour runs and yielded no completed evaluations.

## Authors & Credibility

The five authors span Chengdu University of Information Technology (Yuwei Gu), Eindhoven University of Technology (Yaoxin Wu), Nanyang Technological University (Tong Guo), Shandong University (Wen Song), and Singapore Management University (Zhiguang Cao). This is an established OR × ML group: Wu, Song, and Cao have a track record in learning-guided optimization, neural combinatorial solving, and LLM-assisted solver design (including prior work on large-scale CVRP solver design via LLM-assisted MCTS, cited as Gu, Chen & Ong 2026). The paper engages seriously with the OR community's infrastructure (MIPLib 2017, MINLPLib, Gurobi verification) rather than only with the LLM-agent literature, which lends credibility to the optimization claims. The engineering is also documented unusually thoroughly: the complete skill protocol (OPT task skill, pool lifecycle, branching-state rules, decision defaults, ablation definitions) is specified across appendices A.1–A.6.

## Critical Assessment

- **Single-run evaluation is the paper's biggest weakness.** Each configuration appears to be run once per instance (60 instances × ~6 configs × up to 12 h each on one Apple M4 Pro makes repeats understandable but never acknowledged). No seeds, variance, or confidence intervals are reported anywhere. Several headline margins are small — 31 vs 29 (AutoMIP vs Codex) on Open and 30 vs 29 on Hard are one-instance differences — and without repeated runs it is impossible to know whether these gaps survive stochastic LLM behavior. The 3-hour and token results are more convincing than the final-count records.
- **The "new best solution" bar is low on the Open set.** Success is defined as *any* strict improvement over the best known or incumbent solution, so an epsilon-improvement and a substantial one count identically in the headline 31/60. The paper never reports the magnitude distribution of improvements, which is exactly what an OR audience would want before concluding the agent "discovers new best solutions". Final-objective wins (18 vs 5) partially mitigate this but don't replace it.
- **Baseline coverage has visible holes relative to the related-work section.** FunSearch (island-based executable-program evolution) and CORAL (multi-agent evolution with persistent shared memory) are both discussed as the closest paradigms yet neither is run; instead the evolutionary baselines are AutoEoH and EvoX. Given AutoMIP's core claim is precisely about preserving untested hypotheses and resumable states versus evolution's re-evaluation of implementations, a head-to-head with CORAL would have been the decisive experiment.
- **Good rigor where it matters most for LLM agents.** The independent verification layer (reload the original MPS, re-check objective/constraints/bounds with a real solver, explicitly forbid trusting solver logs) directly addresses the failure mode of agents reporting fabricated or mis-measured solutions — many agent-for-optimization papers skip this. Token accounting for every time interval, matched cutoffs across methods, and internally fair same-hardware comparison are also done properly.
- **Reproducibility is mixed.** The full skill prompts in the appendix are a genuine service (most agent papers underspecify their prompts), but the pipeline depends on proprietary frontier models (GPT-5.5, Claude Sonnet 5), and the cross-agent section concedes that DeepSeek Harness, Gemini CLI, and DeerFlow could not sustain the 12-hour runs at all — a reminder that results are partly an artifact of harness/model stability, not only of the AutoMIP design.
- **Ablation scope is narrow:** NoPool/NoTree are evaluated only on a 20-instance subset of the Open set, with no ablation on MINLPLib or the Hard set, so the claim that both components generalize to nonlinear optimization rests on the full system's numbers alone.
- **Unusual hardware:** Apple M4 Pro with 12 cores/24 GB is a legitimate but nonstandard platform for MILP benchmarking; comparisons are internally fair, but absolute runtimes and success counts may not transfer to the Linux/many-core servers used in most MIPLib work.

## Strengths

- Real community benchmarks, not toy tasks: new strictly-better solutions on MIPLib instances and 86.7% success on MINLPLib under fixed 12-hour budgets.
- Wins on both axes that matter for long-horizon agents: earlier completion (speedups of ×1.24–×3.09 depending on baseline and cohort) *and* lower total token consumption than every baseline — the gains are not bought with brute-force scaling.
- The joint direction–state design is a clean conceptual contribution: separating "what to explore" (pool) from "where to resume" (tree) with an explicit compatibility check K_t(v, q) is a mechanism other autoresearch domains could adopt directly.
- Verification protocol independently re-checks every candidate against the original MPS, closing the most common honesty gap in LLM-for-optimization work.
- Component-wise ablations (NoPool, NoTree) genuinely support the design story: the full system dominates both ablations in success count, final-objective wins, time, and tokens, and each ablation degrades in a way consistent with its role.
- Cross-agent evaluation (Codex vs Claude Code) shows the skill transfers across underlying models, and the failures with other harnesses are reported transparently rather than hidden.

## Limitations

- Single run per configuration; no variance, seeds, or statistical tests, leaving one-instance margins (31 vs 29 Open; 30 vs 29 Hard) statistically uninterpretable.
- Open-set success criterion counts any strict improvement as a "new best solution"; improvement magnitudes are never reported.
- No comparison with FunSearch or CORAL despite positioning against them in related work.
- Ablations restricted to 20 Open-set instances; no MINLPLib/Hard-set ablations.
- Empirical scope confined to MIPLib/MINLPLib (acknowledged in the conclusion); extending to other domains "requires adjustments" to the skill.
- Depends on agent harnesses that can survive 12-hour autonomous runs — three of six tested systems failed outright, limiting practical generality.
- Frontier-model dependence (GPT-5.5 / Claude Sonnet 5) means the framework's behavior and cost profile will shift with model updates; no weaker open-model condition is tested.

## Questions for Further Exploration

- How do the headline margins behave under repeated runs with different seeds — does 31 vs 29 on MIPLib Open and 30 vs 29 on Hard remain outside run-to-run variance?
- What is the magnitude distribution of the "new best solutions" on the Open set — are they epsilon-improvements or meaningful advances over the incumbent?
- How would AutoMIP fare head-to-head against FunSearch or CORAL under the same 12-hour budget, given both share the motivation of preserving diverse candidate directions?
- Does the idea-pool + compatible-parent-tree coupling transfer to non-OR autoresearch domains (ML engineering, kernel optimization), where artifacts are trains/experiments rather than solver code?
- Can the skill run on weaker open-weight models without collapsing, or is the framework implicitly coupled to frontier-model reliability — and what specifically made DeepSeek Harness, Gemini CLI, and DeerFlow unable to sustain the 12-hour runs?
