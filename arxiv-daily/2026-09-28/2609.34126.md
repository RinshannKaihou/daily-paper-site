> **一句话总结：** 提出 JET 两阶段方法——先在有权衡标签的源任务轨迹上进化出一个可执行的"评审程序"（judge，含证据抽取提示、确定性计算与校准逻辑），冻结后迁移到奖励不可见的测试期任务上，用其评分决定候选 agent 程序的保留、用其诊断文本指导改写；在 WebShop 服装→非服装迁移中，冷启动进化达到 0.7797 平均奖励，比固定 rubric 评审引导的 0.6965 高 0.0832，冷启动精确成功率 50.6% 对 37.2%（相对提升 36%），而 PushT 精确评审对照实验证明增益主要来自生成出更好的程序而非选得更好。

> **TL;DR:** JET evolves an executable judge program on labeled source trajectories (WebShop clothing), freezes it, and transfers it to guide test-time evolution of agent programs on reward-hidden target tasks (WebShop non-clothing, PushT control). On unseen WebShop tasks, cold-start evolution under the evolved judge reaches 0.7797 mean reward vs 0.6965 for a fixed-rubric judge (+0.0832) and 50.6% exact success vs 37.2% (+13.4 pts); warm-start gains are +0.0694 vs +0.0333. A PushT exact-judge control shows the advantage comes mostly from better candidate generation, not final selection: perfect selection under fixed-rubric guidance would only close ~9.7% of the gap.

## 核心贡献

- **可执行评审程序的进化与迁移**：JET 把 judge 本身表示为可执行代码（提示、轨迹预处理、确定性计算、校准逻辑、输出解析均可被进化），在带真实奖励的源轨迹上以最小化 MAE 进化，随后冻结并迁移到目标评测器完全不可见的测试期自适应场景；底层模型权重全程不动。
- **"评测器保持不变"的迁移设定**：提出 reward-hidden 设定——目标侧搜索只能用冻结 judge 的分数做晋升、用其诊断文本做改写反馈，环境评测器输出仅用于事后审计，模拟真实部署中"测试时没有 reward 函数"的情形。
- **冷启动迁移大幅领先**：从未进化程序起步，WebShop 冷启动进化 +0.4647（0.3158→0.7797），比固定 rubric 评审的 +0.3906 和自选的 +0.3094 都高；held-out 任务上达到 0.7915 奖励 / 50.6% 成功率。
- **增益归因分析**：PushT 作为精确评审对照（进化出的 judge 从可见位姿精确重建几何覆盖率规则，MAE=0），证明优势主要来自搜索过程中生成了更好的程序（完美事后选择只能弥补差距的 ~9.7%），而非更好的最终选择。
- **组件消融**：可执行进化比只优化提示的 judge 高 0.1473（适应集）/0.1074（held-out）奖励；诊断文本额外贡献 +0.0405，数值分数调整贡献 +0.0211/+0.0484。

## Key Contributions

- **Executable judge evolution and transfer.** The judge is represented as an evolvable program (prompts, trajectory preprocessing, deterministic computations, calibration logic, output parsing), trained on labeled source trajectories to minimize reward-prediction MAE, then frozen and transferred to reward-hidden target tasks; underlying LLM weights never change.
- **An evaluator-preserving shift setting.** At target adaptation time, judge scores decide candidate promotion and judge diagnostics steer rewrites; environment evaluator outputs are isolated for post-hoc auditing only — modeling realistic deployment where no target reward function exists at test time.
- **Large cold-start transfer gains.** From an unevolved program, evolved-judge guidance on WebShop reaches 0.7797 mean reward (+0.4647 over the 0.3158 cold seed) vs 0.6965 for a fixed-rubric judge and 0.6137 for proposer self-selection; on held-out tasks it achieves 0.7915 reward / 50.6% exact success (vs 0.7008 / 37.2% for fixed-rubric).
- **Attribution of the gain.** Using PushT as an exact-judge control (the evolved judge reconstructs the geometric coverage rule from visible poses with MAE 0.0000), the paper shows the advantage comes from generating better programs during search: perfect final selection among fixed-rubric-guided candidates would raise 0.6965 to only 0.7046, closing ~9.7% of the 0.0832 gap.
- **Component ablations.** Executable evolution beats a prompt-only-optimized judge by 0.1473 (adaptation) / 0.1074 (held-out) reward; textual diagnostics add +0.0405 adaptation reward, and numerical score adjustments add +0.0211 / +0.0484 (adaptation / held-out).

## Methodology

JET is a two-stage procedure over an agent "program" (the executable harness/control policy organizing how the LLM acts in a task environment).

**Stage 1 — source-supervised judge evolution.** Given labeled source trajectories D = {(x_i, r_i)} with true evaluator rewards r_i, the judge J is represented as an executable program whose prompts, trajectory preprocessing, deterministic computations, calibration logic, and output parsing are all revisable. A code-writing proposer (GPT-5.5 via Codex, medium reasoning effort) emits candidate judge programs each round; training MAE determines the evolutionary parent, and a private source-validation split selects the final judge after a 20-round budget. Judge fidelity is reported on a source holdout excluded from development. The judge's LLM calls use GPT-OSS-120B served locally (same model as the agent solver). The selected judge is then frozen: code, parameters, and calibration logic cannot change during target adaptation.

**Stage 2 — reward-hidden target adaptation.** The frozen judge transfers to target tasks T_adapt where evaluator outputs are withheld. Each round, the proposer receives the current best program's code and judge score, frozen-judge textual feedback, and reward-scrubbed trajectories, and emits candidate rewrites. Every candidate is executed on all N target tasks and scored by mean judge score S_J(π); promotion occurs only when the highest-scoring eligible candidate beats the incumbent's judge score. Diagnostics from both accepted and rejected candidates feed the next rewrite. Conditions include a "warm start" (program pre-optimized on source tasks) and a "cold start" (unevolved seed), plus an optional source-constraint variant that queries 50 labeled source tasks to enforce a performance floor (Q_G(π) ≥ b − ε) without touching target evaluator outputs.

**Evaluation protocol.** Primary metrics: mean true reward (WebShop) and final goal coverage (PushT), audited post hoc. Each condition runs 5 independent campaigns × 40 evolution rounds × 500 adaptation tasks (max 100 environment steps per trajectory). WebShop uses clothing source tasks (500 train / 300 validation / 300 holdout) and non-clothing adaptation tasks (300 garden, 81 beauty, 71 electronics, 48 grocery) with a disjoint same-composition held-out set, drawn from a 1,181,436-product catalog. PushT target tasks start farther from the goal with damping 0.2; its coverage rule (polygon intersection area ratio, Eq. 3) is exactly reconstructible from visible poses, making it an exact-judge control. Controls include proposer self-selection, a fixed-rubric judge (predefined rubric, no source-label optimization), an isotonic-calibrated fixed-rubric judge, a deterministic (no-LLM) evolved judge, and diagnostics/score-adjustment ablations. Observation scrubbing strips rewards, coverage, success indicators, and evaluator-only annotations from everything the proposer and judge see.

## Results & Highlights

- **WebShop cold start (primary claim):** evolved-judge guidance reaches 0.7797 ± 0.0702 mean reward vs 0.6965 ± 0.0268 for the fixed-rubric judge (+0.0832, ~13% relative) and 0.6137 ± 0.0699 for proposer self-selection (+0.1660 over self-selection); cold-start held-out exact success is 50.6% vs 37.2% fixed-rubric (+13.4 pts, ~36% relative).
- **WebShop warm start:** evolution from the source-optimized program (initial 0.6256) yields 0.6951 ± 0.0706 with the evolved judge vs 0.6589 ± 0.0299 with fixed-rubric (+0.0362 advantage); the optional source constraint variant is best at 0.7034 ± 0.0122. Warm-start held-out: 0.6951 / 34.2% success vs 0.6700 / 32.6% (no evolution: 0.6387 / 27.6%).
- **PushT control:** cold-start evolved-judge guidance reaches 0.7679 ± 0.0157 coverage vs 0.6199 ± 0.0624 fixed-rubric and 0.6306 ± 0.1352 self-selection; from warm (initial 0.3709), evolved reaches 0.6683 ± 0.0459 vs 0.6033 ± 0.0087 fixed-rubric. The evolved judge reconstructs the exact coverage rule (0.0000 MAE on both splits), so the +0.0650 warm-start gap isolates program-search quality from judge error; zero selection regret means the judge picks the oracle-best candidate among its own generated programs.
- **Judge fidelity:** source-evolution cuts seed-judge holdout MAE from 0.1480 to 0.1168 (−21%) and raises Spearman ρ from 0.8138 to 0.8849; on identical target partial-completion trajectories the evolved judge's MAE is 0.1927 vs 0.2516 for the fixed-rubric judge (−23.4%). Isotonic calibration of the fixed-rubric judge only reaches 0.1488 MAE — still worse than the evolved 0.1168; the deterministic evolved judge (no LLM assessment) achieves 0.1153, showing the evolved code encodes a standalone numerical reward-prediction pathway.
- **Selection vs generation decomposition:** the evolved judge incurs zero mean final-selection regret on saved candidates under both guidance regimes, while the fixed-rubric judge errs at a mean of 17 of 40 rounds per campaign; yet perfect final selection among fixed-rubric-guided programs would raise 0.6965 to only 0.7046 (vs 0.7797), closing ~9.7% of the gap — most of the advantage lies in the programs generated during search.
- **Component ablations (adaptation / held-out reward):** evolved judge with scores+diagnostics 0.6984 / 0.6869; unchanged seed judge 0.2905 / 0.3329; prompt-only source-optimized judge 0.5511 / 0.5795 (so executable evolution adds 0.1473 / 0.1074); scalar-feedback-only 0.6579 / 0.6608 (diagnostics worth +0.0405 / +0.0261); removing score adjustments drops 0.6579→0.6368 and 0.6608→0.6124.

## Authors & Credibility

The paper comes from Yao Long Teng, Jiayi Cai, and Bo An at Nanyang Technological University; Bo An is a well-established researcher in reinforcement learning, multi-agent systems, and LLM agents. The work sits in the active "harness evolution / agentic program search" line (related to Meta-Harness, TTHE, GEPA, AlphaEvolve) and positions itself carefully against reward-model transfer work (AgentRM, SimilarRM). Methodological hygiene is above average for the area: 5 independent campaigns per condition with mean ± SD reporting, disjoint held-out task sets with identical domain composition, explicit observation-scrubbing rules, an AI-use statement, a reproducibility statement promising code release, and a dedicated exact-judge control benchmark. Two caveats: the proposer depends on the proprietary GPT-5.5/Codex endpoint, and the fixed-rubric judge baseline was designed by the authors, though they do strengthen it with isotonic calibration and prompt-optimization variants.

## Critical Assessment

- **The transfer setting is narrower than the framing suggests.** Both benchmarks are evaluator-preserving: WebShop's success criterion and PushT's geometric coverage rule stay fixed while tasks or dynamics change. The authors concede this in Section 6 — transfer to changed reward *criteria* is untested, which is precisely the harder and more interesting case for a transferred judge (e.g., a judge trained on reward A asked to guide search for reward B).
- **Sample size and variance deserve scrutiny.** Headline cold-start numbers rest on 5 campaigns: 0.7797 ± 0.0702 (evolved) vs 0.6965 ± 0.0268 (fixed-rubric) — the SDs overlap, and no significance test is reported. Smaller effects (diagnostics +0.0405, score adjustments +0.0211) are explicitly flagged as uncertain by the authors, which is honest, but the headline +0.0832 is itself only ~1.2 pooled SDs.
- **The evolved judge has a specific failure mode the paper quantifies but does not fix.** In the error decomposition (Table 5 Panel B), on true-zero-reward trajectories the evolved judge's bias is +0.3006 vs +0.1523 for fixed-rubric, and its zero-regime MAE (0.3954) is much worse than the fixed-rubric judge's (0.1523): it systematically overcredits complete failures ("occasional severe false optimism," by the authors' own words). A judge that can be wildly optimistic on hopeless candidates is a real risk for long-horizon search, and the paper does not test whether this causes wasted compute or premature promotion in practice.
- **A quiet asymmetry in the warm-start results.** Warm-start exact success is slightly *lower* under the evolved judge (30.6%) than fixed-rubric (31.2%) despite higher mean reward — the mean-reward metric the paper emphasizes partially diverges from the natural success metric, and the cold-start +0.0832 story is not matched by an unambiguous success-rate win in the warm regime.
- **Missing cost accounting.** Stage 2 runs 40 rounds × 500 tasks × 5 campaigns per condition, each round re-executing candidates on all target tasks with an LLM-judged trajectory; the paper acknowledges inference cost and latency are unanalyzed. For a test-time method, the compute-per-point-of-reward comparison against the fixed-rubric judge (same budget, admittedly) and against simply running more seed-rollouts is the practical question, and it is absent.
- **Baseline strength is reasonable but not exhaustive.** The fixed-rubric judge is author-designed, yet the calibrated variant (0.1488 holdout MAE) and prompt-only optimization ablation (−0.1473 adaptation reward vs executable evolution) make the comparison more than a strawman. A learned non-executable judge (e.g., a trained reward model à la AgentRM) as a transfer baseline is missing, so the claim that *executable* judge evolution is the right tool is supported only by the internal prompt-vs-code ablation.
- **Reproducibility is promised, not yet demonstrated.** Code release is pledged but not included; the pipeline spans a proprietary proposer (GPT-5.5/Codex) plus a locally served GPT-OSS-120B, so exact replication will be sensitive to the proprietary endpoint's drift.

## Strengths

- The core question — can a judge built on labeled source trajectories guide program evolution when target rewards are withheld — is well-posed, and the reward-hidden protocol with post-hoc-only auditing is cleanly implemented (observation scrubbing, eligibility checks, regret accounting).
- The PushT exact-judge control is a genuinely clever experimental design: because the evolved judge reconstructs the coverage rule exactly, the warm-start gap (+0.0650) cleanly attributes gains to program search rather than judge error.
- The attribution analysis (selection regret, oracle-best decomposition showing selection explains only ~9.7% of the gap) goes beyond leaderboard reporting and actually explains *where* the improvement comes from.
- Honest, detailed limitations: the authors flag uncertain small-effect ablations, the evaluator-preserving restriction, and missing cost analysis themselves.
- The counterintuitive cold-beats-warm finding (cold-start evolution reaches higher final rewards than warm-start on WebShop) is reported and discussed — source optimization biases later rewrites toward source-specific behaviors, so starting unevolved gives the search more flexibility.
- Strong ablation coverage: prompt-only vs executable judge, deterministic (no-LLM) judge, diagnostics and score-adjustment removal, isotonic calibration control.

## Limitations

- Only two benchmarks, both with fixed evaluation criteria; generalization to changed reward semantics, other domains (code, longer-horizon web tasks), or larger catalogs is untested.
- Five campaigns per condition with no significance testing; several claimed effects (diagnostics, score adjustments) are within reported uncertainty.
- The evolved judge exhibits documented false optimism on zero-reward trajectories (zero-regime MAE 0.3954 vs 0.1523 for fixed-rubric), unexamined for downstream consequences.
- No compute/latency/cost analysis despite the method being explicitly test-time; each candidate is re-executed on all 500 target tasks per round.
- Exact success in the warm-start WebShop regime slightly decreases vs fixed-rubric (30.6% vs 31.2%), so mean-reward gains do not uniformly translate to the success metric.
- Dependence on a proprietary proposer endpoint (GPT-5.5/Codex) complicates replication; code is promised but not released at publication time.

## Questions for Further Exploration

- Does the transferred judge survive a change in the *reward criterion itself* (e.g., judge built on reward A guiding search for reward B), which is the more demanding transfer the paper explicitly leaves untested?
- Does the evolved judge's false optimism on zero-reward trajectories (+0.3006 bias) cause measurable waste (rejected-good / promoted-bad candidates) in longer campaigns, and can a hybrid judge (fixed-rubric for zero detection, evolved for partial credit) fix it?
- How does the test-time compute of JET (40 rounds × 500 executions) compare per unit of reward gain against simply collecting more source labels and doing warm-start optimization?
- The deterministic evolved judge reaches 0.1153 MAE without any LLM call — is the LLM assessment component earning its inference cost beyond the diagnostics it emits, and could the judge be distilled into pure code?
- Would cold-start-beats-warm-start persist in domains where source and target behaviors share less structure, or is it an artifact of WebShop's clothing→non-clothing split?
