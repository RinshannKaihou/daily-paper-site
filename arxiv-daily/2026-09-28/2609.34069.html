Control logicreject · backtrack · repair

loop-back: enforced restrictions block repeated LLM mistakes — even identical proposals are intercepted.

  • Keeps the AlphaEvolve-style skeleton (built on ShinkaEvolve): seed → parent selection → LLM mutation → evaluation.
  • Certification: harness-detected failures become machine-checkable records of conflicting choices, violated requirements, assumptions, evidence — proposed restrictions are themselves verified before enforcing.
  • CDCL-inspired control: reject conflicting combinations, add missing components, repair while preserving compatible edits. API-only — no weight access, no training.
  • Layered acceptance: every evaluation record is hash-tied to exact candidate source; failed mandatory checks block acceptance. Acceptance = “required checks within stated domains”, not program equivalence.

06Strengths

  • Converts failure feedback from advisory (prompt text) to enforceable (checked certificates) — attacks the real failure mode where LLMs repeat the same error.
  • Unusually thorough verification stack for an LLM-code paper: formal proofs, bounded model checking, fragment equivalence, sanitizers, physics laws, statistical tests.
  • Self-improvement via API calls only — quantified by the ablation (55% → 90% passing).
  • Intellectually honest reporting: non-comparable times flagged, acceptance explicitly scoped, paired medians for the hybrid comparison.
  • Discovered non-obvious, precision-aware optimizations that beat expert Celeritas code.
  • Genuinely good anti-gaming practice: withheld validation suite (fresh RNG, boundary inputs) + hash-identified candidate code.

07Limitations

  • Only two functions; the leap to porting whole codebases (all of Geant4) is untested, and independent-optimizability may not hold for interacting physics components.
  • Table 1’s asymmetric allocation handling inflates headline speedups vs the shared-benchmark numbers.
  • Ablation runs on a different LLM (Qwen3-Coder-Plus) at tiny cost scale, with no variance reported.
  • Correctness is deliberately partial: fragment/requirement-scoped; no analysis of false certificates, staleness, or database growth.
  • No code release stated; the multi-tool harness is underdocumented for independent reproduction.
  • The +1.2% hybrid margin over pure CDES is within plausible run-to-run noise.

08Questions for further exploration

  1. Does the certificate database stay healthy at scale — how often do stale or conflicting certificates accumulate, and how often does the pre-use check reject one?
  2. Would the 55%→90% ablation result hold with the headline GPT-5.6-Sol configuration, or is the benefit model-dependent?
  3. Can fragment-scoped formal guarantees (Lean work-assignment, Alive2/VOLTA equivalence) compose into a whole-simulation correctness argument?
  4. How does the approach handle functions that are not independently optimizable — when a certificate from one component invalidates another’s optimization?
  5. Does the +1.2% hybrid gain persist under more paired rounds and different GPU partition sizes — and what is the variance of the six-round medians?
