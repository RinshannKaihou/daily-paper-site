Why it matters

Pinpoints FP8 loss spikes to the exact tensor the backward reads — a training-free, per-operator check you can run for root-cause analysis and kernel acceptance.

把 FP8 训练发散的根因精确定位到 backward 读取的具体张量值，并给出可在算子层面免训练复验的逐 use 故障判据。

The sharpest caveat

Every training result is 390M-scale plus a single 1.5B seed, and evaluation is loss-only. That these per-use sensitivities bind at 70B+, where FP8 recipes actually deploy, is extrapolated, not shown.

01 · Method

One reference, three weapons

S1

A declared reference

“The gradient of the forward pass as it actually ran,” with gradients passing through each rounding unchanged. Every use must read the forward's value, the original, or a substitute whose gradient matches on average given the realized forward.

S2

Controlled forks

FOG's 390M (Llama-3 setting) trains with TE FP8 attention; at step 999, forks differ only in what the correction term D = rowsum(dO ⊘ O) reads: the forward's rounding (R), a fresh stochastic rounding (N), or no copy (D from probabilities P). TE's backward is emulated in FP32 — closest cast placement lands 2.4–7.6% from its true gradients. Failure rules (non-finite loss, >1.5-nat excursion) were fixed before launch.

S3

Shipped-code runs

390M × 20k steps × 3 seeds on TE's own FP8 attention; each intervention swaps only the attention backward (BF16 FlashAttention-2 recompute) or only the saved output it reads. One 1.5B seed replicates the backward swap.

S4

Theory + a training-free checker

An exact two-parameter model; a theorem that no shared substitute is right on average at both uses of FP8 attention probabilities; a checker that adjudicates each use on a single operator with no training — predictions pre-registered on three real operators.

Setup — 10B FineWeb-Edu tokens · Mistral-NeMo tokenizer (131,072) · 8× NVIDIA H20 · E4M3 forward / E5M2 gradients, margin 0 · AdamW (β₂ 0.95), 20k schedule · PyTorch 2.10–2.14, TE 2.10/2.13, cuDNN 9.16–9.20

Aside · Equal loss ≠ same model

A 390M model with a 6-bit RMSNorm store under the R/R policy ends 0.00425 nats below the reference U/R (5-bit: −0.00957, crossing the pre-fixed ±0.010 margin) — a lower held-out loss — yet its normalization gains fall below U/R's in every layer on both seeds (~0.55 vs ~0.70 at 8k steps). Comparable final loss cannot adjudicate the policy: it can hide a different trained algorithm.

03 · Weighing it

Strengths ↔ Limitations

Strengths

  • Near-minimal causal design: same checkpoint, forward, and rounding distribution; only the read differs — and the outcome flips reproducibly across seeds and software stacks.
  • Rare discipline: failure/success thresholds and all operator-test predictions registered before measurement; every registered statement, including misses, tabulated.
  • Exactly checkable theory — closed-form two-parameter model, theorems confirmed by exhaustive enumeration — not hand-wavy asymptotics.
  • Practical payoff: a no-training per-operator checker, plus a one-line wrapper that fixes a shipped failure — cheaper than FOG's architecture change or a full-precision backward.
  • Empirically demonstrates what final-loss comparisons cannot show (the 5-bit R/R run: lower loss, different weights).

Limitations

  • Scale: 390M × 3 seeds, one 1.5B seed for one intervention; loss-only evaluation, no downstream task benchmarks.
  • Operator- and version-specific: TE 2.10/2.13, PyTorch 2.10–2.14, cuDNN 9.16–9.20, H20 — nothing bounds other kernels or future releases.
  • The fork runs rely on an FP32 emulation of TE's backward (2.4–7.6% from the fused kernel's gradients), not the kernel itself.
  • Stochastic rounding is software-emulated; hardware stochastic rounding is discussed, not tested.
  • The checker can return “undecided”, so some policies remain formally unadjudicated.
  • No code release or checker artifact is mentioned in the main text.
04 · Open questions

What to probe next

  1. Do per-use backward-state sensitivities persist at 70B–trillion-parameter scale, where FP8 recipes actually deploy — and do tolerances like the 1.5-nat excursion rule scale predictably?
  2. Could the checker gate kernel releases in CI — a new kernel certifies each use's requirement before shipping — and would vendors adopt a pre-registration culture for numerics?
  3. How do the conclusions transfer to FP4 training and hardware stochastic rounding, where the rounding distribution differs from the software SR emulated here?
  4. Is there a useful dynamic policy — switching U/R/N per use during training (warmup with N, then R) — or does any deviation from the reference accumulate irreversibly, as the store-probe results suggest?
  5. Since comparable final loss hid different trained weights, which downstream-task or representation metrics would detect such discrepancies earlier and more cheaply than probing every layer's gains?
