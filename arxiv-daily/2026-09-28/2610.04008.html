Why This Matters · 为何重要

把 Skill 自进化从"改 Markdown"推进到文档与脚本的一致性修订，服务长时程自主智能体的可信演化。

Critical Edge · 对照观点

Compute is not cost-matched. The AST stage adds three extra model calls the baselines never receive — gains conflate structure with inference.

And every fault is mutation-injected; real skill decay (API drift, dependency rot) is untested. Shell stays at 0.0 Avg even with AST.

Benchmark construction

Two tracks. In-the-Wild Repair injects survey-observed faults (parameter substitution, helper-call bypass, default-value changes) into 100 packages — 150 tasks across six domains, 115 Python / 29 JS / 3 TS / 3 Shell. Controlled Repair fixes the request and builds four matched states per package — Clean, Doc-fault, Script-fault, Joint (50 × 4 = 200) — enabling within-package comparison.

Dual acceptance. A revision passes only if all checks pass in two families: behavioral tests on targets and caller–helper workflows, plus documentation-driven tests that execute commands extracted from the revised SKILL.md against the revised scripts.

AST-Guided Skill Revision — a bolt-on stage

  1. Requirement–structure grounding. Link each request to AST nodes (Python ast / Babel / Tree-sitter) via snapshot + node type + exact source quotation; resolve caller–helper call graphs.
  2. Targets & constraints. Discrepancies become editable repair targets; already-correct behavior becomes explicit preservation constraints.
  3. Coordinated revision. Node-span edits only inside admitted targets (≤8 targets, ≤4,096 B/snapshot), then a Markdown-alignment pass (≤8 edits) reconciles SKILL.md.

Assessment

from Critical Assessment · Strengths · Limitations

Strengths

  • First benchmark to separately measure doc repair, script repair, doc–code consistency, and preservation — a real gap (Table 1): rivals cover at most two of four.
  • AST grounding is a genuine mechanism, not prompting sugar — requirements bind to uniquely resolved syntax nodes with preservation constraints.
  • Conservative reporting: 3 runs, Hit³, paired bootstrap CIs, composition-sensitivity checks, explicit clean-package regression rates.
  • Calibrated anti-gaming: comment-only "fake repairs" rejected 20/20; wrong bindings rejected 49/49; sandboxed, held-out fault labels.
  • Built from 35,554 real repos — packages and fault patterns reflect what the community actually publishes.

Limitations

  • Injected, not organic faults. Real packages break via API drift and dependency rot — no evidence results transfer; closer to fault-injection testing than maintenance.
  • No cost-matched baseline. Three extra model calls per revision; structure vs. compute is conflated. Ablations run on one backbone only.
  • Generator convergence is undiscussed: +AST variants land at 76.7 vs 76.5 — implicitly questioning what CoEvoSkills' verifier loop contributes at all.
  • Thin slices: Shell 0.0 even with AST; TypeScript and branch/route ~3 tasks; heavy Python skew (115/150).
  • Far from saturated: best Overall Avg 76.7%; Doc tasks were ~27% pre-AST; 100-package In-the-Wild scale is modest.
04

Questions for further exploration

what to probe next
  • Structure or compute? Give non-AST baselines equal revision-and-verification rounds — how much of +21.9 / +27.7 pp survives?
  • Organic breakage. Does AST grounding survive dependency updates and API deprecations, when the surrounding call graph itself changed?
  • Beyond the AST. What representation unlocks shell and config-driven skills, stuck at 0.0 with no rich syntax tree?
  • Verifier loops. With +AST variants converged at 76.7 vs 76.5, is CoEvoSkills' loop only useful in high-failure regimes?
  • Chained evolution. How do preservation constraints behave across multi-round self-evolution, where they compound revision over revision?
