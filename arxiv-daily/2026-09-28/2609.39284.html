Why this matters

Names why skill-evolution scores are confounded by solution leakage — and ships an anti-cheating protocol benchmark builders can adopt directly.

Critical edge

The +4.62 pp headline could be noise: n = 3 trials, no significance testing, one of four tasks regresses — and no third-party harness was ever evaluated.

Efficiency claim: solid. Correctness claim: unresolved.

AConstruction — overlap without leakage

Hand-built sandbox projects, not scraped repos: each task has a README contract, a frozen execution plan, and scenario scaffolding. 30 learning tasks across 6 business domains archive 583 turns — including mistakes, test failures, and repair loops — so harnesses have evidence to distill from.

The 13 transfer tasks share zero business logic, API, or codebase with the learning set; only six abstract capabilities recur (idempotency, concurrency, state transitions, failure recovery, versioning, end-to-end validation).

BExecution — multi-hour, user-in-the-loop

Each transfer task is a full-stack build in isolated OCI/Docker sandboxes (TypeScript / Node 22 / React / PostgreSQL / Chromium): avg 23.46 starter files, 622 LOC, 268 public operations.

An LLM-simulated user (DeepSeek V4 Pro) drives 25–30 interactive turns over a multi-hour cycle, checks progress against the frozen plan, and rejects incomplete deliverables.

CProtocol & metric — hard to game

Two-phase decoupling: skill bank frozen with SHA-256 manifests, skill evolution disabled during transfer, hidden evaluator unmounted until delivery. Score is CCPF — the fraction of applicable hidden test cases passed, micro-averaged; unresolved states count in the denominator, penalizing incompleteness.

Adversarial checks: 64 concurrent same-idempotency-key requests, SIGKILL-and-replace worker recovery, and fake-green probes that break dependencies to expose vacuous agent-written tests.

DAblation — 48 audited trajectories

4 transfer tasks × 4 configurations × 3 trials; GPT-5.5 Medium codes throughout, initial plan fixed to isolate execution capability.

Configs: No Skills (zero-shot) · S-Full-20 (20 principles distilled from full history) · S-Ablated-20 (same pipeline, 69.66% less history) · Coreless-3 (core engineering skills stripped, exploratory).

03

Strengths vs limitations

Strengths

  • Crisp problem formulation — Score = f(Distillation Capability × Evidence Presence) explains exactly why in-domain skill-evolution results are uninterpretable.
  • Exemplary anti-gaming — SHA-256-frozen banks, isolated transfer containers, unmounted evaluators, fake-green dependency-breaking checks.
  • CCPF beats Pass@1 for long-horizon tasks; hidden probes (concurrency, SIGKILL recovery, UI consistency) test real engineering, not API surface.
  • Deep efficiency analysis — cached vs non-cached decomposition, pure dev time, and a measurable thrashing signature behind the Coreless-3 collapse.
  • Honest reporting — non-monotonic results and an ablation that beats the full system are reported, not buried.

Limitations

  • Statistically thin — 4 of 13 transfer tasks, 3 trials, no variance or significance analysis, for a paper about measurement reliability.
  • Single-vendor stack — one coder (GPT-5.5 Medium), one simulator/compressor (DeepSeek V4 Pro); no open-weights, no cross-model transfer.
  • No third-party harness — the stated purpose (comparing skill-distillation frameworks) is exercised only on the authors’ own pipeline variants.
  • Frozen bank excludes retrieval — no dynamic RAG or online adaptation, i.e. not the memory mechanisms most current frameworks actually use.
  • Bespoke sandboxes — hand-built tasks plus LLM-simulated users add unquantified variance; adoption costs up to 66M tokens per run.
04

Open questions

What to probe next

  1. Do +4.62 pp and −55.3% hold on the other 9 transfer tasks with more than 3 trials — or sit within run-to-run variance?
  2. Why does CapacityLease regress while EscrowGuard gains +14.81 pp — is there a task-feature taxonomy predicting when static skills help or mislead?
  3. How sensitive is the 20-skill bank to the compressor model (DeepSeek V4 Pro vs coder) — would self-distillation flip S-Ablated-20 > S-Full-20?
  4. How much of the time saving survives if the harness may retrieve and adapt skills mid-task — the Active-RAG setting the protocol deliberately excludes?
  5. Can simulated-user variance be quantified (e.g. scripted session replays) to separate interaction noise from genuine skill transfer in multi-hour runs?
