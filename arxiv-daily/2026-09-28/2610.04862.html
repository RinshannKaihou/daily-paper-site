01 · System

How GitSwarm works — distilled

Each task starts as an immutable root commit. Homogeneous workers — same model, same behavioral contract, no predefined roles — run asynchronously in isolated Git worktrees at concurrency 5. Every episode ends in exactly one of three moves (right).

The substrate’s core trick: a commit’s physical parent (the branch state a worker started from) is separated from its mandatory informed_by= edges — semantic dependencies on other contributions, even across branches. A worker builds on A while citing discoveries from B.

When episode budget B is exhausted, the most-nominated candidate wins by deterministic plurality vote. Nominations live outside the graph, so judging never pollutes the winner’s ancestry. Research tasks swap voting for validation-score selection and add a shared SLURM GPU pool, a utilization dashboard, and gs_inflight scope announcements so peers avoid duplicating in-flight work. The harness schedules and validates — it never directs.

Contribute — one atomic commit

Validation enforces task-specific publication requirements, not correctness. Format gates, not truth gates.

Nominate — pick a candidate

Nominate an existing contribution with a written rationale; tallies feed the final plurality readout.

Abstain — walk away free

Voluntary abstentions are replaced without consuming budget — one worker famously quit after spotting a peer’s duplicate experiment.

04 · Accumulation evidence

Is the compounding real?

99.9%ProgramBench episodes cite earlier work (96.2% on proofs) via declared dependencies
94.7%of published contributions are later built upon (44.4% on proofs)
82–93%of the ProgramBench graph sits in the winner’s ancestry — vs 21–33% on proofs
74%of negative results were later cited in the Looped-Transformer run
49.5 hafter one worker’s failed single-token-memory experiment, another recycled it into the final model’s temporal mixer

Honest fine print: reuse metrics are worker-declared or observational — and the protocol itself mandates dependency declaration. No full-system ablation removes persistence / branchability / attribution to show benchmark gains depend on them. Two accumulation modes emerge: programming synthesizes into the artifact; proving mostly selects and verifies.

05 · Assessment

Strengths vs cracks

+Strengths

  • Minimal substrate, maximal claim — Git commits plus one mandatory dependency field; no planner, no roles.
  • Mechanistic evidence, not scoreboards — a failed idea revived 49.5 h later; a wrong 128-sample rejection reversed; a worker abstained on spotting a duplicate.
  • parent vs informed_by= elegantly solves “build on A, cite B”; nominations kept outside the graph.
  • Two honest accumulation modes — synthesis-dominant (82–93% ancestry) vs selection-dominant proofs (21–33%).
  • Rare self-audit transparency — misrankings, sign reversals, and failed extensions reported in the main text.

−Limitations

  • No matched-compute head-to-head with MetaGPT / AutoGen / AlphaEvolve-class baselines; concurrent Agora only discussed.
  • Single-run benchmark points; seed noise (~0.010 nats) rivals late “improvements” on the RMT path.
  • NanoChat gain rides a 34× parameter increase (50.3M → 1.72B) with uneven checkpoints and hardware; it also used 3:1 experimenter/critic roles — contradicting “no predefined roles.”
  • Reuse metrics are self-declared; no ablation of persistence / branchability / attribution on the full system.
  • Repo-reinspection token overhead unquantified; frontier-model dependence (GPT-5.5/5.6, GPT-6-Astra, Gemini-3.1-Pro) hurts reproducibility.
  • Proof benchmark saturated — oracle Best-of-N also ceilings, at lower token cost.

06 · Open questions

What to probe next

  1. Would GitSwarm still beat a central-selector variant at full benchmark scale — or is decentralization buying latency rather than quality?
  2. How much of the ProgramBench gain survives a persistence ablation (flat workspace, no informed_by=) at matched budgets — the intervention the authors propose but skip?
  3. Does the proof-domain pattern (selection-dominant, 21–33% ancestry) mean the substrate is mismatched for math — or the verifier too weak to reward accumulation?
  4. Can late-blooming contributions (temporal mixer, shared trigram table) be predicted or incentivized structurally, e.g. RL rewards for value that emerges later?
  5. How do repo-reinspection token costs scale beyond B500 — at what budget does the growing-repository overhead negate further gains?
  6. Do results hold with a mid-tier open-weights worker, or does compounding depend on frontier long-context reliability?
