> **一句话总结：** 提出 VERSE——一个"被验证的自进化优化器"：在 harness 进化（优化器读失败轨迹、改 frozen 执行器 agent 的 prompt/tools/工作流）之上增加执行级验证（trace 最小化把失败轨迹从中位 129 步压到 8 步；验证/重放/扰动三工具让优化器在提交前实测草稿编辑）并让优化器每轮至多花 30 turn 自进化自身的 prompt/skill/tool/hook/notes（双模型权重冻结）；在 SWE-rebench 上为 4 个已发表的 harness 优化器（Meta-Harness/AHE/Self-Harness/HarnessX）统一加挂后全部提升——最优配置（Meta-Harness 宿主）在 108 道 held-out Python 任务上 42.28% vs 最强基线 39.20%，在 107 道更新的五语言 OOD 任务上 37.69% vs 28.66%，且 OOD 上 16/16 组比较全胜，而四个基线在 OOD 上的验证集选择版本离 blank 不到 2 个点。

> **TL;DR:** Harness evolution uses a frozen LLM optimizer to edit a frozen executor's harness, but the optimizer's own harness stays hand-built. Two motivating studies show (1) naive optimizer self-evolution on Meta-Harness HURTS without execution-based verification (31.79% vs 39.20% baseline on SWE-rebench; validation selected round 0), but with simple verification gives the study's best result (41.05%), and (2) across five executors a self-evolving optimizer independently builds 51 artifacts clustering into attribution, verification, training-audit, and workflow tools. VERSE provides these from round one: trace minimization (median failed trajectory 129 → 8 steps), three execution-verification tools (draft-on-targets, failure replay, step perturbation; a task counts as fixed only after two passes), a cross-round training audit, and optimizer self-evolution. Under a train/val/test protocol (110/50/108 Python tasks + 107 newer five-language OOD tasks), adding VERSE with self-evolution improves all four reimplemented harness optimizers in all 16 comparisons by 0.6–10.3 points; its best harness reaches 42.28% in-distribution vs 39.20% for the strongest baseline (Meta-Harness) and 37.69% OOD vs 28.66%. Evolution logs explain why: only 1-in-10 "predicted fixes" actually flip a failing task, half of validation outcome changes don't reproduce, and self-evolving optimizers learn to run regression checks (34/81 draft evals vs 2/89 for fixed optimizers).

## 核心贡献

- **两条动机性观察（受控研究）**：(1) 在 Meta-Harness 上直接加优化器自进化而无执行验证会**变差**（31.79% vs 基线 39.20%，验证集在 6 轮中始终选中第 0 轮初始 harness——优化器把未经验证的"教训"写进自身）；配上简单验证（提交前在 1 个训练任务上试跑草稿）后达 41.05%，是该研究最优。(2) 让自进化优化器带简单验证在 5 个执行器（Qwen3.8-27B、Qwen3-Coder-480B、DeepSeek V3.2、GLM-5、Mistral Large 3）上各跑 6 轮，共演化出 51 个自用工件，无论执行器是谁都聚成四类：归因（attribution）、验证（verification）、训练审计（training audit）、工作流控制（workflow）。
- **VERSE 方法**：给优化器从第 1 轮就配好上述能力——(a) **trace 最小化**：重放轨迹步骤子集，保留仍复现同一失败的最少步骤（中位 129→8 步）；(b) **三个验证工具**（提交前可调用，预算 8 unit/候选、24 unit/轮共享）：验证工具（草稿在≤3 个目标任务上实跑，**连过两次才算修复**）、重放工具（复跑记录的失败确认可复现）、扰动工具（删除/替换可疑步骤后重放，检验因果）；(c) **训练审计**：跨轮记录每类失败模式被修复/回归/回退情况；(d) **优化器自进化**：每轮末最多 30 turn 修订自身的 prompt/skill/tool/hook/notes。执行器与优化器权重全程冻结，形成双层（bilevel）学习：内层改执行器 harness，外层改优化器 harness。
- **理论框架**：把 harness 进化形式化为双层学习。定理 1（修复选择）给出误选修复概率上界 ½β₀∏ρⱼ+ε，并证明仅重读既有证据（不新增执行信息）无法把最小错误率压到 λ(1−λ)β₀² 之下；定理 2（发现并选好 harness）给出 E[L(h)] ≤ ℓ₀ + (1−ℓ₀)∏(1−rᵢ(1−eᵢ)) + ε_sel，说明"找对目标"与"修对失败"相乘——修复经常失败时，更好的目标选择无济于事，与观察 1 一致。
- **统一协议下的主实验**：训练/验证/测试三集不相交（110/50/108 道 Python 任务，来自 SWE-rebench 2025-01~2026-02 月度池；测试为 2026-03 封存发布，n-gram 扫描无污染），OOD 测试为 2026-07 发布的 107 道任务（Go/Java/Python/Rust/TypeScript，仅 20 道 Python）。在同一引擎中以相同执行器、编辑空间、候选数、轮限重新实现 4 个已发表 harness 优化器（仅保留各自的证据接口），逐个加挂 VERSE。
- **进化日志的诚实分析**：18 次运行中，提交编辑声称要修的失败任务只有 28/286（10%）在下次训练运行中真的通过；557 次验证结果变化中 275（49%）复跑不复现；验证工具的 170 次草稿评估中只有 17 次确认草稿修复了目标任务。这量化了"只读轨迹"的优化器面临的噪声，解释了为何执行验证是自进化的前提。

## Key Contributions

- **Two controlled motivating studies**: (1) naive optimizer self-evolution without execution verification degrades Meta-Harness (31.79% vs 39.20%; validation selects the initial harness at every round), while the same self-evolution with simple verification achieves the best result of the study (41.05%); (2) audited across five executors, a self-evolving optimizer builds 51 artifacts for itself that fall into four recurring categories — attribution, verification, training audit, and workflow control.
- **VERSE**, a verified self-evolving optimizer layered on any host harness optimizer: trace minimization (median 129 → 8 steps), three optimizer-invoked verification tools (draft verification with a two-pass rule, failure replay, single-step perturbation), a persistent training audit, and up to 30 turns per round of self-evolution of the optimizer's own prompts/skills/tools/hooks/notes — with both model weights frozen, making harness evolution a bilevel process.
- **A theoretical framework** casting harness evolution as bilevel learning: Theorem 1 bounds wrong-repair probability by ½β₀∏ρⱼ + ε and shows re-analysis of existing evidence alone cannot beat a λ(1−λ)β₀² error floor; Theorem 2 decomposes downstream loss into "no good harness found" ∏(1−rᵢ(1−eᵢ)) and selection error terms, explaining why self-evolution without verification cannot help.
- **Controlled experiments on SWE-rebench** with disjoint train/validation/test splits (110/50/108 Python tasks) plus a newer five-language OOD test set (107 tasks): VERSE with self-evolution improves all four reimplemented host optimizers (Meta-Harness, AHE, Self-Harness, HarnessX) in all 16 comparisons, by 0.6–10.3 points, with best val-selected harness at 42.28% in-distribution (strongest baseline 39.20%) and 37.69% OOD (28.66%).
- **Honest process analysis from evolution logs**: only 28/286 (10%) of predicted fixes actually flip their target task, 275/557 (49%) of validation outcome changes fail to reproduce on rerun, and only 17/170 verification-tool draft evaluations confirm a real fix — quantifying the noise that makes read-only diagnosis unreliable, and showing self-evolving optimizers learn regression checks (34/81 vs 2/89 draft evals) and revise refuted drafts more often (79% vs 57%).

## Methodology

**Setup and protocol.** The executor has frozen weights θ and a harness h (prompts, tools, workflow); the optimizer has frozen weights ω and its own harness g (prompts, skills, tools, hooks, notes). The inner loop edits h against training tasks; the outer loop edits g to improve candidate generation and checking; final harness selection uses a validation split whose *content* is never shown to the optimizer (only per-round accuracy, which validation task IDs flipped, and code-error counts — Appendix C.3.2 bounds the adaptive-reuse gap). On SWE-rebench: 110 training and 50 validation tasks drawn from monthly pools (Jan 2025–Feb 2026); the in-distribution test set is the sealed March 2026 release (108 gradable tasks after 2 fail their own reference solutions); the OOD set is the July 2026 release (107 gradable tasks: Go 21, Java 17, Python 20, Rust 25, TypeScript 24). Main configuration: optimizer Qwen3.8-Flash-Next (176B total, 6B active), executor Qwen3.8-27B, 6 rounds × 3 candidates, greedy decoding via vLLM. Harnesses report avg@3 accuracy over three test evaluations.

**Motivating studies.** Observation 1 ablates {self-evolution} × {simple verification} on Meta-Harness. Observation 2 runs the self-evolving optimizer with simple verification against five open-weight executors from an empty workspace and audits all evolved artifacts (51 total), classifying each into attribution / verification / training audit / workflow.

**VERSE components.** (1) *Attribution with trace minimization*: a failed trajectory is reduced by re-running step subsets; a reduced subset is accepted only if its replay fails exactly the same tests as the full trace. (2) *Verification tools*, sharing a pool of 24 units per round (one unit per target task; verification calls include a confirmation rerun; perturbation may cost two replays): the verification tool runs a draft on up to three tasks it claims to fix — a task counts as fixed only after two passes; the replay tool re-executes a recorded failure to confirm reproducibility; the perturbation tool removes or replaces a suspected step in a reproducible trace and replays. (3) *Training audit*: for each attributed failure mode, tracks which training tasks still fail after each round. (4) *Optimizer self-evolution*: up to 30 turns between rounds reviewing validation accuracy, whether expected fixes landed, and its own tool errors, then editing its own harness; self-written code loads only after a safety check and test run; the fixed verification tools remain callable. The replay study (Appendix I) validates the premises on ~300 SWE-rebench instances plus 208 human-annotated CodeTraceBench traces: LLM read-only diagnosis names the injected faulty step exactly only 36.9% of the time (57.3% within one step), while a single minimal edit at the diagnosed step flips 50.3% of 298 failures and up to 5 edits flips 67.1%.

**Theory.** Failure diagnosis is modeled as a binary hypothesis test where evidence overlap is a Bhattacharyya coefficient β; executed checks with cause-dependent feedback lower the overlap product ∏ρⱼ, while pure re-analysis is bounded below by λ(1−λ)β₀². Self-evolution can raise the targeting rate rᵢ and lower the wrong-repair rate eᵢ; their product multiplies in the bound.

**Cost accounting.** Verification tools add only 27–104 agent runs (2–7%) per evolution run but 1.3–2.5× wall-clock time; candidate count, proposal-turn limits, and evaluation protocol are matched across methods — total execution/token cost is not (Appendix D.3 discloses per-run numbers).

## Results & Highlights

- **All four hosts improve, everywhere.** With self-evolution, VERSE beats its unequipped baseline in all 16 comparisons of Table 2 (val-selected and last, ID and OOD), by 0.6–10.3 points. Best configuration on the Meta-Harness host: 42.28±1.11% val-selected in-distribution vs 39.20±1.11% for baseline Meta-Harness (+3.1) and vs 33.95±0.82% for the blank initial harness; OOD 37.69±1.56% vs 28.66±0.82% (+9.0) and vs blank 27.41±0.82% (+10.3).
- **Baselines overfit in-distribution; VERSE's gains transfer.** On the OOD set, val-selected baselines stay within ~2 points of blank — Meta-Harness's +5.2 gain over blank shrinks to +1.2 — while VERSE is 2.8–10.3 points above blank on every host. Per language (averaged over four hosts): +10.3 points on Go, +10.3 Java, +2.3 Rust, +4.9 TypeScript, +4.2 Python; VERSE raises its host in 16 of 20 host×language pairs. On the 87 non-Python tasks, blank scores 25.3% vs VERSE 35.6% (Meta-Harness host) and 37.9% (HarnessX host).
- **Self-evolution is what keeps VERSE above baseline, but is not uniformly additive.** VERSE's tools alone (w/o self-evolve) beat the baseline on 3 of 4 hosts in-distribution (by 4.0–10.5 points on AHE and Self-Harness) yet fall below the baseline in 8 of 16 comparisons overall; with self-evolution VERSE is above in all 16. But versus VERSE-without-self-evolution, adding self-evolution raises val-selected accuracy in only 2 of 7 main-table cases (Meta-Harness both sets, HarnessX OOD) and lowers it in the other five — e.g., on AHE 35.19% w/ vs 37.96% w/o; on Self-Harness 34.88% vs 40.12%.
- **Ablations (AHE host, no self-evolution).** Full VERSE 37.96% vs AHE 33.95%: removing attribution + minimization (which also removes the audit) drops to 35.80% (costs 2.2 of the 4.0 points); removing only the training audit costs 1.2. Without the diagnosis reports the optimizer calls verification tools >3× more often yet selects a worse harness — checks pay off when aimed by good hypotheses.
- **Verification makes optimizer noise visible.** Of 286 failing training tasks that submitted edits were predicted to fix, only 28 (10%) passed next run; 275/557 (49%) validation outcome changes did not reproduce; the verification tool found a real target fix in only 17/170 draft evaluations and a pure regression-check pass in 30 more. Submitted edits fixed 148 validation tasks but broke 134 (reproduced changes only) — harness editing is nearly zero-sum on this pool without verification to steer it.
- **Self-evolution changes *how* the optimizer verifies.** 34/81 draft evaluations by self-evolving optimizers included an already-passing task as a regression check vs 2/89 for fixed optimizers; when a check showed the draft fixed none of its targets, self-evolving optimizers revised before submitting in 30/38 (79%) vs 42/74 (57%). Evaluated drafts fixed targets at similar rates (9/81 vs 8/89) — the difference is in what gets tested and how failures are handled.
- **Replay study premises hold.** Median failed trace compresses 129 → 8 steps (14.4×; 78.9% of 298 traces accept a reduced subset that fails the exact same tests); successful traces 127 → 4 (28.2×). Read-only attribution names the injected faulty step exactly 36.9% / within-one-step 57.3% of the time, but the fault class is among candidates 98.7%; single-step repair at the diagnosed step flips 50.3% of 298 failures, ≤5 edits flips 67.1% (avg 1.65 edits applied). Two injected faults flip 81.0% of solved runs vs 35.7% for one.
- **Small/mid-model replication and transfer.** With a small executor and mid-size optimizer (3 evolution runs each), VERSE (HarnessX host) averages 32.82±0.20% on SWE-rebench vs 28.39–30.56% for baselines, and 40.57±0.45% on Terminal-Bench vs 36.95–37.83%. Domain transfer (SWE ↔ Terminal-Bench): the executor harness stays domain-specific, but the *inherited optimizer harness* carries gains — VERSE with inherited optimizer beats every frozen-optimizer entry on SWE→TB. Executor swap: harnesses tuned to one model mostly stop helping; the exception (HarnessX+VERSE) is a minimal prompt plus an 18KB hook with a tool-call-argument editor that fixes model-agnostic shell-heredoc quoting failures, flipping 8 of 108 tasks on Qwen3-Coder-480B.

## Critical Assessment

- **The headline "improves all four optimizers in all 16 comparisons" is real but the weaker of the two possible claims.** Versus the more natural competitor — VERSE's own tools without self-evolution — adding self-evolution *lowers* val-selected accuracy in 5 of 7 main-table cases (e.g., AHE 35.19% vs 37.96%; Self-Harness 34.88% vs 40.12%). The all-16-wins framing compares against unequipped baselines. The paper is candid about this, but the abstract's framing ("improves all four evaluated harness optimizers") lets a skimming reader overestimate the self-evolution half of the contribution — which is the half the title emphasizes.
- **Compute is not matched, and the delta is modest where it matters most.** Baselines receive no probe allowance; VERSE runs take 1.3–2.5× the wall-clock time (e.g., HarnessX host 19.0 → 47.0 hours), and optimizer self-updates add model calls. The best-host gain in-distribution is +3.1 points (42.28% vs 39.20%) with overlapping SEMs (±1.11 both) on a single evolution run — the main table has one run per row, so evolution-process variance is unquantified in the headline result (the 3-run appendix study covers the small/mid models, not the main configuration).
- **"OOD" is a strong word for what is tested.** The OOD set is the same SWE-rebench benchmark, four months later, in newer languages — temporal plus language shift within one task family and grading pipeline. The genuinely different domain (Terminal-Bench) is the setting where everything flattens: most methods sit within ~2 points of blank, and the authors themselves note Terminal-Bench "is less sensitive to the harness in this setting." So the cross-domain story rests mainly on a 10-task-transfer experiment with wide SEMs (e.g., 39.33±1.12 vs 38.58±0.75).
- **Named models limit independent replication.** The main optimizer/executor pair (Qwen3.8-Flash-Next, Qwen3.8-27B) and the "anonymized small/mid-size model family" are not standard public checkpoints; third parties cannot exactly reproduce the headline numbers even with the released code, though the included open-weight executor study (five executors) partially mitigates this.
- **Validation-set reuse is a real leak channel, only bounded in theory.** The optimizer sees per-round validation accuracy and which validation task IDs its edits flipped — adaptive reuse of a 50-task set across 6+ rounds. The authors bound the gap via adaptive-data-analysis tools (Appendix C.3.2) but the bound's tightness in practice is untested, and the val-selected protocol itself can overstate test accuracy.
- **The verification-tool volume is low.** 170 draft evaluations and 140 verification-tool calls across all self-evolving runs of Table 2 is thin evidence for behavioral claims like the 79%-vs-57% revision-rate contrast (38 vs 74 cases). These are suggestive process findings, not settled effects.
- On the positive side, the *negative results are the most valuable part*: only 10% of predicted fixes land, 49% of validation changes don't reproduce, and read-only localization is near-chance (36.9% exact step). These numbers will be cited by anyone building harness optimizers, and the willingness to publish the w/o-self-evolution-wins-sometimes table increases trust in the rest.

## Strengths

- A rare controlled answer to "why don't optimizers just evolve themselves?" — a clean 2×2-style study showing self-evolution *hurts* without execution verification (31.79% vs 39.20%) and *helps* with it (41.05%), grounded by the observation that self-evolving optimizers independently reinvent the same four tool categories across five executors.
- Methodologically rigorous protocol: disjoint train/val/test splits with a sealed, pre-frozen test set and contamination scan; uniform reimplementation of all four baselines preserving only their evidence interfaces; validation-selected harness as the primary number with last-round also reported; avg@3 with SEM.
- The verification tools are cheap and well-designed: two-pass fix confirmation, replay-verified reproducibility, single-step perturbation for causality, all under an explicit unit budget, with full cost accounting (2–7% extra agent runs, 1.3–2.5× wall-clock disclosed rather than hidden).
- The evolution-log analysis converts anecdote into numbers (10% fix rate, 49% non-reproduction, regression-check adoption 34/81 vs 2/89) — a dataset-grade contribution for anyone studying optimizer reliability.
- Theory that actually connects to the experiments: the λ(1−λ)β₀² floor explains the Observation-1 failure, and the rᵢ(1−eᵢ) product predicts why targeting improvements alone cannot help while repairs keep failing.
- Honest boundary-drawing throughout: the paper reports where self-evolution underperforms its own tool-only ablation, where Terminal-Bench is flat, and which evolved components fail to transfer to a new executor.

## Limitations

- Self-evolution's incremental value is host-dependent and sometimes negative (5 of 7 val-selected comparisons vs tool-only VERSE), so the practical recipe is "tools first, self-evolution maybe" — weaker than the unified branding suggests.
- Main-table results are single evolution runs; SEM covers test re-evaluation, not the stochasticity of evolution itself (only the small/mid-model appendix replicates runs 3×).
- Compute asymmetry: baselines get no probes and VERSE costs up to 2.5× wall-clock; no accuracy-per-cost curve is offered.
- OOD generalization is within-benchmark (temporal + language); true domain shift (Terminal-Bench) shows gains near noise, and executor-model transfer mostly fails except for one model-agnostic tool-use fix.
- Exact replication of headline numbers requires non-public model checkpoints; the adaptive reuse of a 50-task validation set across rounds is bounded theoretically but its practical leakage is not measured.
- Verified self-evolution is only studied on SWE-style coding tasks with executable tests — domains without cheap execution checks (where the reward signal is itself a model) remain open.

## Relevance

这篇论文正中你第一优先方向 Self-Evolving Agents & Automated Research：它把"自进化 agent"推进到优化器本身的 harness 自进化，并给出了自进化何时失效（无执行验证）与何时有效的受控证据，同时其对长时自主系统可靠性/可审计性的处理（两次通过、回归检查、安全检查后加载自写代码）与你的兴趣高度吻合；另外其"验证结果半数不复现"的噪声量化对任何自动化研究循环都有直接参考价值。

## Questions for Further Exploration

- Can the verification tools be replaced by cheaper proxies (e.g., sampled-test replay or static checks) at equal steering quality, closing the 1.3–2.5× wall-clock gap with baselines?
- Why does self-evolution help only some hosts? Is the "first nine verification calls all refuted the drafts, then it stopped calling" failure mode of fixed optimizers predictable from the evidence interface alone?
- The two-pass fix rule assumes flip noise is symmetric — how should budgets be re-allocated when tasks have flaky tests with asymmetric pass/fail noise?
- Does the λ(1−λ)β₀² error floor bind in practice? Measuring β₀ from logged diagnoses would connect the theory to observable quantities.
- Would optimizer self-evolution become uniformly additive with more rounds (the budget that exposes regressions may need more than 6 rounds to pay off), or does the validation-reuse leakage grow faster than the gains?
- The 49% non-reproduction rate for validation changes suggests SWE-rebench evolution operates near the noise floor — what minimum validation-set size or rerun count makes validation-selected harness selection reliable?
