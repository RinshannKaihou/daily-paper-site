# Do Self-Evolving Skills Generalize to Held-Out Tasks?

> **一句话总结：** 本文首次在统一协议下（同一模型 Qwen3-Coder-480B、同一 agent 架构、同一 train/val/test 划分、测试集全程冻结）系统测量了自进化技能方法（SkillGen、Trace2Skill、SkillOpt、EvoSkill、GEPA）的"技能过拟合"：36 个最终技能中 21 个在训练任务上有提升，但只有 5 个能完整保留到测试任务，10 个甚至低于不用技能的 No Skill 基线；据此提出 GSO——只学习一个"元技能"（如何写技能的指南），每个任务现写一个一次性技能——在全部六个基准上超过最强已有方法 4.3 到 22.5 个百分点（如 SWE-bench Verified 上 47.5% vs SkillOpt 25.0%）。

> **TL;DR:** Skills learned by self-evolving agent methods often do not survive contact with new tasks. Under a controlled protocol (one model, Qwen3-Coder-480B-A35B; identical train/val/test splits; test frozen until each method commits its final skill) across six benchmarks (SpreadsheetBench, RBioBench Clinical/Omics, SWE-bench Verified, HealthBench, SciVisAgentBench), 21 of 36 final skills improve on training tasks but only 5 retain the whole gain, and 10 of 36 test scores fall below the No Skill baseline — retention spans +3.4 to −15.0 points. Overfit skills hard-code training-task details (column names, output files, "always create a summary file" rules). The proposed GSO instead learns only a metaskill (a 6-part guide for writing skills) and writes a fresh throwaway skill per task, with edits accepted only if they fix ≥2× more validation tasks than they break; GSO scores highest on all six benchmarks, e.g. 60.0% vs SkillOpt's 40.0% on SpreadsheetBench and 47.5% vs 25.0% on SWE-bench Verified.

## 核心贡献

- **首个公平对照的技能泛化评测：** 用同一模型（Qwen3-Coder-480B-A35B-Instruct-FP8，温度 0）、同一 agent、同一 train/val/test 划分（多数基准 40/20/40 个任务）、测试任务在方法选定最终技能前完全冻结的协议，对比 5 个自进化方法 + one-shot 技能 + No Skill。
- **定义并量化"技能过拟合"（skill overfitting）：** 提出 G_train/G_test/retention 指标（相对 No Skill 的百分点变化）；21 个训练上有增益的技能中，仅 5 个完整保留增益、13 个部分保留、3 个归零（其中 2 个为负增益/有害）；36 个测试分数中 10 个低于 No Skill；retention 范围 +3.4（RBioBench Clinical 上的 EvoSkill）到 −15.0（SpreadsheetBench 上的 EvoSkill）。
- **技能内容分析 + LLM 判官可判性研究：** 过拟合技能的共性是把针对单个训练任务的修补写成适用于所有任务的规则；一个只读技能文本的 LLM 判官对 126 个最终技能对的测试胜负判断与真实结果一致 108 次（85.7%），但对 45 个单次编辑的效果预测很差（SpreadsheetBench 上 Spearman 相关 0.39，RBioBench 上约等于零）——即成品技能的内容质量可读出、单次编辑的效果必须跑了才知道。
- **提出 GSO（Generalizable Skill Optimization）：** 把学习对象从技能 s 换成元技能 m（六部分：理解任务、盘点工具与证据、写逐步过程、检查结果、定位错误、重试一次），每个任务用 m 现写一个一次性技能 s_x = C(m, x)；训练中每次失败只归因并修改一个部分，且仅在 |R| − 2|B| > 0（修复数是破坏数两倍以上）时接受。
- **GSO 在全部六个基准取得最高测试分：** 比每个基准上最强已有方法高 4.3（HealthBench）至 22.5（SWE-bench Verified）个百分点。

## Key Contributions

- **A fair test of skill generalization:** six methods (SkillGen, Trace2Skill, SkillOpt, EvoSkill, GEPA, plus a One-shot LLM Skill) evaluated against No Skill with one fixed model (Qwen3-Coder-480B-A35B-Instruct-FP8, temperature 0), one agent architecture, shared 40/20/40 train/val/test splits, and test tasks hidden until every method has frozen its final skill.
- **Definition and measurement of "skill overfitting":** training gain vs test gain vs retention, all in percentage points relative to No Skill. Of 36 final skills from six methods across six benchmarks, 21 have G_train > 0; of those, 5 keep the whole gain, 13 keep part, 3 keep none (2 of the 3 are harmful). 10 of the 36 test scores are below No Skill. Retention ranges from +3.4 (EvoSkill, RBioBench Clinical) to −15.0 (EvoSkill, SpreadsheetBench).
- **Skill-content analysis and a judge study:** overfit skills convert one-task fixes into rules for every task (hard-coded column names/output files, unconditional checklists, "create a summary file when one is required" that becomes "always"). An LLM judge (gpt-5.6-sol) reading only the skill text ranks finished skills consistently with test outcomes on 108/126 pairs (85.7%), but predicts the effect of 45 individual edits poorly (Spearman 0.39 on SpreadsheetBench, near zero on RBioBench) — so edits must be validated by running them.
- **GSO (Generalizable Skill Optimization):** change of learning target — keep only a metaskill m, a six-part guide (understand the task; pick tools and sources; write a step-by-step procedure; check the result; find what went wrong; retry once), identical human-written initialization m^(0) for all benchmarks; for each task write a transient skill s_x = C(m, x) that never sees gold answers, reference solutions, or grader code, and discard it after the task. During learning, each failure is traced to exactly one metaskill part, that part alone is edited, and the edit is promoted only if it fixes more than twice as many validation tasks as it breaks (utility u = |R| − 2|B| > 0).
- **State-of-the-art on all six benchmarks:** GSO is 4.3 to 22.5 points above the best existing method per benchmark, with the best retention of any skill (−5.2 on HealthBench).

## Methodology

**Controlled protocol.** Eight methods share everything except their skill-update rule: No Skill, One-shot LLM Skill (written once, never changed), five self-evolving methods (SkillGen, Trace2Skill, SkillOpt, EvoSkill, GEPA), and GSO. The agent is Qwen3-Coder-480B-A35B-Instruct-FP8 at temperature 0; each method gets the same tasks, at most 20 practice rounds, and limits on steps and time. Methods differ only in what persists (Table 3): a single skill (SkillGen), a skill directory (Trace2Skill), one compact document (SkillOpt), folders of skill files (EvoSkill), or any textual component (GEPA). Every final artifact is additionally selected on validation and frozen before test; test tasks are never used to edit or choose a skill.

**Metrics.** With a(x, s) the pass/graded score, G_train(s) and G_test(s) are the gains over the empty skill on training and test instances of the same task type (generalization here is within-task-type, e.g. new spreadsheets or new bug-fix repos, not transfer to a different task family). Retention(s) = G_test − G_train: a skill is "overfit" when retention is negative and "harmful" when G_test < 0. SciVisAgentBench and HealthBench use family-balanced scores so each task family counts equally.

**GSO learning loop (per round).** (1) Solve: write a fresh task-local skill s_x = C(m^(t), x) per training task and run the agent. (2) Trace the failure: read the run log, find the first step that went wrong, and attribute it to one of the six metaskill parts m_k. (3) Edit one part: rewrite only m_k. (4) Accept or reject: run m^(t) and the candidate m′ on the same validation tasks; utility u = |R| − 2|B| where R is the repair set (parent fails, candidate passes) and B the regression set; regressions count double because a skill that breaks tasks it used to solve is worse for the user. Promote only if u > 0. Continuous-score variants handle graded benchmarks (SciVisAgentBench/HealthBench: positive family-balanced change, mean gain in ≥3 of 5 validation specialties, no specialty mean below −0.10, penalty for safety-critical regressions). At test time nothing is updated: GSO writes one skill per test task from the final metaskill, checks its output, and may retry once.

**New benchmark.** The authors also built RBioBench (405 R-programming tasks over real clinical-trial and bioinformatics packages): Clinical (197 tasks, packages like admiral, ANCA) and Omics (208 tasks, 38 CRAN/Bioconductor packages like mafftools, TCGA utilities, Biostrings), with outputs checked by exact comparison (356), tolerance-based comparison (30), or a semantic check (19).

**Judge protocol.** A post-hoc LLM judge (gpt-5.6-sol) scores each frozen skill alone on five weighted dimensions (Generalizability 30%, Applicability 20%, Executability 20%, Robustness 20%, Clarity/efficiency 10%); it never influences which skill a method keeps, and its induced ordering over 126 predefined final-artifact pairs is checked against executable test outcomes.

## Results & Highlights

- **Overfitting is common but uneven:** of the 36 final skills from existing methods (six methods x six benchmarks), 21 improve on their training tasks, but only 5 keep the whole gain on test, 13 keep part, and 3 keep none — 2 of those 3 are harmful. 10 of the 36 test scores of existing methods are below the No Skill baseline. Retention spans +3.4 points (EvoSkill on RBioBench Clinical) to −15.0 points (EvoSkill on SpreadsheetBench).
- **GSO wins on every benchmark (Table 2, test split):** SpreadsheetBench 60.0% vs SkillOpt 40.0% (best existing; No Skill 27.5%); SWE-bench Verified 47.5% vs SkillOpt 25.0% (+22.5, the largest margin; No Skill 17.5%); RBioBench Clinical 76.5% vs One-shot 64.7% (No Skill 58.8%); RBioBench Omics 60.9% vs 50.0% for the best existing method and 43.5% No Skill — on Omics no existing skill method beats No Skill at all; SciVisAgentBench 70.0% vs SkillGen 61.4% (No Skill 58.3%); HealthBench 36.7% vs EvoSkill/SkillOpt 32.4% (No Skill 23.9%) — a +12.8-point jump over No Skill, the only benchmark where every skill helps (existing methods reach 28.6–32.4%).
- **Training gains overstate what users receive:** on SpreadsheetBench every existing method loses 17.5 to 30 points from training to test, while No Skill itself loses 15 — which is why retention (Eq. 3), not the training curve, is the number that matters. GSO has the best test score on all six benchmarks and its smallest retention is −5.2 (HealthBench).
- **Judge sees finished skills but not edits:** across 126 final-skill pairs the content-based judge's preferred skill scores higher on test in 108 pairs (85.7%; 8 real disagreements, 10 ties); for the 45 single training edits, the judge-based utility estimate correlates with the real test change at Spearman 0.39 on SpreadsheetBench and about zero on RBioBench.
- **Content quality corroboration:** on SpreadsheetBench the judge's weighted score puts the GSO metaskill at 92 vs 64–82 for all existing final skills (the authors flag this as a loose comparison since the rubric was written for skills, not guides). Figure 1's worked example: two SkillOpt edits in one run both raise training score a little, yet on test one raises +10 points and the other lowers −5.

## Authors & Credibility

Xihao Piao, Zifeng Wang, and Zheng Chen are with SANKEN (The Institute of Scientific and Industrial Research), Osaka University; Zheng Chen is the corresponding author. This is a small academic team rather than an agent-lab group, but the work shows unusual experimental discipline for the area: a shared frozen-test protocol, per-benchmark accounting of task partitions and verifiers, an explicit AI-use statement, figure-level evidence tables (Table 6) stating what each figure can and cannot support, and honest built-in caveats (e.g., they note their own +11.8-point example edit first helped then hurt). They also built and released RBioBench, extending the evaluation infrastructure. The paper is a v2 posted 7 Oct 2026 (cs.AI). No conflicts or external funding flags are stated.

## Critical Assessment

- **The GSO comparison is a whole-system comparison, and the paper says so — but the headline deltas partly conflate learning target with test-time compute.** GSO at test time writes a skill, checks its output, and may retry once; the other methods do not retry. The authors admit "the comparison with GSO is between whole systems," so the +22.5 on SWE-bench Verified cannot be attributed solely to the metaskill idea; a "No Skill + one retry" or "One-shot skill + retry" control is missing, and would likely close part of the gap given No Skill already reaches 17.5–27.5% without any learning.
- **Two of the six benchmarks are the authors' own.** RBioBench Clinical and Omics are author-built, and the strongest existing methods there are relatively weak (existing methods 39.1–50.0% on Omics vs 43.5% No Skill). The big GSO margins on RBioBench (11.8 and 10.9 points) come partly from benchmarks whose difficulty calibration was set by the same group; the smaller margin (4.3 points on HealthBench, a third-party benchmark with physician-written rubrics) is the more conservative estimate of GSO's advantage.
- **Small test sets make several margins fragile, by the authors' own admission.** HealthBench has 40 test questions and SciVisAgentBench 20; the paper states one task moves such scores by 2.5–5.0 points, so the +4.3-point HealthBench margin over the best existing method is roughly one to two tasks. Statistical significance is never reported (no confidence intervals on any test split).
- **Single-model evidence.** Everything runs on Qwen3-Coder-480B-A35B-Instruct-FP8. Whether overfitting rates (and GSO's advantage) hold for other families/sizes is explicitly listed as an open question, which limits how much the "10 of 36 below No Skill" finding generalizes.
- **The judge model choice is not ablated.** gpt-5.6-sol scores skills while Qwen3-Coder acts; the 85.7% agreement number could shift with a different judge, and no alternative judge or human agreement check is reported.
- **To the authors' credit,** the failure-mode analysis (Figure 3 quotes overfit skills word-for-word, e.g. Trace2Skill's "replicate the exact output shape of the training task" and SkillOpt's "ALWAYS create summary.csv even if not mentioned") is concrete and verifiable, and the paper resists overclaiming by scoping generalization to within-task-type only.

## Strengths

- First controlled, apples-to-apples measurement of whether self-evolving skills carry over, with a frozen-test protocol that rules out test-time adaptation as a confound — a genuine gap in the skill/memory literature the related-work section documents well.
- The retention metric and the overfit/harmful taxonomy give the community reusable vocabulary, and the central finding (10/36 below No Skill; retention +3.4 to −15.0) is a useful corrective to training-curve-only reporting in this area.
- Actionable evaluation guidance backed by data: report test gain and retention rather than the training curve; keep an edit only after running it (judge Spearman ≈ 0 on RBioBench); use a skill-reading judge as a cheap filter for finished skills (85.7% agreement).
- GSO is a simple, well-motivated design: the metaskill never names task-specific file/column/parameter bindings, edits are single-part and regression-penalized (u = |R| − 2|B|), and the full initial metaskill is reproduced in the appendix for reproducibility.
- Unusually transparent for the field: information-boundary table (Table 4), expanded benchmark inventory (Table 5), figure-level evidence boundaries (Table 6), and explicit caveats about small test sets.

## Limitations

- Generalization is studied only within one task type; cross-type transfer (metaskill learned on spreadsheets applied to code) is deferred to future work.
- One model (Qwen3-Coder-480B), one temperature, no variance estimates, and no significance testing despite test splits as small as 20 tasks.
- GSO's test-time skill-writing adds one model call (plus possible retry) per task — inference cost relative to baselines is not quantified.
- Two of six benchmarks are self-built (RBioBench), where prior methods happen to be weakest.
- The metaskill is learned per benchmark family and never shared across benchmarks, so the "learn how to write skills" claim is not yet tested at the level of a single reusable metaskill across domains.
- The judge study uses a single undisclosed-cost judge model with no human-verification sample.

## Relevance

这篇论文与你的第一优先方向 Self-Evolving Agents & Automated Research 高度契合：它用受控实验直接量化了自进化 agent 的"技能过拟合"问题（训练增益无法保留到 held-out 任务），并指出 report retention 而非训练曲线、编辑必须跑过验证等可靠性准则，对评估长时自治 agent 系统的可信性很有参考价值。GSO"只学元技能、每任务现写一次性技能"的思路也值得在你的自动化科研 loop 设计中借鉴。

## Questions for Further Exploration

- Does the metaskill learned on one task family (e.g., spreadsheets) transfer to another (e.g., code repair), or must GSO re-learn m(0)→m per domain — and can a single domain-general metaskill match per-benchmark metaskills?
- How much of GSO's margin survives a test-time-compute-matched control (No Skill / One-shot with the same retry budget), isolating the metaskill's contribution from the extra retry?
- Do the overfitting rates (10/36 below No Skill) persist across model families and scales, and is overfitting severity correlated with model capability?
- Could the skill-reading judge (85.7% agreement on finished skills) be used inside training as a cheap pre-filter to reject likely-overfitting edits before paying for validation runs — and is its reliability stable across judge models?
- Is there a systematic taxonomy of which failure types (hard-coded bindings vs. unconditional checklists vs. overgeneralized rules) cause negative retention, and can detectors be automated rather than found by reading?
