01 Methodology 方法论

Design axiom: integrity is enforced mechanically at the write path. Enforcement reliability differs by roughly an order of magnitude across three placements:

  1. L1
    A prompt sentence“a sentence in a prompt is not a capability until its effect on behavior has been observed”
  2. L2
    A post-hoc checkdetects the violation after the fact; work can be retried around it
  3. L3
    An unrepresentable statethe non-compliant state cannot be written at all — this is where AeS puts every invariant

8 producing/service nodes (Analysis · experiment · observation · derivation · writing · literature · data · postprocess) + 3 architecture nodes (orchestrator · reviewer · curator) — capability grows by deepening contracts, never by adding node types.

Within a run
Each node is a directory with one strict contract (prompt, rules, tool whitelist, required artifacts); a contradictory contract raises instead of silently degrading. Evidence nodes are admitted by a distinct uncatchable sin — experiment: fabricated execution; observation: cherry-picking; derivation: an invalid step disguised as valid — each gated by frozen manifests, adversarial search protocols, or a symbolic proof kernel returning verified / numerically_supported / inconclusive / failed.
Within a project
The loop is driven by verdicts, not position: only the Analysis node may record a scientific verdict; evidence nodes return execution-level verdicts at most. Artifacts freeze onto an append-only SHA-256 hash-chained ledger; amendments need a reason and a new draft; a forgery guard refuses any save carrying frozen:true metadata.
Across projects
Memory compounds by promotion-as-rewrite into a two-tier knowledge base with no birth channel except promotion, gated by three checks plus ~5 human decisions/week. Project memory is one Git-tracked MEMORY.md with constant byte budgets.
Runtime substrate
Context renders as a view over an append-only per-run log (at most one live copy per tool result); ten terminal causes with no i_am_done tool; stall aborts at 5, repeat never does; every command passes one sandboxed choke point; unknown model prices are recorded as unknown, never zero.

03 Strengths 优势

  • A clear, falsifiable engineering thesis with an immediately actionable reliability ladder: prompt < post-hoc check < unrepresentable state.
  • Each mechanism stated exactly once — invariant, prevented failure, realization, cost — unusually readable for a 34-page system description, and designed to be argued with.
  • Measured self-criticism of its own removed designs explains why common harness patterns fail — more useful than most benchmark-chasing papers provide.
  • C2 is a small but complete demonstration of preregistration biting: the platform refuted its own hypothesis against an exact solution and recorded the negative result first-class.
  • Runtime substrate details (context as a view, at-most-one-live-copy, no i_am_done tool, stall-vs-repeat asymmetry) are independently valuable implementation guidance.

04 Limitations 局限

  • No benchmark, no cross-system comparison, no gate ablation; the process-integrity suite is “under construction” and its early version was itself unstable.
  • Single model family (DeepSeek V4); token and wall-clock ratios may not transfer, and a gate built for one model’s failure mode may catch failures stronger models make less often.
  • Two campaigns only: one heavily human-steered (≥23 instructions), one on a problem with an exact analytic solution — best-case demonstrations, not stress tests. Where there is no external truth, a wrong result would be caught “never”, not “immediately”.
  • Process overhead is heavy: ~half of round wall clock is closing/orchestration; no per-node spending ceiling (one run hit turn 153 / 17.5M tokens).
  • The honesty block cannot catch an unsound validation protocol — that mechanical gate is designed but not built.
  • No code or artifact release: none of the ledger-derived numbers are independently checkable.

05 Questions for further exploration 待探索

  1. The gates were never ablated: which of the six laws contributes most of the trustworthiness gain — and does any gate’s false-positive cost exceed its protection on real projects?
  2. Does the preregistration machinery survive domains with no exact solution, where “how would a wrong result be caught” is never rather than immediately?
  3. The C2 manuscript error survived four LLM reviewer rounds and was caught by a human — what mechanical check would have caught it, and would a closure condition on the fit scheme alone have sufficed?
  4. Would the promotion-by-rewriting knowledge base measurably improve a downstream project if the ceiling effect were removed in a controlled comparison?
  5. How do token and wall-clock overheads scale with a stronger model family — and is a per-node spending ceiling compatible with the “budget must be visible in the model’s text” principle?
