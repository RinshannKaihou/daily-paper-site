> **一句话总结：** Meta 提出的 GitSwarm 把推理时计算组织成一棵持久的、可分支的 Git 提交图——同质化异步 agent 在共享仓库上自主决定探索/验证/修补/综合，用强制的 `informed_by=` 语义依赖边记录跨分支继承；在 ProgramBench 程序重建上以 79.4% 均分远超同预算最强基线 Forced Codex 的 65.1%，用 GPT-5.5-High 一次性解出 IMOProofBench-Advanced 全部 30 道证明题，并在 RMT/Looped Transformer/NanoChat 三个 GPU 架构研究任务上通过"失败结果被 49.5 小时后回收再用"等机制真实改进了起点架构。

> **TL;DR:** GitSwarm operationalizes "compounding inference" — intermediate agent work persists as atomic commits in a shared, branchable Git repository, and homogeneous asynchronous workers independently decide what to extend, with mandatory `informed_by=` edges recording cross-branch semantic dependencies and a plurality nomination vote replacing a central judge. On ProgramBench (50-task subset) it reaches 79.4% mean score at a 500-worker budget versus 65.1% for the strongest baseline, a repeatedly-continued single "Forced Codex" agent (+14.3 pts), improving monotonically from 73.1% at B100. On IMOProofBench-Advanced it solves all 30 proofs with GPT-5.5-High workers (Gemini-3.1-Pro: 23.3 → 29.0 fully-correct proofs from B20 to B160). On three GPU-backed research tasks it improves real architectures — RMT held-out loss 2.890 vs 3.147 reference at the same 1.3B-token budget, Looped Transformer 3.187 vs 3.265, NanoChat validation BPB 0.993 → 0.905 — while 94.7% of ProgramBench contributions are later built upon and the winning solution's transitive ancestry covers 82–93% of the contribution graph.

## 核心贡献

- **提出"复合推理"(compounding inference) 范式**：不同于围绕单条轨迹或单轮候选组织推理时算力，让中间产物（部分解、失败实验、验证工具）持久化，供后续计算检查、扩展、组合与质疑，跨 episode 复利积累。
- **GitSwarm 系统**：以共享可分支 Git 仓库为结构化持久记忆；同质 worker 异步运行（无中心规划者、无预设角色），每个 episode 以 Contribute（一个原子提交）/ Nominate（提名现有候选）/ Abstain 三种动作结束；区分物理 Git parent 与强制的 `informed_by=` 语义依赖，使 worker 可以站在 A 分支上却引用 B 分支的发现；最终通过 worker 提名 + 确定性多数票"去中心化读出"选出提交解。
- **评测覆盖两类场景**：长程问题求解（IMOProofBench-Advanced 数学证明、ProgramBench 程序重建）与持续实验研究（RMT、Looped Transformer、NanoChat 三个 GPU 架构改进任务），后者通过 SLURM 共享 GPU 池模拟真实研究组。
- **对"积累是否真实发生"的测量**：声明依赖率（99.9%/96.2% 的 episode 引用前作）、选中解的传递祖先覆盖率（ProgramBench 81.6–92.6% vs 证明题仅 21.3–33.0%）、执行轨迹中的工件消费率，并用三个受控合成任务（Hidden Rulebook / Hidden Maze / Retracted Evidence）分别隔离持久性、可分支性与归因三个 substrate 性质。
- **罕见的过程发现**：128 样本小规模评估在 12 对模型比较中错排 5 对；种子噪声 (0.010 nats) 与后期多步改进同量级；一个失败的单 token 记忆复用实验在 49.5 小时后被另一 worker 引用并推广成进入最终模型的时间混合器。

## Key Contributions

- **Formulates "compounding inference"** as a paradigm: organize inference-time computation so intermediate work persists and can be inspected, extended, combined, or challenged by subsequent episodes, rather than evaporating when an episode ends.
- **Introduces GitSwarm**: asynchronous, role-free, homogeneous workers over a shared branchable Git repository; atomic commits; a mandatory `informed_by=` field separating the physical starting state (Git parent) from additional semantic dependencies, enabling a worker to extend one branch while citing discoveries from others; decentralized readout via worker nominations plus deterministic plurality selection; a dashboard and `gs_inflight` activity logs to reduce duplicate work — with the harness managing only scheduling/validation, never intellectual direction.
- **Evaluates task performance AND the accumulation process itself** across long-horizon problem solving (math proof, program reconstruction) and sustained GPU-backed experimental research (Residual Matrix Transformer, Looped Transformer/Huginn, NanoChat), reporting declared-dependency rates, trace-verified artifact consumption, and transitive ancestry of selected solutions.
- **Three controlled synthetic tests** (Hidden Rulebook, Hidden Maze, Retracted Evidence) that isolate persistence, branchability, and attribution respectively, showing each substrate property reduces a distinct form of repeated work (rediscovery, re-traversal, lineage reconstruction).
- **Honest characterization of two compounding modes**: program reconstruction accumulates contributions INTO the final artifact (ancestry 82–93% of the graph), while proof solving uses earlier work mainly to verify and compare candidates (ancestry only 21–33%), i.e., useful computation need not appear in the winner's ancestry.

## Methodology

**System.** For each task, GitSwarm initializes a Git repo containing the task spec as an immutable root commit. Accepted contributions form a graph where each node is an atomic Git commit with (a) a physical parent identifying the branch state the worker started from, and (b) a mandatory `informed_by=` set of additional prior contributions its work depends on (parent must be included). Workers are homogeneous (same model, same behavioral contract, no predefined roles), run in isolated Git worktrees up to concurrency C=5 for problem-solving, and end each episode by contributing one validated commit (validation enforces task-specific publication requirements, NOT correctness), nominating an existing candidate with a rationale, or abstaining (voluntary abstentions are replaced without consuming budget B). After the budget is exhausted, the candidate with the most nominations is selected (deterministic tie-break). Nomination records live outside the contribution graph so evaluating a candidate never alters its ancestry.

**Coordination surfaces.** A per-worker dashboard reports remaining budget, in-flight workers, nomination tally (explicitly labeled "not correctness evidence"), and for research tasks shared GPU/CPU/job usage with a low-utilization warning plus best validation score. `gs_inflight` lets each worker announce scope (gap, deliverable, success/abort criteria) before editing and post progress, so peers can avoid duplicating in-flight work.

**Problem-solving evaluation.** IMOProofBench-Advanced: all 30 proof problems, scored {0,1,6,7}, full score 7 counted as solved; workers Gemini-3.1-Pro or Codex (GPT-5.5-high); budgets B ∈ {20,40,80,120,160}. ProgramBench: a fixed 50-task subset of 200 (stratified by language/difficulty/test-suite size/runtime), score = fraction of hidden tests matching an execute-only reference; budgets B ∈ {100,200,300,500}. Baselines are "Forced" single agents (bash / mini-SWE-agent / Codex) repeatedly prompted to continue, evaluated at natural stopping checkpoints at comparable compute; scaling is plotted against input and output tokens.

**Research tasks (AutoResearch).** RMT: improve a 305M-param Residual Matrix Transformer (matrix-valued residual stream), cap 350M params, 1.3B-token training budget, 72 h on 8×H200, two 12-worker swarms (GPT-5.6-sol xHigh) sharing 8 or 4 GPUs; metric = next-token loss on a 4,873-example protected dev set (reference 3.158 dev / 3.147 held-out). Looped Transformer: Huginn 308M weight-tied recurrent model, ≤350M unique params, 12 workers, 48 h budget (reported at 26 h), loss at exactly 8 recurrences (reference 3.265). NanoChat: 50.3M-param base, 5-minute from-scratch training clock, validation BPB, 20 workers sharing 16 GB300 GPUs (GPT-6-Astra), compared with single-agent Codex and an Atlas-style evolutionary search (AIRA2) — notably with NO parameter/token caps, so capacity itself is a search variable. For research tasks, nomination readout is replaced by validation-score selection.

**Reuse measurement.** Three independent instruments: (1) declared dependencies (Git parents + `informed_by=`), (2) execution-trace artifact consumption (accessed / executed-or-adapted / feeds selected ancestry), (3) transitive ancestry of the selected solution through both edge types. Supplemented by three synthetic tasks with 3 seeds each sweeping target count, chain depth, maze depth/branching, lineage depth, ambiguity, and fan-out.

## Results & Highlights

- **ProgramBench (mean score, 50 tasks):** GitSwarm with Codex (GPT-5.5-high) workers improves from 73.1% at B100 to 79.4% at B500, versus 63.1–65.1% for the Forced Codex baseline across all its checkpoints — a +14.3 pt gap at the top budget. With default-effort GPT-5.5 workers: 64.6% (B100) → 71.2% (B300).
- **IMOProofBench-Advanced:** with GPT-5.5-High workers GitSwarm solves 28/30 at B20 and all 30/30 at B40 and B80 (one run, slightly under 1M output tokens). With Gemini-3.1-Pro, mean fully-correct proofs rise from 23.3 (B20) to 29.0 (B160) — non-monotonically, dipping at B80; the Forced mini-SWE-agent baseline peaks at 23 and the continued bash agent reaches 26.5 at similar input-token budget. The authors candidly note oracle Best-of-N also saturates this benchmark.
- **RMT architecture research:** both 12-worker swarms beat the reference at its own 1.3B-token budget — held-out loss 2.890 (8-GPU swarm) and 2.894 (4-GPU swarm) vs 3.147 reference. Baselines needed far more tokens: Forced GPT-5.6-sol reaches 2.927 with 3.0B tokens and Codex 2.690 with 10.1B (~3/4 of its gain from extra tokens). The 8-GPU winner integrates six mechanisms, four of which originated on other branches; its declared dependency set spans 24 commits by 24 distinct workers. A seeded run combining winners of three prior runs improved 2.909 → 2.898 in ~28 h.
- **Looped Transformer:** at 26 h the swarm reaches protected-dev loss 3.187 vs 3.265 reference, 3.274 direct GPT, and 3.479 Codex; a parameter-matched control (3.212) confirms ~2/3 of the gain survives equal capacity. The winning gated-FFN re-injection adapter was initially REJECTED on a 128-example eval, revived by a 512-example re-check, and confirmed at full size — 128-example evals misranked 5/12 model pairs. Its 6-commit code lineage declares 89 evidence dependencies by 89 workers; 395 experiments across 12 idea families in 26 h, with 74% of negative results later cited.
- **NanoChat:** in the first 24 active hours the GPT-6-Astra/GB300 swarm reduces validation BPB from 0.9927 to 0.9052 (−8.81%) over 1,465 successful evaluations, beating the Atlas-style evolutionary search and single-agent Codex configurations plotted — but the model grows from 50.3M to ~1.72B params (1.61B in a hashed bigram/trigram lexical table), so this is joint capacity+architecture search, not an equal-parameter comparison. A failed separate-trigram experiment (0.9299 vs 0.9291 bigram-only controls) was explicitly cited 21 active hours later and recycled into the shared-table design of the 24-h incumbent.
- **Evidence of compounding:** 99.9% (ProgramBench) / 96.2% (IMOProof) of episodes cite earlier work; 94.7% / 44.4% of published contributions are subsequently built upon. Selected-solution ancestry covers 81.6–92.6% of the ProgramBench graph (only ~1/4 via Git parents — the rest via cross-branch `informed_by=` edges) versus 21.3–33.0% on proofs. Traces show 79.9–82.5% of voluntary artifact bundles actively reused on ProgramBench; on proofs, 583/759 probe bundles opened, 172 executed or adapted, 52 feeding the selected proof's ancestry.
- **Controlled substrate tests:** shared persistent memory keeps high relevant-record coverage as targets/depth grow while independent baselines with ~4/3 LARGER aggregate query budgets plateau at ~70–75% (B=2) or 20–23% (k=4); branch-native maze memory cuts repeated-move fraction versus flat persistent memory; explicit attribution metadata shrinks the archive fraction workers must read, with the gap widening with lineage depth.
- **Design tradeoffs (9 dev tasks, 3 seeds):** asynchronous execution scores 62.06±2.44% in 38.0 min vs 63.11±0.58% in 49.3 min for synchronized waves; decentralized nomination scores 62.06±2.44% in 38.0 min vs 64.40±1.49% in 34.9 min for a central selector, and 58.19±4.53% in 43.9 min for a central aggregation agent.

Carole-Jean Wu (systems/hardware) and Anirudh Goyal (shared-workspace architectures, prior work on global-workspace neural modules) map directly onto the paper's systems + cognitive-architecture framing. Credibility: very high; conflicts none declared beyond Meta affiliation.

## Critical Assessment

- **The headline benchmark baselines are thin.** On ProgramBench, the central comparison is "Forced Codex" — a single agent repeatedly told to continue — not any actual competing multi-agent or memory system (no MetaGPT/AutoGen-style team, no PDR/RSA, no AlphaEvolve-style population method on this benchmark). Beating a continued single agent by 14 points establishes that naive continuation is weak, not that Git-style persistent memory is the best way to spend the same tokens. The appendix design-tradeoff experiments even show a CENTRAL selector (64.40±1.49%) outscoring decentralized nomination (62.06±2.44%) on the dev set — an awkward data point for the "decentralization" thesis that goes un-pursued at benchmark scale.
- **IMOProofBench-Advanced is saturated and the 30/30 claim is fragile.** The perfect score is a single run at B40/B80, the authors themselves flag that oracle Best-of-N also hits the ceiling at lower token cost, the Gemini scaling curve is non-monotonic (dips at B80), and "execution conditions differ across some proof comparisons" (Appendix B.4) — so the cross-budget curve is descriptive, not a controlled effect estimate. Solving all 30 problems says more about the benchmark's ceiling under GPT-5.5-High than about GitSwarm specifically.
- **The NanoChat result is confounded by unconstrained capacity.** The 50.3M base becomes a 1.72B-parameter model (96.7% of parameters in one lexical table), with differing starting checkpoints and GPU allocations across compared methods. A −8.81% BPB gain largely bought by a 34× parameter increase cannot support claims about collective architecture discovery; the authors admit this but the headline number still reads as a win. The NanoChat run also silently contradicts the "no predefined roles" design: it configured 3:1 experimenter/critic roles.
- **Causality is asserted by narrative, not intervention.** All reuse metrics (declared `informed_by=` edges, ancestry coverage, artifact consumption) are worker-declared or observational. The paper honestly says a proper test would resume matched runs with and without research history, and the synthetic tasks show substrate properties help in isolation — but no ablation removes persistence/branchability/attribution from the FULL system to show benchmark gains depend on them. "94.7% of contributions are built upon" could partly reflect the protocol mandating dependency declaration.
- **Statistical rigor is thin where it matters most.** Main benchmark points are single runs per budget (3 seeds appear only in the 9-task design-tradeoff experiments); the RMT appendix concedes seed noise (~0.010 nats) is comparable to several late "improvements" on the solution path, which casts doubt on fine-grained ranking of 2.890 vs 2.894-class differences; Looped Transformer results are from runs "still in progress" at 26 of 48 hours; the seeded RMT run is explicitly not comparable.
- **Cost accounting favors the method's framing.** Budget B counts "charged episodes," with voluntary abstentions free; input tokens grow as workers inspect an expanding repository, and the paper concedes benefits-over-costs at longer horizons is untested. There is no matched-compute comparison against simply running more independent samples with a cheap verifier on ProgramBench.
- **Redeeming rigor:** the honesty is exceptional — mis-rankings by proxy evals, sign reversals at full scale, an unverifiable best NanoChat observation (its exact-source repeat differs by 0.0012 BPB and it was rejected for an out-of-policy file), and explicit "does not establish a unique advantage" hedges are all reported in the main text. That level of self-audit is rarer than the results themselves.

## Strengths

- A crisp, well-motivated paradigm (compounding inference) with a genuinely simple substrate: Git commits + one mandatory dependency field, no central planner, no role assignments — close to the minimum mechanism needed for cross-episode accumulation.
- The strongest evidence in the paper is mechanistic, not just scoreboard: documented recovery of a failed single-token-memory idea into a temporal mixer 49.5 h later; reversal of a wrong 128-example rejection via re-evaluation; a worker predeclaring a reversed experiment-order control; a worker abstaining after spotting a peer's duplicate in-flight experiment. These are concrete instances of computation actually compounding.
- Separation of physical parent from semantic `informed_by=` dependencies is an elegant fix for "build on branch A while citing branch B," and keeping nominations outside the graph keeps the winner's ancestry clean.
- Two-mode finding (synthesis-dominant programming vs selection-dominant proof) is an honest, useful characterization that goes beyond "our ancestry is big."
- Broad evaluation across answer-verification tasks AND open-ended GPU research with real artifacts (SLURM, H200/GB300), plus controlled synthetic isolations of each substrate property.
- Exceptional transparency: limitations section, per-task caveats, and even failed/unverifiable extension results are reported in detail.

## Limitations

- No head-to-head against real multi-agent or memory baselines (MetaGPT, AutoGen, PDR/RSA, AlphaEvolve, Agora) at matched compute on the benchmarks; the concurrent Agora system is discussed but not compared.
- Single-run benchmark points; 3 seeds only in small dev-set experiments; non-monotonic proof scaling and seed noise (~0.010 nats) comparable to reported gains undermine fine-grained claims.
- NanoChat lacks parameter/token controls (1.72B vs 50.3M) and uses heterogeneous starting checkpoints/hardware across compared methods; Looped Transformer runs unfinished; RMT single-agent baselines used 2.3–7.8× more training tokens.
- Reuse metrics are declared/self-reported; no full-system ablation isolating persistence, branchability, or attribution effects on benchmark performance.
- Computational overhead of persistent collaboration (input tokens spent re-inspecting a growing repo) is acknowledged but not quantified against alternatives; gains-over-costs at long horizons untested.
- Frontier-model dependence (GPT-5.5/5.6, GPT-6-Astra, Gemini-3.1-Pro) makes results expensive to reproduce and likely model-generation-specific; the 30/30 proof result is one run.
- ProgramBench evaluated on a fixed 50/200-task subset.

## Questions for Further Exploration

- Would GitSwarm still beat a central-selector variant at full benchmark scale, given the dev-set result where the central selector scored higher (64.40% vs 62.06%)? Is decentralization buying latency rather than quality?
- What fraction of the ProgramBench gain survives when persistent memory is ablated (flat workspace, or no `informed_by=`) at matched episode budgets — the causal intervention the authors themselves propose but do not run?
- Does the proof-domain pattern (selection-dominant, 21–33% ancestry) indicate the substrate is mismatched for math, or that IMOProofBench's verifier is too weak to reward accumulation?
- Can the documented failure-recovery behaviors (temporal mixer, shared trigram table) be predicted or incentivized structurally, e.g., by training workers with RL rewards for contributions whose value emerges later, as the conclusion sketches?
- How do the repo-inspection token costs scale beyond B500, and at what budget does the growing-repository overhead negate further gains?
- Would the results hold with a mid-tier open-weights worker model, or does compounding depend on frontier-model long-context reliability?
