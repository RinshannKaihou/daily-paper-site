→ How it works

Critical edge

The deployed plan-merge's celebrated 70.8% is substantially a budget artifact: capped to the envelope it ties CC→Codex→CC at exactly 62.5% (paired 0.0, CI [−5.5, 5.5]).

ExecML's 96 tasks are also seeded from the authors' own incidents — independent task curation is missing.

→ Limitations
01

Methodology, distilled

RankEvolve harnesses the harnesses: commercial coding agents are already harnesses over raw models, and RankEvolve stacks two more levels of discipline on top.

  1. LAYER 1

    Authoring — Executable Operating Protocol (EOP)

    Phases, dependencies, human-confirmation gates, branch/loop edges and tool allowlists are authored once as a versioned, semi-structured document, statically checked, and compiled into a state machine the runtime enforces. Semantic code correctness is expressly not guaranteed.

  2. LAYER 2

    Control — meta-meta-harness

    Whole black-box products (Claude Code, Codex; OpenHands substitutable) bind to one adapter contract: task, repo snapshot and budget in; patch, status, trace and usage out. Routing, aggregation, gates and metrics stay deterministic runtime functions; nodes checkpoint at boundaries and time-outs fail closed.

  3. LAYER 3

    Knowledge — provenance + memory

    Every hypothesis, patch, metric and cost is recorded with full provenance. Negative results persist as first-class leaderboard rows; each phase reads back only phase-relevant lessons from a two-tier experiential memory.

Measurement. ExecML seeds 96 hidden-oracle private tasks per repo (HSTU + LitGPT) across six defect families, under six pre-registered budget-matched conditions with exact McNemar tests and task-clustered bootstrap CIs. The 12-iteration HSTU deployment (~55 leaderboard entries, 1–8 H200s) separates canonical full-test NDCG@10 from a subset evaluation that ran ≤0.005–0.010 higher — without that separation, the system chased phantom gains.

Decorrelation condition met: β₃ = 0.34, 95% CI [0.12, 0.56] — "complementary error mass × conversion efficiency", not vague diversity.

  • Context-scope ablation. Per-step vs full-protocol injection, identical runtime: +2.1 / +6.2 / +10.4 EA (early / middle / late phases); CDR 11.5 vs 17.7; −$0.57/task. The state machine, not the prompt, should carry the process.
  • Process-faithfulness pilot. Of 10 runs given the whole playbook as one in-context prompt, 0 were fully faithful — 4 stopped early, 4 skipped the confirmation gate, 3 called tools off-spec.
03

Strengths

  • Execution accuracy as the binding constraint — hidden multi-part oracles (regression + behavior + scientific-safety + evaluator-integrity), not visible pass@1.
  • Rare statistical discipline for an agent paper: pre-registration, frozen budgets, Holm correction, exact McNemar, clustered CIs — with nulls reported whatever the outcome.
  • First-class negative results — a genuinely useful failure catalog for anyone auto-evolving recommenders.
  • Mechanism analysis turns "diversity is good" folklore into a quantitative, falsifiable decorrelation claim with held-out prediction.
  • Context-scope ablation cleanly isolates prompt scope from runtime enforcement — per-step injection wins increasingly late (+10.4 EA), at lower cost.
04

Limitations

  • Benchmark circularity — ExecML tasks are seeded from the authors' own incidents; no independent curation.
  • n = 1 product pair (Claude Code × Codex); OpenHands named but unmeasured; the decorrelation generalization is untested.
  • Deployment attribution — agent and human-operator contributions are conflated; endpoints are best-checkpoint values from one run lineage.
  • Black-box budgeting — matching is by observable tokens/actions/dollars; provider-side compute and cached context stay hidden.
  • Knowledge layer un-ablated — its marginal contribution is asserted by design, not measured.
  • Narrow domain — both codebases are Python/PyTorch; cross-domain transfer is probed, not established; oracles still admit some false passes.
05

Questions for further exploration

Q1Does the heterogeneous-pairing gain survive an independently curated task corpus — or a third/fourth product (OpenHands, open-weights) in the review-repair cycle?

Q2Does the decorrelation mechanism (β₃=0.34) hold when both products share one base model family, where error correlation should be much higher?

Q3What is the knowledge layer's marginal contribution? A memory on/off ablation across the 12-iteration deployment would isolate how much proposal quality comes from persisted negative results.

Q4Could a cheap offline probe predict doomed runs (DPO −35.9%, focal-reweighting null) before GPU-hours are burned — a veto gate inside the EOP?

Q5Would the extra plan-merge budget buy more end-to-end NDCG per GPU-hour if spent on diverse candidate proposals instead of deeper plan merging?

Q6Does per-step context injection's late-phase edge (+10.4 EA) persist with a simplified runtime state machine — or is it compensating for context crowding a better summarizer would remove?
