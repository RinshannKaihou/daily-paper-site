> **一句话总结：** 提出 Gödel Forest——用多个各自维护持久搜索树、并通过共享"演化记忆"（排行榜 + 约100 token 结构化经验教训）异步协同的多智能体框架来做数据中心的递归自我改进（直接生成数据并 LoRA 微调 Qwen3.5-35B-A3B-Base），在 RSIBench-Data 六个基准上平均比单智能体基线高 10.70 个百分点（SWE-bench Verified 35.00%→54.00%），且五个基准上墙钟时间更短；消融显示共享记忆贡献 +7.00 个百分点。

> **TL;DR:** Gödel Forest tackles data-centric recursive self-improvement (RSI) — agents generate training data, fine-tune a fixed base model (Qwen3.5-35B-A3B-Base with LoRA), and evaluate on downstream tasks — where a single search agent stagnates in narrow directions and naive parallel search wastes compute. It runs K=3 workers, each cultivating a persistent search tree with diagnostic-gated evaluation, coordinated only through a shared memory of a verified-utility leaderboard plus ~100-token distilled "lessons" (read-evolve-publish, no raw trace sharing). Against a vanilla Claude Code (Sonnet-5) single-agent RSI baseline, it gains +10.70 pts on average across six RSIBench-Data benchmarks — e.g., SWE-bench Verified 35.00%→54.00% (+19.00) and Terminal-Bench 2.0 5.62%→17.98% — while finishing faster on five of six benchmarks (SWE-bench Multilingual 14.20h→11.02h). The ablation is the strongest part: three independent workers without shared memory reach only 47.00% on SWE-bench Verified at comparable budget ($421.63), so co-evolution itself is worth +7.00 pts.

## 核心贡献
- **形式化"数据中心 RSI"的搜索问题**：把自我改进建模为在数据策略空间上的树搜索——每个候选 agent 是一段数据合成/筛选程序，执行后生成数据 D_a、从固定基座 LoRA 训练出 θ_a、在下游基准上评估效用 U(a)。指出训练在环（training-in-the-loop）验证昂贵，导致"深度 vs 广度"两难：单树易陷入路径依赖的窄方向，朴素并行或共享完整执行轨迹要么重复失败要么上下文爆炸。
- **提出 Gödel Forest 多智能体协同演化框架**：局部深度上，每个 worker 维护一棵持久搜索树和证据台账，走"诊断→提案→验证（诊断子集门控，先在小子集上筛掉不可行候选再跑全量评测）→复盘（继续/改超参/回溯祖先节点）"四阶段认知循环；全局广度上，K 棵树各自探索数据组合空间的不同区域。
- **异步共享演化记忆**：协调不靠共享原始轨迹，而靠 (a) 全局排行榜 Λ（汇总所有通过全量评测的已验证效用）与 (b) 结构化经验教训 L（每条约 100 token，形如 ⟨意图假设, ΔU, 归因, 可执行规则⟩）。负教训充当"归纳护栏"剪掉同伴树上已证伪的路径，正教训充当"催化种子"启发新方向；读写均为拉取式、非阻塞、无全局同步屏障。
- **实证验证**：在 RSIBench-Data 六大基准（SWE-bench Verified/Multilingual/Pro、Terminal-Bench 2.0、GPQA Diamond、AIME 2026）上全面超越单智能体基线，平均 +10.70 pts，且 5/6 基准墙钟时间更短；消融证明共享记忆协同贡献 +7.00 pts，worker 数 K=3 是性能-成本 Pareto 最优。

## Key Contributions
- Formalizes **data-centric RSI as open-ended tree search** over data strategies and identifies the core tension: under expensive training-in-the-loop validation, single-agent search lacks breadth while naive parallelism or raw-trace sharing sacrifices depth or bloats context.
- Proposes **Gödel Forest**, an ensemble of K co-evolving search trees: each worker autonomously deepens its persistent tree via a Diagnose→Propose→Validate (diagnostic-subset gating to prune weak candidates before full evaluation)→Review loop, while trees coordinate asynchronously through a **shared evolution memory** = global leaderboard (outcome anchor) + distilled structured lessons (~100 tokens each), replacing heavy trace exchange.
- Demonstrates **consistent gains across six RSIBench-Data benchmarks** (+10.70 pts average over the single-agent baseline), lower wall-clock time on 5/6 tasks, cross-backbone generality (Codex gpt-5.6-sol instantiation), and a controlled ablation isolating a **+7.00-pt contribution from shared-memory co-evolution** over equally-budgeted independent workers.

## Methodology
- **Problem setup.** Each archived agent a is a data-engineering program: (D_a, λ_a) = Generate(a); θ_a = Train(θ_0; D_a, λ_a); U(a) = Eval_B(θ_a). All candidates start from the same fixed base model Qwen3.5-35B-A3B-Base (LoRA SFT via the Tinker backend), so recursion lives in the agent's evidence-driven evolution of data strategies, not in the initial weights.
- **Persistent tree search (local depth).** Worker i ∈ {1..K} keeps a private tree T_i and evidence ledger H_i and runs a four-stage cognitive loop: (1) **Diagnose** failure modes of prior attempts (e.g., runaway completion, ungrounded actions); (2) **Propose** an evolved successor program a′ = Φ(a, H_i, M_t) conditioned on both private history and shared memory; (3) **Validate & Evaluate** — first evaluate on a worker-chosen diagnostic subset B_diag, and only if the gating threshold is passed proceed to full-benchmark evaluation with the same checkpoint (early pruning of unviable candidates); (4) **Review** — decide to exploit, revise hyperparameters, or backtrack to an ancestor node.
- **Shared evolution memory (global coordination).** Memory M_t = (Λ_t, L_t): a leaderboard of all fully-evaluated utilities, plus distilled lessons t = ⟨H_intent, ΔU, Attribution, ρ⟩ (~100 tokens) that decouple actionable takeaways from execution logs. The Read-Evolve-Publish loop is pull-based and non-blocking: workers retrieve lessons relevant to their current failure symptoms; negative lessons act as inductive guardrails, positive ones as catalytic seeds.
- **Budgets and infrastructure.** Each forest run is governed by a 16-hour wall-clock limit and a $500 cumulative Tinker budget. Claude Opus 4.8 serves as the external rollout generator; SWE-bench suites run under Mini-SWE-Agent in isolated E2B sandboxes via Harbor. After search, the selected checkpoint θ_r is frozen and officially re-evaluated in an isolated canonical run (S_off = Eval_off(θ_r)).
- **Baselines.** Primary baseline: vanilla Claude Code with Sonnet-5 acting as a single-agent data-centric RSI search (same underlying tasks, no forest coordination, no shared memory). Generality check: Gödel Forest instantiated with OpenAI Codex (gpt-5.6-sol) and Claude Code at high reasoning effort. Ablations on SWE-bench Verified: K ∈ {1,2,3,4} with full shared memory, and "3 Indep." (three concurrent workers without shared memory) at comparable budget.

## Results & Highlights
- **Universal gains over the single-agent baseline (Claude Code + Sonnet-5, Table 1):** SWE-bench Verified 35.00% → 54.00% (+19.00 pts); SWE-bench Multilingual 22.00% → 30.00% (+8.00); SWE-bench Pro 4.00% → 15.00% (+11.00); Terminal-Bench 2.0 5.62% → 17.98% (+12.36); GPQA Diamond 52.00% → 55.00% (+3.00); AIME 2026 49.17% → 60.00% (+10.83). Average absolute gain: +10.70 pts.
- **"Efficiency paradox" — faster despite broader search:** wall-clock time drops on 5/6 benchmarks (SWE-bench Multilingual 14.20h → 11.02h; SWE-bench Pro 9.54h → 7.49h; GPQA 6.43h → 5.76h; AIME 9.29h → 8.61h; SWE-bench Verified 14.91h → 14.06h), attributed to parallel execution plus negative lessons letting workers prune dead ends before committing training cycles. The exception is Terminal-Bench 2.0 (8.87h → 15.50h).
- **Cost is honestly reported as higher on long-horizon agentic tasks:** cumulative Tinker expenditure rises from $45.63 to $419.87 on SWE-bench Pro (~9x) and from $156.93 to $295.06 on Terminal-Bench 2.0, while it falls on AIME 2026 ($121.21 → $49.94) and GPQA ($16.03 → $15.22). The authors attribute this to evolved models sustaining coherent multi-turn trajectories instead of crashing/terminating early like the baseline.
- **Cross-backbone generality (Codex gpt-5.6-sol, Figure 2):** SWE-bench Verified 33.00% → 44.00% (+11.00 pts, wall-clock 6.81h vs 4.41h); Terminal-Bench 2.0 20.22% → 23.60% (+3.38 pts, 9.85h vs 9.56h), with cost $319 vs $55 and $214 vs $69.
- **Ablation (SWE-bench Verified, Figure 3):** K=1: 45.00%; K=2: 51.00%; K=3: 54.00%; K=4 plateaus at 54.00% but costs 15.80h / $404.43 — K=3 is the Pareto point. Crucially, "3 Indep." (three workers, no shared memory) reaches only 47.00% at comparable budget ($421.63, 13.38h), isolating a +7.00-pt effect for co-evolving shared memory over naive parallelism.
- **Mechanism case study (Figure 5):** Lesson #1 — dense all-turn supervision degrades termination tokens; masking loss to the final assistant turn restored stable termination, and a peer worker adopted it via shared memory, jumping from near-zero to 22%. Lesson #2 — final-turn supervision starves intermediate verification actions of learning signal; prefix-truncated pseudo-terminal trajectories fixed this and produced the 55% in-run peak that earned final checkpoint selection.

## Critical Assessment
- **The evaluation is self-benchmarked.** Six of the authors published RSIBench-Data (ref [9]), and all six benchmarks in Table 1 come from it; the "official score" S_off is post-selection verification on the same benchmark identities used for search selection — the paper itself notes it is "rather than a held-out generalization benchmark." So the headline +10.70 pts measures selection on benchmarks the system is explicitly optimized against, with no held-out transfer result.
- **No variance / single-run results.** Every cell in Table 1 and Figure 3 is a single run with no seeds, error bars, or confidence intervals. The GPQA Diamond gain (+3.00 pts, 52.00%→55.00%) is on a ~200-question benchmark — plausibly within run-to-run noise — yet it is folded into the +10.70 average. Similarly, AIME 2026 has very few problems, so 49.17%→60.00% moves a handful of items.
- **Budget asymmetry is under-analyzed.** The +10.70 average coexists with up to ~9x higher compute cost (SWE-bench Pro: $419.87 vs $45.63) and ~2x wall-clock on Terminal-Bench 2.0. The "efficiency paradox" framing leans on 5/6 tasks; the cost discussion reframes extra spend as a "capability artifact," which is plausible but conflates capability with resource use — a compute-matched comparison exists only in the K-ablation, not against the vanilla baseline.
- **Missing ablations on the recipe itself.** The lesson format (~100-token structured schema), the diagnostic gating threshold (chosen autonomously by the worker LLM — risk of overfitting to B_diag is never quantified), and the choice of Claude Opus 4.8 as rollout generator are each load-bearing but un- ablated. K=3 optimality is established only on SWE-bench Verified and may not transfer to the other five benchmarks.
- **Baseline strength.** The comparison is a vanilla single Claude Code agent, not strong prior data-centric RSI or multi-agent systems the paper cites (AutoData, PosttrainBench, Mendel Gödel Machine, Huxley Gödel Machine) — none are numerically compared. The main model is also only LoRA-tuned on one base model (Qwen3.5-35B-A3B-Base); whether the pipeline survives full fine-tuning or larger backbones is untested.
- That said, the **3-Indep. ablation is genuinely well-controlled** (matched $421.63 budget and 13.38h), and the paper is commendably honest about time and cost regressions on Terminal-Bench 2.0 and SWE-bench Pro.

## Strengths
- The **depth-breadth decomposition is clean and well-motivated**: persistent per-worker trees secure long-horizon refinement; a leaderboard + tiny distilled lessons give breadth without the context bloat of trace sharing (MGM-style coordination is the explicit strawman).
- The **coordination ablation directly tests the central claim**: equal-budget 3-Indep. (47.00%) vs Gödel Forest (54.00%) shows the +7.00 pts comes from collective distillation, not from parallel compute.
- **Diagnostic gating** (evaluate on a worker-chosen subset before committing full-benchmark evaluation) is a practical mechanism for the training-in-the-loop cost problem, and the Figure 5 case study concretely shows lessons propagating across workers (0% → 22% via Lesson #1).
- **Honest negative reporting**: higher cost on SWE-bench Pro/Terminal-Bench 2.0 and slower completion on Terminal-Bench 2.0 are stated plainly rather than hidden.
- Cross-backbone replication with a different frontier agent (Codex gpt-5.6-sol) reduces the chance that results are an artifact of one agent harness.

## Limitations
- All gains are measured on the authors' own RSIBench-Data suite with selection and evaluation on the same benchmark identities; no held-out generalization or transfer benchmark is reported.
- Single run per configuration, no variance estimates; small-n benchmarks (GPQA Diamond, AIME 2026) make the smaller deltas (+3.00, +10.83) statistically fragile.
- Compute-matched comparison against the vanilla baseline is absent; Gödel Forest spends up to ~9x more training/eval compute on some tasks, and Terminal-Bench 2.0 takes nearly 2x longer.
- Only LoRA SFT on one 35B-A3B base model; the K=3 optimum, gating thresholds, and lesson schema are validated only on SWE-bench Verified and are not ablated elsewhere.
- Worker autonomy in choosing B_diag and the gating threshold introduces unquantified selection-pressure risk (optimizing the diagnostic subset rather than the true objective).
- Coordination quality depends on the rollout generator LLM's ability to write correct lesson attributions; failure modes of wrong lessons propagating forest-wide are not analyzed.

## Questions for Further Exploration
- Do the +10.70-pt gains transfer to a held-out benchmark not in the selection loop, or to full fine-tuning and larger base models?
- How robust is the forest to a single poisoned or wrong lesson — can one worker's mis-attributed failure guardrail collapse peer trees? Is there a mechanism for lesson verification or expiry?
- Is K=3 optimal on the other five benchmarks, and how does the Pareto frontier shift with cheaper training backends (e.g., full-epoch LoRA cost curves)?
- Can the ~100-token lesson schema be made machine-verifiable (e.g., replayable counterfactual checks) rather than trusting the rollout LLM's attribution?
- How does Gödel Forest compare head-to-head against Mendel/Huxley Gödel Machine or AutoData under matched compute, rather than only against a vanilla single-agent baseline?
