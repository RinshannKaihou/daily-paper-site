> **一句话总结：** 针对"硬件可继续运行故障"（HOF：显存不可纠错误、瞬时网络中断等硬件无需重置即可复用的情况），UT Austin 提出容错训练系统 Leto：用主机内存两阶纠删的 Resilient Memory Pool 原位保留模型/进程状态、用块级事务的 Resumable Model Updater 保证原地优化器更新的崩溃一致性、用可被运行时回收的 shadow trainer 预初始化 CUDA/NCCL 状态，从而在故障后由 shadow 原位接管而非重载检查点；在 72×A100 集群、5 个模型（Qwen 4.0B ~ Kimi-MoE 49.4B）、每 10 分钟注入一次 HOF 下，恢复时间 6–19 秒，比最快的内存检查点基线（Gemini+）快 3.6–6.5×，ETTR 最高提升 13.7 个百分点（Kimi-MoE 94.2% vs 80.5%），而稳态开销仅 0.6–0.8%；模拟显示 131,072 卡跑 DeepSeek-V4（1.6T 参数）时仍能保持 95–96% 的有效训练时间。

> **TL;DR:** Leto is a fault-tolerant LLM training system that recovers from hardware-operable failures (HOFs — contained HBM errors, transient network faults) *in place* on the surviving hardware instead of reloading checkpoints. It keeps model/process state recoverable outside the failed trainer (a Resilient Memory Pool with two-tier Reed–Solomon erasure coding in host memory), makes in-place optimizer updates crash-consistent via chunk-level transactions (Resumable Model Updater), and pre-initializes CUDA/NCCL process state in a shadow trainer whose GPU memory can be reclaimed at OOM time. On five workloads (Qwen 4.0B to Kimi-MoE 49.4B) on 72 A100s with one HOF every 10 minutes, Leto recovers in 6–19 s — 3.6–6.5× faster than the best of Gemini+, MoEvent+, and JIT-Ckpt+ — and lifts productive training time (ETTR) by 1.5–13.7 percentage points (Kimi-MoE: 94.2% vs Gemini+'s 80.5%), at only 0.6–0.8% steady-state overhead. Fatal failures (dead hardware) still fall back to conventional checkpointing.

## 核心贡献

- **问题重定义：** 把训练故障分成"硬件可继续运行故障"（HOF，如被 ECC 控制器隔离的显存不可纠错误、瞬时链路中断——ByteDance 19 个生产训练作业中 22.7% 的故障、另一项 256-GPU 研究中 73% 的故障都属于此类）和"致命故障"（FF），并指出对 HOF 而言检查点重载 + 重算 + 进程重建是纯浪费：幸存硬件上的工作模型状态和可复用进程状态本可以被直接接管的进程重用。
- **Resilient Memory Pool（RMP）+ 两阶纠删保护：** 用 GPU 虚拟内存 API 把保留状态组织成 2 GiB 保护组（1024 个 2 MiB HBM 页 + 16 个一阶校验页 + 1 个二阶校验页），校验页全部放主机内存——若把一阶校验放 HBM，Kimi-MoE 规模需额外 256 MiB 显存（两阶并发容错需 1 GiB）；一阶容忍每组 16 个 HBM 页失效，二阶保护一阶校验本身，超出容忍度才回退检查点。
- **Resumable Model Updater（RMU）：** 利用现代优化器逐元素/逐层更新的可交换性和 RS 线性码"更新校验即更新数据校验"的性质，把每次模型更新做成**块级（chunk-level）事务**：undo 缓冲保存更新前状态、parity 缓冲编码最后已提交块的校验、主机内存小标记记录进度——HOF 打断更新后从最近提交块边界恢复，无需全模型快照，故障空闲迭代开销仅 0.6%（快照 strawman 为 +5.7%~+6.3%），且复用反向传播结束后的激活内存，不增加峰值显存。
- **可回收预初始化（Preinitialization Controller）：** 同节点 shadow trainer 预先构建 CUDA context（494 MiB）、NCCL communicator（1,512 MiB）、运行时模块（196 MiB）共约 2.2 GiB 进程状态（OLMoE 配置），并在 PyTorch CUDACachingAllocator 中挂 OOM 回调——主动训练需要显存时按 L1/L2/L3 三级逐级降级回收 shadow，既保住预初始化收益又不引发训练 OLMoE 式 OOM。
- **系统实现与评估：** 基于 Megatron-Core v0.13.1 + PyTorch 2.8.0 + NCCL 2.27.3，约 7.8K 行 Python + 2.4K 行 C++/CUDA（承诺开源）；在 72×A100-40G（AWS）和 12×A100-80G 集群上对 5 个稠密/MoE 模型评估，配合经校验（迭代时间预测误差 ≤3.1%）的模拟器外推到 131K GPU 规模，并验证恢复后训练 loss 与无故障参考逐位一致。

## Key Contributions

- **Reframes HOF recovery as state retention, not state rebuild:** for failures where hardware survives (22.7% of failures in ByteDance's 19-job study; 73% in a 256-GPU study), Leto retains the working model state and reusable process state on the surviving hardware so a replacement trainer can attach to them directly — skipping checkpoint loading, recomputation of completed iterations, and process-state setup (35 s init + 53 s recompute for Gemini+ on Kimi-MoE, 88 s total).
- **Resilient Memory Pool (RMP) with two-tier erasure protection:** partitions retained GPU state into 2 GiB protection groups (D=1024 HBM pages of 2 MiB, H1=16 first-tier and H2=1 second-tier parity pages), storing all parity in host memory so persistent redundancy costs zero scarce HBM (the naive in-HBM design would add 256 MiB for Kimi-MoE's model state, 1 GiB for tolerating two concurrent failures). Tier 1 survives up to 16 failed HBM pages per group; tier 2 repairs a failed first-tier parity page; beyond tolerance Leto falls back to checkpointing.
- **Crash-consistent in-place updates without snapshots:** the Resumable Model Updater (RMU) exploits element-wise/layer-wise commutative optimizer updates plus linear Reed–Solomon codes (updating a chunk delta updates the group parity with the same delta) to commit model state and parity together in chunk-level transactions with an undo buffer — recovering from mid-update HOFs at the last committed chunk boundary at only 0.6% fault-free iteration overhead (Table 1: 12,693 ms vs 12,663 ms reference on OLMoE, vs +6.33% for synchronous and +5.7% for asynchronous snapshotting), reusing activation memory so peak HBM usage does not grow.
- **OOM-free shadow preinitialization:** a preinitialization controller builds CUDA contexts + NCCL communicators + runtime modules (≈2.2 GiB on OLMoE; 494 MiB + 1,512 MiB + 196 MiB) in a same-node shadow trainer, and integrates an OOM callback into PyTorch's CUDACachingAllocator so the shadow is torn down at levels L1/L2/L3 and its memory reclaimed when the active trainer needs it — preserving fast recovery (26–27 s from L3, 33–34 s from L2, 52 s from L1) without causing training OOMs (Figure 7 shows the naive shadow crashing the active trainer at 177 s).
- **Comprehensive evaluation:** 72×A100 (AWS, 9 nodes) + 12×A100-80G testbeds, five dense/MoE models (Qwen 4.0B, OLMoE 6.9B/1.3B-active, DeepSeek-MoE 16.4B, GPT-MoE 20.9B, Kimi-MoE 49.4B/3.1B-active), three checkpointing baselines with sparse variants (Gemini/+, MoEvent/+, JIT-Ckpt/+), plus a profile-based simulator (iteration-time prediction error ≤3.1%, mean 2.18%) extrapolating to DeepSeek-V2/V3/V4 at 1K/16K/131K GPUs.

## Methodology

**System model and goals.** Leto targets hardware-operable failures (HOFs): a trainer process terminates or hangs but its GPU/node remains operable (contained uncorrectable HBM errors that retire pages without resetting the device; transient network outages that hang collectives). Fatal failures (FFs) are delegated to existing checkpointing (Gemini+/JIT-Ckpt+ depending on workload). Design goals: exact recovery (deterministic re-execution), minimal steady-state overhead, minimal GPU memory overhead. Each active trainer is paired with a lightweight *state manager* (owning retained state) and a *shadow trainer* (pre-initializing process state) on the same node.

**Resilient state retention (RMP).** RMP is a memory-management component in each state manager that owns allocations for retained model and process state. Protection groups hold D=1024 HBM data pages (2 MiB each, matching A100 virtual-memory granularity) with H1=16 first-tier parity and H2=1 second-tier parity, both resident in host memory; Reed–Solomon coding over GF(2^32) with carry-less multiply (clmul) instructions, tiled asynchronously with pipelining to maximize throughput. The separation exploits the insight that retained data and its redundancy need not live in the same memory — keeping parity in HBM would consume 256 MiB of training memory for Kimi-MoE (and 1 GiB for two-failure tolerance). Trainers touch retained state without pointer dereference: RMP allocates HBM pages, maintains allocation/failure metadata, and remaps failed pages. After a HOF, RMP localizes faults by recursively bisecting regions returning EHWPOISON on madvise, cross-checking with cuPointerGetAttribute; the promoted trainer then reconstructs protected pages from parity (second-tier parity first repairs missing first-tier parity, then first-tier parity rebuilds failed HBM pages).

**Crash-consistent model updates (RMU).** An iteration interrupted mid-update leaves model state and parity partially updated and inconsistent across ranks. RMU partitions each protection group into chunks; during the update phase, each chunk's pre-update value is preserved in an *undo buffer* and a *parity buffer* encodes RS-parity of the latest committed chunk. Committing a chunk atomically swaps model, undo, and scratch buffers; a host-memory marker (updated by lightweight CUDA kernels in-stream) records the last committed boundary. During compute, gradients are RS-encoded per chunk before the global synchronization so all ranks' gradients are recoverable before any model state changes. Recovery resumes each rank from its last committed chunk; uncommitted chunks are restored from the undo buffer, and ranks re-finish the interrupted update. The whole scheme adds 0.6% to fault-free iteration time because chunk commits overlap with propagation and buffers reuse activation memory.

**OOM-free preinitialization.** The shadow trainer pre-creates the replacement trainer's process state for the same GPUs/rank: CUDA context, NCCL communicators (the dominant cost: 1,512 MiB of OLMoE's ~2.2 GiB footprint), and runtime-loaded modules. Because dynamic memory pressure (e.g., MoE routing imbalance) can make a fully preinitialized shadow evict the active trainer into OOM, a *preinitialization controller* with three levels (L1: before GPU state creation; L2: after CUDA context, before NCCL; L3: fully preinitialized) is integrated into the allocator: when a training allocation fails, the OOM callback synchronously terminates the shadow at its current level, releases its GPU memory, and the allocator retries. After each HOF, the replacement shadow re-adopts the highest level fitting the observed peak headroom.

**HOF recovery workflow.** On failure, the state manager marks inaccessible pages; surviving shadows complete deferred initialization and take over the failed rank, reattaching to retained state; RMU rebuilds any failed protected pages from parity and resumes from the committed chunk boundary; demoted active trainers re-initialize as new shadows. FFs fall back to the existing checkpoint path unchanged.

**Implementation and evaluation protocol.** Megatron-Core v0.13.1, PyTorch 2.8.0, NCCL 2.27.3; ~7.8K lines Python, 2.4K lines C++/CUDA. Fault injection: SIGKILL to the target rank (detection <1 s); memory faults emulated by unmapping 16 HBM pages per group (cuMemUnmap) and poisoning host parity pages (madvise MADV_HWPOISON); mid-kernel interruption via an NVBit-instrumented kernel writing random values to its destination. Metric: ETTR (fraction of wall-clock time spent in productive training) and recovery time (failure detection to pre-fault progress). A profile-based simulator (validated: iteration-time MAPE 2.18%; ETTR prediction errors 3.1%/0.7% vs measurements) extends results to 1,024–131,072 GPUs.

## Results & Highlights

- **End-to-end ETTR on 5 workloads (72×A100, one HOF every 10 min):** Leto sustains 91–98% ETTR, exceeding each workload's best baseline (Gemini+, MoEvent+, or JIT-Ckpt+) by 1.5–10.4 percentage points, and recovers in 6–19 s — 3.6–6.5× faster than the fastest baseline for each workload (Figure 8). All baselines rebind to checkpoints and replay lost work; Leto replays at most the interrupted iteration.
- **Kimi-MoE (49.4B) recovery breakdown (Table 3):** at checkpoint interval 11, Leto recovers in 19 s (15 s init + 5 s recompute) for 91.0% ETTR, vs Gemini+ at 88 s (35 s + 53 s) / 80.5% and Gemini at 127 s / 74.1% — a 4.5× recovery speedup over Gemini+ at identical checkpoint cost. Extending Leto's interval to 32 cuts recovery to 16 s and raises ETTR to 94.2% (+13.7 pp over Gemini+'s peak at its tuned interval of 5).
- **Checkpoint-interval sensitivity (Figure 9):** because Leto recovers HOFs without rollback, longer intervals help it: ETTR rises from 93.8% to 95.8% on OLMoE (interval 5→16) and from 91.0% to 94.2% on Kimi-MoE (11→32), while Gemini+ peaks at 84.5% and 80.5% at interval 5 — Leto exceeds the baseline's peak by 11.3 and 13.7 pp.
- **Steady-state overhead is negligible:** fault-free OLMoE iteration is 12,693 ms with RMU vs 12,663 ms reference (+0.6%), vs +6.33% (sync snapshotting) and +5.7% (async) for the strawman crash-consistency designs (Table 1); overall steady-state cost is 0.8 pp of ETTR. At a 0% HOF ratio, simulated Leto trails Gemini+ by only 0.3 pp.
- **HOF-ratio sweep (Figure 10, OLMoE):** at 100% HOFs Leto reaches 95.8% ETTR (interval 16) vs Gemini+'s 83.3%-ratio-tuned 83.7%→ beats it by 3.5 pp even over the baseline's best case; with only 0.8 pp steady-state overhead.
- **Realistic failure trace:** replaying 8 evictions from a public GCP A100 spot-instance trace over 80 minutes (4 HOFs + 4 FFs), Leto achieves 91.2% ETTR vs Gemini+'s 86.6%, cutting total recovery time from 7.8 to 4.6 minutes; HOF recovery averages 11 s (Leto) vs 37 s (Gemini+).
- **Under memory pressure (Figure 13):** with reclamation forcing L3→L2→L1 transitions, every HOF recovery still goes through a preinitialized shadow (26–27 s from L3, 33–34 s from L2, 52 s from L1) and Leto reaches 91.8% ETTR — 4.1 pp above Gemini+ with reclamation — never rolling back to a checkpoint.
- **Correctness and fault handling:** RMP localizes an injected memory fault in 36 ms and RMU reconstructs failed pages in 140 ms; training loss after every injected HOF reproduces the fault-free reference exactly (Figure 12), whereas RMP alone (without RMU) diverges and goes NaN after the first mid-update HOF.
- **Large-scale simulation (Figure 14):** at a 10-minute MTTF on DeepSeek-V2 (236B, 1,024 GPUs), DeepSeek-V3 (671B, 16,384 GPUs), and DeepSeek-V4 (1.6T total/49B active, 131,072 GPUs), Leto sustains 95–96% ETTR at 100% HOFs vs 83.0–85.3% for Gemini+; at 50% HOFs the gain is 3.4–3.5 pp; at 0% HOFs Leto trails by 0.3 pp.

## Authors & Credibility

All three authors are at The University of Texas at Austin. Geon-Woo Kim and Joon Ha Kim are PhD students; Daehyeok Kim leads the effort and has an established systems-research track record. The group has clearly worked this problem space before: their own prior works are cited, including a study characterizing GPU resilience on Hopper and Ampere hardware ("Story of Two GPUs", p3-14), Hopper-based heterogeneous in-training checkpointing, and a configuration-agnostic profiling simulator for LLM inference (the evaluation's simulator builds on that lineage, with a dedicated appendix validating its accuracy). The paper is a full experimental systems paper with a working ~10K-line implementation on Megatron/PyTorch/NCCL, multi-cluster experiments, trace replay, and a quantitatively validated simulator — strong credibility for the claims made at testbed scale. The authors state the implementation and the simulator will be open-sourced, which if delivered substantially aids reproducibility.

## Critical Assessment

**Novelty:** genuine and well-positioned. The systems literature on LLM fault tolerance (Gemini, MoEvent, JIT-Ckpt, CheckFreq, ByteCheckpoint, Bamboo) all treats recovery as *state rebuild from checkpoints or redundant computation*; Leto's premise — that HOF-class failures leave the state on the GPU itself recoverable, and that process state can be prepared *before* the failure on hardware that is already assigned — is a legitimately new angle, and the three mechanisms (host-parity erasure coding for HBM-resident training state, chunk-level transactional optimizer updates, reclaimable shadow preinit) are each non-trivial designs, not engineering tweaks. The RMU observation that linear RS codes let parity track in-place commutative updates at delta cost is the cleverest piece.

**Rigor:** above average for the area. The baselines are the actual state of the art (Gemini+, MoEvent+, JIT-Ckpt+ — sparse variants included, intervals tuned per workload), five workloads spanning 4B–49.4B parameters, bit-exact correctness verification (loss curves), an NVBit-based mid-kernel fault injection that is more realistic than pure SIGKILL, sensitivity sweeps over checkpoint interval, HOF ratio, and memory pressure, and honest reporting of the 0% HOF case where Leto *loses* 0.3 pp.

**Weaknesses and red flags.** First, the headline 131,072-GPU / DeepSeek-V4 claims rest entirely on simulation: the simulator is validated only for iteration time and ETTR on a 72-GPU testbed, and its ETTR model assumes independent, uniformly arriving failures with no overlap — correlated rack/network-level failures at 100K-GPU scale, which is precisely where large clusters fail differently, are unmodeled. Second, the fault model is synthetic: HBM faults are emulated by unmapping exactly 16 pages per protection group (the maximum the code tolerates) — real ECC failures arrive at DRAM-row granularity, can be bursty and recurring on aging GPUs, and the paper has no experiment with hardware-actual injected errors, so the 36 ms/140 ms fault-handling numbers and the "never falls back to checkpoint" claim are untested against realistic fault distributions. Third, the entire value proposition is conditional on the HOF share: the motivating 22.7% (ByteDance) and 73% (256-GPU study) figures come from other people's clusters, and at 0% HOFs Leto is strictly worse than plain Gemini+. Fourth, portability: the implementation is deeply tied to NVIDIA/CUDA internals (cuPointerGetAttribute, virtual-memory APIs, CUDACachingAllocator OOM callbacks, NCCL) and A100 40GB; the OOM-callback coupling to PyTorch allocator internals is exactly the kind of thing that breaks across framework versions. Fifth, runs are 30 minutes with one injected failure — long-horizon effects (parity-page accumulation of faults on the same ranks, shadow preinit churn across many failures) are unobserved. None of these invalidate the testbed results, but the abstract's framing ("large-scale simulation shows over 95%...") leans on the least-validated part of the evaluation.

## Strengths

- Large, honest wins at testbed scale: 3.6–6.5× faster recovery than the strongest available baselines across all five workloads with 1.5–13.7 pp ETTR gains, achieved at 0.6–0.8% steady-state cost — the overhead/results trade is exceptional for a fault-tolerance layer.
- Two-tier host-memory erasure coding solves the "where does redundancy live" problem without touching scarce HBM, and the paper quantifies the avoided cost (256 MiB–1 GiB on Kimi-MoE) rather than hand-waving it.
- RMU achieves crash consistency for in-place optimizer updates without full-model snapshots, at 10× lower overhead than snapshot strawmen, with a bit-exact recovery guarantee verified empirically.
- The preinit controller's L1/L2/L3 reclamation design addresses the real OOM interaction between shadow state and dynamic MoE memory pressure, with measured per-level recovery costs.
- Unusually complete evaluation practice: tuned baselines, both failure classes, a public spot-eviction trace, correctness verification against the fault-free reference, and a simulator with published prediction-error numbers.
- Compatible-by-construction with existing checkpointing for fatal failures, and the authors commit to open-sourcing both the system and the simulator.

## Limitations

- **HOF-conditional benefit:** fatal failures (actual hardware death) still take the legacy checkpoint path; the system's value scales directly with the HOF ratio, which is infrastructure-dependent (22.7% at ByteDance vs 73% in the smaller study) and unknown for most operators. At zero HOFs, Leto is 0.3 pp worse.
- **Scale claims are simulated:** real experiments top out at 72 A100s (9 nodes); the 16K–131K GPU results inherit the simulator's assumptions of independent, uniformly distributed, non-overlapping failures.
- **Synthetic fault model:** memory faults are emulated at the tolerance boundary (16 pages/group via cuMemUnmap/madvise) rather than with real HBM ECC events; behavior under bursty, row-granular, or recurring faults — and how often the checkpoint fallback triggers in practice — is not measured.
- **Hardware/software specificity:** NVIDIA A100 + CUDA UVM + NCCL + Megatron only; no AMD/TPU/newer-NVIDIA results, and the PyTorch allocator OOM-hook coupling is fragile across versions.
- **Recovery time is memory-dependent:** under pressure, shadow state may only reach L1, and recovery degrades to 52 s (still fast, but 3× the 16–19 s headline); on 40 GB-class parts the reclaim/re-adopt cycle will be a regular occurrence.
- **Short runs:** 30-minute evaluations with one scheduled failure each; multi-day behavior (parity fault accumulation, shadow lifecycle churn, interaction with real scheduling systems) is unexplored.

## Questions for Further Exploration

- How does the two-tier RMP scheme behave under realistic HBM ECC fault distributions — bursty row-granular failures, recurring faults on aging GPUs — and how often does the checkpoint fallback trigger in production, where the 16-pages-per-group tolerance is the cliff edge?
- Since RMP recomputes parity from retained state on every update, could parity mismatch be repurposed as a *silent data corruption* (SDC) detector for bit flips that ECC fails to catch, rather than only handling reported uncorrectable errors?
- Would the design port to H100/Blackwell (MIG partitioning, larger HBM reducing memory pressure) or non-NVIDIA stacks, given the dependence on CUDA virtual-memory APIs, CUDACachingAllocator internals, and NCCL?
- The simulator assumes independent uniform failure arrivals and no overlap — how do correlated failures (rack power events, network fabric incidents) at 100K-GPU scale change the 95–96% ETTR conclusion, and can the state-retention idea survive a top-of-rack switch failure that partitions ranks?
- What is the real-world HOF ratio across clusters beyond ByteDance's 22.7% figure — is in-place recovery a niche optimization or the common case, and should orchestrators classify HOF vs FF automatically (the paper assumes the infrastructure already does this reliably)?
- Could retained in-place state enable verification of recovered state (e.g., replay the interrupted chunk and compare against parity) to guard against the fault having corrupted data silently before the page failed?
