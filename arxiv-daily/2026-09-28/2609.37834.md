> **一句话总结：** Meta 团队把 agent harness 的递归自改进搜索组织成多个并行分支——每个分支拥有各自演化的开发集子集和分支专属的提案引导策略，通过覆盖率投票动态转移"案例所有权"迫使分支特化，最后用一个仅在开发数据上训练的 LLM 路由器为每个新问题选择分支最优 harness——在 4 个 benchmark-model 设置上全面超越 Meta-Harness（如 IMO 级数学上 Gemini 3 Flash 从 46.0% 提升到 62.0%，相对提升 34.8%），且路由器在 Math-Gemini 上甚至超过了用测试集事后挑出的最优单 harness（62.0% vs 58.0%）。

> **TL;DR:** Prior harness-evolution systems like Meta-Harness evolve an LLM agent's scaffolding against a single fixed development set, risking a local optimum. This paper runs B=2 parallel search branches, each with its own evolving development subset (cases are pruned when every branch's frontier solves them, and re-owned by the branch whose frontier outperforms by a margin Δ=2) plus branch-specific proposal guidance updated every 5 iterations, then deploys a GEPA-optimized router that picks one branch head per new input using only development-derived evidence. On 200 held-out IMO-level math problems with Gemini 3 Flash, accuracy rises from Meta-Harness's 46.0% to 62.0% (+16.0 pts, +34.8% relative); on Terminal-Bench 2.0 it goes from 44.8% to 50.0% (+11.6% relative) over Meta-Harness and 43.1% for Terminus-KIRA; on SWE-bench Lite from 63.6% to 66.0%. The cost is honesty about compute: 1.5–2.2x Meta-Harness's token budget and no error bars.

## 核心贡献

- **动态开发集的分支化搜索**：将 harness 进化组织为 B=2 个并行分支，每个分支持有独立的开发集子集、候选历史与提案引导；通过"覆盖率投票 + 所有权边际 Δ=2"的确定性规则，删除所有分支前沿都能解决的案例、把相对优势案例划给领先分支，从而诱导分支特化而非单轨迹收敛。
- **分支专属提案自适应**：借鉴 SkillOpt，同一个提议者（Claude Opus 4.6）每 5 次迭代依据各分支的本地执行记录改写分支级 SKILL.md 引导文件，记录哪些修改有效并存活、哪些失败模式反复出现、哪些问题仍未解决。
- **开发信息驱动的专家路由**：部署时每分支保留一个开发集最优 head，路由器（由动作模型自身担任）基于 GEPA 优化后的指令、专家源代码和"仅被单一 head 解决"的开发案例，在执行前为每个新输入选择一个 head——全程不接触任何测试集结果。
- **无需测试集选择的可部署增益**：路由系统在全部 4 个 benchmark-model 设置上超越固定基线与 Meta-Harness；消融证明开发集剪枝与提案自适应必须联合启用（62.0%）才有效，单独启用分别为 54.0% / 50.0%（都不启用为 51.0%）。

## Key Contributions

- **Search with dynamic development subsets**: Multiple parallel branches adapt their development subsets based on cross-branch comparative performance (coverage votes over per-branch top-q=5 frontiers), encouraging complementary rather than redundant harnesses.
- **Branch-specific proposal adaptation**: A shared proposer maintains distinct branch-local guidance (SKILL.md) distilled from each branch's own successes, persistent failures, and unresolved problems.
- **Deployable expert routing**: A router selects among development-best branch heads before execution, trained only on head-exclusive development cases and expert source code — no test outcomes, no held-out leakage.
- **Improved benchmark performance**: The development-selected routed system outperforms fixed baselines and Meta-Harness across four settings spanning mathematical reasoning and agentic coding, with relative gains of 34.8% / 5.2% / 11.6% / 3.8%.

## Methodology

**Framing.** An agent's *harness* is the scaffolding around the action model — retrieval, tool interfaces, control flow, verification — and "harness optimization" is recursive self-improvement (RSI): agent-generated code modifications guided by execution feedback. Prior work (Meta-Harness, Lee et al. 2026) evolves harnesses with an agentic proposer (Claude Opus 4.6) against a *fixed* development set and *fixed* proposal instructions, constraining evolution to one trajectory prone to local optima.

**Branch-local search.** The method runs B=2 branches for N=20 iterations. Each branch b maintains its own development subset X_b (initialized to the full dev set), candidate population, execution filesystem, and proposal guidance S_b. Per iteration the proposer generates one candidate harness per branch; candidates are scored by mean task reward on X_b, and the branch head is the highest-scoring candidate.

**Development-driven subset evolution.** For each branch, a frontier F_b is the top-q (q=5) harnesses by mean reward on its current subset. Every C_p=1 iterations (once all branches have ≥q candidates), each dev case x gets a coverage vote per branch: c_b(x) = number of frontier harnesses in branch b that solve x. If every frontier in every branch solves x, the case is removed from all subsets (it no longer discriminates). A branch gains ownership of x when c_b(x) − max_{b'≠b} c_{b'}(x) ≥ Δ (Δ=2), and x is then removed from all other branches' subsets — preserving cases where a branch shows a relative advantage so it can specialize. Frontier membership is recomputed each update, so rankings can change even when implementations don't.

**Branch-specific proposal adaptation.** Every C_s=5 iterations, the same proposer P rewrites each branch's guidance S_b (a SKILL.md file) from recent execution records, using fixed update prompts (Appendix C) that treat individual scores as evidence about single implementations and require cross-iteration agreement before strong claims.

**Development-informed routing.** After search, one head per branch is kept (best mean reward on its final subset). Since dev scores across branches are not comparable, a router R — the action model itself — picks one head per new input before execution. R is built from head-exclusive development cases (solved by exactly one final head), receives the two experts' source code plus the case examples with both heads' outputs, and has its instruction optimized with GEPA. When both a subset update and a guidance update fall due, the subset update happens first.

## Results & Highlights

- **Math (200 held-out IMO-level problems, Gemini 3 Flash action model):** the routed system reaches **62.0%** vs **46.0%** for Meta-Harness (**+16.0 pts, +34.8% relative**) and **46.5%** for the strongest fixed baseline (BM25-geometry retrieval); no-memory / few-shot / BM25-all fixed baselines score 34.0 / 40.0 / 40.5. With Claude Sonnet 4.5 the gain is smaller: **30.5% vs 29.0%** Meta-Harness (+5.2% relative) and 27.0% BM25-geometry.
- **Terminal-Bench 2.0 (58 held-out tasks, Sonnet 4.5):** **50.0%** task completion vs **44.8%** Meta-Harness (**+5.2 pts, +11.6% relative**), beating the best fixed harness Terminus-KIRA at **43.1%** and Terminus 2 at 34.5%.
- **SWE-bench Lite (250 held-out tasks, Sonnet 4.5):** **66.0%** issue resolution vs **63.6%** Meta-Harness (+3.8% relative) and **62.8%** for mini-swe-agent.
- **Branch complementarity:** combined held-out coverage of the two heads exceeds the stronger individual head by **4.0–9.0 pts absolute** in all four settings (e.g., TB2 union 55.2% vs head2 48.3%; SWE union 70.4% vs 66.4%; Math-Gemini union 67.0%).
- **Router vs heads:** routing exceeds the stronger development-selected head by **+4.0 pts on Math-Gemini (62.0 vs 58.0)** and **+1.7 on Terminal-Bench 2.0 (50.0 vs 48.3)**, but falls short by 0.5 (Math-Sonnet) and 0.4 (SWE). On Math-Gemini it recovers 12/18 (66.7%) of Branch-1-only and 18/22 (81.8%) of Branch-2-only exclusive successes (75% overall), leaving a 5.0-pt gap to union coverage.
- **Test-best analysis:** evaluated on test, the best of 10 pooled harnesses per method gives Meta-Harness 49.0 on Math-Gemini (a +3.0 selection gap over its dev-selected 46.0) and **58.0 for this method — yet the router still reaches 62.0%, exceeding even the test-best individual harness** without using test data.
- **Ablations (Math-Gemini):** development-update frequency matters — every iteration **62.0%** vs 56.0% (every 3) and 53.0% (every 5). Components interact super-additively: neither 51.0%, pruning alone 54.0%, guidance adaptation alone 50.0% (worse than neither), both **62.0%**. Router-input ablation (Table 6): expert-outputs-only reaches 60.5%, adding exclusive cases without GEPA drops to 57.0%, and GEPA adds the largest gains with full context (59.5→62.0 Math-Gemini, 46.6→50.0 TB2).
- **Token cost (Appendix A, Table 5):** the method uses **2.16x** (Math: 172.90M vs 79.92M), **1.69x** (TB2: 4,001M vs 2,367M), and **1.55x** (SWE: 2,951M vs 1,907M) the total tokens of Meta-Harness.

## Critical Assessment

The core idea — diversifying the search *objective* (the dev subset) rather than just the candidates — is a genuine and well-motivated twist on harness evolution, and the deterministic coverage-vote/ownership-margin rule is more principled than "prompt the proposer for diversity." The evaluation hygiene is also better than typical: dev/test splits are disjoint, selection uses development data only, and the test-best analysis (router 62.0 vs test-best 58.0 on Math-Gemini) is a legitimately interesting result.

That said, several issues temper the headline claims. **First, the compute confound is real and acknowledged but not resolved:** the method spends 1.55–2.16x Meta-Harness's tokens, and there is no compute-matched control — e.g., a 40-iteration Meta-Harness run, or two independent Meta-Harness searches with the same router on top. The component ablation's "neither" condition (two branches with fixed full dev subsets, 51.0%) is *more* expensive than Meta-Harness, so the branching-vs-budget attribution remains open. **Second, statistical support is thin:** 200 math problems mean one problem = 0.5 pts, so the +1.5 gain on Math-Sonnet is 3 problems and the +2.4 on SWE-bench Lite is 6 tasks; there are no repeated runs, no confidence intervals, and the authors admit "limited repeat evaluations." The suspiciously non-monotonic ablation (guidance adaptation alone at 50.0 < neither at 51.0, yet both-on at 62.0) spans 11-12 points — plausibly real, but with this noise floor single-run differences of 1-2 pts (which decide 2 of the 4 settings) are hard to trust. **Third, the gain is highly uneven:** +16.0 on Math-Gemini vs +1.5/+5.2/+2.4 elsewhere, and part of the Math-Gemini headroom comes from Meta-Harness being a weak baseline there (46.0, barely under the trivial BM25-geometry fixed baseline at 46.5). **Fourth, B=2 is never ablated** — no evidence on whether more branches help, or how Δ and q should scale. **Fifth, the router hurts in 2 of 4 settings** (−0.5 Math-Sonnet, −0.4 SWE), so the "mixture" story rests mainly on one setting. Finally, no code release is mentioned, and reproduction at ~4B tokens for one Terminal-Bench run is out of reach for most labs.

## Strengths

- Consistent improvement over Meta-Harness in all four benchmark-model settings, spanning two action models (Gemini 3 Flash, Claude Sonnet 4.5) and three task families (math reasoning, terminal agentic tasks, repository-level SWE).
- The development-subset evolution mechanism is concrete and deterministic (coverage votes, ownership margin), not a vague diversity prompt — and the ablation showing it unlocks the value of guidance adaptation (54.0/50.0 alone vs 62.0 together) supports the central design claim.
- The router never touches test data, and the paper demonstrates the striking result that routing can exceed even test-selected-best individual harnesses (62.0 vs 58.0 on Math-Gemini).
- Unusually honest bookkeeping: a dedicated token-accounting appendix, explicit admission of routing losses in two settings, a named head-replacement case study (geometry-aware dual solver → freeform_derivation_dual at iteration 13), and concrete descriptions of the four discovered harnesses (e.g., verification_once_gate reaching 50.0% on TB2; test_aware_edit at 66.4% on SWE).

## Limitations

- **Compute overhead:** 1.5–2.2x Meta-Harness token usage with no compute-matched baseline; efficiency-adjusted gains are unknown.
- **Statistical fragility:** single run per setting, no error bars; held-out sets are small (58 tasks for TB2, 200 problems for math), so the +1.5 (Math-Sonnet) and +2.4 (SWE) gains are within plausible noise, and the router's losses in those two settings are likewise.
- **Scale of the mechanism unexplored:** only B=2 branches; no sensitivity analysis on branch count, and fixed q=5, Δ=2.
- **Router ceiling:** recovers only 75% of exclusive successes, leaving ~5 pts of union coverage unrealized, and underperforms the stronger head in 2 of 4 settings.
- **Dependence on frontier models:** proposer is Claude Opus 4.6, routers are the action models themselves; costs and generalization to weaker action models are untested, and no code release is stated.

## Relevance

这篇论文正中你最高优先级的"Self-Evolving Agents & Automated Research"方向：它把 harness 优化形式化为递归自改进（RSI），并给出了一个具体可行的"多分支演化搜索目标 + 开发信息路由"方案，还诚实报告了 token 开销与路由失败情形，对理解长程自治 agent 系统的可靠性与评估方法都有直接参考价值。

## Questions for Further Exploration

- Do the gains survive a compute-matched comparison — e.g., Meta-Harness run for 40 iterations, or two independent Meta-Harness searches combined by the same router?
- How does performance scale with B > 2 branches, and should the ownership margin Δ and frontier size q grow with B?
- Why is the interaction between dev-subset pruning and guidance adaptation so super-additive (54.0 and 50.0 alone vs 62.0 together)? Is the guidance-alone degradation (50.0 < 51.0) real or noise?
- Can the router be improved beyond 75% exclusive-success recovery to close the 5-pt gap to union coverage — e.g., by allowing abstention or executing both heads on ambiguous inputs?
- Do the discovered mechanisms (gap_directed_construction, verification_once_gate, test_aware_edit) transfer across action models and benchmarks, or are they benchmark-specific artifacts of each search run?
