01

Methodology

one protocol · eight systems

Eight systems share everything except the skill-update rule: No Skill, a one-shot LLM skill, five self-evolving methods (SkillGen, Trace2Skill, SkillOpt, EvoSkill, GEPA), and GSO. Generalization here is within-task-type — new spreadsheets, new bug-fix repos — not new task families. The unit of analysis is retention: test gain minus training gain, in points over No Skill. Negative retention = overfit; negative test gain = harmful.

The GSO loop — what is learned is not a skill but a six-part metaskill: a guide for writing skills. Each task gets a fresh throwaway skill that never sees gold answers or grader code.

  1. Solve — write a task-local skill from the metaskill, run the agent.
  2. Trace — find the first failed step; blame exactly one of the six parts.
  3. Edit — rewrite only that part, nothing else.
  4. Accept — promote only if the candidate beats the parent on shared validation tasks.
  • 1understand the task
  • 2pick tools & sources
  • 3write a procedure
  • 4check the result
  • 5locate the failure
  • 6retry once
u = |R| − 2|B| > 0 Regressions count double: a skill that breaks tasks it used to solve is worse than one that merely fails to help.

The team also releases RBioBench — 405 R-programming tasks over real clinical-trial and bioinformatics packages (197 clinical, 208 omics).

Read a finished skill: yes. Predict an edit before running it: no — validate edits by executing them.

Training curves overstate delivery — on SpreadsheetBench every existing method loses 17.5–30 pts from train to test (No Skill itself loses 15). Retention is the number that matters.

03

Strengths

  • First apples-to-apples measurement of skill carry-over; the frozen-test protocol removes test-time adaptation as a confound.
  • Reusable vocabulary: the retention metric and overfit/harmful taxonomy correct training-curve-only reporting in this area.
  • Actionable evaluation guidance: report test gain and retention; accept edits only after running them; use a skill-reading judge as a cheap filter for finished skills.
  • GSO is simple and well-motivated: no task-specific file/column bindings, single-part edits, regressions penalized double; the initial metaskill is published.
  • Unusually transparent: information-boundary and figure-level evidence tables, explicit caveats about small test sets.
04

Limitations

  • Generalization is within-task-type only; cross-domain transfer of the metaskill is deferred to future work.
  • One model, one temperature; no variance estimates or significance tests despite test splits as small as 20 tasks.
  • GSO’s test-time skill-writing (plus possible retry) adds inference cost that is never quantified.
  • Two of six benchmarks are author-built (RBioBench), where prior methods happen to be weakest.
  • The metaskill is learned per benchmark and never shared — “one reusable metaskill” remains untested.
  • Judge study uses a single judge model with no human-verification sample.
05

Questions for further exploration

  • Does a metaskill learned on spreadsheets transfer to code repair — or must every domain re-learn? Can one domain-general metaskill match per-benchmark ones?
  • How much of GSO’s margin survives a compute-matched control (No Skill / One-shot with the same retry budget)?
  • Do overfitting rates (10/36 below No Skill) persist across model families and scales — and does severity track model capability?
  • Could the skill-reading judge pre-filter likely-overfit edits inside training, before paying for validation runs?
  • Can overfitting failure modes — hard-coded bindings, unconditional checklists, overgeneralized rules — be detected automatically rather than found by reading?
