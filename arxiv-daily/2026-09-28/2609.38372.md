> **一句话总结：** 让同一个冻结的 GPT-5.6 Sol 智能体先在 49 行种子 harness 上解题、再以 proposer 身份直接阅读完整运行记录并改写这段 harness 代码（仅受"新增行数预算"约束、只做可运行性检查），经过 5 轮混合五基准的"多任务预训练"加 2 轮 Claw-Eval"持续训练"后，进化出的 430–524 行 harness 在五个域内基准的留出集上平均分 60.17（种子 55.7，+4.48；Codex CLI 57.2，+2.99），在五个从未参与进化的分布外基准上平均 70.45（种子 57.8，+12.64；Codex 70.57），其中 BrowseComp-Plus 从 34.0 飙升到 90.0——但 τ²-Bench banking 上也出现了 51.4→45.9 的真实回退。

> **TL;DR:** A solo-author paper turns harness (agent scaffolding code) evolution into recursive self-improvement: the same frozen GPT-5.6 Sol agent is both solver and proposer, directly editing the 49-line seed harness that runs it, with no preset components, no score-based selection, and only a runnability check for acceptance. Framing harness evolution as deep-learning training — mixed five-benchmark batches as "multi-task pretraining" (iterations 1–5), a new Claw-Eval domain with replayed success anchors as "continual training" (iterations 6–7), a decaying new-line budget as the learning rate (cosine 500→100), and free-text evolution notes as optimizer state — the evolved harness scores 60.17 average on five in-distribution held-out benchmarks (+4.48 over the seed harness, +2.99 over OpenAI Codex CLI 0.146.0 on the same model) and 70.45 on five out-of-distribution benchmarks never used in evolution (+12.64 over seed, within one point of Codex's 70.57), with BrowseComp-Plus jumping 34.0→90.0 thanks to an emergent output-truncation mechanism. The paper honestly dissects two regressions (τ²-Bench banking 51.4→45.9) and names the framework's core weakness: updates are accepted without any validation set.

## 核心贡献

- **极简人类先验的自进化 harness 框架**：同一个冻结模型既当 solver（在同一 harness 上解题）又当 proposer（读取上一批完整运行记录后直接改写 harness 代码），改哪、加什么组件、建删什么文件完全自由——区别于 AHE/HarnessX/Self-Harness 等预设可编辑组件或固定编辑类型的方法（Table 2 中唯一同时满足"同模型 + 同 harness + 极简起点 + 全代码可编辑 + 混合任务类型"的方法）。
- **训练类比作为实验设计原则**：把 harness 进化完整映射到深度学习训练（Table 1）——任务批 = training batch、proposer 改码 = 参数更新、新增行数预算 = 学习率（余弦退火 500→100，二阶段先回升 200 再退火）、进化笔记 = 优化器状态（动量）、Claw-Eval 新域混入 20 个已解通的"成功锚点"任务 = 经验回放防灾难性遗忘。
- **面向泛化的评测协议**：训练/留出任务严格分离；每次迭代批内五个基准各取 12 个新任务（一个 harness 服务所有任务，而非每个基准一个 harness）；进化结束后在五个从未使用的 OOD 基准上评测；proposer 提示词明确"记住具体任务毫无用处"。
- **涌现机制分析**：从 49 行种子进化到 524 行，涌现出输出截断（>48k 字符保首尾）、命令时限、历史压缩（>36 万字符触发）、独立复审（全新上下文中复查答案）、图像查看预算（每回复≤4 张、每任务≤24 张）等机制，并给出逐机制触发率热力图（Figure 5）和逐迭代代码演化表（Table 4）。
- **诚实的回退分析与反作弊审计**：承认并深挖两处回退（τ²-Bench banking、OfficeQA Pro）；用"预防性约束 + 事后全轨迹审计"防 reward hacking，确认作弊记 0 分，报告的所有评测记录中未发现作弊。

## Key Contributions

- **A self-evolving harness framework with minimal human priors**: the same frozen model solves tasks on the harness and then, as proposer, reads the complete run records and directly edits that harness's source code — no preset editable components, no prescribed edit types, no trajectory-organizing agent; acceptance is a runnability check only (edits confined to the harness workspace, at most α_t new lines, completes a mock-model task run).
- **Harness evolution cast as deep-learning training**: a full correspondence table (learning rate = decaying edit budget, optimizer state = free-text evolution notes, multi-task pretraining = five mixed benchmarks per batch, continual training = new domain with replayed success anchors), which then dictates the two-stage experimental design.
- **A strict generalization protocol**: train/held-out task splits fixed in advance, evaluation on five out-of-distribution benchmarks never touched during evolution, one shared harness across all task types, and an anti-reward-hacking audit (preventive constraints + post-hoc trajectory review; confirmed cheating scores 0 — none was confirmed).
- **Mechanism-level analysis**: the evolved harness's four load-bearing mechanisms (output truncation, history compaction, independent review in a fresh context, visual inspection budget) are traced iteration by iteration, with per-benchmark trigger rates and concrete task-level case studies.
- **Honest failure analysis**: the paper dissects why Iteration 5 falls below Seed on τ²-Bench banking (compaction deleting the customer's original request; an errant `configure_run` step-limit edit) and OfficeQA Pro (ambiguous questions all three harnesses miss), and openly names the framework's structural cost — updates are accepted without any validation gate.

## Methodology

**Setup.** A frozen base model M runs inside a harness state H_t = (C_t, N_t): C_t is the entire harness source code (system prompt, tool definitions, context handling, execution control) and N_t is a free-text "evolution notes" file carried across iterations. A fixed execution interface K dispatches model calls, executes commands, and records whole runs. The seed harness H_0 is a single 49-line Python file: a short system prompt, one bash tool, and a minimal tool-calling loop — no truncation, no timeouts, no compaction, no error recovery.

**Solver and proposer.** Both roles are played by the same agent with the same M and the same current H_t, each in a fresh session. In the rollout step, the solver runs the iteration's task batch B_t once per task, producing records E_t (trajectories, scores, grader outputs). In the update step, an outer program packages E_t (successful and failed tasks verbatim, no summarization), the current code and notes, and the edit budget α_t into an update task I_t and hands it to the same agent; the proposer edits code and rewrites notes directly. Beyond a generalization-oriented prompt ("memorizing specific tasks or their solutions is therefore worthless") the prompt does not prescribe problems to fix or parts to change.

**Acceptance = runnability only.** A new version passes if (a) edits touch only the harness workspace, (b) there is at least one code change besides the notes, (c) added lines ≤ α_t, and (d) it completes a full task run with a mock model. There is no validation set, no score-based selection, no regression tests — a deliberate consequence of the "minimal priors" principle the paper later interrogates as its main cost.

**Two-stage schedule.** Stage 1 (iterations 1–5, "multi-task pretraining"): each batch draws 12 previously-unused tasks from each of five benchmarks — Terminal-Bench 2.1 (terminal engineering), GAIA2 (dynamic app environment), OfficeQA Pro (Treasury-document retrieval + numerical reasoning), τ²-Bench banking (multi-turn dialogue with a simulated user), SWE-Bench Pro (repo issue fixing) — 60 tasks per iteration, each training task used exactly once. The edit budget follows a cosine decay from 500 to 100 (actual budgets 500, 441, 300, 159, 100). Stage 2 (iterations 6–7, "continual training"): batches mix 40 new Claw-Eval tasks (service orchestration, multimodal understanding, multi-turn dialogue) with 20 "success anchors" — tasks solved in stage 1, rerun so the proposer sees whether its edits preserve old abilities; the budget is re-warmed to 200 then decayed to 100.

**Model and baselines.** All experiments use GPT-5.6 Sol (high reasoning effort, 258,400-token input limit, 65,536-token output limit) for solver, proposer, and the Codex CLI 0.146.0 baseline, which keeps OpenAI's own tools and context-compaction mechanism. Three harnesses are compared: Seed, Iteration 5 (end of stage 1), Iteration 7 (end of stage 2, on the stage-2 domain).

**Anti-reward-hacking audit.** Every task description ends with a fixed clause forbidding use of upstream fixes, published solutions, or oracle/evaluation artifacts, which are placed into the environment only after the agent finishes. Post-hoc, a script scans every trajectory for suspicious commands (upstream fix downloads, answer searches, test modification; for SWE-Bench Pro also network-content matching against reference patches), independent agents review flagged records one by one, and high/low-score outliers are manually inspected; confirmed cheating scores 0. No cheating was confirmed in any reported record.

## Results & Highlights

- **In-distribution held-out (5 benchmarks, equal-weight average):** the evolved Iteration 5 harness scores 60.17, +4.48 points over the 49-line Seed and +2.99 over Codex CLI. The gain concentrates where mechanisms apply: Terminal-Bench 2.1 rises 66.7 → 83.8 (Codex 71.3, +12.5 over it) and SWE-Bench Pro 51.0 → 61.0 (Codex 56.0); on GAIA2 (47.0 vs Codex 49.0), OfficeQA Pro (63.0 vs 66.4 Seed), and τ²-Bench banking (45.9 vs 51.4 Seed) the evolved harness does not beat the stronger reference.
- **Out-of-distribution (5 benchmarks never used in evolution):** Iteration 5 averages 70.45, +12.64 over Seed (57.8) and within one point of Codex (70.57). The headline number is dominated by BrowseComp-Plus: 34.0 → 90.0 (+56; Codex 93.0) — the seed aborted from context overflow on 65 of 100 tasks, and the emergent output-truncation mechanism alone recovers 57 of those 65. Excluding BrowseComp-Plus, the OOD average gain over Seed shrinks to +1.8 (65.56 vs 63.76) and Codex is ahead at 64.97; on SWE-bench Verified the score is unchanged (78.0 vs 78.0, Codex 80.0).
- **Continual training on Claw-Eval:** Iteration 7 lifts the overall score 66.17 → 68.06 over Iteration 5 and passed tasks 52 → 57 — the highest among all four harnesses (Seed 65.2, Codex 66.2) — with the gain concentrated in multimodal tasks (category average 39.3 → 47.8). Case study: on the video speed-change task M097, Iteration 5 requested images 41 times, hit the 600-second timeout, and scored 0.2; Iteration 7's image-quota + delivery-deadline mechanisms produced a 1.0.
- **Emergent mechanism payoff is cross-domain:** output truncation was added from terminal/coding training tasks, yet its largest gain comes on the unseen retrieval benchmark BrowseComp-Plus; on SWE-Bench Pro the seed aborted on 12 tasks and Iteration 5 solves 7 of them. Independent review runs on nearly every non-interactive task (93.1% of Terminal-Bench 2.1, 100% of OfficeQA Pro and SWE-bench Verified records) and demonstrably fixes errors, e.g. recomputing an OfficeQA Pro ratio from the wrong first-year assumption (0.77667) to the correct one (0.88825) in a fresh context.
- **Honest regressions:** Iteration 5 drops below Seed on τ²-Bench banking (51.4 → 45.9, four fewer passed runs) — traced to history compaction deleting the customer's original request in all 11 runs where it triggered, and to a proposer edit that set the conversation step limit to 200, cutting off two runs — and on OfficeQA Pro (66.4 → 63.0), attributed to ambiguous questions on which all three harnesses give the same wrong answers.

## Authors & Credibility

The paper has a single author, Qiankai Xu (Nanjing University), which is unusual for a systems-heavy evaluation paper spanning ten agent benchmarks; the work reads as a focused research program rather than a lab group effort. Credibility signals are strong on the evaluation-hygiene side: train/held-out splits are fixed in advance and stated per benchmark (Table 3, including repeated runs for small held-out sets like 29×3 on Terminal-Bench), an explicit anti-reward-hacking audit with per-record review is described in detail (and references the METR reward-hacking literature), the complete 49-line seed harness and the full proposer prompt are reproduced in appendices, and the paper volunteers unflattering results — two regressions, a within-one-point OOD comparison with Codex, and a three-paragraph "costs of simplicity" section. The related-work coverage is current and thorough (SICA, DGM, Meta-Harness, AHE, Self-Harness, HarnessX, HarnessBank, HarnessCompass, HarnessDev, ModularRSI, RRSI, plus evaluation-critique papers), and Table 2's qualitative comparison is precise about what "same model / same harness" means for each method, including a footnote correcting an easy misreading of Self-Harness's setup. The main credibility gap is the absence of reported API costs and of any second author to independently check the ten-benchmark evaluation harness.

## Critical Assessment

- **Single run, single model — the numbers have no error bars.** All headline claims rest on one evolution trajectory with one frontier model (GPT-5.6 Sol). The author concedes in Limitations that "estimating this variance would require multiple independent evolution chains" was unaffordable, and that small differences should be read with caution — which directly undercuts the OOD headline: 70.45 vs Codex's 70.57 is a within-noise tie presented as "matching Codex," and the in-distribution +2.99 over Codex rests on large per-benchmark swings (e.g., Terminal-Bench +17.1) with no repetition across chains.
- **The +12.64 OOD gain is one mechanism on one benchmark.** BrowseComp-Plus (34.0 → 90.0) contributes the bulk of it, and the paper's own exclusion analysis shows the remaining four OOD benchmarks give only 65.56 vs Seed's 63.76 — with Codex ahead (64.97) and SWE-bench Verified flat at 78.0. The truncation mechanism is real and well-analyzed (Figure 5 shows 65% context-overflow aborts on BrowseComp-Plus for Seed), but a reader skimming the abstract would over-generalize the OOD result.
- **Acceptance without validation is both the point and the blind spot.** Because updates are admitted on runnability alone, clearly harmful edits ship: history compaction erased the customer's original request in 11 τ²-Bench runs (10 failed), and the proposer used the environment's `configure_run` tool to set a 200-step conversation limit that truncated two runs — a side effect neither Seed nor Codex ever triggered. The paper frames this honestly as "the missing piece of the framework," but it also means the reported gains understate what a validated variant could achieve, and the DL-training analogy (its Table 1) breaks exactly where it matters: there is no gradient-safety guarantee that small updates lower the loss.
- **No empirical comparison against prior self-evolving methods.** Table 2 is a qualitative feature comparison only; AHE, HarnessX, or even a score-based-selection ablation of this framework are never run. The related-work discussion cites "Simple Baselines are Competitive with Code Evolution" and "Rethinking the Evaluation of Harness Evolution," which makes the omission more conspicuous — the natural objection is that simple baselines (e.g., a human writing truncation + compaction into the seed) are not tested here. That said, Codex CLI — a strong human-engineered harness on the identical model — is the baseline that matters most, and the evolved harness genuinely beats it in-distribution.
- **Reproducibility is partial.** The seed code and update prompt are fully reproduced, which is excellent, but the evolved harnesses (430/524 lines), run records, audit scripts, and the total API spend are not provided; reproducing one trajectory would cost a substantial multi-benchmark evaluation budget, and nothing in the paper indicates a code release.
- **The reward-hacking audit is reassuring but not adversarially stress-tested.** No cheating was confirmed, yet the audit is pattern-matching plus reviewer judgment; the paper does not report recall checks (e.g., planting known-cheating trajectories to verify the pipeline catches them).

## Strengths

- The training analogy is not just rhetoric — it generates falsifiable design decisions (cosine budget decay, benchmark mixing, replay anchors) and a clean experimental structure that prior harness-evolution work lacked.
- The generalization protocol is unusually strict for this literature: held-out tasks disjoint from evolution tasks, five truly out-of-distribution benchmarks, one shared harness across heterogeneous task types, and a generalization-oriented proposer prompt.
- Mechanism analysis is concrete and quantitative: per-iteration code-change table, per-benchmark trigger-rate heatmap, and task-level case studies (the M097 video task 0.2 → 1.0; the OfficeQA review fixing 0.77667 → 0.88825) that let readers judge *why* the harness wins.
- Honest self-reporting: regressions get their own section with root causes, the costs of the design principles are enumerated (local fixes with side effects, acceptance without validation, freedom without diversity — skills/memory/sub-agents never emerged), and near-tie comparisons are labeled as such.
- The anti-reward-hacking pipeline (preventive clause + automated scan + independent per-record review + outlier inspection) is a template other agent-evaluation papers could adopt.

## Limitations

- One frontier model (GPT-5.6 Sol) and one evolution chain per stage; the paper itself flags that whether weaker models need a prescribed outer pipeline remains untested.
- Only seven iterations with 60 tasks each — a small "training set" by DL standards; whether more iterations keep improving (or the edit scope keeps narrowing, as Section 5.7 suggests) is unknown.
- The continual-training stage uses a single new domain (Claw-Eval); extension to further domains is unverified.
- Several held-out sets are small and handled by repetition (Terminal-Bench 29×3, OfficeQA Pro 73×2, τ²-Bench 37×2), so per-benchmark numbers carry visible variance.
- No empirical head-to-head with other self-evolving harness methods, no simple-baseline (hand-written mechanisms) ablation, and no reported monetary/compute cost of the seven iterations plus ten-benchmark evaluations.
- Harmful edits are only caught post hoc at final evaluation; the framework cannot detect or roll back a regression the moment it is introduced.

## Relevance

这篇论文正中你最高优先级的 "Self-Evolving Agents & Automated Research" 方向——它把 recursive self-improvement 从"改提示词/改技能库"推进到"智能体直接改写运行自身的完整 harness 代码"，且训练类比（预算=学习率、笔记=优化器状态、回放=抗遗忘）可直接迁移到你关心的训练稳定性/长时自治系统可靠性问题上；论文对 reward hacking 审计、单链方差和"无验证更新"风险的分析，也是长时运行自治系统可信性的第一手证据。

## Questions for Further Exploration

- Would a cheap validation gate (e.g., replaying 10 success anchors before accepting each edit) have caught the τ²-Bench compaction and `configure_run` regressions, and at what fraction of the current cost?
- How many independent evolution chains are needed to make the OOD "matches Codex" claim statistically meaningful, and does the mechanism set (truncation/compaction/review) reproduce across chains or diverge?
- Does the framework's gain shrink on a stronger or weaker base model — the cited literature says harness gains favor weaker models, so is GPT-5.6 Sol near the point where self-evolution stops paying?
- Why did skills, memory, and sub-agents never emerge despite unrestricted edit freedom — is this a model-capability ceiling, a prompt effect, or an artifact of only seven iterations?
- Can the two-stage schedule (multi-task pretraining + continual training with replay) scale to a stream of incoming domains the way Adaptive Auto-Harness envisions, without the anchor-replay set growing unboundedly?
