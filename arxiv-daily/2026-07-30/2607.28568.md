> **一句话总结：** 清华大学与 Frontis.AI 团队构建了开源全栈系统 OpenMLE（含任务环境 OpenMLE-Gym、算子训练 OpenMLE-ERL、长程搜索 OpenMLE-Evo），训练出 35B 的元进化智能体 Frontis-MA1，在 MLE-Bench Lite 上把 Medal Average 从基座模型的 39.39% 提升到 60.61%（同一搜索框架下），叠加 OpenMLE-Evo-Max 后达到 71.21%，超过 GPT-5.5+Codex。

> **TL;DR:** The paper introduces OpenMLE, a full open stack (task gym + operator RL/SFT + evolutionary search) for training LLM agents that iteratively build and improve ML solutions via execution feedback. Under the identical OpenMLE-Evo harness on MLE-Bench Lite, the post-trained Frontis-MA1-35B raises Medal Average from 39.39% (Qwen3.6-35B-A3B base) to 60.61%, and reaches 71.21% with the enhanced OpenMLE-Evo-Max search, surpassing GPT-5.5 paired with Codex (68.18%) and approaching GPT-5.6 Sol / Kimi K3 (72.73%).

## 核心贡献

- 提出 OpenMLE 全栈系统，把可验证任务环境（OpenMLE-Gym）、算子级训练（OpenMLE-ERL）与经验驱动长程搜索（OpenMLE-Evo）统一在同一个 Draft/Improve/Debug/Crossover 算子接口下，使训练与推理共享同一套可组合的程序变换动作。
- 构建 OpenMLE-Gym：从 Kaggle 竞赛与数据集及人工挑选的经典基准中筛选出 5,758 个可执行、经质量门控的任务（比 MLE-Smith 的 606 个和 MLE-Dojo 的 200+ 个规模大出一个数量级），覆盖 8 种模态、6 类核心任务，并提供隔离沙盒执行、结构化反馈与任务专属评估器。
- 提出 OpenMLE-ERL：用执行结果驱动的、预算自适应 SFT（26,259 条样本）做热启动，再用带自适应奖励边界与"熵优势"（entropic advantage）的强化学习训练可复用算子，使模型学会修复、精炼与重组程序，而不仅仅是一次性生成解答。
- 提出 OpenMLE-Evo：在 AIRA-Evo 式种群搜索基础上，用结构化"经验卡片"记录节点质量、相对父节点进展与方法族新颖度三因子做非贪心的父节点选择，并按算子需要按需（而非急切地）合成自然语言记忆，从而用更少 token 得到更高的搜索产出。
- 训练并发布 Frontis-MA1-35B（及配套的 Frontis-MA1-30B），在 MLE-Bench Lite 与 held-out 的 NatureBench Lite 上同时验证了训练增益与搜索增益可以复合叠加，并公开了数据集、训练/评测代码、沙盒基础设施与最终模型权重。

## Key Contributions

- Introduces OpenMLE, a full-stack system that unifies verifiable task environments (OpenMLE-Gym), execution-grounded operator training (OpenMLE-ERL), and experience-driven long-horizon search (OpenMLE-Evo) around a shared Draft/Improve/Debug/Crossover operator interface, so the trained model literally is the variation engine used by the evolutionary search harness.
- Builds OpenMLE-Gym: 5,758 quality-gated executable tasks constructed from curated anchors, Kaggle datasets, and Kaggle competitions (an order of magnitude larger than MLE-Smith's 606 or MLE-Dojo's 200+), spanning 8 modalities and 6 core task types, each with isolated sandbox execution, structured feedback, and task-specific evaluators.
- Introduces OpenMLE-ERL: budget-adaptive execution-grounded SFT (26,259 examples from parallel Draft rollouts and evolutionary Improve/Debug/Crossover trajectory segments) as a warm start, followed by RL with adaptive score bounds and an "entropic advantage" that concentrates learning signal on the upper tail of candidate quality rather than mere validity.
- Introduces OpenMLE-Evo: an AIRA-Evo-style population search redesigned around structured experience cards, a three-factor (quality/progress/novelty) non-greedy parent-selection utility, and on-demand (rather than eager) LLM memory synthesis — cutting token usage nearly in half while increasing new-best discoveries per token by 84%.
- Trains and releases Frontis-MA1-35B (with a companion Frontis-MA1-30B for cross-model replication), showing on MLE-Bench Lite and held-out NatureBench Lite that training gains and search gains compose, and releases the full datasets, training/eval code, sandbox infrastructure, and final checkpoints.

## Methodology

The paper formalizes MLE as executable program evolution: at each search step, an operator-conditioned policy g_θ(·|τ, a, c) proposes a candidate program p given a task τ, an operator a ∈ {Draft, Improve, Debug, Crossover}, and a context c built from parent programs and their execution feedback; the sandbox executes p and a task-specific evaluator returns a scalar score. Both SFT and RL are framed as maximizing the same weighted log-likelihood objective L_evo(θ) over verified (task, operator, context, program) tuples, differing only in how the weight ω(s) is derived from the execution score.

**OpenMLE-Gym** builds tasks from three sources with different quality/scale trade-offs — 156 manually curated "anchor" tasks, 3,362 Kaggle-dataset-derived tasks (extending the MLE-Smith pipeline), and 2,240 Kaggle-competition-derived tasks (with MLE-Bench-overlapping competitions excluded to preserve evaluation integrity). A competition slug is automatically converted into a standardized package (public data, hidden private answers, generated metric.py) via an LLM-assisted framework that inventories files, cross-references Meta Kaggle records, and validates the package by executing prepare.py and scoring a sample submission; an LLM-based quality filter then judges task validity, data sufficiency, raw-data usage, task complexity, and data quality, retaining only packages that receive a strict "recommended" verdict. A centralized scheduler dispatches jobs to CPU/GPU Docker workers, returning one of six feedback modes (success, runtime error, missing code, missing submission, scoring failure, timeout).

**OpenMLE-ERL** trains four atomic, reusable operators rather than full search trajectories. The SFT stage collects a budget-adaptive corpus: a parallel path samples complete Draft solutions (17,245 examples), and an evolutionary path applies Improve/Debug/Crossover to executed programs and retains useful steps from high-quality local trajectory segments (9,014 examples), for 26,259 total examples; collection for each task stops at an accepted-example quota or an execution-budget limit. The RL stage first converts heterogeneous raw task metrics into a bounded "base reward" using clipped-and-power-transformed fixed bounds (Eq. 1), then further remaps this to task-specific "adaptive bounds" derived from each task's on-policy score frontier to preserve discriminative signal as the policy improves. An "entropic advantage" (Eq. 2, a softmax-temperature-controlled transform) then concentrates the learning signal on the best candidate in each rollout group rather than uniformly rewarding all non-failing programs — shown empirically to increase the "best-candidate advantage" 4x (1.58 → 6.39) and to yield a stronger smoothed test medal-rate trajectory (peak 0.666, +0.089 over a non-entropic baseline). Parent-state selection for RL uses a fitness-proportional utility F(p) = norm(R_p) + norm(Var_child(p)(R_c)) + norm(C_p) combining parent reward, child-reward variance (informativeness), and a visit-cooling term (anti-monopolization). Asynchronous rollouts decouple policy updates from the slowest sandbox job, addressing the long and highly variable execution latencies characteristic of MLE (minutes to hours per candidate).

**OpenMLE-Evo** composes the trained operators into long-horizon evolutionary search. After each sandbox evaluation, the harness creates a deterministic node-level "experience card" (provenance, performance, execution outcome, resource usage) and aggregates cards into a task-global "experience board" tracking population-level statistics (explored method families, underexplored directions, repeated failures, score trends). Parent selection uses an experience-guided utility U_i = λ_s·s̃_i + λ_Δ·Δ̃_i + λ_n·ν_i (normalized validation score, improvement-over-strongest-parent, and method-family novelty; Eq. 3-4) sampled via softmax, rather than AIRA-Evo's score-only softmax. Memory synthesis is deferred until an Improve/Crossover/Debug call actually selects a parent, at which point an LLM is invoked only on the selected node(s) and their retrieved ancestors/siblings/error-matched attempts to produce a bounded, operator-conditioned context (vertical ancestor trace + horizontal sibling set for Improve; complementarity cues for Crossover; error-signature retrieval for Debug) — replacing AIRA-Evo's eager full-history serialization. OpenMLE-Evo-Max additionally distills reusable cross-task priors from public competition artifacts (with MLE-Bench-related sources excluded) and enables asynchronous multi-GPU parallel search within the same total sandbox compute budget.

## Results & Highlights

- **Primary MLE-Bench Lite result (Table 1, Panel A):** Under the identical OpenMLE-Evo harness (12-hour per-task budget, single RTX 4090 capped at 12GB VRAM, 22-task official MLE-Bench Lite split), Frontis-MA1-35B improves Medal Average from 39.39% (Qwen3.6-35B-A3B base, Valid Rate 19.67/22, Human Rank 0.5828) to 60.61% (Valid Rate 21.67/22, Human Rank 0.7647). Adding OpenMLE-Evo-Max (benchmark-independent priors + asynchronous parallel search) raises this further to 71.21% Medal Average, 22.00/22 Valid Rate, and 0.8126 Human Rank — exceeding GPT-5.5 + Codex (68.18% Medal Average, Human Rank 0.7833) and approaching GPT-5.6 Sol / Kimi K3 (both 72.73%).
- **Cross-model replication (Table 1):** The same OpenMLE-ERL post-training applied to a second backbone, Frontis-MA1-30B, improves Medal Average from 34.85% (Qwen3-30B-A3B-Thinking-2507 base) to 53.03% under OpenMLE-Evo, and to 66.67% with OpenMLE-Evo-Max (Human Rank 0.8053) — confirming the gain is not confined to the primary 35B checkpoint.
- **Matched-harness comparisons (Table 1, Panel A):** Holding the model fixed and varying only the harness, OpenMLE-Evo outperforms general-purpose Claude Code/Codex scaffolds across four frontier models, e.g., MiniMax M2.7 rises from 45.50% (Claude Code) to 50.00% (OpenMLE-Evo), and Kimi K2.6 rises from 59.09% (Claude Code) to 66.67% (OpenMLE-Evo); against the original AIRA-Evo harness on the same Frontis-MA1-35B checkpoint, Medal Average rises from 53.03% to 60.61%.
- **Search efficiency (Figure 16):** Over 66 matched task-runs on the same Frontis-MA1-35B checkpoint and seed, OpenMLE-Evo versus original AIRA-Evo reduces total model-token consumption by 41.7% (129.3M → 75.3M) and prompt tokens by 50.3% (83.5M → 41.5M) while evaluating only 12.4% fewer nodes (3,430 → 3,004), yet records more new-best validation updates (229 → 246) and 84.3% more new-best updates per million tokens (1.77 → 3.27); Improve operations that set a new best rise from 4.73% to 9.36% of all Improve calls.
- **Transfer to NatureBench Lite (Table 2):** On a fixed 10-task subset, holding the adapter fixed, Frontis-MA1-35B improves over its Qwen3.6-35B-A3B base by 20 points in All-Match-SOTA (7/10 vs 5/10) and 10 points in All-Surpass-SOTA (3/10 vs 2/10); holding the base model fixed, OpenMLE-Evo improves over original AIRA-Evo by 30 points in All-M (5/10 vs 2/10) and 10 points in All-S (2/10 vs 1/10). The combined Frontis-MA1-35B + OpenMLE-Evo system (3/10 All-S, 7/10 All-M) matches GPT-5.4, GLM-5.1, and MiniMax-M3 reference agents on this subset and exceeds DeepSeek-V4-Pro, Claude Opus 4.6, and MiniMax-M2.7.

## Authors & Credibility

Authored by a large team from Horizon Research/Frontis.AI, Tsinghua University, Zhejiang University, Shanghai Jiao Tong University, and Georgia Institute of Technology, with Junlin Yang and Che Jiang as project leaders and Kaiyan Zhang as corresponding author. The work is positioned as "OpenRSI," an open technical report (not yet indicated as peer-reviewed) with a project page, GitHub, and HuggingFace release, suggesting an industry-lab-style release rather than a conference submission at this stage. The related-work section is unusually extensive and self-aware, explicitly situating OpenMLE against MLE-Dojo, MLE-Smith, MLE-Bench, AIRA/AIRA_2, AIDE, ThetaEvolve, and TTT-Discover, and includes a comparison table (Appendix Table 11, not read in full here) auditing which public systems jointly span task/environment construction, post-training, and evolutionary deployment.

## Critical Assessment

**Novelty:** The core contribution — training the same Draft/Improve/Debug/Crossover operators used by an external evolutionary harness via SFT+RL, then deploying them back into that harness — is a genuinely distinctive "meta-evolution" framing versus prior work that either trains full trajectories (MLE-RL, ML-Master) or treats the harness as a frozen scaffold around a frozen model (AIRA, AIDE). The three-factor (quality/progress/novelty) parent-selection utility and on-demand operator-conditioned memory synthesis are also concrete, well-motivated departures from AIRA-Evo's score-only selection and eager memory logging, and the paper backs both with token/efficiency ablations (Figure 16) rather than just end-task numbers.

**Rigor:** The controlled comparisons are a strength — same checkpoint/seed/budget contrasts (OpenMLE-Evo vs. original AIRA-Evo), a second-backbone replication (Frontis-MA1-30B), and a held-out transfer benchmark (NatureBench Lite) with a separately-built adapter all reduce the risk that results are an artifact of one lucky configuration. That said, the primary evaluation budget (12 hours on one RTX 4090 capped at 12GB VRAM) is explicitly called out by the authors themselves as smaller than "the vast minority of reported MLE-Bench evaluations" (footnote, Section 6.1), and the paper does not normalize for compute or inference cost when comparing to GPT-5.5/GPT-5.6/Kimi K3 — the headline "exceeds GPT-5.5 + Codex" claim is a leaderboard-style Medal Average comparison under different underlying compute budgets and models, not a controlled compute-matched comparison. The reported standard deviations (Appendix D.1, not fully read here) and only-three-run averaging for a 22-task benchmark also leaves individual task variance somewhat under-characterized in the main text.

**Reproducibility:** Strong on paper — the authors commit to releasing datasets, training/eval code, sandbox infrastructure, harness code, and final checkpoints, and 1,415 of 5,758 OpenMLE-Gym tasks will include full task-package data (the remaining 4,343 release only prepare.py/metric.py without redistributing licensed source data, e.g., from Kaggle), which is a reasonable but non-trivial partial-reproducibility caveat that could complicate independent verification of the full training pipeline.

**Significance and red flags:** The explicit "Limitations and Future Work" section is unusually candid for a first-party technical report: the authors state OpenMLE does not yet realize general RSI, that the improvement signal is limited to measured execution outcomes (not hypothesis quality or research-direction judgment), that the evolutionary system itself remains fixed rather than evolving, and that the three parent-selection factors are hand-weighted rather than learned. A concrete paper-specific detail worth flagging: NatureBench Lite transfer is evaluated on only a 10-task subset (not the full 90-task benchmark) with search restricted to a "web-search-disabled" 4-hour budget and no access to hidden labels or paper solutions, which is a much thinner evidence base than the MLE-Bench Lite results and is explicitly acknowledged by the authors as limiting "the breadth of both conclusions." Overall the work reads as an honest, well-instrumented systems paper rather than an overclaiming one — the title's "towards Recursive Self-Improvement" framing is appropriately hedged in the text itself.

## Strengths

- Unifies task construction, operator-level post-training, and evolutionary test-time search into one coherent, fully open-sourced stack with a shared operator interface — addressing a fragmentation problem the authors document explicitly against prior systems (Appendix Table 11).
- Extensive controlled ablations isolate the separate contributions of post-training (same harness, different model) versus search improvements (same model, different harness) rather than only reporting an end-to-end number.
- Concrete, mechanism-level case studies (Figures 13, 14, 17, 18) trace specific search trajectories (e.g., a Crossover step combining a physics-informed GNN parent with a robust-parser parent to cut validation RMSE by 8.2%) rather than relying solely on aggregate metrics.
- Candid, specific limitations section that names exactly which capabilities (hypothesis-quality judgment, evolving the evolutionary system itself, learned rather than fixed selection weights) remain missing for genuine RSI.

## Limitations

- Evaluation compute (12 GPU-hours/task on a single 12GB-capped RTX 4090) is self-acknowledged as smaller than most reported MLE-Bench evaluations, so absolute comparisons to frontier-model + Codex/Claude Code baselines run under different (likely larger) compute budgets should be read with that caveat.
- The system learns only from final execution scores, not from the quality of reasoning, hypotheses, or research strategy — a limitation the authors state directly, which bounds how much "judgment" the model can be said to have acquired.
- NatureBench Lite transfer evidence is confined to a 10-task subset with a shortened, web-search-disabled 4-hour budget, limiting generalizability claims beyond competition-style MLE.
- The evolutionary search framework (parent-selection weights, memory-synthesis triggers) is itself fixed and hand-designed rather than learned or evolved, so the "meta-evolution" loop currently trains the operators but not the search policy around them.
- Full task-package data is withheld for 4,343 of 5,758 OpenMLE-Gym tasks due to source-data licensing constraints, partially limiting reproducibility of the exact training corpus.

## Relevance

该工作提供了一个可复现、可量化的"训练+推理协同进化"框架，对研究 LLM 智能体在长程、可执行反馈任务（如自动化机器学习工程）中的自我提升机制，以及对比评估算子级训练 vs 搜索策略改进的边际贡献，具有较高的方法论参考价值。

## Questions for Further Exploration

- How would results change if compute budgets were normalized (e.g., matched wall-clock or FLOPs) against the strongest general-purpose coding-agent baselines (GPT-5.6 Sol, Kimi K3), rather than comparing Medal Average under differing hardware/model-size regimes?
- Can the hand-tuned λ_s, λ_Δ, λ_n weights in the experience-guided parent-selection utility (Eq. 4) be learned per-task or per-domain, and would this close more of the gap the authors identify in "Richer use of experience in node expansion"?
- Does the entropic-advantage upper-tail weighting risk reward hacking or mode collapse toward a narrow set of high-scoring but low-diversity solution strategies over very long search horizons, beyond the 12-hour budgets tested here?
- How sensitive is the 5,758-task OpenMLE-Gym quality filter's "recommended" LLM judgment to the specific judge model used, and could a different judge substantially change which tasks pass the semantic quality gate?
- Would the same operator-training-plus-evolutionary-search recipe transfer to non-MLE AI4AI domains (e.g., improving training code, hardware-aware kernels, or agent harness design itself), as the authors suggest in their "Future Work" section on evolving the evolutionary system?
